*Revision 0.1 (19 October 2026): first draft, written from the seven research notes by the synthesis author.*

M-1 2.3.0 removes Taffy and Parley from Izcal, and with them the Stage 1 plan to lay out block, flex, grid and floats through a library and to write only the long tail; the Phase 2 reconciliation records layout as the largest unowned item on Stage 1's critical path ([P23][RN]). The history of layout engines has one clear lesson. **Every engine of 1998–2015 kept inputs, outputs and dirty state in one mutable tree, and every one later paid for it**: Blink spent about six years replacing that design with LayoutNG, whose stated failure modes were under-invalidation, "hysteresis" (an "infinitely growing" box in Chrome 92 and earlier) and 2ⁿ cost for nested two-pass layouts ([HP 2.9–2.10, 2.18][HP]; [Chrome](https://developer.chrome.com/docs/chromium/layoutng)); every engine that sliced a tall strip for columns and pages instead of fragmenting in layout had to rewrite it ([FR 3.1–3.2, 3.13][FR]); Servo's eager parallel layout was abandoned for a design that parallelizes only where the tree allows ([HP 3.8–3.12][HP]), and the one rigorous measurement of parallel *layout* found its average total layout time rose from 221 ms on 1 thread to 264 ms on 4, because layout proper was 7.8% of the time and style 67% ([Zambre et al., HiPC 2016](https://arxiv.org/abs/2002.03850); [IP 3.9][IP]). Meanwhile the specifications leave central parts undefined: the automatic table algorithm has had no finished normative text for 27 years ([HP 4.10][HP]), fragmentation "does not define whether content breaks at a particular allowed break" ([FR 1.9][FR]), flex and grid fragmentation are "not defined", and the interleaving of style and layout that container queries and anchor positioning need is, in the anchor spec's own words, "undefined, but at least it's interoperable (to some extent?)" ([SM 1.7][SM]). **The central idea: layout is a pure function from recorded inputs (the one-copy DOM, computed style, shaped text, the frame's recorded state) to an immutable fragment tree, with fragmentation and the style re-entry inside the function's contract from the first milestone, every UA-defined choice written down as an Izcal algorithm, and every optimization (caching, incremental reuse, parallelism) checked against both the engine's own from-scratch path and an independent spec-literal reference engine.** The decisions that matter most: (1) one layout contract, `layout(box, constraint space, break token) → immutable fragment + break token`, with the constraint space as the complete input and cache key (LY-D1); (2) geometry in 32-bit fixed point at 1/64 CSS px with saturating arithmetic, matching the text stack's integer contract (LY-D3); (3) an independent reference layout engine compared on every CI run (LY-D5); (4) fragmentation, pagination and the style re-entry designed into the contract at LY-M0, with one recorded re-entry protocol for container queries and anchor fallback (LY-D8, LY-D12); (5) layout geometry that is the same on every OS, because scrollbars and form controls have Izcal-defined metrics (LY-D11). The work is about **52–66 engineers† at full strength, reached through a ramp, for 5.5–7 years† to parity**, and it moves Stage 1's exit to 48–60 months† (Section 9).

## 2. History: what came before and why it was built that way

### 2.1 Chronology

| Year | Project | What it did | Why that way | Fate and why |
|---|---|---|---|---|

| 1996–98 | **CSS1, CSS2** | Layout described as prose about results: normal flow, floats, positioning, tables | A styling language for documents, not a layout algorithm; engines invented their own algorithms ([HP 1.1][HP]) | CSS 2.1 (REC 2011) is still the only REC defining block, inline, float and table layout end to end ([SP 1.1][SP]) |

| 1999–2000 | **DOCTYPE switching** (Mozilla M11; IE5 Mac "Tasman") | Quirks and standards modes | Fix layout bugs without breaking existing pages | A permanent second set of layout behaviours in every engine ([HP 1.4–1.5][HP]) |

### 2.2 Technology mismatches: assumptions that no longer hold

| Assumption baked into older designs | Why it no longer holds | Consequence for Izcal |
|---|---|---|
| Layout objects are mutable and persist between frames, holding inputs and outputs | The mutable tree produced under-invalidation, hysteresis and exponential nesting; LayoutNG's fix was to forbid reads of the previous layout's state ([HP 2.9–2.11][HP]) | Fragments are immutable outputs; a layout reads only its inputs (LY-D1) |
| Fragmentation is for printing and can be done at paint | Fragmentation runs on screen (multicol, `column-wrap`, `::column` carousels, `line-clamp`, EPUB readers) and paint-time slicing cannot do `break-*: avoid` or per-fragment effects ([FR 3.2, 7.1–7.8][FR]) | Break tokens are in the contract from LY-M0 (LY-D8) |
| Parallel layout is the next big speedup | Measured layout gains are 1.4–4x at best and negative on some pages; floats serialize ([IP 3.3, 3.9][IP], [HP 3.7][HP]) | Parallel-capable by construction; parallel only where measured to pay (LY-D6) |
| Platform widgets and scrollbars give native metrics | Native metrics make geometry differ by OS, which breaks cross-OS determinism (DET-1) and reveals the OS to fingerprinting | Izcal-defined scrollbar and control metrics (LY-D11) |
| One process lays out the whole page | Site isolation puts cross-site iframes in other processes; a parent needs only the frame's box | A typed, recorded geometry protocol for out-of-process frames (6.15) |
| Layout and paint can rely on floating point that "usually" agrees | Cross-OS and cross-ISA bit identity is a target (DET-1, FP-24); the text stack is integer-only (TX-D4) | Integer layout units; a small, audited floating-point module (LY-D3) |
| UA-defined behaviour can stay in code | Under M-1 another engine's code is never evidence, and Izcal's oracle is its own reference engine, which needs a written algorithm | Every UA-defined choice (break scoring, `pretty`, re-entry order, limits) is written in this spec and the observation log (LY-D5, M-1 part 2) |

## 3. Today: the landscape and its gaps

**Specifications are moving or missing.** Of the layout core, only CSS 2.1, Box 3 and Writing Modes 3 are RECs; Flexbox, Grid 1 and 2 are CRDs; Sizing 3 and 4, Position 3, Box Alignment 3, Inline 3 and Tables 3 are WDs; Tables 3 says it is "not yet ready for implementation" ([SP 1.1–1.9][SP]). Position 3 rewrote absolute positioning around the inset-modified containing block in 2024–25 ([SP 6.1–6.3][SP]); Flexbox replaced its intrinsic-size algorithm after it proved not Web-compatible ([SP 8.1–8.2][SP]). The CSS layout tests in WPT are about 25,000 files, over a third of them CSS 2.1's legacy suite ([SP 1.12][SP]).

**Interop is uneven where layout is hardest.** Firefox has no `orphans` or `widows`; Firefox and Safari ignore `break-before/after: avoid`; page-margin boxes are Chrome-only; WebKit's bug asking for repeated table headers in print has been open since 2008 ([FR 4.1–4.9][FR]). Anchor positioning was the top-named incompatibility in State of CSS 2025 ([GO 1.6][GO]). Scroll anchoring reached all three engines only in September 2026 ([SM 2.11][SM]).

**What no tool shows** ([GO 3][GO]): why a box relaid out; which boxes were laid out and how many times; why a box is its size (the chain from specified size through percentages, automatic minimum size, intrinsic contributions and distribution); why a line broke where it did (`pretty` is UA-defined and differs per engine, [GO 3.4][GO]); why a scrollbar appeared; what caused a layout shift; which node scroll anchoring chose and why it was suppressed; which `position-try` option won; why a page break fell where it did. Each shipped "why" tool (Firefox's flex panel, inactive-CSS hints, CLS culprits) was hand-built for one feature and explains one step ([GO 2.1–2.9][GO]).

**State that persists between frames is invisible.** The last successful position option, last remembered sizes, remembered scroll offsets, scroll-state snapshots, `content-visibility` proximity and the scroll anchor are all inputs to later layouts ([GO 3.9–3.12][GO], [SM 1.13, 1.21, 3.4, 3.6][SM]). In Izcal these are recorded decisions anyway (JS-D15), so the replay data and the developer-tool data are the same data ([GO 7.4][GO]).

**What Izcal can do that others cannot** (`.claude/skills/first-principles-spec/references/izcal-capabilities.md`): attribute every relayout and shift to the mutation-log entry that caused it (B4); check every incremental layout against a from-scratch layout and say so (B5); replay a layout exactly and diff two fragment trees instead of two screenshots (B1, TX-D4; [GO 7.5][GO]); link every box size to the spec step that decided it (ANC-1; [GO 7.1][GO]); give agents structured answers instead of screenshots (B9, B10; [GO 7.10][GO]); and run WCAG reflow and reading-order checks as engine queries (B8; [GO 7.9][GO]).

## 4. First principles

### 4.1 Users' real tasks

- **Read and use a page**: it must render correctly the first time, stay put while loading (layout shift), respond to input at frame rate, and print. Layout must therefore be correct, fast on the interaction path (hover, typing, small mutations), and stable.
- **Find out why a page looks the way it does**: the question is always about one box, one line, one shift or one break, and the answer is a chain of decisions. Layout must therefore be able to emit its decisions as data, with the spec step that made each one.
- **Change a page and see the effect**: developers and agents mutate and re-measure; forced synchronous layout is the platform's model ([HGBA-3 Section 3][H3]). Layout must answer geometry queries synchronously and cheaply.
- **Trust the result across machines**: tests, bug reports and replays need the same geometry on every OS and CPU.

### 4.2 Platform primitives

The specifications define layout as functions of a box tree and computed values: box generation (Display 3/4, HTML Rendering), formatting contexts (CSS 2.1, Flexbox 1, Grid 1–3, Tables 3, Multicol 1–2, Inline 3, Ruby 1, MathML Core), the inputs a box receives from its container (CSS Sizing's available space, percentage bases and definiteness; Fragmentation's fragmentainer), and outputs (box fragments, baselines, scrollable overflow). The HTML Standard fixes when layout runs ("update the rendering", [SM 7.1][SM]) and requires synchronous answers to geometry APIs. CSSOM View, Resize Observer, Intersection Observer, Layout Instability and LCP define what script and metrics read. What no specification defines: data layout, invalidation, caching, scheduling, parallelism, numeric representation, hit-testing internals, and the interleaving of style and layout.

### 4.3 Izcal's principles that bind this design

P1 (layout is a large, fuzzable attack surface; no `unsafe`, no re-entrancy, partitioned caches), P2 (WPT and the reference engine gate every optimization; a faster wrong answer is a regression), P3 (deterministic, specified behaviour at every limit), P4 (interaction latency first), P6 (every number sourced or marked †), M-1 (built from the specifications; UA-defined behaviour written down; other engines only as black-box signals), and the accepted decisions JS-D4, JS-D15, FP-11, FP-12, FP-D16, ST-D7, ST-D13 and TX-D4.

### 4.4 Assumptions kept and broken

| Assumption | Keep or break | Reason |
|---|---|---|
| Layout runs on the script thread's flush, synchronously for geometry queries | **Keep** | The platform requires it; Servo moved layout back onto the script thread in 2024 ([HGBA-3 Section 3][H3]) |
| A separate box tree, distinct from the DOM | **Keep** | Boxes and elements are not one-to-one (anonymous boxes, `display: contents`, pseudo-elements, fragments); hasLayout shows what happens when internal boundaries differ from the spec's ([HP 1.8][HP]) |
| Layout output is a mutable tree updated in place | **Break** | The source of under-invalidation and hysteresis ([HP 2.9][HP]); immutable fragments make layout a checkable function |
| Dirty bits walked from the root | **Break, by measurement** | Spineless Traversal found a priority queue faster on 83% of 2,216 frames ([IP 1.17][IP]); Izcal builds both and keeps the measured winner (LY-D4) |
| Fragmentation is a print feature added later | **Break** | Every engine that did this rewrote it ([FR 3][FR]) |
| Parallel layout is a goal in itself | **Break** | Measured gains are small and page-dependent; parallelism is a capability used where it pays (LY-D6) |
| Floating-point geometry | **Break** | Cross-OS identity, TX-D4's integer metrics; fixed point is also what Blink and WebKit chose for zoom ([IP 7.1][IP]) |
| Native OS scrollbars and form controls | **Break** | Cross-OS determinism and fingerprinting (LY-D11) |
| UA-defined behaviour is an implementation detail | **Break** | It is web-observable; Izcal writes it down and files it upstream (M-1 part 2) |
| Hit testing is a separate traversal from painting | **Break** | "Hit-testing should always match painting" ([SM 8.4][SM]); one paint order, walked in reverse (LY-D14) |
| Quirks mode as an afterthought | **Break** | It is a recorded mode of every algorithm from day one ([HP 1.5][HP], [SP 2.10][SP]) |
| WPT is the definition of correct | **Break** | Tests sometimes contradict the spec ([SP 12.7][SP]); WPT is a floor, the spec plus the reference engine decide |

### 6.1 The flush, the frame and decision points

**When layout runs.** Layout runs in HTML's "update the rendering" loop ("recalculate styles and update layout", repeated with the `content-visibility` proximity and ResizeObserver steps, [SM 7.1][SM]) and at every forced flush, always after style and with the script thread blocked (B4 as restated by JS-D4). Documents are processed container document first, then child navigables in tree order ([SM 7.2][SM]). Layout runs **no script**: no crate of this spec can call anything that enters the JS engine (G37), and every event layout causes (resize, intersection, scroll, `scrollend`, `contentvisibilityautostatechange`, layout shift, `ResizeObserver` loop errors) is queued as data and dispatched after the pass, at the point HTML defines. This removes, by construction, the root cause of most C++ layout CVEs: script or style work running while layout holds a pointer ([SR 2.1–2.3][SR]).

**Which APIs force layout.** No specification lists them ([SM 7.12][SM]). Izcal derives its list from the specifications (every getter whose result is defined in terms of boxes, fragments or scroll positions: CSSOM View geometry and scrolling, `innerText`, `getComputedStyle` for resolved values that are used values, Range rectangles, `focus()` with scrolling, SVG geometry, mouse-event offsets, `caretPositionFromPoint`, `checkVisibility`) and records it in `hg-layout-query`'s generated table, each entry with its anchor. The table is checked against an **exhaustive black-box probe** of every WebIDL attribute and operation of the geometry, scrolling, focus and observer interfaces in the three shipping engines at LY-M0 (Q-LY-4). The widely cited prose list of "what forces layout" was built by its author from Blink source ([SM 7.12][SM]), so it is not an input to the table (M-1 part 3).

**Demand-driven queries (FLUSH-1).** A forced query names what it needs: one element's border box, one scroll container's offsets, one element's resolved value. `hg-layout-query` computes the smallest set of boxes whose fragments the answer depends on: the element's containing-block chain up to the nearest box whose input constraint space is unchanged and whose subtree is clean (a relayout boundary, 6.11), plus out-of-flow and anchor dependencies. Everything else stays dirty for the next frame. The answer equals what a full flush would give; CI compares both paths on every query of the mutation corpus (LY-3).

**Decision points (JS-D15).** Layout itself is a pure function and makes no timing-dependent decision. Its inputs from outside the pure function are B1 inputs of two kinds. **Recorded inputs and decision points** (logged when recording, enforced in replay): the viewport and visual viewport size, device scale and zoom (the environment snapshot of [ST 6.10][ST]); compositor scroll deltas applied at the scroll step (6.10); the visual viewport's scale and offset returned by the compositor after a pinch ([GR 6.28][GR]); image natural sizes, taken from the first decoded header and never changed by full decode; web-font installations ([TX 6.8a][TX]); out-of-process frame geometry and visibility messages (6.15); the print environment (6.7); lazy-load fetch starts and the loader's viewport-driven priority updates ([NW 6.3][NW]); and the points at which the frame-boundary state of 6.9 is captured, which HTML fixes. **Clock reads** (from the substrate clock, so exact under replay): IntersectionObserver v2's minimum delay, Layout Instability's 500 ms recent-input window, LCP and paint timing, and ResizeObserver delivery times. That is the complete list; adding an input is a spec change. Recording these inputs costs a share of **one** whole-renderer recording budget (HGBA-3 DET-1, JS-52), measured jointly with the engine, media and graphics and attributed per subsystem ([RN2 Q15][RN2]).

### 6.2 Numbers and units (LY-D3)

**The layout unit.** Positions and sizes are **`LayoutUnit`: a signed 32-bit integer counting 1/64 CSS px**, so the range is ±33,554,431.98 px. The reasons, from first principles:
- **Determinism**: integer arithmetic is identical on every ISA and OS, which DET-1, FP-24 and cross-OS replay need.
- **The text contract**: TX-D4 quantizes the font size to the finer of 1/64 of a unit and 2⁻¹⁶ em and computes advances as `round_half_even(value_fu × size_q / unitsPerEm)`, accumulating positions in that quantum ([TX 6.8][TX]); for font sizes under 1,024 px that quantum is finer than 1/64 px. Layout therefore keeps the text stack's **cumulative** positions in their own quantum as i64 and converts **cumulative offsets, never individual advances**, to `LayoutUnit` with `to_layout_unit` at item and line boundaries: a run's width is `to_layout_unit(end) − to_layout_unit(start)`. Line widths never drift, TX-D4 is unchanged, and layout widths equal what `measureText` reports after the same rounding; a CI check compares them (LY-9).
- **Exact powers of two**: 1/64 converts to and from binary floating point exactly (style's computed lengths are IEEE binary, [ST 6.9][ST]); WebKit moved from 1/60 to 1/64 in 2012 to stop losing precision in conversions and to avoid integer division ([WebKit wiki: LayoutUnit](https://trac.webkit.org/wiki/LayoutUnit); [IP 7.2][IP]). Thirds are inexact; 1/60 would make them exact but make every float conversion lossy ([IP 7.8][IP]). 1/64 is fine enough for TX-D4's positions once they are converted cumulatively.
- **Memory**: 4 bytes per coordinate inside FP-11's budget; i64 would double the geometry in every fragment (LY-D3 option (b)).
- **Compatibility**: Blink and WebKit use the same unit ([IP 7.1][IP]), so rounding of `offsetWidth` and friends agrees; the range limit near 33.5 million px that developers report in Chrome is the same order (unverified, Q-LY-2).

**Arithmetic.** Every `LayoutUnit` operation **saturates** at the range, never wraps and never panics; products and sums of many terms (percentages, flex distribution, grid track sums, table column distribution, aspect ratios) are computed in **i64 or i128** and converted back by one function, `to_layout_unit`, that rounds half to even and saturates. Division by zero is defined per call site from the spec (for example a zero flex-grow sum). Overflow is a specified, testable behaviour: the same overflowing page lays out identically on every platform (LY-13).

**No floating point after the boundary.** CSS numbers (flex factors, `aspect-ratio`, `<number>` line heights, zoom factors) and computed lengths arrive from style as IEEE binary values ([ST 6.9][ST]). `hg-layout-num` converts each **once**, at the boundary, to fixed point: lengths to `LayoutUnit`, unitless numbers to a signed 64-bit value with 24 fractional bits, clamped to ±2³⁹, with round-half-to-even, NaN mapped to 0 and infinities to the range limits, as CSS Values 4 allows for out-of-range values ([Values 4 §10.9](https://drafts.csswg.org/css-values-4/#calc-ieee); [SR 5.4–5.5][SR]). Every ratio (free space divided among flex factors, sizes transferred through an aspect ratio, percentages of a basis) is then computed in **i128 integer arithmetic with one rounding**, so layout needs no floating point at all after the boundary, as the text stack needs none (G28). The boundary functions are the only place `f32` or `f64` appears in layout crates, and a lint rejects them anywhere else (G39). Flex factors smaller than 2⁻²⁴ therefore count as 0; this is a deterministic precision limit of the kind CSS Values 4 permits ("UAs should support reasonably useful ranges and precisions"), recorded as a deviation and checked black-box (Q-LY-22).

**Pixel snapping** is not layout's job. Fragments are in fractional CSS px; paint snaps to device pixels. Where an API returns integers (`offsetWidth`, `clientWidth`, `scrollWidth`) the rounding rule is CSSOM View's, applied in `hg-layout-query`; ResizeObserver's `device-pixel-content-box` is computed with the graphics spec's snapping rule, because authors "cannot determine the correct way to round" ([SM 7.4][SM]).

**Index types.** Counts used as indices (table rows and columns, grid lines and tracks, line numbers, fragment ids, box ids) are separate integer newtypes with explicit caps, never `LayoutUnit` and never `usize` from content: grid lines are clamped to ±10,000 as Grid 2 suggests ([Grid 2 §5.4 "Limiting Large Grids"](https://drafts.csswg.org/css-grid-2/#overlarge-grids); [SR 5.3][SR]); table spans follow HTML's caps of 1,000 columns and 65,534 rows per span ([HTML tables](https://html.spec.whatwg.org/multipage/tables.html#attributes-common-to-td-and-th-elements); [SP 9.1][SP]).

### 6.3 The box tree (LY-D2)

**What it is.** The box tree is the specifications' box tree: the boxes Display 3 and 4, HTML's Rendering section and the other modules generate from elements, text and pseudo-elements, including anonymous boxes (table wrappers and missing table parts, ruby containers, block-in-inline splits, anonymous blocks around inline runs, flex and grid item wrappers for text). It is built by `hg-box-tree` from the node columns (JS-D4), through `hg-tree-traits` (G1), and from computed styles read through `hg-style`'s read API.

**Representation.** Boxes live in **box columns** owned by `hg-box-tree`, indexed by a 32-bit box id: parent, first child, next sibling (12 B), the generating node slot or anonymous marker (4 B), the computed-style id (4 B; anonymous boxes get the style id of their generated anonymous style from the style system), box kind and display-derived flags (4 B), the layout-cache slot (4 B) and dirty and relayout-boundary flags (4 B): **32 B per box**. A node-slot-to-box map (one 32-bit entry per element that generates a box; `display: contents` and `display: none` map to none) lets layout and the query layer go from a node to its principal box. Rare per-box data (list markers, `::first-letter` and `::first-line` split points, table cell spans, multicol spanner links) lives in side tables keyed by box id. Box columns are class (a) derived data (FP §6.4): dropping them and rebuilding gives bit-identical box trees (LY-32).

**Generation inputs that are not plain CSS.** HTML element rules ([SP 2.7–2.10][SP]): `button` honours only some `display` values and always establishes a formatting context; `fieldset` and its rendered legend; `details` as a shadow tree with `::details-content` hidden by `content-visibility`; replaced elements and form controls under `display: contents` compute to `none`; quirks-mode margin and line-height rules. Blockification and inlinification are computed-value fixups in the style system ([SP 2.2, 13.1][SP]); the box tree reads their results. Quirks mode is a recorded document mode input of every algorithm, not a separate code path bolted on ([HP 1.5][HP]).

**Form controls (LY-D11).** Every form control is a UA shadow tree styled by the UA sheet in the engine image and laid out by ordinary CSS layout, with **Izcal-defined intrinsic metrics** (the inner padding, the `select` arrow's min-content floor that Sizing 3 allows, [SP 7.3][SP], caret width, range-track sizes). No OS widget metric reaches layout, and `appearance: none` and `auto` devolve as CSS UI 4 and HTML's widget rules say. Three details are inputs, not constants: **localized control strings** (the file input's button and label text) come from the environment snapshot's UI locale, recorded and counted in PRIV-2's entropy budget; **pickers** (`select` popups, date and colour pickers) are browser-process UI whose anchor rectangle `hg-layout-query` supplies; and customizable `<select>` (`appearance: base-select`) is held by LY-D10 until it meets the admission rule. Owning the metrics also makes `field-sizing: content` ([GO 6.6][GO]) ordinary intrinsic sizing.

**Incremental rebuild.** The style pass's per-element "affects" mask (owned by this spec, [ST 9.5][ST]) has five categories: **box-tree** (`display`, `position` when it changes out-of-flow status, `float`, `content`, list properties, `contain` and `container-type` when they create or remove a formatting context, `columns` presence, `content-visibility`), **layout** (sizes, margins, padding, borders, fonts and text properties, alignment, flex and grid properties, insets, `writing-mode`, `direction`), **overflow and scroll** (`overflow-*`, `scrollbar-gutter`, snap properties, `overflow-anchor`), **paint-only**, and **hit-test-only** (`pointer-events`, `visibility` change between visible and hidden only). The paint-only category carries one extra flag, **scroll-anchoring trigger**, set for `transform` changes, because a transform on the anchor's path suppresses an anchoring adjustment ([SM 2.10][SM]). A box-tree change rebuilds the box subtree of the nearest ancestor whose box structure can be affected (for an inline-level change, the containing block's inline formatting context; for a table-internal change, the table) and marks the rebuilt boxes dirty. DOM insertions and removals in the mutation log do the same. The rebuild is checked in CI against a from-scratch box-tree build (LY-3).

### 6.4 The layout contract (LY-D1)

**The function.** Every formatting context implements one signature:

```
layout(box, &ConstraintSpace, Option<&BreakToken>) -> LayoutResult
LayoutResult = { fragment: FragmentId, break_token: Option<BreakTokenId>, status: Complete | BrokenInside | BreakBefore,
                 baselines: Baselines, end_margins: AdjoiningMargins, out_of_flow: OofList, best_break: Option<BestBreak> }
intrinsic(box, &IntrinsicInput) -> MinMaxSizes        // min-content and max-content contributions, per axis
```

**The constraint space** is derived from CSS Sizing's and Fragmentation's definitions of a box's input, and it is the **complete** input besides the box's own subtree, its computed styles and the frame's recorded state: available inline and block size (each definite, indefinite, or a min-content or max-content constraint); percentage-resolution sizes per axis and the replaced-element percentage basis; which sizes are fixed by the parent (flex and grid stretch, table cells' second pass); the containing block's writing mode and direction; the BFC offset if known and the **float area** (floats and shapes intruding from the containing BFC); the incoming adjoining-margin summary and whether clearance applies; the fragmentainer (block size, block offset, kind page/column/clamp, whether it is the first fragmentainer, the break-appeal threshold); the orthogonal-flow fallback size (Writing Modes 4 §7.3.1 uses the ICB or a scrollport size, [SP 11.1][SP]); baseline requests; and the **style-version id** of the box's subtree when a re-entry produced a size-specific style version (6.9). Nothing else is read: no previous fragment, no sibling's state, no global. This is the rule that ended hysteresis in LayoutNG ([Chrome: LayoutNG](https://developer.chrome.com/docs/chromium/layoutng); [IP 2.4, 7.9][IP]).

**Caching.** Constraint spaces are **interned per pass** (siblings usually share one), so a space is a 32-bit id plus its stored contents. Each box has one layout-cache slot holding up to two entries keyed by **(constraint-space id, incoming break-token id)**, each with its `LayoutResult` (the measure and final layouts that flex, grid and tables need), and an intrinsic-size memo keyed by `IntrinsicInput`. **One central function**, `relayout_needed(old_space, new_space, box_flags)`, reads the two stored spaces and decides whether a cached result is valid for the new one: a box whose inline size does not depend on available inline size, with no percentage resolving against a changed basis, reuses its result; a percentage-sized box relays out only when the percentage basis changed. LayoutNG's published account describes this diff as kept in one place and easy to unit-test ([HP 2.11][HP]); in Izcal it is also property-tested: a cache hit must equal a fresh layout (LY-3). **Fragmented boxes**: the cache holds the first fragment's result only; later fragments are re-run from their break tokens, which the cache key distinguishes, so a fragment-2 request can never hit fragment 1's entry. **Eviction**: none inside a pass; between passes, entries of boxes not laid out for 64† consecutive passes are dropped, a rule driven only by canonical pass counters, so eviction is deterministic (FP-24) and, because every entry is reproducible, invisible (LY-3). This replaces FP 6.4's sentence on fragment-cache eviction (Section 9.5).

**Purity and the cache are what make nesting linear.** Without a cache, a two-pass layout nested n deep costs 2ⁿ ([Chrome: LayoutNG](https://developer.chrome.com/docs/chromium/layoutng); [IP 2.1][IP]); with measure and layout results keyed by the full input, each box is laid out a bounded number of times per distinct input. LY-23 states the bound and tests it at depth 20.

**Break tokens** are hashable records in a side table: the box id, consumed block size, a child-token list, and per-mode state (flex line index and item offsets, grid row and item tokens, table row and cell tokens, multicol column-row and spanner position, inline item offset and line count for orphans and widows). A token is data, never a pointer into mutable state, so it is part of fragment-tree hashes (DET-1) and of the reference comparison ([FR 9.2][FR]).

**Out-of-flow** descendants are returned upward in `out_of_flow` until their containing block's layout completes, then laid out there, in the order 6.9 requires for anchor positioning. In a fragmentation context, out-of-flow placement is a pass at the fragmentation root: boxes are placed as if the flow were continuous, then broken ([FR 2.6, 9.5][FR]).

### 6.5 Formatting contexts

Each context is written from the pinned specification with step anchors (G9, ANC-1). Where the spec is UA-defined, ambiguous or contradicted by the deployed web, the choice is written in this section or in `compat/observations/` as a black-box observation (M-1 part 2) and filed upstream.

#### 6.5.1 Block layout, margins and floats

Block layout follows CSS 2.1 §8.3.1 and §9.4–9.5, Box 4 and Display 3. **Margin collapsing** is carried as an **adjoining-margin summary** (the largest positive and most negative adjoining margins plus flags), the compact summary VizAssert showed suffices ([HP 6.10][HP]). Collapsing through empty boxes and the clearance rules (the hypothetical position computed as if `clear: none`, [SP 3.1–3.2][SP]) can make a block's BFC offset unknown until a later sibling resolves it; the block then lays out its children with an unresolved offset and re-lays out at most once when the offset is resolved, a bound the reference engine checks. **Floats** are placed by CSS 2.1's nine rules into the BFC's **float area**, a per-BFC structure of float rectangles and, with CSS Shapes, polygon or raster shapes ([SP 5.1–5.2][SP]); it is part of the constraint space and is persistent (unchanged prefixes are shared), so a later layout with the same incoming exclusions hits the cache. A BFC root next to floats takes the first position where its width fits, considering all floats, which LayoutNG fixed against legacy's "fixed number of retries" ([HP 2.6][HP]). `margin-trim` is implemented when admitted (LY-D10).

#### 6.5.2 Inline layout and line breaking

**What comes from the text stack** ([TX 6.8][TX]): per paragraph, white-space processing (Phase I), bidi levels, itemized and shaped runs with integer advances in the 1/64 quantum, soft-wrap, hyphenation and justification opportunities, `break_reshapes` and `join_reshapes` flags, metrics and baseline tables, vertical text data, and the `MATH` table. **What layout owns**: the inline formatting context's **item list** (a flat, index-addressed sequence of open-box, close-box, text-run, atomic-inline, float, out-of-flow and forced-break items, as published for LayoutNG, [IP 5.2][IP]), line boxes, the line breaker, `vertical-align` and baseline alignment (Inline 3), `line-height` and `text-box-trim` (Inline 3 §§4–5, from the text stack's metrics), `text-indent`, `text-align` and justification (distributing space over the text stack's justification opportunities), `initial-letter`, ruby layout (Ruby 1), Phase II white-space trimming, bidi reordering per line (UAX 9 L1–L4 through the text stack's maps, Writing Modes 4 §2, [SP 4.9][SP]), `::first-line`, and overflow and ellipsis.

**The line breaker is layout's, not the text stack's.** Line widths vary line by line (floats, shapes, `initial-letter`), inline boxes contribute margins, borders and padding, atomic inlines and out-of-flow placeholders sit in the item list, and `text-wrap` styles optimize across lines. The text stack's helper described in [TX 6.8][TX] ("finds the last break opportunity that fits") becomes, by amendment, a provider of **opportunities with cumulative widths and reshape-on-demand**: layout asks for the width between two opportunities, and when it breaks at an opportunity marked `break_reshapes`, asks the text stack for the reshaped edge segments (Section 9.5). Reshaping happens only at edges, as CSS Text requires; every line is reshaped from scratch and compared in CI (TX-6).

**Line-breaking objectives (LY-D16).**
- `text-wrap: wrap` (greedy): break at the last opportunity that fits, CSS Text 3's default.
- `balance`: minimize the variance of remaining space, measured before justification, never changing the line count for paragraphs of 5 lines or fewer, as CSS Text 4 requires; Izcal balances paragraphs of **up to 10 lines** (the most CSS Text 4 lets a UA skip: above 10 lines it may fall back) and falls back to greedy above ([CSS Text 4 `text-wrap-style`](https://drafts.csswg.org/css-text-4/#text-wrap-style); [SP 4.6][SP]).
- `pretty`: an **Izcal-defined total-fit objective**, published in this spec's companion text: a Knuth–Plass-style dynamic program over the paragraph's break opportunities ([HP 5.1][HP]) with integer costs for line-length variance, a short last line, consecutive hyphens and hyphenation itself, computed exactly in i64. Cost is quadratic in candidate breaks per line window; Izcal bounds it with a fixed window of **8 lines†** of look-back and runs it on paragraphs of up to **200 lines†**, greedy-plus-last-lines beyond that. CSS Text 4 leaves `pretty` UA-defined ([SP 4.7][SP]); WebKit optimizes the whole paragraph and Chromium only the last four lines ([GO 3.4][GO]), so any choice differs from one engine; Izcal's is deterministic, documented and explainable (6.16).
- `stable`, `avoid-short-last-line`: as CSS Text 4 defines them when admitted.

**Inline in fragmentation**: line boxes are Class B break points; `orphans` and `widows` (initial 2) apply with the scored-break mechanism of 6.7.

#### 6.5.3 Flexbox

Flexbox 1 §9 at the pinned CRD plus the editor's draft changes since, including the **Web-compatible intrinsic main-size algorithm** (§9.9.1.2: max-content is the sum of items' max-content contributions; single-line min-content the sum of min-content contributions), because the "Ideal Algorithm" is declared not Web-compatible ([Flexbox 1 §9.9.1](https://drafts.csswg.org/css-flexbox-1/#intrinsic-main-sizes); [SP 8.1–8.2][SP]). The automatic minimum size (`min-width: auto`) needs a min-content measurement of most items ([SP 8.4][SP]); measurements go through the intrinsic memo and the two-entry layout cache, so a nested flex tree stays linear. Fragmentation follows Flexbox §10's constraints and the sample algorithm's 50% pull-up rule, recorded as an Izcal algorithm ([FR 2.1–2.2][FR]).

#### 6.5.4 Grid, subgrid and grid lanes

Grid 1 and Grid 2 (subgrid) at the pinned CRDs. The **track sizing algorithm** is one implementation shared by grid, subgrid and, when admitted, grid lanes; it asks items for intrinsic contributions through the memo and lays items out at most twice per sizing round (the spec's row-size dependency on column sizes). Subgrids participate in their parent's track sizing through a per-subgrid contribution record. The implicit grid is clamped to lines ±10,000 ([SR 5.3][SR]). **Grid lanes** (`display: grid-lanes`, Grid 3) is not admitted at 19 October 2026: one engine ships it, under a property name the editor's draft has since renamed twice, and Chrome's status reads "No active development" ([SP 8.6–8.10][SP]). The track sizing and placement code is written so that lanes are a placement variant (items into the shortest lane, with a tolerance) on the same sizing, so admission costs a placement mode, not a rewrite (LY-D10). Grid fragmentation follows Grid 2 §13's constraints, row-wise, recorded as an Izcal algorithm ([FR 2.3][FR]).

#### 6.5.5 Tables (LY-D17)

The HTML table model forms the grid (with HTML's span caps); **CSS Tables 3** at a pinned editor's draft defines the box tree fix-up, the fixed and auto layout algorithms (column measures §3.8.3, distribution §3.9.3), row heights with the cells' second pass, `border-collapse` resolution as its own precomputed pass, `visibility: collapse`, captions, and fragmentation (rows whole up to half a fragmentainer; header and footer repetition within a quarter page each, [FR 2.4–2.5][FR]). Tables 3 still says "not yet ready for implementation" and has open issues on border collapsing ([CSS Tables 3](https://drafts.csswg.org/css-tables-3/); [SP 9.2][SP]). Where it is silent or disputed, Izcal's choice is a black-box observation against the three engines on the `css-tables` directory plus a colspan and percentage corpus (Q-LY-6), filed upstream. The cell grid is **sparse** (a span is one record, never 65,534 × 1,000 slots, [SR 5.2][SR]). Sticky table headers work by construction, because sticky is a property of any box (6.10).

#### 6.5.6 Multicol

Multicol 1 at the pinned CR: column boxes are fragmentainers of a fragmentation context; `column-span: all` splits the content into column rows around spanners; overflow columns in continuous media, extra columns moving to the next page in paged media ([FR 2.9][FR]). **Balancing** (`column-fill: balance`) uses a bounded method: lay out once in a single column of unconstrained height while **recording every break opportunity with its block offset and its appeal**, compute the minimum column height that fits the content into the column count honouring forced breaks, `avoid` and orphans and widows from that record, lay out once at that height, and if content still overflows (because a break's appeal forced an earlier break), stretch by the smallest recorded shortfall and lay out again, at most **3 layouts per column row in total†**. This is the "record every break point" approach Gecko's bug discussed as "more work" ([Bugzilla 575614](https://bugzilla.mozilla.org/show_bug.cgi?id=575614); [FR 3.14][FR]); its bound is a target (LY-24). **Nesting does not multiply the bound.** A fragmentation root inside an outer root's trial layout records its own break opportunities once, from its single-column layout, and is not re-balanced for each outer trial height: the outer root's trials reuse the inner record and only the outer's final placement lays the inner content out at its final column height. Work for k nested balanced multicols is therefore at most 3 layouts per level plus one final placement, linear in k, not 3ᵏ; LY-12's DoS suite includes a 10-deep nest. `column-wrap` and `::column` (Multicol 2) are admitted when they meet LY-D10; `::column` fragments are addressable fragmentainer records for scroll snapping and markers ([FR 7.2–7.3][FR]).

#### 6.5.7 Positioning and the top layer

Position 3's model: the **inset-modified containing block**, sizes resolved against it, then auto margins, then self-alignment; the **static-position rectangle**; the initial fixed containing block; top-layer boxes using the initial containing block ([Position 3 §4](https://drafts.csswg.org/css-position-3/#abspos-layout); [SP 6.1–6.4][SP]). The CSS 2.1 §10.3.7 and §10.6.4 equations are test oracles only. Where Position 3 and CSS 2.1 conflict (negative inset-modified containing blocks, #11478) and where it is open (containing blocks from fragmented inline boxes, #8284), the choice is a black-box observation (Q-LY-7). Relative positioning and transforms are post-layout: they move fragments in paint's property trees and never relayout ([FR 8.7][FR]). Sticky positioning is computed as constraints for the scroll machinery (6.10). `position: fixed` content in paged media repeats on every page as paint-time instances of one laid-out fragment, never re-laid out per page ([FR 8.6][FR]).

#### 6.5.8 Replaced elements

Replaced elements are leaves: a natural size, a natural aspect ratio (including the `width`/`height` attributes' mapping to `aspect-ratio: auto w / h`), the default sizing algorithm of CSS Images 3 (300×150 fallback), `object-fit` and `object-position` ([SM 4.1–4.5][SM]). Natural sizes arrive from decoding as recorded inputs; a size arriving is a mutation-log entry for that element, so unsized images shifting layout is visible as a cause (6.16). Video controls never affect layout ([SM 4.2][SM]). An iframe's layout needs only its used size; its document lays out in its own process if cross-site (6.15).

#### 6.5.9 MathML Core (LY-D21)

`hg-layout-math` implements **MathML Core** ([Candidate Recommendation, 24 June 2025](https://www.w3.org/TR/2025/CR-mathml-core-20250624/)): the math content box with ink ascent and descent, alphabetic and mathematical baselines, italic correction and top-accent attachment; the per-element algorithms (`mrow` with block-axis stretching, `mfrac`, `msqrt`/`mroot`, scripts, under/over with inline-axis stretching and `movablelimits`, `mmultiscripts`, `mtable`, `mpadded`, `mspace`, `mtext`, `mo` with the operator dictionary); and `display: block math`/`inline math`, `math-style`, `math-shift`, `math-depth` ([SM 5.3–5.5][SM]). It reads the 49 `MathConstants`, glyph info, size variants and glyph assemblies from `hg-text`'s `MATH` access as integers ([SM 5.6–5.7][SM], [TX 6.8][TX]), with the spec's fallbacks when a constant is missing, and Unicode-based assemblies when the font has none. The operator dictionary (about 1,178 rows) is standards data compiled into the engine image. MathML outside Core is not implemented; legacy MathML 3 attributes are ignored as Core says. Ink extents come from the text stack's glyph bounds; the open spec issue on ink ascent (issue 78) is a black-box observation (Q-LY-10).

#### 6.5.10 The SVG boundary

This spec owns the CSS side of SVG: the outer `<svg>` element is sized as a replaced element with natural size from its `width` and `height` when they are lengths and natural ratio from `width`/`height`, the active view or `viewBox`, in SVG 2 §8.12's order ([SM 6.1–6.2][SM]); `foreignObject` establishes a CSS layout root whose containing block is its positioning rectangle in user space, "implicitly absolutely-positioned" ([SM 6.3][SM]), laid out by `hg-layout` and then transformed by paint; SVG geometry that reaches CSSOM View and ResizeObserver (bounding boxes for elements without a CSS box) is answered by the **SVG spec** (`reports/Izcal SVG.md`, draft 0.3, owner decisions accepted 20 October 2026) through a trait `hg-layout-query` calls, whose values convert through `hg-layout-num`'s one rounding function (R6, applied 20 October 2026, so SV-D2's binary64 geometry and layout's fixed point meet at one boundary). SVG text uses CSS inline layout for its line(s) and then SVG's per-character positioning ([SM 6.4][SM]): `hg-layout` exposes its inline layout as a library call (one line, no wrap, or `inline-size` wrapping) returning per-character positions from the item list and the text stack's cluster map; the SVG spec applies `x`, `y`, `dx`, `dy`, `rotate` and paths. One text pipeline serves both (TX 6.8). **SVG roots and `foreignObject` roots form one work list** with the CSS boxes, merged under G43 (R6).

### 6.6 Intrinsic sizing and percentages

Every formatting context answers `intrinsic(box, IntrinsicInput)` for min-content and max-content contributions, with the input naming the axis, the cyclic-percentage mode (Sizing 3 §5.2.1's rules for replaced and non-replaced boxes, min, max and preferred sizes, [SP 7.1–7.2][SP]), the available-size class, and, for orthogonal flows, the fallback size. Results are memoized per box by input, in the box's intrinsic memo, cleared by the same dirty propagation as layout results (a box's intrinsic sizes depend only on its subtree and styles, not on its position, which is why a relayout boundary for intrinsic sizes is wherever size containment or a fixed size cuts the dependency). `aspect-ratio`, `contain-intrinsic-size` (with the last remembered size, 6.9), `fit-content()`, `stretch`, `min-content`, `max-content` and, when admitted, `calc-size()` are applied by one sizing module shared by all contexts, so every context resolves them identically ([SP 7.4–7.5][SP]). Percentages stay symbolic in computed values and resolve against the constraint space's bases in layout ([SP 13.1][SP]).

### 6.7 Fragmentation, pagination and print (LY-D8, LY-D9)

**One contract for continuous and fragmented flow.** A constraint space with no fragmentainer is continuous layout; with a fragmentainer, a layout returns `BrokenInside` with a break token, or `BreakBefore` when it should start in the next fragmentainer. Every context implements the fragmented case from LY-M1 or LY-M2 as its algorithm lands; an algorithm whose fragmentation is not yet written returns its whole fragment as **monolithic**, which is a conforming result (Fragmentation 3 allows monolithic content to overflow) and is listed in the conformance report, never silently sliced ([FR 9.1][FR]).

**Break scoring (Izcal-defined; the spec "does not define whether content breaks at a particular allowed break", [Fragmentation 3 §4.5](https://www.w3.org/TR/css-break-3/#best-breaks); [FR 1.9][FR]).** Each candidate break gets an **appeal** in a total order: forced; perfect (no rule violated); violating `orphans`/`widows` (Rule 3); violating `break-before/after: avoid` (Rule 1); violating `break-inside: avoid` (Rule 2); violating the Class B and C ancestor rule (Rule 4); last resort (better than overflowing the fragmentainer). Rules are relaxed in Fragmentation 3's order ([FR 1.8][FR]). Within one appeal, the latest break that fits wins. The best break seen so far is kept as a **best-break record** (a chain through nested boxes); if a later point is worse, layout of that fragmentation flow reruns once, up to the recorded break, so **each flow re-lays out at most once per fragmentainer** ([RenderingNG: block fragmentation](https://developer.chrome.com/docs/chromium/renderingng-fragmentation); [FR 3.4][FR]). As with balancing, a nested flow's rerun reuses its inner records, so reruns do not compound with nesting. Margins at breaks, `box-decoration-break`, monolithic content, parallel flows and the progress rule ("must not break at the top of the page") follow Fragmentation 3 §5. Fragmentation 4's `margin-break` and `always`/`all` are admitted by LY-D10's rule.

**Nested fragmentation** (multicol inside pages, a table inside columns inside pages) passes the outer fragmentainer in the constraint space of the inner fragmentation root; break tokens nest. `always` and `all` propagate outward through the token chain. This is designed at LY-M0 although no prose describes how another engine does it ([FR 8.9][FR]).

**Paged media and print.** CSS Paged Media 3: page boxes, the 16 page-margin boxes sized as §5.3.2 says, named pages, page selectors with their specificity, `size`, `page-orientation`, `marks` and `bleed`, the `page` and `pages` counters ([FR 5.1–5.5][FR]). Printing takes the **print environment** (sheet size, margins, scale, header and footer toggle, printer insets for `page-margin-safety`) as **one recorded input** (JS-D15); HTML's printing steps take a snapshot after `beforeprint`, at a recorded point ([FR 6.1][FR]); the printed fragment tree is a pure function of (snapshot, styles, print environment), so page counts replay exactly ([FR 6.6][FR]). Paged layout is Stage 1 work in this spec because it is the same fragmentation engine and is web-observable (`window.print()`, `@page`, `matchMedia('print')`, print reftests); the print UI and the PDF writer remain Stage 2 features as Stage 1 13.2 decided. Vector print output and the PDF writer take their **appearance from the display list** (paint order, clips, effects) and their **structure** (tags, links, reading order) from the fragment tree and the semantic plane ([GR 6.27][GR]; [FR 6.3–6.4][FR]); the print raster and preview are the graphics spec's, and the PDF writer belongs to a future PDF spec that has no owner yet ([RN2 Q24][RN2]).

**Room for GCPM (LY-D9).** Footnotes, running elements and page floats are not admitted (no browser ships them; the GCPM draft says "we need an algorithm for laying out footnotes", [FR 5.7–5.8][FR]). The page fragmentainer is nonetheless designed at LY-M0 with **reserved-area slots** (a footnote area and top and bottom float areas whose extents can grow while a page is laid out), so GCPM can be added without changing the token model ([FR 9.9][FR]).

**Fragmentation on screen.** `line-clamp` and `continue: discard` turn ordinary blocks into fragmentation containers ([FR 1.17][FR]); multicol, `column-wrap` and `::column` run in ordinary browsing ([FR 7.1–7.8][FR]). Break tokens and multi-fragment lists live in side tables; one bit per box says "has more fragments" ([FR 9.10][FR]).

### 6.8 Writing modes and bidi

Every algorithm is written in **logical coordinates** (inline and block axes, start and end) from its first line; the constraint space carries the writing mode and direction; conversion to physical coordinates happens once, when a fragment is written into the store ([SP 11][SP]). Orthogonal flows use Writing Modes 4 §7.3's fallback size; the clause that turns an overflowing orthogonal block into columns ([SP 11.2][SP]) is implemented as written if a black-box check (Q-LY-11) shows any engine does so, and recorded as a deviation otherwise. `text-orientation`, `text-combine-upright` and the sideways modes use the text stack's vertical data ([TX 6.8][TX]). Bidi: inline boxes map to embeddings or isolates; paragraph levels come from the text stack; reordering happens per line after breaking, using the text stack's visual-to-logical maps; fragments of an inline box split by bidi are separate fragments, and `box-decoration-break` applies to them as the spec suggests ([FR 1.12][FR]).

### 6.9 Style and layout re-entry, and frame-boundary state (LY-D12, LY-D20)

**The problem.** Container size queries and container-query units, `@position-try` fallbacks, anchored container queries and `text-fit` all feed layout results back into style; no specification defines the interleaving, and issue #11562 on its interaction with anchor positioning is open ([SM 1.7–1.8][SM], [GO 6.10, 6.17][GO]). The style spec defines the style side (`style_container_subtree`, with its own deterministic merge) and leaves the scheduling here ([ST 6.10][ST]).

**One protocol.** Layout owns a single re-entry mechanism with these rules:
1. **Container size queries and cq units.** The style pass stops at each size container with dependent rules and marks the subtree pending. When a layout task reaches such a container with a constraint space, the container's size in the queried axes is determined without its contents (size or inline-size containment). The task does **not** call style itself: it returns `NeedsStyle(container, size)` to the scheduler and suspends that subtree.
2. **Re-entry is a phase boundary, not a call inside a worker.** When no runnable layout task remains, the scheduler runs every pending re-entry of the frontier, in box-tree order, as **one style phase**: style's own traversal and deterministic merge ([ST 6.10, 6.12][ST]), with **no layout worker running**. It then applies the resulting box-tree changes sequentially (a query can change `display`) and resumes layout. Re-entry output is published only at that barrier, so no worker ever reads a style or box column another task is writing, and results do not depend on thread count (G44, LY-4). The cost is one barrier per re-entry wave, counted (6.16) and measured at LY-M2.
3. **Several sizes in one pass are versions, not overwrites.** A container may be laid out with several constraint spaces in one pass (a flex measure and final layout, grid sizing rounds, a balancing trial). Each distinct queried size produces a **style version** of the subtree, keyed by (container, size), held in a **pass-local style overlay**; box-tree changes for a size that is not the final one are built in a task-local box buffer and never replace the shared box tree. The constraint space carries the **style-version id**, not the size, so a cached layout is always keyed by the styles it used. Only the final size's version is published to the style columns and the box tree at the end of the pass. Style's content-addressed groups make a version identical to an earlier one free.
4. **The bound is structural.** The number of distinct constraint spaces a formatting context gives one child per pass is fixed by its algorithm: block 1, flex 2 (measure, final), grid at most 2 per sizing round with the rounds Grid's track sizing bounds, table 2 (column measure, final), multicol balancing at most 3 (6.5.6). Re-entries per (container, pass) are therefore bounded by the product of these factors along the ancestor chain, which the cache and LY-23 already bound; no numeric cap and no exhaustion rule exists, so the result is a function of the inputs alone and incremental and from-scratch layout agree (LY-3). A DoS case that nests re-entry under many measuring ancestors is bounded by LY-12's canonical work bound like any other layout.
5. **Anchor positioning.** An anchor must be laid out before the positioned box that uses it; the spec's acceptable-anchor rule guarantees an order exists ([Anchor Positioning 1 §2](https://drafts.csswg.org/css-anchor-position-1/#acceptable-anchor-element); [SM 3.2–3.3][SM]). Layout lays out out-of-flow boxes at their containing block in **top-layer level, then tree order**, which satisfies it; anchor lookups read the already-laid-out anchor's fragment through the containing-block chain. `@position-try` fallbacks are tried in `position-try-order`, **the last successful position option first** ([SM 3.6][SM]); a try whose declarations change styles is a re-entry like rule 2, keyed by the fallback, at the next barrier. Anchors in other scroll containers use **remembered scroll offsets** captured at the anchor recalculation point, and only the default anchor's later scrolling shifts the box, without relayout ([SM 3.4][SM]); the shift is handed to the scroll machinery (6.10).
6. **No fixed point.** Style changes caused by a frame's re-entries never re-trigger re-entry in the same pass; the next frame sees them as ordinary inputs.

**Frame-boundary state.** Some layout inputs are captured at fixed points of the frame and used until the next capture. They are **primary data** held in `hg-layout-state`, written only by the script thread at those points, never by workers (G43), recorded for replay, and kept across discard of derived data (FP-12) and in bfcache:

| State | Captured when | Read by | Spec |
|---|---|---|---|
| Last remembered size (`contain-intrinsic-size: auto`) | When ResizeObserver observations are determined and delivered | Intrinsic sizing of skipped and size-contained boxes | [SM 1.21][SM] |
| Last successful position option | Same point | Fallback order (rule 4) | [SM 3.6][SM] |
| Remembered scroll offsets | Anchor recalculation points | Anchor positioning across scroll containers | [SM 3.4][SM] |
| `content-visibility: auto` proximity and relevance | HTML's step after layout, with initial determinations in the same frame and later ones a frame late | Skipping decisions, `contentvisibilityautostatechange` | [SM 1.16–1.17][SM] |
| Scroll-state snapshot (`stuck`, `snapped`, `scrollable`, `scrolled`) | CSSOM View's "run snapshot post-layout state steps"; Izcal runs them right after the ResizeObserver loop, because HTML does not yet call them ([SM 1.13][SM]) | Style's scroll-state queries | Q-LY-12 |
| Scroll offsets and the scroll anchor | Scroll steps; anchoring adjustments at suppression-window ends (6.10) | All layout, IO, scroll APIs | [SM 2.7–2.10][SM] |
| ResizeObserver and IntersectionObserver last-reported values | Their delivery steps | The observers | [SM 7.3–7.6][SM] |
| Previous frame's start points of shift-tracked nodes | After each frame's layout | Layout Instability | [SM 7.7][SM] |

**`content-visibility`.** `hidden` skips contents; `auto` always applies layout, style and paint containment and adds size containment while not relevant ([SM 1.14–1.15][SM]). A skipped subtree is not laid out; its fragment is the size-contained box with `contain-intrinsic-size` (or the last remembered size). Find-in-page and `hidden=until-found` lay out skipped content synchronously for the search as HTML says ([SM 1.22][SM]). **Accessibility**: the semantic plane never causes layout work that the visual path skipped, because CSS Containment 2 §4.6 forbids a timing signal that would reveal AT use ([Contain 2 §4.6](https://drafts.csswg.org/css-contain-2/#cv-a11y); [GO 4.8][GO]). Skipped `auto` content **stays in the semantic tree** with its bounds marked **not determined**; bounds are computed only when the visual path lays the content out. Content is omitted only where a platform accessibility API demands an exact position synchronously, which §4.6 allows. A test in the A11Y-1 style checks that semantic-tree contents and layout work counters for skipped subtrees are identical with AT on and off (LY-16), and the accessibility track reviews the rule.

### 6.10 Scroll containers, scrolling, sticky, anchoring and snap (LY-D13)

**What layout computes.** For each scroll container: the scrollport, the **scrollable overflow rectangle** as Overflow 3 §3.3 defines it (padding box, line boxes, border boxes of boxes it contains, flex and grid items' margin areas, end padding added so both start and end alignment are reachable; zero-area boxes excluded; the unreachable region clipped), stored as a first-class fragment field ([SM 2.4–2.5][SM]); scrollbar gutters (`scrollbar-gutter`) with Izcal's fixed thickness (LY-D11); snap areas and snap containers; sticky constraint rectangles. Overflow 3's three open points (transform projection, margin areas of other children, end padding) are black-box observations (Q-LY-13).

**Who owns scroll offsets.** Scroll offsets are **primary state** in `hg-scroll` (part of `hg-layout-state`). Script and layout change them on the script thread; the compositor (graphics spec) changes them asynchronously during user scrolling. The two sides reconcile with a **delta protocol with sequence numbers**, so neither side's change can be lost: the compositor sends (scroll node, delta, gesture phase, sequence number); the script thread applies compositor deltas at the frame's scroll step, as recorded inputs (JS-D15), and sends back its own changes (scroll anchoring adjustments, `scrollTo`, `scrollIntoView`, re-snap after layout, anchor-positioning shifts) as deltas tagged with the last compositor sequence number it consumed; both directions are recorded. During a gesture the compositor snaps; after a layout change the script thread re-snaps and sends the result as a programmatic scroll. `scrollend` is dispatched at the first scroll step after the gesture-end message. Geometry APIs on the script thread always use the script thread's offsets as of the last scroll step, including for sticky boxes, which move on the compositor between frames with no relayout. Layout hands the graphics spec, through paint's scroll property tree: scroll container geometry, the scrollable overflow, sticky constraints, snap areas, anchor-positioning scroll shifts, and scroll-timeline ranges. **Amended 20 October 2026 (the animation spec's amendment): view-timeline subject geometry and the scroll ranges scroll-driven and view timelines read are layout's**, published per flush as recorded values ([SM 2.15][SM]; the animation spec 6.6), so the animation engine samples exactly what layout computed. **A stale timeline re-runs as one more pass of the style and layout loop** — the animation spec's zero-range resolutions name the stale rule, and layout's loop bounds it exactly like container re-entry (6.9), at most once per flush. This is the shared model whose absence made Chrome unship `position: sticky` ([Chrome blog](https://developer.chrome.com/blog/position-sticky); [HP 6.4][HP]).

**Scroll anchoring** follows [CSS Scroll Anchoring 1](https://drafts.csswg.org/css-scroll-anchoring-1/): anchor selection (priority candidates: the focused editable element, then the active find-in-page match; then the DOM walk with the exclusion rules), the adjustment as the anchor's block-start movement, suppression triggers, and the **suppression window**, which the spec ends at the end of the event-loop iteration or just before an operation whose result depends on scroll position ([SM 2.7–2.10][SM]). Izcal uses exactly those boundaries: (a) the end of each event-loop iteration, and (b) the entry of the **scroll-position-dependent subset** of `hg-layout-query`'s forcing table (geometry relative to the viewport, scroll offsets, `elementFromPoint`, IntersectionObserver computation), each entry tagged in the table. The spec notes these boundaries should move into HTML; until then the tagged subset is recorded in the observation log and filed (Q-LY-14). The selected anchor, each adjustment and each suppression with its trigger are decision records (6.16): no engine shows them today ([GO 2.10][GO]).

**Scroll snap** re-snaps after layout changes to the same snap areas when they still exist, with the focused, then targeted, then block-axis priority ([SM 2.12][SM]); `scrollsnapchange` and `scrollsnapchanging` are admitted per LY-D10.

### 6.11 Incremental layout and invalidation (LY-D4)

**Dirty state.** Inputs to a box's layout change through: a style change (the "affects" mask, 6.3), a box-tree change, a text change (a mutation-log `SetText` or a font installation), a replaced element's natural size, a frame-boundary state change (6.9), the viewport, or a change in the constraint space its parent passes. The first six mark the box **self-dirty** and its ancestors **child-dirty** up to the nearest **relayout boundary**: a box whose layout result cannot change size or baselines when its subtree changes (size containment; fixed width and height with no percentage dependence and `overflow` other than `visible`; a scroll container whose scrollbars cannot appear or disappear because of `scrollbar-gutter: stable` or `overflow: scroll`; the root). Containment and fixed sizes are the CSS facts Flutter's cut-off rules mirror ([IP 1.12][IP]). The parent's constraint-space change is caught by the central diff (6.4).

**Relayout.** Layout starts from the dirty roots (the child-dirty boxes nearest the root, or the relayout boundaries), and each layout call first consults the cache: a clean box with an equal (or diff-compatible) constraint space returns its cached result; a dirty box lays out, reusing the cached results of clean children. Unchanged subtrees keep their fragment ids, so a relayout writes new fragments only along the **spine** from each change up to its relayout boundary ([IP 1.5, 5.3][IP]). **Early cutoff**: if a box's new fragment equals its old one in size, baselines, adjoining-margin summary, overflow and out-of-flow list, its parent's layout reuses the rest of its old result and stops propagating; this comparison is the incremental analogue of style's content identity check.

**Two traversal strategies, measured (B5, INC-1).** (a) the root-down walk over child-dirty bits that every engine uses; (b) an **ordered dirty queue** keyed by box-tree order (Spineless Traversal's idea, [IP 1.17][IP]), which visits only dirty boxes and their spines without touching clean siblings. Both are built behind a switch from LY-M2; INC-1 measures them on the mutation-trace corpus, and the measured winner is the default (LY-25). A **bulk fallback** lays out from scratch, in parallel where it pays, when the dirty set exceeds a share of the document measured at LY-M2 (initial load, large `innerHTML`, sheet swaps, lazy-load bursts), as B5 specifies; its rate is published (INC-4).

**Durability tiers** (B5) apply to layout through the cache: UA-image style and the Izcal font set are high durability, author styles medium, DOM and state low. Layout needs no separate durability machinery, because the inputs' durability is already reflected in which boxes are dirtied.

**Every relayout has a cause.** Each box laid out carries a cause id (the mutation-log entry, the style "affects" category, the frame-state change, the constraint-diff reason, a re-entry barrier, or the bulk fallback) in the pass's scratch arena, discarded unless recording (6.16). Two counters are canonical and always on: boxes laid out whose fragment did not change (over-invalidation), and cache hit rates per context.

**Checked every CI frame (LY-3).** In CI and DST, every flush of the mutation corpus is followed by a from-scratch layout of the same inputs in the production engine (cache off, incremental off, sequential) and the canonical fragment trees (6.13) are compared byte for byte; a difference fails the build with the mutation and the box. Initial layouts are also compared with the reference engine (LY-5). This catches under-invalidation, which LayoutNG called the dominant legacy bug class, and hysteresis ([IP 1.2, 6.5–6.7][IP]).

### 6.12 Parallel layout and determinism (LY-D6)

**Designed in, used where measured to pay.** The traversal runs on the substrate's phase pool (B3, G3). Workers hold `&` references to the node columns, style columns and groups, box columns, text data and the previous fragment store, and `&mut` only to task-local fragment buffers and scratch arenas; the only writers of the fragment store, the box columns' cache slots and `hg-layout-state` are the sequential merge and the script thread (G42, G43). Three kinds of parallel work, in order of expected value:
1. **Text preparation**: itemization, shaping and break-opportunity computation of dirty paragraphs, before line breaking. Text work parallelized 2–4x in the only published study, while boxes were "too fast" to gain ([IP 3.3, 3.5][IP]); it is independent per paragraph. Shaping-cache insertions in parallel are outside canonical bytes by OD-4 ([TX 6.8][TX]).
2. **Independent formatting-context subtrees whose constraint space is known before positioning**: flex items once their main sizes are resolved, grid items once tracks are sized, table cells once column widths are known (Servo parallelizes table rows, [IP 3.11][IP]), out-of-flow boxes once their containing block is done and their anchors are laid out, multicol column rows, and independent BFC roots not adjacent to floats.
3. **Independent documents**: same-agent iframes' documents, after their containers' sizes are known.

Floats serialize the BFC they live in, as every source found ([HP 6.11][HP]); Izcal does not speculate around them.

**Determinism.** A worker's fragments get **provisional ids** in its buffer; the merge, in box-tree order, assigns final ids and writes the store, so ids, store layout and canonical bytes are identical for every thread count (LY-4, FP-24). A task writes cache-slot entries only into its task-local buffer, with provisional ids (each box has one parent, laid out by one task, so no two tasks produce entries for one box), and the merge publishes them (G43). Re-entry into style happens only at scheduler barriers with no worker running (6.9, G44). Layout has no floating point after the boundary conversion (6.2), so no reduction order can change a result. **Adaptivity**: layout starts sequentially and spawns parallel tasks only when a subtree's estimated work (box count plus text length, a canonical measure) exceeds a threshold set by measurement at LY-M2, per HGBA-2 4.3. Because the only rigorous measurement found layout's average total time higher at 4 threads than at 1 ([IP 3.9][IP]), LY-26 states the sequential baseline first and requires the parallel path never to be slower by more than 2%†; it is one half of HGBA-2's target P-1, restated jointly with the style spec's ST-26 (Section 9.5).

### 6.13 The fragment store, primary state and footprint (LY-D7, LY-D20)

**Fragments.** The store is per **style scope** — one agent, or one static document (the SVG spec's R6, applied 20 October 2026: a scriptless SVG image owns its store, as it owns its style scope; [ST 6.9][ST]) — an arena of fixed-size **fragment records**: box id (4 B), kind and flags (4 B), physical offset relative to the parent fragment (8 B), physical size (8 B), first child and child count (8 B), and an index into a side table for rare data (4 B): **36 B**. Rare data (scrollable overflow for boxes with overflow, baselines when they differ from the default, break token, border and padding when paint or the query layer needs them and they are not cheaply recomputable from style and size, fragmentainer geometry, multicol column rows, table grid geometry, flex and grid line and track positions for gaps and DevTools) lives in side tables. **Line boxes and inline items** are records in the inline formatting context's flat list (line: start item, item count, block offset, height, baseline, 16–20 B; item fragment: item index, inline offset, width, 12 B); glyph runs are the text stack's and are charged to the text-shaping line, never here ([RN P9][RN]). **No up-pointers** and **no mutation after the merge**: a relayout writes new records for the spine and reuses old ids elsewhere ([IP 1.5][IP]). Consumers (paint, `hg-hit`, `hg-layout-query`, `hg-semantic`, DevTools) depend only on `hg-fragment`'s read API (G38). Physical coordinates are stored because every consumer works in physical space; layout algorithms work in logical space and convert once (6.8). **Paint's identities never use fragment ids**: property-tree node ids and display-item identities derive from the node slot (or an anonymous box's path from its nearest node), the pseudo-element and the fragment's index within its box, so the display-list hash is history-independent like the canonical fragment tree ([GR 6.3][GR]; [RN2 Q1][RN2]).

**Fragment identity and the canonical fragment tree (LY-D18).** Fragment ids are store indices; an incremental pass keeps the ids of reused subtrees and a from-scratch pass allocates all of them fresh, so ids depend on history. Ids are therefore **never part of what is compared or hashed**. The **canonical fragment tree** is a pre-order serialization of fragment records with child order, geometry, side-table contents and break tokens inlined, and no ids or store offsets. DET-1's fragment-tree hash, LY-3, LY-32 and LY-40 use it; LY-4, whose premise is equal histories, additionally compares raw store bytes. Footprint counts **live** records only, so canonical bytes do not depend on history (FP-24).

**Handles and reclamation.** The store has a 32-bit **epoch**, incremented by each reclamation. Any fragment handle held beyond one pass (by `hg-semantic`, `hg-hit`'s caches, DevTools, decision-record replays) is (id, epoch) and is checked on use, as FP 6.4 requires of handles that cross threads or are stored ([FP 6.4][FP]); a stale handle is detected, never aliased. **Primary state never stores a fragment id** (G45): it stores node slots and values (offsets, sizes, option indices). Unreferenced fragment records (the old spine after a relayout) are reclaimed by a mark from the roots (each document's root fragment and the cached results in box columns) at the end of a pass when the store's canonical garbage bytes exceed a threshold, so the trigger and the resulting store are deterministic; no reference counting runs in the parallel phase. This replaces Stage 1 5.6's `Arc<Fragment>` (Section 9.5).

**Classes and the safepoint.** Box columns, fragment store, caches and inline item lists are class (a) derived data (FP §6.4): dropped under pressure after the safepoint handshake, rebuilt by a from-scratch layout with an identical canonical fragment tree (FP-12, LY-32). They are discardable **only at a safepoint outside a flush**: workers hold `&` references into the previous store during a pass, which no type rule can protect across an unmap. A pass checks the pressure flag at task boundaries; at Critical it finishes with caches off (no new cache entries, no new memo entries) rather than stopping, and the discard follows at the next safepoint. LY-32 draws its random discard points from those safepoints. `hg-layout-state` (6.9) is **primary**: small, kept across discard, serialized into bfcache and suspend files, and recorded. Without this split, discarding fragments would lose scroll offsets and remembered sizes, and the rebuild would differ.

**Budget (co-signed by the graphics spec, GR-D23).** The style spec gives layout and paint 360 B† per node of FP-11's 512 B† ([ST 6.11][ST]). Layout takes **≤ 200 B† per node averaged over the corpus**, and paint **160 B†**, counted across processes: about 72 B in the renderer and ≤ 88 B† of display items in the content GPU process ([GR 6.22][GR]); Q-LY-15 confirms the fragment-to-box ratio at LY-M0. Every box laid out keeps a cached result, so the ledger counts one cache entry per laid-out box:

| Item | Low | Expected | High |
|---|---|---|---|
| Box record | 32 B | 32 B | 32 B |
| Fragment records (1.0, 1.15, 1.4 per box × 36 B) | 36 B | 41 B | 50 B |
| Cache entry per box (result 24 B, keys 8 B) plus a second entry for measured boxes (amortized) | 32 B | 40 B | 56 B |
| Interned constraint spaces (shared by siblings; amortized) | 4 B | 8 B | 16 B |
| Intrinsic memo for measured boxes (amortized) | 4 B | 8 B | 16 B |
| Line and inline item records (amortized; glyph runs excluded) | 16 B | 24 B | 32 B |
| Side tables: overflow, baselines, tokens, track geometry (amortized) | 12 B | 20 B | 32 B |
| `hg-layout-state` (amortized) | 4 B | 8 B | 12 B |
| Arena slack | 10 B | 19 B | 30 B |
| **Total** | **150 B** | **200 B** | **276 B** |

The high column exceeds 200 B; if measurement lands there, the failure order, shared with the graphics spec ([RN2 Q3][RN2]), is: (1) representation work on the side that is over (here fewer cache entries for clean leaves, packed side tables); (2) a joint re-split of the 360 B† with the graphics spec; (3) FP-11's own failure action, owned by FP, with the style spec's 72 B† and 80 B† unchanged unless the style spec agrees; never a separate ledger line. The LayoutNG design document's estimate of 5–10x as many fragments as layout objects ([HP 2.4][HP]) is why fragments are packed records and rare data lives off the record. **Fixed cost**: layout's share of an empty agent is created lazily, with zero initial capacity, and bounded by LY-31 at **≤ 64 KiB†**, inside FP §6.3's 0.25 MiB per-agent document line together with style's ST-34.

**Partitioning.** All layout data is per agent and therefore within one (site, container) process (I-1). Per-agent tables can hold data of two partitions only when both documents are in one agent, which already lets them script each other, so no channel arises (the style spec's argument, [ST 6.11][ST]). Nothing derived from content crosses agents or processes, except the geometry and visibility messages of out-of-process frames (6.15), which are typed messages.

### 6.14 Hit testing and the paint-order contract (LY-D14, LY-D22)

CSSOM View defines `elementsFromPoint` as walking boxes "in paint order, starting with the topmost box" and leaves hit testing otherwise undefined ([CSSOM View](https://drafts.csswg.org/cssom-view/#dom-document-elementsfrompoint); [SM 8.1–8.2][SM]). Izcal makes **hit testing the reverse of the one paint order**, so "hit testing matches painting" holds by construction and is property-tested (LY-7).

**The paint-order contract.** This spec states the read-only contract hit testing needs, in the small L4 crate `hg-paint-order`: the stacking-context and paint-chunk order (CSS 2 Appendix E within stacking contexts, [SM 8.3][SM]), a chunk-to-fragment map, and property-tree lookups (transform, clip, effect including opacity and filters, scroll) plus ink overflow per chunk — **and, since 20 October 2026 (the SVG spec's R6), the chunk-to-SVG-record map**, so hit testing and paint can walk from a paint chunk to the SVG render-tree records that produced it without reparsing. **The graphics spec owns the crate** and its production implementation ([GR 6.3][GR]); this spec owns the requirements above and the reference paint-order builder written from Appendix E, which stays a test oracle that the production implementation must match (LY-7, GR-5); a change to the contract needs both owners ([RN2 Q2][RN2]). Everything the contract serves stays in the renderer after the content GPU process acknowledges a frame (inside paint's 72 B renderer share), so hit testing never waits on another process. `hg-hit` and `hg-layout-query` depend on that contract and on `hg-fragment` (G38).

**The walk.** `hg-hit` walks chunks from the top, maps the point through the property trees' transforms and clips, and tests each chunk's fragments precisely (border-radius and `corner-shape` regions, `clip-path`, line and glyph boxes from the fragment store and the text stack's cluster map), skipping `pointer-events: none`, `inert` and `visibility: hidden` content ([SM 8.5][SM]). Where no specification decides, Izcal writes the rule down: for 3D transforms, the region hit is the region painted topmost after depth sorting, matching the principle "Hit-testing should always match painting" in [csswg-drafts #3997](https://github.com/w3c/csswg-drafts/issues/3997) ([SM 8.4][SM]); for `foreignObject` under transforms, the point maps through the transform into the CSS layout root. Input events carry the compositor's scroll offsets at event time, recorded, so hit testing uses the geometry the user saw.

**Cross-process frames.** The browser process routes input to the right renderer by hit-testing composited surfaces, so each renderer sends, per frame, a **hit-test region message**: for each out-of-process child frame and for the document itself, the region in surface coordinates (rectangles, with a flag for regions whose shape needs an exact test in the renderer), the transform class, and whether `pointer-events` or `inert` exclude it. The message is typed IPC, recorded on both sides (JS-D15), and **untrusted** in the browser process (I-2): the broker clamps every child frame's region to the region its embedder renderer reported for that frame, recursively up to the top-level renderer, whose regions it clamps to the window; compositor geometry is only a cross-check and never decides consent ([GR 6.1, GR-D28][GR]; [RN2 Q4][RN2]); the broker never lets a child's region extend outside the parent's clip for it, and uses the regions only to choose a target renderer, which then hit-tests precisely within its own document. A frame's content never hit-tests or paints outside its clip ([SR 2.8][SR]; LY-15).

### 6.15 Geometry APIs, observers and cross-process frames

`hg-layout-query` implements CSSOM View (box geometry, client and scroll metrics, `elementFromPoint(s)`, `caretPositionFromPoint`, scrolling with promises where admitted, `checkVisibility`), ResizeObserver (its depth-ordered loop and the fixed error string, which bounds iterations by tree depth, [SM 7.3][SM]), IntersectionObserver v1 and **v2** (`trackVisibility`, with the 100 ms minimum delay and "no false positives": a target is visible only if Izcal can prove it unoccluded, untransformed beyond 2D translation and proportional upscale, unfiltered and fully opaque from the fragment and paint trees, [SR 8.1–8.3][SR]), the Layout Instability API (start points, impact and distance fractions, the 500 ms input exclusion, Izcal's "pixels to significance" set at **3 px†**, the same value Chrome states, [SM 7.7–7.8][SM]), LCP's geometry, and HTML's lazy-load intersection observer with a fixed, published lazy-load scroll margin (Q-LY-16). Lazy loading is off when scripting is disabled, as HTML requires ([SM 4.7][SM]). Each API's anchor names its spec step; each forces layout as 6.1 says. **The forcing table also covers the SVG geometry methods** (`getBBox`, `getCTM`, `getScreenCTM`, `isPointInFill`, `isPointInStroke`, answered through the SVG spec's `SvgGeometry` trait) **and any read that resolves a `use` shadow root**, which first resolves pending instance builds for that root — both entry kinds are tagged in the table, so a forced flush resolves instances exactly as a normal flush would (the SVG spec's R6, applied 20 October 2026).

**Layout shifts with causes.** Because each relayout carries a cause (6.11), each shifted node's movement is attributed to the mutation-log entries that dirtied the boxes whose layout moved it: the culprit is computed, not guessed from four classes ([GO 2.9, 7.3][GO]). The Layout Instability API itself exposes only what its spec defines; the causes go to DevTools (6.16).

**Out-of-process frames.** A cross-site iframe's document lays out in its own (site, container) process. The parent sends, over typed IPC, the frame's **content-box size, device scale and zoom, the viewport intersection rectangle in the child's coordinates, a transform class (identity, 2D translation and proportional scale, or other), the throttled flag and visibility**; the child sends nothing about its layout back (an iframe is a replaced element with no natural size unless `frame-sizing` is admitted, [SP 7.4][SP]). Both sides record these messages (JS-D15). The child's IntersectionObserver and lazy loading use the received intersection. **IntersectionObserver v2 across processes**: the parent computes, at each frame-boundary update, one **visibility bit** per child frame: true only if the parent can prove the frame's composited content unoccluded, its effective transform a 2D translation or proportional upscale, its effective opacity 1 and no filter on its ancestor chain, the same conditions IO v2 defines for an element ([IO v2](https://w3c.github.io/IntersectionObserver/v2/); [SR 8.1–8.3][SR]). The parent applies the graphics spec's rule: a frame is not provably visible if any ancestor has a compositor-mutable opacity or transform, a filter, or a GR-D18 clamp or transparent-black substitution, computed in the renderer from the display list and recorded state, never from compositor output ([GR 6.28][GR]). The child combines the bit with its own in-document proof. The bit reveals only what IO v2's `isVisible` already exposes to the child about its own visibility, and LY-14 includes a probe showing the child learns nothing else about the parent's layout (Q-LY-17).

**Admission exceptions.** The Layout Instability API and IntersectionObserver v2's `trackVisibility` ship only in Chromium-based browsers ([SM 7.6, 7.9][SM]), so LY-D10's rule alone would hold them. This spec recommends an **owner exception** for both: Layout Instability is the basis of CLS, which users experience and site owners are measured by, and IO v2 is an anti-clickjacking mechanism, where P1 outranks P2. `interpolate-size` and `calc-size()` (Chrome only, [SP 7.5][SP]) are held.

### 6.16 Observability: what layout shows (LY-D19)

**Production counters, always on and canonical**: boxes laid out per pass, cache hits and misses per context, boxes relaid out whose fragment did not change, bulk fallbacks, re-entries and their bound exhaustion, re-layouts per fragmentation flow, parallel tasks spawned. They feed DevTools' performance view and LY-50's overhead targets.

**Decision records, under replay.** The questions developers ask ([GO 3][GO]) need the decisions layout made, with their inputs and spec steps. Izcal does not keep these in production memory (they cannot fit in 200 B per node, [GO 7.11][GO]); it **re-runs the production layout under replay with probes on** (DT-D3's model), and each algorithm's anchored steps emit typed **decision records**: for a box size, the chain (specified size, percentage basis, automatic minimum size, min- and max-content contributions of the children that decided it, flex or grid distribution step, clamping); for a line break, the candidate opportunities, the objective's costs and the chosen break; for a page or column break, the candidates with their appeal and the rule that was relaxed; for scroll anchoring, the candidate walk, the chosen anchor, the adjustment or the suppression trigger; for anchor positioning, the fallbacks tried and why each failed; for a re-entry, the container, size and the rules it changed; for overflow, the boxes contributing to a scroll container's scrollable overflow beyond its scrollport, ordered by how far they extend it. Because the records come from the production algorithm, not a second model, they match the result by construction, and LY-51 checks that replaying a record's inputs through the reference engine reproduces the value.

**What developers and agents get** (through the DevTools spec's IIP and its adapters): a **size explainer** for any box ("why is this 312 px": each step with its spec link and WPT tests); an **overflow finder** ("which box makes this page scroll horizontally"); **relayout causes** in the performance view, from mutation to boxes to shift; **shift culprits** computed from causes; a **stateful-decision view** (last successful position option, remembered sizes, scroll anchor, scroll-state snapshot, proximity, with when each was captured); **break explanations** for print and multicol; **layout diffs** between two replays, two builds or two viewport sizes, as fragment-tree diffs rather than pixels; and **accessibility layout checks** (visual order versus DOM order per container, reflow at 320 CSS px, text-spacing clipping per WCAG 1.4.12) run as replays at a forced environment ([GO 7.1–7.11][GO]). Agents receive the same records through MCP when AI is on, as data, never as screenshots. Every decision record carries the **origin and frame** of the box it describes; the MCP adapter filters records by the agent task's read set and redacts cross-origin geometry beyond what the page itself could observe (B9). Records are computed only on request, under replay, for DevTools or an agent, so nothing runs when no one asks, and the MCP export path lives in an `ai`-feature crate, so with AI off it is not even linked (B10, G4).

### 6.17 Security, privacy and robustness (LY-D11, LY-D15)

**Memory safety.** All layout crates are `#![forbid(unsafe_code)]` with no inventory entry (G40). Indices are typed and checked; a panic reachable from content is a denial-of-service bug triaged like a crash, because FreeDom found a reachable Rust assertion in Firefox (HTML/CSS) that way ([FreeDom, CCS 2020](https://gts3.org/assets/papers/2020/xu:freedom.pdf); [SR 4.3][SR]). Arithmetic saturates (6.2); the JS spec's G18 (checked arithmetic on untrusted sizes, no wrapping) extends to every layout value derived from content (G39).

**No re-entrancy.** Layout calls no script (G37) and reads only frozen inputs; nothing outlives the pass except published fragments and primary state written by the script thread. A planted-bug suite (a fragment id used after reclamation, a box id read after its slot was reused, a layout call from inside an observer callback, a cache entry read across a re-entry) must be caught at compile time or by generation checks (LY-11).

**Depth and fuel (LY-D15).** Layout algorithms are written recursively, as the specifications are, but never on the small OS thread stack. Each layout pass, on the script thread or on a worker, runs on **stack segments from the substrate**: the same guard-paged, chained segment mechanism the JS spec defines for script (JS-D19), moved into the substrate so one audited, inventoried implementation serves both, with the same shadow-stack, unwinding and sanitizer support. Overflow is decided by a **canonical stack budget**: each recursive layout entry charges a fixed size by its kind, whatever the machine, as JS's canonical frame budget does ([JS 6.9][JS]); the real segment is always larger than the budget plus the deepest runtime call. On an OS where the JS track adopts JS-D19's fallback (c), runtime calls on the OS stack because Rust frames on segments fail verification there, layout cannot run on segments either and uses explicit work stacks (LY-D15 (c)) on that OS, with the same canonical budget and depth limit ([RN2 Q16][RN2]). The budget is set at LY-M0 from measured frame sizes so that the resulting box-depth limit is **at least 10,000† levels**; boxes beyond it are not generated (their subtree is treated as `display: none`, so geometry APIs report empty rectangles and `checkVisibility()` false), a deterministic limit identical on every platform, recorded as a deviation and compared with what the three engines do (Q-LY-1). Every loop whose trip count content controls (lines, floats, tracks, columns, fragmentainers, re-entries, fallback options, balancing passes) has a stated bound in Section 6 or a canonical fuel counter; exhausting fuel produces the specified result, never a timeout-dependent one (B1). The DoS suite (LY-12) includes 10⁶-deep trees, depth-20 nested flex and grid, a 10-deep nest of balanced multicols, `colspan=1000 rowspan=65534`, 10⁵ floats, grid lines at ±10,000, pathological `pretty` paragraphs, container and anchor re-entry chains and ResizeObserver chains.

**Fuzzing.** Tier 1 fuzz targets: the box-tree builder, every formatting context, the line breaker, fragmentation, re-entry and the query layer, driven by a grammar fuzzer generating DOM, CSS and mutation interleavings whose oracles are (a) no panic, (b) incremental equals from-scratch, (c) production equals reference where both claim conformance, and (d) metamorphic visual-delta consistency ([SR 4.6–4.8][SR]). Every historical layout CVE class in [SR 1–2][SR] is a regression case.

**Privacy.** Layout geometry is a fingerprint (font metrics alone identified 34% of over 1,000 browsers, [SR 7.1][SR]). TX-D4 makes text metrics identical per build for scripts with Izcal faces ([TX 6.8][TX]); **LY-D11** makes the rest of geometry identical too: scrollbar thickness and overlay behaviour are Izcal constants, and no OS metric reaches layout. Classic scrollbars are **15 device-independent px†** thick (`scrollbar-width: thin` 8†, `none` 0), converted to CSS px through the recorded page zoom and device scale (thickness in CSS px = 15 ÷ zoom), so at 400% zoom a scrollbar does not take four times the viewport that WCAG 1.4.10's reflow test needs; geometry is therefore identical across OSes at each zoom level. Overlay or classic is one preference whose default is the **OS accessibility setting** (for example "always show scroll bars"), read once per session into the environment snapshot, recorded, counted in PRIV-2's entropy budget, and reviewed by the accessibility track. Form controls use Izcal metrics (6.3). Layout work never depends on secret state: `:visited` styles are restricted to colour by style ([ST 6.7][ST]) and layout never reads visited state, so layout time cannot leak history ([SR 7.3][SR]); cross-origin frame contents are never laid out by the parent. Timing-sensitive features (lazy loading, `content-visibility` relevance, scroll-to-text) are policy decisions recorded as inputs, not side effects ([SR 7.7–7.8][SR]); scroll-to-text-fragment scrolling happens only in top-level navigations. Layout caches are per agent; an agent spans two partitions only when its documents can already script each other (6.13), so FP-36's channel suite has no layout cache to probe across partitions; the suite still includes layout timing probes.

**Clickjacking.** A frame's content never paints or hit-tests outside its clip (LY-15); IntersectionObserver v2's visibility is computed exactly and returns false whenever the proof fails (6.15).

### 6.19 User experience and integrations

**For people browsing.** Layout is invisible when it works. Its visible effects: pages render the same on every OS for scripts with Izcal faces, scrollbars look the same everywhere (LY-D11; the shell offers overlay or classic scrollbars as a user preference, which is an environment input), printing works on Stage 2's print UI with Stage 1's paged layout, and the browser zooms to 400% with reflow.

**Developers and agents**: Section 6.16. **Accessibility**: the semantic plane (B8) reads bounds, line boxes, per-character bounds through the text stack's cluster map, `reading-flow` order when admitted (Chrome-only today, [GO 4.4][GO]), and the `content-visibility` rule of 6.9. **Editing** (future spec): caret and selection rectangles from fragments and the text stack. **Animations** (future spec): scroll timelines read layout's scroll ranges; view transitions capture old and new geometry from the fragment store ([GO 6.12][GO]); `interpolate-size`, when admitted (LY-D10), evaluates intrinsic sizes per frame through the intrinsic memo. **Graphics** (future spec): consumes `hg-fragment` and `hg-scroll`'s outputs; owns stacking contexts, paint order, ink overflow and snapping. **SVG** (future spec): 6.5.10.

### 11.2 Claims that are single-source, unverified or conflicting

- **Parallel layout evidence** rests on two studies: HiPC 2016 (one engine, 2016 hardware) and Meyerovich and Bodík (a simplified engine). Both are primary, but neither measures a modern engine ([IP 3][IP]).
- **Spineless Traversal's numbers** differ between paper versions: 3.23× and 78.2% (arXiv v1–v3), 1.78× and 74.86% (v4, 27 March 2025), 1.80× and 83.0% (v5–v8, the PLDI version) ([arXiv 2411.10659](https://arxiv.org/abs/2411.10659); [H3 B5][H3]).
- **LayoutNG's 5–10x fragment estimate** is a 2017 design-document expectation, not a measurement ([HP 2.4][HP]).
- **Chrome's "pixels to significance" of 3** for layout shifts is stated only as Chrome's choice in a spec note ([SM 7.7][SM]); Izcal adopts it as a † value.
- **The forced-layout list** is a single prose source derived from engine code ([SM 7.12][SM]); it is hypotheses only.
- **CVE counts** are lower bounds from keyword searches, and the 2015–2020 Chrome gap is a naming artifact ([SR 1.1][SR]). The 2026 CVE identifiers in [SR 1.2, 1.6][SR] were confirmed on NVD by the fact-check; CVE-2026-2441 is also in CISA's Known Exploited Vulnerabilities catalogue.
- **Grid-lanes status** in Chrome and Firefox rests on Chrome Status prose and a WebKit post ([SP 8.10][SP]); re-checked before any admission decision.
- **Anchor positioning's Baseline status** conflicts between `web-features` and vendor posts ([GO 5.9][GO]); MDN data says three engines ship it by January 2026 ([SM 3.7][SM]).
- **Scroll anchoring in Safari 27** is from MDN compatibility data and a WebKit post snippet; Apple's release notes line was not seen ([SM 2.11][SM]).
- **The 15 device-independent px scrollbar thickness, the 10,000-level minimum depth, the 2⁻²⁴ factor precision, the 8-line `pretty` window, the 3-layout balancing bound and the 64-pass cache eviction** are first-principles values (†) to confirm by measurement.
- **Blink's balancing method** is described in one research-note row in terms no cited prose uses; that row was removed, and 6.5.6's stretch rule is argued from first principles (6.21).
