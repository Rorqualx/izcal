HGBA-2.1 and HGBA-3.1 say **what** must be true and how each claim can fail. This document says **how the engine is built**: the process map, the crate graph, the substrate, IPC, the renderer pipeline, the shell features, the build and test infrastructure, the milestones and the team. It changes no target. Where it makes a design choice the specs leave open, it states the choice, the alternative and what would reverse it. Choices that belong to the project owner are collected in Section 11, each with a recommended default.

**Retired record (0.14).** Drafts 0.1–0.13 opened with four "verified facts" about V8, Servo, Stylo and WebRender, and Section 12 listed the resulting amendments. HGBA-2 2.3.0 removed V8, Servo layout, Stylo, Taffy, Parley, WebRender, wgpu, AccessKit and html5ever as engine components (D-S10), and the 22 accepted component specifications now own every engine component. The four facts described dependencies that this design no longer has: no V8 embedding, no Stylo adapter, no WebRender, no Taffy or Parley layout driver. They are kept only as history in Section 12; no section of this document depends on them. What replaces each is named where it was used, and the owning specification is cited.

Naming: crates use the prefix `hg-`. Crate-graph rules are G1–G9 in this document; the G-rule registry continues in the owning specifications, and Section 2.2 records every range (G10–G219, with G220 onward assigned to the next specification). Accessibility repair classes are R0–R4 (HGBA-3.1.1 B10). "Stage 1" means HGBA-2.1's Stage 1, which HGBA-3.1 overlays with Stages A and B. Thresholds marked † are set by this document from first principles. A **spec anchor** is a comment `// spec: <URL>#<fragment> [step N[.M]]` naming the specification section and step a hand-written algorithm implements, at a pinned specification revision (HGBA-2 M-1). Izcal implements web-visible behavior from the specifications (M-1); other engines are black-box references only (D-S10).

**Threads (FP-32).** A renderer runs one script thread per agent cluster; workers are script agents on their own threads; `hg-raster` and image decode use the renderer's worker pool; Stage 1 lays out on the script thread and assumes no parallel layout. Each service is a single-threaded event loop over the substrate's `Executor`; no service shares a thread or an address space with another. WebRTC runs in the renderer's worker threads with sockets granted by the broker; a native CDM runs only in its own CDM process. The profile's process count is FP-D17's measured quantity; the counts above are the starting policy.

**Isolation key and the I-1 exceptions.** I-1 has five parts, and this table implements all five:

1. **Key.** Renderer processes and all browser-side state are keyed by **(site, container)**, where a container is a policy context (Section 6). On devices above a RAM threshold, the site component becomes the origin, so subdomains of one registrable domain stop sharing a process; that is the only case origin keying adds, because site keying already separates different registrable domains (Kilger et al., IEEE S&P 2026, exfiltrated data through same-site subdomains sharing a process). The threshold is a decision-log entry set by measurement against S-3, with containers multiplying the process count on top.
2. **Network state.** Every network service partitions **all** of its state by (top-level site, container), rather than an enumerated list. The axes are HTTP cache, connection and socket pools, DNS cache, Alt-Svc, TLS session tickets, HSTS, revocation-check caches, reporting endpoints and service-worker registrations; the static globals of NW-D7 (HSTS preload, root store, CT log list, revocation filters, PSL) are the only exceptions, and they are the same for every key by construction. In-process caches key by the projection **(T, C, X, n)** of P18: T is the top-level site, C the container, X the cross-site-ancestor bit, n the per-navigation nonce; F is fixed by the process's site lock and N is set only for navigation requests. Each axis is one on which an attacker who can measure timing could otherwise correlate two containers.
3. **Shared-process exceptions.** Four services are shared (OD-8, ML-D5): the compositor GPU service, the audio service, the capture service and the ML service. Each is keyed to no site, receives only the typed messages its contract allows, never page payloads or credentials, and is reported on its own line in FP-7 with an absolute budget (OD-5(d)); none is co-located with a renderer.
4. **Extension origins.** Extension origins own site keys; an extension renderer is never co-located with a web site (EX-D3), and no reduced mode applies to it.
5. **Reduced isolation.** Below about 2 GB of RAM the browser enters a documented reduced-isolation mode, not silent co-location: the mode is a decision-log entry, the UI exposes it, cross-site frames may share a renderer only within the documented limit, and extension origins are never co-located. Stage 1 ships desktop only; Android is S-8 in Stage 2.

AG-0 is a property of this table: with defaults, the ML service and agent host have count 0, the prompt renderer has count 0 until a prompt exists, and their crates are not linked into any process that does launch (Section 2.3, rule G4). Model files are a watched category: with both grants off, the profile holds none (ML-9, AG-0).

### 2.3 Why this shape

The layering puts the three things that cannot be retrofitted (the substrate, the tree-access traits and the engine/DOM boundary) at the bottom, so every later crate is born under them. G1 and G2 are the oracle rules; G3 is the determinism rule; G4 is the AI-off rule; G6 is the cage rule; G9 is the provenance rule (M-1). Each is mechanical, so it costs nothing per review and fails loudly. The layer set follows HGBA-2 2.3.0's component model: L2s leaf/pure crates and the L2 contracts are shared by everything above them, L2e, L2p, L2t, L2m, L2g and L2d are the standards-implementing layers, L3 is the document model, L3s the service internals, L4 the renderer, L5 the services and L6 the binaries.

## 3. Runtime substrate (B1)

### 3.1 Interfaces

The substrate is a set of synchronous traits plus a task model. Async traits are avoided in public interfaces because `dyn` async traits are not yet stable in a usable form (HGBA-3.1 B3).

```rust
/// Time. Production: OS clocks. Simulation: virtual, advanced only by the scheduler.
pub trait Clock: Send + Sync {
    fn monotonic(&self) -> Instant;      // hg_types::Instant, not std
    fn wall(&self) -> SystemTime;        // for Date.now(), cookies, HTTP dates
}

/// Randomness. Every consumer gets a named, seeded stream so adding a consumer
/// does not perturb existing ones.
pub trait Entropy: Send + Sync {
    fn stream(&self, purpose: EntropyPurpose) -> Box<dyn RngCore + Send>;
    fn crypto(&self) -> &dyn CryptoRng;  // simulation: seeded; production: OS CSPRNG only
}

/// Serial task queues ("sequences", B3). The substrate owns every thread.
pub trait Executor: Send + Sync {
    fn sequence(&self, name: &'static str, priority: Priority) -> SequenceHandle;
    /// `delay` is a floor; `tolerance` is the band the scheduler may use.
    /// Production timers use the band (battery, coalescing); the simulator
    /// records the exact wakeup it chose and charges it to CC/CT and wakeups.
    fn post(&self, seq: &SequenceHandle, task: Task, delay: Option<Duration>, tolerance: Duration);
    fn fork_join(&self) -> &dyn PhasePool;   // Rayon in production, see 3.3
}

/// Address space. One trait set for heaps, arenas and code: production is the OS;
/// the simulator counts committed and touched bytes and faults on overcommit.
/// `MemoryKind` carries the FP 6.2 ledger tag, so every region is charged to its
/// ledger line (process part, per-agent part, canonical-exempt cache) by construction.
pub trait Memory: Send + Sync {
    fn reserve(&self, bytes: usize, kind: MemoryKind) -> Result<Region, MemoryError>;
    fn commit(&self, region: &Region, bytes: usize) -> Result<(), MemoryError>;
    fn decommit(&self, region: &Region, bytes: usize);
    /// Drop the pages but keep the reservation; the ledger records the purge
    /// and the reclaim ladder (FP 6.7) sees the released resident bytes.
    fn purge(&self, region: &Region, bytes: usize);
    fn release(&self, region: Region);
    fn stats(&self) -> MemoryStats;
}

/// Executable memory for the JIT tiers. Writable or executable, never both;
/// every flip is recorded so the simulator can enforce the no-WX invariant and
/// count the flips. Absent in the jitless binary (Option::None).
pub trait CodeMemory: Send + Sync {
    fn map_code(&self, bytes: usize) -> Result<CodeRegion, MemoryError>;
    fn seal(&self, region: &CodeRegion, executable: bool) -> Result<(), MemoryError>;
}

/// Socket requests. The caller never holds a socket: the broker mints one against
/// the partition key, the route policy and the LNA ticket, and the owning network
/// service is the only holder (NW-D4). Wire identifiers come from Entropy::crypto().
pub trait NetTransport: Send + Sync {
    fn request(&self, grant: SocketGrant) -> Result<ConnId, NetError>;
    fn send(&self, conn: ConnId, bytes: Bytes);
    fn on_event(&self, conn: ConnId, sink: SequenceBound<NetEvent>);
}

pub trait Storage: Send + Sync { /* files in the storage service only */ }
pub trait Ipc: Send + Sync { /* Section 4 */ }

pub struct Substrate {
    pub clock: Arc<dyn Clock>, pub entropy: Arc<dyn Entropy>,
    pub exec: Arc<dyn Executor>, pub ipc: Arc<dyn Ipc>,
    pub mem: Arc<dyn Memory>, pub code: Option<Arc<dyn CodeMemory>>,
    pub net: Option<Arc<dyn NetTransport>>, pub storage: Option<Arc<dyn Storage>>,
}
```

DET-2 bounds the cost of this indirection at ≤1%†. If dynamic dispatch misses it, the hot interfaces (`Clock`, `Executor::post`) become generic parameters on the renderer's top-level type, which removes the vtable without changing any call site.

**The task model is the coding standard's CS-D8:** a task runs to completion on its sequence; no crate carries an async runtime or an executor of its own. `Entropy::crypto()` is the OS CSPRNG in every shipping binary and is seeded only under `hg-substrate-sim`, which answers Q-CS-1 at M1 (Section 8.1).

### 3.2 Simulation mode

`hg-substrate-sim` runs the **whole multi-process browser in one OS process**. Each simulated process gets its own substrate instance, and the IPC transport delivers messages through the scheduler. One seeded scheduler picks the next runnable task among all sequences of all simulated processes. Virtual time advances only when no task is runnable, jumping to the next timer. Faults are injected by the scheduler: network resets, slow and reordered bytes, IPC delay, process crash and restart, GPU-device loss (HGBA-2.0 R-2). `hg-netsim` adds protocol-level faults through the recorded stack — DNS failures and slow delegation, TLS alerts (bad certificate, revoked chain, handshake failure), QUIC loss, reordering and migration failure, HTTP/1.1 resets and truncated bodies, and h2/h3 GOAWAY and 421 — so a fault is a scenario in the corpus, not a patch to the stack.

The network side replays a **recorded corpus archive** per NW-D2: one archive per browsing context group, holding every request, response, timing, the decision-point log, the engine build ID, the data versions and the seed. Stage 1 writes its own compact format with a WARC importer, so corpora recorded by other tools can be reused. The simulator charges canonical and touched bytes (CC/CT) and wakeups per simulated process (FP's meters), so every determinism run reports its memory and wakeup envelope with its hashes.

### 3.3 Where determinism comes from in each layer

| Layer | Determinism mechanism | Risk |
|---|---|---|
| Event loop, IPC, timers, network | Seeded scheduler and virtual clock; a timer's tolerance band is part of the record, and the simulator records the exact wakeup it chose | Low; this is the FoundationDB/turmoil model |
| Style, layout, paint, semantic phases | **Phase purity**: workers read immutable inputs and write disjoint outputs, so the pool's interleaving cannot change results. DET-1 compares parallel and sequential hashes. ST-D7 closes the old style-sharing risk: no cache may be inserted into inside a phase whose result depends on the insertion; font installs happen at task boundaries (TX); cache insertions are outside results; session-image identity and manifests are recorded inputs; layout keeps the same rule by type, with one writer per cache slot, `hg-layout-state` written only by the script thread, and stable fragment IDs. Check: ST-5 | Medium only until ST-D7's check passes; any shared mutable cache whose insertion order reaches a result breaks it |
| JS semantics | The engine is Izcal's own (`hg-js-*`). Time, randomness and scheduling enter only through `hg-js-host` hooks over the substrate, so tier choice cannot change an observable result: the virtual clock advances only through the scheduler, and a faster or slower tier sees the same clock | See the next two rows; the hook table is audited at JS-M0 |
| JS: `Math.random`, `Date.now`, `performance.now` | All three are host hooks: `performance.now` and `Date.now` read the substrate clock at the hook boundary, and `Math.random` draws from `Entropy::stream(Random)`. No engine clock exists to fake; the jitless and JIT tiers call the same hooks | Low; the hooks are part of L2e's interface, not a patch |
| JS: GC-observable behavior | `WeakRef`, `FinalizationRegistry` and finalization order are functions of the collector's decisions; `hg-heap` records every scheduling decision as a decision point (JS-D15), and replay drives the collector from that log. GC-stress mode and the heap verifier run in T1 (Section 7.2) | Medium: the decision-point protocol is new; it is measured at JS-M1 (DET-1's GC case), not assumed |
| GPU, audio, media | Canonical rendering is the CPU back end (`hg-raster`), bit-identical on every OS and ISA (GR-D3); display lists are hashed. WebGL and WebGPU pixels are out of scope; video and hardware/OS-decode frames are identified by frame hash, and the software media path is in scope (MD). Audio is out of scope. Vsync is the compositor's `BeginFrame` — a recorded scheduling decision, not a GPU service clock | Accepted; the canonical path is the CPU one, so a GPU difference can never enter a hash |

**The first Stage A experiment** is the engine's decision-point probe (JS-M0): run a corpus page's script 1,000 times under the simulation substrate, with a seeded entropy source and the decision-point log enabled, and compare DOM serialization hashes. It answers HGBA-3.1 Q-3 early, before the substrate is built around a false assumption. M0's V8 result is history (Section 12): V8 needed a fork to become predictable; `hg-js` is built with the hooks from its first commit, so the probe confirms the design rather than retrofitting it. The fields that replace the old worker-task-mode field are the engine build ID, the data versions and the decision-point log (A-S1-20); a recording missing any of them is refused.

**Rust DST libraries** are models, not dependencies: `turmoil` 0.7 is active, `madsim` 0.2 is in maintenance, and `shuttle` 0.9 (randomized concurrency testing) is very active and useful for the substrate's own unit tests. None of them can reach inside the engine; the engine's own hooks (JS-D15) are what make it deterministic, and the simulator drives them.

### 3.4 Production recording

In production the same interfaces can log their inputs, which gives replayable bug reports. Recording is **off by default** and user-initiated per tab, because the log contains page content. Enabling it reloads the tab: recording starts at process launch, in a dedicated, fresh renderer for the browsing context group (the "Reload to record" affordance), so a recording has a launch boundary and never contains pre-recording heap state. Credential-mode input is never recorded (ED-D8, ED-D6). One replay host process serves one recorded session. A recording keeps pre-noise data and the seed, so a D-S1 surface can be re-derived after the fact (OD-6). Replays run in the simulator.

## 4. IPC (B2)

### 4.1 Model

- **IDL.** Interfaces are declared in `.hgidl` files: methods, typed messages, and handle-carrying fields (endpoints, shared-memory regions, files). `hg-ipc-codegen` generates Rust endpoint types, serializers and a Kani harness per message.
- **Endpoints are capabilities.** A `Remote<T>` can only be obtained by being sent one. Renderers start with exactly one endpoint, to the browser process, and receive the rest from the broker.
- **Sequence affinity.** An endpoint is bound to one sequence. Messages are delivered as tasks on it, so the event loop and IPC share one ordering model and the simulator controls both.
- **Synchronous calls** are an explicit IDL attribute with an allowlist reviewed by the security owner. Stage 1's allowlist holds `localStorage` reads and sync XHR only. `document.cookie` is not on it: the network spec makes cookie access asynchronous by design, and NW-2's ordering cases are the evidence that removing it is safe (A-S1-32). Everything else is async.
- **Network IPC.** No socket handle is ever sent to a renderer; a renderer asks the broker for a connection, which mints it against the partition key, the route policy and the LNA ticket (NW-D4). The networking spec's IPC-R1–R17 constraints hold by construction: capability endpoints, no ambient handles, and every bulk buffer is a read-only shared region owned by the service that filled it.
- **Device IPC (I-2 note, 21 October 2026).** The device-access service is a broker-side service, not a new I-2 exception: no renderer, content GPU, media, network or device session opens a device; only the arbiter calls the OS device backends, and the session and enumeration configurations hold no OS handle. Device messages are typed, bounded and accounted; `DeviceHandle` is an IPC handle kind, and no file descriptor crosses the browser IPC schema (security scope 6.6; the one Android consent handoff, if Q-DV-17 requires it, is a broker-owned OS surface). The MD-D10 video-only exception is unchanged and is not extended.
- **Serialization (VER-1).** A fixed, little-endian, length-prefixed wire format with no self-describing schema, so the generated parser is small and provable. Every message type gets a generated Kani harness in CI. EverParse-class proofs are a Stage A stretch goal for renderer-to-broker messages.
- **Bulk data** crosses as read-only shared memory, never as large messages.

### 4.2 Transports

| Backend | Mechanism | Status |
|---|---|---|
| OS, Linux | Unix domain sockets plus `SCM_RIGHTS`, `memfd` shared memory | Build |
| OS, macOS | Mach ports (send rights carry capabilities), `mach_vm` shared memory | Build |
| OS, Windows | Named pipes plus `DuplicateHandle` brokered by the browser process | Build |
| Simulation | In-memory queues delivered by the seeded scheduler | Build (`hg-substrate-sim`) |

**Why build.** No standalone Rust library passes arbitrary capability handles between processes. Servo's `ipc-channel` 0.23 passes its own channels and shared memory across processes on all three OSes but not arbitrary handles. Cap'n Proto RPC cannot pass file descriptors yet, `interprocess` 2.x dropped descriptor passing, and Fuchsia's FIDL bindings are not published. The three OS backends are **written from OS documentation**: unix(7) and `SCM_RIGHTS` plus `memfd_create` on Linux; Mach ports and XPC on macOS; Win32 `DuplicateHandle` with named pipes or ALPC on Windows. `ipc-channel` is not a source (D-S10). The backends are a few thousand lines each and sit on the Tier 1 verification list. The design (capability endpoints, sequence affinity, fixed wire format) is derived from I-2, B2 and VER-1 (Section 4.1), not from another engine's IPC system.

### 4.3 Navigation (`hg-navigation`), built on this transport

`hg-navigation` runs in the browser process. Its model is derived from the HTML specification, not from another engine: **navigables** and traversable navigables (the frame tree), **session history** (session history entries and the traversal algorithms), and the **navigate**, history-traversal and reload algorithms, each function carrying its spec anchors (G9). Two responsibilities no specification defines are derived from HGBA-2 requirements: **site-instance assignment** and process locking (HGBA-2.0 I-1, keyed by (site, container), Section 1), and process launch and crash recovery (R-2). HGBA-3.0's "constellation" (Servo's term) named these responsibilities; the term survives only in that history. The state machines are written as pure functions over IPC events, so the simulator can drive them and property tests can check them, both against the spec algorithms' invariants (for example: a traversal never activates an entry outside the traversable's session history) and against I-1 (no frame is ever committed into a process locked to another site). The broker also runs `hg-agents` (agent principal, origin sets, tool registry) and `hg-input-route` (CON-R3: input is routed by the broker, never initiated by a renderer); recorded sessions navigate only in dedicated, fresh renderers (Section 3.4).

## 5. Renderer pipeline

### 5.1 Script thread and event loop (B3)

One script thread per renderer runs one sequence per agent cluster. It implements the HTML event loop: task sources, microtask checkpoints, and the "update the rendering" steps. The engine hands microtasks to the host at exactly the points the HTML specification names (JS-D15's host hooks, A-S1-34); the host, not the engine, decides when a checkpoint runs. Workers are script agents on their own threads, each with its own heap realm and its own sequence; ports marshal structured clones through `hg-messaging`. Frame timing comes from the compositor's `BeginFrame` message (Section 5.7), which in simulation is just another scheduled decision.

### 5.2 The one-copy DOM in `hg-node-store`

The DOM has one representation. `hg-dom`'s node data lives in `hg-node-store`'s columns outside the JS heap; `hg-heap` holds the JS objects, and a wrapper holds a node handle, never a tree node. There are no `cppgc` objects, no prefinalizers and no second copy of the tree (JS-D4, A-S1-35).

| Part | Design |
|---|---|
| Node header | `NodeId` (32-bit slot plus 32-bit epoch), parent, first child, last child, previous and next sibling as `NodeId` columns, node type and flags. The columns live in `hg-node-store`; the script thread owns writes, and style, layout, paint and the semantic plane read them through `hg-tree-traits` |
| Wrapper | A `hg-bindings`-generated wrapper is created lazily on first script access and holds a checked `NodeHandle` (slot plus epoch). Node→wrapper is a weak slot; the collector traces handles, not tree pointers |
| Payload | Attributes are an attribute-set ID (interned, copy-on-write); text lives in the text arena; per-type state lives in `hg-dom`'s side tables keyed by `NodeId`. No Rust field sits inside a GC object |
| Strings | Izcal's atom table in `hg-node-store`, generated at build time from the HTML named character references and the specification's tag and attribute lists; no `markup5ever` |
| Release | **Release-by-ID**: when the collector finds a node unreachable, it enqueues `(NodeId, epoch)`; the DOM releases the payload and the semantic entry at the next safepoint. A stale ID is detected by its epoch, never aliased onto a new node |
| Write barriers | Generated setters write through `StoreWriter<TracedBarrier>`; the barrier keeps `NodeHandle`s visible to the collector. The heap verifier in T1 checks the barrier, because there is no debug-engine configuration to catch a missing one |
| Slot reuse | Generational IDs, as above; a property test checks that a stale handle held by the semantic plane or an agent is rejected |

### 5.3 WebIDL bindings

`hg-webidl` parses and resolves the WebIDL from the specifications (pinned via the WPT `interfaces/` directory, which mirrors the spec IDL), and `hg-webidl-codegen` targets `hg-js-host`, not an engine's template API. For each interface it emits a **shape family** and an **inline-cache generator** (`.hgop`) that the engine compiles into its own inline caches, plus attribute accessors and operations, type conversions, overload resolution, `[CEReactions]`, `[SameObject]`, exceptions and the wrapper creation path (A-S1-36). The front end (parser and resolved IDL model) is engine-agnostic, as HGBA-2.0 D2 requires. The parser is Izcal's own, written from the WebIDL specification (D-S10, M-1); `webidl2.js`, the W3C-maintained parser that WPT's idlharness uses, runs in CI as a black-box differential oracle on the parsed model for every pinned IDL file, and a disagreement is triaged against the specification. `weedle` is not a dependency: owning the resolver is required for the overlay checks in any case (DOM spec 6.x). `hg-webidl-codegen` is **not modelled on any engine's binding generator**: what it emits is derived from the WebIDL specification's algorithms, and the generator's own code carries their spec anchors (G9). The generated code is the largest single body of Stage 1 code, and **it is generated, not translated**, so its oracle is WPT `webidl/` plus `idlharness.js` tests for every interface, which exist before any interface is generated (ORC-1).

**Anchors on generated code (G9).** The generator emits a `// spec:` anchor on every generated binding item, naming the IDL source URL and the interface or member it binds, so `hg-anchor` maps each binding to its specification and its WPT tests. Hand-written algorithm code behind a binding (the operation's steps) carries its own anchors; such code without an anchor is rejected in T0.

**The fast-call rule retires (A-S1-36).** It existed because V8's fast API passed raw pointers across a C++ boundary under the sandbox. `hg-js-host` passes handles, so there are no raw pointers to forbid. The generator keeps its golden-file test on a fixed sample IDL and its full-coverage check over the pinned interface set, as generator-regression checks rather than safety rules.

### 5.4 Data plane and mutation log (B4)

```rust
pub enum Mutation {
    Insert { node: NodeId, parent: NodeId, before: Option<NodeId> },
    Remove { node: NodeId, old_parent: NodeId },
    SetAttr { node: NodeId, set: AttrSetId, old: Option<AttrSetId> },
    SetState { node: NodeId, old: ElementState, new: ElementState },
    SetNeighbours { node: NodeId, old: [Option<NodeId>; 2] },
    SetTextEmptiness { node: NodeId, old: bool, new: bool },
    SetSheet { node: NodeId, old: Option<SheetId>, new: Option<SheetId> },
    Environment { snapshot: EnvSnapshotId },
}
```

The mutation log is the DOM's write-ahead record: every write goes through `hg-dom`, which appends one entry and applies it to the node store. Entries carry, by ID, exactly the values that change what style must re-evaluate: attribute-set pairs, element state, the neighbour slots a selector can read, text emptiness, the element's sheet, and the environment snapshot (viewport, media, preferences, font metrics). Style's invalidation builds its snapshots from the log, without a second bookkeeping path; the log never holds a copy of the tree (A-S1-38).

Flush runs at the start of every style and layout pass and on every forced synchronous flush (HGBA-2.0 F1 contract, unchanged). `hg-projection` independently replays the log into its own tree for the equality oracle (G2).

### 5.5 Style

`hg-style` runs the pipeline the style specification defines (ST 6.6–6.12). `hg-css-syntax` tokenises and parses stylesheets into the rule index; `hg-css-props` (generated from the property database) gives typed declarations; `hg-selectors` compiles selector lists into a matching automaton and, at the same time, into the invalidation sets that `hg-style` uses to decide which elements a change can restyle — the mutation log's `SetAttr`, `SetState`, `SetNeighbours`, `SetTextEmptiness` and `SetSheet` entries map directly onto those sets. `hg-style` owns the cascade, the substitution interpreter for variables and `env()`, style groups and arenas, the style columns, the traversal (parallel over independent groups, phase-pure), container re-entry, the environment snapshot and the cascade trace. It reads the DOM only through `hg-tree-traits` (G1). Stylesheets, CSSOM and inline style blocks are `hg-cssom`'s data, derived from the CSSOM specification.

**Dependency rule (stated once; Sections 5.6, 5.7, 6 and 13.2 refer back to it).** Every engine component is Izcal's own — `hg-style` replaces the old "Stylo adapter" — so no style, selector, layout, text, graphics or accessibility library is a dependency. Generic MIT crates are used unmodified through their crate APIs; a fix to a generic crate goes upstream, never into an Izcal copy (M-1, D-S10). The old rule that named Stylo, `selectors`, WebRender, Brave's `adblock` and Mozilla's `neqo` is retired with the dependencies themselves.

**Oracle.** `hg-style-reference` runs a second, deliberately slow implementation of matching and the cascade over the same inputs and the same specifications; every WPT style test and every corpus page compares the two, and every disagreement is triaged against the cited specification section. `hg-html-syntax` and `hg-css-syntax` are the only parsers of web syntax (G23), and `hg-cb-format`'s reader is the only parser of the content-blocking subset `hg-style` consumes (G24).

| Block, flex, grid, floats | `hg-layout`'s own formatting contexts, written from CSS 2, Flexbox and Grid; boxes in the layout arena; floats inside block formatting | **Primary:** the specifications plus WPT `css/`. **Secondary:** the LY reference implementation (`hg-layout-reference`) and black-box reference-engine differential (Chrome, Firefox, Servo), every disagreement triaged against the cited spec section |
| Inline and text | `hg-text` (TX-M1) shapes runs, breaks lines and resolves bidi; `hg-layout` integrates the inline formatting context around it | **Primary:** CSS 2 inline formatting, CSS Inline, CSS Text plus WPT; `hg-text-oracle` (TX) for the text half. **Secondary:** reference-engine differential, triaged against the spec |
| Tables, fragmentation, writing modes, the long tail | **Built in `hg-layout`** from the CSS 2, CSS Table, CSS Fragmentation and CSS Writing Modes specifications, ordered by WPT and corpus usage; tables first; from-scratch path first, incremental path later | **Primary:** the specifications plus WPT and `hg-layout-reference`. **Secondary:** reference-engine differential, triaged. No lockstep oracle exists for these; EQ-1 reports them in the spec class |

The contract is `layout(box, constraint space, break token) -> (fragment, break token)`. The constraint space carries what CSS Sizing defines as a box's input (available inline and block size, percentage resolution sizes, definiteness) and what CSS Fragmentation defines as fragmentainer state; a fragment is CSS Fragmentation's box fragment. Fragments are immutable and cached by constraint space, so layout is a pure function of its input, which DET-1 and the from-scratch reference check need (LY-D3). Fragment identity is the id-free canonical tree, and handles carry an epoch, so a fragment id never enters a hash. `hg-layout-state` and `hg-scroll` are written only by the script thread in Stage 1 (A-S1-24); `hg-fragment` and `hg-hit` are layout's outputs. Blink's published LayoutNG design is cited only as evidence that the pure-function shape scales.

**Units.** Geometry is fixed point: 1/64 px with saturating conversions, and one rounding function in `hg-layout-num`; no crate converts on its own (LY-D6). Geometry types are `hg-types`'.

**No third-party layout.** HGBA-2 2.3.0 removed Taffy, Parley and Servo layout as components, and this design has no layout driver over another engine's tree. The table, fragmentation and writing-mode long tail is still new code on the Stage 1 critical path; its oracle is now the specifications, WPT and LY's own reference implementation, with reference engines black-box only (D-S10). Stage 1 implements caching and from-scratch layout only. The Spineless ordered dirty queue, durability tiers and demand-driven forced flush are Stage B (INC-1, INC-2, INC-4, FLUSH-1), added behind a switch and checked against from-scratch output on every frame in CI; LY-M2, which delivers them, is on the critical path (Section 8.2).

### 5.7 Paint and pixel-optional rendering

`hg-paint` consumes `hg-fragment` and `hg-scroll`, never the DOM. It computes stacking contexts and ink overflow, snaps to the device pixel grid, and emits property trees (transform, clip, effect, scroll) and paint chunks in the graphics specification's display-list format. Chunk order is `hg-hit`'s walk, so hit testing and painting share one order; paint owns stacking, ink and snapping (GR-D1). The order and grouping are derived from the specifications: CSS 2 Appendix E painting order and stacking contexts, CSS Transforms (transform and 3D rendering contexts), CSS Masking (clip), Compositing and Blending plus Filter Effects (effect), and CSS Overflow for scroll containers. Separating the four trees is a first-principles choice: a change to one (a scroll offset, say) skips repaint, and chunks bound the display-list diff. Blink's published property-tree design is cited only as evidence that the split works.

**GPU processes, one stack.** The compositor GPU service validates the display list, aggregates surfaces, schedules `BeginFrame` and presents. Content GPU processes, one per visible renderer key, generate chunks — with `hg-raster`'s CPU back end or its GPU back end. The **canonical** rendering path is the CPU back end, and it is bit-identical on every OS and ISA (GR-D3); the GPU back end is a performance path checked by reftests, never by a canonical hash. There is no WebRender, no wgpu and no "two GPU stacks" (the old plan is retired; Section 12): `hg-gpu-hal` selects Metal, Vulkan, D3D12 or OpenGL per OS for the GPU back end, and WebGL and WebGPU are host-side implementations on the same HAL. Pixel-optional mode (B7) stops after chunk generation, which keeps the display-list hash available to DST while skipping raster and compositing; it applies only to agent tabs (AI switch on) and background tabs the shell marks as unobserved. A content GPU process starts device-less (≤ 2 MiB†), takes a device only when a GPU-backed surface needs one (≤ 12 MiB†), closes the device after 30 s† hidden and exits, per OD-5; the compositor's `BeginFrame` is the only vsync source in the system.

### 5.8 Semantic plane

`hg-semantic` builds the semantic tree from `hg-tree-traits`, computed style and `hg-fragment`, with stable IDs taken from node IDs and epochs. It produces the semantic model (`hg-semantic-model`) and the platform mappings (`hg-ax-mappings`); AX-D3 defines this renderer-side plane as the computed tree, AX-D4 the broker-side mirror (`hg-ax-mirror`, one per renderer key), and AX-D9 the UI host where a platform requires a UI thread (Windows). The roles and names follow the Core-AAM, HTML-AAM and accname specifications, with spec anchors (G9). Text facts come from `hg-text`: per-character bounds, word boundaries and the glyph-to-character map (A-S1-44); line records, `reading-flow` and `content-visibility` come from layout (A-S1-45). Platform APIs are reached through the `hg-ax-*` adapters — UIA and IA2 on Windows, NSAccessibility on macOS, AT-SPI on Linux, Android later — each a thin mapping over the model. There is no AccessKit: the accessibility specification owns the model and the adapters (AX-D3, AX-D9). Agent extras (provenance export, visibility flags, diffs for agents) are compiled only with feature `ai` (G4).

**Repair overlay (HGBA-3.1.1 B8 and B10).** Accessibility repairs live in `hg-semantic-repair`, a sparse map over the author tree keyed by stable node ID, isolated by crate rule G8. It is computed only when assistive technology is active and a repair class is enabled. Forced colors and contrast (R0) are style-system behavior and do not belong to this crate. R1 (AT-only language hint) is on; R2 (heuristic names) is opt-in; R3 is user-invoked per site; R4 (model-based) sits behind the accessibility-model setting and runs in the ML service. Each entry records class, rule, source nodes and provenance, and its sources must share the repaired node's origin and frame. `hg-ax-mirror` receives the author tree with overlay values applied; agents receive the author tree, with any repaired value tagged `repaired`. The reference-engine differential and WPT accessibility-mapping tests run on the author tree only. A "What the browser changed on this page" inspector lists every repair, and one toggle reverts them all.

## 7. Build and test infrastructure

### 7.1 Build

- One Cargo workspace, pinned Rust toolchain, `cargo-vet`/`cargo-deny` for supply chain, vendored generic dependencies for release builds.
- **Nothing is built from another browser's source.** The engine, DOM, style, layout, text, graphics, media, PDF and accessibility components are workspace crates (Section 2.1). The generated inputs are data and code produced by Izcal's own tools from pinned specifications and published data: `hg-css-props`, `hg-webidl-codegen`, `hg-ipc-codegen`, `hg-scriptgen`, `hg-fontgen`, `hg-unicode-build`, `hg-phish-compile`, `hg-list-build`. Every generator runs in CI and its output is compared byte for byte with the workspace copy, so a stale generated file fails T0. The old M0 V8 build facts (V8 build farm, archive sizes, `RUSTY_V8_MIRROR`) are retired with the dependency (Section 12).
- **Pinning.** Every downloaded artifact — a WPT revision, a test262 revision, a UCD release, a specification snapshot — is hash- and version-pinned: `specs.lock` records repository commit SHAs and `downloads.lock` the hashes (A-S1-56). A download without a pin fails the build.
- **No remote build cache in release or DST builds.** `sccache` and equivalents are not used where an artifact's bits are a claim: a cache can return a different artifact than the inputs, which would make a determinism claim unverifiable (A-S1-56). Developer builds may cache locally; CI rebuilds release, checked and DST profiles from clean inputs.
- **Profiles.** `release` ships; `checked` enables overflow checks and debug assertions and is the T0/T1 profile; `dst` is the deterministic build, which aborts on any overflow, assertion or allocation failure; `debug` is for developers. Shipping and DST builds abort on integer overflow; clippy runs on all three OSes in T0 (A-S1-59).
- **Executable memory.** Only the JIT's generated code is executable, and only through `CodeMemory` (Section 3.1); the jitless binary has no executable-memory producer at all.

**Triage rule.** A mismatch between Izcal and any engine is resolved against the specification, never against an engine's output or code. If the spec is silent, ambiguous or contradicted by the deployed web, the behavior follows documented interoperability evidence (WPT results across engines, Interop and web-compat data), is logged as a compat decision, and is filed upstream as a specification issue.

**Black-box observation log.** `compat/observations/` records each consulted engine behavior as a test case plus each engine's observed result, with the resulting decision and the spec section it concerns. It never links to another engine's source. Tolerance rules, compat decisions and the on-disk formats behind the importers (Section 13.2) all cite entries in this log.

### 7.4 DST farm

`hg-dst` runs seeds in parallel across machines. Each failure is minimized (shrinking the seed's fault schedule and input archive), deduplicated by crash signature, and filed with a one-line replay command. DST-1 compares its unique-bug yield per CPU-hour against coverage-guided fuzzing on the same surfaces, so both farms log CPU-hours and bug IDs in one database.

### 7.5 Fuzzing

- **Bindings and DOM:** a project-owned grammar fuzzer in the Domato style (Domato itself has been dormant since November 2024), run through the renderer in simulation mode so every crash is a replayable seed.
- **JS engine and embedding:** Fuzzilli works with any target that speaks its REPRL protocol and is built with sanitizer coverage. The renderer gets a REPRL mode, so Fuzzilli fuzzes the engine *through* `hg-js-host`, which is where the project's own bugs live (A-S1-52).
- **Parsers and IPC:** `cargo-fuzz` targets for every IPC message type, URL, image, font, media container, PDF and SVG parser (Tier 1 surfaces), registered with OSS-Fuzz; `hg-font-fuzz` covers every `.hgfont` table, `hg-parse-fuzz` every Unicode algorithm it can generate inputs for, and `hg-edit-fuzz` and the PDF and SVG corpora feed the same farm (A-S1-54).
- **Adversarial peers and protocols:** `hg-netsim`-driven campaigns against HTTP/2 and HTTP/3, TLS and certificate verification, DNS, WebRTC (`hg-ice`, `hg-dtls`, `hg-srtp`, `hg-sctp`), and the display-list and GPU message parsers; each campaign has a replayable seed and a named triage owner (A-S1-57).

### 7.6 Performance lab

Reference device classes **DC-16, DC-8, DC-4 and DC-2** (FP 8.4); Stage 1's lab holds one machine per class. The corpus is recorded archives (Section 3.2) of a published site list plus Speedometer 3, JetStream and MotionMark. Every merge to main gets an A/B run on one device; nightly runs all classes. Metrics: p95 interaction latency, frame time, style and layout time (P-1), memory as charged and touched time series (CC/CT, INC-3, S-3), energy (X-4), and FP-S30's composite score (A-S1-55).

### 7.7 Security and upstream pipeline

| Upstream | Owner | Pin | Lag metric | Fork trigger |
|---|---|---|---|---|
| Generic crates (`smallvec`, `bitflags`, `hashbrown`, `memmap2`, `libloading`, the acknowledged RustCrypto crates) | Supply-chain owner | Exact, vendored | Days behind a published security advisory | **None**: a fix escalates upstream, or the crate is replaced by an Izcal-written one from its specification. A project fork needs an owner decision, because a maintained copy of a generic crate is a liability, not a plan |
| Specification and test snapshots (WPT, test262, UCD, specification repositories) | Spec-pin owner | Commit SHA in `specs.lock` | Per release | Not a fork: a snapshot is data, and `downloads.lock` holds its hash |
| Test-only models (`turmoil`, `madsim`, `shuttle`) | Substrate owner | Exact | Optional | None; they never ship |

There is no engine upstream and no engine fork. Every browser component is Izcal's own, so the V8/`rusty_v8`, Stylo/`selectors`, WebRender/wgpu and Taffy/Parley/html5ever rows are retired with the dependencies (Section 12), and the V8 update bot with them. The **snapshot-drift bot** remains: it moves `specs.lock` and the WPT pin together and opens `hg-anchor`'s drift PR, which lists the anchors whose pinned section text changed; T0 to T1 must pass, and the coverage report must not fall (ANC-1). The extension host is Izcal's own component host (JS-D10), not a third-party runtime, so it has no upstream row.

### 7.8 Release engineering

Nightly, Beta and Release channels. Nightly carries the sampled projection-equality check (HGBA-3.1 B4) and reports mismatches as crashes. Symbol server and crash reporting follow D-S4 (opt-out minidumps with a per-crash prompt). Every release is built from a pinned clean input set with **build attestations** (provenance and SBOM) and published as an **immutable release**; artifacts and metadata are append-only. Updates are verified through the **TUF roles** (root, targets, snapshot, timestamp) by the updater process (Section 1), with offline root keys, an online targets key and a documented rotation; **update drills** replay a bad update, a lost timestamp key and a rollback before each release (A-S1-58).

## 11. Decisions for the project owner (signed off 14 October 2026; open conflicts in 11.1)

| ID | Question | Decision | Change from the proposed default, and why |
|---|---|---|---|
| D-S1 | Anti-fingerprinting model | **Hybrid, with one output-transform rule (OD-6)**: noise is applied once, only where a non-canonical output leaves for a readable surface — WebGL and WebGPU pixels, audio from OS tolerance decoders, and video from OS decoders that do not pass MD-42 on that device. Nothing else is noised: 2D canvas, export (`toBlob`, `toDataURL`, `convertToBlob`), `measureText`, Izcal-rendered audio, and Izcal-decoded images and video are canonical by construction. Discrete surfaces are normalised by construction, including scrollbar and form-control geometry (LY-D11); per-script uniformity is built and enabled only under CB-D3's two measurements; full uniformity (RFP-style) remains a user opt-in | **Changed** from uniformity, and **revised on 21 October 2026** (C-1) from "seeded noise on readback surfaces". The readback list was too broad — it noised canvas export and `measureText`, which are canonical outputs and measurable compatibility risks — and too narrow, because OS decoders are the real non-canonical source for audio and video. The one rule is OD-6: noise follows the output, not the API name. Noise still draws from `Entropy` seeded by (site, container, session), so DET-1 replays it, and recordings keep pre-noise data (OD-7). RFP-style uniformity breaks fonts, canvas, WebGL, timezones and colour profiles on real sites, which collides with P2; effectiveness is PRIV-2's distinguishability, not an asserted entropy estimate |

### 13.1 Owner decisions (D-S7, D-S9, D-S10, D-S11 and D-S12 decided, D-S8 deferred)

**Excluded regardless of D-S7 (14 October 2026):** HGBA never ships an unlicensed or reimplemented DRM module (for example OpenWV) or extracted device credentials. Using a device identity the project is not licensed to hold is circumvention of a technical protection measure (17 U.S.C. §1201; InfoSoc Directive Article 6), breaches streaming services' terms, fails whenever the identity is revoked, and would end any prospect of a Widevine or PlayReady agreement. The only DRM paths are licensed modules: Widevine with Google's approval, or the PlayReady module that ships with Windows, where each streaming service's allow-list is the gate. A project-generated key pair or certificate authority is lawful but cannot obtain licenses from Widevine or PlayReady servers, which accept only identities that chain to the DRM vendor's root; presenting a self-made identity as a vendor-provisioned one would be circumvention.

### 13.1a DRM strategy (D-S7)

**Goal:** a user can play content they pay for, and no single licensor can take that away. **Constraint:** licensed components only (the exclusion above).

1. **Protected media mode (Windows and macOS, primary).** When a page actually starts encrypted playback with a key system HGBA's engine lacks (an `encrypted` event on a media element, or `MediaKeys` created and a license request generated), the tab switches automatically into the protected-media host. That host runs the page in the operating system's licensed engine: **WebView2** on Windows, with Widevine and PlayReady under Microsoft's license; **WKWebView** on macOS, with FairPlay under Apple's license. The precedent is Edge's IE mode. Rules:
   - A bare `requestMediaKeySystemAccess` capability probe never triggers a switch, because fingerprinting scripts call it routinely. Cross-origin iframes cannot switch the top-level page.
   - The tab is labelled ("Playing protected video using Windows' media engine" or "macOS's media engine"), offers one-click switch-back, and remembers the site per container. A per-site "never switch" override exists.
   - Storage is per (site, container): a WebView2 user-data folder or a `WKWebsiteDataStore` per identifier.
   - HGBA protections apply where the host allows: content blocking through `hg-cb-export`'s Safari content-blocker JSON subset on WKWebView (`WKContentRuleList`) or WebView2's request interception routed to a partition service (A-S1-87), and permissions through host callbacks. Anti-fingerprinting, the semantic plane and agent features do not apply, and the label says so.
   - The user agent is the host engine's own (Edge or WebKit), which is truthful because that engine renders the page; an application-name suffix may identify HGBA. Agent tabs (B9) never use protected media mode.
   - Spikes DRM-1 (Windows) and DRM-2 (macOS) in `m0/drm-spike/` verify playback, resolution and container isolation per service before this is built into the shell.
   - **Status (14 October 2026):** both spikes are built, and their probe pages were run. The probe page queries which DRM systems each system web engine supports, without starting playback. **WebView2** (Windows 11) supports Widevine at the software security level, PlayReady including the hardware level, and Clear Key. **WKWebView** (macOS 15.6) supports FairPlay and Clear Key. Per-container storage and content blocking work on both. A capability-only probe correctly did not trigger a switch. **The signed-in playback tests are deferred by the owner**, so per-service playback and resolution remain unverified.
2. **Native PlayReady in HGBA's engine (Windows, M7).** EME against the PlayReady module Windows ships, through Media Foundation. The implementation is written from the W3C Encrypted Media Extensions specification and Microsoft's Media Foundation documentation (its Content Decryption Module and protected media path APIs); Firefox 132 shipping the same route is the precedent that it works. Where a streaming service allow-lists HGBA, playback stays in HGBA's engine with every protection; protected media mode remains the fallback. MD-D32's key-system policy applies — the engine never claims a key system it cannot play, and the shell shows the protected-playback affordance — and MD-M2's PlayReady exit depends on spike MD-S5 (A-S1-86).
3. **Licensing track (from M0, no cost):** a Widevine license request to Google; a castlabs third-party-licensee quote (the only Linux route); a PlayReady terms enquiry to Microsoft; allow-listing requests to streaming services' partner teams, Netflix first.
4. **Linux:** no route avoids Google today. Linux ships Clear Key only, and onboarding says so plainly, until the licensing track succeeds.
5. **Regulatory track (deferred by the owner).** Recorded for later: an EU DMA Article 6(7) interoperability complaint (Android's DRM as an operating-system feature Google must offer on equal terms); a submission to the UK CMA under Google's mobile-platform Strategic Market Status, which covers browser engines; a coalition of affected browsers. No complaint about Widevine access has been filed with any regulator (research, 14 October 2026), so these are untested.

**Why it is permanent:** the Windows and macOS paths depend on components their owners already license to every user of their operating system, not on an agreement HGBA must win. The licensing track improves quality (native playback, Linux), and the regulatory track addresses the root cause; neither is on the critical path for Windows and macOS users.

### 13.3 Resource targets (Stage 1, from the resource footprint spec)

RES-1 to RES-5 are **retired (21 October 2026; A-S1-61)**. The resource footprint spec's §8.4 replaces them, and its thresholds are **absolute**, set from first principles and marked † there; comparisons with Chrome, Firefox and Safari stay published information, never the gate. Stage 1 gates **every** target of that spec at FP-M6 (M8), met or waived in the decision log with the failed gate and its evidence, and the ones this table used to carry, alongside FP-1 (small baseline), FP-7 (isolation is nearly free; scope per OD-2 and OD-5: renderer isolation only, with network services and per-key service processes on their own published lines), FP-28 (blocking is a lever, not a cost) and FP-S30/FP-6 (many tabs, every process counted), are mapped below. **FP-7's corpus limit remains open until FP-M3 measures it:** FP-S30 is projected to break at 15 frames per iframe-heavy page even without graphics (RN2 Section 3), and no owner decision changes FP-7's scope before that measurement (C-3).
