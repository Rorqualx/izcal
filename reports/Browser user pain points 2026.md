# Sorting Browser Pain Points Engines Can Fix

*Fact-check and engineering mapping for HGBA-3.0. Evidence cut-off: 14 October 2026. This report was written against the HGBA-3.0 direction document as frozen at 3.0.5 (revision then current: 3.1.4; HGBA-3 is now 3.3.3), uses it for context only and does not change it.*

Of the 31 claims in the pasted October 2026 list, **13 hold up as stated, 12 are partly correct, 1 is wrong and 5 cannot be verified**. The wrong one is "up to 90% find autoplay with sound irritating": surveys put it at 49–71%. The 13 that hold include the WebAIM Million 2026 figures, Chrome's 4GB Gemini Nano download, the notification rate limits, the compatibility version numbers and the existence of 100+ malicious extensions. The partly correct claims mostly fail on attribution or framing. The "53% abandon after 3 seconds" figure is a modeled 2016 Google estimate. The "55% set cookies after Reject" audit actually tested the Global Privacy Control signal, not a Reject click. The "32-second CAPTCHA" comes from Cloudflare, not Stanford. Edge never had Compatibility View; that was Internet Explorer 11. Three of the most-quoted statistics come from parties with a commercial interest: the burnout and tab figures (Shift, a browser vendor), the Windows 11 default-browser survey (the Browser Choice Alliance, whose members include Google) and the travel error rates (Contentsquare's own customer data). For HGBA-3.0, the verified pain points split three ways. A few are things an engine can fix: fingerprinting surface, autoplay, notification-prompt gating, content blocking that does not depend on extension APIs, scheduling and bfcache. More are browser-shell policy: defaults for cookies, GPC and AI, tab discarding, and extension review. Most of the rest belong to sites (accessibility errors, consent violations, scrolljacking, login walls), OS vendors (default-browser resets, passkey providers, device attestation) or regulators (DMA, AB 566, the EAA). Strong measured evidence of effect exists only for notification-prompt gating and for some performance levers. HGBA-3.0's decision to keep AI off by default is the decision the 2026 evidence supports most directly. Its accessibility plane, however, runs into B10: AI-based repair needs a model, and B10 forbids one by default.

## Only three pain points have a measured browser-side fix

The main finding of the mapping is uneven evidence. Browsers have shipped mitigations for almost every verified pain point, but measured effects exist for only a few: notification gating, performance interventions and tab memory. The rest are shipped features with no published outcome data, so for those HGBA-3.0 would be relying on the design rationale alone.

### Who can fix each verified pain point

| Pain point | Layer that can fix it | Existing implementations and measured effect | Evidence of effect |
|---|---|---|---|

| Site API and JS errors (3) | **Site** | None at the browser layer | None; the browser's only job is not to cause them |

### What HGBA-3.0 should build, and where it should live

The engine-versus-shell split matters for HGBA-3.0 because the direction document is almost entirely about the engine. The shell's policies are not specified, yet that is where most user-visible pain points are decided. The table below assigns each candidate feature to a layer and notes where it collides with an existing HGBA principle.

| Candidate feature | Engine or shell | Pain points addressed | Evidence of effect | Interaction with HGBA-3.0 |
|---|---|---|---|---|
| Built-in content blocking, independent of extension APIs | **Engine** hook in the network and style pipeline (request blocking, cosmetic filtering); **shell** owns lists and defaults | 1, 6, 7, and partly 11 | Memory cost is known (Brave); blocking rate vs uBO is not | Fits HGBA's reuse-first stance: a Rust ad-block engine already exists in production. Cosmetic filtering touches style, so it needs a WPT-neutral design under P2 |
| Default-on anti-fingerprinting | **Engine**: Canvas, audio, font and hardware values come from engine code | 6 | Vendor-reported only (Safari, Firefox) | B1's injectable randomness makes seeded per-site noise replayable, so it is compatible with P3 (inference). B10 already applies anti-fingerprinting logic by keeping AI APIs "inert, not missing" |
| GPC on by default | **Shell** policy (the header is trivial in the engine) | 4 | 55% of sites ignore it today | AB 566 requires a setting from 2027, not a default; default-on is a product choice that costs nothing in compatibility |
| User-gesture requirement for notification prompts | **Engine**: transient user activation is engine state; **shell** for quiet UI and auto-revocation | 14 | **Strong** (Firefox, Chrome) | Low risk. Chrome's FCM rate limit is a push-server lever; HGBA gets it only by operating or choosing a push service |
| Block audible autoplay | **Engine** media policy | 11 | One 2018 vendor figure | Universal across browsers, so it carries no compatibility risk |
| Reduced-motion and scroll overrides | **Engine** (force `prefers-reduced-motion`, restore native scrolling); **shell** per-site toggle | 10 | **None** | Overriding script-driven scrolling breaks pages, so under P2 it must be a user-invoked, per-site override, never a default |
| Tab discarding and freezing | **Engine** (freeze and discard primitives, background timer throttling); **shell** thresholds | 9, 1 | Memory savings measured; burnout effects not | B1's virtual clock makes timer throttling testable in simulation |
| AI off by default, no silent model downloads | **Shell** policy enforced by engine process structure | 15, 16 | Not applicable; it is a policy | Already B10/D13/AG-0; see next section |
| Accessibility repair with user review | **Engine** (B8 semantic plane annotations); **shell** for UI and consent | 19, 20 | Weak: good on photos, poor on charts; LLM code repair near zero | Collides with B10 if repair uses a model; see next section |
| Native cookie-notice handling | **Shell** with maintained lists | 4, 5, partly 12 | **None**; Firefox withdrew its curated version | Lower priority than GPC plus third-party cookie blocking |

Layers outside HGBA's reach constrain several of these. Default-browser resets and choice screens are OS-vendor and regulator territory. A new browser is a beneficiary of those rules, not a fixer, and should use only OS-sanctioned default APIs. Private Access Tokens depend on Apple attestation, which a third-party engine cannot issue. Passkey autofill depends on platform credential providers. That last point is the real lesson of the stale Firefox Android claim: a capability-detection API can return true while the OS integration underneath is missing ([1Password community](https://www.1password.community/1password-at-home-31/firefox-passkeys-1password-android-14-3469)).

One tradeoff deserves a warning. Default-on anti-fingerprinting and content blocking make a browser look less like Chrome to bot detectors. Searles et al. found bots already beat humans on speed and accuracy ([USENIX 2023](https://www.usenix.org/conference/usenixsecurity23/presentation/searles)), so detectors lean on browser signals. Cloudflare's alternatives are measured only on mainstream devices ([Cloudflare](https://blog.cloudflare.com/eliminating-captchas-on-iphones-and-macs-using-new-standard/)). No source in the notes measures challenge rates for privacy-hardened or non-Chromium browsers. HGBA should expect its privacy defaults to raise CAPTCHA exposure, a pain point users would blame on the browser, and should measure it before launch.

## How the evidence bears on HGBA-3.0's existing decisions

**AI off by default (B10, D13, AG-0) is the decision the 2026 evidence supports most strongly, and AG-0 should copy its test from Hanff.** The Chrome Nano episode is exactly what AG-0 is designed to rule out. On a fresh profile with no user input, a 4GB model appeared on disk, was downloaded again after deletion, and was justified after the fact as powering scam detection ([That Privacy Guy](https://www.thatprivacyguy.com/blog/chrome-silent-nano-install/); [Yahoo/Quartz](https://tech.yahoo.com/ai/gemini/articles/google-chrome-silently-downloads-4gb-143602025.html)). AG-0's conditions (zero model files, zero AI endpoint requests, zero model-host processes) match Hanff's method, so AG-0's harness should replicate it: fresh profile, idle period, and a file-system watch for weights. The evidence exposes three gaps in AG-0 as written. First, AG-0 covers processes, files and network, not **UI surfaces**. Chrome's NTP chips are an AI pain point that downloads nothing, so a shell clause is needed: no AI entry points or promotions in default UI. Second, Google classifies an on-device model as a **security** feature (scam detection). HGBA must decide in advance whether ML-based security classifiers count as "AI" under B10. If they do not, AG-0's "zero model files" condition needs a stated exception, or it will be broken by the first safe-browsing model. Third, Firefox's experience shows a kill switch earns trust only if choices "persist across updates" ([Mozilla](https://blog.mozilla.org/en/firefox/ai-controls/)). AG-0 already repeats on every release; it should also test the upgrade path from a profile where the user switched AI off.

**Agent capabilities stay a bet, and the pain-point evidence neither asks for them nor undermines them.** No verified pain point is "the browser cannot act for me". The closest are CAPTCHAs and bot walls, which agents will hit harder than humans, and malicious extensions, which support B9's choice of an agent as a separate principal rather than a privileged extension (D12). The 2025–26 extension incidents were update-time hijacks of trusted code ([Infosecurity](https://infosecurity-magazine.com/news/shadypanda-infects-43m-chrome-edge)). The same threat applies to any agent tool or model update, so B9's per-task origin sets should be paired with re-consent when an agent component's capabilities change. That is a shell rule, not an engine one.

**INP-oriented scheduling has a ceiling set by site code, and HGBA cannot use CrUX to show it worked.** P5's p95 interaction latency and X-2's corpus p95 INP are the right metrics, but field INP is already good on 77% of mobile origins while lab TBT rose 58% ([Almanac](https://almanac.httparchive.org/en/2025/performance)). The remaining jank is site JavaScript holding the main thread, and B3's sequences can prioritize input only between tasks, not inside them. The evidence offers no engine-wide measured gain from input prioritization or `scheduler.yield`. The levers with measured effects are elsewhere: bfcache eligibility (relaxing `unload` and `no-store` blockers), same-origin prerender, background throttling and heavy-ad unloading. A native content blocker is probably the largest single lever, because heavy ads alone consume over a quarter of ad CPU ([Chromium](https://goo.gle/2Xj8HJD)). HGBA should ship `scheduler.postTask`/`yield` for compatibility, since Chrome and Firefox have them ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Scheduler/yield)), but should not budget INP gains on them. Measurement is a further problem: CrUX is Chrome-only and LoAF is Chromium-only, so X-2's published corpus is the only place HGBA's responsiveness can be shown at all.

**The semantic plane (B8) faces a web that is 95.9% broken, and repair collides with B10.** B8 already lists authoring quality as its main risk, and WebAIM confirms the scale: 56.1 errors per page and rising ARIA misuse ([WebAIM](https://webaim.org/projects/million/)). A repair layer fits B8 naturally, because nodes already carry IDs and visibility flags, and B8's contrast flag doubles as a detector for the most common failure, low contrast at 83.9%. The repairs split into two classes. **Rule-based repairs** need no model, but heuristic names can be wrong or misleading; only preference-honoring repairs (forced colors) and AT-only metadata copied from deterministic sources carry no risk of a wrong label (corrected 14 October 2026; see HGBA-3.1.1 B10 classes R0–R4). Examples: forced colors and contrast enforcement, a default document language, and heuristic names for empty links and buttons taken from URLs or icon file names. They are not AI, so under P6 they are never gated by the B10 switch. **ML repairs**, such as alt text for images, need a model. Under B10 and AG-0, no model may download by default, even though P6 says accessibility is never gated by the AI switch. The cleanest resolution is a separate, explicit accessibility opt-in. It would download a local model only on request, follow Firefox's on-device design rather than Chrome's and Edge's cloud calls ([Mozilla Hacks](https://hacks.mozilla.org/2024/05/experimenting-with-local-alt-text-generation-in-firefox-nightly/embed/)), and mark every generated label as generated in the accessibility tree. "User review" then has a precise meaning: the screen reader announces that the label is machine-generated and the user can dismiss or report it. A blind user cannot inspect the image, so the label's disclosure is the review. The accessiBe ruling sets the boundary on claims: HGBA may describe repair as a user aid, never as making a site compliant ([FTC](https://www.ftc.gov/news-events/news/press-releases/2025/04/ftc-approves-final-order-requiring-accessibe-pay-1-million)).

## Conclusion

The fact-check changes what HGBA-3.0 should claim more than what it should build. The pain points users feel most are mostly decided outside the engine, by sites, OS vendors and regulators, or by shell defaults that HGBA's direction document leaves unspecified. The engine-level contributions with the best evidence are unglamorous: gate notification prompts behind a user gesture, block audible autoplay, reduce the fingerprinting surface, provide a content-blocking hook that does not depend on extension APIs, and keep bfcache eligible. Those cost little against P2 and are what a user would notice. Most other mitigations, including reader modes, scroll overrides, banner handlers, tab-burnout features and accessibility repair, have no published outcome data from any vendor. HGBA's oracle-first method (P3, P7) is a real differentiator here: it can publish measured effects for features competitors ship on faith.

Two design debts follow that the 3.0.5 freeze does not yet record. (Both are now recorded in HGBA-3.1: the boundary cases in B10, and the CAPTCHA cost as target PRIV-1.) First, B10's "AI off" needs boundary cases written down: security classifiers, UI promotions, and accessibility models the user asked for. Without them, AG-0 will either fail on the first legitimate model or let a Chrome-style surprise through by classification. Second, HGBA's privacy defaults will plausibly raise its CAPTCHA and bot-wall exposure, and no public data exists on that cost. A new browser that protects users from tracking and then makes them prove they are human more often has traded one verified pain point for another. That rate should be measured alongside AG-0 and X-2 before any default ships.
