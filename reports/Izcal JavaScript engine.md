*Revision 0.1 (19 October 2026): first draft, written from the six research notes by the synthesis author.*

HGBA-2 2.3.0 excludes V8 and every other engine library, so Izcal builds its own JavaScript and WebAssembly engine. The owner's direction is the best engine from first principles, with cost recorded as a planning fact and never as a reason for a lesser design. The record is unusually clear about what goes wrong. **Every in-the-wild JS-engine exploit with a published root cause (Project Zero's analyses, 2019–2022) was memory corruption reached through an engine logic error**: a JIT's model of side effects disagreeing with the runtime, a GC's root set disagreeing with the code, a validator's limit disagreeing with the type encoding ([P0 RCA index](https://googleprojectzero.github.io/0days-in-the-wild/rca.html), [SE 1–2][SE]). V8 says its exploited bugs are "rarely 'classic' memory corruption" ([V8](https://v8.dev/blog/sandbox)); the 2023–2026 rows of the sheet carry advisory titles only, with no published root cause. Rust removes the minority that are classic memory bugs and none of the rest ([SE 3][SE]). No major engine died of its execution design; they died because keeping a whole engine compatible with a yearly specification cost more than the owner would pay ([HP 6][HP]). **The central idea: state each invariant once, in a machine-checkable form, and derive every part of the engine that must agree on it from that one statement.** One semantic description of each bytecode operation generates the reference interpreter, the production interpreter, the baseline compiler, the inline-cache language and the optimizer's knowledge of effects. One heap, one tracer and one barrier discipline serve JavaScript, WebAssembly GC objects and DOM nodes, with rooting proven by Rust's type system rather than by a lint or a conservative scan. One cage holds every GC object and no raw pointer, and nothing outside it trusts what it reads from it. One rule makes the engine deterministic by construction: **concurrency may change when work is done, never what is decided**, and any timing-dependent decision is a recorded input. The decisions that matter most: (1) 32-bit compressed, cage-relative references, designed together with the security boundary (JS-D1); (2) precise rooting everywhere, with a token-branded API whose soundness argument is written down (JS-D2); (3) tiers generated from one description, with optimizer rewrites verified by SMT and every emitted function checked by a machine-code validator (JS-D5, JS-D7); (4) every tier, the optimizer included, is designed from the first milestone and ships when its verification gates pass, never on a date (JS-D8); (5) a trusted region outside the cage for everything the interpreter and compilers rely on, with data read from the cage treated as untrusted (JS-D16, H-2). The engine targets x86-64, AArch64 and riscv64 (RVA23) as first-class ISAs from the start (JS-D22). It is the largest single component Izcal builds: about 65–82 engineers† at full strength, reached through a hiring ramp, for 5–7 years† to reach parity with the best shipping engine (Section 9).

| User | Task, in their words | What fails today |
|---|---|---|
| **People browsing** | "The page should load, respond and not drain my battery, and it must not be the way I get hacked" | JS engines are the largest source of exploited browser bugs: V8 has 32 in-the-wild 0-days in Project Zero's sheet from 2020 to September 2026, 59% of them type confusion ([P0 sheet](https://docs.google.com/spreadsheets/d/1lkNJ0uQwbeC1ZTRrxdtuPLCIl7mlUreoKfSIgajnSyY/), [SE 1.1–1.2][SE]); 60% of Chrome's in-the-wild exploits in 2021–2023 were V8 bugs ([V8 sandbox](https://v8.dev/blog/sandbox)). Scripts took 10–30% of page-load time on typical sites in Microsoft's 2010 measurement ([IE Blog](https://web.archive.org/web/2010/http://blogs.msdn.com/b/ie/archive/2010/03/18/the-new-javascript-engine-in-internet-explorer-9.aspx), [HP 2.7][HP]) |
| **Web developers** | "Why is this slow?", "why did it deopt?", "what keeps this object alive?", "why did this fail only once?" | Deopts and megamorphic ICs are found only with expert tools outside the browser: Deopt Explorer's command line lists 13 V8 logging flags, "known to change from release to release" ([Microsoft](https://devblogs.microsoft.com/typescript/introducing-deopt-explorer/), [GO 1.2][GO]); a heap snapshot needs about twice the heap and blocks the event loop ([Node.js](https://nodejs.org/api/v8.html), [GO 2.1][GO]); sampling profilers disagree on the hottest method ([GO 3.1–3.2][GO]) |
| **Wasm toolchains and their users** | "Compile my C++, Rust, Kotlin or Dart app and run it fast, with GC objects shared with JS" | Page Wasm needs GC objects shared with JS, JSPI and WebIDL in one engine ([HGBA-2 4.2][H2]); turning the JIT off has meant turning Wasm off or onto a slow interpreter ([GO 7.1–7.4][GO]) |
| **Izcal's engineers and agents** | "Reproduce this exactly", "prove this optimization is right", "track this year's edition without a rewrite" | V8 needed a forked platform, not flags, to be deterministic ([M0](../m0/determinism_crossplatform.md)); Nashorn was deprecated because it was "challenging to maintain" ([JEP 335](https://openjdk.org/jeps/335), [HP 6.4][HP]) |
| **Izcal's own UI** (shell, prompts, DevTools) | "Start fast and stay safe while rendering untrusted page titles" | Izcal-only renderers are jitless by default ([security scope 6.7][SS]), so their speed depends entirely on the interpreter and on startup |

**What Izcal's specs already decide.**

- **[M-1][H2] (2.3.1).** No code from another engine, and no library that does engine work. Izcal builds its own engine and garbage collector from the specifications. Specifications are anchored at pinned revisions (ANC-1); other engines are black-box differential signals only, and their source code is never evidence (part 3): this spec cites published prose and black-box observation only.
- **[HGBA-2 4.2][H2].** Page Wasm runs inside the JS engine, because Wasm GC, JSPI and WebIDL need shared GC objects. The V8, `cppgc`, D2, S-4b/c/e and Q-1 text is superseded and is rewritten from this spec (Section 9.5).
- **P1 and I-1.** One renderer process per (site, container); no cross-site data in one address space; Spectre confidentiality comes from process isolation, never from in-process mechanisms (I-6). I-1 also allows a documented reduced-isolation mode below a RAM threshold, which the engine must handle (Section 6.7, JS-D20).
- **[Resource-footprint spec][FP] 0.2.** Budgets for an empty site process (FP-2, with a 1 MiB† line for the engine runtime and one realm), per further agent (FP-34), per realm and frame (FP-4), per page (FP-5), for the engine heap and its limits (FP-35, with limits identical on every device, FP-D19) and for start-up (FP-27); a read-only, position-independent engine image (FP-D1); one copy of the DOM (FP-D2, whose decision this spec owns as JS-D4); discardable derived data and reclaim that never needs memory. Numbers that belong to that spec are referenced here, not set here.
- **[HGBA-3 B1][H3], DET-1, DET-2.** No engine code reads the OS clock, threads or randomness directly. A recorded page plus a seed must replay bit-identically in 1,000 of 1,000 runs, at ≤1%† substrate cost.
- **[HGBA-3 B4][H3] and [Stage 1 5.2–5.4][S1].** The DOM lives in a GC heap; a Rust data plane outside it, keyed by generational node IDs, is what style, layout and the semantic plane read. Workers never touch GC memory. (Section 6.2 restates B4 for a one-copy DOM.)
- **[Stage 1 Section 2][S1].** Crates are named `hg-*` in layers L0–L6 with rules G1–G9; G6 names `v8` and must change. The DevTools spec proposes G10–G12, so this spec's rules start at G13.
- **Security scope 0.3.** Izcal-only renderers are jitless; SEC-D5 gives the banking container the jitless tier by default; the emergency channel (UPD-R5) can switch on jitless or Wasm off for all users.
- **Coding standard 0.3.1.** Script-reachable Rust state lives in `TokenCell<T>` borrowed against a `ScriptToken` (CS-D3 (a), CS-TY-10); allocation does not take that token (Q-CS-7).
- **[DevTools spec][DT].** IIP is the inspection protocol; recorded sessions start at process launch; `script.v8` passes V8's inspector through, which this spec replaces (Section 9.5). DT-D10 Option B (owner decision, 18 October 2026) puts the CDP profile's JS domains, the WebDriver slice's script evaluation (M2) and recorded sessions with a scrubbable console (M7) in Stage 1; this spec's debugger and profiler core is therefore Stage 1 work (Section 6.10, JS-M1, JS-M2).

**Success** is measured by Section 8: test262 and the Wasm spec tests passed in every tier alike; each exploited bug class closed by a named mechanism and shown closed by planted bugs; verified rewrite and lowering rules; benchmark parity with the best shipping engine on each reference device by Stage 3; GC cost judged by total cost as well as pauses; determinism in the production configuration, not a special mode; and engine facts no other engine exposes.

### 2.2 Technology mismatches: assumptions that no longer hold

| Assumption | Where it came from | Why it no longer holds | Evidence |
|---|---|---|---|
| Peak throughput on synthetic suites is the goal | SunSpider and Octane, 2007–2017 | Real pages are cold code, short functions and event-driven work; Octane-driven work made real sites slower | [V8](https://v8.dev/blog/real-world-performance); up to 50–70% of functions never ran in the authors' sessions in 2010 ([JSMeter](https://www.usenix.org/legacy/event/webapps10/tech/full_papers/Ratanaworabhan.pdf)); 44% of shipped JS unused ([Web Almanac 2024](https://almanac.httparchive.org/en/2024/javascript)) |
| The host language makes the engine safe | 2010s memory-safety push | Exploited engine bugs are logic bugs that corrupt memory through generated code and the GC | [V8 sandbox](https://v8.dev/blog/sandbox); Wasmtime's 7 GC-reference memory corruptions in Rust ([advisories](https://github.com/bytecodealliance/wasmtime/security/advisories)) |
| An interpreter written in C, C++ or Rust is good enough | Portability | Compilers produce mediocre interpreter loops ([Pall](http://lua-users.org/lists/lua-l/2011-02/msg00742.html)); and, this spec's own point, its frames must match the JIT's | Rust `become` still unstable ([#112788](https://github.com/rust-lang/rust/issues/112788)) |
| A general-purpose backend can be borrowed | LLVM's success | It modelled patchpoints only as experimental intrinsics and often spent three quarters of compile time | [B3](https://webkit.org/blog/5852/introducing-the-b3-jit-compiler/) |
| JIT is on or off for the whole browser | Process-wide memory permissions | Process per (site, container) lets the tier ceiling be a capability of the site's process | [GO 7][GO]; I-1 |
| GC timing is an implementation detail | Single-run browsing | Under DST and replay, GC-observable behaviour must be a function of inputs; flags did not achieve it in V8 | [M0](../m0/determinism_crossplatform.md) |
| The DOM and JS need separate memory managers | C++ DOMs with reference counting | Every two-manager design paid in leaks, UAFs or pauses; Izcal owns both sides | [GC 4][GC] |
| Hand-maintained formal semantics freeze | JSCert and KJS stopped at ES5 | Extraction from `spec.html` (ESMeta) follows yearly editions and runs in TC39's CI | [SP 5][SP]; [esmeta-typecheck.yml](https://github.com/tc39/ecma262/blob/main/.github/workflows/esmeta-typecheck.yml) |
| Deoptimization, OSR and stack switching may write return addresses | Pre-CET hardware | Shadow stacks (CET, Arm GCS) and PAC forbid forged return addresses; a JIT designed now can make every frame transition with genuine calls and returns (JS-D19) | First principles; backward-edge CFI is a design problem for a JIT ([V8 CFI](https://v8.dev/blog/control-flow-integrity)) |
| Everything inside the engine's heap is the engine's own data | Pre-sandbox engines | Under the cage's attacker model, anything in the cage may have been written by the attacker after it was checked | V8 moved bytecode and code metadata to a trusted space outside its sandbox ([V8 sandbox README](https://chromium.googlesource.com/v8/v8/+/refs/heads/main/src/sandbox/README.md)) |

## 3. Today: the landscape and its gaps

**Conformance is no longer the differentiator.** On 19 October 2026, test262.fyi counts 53,616 tests: JSC passes 98.80%, LibJS 97.72%, V8 97.69% and Boa 95.59% ([index.json](https://raw.githubusercontent.com/test262-fyi/data/gh-pages/index.json), [SP 4.3][SP]). Young, spec-literal engines reach the incumbents within a few years. Performance, security, footprint and spec-tracking cost separate engines.

**Security is decided in the JIT, the GC and the validator.** About half of exploited V8 bugs were in compilers ([V8](https://v8.dev/blog/sandbox)). The named root causes are side-effect modelling (CVE-2020-6418), dependency invalidation (CVE-2020-16009, CVE-2021-30632), range analysis feeding bounds-check removal, GC root and barrier bugs (CVE-2021-37975, CVE-2021-4102), deopt materialization (CVE-2022-1364), builtin TOCTOU, bytecode generation (CVE-2022-4262) and Wasm validation limits (CVE-2024-2887) ([P0 RCA list](https://googleprojectzero.github.io/0days-in-the-wild/rca.html), [ZDI](https://www.zerodayinitiative.com/blog/2024/5/2/cve-2024-2887-a-pwn2own-winning-bug-in-google-chrome), [SE 2][SE]). Fixes are attack surface too: incomplete patches produced variants ([P0](https://projectzero.google/2021/02/deja-vu-lnerability.html)).

**Verification has reached exactly those components, in engines designed to be checkable.** VeRA verified Firefox's range analysis and found a bug latent for six years ([PLDI 2020](https://cseweb.ucsd.edu/~dstefan/pubs/brown:2020:vera.pdf)). Icarus verifies every IC stub a DSL can emit ([SOSP 2024](https://www.cs.utexas.edu/~hovav/dist/icarus.pdf)). Arrival verified 97.8% of in-scope AArch64 instruction-lowering paths reachable from Wasm in 11 minutes, with ISA semantics from Arm's ASL ([OOPSLA 2025](https://www.contrib.andrew.cmu.edu/~bparno/papers/arrival.pdf)). VeriWasm checks the isolation property of each compiled module in 1.7 s median ([NDSS 2021](https://cseweb.ucsd.edu/~dstefan/pubs/johnson:2021:veriwasm.pdf)). Retrofitting V8 has produced only translation validation, with no V8 bug count in the abstract (it reports one new LLVM miscompilation) ([TurboTV](https://prosys.kaist.ac.kr/publications/icse24.pdf)).

**Benchmarks now measure the whole browser and its worst case.** Speedometer 3 measures whole-browser work: Safari's ~60% gain between 17.0 and 17.4 came from work across JavaScriptCore, DOM, style, layout and rendering, with no published breakdown ([WebKit](https://webkit.org/blog/15249/optimizing-webkit-safari-for-speedometer-3-0/)). How much of Izcal's Speedometer time is engine time is something Izcal measures with its own time accounting (JS-21). JetStream 3 (31 March 2026) scores first iteration, worst-case iterations and average separately, and includes 12 Wasm workloads ([BrowserBench](https://browserbench.org/announcements/jetstream3)).

**What is invisible today** ([GO 12][GO]):

| Gap | Evidence | What an owned engine can do |
|---|---|---|
| Why code is slow (deopts, megamorphic ICs, shape churn, tier changes) | 13 internal flags whose format changes per release ([Microsoft](https://devblogs.microsoft.com/typescript/introducing-deopt-explorer/), [GO 1.2][GO]); Firefox's JIT view was "arcane runes" ([bug 1163268](https://bugzilla.mozilla.org/show_bug.cgi?id=1163268)) | A versioned event stream with reasons tied to source (Section 6.10) |
| What keeps memory alive | Snapshots cost 2× heap and minutes ([V8](https://v8.dev/blog/speeding-up-v8-heap-snapshots)); retaining paths across JS and DOM were wrong until unified tracing ([V8](https://v8.dev/blog/tracing-js-dom)) | One heap with in-place retaining-path queries, and leak diffs under replay |
| Exact profiles | Sampling profilers disagree ([GO 3][GO]) | Re-execute a recording with full instrumentation |
| Determinism of the engine itself | Predictable modes switch concurrency off and still leak ([GO 5][GO]) | Determinism as a design property (Section 6.9) |
| Per-script CPU and energy | OS meters stop at the process ([GO 8][GO]) | Attribution by script, realm and origin |
| JIT policy per site without losing Wasm | SDSM and Chrome's policy turned Wasm off or slow ([GO 7][GO]) | A tier-ceiling capability with a jitless Wasm path |

No public, current breakdown of engine time on real pages exists, nor a distribution of IC states on the web, nor a per-tier energy study ([EX 1.6, 4.4, 14.4][EX]). Izcal has to measure all three itself; the design makes that measurement a built-in (Section 6.10).

## 4. First principles

### 4.1 Users' real tasks

| ID | Task | Who | What the engine must provide |
|---|---|---|---|
| U1 | Load a page whose code is mostly cold | People browsing | Fast lazy parsing, a compact bytecode, a fast first tier and cheap feedback; real pages, not peak loops, set priorities ([EX 1][EX]) |
| U2 | Keep interactions under a frame | People browsing | Short, bounded main-thread pauses for GC and compilation; work moved off the main thread without changing results |
| U3 | Run compute-heavy apps (editors, spreadsheets, games, Wasm ports) | People browsing, Wasm users | An optimizing tier for JS and Wasm; Wasm GC objects in the same heap as JS |
| U4 | Stay safe on a hostile page | People browsing | Bug classes closed by construction; corruption contained; per-site tier ceilings; fixes shipped fast |
| U5 | Save battery and memory | People browsing, low-RAM devices | Small references and headers, bytecode instead of baseline code for cold functions, energy measured per run |
| U6 | Find out why code is slow or leaks | Web developers | Stable engine facts with reasons, exact retaining paths, exact profiles |
| U7 | Reproduce a failure exactly | Developers, Izcal engineers, agents | Determinism in the production configuration; replay at any tier |
| U8 | Track the specification every year | Izcal engineers | Spec anchors, spec-extracted oracles, spec coverage, generated code where the spec is regular |
| U9 | Change the engine without fear | Izcal engineers and agents | One source of truth per invariant; differential and verified oracles; rules that fail at compile time |
| U10 | Run Izcal's own UI | Shell, prompt, DevTools renderers | Jitless speed, AOT bytecode in the startup image, small footprint |

### 4.2 Platform primitives

- **ECMA-262** is a typed program in all but name: about 14,480 numbered algorithm steps in 2,302 algorithm blocks, about 800 typed operations, Completion Records with `?` and `!`, and a type checker (ESMeta) running in TC39's CI with 16 known exceptions ([SP 1.3, 1.9][SP]). A machine-readable index of clause ids and signatures is published to npm on every merge ([publish-biblio.yml](https://github.com/tc39/ecma262/blob/main/.github/workflows/publish-biblio.yml)). The spec has 56 implementation-defined, 47 implementation-approximated and 50 host-defined occurrences ([SP 1.5][SP]); these are exactly what determinism must pin.
- **The engine–host boundary** is 16 host-defined abstract operations at `main` (17 once Temporal's HostSystemUTCEpochNanoseconds merges with [PR #3966](https://github.com/tc39/ecma262/pull/3966)), plus a few object protocols (exotic objects, internal slots, realms) ([SP 1.6, 8][SP]). HTML implements the hooks; jobs become microtasks the host schedules, so the engine must not own the job queue ([HTML](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint)).
- **WebIDL** requires per-realm interface objects and exotic objects defined outside ECMA-262 (legacy platform objects, observable arrays, `[[IsHTMLDDA]]`) ([WebIDL](https://webidl.spec.whatwg.org/#js-legacy-platform-objects)). An engine that treats them as first-class can inline them.
- **Wasm 3.0** (17 September 2025) adds GC, typed references, tail calls, exceptions, memory64, relaxed SIMD and a deterministic profile; its spec is written in SpecTec, whose meta-interpreter passes the applicable suite ([Wasm 3.0](https://webassembly.org/news/2025-09-17-wasm-3.0/), [SP 6–7][SP]). JSPI and stack switching require suspending and resuming stacks ([SP 6.3][SP]).
- **Weak references are deliberately loose.** ECMA-262 promises nothing is ever collected, clears weak targets atomically per non-live set, keeps `deref()` targets alive to the end of the synchronous job, and leaves cleanup scheduling to the host ([ECMA-262 §9.9](https://tc39.es/ecma262/#sec-weakref-processing-model), [GC 8][GC]). That freedom is what lets Izcal make GC-observable behaviour deterministic.
- **Hardware and OS** offer W^X with per-thread toggling (Apple `MAP_JIT`), protection keys, BTI and PAC on Arm, CET and IBT on x86 ([SE 4.7, 4.9][SE]), and on riscv64 Zicfilp landing pads and Zicfiss shadow stacks, encoded so that they are no-ops on RVA23 hardware without them ([RV 3][RV]). A JIT designed now can be compatible with all of them from the start.
- **Three ISAs.** Izcal's engine targets x86-64, AArch64 and **riscv64 (RVA23U64)** as first-class ISAs from JS-M0 (owner decision, 19 October 2026; HGBA-2 X-1). RVA23 makes the vector extension, Zicond, Zfa and the may-be-operation space mandatory and was ratified in October 2024; Ubuntu requires it from 25.10 ([RV 1, 5][RV]). Section 6.18 gives the riscv64 design.
- **Izcal's own architecture** gives the engine a seeded substrate (B1), a renderer per (site, container) (I-1), a data plane that keeps workers out of the heap (B4), and generated WebIDL bindings (Stage 1 5.3).

### 4.3 Izcal's principles that bind this design

P1 outranks P4: a verified, contained design is preferred to a faster unverified one, and the cost is stated. P2: every tier implements exactly the same semantics, so test262 passes identically with any tier ceiling. P3: every accelerated path has a correct slower path, and the engine never fails open. P4: real-page latency, worst-case iterations and energy are targets alongside peak throughput. P6: no number in this spec is presented as measured unless it was. M-1: everything is built; specifications, conformance suites and spec-extracted models are the oracles.

### 4.4 Assumptions kept and broken

| Assumption | Keep or break | Why |
|---|---|---|
| Shapes (hidden classes) and inline caches | **Keep** | Every fast engine converged on them within a year of 2008 and kept them, because real programs are structurally regular ([HP 2, 12][HP]) |
| Bytecode is the first tier | **Keep** | Machine code for run-once code wasted a third of V8's heap ([V8](https://v8.dev/blog/launching-ignition-and-turbofan)) |
| Register bytecode | **Keep** | About 47% fewer executed instructions for about 25% more bytecode ([VEE 2005](https://usenix.org/legacy/events/vee05/full_papers/p153-yunhe.pdf)); JSC, Carakan, Ignition, Hermes and Boa chose it |
| Each tier is written by hand | **Break** | Duplicated tier code drifted (CacheIR's reason); generated tiers beat hand-written ones in Deegen ([EX 6.2][EX]) |
| The interpreter is compiled by a general compiler | **Break** | Pall's argument ([lua-l](http://lua-users.org/lists/lua-l/2011-02/msg00742.html)); JSC's offlineasm and LibJS's AsmInt; Rust has no guaranteed tail calls ([EX 5.5][EX]) |
| The optimizer is trusted because it is tested | **Break** | Half of exploited V8 bugs are compiler bugs; fuzzing "lacks the assurance of verification" ([Arrival](https://www.contrib.andrew.cmu.edu/~bparno/papers/arrival.pdf)) |
| Side-effect models are written by hand per compiler | **Break** | CVE-2020-6418 was a hand-written model disagreeing with the runtime; derive effects from the operation's semantics |
| Sea of nodes | **Break** | V8 left it after a decade for complexity, cache misses and compile time ([V8](https://v8.dev/blog/leaving-the-sea-of-nodes)) |
| Speculate only when nearly certain | **Keep** | A failed speculation costs thousands of nanoseconds against about a nanosecond of gain ([Pizlo](https://webkit.org/blog/10308/speculation-in-javascriptcore/)) |
| Frame transitions that write return addresses (lazy and eager deopt, OSR, stack switching) | **Break** | Incompatible with shadow stacks and PAC; Izcal checks a status word on return and rebuilds frames only through genuine calls (Section 6.4, JS-D19) |
| Conservative stack scanning is the convenient root set | **Break** | It pins objects, leaks addresses to page script ([GC 5.3][GC]), and makes liveness depend on stack garbage, which threatens cross-OS determinism ([GC 5.4][GC]) |
| The DOM and JS have separate memory managers and wrappers | **Break** | Every such design paid in leaks, UAFs or pauses ([GC 4][GC]) |
| A heap sandbox is retrofitted | **Break** | V8's took years; one outside observer estimates it at about a fifth of V8's ~4-engineer GC effort over two years, from what he calls "made-up numbers" ([Wingo](https://wingolog.org/archives/2025/11/13/the-last-couple-years-in-v8s-garbage-collector), commentary); Izcal designs the cage, the trusted region and the boundary rule H-2 first |
| NaN-boxed 64-bit values | **Break** | Compressed 32-bit references cut V8's heap by up to 43% and double as a boundary ([V8](https://v8.dev/blog/pointer-compression)); NaN-boxing also relies on user addresses fitting its payload: 47 bits in SpiderMonkey's x86-64 format ([Pierron, Mozilla, 2011](https://www.lrde.epita.fr/dload/seminar/2011-10-26/Javascript-Perf.pdf)), 48 in JSC's ([saelo, Phrack 70](https://phrack.org/issues/70/3)), and Linux maps above 47 bits only on request because JITs keep tags in high pointer bits ([kernel.org](https://docs.kernel.org/arch/x86/x86_64/5level-paging.html)). The full derivation is Section 6.2a |
| GC timing and background compilation are invisible | **Break** | They are the main sources of engine non-determinism ([GO 5.7–5.8][GO]) |
| Backtracking regular expressions by default | **Break** | ReDoS is common ([Davis et al.](https://davisjam.github.io/files/publications/DavisCoghlanServantLee-EcosystemREDOS-ESECFSE18.pdf)); linear-time matching now covers JS lookarounds ([arXiv 2311.17620](https://arxiv.org/abs/2311.17620)) |
| JIT on or off per browser, Wasm lost with it | **Break** | The tier ceiling is a per-site capability, and Wasm keeps an interpreter (Section 6.8) |
| Engine internals are visible only through flags | **Break** | A versioned event stream (Section 6.10) |
| Heap snapshots copy the whole heap | **Break** | A streamed, versioned heap format (Section 6.11) |
| Constant blinding against JIT spraying | **Break** | Blinding was bypassed and full blinding costs up to 80% ([NDSS 2015](https://www.ndss-symposium.org/ndss2015/ndss-2015-programme/devil-constants-bypassing-defenses-browser-jit-engines/)); W^X, landing pads and shadow stacks remove the gadget value instead (Section 6.7) |
| One engine runs many sites in one process | **Keep broken** | I-1 forbids it; isolate-per-tenant figures (3 MB per isolate) are not Izcal's ([GO 10.1][GO]). Where I-1's reduced-isolation mode applies, the engine changes posture (JS-D20) |
| The engine's own heap data can be trusted once checked | **Break** | The cage premise is an attacker with arbitrary read and write inside it; checks done once (bytecode verification, code-table contents, typed-array lengths) are time-of-check only if the data stays in the cage. H-2 and the trusted region (Section 6.1, JS-D16) |
| The DOM needs a second copy for style and layout | **Break** | The mirror existed because the DOM's memory belonged to a GC Izcal did not own; one copy outside the cage serves both (JS-D4, FP-D2) |

## 5. Lessons learned

Lessons are ideas and evidence, never code or templates (M-1).

| Project | What happened | Lesson | How Izcal applies it |
|---|---|---|---|
| Mocha → SpiderMonkey | Engine written before the spec; quirks frozen into it ([HOPL](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf)) | Anchor to the spec first | Spec anchors on every op description and builtin (ANC-1); ESMeta coverage |
| TraceMonkey | Bimodal performance, trace explosion; removed ([Nethercote](https://blog.mozilla.org/nnethercote/2011/11/23/memshrink-progress-report-week-23/)) | Global speculative machinery every tier must honour becomes the bottleneck | No tracing tier; per-site recorded feedback only |
| SpiderMonkey TI → Warp | Global type inference cost memory and GC; CacheIR-fed Warp won on real pages ([Mozilla](https://hacks.mozilla.org/2020/11/warp-improved-js-performance-in-firefox-83/)) | One recorded IC language should be the profile, the baseline code and the optimizer's input | IC programs (Section 6.2) |
| JSC FTL on LLVM | Often ¾ of compile time in LLVM; patchpoints only as experimental intrinsics ([WebKit](https://webkit.org/blog/5852/introducing-the-b3-jit-compiler/)) | Own the backend; design deopt and patching into the IR | `hg-codegen` built for JS and Wasm, with deopt as a first-class instruction |
| Cranelift in Firefox | Shared external backend removed for "wrong shape" ([bug 1781425](https://bugzilla.mozilla.org/show_bug.cgi?id=1781425)) | Integration shape and ownership decide survival | One backend for JS and Wasm, owned by Izcal |
| V8 Full-codegen | Baseline machine code ≈ ⅓ of the JS heap ([V8](https://v8.dev/blog/launching-ignition-and-turbofan)) | Memory decides first-tier design | Bytecode first; baseline code only for warm functions |
| V8 Ignition, SM Baseline Interpreter, Sparkplug | Generated interpreter handlers; shared frames between tiers ([V8](https://v8.dev/blog/sparkplug)) | Shared frames and ICs make extra tiers cheap | One frame layout for interpreter and baseline; tiers generated from one description |
| Deegen | Generated interpreter 28% faster than LuaJIT's hand-written assembly interpreter (geometric mean; faster on 31 of 34 benchmarks) ([Xu 2022](https://sillycross.github.io/2022/11/22/2022-11-22/)); baseline at 19.1 M bytecodes/s ([Xu 2023](https://sillycross.github.io/2023/05/12/2023-05-12/)) | Generation beats hand-writing for lower tiers | `hg-opgen` (Section 6.3) |
| CPython 3.14 tail-call interpreter | Gain was mostly a compiler regression ([Elhage](https://blog.nelhage.com/post/cpython-tail-call/)) | Interpreter speed claims depend on the toolchain | Pinned toolchains; generated assembly, not compiler-dependent dispatch |
| V8 sea of nodes | Abandoned after subtle effect-chain bugs and cache misses ([V8](https://v8.dev/blog/leaving-the-sea-of-nodes)) | CFG SSA with explicit effects; float only pure nodes | Aegraph-style pure-node freedom in a CFG IR ([Fallin](https://cfallin.org/blog/2026/04/09/aegraph/)) |
| V8 2019 `CheckBounds` hardening | Attackers went around it via another constant-folded comparison ([doar-e](https://doar-e.github.io/blog/2019/05/09/circumventing-chromes-hardening-of-typer-bugs/)) | Patching instances does not close a class | Check removal only through verified rules |
| Icarus, VeRA, Crocus, Arrival | Verified IC generators, range analysis and lowering rules found real bugs ([SE 6][SE]) | Verification works on compilers designed for it | SMT-verified rule languages from day one |
| CVE-2024-2887 | A Wasm type-count limit aliased an internal type; RWX Wasm code page ([ZDI](https://www.zerodayinitiative.com/blog/2024/5/2/cve-2024-2887-a-pwn2own-winning-bug-in-google-chrome)) | Validators are as type-rich as JITs; no RWX ever | Validator checked against SpecTec; W^X with no RWX mapping |
| Winch CVE-2026-34987 | A baseline compiler's register-width assumption (aarch64, non-default backend) escaped the sandbox ([GCVE](https://db.gcve.eu/vuln/CVE-2026-34987)) | Baseline tiers are security-critical | Machine-code validator on every tier (JS-D7) |
| JScript GC bugs | Four exploited variants of one "not tracked by the GC" root cause ([P0](https://projectzero.google/2021/02/deja-vu-lnerability.html)) | Rooting must be enforced, not remembered | Token-branded rooting (Section 6.5) |
| Servo reflectors | One GC, but rooting safety rested on a lint ([Mozilla Research](https://research.mozilla.org/2014/08/26/javascript-servos-only-garbage-collector/)) | Put rooting in the type system | The `Mutator` token proves where GC can happen |
| Nova | Lifetime-scoped handles need bind and unbind calls around every GC-capable call ("a soup" of them, uncounted in the source); covariant handles "do not work" and the contravariant design is "currently unsound/incomplete, requiring runtime checks" ([Nova](https://trynova.dev/blog/garbage-collection-is-contrarian)) | The pattern is right; the ergonomics need generated code | Builtins and bindings generated with rooting emitted; invariant brands |
| gc-arena | "Mutation xor collection" is sound ([gc-arena](https://github.com/kyren/gc-arena)) but needs a stackless interpreter ([Nova](https://trynova.dev/blog/garbage-collection-is-contrarian), 11 January 2026 update) | A capability token can prove safe points | Token on `&mut Mutator`; roots for values that cross it |
| Blink object grouping, Gecko CC | Heuristic wrapper liveness lost properties; CC pauses reached seconds ([V8](https://v8.dev/blog/tracing-js-dom), [GC 4.5][GC]) | Two collectors for one graph cost leaks and pauses | One heap; DOM node is the JS object (JS-D4) |
| Riptide, Oilpan | Non-moving cores with conservative stacks worked; V8 took a decade to adopt the idea and still had not shipped it ([GC 5.1–5.2][GC]) | Rooting is near-impossible to change later | Decide precise rooting before the first runtime line |
| Chromium issue 1144662 | Conservative scanning gave page script an address oracle; closed WontFix ([The Register](https://www.theregister.com/2021/02/26/chrome_aslr_bypass)) | Conservative roots leak information | Precise roots |
| LXR, OCaml 5, Shenandoah | Short STW parallel pauses with a cheap barrier beat concurrent evacuation with read barriers; "low pauses do not translate into low application latency" ([LXR](https://www.steveblackburn.org/pubs/papers/lxr-pldi-2022.pdf)) | Judge by total cost and tail latency, not pause alone | Mark-region old space, copying nursery, no read barrier; LBO-style cost target |
| V8 pointer compression and sandbox | Heap up to 43% smaller; ~1% sandbox cost, retrofitted 2020–2024; bytecode and code metadata later moved to a trusted space outside the sandbox ([V8](https://v8.dev/blog/pointer-compression), [V8 sandbox README](https://chromium.googlesource.com/v8/v8/+/refs/heads/main/src/sandbox/README.md)) | Value representation, compression and boundary belong together, and the boundary must decide what is trusted | JS-D1, JS-D16 and JS-D17 decided as one design |
| Replay.io | Finalizers broke replay; the recorder leaked finalizable objects ([Replay](https://www.replay.io/blog/effective-determinism)) | Finalization is the determinism hazard | Cleanup only at host-scheduled, deterministic points |
| JARDIS (ChakraCore) | Time travel at under 2% run-time overhead in record mode (27–71% memory overhead); died with its engine ([FSE 2016](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/09/TTNode.pdf)) | An engine feature lives or dies with its owner | Determinism is a CI dependency of the engine, not a tool |
| Node CVE-2017-11499 | Snapshots froze the hash seed ([Red Hat](https://bugzilla.redhat.com/show_bug.cgi?id=1475327)) | Restored state must re-derive its entropy | Heap images re-seed all external state (Section 6.11) |
| Edge SDSM, Chrome JIT policy | With the JIT off, Wasm was first unsupported, then ran on an interpreter that "might not yield the expected level of performance" ([Microsoft Learn](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-security-browse-safer)); JIT policy arrived as enterprise policy ([Edge VR](https://microsoftedge.github.io/edgevr/posts/Super-Duper-Secure-Mode/)) | Safety controls must not remove features | Tier ceilings with a jitless Wasm path |
| Hermes | AOT bytecode, mmapped, no JIT, for startup ([Meta](https://engineering.fb.com/2019/07/12/android/hermes/)) | Known code can be compiled ahead of time | Shell, prompt and DevTools JS ships as bytecode in the startup image |
| Opera, Edge, Nashorn | Engines ended because maintenance cost outran the owner's budget ([HP 6][HP]) | Spec-tracking cost is the cause of death to plan against | Oracles, anchors and generated code make each edition cheaper |
| Ladybird → Rust | Rust rejected in 2024 for GC and inheritance, adopted in 2026 with equivalence gating ([Ladybird](https://ladybird.org/posts/adopting-rust/)) | The GC fit is the hard part of a Rust engine | The rooting argument is written before code (Section 6.5) |

## 6. Design

### 6.0 Architecture at a glance

The engine runs inside every renderer (one per (site, container), I-1), and in jitless form inside the shell, prompt, DevTools and replay-host renderers and in three embedders with no DOM: the code-cache builder (JS-D21), the component host (JS-D10) and the networking spec's **proxy-resolver utility process**, which runs PAC scripts with the jitless engine, one per (container, route), at the strictest sandbox tier, through `hg-pac-host` ([NW 6.13][NW]). A DOM-less embedder implements `hg-js-host`'s hooks itself: it has no `hg-script` event loop, no WebIDL bindings and no UI image, maps only the engine image's JS section, and its host functions (for PAC, `dnsResolve` and `myIpAddress`) are typed requests to its own services. Each **agent** (a window event loop, a dedicated worker, a worklet) owns one **agent heap** and one `Mutator`. A process may hold several agents of the same (site, container), including agents of different agent clusters (site B framed by site A and by site C); it never holds two sites, except in I-1's reduced-isolation mode (JS-D20). All agent heaps of a process share **one cage** and **one trusted region**, each heap in its own blocks (JS-D17). A `SharedArrayBuffer` agent cluster always lives in one process, so a process split (FP-D3) happens only at agent-cluster boundaries.

### 6.1 Value representation, addressing and the security boundary (JS-D1, JS-D16, JS-D17)

These are one decision, because each constrains the others: V8 needed pointer compression before it could build its sandbox, pointer compression cost it unboxed double fields ([V8](https://v8.dev/blog/pointer-compression), [EX 3][EX]), and the sandbox later had to move bytecode and code metadata out of the sandbox into a trusted space ([V8 sandbox README](https://chromium.googlesource.com/v8/v8/+/refs/heads/main/src/sandbox/README.md)).

**Regions.** Each process reserves these address ranges at start-up through the substrate's `Memory` interface (G3; one trait set shared with the resource-footprint spec, Section 6.15):

| Region | Holds | Addressed from GC objects by | Never holds |
|---|---|---|---|
| **Cage** (one per process, 16 GB† reservation, JS-D17) | Every GC object: JS objects, strings, shapes, closures, feedback (call counts and value profiles, which are hints only), Wasm GC structs and arrays, DOM node wrappers. Each agent heap owns its own blocks; a later shared heap owns its own | 32-bit compressed references | A raw pointer of any kind (**H-1**); anything that code outside the cage relies on without re-checking (**H-2**) |
| **Trusted region** (one per process, JS-D16) | Verified bytecode and constant pools; validated Wasm function bodies and their side tables; IC programs and the IC site table; stencil patch data; frame states, deopt and safepoint metadata, stack maps; **code-table** and **buffer-table** entries | Index into a typed trusted table, with a kind tag and a generation | Anything a mutator thread writes directly; it is written only by the verifier, the compilers and the runtime's IC-attach path, through a write window (Section 6.7) |
| **Buffer region** | ArrayBuffer and SharedArrayBuffer backing stores; Wasm linear memories, each in its own reservation with guard pages | Index into the **buffer table** (base, length, flags), bounds-checked against the table | GC references |
| **Outside** | Machine code (code region), engine metadata, the DOM's node columns and text arena (Section 6.2), Rust-owned payloads in side tables, substrate objects, tier-ceiling state | Index into a typed **external table** or the code table, with a type tag and generation (as CS-TY-1 and FFI-R1 do for IDs) | — |

**References.** A heap slot is 32 bits. The low bit tags it: a **small integer** has tag 0 and carries 31 bits; a **reference** has tag 1 and carries a 31-bit offset in units of 8 bytes, so a cage spans 16 GB. The stored slot is `v = (offset << 1) | 1`, so the address is `base + 4·v − 4`. On x86-64 that is one memory operand (`[base + v*4 − 4]`). On AArch64 register-offset loads scale only by the access size and take no displacement, so decompression is one extended-register `ADD Xd, Xbase, Wv, UXTW #2` followed by a load with an immediate offset of −4, the same instruction count as V8's unscaled scheme (checked with the system assembler by the fact-check, [factcheck §6][FC]). On riscv64, Zba's `sh2add.uw` zero-extends the 32-bit slot, scales it by 4 and adds the base in one instruction, followed by a load with an immediate offset of −4: also two instructions ([RV 7][RV], Section 6.18). The cost is a first-principles claim measured at the JS-M0 spike (JS-D1's reversal trigger). The cage base is a process-wide constant, held in a reserved register in generated code and in a read-only global for Rust, so dereferencing a `Gc` never needs to know which heap it came from. V8's 4 GB byte-offset cage is the measured alternative: it gave a heap up to 43% smaller and up to 20% less renderer memory on desktop ([V8](https://v8.dev/blog/pointer-compression)), and its 4 GB limit is the cost Izcal's scaling avoids for large Wasm GC and DOM heaps.

**Numbers.** Doubles have no tag bits in a 32-bit slot. Izcal stores them in three ways, chosen by the object's layout, not by a global encoding:
- **Raw fields.** Every object has a **layout descriptor** (its shape, Section 6.2) that splits its body into a tagged region, which the GC traces, and a raw region, which it does not. A property whose shape records a double representation lives unboxed in the raw region. Wasm GC structs with `i32`, `i64`, `f32`, `f64` and packed `i8`/`i16` fields use exactly the same mechanism ([Wasm GC MVP](https://github.com/WebAssembly/gc/blob/main/proposals/gc/MVP.md)), so JS objects and Wasm structs share one layout system.
- **Boxed numbers** in the nursery where a tagged slot must hold a non-small number, for example in an interpreter register. Nursery allocation is a bump, and most such boxes die young.
- **Unboxed values** in optimized code, where SSA values carry representations (Section 6.4).

The alternative of a 64-bit NaN-boxed value everywhere (SpiderMonkey, JSC, Boa) avoids boxing in the interpreter but doubles every reference and relies on 47- or 48-bit user addresses ([Pierron 2011](https://www.lrde.epita.fr/dload/seminar/2011-10-26/Javascript-Perf.pdf), [kernel.org](https://docs.kernel.org/arch/x86/x86_64/5level-paging.html)). Izcal chooses one 32-bit representation for heap, stack and interpreter registers, which gives one set of invariants to verify (derivation in Section 6.2a). The reversal trigger is measured: if heap-number allocation exceeds 5%† of interpreter and baseline time on JetStream 3's numeric workloads at JS-M2, interpreter registers become 64-bit wide values (tagged reference or raw double) while heap slots stay 32-bit.

**The read-only image and static roots.** The JS section of the engine image (one image inventory with the resource-footprint spec's `hg-image`, Section 6.11) is mapped once per process at the start of the cage. The cage base is random per process, so each process keeps its own ASLR while core objects (`undefined`, `null`, booleans, the core shapes) sit at the same offsets in every process, and "is this a string?" becomes a range check on the shape's offset. V8 measured about +1% on Speedometer 2 from this idea ([V8](https://v8.dev/blog/static-roots)). The image is read-only by protection, and its rules are fixed now, because they constrain the object model:
- **Image objects are immortal and immutable.** The collector treats the image range as a root set that is never traced into and never marked in place; image objects hold no references into a heap.
- **Mutable state associated with image objects lives in per-heap side tables keyed by image offset**: transition tables of core shapes, fact cells registered on image prototypes (Section 6.2), IC state and lazily computed fields. This is the footprint spec's rule 2 ([FP 6.3][FP]).
- **Per-realm intrinsics are created from image descriptors on first use**, and an intrinsic is copied into the realm's heap on its first write (script may modify `Array.prototype`); the realm keeps an indirection per intrinsic. WebIDL interface objects follow the same rule. JS-22's realm budget and FP-4's per-realm budget cover this copy.
- **Hash structures in the image are perfect hashes over fixed key sets.** Any table that grows at run time is a per-process table under the process's hash key (CS-AS-2), so no build-time seed is shared by every user (the Node CVE-2017-11499 lesson, Section 5).

**Why this is the security boundary.** V8's sandbox assumes an attacker with arbitrary read and write inside its region and keeps the damage there ([V8](https://v8.dev/blog/sandbox)). Izcal's cage makes the same assumption, and security scope ATK-2 assumes an attacker who reads its own memory, including the cage ([SS 6.1][SS]). Under that premise, a type rule about what Rust can store is necessary but not sufficient; the property that matters is that **nothing outside the cage trusts a value it reads from the cage**. The design rests on two invariants and four mechanisms:
1. **H-1: no raw pointer is representable in the cage.** The types that may be stored in a GC object are tagged references, small integers, raw scalars and table indices; `hg-heap`'s field types make anything else a compile error. A corrupted cage can produce wrong offsets and wrong indices, and both are confined: offsets stay inside 16 GB of cage plus guard space, and table indices are bounds-, kind- and generation-checked on use.
2. **H-2: everything read from the cage is untrusted input** to code outside it: the Rust runtime and builtins, the collector, the heap-image writer, `hg-js-observe`, the interpreter, the IC interpreter and generated code. A length, index, kind or offset taken from a cage object is either re-checked against a bound that lives outside the cage (a table entry, the trusted region, the cage reservation) or used only to address the cage itself. Rule **G17** (Section 6.15) makes this a lint: no slice, unchecked index or pointer offset derived from a cage value without such a clamp, in any crate that reads heap data. The collector obeys it too: object sizes and traced regions come from shapes, which are cage data, so it clamps every size to its block and treats every traced slot as an arbitrary 32-bit value. Under corruption the heap may compute wrong answers; it must never touch memory outside the cage, its side tables or a checked table entry. The unsafe core's verification conditions (Section 6.5, step 8) are stated for arbitrary cage contents.
3. **Code the engine relies on lives in the trusted region (JS-D16).** Bytecode is verified once and then stored outside the cage, so the verification cannot be undone by a later write: a register operand in bytecode indexes the native interpreter frame, which is outside the cage, and a rewritten operand would otherwise be an out-of-cage stack write. IC programs, frame states, deopt metadata and stack maps live there for the same reason.
4. **Code-table entries are typed.** A function object stores a code-table index. Each entry holds the kind (JS function, Wasm function, builtin, trampoline), the **parameter count**, the owner's trusted function ID, a generation and the entry address. A JS call loads the entry, adapts the arguments to the entry's parameter count, never to a count read from the cage, and jumps to a landing pad. Compiled code addresses its frame relative to that count, so swapping two indices in the cage calls the wrong function with a correctly shaped frame, which is confusion inside the cage only. Wasm `call_indirect` checks the callee's canonical type ID from the trusted table entry.
5. **Buffer bounds come only from the buffer table.** Typed-array length, byte offset and the detached state are cage fields: they decide JS semantics and are hints for range analysis. The access that reaches memory is checked against the buffer table's length, or covered by a reservation sized so that every index the access can form lands inside it (Wasm 32-bit memories). The machine-code validator's certificate names which of the two applies to each access (Section 6.7).
6. **Machine code addresses the cage, the trusted region and buffers only through base registers, 32-bit offsets and table entries**, a property the machine-code validator checks on every emitted function and, at build time, on the generated interpreters (Section 6.7).

**Testing the premise.** A test-only build exposes an **in-cage corruption API**: a fuzzer gets arbitrary read and write inside the cage while script runs, and any fault, sanitizer report or write outside the cage, its side tables or a checked table entry is a security bug (JS-10, JS-13). This is how the claim "corruption stays in the cage" is tested rather than asserted.

The cage is a layer, not the boundary. The process sandbox and I-1 remain the boundary, and the cage confines the bug classes that Rust cannot (Section 6.7).

### 6.2 Object model and inline caches

**Shapes.** An object's first word is a reference to its **shape**: a heap object holding the layout descriptor, the property table (keys, attributes, slot or raw offset, representation), the prototype and the element layout, all immutable once the shape is published, plus a transition table, which is the shape's one mutable part (for shapes in the read-only image, the transition table is a per-heap side table, Section 6.1). Adding a property follows or creates a transition. Objects with many additions and deletions move to **table mode**, a hash-table layout that keeps add and delete cheap but defeats ICs, so the switch is an event developers can see (Section 6.10). Indexed elements are stored apart with an **element layout** (packed or holey; small-integer, double or tagged; typed arrays; sparse table). Section 6.2a derives each of these choices.

**Fact cells and dependencies.** Assumptions about prototype chains and global properties are **fact cells**: heap objects that compiled code and ICs register on and that the runtime invalidates when the fact changes. Every speculation in compiled code is either a guard instruction or a registration on a fact cell, never neither (Section 6.4's assumption ledger). Missing invalidation is the class behind CVE-2020-16009 and CVE-2021-30632 ([P0 RCA list](https://googleprojectzero.github.io/0days-in-the-wild/rca.html)). A fact cell's registrations are code-table entries, which live in the trusted region; the cell itself is a cage object, so invalidation is driven by the runtime's own record of registrations, never by a list read from the cage (H-2).

**IC programs.** An inline cache stores **IC programs**: short, linear, branch-free sequences of guards and operations over typed operands (shape, slot offset, fact cell), with the constants in separate fields so identical programs share code ([de Mooij](https://jandemooij.nl/blog/cacheir/), [EX 4.2][EX]). IC programs and the per-site table of attached programs live in the trusted region and are written only by the runtime's IC-attach path; counters and value profiles are feedback in the cage, used only as hints that a guard re-checks. The IC programs are the single source of truth for property access in every tier:
- the interpreter and the jitless profile run them through a small **IC program interpreter**;
- the baseline tier compiles them to stubs;
- the optimizer transpiles the recorded programs into its IR instead of consulting any global type inference, an idea Warp showed works ([Mozilla](https://hacks.mozilla.org/2020/11/warp-improved-js-performance-in-firefox-83/));
- `hg-js-observe` reports their states and transitions, and B1 replays them as part of execution.

IC *generators* (which program to attach for a given receiver and key) are written in the operation description language, so they share semantics with the slow path they replace and can be verified the way Icarus verifies IC generators ([SOSP 2024](https://www.cs.utexas.edu/~hovav/dist/icarus.pdf)). Megamorphic sites use a **probe table** per agent heap keyed by (shape, key). No cache is shared across sites: one process holds one site, and in I-1's reduced-isolation mode every such cache is keyed per site (JS-D20).

**Host exotic objects are first-class.** WebIDL's legacy platform objects, observable arrays, `WindowProxy`, `Location` and `[[IsHTMLDDA]]` ([WebIDL](https://webidl.spec.whatwg.org/#js-legacy-platform-objects), [SP 9][SP]) are shapes with **host hooks** for the overridden internal methods. `hg-webidl-codegen` emits, per interface, a shape family and IC generators for attribute getters, setters and operations, so a DOM property access is cached and inlinable like any other property. Proxies are not used to emulate them.

**The DOM is stored once (JS-D4).** This spec owns the DOM-representation decision jointly recorded with the resource-footprint spec's FP-D2, whose requirements it meets: one copy of the links, total bytes per node counted across every copy, and workers that never trace or write ([FP 6.4][FP]).
- **Node columns outside the cage.** Node structure lives in **columnar node storage** owned by `hg-dom`, non-moving and indexed by a 32-bit node slot with a generation: five links, tag (a static index or an atom), flags and element state, attribute-set reference, inline-style reference, rare-data index and generation. The 48 B† core sits inside the DOM's 72 B† share of FP-11's per-node budget (the style spec's 72 / 80 / 360 split, [RN P9][RN]). Of it, **8 B hold 32 bits of node flags and 32 bits of the most used element state**; other element-state bits and custom `:state()` names live in rare data ([ST 6.11][ST]). Rare fields (shadow root, listener lists, observers, the remaining state and others) live in side tables keyed by slot.
- **What the columns do not hold.** Atom text, attribute-set contents and inline-style source live outside the cage in `hg-dom`'s stores, and JS reads them as external strings (below). An attribute set carries its class atoms, its id atom, its filter hashes and its presentational-hint block, which style reads without a second lookup. Style output (computed values and style flags) lives in `hg-style`'s columns, keyed by the same slot, never in `hg-dom`'s ([ST 9.5][ST]).
- **Lazy wrapper, held strongly once created.** The JS object for a node is an ordinary heap object in the cage holding the node's generational ID, created on first script access; most nodes of most pages are never touched by script. Once created, the node holds its wrapper strongly and the wrapper holds the node, so identity, expando properties and `WeakMap` or `WeakRef` keys on a node behave as for any object, and the pair is collected together. There is no wrapper-lifetime heuristic, which is the failure that Blink's object grouping and Gecko's cycle collector paid for ([GC 4][GC]).
- **One collector traces both.** `hg-heap` treats node storage as a **node space**: mark bits in a per-slot side bitmap; edges are the links (slot indices) and **external traced slots**, which are `hg-heap` field types held outside the cage (the wrapper, event-listener functions and other GC references in rare data). `hg-dom` cannot dereference them raw. Cycles among JS, DOM and Wasm objects are ordinary cycles. Link writes happen on the script thread through `hg-dom`'s API, which performs the SATB barrier, with 32-bit atomic stores (Section 6.5).
- **Why outside the cage (H-2).** Style, layout and the semantic plane trust the tree they read. In the cage, an in-cage write could hand layout an arbitrary tree, and every reader would need H-2's re-checks. Outside the cage the columns are written only by `hg-dom`'s Rust code. The wrapper's node ID, which is cage data, is checked against the slot's generation on every binding call.
- **B4 restated: the columns are the data plane.** The second copy retires. B4's other reasons hold without it: a serializable boundary (the columns), explicit inputs with stable identities (generational node IDs and the **mutation log**, which stays because restyle invalidation, B1 replay and B5 need old values), and workers that never touch GC memory. Style and layout workers read the columns only during a flush, while the script thread is blocked (the F1 quiescence contract, unchanged); they never read the cage, never trace and never write the columns. Script reaches the DOM only through `hg-dom`'s API on the script thread. The projection-equality oracle survives as a debug and Nightly check.
- **Text is stored once.** DOM text lives in an arena of immutable buffers outside the cage. A JS string obtained from the DOM is an **external string**: a cage object that names the buffer through the external table, whose entry holds the length (H-2), so `textContent` copies nothing and layout reads the same bytes. A script string assigned to the DOM is copied once into the arena; the copy rate is published, as the footprint spec asks. Buffers the HTML and XML parsers produce are adopted by the arena without copying ([ST 9.5][ST]), so parsed text is stored exactly once from the network to layout.
- **What is measured.** The JS-M0 spike measures one metric across every copy of node structure: bytes per node over node columns, rare data, wrappers that exist, text and any remaining data-plane state, plus the node space's share of GC time. JS-D4 lists the alternatives and the reversal trigger. No modern engine has measured these designs against each other ([GC 14][GC]).

### 6.2a Representation choices, derived (M-1 part 3)

The representation layer resembles what the shipping engines converged on. M-1 part 3 requires that it be derived, not inherited, so each choice below starts from properties of JS programs and of the hardware, names an alternative, and names the evidence that decides it. Izcal's names are its own.

| Choice | Derivation from first principles | Alternative considered | What decides it |
|---|---|---|---|
| **Low-bit tag, small integers with tag 0 and 31 bits** | References are 8-byte aligned, so a 32-bit offset has spare low bits; one is enough to separate integers from references. With tag 0, adding or subtracting two tagged integers is one machine add whose overflow flag decides exactness, so integer arithmetic needs no untagging. riscv64 has no flags register, so there the add is followed by an explicit check (a 32-bit and a 64-bit add compared, about three instructions); that is a per-ISA cost, measured at the JS-M0 spike, not a property of the tag ([RV 7.5][RV]). Immediates such as `undefined` need no tag because they are static roots at fixed offsets (Section 6.1). Array indices, loop counters and lengths below 2^30 dominate integer use (first principles; measured below) | No integer tag (every number boxed or a raw double in a 64-bit slot); a 2-bit tag with 30-bit integers and a second immediate kind | Share of integers outside the 31-bit range, and of boxed numbers, on the corpus at the JS-M0 spike; JS-D1's heap-number trigger |
| **Element layouts in a monotone lattice** (packed or holey; small integer, double, tagged) | Arrays in real programs are mostly homogeneous; storing doubles raw avoids a box per element, and a hole marker is only needed when holes exist. If layouts only ever move to a more general one, an IC that saw a layout stays valid for all more specific inputs and no backward transition has to be checked | One generic tagged layout, with raw double storage only for typed arrays | The element-layout distribution on the corpus (Q-JS-9) at JS-M1; if more than 90%† of element reads see the generic layout, the lattice collapses to two layouts |
| **Fact cells** | Prototype chains and globals change rarely after start-up, so checking them on every access wastes work in proportion to chain length. A per-fact cell lets code depend on exactly the facts it used and be invalidated when one changes | Guard the whole prototype chain on each access; or one global epoch that invalidates all code on any prototype change | Invalidation rate and the cost of registrations on the corpus at JS-M2; the assumption ledger requires one of guard or registration either way |
| **Table mode** | Objects used as dictionaries add and delete many keys; with shapes alone, each add creates a transition, so the shape tree grows without bound and ICs never stabilize. Above a threshold of deletions or keys, a hash table per object is cheaper | Shapes only, with shape-tree pruning by the GC; or hash tables only (no ICs) | Shape-tree growth and IC hit rate on the corpus; the threshold is set from measurement at JS-M1 |
| **Probe table for megamorphic sites** | A site that sees many shapes cannot afford a per-site list; a small direct-mapped table keyed by (shape, key) answers most lookups in a few loads without per-site memory | A generic lookup on each access; larger per-site polymorphic lists | Megamorphic hit rate and memory on the corpus at JS-M2 |
| **Register bytecode with an accumulator** | About 47% fewer executed instructions for about 25% more bytecode than a stack machine ([VEE 2005](https://usenix.org/legacy/events/vee05/full_papers/p153-yunhe.pdf)); the accumulator keeps most operands implicit, which shrinks the encoding | Stack bytecode (SpiderMonkey, [HP 11.2][HP]) | Bytecode size and T0 dispatch counts on the corpus at JS-M2 |
| **A baseline that shares the interpreter's frames** | Sharing frames makes tier changes in both directions a matter of which code runs, not of rebuilding frames, and lets deoptimization target one frame layout | A baseline with its own frames (and its own deopt path) | Deopt and OSR cost at JS-M3 |

These choices are checked against M-1 part 3 in Section 7. Where the evidence above contradicts a choice, the alternative is adopted; similarity to another engine is never a reason in either direction.

### 6.3 Bytecode, interpreter and the tiers generated from one description (JS-D5)

**Front end.** `hg-js-syntax` is a hand-written recursive-descent parser with cover grammars and the spec's early errors, anchored to the grammar productions it implements. It parses lazily: a fast preparser checks inner functions, and full compilation happens on first call. Parsing and bytecode generation of a script run off the main thread while it downloads, and the result is installed at a task boundary (Section 6.9). V8 measured about 40% less main-thread parse and compile time from moving this work off-thread ([V8](https://v8.dev/blog/cost-of-javascript-2019)). Its oracle is the spec grammar: grammar-derived generated tests, test262's parse-phase negatives, and ESMeta's spec-synthesized parser as a differential (JS-D9).

**Bytecode.** A register machine with an accumulator and variable-width operands (8-bit by default, with wide prefixes), with scopes resolved statically where the spec allows (derivation in Section 6.2a). Bytecode, constant pools and IC slot indices are one compact, position-independent format that the code cache and startup image store as is.

**Bytecode verifier.** Before any bytecode runs, a linear verifier checks register bounds, jump targets, operand kinds, IC slot indices and stack-height invariants, and the verified bytecode is then stored in the **trusted region** (JS-D16), where no mutator write can reach it. The interpreter and baseline assume only what the verifier proved, and that is sound because the proof and the bytecode cannot drift apart: the alternative, bytecode in the cage, would make verification a time-of-check, since a register operand indexes the native frame outside the cage. Bytecode loaded from the code cache or an image is verified again before it enters the trusted region. CVE-2022-4262 ("incorrect bytecode generation", exploited) is the class this closes: a generator bug becomes a verifier rejection, not an interpreter that trusts bad bytecode ([P0 RCA list](https://googleprojectzero.github.io/0days-in-the-wild/rca.html)).

**The one semantic description.** Every bytecode operation, Wasm instruction, IC operation and DSL builtin is written once, in Izcal's **operation description language** (`.hgop` files). A description states, for one operation: its operands and their representations; its fast paths and guards; its slow path as a call into the runtime; whether it can allocate, throw, call user code or reach a host hook; its effect on the frame; its deopt and safepoint points; and the ECMA-262 or Wasm steps it implements (a spec anchor per path). The language is small and total: no unbounded loops except through runtime calls, no raw memory access except through typed heap operations, so each description has an SMT encoding.

`hg-opgen` (a tier T tool) generates from these descriptions:

| Output | Used for | Evidence that this shape works |
|---|---|---|
| **Reference interpreter** in plain Rust | Differential testing of every tier; bring-up on new ISAs; Miri runs | Readable executable semantics; ESMeta and SpecTec show spec-shaped interpreters pass the suites ([SP 10.1][SP]) |
| **Production interpreter (T0)** as assembly per ISA (x86-64, AArch64 and riscv64, all three from the start), with a fixed register assignment across handlers, fast paths in registers, slow paths out of line and next-instruction pre-decode | Every renderer; the whole jitless profile | Pall's argument ([lua-l](http://lua-users.org/lists/lua-l/2011-02/msg00742.html)); offlineasm ([WebKit](https://webkit.org/blog/10308/speculation-in-javascriptcore/)); AsmInt, which with a new regex engine and other work gave 1.37–1.69× ([Ladybird](https://ladybird.org/newsletter/2026-03-31)); Deegen's generated interpreter was 28% faster than LuaJIT's hand-written one (geometric mean, faster on 31 of 34 benchmarks; [Xu](https://sillycross.github.io/2022/11/22/2022-11-22/)). The machine-code validator runs over the generated interpreter at build time (Section 6.7) |
| **Baseline stencils (T1)**: copy-and-patch machine-code templates per operation, sharing the interpreter's frame layout and IC slots | Warm functions | Copy-and-patch compiled 4.9–6.5× faster than Liftoff ([Xu and Kjolstad](https://arxiv.org/abs/2011.13127)); Deegen's baseline compiles 19.1 M bytecodes/s ([Xu](https://sillycross.github.io/2023/05/12/2023-05-12/)); Sparkplug kept interpreter frames ([V8](https://v8.dev/blog/sparkplug)) |
| **IC program semantics and the IC interpreter** | ICs in every tier; the IC interpreter is validated at build time like T0 | CacheIR ([de Mooij](https://jandemooij.nl/blog/cacheir/)) |
| **Optimizer operation facts**: effects, possible re-entry into user code, allocation, type transfer, deopt points, and the generic lowering of each operation | T2 | Derived, so the optimizer's side-effect model cannot disagree with the interpreter (CVE-2020-6418's class) |
| **SMT encodings** of each operation's fast paths | Rule verification (Section 6.4) | Arrival's ISA-derived semantics ([OOPSLA 2025](https://www.contrib.andrew.cmu.edu/~bparno/papers/arrival.pdf)) |
| **Fuzzer grammar** and **anchor index entries** | Fuzzilli-class fuzzing; ANC-1 | — |
| **Debugger facts**: which operations may write the heap, call user code or reach a host hook | Side-effect-free evaluation in the debugger (Section 6.10) stops before any operation the facts mark as effectful | Derived from the same effect facts the optimizer uses |

**What is not generated, and why.** The idea was evaluated seriously in both directions:
- **Generating the whole engine from ECMA-262 is not possible today.** ESMeta and SpecTec produce complete, slow interpreters, but no published work derives shapes, ICs, bytecode, register allocation or compressed values from a specification; the gap is representation and optimization, which M-1 part 3 leaves to first-principles design ([SP 10.4][SP]). So `.hgop` describes Izcal's operations over Izcal's representation, anchored to the spec, and spec-extracted models check it from outside.
- **Generating the optimizer by partial evaluation of the interpreter** (Truffle) reached 0.83× V8 on its own benchmarks, but pays warm-up on exactly the short-lived, cold code that dominates real pages ([PLDI 2017 paper](https://chrisseaton.com/truffleruby/pldi17-truffle/pldi17-truffle.pdf), [EX 1, 6.4][EX]). Rejected as T2's construction, kept as a research reversal: if a partially evaluating optimizer matches T2 on JetStream 3's first-iteration score.
- **Meta-tracing** (PyPy) is ruled out by the tracing record in browsers ([EX 6.6][EX]).
- **Speculative transformations** (inlining, escape analysis, range-based check removal, load elimination) are written as rules in a rule language and verified (Section 6.4), not generated.
- **The GC, the parser, regex, Intl and the backend's register allocator** are hand-designed.

**The common-mode risk, stated plainly.** If a description is wrong, every generated tier is wrong in the same way, and differential testing between tiers cannot see it. Independence therefore comes from outside the description: test262, the Wasm suite, WPT, ESMeta's and SpecTec's interpreters, and spec-coverage measurement. Differential testing between tiers catches generator and backend bugs; spec oracles catch description bugs. Both are required (JS-4, JS-5).

**Builtins (JS-D14).** Builtins on hot paths, and every builtin the optimizer may inline (`Array.prototype.push`, `Map.prototype.get`, string and typed-array accessors), are written in the description language, which makes them inlinable, verifiable and anchored, and makes TOCTOU bugs such as a length read before a user callback structurally visible: a description that calls user code must re-validate anything it read before the call, and the generator rejects one that does not. The long tail (for example `Intl` formatting and `Temporal` arithmetic) is plain Rust over the `hg-heap` API.

**Tiering.** Tier-up is a deterministic function of counters (calls, loop back-edges, IC stability), as in JSC, where thresholds scale with function size ([Pizlo](https://webkit.org/blog/10308/speculation-in-javascriptcore/), [EX 7.1][EX]). Compilation runs on background threads and is installed only at deterministic points (Section 6.9). Thresholds are tuned offline against recorded corpus sessions under B1 and fixed per build, so a tiering decision is reproducible from the recording and the build (B1, DET-1); a runtime-learned policy would make tiering depend on history that a recording does not contain.

### 6.4 The optimizing compiler and how its correctness is verified (JS-D6, JS-D7)

**One optimizer, two levels.** T2 is one compiler with one IR, run at **O1** (quick: graph building with IC-program speculation, a few cleanup passes, linear-scan allocation) for functions that are warm but short-lived, and **O2** (inlining, escape analysis, load elimination, range analysis, loop optimizations, a better allocator) for long-running hot code. V8 needed a separate mid-tier (Maglev) because TurboFan's compile cost could not be cut, and is now moving TurboFan's frontend onto Maglev's graph builder ([V8](https://v8.dev/blog/leaving-the-sea-of-nodes)); Maglev itself cut Speedometer energy by 10% ([V8](https://v8.dev/blog/maglev)). Izcal starts where that convergence ends: one IR, one lowering, one verification effort, two pass lists. The reversal trigger is measured: if O1's compile throughput cannot reach 10%† of T1's when O1 first runs the corpus (JS-M2), a separate quick compiler is designed.

**IR.** SSA over a control-flow graph. Every instruction carries an explicit **effect set** from a typed lattice (reads and writes of named heap categories, allocation, may-call-user-code, may-throw, may-deopt), taken from the generated operation facts. Effectful instructions keep their order in the CFG; pure instructions are hash-consed and float, in the acyclic e-graph style that Cranelift measured at about 2% better code for 7–8% more compile time ([Fallin](https://cfallin.org/blog/2026/04/09/aegraph/)). Full equality saturation and a sea of nodes are rejected on the evidence ([V8](https://v8.dev/blog/leaving-the-sea-of-nodes), [EX 8][EX]). The IR is stored as compact, index-based arrays, the property LuaJIT and Turboshaft chose for cache behaviour ([HP 7.8][HP]).

**Speculation and deoptimization.** Speculation comes from IC programs and value profiles. Each speculation is a **guard** with a **frame state** describing how to rebuild interpreter frames, or a **dependency** on a fact cell. Deoptimization is an OSR exit to the interpreter (which shares frames with the baseline), as JSC prefers ([Pizlo](https://webkit.org/blog/10308/speculation-in-javascriptcore/)). A function that deopts repeatedly is recompiled with the failing speculation removed, with exponential back-off as JSC does.

**Return-address discipline (JS-D19).** Shadow stacks (Intel CET, Arm GCS, RISC-V Zicfiss) reject a return to an address that a `call` did not push, and PAC rejects a return address that was not signed in the callee's prologue. A JIT that writes return addresses must therefore forge shadow-stack entries or sign pointers, which is a signing gadget for an attacker. Every frame transition in the engine is designed so that **no return address is ever written or signed outside a prologue and epilogue**:

| Transition | How it works without writing a return address |
|---|---|
| **Lazy deopt** (code invalidated while it is on the stack) | Every call site in optimized code checks one **return status word** after the call returns: "invalidated" (a per-code-object bit set by invalidation) or "exception pending". Either sends it to the deopt or unwind path. The return address is never patched |
| **Eager deopt with inlining** (one optimized frame becomes several interpreter frames) | The deoptimizer reconstructs the frames as data, then **resumes them with genuine calls**: the outermost rebuilt frame reuses the optimized frame's slot and its genuine return address, and each inner frame is entered by a real `call` into a resume stub, so every return address on the stack, and on the shadow stack, was pushed by a call and signed by a prologue. The deopt path is rare, so the nested calls cost nothing measurable (checked at JS-M3) |
| **OSR entry** (T0 or T1 into T2, W0 or W1 into W2 at a loop header) | The frame's own return address is untouched; the frame body is rewritten as data and control jumps to the optimized code's OSR entry, which begins with a landing pad. **OSR exit** is an eager deopt |
| **Exceptions** | Unwinding returns normally through each frame with "exception pending" in the status word, so the shadow stack is popped by ordinary returns; no `INCSSP`-style adjustment and no unwinder that skips frames |
| **Stack-segment switch** (JSPI, Stack Switching) | Each segment has its own shadow stack, created by the OS and switched with the architecture's switch instructions, never written by the engine (Section 6.6) |

The machine-code validator checks the discipline (Section 6.7): no shadow-stack write, shadow-stack pointer change or pointer-signing instruction outside the standard prologue and epilogue in any generated function or in the generated interpreters. The status-word check costs a load and a branch per call site in optimized code; JS-15 bounds it with S-7's ≤2% (Q-JS-14). V8's CFI plan treats the backward edge for a JIT as an open design problem ([V8 CFI](https://v8.dev/blog/control-flow-integrity), [SE 4.9][SE]); this discipline is Izcal's answer, stated as first principles and tested by JS-15's probe.

**How correctness is established.** Each mechanism names the exploited class it closes ([SE 2][SE]):

| Class (exploited example) | Mechanism | Strength |
|---|---|---|
| Side-effect modelling (CVE-2020-6418) | Effects come from the generated operation facts; no pass may assume an effect set narrower than the facts give | By construction |
| Missing invalidation (CVE-2020-16009, CVE-2021-30632) | **Assumption ledger**: each compilation records every fact it assumed; at the end a checker verifies that each fact is covered by a guard on every path or by a dependency registration, or the compilation is discarded | Checked per compilation |
| Range analysis and bounds-check removal (VeRA's six-year bug; SpiderMonkey's CVE-2025-4919, a Pwn2Own 2025 entry) | Range analysis written in the rule language and proven sound against the IR semantics with SMT; checks are removed only by verified rules | Verified ([VeRA](https://cseweb.ucsd.edu/~dstefan/pubs/brown:2020:vera.pdf)) |
| Rewrite and lowering errors (Wasmtime CVE-2023-26489) | All rewrites and instruction-selection rules in the rule language; each rule SMT-verified against IR semantics and ISA semantics: Arm's ASL for AArch64, as Arrival does; the Sail RISC-V model, the formal specification RISC-V International adopted, for riscv64 ([RV 7.6][RV]); for x86-64 the best machine-readable specification, chosen at JS-M2 | Verified ([Arrival](https://www.contrib.andrew.cmu.edu/~bparno/papers/arrival.pdf), [Crocus](https://cs.wellesley.edu/~avh/veri-isle-preprint.pdf)) |
| Write-barrier elision (CVE-2021-4102) | Barriers are emitted by lowering; elision only by a verified rule whose premise is "the stored value or target needs no barrier"; the IR verifier rejects a heap store of a tagged value without a barrier or a proof | Verified rule plus IR check |
| Deopt materialization (CVE-2022-1364) | Frame states are checked by a frame-state verifier; in CI and fuzzing a **deopt-everywhere** mode exits at every guard and compares the result with the reference interpreter | Checked plus differential |
| Register allocation and stack maps | Allocation checker (the allocation is validated after the fact, not trusted); stack maps cross-checked by a GC stress mode that moves every object at every safepoint | Checked |
| Anything left | Per-function **translation validation** in CI and fuzzing (bounded SMT, as Alive2 and TurboTV do ([Alive2](https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf))); differential fuzzing against the reference interpreter and ESMeta | Tested |
| Machine code escaping the cage, a buffer or the code table (Winch CVE-2026-34987) | **Machine-code validator** on emitted code and on the generated interpreters (Section 6.7) | Checked per function |
| Data in the cage trusted after a check (bytecode, code-table indices, buffer lengths) | Trusted region, typed code-table entries and buffer-table bounds (Section 6.1, H-2); in-cage corruption fuzzing | By construction, tested |

Since 2020 verification has reached range analysis, IC generators and instruction selection, each time in a compiler designed for it ([SE 6][SE]). Izcal designs every rule language for it from the first rule, so verification coverage is a target (JS-11), not a hope. What remains unverified is stated: the optimizer's heuristics (which can cost speed but not soundness), the register allocator's choices (validated, not proven) and the generator itself (covered by the spec oracles).

### 6.5 One GC for JavaScript, Wasm GC and the DOM (JS-D2, JS-D3)

**One heap per agent.** JS objects, Wasm GC structs and arrays, and DOM nodes (through the node space, Section 6.2) live in one agent heap, traced by one collector, with one barrier discipline. HGBA-2 4.2 already requires shared GC objects for Wasm GC, JSPI and WebIDL; the history of two memory managers (Gecko's cycle collector, Blink's object grouping, WebKit's opaque roots) is the reason to go further and remove the DOM's separate manager altogether ([GC 4][GC]). Cycles between JS, DOM and Wasm are ordinary cycles. Style, layout and the semantic plane never read the cage; they read the node columns during a flush, while the script thread is blocked (B4 as restated in Section 6.2), so phase workers need no GC coordination at all.

**Collector (JS-D3).** The design follows the best published total-cost results ([GC 1–2][GC]):

| Part | Design | Evidence |
|---|---|---|
| Allocation | Per-agent bump allocation in a nursery; large objects in a non-moving space | — |
| Young generation | **Copying nursery**, parallel stop-the-world scavenge | V8's copying nursery beat its mark-sweep nursery by late 2025 ([Wingo](https://wingolog.org/archives/2025/11/13/the-last-couple-years-in-v8s-garbage-collector), Medium); generational ZGC used ¼ of the heap for 4× the throughput of non-generational ZGC on Cassandra ([JEP 439](https://openjdk.org/jeps/439)) |
| Old generation | **Mark-region** (Immix blocks and lines) with **opportunistic evacuation** of fragmented blocks, which precise roots make possible | Immix: +7–25% over canonical collectors ([PLDI 2008](https://www.steveblackburn.org/pubs/papers/immix-pldi-2008.pdf)) |
| Old marking | Incremental and concurrent, snapshot-at-the-beginning, parallel helpers; a **field-logging write barrier**; **no read barrier** | Field-logging barrier 1.6% average ([LXR](https://www.steveblackburn.org/pubs/papers/lxr-pldi-2022.pdf)); read barriers cost as little as 5.4% against 0.9% for write barriers ([ISMM 2012](https://www.steveblackburn.org/pubs/papers/barrier-ismm-2012.pdf)) |
| Sweeping | Lazy and concurrent; finalization-free (below) | Background sweeping cut Oilpan main-thread sweep time ~42% ([V8](https://v8.dev/blog/high-performance-cpp-gc)) |
| Pacing | Allocation debt in **canonical units** (Section 6.9); heap growth from one knob per heap, whose values per page state, minimum trigger and nursery bounds the footprint spec sets ([FP 6.20.2][FP]), bounded by the broker-granted heap limit, which is identical on every device (FP-D19, [FP 6.20.4][FP]) | Go's single-knob model ([Go GC guide](https://go.dev/doc/gc-guide)) |
| Idle work | Marking and sweeping increments in frame gaps, scheduled by the event loop | V8 idle-time GC: Gmail idle heap −45% ([V8](https://v8.dev/blog/trash-talk)) |

The measured alternative is **LXR**: reference counting with coalescing in short stop-the-world pauses plus a backup trace, which beat G1 by 4% and Shenandoah by 43% in throughput ([LXR](https://www.steveblackburn.org/pubs/papers/lxr-pldi-2022.pdf)). It was measured on server JVM workloads, not on many small browser heaps ([GC 14][GC]), so it is a JS-M3 experiment on the corpus, not the starting design. Concurrent copying with read barriers (ZGC, Shenandoah) is rejected: lower pauses did not give lower request latency, and on one workload (lusearch at 1.3× heap) Shenandoah's throughput was 7× lower than G1's ([LXR Table 1](https://www.steveblackburn.org/pubs/papers/lxr-pldi-2022.pdf), [GC 1.3][GC]). GC is judged by total cost (time, cycles and energy over a lower bound, as Cai et al. measure ([ISPASS 2022](https://arxiv.org/abs/2112.07880))) and by frame-time tails, never by pauses alone (JS-40, JS-41).

**Rooting: precise everywhere (JS-D2).** The rejected option is conservative scanning of Rust frames, which Riptide and Oilpan use and V8 has spent a decade trying to adopt ([GC 5][GC]). It costs only 2–3% in a mark-region heap ([OOPSLA 2014](https://www.steveblackburn.org/pubs/papers/consrc-oopsla-2014.pdf)), but it pins objects, it gave page script an address oracle that Chromium closed WontFix ([The Register](https://www.theregister.com/2021/02/26/chrome_aslr_bypass)), and it makes liveness depend on stale stack contents, which differ by compiler, ABI and register allocation, so GC-observable behaviour would no longer be a function of inputs (DET-1, [GC 5.4][GC]). Izcal owns every frame kind, so it can be precise in all of them:

| Frame kind | Roots found by |
|---|---|
| Rust runtime code | The `Mutator` token API and root scopes (below) |
| Interpreter and baseline frames | One frame layout; every register slot is a tagged 32-bit value, so the frame is scanned exactly |
| Optimized frames | Stack maps emitted by the register allocator at every safepoint (calls, allocations, loop back-edges) |
| Wasm frames | Stack maps from the Wasm tiers; reference-typed locals only |

**The Rust API, as a sketch** (names illustrative, not an interface freeze). Every handle type carries the heap's brand `'h` (JS-D18):

```rust
/// One per agent heap. !Send, !Sync. Exists only inside `Heap::enter(|m| ...)`, whose
/// closure is generic over a fresh, invariant brand 'h: no two heaps share a brand.
/// Holding `&mut Mutator<'h>` is the only way to allocate, run script or reach a GC point.
pub struct Mutator<'h> { /* invariant in 'h */ }

/// An unrooted reference into heap 'h, valid only while the shared borrow 'm of the
/// Mutator lives. Copy, invariant in 'h and 'm, !Send, 4 bytes (a compressed reference;
/// the cage base is per process, so dereferencing needs no per-heap base).
pub struct Gc<'h, 'm, T: Trace> { /* compressed reference */ }

/// A rooted reference: a slot in a root scope of heap 'h. Survives GC points (the
/// collector updates moved objects through the scope) and cannot outlive scope 's.
pub struct Root<'h, 's, T: Trace> { /* scope slot index */ }

/// A traced field inside a heap object. Its storage (an atomic 32-bit slot) is private,
/// and no public method takes `&Field`: fields are reached only through projections
/// that #[derive(Trace)] generates on a branded `Gc`.
pub struct Field<T: Trace> { /* AtomicU32 */ }

// Generated by #[derive(Trace)] for `struct Node { next: Field<Node>, .. }`:
impl<'h, 'm> Gc<'h, 'm, Node> {
    pub fn next(self, m: &'m Mutator<'h>) -> Gc<'h, 'm, Node>;
    pub fn set_next(self, m: &Mutator<'h>, v: Gc<'h, '_, Node>);   // barrier inside; no GC
}

impl<'h, 's, T: Trace> Root<'h, 's, T> {
    pub fn get<'m>(&self, m: &'m Mutator<'h>) -> Gc<'h, 'm, T>;
}

/// Initial field values for `alloc`: roots and scalars only, never a `Gc`, so that
/// `alloc` can take `&mut Mutator`. Fields are written after allocation, into an object
/// that no other code can see yet.
pub struct Init<'h, 's, T: Trace> { /* generated per type */ }

impl<'h> Mutator<'h> {
    pub fn alloc<'s, T: Trace>(&mut self, s: &Scope<'h, 's>, init: Init<'h, 's, T>)
        -> Root<'h, 's, T>;                                                          // GC point
    pub fn call<'s>(&mut self, t: &mut ScriptToken, s: &Scope<'h, 's>, f: Root<'h, 's, Function>,
                    args: &[Root<'h, 's, Value>]) -> Completion<'h, 's>;             // GC and script point
}

/// Trace is implemented only by `#[derive(Trace)]` (hg-heap-derive) or inside hg-heap.
pub unsafe trait Trace: 'static { /* generated */ }
```

**Soundness argument.** The claim: **no safe Rust code using this API can read a freed or moved object, store an untraced or cross-heap reference into the heap, or skip a barrier.** It rests on eight steps; steps 1–6 are enforced by the Rust type checker, 7–8 by checks that run in CI:

1. **GC happens only at GC points, and every GC point takes `&mut Mutator<'h>`.** The collector's entry points are private to `hg-heap` and are reached only from `alloc`, `call`, explicit safepoints and the event loop's idle and freeze hooks, all of which take `&mut Mutator<'h>`.
2. **Every unrooted `Gc<'h, 'm, T>` carries the shared borrow `&'m Mutator<'h>`.** By Rust's aliasing rule (shared xor mutable), no `&mut Mutator<'h>` can be taken while any `Gc<'h, 'm, T>` is live. So no unrooted reference survives a GC point of its own heap, and the collector may move or free anything not reachable from roots.
3. **Values that cross a GC point are `Root<'h, 's, T>`**, indices into a per-mutator root scope that the collector enumerates and updates. Scopes nest by closure (`m.scope(|m, s| …)`), so a root cannot outlive its scope; the scope lifetime is generative, so roots from different scopes cannot be confused, and the brand `'h` keeps roots of different heaps apart.
4. **Heap edges are `Field<T>`, reachable only through generated projections.** A projection takes a `Gc<'h, 'm, Obj>` and a `&Mutator<'h>` with the same brand, and its setter accepts only a `Gc<'h, '_, T>`, so a store can neither skip the barrier nor create a cross-heap edge. A heap object type is `'static` and cannot contain a `Gc` or a `Root`, because both carry non-`'static` lifetimes, so an unrooted or scope-bound reference cannot be stored into the heap by mistake. This is the hole Nova found when covariant handles were written into the heap ([Nova](https://trynova.dev/blog/garbage-collection-is-contrarian)); `Gc` is invariant in `'h` and `'m`, and `Field` erases both, so it does not arise.
5. **Tracing is complete because `Trace` is generated.** `Trace` is an `unsafe trait`; the derive enumerates every field and refuses types that hold `Gc`, `Root`, raw pointers, `TokenCell` or a non-trivial `Drop`, which carries CS-V8-9's `GcPayload` rule over unchanged. A hand-written `impl Trace` outside `hg-heap`'s inventoried modules is a lint error (G5, CS-TY-13).
6. **Heaps do not mix, on one thread or many.** Every handle type carries the invariant brand `'h` from a generative `Heap::enter`, so reading a field through another heap's mutator, storing a reference of heap A into an object of heap B, and reading a root of heap A through heap B's mutator are type errors, even when both heaps run on one thread. `Gc` and `Root` are `!Send`. Dereferencing a `Gc` uses the process's cage base (JS-D17), so it is unambiguous with several heaps on a thread. As defence in depth, every GC point asserts in debug builds that the mutator's heap is the thread's current heap.
7. **Generated machine code obeys the same rules**, checked rather than typed: the IR verifier rejects tagged heap stores without barriers or a verified elision rule; stack maps are checked by the stress mode that moves every object at every safepoint; the reference interpreter compares results.
8. **The unsafe core is small, inventoried and checked, and its conditions hold under arbitrary cage contents (H-2).** It is the allocator, the tracer and evacuator, `Field` storage, root scope storage, the node space, decompression and the stack-map walker. Each module states its verification condition in the style RustBelt gives for unsafe libraries that extend safe Rust ([RustBelt](https://plv.mpi-sws.org/rustbelt/popl18/paper.pdf)), for a heap whose contents may have been written by an attacker: wrong answers are allowed, accesses outside the cage, its side tables or a checked table entry are not. Each runs under Miri with a test collector that moves every object on every allocation, under Kani harnesses for barrier and remembered-set invariants, under loom and TSAN for the concurrent marker (below), and under the in-cage corruption fuzzer (Section 6.1); debug builds run a heap verifier after every GC.

The cross-heap cases (read through the wrong mutator, store across heaps, root through the wrong mutator, `Gc` dereference with two heaps on a thread) are compile-fail tests in JS-M0's re-run of the CS-D3 criteria and planted bugs in JS-10.

**The concurrent marker's data-race protocol.** `Field` setters mutate through a shared borrow while marking threads read the same slots, so the protocol is part of the design, not an implementation detail:
- **Slots are atomics.** Every traced slot (`Field`, interpreter frame slots scanned concurrently, node-column links and external traced slots) is an `AtomicU32`. Mutator stores and marker loads are `Relaxed`; the write barrier logs the old value once per field per cycle (field-logging SATB) into a buffer published with `Release` and drained by markers with `Acquire`. Objects allocated during marking are allocated marked, so a marker never reads the fields of an object initialized during the cycle.
- **No slot is reinterpreted in place while marking is active.** A layout change that alters a slot's representation (double to tagged, an in-object field becoming raw, a move to table mode) first claims the object with the same compare-and-swap the marker uses to claim an object for scanning; if the marker has not scanned it, the mutator scans it under the old layout, then changes it. The marker therefore never reads a slot under a layout other than the one it was written with.
- **The rope cache** (Section 6.13) is written with a `Release` store and read with `Acquire`; the write is idempotent, so a race between two flattenings is benign.
- Each rule is a loom model and a JS-10 planted bug (a non-atomic slot store, an in-place reinterpretation, a relaxed rope publish).

**Relation to `TokenCell` and CS-D3.** Two tokens, with two jobs. `Mutator` guards **GC references**: an unrooted reference cannot survive a GC point. `ScriptToken` guards **Rust state outside the heap that script can reach** (the DOM side tables, binding state), held in `TokenCell<T>` (CS-D3 (a), CS-TY-10): no borrow can survive a call that can run script. Running script takes both; allocating takes only `&mut Mutator`, which keeps Q-CS-7's ruling ("allocation does not take the token") and adds the GC token that a moving, precise collector needs. The CS-D3 spike's finding that "the scope cannot be the token" was about V8's per-callback `PinScope`; with Izcal's own API the scope and the tokens are designed together, and the spike's five soundness criteria are re-run against `hg-heap` at JS-M0 (Section 9.5).

**Ergonomics.** Lifetime-scoped handles need explicit rooting around every GC-capable call; Nova describes the result as "a soup" of bind and unbind calls and publishes no count ([Nova](https://trynova.dev/blog/garbage-collection-is-contrarian)). Izcal moves most GC-touching code into generated code: DSL builtins, bindings from `hg-webidl-codegen`, field projections and IC generators all get their rooting from the generator. Hand-written Rust that touches GC references is limited to the runtime core and the long-tail builtins, and JS-M1 counts its rooting sites per thousand lines as an ergonomics measure (Section 10).

**Finalization and DOM cleanup.** No GC object has a `Drop`. When the sweeper finds a dead object or node slot that owns an outside resource (a node's columns and side-table slots, a text buffer, a buffer-table entry, an external-table or trusted-table entry), it records the ID in a per-heap release list. The sweeper and the collector never touch side tables themselves. The owning thread processes the list only at **event-loop points between tasks**, never inside `alloc`, `call` or any other GC point, and the processing function takes `&mut ScriptToken`, so no `TokenCell` borrow of a side-table slot can be live while the slot is freed. Releasing a node slot also **notifies `hg-style` and `hg-box-tree`**, which clear their per-slot entries (computed style, the node-to-box entry) before the slot's generation is bumped and the slot reused, so no later node inherits a dead node's style or box ([ST 9.5][ST], [LY 9.5][LY]). This replaces Stage 1 5.2's `cppgc` prefinalizer and keeps CS-V8-9's discipline: release is integer work, never a walk of the heap. CS-TY-10's planned M2 test ("allocates under a live `TokenCell` borrow with GC stress on") runs with a non-empty release list.

**Weak references and finalization.**
- **Ephemerons** back `WeakMap` and `WeakSet`; marking runs them to a fixpoint, as the spec requires ([ECMA-262 §9.9](https://tc39.es/ecma262/#sec-weakref-processing-model)).
- **`WeakRef.prototype.deref`** adds its target to the agent's `[[KeptAlive]]` list, which the host clears through `ClearKeptObjects` when a synchronous run ends.
- **Clearing** of weak targets happens only when a **canonical** GC cycle finishes, at a decision point that is deterministic or recorded (Section 6.9, JS-D15). All `WeakRef`s, registry cells and weak-collection entries that could observe a non-live set are cleared together, as §9.9.3 requires.
- **Collections forced by real memory are unobservable.** A nursery that fills by real bytes before a canonical trigger, a collection forced by OS pressure and any scavenge treat weak targets as strong, keep ephemeron entries and enqueue no cleanup; a young `WeakRef` target survives a scavenge and is cleared only by a canonical cycle. Only canonical cycles clear weak references. A DST case forces real-memory collections at random points and checks digests (JS-50).
- **FinalizationRegistry cleanup** is never run by the engine directly: the engine calls `HostEnqueueFinalizationRegistryCleanupJob`, and the host posts the job on the seeded scheduler. Replay.io's workaround (leak finalizable objects during recording) is unnecessary ([Replay](https://www.replay.io/blog/effective-determinism)).
- **Escape analysis** never removes an allocation whose reference reaches a `WeakRef`, a registry or a weak collection, and canonical allocation accounting (Section 6.9) charges removed allocations anyway, so optimization cannot change when weak targets clear.

**Accounting: two canonical measures, never mixed.** GC debt is counted in **canonical allocation units**: each operation that semantically allocates charges a size fixed by its description. Engine-internal allocation (shapes and transition tables, feedback, compiled-code metadata, rope flattening, interned atoms, table growth, lazy compilation and recompilation after a flush) **never counts toward GC debt**, because it depends on the tier and on timing; if it did, flushing and rebuilding engine data would shift GC timing and `WeakRef` clearing. All memory, engine-internal included, is charged in the footprint spec's two canonical byte measures ([FP 6.2][FP]), both counted in 16 KiB granules with ledger tags per realm and script: **canonical committed bytes (CC)**, the granules committed through `Memory::commit` and not yet decommitted, which predict Windows commit charge; and **canonical touched bytes (CT)**, the granules an allocator has handed to use since their last purge plus the nursery's and each stack segment's high-water mark since their last trim, which predict charged memory on Linux and macOS, where the OS bills touched pages, not commits. CT and CC drive footprint gates and budgets but no JS-observable decision. Neither GC debt nor CT and CC depend on the ISA once machine code is excluded: GC debt is semantic, and the CT and CC of machine code are reported separately per ISA and tier ceiling.

**Limits and real exhaustion.** Every JS-visible allocation failure is decided canonically: `ArrayBuffer` and `SharedArrayBuffer` allocation and growth, `memory.grow` and `table.grow` and the heap limit are checked against the broker-granted limit in canonical units, and fail with the error the specifications define. The limits are **identical on every device** (FP-D19: 4 GiB† per agent heap and 16 GiB† of buffer and linear-memory backing per process, [FP 6.20.4][FP]), so a JS-visible allocation failure depends only on what the page allocated and is never a fingerprint of the device's memory; device memory is protected by the footprint spec's pressure ladder, whose actions are not JS-visible. If real memory runs out first, the renderer process crashes (allowed for a tier R process); a JS-visible difference that depends on real memory is not allowed.

**Returning memory, flushing engine data, and pressure.** Engine data falls into two classes (the resource-footprint critique's split, applied here):
- **(a) Stores no running mutator can reach**: free heap blocks, the unused part of stack segments, empty large-object spaces, the dead agent heaps of a destroyed agent. These can be released off-thread without tracing and without allocating, which is all the engine's pressure hook does at Critical (it runs on the control thread and is allocation-free).
- **(b) Data a running mutator can reach**: bytecode and IC programs in the trusted region, feedback, shapes and machine code. These are flushed only at deterministic points (the end of a canonical GC cycle, the freeze trim, navigation away), never on the Critical path. Bytecode of a function that has not run for N† canonical cycles is dropped and the function returns to its lazily compiled state (its source is kept); machine code not on any stack whose function has passed its own age threshold is dropped and its code-table entry reset to the next lower tier; feedback goes with the bytecode or the machine code, whichever goes first. N and the machine-code and feedback ages are set per trigger by the footprint spec ([FP 6.20.3][FP]: at the end of a canonical cycle, 8† for bytecode and 4† for machine code and feedback; at a freeze trim, 4† for bytecode and every function not on a stack for machine code and feedback). Because every tier implements one semantics and recompilation is deterministic, flushing is invisible to script, and its trigger is a function of canonical age, or of a recorded B1 pressure input.
- **Shrink on freeze.** A freeze is a B1 input. On it, the engine runs a full canonical cycle with evacuation of fragmented blocks, flushes class (b) data by the freeze policy, decommits the nursery and empty blocks, and trims stack segments to their used part. **On navigation away**, an agent heap whose agent is destroyed is released whole by unmapping its blocks, with no trace, because no other heap can reference it (step 6). The footprint spec schedules both outside pressure.
- **Handshake.** When the reclaim path needs the script thread (class (b) data on a visible page), it posts a safepoint request; the script thread reaches a safepoint at the next interrupt check (loop back-edges, calls, and every iteration of long builtins and regex steps). Its latency is published as part of JS-42.

### 6.6 WebAssembly: tiers that share the backend

| Tier | Design | Evidence |
|---|---|---|
| **Validation** | Single-pass decoder and validator in Rust, anchored to the Wasm 3.0 rules; type canonicalization of recursive groups with explicit, checked limits and internal type IDs that cannot alias | Single-pass validation was a design goal ([Titzer](https://arxiv.org/abs/2205.01183)); CVE-2024-2887's type-index alias ([ZDI](https://www.zerodayinitiative.com/blog/2024/5/2/cve-2024-2887-a-pwn2own-winning-bug-in-google-chrome)) |
| **W0 in-place interpreter** | Runs the original Wasm bytes with a small side table for branch targets; generated from `.hgop` like T0; also the jitless Wasm path | Side table about 30% of code size, against up to 4× for rewriting interpreters ([Titzer](https://arxiv.org/abs/2205.01183)); JSC's IPInt ([WebKit](https://webkit.org/?p=17899)) |
| **W1 baseline** | Single pass over the abstract value stack, emitting the same copy-and-patch stencils family as T1, with streaming compilation during download | Baseline compilers are 3–10× faster than interpreters at run time ([CGO 2024](https://arxiv.org/abs/2305.13241)); Liftoff fixed 30-second startups ([V8](https://v8.dev/blog/liftoff)) |
| **W2 optimizer** | Wasm lowered into T2's IR, non-speculative except speculative inlining of `call_ref` and cast elimination by verified rules; same rules, same backend, same validator. Its only gate is verified rules (JS-11); it needs no recorded IC data | V8 moved its whole Wasm pipeline onto the JS backend's IR ([V8](https://v8.dev/blog/leaving-the-sea-of-nodes)); speculative inlining ~30% on Sheets ([V8](https://v8.dev/blog/wasm-gc-porting)) |

Tier-up is **dynamic** (hot functions only), because eager tier-up took cores from workers and compiled code that never ran ([V8](https://v8.dev/blog/wasm-dynamic-tiering)). Unlike V8's Wasm, which has no OSR ([V8 docs](https://v8.dev/docs/wasm-compilation-pipeline)), Izcal's W0 and W1 support OSR into W2 at loop headers, so long-running loops do not stay in the baseline.

**Validation is checked against the specification.** The SpecTec rules are the source of Wasm 3.0 ([SP 7][SP]). Izcal runs SpecTec's meta-interpreter and the reference interpreter as differential oracles (JS-D9) and aims at a mechanized proof that its validator accepts exactly what the SpecTec typing rules accept, starting with the Wasm 2.0 subset that WasmCert already covers ([WasmCert-Coq](https://github.com/WasmCert/WasmCert-Coq)). That is the right place for Izcal's first verified component: Wasm GC made validation as type-rich as a JIT's type system ([SE 2][SE]).

**Memory and sandboxing.** A 32-bit linear memory gets a reservation large enough that every 32-bit index plus offset lands in the memory or its guard region, so bounds checks are elided by construction; memory64 uses explicit checks. In both cases the machine-code validator checks that every linear-memory access is base plus a zero-extended 32-bit index (or an explicitly checked 64-bit index) — precisely the property whose violation was Winch's CVE-2026-34987 on aarch64 ([GCVE](https://db.gcve.eu/vuln/CVE-2026-34987)).

**Shared object model.** Wasm GC objects are heap objects with layout descriptors (Section 6.1), so `any.convert_extern` and the JS API's GC object behaviour need no wrappers. JS String Builtins operate on Izcal's strings directly. Exceptions (`exnref`) and JS exceptions share one unwinding mechanism.

**Stacks: one model for JS and Wasm (JS-D19).** All JS and Wasm execution runs on **stack segments** (guard-paged, growable by chaining, reserved through the substrate's `Memory` interface, charged only for touched pages) rather than the OS thread stack, which stays small and holds only Rust frames outside script. **The segments live in the substrate**, not in the engine: one audited, inventoried implementation in `hg-substrate-os` (simulated in `hg-substrate-sim`), with its shadow-stack, unwinding and sanitizer support, serves the engine and layout, whose recursive passes run on segments under layout's own canonical stack budget (LY-D15, [LY 6.17][LY], [RN2 Q16][RN2]). This spec owns the mechanism and its per-OS verification below; the substrate owns its placement; layout owns its budget. Wherever this spec adopts JS-D19 (c) on an OS, because Rust frames on segments fail verification there, layout's LY-D15 reversal fires on that OS too and layout uses explicit work stacks with the same budget, so the two decisions are taken per OS together. JSPI suspension and Stack Switching become a segment switch ([SP 6.3][SP]); stack overflow is decided by a canonical limit (Section 6.9); precise scanning walks only engine frames. JSPI is at phase 5 and ships with W0 and W1; Stack Switching is at phase 3 and is implemented when it reaches phase 4, the correctness gate that also holds shared structs back ([SP 6.3][SP]); the segment design serves both from JS-M0.

- **Rust runtime code on segments.** Runtime calls from JS run on the current segment, which reserves headroom for the deepest runtime call; that depth is finite because every recursive Rust path reachable from content has a canonical depth limit (Section 6.9). The alternative, switching to the OS thread stack for every runtime call, costs a switch per call and is the per-OS fallback if verification below fails. On Linux and macOS the fault handler recognizes segment guard pages and Rust's stack probes work against any guard page; on Windows the thread's recorded stack bounds must follow a switch, as fibers do (unverified; JS-M0).
- **A shadow stack per segment, created by the OS.** On Linux x86-64, `map_shadow_stack` with `SHADOW_STACK_SET_TOKEN` creates a shadow stack holding a restore token, written by the kernel, which user code pivots to with `RSTORSSP` ([x86/shstk patch](https://lkml.iu.edu/hypermail/linux/kernel/2307.2/05286.html)). On Linux arm64, `map_shadow_stack` creates a Guarded Control Stack with a cap token, and the architecture provides instructions for switching between them ([kernel GCS docs](https://docs.kernel.org/arch/arm64/gcs.html)). On Linux riscv64 (Linux 7.0 and later), `map_shadow_stack` creates a Zicfiss shadow stack, user code may place its own restore token with `ssamoswap`, and a switch is a token check followed by a write of the user-writable `ssp` CSR ([RV 3.3–3.6][RV]); because the CSR is user-writable, the machine-code validator confines `ssp` writes and `ssamoswap` to the substrate's switch stub (Section 6.18). On macOS arm64 (PAC-RET), a return address is signed with the stack pointer as its modifier, so frames on a segment keep valid signatures as long as a switch restores the exact stack pointer (first principles; verified at JS-M0). The engine never writes a shadow stack itself.
- **Windows: what must be verified at JS-M0.** User-mode Hardware-enforced Stack Protection treats dynamic code as CET-compatible only if it is registered with `SetProcessDynamicEnforcedCetCompatibleRanges`; exception continuation targets in dynamic code are registered with `SetProcessDynamicEHContinuationTargets`; and the `CetDynamicApisOutOfProcOnly` policy makes both callable only from outside the process ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-process_mitigation_user_shadow_stack_policy)). Five questions are open and are JS-M0 exit items: (1) whether user mode may create and switch shadow stacks for engine-managed segments outside the thread and fiber APIs; (2) if not, whether each fiber gets its own shadow stack and what `SwitchToFiber` costs, so that a segment can be a fiber; (3) how JIT code ranges are registered when `CetDynamicApisOutOfProcOnly` is set (by the broker over IPC, at a cost per code region); (4) whether Rust code runs correctly on a segment with the thread's stack bounds updated; (5) whether strict mode can stay on with the JIT. If (1) and (2) both fail, JSPI still ships on Windows: JIT code on switched segments is left unregistered, which makes its shadow-stack violations non-fatal under compatibility mode, and `izcal://sandbox` reports the reduced CFI for that renderer. JSPI is never dropped to keep a CFI feature, and a CFI feature is never silently lost.
- **Exceptions across segments.** Unwinding is return-based inside a segment (Section 6.4). At a segment boundary the exception travels with the switch: the parent segment resumes with "exception pending", so no unwinder crosses segments.

**Wasm for internal components (JS-D10).** HGBA-2 D5 runs extensions and privileged components in a Wasmtime host. Under M-1 2.3.0 a Wasm engine is engine work, and Izcal now has one. The recommendation is a separate **component host process** running Izcal's own Wasm engine with a WASI embedding, which removes HGBA-2's "two code generators and two GC heaps" cost. Native Component Model support (HGBA-2 X-3) then lands in one engine. The component host is not a per-site process, so under CS-ST-10's "declared ≥ computed tier" rule the crates it links compute to **tier P**, which may never panic on any input. It therefore links a separate **tier-P build** of `hg-wasm`, `hg-heap` and `hg-codegen` (feature `tier-p`: overflow checks on, every panic path on untrusted input turned into an error), checked by the coding standard's tier lint, rather than a documented exception (amendment in Section 9.5).

### 6.7 Sandboxing generated code, and the Spectre posture

**Which layer stops which class.** Rust removes classic memory bugs in the runtime, parser and builtins; it does not touch JIT output, GC interface errors, validator logic, Spectre or denial of service ([SE 3][SE]). The engine's layers are therefore:

| Class | First layer | Second layer | Last layer |
|---|---|---|---|
| Memory bug in runtime, parser, builtins | Safe Rust; DSL builtins with no raw memory; checked arithmetic on untrusted sizes (G18) | Cage (H-1); H-2 for any Rust that reads the cage | Process sandbox, I-1 |
| Corrupted cage data trusted outside the cage | Trusted region; typed code-table entries; buffer-table bounds (Section 6.1) | H-2 lint (G17); in-cage corruption fuzzing | Process sandbox |
| GC rooting, barrier, tracing | Token-branded API (Section 6.5) | Heap verifier, GC stress mode, Miri | Cage, process sandbox |
| JIT logic (effects, invalidation, ranges, lowering) | Generated facts, assumption ledger, verified rules (Section 6.4) | Machine-code validator | Cage, W^X and CFI, process sandbox |
| Wasm validation | Validator checked against SpecTec | Machine-code validator (bounds property) | Buffer reservations with guards, process sandbox |
| Bytecode generation | Bytecode verifier | Verified bytecode kept in the trusted region, so the verified operands cannot change | Machine-code validator over the generated interpreter; process sandbox |
| Code injection and reuse | W^X, no RWX ever | BTI or IBT landing pads; shadow stacks or PAC on returns | Jitless tier ceiling where policy requires |
| Spectre | Process isolation (I-1, I-6) | Timer coarsening and SAB gating by the host | In reduced-isolation mode only: index masking, speculation barriers and per-site caches (JS-D20) |
| ReDoS and runaway script | Linear-time regex by default (Section 6.13) | Interrupt checks at loop back-edges and in backtracking | HTML's slow-script handling |

The security scope asks for this table to be published at M7 ([SS 6.8][SS]); for the engine it replaces V8's sandbox as "one layer under the process sandbox".

**W^X with no RWX mapping, ever.** Machine code is written only by `hg-codegen`'s code writer, through a `CodeMemory` interface of the substrate (G3), on a **dedicated code-writer thread identity**: the write permission is per thread on Apple silicon (`MAP_JIT`) and with protection keys, so that thread runs nothing else, in particular no image decoder or other parser of untrusted input; it is created on the first compilation, never at start-up. The trusted region uses the same write window. The mechanism per platform: on Apple silicon `MAP_JIT` with per-thread write protection; elsewhere protection keys (PKU, Arm POE) where the hardware has them; otherwise a **second, writable mapping** of the code pages that exists only while the code writer works. x86-64 and Arm offer no write-only page permission, so that alias is readable and writable, and while it exists it is visible to every thread of the process; the window is kept as short as one compilation's install, and its exposure is stated on `izcal://sandbox`. Each mode depends on syscall filtering, as HGBA-2 I-4 requires: `pkey_mprotect`, `pkey_alloc` and `mprotect` on code and trusted pages are denied to every thread but the code writer's setup path, writes to `/proc/self/mem` are denied, and `mmap` of new executable mappings is denied after start-up (Linux seccomp; the macOS and Windows equivalents are the hardened-runtime entitlement and ACG where the tier allows it). The Pwn2Own 2024 chain wrote shellcode into an RWX Wasm page ([ZDI](https://www.zerodayinitiative.com/blog/2024/5/2/cve-2024-2887-a-pwn2own-winning-bug-in-google-chrome)); JS-15 makes "zero RWX pages" a probe-tested ship blocker.

**Control-flow integrity designed in.** Every indirect branch target in generated code begins with a BTI, IBT or Zicfilp landing pad; calls between JS functions go through the typed code table; no frame transition writes or signs a return address (Section 6.4, JS-D19), so shadow stacks (CET, Arm GCS, Zicfiss) and PAC on return addresses can stay on in renderers that run the JIT, subject to the Windows items Section 6.6 lists for JS-M0. A 2024 WebKit chain targeted only Intel Macs, likely for lack of a PAC bypass ([GTIG](https://cloud.google.com/blog/topics/threat-intelligence/2024-zero-day-trends)). HGBA-2 S-7's bound applies: PKU or POE W^X with CET or BTI costs at most 2% on Speedometer 3 (JS-15). Where the hardware lacks a feature, the renderer reports the tier it achieved on `izcal://sandbox` ([SS 6.7][SS]).

**No constant blinding.** JIT spraying hides gadgets in immediates. Blinding was bypassed in practice, and extending it to small constants would cost up to 80% ([NDSS 2015](https://www.ndss-symposium.org/ndss2015/ndss-2015-programme/devil-constants-bypassing-defenses-browser-jit-engines/)). With landing pads and protected returns, a gadget in an immediate is not a valid branch target. Reversal trigger: a published bypass of landing-pad CFI through JIT immediates.

**The machine-code validator (JS-D7).** A linear-time checker runs over each emitted function before it becomes executable and proves a **sandbox property**: every memory access is to the frame (within the size the code-table entry's parameter count and the frame descriptor allow), to the cage through the cage base register and a 32-bit offset, to the trusted region read-only through a table entry, to a buffer through a base from the buffer table and an index checked **against the buffer table's length** or covered by a reservation that contains every index the access can form (the certificate names which), or to engine data through a fixed table; every indirect branch goes through the code table to a landing pad; no instruction writes the base registers or the stack pointer except in the prologue and epilogue; and **no instruction writes the shadow stack, changes the shadow-stack pointer or signs a pointer** outside the standard prologue and epilogue (JS-D19). This is VeriWasm's idea (verify the output, not the compiler; [NDSS 2021](https://cseweb.ucsd.edu/~dstefan/pubs/johnson:2021:veriwasm.pdf)) made cheap by a compiler that emits a certificate (register roles and access kinds) alongside the code, in the proof-carrying-code tradition ([SE 6.9][SE]). V8's CFI plan reported no JetStream or Speedometer regressions in preliminary tests of validating JIT output ([V8](https://v8.dev/blog/control-flow-integrity)). The validator is small, separate from the compiler, and in the TCB instead of the compiler. It runs **at build time over the generated production interpreters** (T0, W0 and the IC interpreter) and the baseline stencils, which are machine code the engine executes just as much as JIT output, and at run time over every emitted function. JS-D7 recommends running it in production on every tier if its cost is at most 10%† of compile time.

**Out-of-process JIT** (compile in another process and map code read-execute, which lets Windows ACG cover the renderer; Edge's 2017 answer, [SS 6.7][SS]) is the alternative for renderers that need ACG with a JIT. The recommendation keeps Standard renderers in-process and gives ACG to the jitless tier, as SEC-D5 decided; the reversal trigger is a measured out-of-process compile path within 5%† of in-process on JetStream 3's first-iteration score. That comparison needs a build: the out-of-process compile path is a JS-M3 experiment on Windows, so the trigger can fire (it also answers Section 6.6's Windows question 3).

**Spectre posture.** Software cannot mitigate all Spectre variants inside a process, and V8 concluded that "the only effective mitigation is to move sensitive data out of the process's address space" ([V8](https://v8.dev/blog/spectre)). Izcal's renderer normally holds one (site, container), so the engine makes no in-process confidentiality claim and adds no general speculation barriers or index masking to JS. Its duties are narrower:
- never place another site's data in the heap or a cache: no cross-process shared bytecode or string tables except the read-only engine image, which holds only public engine data (I-6 permits read-only sharing);
- read time only through host hooks, so HR-Time coarsening and jitter apply to every clock the page can see;
- expose `SharedArrayBuffer` and `Atomics.wait` only where the host says the agent cluster is cross-origin isolated ([HTML](https://github.com/whatwg/html/blob/main/source), [SP 8.3][SP]);
- where origin keying is off, same-site subdomains share a renderer, and the same-origin policy is relied on between them; the engine adds nothing there and says so ([SS 6.5][SS]). The engine follows the footprint spec's FP-D8, which the owner accepted (origin keying on every desktop class; isolation is never the lever for a memory target), so this case is confined to the device classes FP-D8 leaves out.

**Reduced-isolation mode (JS-D20).** HGBA-2 I-1 allows a documented reduced-isolation mode below a RAM threshold, which the Stage 1 design repeats and which matters for Android (Stage 2). The broker tells the engine at launch, as part of the tier-ceiling grant (Section 6.8), that the process may hold several sites. The engine then: gives each site its own cage and trusted region (JS-D17's multi-site rule); keys every cache per site (probe tables, code cache, atom tables, the shared code space); turns on **Spectre hardening** for JS and Wasm: index masking on bounds-checked accesses, speculation barriers on type checks that guard memory accesses, and no Wasm memory without explicit bounds checks, at a cost measured on the corpus and published (JS-27); and reports the mode on `izcal://sandbox`. The footprint spec's FP-8 aims to make the mode unnecessary on devices of 2 GB† and more; the engine is designed for it anyway, because the mode exists in HGBA-2. Reversal trigger for the default of no in-process hardening: any process that co-locates sites, which switches hardening on for that process.

### 6.8 Per-site tier policy as a capability

The tier ceiling is a **capability of the renderer process**, granted by the broker when it launches the process for a (site, container), and enforced by the operating system, not only by an engine flag:

| Ceiling | JS tiers | Wasm tiers | Executable | OS enforcement |
|---|---|---|---|---|
| **Full** (Standard) | T0, T1, T2 | W0, W1, W2 | `hg-renderer-main` | — |
| **Baseline** | T0, T1 | W0, W1 | `hg-renderer-main` | Engine policy only (code generation still needed); the ceiling is stored outside the cage, read-only after initialization, so an in-cage write cannot raise it (JS-10) |
| **Jitless** (Hardened; Izcal-only renderers) | T0 | W0 | `hg-renderer-jitless-main`, built without the code generator; no library it loads contains it either, so the process never maps it (G14, checked on the loaded-library closure) | macOS: no `allow-jit` entitlement; Linux: seccomp denies `PROT_EXEC`; Windows: ACG and CET ([SS 6.7][SS]) |

**Wasm keeps working without a JIT.** With Edge's JIT off, Wasm was first unsupported and then ran on an interpreter that "might not yield the expected level of performance" ([Microsoft Learn](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-security-browse-safer), [GO 7.1–7.4][GO]); HGBA-2's Hardened profile used DrumBrake, about which an OffensiveCon 2026 talk claims 23 RCE bugs (unverified, [HGBA-2 4.2][H2]). Izcal's W0 is the same in-place interpreter every renderer has, generated from the same descriptions, so the jitless profile adds no new interpreter to defend. The same holds for regex: the jitless ceiling runs the regex automata interpretively.

**Conformance is identical in every ceiling.** All tiers implement one semantics, so test262, the Wasm suite and WPT pass identically jitless (JS-1). Apple's EU rules require that alternative engines meet 90% WPT and 80% test262 when JIT is unavailable ([Apple](https://developer.apple.com/support/alternative-browser-engines/)); Izcal meets its own, higher bar in every ceiling.

**Who sets it (JS-D13).** Defaults come from the container (SEC-D5: the banking container is jitless) and from process kind (Izcal-only renderers are jitless). Users get a per-site setting; enterprise policy gets per-URL lists; the emergency channel (UPD-R5) can lower every renderer's ceiling until a fix ships. Edge's Balanced mode applies to "unfamiliar sites" ([Microsoft Learn](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-security-browse-safer)), judged by an engagement score ([Edge VR](https://microsoftedge.github.io/edgevr/posts/Super-Duper-Secure-Mode/)); Izcal does not adopt an automatic heuristic in Stage 1 because its cost to users is unmeasured, and JS-24 measures what the jitless ceiling costs on the corpus first.

**Budgets as capabilities.** The same grant carries the heap and buffer limits, a CPU budget per renderer and, where it applies, the reduced-isolation flag (JS-D20), so a site's memory and CPU caps are set by the broker rather than inferred inside the process. The heap and buffer limits are **identical on every device** (FP-D19), so the grant reveals nothing about the device and a JS-visible allocation failure is never a device-memory fingerprint; the broker never scales them to device RAM. The numbers and the behaviour at each limit belong to the resource-footprint spec ([FP 6.20.4][FP], FP-35). Because the engine attributes time to scripts (Section 6.10), a cap can deprioritize a script rather than only a frame, unlike Chrome's frame-level heavy-ad intervention ([Chrome](https://developer.chrome.com/blog/heavy-ad-interventions)). Every intervention decision is recorded as a B1 input, so replay reproduces it. All ceiling, budget and policy state lives outside the cage and is read-only to the mutator after initialization; the emergency channel (UPD-R5) lowers a ceiling through the broker, never through state script can reach.

### 6.9 Determinism by construction (B1)

**The rule: concurrency and heuristics may change when work is done, never what is decided.** Everything JS can observe is a function of the inputs B1 records (clock readings, entropy streams, network bytes, scheduler choices, host events, and the engine's own recorded decision points) and of the engine build. That holds in the **production configuration**, so the DevTools recording configuration and the shipping configuration become the same engine configuration.

**Decision points (JS-D15).** A decision point is a moment where the engine applies the result of work whose timing depends on other threads: installing compiled code, finishing a GC cycle (and so clearing weak references), installing an off-thread parse, applying a pressure signal. Draft 0.1 fixed each decision point at a position in canonical units and made the main thread wait for late background work. That makes results a pure function of the inputs, but the wait is unbounded by anything in the design and lands on the main thread, against JS-40 and U2. 0.2 makes **each decision point a recorded B1 input** instead:
- **Production.** Work is applied at the first safepoint after it is ready. The main thread never waits for a background thread. When the session is being recorded, the canonical position (agent, progress counter) at which each decision was applied is logged, at the cost of one log entry per decision.
- **Replay.** The replay host applies each decision at its logged position, waiting for its own background work if needed. Replay is not interactive, so the wait costs nothing that matters.
- **Simulation (DST).** Background threads run on the seeded scheduler (Stage 1 3.3), so "ready" is itself a function of the seed and the decisions are reproducible from the seed alone; JIT speed does not matter under the virtual clock.

**One consolidated list, one recording budget ([RN2 Q15][RN2]).** JS-D15 is the rule for the whole renderer, not only the engine. Each spec owns its decision points and lists them as complete; together they are the consolidated list below, and adding a point is a change to the owning spec:

| Owner | Recorded decision points and inputs |
|---|---|
| JS engine (this spec) | Compiled-code installation, GC-cycle completion and weak clearing, off-thread parse and code-cache installs, pressure signals, intervention decisions (Section 6.8), real-time worklet installs at quantum boundaries (Section 6.12) |
| Layout ([LY 6.1][LY]) | Viewport and **visual viewport** size, scale and offset; device scale and zoom; compositor scroll deltas; image natural sizes from the first decoded header; web-font installations; out-of-process frame geometry and visibility; the print environment; lazy-load fetch starts and viewport-driven priority updates; frame-boundary state capture |
| Graphics ([GR 6.21][GR]) | BeginFrame ticks; canvas command-log snapshots and readback completion; the switch to content-process-only; chunk resend; the listener timeout; `will-change` expiry; `requestVideoFrameCallback` metadata |
| Images and media ([MD 6.13][MD]) | Decode completion, cache hits, header results, frame selection, hardware-or-software choice, autoplay decisions, ManagedMediaSource evictions, WebCodecs output timing (per-frame entries batched per composited frame) |
| Fonts and text ([TX 6.11][TX]) | Font installations at task boundaries; session-image identity and manifest versions |

All of them share **one whole-renderer recording budget**, HGBA-3 DET-1's ≤ 1%† of p95 frame time, which JS-52 measures jointly and attributes per subsystem; LY-40's 1%† and media's measured share are shares of it, and graphics reports its own share. The engine's log format carries every subsystem's entries in one ordered stream keyed by (agent, progress counter), so replay applies a layout or media decision at the same canonical position as an engine decision.

What this gives up: two **unrecorded production runs** from the same inputs may install code or clear weak references at different points. Nothing relies on that: DET-1 and JS-50 are defined over recordings, exact profiles and leak diffs run on replays (Section 6.10), and DST runs in simulation. Tier installation is made reproducible even though every tier implements one semantics and script cannot see which tier ran; the reason is to **reproduce engine bugs** and to replay performance exactly, which is a different reason from correctness, and recording the decision is its cheapest design. JS-D15 keeps the forced-wait design and a hybrid as alternatives.

| Source of non-determinism ([GO 5.1][GO], [SP 1.5][SP]) | How it is pinned |
|---|---|
| `Math.random` | A per-realm generator seeded from a named B1 entropy stream; each realm gets a distinct sequence, as ECMA-262 requires ([§21.3.2.28](https://tc39.es/ecma262/#sec-math.random)) |
| `Date.now`, `performance.now`, Temporal's current time | Host hooks only (HostSystemUTCEpochNanoseconds once Temporal merges, and the HTML clocks), which read the substrate clock; no engine code reads an OS clock (G13) |
| Hash seeds (property tables, Map and Set) | One key per process from B1 entropy (CS-AS-2); image tables are perfect hashes over fixed keys (Section 6.1); iteration order of JS collections is insertion order by spec, never hash order |
| GC triggers | Counted in **canonical allocation units**: each operation that semantically allocates charges a size fixed by its description, whether or not the tier actually allocated (escape analysis does not change the count); engine-internal allocation never counts (Section 6.5); never OS pages, real sizes or wall time |
| GC completion, weak clearing, finalization | A cycle **starts** at a canonical trigger and marks snapshot-at-the-beginning, so its result depends only on the heap at the snapshot. It **finishes** at a decision point (JS-D15), recorded when recording. If marking falls behind allocation, pacing gives the mutator bounded marking increments within JS-40's pause budget; it never finishes the whole cycle synchronously. Cleanup jobs go through the host's seeded scheduler |
| Collections forced by real memory | Unobservable: weak targets kept, no cleanup enqueued (Section 6.5) |
| Memory pressure | OS pressure signals are B1 inputs, recorded and replayed; heap and buffer limits are canonical (Section 6.5) |
| Tier-up | Decided by counters; compiled in the background; **installed** at the first safepoint after compilation finishes, as a decision point (JS-D15). All tiers implement one semantics, so the installed tier changes speed, never results |
| Stack overflow and deep recursion | `RangeError` is decided by a **canonical frame budget** (each frame charges a size fixed by its function, whatever its tier). Every recursive Rust path reachable from content also has a **canonical depth limit** that throws the spec-appropriate error: parser nesting, `JSON.parse` and `JSON.stringify`, structured clone, Proxy trap chains, regex compilation, `toString` and `valueOf` re-entry. Regex matching iterates and never recurses. A DST case runs deeply nested inputs on every OS and ISA. The real segment is larger than the canonical budget plus the deepest runtime call |
| Off-thread parsing and code-cache loads | Installed at task boundaries, as an input the scheduler orders |
| Implementation-approximated `Math` functions | One Izcal implementation per function in `hg-math` (L2s, owned here), identical on every tier and ISA; never the platform libm, and no fused multiply-add contraction in generated code or in `hg-math`. The same functions serve CSS `calc()` and computed colours (f64), the graphics spec's feTurbulence and colour tables (f64) and the media spec's audio paths through **f32 entry points**, each defined as the f64 function's result rounded once to f32 (round to nearest, ties to even), so an f32 result is a function of the f64 one and needs no second verification. Both widths are tested bit for bit across ISAs (JS-50) |
| Array sort with an inconsistent comparator | One algorithm in every tier |
| Intl data | CLDR, UCD and tz versions are part of the engine build and recorded; no data is ever fetched because a page asked for it (the footprint critique's H4 rule) |
| Shared memory races | Production races are real and non-deterministic. Under simulation, agents sharing memory run on the seeded scheduler with preemption at canonical instruction counts, so races replay; production recordings list SAB races as an excluded class, as DT-1 does |
| NaN bit patterns and relaxed SIMD | x86-64 produces a sign-set default NaN (`0xFFF8000000000000`) and AArch64 a sign-clear one (`0x7FF8000000000000`) for an operation with no NaN input, and propagation differs when several inputs are NaN ([Wasm rationale](https://raw.githubusercontent.com/WebAssembly/design/main/Rationale.md); Intel SDM Vol. 1 §4.8.3.7; Arm ARM, FPCR.DN); riscv64 returns the canonical NaN (`0x7FF8000000000000`) from every arithmetic operation and never propagates a payload, while loads, stores and moves keep payloads ([RV 7.2][RV]). **JS-D12 (a)**: canonicalize NaNs where their bits become observable (typed-array and `DataView` float stores, Wasm stores to memory and reinterpret instructions, structured clone) and run Wasm under the Wasm 3.0 **deterministic profile**, which fixes NaN and relaxed-SIMD results ([Wasm profiles](https://webassembly.github.io/spec/core/appendix/profiles.html)); measured first, with (b) per-ISA identity as the fallback. Under either option, two rules hold on every ISA: **one relaxed-SIMD lowering per ISA**, independent of CPU features such as FMA; and **constant folding and runtime helpers produce exactly the NaN the generated code would**, so tiers cannot disagree on one ISA |

**Why this is new.** V8's predictable mode is a set of testing flags (`--predictable`, used with `--single-threaded`), and Izcal's M0 observed, black-box, that a GC-observable channel still diverged occasionally under those flags and became deterministic only with a forked embedder platform ([M0](../m0/determinism_crossplatform.md)). Izcal keeps concurrency on and records only the *decision points*. What recording them costs, and whether the main thread ever waits at one, has not been measured anywhere ([GO 14][GO]); JS-52 measures both, with a tail metric. If the cost exceeds its bound, the fix is to make decisions cheaper to record or to move more work onto deterministic paths, never to drop determinism (DET-2's rule).

**Consequences for other specs.** A recording made at one tier ceiling replays at any other, because tiers are semantically identical, accounting is canonical and decision points are logged by canonical position (JS-51). That reverses REC-R6's "a jitless replay exists only for jitless recordings" ([SS 6.13][SS]) and lets the replay host run jitless **by default**, which suits untrusted imported bundles (REC-R1). An **engine-triage replay mode** replays at the recorded tier, in a replay host with REC-R1's isolation, so an engineer can reproduce a T1 or T2 bug; exploited engine bugs live mostly in compilers, so a jitless-only replay could not. The recording format's "mandatory worker-task mode" field (Stage 1 3.3) disappears with V8's platform; the engine build ID, its data versions and the decision-point log replace it.

### 6.10 Observability: what the engine shows

`hg-js-observe` turns engine facts into a **typed, versioned event stream and query interface**, declared in `.hgidl` and served through IIP (DevTools spec DT-D1). No consumer, no cost beyond a branch on a per-agent flag (JS-60).

| Stream or query | Content | Replaces |
|---|---|---|
| **Shapes** | Creation, transition, switch to table mode, deprecation; with the allocation site and source position that caused each | V8's `--log-maps` |
| **ICs** | State changes (uninitialized, monomorphic, polymorphic, megamorphic) with the shapes that caused them | `--log-ic`; Deopt Explorer ([Microsoft](https://devblogs.microsoft.com/typescript/introducing-deopt-explorer/)) |
| **Tiers** | Tier-up, tier-down and why (including tier-down caused by the debugger, which Wasm debugging hides today, [GO 1.9][GO]) | — |
| **Deopts** | Guard, speculation, the shape transition or validity-cell change that broke it, source position, frequency; plain-language reason text from the description's anchor | `--log-deopt` |
| **GC** | Cycles, phases, pause times, cause (canonical trigger), bytes by category, release-list sizes, flushes and decision-point waits | Trace flags |
| **Live allocation attribution** | Per-allocation-site counters in canonical units, aggregated per script, realm and origin, always on at the cost of one increment per allocation site visit in T0/T1 and a hoisted counter in T2; live attribution can claim bytes **allocated** by a script, not bytes **retained**, which only a heap query answers | Region-level tags, which cannot split one heap's blocks by script (footprint critique M13) |
| **API-call attribution** (CB-D10) | The **responsible script** of a Web API call is the attributed script of the innermost non-builtin frame on the calling agent's stack. Code a script creates **inherits its creator's restriction**: code from `eval`, `Function`, string timers, `javascript:` URLs, inline scripts it inserts and same-origin child documents it writes. Each function's script ID is held with its trusted function ID (Section 6.1), and the per-script restriction profile in the host's tables, both **outside the cage**, so an in-cage write cannot change who is responsible. `hg-bindings` reads it at the API entry for the content-blocking spec's restriction profiles ([CB 6.4][CB]); the cost is inside JS-60's budget | Nothing; no engine attributes API calls to scripts |
| **Time accounting** | Main-thread time per engine component (parse, compile per tier, interpret, IC miss, GC, builtins) and per script, realm and origin, from thread CPU clocks read through the substrate. This is the **one** accounting mechanism: the footprint spec's per-site and per-script CPU and energy attribution consumes it rather than measuring again, and the always-on part shares one overhead budget with it (JS-60, FP-23) | V8's internal Runtime Call Stats, never public ([EX 1.1][EX]) |
| **Progress counter** | A canonical count of back-edges and calls per agent, identical across tiers | Answers Q-DT-11: execution points become as fine as one loop iteration |
| **Heap queries** | Retaining paths, dominators, detached DOM subtrees, allocation-site provenance, answered in place in a replay host | 2× heap snapshots ([Node.js](https://nodejs.org/api/v8.html)) |
| **Debugger and profiler core** | Script evaluation and console (JS-M1); breakpoints, stepping, scopes, evaluation without side effects (stopped at the first operation the generated facts mark as effectful), exceptions, async stack traces, sampling profiler and heap export (JS-M2); served as **native IIP script domains** and translated to the CDP profile's Runtime, Debugger, Profiler, HeapProfiler and Console domains by `hg-cdp` | V8's inspector, passed through as `script.v8` today |

**Stage 1 scope, kept.** The DevTools spec's owner-approved Stage 1 scope (DT-D10 Option B) needs script evaluation for the WebDriver slice at Stage 1 M2, the inspector's script surface at M2, the CDP JS domains at M7 and a scrubbable console in recorded sessions at M7. All four assumed V8's inspector. This spec therefore delivers evaluation, console and exceptions at JS-M1 (before Stage 1 M2) and the full debugger and profiler core with the native script domains at JS-M2 (Stage 1 M6, before M7), staffed by its own track (Section 9.3) and measured by JS-63. The debugger is part of the engine, not a later tool: breakpoints, stepping and tier-down for debugging use the same frame states and code-table entries as deoptimization.

**Exact profiles by replay.** Live sessions use a sampling profiler for costs. In a recorded session, a replay host re-executes with full instrumentation (every call and back-edge counted, no sampling and no observer effect on the original run), and wall-clock time comes from the recording ([GO 3][GO]). Counts are exact because execution is deterministic.

**Exact leak finding.** A leak hunt replays a navigate-away-and-back loop N times from the same seed and diffs the heap at the same execution points, which is exact where MemLab and BLeak are heuristic ([GO 2.4][GO]).

**Privacy.** The stream contains page internals. It flows only through IIP sessions with grants, AI off by default (B10), and through the B9 tool registry only when AI is on. Any page-facing profiling API keeps JS Self-Profiling's cross-origin limits ([WICG](https://wicg.github.io/js-self-profiling/)).

**Gated by measurement, designed for now.** Engine-level hot reload with explicit code-versus-state rules, as the Dart VM and Erlang define ([GO 6][GO]), and opt-in taint tracking in engine strings and generated bindings ([GO 9][GO]) ship when their cost and value are measured on real pages, which no one has published ([GO 14][GO]); they carry no stage label. Both need hooks the design keeps open: function replacement in the code table, and a taint side table that costs nothing when the mode is off.

### 6.11 Snapshots, the engine image and the heap image format

One versioned **heap image format** (`hg-js-snapshot`) serves every use below, because every form of snapshot elsewhere tripped over the same problem: state that must not be copied ([GO 10][GO]). `hg-js-snapshot` owns the format for every use, including the live-page snapshot whose lifecycle the footprint spec's `hg-suspend` drives.

| Use | Contents | When it ships, and why |
|---|---|---|
| **Engine image, JS section** | Builtins' bytecode, immutable shapes and read-only roots, intrinsic and WebIDL interface **descriptors** from which each realm creates objects on first use; mapped once per process at the start of the cage (Section 6.1) | Stage 1: every renderer needs it |
| **UI image** | Izcal's own UI code (shell, prompt, DevTools) as AOT bytecode (Hermes' lesson, [EX 10.5][EX]) | Stage 1; mapped only by Izcal-only renderers, never by site renderers |
| **Code cache** | Verified bytecode for network-fetched scripts that ran, built outside the renderer by the code-cache builder (JS-D21) and keyed below; no feedback or IC state | Stage 1 |
| **B1 checkpoints** | Heap state at task boundaries in the replay host, for faster seeking | When the DevTools recording view needs seeking (its M7 scope); no stage label of its own |
| **DevTools heap export** | Streamed in the same format, without a second in-memory copy | With the debugger core's heap export (JS-M2) |
| **Live-page snapshot** | A frozen page's heap, serialized and restored with external state re-derived | Gated by the footprint spec's FP-31 measurement: its suspend-to-disk spike *is* the measurement, so `hg-js-snapshot` supplies a serializable live heap for that spike (JS-M2) and the feature ships if and when FP-31's criteria pass, with no stage label and no schedule fallback |

**One image inventory.** The engine image is part of one inventory shared with the resource-footprint spec's `hg-image` ([FP 6.3][FP]): one file set per installation, each file with an owner and a list of the process kinds that map it. Site renderers map the shared engine image (Unicode tables, name tables, UA style data, the JS section above, CLDR data compiled by `hg-cldr-build`); Izcal-only renderers also map the UI image. Every file is read-only by protection, position-independent, signed and free of site data. FP-25's size budget covers all of them.

**The code cache is partitioned like the HTTP cache.** A renderer for a third-party iframe belongs to the script's site, so a cache keyed only by that site would be shared across top-level sites, and whether a script compiles from cache is visible to page script through timing. I-1 extension (b) partitions the HTTP cache and all network state by (top-level site, container) for this reason. The code cache, in memory and on disk, is keyed by **(top-level site, container, script URL, content hash, engine build)**, and lives in that partition's storage. A cross-site cache-probing case joins PRIV-2's test set (Section 9.5).

**Code-cache entries are built outside the renderer (JS-D21).** *Threat.* If the renderer wrote its own entries, an attacker who controls a site renderer (ATK-2's in-cage attacker who escalates, or a full compromise of the process) could write an entry for any script of its own partition: bytecode that passes the bytecode verifier, because the verifier proves safety (register bounds, jump targets, operand kinds, stack heights), not that the bytecode is what the script's source compiles to. Every later, uncompromised renderer of that (top-level site, container) would then run attacker-chosen behaviour with the site's authority (reading what the user types into a login form, for example) or replay bytecode sequences the generator never emits, which widens the surface for a second engine bug. The regenerable-cache rules bound this, but only to the 14-day† time-to-live ([FP 6.12][FP]), the next engine update or a crash of the writer, and a careful attacker refreshes the entry on each load and never crashes. *Design.*
1. **The key's hash is computed by the network service** over the response body it delivers, never by the renderer. Only scripts whose bytes came from the network service get an on-disk entry: classic and module scripts fetched over the network, including responses stored unmodified in Cache Storage, which keep the network service's hash. Inline scripts, `eval`, `blob:` and `data:` URLs, responses a service worker constructed, and responses the HTTP cache does not keep (`no-store`) get none; in-memory same-site sharing (below) is unchanged.
2. **Only the code-cache builder writes entries.** The builder is a utility process at the strictest sandbox tier, running the jitless executable (no code generator, G14), with no network access, no storage handle and no IPC channel to any renderer. The storage service starts one builder per job, and a job is one script of one partition: the storage service passes the source bytes from the HTTP cache entry that carries the network service's hash; the builder parses and emits bytecode with the same `hg-js-syntax` and `hg-js-bytecode` the renderer uses, verifies it and returns the serialized entry; the storage service stores it in the partition's index with its SHA-256 digest. The builder exits after the job, so a builder compromised by one script's source cannot write another script's entry.
3. **The renderer can only ask.** Its only code-cache message is "the script with this key ran, and these function source ranges were compiled", sent after the script's first run. The range list is an untrusted hint: it selects which functions of the trusted source the builder compiles eagerly, capped at the source's own function count, so a forged list wastes at most one compilation of that source at background priority. Feedback and IC state are never persisted, because the renderer produces them.
4. **Loading.** The storage service hands the renderer a read-only sealed handle and the digest from its index; the loader checks the digest, then bounds-checks, parses and re-verifies the entry as before (VER-1) before it enters the trusted region. A mismatch discards the entry.
5. **Faithfulness is checked, not assumed.** Bytecode generation is deterministic (B1), so an entry is a function of (source, engine build); JS-18 rebuilds a nightly sample from source in a clean process and compares bit for bit.

*Why not validate on load.* Checking on load that bytecode matches its source means compiling the source again, which is the work the cache exists to save; a signing key the renderer cannot read does not help while the renderer is the producer. The structural verifier and the trusted region stay as defence in depth, not as the answer. *Cost.* Every cached script is compiled twice, once in the renderer to run it and once in the builder, at background QoS off the critical path; one process spawn per cached script on FP-27's spawn path, with at most one builder at a time per profile†; IC state is rebuilt on every load; scripts that are not network-fetched get no on-disk entry; and a new process kind whose footprint line belongs to the footprint spec (Section 9.5). The first visit gains nothing, as before. JS-18 bounds and publishes the cost; JS-D21 records the alternatives.

**Same-site sharing within a process.** Agent heaps of one process share one trusted region (JS-D17), so verified bytecode for the same code-cache key is stored once and referenced by every agent heap that runs it; feedback, IC site state and compiled code stay per agent heap. Each shared entry carries a reference count in its trusted-table entry, decremented through the release lists, so freeing it is integer work. This is the only cross-heap sharing, it is read-only and same-site (I-6 permits it), and it obeys the partition key above, so B-in-A and B-in-C share nothing.

Rules that apply to every image:
- **External state is classified, not copied.** B1 already routes all clocks, entropy, handles and seeds through injected interfaces, so the image format records them as references to be re-derived on load. Hash seeds and PRNG state are re-seeded on every restore, which is the failure behind Node's CVE-2017-11499 and AWS SnapStart's rules ([Red Hat](https://bugzilla.redhat.com/show_bug.cgi?id=1475327), [AWS](https://docs.aws.amazon.com/lambda/latest/dg/snapstart-uniqueness.html)).
- **One partition per image.** An image other than the engine and UI images holds one (top-level site, container) partition's data, stays in that partition, is encrypted at rest with the profile key and is deleted with the container (REC-R rules).
- **Loading is parsing untrusted input.** A site's own compromised renderer can write the images it produces (B1 checkpoints, heap exports, live-page snapshots), and a code-cache entry is only as trustworthy as the builder that wrote it, so the loader treats every image as hostile: bounds-checked, typed, every bytecode re-verified, and fuzzed as a Tier 1 parser (VER-1).
- **A compromise must not persist through an image.** Encryption does not help when the renderer that writes the image is the attacker. Images are therefore a **regenerable cache**, never storage: bound to the engine build; discarded, never repaired, on any failure; discarded if the process that wrote them later crashed, failed a check or was killed for a bad message; given a time-to-live†; and never the only copy of anything. Restoring one gives nothing a fresh load would not. For the code cache the renderer is not a writer at all (JS-D21). This spec and the footprint spec propose one HGBA-2 4.6 amendment that defines this class and names its members (code cache, checkpoints, heap export files, live-page snapshots) (Section 9.5).
- **Versioned.** An image from another engine build is discarded, never migrated.

V8's snapshot cut context creation from 40 ms to under 2 ms on desktop ([V8](https://v8.dev/blog/custom-startup-snapshots)), and code caching cut parse and compile time 20–40% on most pages ([V8](https://v8.dev/blog/improved-code-caching)); both are Stage 1.

### 6.12 Threads, SharedArrayBuffer and shared structs

- **One heap per agent; several agents may share a thread.** A dedicated worker has its own agent heap and `Mutator` and, as a `[[CanBlock]]` agent, its own OS thread. Window agents of the same (site, container) in one process may share the script thread, as HTML allows ([SP 8.3][SP]); that is sound because every handle carries its heap's brand (JS-D18, Section 6.5 step 6), not because of a one-heap-per-thread rule.
- **Engine threads.** The engine uses the process's shared worker pool (footprint spec, [FP 6.3][FP]) for marking helpers, background compilation and off-thread parsing; it creates no thread of its own except the **code writer** (Section 6.7), a dedicated thread identity created on the first compilation, which runs no decoder or other untrusted-input parser. An idle empty renderer therefore has no engine thread beyond the script thread (FP-32). Script runs on engine stack segments (Section 6.6), so the script thread's OS stack is small.
- **Real-time agents: AudioWorklet (MD-D31).** AudioWorklet runs page script on the audio render thread, which has one render quantum (128 frames, 2.67 ms at 48 kHz) to produce output. The media spec puts the worklet agent on a real-time thread only if the engine guarantees four things for that agent ([MD 6.8][MD]); they are designed in, not added later:
  1. **Pauses below a quantum, with no shared safepoint.** The worklet agent has its own agent heap (as every agent does) and is never stopped for another agent's collection or for a process-wide safepoint; it does not join a shared heap's global safepoints, so a worklet global cannot hold a shared-struct reference until that interaction is designed (shared structs are not shipped, Section 9.1). Its collections run **only at quantum boundaries**: a nursery scavenge whose size the broker grant caps so that its pause stays within the target, and old-generation marking done by the process's background markers, with the worklet thread's own increments bounded by the same target. Canonical triggers are unchanged, so a collection that falls inside a quantum is deferred to the next boundary, which changes when and never what (Section 6.9).
  2. **Allocation without process-wide locks.** The worklet's allocator bumps in its own nursery and takes fresh blocks only from a per-agent reserve that a background thread refills ahead of use, so no allocation on the real-time thread waits on a lock another thread can hold (priority inversion); an exhausted reserve forces a scavenge at the next boundary, not a lock.
  3. **No code installation, tier-up compilation or W^X change on that thread.** Compilation for the worklet runs on the shared pool and the code writer writes code on its own thread identity (Section 6.7); the worklet thread only observes a new code-table entry at a quantum boundary, which is a recorded decision point (JS-D15). Interrupt checks and tier-up counters stay, since they are loads and stores.
  4. **The OS real-time mechanism through the broker.** The substrate joins the thread to an audio workgroup on macOS, an MMCSS "Audio" or "Pro Audio" task on Windows, and RTKit or the Realtime portal on Linux, requested by the sandboxed renderer through the broker ([MD 6.8][MD]); the engine requests nothing itself (G13).
  Target JS-43 measures these four; spike MD-S8 runs them on each OS. Until both pass on an OS, the worklet runs on a high-priority, non-real-time thread with one extra quantum of buffering there (MD-D31 (b)).
- **SharedArrayBuffer** backing stores live in the buffer region and are shared by the agent heaps of one agent cluster, which always lives in **one process**: a process split (FP-D3) may never divide an agent cluster. Growable shared buffers grow in place inside a reservation. `Atomics` lowering in every tier is checked against the mechanized JS memory model of Watt et al., which found that the model, against its design intention, did not support the ARMv8 compilation scheme used in practice, and repaired it ([Watt et al.](https://doi.org/10.1145/3385412.3385973), [arXiv](https://arxiv.org/abs/2005.10554)).
- **Shared structs** (TC39 Stage 2, [proposal](https://github.com/tc39/proposal-structs)) wait for Stage 3, because the proposal can still change; the heap is designed so they need no retrofit. References are 32-bit, atomic and aligned, so field accesses do not tear; strings are immutable once published (Section 6.13), which removes the proposal's hardest sharing problem ([GC 10.2][GC]). Because all agent heaps of a process share one cage (JS-D17), a **shared heap** per agent cluster is simply another set of blocks in the same cage, with its own allocator and global safepoints, and a reference from an agent heap into it is an ordinary 32-bit compressed reference: no second base, no overlapping reservation. The brand discipline extends with a shared-heap brand that agent heaps may reference one way. The JS-M0 spike measures this encoding with JS-D1. Wasm shared-everything threads (Phase 1) would use the same shared heap.

### 6.13 Strings, numbers, regular expressions and Intl

**Strings.** Sequential one-byte (Latin-1) and two-byte (UTF-16) strings, ropes for concatenation, and slices of large strings, with **no in-place representation change after a string is published**: flattening a rope produces a new sequential string and caches it in the rope's single cache field with an atomic release store, an idempotent write that is safe to race (Section 6.5). DOM text is one copy: strings that come from the DOM are external strings over the DOM's text arena (Section 6.2). Property keys are interned atoms with a hash computed from the process key (CS-AS-2). **One per-agent atom table** serves property keys and the DOM's dynamic tag, attribute and CSS names, shared with `hg-dom` and `hg-style` ([ST 6.4][ST], [RN P4][RN]); it is written only on the agent's script thread and keyed under JS-17's partition rule. Workers that intern names (the speculative HTML parser, off-thread style-sheet parsing) use **private atom scopes** that cannot reach an agent's table, a type rule of the atom-scope API (the style spec's G23), and their names are re-interned on the script thread when the result is installed. Strings were 70% of Facebook's heap in MemLab's study ([Meta](https://engineering.fb.com/2022/09/12/open-source/memlab/)), so string footprint is a first-class metric (JS-31).

**Numbers.** Shortest round-trip number-to-string from the published algorithms (Ryu, Schubfach, Dragonbox; [Dragonbox](https://github.com/jk-jeon/dragonbox)), implemented by Izcal; exact string-to-number; one `Math` implementation per function on every ISA.

**Regular expressions.** `hg-regex` parses the ECMAScript pattern grammar, Annex B included, into one IR with two engines:
- a **linear-time engine** (automaton with lockstep simulation, including JS lookarounds per Barrière and Pit-Claudel ([PLDI 2024](https://arxiv.org/abs/2311.17620))) that runs **every pattern it can express**, producing exactly the spec's backtracking-priority match;
- a **backtracking engine** only for patterns that need it (backreferences), with an interrupt check per step so HTML's slow-script handling can stop it.

V8's default is backtracking only; a linear fallback after 50,000 backtracks exists behind an experimental flag, because its linear engine is "orders of magnitude" slower than its backtracking one ([V8](https://v8.dev/blog/non-backtracking-regexp)). The speed of a linear-first default is therefore the risk, and Izcal compiles hot regexes of both kinds through `hg-codegen` and measures the cost (JS-25). ReDoS from patterns without backreferences is removed by construction, a property no shipping engine has by default ([EX 11][EX]).

**Intl (ECMA-402).** A second engine-sized project ([SP 3][SP]). ECMA-402 requires the IANA tz database and BCP 47 identifiers but not CLDR; interoperable output in practice needs CLDR data and UTS 35 algorithms. Under M-1, CLDR, the UCD and tz are standards data, and Izcal writes the code: number and date formatting, plural rules, collation (UTS 10), display names, calendars for Temporal, and time-zone resolution in `hg-intl` and `hg-tz`. Segmentation (UAX 29), normalization (UAX 15), case mapping and the UCD tables belong to the fonts and text spec's `hg-unicode` and `hg-ucd` in L2s, written to tier P (owner decision OD-1, [RN P3][RN]), because the text stack is their largest user and URLs (UTS 46) need them in tier-P processes; `Intl.Segmenter`, `String.prototype.normalize`, `toLowerCase`, `toUpperCase` and their locale forms call `hg-unicode`, and one Unicode version is pinned per build and recorded once for the engine, the text stack and URLs. `hg-cldr-build` compiles pinned CLDR and tz releases into a compact, read-only, versioned format that renderers map and share (public data, I-6). ICU4C, ICU4X and `temporal_rs` are excluded. Locale data size enters the resource-footprint budgets; under one rule shared with the footprint spec, no web-observable data is ever fetched because a page asked for it, and under FP-D13 (a), accepted by the owner, the locale set **follows the build only**: every locale ships, identical in every installation, mapped clean, so untouched locales cost disk and no memory ([FP 6.20.5][FP]). The locale set never depends on the user's settings or on page behaviour. The compiled data's size is Q-JS-6.

### 6.14 Modules and the HTML host hooks

`hg-js-host` is the embedding API, designed and frozen from the specifications rather than from any engine's API ([SP 8][SP]):
- **The 16 ECMA-262 host hooks** (17 once Temporal's HostSystemUTCEpochNanoseconds merges) are one Rust trait implemented by `hg-script`, each method anchored to its ECMA-262 and HTML sections. HostEnsureCanCompileStrings carries the Dynamic Code Brand Checks (Stage 3) for Trusted Types.
- **Jobs belong to the host.** Promise jobs, cleanup jobs and timeout jobs are handed to the host, and the host runs microtask checkpoints where HTML puts them, including "clean up after running script" ([HTML](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint)). The engine exposes "execution-context stack is empty" cheaply. CS-AS-4's rule that JS Promises are never bridged to Rust futures stands.
- **Realms and settings objects.** Current, relevant, entry and incumbent realms are cheap to read, and incumbent tracking crosses HostMakeJobCallback and HostCallJobCallback ([HTML](https://html.spec.whatwg.org/multipage/webappapis.html#realms-and-their-counterparts)). WebIDL's per-realm initial objects are created on first use from descriptors in the engine image (Section 6.1).
- **Modules** are a phase-aware state machine from the start (fetch, source phase, instantiate, evaluate, deferred evaluation), because the module surface (import attributes, JSON and text modules, source phase imports, `import defer`, Wasm ESM integration) is the fastest-moving part of the language ([SP 2][SP]). ECMA-262 owns the graph algorithms and HTML owns fetching and import maps; the split follows the specs.
- **Structured clone** gets internal-slot access through a typed serializer interface over engine objects, never raw layouts, so `hg-script` can implement HTML's StructuredSerialize.
- **Not until Stage 4**: decorators (moved back to Stage 2.7 in May 2026) and ShadowRealm (Stage 2.7; no engine passes its tests) ([SP 2.4–2.5][SP]), because a Stage 2.7 proposal can still change (a correctness gate, not a date). Temporal is in, from its Stage 4 text, with the merge PR tracked at each pin ([SP 2.2][SP]).

### 6.16 User experience, integrations, security and privacy

**For people browsing.** The engine is invisible except in three places: `izcal://sandbox` shows each renderer's tier ceiling and the CFI features it achieved; a per-site setting lowers a site's ceiling; and when a ceiling or emergency switch makes a site slower, the shell says so in plain language, as S-4a requires.

**For developers.** Engine facts appear where the DevTools tasks start (DevTools spec T2, T3, T6): a slow function shows its tier history and deopt reasons with a link to the spec step; an object shows its shape history; a leak shows its retaining path through JS, DOM and Wasm objects alike. Explanations are deterministic and anchored, never generated by a model (DT-D4).

**Integrations.**

| With | Through | Notes |
|---|---|---|
| HTML event loop (`hg-script`) | `hg-js-host` hooks | B3 sequences; microtask checkpoints by the host |
| WebIDL bindings | `hg-webidl-codegen` emits shape families, IC generators and conversions against `hg-js-host` | CS-V8-5's "only generated conversions" carries over |
| DOM (`hg-dom`) | Node columns outside the cage, traced as `hg-heap`'s node space; lazy wrappers; text arena | One copy of the DOM; the columns are B4's data plane (JS-D4) |
| B1 substrate | Clock, entropy, executor, thread CPU clocks, `Memory`, `CodeMemory` | G3, G13; one trait set with the footprint spec |
| DevTools (IIP) | `hg-js-observe`; native script domains replace `script.v8` from JS-M1 (evaluation, console) and JS-M2 (full) | CDP profile's JS domains translated by `hg-cdp`; Stage 1 per DT-D10 |
| Resource footprint | Ledger tags on every `Memory` call; derived-store registration for bytecode, feedback and code; allocation-free pressure hook; shrink-on-freeze and navigation hooks; time accounting | Numbers (FP-2, FP-4, FP-5, heap limits, locale budget) belong to the footprint spec |

**Security and privacy rules.** H-1 (no raw pointers in the cage), H-2 (nothing outside the cage trusts cage data) and the machine-code validator are ship blockers. Engine images and recordings are sensitive user data. The event stream and heap queries never leave a (site, container)'s pane renderer or replay host except through granted IIP sessions. The engine never reads OS state directly, so a compromised engine has no ambient authority beyond its renderer's (I-2).

### 6.18 riscv64: the third first-class ISA (JS-D22)

HGBA-2 X-1 promised a riscv64 tier with the JIT and the full sandbox; drafts up to 0.3.1 deferred riscv64 to JS-M5 because no reference device ran it. The owner decided on 19 October 2026 that riscv64 is first-class from the start. Everything below follows from that decision and from published evidence ([RV][RV]); no part of it comes from another engine's riscv64 port, which this spec cites only for its existence ([RV 8][RV]).

**Profile: RVA23U64, and only RVA23U64.** One build per ISA with one lowering per operation is a JS-D12 rule (relaxed-SIMD results, constant folding and NaNs must not depend on CPU features), and the validator and the rule verifier are simpler for one instruction set. RVA23U64 is the smallest ratified profile that gives the backend everything it needs without dispatch ([RV 1.2][RV]): **V** (RVV 1.0, with at least 128-bit vectors) for Wasm SIMD and relaxed SIMD; **Zba** (`sh2add.uw`) for two-instruction decompression; **Zbb** and **Zbs** for bit operations; **Zicond** (`czero.eqz`, `czero.nez`) for branchless selects and index masking; **Zfa**, whose `fcvtmod.w.d` computes ECMAScript ToInt32 in one instruction, the stated reason it exists ([RV 7.1][RV]); **Zcb** for code density; and **Zimop/Zcmop**, which make Zicfiss instructions harmless no-ops where CFI is absent ([RV 3.2][RV]). Ubuntu requires the same profile from 25.10 ([RV 5.1][RV]). The alternatives are rejected on the evidence: RVA22U64 with V as an option would need a second lowering for Wasm SIMD and for ToInt32, against JS-D12; a jitless-only RV64GC build would give riscv64 users a different engine from everyone else's, against "first-class". Hardware older than RVA23 (SpacemiT K1, Sophgo SG2042 and SG2044, TH1520) is not a target; a part that claims "RVA23 without V" (UltraRISC UR-DP1000) is not RVA23 and is not a target either ([RV 4.2, 4.4][RV]).

**Representation and code generation.**

| Concern | riscv64 design | Evidence or reason |
|---|---|---|
| Decompression (JS-D1) | `sh2add.uw rd, v, cage_base` then a load at offset −4: two instructions, as on AArch64 | [RV 7][RV]; measured at the JS-M0 spike with JS-D1's trigger |
| Small-integer overflow | Explicit check (32-bit and 64-bit add compared) instead of a flags branch; the IR exposes "add with overflow" as one operation, so each ISA lowers it once, verified | No flags register ([RV 7.5][RV]); cost per ISA reported by JS-27 |
| ToInt32 (bitwise operators, Int32Array stores) | `fcvtmod.w.d` with RTZ | [RV 7.1][RV] |
| Floating-point rounding | Every generated FP instruction encodes its rounding mode statically (RNE or RTZ); generated code never uses the dynamic mode and never writes `frm` or `fflags`, so no CSR state can change a result | First principles; the validator checks it |
| NaNs | Arithmetic returns the canonical NaN; payloads survive loads, stores and moves; JS-D12 (a)'s canonicalization at observable boundaries covers riscv64 without a third rule | [RV 7.2][RV] |
| Wasm SIMD and relaxed SIMD | RVV at a fixed 128-bit configuration (`vsetivli` with an element count of 128 bits' worth, whatever the hardware's vector length), so results never depend on VLEN; one relaxed-SIMD lowering for the ISA | JS-D12's rule; RVA23 guarantees 128-bit vectors |
| Possibly misaligned accesses (DataView, Wasm loads with an alignment hint below natural) | An alignment test, a native access on the aligned path and a byte-assembled access otherwise; never a reliance on hardware misaligned access, which may trap and be emulated | Zicclsm is "for correctness, not for performance" ([RV 7.3][RV]) |
| Atomics | A's AMOs and LR/SC; byte and halfword `Atomics` and compare-exchange as LR/SC loops within the ISA's forward-progress constraints; Zacas and Zabha are not assumed (development options only). Lowering checked against the mechanized JS memory model with RVWMO's axiomatic model, as for ARMv8 (Section 6.12) | [RV 7.4, 1.6][RV] |
| Branch reach | Conditional branches reach ±4 KiB, so the assembler relaxes them (inverted branch over `jal`, ±1 MiB) and stencils use `auipc`+`jalr` (±2 GiB) for runtime calls; JS calls go through the code table as on every ISA | [RV 7.5][RV] |
| Compressed instructions | Emitted (C and Zcb), for code size (U5); the validator decodes both widths; landing pads stay 4-byte aligned, as Zicfilp requires | [RV 3.1][RV] |
| Fixed registers | Cage base, trusted-region base and the agent's context in callee-saved registers; x7 reserved for landing-pad labels (below) | Zicfilp's label register ([RV 3.1][RV]) |
| Counters | Generated code never reads `cycle`, `time` or `instret`; time reaches script only through host hooks (Section 6.7) | The validator rejects every CSR access outside the substrate's stubs |

**Address space.** RVA23 requires only Sv39, whose user half is 256 GiB ([RV 2.1][RV]). The per-process cage (16 GB†, JS-D17), the trusted region and the code region fit in about 20–24 GiB. What does not scale is guard-elided Wasm 32-bit memory, whose reservation covers every index plus offset: the buffer region therefore keeps a **per-process count of guarded reservations** set from the paging mode the kernel reports at start-up (16† on Sv39, unbounded on Sv48 and above), and a memory beyond the count uses explicit bounds checks against the buffer table. Both forms trap identically on an out-of-bounds access, so the choice changes speed, never results (JS-50), and the validator's certificate already names which form each access uses (Section 6.1, item 5). On Linux the engine reserves below 2^47 by default, as the kernel places mappings there unless asked ([RV 2.2][RV]).

**W^X and code installation.** RISC-V has no per-thread write permission (no `MAP_JIT` equivalent and no user protection keys), so riscv64 always uses Section 6.7's third mechanism: a writable alias that exists only while the code writer installs one compilation, with its exposure stated on `izcal://sandbox`. The out-of-process JIT experiment (Section 6.7, JS-M3) is run on riscv64 as well, because riscv64 is where an in-process alias is the only option; its reversal trigger applies per ISA. Instruction-cache coherence is explicit: `fence.i` covers only the executing hart ([RV 6.4][RV]), so each process sets Linux's `PR_RISCV_SET_ICACHE_FLUSH_CTX` per thread at start-up, the code writer completes its stores with a `fence` before publishing a code-table entry, and every thread that may run the new code executes `fence.i` at the safepoint where it applies the install (a recorded decision point, JS-D15) before it can reach the entry ([RV 6.5][RV]). The kernel keeps that thread's context coherent across migration. JS-28 (c) tests the protocol.

**Control-flow integrity.** Forward edge: every indirect-branch target in generated code and the generated interpreters starts with a 4-byte-aligned `lpad`. Labels are used, because they cost nothing beyond setting x7 before the jump: each **entry kind** (JS call entry, Wasm call entry, OSR entry, deopt-resume stub, IC stub, runtime trampoline) has its own 20-bit label, so a corrupted code-table index that reaches a valid pad of the wrong kind faults. The code-table entry's kind already decides which label a caller sets. Backward edge: every generated prologue pushes the return address with `sspush` and every epilogue checks it with `sspopchk`; RISC-V has no pointer authentication, so the shadow stack is the whole backward-edge defence ([RV 3.9][RV]). Because these instructions are no-ops on RVA23 hardware without Zicfiss and Zicfilp, **the same code runs on every RVA23 device**, protected wherever silicon and the kernel enable the extensions (Linux 7.0 and later, [RV 3.5][RV]). JS-D19's discipline holds unchanged: the machine-code validator rejects `ssamoswap`, any write of `ssp` and any `sspush` or `sspopchk` outside the standard prologue and epilogue, except in the substrate's segment-switch stub, which is inventoried with the segments (Section 6.6). No shipping silicon implements either extension today ([RV 3.7][RV]), so JS-15's probe runs on riscv64 under an emulator that implements both, and enforcement is reported per device on `izcal://sandbox`.

**Spectre posture.** Out-of-order RISC-V cores are vulnerable to Spectre, and the ISA has no dedicated speculation barrier ([RV 6.1, 6.2][RV]). Process isolation is the mitigation on riscv64 as on the other ISAs (Section 6.7), and nothing more is claimed. JS-D20's in-process hardening needs speculation barriers, which riscv64 lacks, so **a riscv64 process never holds two sites**: the broker does not grant the reduced-isolation flag on riscv64, and a riscv64 device class that needed I-1's reduced mode would be re-decided by the owner with this fact (JS-D22's trigger). Known hardware errata such as GhostWrite on C910-class cores are outside the engine's reach and are another reason those parts are not targets ([RV 6.3][RV]).

**Verification.** `hg-rulecheck` reads riscv64 semantics from the Sail RISC-V model ([RV 7.6][RV]), which answers Q-JS-4 for this ISA; whether the model already covers V, Zicfilp and Zicfiss in full is checked at JS-M0, and any gap is filled by Izcal's own Sail-style semantics for those instructions, reviewed against the ISA manual. The machine-code validator gets a riscv64 decoder for exactly the instruction subset `hg-codegen` emits (an allow-list; any other encoding is a rejection), covering both instruction widths.

**Determinism across three ISAs.** JS-D12 (a) aims at identical results across x86-64, AArch64 and riscv64; the cross-ISA matrix is every recording made on one ISA replayed on the other two (JS-50). Under (b), riscv64's NaN payloads and relaxed-SIMD results join the excluded classes.

**Hardware, CI and the lab.** No hosted CI runs RVA23 today: the RISE runners and Scaleway's machines are TH1520 boards, and RISE's RVA23 label waits for hardware ([RV 4.5, 4.6][RV]). Izcal therefore owns its riscv64 pool:
- **Reference device: a SpacemiT K3 board** (8 X100 cores at 2.4 GHz, RVA23 with RVV 1.0, shipping as the K3 Pico-ITX and Milk-V Jupiter 2), the one RVA23 part with RVV 1.0 buyable in volume; its performance is roughly Cortex-A76 class by vendor claim and behind a Raspberry Pi 500+ in Phoronix's tests, and is unmeasured by Izcal† ([RV 4.1][RV]). Later RVA23 silicon (XuanTie C930, Tenstorrent Ascalon-based parts) joins the lab when it can be bought ([RV 4.3][RV]).
- **T1 on hardware for every change**: a pool of **16–24† K3 boards** runs `hg-test262`, `hg-wast` and the differential suites on riscv64 for each change, sized from the x86-64 T1 time per change scaled by the K3's single-thread speed†; it is re-sized when RVA23 hosted runners exist.
- **Scale under emulation**: fuzzing, the DST farm's riscv64 share and the CFI probe run under emulation on x86-64 and AArch64 hosts, which reproduces architectural results exactly (DST needs results, not timing); every emulated finding is re-run on a board before it is closed.
- **Performance lab**: 3† K3 boards under JS-20 to JS-27, with energy from board-level power measurement†. "Best shipping engine" on riscv64 means the best of the browsers that run there (Firefox and distribution Chromium builds), measured on the same board; Google ships no Chrome for riscv64 ([RV 5.4][RV]).

**What riscv64 costs.** Per track, from each track's riscv64 deliverables (no published figure sizes a JIT port, [RV 8][RV]): operation language and generators +1† (T0, W0, IC interpreter and stencils for a third ISA); backend +2† (assembler with both instruction widths, rule-based instruction selection for RVV and the scalar set, branch relaxation, the icache protocol, segments and shadow stacks on Linux riscv64); verification +1–2† (Sail-based semantics in `hg-rulecheck`, every riscv64 lowering rule verified, the validator's riscv64 decoder and certificate); engine security +0.5–1† (riscv64 fuzzing, the CFI probe under emulation, the riscv64 rows of JS-10's planted bugs); performance and observability +0.5–1† (the riscv64 lab and pool). Total **+5–7†** engineers at full strength, two of them (the backend and verification leads for riscv64) from JS-M0, plus the hardware pool. The generated tiers (JS-D5) are why the figure is this small: T0, T1 and the IC interpreter come from `.hgop` for every ISA, so a third ISA costs a generator target, a rule set and a validator decoder, not a third set of tiers. The engine's semantics, its targets' thresholds and its gates are the same on every ISA, and nothing in this section changes x86-64 or AArch64.

## 7. M-1 compliance

**Built new, by Izcal, from the specifications.** Everything in Section 6.15: parser, bytecode and verifier, the operation description language and its generator, the interpreter, baseline and optimizing compilers, the backend and assemblers for each ISA, the machine-code validator, the garbage collector and heap, the object model and inline caches, every builtin, strings and numbers, regular expressions, Intl, Temporal, time zones, the Wasm decoder, validator and tiers, the JS API, JSPI stacks, the heap image format, the event stream, debugger and profiler core, and the embedding API. No code, design template or internal API shape is taken from V8, SpiderMonkey, JavaScriptCore, LibJS, Boa, Nova, Brimstone, Kiesel, QuickJS, Hermes, Wasmtime, Cranelift, Winch or any other engine. Other engines appear in this document only as published evidence (M-1 part 3).

**M-1 part 3, checked for the representation layer.** The design critique found that the representation layer (tag scheme, element layouts, fact cells, table mode, probe table, register bytecode, a baseline sharing interpreter frames) resembles the shipping engines' taxonomy closely enough to need its own derivation. Section 6.2a gives one per choice, with a considered alternative and the measurement that decides it, and the spec uses Izcal's own names (fact cell, element layout, table mode, probe table) where a V8 term would suggest a template. The parts where Izcal departs from every shipping engine are the trusted region with H-2, typed code-table entries, generation from one description, verified rule languages, recorded decision points, the one-copy DOM outside the cage and the return-address discipline.

**M-1 part 3, evidence (2.3.1).** Another engine's source code (code files, headers, commits, diffs and code reviews) is never evidence in this spec or its notes, and no constant, data layout or algorithm is taken from it. Claims about other engines rest on published prose (papers, documentation and prose design documents, talks, blog posts, release notes, bug-tracker and standards discussions) or on black-box observation, such as M0's determinism runs and the differential oracles of the table below. The 0.3.1 pass removed or replaced every source link (`research_notes/Izcal JavaScript engine/source_evidence_pass.md`).

**Dependencies used unmodified.** Generic infrastructure only: the Rust standard library; general-purpose crates for data structures, error handling, hashing and serialization of Izcal's own formats; test tooling (proptest, Miri, Kani, loom). Nothing that parses, compiles, interprets, collects or formats for the engine comes from a library.

## 9. Milestones and staffing

### 9.1 What is staged, and why

The owner's direction allows staging only where a first-principles argument (correctness, security or measurement) favours it, never schedule. Draft 0.1 staged the optimizer to Stage 2; the design critique found that the deciding part of that argument was schedule, and 0.2 removes it (JS-D8). The rule for every item is now: **design it from the start, build it in parallel, enable each part when its gate passes, ship it when its gates pass, whatever the stage.** A stage exit waits for an item unless an owner decision records which correctness or security gate failed and the evidence; "not finished by the date" is never that reason. The table lists **every** item that is ordered or held, with its reason.

### 9.3 Staffing and duration

No primary source gives the size of any JS engine team. The data points are indirect: Opera kept about 200 engineers on its whole core product (press, [HP 6.1][HP]); one outside observer estimates that V8's sandbox took about a fifth of a roughly 4-engineer GC effort over two years, from what he calls "made-up numbers" ([Wingo](https://wingolog.org/archives/2025/11/13/the-last-couple-years-in-v8s-garbage-collector), commentary, not an input to the rows below); LibJS and Boa reach 96–98% on test262.fyi ([SP 4.3][SP]) and Brimstone self-reports over 97% of the language tests ([HP 8.6][HP]), with small teams. Conformance is reachable by a small team; competitive performance has taken large teams most of two decades. **Hiring ramp†.** A team this size cannot be hired at once, and "hiring JIT and GC specialists" is a High risk (Section 10). The plan therefore starts at JS-M0 with **22–27 engineers**†, the leads of every track, optimizer, backend, verification and security included, plus the riscv64 backend and verification leads, reaches **about 43**† by month 12 and full strength by month 24. The milestone dates follow from the ramp, not the other way round.

**Duration†** (planning placeholders, replaced from measured velocity at each review, as Stage 1 8.3 does): JS-M0 at 9–12 months, JS-M1 at 15–21 months, JS-M2 at 27–36 months, JS-M3 (Stage 1 exit, every tier through its gates) at 39–51 months, JS-M4 at 4–5 years and JS-M5 (parity) at 5–7 years from the start of JS-M0. Engineer-years to parity, with the ramp: about 32 in year one and 59 in year two, then 65–82 a year, which gives 32 + 59 + 3 × 65 ≈ **285** over five years and 32 + 59 + 5 × 82 ≈ **500** over seven, so about **285–500 engineer-years**† (0.3.1: 270–470; reconciliation 1 after OD-1: 265–460). The riscv64 hardware pool and lab (about 20–27† K3 boards) are equipment, not staff. The measured velocities are test262 tests passing per engineer-month (front end and runtime), rules verified per month (verification), and benchmark ratio per quarter (optimizer and backend).

**Effect on Stage 1's plan.** These are planning facts, not reasons to change the design:
- Stage 1 design 8.3's 23–30.5 engineers did not include an engine. The JS, bindings and DOM track (5–6) keeps bindings, DOM and event-loop work; its V8 embedding work, the V8 build farm, the `rusty_v8` owner role and the SEC-1 V8 pipeline disappear. DevTools' 1–1.5† of work in other tracks now includes coordination with this spec's debugger track.
- Stage 1's 24–36-month placeholder no longer holds: the engine is on the critical path, and Stage 1 exit follows JS-M3, which now includes the optimizer's gates. Draft 0.1's 30–42 months assumed the optimizer outside Stage 1; 0.2's 39–51 months† is the honest figure for a Stage 1 that ships every tier whose gates pass. Reconciliation 2 has since re-dated Stage 1 exit from the specs to 48–60 months†, set by layout ([RN2 Q29][RN2]), so JS-M3 keeps about 9 months of float; riscv64's tiers (JS-D22) are built by their own staff inside that window, not after it.
- D-S8 (funding) must cover this track, including its ramp, before JS-M0 can be staffed.

## 11. Open questions and flagged claims

### 11.1 Open questions

- **Q-JS-1.** What does decompressing ×8-scaled references cost on the reference devices (one operand on x86-64, an extended-register add plus a load on AArch64), and what share of integers falls outside 31 bits on the corpus? (JS-D1; JS-M0 spike.) With one cage per process (JS-D17), the address-space question becomes one 16 GB† reservation per process plus Wasm memories.
- **Q-JS-2.** How many bytes per node does the one-copy DOM cost across every structure (columns, rare data, wrappers that exist, text), and what share of GC time does the node space take, against a node held in the cage? No engine has measured these designs against each other ([GC 14][GC]). (JS-D4; JS-M0 spike.)
- **Q-JS-3.** What does recording decision points cost, on average and in the frame-time tail, and how large is the log? (JS-D15, JS-52.)
- **Q-JS-4.** Which machine-readable ISA semantics serve x86-64 rule verification as Arm's ASL serves AArch64? (JS-11; decided at JS-M2.) For riscv64 it is answered by the Sail RISC-V model; its coverage of V, Zicfilp and Zicfiss is checked at JS-M0 (Section 6.18).
- **Q-JS-5.** Can ESMeta's interpreter run the current test262 (Temporal included) per commit, or only nightly ([SP 11][SP])?
- **Q-JS-6.** How large is the compiled CLDR data for every locale, which FP-D13 (a) ships in every installation? (Measured at FP-M2 with the resource-footprint spec.)
- **Q-JS-7.** Will SpecTec gain a maintained Rocq or Isabelle backend for Wasm 3.0, which the verified validator would build on ([SP 7.2][SP])?
- **Q-JS-8.** Does LXR keep frame-time tails low on many small browser heaps? It was measured on server JVM workloads only ([GC 14][GC]).
- **Q-JS-9.** What are the IC-state distribution and the engine-time breakdown on Izcal's corpus? No public figure exists ([EX 1.6, 4.4][EX]); time accounting measures them from JS-M1.
- **Q-JS-10.** Should `ScriptToken` and `Mutator` merge? Merging would make allocation a script-reentry point for `TokenCell`, against Q-CS-7; this spec keeps them separate.
- **Q-JS-11.** Do ESMeta's and SpecTec's licenses allow their use as CI tools ([SP 11][SP])? (JS-D9.)
- **Q-JS-12.** When do `import defer` and source phase imports reach Stage 4, which Wasm ESM integration depends on ([SP 11][SP])?
- **Q-JS-13.** Is a compiler-emitted certificate enough to keep the machine-code validator under 10%† of compile time (JS-D7)?
- **Q-JS-14.** What do landing pads and the return status check cost in optimized code, inside S-7's ≤2%? (Section 6.4; measured when T2 first runs the corpus, JS-M2, and at JS-M3.)
