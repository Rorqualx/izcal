*Revision 0.1 (19 October 2026): first draft, written from the five research notes by the synthesis author.*

HGBA-2 2.3.0 drops html5ever, Stylo, `selectors` and `cssparser`, so Izcal builds its parsers and its style system from the specifications. The history of this area has an unusually clear pattern. **What survived in every engine is deterministic, data-driven and checkable against a specification or a reference; what was removed depended on timing, on thread assignment, or on a second implementation that could disagree** ([HP 12][HP]). Blink introduced a budgeted foreground HTML parser that its author expected to be "less complicated" with "a faster time-to-first paint" ([bc34c4e, 2020](https://chromium.googlesource.com/chromium/src.git/+/bc34c4e1b5de52bec36a83548810f0be3c72ed19)), made it the default and deleted the background parser on 2 February 2022 ([4dbb354](https://github.com/chromium/chromium/commit/4dbb35444daf)); Blink removed opportunistic style sharing in 2017, partly because it made recalculation "unpredictable to developers" ([style-dev](https://groups.google.com/a/chromium.org/g/style-dev/c/8BV0QYubjos)); WebKit's selector JIT forces it to keep two matchers, and in 2025 an invalidation bug appeared only when the JIT was off ([WebKit bug 301090](https://bugs.webkit.org/show_bug.cgi?id=301090)); mXSS, as the HTML standard defines it, and every sanitizer bypass in the security note come from two parsers, or two parses, disagreeing ([HTML §8.6](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html#mutation-xss), [SR 2][SR]); and Stylo's thread-local sharing cache made the number of style contexts on one page 2.3 times larger in parallel than sequentially in 2017 ([Mozilla bug 1385982](https://bugzilla.mozilla.org/show_bug.cgi?id=1385982)). Meanwhile no engine publishes how often it over-invalidates, how often it falls back to a full restyle, or its sharing hit rate ([PI 13][PI]). **The central idea: one implementation of each grammar and algorithm, every derived structure a deterministic function of its inputs, and every optimization checked against an independent, spec-literal reference on every CI run.** One HTML tokenizer and tree builder serve the document, every fragment entry point, the sanitizer and the speculative parser. One property description per CSS property, imported from the specifications' own data and checked against it, generates parsing, computed values, inheritance, interpolation type, serialization and DevTools metadata. Computed styles are content-addressed and shared by exact inputs, so parallel and sequential styling produce the same bytes, not only the same values. The cascade explains itself: the production cascade, not a second model, produces the "why" for DevTools. The decisions that matter most: (1) one parser core with the spec's parameters, sanitizing inside the tree builder, on the script thread with budgeted yields, and a speculative parser that runs the same code on mock nodes (ST-D1, ST-D2); (2) property code generated from W3C webref data plus an Izcal overlay, with the build failing on disagreement (ST-D6); (3) content-addressed style groups with deterministic identities (ST-D7); (4) feature-indexed invalidation with old-value precision, causes recorded, and incremental-equals-from-scratch checked on every CI frame against an independent reference style engine (ST-D10, ST-D12); (5) partitioned `:visited` history, keyed by the container as well, from the first release (ST-D15). The work is about **31–40 engineers† at full strength, reached through a ramp, for 4.5–6 years† to parity**, including the browser's one URL parser (Section 9).

## 1. The problem and who has it

| User | Task, in their words | What fails today |
|---|---|---|
| **People browsing** | "The page should appear quickly, react at once, look right and not leak what I visited" | Microsoft measured style recalculations of 100 ms to over 1 s on interactions in its own apps (10k–28k rules) ([PI 1.5][PI]); the only in-the-wild CSS exploit in Project Zero's sheet, CVE-2026-2441 (February 2026), was a stale iteration over a CSSOM map that script mutated ([Chrome Releases](https://chromereleases.googleblog.com/2026/02/stable-channel-update-for-desktop_13.html), [fix e045399a1e](https://github.com/chromium/chromium/commit/e045399a1e), [SR 1.1–1.2][SR]); history sniffing through `:visited` reached 3,000 URLs per second in 2018 ([Smith et al., WOOT 2018](https://www.usenix.org/conference/woot18/presentation/smith)) |
| **Web developers** | "Why is this element not red?", "why did this restyle?", "which selector is slow?", "why did the parser move my element?" | `css` questions titled "not working" outnumber those mentioning "specificity" 28,359 to 357 ([GO 1.9][GO]); CDP returns matched rules without a winner or a reason, so a client must re-derive the cascade itself ([CDP protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json), [GO 3.8][GO]); the only documented restyle causality in Chrome is an initiator arrow ([Chrome](https://developer.chrome.com/docs/devtools/performance/reference), [GO 3.5][GO]); no browser shows tree-construction decisions ([GO 5.4][GO]) |
| **Authors of sanitizers and templating systems** | "What I sanitize must be what the browser builds" | Chrome 146's sanitizer had two bypasses, each from a check that disagreed with the full parser of its micro-grammar (an SVG attribute name, a URL) ([Searchlight Cyber](https://www.slcyber.io/research/two-bypasses-for-chromes-sanitizer-api), [SR 2.7][SR]); a differential generator bypassed 9 of 11 sanitizers ([GO 5.7][GO]) |
| **Izcal's engineers and agents** | "Reproduce this restyle exactly", "prove this invalidation is complete", "track the specs without a rewrite" | The HTML parser lost two insertion modes and gained five tokenizer states, a node type and a sanitizer in 2025–2026, in more than ten parser changes in 2026 alone ([SP 1][SP], [factcheck][FC]); `:has()` invalidation bugs were still being fixed in WebKit four years after it shipped ([HP 8.8][HP]); invalidation bugs are silent wrong-style bugs |
| **Izcal's own UI** (shell, DevTools, prompts) | "Render untrusted page titles and user themes safely" | The shell is an HTML application rendered by Izcal (Stage 1 D-S2), so the parser and style system run in Izcal-only renderers too |

**What Izcal's specs already decide.**

- **[M-1][H2] (2.3.0).** No engine library: Izcal builds the DOM, HTML and CSS parsers, selector matching and style system from the specifications, anchored at pinned revisions (ANC-1), with other engines as black-box differential signals only.
- **[HGBA-2 4.3][H2].** Adaptive parallelism, bit-identical to the sequential path; its "uses the `stylo` crate" text is superseded and is rewritten from this spec (Section 9.5).
- **[HGBA-3 B5 and B6][H3].** Specialized invalidation with early cutoff and a from-scratch reference path; INC-2 (no frame class slower than from-scratch by more than 1.2×) and INC-4 (fallback rate published, ≤ 50%†) apply to style (ST-28, ST-29); computed style shared by sharing at several levels, with per-property struct-of-arrays rejected. B5's "Style keeps Stylo's own invalidation" text is superseded (Section 9.5).
- **[Stage 1 3.3][S1].** Phase purity: workers read immutable inputs and write disjoint outputs; "a style-sharing cache with racy insertion order" is named as the risk.
- **[JavaScript engine spec][JS] (owner-accepted).** JS-D4: one copy of the DOM, as node columns outside the cage (32-bit slot plus generation; tag as static index or atom; flags and element state; attribute-set reference; inline-style reference; rare-data index), read by style workers only during a flush with the script thread blocked, never written by them; the mutation log with old values stays. JS-D15: decision points whose timing depends on other threads are recorded B1 inputs. One implementation of each implementation-approximated math function on every ISA (JS 6.9).
- **[Resource-footprint spec][FP] (owner-accepted).** FP-11: node columns ≤ 48 B† and DOM + style + layout + paint ≤ 512 B† per node on the corpus; FP §6.4: attribute sets, computed-style groups and parsed sheets shared only within one partition; derived data in class (a) arenas, released after a safepoint handshake; FP-12 discard-and-rebuild bit-identical; FP-24 canonical bytes bit-identical across runs; UA style data in the read-only engine image; FP-D16's regenerable-cache class.
- **[DevTools spec][DT] 0.3.** Why-queries under replay (DT-D3), a Style domain at M3, and Q-DT-4, which asked what Stylo's API would expose. Under 2.3.0 that question disappears (Section 6.13).

**Scope.** In: byte-stream decoding for HTML and CSS, the HTML tokenizer, tree builder, fragment parsing, the sanitizer's parser integration, serialization, `document.write`, speculative parsing, the XML parser, CSS syntax, property value grammars, selectors, the cascade, computed values (including the substitution functions and registered properties), media and container query evaluation on the style side, CSSOM's data model, invalidation, and the style data structures. Out, with interfaces stated here: fetch and the network service (networking spec, written in parallel), fonts and text shaping (fonts and text spec, written in parallel), layout and paint (a later spec), the animation engine (a later spec; this spec defines its cascade inputs), and the JavaScript engine.

**What success looks like.** Every html5lib tokenizer test and WPT tree-construction case passes; WPT parsing, selector and cascade directories at or above the best shipping engine; incremental restyle equal to from-scratch restyle on every frame of the mutation corpus; parallel equal to sequential down to canonical bytes; style bytes per element within FP-11; restyle latency on rule-heavy applications competitive with the best shipping engine; every computed value explained down to its winning declaration and the spec step that decided it.

## 2. History: what came before and why it was built that way

### 2.1 Chronology

| Year | Project | What it did | Why that way | Fate and why |
|---|---|---|---|---|
| 1998–2005 | Pre-HTML5 parsers (Netscape, IE, Gecko's 1998 parser) | Turned invalid markup into trees by reverse-engineering the market leader | No specification for invalid input; HTML was nominally SGML ([HP 1.1][HP]) | Replaced: not spec-defined, hard to maintain, blocked off-main-thread parsing and inline SVG ([HP 10.1][HP]) |
| 2006–08 | HTML5 parsing algorithm (Hickson), html5lib and html5lib-tests | An error-handling algorithm for all input, plus an engine-neutral test corpus | A billion-document crawl showed what the web did; tokenizer closer to IE, tree builder closer to WebKit ([HP 1.2–1.4][HP]) | **Survived** everywhere; ended fifteen years of reverse-engineering |
| 2008 | WebKit preload scanner; IE8 parallel script downloads | A side parser fetches resources while the main parser is blocked on a script | Blocking scripts serialized loads: WSJ 6.3 s → 3.5 s with 50 ms latency ([WebKit](https://webkit.org/blog/166/optimizing-page-loading-in-web-browser/)) | **Survived** in every engine; it does not have to be right to be useful |
| 2009–11 | Gecko HTML5 parser (Firefox 4) | Validator.nu's Java parser mechanically translated to C++; tokenizer and tree builder off the main thread, producing tree operations | One conformance-tested source for validator and browser ([HP 1.5–1.6][HP]) | Alive in 2026, still regenerated from Java; every change crosses two languages and a custom translator ([HP 1.7][HP]) |
| 2009, 2011 | Two attempts to parallelize Gecko's cascade | Parallel styling in C++ | Cascading "looks an ideal parallel problem" | **Abandoned**: thread-safety bugs in caches and global mutable state ([HP 7.1–7.2][HP]) |
| 2011 | WebKit ancestor Bloom filter | Rejects descendant selectors without walking ancestors | Descendant-heavy sites spent most matching time walking up (~30% faster, a profiler estimate) ([WebKit bug 53880](https://bugs.webkit.org/show_bug.cgi?id=53880)) | **Survived**; every engine uses the idea ([HP 12][HP]) |
| 2013–22 | WebKit/Blink background HTML parser | Tokenizer on a thread, with a tree-builder simulator and rewind for `document.write` | 2013 mobile hardware: −8–14% DOMContentLoaded on a 2012 Android tablet (Nexus 7) ([WebKit bug 110408](https://bugs.webkit.org/show_bug.cgi?id=110408)) | **Removed** in WebKit after the Blink fork (2014, no stated reason) and in Blink (deleted 2022-02-02), after a budgeted foreground parser its author expected to be "less complicated" with "a faster time-to-first paint" became the default ([HP 2.6–2.8][HP]) |
| 2013 | CSS Syntax 3 | Algorithmic tokenizer and parser with defined error recovery | Bison grammars got error recovery wrong ([HP 4.2–4.3][HP]) | **Survived**; Blink rewrote from ~2014, WebKit switched in December 2016 ([HP 4.4–4.5][HP]) |
| 2014 | WebKit CSS selector JIT | Selectors compiled to machine code; ~2× on common selectors in a microbenchmark | Interpreter dispatch cost ([WebKit](https://webkit.org/blog/3271/webkit-css-selector-jit-compiler/)) | Alive in 2025; needs a second matcher for JIT-off modes such as Lockdown Mode, and their divergence produced bugs ([WebKit bug 301090](https://bugs.webkit.org/show_bug.cgi?id=301090)) |
| 2014–15 | Blink invalidation sets | Selector features compiled into invalidation data; pending sets applied lazily | Exact rule-to-element dependencies cost too much (Blink's published design document, [HP 8.3][HP]) | **Survived** in the same shape in every engine: static data, dynamic flags, broad fallback ([HP 8][HP]) |
| 2016 | Chrome `document.write` intervention | Skips cross-site parser-blocking written scripts on 2G | 7.6% of 2G loads had such a script; FCP −21% ([Chrome](https://developer.chrome.com/blog/removing-document-write)) | Kept; the HTML standard now explicitly allows skipping them ([HP 3.1, 3.3][HP]) |
| 2016–17 | Blink generated `ComputedStyle`; Blink style-sharing removal | Property storage generated from a data table, as Blink's published `ComputedStyle` documentation describes; per-element sharing guesses deleted | Hundreds of properties cannot be hand-maintained consistently; sharing was unpredictable and blocked other work ([HP 6.4–6.5][HP]) | Generation **survived** (Blink documents it); opportunistic sharing **removed** at a <10% cost |
| 2017 | Stylo (Firefox 57) | Parallel Rust style system; rule tree, sharing cache with revalidation selectors | Rust made shared state visible; a static analysis found >30 hazards in the C++ boundary ([HP 7.3–7.4][HP]) | Alive. | 2021–22 | `:has()` (WebKit, then Blink) | Upward invalidation with argument-feature filters, flags, caches and a subtree Bloom filter | Long refused as too slow for a streaming, right-to-left matcher ([HP 5.3][HP]) | Shipped everywhere by December 2023; still being tuned in 2026 ([HP 8.5–8.8][HP]) |

### 2.2 Technology mismatches: assumptions that no longer hold

| Assumption | Where it is baked in | Why it no longer holds |
|---|---|---|
| Parsing and style are sequential, single-core work | Pre-2017 style systems | Every device has many cores, but the published gains of parallel style are page-dependent and small (≈0% on 2011-era pages; ≈1.35× on one custom-property test; gains that "level off" at 6 threads) and parallelism costs sharing and memory ([PI 4.2–4.3, 6][PI]) |
| Pages are parsed once from the network | Background parser designs | Fragment parsing (`innerHTML`, `DOMParser`, `setHTML`) is a hot path: WebKit gained ~20% on one Speedometer 3 subtest from `DOMParser` work, and `innerHTML` is ~4.5% of Speedometer 3 time ([PI 2.2][PI], [HP 2.9][HP]) |
| Style does not depend on layout | All classic pipelines | Container size queries force style to re-enter after the container's layout ([SP 15.6][SP]) |
| Values are static per declaration | The CSS 2 pipeline | `var()`, typed `attr()`, `if()` and `@function` make computed values an interpreter with cycles, limits and taint ([SP 14][SP]) |
| Mutations invalidate only the element and its descendants | Pre-`:has()` invalidation | `:has()` invalidates ancestors and earlier siblings ([PI 7.7][PI]) |
| Stylesheets rarely change | Coarse sheet invalidation | Constructed sheets and CSS-in-JS mutate rules at runtime ([HP 11][HP]) |
| Runtime code generation is acceptable for speed | Selector JIT | Jitless policies, Lockdown modes and Izcal's jitless Izcal-only renderers make a JIT-only fast path a second implementation ([HP 5.7][HP]) |
| Equal values are enough | Stylo's thread-local sharing | Izcal observes memory too: DET-1 hashes, FP-11 budgets and FP-24 canonical bytes ([GO 8.3][GO]) |
| `:visited` is safe with property restrictions | 2010 mitigation | Timing attacks defeated it ([WOOT 2018](https://www.usenix.org/conference/woot18/presentation/smith)); Chrome 136 partitions history ([Chrome](https://developer.chrome.com/blog/visited-links)), and Selectors 4 describes partitioning in Appendix C and calls the restrictions "an arms race that can't be won" ([Selectors 4](https://drafts.csswg.org/selectors-4/#visited-privacy)) |

## 3. Today: the landscape and its gaps

**What developers and engines cannot see.**

- **No "why" in the protocol.** CDP's `CSSProperty` has no overridden flag and no reason, so a client must re-derive the cascade ([GO 3.8][GO]). Cascade-feature views (layers, container badges, `@scope`) show where a rule lives, not which criterion decided the winner ([GO 3.11][GO]).
- **Restyle causality is thin.** Chrome documents one initiator arrow from an invalidation to a recalculation; Microsoft added a per-selector invalidation count in July 2025 ([GO 3.2, 3.5][GO]). Nothing links a mutation to the restyle it caused and the properties that changed.
- **Parser decisions are invisible.** Firefox View Source shows a subset of parse errors; no tool shows foster parenting, adoption-agency moves or implied end tags; the tree-construction tests check trees and error counts, not reasons ([GO 5.2–5.5][GO]).
- **Nobody publishes the numbers that keep an incremental style system honest**: over-invalidation, full-restyle fallback frequency, sharing hit rate, container-query restyle cost, document-parser MB/s ([PI 13][PI]).
- **Static analysis of selectors exists only in research.** "Can this rule ever match?" and "do these selectors overlap?" are decidable in bounded forms (selector intersection is NP-complete) and have tools outside browsers ([GO 7.3–7.4][GO]).

**What the evidence says about where time goes.** No current public split of main-thread time by phase exists ([PI 1.7][PI]). WProf (2013) found HTML parsing the largest compute item on the load critical path at 10% of load time ([PI 1.2][PI]); style recalculation is now mostly an interaction-latency problem on rule-heavy applications ([PI 1.5][PI]). Scanning for special characters reaches 6.8–7.5 GB/s in shipping engines ([Lemire 2025](https://arxiv.org/html/2503.01662v2)), so tokenizing is unlikely to be the bottleneck; tree building, node creation and yielding are the likelier costs, and Izcal measures tokenizer throughput at ST-M0 ([PI 8.1][PI]). The median mobile page has 594 elements (2024 crawl) and 613 style rules (2022 crawl); the heavy tail of applications has 10k–28k rules ([PI 11][PI]).

**What Izcal could expose that no one does** (Izcal capabilities: B1 replay, the B4 mutation log with old values, the B5 reference path, ANC-1 anchors, its own UI renderer):

| Opportunity | Evidence of need | Who does it today |
|---|---|---|
| A **cascade trace** produced by the production cascade: every candidate declaration and the criterion that eliminated it, with its spec anchor | [GO 1, 3.8, 4][GO] | No one ([GO 10.1][GO]) |
| **Restyle causality**: mutation → invalidation entry → restyled element → changed groups, and a "restyled for nothing" count | [GO 3.2, 3.5][GO]; [PI 7][PI] | Partly (an initiator arrow, a per-selector count) |
| A **parse-decision log** with error codes, source ranges, insertion mode and the action taken | [GO 5][GO] | No one |
| **Probes at no live cost** (selector statistics, `:has()` cost per rule, container-query evaluation) run on a B1 replay | [GO 3.1, 3.13][GO] | No one |
| **Deterministic sharing**: parallel equals sequential including memory | [GO 8.3][GO]; [PI 4.3][PI] | No one |
| **Bounded static selector queries**: never matches, may affect, overlap | [GO 7.3–7.4][GO] | Research tools only |
| **Property tables generated from the specs' own data**, checked at build time | [GO 6.9–6.10][GO]; [HP 6.5][HP] | No one; Blink documents a private table |
| **Answers for agents, not dumps**: non-default properties and their reasons | [GO 9.1–9.2][GO] | No one |
| The **user origin** as a capability-scoped, in-memory style sheet with a real UI | [GO 9.3–9.5][GO] | Partly (Firefox, behind a pref) |

## 4. First principles

### 4.1 Users' real tasks

| Task | What the engine must provide |
|---|---|
| See the page soon after the first bytes arrive | A streaming parser whose first node appears within a bound of the first byte; resources behind a blocking script discovered at once; render-blocking style applied as soon as it arrives |
| Interact without delay | Restyle cost proportional to what changed, with `:has()`, custom properties and container queries bounded per mutation |
| Get the same page every time | Parse and style results that are functions of the bytes, the recorded inputs and the build, never of thread timing |
| Insert markup safely | One parse, in the right context, with sanitization during that parse, and a serializer whose output re-parses to the same tree except where the spec says otherwise |
| Understand why something looks as it does | The winning declaration, every loser and the criterion that eliminated it; the mutation that caused a restyle; the parser decision that placed a node |
| Keep the browser small and private | Style bytes per element within FP-11; caches keyed by partition; no history the site could not observe |

### 4.2 Platform primitives

The specifications define the semantics, at pinned revisions (M-1 part 2):
- **HTML** (whatwg/html commit): the input byte stream and encoding sniffing (§13.2.3), the tokenizer (84 states as of 19 October 2026) and tree builder (21 insertion modes, foreign content rules), the re-entrancy control state (script nesting level, parser pause flag, insertion point, the throw-on-dynamic-markup-insertion and ignore-destructive-writes counters), the fragment parsing algorithm and its parameters (context element, root insertion target, scripting mode with four values, declarative shadow roots allowed, sanitizer configuration, insertion-target redirection map), speculative HTML parsing (§13.2.8), serialization (§13.3), dynamic markup insertion (§8.4), the sanitizer (§8.6) and XML integration (§14) ([SP 1–9][SP]).
- **CSS**: Syntax 3 (25 token types plus EOF; ten parser entry points; nesting's declaration-then-rule back-track), Selectors 4 and CSS Shadow 1, Cascade 5 and 6 (seven sort criteria, eight origin levels), Nesting 1, Values 4 and 5 (computed-value pipeline, `calc()` typing and simplification, arbitrary substitution functions with cycle and length rules, `attr()` taint), Properties and Values API, Conditional 5 (media, supports, container queries), CSSOM 1 (rule interfaces, constructed sheets, resolved values, origin-clean) ([SP 10–16][SP]).
- **Encoding Standard**: decoders, encoders, labels and index data.
- **Spec-extracted data**: `entities.json` (2,231 named references), `@webref/css` (822 property entries, 758 distinct; 55 at-rules; 171 functions; 157 selectors; 529 value types) ([SP 1.6, 14.9][SP]).
- **Oracles**: html5lib-tests (6,827 tokenizer tests), WPT (1,973 tree-construction cases in `html/syntax/parsing`, and the CSS directories with their sizes in [SP 17.3][SP]).

The engine's data: JS-D4's node columns and rare data, the attribute sets (hash-consed, immutable, copy-on-write per partition, FP §6.4), the mutation log with old values, the text arena, and the environment inputs B1 records (viewport, preferences, fonts, time).

### 4.3 Izcal's principles that bind this design

P1 (security and privacy first: one site per process, partitioned caches, no history the site could not observe); P2 (spec conformance gates every optimization: incremental, parallel, shared and speculative paths must equal the reference); P3 (a correct fallback for every fast path: from-scratch restyle, foreground parsing); P4 (latency measured end to end); P6 (every number sourced or marked †); M-1 parts 1–4; B1 (determinism by construction: concurrency changes when work is done, never what is decided, JS 6.9); B4 as restated by JS-D4; B5 (early cutoff, reference path); FP-11, FP-12, FP-24.

### 4.4 Assumptions kept and broken

| Assumption from existing engines | Keep or break | Why |
|---|---|---|
| The HTML parser runs on the main thread | **Keep**, with a speculative parser off it | Node creation must happen on the script thread (JS-D4); scanning runs at GB/s, so tokenizing is unlikely to dominate (measured at ST-M0); Blink replaced its background parser with a budgeted foreground parser ([HP 2.7–2.8][HP]); the measured gain of a threaded parser (8–14%) was on 2013 mobile hardware with a 2012 tablet ([HP 2.5][HP]). ST-D2 keeps a measured alternative |
| A separate fast-path parser for `innerHTML` | **Break** | A second HTML parser that must agree with the first is the shape of every mXSS case: two parses that disagree, with the sanitizer's parse different from the sink's ([SR 2.3–2.4, 2.10][SR]). Izcal makes the one parser fast for fragments |
| A separate preload scanner tokenizer | **Break** | The spec models speculation as the normal tree builder on mock elements ([SP 5.2][SP]); running the same code on a mock sink makes speculation differential-testable and removes a second tokenizer |
| Sanitizing after parsing | **Break** | The standard now sanitizes inside the parser (13 October 2026); a post-pass reintroduces the round trip that mXSS exploits ([SP 6.6][SP]) |
| Hand-written property code | **Break** | Blink documents generating it from a private table ([HP 6.5][HP]); Izcal generates it from the specs' own data, checked |
| Selector matching right to left with a rule index and an ancestor filter | **Keep**, derived (Section 6.18) | Most rules can be rejected from the subject's own features and a small summary of its ancestors; published evidence: Meyerovich and Bodík's 4–25× from indexing ([PI 3.1][PI]) and WebKit's filter ([WebKit bug 53880](https://bugs.webkit.org/show_bug.cgi?id=53880)) |
| A selector JIT | **Break** | A second matcher that can disagree ([WebKit bug 301090](https://bugs.webkit.org/show_bug.cgi?id=301090)), a code generator fed by page CSS, and unavailable in jitless renderers |
| Sharing by guessing a similar sibling | **Break** | Unpredictable ([HP 6.4][HP]); correctness rests on a hand-kept list of selectors that could tell candidates apart ([HP 6.3][HP], from Mozilla's published description); thread-dependent ([bug 1385982](https://bugzilla.mozilla.org/show_bug.cgi?id=1385982)) |
| Sharing from the data model (shared groups, a matched-declarations key) | **Keep**, made content-addressed | It survived in every engine because it is deterministic ([HP 12][HP]) |
| Invalidation from selector-compiled data plus dynamic flags plus a fallback | **Keep**, with three changes | Old values make the self check exact; flags are recomputed on every match and never accumulate (the sticky-flag pathology, [PI 3.9][PI]); every restyle records its cause, and over-invalidation is measured against the reference |
| Style recursion on DOM depth | **Break** | A parser depth cap does not stop script-built trees ([Mozilla's 2010 review](https://wiki.mozilla.org/Security/Reviews/Firefox4/HTML5_Parser_Security_Review)); recursion has crashed engines ([WebKit bug 243957](https://bugs.webkit.org/show_bug.cgi?id=243957)). Every tree walk is iterative |
| `:visited` with property restrictions as the defence | **Break** (restrictions kept as defence in depth) | Partitioned history makes the state observable to the site anyway ([SR 3.10–3.11][SR]) |
| Mutation events | **Break**: not implemented | Removed from Chrome as "the source of many crashes and security bugs" ([Chrome](https://developer.chrome.com/blog/mutation-events-deprecation)) |
| XSLT | **Break**: not implemented | Marked deprecated in HTML on 25 August 2026 ([whatwg/html 208004fb](https://github.com/whatwg/html/commit/208004fb)) |
| Parallel style is a large win | **Break** | The published measurements are small and page-dependent: ≈0% on 2011-era TP5 pages ([bug 1331578](https://bugzilla.mozilla.org/show_bug.cgi?id=1331578)), ≈1.35× on one custom-property test ([PI 6.3][PI]), gains that "level off" at 6 threads ([bug 1431285](https://bugzilla.mozilla.org/show_bug.cgi?id=1431285)); one MotionMark stress test bound by an allocator lock gave 31 → 24 ms at 6 threads ([PI 6.2][PI]). Parallelism is designed in for heavy pages and never allowed to change results or memory |

## 5. Lessons learned

Ideas and evidence only; no code and no template is taken from any project (M-1).

| Project | What happened | Lesson | How Izcal applies it |
|---|---|---|---|
| HTML5 algorithm and html5lib-tests | A complete error-handling algorithm and a shared corpus ended reverse-engineering ([HP 1][HP]) | Specify all input; test against a shared oracle | Implement from the pinned text; html5lib-tests and WPT `.dat` cases at 100% (ST-1) |

| Gecko speculative tree building | Tokenizes and builds speculatively off the main thread and loses that work when `document.write` intervenes ([Mozilla Hacks 2017](https://hacks.mozilla.org/2017/09/building-the-dom-faster-speculative-parsing-async-defer-and-preload/), [PI 8.6][PI]) | Speculation needs a measured failure policy | ST-D2's alternative (b) is built at ST-M1 and measured, with the failure rate published (ST-25) |

| Chrome 146 sanitizer bypasses | Two bypasses, each from a check that disagreed with the full parser of its micro-grammar: an SVG attribute name and a URL ([Searchlight Cyber](https://www.slcyber.io/research/two-bypasses-for-chromes-sanitizer-api)) | One parser per micro-grammar | No check may decide anything the full parser of its grammar would decide differently (G22); a differential suite (ST-8) |

| Stylo thread-local sharing cache | 2.3× more style contexts in parallel on one page; +20 MB going 1 → 3 threads on a 154k-element page before a fix ([bug 1385982](https://bugzilla.mozilla.org/show_bug.cgi?id=1385982), [bug 1397380](https://bugzilla.mozilla.org/show_bug.cgi?id=1397380)) | Parallelism can defeat sharing | Deterministic interning after the parallel phase; parallel equals sequential in canonical bytes (ST-5) |

Parsers and the style system are tier R crates with `#![forbid(unsafe_code)]` (G5), except where Section 6.15 names an inventoried module.

### 6.1 Bytes in: encoding and streaming

**Decoders (ST-D16).** `hg-encoding` implements the Encoding Standard's decoders and encoders, with tables generated at build time from the standard's index files (standards data, M-1 part 1). `encoding_rs` is excluded: it was written for Gecko and does browser-engine work. The same crate serves `TextDecoder`, `TextEncoder`, `hg-url`'s query encoding and form submission, so it lives in the shared sub-layer L2s (Section 6.15), written to tier P because network services and the broker link it through `hg-url`; this spec owns it ([reconciliation P2][RN]).

**URLs.** `hg-url` implements the WHATWG URL Standard: the parser and serializer, host parsing with UTS 46 (IDNA) from the fonts and text spec's `hg-ucd` and `hg-unicode`, the registrable domain from the networking spec's `hg-psl`, and the backing of `URL` and `URLSearchParams`. It is the browser's one URL parser (G31): renderers, network services and the broker's navigation code link it, so it is tier P, and a URL check elsewhere that disagreed with it would repeat one of the two Chrome 146 sanitizer bypasses ([Searchlight Cyber](https://www.slcyber.io/research/two-bypasses-for-chromes-sanitizer-api), G22). No spec owned it before the reconciliation; this spec does, because it has the parser-generation and differential machinery and owns `hg-encoding` ([P6][RN]). WPT `url/` is its oracle (ST-15).

**Sniffing.** The HTML byte stream follows the spec's order exactly: BOM, user override, transport charset, prescan of the first 1024 bytes, XML declaration, same-origin parent's encoding, then the locale default ([SP 2.2–2.3][SP]). **Izcal performs no statistical autodetection on network content**, which the spec calls "generally discouraged"; it applies UTF-8 detection to local files, as the spec recommends. The locale default is a recorded B1 input. Raw bytes are kept until confidence is certain or the prescan window has passed, so the one permitted "change the encoding" re-parse re-reads memory, never the network ([SP 2.4][SP]). Stylesheets follow CSS Syntax 3's four-step fallback, with the referring document's encoding as the environment encoding ([SP 10.4][SP]).

**Streaming.** Decoded code points flow to the tokenizer in chunks as the network service delivers bytes. Chunk boundaries are B1 inputs: the renderer records each data-pipe read as an IPC input (Stage 1 3.4), and the networking spec's own recording (NW-D2) is joined to it by request ID ([P20][RN]). For a document whose scripts do not observe parsing, the resulting tree is independent of the chunking; a property test splits every corpus document at random points and compares trees (ST-40).

### 6.2 One HTML parser core (ST-D1, ST-D3)

**One core, many sinks.** `hg-html-syntax` contains the tokenizer and the tree builder and nothing that touches the DOM. The tree builder is generic over a `TreeSink` trait whose operations are the spec's tree mutations (create an element for a token, insert at an appropriate place, append text, reparent for the adoption agency algorithm, attach a declarative shadow root, and so on). Four sinks exist:

| Sink | Used by | Builds |
|---|---|---|
| `DomSink` (`hg-html-driver`) | Document parsing; script-created parsers | Nodes in `hg-dom`'s columns, on the script thread |
| `FragmentSink` | `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `setHTMLUnsafe`, `parseHTMLUnsafe`, the positional `*HTML` methods, `createContextualFragment`, `DOMParser` (`text/html`) | Nodes in an inert document, or directly into the root insertion target as the 9 July 2026 refactor specifies ([SP 6.1][SP]) |
| `SanitizingSink` | `setHTML`, `parseHTML` and the safe positional methods | As `FragmentSink`, with the parser sanitizer configuration and redirection map applied at element creation, as the standard specifies since 13 October 2026 ([SP 6.6][SP]) |
| `MockSink` | The speculative parser (Section 6.4) | Speculative mock elements; its only output is speculative fetches |

The parser's parameters are exactly the spec's: context element, root insertion target, scripting mode (Normal, Disabled, Inert, Fragment), declarative shadow roots allowed, sanitizer configuration and redirection map ([SP 1.7–1.8][SP]). **No entry point has its own parser**, including the preload path and the fragment fast path: that is the engine-side rule the mXSS record supports ([SR 2][SR]). The sink is a generic parameter, so each sink is monomorphized and the fragment path pays no dynamic dispatch.

**Fragments are fast without a second parser.** The fragment path's costs are likely to be node creation and attribute interning rather than tokenizing ([PI 8][PI]); ST-M0 measures the split. `FragmentSink` writes nodes and text directly in their final form (no intermediate fragment), and the tokenizer's data-state loop scans for its special characters with the `memchr` crate's vectorized search (generic infrastructure). ST-21 sets the fragment throughput target. A subset parser that bails out is rejected (ST-D1 (b)).

**The tokenizer is generated from a state description (ST-D3).** The tokenizer's 84 states are written in a declarative description (`.hgtok`, Izcal's own format): per state, the code-point classes, the actions (emit, append, switch, reconsume, named parse error) and the `// spec:` anchor of each transition. `hg-htmlgen`, a Rust build tool, generates three things from it: the production tokenizer (a loop over states, with vectorized scanning in the states that consume long runs: data, RCDATA, RAWTEXT, script data, attribute values, comments); a **reference stepper** that executes one code point per step in the spec's literal order, used only as an oracle; and the transition coverage table that ANC-1 and the fuzzers read. The description and the generator are Rust and Izcal formats only: no second source language, which is the lesson of Gecko's translator ([HP 1.7][HP]). Named character references come from `entities.json` as a generated, read-only lookup structure in the engine image.

**The tree builder is hand-written in spec order.** Its 21 insertion modes and the foreign-content rules are prose algorithms with many cross-references; a table cannot express them more clearly than structured Rust can. Each step carries its anchor; the bounded loops of the adoption agency algorithm (8 and 3) and the Noah's Ark clause (3) are explicit constants with anchors ([SP 4.1–4.2][SP]).

**Parse errors and the parse-decision log.** The tokenizer's 52 named errors carry their codes; tree-construction errors, which have no codes in the spec ([SP 1.4][SP]), get Izcal names derived from the insertion mode and the step anchor. When recording is on (DevTools or a B1 replay), the tree builder emits a **parse-decision log**: error code, source range, insertion mode, and the action taken (foster-parented, reparented by adoption agency step N, implied end tag, dropped by the sanitizer, capped at depth 512), keyed to the produced node IDs. It costs nothing when not recorded (Section 6.13).

**Depth.** Izcal adopts the interoperable cap: past 512 open elements, new elements are inserted as children of the 512th, which WebKit's published layout-test expectation shows ([SR 4.2][SR]) and which ST-M0 confirms black-box on every shipping engine (Q-ST-3), recorded as a resource-constraint deviation with an anchor to [whatwg/html #3732](https://github.com/whatwg/html/issues/3732). The XML parser caps nesting at 5,000, the value a Mozilla web-platform test states for most engines ([SR 4.4][SR]), also confirmed black-box.

### 6.3 Re-entrancy: typed call-outs, nothing held across them

The parser calls into script at three kinds of points, and script calls back into the parser or mutates the nodes it holds ([SP 3][SP], [SR 6][SR]):

| Call-out | When | What the parser holds across it |
|---|---|---|
| Script execution at `</script>` | Parser-inserted classic scripts | Nothing: the tree builder **returns** `Yield::RunScript(node)` to the driver, which runs the script after the parser's borrow ends |
| Custom element construction | "Create an element for a token" with a definition and a non-fragment parser | Nothing: the builder returns `Yield::ConstructElement`; the driver runs the constructor with the throw-on-dynamic-markup-insertion counter raised, then resumes the builder with the new node's ID |
| `attributeChangedCallback` and other reactions | While appending parsed attributes | As above |
| Microtask checkpoint | Before synchronous construction when the JS stack is empty | As above |
| `document.write` / `writeln` | From script, possibly nested | The driver inserts at the insertion point and invokes the tokenizer again; the nesting is explicit state, not Rust recursion |

**The rule, enforced by types.** Parser and driver state live in `TokenCell`s, and every call that can run script takes `&mut ScriptToken` (CS-TY-10, CS-D3), so no borrow of parser, DOM or CSSOM state can be live across a call-out. The tree builder holds **node IDs with generations** (JS-D4), never references, and re-validates its insertion target after every call-out, which the four 2026 spec changes for script-mutated trees now require ([SP 3.6][SP]). A stale ID is detected, never aliased. Compile-fail tests and planted bugs cover each call-out (ST-11).

**`document.write`.** Implemented exactly, with both counters, the unload counter and the "active parser was aborted" flag ([SP 3.2–3.3][SP]). The nesting depth of `document.write` is unspecified (whatwg/html #1954); Izcal caps it at a depth measured black-box at ST-M0 to match the engines, recorded as a deviation (Q-ST-4). Izcal applies **no network-conditioned intervention** that skips written scripts: the spec permits one ([HP 3.1][HP]), but a hidden heuristic would make page behaviour depend on network type. Any future intervention is a recorded B1 input and an owner decision.

**Not implemented (ST-D4).** Synchronous mutation events, the largest historical source of re-entrancy bugs ([SR 6.4][SR]), and XSLT, now deprecated in HTML ([SP 9.3][SP]).

### 6.4 Scheduling the parser, and speculation (ST-D2)

**The parser runs on the script thread.** It must: node creation writes `hg-dom`'s columns, which only the script thread writes (JS-D4), and running scripts and constructors interleaves with tree building. Tokenizing a typical page takes well under a millisecond at the speeds measured ([PI 8.1][PI]), so moving it off-thread buys little and costs a hand-off per token batch.

**Yields are decision points.** The parser runs in tasks of the networking task source and yields to the event loop so the page can render progressively and input is not starved. Two budgets follow from first principles: a **token budget** bounds the work between yields as a function of the input alone, and a **time budget** bounds the wall-clock delay that slow tokens (large attribute values, deep reconstruction of formatting elements, custom-element construction) could otherwise add to input latency. A task ends when either is spent, so where the parser yields depends on timing and is therefore a **recorded decision point** (JS-D15): when recording, the token position of each yield is logged; on replay the parser yields at the logged positions; in simulation the time budget reads the virtual clock. The budget values are set from Izcal's corpus measurement at ST-M1. So production stays responsive and replays stay exact.

**The speculative parser runs the real code on mock nodes.** When the parser blocks on a script, a worker runs the same tokenizer and tree builder over a copy of the remaining bytes into `MockSink`, exactly the spec's model ([SP 5.2–5.3][SP]). It works in a **private, discardable atom scope**: unknown names are compared by string or by scope-local IDs and never interned into the agent's or the JS engine's atom tables, so the worker writes no shared state (Stage 1 3.3) and atom IDs never depend on its timing; G23 makes the agent's intern tables unreachable from the speculative path. It applies `<base>`, the CSP `<meta>`, `<meta name=referrer>` and `<meta name=viewport>`, and emits **speculative fetches only**: scripts (respecting `type`, `nomodule`, `async`, `defer`, `integrity`, `crossorigin`, `referrerpolicy`, `fetchpriority`), style sheets (evaluating `media` against the environment snapshot), images (`srcset` and `sizes` against the same snapshot), `<link rel=preload|modulepreload|preconnect>`, `<picture>` sources, and `@import` in inline `<style>` through `hg-css-syntax`'s prelude scan. It fetches each URL at most once per document, never fetches inside non-declarative template contents, and never while sanitizing ([SP 5.3–5.4][SP]). CSP follows the networking spec's split: the renderer runs the pre-request checks that need the document's policy (including policies added by `<meta>`, which only the renderer and the speculative parser see) before issuing a speculative or style-initiated request, and the partition service re-checks the fetch directives of the document's header-delivered policy, which it parsed itself from the document response it delivered; the broker parses no CSP (IPC-R15), so a compromised renderer can bypass only `<meta>` policies, a limit recorded in the renderer threat model ([NW 6.7][NW], [P16][RN]). Speculative requests are ordinary subresource fetches through the frame's `FetchEndpoint`, marked speculative ([NW 6.7][NW], [P22][RN]). Requests carry the document's partition and policy container; the partition service never trusts that container for its own check. Because it runs the real tree builder, the speculative parser's fetch set can be checked against what the real parser fetches on the same bytes when the blocking script does nothing: it must be a subset (ST-9).

**Speculation is discarded, not reused.** When the blocking script finishes, the real parser continues from its own state; the mock tree is dropped. Reuse (Gecko's design) saves tree-building work, but the real builder must still create every node on the script thread, and reuse needs a rewind path for `document.write`. ST-D2 keeps reuse as alternative (b), built at ST-M1 in an experimental build and measured: it is adopted if it cuts corpus time-to-first-paint by more than 5%† without raising main-thread time.

**Determinism: speculation is a recorded decision point.** How far the speculative parser gets before the blocking script finishes depends on two threads' relative speed, and its requests are observable (Resource Timing, cache state of the later real fetch, the recorded network fixture). So, following JS-D15: in production each speculative request issuance is logged with the speculative parser's token position when recording; on replay the speculative parser runs to exactly the logged positions and issues exactly the logged requests; in simulation the worker runs on the seeded scheduler. When the real parser later requests a URL that speculation already fetched, it reuses the speculative response only if the request matches (URL, mode, credentials, integrity, destination), and that reuse is part of the logged decision. ST-41 covers speculation.

### 6.5 Fragments, the sanitizer, serialization, declarative shadow DOM and XML

- **Declarative shadow DOM** follows the parser flag: legacy sinks (`innerHTML`, `outerHTML`, `insertAdjacentHTML`) never attach shadow roots; the newer methods do ([SP 6.3–6.4][SP]).
- **Sanitizing inside the parser.** `SanitizingSink` never creates a disallowed element, drops disallowed attributes before creation, creates sanitized-away elements with no registry so no constructor runs, and starts no fetch. The configuration's allow and remove lists are compiled to atom sets at `Sanitizer` construction ([SP 6.6][SP]).
- **Serialization** implements §13.3, including `<` and `>` escaping in attribute values (May 2025) and the processing-instruction form ([SP 7.1–7.2][SP]). A **round-trip suite** parses, serializes and re-parses every corpus page, every WPT case and fuzz output in every fragment context with each scripting mode; the result must be a fixed point except for the cases the spec lists as non-idempotent, which are themselves tests ([SP 7.3][SP], ST-8).
- **XML (ST-D5).** `hg-xml-syntax` is Izcal's own XML 1.0 and Namespaces parser, driving the same sinks through the HTML standard's XML integration (§14): elements created through "create an element for a token", the 11 public identifiers mapped to the built-in entity DTD, no other external entities, `template` children into template contents, scripts at end tags, no `document.write`, and the `parsererror` document on failure ([SP 9][SP]). Library XML parsers are excluded as engine work under M-1's default; the owner confirms the classification.

### 6.6 CSS syntax and the property system (ST-D6, ST-D19)

**Syntax.** `hg-css-syntax` implements CSS Syntax 3 by hand, in spec order, with anchors: the tokenizer (25 types, with source offsets on every token so custom properties keep their exact source text and `unicode-range` can be re-tokenized), the ten entry points, nesting's declaration-then-rule back-track, `CSSNestedDeclarations`, and the "drop the whole declaration" rule for partial support ([SP 10][SP]). The shortcut "an ident that is not a known property means re-parse as a rule" reads the same generated property table that validation uses, so the two cannot disagree ([SP 10.6][SP]).

**One description per property, from the specs' own data (ST-D6).** `hg-cssgen` builds `hg-css-props` from two inputs:
1. **`@webref/css` at a pinned version**, as standards data: for each property its value grammar (`syntax`), initial value, inherited flag, animation type, longhands and spec URL ([GO 6.9][GO]).
2. **An Izcal overlay** (`.hgprop`, Izcal's own format) for what webref leaves as prose or does not cover: a closed set of **computed-value kinds** into which the 168 distinct computed-value texts are classified by hand ([factcheck 4][FC], [GO 6.10][GO]); the style group each property belongs to (Section 6.9); what a change affects (layout, paint, composite, nothing); quirks; pseudo-element applicability; and hand-written hooks for the few grammars with prose constraints.

From these, the generator emits: a parser per property from its value-definition-syntax grammar (CSS Values 4 §2), the computed-value type and conversion, inheritance and initial values, the interpolation type, CSSOM serialization, resolved-value rules for `getComputedStyle`, shorthand expansion and serialization, the "affects" mask that tells layout what a change dirties, DevTools metadata with the spec URL, and fuzz grammars. **The build fails** when the overlay contradicts webref (a different initial value, an inheritance flag, a grammar), so a spec change reaches Izcal as a build error with the pinned diff, not as silent drift. Blink documents generating from a private table ([HP 6.5][HP]); generating from the specs' own extracted data, with a failing cross-check, is new. Using webref's data is M-1-clean; using CSSTree or any CSS parser library is not.

**Parsed sheets.** A sheet is immutable `SheetContents`: flat arrays of rules, compiled selectors (Section 6.7) and declaration blocks of (property ID, value) entries, with `url()` values kept **unresolved**. Contents are shared within one partition, keyed by **(partition, URL, decoded-content hash, parsing mode (quirks, limited-quirks, no-quirks), environment encoding)** (FP §6.4), where the partition is the in-process projection (T, C, X, n) of the networking spec's key (NW-D7, [P18][RN]), and deduplicated by content, which Chrome found worth doing for identical sheets ([Chromium blog](https://blog.chromium.org/2024/06/how-chrome-achieved-highest-score-ever.html)). Everything that depends on how a document loaded the sheet stays **outside** the shared contents, on that document's `CSSStyleSheet`: the **origin-clean flag**, the CORS mode and response type, and the **base URL** against which `url()` values resolve at computed-value time. So a document that loaded a cross-origin sheet without CORS can never read rules through contents another document loaded with CORS, and a quirks document never sees a no-quirks parse. CSSOM mutation copies the contents for that sheet on first write (copy-on-write), and the copy is primary data (Section 6.11).

**Lazy declaration parsing (ST-D19).** The first-principles case: a declaration costs parse time and parsed-value memory, and a declaration whose rule never matches is never needed, while its source bytes must be kept anyway until the sheet is fully parsed. So selectors and at-rule preludes are parsed eagerly, because the rule index needs them, and a declaration block is tokenized for bounds and parsed into values on first need. Because shared contents are immutable, a block first needed during a parallel style pass is **parsed into the worker's task-local buffer** and **published in the deterministic merge** (Section 6.9), in document order, after which it is immutable; a block first needed by CSSOM is parsed on the script thread outside a pass. The parse is a pure function of the bytes, so which worker parsed first changes nothing, and the published block is the same whatever the thread count. Observers of a declaration's parse (the cascade, CSSOM) both force it, so laziness is not observable by script. Whether it pays depends on the share of declarations never used, which no source measures; ST-M0 measures it (Q-ST-7).

**The UA style sheet is in the engine image.** `hg-ua-style-build` compiles the HTML rendering section's UA sheet, the MathML and SVG UA sheets and the quirks sheet into the read-only, position-independent engine image (FP §6.3): parsed rules, the rule index, and the interned initial and UA-derived style groups. A site process maps it and writes nothing (FP-3).

**UA variants.** The UA cascade has environment-dependent parts (quirks rules, `forced-colors`, `prefers-color-scheme` defaults). Each variant's parsed rules and index are in the image; only the variant a document uses is touched, and its initial groups are interned per agent on first use (Section 6.11's fixed-cost table).

### 6.7 Selectors: representation and matching (ST-D9)

**Compiled selector programs.** Each complex selector compiles to a compact program over compounds, ordered right to left, with simple selectors ordered cheapest first inside each compound (tag and id before attribute substring tests, structural pseudo-classes last). `:is()`, `:where()`, `:not()` and nesting's `&` (as `:is()` with the maximum specificity of the parent list, [SP 13.1][SP]) are sub-programs; `:has()` arguments are relative sub-programs (Section 6.7.2). Programs are interpreted. **No machine code is generated for selectors** (ST-D9): the 2× microbenchmark gain is not worth a code generator fed by page CSS, a second matcher, or a fast path unavailable in jitless renderers ([HP 5.4–5.7][HP]).

**Rule index.** Per style scope (the document and each shadow root, with constructed sheets shared across scopes), rules are bucketed by the most selective required feature of their rightmost compound. The order of preference among key kinds (id, class, attribute name, tag, and any pseudo-class or scoping buckets) is chosen from Izcal's corpus selector statistics at ST-M0 to minimize candidates per element (Section 6.18), not taken from another engine. Each entry holds the selector program, the cascade key (Section 6.9), a **subject-covered flag** when the bucket key proves the whole selector, and the precomputed ancestor-filter hashes of the selector's ancestor compounds.

**Ancestor filter.** During a top-down traversal, the traversal keeps a compact, fixed-size summary of the current element's ancestors' tags, ids, classes and attribute names; an entry whose required ancestor hashes are absent is rejected without walking up. Size and hash count are chosen at ST-M0 from the measured distribution of ancestor-feature counts on the corpus, to minimize rejection cost per byte (Q-ST-6); the rejection and false-positive rates are published (ST-22). The summary is a function of the ancestor chain only, so a parallel task that starts at an element rebuilds it from that element's ancestors before its first match; its contents, and therefore every rejection, are independent of which worker runs the task.

**Counters by construction.** The matcher counts, per selector, attempts, matches, filter rejections and failures after the full program ran. In production these are compiled out; on a replay with probes enabled they produce selector statistics at no live cost (Section 6.13).

#### 6.7.1 State outside the tree

About 35 pseudo-classes depend on state outside the DOM tree: user action, location, media, display state, form state, `:defined`, `:state()`, `:dir()` and `:lang()` ([SP 11.6][SP]). Each has a named **state source**. Every source writes through `hg-dom`'s API **on the script thread**, either as a posted task or at a named step of "update the rendering", and logs a mutation with the old bits; the bit lives in JS-D4's element-state column if it is common, otherwise in rare data (Section 6.11). Sources outside script (media playback, fullscreen and the top layer, `:target` after navigation, `:autofill` from the shell) post a task whose input is a recorded B1 event. **`:hover` and `:active`** are recomputed at a named rendering step after layout, as a function of layout output and the recorded pointer position, so content moving under a still pointer changes hover deterministically. The heuristic of `:focus-visible` runs in the focus code, so its result is an input, not a style-time decision. The table of sources, with each writer and B1 input, is an ST-M0 deliverable.

#### 6.7.2 `:has()` (ST-D11)

`:has()` inverts the direction of matching and invalidation: the subject is the anchor, and its result depends on descendants or later siblings ([PI 7.7][PI]). Its matching design:

- **Per-pass memo.** Within one style pass, the result of (anchor, argument) is computed once. The memo lives for one pass because the tree is fixed only during a pass; it is per worker so that no worker writes shared state; its content is a pure function of the tree, so it cannot change results, only cost.
- **Choose the direction by cost.** For an argument whose rightmost compound is selective (an id, a class or attribute present on few elements), the matcher evaluates from the candidates upward: each element matching the rightmost compound walks toward the anchor checking the rest of the relative selector, and marks the anchors it satisfies. For a broad argument, the anchor searches its subtree or siblings downward with the memo. The choice is made per argument per pass from counts the rule index already has, so it is deterministic.
- **Subtree summaries.** A pass can compute, bottom-up, a summary per element of the features present in its subtree (the same hashes as the ancestor filter), so an anchor whose summary lacks the argument's required features is rejected without a walk. This mirrors the ancestor filter's reasoning in the other direction; it is computed only for subtrees under elements that the last match flagged as possible anchors, and its value is measured on a `:has()`-heavy corpus (ST-D11's trigger).
- **Bounds.** `:has()` cannot nest and excludes pseudo-elements ([SP 11.3][SP]); within that, the remaining super-linear cases (descendant chains inside the argument) are bounded by a **work budget per pass**, beyond which the pass falls back to the plain downward search for that argument, recorded as a cause.

### 6.8 Invalidation: precise where cheap, recorded always, checked against the reference (ST-D10)

**Inputs.** The flush reads the mutation log since the last flush. Its entries carry old values (JS-D4), and with immutable attribute sets an attribute change is a pair of set IDs, so the old and new features (classes, id, attribute names and values) are both available at no extra bookkeeping. State changes carry old and new bits; tree changes carry the old neighbours; text changes carry the old emptiness. Sheet changes (insert, remove, CSSOM mutation, `adoptedStyleSheets`, media or container environment change) are entries too.

**The invalidation index.** When a scope's sheets change, `hg-style` compiles, from every selector, an index from **features** (id, class, attribute name, state bit, `:has` argument feature, custom-element state, `:dir`/`:lang` inputs) to entries describing where the feature occurs: in the subject compound, in an ancestor compound (with the combinator path), in a previous-sibling compound, or inside a `:has()` argument (with the anchor's relation). The index is per sheet, memoized, and merged per scope, so changing one sheet rebuilds one part.

**From a mutation to a restyle set.** For each log entry, the changed features select index entries, and each entry yields a set of elements to re-match:

| Where the feature occurs | Elements re-matched | Precision step |
|---|---|---|
| Subject compound | The element itself | **Exact self check**: the whole selector is matched against the element's old and new state (both available from the log); only a real change in match result marks it |
| Ancestor compound | Descendants that can match the subject compound | Walk the subtree, testing only the subject compound's key; for `>` only children |
| Previous-sibling compound | Next sibling (`+`) or later siblings (`~`), and their descendants when the sibling compound is not the subject | Bounded by the longest `+` chain in the index |
| Inside a `:has()` argument | Anchors among ancestors or previous siblings | The argument's match for the mutated element is checked old versus new first; then the walk visits only elements whose **last match** flagged them as possible anchors |

**Flags are outputs of the last match, never accumulated.** Matching records on each element the dynamic facts invalidation needs (depends on hover, on its sibling index, may be a `:has()` anchor), and a later match of that element **replaces** them. The pathology Microsoft hit, flags set by `+` and `~` on `body`'s children that were never cleared, cannot occur ([PI 3.9][PI]).

**Early cutoff.** Re-matching yields a new match key and, through the cascade, a new computed style. Because styles are content-addressed (Section 6.9), equality with the old style is decided by comparing provisional content identities (a hash compare, then a full compare on a hash match): if equal, inherited inputs of the children are unchanged and the descent stops, unless a child was marked for its own reason. The groups that differ tell layout and paint what changed through the generated "affects" mask.

**Bulk fallback.** When the restyle set of one flush would exceed a share of the document set from measurement (initial load, large `innerHTML`, sheet swaps), the flush restyles from scratch in parallel instead, as B5 specifies. The fallback is a recorded cause; how often it fires is published (ST-23).

**Every restyle has a cause.** Each element in the restyle set carries a cause ID: the mutation-log entry, the index entry (selector and position) or the fallback reason. The cause costs one 32-bit word per restyled element in the pass's scratch arena and is discarded after the pass unless recording (Section 6.13). **Two metrics, two oracles.** *Over-invalidation* (elements restyled whose style did not change) needs only the old and new style identities and is counted in every pass, in production too, as a canonical counter; no engine publishes it ([PI 7][PI]). *Under-invalidation* (elements whose style changed but were not restyled) needs the from-scratch reference and is ST-4.

**Checked on every CI frame.** In CI and in DST, every flush of the mutation corpus is followed by a from-scratch restyle in the reference engine, and the computed styles are compared bit for bit (ST-4). An invalidation bug is a test failure with the mutation and the selector that missed it, not a silent wrong style.

### 6.9 Cascade and computed values (ST-D7, ST-D8, ST-D14)

**Cascade keys.** Each matched declaration block gets a cascade key encoding Cascade 6's seven criteria in order: origin and importance (eight levels with animations and transitions), shadow context, element-attached, layer rank, specificity, scope proximity, order of appearance ([SP 12.1–12.2][SP]). Layer ranks are fixed per scope when the sheet set changes (with the reversal for `!important`); scope proximity is computed per match. The key is a fixed-width integer tuple compared lexicographically.

**Match keys (ST-D8).** The ordered list of an element's matched (declaration block, cascade key) pairs is interned per agent as a **match key**. It is derived from what the cascade needs: the full sorted declaration list, because `revert`, `revert-layer` and `revert-rule` roll back to lower entries ([SP 12.5][SP]), and cheap equality, for sharing. Interning makes identical lists one object. Gecko's published documentation describes a rule tree holding the same information as a trie ([HP 6.1][HP]); ST-D8 keeps the rule tree as the measured alternative.

**Computing values.** For an element, the cascade walks its match key from the highest priority down, filling a per-element "decided" bitset over the ~760 longhands, and stops when every property is decided or the list ends; undecided properties inherit or take their initial value. Then each **style group** is computed:
- **Groups.** Longhands are partitioned into groups (inherited and reset, split by measured usage frequency and change rate, generated from the overlay), following B6's rejection of per-property columns; the boundaries come from Izcal's own corpus measurement at ST-M0, chosen to minimize bytes per element (ST-30) at the memo's hit rate (ST-31).
- **Inherited groups with no declaration share the parent's group** (zero work); reset groups with no declaration are the image's initial group.
- A group with declarations is computed by the generated conversions, then **interned by content**.
- A computed style is the vector of its group IDs plus a few per-element fields; it is interned too, and the element's style column holds its 32-bit ID.

**The computed-style memo.** A memo keyed by (match key, parent computed style's content identity, digest of element-dependent inputs: inline style block, presentational-hint block, `attr()` reads, container-query results, `sibling-index()` reads) returns the computed style directly. A hit is exact by construction, so it is sharing without guessing: two elements share a style only when every input of the function is equal. Hit rates are published (ST-31), the number no engine publishes ([PI 4.6][PI]).

**Deterministic identities (ST-D7).** Two kinds of identity, so that nothing the parallel phase decides waits for the merge:
- **Provisional identity, during the pass.** Every group, computed style and match key a worker creates gets a 128-bit **content hash** (with the agent's keyed hash, below) and lives in the worker's task-local buffer. Inheritance passes the parent's group by reference to its provisional object; the memo is keyed by content hashes; early cutoff compares content hashes and then contents. Every decision taken during the pass therefore depends only on contents, never on which worker made an object or in what order.
- **Final identity, after the pass.** Workers write their results (slot, provisional style) to **task-local output buffers**, not to the style columns. A **merge step in document order** then interns the new contents into the agent's tables, assigns 32-bit IDs and scatters them into the style columns. Because every decision was content-based, the merge's mapping cannot change any decision; it only publishes. IDs, table layout and the canonical bytes counted by the footprint ledger are therefore the same for sequential and parallel runs and every thread count (ST-5, FP-24); the 2.3× inflation of style contexts that Stylo's thread-local cache produced on one page cannot occur ([bug 1385982](https://bugzilla.mozilla.org/show_bug.cgi?id=1385982)).
- **Whose tables.** The intern tables are **per agent** (per event loop), not per partition. JS 6.12 allows several agents of one (site, container) on different script threads; per-agent tables give each table a single writer, the merge of that agent's flush, so no two flushes ever write one table, and reclamation takes roots only from that agent's documents. What is shared across agents of a partition is immutable, published data: parsed sheet contents (Section 6.6a) and the image's UA groups. ST-5 and ST-33 include a two-agent, two-thread case.
- The merge is a sequential pass over restyled elements; its cost is measured (Q-ST-8). ST-D7 keeps a merge-free alternative: 64- or 128-bit content hashes as the final identities, with collision checks, costed in ST-30 bytes.

**Hashing.** Interning hashes attacker-controlled content, so tables use the coding standard's keyed hash with one key per process from B1 entropy (CS-AS-2), as the JS engine does (JS 6.9), and every hash match is confirmed by a full content comparison, so a collision costs time, never correctness. Image-resident UA tables and ancestor-filter keys use fixed perfect hashes over fixed keys. Canonical bytes count unique entries, which do not depend on the key or on bucket order.

**The substitution interpreter.** Computed values run Values 5's arbitrary substitution functions: `var()`, typed `attr()`, `if()`, `inherit()`, `first-valid()`, custom functions (`@function`), and the tree-position functions ([SP 14.2–14.5][SP]). It is one component with its own anchors and fuzz target:
- **Cycles** are found with the spec's guarded substitution contexts; every participant becomes guaranteed-invalid.
- **The mandatory length limit** is a named constant: substitution output above **65,536† tokens** per declaration becomes the guaranteed-invalid value, with tests at the limit minus one, at the limit and above it ([SP 8.4][SP], [SR 4.7][SR]). Custom-function call depth is bounded by the same budget.
- **`attr()` taint is a type**: substituted token streams carry a taint bit, and the generated URL-accepting parsers reject tainted input, so the spec's rule cannot be bypassed by a property whose parser forgets to check ([SR 3.4][SR]). The implicit-flow gap the security note found (a condition on a tainted value choosing a literal URL, [SR 3.5][SR]) is raised with the CSSWG, not patched unilaterally (Q-ST-10).
- **`calc()`** follows Values 4's typed arithmetic and simplification, supports at least the required 32 terms and 32 nesting levels with a recorded upper limit ([SR 4.9][SR]), and uses the one implementation of `sin`, `pow`, `exp`, `log`, `hypot` and `sqrt` that the JS engine uses on every ISA (JS 6.9), shared through `hg-math`, which the JS spec owns in the shared sub-layer L2s ([P4][RN]), with no fused multiply-add contraction. Color conversions (`color-mix()`, relative colors, Oklab) use the same crate.

**Custom properties by reference (ST-D14).** An element's inherited custom properties are stored as its own changes over its parent's set, with the unchanged case a reference to the parent's set. The first-principles reason: about 60% of custom properties are set on the root and two-thirds act as global constants ([PI 5.5][PI]), so most elements change nothing and should store nothing. A lookup walks the chain of change sets, so the chain length is bounded; past the bound the set is flattened, and the bound is chosen at ST-M0 from the measured distribution of chain depths and lookup counts on the design-system corpus. The cascade records, per element, the custom property names its declarations read. When an inherited custom property changes on an element, only descendants that **read** the name (directly, or through a registered property that depends on it) are recomputed; the others take the new set by reference with no group recomputed. A change therefore costs in proportion to its readers, not its subtree, which is where the measured 1,000× gap between inheriting and non-inheriting changes comes from ([PI 5.3][PI]). Registered properties (`@property`) compute as typed values; `inherits: false` ones are an invalidation boundary.

**Font-relative units.** `em`, `rem`, `ex`, `ch`, `ic`, `cap`, `lh` and `rlh` compute to absolute lengths, so style needs font metrics. The fonts and text spec's metrics query takes (font list, size, style, language) and returns, per metric, the **exact ratio** for the first available font (the value in font units of the instance over `unitsPerEm`, with `size-adjust` and the metric overrides applied as exact factors); style multiplies it by the computed font size in its own computed-length type. Quantization to the text stack's integer quantum therefore stays a used-value rule and never enters computed values ([TX 6.8][TX], [P17][RN]). The computed-length type is an IEEE binary type fixed at ST-M0, with no fused multiply-add contraction, and every conversion into the text stack's integer contract uses its round-half-to-even rule (TX-D4). Results are a deterministic function of the installed Izcal font set and the recorded web-font installs; a web-font install that changes metrics is a mutation-log entry for the elements that used them. The `@font-face`, `@font-feature-values` and `@font-palette-values` rules parsed here, and the descriptor strings of the `FontFace` constructor and canvas `font` strings, are parsed only by `hg-css-props`' generated parsers (in `hg-cssom` and the bindings, L3) and reach the font loader as **typed descriptors**, because the text stack's L2t crates cannot depend on L2p and G22 and G23 forbid a second parser of a CSS grammar ([P8][RN]).

### 6.10 Style, layout and the event loop

**Flush points.** Style runs in the HTML event loop's "update the rendering" steps and at every forced flush (`getComputedStyle`, layout getters), with the script thread blocked (B4, JS-D4). The style pass runs no script by construction: matching, cascade and computed values call nothing that can enter the JS engine, which `hg-style`'s dependency rules enforce (Section 6.15). Events that style changes cause (transition and animation events, `ResizeObserver`) are queued, never dispatched inside the pass ([SR 6.7–6.8][SR]).

**Demand-driven style for script queries.** `getComputedStyle` on a property that needs no layout restyles only the element and the dirty part of its ancestor chain; the matched rules of an element depend on the whole tree, which is fixed during the flush, so the answer is the one a full flush would give. Two cases force layout first: properties whose resolved value is a used value (colors, `line-height`, sizes, margins, paddings, insets, [SP 16.4][SP]), and **any element inside a size container** whose size is dirty when the element's matched rules include `@container` conditions or its values use container-relative units. The demand path checks the container chain before answering. Both paths are compared in CI (ST-4), which is how this spec meets FLUSH-1's bit-identical requirement.

**Container queries re-enter from layout.** The style pass stops at each size container whose subtree has rules or units that depend on it, and marks the subtree pending. Layout lays out the container (its size cannot depend on its contents, because of containment), then calls `style_container_subtree(container, size)`, which evaluates the queries, restyles the subtree and returns what changed; layout continues inside ([SP 15.2–15.6][SP]). Re-entry runs on the layout phase's workers under the same rules as a style pass: read-only inputs, task-local outputs and its **own deterministic merge** before layout reads the subtree's styles, so the identities it creates are the same whatever the thread count. Style queries need no layout and are evaluated in the normal pass against the container's computed values. Scroll-state queries read the snapshot taken at the spec's "run snapshot post-layout state steps", which is a B1-recorded input ([SP 15.5][SP]). Each container is re-entered at most once per layout pass, so the loop is bounded. The API belongs to both specs and the layout spec owns the scheduling; until that spec's layout exists, ST-M2 tests re-entry against a reference block layout with size containment, built by the layout track (Section 9.2, Section 10).

**The environment snapshot.** Media queries, `matchMedia()`, `env()`, the default font size, preferences (`prefers-*`, `forced-colors`) and viewport sizes come from **one environment snapshot per document per frame**, built by the renderer from B1 inputs with D-S1's anti-fingerprinting quantization applied in that one place, so CSS and script can never disagree or reveal more than the snapshot ([SR 7][SR]). A change to the snapshot is a mutation-log entry with old and new values, so media-dependent rules are invalidated like any other feature.

**Animations and transitions as cascade inputs.** The animation engine (a later spec) supplies, per element at each flush, the animation-origin and transition-origin declaration blocks at the document timeline's current time. Style supplies the before-change and after-change styles CSS Transitions defines, the `@starting-style` rules, and the per-property interpolation types generated from the property descriptions. An animated element whose animated properties do not affect matching is restyled by recomputing only the affected groups, because the other groups' inputs are unchanged. Two inputs are left for the animation spec to define, with their B1 status: **scroll-driven timelines**, which read scroll positions from the post-layout snapshot, and **compositor-run animations**, whose intermediate values style must never see as main-thread inputs.

### 6.11 Data structures beside the one-copy DOM

**What style reads from `hg-dom` (JS-D4).** Tag (static index or atom), element-state bits, the attribute-set reference, the inline-style reference, the links, and rare data (shadow root, slot assignment, custom element state, `:state()` names). **Everything style reads lives outside the cage**: atom text, attribute-set contents (names and values) and inline-style source are stored in `hg-dom` or `hg-types` storage that workers read during a flush, and JS strings made from them are external strings, as for DOM text (JS-D4). Style crates cannot name `hg-heap` types (G1). **Attribute sets** are immutable and hash-consed per partition (FP §6.4); each carries, computed once at interning, its class atom list, its id atom, the ancestor-filter hashes of its features and its presentational-hint declaration block, so the work is done once per distinct set, not per element. Inline style is a declaration block shared by identical source text and copy-on-write on CSSOM mutation; it is primary data (below).

**The 48 B column budget.** JS-D4's columns are five 32-bit links (20 B), generation, tag, attribute-set reference, inline-style reference and rare-data index (20 B), leaving 8 B for node flags and element state. This spec asks for **32 bits of element state in the column** for the pseudo-classes the corpus uses most (to be confirmed by measurement at ST-M0), with the rest (media, form validity, fullscreen and top layer, `:state()`) in rare data, so node flags keep their 32 bits and FP-11's 48 B† holds; a CS-PF-1 size assert checks it.

**What style writes: its own columns.** JS-D4 forbids workers to write `hg-dom`'s columns. Style output therefore lives in **style columns owned by `hg-style`**, indexed by the same node slot: a 32-bit computed-style ID and a 32-bit word of style flags (dirty bits, last-match dynamic flags, pending container subtree, has pseudo-element styles). Pseudo-element styles and other rare style data live in a side table keyed by slot. Workers never write the columns: they write task-local output buffers that the merge scatters into the columns (Section 6.9); the script thread reads the columns for `getComputedStyle` outside a pass. **Slot reuse**: when `hg-dom` releases a slot (JS 6.5's release-by-ID list), it notifies `hg-style`, which clears the slot's style columns, flags and side-table entries before the slot can be reused; style entries also carry the slot's generation, so a stale entry is detected, never read (a planted-bug case in ST-11).

**Primary data and derived data are stored apart.** A class (a) store must be rebuildable from primary data (FP §6.4, FP-12), so the split is:

| Data | Class | Owner | Why |
|---|---|---|---|
| Parsed contents of network sheets, unmodified | (a), shared per partition | `hg-css-syntax` cache | Re-parsed from a copy of the decoded bytes kept with the entry; a rebuild never refetches, because a refetch is a new network input and would break FP-12 ([P19][RN]) |
| Sheets after CSSOM mutation; constructed sheets (`replace`, `replaceSync`, `insertRule`) | **Primary** | `hg-cssom` | Their only copy |
| Inline-style declaration blocks referenced from JS-D4's inline-style column | **Primary** | `hg-dom` | Referenced from primary columns; CSSOM may have edited them |
| **Before-change styles** of elements with a non-`none` `transition-property` or live animations, and a "had a computed style" bit per element | **Primary** (small) | `hg-style` transition state | CSS Transitions compares before-change and after-change styles, and `@starting-style` applies only to elements with no previous style; both must survive a discard |
| Interned groups, computed styles, match keys, custom-property sets, memo, rule and invalidation indexes, style columns | (a) | `hg-style` per-agent arenas | Rebuilt by a from-scratch restyle, which restores the same contents; transitions see the retained before-change styles, so discard is invisible (ST-33) |

The memory manager may drop the class (a) arenas (after the safepoint handshake on a running page); the next flush restyles from scratch with bit-identical results (FP-12). Unreferenced interned objects are reclaimed by a mark phase whose roots are the agent's style columns, rule and invalidation indexes, memo and retained transition state; it runs at the end of a flush when the arena's **canonical** garbage bytes exceed a threshold, so the trigger is deterministic. No reference counting runs on the parallel hot path.

**Bytes per element.** ST-30's components, all counted: the 8 B of style columns; pseudo-element styles and other rare style entries; the custom-property **reader sets** of ST-D14; retained transition state; and the amortized share of the agent's unique groups, computed styles, match keys and custom-property sets. ST-30 bounds the sum at **≤ 80 B† per element averaged over the corpus**; rule and invalidation indexes and sheets are counted per sheet in ST-32. The only published per-element figure is Stylo's 32 B of element data plus shared structs ([bug 1397380](https://bugzilla.mozilla.org/show_bug.cgi?id=1397380)); the threshold is first-principles and is confirmed at ST-M0. **Proposed split of FP-11's 512 B†**: DOM (columns, rare data, wrappers) 72 B† as FP-11 already sets, style 80 B† (ST-30), and **360 B†** for layout and paint, which the layout spec inherits as its budget (Section 9.5). Shaped glyph runs that layout keeps grow with text, not with nodes: they are charged to the footprint ledger's text-shaping category and the fonts and text spec's TX-50 line, never to the 360 B† ([P9][RN]).

**Per-process and per-agent fixed cost (FP-2).** The footprint spec gives document, DOM and style state for `about:blank` 0.25 MiB of the 4 MiB empty-process budget and repeats it per agent. Style's share is bounded by design: the UA rules, indexes and initial groups are in the read-only image (0 private dirty bytes); the agent's intern tables, memo, arenas and per-worker scratch are created **lazily** at the first style use beyond the UA initial style, with zero initial capacity; the environment snapshot is a few hundred bytes. ST-M0 measures the line items, and ST-34 bounds style's share at **≤ 64 KiB†** per empty agent.

**Sharing scope.** Interned style data is per agent; parsed sheet contents and attribute sets are shared only within one partition (the (T, C, X, n) projection, [P18][RN]), matching FP §6.4's rule; per-agent tables can hold data of two partitions only when both documents are in one agent, which already lets them script each other, so no channel arises; nothing derived from content crosses partitions or processes. The UA-derived groups in the engine image are shared by every process because Izcal built them (FP-3).

### 6.12 Parallelism and determinism (ST-D13)

**Designed in, used where it pays.** The traversal is written once as a top-down fork/join over the substrate's phase pool (B3, G3): each task receives shared, read-only inputs and owns a task-local scratch arena and output buffer. The types make phase purity a compile-time property: workers hold `&` references to the node columns, attribute sets, sheets, rule indexes and the previous style columns, and `&mut` only to their own task-local buffers; the only writer of the style columns and the intern tables is the sequential merge. The traversal starts sequentially and goes parallel only when the dirty set at a level is wide enough, with the threshold and work-unit size set from measurement (HGBA-2 4.3's adaptive rule). Published gains elsewhere are small and page-dependent (Section 2.2), so parallelism is never assumed: ST-26 states the sequential baseline first and the parallel gain separately.

**What makes parallel equal sequential, including memory.** Worker scratch arenas (no shared allocator lock; an allocator lock bound one Stylo stress test, [bug 1431285](https://bugzilla.mozilla.org/show_bug.cgi?id=1431285)); per-task ancestor filters and per-worker `:has()` memos whose contents are pure functions of the tree; content-based provisional identities; and the deterministic merge of Section 6.9. ST-5 checks bit-identical computed styles and canonical bytes across thread counts.

**What the flush records.** Style is a pure function of the DOM state, sheets, environment snapshot, font metrics, container sizes and animation inputs, all of which are B1 inputs or derived from them. Nothing in a style pass is a decision point: no style result depends on when background work finished. The parser's yields, speculative requests (Section 6.4) and sheet installs (Section 6.6a) are decision points (JS-D15), logged when recording.

### 6.13 Observability: what the parser and style system show

| Output | Contents | Cost when not used |
|---|---|---|
| **Cascade trace** (per element, per property, on demand) | Every candidate declaration from the match key, in cascade order, with the criterion that eliminated each (origin and importance, context, element-attached, layer, specificity, scope proximity, order), the `var()`/`attr()`/`if()` substitution chain, inheritance from which ancestor, and the computed-value step, each with its spec anchor and the property's spec URL | None: produced by running the production cascade for one element with a tracing sink (a generic parameter) |
| **Restyle causes** | For each restyled element: the mutation-log entry, the invalidation index entry (selector and position) or fallback reason, and the groups that changed; plus "restyled, nothing changed" counts | One word per restyled element in scratch, discarded unless recording |
| **Parse-decision log** | Parse errors with codes and source ranges, insertion mode, and the action taken, keyed to node IDs | None unless recording |
| **Selector statistics** | Per selector: attempts, matches, filter rejections, full-program failures, `:has()` evaluations and their work, time in canonical units | Compiled out of production; produced on a replay |
| **Static selector queries** | "Can this rule match anything in this document and its recorded mutations?", "which elements could this rule affect?", "do these two selectors overlap?", as bounded queries that may answer "unknown" (selector intersection is NP-complete, [GO 7.4][GO]) | Run on demand in DevTools |
| **Counters** | Over-invalidation, fallback frequency, memo hit rate, ancestor-filter rejection and false-positive rates, merge cost, parse throughput | Always on as canonical counters, inside FP-23's attribution budget |

**The explainer is the cascade.** DevTools renders the cascade trace; it never re-derives the cascade. A test checks, on every element of the WPT CSS directories and a corpus sample, that the trace's winner equals the computed value (ST-50). This answers the DevTools spec's Q-DT-4: the contingent cascade explainer and the Stylo spike it budgeted are no longer needed (Section 9.5).

**Why-queries under replay (DT-D3).** "Why does this element look like this?" chains: pixel → box → computed value → cascade trace → winning declaration → the sheet and the network response that delivered it; "why did this restyle?" chains: restyle cause → mutation → JS stack that made it. Both run on a B1 replay, so the live page pays nothing.

**For agents.** The agent principal (B9, with AI off by default, B10) receives answers, not dumps: the properties that differ from initial or inherited values on the nodes asked about, with their winning declarations, or a style diff between two execution points of a recording ([GO 9.2][GO]).

**What may be exposed, and to whom.** These outputs carry data the page itself cannot read: declarations from **non-origin-clean sheets** (CSSOM throws `SecurityError` for them, [SR 3.12][SR]), the visited state of links, and the source of cross-origin sheets. Each output is an IIP type in `hg-inspect-schema` (DevTools G10), and every field that holds such data is `Redacted<T>` (DevTools G11) and is served only to a session holding the read capability on the sheet's origin (or, for visited state, on the top-level site). Agents never receive non-origin-clean declarations or visited state by default; the user grants them per session. In recordings and exports, visited state appears only as the per-partition salted membership answers, never as URLs (Section 6.14). ST-13 includes these cases.

### 6.14 Security, privacy and robustness

**Bug classes and the mechanism that closes each.**

| Class | Evidence | Mechanism |
|---|---|---|
| Memory corruption in parser or style code | 51 of 69 Gecko style-system security bugs would not have been possible in Rust ([Mozilla Hacks](https://hacks.mozilla.org/2019/02/rewriting-a-browser-component-in-rust/)) | `#![forbid(unsafe_code)]` in every crate of Section 6.15 except inventoried modules; SIMD through `memchr` |
| Stale iteration over a container that script mutates (CVE-2026-2441's class) | [fix e045399a1e](https://github.com/chromium/chromium/commit/e045399a1e): "Avoid stale iteration in CSSFontFeatureValuesMap" | `TokenCell` state and `ScriptToken` call-outs (CS-TY-10); CSSOM iterators hold indices with generations, re-checked after every callback (Section 6.3) |
| Parser differentials (mXSS, sanitizer bypasses) | [SR 2][SR]; [Searchlight Cyber](https://www.slcyber.io/research/two-bypasses-for-chromes-sanitizer-api) | One parser core and sinks (ST-D1, G23); sanitizing in the tree builder; one parser per micro-grammar (G22); the round-trip suite (ST-8) |
| Exfiltration through CSS | [SR 3.1–3.6][SR] | Spec mechanisms implemented as types: `attr()` taint, CSP nonce hidden from selectors, origin-clean per document (Section 6.6); CSP checked for every style-initiated and speculative fetch, by the renderer for document-derived policy and re-checked by the network service (the networking spec's split) |
| History sniffing | [SR 3.8–3.11][SR] | ST-D15 (below) |
| Resource exhaustion | [SR 4][SR] | Named limits (below); iterative tree walks; work budgets for `:has()` and invalidation |
| Allocation failure and stack overflow | A Stylo launch-time crash signature was a failed 16-byte allocation ([bug 1404633](https://bugzilla.mozilla.org/show_bug.cgi?id=1404633)) | Fallible allocation with defined outcomes in the parsers, the substitution interpreter and the rule index; no recursion on content depth on any native stack |
| Logic regressions in privacy behaviour | Stylo's `:visited` regression, tests disabled for CI speed ([SR 1.7][SR]) | The privacy and history suites are ship blockers that cannot be skipped (ST-13, SEC-24) |

**Named limits.** Each limit is a constant with an anchor, a spec-conformant overflow behaviour and tests at the limit minus one, the limit and above it:

| Limit | Value | Overflow behaviour | Basis |
|---|---|---|---|
| HTML parser nesting depth | 512 | Insert as child of the 512th open element | WebKit's layout-test expectation ([SR 4.2][SR]); black-box on all engines at ST-M0; whatwg/html #3732 |
| XML nesting depth | 5,000 (confirmed black-box at ST-M0) | XML well-formedness error | [SR 4.4][SR] |
| XML internal-subset entity expansion (ST-D20) | 1,048,576† characters per document, 64† nesting levels | XML well-formedness error | The billion-laughs case; first principles |
| `document.write` nesting | Measured black-box at ST-M0 | Ignore the nested write | whatwg/html #1954 (Q-ST-4) |
| Substitution output per declaration | 65,536† tokens | Guaranteed-invalid value | Values 5 Appendix A requires a UA-defined limit ([SR 4.7][SR]) |
| `calc()` terms and nesting | ≥ 32 each (spec floor); upper bound 256† | Treated as invalid | [Values 4 #calc-range](https://drafts.csswg.org/css-values-4/#calc-range) |
| Custom-function call depth | 64† | Guaranteed-invalid value | Mixins 1 cycle rules ([SR 4.13][SR]) |
| `@import` depth | 16† | The import fails | First principles |
| `@import` sheets per document | 1,024† sheet instances in total, with one fetch per URL | Further imports fail | Fan-out: two imports per level at depth 16 would otherwise create 2¹⁶ sheets |
| Selector nesting (`:is()`, `:not()`, `:where()`, `:nth-child(of S)`) and selector-list length | 32† levels; 4,096† selectors per list | Selector invalid | First principles; compiled programs stay bounded |
| `@layer`, `@container`, `@scope`, `@media`, `@supports` nesting | 256†, shared with rule nesting | Rule dropped as invalid | First principles |
| Invalidation-index entries per scope | 1,048,576† | Sheets beyond the bound restyle their scope by subtree, recorded as a cause | `:has()` arguments times features can grow the index |
| Attributes per element; declarations per block | No limit; every algorithm linear in their count, tested at 10⁵ | — | The HTML parser sets no attribute limit ([SP 8.1][SP]) |
| CSS nesting depth of rules | 256† | Rule dropped as invalid | First principles; the parser is iterative |
| `:has()` and invalidation work per pass | Measured budget | Fall back to the downward search or to subtree restyle, recorded as a cause | Section 6.7.2, 6.8 |

The style and parser algorithms never recurse on DOM, rule or value depth on a native stack: tree walks use explicit stacks, so a script-built tree of any depth is handled (a parser cap does not stop such trees, [SR 4.3][SR]).

**`:visited` (ST-D15).** The renderer's visited state is **partitioned by (link URL, top-level site, frame origin, container)**. Chrome 136 ships the first three ([Chrome](https://developer.chrome.com/blog/visited-links)) and Selectors 4 Appendix C describes them ([Selectors 4](https://drafts.csswg.org/selectors-4/#visited-privacy)); Izcal adds the **container**, because Izcal's partition is (top-level site, container) and a link visited in one container must not render as visited in another. The broker records a visit under the full key at navigation time and sends a process only the entries of its own partitions, as membership answers salted with a per-(partition, profile) salt that never leaves the broker, so the renderer never holds history the site could not have observed. Visited-set updates after a navigation are B1 inputs applied at a task boundary; recordings contain only the salted answers, never URLs or salts (SEC-21). Defence in depth stays: the 2010 property restrictions, `getComputedStyle` and `querySelector` answering as if unvisited, and **constant work**: every link's visited-dependent properties are computed in both states whatever its visited bit, so restyle time does not depend on history. The restrictions are dropped only on a positive analysis, not on elapsed time (ST-D15). `:visited` never matches inside `:has()`. In a nonce partition (a credentialless iframe or a fenced frame) the broker sends no visited answers, so `:visited` never matches there ([P18][RN]).

**Cross-partition channels.** The parsed-sheet cache, the rule-index cache, the style arenas and the attribute-set tables are keyed by partition (FP §6.4, with the (T, C, X, n) projection of [P18][RN]); FP-36's probing suite gains them (ST-13).

**Fuzzing (Tier 1 surfaces).** Byte-level fuzzers for the encoding decoders, the HTML tokenizer (against the reference stepper), the tree builder (against WPT-format expectations and the round-trip property), the XML parser, the CSS tokenizer and parser, every generated property parser, the selector parser and the substitution interpreter (with the length limit as an oracle). A grammar fuzzer generates DOM, CSS and mutation interleavings whose oracle is "incremental equals from-scratch" (Domato's results show DOM and style bugs come from such interleavings, [Project Zero](https://projectzero.google/2017/09/the-great-dom-fuzz-off-of-2017.html)). Every historical CVE class in [SR 9.11][SR] is a permanent regression case.

### 6.15 Crate layout and the crate graph

Stage 1 reserves L1 for the substrate and L2 for contracts, so this spec adds two layers, as the JS spec added L2e ([P1][RN]). **L2s, shared standards**, is a sub-layer of L2, so the JS spec's G13 holds unchanged. It holds the crates that more than one of the engine, the parsers, the text stack, the network services and the broker link: `hg-encoding` and `hg-url` (this spec), `hg-math` (JS spec), `hg-ucd` and `hg-unicode` (fonts and text spec), and `hg-compress`, `hg-net-wire`, `hg-cookie-parse` and `hg-psl` (networking spec). They are written to tier P's rules (never panic, CS-ER-3's lint set), because network services and the broker link several of them. **L2p, parsers and style computation**, sits beside L2e and the text stack's L2t, between L2 and L3 document: L2p crates depend only on L2 (L2s included) and on each other, and never on L2e, L2t or L3 (G24).

### 6.16 User experience and integrations

**For people browsing.** Style and parsing are invisible, except that pages show content progressively, `:visited` keeps working for links the site itself shows, and the shell's **user style sheets** (ST-D17) let a person set styles per site, held in memory and shown in DevTools as the user origin. The shell's own themes (D-S2's CSS-only theming) use the same mechanism.

**User style sheets and fingerprinting.** A user sheet changes computed styles that `getComputedStyle`, layout geometry and `matchMedia` expose, so a distinctive **global** sheet would be a cross-site identifier (PRIV-2, D-S1). The design therefore makes **per-site sheets the default**; a global sheet is possible only after the shell explains, in plain language, that every site can observe it; and accessibility-motivated global overrides (forced colors, reduced motion, minimum font size) go through the environment snapshot's quantized preferences, which D-S1 already normalizes, rather than through arbitrary CSS. User sheets are compiled once by the shell renderer (IPC-R15 forbids parsing in the broker) into a read-only file that a site process maps only when a sheet applies to it, so a process without one pays nothing. The compiled file joins FP-D16's regenerable-cache class as a member; the sheet's source, the only copy, lives in the storage service ([P19][RN]). PRIV-2 gains a case with a global sheet.

**Cosmetic filters.** Content blocking's cosmetic rules are compiled by the networking spec's content-blocking utility job into per-site CSS subsets ([NW 6.15][NW]) and arrive as a user-origin sheet of at most 256 KiB† per site process (FP 6.11), parsed by `hg-css-syntax`, shared per partition and shown in DevTools as the user origin. They change computed styles, so a container's list set is engine configuration, recorded, and covered by PRIV-2's global-sheet case ([P21][RN]).

**For developers.** The Styles pane renders the cascade trace with the eliminating criterion on each crossed-out declaration and its spec link; the Elements pane shows, on a node, the parser decisions that placed it and the restyles it went through, each with its cause; the Performance view shows restyles with causes and the "restyled for nothing" count; the selector view shows statistics from a replay and the static queries ("never matches in this document").

**Integrations.** Networking: speculative fetch requests, encoding labels, early hints, CSP and ORB enforcement on style-initiated fetches, MIME types parsed by `hg-net-wire`, and `hg-url` and `hg-encoding`, which this spec owns for the whole browser. Fonts and text: the metrics query (exact ratios, [P17][RN]), typed `@font-face` and `FontFace` descriptors parsed here ([P8][RN]), and font-load events as mutations. Layout: the computed-style read API, the "affects" mask, container re-entry. Semantic plane (B8): computed values it needs (display, visibility, `content`, `speak`). WebDriver: `getComputedStyle`-based commands unchanged; the IIP Style domain carries the cascade trace.

| Area | Chosen | Alternatives | Cost of the choice | Reversal trigger |
|---|---|---|---|---|

| Fragment speed | One parser with a direct sink | Subset fast-path parser with bail-out | Engineering of the one parser's inner loops | ST-21 missed by >25%† with no fix in the one parser |
| Tokenizer (ST-D3) | Generated from `.hgtok` | Hand-written | A generator before the first tokenizer | Generated tokenizer >10%† slower than a hand-tuned one on the corpus at ST-M1 |
| Property code (ST-D6) | webref + overlay, build fails on disagreement | Overlay only; webref directly with no overlay | Classifying 168 computed-value texts; tracking webref releases | webref's data is withdrawn or its license changes (Q-ST-1) |
| Selector execution (ST-D9) | Interpreted programs | JIT in JIT-ceiling renderers | Matching speed of an interpreter | Matching >25%† of style time on the rule-heavy corpus after the filter and memo work |
| Matched rules (ST-D8) | Interned match keys + memo | Rule tree | One intern table per partition | Rule tree saves >10%† style memory or time in a comparison build at ST-M2 |
| Style storage (ST-D7) | Content-addressed groups, provisional content identities, per-agent tables, deterministic merge | Per-element structs; pointer-shared structs with per-thread caches; wide content hashes as final identities (no merge) | The merge pass | Merge cost >10%† of style time at ST-M2, or wide hashes within ST-30 and faster |
| Invalidation (ST-D10) | Feature index + exact self check + last-match flags + causes + reference check | Conservative sets only; subtree restyle on every change | Index compile time and memory | Over-invalidation and restyle time no better than conservative sets on the corpus |
| Custom properties (ST-D14) | Shared by reference; readers recomputed | Per-element copies; chains without reader tracking | Reader sets per element | Reader tracking costs more memory than it saves time on the design-system corpus |
| `:visited` (ST-D15) | Partitioned with the container + restrictions + constant work | Partitioned only; restrictions only | Visited styles computed twice for links | A published analysis shows every observation possible without restrictions is one the site could make itself under the full key, and ST-13 is green: drop the restrictions; constant work stays unless ST-23 shows its cost |

### 6.18 Representation choices, derived (M-1 part 3)

Several structures above resemble what shipping engines use (a rule index keyed by the rightmost compound, an ancestor filter, invalidation data compiled from selectors, shared style groups). Resemblance alone is not a reason to adopt them; each is derived here from the problem, with the measurement that decides it, and named in Izcal's own terms. Every structure the design critique listed as having only a source-file precedent in the research notes is derived below; the report cites no engine source file ([critique 1][CR]). ST-M0's design review includes a provenance check by a reviewer who has not read the source files the notes once cited.

| Choice | Derivation from first principles | Alternative considered | Decided by |
|---|---|---|---|
| **Rule index** keyed by the rightmost compound's most selective feature | A rule can match only an element that has every feature of its subject compound; indexing by one required feature makes the candidate set per element proportional to the rules that could match, not to all rules | Per-element evaluation of all rules (Meyerovich's baseline, 4–25× slower, [PI 3.1][PI]) | Candidate counts per element on the corpus (ST-M0) |
| **Ancestor filter** | A descendant selector needs features on some ancestor; a fixed-size summary of the ancestor chain's features answers "certainly absent" cheaply, and the answer is a pure function of the tree | Walking ancestors per rule | Rejection and false-positive rates on the corpus (ST-22) |
| **Invalidation index** | Invalidation must find a superset of elements whose match results changed; a change of feature F can only affect selectors containing F, at the positions where F occurs, so indexing by feature and position bounds the search | Restyle subtree on every change | Over-invalidation and restyle time against the reference (ST-23) |
| **Match key** (interned matched-declaration list) | The cascade's output for an element depends only on its matched declarations in cascade order; interning that list makes equal inputs one object, which sharing, the memo and `revert*` all need | Rule tree (a trie of the same lists) | Comparison build at ST-M2 (Section 6.17) |
| **Style groups** (content-addressed) | Most properties of most elements are inherited unchanged or initial; grouping by change rate lets one integer carry a whole unchanged group, and content addressing makes sharing exact and deterministic | Per-element full structs; per-property columns (rejected by B6) | Bytes per element and memo hit rate (ST-30, ST-31) |
| **Generated property code** | ~760 properties with grammars, initial values and inheritance flags already exist as extracted spec data; generation makes each a function of that data and the overlay | Hand-written code per property | Build-time disagreement count (ST-7) |
| **Rule-index key kinds and their order** | The best key for a rule is the required feature that the fewest elements have; which kinds (id, class, attribute, tag, scoping pseudo-classes) are rarest is a property of the corpus, so the preference order is computed from Izcal's selector and element statistics, and pseudo-class buckets exist only where the statistics show they cut candidates | A fixed order chosen by hand | Candidates per element on the corpus (ST-M0) |
| **Ancestor filter per task, rebuilt from the task's root** | The filter must equal a function of the ancestor chain; a task starting at an element can only make it so by rebuilding from that element's ancestors, which costs O(depth) once per task | A shared filter (needs synchronization) or none | Rejection rate per byte and rebuild cost per task (Q-ST-6) |
| **`:has()` memo scope: one pass, one worker** | The tree is fixed only within a pass, so a memo can live no longer; a per-worker memo needs no synchronization, and duplicate work across workers is bounded by the number of workers | Cross-pass caches with invalidation; a shared memo | `:has()` work per pass on a `:has()`-heavy corpus (ST-D11) |
| **Lazy declaration parsing, published in the merge** | Unused declarations need no parse; the parse is a pure function of bytes, so publishing in the merge keeps contents immutable and identical across thread counts (Section 6.6) | Eager parsing | Share of declarations never used (Q-ST-7) |
| **Custom-property change sets with a bounded chain** | Most elements change no custom property, so storing changes avoids per-element copies; a bounded chain bounds lookup cost | Per-element copies; unbounded chains | Chain depth and lookup counts on the design-system corpus (ST-24) |
| **Token and time budgets for parser yields** | The token budget is the deterministic bound; the time budget bounds input latency from slow tokens; both are needed, and the time budget makes the yield a recorded decision (Section 6.4) | Token budget only (deterministic but can stall input); time only | Input latency during parsing and time to first paint on the corpus (ST-M1) |

The parts where Izcal departs from every shipping engine: one parser core for every entry point, including the speculative parser; recorded parser yields; property code generated from the specifications' own data with a failing cross-check; content-addressed style with deterministic identities; exact self checks from old values and flags that never accumulate; a cascade trace that is the production cascade; restyle causes and measured over-invalidation; and an independent reference style engine compared on every CI frame.

## 8. Targets

† marks thresholds set by this document from first principles; none is measured on Izcal yet. "Best shipping engine" is the best result among the stable releases of Chrome, Firefox and (on macOS) Safari on the same reference device, corpus and day, as in the JS spec. **Relative thresholds** are used only for speed (ST-21 to ST-23), following the JS spec's and footprint spec's policy, and each has **one threshold**, first measured at Stage 1 exit: the design does not change between stages, so a lower interim bar would be schedule staging. Memory thresholds are absolute and sit inside the footprint spec's budgets. - **Q-ST-2.** *Closed in 0.3:* `hg-encoding` belongs to this spec, in the shared sub-layer L2s, with `hg-url` beside it ([P2][RN], [P6][RN]).
- **Q-ST-3.** How do the shipping engines behave, black-box, at the HTML depth cap of 512 with table and template foster parenting, and at the XML depth cap? (ST-M0; the notes read the constants from source, which this spec does not rely on.)
- **Q-ST-4.** What nesting depth of `document.write` do the shipping engines accept? (whatwg/html #1954; black-box at ST-M0.)
- **Q-ST-5.** What are the bytes per element of style (ST-30) and the best group boundaries on Izcal's corpus? (ST-M0 spike.)
- **Q-ST-6.** What ancestor-filter size and hash count give the best rejection per byte on the corpus?
- **Q-ST-7.** What share of declarations is never matched on the corpus? (ST-D19.)
- **Q-ST-8.** What does the deterministic merge cost per flush? (ST-D7.)
- **Q-ST-9.** Does keeping speculative trees (ST-D2 (b)) pay on modern pages, where parser-blocking scripts are rarer?
- **Q-ST-10.** Does the CSSWG consider the implicit flow through `if()` on a tainted `attr()` value in scope for the taint rule? ([SR 3.5][SR]; Izcal files the issue.)
- **Q-ST-11.** Which scripting mode do `DOMParser` and `parseHTMLUnsafe` documents use after the 2026 refactors? ([SP 19][SP].)
- **Q-ST-12.** Is 65,536† tokens the right substitution limit? Valid custom properties reach kilobytes ([SR 4.7][SR]); measure the corpus maximum.
- **Q-ST-13.** What over-invalidation rate is achievable? No engine publishes one, so ST-23's 20%† has no external baseline.
- **Q-ST-14.** Is CSS Typed OM admitted under ST-D18 (it ships in Chrome and Safari, partly)?
- **Q-ST-15.** Do 32 bits of element state in JS-D4's columns cover the pseudo-classes that matter for matching speed on the corpus, with the rest in rare data? (ST-M0.)
- **Q-ST-16.** What does running the reference engine on every flush cost the DST farm? (ST-M1; ST-D12's trigger.)
- **Q-ST-17.** How much style data would agents of one partition on separate threads share if tables were per partition (ST-D7 (e))? (ST-M2.)

### 11.2 Claims that are single-source, unverified or conflicting

**Carried from the research notes.**
- **Single-source:** the 30% Amazon Stylo gain, the ~30% WebKit Bloom-filter estimate, the 2× selector JIT microbenchmark and the Nexus 7 threaded-parser figures ([HP 12, open questions][HP]); the 2.3× style-context inflation is one page in 2017; the ≈1.35× parallel gain is one test ([PI 6.3][PI]).
- **Second-hand or old:** the 19–20% preload-scanner gains ([PI 9.1][PI], Low); the "60% of mobile load latency is computation" figure ([PI 1.3][PI], Low); Microsoft's application rule counts are from slides ([PI 1.5][PI], Medium).
- **Researcher arithmetic:** MB/s figures for library parsers, the ≈1.35× parallel ratio and the 2.3× style inflation ([PI 13][PI]); the fact-check confirmed 5,164 / 2,236 = 2.31.
- **Inference:** why `innerHTML` excludes declarative shadow DOM ([SP 6.3][SP]); the implicit-flow gap in `attr()` taint ([SR 3.5][SR]); that Stylo's sharing depends on thread assignment in memory, not values ([GO 8.3][GO]).
- **Unverified:** the final removal date of mutation events in Chromium and their status in WebKit and Gecko ([SR 6.4][SR]); the jQuery mechanism behind unforgiving `:has()` ([SP 11.2][SP]); shipping versions taken from webstatus.dev without release-note cross-checks ([SP 19][SP]); Chrome's removal of user style sheets "around version 33" ([GO 9.3][GO]).
- **Conflict resolved:** the gaps note left open whether HTML now creates processing-instruction nodes; the specifications note confirms it from the standard's text and commit `320c05f6` (25 June 2026) ([SP 1.3][SP]).
- **Confirmed by the phase 8 fact-check** ([factcheck][FC]): CVE-2026-2441's root cause, by its fix commit `e045399a1e`; the 512 depth cap in all three engines (this spec still relies only on WebKit's test expectation and the planned black-box test); 84 tokenizer states, 21 insertion modes, 52 error codes; 6,827 and 1,973 test cases; webref's 822 and 758; every WPT rate used.
- **Corrected by the phase 8 fact-check:** Blink's background-parser history (two commits, two reasons); the Stylo "≈1.3× at 6 threads" figure, now stated as one allocator-bound stress test; the Nexus 7 is a quad-core tablet; 168, not 169, computed-value texts; the Chrome 146 bypasses were micro-grammar checks, not an HTML fast path; `@scope` universal by March 2026; +20 MB, not +10 MB, for Stylo going from 1 to 3 threads.
- **Provenance:** rows in the research notes that were read from engine source files (constants and comments) are marked in the notes and not used by this report ([critique 1][CR]).

**Introduced in this draft, first-principles and to be measured.** Every † threshold in Section 8; the 65,536† substitution limit and the other † limits of Section 6.14; ST-D2's 5%† trigger; the staffing, ramp and durations of Section 9.3; the claims that the deterministic merge is cheap (Q-ST-8), that exact sharing reaches ST-31, and that reader-tracked custom properties meet ST-24.

**Prefix check.** `ST-` (targets ST-1 to ST-54, including ST-15 added in 0.3, decisions ST-D1 to ST-D20, milestones ST-M0 to ST-M5, questions Q-ST-1 to Q-ST-17) does not collide with any prefix in `reports/` on this branch. The coding standard's `CS-ST-` IDs are a different prefix.
