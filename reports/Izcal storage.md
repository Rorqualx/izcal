## Summary

Web storage is where a browser keeps the user's data: eight accepted Izcal documents already hand this spec a client list — the DOM bindings (IndexedDB, Cache API, `localStorage`, quota), the network services (cookie jars), the broker (attribution history, the interaction record, the user style sheets' source), the shell (rows on screen only), and DevTools (views, never direct access) — and one stale idea in six places (SQLite in WAL mode) that M-1's 2.3.0 ruling and the MIT-only licence rule already forbid. The central idea of this spec: **storage is a deterministic, capability-addressed object service whose committed state is immutable at page granularity**. One sandboxed storage-service process owns everything persisted; its engine (Izcal's own, built from the specifications under M-1) publishes committed roots as snapshot handles, which is exactly what the DOM spec's `localStorage` protocol (DM-D11), the bucket file system's synchronous handles, and deterministic replay all need. The four decisions that matter most: **(1)** Izcal builds its own storage engine — a copy-on-write page forest with atomic commit slots plus an append-only value log for large values (SG-D2), never a third-party embedded store; **(2)** the engine implements the Storage standard's shed/shelf/bucket/bottle model natively, keyed by the storage key (T, C, X) + O that the networking spec already fixed, with quota per shelf and whole-bucket eviction that is a pure function of recorded inputs (SG-D4, SG-D5); **(3)** everything persisted is encrypted and authenticated at rest under per-container keys the broker unwraps from the OS key store (SEC-34's discipline), with the honest limit that this answers theft and other local users, not malware already running as the user (SG-D7); **(4)** every storage fact a person, developer or agent can see — exact usage, eviction reasons, transaction states, write provenance — is one recorded, typed fact base served through IIP, with the shell owning consent and prompts (SG-D12, SG-D6).

## 1. The problem and who has it

**People browsing** lose data without ever learning why: eviction is silent and whole-origin, there is no event, no API and no log ([G2.4–G2.5][GO]); their storage lives unencrypted next to everything else on a shared device; and clearing a site's data leaves remnants until an unspecified checkpoint ([SEC 5.2][SR]). **Web developers** build on the least observable subsystem in the platform: today's tooling is editable snapshot tables with no write provenance, no transaction view, no eviction explanation, and one number (`estimate()`) documented as padded and, in the field, inconsistent with the browser's own other view ([G1.1–G1.9][GO]). Every major IndexedDB pain class — blocked upgrades, "backing store" corruption, disappearing data, untyped quota errors — is a missing-fact class, not a missing-chart class ([G2.7][GO]). **Izcal the project** has eleven documents pointing at a process ("the storage service") that no specification defined: the ledger records this as gap G-19, blocking the Stage 1 process map and the security scope. **The engine team** needs the storage layer to be deterministic (B1) — random or time-derived values stored by pages, and every policy decision the storage layer makes, must replay exactly — and capability-clean (I-2): a renderer never holds another origin's bytes.

Success, measurably: recorded sessions replay storage exactly (SG-6); a crash-injection suite finds no committed transaction lost and no uncommitted state exposed (SG-1); no byte of one partition is ever mapped into a process keyed for another (SG-8); a person can answer "why did my data disappear" from a log, not a forum ([G4.1][GO]).

## 2. History: what came before and why it was built that way

(The research note carries the full chronology with sources; this section is the design-bearing skeleton. [H1–H11][HP].)

| Year | Project | What it did | Why that way | Fate and why |
|---|---|---|---|---|
| 1994 | Cookies | First client-side state for stateless HTTP (the shopping-cart problem) | Sessions had to survive server restarts; no other mechanism existed | Still here, re-specified four times (2109, 2965, 6265, bis); misused as storage for a decade because it was the only store ([H1][HP]) |
| 1995–2002 | IE `userData`; Flash LSOs | Per-page / per-domain blobs persisted by the browser or a plug-in | The platform provided nothing, so single vendors filled the vacuum | Forgotten or removed; Flash LSOs became the tracking store of the mid-2000s because they outlived cookie clearing ([H2][HP]) |
| 2007 | Google Gears | SQLite-backed database, resource cache, worker pool — as an extension | No browser would ship the features; an extension needed no standards process | Deprecated Feb 2010 when HTML5 absorbed the ideas; its Database, LocalServer and WorkerPool modules are the ancestors of WebSQL, AppCache and Workers ([H2][HP]) |
| 2006–2009 | Web Storage (`localStorage`/`sessionStorage`) | A synchronous per-origin string dictionary | Shaped to let a page swap cookie code in an afternoon; predated promises and workers by years | Universal; the synchronous execution model became structural jank by 2015 (10k writes: ≥ 527 ms Chrome — the source later corrected its LocalStorage figures as understating the cost) and is unfixable by compat — the call-site shape survived, the model did not ([H3][HP]) |
| 2009 | Web SQL Database | Real relational storage in pages, SQL strings, backed by SQLite | SQL was the only known language for "a database in a page"; SQLite was free and embedded | Abandoned after 19 months: the spec pinned "the SQL dialect supported by Sqlite 3.6.19", Mozilla refused, and the W3C's own note states the impasse — "we need multiple independent implementations". It was *faster* than IndexedDB when it died; it died of standards hygiene, not speed ([H4][HP]) |
| 2009–2018 | IndexedDB | Async, transactional object stores with indexes and cursors | Mozilla's design: no query language, no library pin, explicit transactions against "application and system failures" | W3C REC 2015; 2.0 in 2018; 3.0 still a Working Draft in 2025 — sixteen years from the 2009 proposal, promise-less in the standard, with early interop so rough that wrapper libraries became standard practice ([H5][HP]) |
| 2009 | AppCache | Declarative offline manifest | One pattern, zero code for the common case | A documented disaster ("nothing updates, ever"); the maintainers' postmortem: "we didn't have enough evidence, and created a high-level solution that couldn't be used the way developers wanted" ([H6][HP]) |
| 2014–2018 | Service Worker + Cache API | Programmable per-scope proxy with explicit, named, versioned caches | AppCache's lesson: give developers moving parts, not one declarative scheme | Universal; the Cache API's store is author-managed and strictly isolated from the HTTP cache ([H6][HP]; [SP 5.2][SW]) |
| 2011 | LevelDB era | Chromium-class browsers adopted log-structured (LSM) embedded stores for state like localStorage | Write-optimized ingest on flash; atomic batches; snapshots | The LSM economics carry documented costs: compaction rewrites, write stalls that pause a whole store, multi-level point reads ([H11][HP]; [ED §1][ED]) |
| 2020–2023 | OPFS / bucket file system | Private, origin-scoped, byte-addressable files with synchronous access handles from workers | User-visible file I/O is slow by design (checks, prompts, temp-file writes); OPFS drops them, and workers may pay sync costs the main thread may not | Interop across all three engines; SQLite-over-OPFS is the platform's own recommended WebSQL successor ([H8][HP]) |
| 2022–2024 | Storage Buckets | Per-origin named groupings that evict independently | Per-origin all-or-nothing persistence is the wrong granularity; sites want to sacrifice caches before data | Draft Community Group Report (19 Dec 2023), shipping in one engine — the WebSQL pattern's shadow ([H10][HP]; [SSB][SB]) |

**Technology mismatches** — assumptions baked into these designs that no longer hold:

- **A synchronous storage call is acceptable.** True in 2006 (single-threaded pages, no workers); false since. Izcal's DOM spec already broke it with the snapshot protocol (DM-D11); the service side must never re-admit a blocking call (G156).
- **Storage implementation is out of scope for the standard.** The 2008 stance ("it doesn't affect interoperability") produced fifteen years in which every policy a user experiences — when data disappears, how much there is, whether it is encrypted — is an accident of implementation. The current Storage standard has begun to fix this (shed/shelf/bucket/bottle, "must not be a function of the available storage space"); the latitude inventory ([SP §10][SPN]) is now the design surface.
- **The browser's own persistence may be a borrowed engine.** WebSQL died of exactly this; the MIT-only rule and M-1 2.3.0 forbid it for Izcal; and FP-D16's accepted fallback ("moves to a crash-consistent embedded store") needs that store to be Izcal's.
- **Per-origin keying is enough.** Evercookie (2010) and the partitioning literature made the top-level site part of the key; the Privacy CG calls single-keyed state "an acknowledged privacy and security bug" ([SEC 1.1][SR]). A new engine keys partitions from its first commit ([H9][HP]).
- **Quota can follow free disk space.** The Storage standard now forbids it outright: quota "must not be a function of the available storage space on the device" ([SP §6][SPN]).

## 3. Today: the landscape and its gaps

What shipping tools cannot show ([GO]):

- **No write provenance.** No documented view in any engine shows which script, call site, transaction or time last wrote a key. The Application panel's localStorage documentation has not been updated since 2019-03-14 ([G1.1, G1.4][GO]).
- **No transaction view.** Nothing shows live IndexedDB transactions, their participants, or which connection blocks an upgrade; the `blocked` case has had an open spec issue since the spec's early days because the app cannot even observe when the block clears ([G1.5][GO]; [G2.1][GO]).
- **No eviction explanation.** Eviction is silent by design and deletes whole origins; the top-voted developer question is literally "how can I or my app know that the browser is discarding items" — the answer is: you cannot ([G1.6][GO]; [G2.4–G2.5][GO]).
- **Numbers that disagree with themselves.** `estimate()` is padded for fingerprinting, omits or includes `usageDetails` by engine, and in the field disagrees with the browser's own DevTools (one browser: API reports 2 GiB, DevTools shows ~149 GB) ([G1.7][GO]).
- **A measured-record gap.** No published, dated answer to "how much storage do sites actually use" was verifiable — the Web Almanac has no Storage chapter in any checked edition ([G6.3][GO]). Izcal's opt-in telemetry could publish the first credible distribution (Section 6.9).

The incumbent quota *rules* are documented ([G6.1][GO]) but the *policies* — eviction order, pressure definition, idle deletion, persistence grants — are either heuristics or prompts, decided silently ([G5.1–G5.4][GO]; [SEC 3.2][SR]). That muddle is the gap a first-principles engine closes.

## 4. First principles

**Users' real tasks.** A person wants their data to still be there tomorrow, to know when and why it would not be, and to be able to delete a site's data completely. A developer wants to answer "who wrote this key, which transaction is stuck, why was my data dropped, how full am I" without shipping logging code. An agent principal (B9) needs the same answers as typed facts with provenance. None of these tasks names a panel; they name facts the engine must hold.

**Platform primitives.** The specifications fix the surface, not the substance: HTML §11's `Storage` semantics and `storage` event; IndexedDB's keys (total order array > binary > string > date > number), key paths, generators (2⁵³ ceiling), stores, indexes (silent skip on key-path failure), cursors (four directions), transactions (readonly/readwrite/versionchange; commit when all requests are handled and none new), durability (`default`/`strict`/`relaxed` per transaction), upgrade/versionchange and exceptions ([SP §1–2][SPN]); the Storage standard's shed/shelf/bucket/bottle model, storage key, pressure and "cleared in its entirety" rule, `persistent-storage` permission, and the quota constraints ([SP §3][SPN]); the Cache API's put/match/Vary rules and strict isolation from the HTTP cache ([SP §5][SPN]); the File API's blob URL store and snapshot state ([SP §6][SPN]); the File System standard's bucket file system, lock tri-state, sync-handle rules and write-on-close atomicity ([SP §7][SPN]); service-worker registrations as persistent records in their own bottle ([SP §9][SPN]). Fifteen places leave the substance to the user agent ([SP §10][SPN]) — every one is a decision this spec makes and records, never an accident.

**Izcal's principles.** P1 (security and privacy) makes the partition key unforgeable and cross-partition bytes unshippable; P2 (compatibility) makes the web-visible surface WPT-gated and the latitude choices conservative; B1/DET-1 makes every storage decision a recorded input; B2 makes every storage operation typed, inspectable IPC; M-1/D-S10 makes the engine Izcal's own; the MIT-only rule makes every shipped byte of it MIT (which SQLite — public domain, not MIT — fails on licence before M-1 even reaches it).

**Assumptions kept and broken.**

| Assumption inherited from incumbents | Keep or break | Reason |
|---|---|---|
| Per-origin (storage-key) address spaces with the web's identity model | **Keep** | The Storage standard's own model; the partition key's extension (T, C, X) is NW 6.8's, not a new invention |
| Whole-bucket atomic eviction ("cleared in its entirety") | **Keep** | Normative; and partial deletion is exactly the inconsistency AppCache taught |
| Transactions and async-first design in IndexedDB | **Keep** | The right core; the debt was in the API's era, not the idea |
| Quota classes (best-effort vs persistent) | **Keep** | Normative bucket mode; it survives into Storage Buckets |
| Synchronous storage IPC into the service | **Break** | DM-D11 and NW-D10 already removed the last two sync callers; the service admits none (G156) |
| Quota numbers opaque, padded, and inconsistent between views | **Break** | The engine owns the store; one exact internal ledger feeds the page-facing estimate (still padded, for compat), DevTools and the shell; disagreement between views is a defect class Izcal defines away ([G4.5][GO]) |
| Silent eviction; silent persistence grants | **Break** | An eviction decision log and a real `persistent-storage` prompt cost little and answer the highest-pain bug classes ([G4.1, G4.8][GO]); hidden engagement heuristics are authority the user never exercised (P1) |
| One borrowed engine under everything (SQLite-class) | **Break** | WebSQL's postmortem, M-1 2.3.0, MIT-only; and the snapshot-mapping requirement (SG-D2) needs a structural property no borrowed general store documents |
| Whole-profile single database file | **Break** | One torn write must not take down a profile; per-shelf file sets contain corruption ([SEC 6][SR]) |
| Time-based invisible idle deletion as a privacy default | **Break** | Safari's 7-day rule breaks sites for a privacy benefit partitioning already delivers; Izcal's privacy tools are the partition key, bounce-tracker deletion (CB 6.5) and user clearing; idle deletion stays a user setting ([H7.6][HP]; SG-D5) |

## 5. Lessons learned

| Project | What happened | The lesson | How Izcal applies it |
|---|---|---|---|
| Cookies | A 1994 stopgap won adoption and has been patched for thirty years (SameSite, CHIPS, prefixes) | A stopgap that wins becomes permanent | Cookie jars are a distinct asset class with their own store and keys (NW 6.9); never a storage fallback ([H1][HP]) |
| Flash LSOs, `userData` | Platform vacuum filled by worse storage, including unpartitioned tracking storage | Ship the real primitive early, keyed right from the first commit | The partition key is engine-native from day one (SG-D4) ([H2][HP]) |
| Web Storage | The dictionary shape survived; the synchronous model became unfixable jank | Keep the call-site shape, modernize the execution model | DM-D11's snapshot reads keep the trivial shape; writes are async service-side ([H3][HP]) |
| WebSQL | Dead in 19 months for pinning one library and dialect | Standards must be implementable from text; components under the standard must tolerate adversarial input | The engine is Izcal's, spec-anchored, fuzzed at every parser (G158–G159); no component name in any normative dependence ([H4][HP]) |
| IndexedDB | Right core, sixteen-year gestation from the 2009 proposal, durability retrofitted in v3 | Design the durability dial and the concurrency model in from day one | Durability is a first-class commit policy (SG-D3), not a retrofit ([H5][HP]) |
| AppCache | One declarative pattern, unfixable, removed | Declarative layers need evidence of pattern fit | Primitives first; named buckets ship only when the draft stabilizes (SG-D4) ([H6][HP]) |
| Safari's 7-day deletion | Persistence aligned with cookie lifetimes for privacy | Silent time-based deletion trades user data for a policy partitioning delivers better | No default idle deletion; eviction explained; privacy via keys and targeted deletion ([H7][HP]) |
| Chrome ABE | Path-based trust check fell to injection into the trusted process | Trust decisions must be structural (capabilities), never name- or path-based | The service checks the endpoint's minted capability on every call (G155) ([SEC 4.2–4.3][SR]) |
| ALFS/ALICE | 60 crash-consistency vulnerabilities across 11 stores including the two engines browsers borrowed | Ordering assumptions between two writes are assumptions the filesystem may not honor | One atomic commit surface (dual slots), verified by a crash-injection harness from SG-M0 (G157) ([SEC 6.2][SR]; [ED §5][ED]) |
| LevelDB-class stores in browsers | "Backed store" corruption reported across whole app ecosystems; remediation is deleting user data | Corruption must be contained per key, and never answered with deletion | Per-shelf file sets; index rebuild from values; user data is never auto-deleted (SG-D1's durability clause) ([G2.3][GO]) |
| FoundationDB, TigerBeetle | Deterministic simulation found bugs black-box testing could not; Jepsen still found what fuzzers missed | Simulation tests the real code; independent testing still needed | The engine is sim-first (G151); DST drives it from M1; WPT and differential suites stay independent (SG-6) ([ED §10][ED]) |

## 6. Design

### 6.1 The process and its capability surface

The **storage service** is one sandboxed process per profile, launched at first storage use, launched at the strictest sandbox tier (it parses page-influenced bytes: record formats, metadata, file names) — the Stage 1 process-map row stands ([S1 §1][S1]). It holds every partition, keyed internally by the storage key; it is per-profile, not per-partition, because FP-1 charges it ≤ 4 MiB† idle and the per-key process pattern is reserved for the keys renderers serve ([FP 8.2][FP]). **Why one process does not violate P1's "never co-locate cross-site data in one address space"**: that rule addresses *content* processes — address spaces a compromised page's code can reach. The storage service runs no content, exposes no content-reachable code path beyond its record parsers, sits at the strictest sandbox tier, holds no renderer authority, and checks every call's minted key (G155). The residual is stated plainly and accepted, as DM 6.16 states I-1's: a memory-corruption bug inside the service could read all partitions' plaintext while keys are unwrapped; the mitigation is the Rust no-unsafe discipline (G5), the fuzzed parsers (G159), the crash harness (G157) and the per-process threat model this spec hands the security scope (9.5). A per-key service split was rejected on footprint (it multiplies baseline cost by open keys) and because storage is the natural single chokepoint for clearing and quota; the reversal trigger is the first service-process escape or cross-partition bug in the field, which reopens the split. It opens files only through the substrate (`hg-substrate-os`, G3), holds no socket, no clock of its own beyond the substrate's, and no ambient authority: every client reaches it through a broker-minted `.hgidl` endpoint bound to one sequence, carrying the client's partition capability; the service checks the endpoint's key on every call and never trusts a renderer-supplied key string (G99's rule, service-side: G155).

Clients and their endpoints:

| Client | Endpoint | Writes it may do |
|---|---|---|
| Renderer (per document/worker of a key) | `StorageClient<T,C,X,O>` — IndexedDB, Cache API (DOM glue per DM 6.13), localStorage overlay writes (DM-D11), OPFS, quota queries | Only its own key's data; opaque response bytes are never deliverable to it (MD-31) |
| Container service / partition services (NW) | `CookieJar<T,C>` bound per jar scope (NW 6.1's broker binding) | Only the bound jars |
| Broker (`hg-agents`, `hg-profile`) | `StorageAdmin` — attribution history, interaction record, user-sheet sources, SW registration store access for `hg-agents`, usage facts, clearing | Per-container scoping (IPC-R2) |
| Shell renderer | `StorageFacts` — displayed rows only, never the store (FP 6.14) | None |
| DevTools / agents (IIP) | `StorageInspect` under the DT scoped-principal grant (Section 6.10) | None by default |

There is no synchronous call on any storage endpoint (G156): the Stage 1 sync-IPC allowlist that once named `localStorage` reads and `document.cookie` is emptied by DM-D11's and NW-D10's accepted amendments (pending application to Stage 1's text), and this spec adds nothing to it ([DM 9.5][DM]; [NW 9.5][NW]). Bulk data crosses as read-only shared memory (the snapshot windows, Section 6.7) or as `hg-clone-wire` bytes for IndexedDB values (DM-D12): **the service stores and returns opaque bytes and never interprets a value** ([DM 6.11][DM]).

### 6.2 The engine: Izcal's store

`hg-store-engine` is a from-scratch, spec-anchored storage engine (M-1). Its architecture, decided from the evidence in [ED][ED]:

**A copy-on-write page forest with atomic commit slots, plus an append-only value log for large values.**

- **Pages and forests.** Each shelf (storage key) is its own file set: one forest file for the small-record indexes and one value-log file set. Pages are 16 KiB†. Committed pages are **never modified in place**; a write allocates fresh pages and rewrites the path from the affected leaf to the root (path copying). The forest carries: one B+-tree per object store (table tree), one per index (index trees keyed by (index key, primary key) to make duplicate index keys orderable for cursors), the key-generator record, the bucket and bottle metadata, and the shelf's usage ledger entries.
- **Commit.** A transaction's changed pages are appended; the commit point is a dual **commit slot** in the file header: the slot carries the new root page number, the transaction id, and an AEAD tag over both (SG-D7's keys authenticate structure as well as content). Publishing is one atomic slot flip after one group fsync; on recovery the engine validates both slots' tags and takes the higher valid id — or neither, leaving the previous root intact. This is the smallest durable-commit surface the evidence documents (a 1-fsync, detect-and-rollback design; [ED §5.3][ED]), and it assumes only: single-byte atomicity, post-`fsync` durability, and powersafe overwrite ([ED §5.3, §3.1][ED]).
- **Crash consistency by construction.** Because committed pages are immutable and the commit slot is the only ordering-sensitive write, there is no replay pass and no repair-on-open in the normal case ([ED §2.2][ED]). Torn or reordered writes surface as tag failures, which roll back to the previous root — detected, never trusted.
- **Value log.** Values above **256 KiB†** (and everything the OPFS and blob stores hold, regardless of size, and Cache API bodies) live in an append-only value log as extent chains; the forest's records hold (log id, offset, length). Large values are written once and never rewritten to update a neighbour — the key–value-separation result, without an LSM ([ED §1.3, §7][ED]). Dead extents are reclaimed by a refcount sweep at transaction boundaries, bounded per pass†.
- **Space reclamation.** Forest pages freed by path copying are reclaimed with an epoch scheme: a freed page is reusable only when no published root older than the freeing commit remains pinned (G-carrying readers hold generation pins). Renderer snapshot pins (Section 6.7) are bounded — the snapshot window carries at most two generations — so a slow reader cannot grow the file unboundedly, LMDB's documented failure mode ([ED §8.1][ED]).
- **Indexes and cursors.** Index maintenance follows IndexedDB's steps exactly, including the silent skip: a record whose key-path evaluation fails stores **without** an index entry, no exception ([SP 2.14][SPN]). Cursors iterate (index key, primary key) pairs with the four directions' exact positioning rules ([SP 2.15][SPN]). `multiEntry`, unique constraints (checked at the transaction's operation, aborting on violation) and generators follow the pinned text ([SP 2.11–2.13][SPN]).
- **Transactions.** One writer per shelf, serialized in the service's sequence order (this is the total order recording depends on); readers run on pinned roots without locks. IndexedDB's scheduling rule — read-only transactions may overlap; read/write wait for earlier overlapping transactions — is enforced by the service per database scope ([SP 2.6][SPN]). Upgrade (`versionchange`) transactions are service-mediated connection-state machines: `blocked` fires from the service's connection ledger, which is also what the transaction waterfall (Section 6.10) shows. `IDBFactory.databases()` resolves from the shed's catalog with the fact base's provenance like any other surface. Web SQL is **not** implemented — the W3C's own note is its death certificate, and the OPFS path (Section 6.7) is the platform's own successor ([H4][HP]; [H8][HP]).
- **Determinism.** The engine consumes no wall clock, no thread scheduling, no randomness (G151): every input — operation stream, durability decisions, pressure events, entropy draws — arrives as a message or a recorded value, and all background work (reclamation, checkpoint-free by design) runs at transaction boundaries. This is the COW family's structural advantage over compaction-scheduling LSMs ([ED §10.5][ED]) and it is what makes SG-6 stateable.

**Architecture alternatives considered (SG-D2):**

| Option | Verdict | Reason |
|---|---|---|
| (a) COW page forest + commit slots + value log | **Chosen** | Snapshot mapping is structural (a committed root is the handle); crash consistency without a recovery pass; fewest asynchronous subsystems, hence best determinism fit; moderate complexity ([ED §2, §8, §10][ED]) |
| (b) Log-structured (LSM) | Rejected | Compaction stalls pause a page's writes; write amplification; a continuous background scheduler is the largest nondeterministic subsystem; snapshot publication needs a manifest-of-files construct ([ED §1, §10.5][ED]) |
| (c) B-tree + WAL | Rejected | The committed view spans base file plus WAL, so cross-process readers need shared-memory coordination and never get one mappable immutable range; multi-store atomicity needs a super-journal construct; checkpoint starvation under continuous readers ([ED §3, §8.3][ED]) |
| (d) A third-party embedded store (sled, redb, fjall — all MIT-optioned; or SQLite, LMDB, LevelDB — not MIT) | Rejected | D-S10's standing answer (build our own, following our specs); none documents cross-process read-only mapping of committed state; none is deterministic-simulation-first; SQLite additionally fails MIT-only (public domain) and M-1 2.3.0 ([ED §6][ED]) |

Reversal trigger for SG-D2: if SG-M0's browser-workload benchmark measures write amplification above **10×†** on the indexed-write-heavy percentile of the corpus (path-copying cost), or if a DM amendment removes the snapshot-mapping requirement, the architecture reopens; the value log, per-shelf containment and the commit-slot discipline survive any reopening.

### 6.4 Shed, shelf, bucket, bottle — implemented natively

The engine's metadata implements the Storage standard's hierarchy directly ([SP §3][SPN]): the **shed** is the service's root catalog; a **shelf** per storage key groups that key's file sets and holds the bucket map; the **default** bucket holds today's endpoints (`caches`, `indexedDB`, `localStorage`, `serviceWorkerRegistrations`, each a **bottle** with its data); session storage lives in traversable sheds the broker holds, outside the service. Two assets the standard's endpoint table does not name — the bucket file system's tree and value-log blob backing — are charged against their shelf's quota outside the bottle list, a recorded decision until a standard assigns them an endpoint (Q-SG-10). Bucket **mode** (`best-effort`/`persistent`) is engine metadata, which makes named buckets (Storage Buckets draft) a record-level extension, not a rewrite — Izcal ships the `default` bucket only until the draft advances past single-engine status ([SSB][SB]; SG-D4). Each bottle's proxy map and the shelf's usage ledger are maintained transactionally, so the exact usage number (Section 6.10) is always consistent with the data.

### 6.5 Quota and storage pressure (SG-D4, SG-D5)

- **Pool.** The browser's storage pool is **60% of total disk size, rounded down to 64 GiB† granularity** — computed from *total* disk, never free space, because the standard forbids free-space-derived quota and total-disk derivation resists fingerprinting the same way ([SP §6][SPN]; [H7.4][HP]).
- **Shelf quota.** A best-effort shelf gets **min(4 GiB†, one quarter of the unused pool)**; a persistent shelf **min(16 GiB†, the unused pool)**; a (site, container) group is capped at **16 GiB†** across its shelves. `estimate()` reports the shelf's quota and usage at page-facing resolution: quota as the shelf's coarse bucket, usage rounded up to 128 KiB† steps — padded toward content exactly as far as compatibility requires, while DevTools and the shell read the exact ledger ([G4.5][GO]).
- **Pressure.** Pressure begins when committed storage bytes exceed **90%† of the pool**, or when the OS reports pressure (an environment input, hence a recorded one). Response order: (1) stop accepting relaxed-durability backlog; (2) evict best-effort buckets by score; (3) inform the user and offer clearing (Storage §7's own sequence, made concrete: [SP 3.4][SPN]).
- **Eviction.** Whole buckets only ("cleared in its entirety"; [SP 3.4][SPN]). The score is a pure function of recorded inputs: `score = recency(last-use recorded time) × size class × endpoint class weight†`, persistent buckets never evicted, and the next-eviction prediction is shown in DevTools ([G4.1][GO]). No time-based idle deletion exists by default (SG-D5); idle deletion is a per-container user setting, and CB's bounce-tracker deletion does the targeted work.
- **Determinism.** Every number above is a function of recorded inputs: the pressure events, the operation stream, the entropy draws. Re-running a recording under a changed policy (bigger pool, different weights) is a DevTools what-if ([G4.7][GO]).

### 6.6 Durability (SG-D3)

The transaction's durability hint maps onto the commit policy: **`strict`** — the commit's fsync completes and is verified before the transaction's `complete` event; **`relaxed`** — the commit joins the group-commit backlog (bounded at **500 ms†** or the next strict commit, whichever first) and its `complete` may precede the flush; **`default`** — the shelf's configured default, which is **strict** for `indexedDB`, `localStorage` writes and `serviceWorkerRegistrations`, and **strict** for `caches` puts as well: Izcal's default is the conservative end of the hint's documented spectrum, because a lost Cache API entry silently changes what a service worker serves, and the group-commit cost of strict is one fsync per batch, not per request. `localStorage` writes follow DM-D11's service-side ordering; their durability is strict (an area is small; the cost is negligible). Relaxed commits that fail at flush time surface as aborted transactions with `UnknownError`, per the pinned commit algorithm ([SP 2.4][SPN]).

### 6.7 Snapshots: `localStorage`, OPFS reads, and the mapping discipline

The engine's committed-immutable-pages property is what makes DM-D11 implementable without copies ([ED §8][ED]):

- **`localStorage` snapshot windows.** Per storage key with a non-empty area, the service maintains a small **snapshot window** file (double-buffered generations, ≤ 2 × the 5 MiB recommended quota plus headers) holding the area as a flat page image with a generation header; at rest it is AEAD-encrypted like every other file. Publishing has two steps. First, on commit, the service publishes the new generation into the window file (one header slot) and decrypts that generation into a **staging region**: a read-only shared region holding one generation's plaintext, which the **broker allocates and hands to the requesting renderer as a handle** (HGBA-2 4.6's shared-region rule; IPC-R1/IPC-R2: the handle is single-key-scoped, and the broker never parses the bytes, IPC-R15). Second, the DOM glue installs the version at a task boundary as a recorded input — exactly DM-D11's protocol, service side ([DM 6.13][DM]). The staging region is the one exception to G153's no-plaintext-mapped rule, and it is the narrowest possible one: it holds only one key's own committed data, the service verified its authenticity at decryption, and its bytes can never cross the key's capability scope (G155).
- **OPFS sync handles.** `FileSystemSyncAccessHandle` reads map the committed file extents read-only into the worker (the same publish-subscribe discipline, per-file); writes go through the service and take the file's exclusive lock ([SP 7.3–7.4][SPN]). Write-on-close atomicity is native: a writable's new extents simply commit at close ([SP 7.5][SPN]).
- **The mapping discipline (G155).** A process never holds a mapping whose generation includes data outside its own capability's key. The service checks this at publish; the DST compromised-renderer suite attacks it (SG-8). Snapshot staging regions are anonymous shared memory (not file-backed pages), read-only, and charged to the mapping renderer's resident set, not to the service's idle 4 MiB† line (an FP accounting note, Section 9.5); staging-region lifetimes are bound to their generation, and the region is destroyed when the version it carries is superseded and acknowledged.

### 6.8 Partitioning and identity

Persisted state is keyed by the storage key **(T, C, X) + O** — top-level site, container, cross-site-ancestor bit, origin — the projection NW 6.8 already fixed for service-worker registrations and Cache Storage, extending the Storage standard's origin-only key with the partitioning work it says it expects ([NW 6.8][NW]; [SP 3.2][SPN]). The distinction from the renderer-cache projection (T, C, X, n) is load-bearing and restated in G154's terms: navigation nonces never enter storage keys ([NW 6.8][NW]). Keys are minted by the broker and carried in capabilities; the service never parses one out of a message body (G99 service-side). Storage Access grants (the pairwise ⟨top-level site, embedded site⟩ relaxation) are honoured exactly where NW's cookie model places them; partitioned storage itself has no silent exceptions — the SAA path is the only door to unpartitioned state, it expires, and its grant decisions are recorded facts like `persist()`'s ([SEC 1.8–1.9][SR]).

**Extension keys (registered 21 October 2026).** Extension storage is keyed by the storage spec and mapped by the extensions spec (EX-D6): `storage.local` is keyed **per (extension, profile)** by default and **per (extension, container)** in `split` mode, so a per-container agent's writes are invisible to the other containers' agents of the same extension; `storage.session` never reaches this service at all (it lives in the component host's memory and dies at profile exit); `storage.managed` is read-only enterprise policy, not stored here. Extension-origin documents (`ext://<id>` pages, their IndexedDB and Cache API areas) are keyed like any other origin, per (origin, container) — the origin is the signature-derived `ext://<id>` origin the style spec registers with `hg-url` — so extension-page storage needs no new key form and no new capability shape (G154's rule applies unchanged). Quota for `storage.local` is charged on the extension's own line, not the hosting page's.

### 6.9 Security and privacy

- **At rest (SG-D7).** Every persisted byte — data pages, metadata, value-log extents, snapshot windows, the usage ledger — is encrypted and authenticated under a **per-container data key**, wrapped by the profile's OS-bound key that the broker unwraps from the OS key store at first storage use (SEC-34's discipline; NW 6.9's per-container keys for cookies generalize to all page data). AEAD gives integrity for free, which is what the commit slots' tags verify (SG-D2). **Honest scope:** this answers device theft, other local users, and offline disk images; it does not answer malware already running as the user, and the settings page says so in one sentence — Chrome's app-bound encryption is the documented cautionary tale for promising more ([SEC 4.1–4.6][SR]). Linux without a Secret Service falls back to a profile-key file with mode 0600 and the disclosure upgraded ("stored unencrypted on disk").
- **Key-bearing records (registered 21 October 2026, WebCrypto WC-D6).** The one class of record this service handles whose plaintext it must never see is the sealed `CryptoKey` clone-wire record. A key-bearing record arrives as **ciphertext produced by the creating renderer's partition service under the partition's at-rest key**; the storage service stores it, serves it back, and deletes it, and **never decrypts, never indexes and never logs it** — its value-log and forest code treat the record as opaque bytes, the same discipline as MD-31's opaque responses (6.9's renderer-compromise bullet). Seal and unseal live in the partition service, outside this process, so a compromised storage service cannot read a key; the seal/unseal interface and the record format are the WebCrypto spec's, and the DOM spec's 6.13 clone-wire interface is the glue. The `CryptoKey` IndexedDB path is **feature-gated on this interface**: no sealed-record storage means no `CryptoKey` structured cloning into IndexedDB, never a plaintext fallback. SG-9's "0 plaintext keys at rest" is met by construction, because this service never holds a plaintext key at any point.
- **Clearing as a remnant contract.** "Cleared" means: records removed transactionally, the affected extents reclaimed, the shelf's files **checkpointed and rotated** in the same operation, and the disclosure states the flash reality (wear leveling is beyond user-space control; crypto-erase of a removed container's key is the strong form, and container removal takes it) ([SEC 5.1–5.4][SR]). A **`Clear-Site-Data`** request with `cache` or `storage` runs NW-D18's container-scoped selection against this clearing path — the same transactional clear as site data, a recorded decision — and unpublishes the affected key's snapshot staging region, which the next touch rebuilds. Private windows never touch the service: their storage is memory-only in the renderer and broker (FP-D18's rule, generalized).
- **Renderer compromise.** The service assumes every renderer is hostile (5–15 exploitable renderer bugs per milestone is the published historical rate ([SEC 3.1][SR])): capability checks per call, no path resolution on renderer-supplied strings, all parsing of untrusted record bytes inside the sandboxed service with memory-safe code and fuzzed parsers (G159), and per-shelf file sets so one corruption is one key's problem ([SEC 6][SR] implication). Opaque response bytes are stored by the service and never delivered to a renderer, participating in MD-31's zero-mapping target ([MD 8][MD]).
- **Fingerprinting.** Quota derives from total disk in coarse steps; usage is padded toward content; eviction order is deterministic *given the recorded inputs* but not probed cross-site without partitioned-state reads, which the partition key denies; `estimate()`'s shape is constant across origins a site cannot distinguish ([SEC 8.1–8.4][SR]). PRIV-2 gains a storage-probing case (Section 9.5).
- **Quota exhaustion as DoS.** Per-shelf and group caps bound one site's share; `persist()` grants are per (site, container), user-visible, revocable with site data, and capped by the pool — persistent storage is never a free reservation ([SEC 7.1–7.3][SR]).

### 6.10 Observability: one fact base, three consumers

The service maintains, beside the data, a **storage fact base** (`hg-store-observe`): the exact usage ledger per shelf/bucket/bottle; the **eviction decision log** (what, when, why — pressure inputs, score, what was freed); the **transaction ledger** (state machines per transaction and connection, who blocks an upgrade since when); **write provenance** (key, transaction, principal, script position and cause from the DOM's decision-point register, virtual time, size delta); **typed quota-failure reasons**; and `persistent-storage`/Storage-Access grant decisions with reasons. It is browsing-history-adjacent, so **FP-D18's rules govern it end to end**: 24 h† for event-class detail, 7 days† for aggregates, cleared with history and site data, memory-only in private windows, never synced ([FP-D18][FP]; [G4][GO]).

Three consumers, one source: the **shell** reads facts to render site-data settings, the pre-eviction warning ("these sites' data will be removed under pressure unless persisted") and the `persistent-storage` prompt; **DevTools** reads the same facts through the IIP **Storage domain** (`hg-store-observe`'s IIP surfaces: usage tree, eviction log, transaction waterfall with blocked-by participants, per-key provenance, storage-diff scrubbing over recordings, quota what-if), under the DT scoped-principal rules — storage values are a sensitive class, masked and redacted like cookies ([DT 6.5][DT]; [G4.2–G4.4, G4.6][GO]); **agents** (AI on) read the same typed facts under B9's grants. What is *not* built: a sixth isolated panel; every storage view joins the IIP cause chains (`caused_by`) so a write, the request that fetched the data, and the console line that triggered it are one timeline ([G4][GO]).

### 6.11 The user experience

For a person, storage becomes visible in exactly three places: the **`persistent-storage` prompt** (a real prompt, remembered per (site, container), never a silent engagement heuristic — SG-D6), the **site-data settings page** (exact per-site usage from the ledger, per-bucket detail, one "clear" action that is the remnant contract of 6.9), and the **pre-eviction warning** (shown once per pressure episode, with per-site breakdown and a "keep this site's data" action that is a persisted-mode grant in disguise — the user performs the `persist()` decision the site asked for). Developers get the transaction waterfall and eviction log in DevTools. Nobody is ever surprised twice the same way: the first eviction of a key that never had a warning is preceded by the warning ([G5.5][GO]).

### 6.12 Recording and replay (SG-D8)

Storage operations are already typed IPC, so recording them is B2's default. The recorded facts: the operation stream with sequence order, every decision point in G154's list, and the shelf state hash at session start and end. **Recorded sessions never touch live stores, for reads or writes.** A recorded browsing context group runs in dedicated fresh processes (DT) whose storage endpoints bind to a **scratch shelf**: at recording start the service publishes a pinned copy of the recorded keys' shelves (cheap by construction — the engine's committed pages are immutable, so the copy is a root pin plus lazy materialization), and every read and write of the session lands on the scratch shelf, which starts in exactly the pinned state. The scratch shelf is served by a **dedicated memory-only storage-service instance** — the same crates, no files, strictest sandbox tier — created with the recording and dropped with it; its budget is the recording's own (DT 6.5's recording bundle line), not FP-1's idle line. A **replay host holds no storage service at all** ([DT 6.5 rule 8][DT]): it re-executes the recorded operations against the scratch shelf's recorded start state inside the simulator (the engine runs in-process there, G151), comparing state hashes at every recorded decision point. This differs from the network side, where NW 6.16 records values read from long-lived stores: storage needs no values-read rule, because the scratch shelf *is* the start state. Random or time-derived values that pages store replay because their producers are already deterministic (the substrate clock and entropy), and the storage layer adds no new nondeterminism of its own (G151) — which is what makes SG-6 stateable at all.

### 6.13 Integrations

**DOM spec**: DM-D11's snapshot protocol service side (6.7); `hg-clone-wire` opaque values (6.1); transaction auto-commit's service-side completion (the commit trigger is request-completion, no event-loop coupling ([SP 2.5][SPN])); connection/upgrade state machines feeding `hg-agents`' freeze decisions (open IndexedDB connections that block another context keep a page unfrozen — the service's ledger is the data source; interfaces 2.17). **Networking**: cookie jars (6.3); the boundary that the Cache API's store is here and the HTTP cache is NW-D11's regenerable-cache member, never merged ([NW-D11][NW]). **DevTools**: the Storage domain, Stage 2 Application panel's data source; recorded-session storage semantics (6.12). **Footprint**: FP-1's idle line; FP-11-style accounting for the service's resident state; FP-37's clearing tests; FP 6.12's disk budgets for the regenerable caches that are *not* here. **Content blocking**: the interaction record's notifications and scoped deletion (6.3). **Shell**: prompts and site data (6.11). **Security scope** (in review): the storage service's per-process threat model (Stage 1 13.2's list already names it), SEC-34 key discipline, and the picked-file byte transport of Section 6.14.

### 6.14 Picked files (File System Access) — the coordination boundary

The bucket file system (OPFS) is unambiguously this spec's: private, storage-keyed, quota-charged ([SP §7][SPN]). User-picked files are not storage: the *grant* belongs to the security scope's picker rules (SH-R6–R9, in review) and the permission store, and the DOM handle objects belong to the DOM spec's surface. This spec owns the **byte transport**: a granted handle's reads and writes stream through a broker-minted capability into the storage service's file-I/O path (the only process that touches files, G150), with the lock tri-state and write-on-close atomicity enforced service-side. If the security scope's text assigns picked-file I/O elsewhere, this section yields and the amendment is recorded (Q-SG-9); nothing else in this spec depends on it ([SP 7.7][SPN]; interfaces 5.1).

## 11. Open questions and flagged claims

**Open questions.**

- **Q-SG-1 (adoption numbers).** No published, dated distribution of origin storage usage or per-API adoption was verifiable ([G6.3][GO]); the corpus and Izcal's opt-in telemetry should publish one. No quota threshold in this spec depends on it.
- **Q-SG-2 (Firefox quota conflict) — settled by the fact-check.** MDN's page (modified 5 January 2026) is current: Firefox best-effort quota is min(10% of total disk, 10 GiB group limit), persistent 50% capped at 8 TiB; web.dev's 2024 figures (50% of free disk, 2 GB per eTLD+1) are superseded. Any comparative figure this spec quotes uses the MDN numbers with their date.
- **Q-SG-3 (partitioned storage-key text).** The Storage standard's origin-only key "is expected to change"; which partitioned text is current was not verified — SG-D4's reversal covers the landing text.
- **Q-SG-4 (`IDBTransaction.commit()` details).** Present in the IDL; algorithmic text not re-read ([SP 2.16][SPN]). Pinned at SG-M2 implementation time.
- **Q-SG-5 (`estimate()` padding magnitudes per engine).** Black-box measurement to plan ([G, open questions][GO]); affects only page-facing padding, not the ledger.
- **Q-SG-6 (history/bookmark schema ownership).** SG-D11 claims the stores; the schema and settings UI belong to the shell, whose design document should name them (an A-UI-class row this spec's 9.5 pre-seeds for Stage 1 13.2).
- **Q-SG-7 (picked-file transport vs SEC's SH-R6–R9).** Section 6.14 yields if the security scope (in review) assigns the byte transport elsewhere.
- **Q-SG-8 (corruption rates in the wild).** Beyond single-app reports (~0.1% of sessions in one report, [G2.3][GO]) no published rate was found; a candidate for Izcal's opt-in telemetry and a black-box measurement (never source-derived).
- **Q-SG-9 (secret-service-absent Linux distribution share).** Determines how often SG-D7's fallback path runs in practice; measurement, not design.
- **Q-SG-10 (bottle assignment for the bucket FS and blobs).** The Storage standard's endpoint table names neither; 6.4 charges both against the shelf outside the bottle list until a standard assigns them an endpoint, then adopts that assignment.

**Flagged claims.** The Chrome 60%/80% and Firefox/Safari quota figures are vendor-documentation quotes with dates, not measurements ([G6.1][GO]); the Safari 1 GB/200 MB prompt numbers are explicitly unofficial ([G5.2][GO]); the "~0.1% of sessions" corruption figure is one developer's report ([G2.3][GO]); the Dostoevsky amplification figures are Medium-confidence secondary summaries ([ED §1.4][ED]) and no threshold in this spec rests on them; the "2014-era Safari 30-day eviction" story is unverified in primary prose and is not relied on anywhere ([H, open question 1][HP]); every † in this document is this document's own first-principles setting (page size, thresholds, budgets, weights, floors and prompt ceilings alike), none measured on Izcal yet, while numbers taken from other accepted documents or from pinned specifications carry their source, not a †.
