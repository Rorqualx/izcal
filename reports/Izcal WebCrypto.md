**The problem.** The web's cryptographic surface — `crypto.subtle` (`SubtleCrypto`), `crypto.getRandomValues` and `crypto.randomUUID` — has no owner in Izcal's record: the networking spec created `hg-crypto` for TLS and left WebCrypto as open question Q-NW-14 and ledger gap G-18, the DOM spec deferred the bindings "once the owner of the algorithms is named", and the work is "counted nowhere" in staffing. Meanwhile the surface is large: sixteen registered algorithms plus the secure curves, each with an implementation hazard the standards prose names (GCM nonce reuse, RSA decryption oracles, ECDSA nonce reuse, X25519's all-zero output, Ed25519 malleability, ML-KEM's no-error-path decapsulation), a key model that persists private key material through structured clone into storage, and an entropy source every other consumer of randomness depends on.

**The central idea: one cryptography implementation, two owners of its growth.** G36 already says only `hg-crypto` implements a cryptographic primitive, and `hg-crypto` sits in the shared layer L2s "so that … WebCrypto if its owner chooses (Q-NW-14), link one implementation". This spec takes that option: **the WebCrypto surface is owned here; the primitives stay in `hg-crypto`, which stays the networking spec's crate**, and every primitive the web API needs that the network stack does not have is added to `hg-crypto` under the networking spec's own verification regime (NW-49 vectors, NW-50 constant time, NW-52 audit), amended in Section 9.5. Nothing duplicates: TLS and `SubtleCrypto` share one AES-GCM, one ECDSA, one RSA. The second idea is that **randomness is a recorded input, not an ambient fact**: every byte any web-crypto operation consumes or produces is a drawn value on the B1 recording, so a replay reproduces the page's randoms bit-identically and no seed ever exists in a recording. The third is that **the key, not the operation, is the custody question**: a page's authority already includes its keys' operations, so operations run in the key's renderer on the substrate pool, while key bytes live in `hg-crypto`'s zeroizing secret types outside the JS cage and never enter recordings, the IIP protocol or DevTools as anything but metadata.

**The decisions that matter most:** (1) **WC-D1** — this spec owns WebCrypto; `hg-crypto` stays NW's; Q-NW-14 and G-18 close; (2) **WC-D2** — the web API adds RSA private-key operations, ECDSA P-384 signing, ECDH P-384, Ed25519 signing, AES-CBC/CTR/KW and PBKDF2 to `hg-crypto`, and seven new operations join the constant-time surface (NW-50 amended, riscv64 included); (3) **WC-D4** — entropy comes from the OS kernel interface per platform, no userspace DRBG, no weak fallback, ever; (4) **WC-D8** — all randomness is recorded drawn values and replay never re-derives it; (5) **WC-D9** — no post-quantum surface in the web API in Stage 1; a from-FIPS-203-prose ML-KEM reference exists as a test-only differential oracle; (6) **WC-D10** — a `crypto` IIP domain shows every operation, its key's metadata and its true failure reason, with key material structurally excluded. The work is **3.5–5.5† engineers** with 0.5† of the security-response rotation (Section 9.3), additive to the networking spec's cryptography track and counted at last (G-18's complaint), over roughly 27–42 months† of the Stage 1 window.

## 1. The problem and who has it

| User | Task, in their words | What fails today |
|---|---|---|
| **People browsing** | "My password manager, my wallet, my end-to-end-encrypted chat should be as safe in a browser tab as in an app" | Web E2EE clients hold long-lived identity private keys as non-extractable `CryptoKey`s persisted through IndexedDB; in today's engines those bytes sit in renderer memory in whatever form the engine keeps them, and a renderer exploit can lift them for offline use |
| **Web application developers** | "Why did `importKey` throw `DataError`?", "why is my AES-GCM decrypt failing?" | `SubtleCrypto`'s errors carry no detail: an import failure is `DataError` whether the base64url is padded, the `key_ops` disagree with `usages`, or the DER length overflows, and no tool shows the normalized algorithm or the key's actual parameters ([GO 1][GO]) |
| **Authors of encryption-heavy apps** | "Bulk AES in a tab should not cost me the frame budget" | Operation placement differs per engine (main thread vs worker pools), is undocumented, and shows up as jank on large payloads; no API says where an operation ran |
| **Security reviewers and auditors of web apps** | "Show me every key this page created and every weak primitive it used" | No browser tool lists a page's `CryptoKey`s, their parameters or their usage; PBKDF2 iteration counts below every current recommendation pass silently |
| **Izcal's own services** | "One cryptography implementation for TLS, WireGuard, update verification and the web platform, audited once" | Without an owner, WebCrypto would fork primitives or link a second crypto library into renderers, doubling the audit surface NW-D23 exists to avoid |
| **Izcal's engineers and agents** | "Replay this page's session exactly" | Randomness drawn by pages is invisible in every current engine's recording; a replayed session diverges at the first `crypto.getRandomValues` |

**What Izcal's specs already decide** (the full digest is [IF §9][IF]):

- **[M-1][H2] (2.3.3).** Web-visible behavior is implemented from the normative specification at a pinned revision with spec anchors (ANC-1); every primitive is implemented from the NIST SP, FIPS and RFC texts — standards prose is the allowed evidence class — and no third-party project's source code is ever read, so no reference implementation guides this work; correctness comes from vectors, differential fuzzing against black-box implementations, and the audit (M-1 part 4).
- **MIT only (2.3.2).** Every primitive crate `hg-crypto` pins is MIT OR Apache-2.0 with its resolved tree free of non-MIT links, checked per pin as NW 6.5 does; anything not available on those terms Izcal writes (the NW-D23 rule this spec extends, not changes).
- **G36.** Only `hg-crypto` implements a cryptographic primitive or depends on a cryptography crate; secret-dependent code in it passes `hg-crypto-check` on every target ISA before merging. This spec's crates therefore contain no primitive code and no direct cryptography-crate dependency.
- **[NW-D23][NW], owner decision of 19 October 2026.** Hashes, HMAC, HKDF, AES-GCM, ChaCha20-Poly1305, BLAKE2s and ML-KEM come from pinned MIT-dual RustCrypto crates; X25519, P-256/P-384 curve arithmetic, Ed25519 and RSA verification, HPKE and the constant-time helpers are Izcal's own on `fiat-crypto`; the reversal trigger is per primitive (a pin fails review → Izcal writes that primitive).
- **B1, Stage 1 3.1, Q-CS-1.** No engine code touches OS randomness directly; `Entropy::crypto()` is the one crypto-quality source — OS CSPRNG in production, seeded only under `hg-substrate-sim` — and its draws are recorded as values, never seeds ([Stage 1 §3.1][S1], [NW §6.16][NW]).
- **JS-D15 and JS §6.9.** `Math.random` is a per-realm generator on a named B1 stream; the CSPRNG is a different stream class, and nothing may couple them.
- **DM-D8, DM-D12, DM-D18, G95.** Workers of a key run in the key's renderer; everything serialized crosses agents in one versioned wire format whose decoder is the only parser; observability has three cost classes and a record type for everything the engine decides.
- **FP-1, FP-2, FP-32, FP-34.** Process kinds and threads are budgeted lines; a design that adds either must say where its row comes from.
- **DT-D1, DT-D2, DT G11.** IIP is generated from `.hgidl`; recordings never contain credential-class values; export writers accept only `Redacted<T>` values.
- **The renderer threat model (security scope 0.3).** Renderer compromise is assumed in the model; I-1 keeps one site per renderer process; the network tier-P set (NET-R5) names `hg-tls` and `hg-crypto`; the advisory-response scope (SEC-25) covers `hg-crypto`'s pins and Izcal's own cryptography.

**What success means, measurably.** The full registered algorithm set plus secure curves passing the pinned W3C WebCryptoAPI conformance suite at or above the best shipping engine's black-box rate per directory (WC-1); every secret-dependent operation passing the binary taint check and statistical timing tests on x86-64, arm64 and riscv64 (WC-3); zero weak fallbacks provable by fault injection (WC-7); recorded sessions replaying bit-identically through every random draw (WC-8); no non-extractable key byte ever in the JS cage (WC-9); and every `DataError`/`OperationError` explainable in the crypto panel (WC-10).

## 2. History: what came before, and why it was built that way

### 2.1 Chronology

| Year | Project / event | What it did | Why that way | Fate and why |
|---|---|---|---|---|
| 1995–96 | Netscape SSL RNG | Seeded SSL keys from clock + PID + PPID | No kernel RNG contract existed; seeding undocumented and unreviewed | Broken publicly by Goldberg–Wagner (≤ 47 bits of a "128-bit" key; 25 s local attack); patched in Navigator 1.22; founded the seed-from-kernel rule ([HP 3.1–3.2][HP]) |
| 1996–98 | Kocher 1996; Bleichenbacher 1998 | Timing and padding-oracle attacks on RSA in SSL | Implementations optimized first, analysed later | Blinding deployed; the padding oracle resurfaced for 20+ years (ROBOT 2017) ([HP 4.1–4.2, 4.7][HP]) |
| 1998 | OpenSSL and NSS open-sourced | Browsers' TLS and crypto backends | No maintained free library existed in 1995–98 | Dominated 15+ years; both later forked when engine needs diverged ([HP 2.1, 2.3][HP]) |
| 2001–12 | Plugin crypto era | Java applets, ActiveX/CAPICOM, Flash did page crypto | The page sandbox had no crypto at all | Died with NPAPI (2015–2017) and Flash (2020): a trust boundary cannot depend on installing code ([HP 5.1][HP]) |
| 2006–08 | Debian OpenSSL bug | The entropy pool silently lost its inputs | Valgrind cleanup on crypto code without crypto review; wrong review channel | Disclosed 2008-05-13; 98 301 possible streams; global key regeneration ([HP 3.3–3.5][HP]) |
| 2006–15 | Dual_EC_DRBG | A NIST-standardized DRBG with NSA-influenced constants | Standardization accepted unexplained constants; FIPS compliance spread it | Backdoor shown 2007, removed 2014-04-21, Rev. 1 without it 2015-06; Juniper showed the constants living on ([HP 3.6–3.8][HP]) |
| 2011–17 | WebCrypto v1 | The standard JS crypto API | Started event-driven and streaming (2012 FPWD: `CryptoOperation`, `KeyStorage`, no promises), rewritten to one-shot promises; no mandatory algorithms | REC 2017-01-26 after about 5.5 years; engines shipped subsets; secure curves took until 2023–2025 ([HP 1.1–1.6][HP]) |
| 2011–13 | `getRandomValues` era | Browsers shipped randomness years before `SubtleCrypto` | It was uncontroversial, unlike the rest | Still the only `Crypto` member allowed in insecure contexts — the settled piece ([HP 1.8][HP]) |
| 2013 | Android `SecureRandom` theft | Weak PRNG initialization drained a Bitcoin wallet | Mobile stacks inherited OpenSSL without initialization guarantees | Google fixed at the OS level (KitKat baseline) ([HP 3.10][HP]) |
| 2014 | BoringSSL; Heartbleed; `getrandom(2)` | Chrome forked OpenSSL (70+ carried patches, ABI mismatch); OpenSSL's funding crisis exposed; Linux gained a blocking-seed syscall | Engine needs and a shared library's stability promises diverged | BoringSSL became the engine norm; the kernel took over the entropy contract ([HP 2.3–2.6, 3.11][HP]) |
| 2017–19 | ROBOT; Spectre; WebAuthn | The old oracle at internet scale (27 of the top-100 domains); in-process memory disclosure; credentials moved off the JS heap | Legacy TLS_RSA everywhere; JS-held "non-extractable" keys | Browsers throttled timers; WebAuthn (REC 2019-03-04) became the credential path — not WebCrypto ([HP 4.7, 5.3][HP], [SR 4.2–4.3][SR]) |
| 2017–20 | Verified crypto deploys | HACL\*/Fiat-Crypto code shipped in Firefox (57, 60, 77), NSS and the Linux kernel | Hand-written constant-time code was unauditable; verification caught up in performance (~10× and +27% measured) | Constant-time-by-construction became the default answer ([HP 4.9][HP]) |
| 2020–25 | WebCrypto Level 2; the HPKE gap | A fresh FPWD (2025-04-22) after 8 idle years; HPKE (2022) never exposed at the API | Standards capacity exhausted; engines routed new algorithms via WICG and platform features | WebCrypto remains a frozen core with late additions ([HP 1.7, 5.5–5.6][HP]) |

### 2.2 Technology mismatches: assumptions that no longer hold

- **The API shape froze in 2012's compromises.** The streaming model was cut for good API reasons and never replaced ([HP 1.2, 5.4][HP]); large-file encryption left the platform for WebAssembly ports with hand-rolled per-chunk nonce management — the exact class of bug the platform should own.
- **"Non-extractable" meant something in 2017 and less every year after.** Spectre made renderer memory readable in principle; WebAuthn moved the credentials that matter to a hardware boundary ([HP 5.3][HP], [SR 4.1–4.3][SR]). An API-level flag is not a custody story.
- **A userspace DRBG made sense when the kernel had no contract.** Since `getrandom(2)` (2014) and its successors, the kernel owns reseeding and entropy sources; an app-level generator is now pure liability ([HP 3.11][HP]).
- **Hand-written constant-time assembly was the only option; it no longer is.** Generated, verified arithmetic won on auditability *and* measured speed ([HP 4.9][HP], [SR 2.6–2.8][SR]).
- **Standards velocity for crypto APIs is near zero.** A frozen registry plus WICG incubation is the steady state; a new browser must anchor to the stable NIST/RFC texts and treat the W3C registry as a compatibility surface, not a roadmap ([HP 1.7, lesson 4][HP]).

## 3. Today: the landscape and its gaps

**The implementations.** The registry's sixteen algorithms plus the secure curves now ship in all three engines: Ed25519 landed in Firefox 129, Safari 17.x and Chrome 137; X448 is specified and shipped by none; Chrome alone adds a non-registry `CHACHA20-POLY1305` ([SA 1.6–1.8][SA]). SHA-1 remains in the registry for `digest` only, years after NIST disallowed it for signatures ([SA 1.11][SA]). Post-quantum is TLS-internal everywhere: no browser exposes ML-KEM through `SubtleCrypto`; the standards work sits in a single W3C tracking issue and a WICG incubation whose Draft CG Report (September 2026) drafts the `encapsulateKey` surface; Cloudflare's Workers runtime added ML-KEM/ML-DSA to its Web Crypto layer in October 2026, ahead of every browser (Medium — from search summaries, [GO 6.4][GO]; the rest of this paragraph is High) ([SA 1.10][SA], [GO 6.1–6.4][GO]).

**What is used.** The API is dominated by randomness: `getRandomValues` runs on 34.45% of desktop and 40.95% of mobile pages, while `SubtleCrypto.sign` runs on 0.13% and `SubtleCryptoDigest` on 2.65% desktop / 2.98% mobile ([GO 5.1–5.2][GO]). Where the use case is standardized the native path dominates — the `jose` JWT library, built on WebCrypto, draws 93.4 million weekly npm downloads against `crypto-js`'s 10.9 million and `node-forge`'s 23.1 million, the polyfills whose persistence measures the API's gaps ([GO 5.3–5.4][GO]).

**What cannot be seen.** No browser has any crypto view: Chrome's DevTools documentation enumerates every panel and sidebar tool and WebCrypto appears nowhere, while the same Application panel that lists IndexedDB and cookies has a WebAuthn section and no `CryptoKey` section — a non-extractable key, the recommended kind, is completely unobservable once created ([GO 1.1–1.2][GO]). The API's own errors are coarse by specification: five error types, no reason field; every AES-CBC decryption failure — wrong key, wrong IV, corrupted padding — is one identical `OperationError`, and import-format mismatch is the canonical failure class, documented across the tracker since 2017 ([GO 1.3–1.5][GO]). The standard developer response is to log intermediate values outside the crypto calls and diff them by hand ([GO 1.7][GO]).

**What cannot be pinned.** The spec fixes no ordering between operations ("makes no specific requirements on the ordering of responses") and no thread; `getRandomValues` has a 65 536-byte cap, no entropy accounting, no rate limit; there is no seed API and no deterministic mode anywhere in the surface ([GO 2.2, 3.5][GO], [SR 6.2][SR]). The consequence reaches the tooling: fake-timers fakes timers, `Date` and `performance.now` but no randomness; WebDriver BiDi's ten modules include timezone and geolocation emulation and nothing for entropy — an automated test that wants deterministic randoms must monkey-patch `crypto` and hope it races nothing ([GO 2.5–2.6][GO]). Record-replay tools solve this one layer down: rr records kernel entropy as an input and replays it exactly ([GO 2.1][GO], [SR 6.1][SR]).

**The permission answer already exists.** There is no permission gate and no enterprise policy for WebCrypto anywhere; the access model is `[SecureContext]` plus origin-scoped keys, and the one consent clause in the spec is DoS mitigation, not access control; the fingerprinting literature studies canvas, WebGL and fonts and does not study RNG output — an absence-of-evidence finding (Low), consistent with uniform random carrying no device signal ([GO 3.1–3.4][GO]).

**The security reality.** Non-extractable is an API-level word, not a protection boundary: key material lives in renderer memory, no standardized hardware access exists (that is WebAuthn's authenticator boundary), and Spectre-class disclosure makes renderer memory potentially readable by web-authored code — which is why process-per-site is the shipped mitigation ([SR 4.1–4.4][SR]). Shipping crypto code still fails in the historical classes: biased ECDSA nonces (PuTTY 2024, ~60 signatures to a P-521 key, fourteen years after the PS3), Bleichenbacher oracles in major TLS stacks in 2017, an unaudited-by-its-own-documentation ML-KEM crate in the Rust ecosystem ([SR 3.3, 3.5, 3.7, 5.5][SR]). The verification stack that catches these — Wycheproof's attack vectors, ACVP's negative cases, taint checks, statistical timing, independent audit — is published and proven ([SR §2, §5][SR]).

**The gaps, in one table.**

| Gap | Today | Evidence |
|---|---|---|
| No operation is observable | 0 of 3 engines show any crypto operation, key or failure reason | [GO 1.1–1.7][GO] |
| No key inventory | Non-extractable keys are invisible once created | [GO 1.2, 4.3][GO] |
| No determinism hook | No standard way to pin randomness in tests or automation | [GO 2.5–2.6][GO] |
| No recorded randomness | Record-replay stops at the engine boundary; pages diverge at the first draw | [GO 2.1–2.4][GO] |
| Key custody is a word, not a boundary | Non-extractable bytes sit in renderer memory | [SR 4.1][SR] |
| PQ at the API is unbuilt in browsers | TLS moved years ago; edge runtimes moved first; the browser spec incubates | [GO 6.1–6.4][GO] |

Izcal can close all six in one design because it owns the implementation, the substrate and the tools (see `references/izcal-capabilities.md`): the crypto event stream is an IPC output of code Izcal wrote, the key inventory is metadata over objects Izcal allocated, recorded randomness is B1's recorded-input model applied to the last ambient input, and the ML-KEM oracle is M-1's oracle class applied to a primitive whose prose is final ([GO §4][GO]).

## 4. First principles

### 4.1 The users' real tasks

1. Keep a secret secret for as long as its owner intends (session tokens: hours; E2EE identity keys: months or years).
2. Prove who sent something (signatures, JWTs, WebAuthn-adjacent flows that use the platform instead of SubtleCrypto).
3. Derive a key from a password (PBKDF2) without a server seeing it.
4. Encrypt bulk data (files, media chunks) at memory speed.
5. Get unguessable bytes (tokens, nonces, UUIDs) from the platform rather than from `Math.random`.
6. Debug all of the above when it fails, and audit it after the fact.

### 4.2 The platform's actual primitives

The [W3C Web Cryptography API][WC] is the normative surface: a `SubtleCrypto` object with twelve operations (encrypt, decrypt, sign, verify, digest, generateKey, deriveKey, deriveBits, importKey, exportKey, wrapKey, unwrapKey), a **closed algorithm registry** — sixteen algorithm families at Level 1; the pinned editor's draft (Level 2) registers eighteen with the secure curves ([SA 1.2][SA]), "normalize an algorithm" as the central error funnel, `CryptoKey` with `type`/`extractable`/`usages`/`algorithm`, four import-export formats (`raw`, `spki`, `pkcs8`, `jwk`), `[SecureContext]` exposure, `crypto.getRandomValues` (≤ 65 536 bytes per call, integer typed arrays, filled in place) as the one `Crypto` member available outside a secure context, and `crypto.randomUUID` — `[SecureContext]`-gated like `subtle` ([SA 1.1–1.5][SA], [ER 4.1, 4.4][ER]). The secure curves (X25519, Ed25519) merged into the main spec's editor's draft in December 2024 and ship in all three engines ([SA 1.6–1.7][SA]). Each primitive's normative text is a NIST SP, FIPS or RFC, every one final ([SA §2–3][SA]): FIPS 180-4, 197, 186-5, 198-1, 203; SP 800-38A/38D/38F, 800-56A, 800-57, 800-132, 800-186, 800-227; RFCs 2104, 5869, 6979, 7748, 8017, 8018, 8032, 8439, 10024. Every one is implementable from prose plus its vectors ([SA §5][SA]) — this is the same evidence class NW 6.5 already commits to, and the reason no part of this spec needs a reference implementation.

Beneath the API, the platform primitives Izcal already has are decisive: `Entropy::crypto()` with its production/simulation duality ([Stage 1 §3.1][S1]); `hg-crypto`'s secret types (zeroize on drop, no `Debug`, `Clone` or serialization [NW §6.5][NW]); `hg-clone-wire`'s versioned record format ([DM §6.11][DM]); the substrate's sequences and pool (no engine code owns a thread); IIP's typed domains ([DT-D1][DT]).

### 4.3 Izcal's principles that bind this design

The accepted principles, as HGBA-2 states them: **P1** (treat web content as hostile; renderers hold zero ambient authority; never co-locate cross-site data in one address space), **P2** (spec conformance gates everything; a faster wrong answer is a regression), **P3** (every accelerated path has a correct fallback; device loss and OOM degrade performance, never correctness), **P4** (performance and energy on the corpus, measured). This spec derives from them, and where a derivation bends a principle it says so: fail-closed entropy (WC-D4) is a **named exception to P3 as written** — a failed entropy interface degrades to a failed call, never to weak randomness, because P1 outranks P3 and weak randomness is a correctness failure in kind, not a performance loss; and in-renderer operations on the substrate pool (WC-D3) are this spec's **application of P4**, not P4's text. M-1 (primitives from prose and vectors; anchors on every algorithm) sits outside the ranking, and the ledger's G-18 requirement that the work be staffed somewhere is this section's fourth input.

### 4.4 Assumptions kept and broken

| Assumption inherited from existing browsers | Keep or break | Why |
|---|---|---|
| `[SecureContext]` gate; `getRandomValues` alone available everywhere (randomUUID is gated) | **Keep** | Spec text; no evidence a permission gate helps (WC-D7); breaking it breaks compat for zero security gain |
| No permission prompt for any SubtleCrypto operation | **Keep** (WC-D7) | Keys are same-origin by construction; a prompt would be ignored within a week and protects nothing the origin model does not |
| The registry's names, casing-insensitivity and error classes | **Keep** (WC-1, WC-2) | P2. Chrome's non-standard `CHACHA20-POLY1305` name is kept for parity, documented as non-standard ([SA 1.8][SA]) |
| `CryptoKey` is structured-cloneable, including non-extractable keys, so IndexedDB can persist them | **Keep** (WC-D6) | Spec-required; E2EE web clients depend on it. The *explicit decision* is where the bytes rest: in `hg-clone-wire` records under the storage service's at-rest encryption, never as plaintext rows |
| Key material lives in ordinary renderer memory the JS heap can reach | **Break** | Non-extractable key bytes go into `hg-crypto`'s secret types outside the JS cage (WC-D3, WC-9). The JS cage's threat model is in-cage corruption; keys outside it are one class harder to lift |
| Operations run wherever the engine's implementation happens to put them | **Break** (as an unrecorded fact) | Operations run on the substrate pool of the key's renderer, and the placement is observable data (WC-D10), not an accident |
| Randomness is ambient and unrecorded | **Break** | Every draw is a recorded B1 input; replay reproduces it (WC-D8). This is B1 applied to the last ambient input the engine specs had left |
| Crypto failures are opaque `OperationError`s | **Break** | The operation is Izcal's own code, so every failure has a reason code in the journal (WC-D10); the *page-visible* error stays exactly what the spec says (P2) |
| The browser keeps a userspace DRBG (NSS-era inheritance) | **Break** | The kernel owns the DRBG; Izcal draws per call (WC-D4). Fewer moving parts, no reseed logic to get wrong, and the record/replay story becomes trivial: record values, not generator state |
| X448 ships because the draft names it | **Break** (staged by evidence) | No engine ships it ([SA 1.7][SA]); Izcal implements it only when corpus or WPT evidence shows use, on the recorded-divergence rule every spec applies to dead surface |

## 5. Lessons learned

| Project | What happened | The lesson | How Izcal applies it (ideas only, M-1) |
|---|---|---|---|
| Netscape SSL RNG (1996) | Keys seeded from clock + PID; ≤ 47 bits; broken in weeks | Userspace-visible state is not entropy; security code needs public design review | Kernel-only entropy, fail closed (WC-D4); every parameter cited to a public standard (lesson 10) |
| Debian OpenSSL (2006–08) | Two deleted lines gutted entropy for 20 months; no detection | Entropy-adjacent code is crypto code; silent degradation is the failure | Startup health check at every launch (6.4); crypto review for any change near entropy (CONTRIBUTING's carve-out scope, 9.5); fail-loud diagnostics (WC-11) |
| Dual_EC_DRBG → Juniper (2007–15) | An unexplained constant entered a standard and outlived its removal | Provenance of constants matters; compliance is not review | Every curve and constant in `hg-crypto` carries a citation; pins are reviewed with `cargo vet`, never adopted because a vendor shipped them ([HP 3.6–3.8][HP]) |
| WebCrypto v1 (2011–17) | Streaming → promises rewrite; optional algorithm set; 5.5 years; engines shipped subsets | API shape costs more than ciphers; an optional core costs a decade of matrices | A generated registry table with every pair implemented or spec-exactly rejected (WC-2); streaming decided deliberately — kept out, spec-exact, with the journal making chunked patterns debuggable (6.10) |
| BoringSSL fork (2014) | 70+ carried patches justified a fork; the fork divided security response forever | Owning a crypto core is a permanent tax — keep it small | One `hg-crypto` for TLS, WireGuard, update verification and the web (WC-D1); small enough for one team to audit (9.3) |
| Heartbleed (2014) | A missing bounds check leaked keys from the most-audited library | Memory safety is a crypto requirement | Rust, tier-P no-panic rules, fuzzed format parsers (WC-14) ([SR 3.1][SR]) |
| ROBOT / Marvin (2017–23) | The 1998 oracle persisted through rewrites | Error-path design, not arithmetic, is what repeats | Single indistinguishable failure paths as a merge gate (WC-4) ([SR 3.7][SR]) |
| PS3 → Biased Nonce Sense → PuTTY (2010–24) | Nonce generation is the most fragile secret in ECDSA | Deterministic hedged nonces; no RNG-dependent nonce | RFC 6979 hedged nonces as NW 6.5's rule, extended to P-384 (6.3) ([SR 3.3, 3.5][SR]) |
| Firefox's verified-crypto deploys (2017–20) | Generated verified arithmetic shipped and was *faster* | Generate or verify; hand-written constant-time code is unauditable at scale | `fiat-crypto`-generated field arithmetic under Izcal's own scalar multiplication; three named verification gates (6.6) ([HP 4.9][HP]) |
| Spectre → WebAuthn (2018–19) | JS-held non-extractable keys stopped being a custody story; hardware moved the credentials | JS-reachable memory is not a key store; the credential boundary is elsewhere | Secret types outside the cage (WC-D3); WebAuthn stays the platform's credential path; WC-D3(b)'s trigger exists for the E2EE gap between them (6.5) ([SR 4.2][SR]) |
| Plugin crypto (1996–2015) | Page crypto lived outside the sandbox; the era died with NPAPI | Trust boundaries must not depend on installed code | Everything inside the renderer's sandbox, on the substrate pool (6.5) ([HP 5.1][HP]) |

New crates: **`hg-webcrypto`** and **`hg-webcrypto-observe`** (L4, tier P), with the tool additions living in NW's existing `hg-crypto-check` (vector runners and constant-time gates are one toolchain, not two). No new process kind, no new thread at rest: operations run on the key's renderer's substrate pool (FP-32 unchanged), which is why the footprint spec's budget table gains one *charged-memory* line and no process row (WC-12).

### 6.2 The registry is generated data (WC-2)

The pinned W3C WebCryptoAPI snapshot's registry — every (algorithm, operation) pair, its supported usages, its parameter dictionary and its error cases — is compiled into a table by the same generator discipline the DOM spec applies to WebIDL (DM-D2's inputs): the table is generated from the pinned spec text, each row carries its `// spec:` anchor, and hand-written name dispatch is rejected by an `ast-grep` rule (G168). "Normalize an algorithm" is one function over that table; `NotSupportedError`, `SyntaxError` and `DataError` come from the table's error column, never from ad-hoc checks. The registry is closed ([SA 1.2][SA]): admitting a new algorithm is a spec-pin bump plus a table regeneration plus this section's process, never a fast path.

The name set is the registry plus one documented non-registry entry kept for de-facto parity: `CHACHA20-POLY1305` (RFC 8439; the primitive exists in `hg-crypto` for TLS already, so the web binding is glue; shipped by Chrome as non-standard [SA 1.8][SA]) and nothing else. SHA-3, AES-SIV and HPKE stay unexposed ([SA 1.9][SA]). The table carries **two columns, implemented and exposed**: WC-2's completeness target is scoped to **exposed** pairs, and exposure follows the registry. **X448 is staged**: the pinned snapshot's registry contains it (the secure curves merged in December 2024, [SA 1.6][SA]), no engine ships it ([SA 1.7][SA]), and `hg-crypto` has no X448 — so its row sits at *not implemented, not exposed*, with the evidence rule of 9.1 governing when it moves; WC-1 treats unexposed algorithms as N/A, never as failures (4.4's dead-surface rule applied to a registry the spec did not write).

### 6.3 Primitives: what the web API adds to `hg-crypto` (WC-D2)

Every row below is implemented from its governing prose and vectors ([SA §2][SA]) under NW-49 (100% Wycheproof/ACVP/RFC vectors, differential fuzzing against two black-box implementations) and, where marked, NW-50 (constant time). "Source" follows NW-D23's split: pinned MIT crates where the resolved tree is clean, Izcal's own code elsewhere, with the same reversal trigger per primitive.

Two structural notes. First, RSA private-key operations are the largest single addition and the reason WC-M2 is sized as it is: blinding, the Montgomery ladder's constant-time audit, and the single-error-path rule for OAEP decryption ([SA 2.11][SA]). Second, AES-CBC decryption joins the constant-time surface not because AES is secret-dependent in a new way but because **padding validity is secret**: the unpad is a constant-time selection and the failure path is one shared `OperationError`, the Lucky13 lesson applied at the API layer ([SA 2.8][SA], [SR 1.5][SR]). The pin additions (`ctr`, `cbc`, `aes-kw`, `pbkdf2`) go through NW's existing licence-and-tree check (each resolved alone with `cargo tree`, no `subtle`); if any fails, Izcal writes that primitive from the SP text, which for these four is small — the NW-D23 reversal trigger, unchanged. AES-CTR arrives **once, not twice**: the ledger's A-NW-5 (media) already routes AES-CTR and `cbcs` into `hg-crypto`, so this spec's amendment names the media row and the pins land in one reconciliation ([LG A-NW-5][LG]).

### 6.4 Entropy: the OS kernel owns the DRBG (WC-D4)

`Entropy::crypto()`'s production implementation per platform ([ER §1][ER], table there):

| Platform | Interface | Fallback |
|---|---|---|
| Linux (x86-64, arm64, riscv64) | `getrandom(2)`, blocking until the kernel's pool is initialized; the vDSO `getrandom` of Linux ≥ 6.11 for bulk draws where present | none — launch blocks, surfaced in diagnostics (WC-11) |
| macOS / iOS-class | `CCRandomGenerateBytes` (the Darwin CCRNG; Apple documents a Fortuna-derived kernel design at a 256-bit target, and the CCRNG's construction is not documented in prose, [ER 1.9][ER]) | none |
| Windows | `ProcessPrng` | none |
| Simulation (`hg-substrate-sim`) | seeded stream (the one place a CSPRNG is seeded, Q-CS-1) | — |

Design rules:

- **No userspace DRBG in the browser.** The kernel maintains the DRBG, its reseeding and its entropy sources; Izcal draws per call. A userspace DRBG would add generator state to protect, reseed logic to test, and a recording problem (state, not values) for no benefit: the draw costs are dominated by the call boundary, and the vDSO path exists precisely for bulk ([ER §1][ER]). The alternative — one seeded process-lifetime DRBG, the pattern the W3C spec's own note describes ([ER 3.6][ER]) — is the written fallback (6.11), taken only if WC-M0's measurement shows per-call draws cost more than 10 µs† p50 with no vDSO path available.
- **Fail closed, loudly.** A failed or unseeded OS interface fails the operation (`OperationError` at the API) and raises a diagnostic; **no code path in any shipping binary falls back to `Math.random`, timestamps, addresses or any non-crypto source for a web-observable crypto output** (G161; WC-7). Linux's `GRND_INSECURE` — a flag whose own reviewer named it to discourage use ([ER 1.4][ER]) — is forbidden by name. A startup health check runs at every launch (the interface answers; a draw of fixed size succeeds), because entropy handling is load-bearing and its changes need adversarial review — the Debian lesson ([HP §3][HP], [SR 3.2][SR]): every documented catastrophe in this class is a fallback or a custom generator.
- **One draw-point per process, in `hg-substrate-os`, at which recording attaches.** Bulk draws loop over the interface's safe sizes (≤ 256-byte uninterruptible reads on Linux, [ER 1.1–1.2][ER]). The draw-point, not the syscall, is the recording seam — deliberately, because the vDSO path is invisible to strace and seccomp and glibc uses it transparently since November 2024 ([ER 1.6, 6.2][ER]): Izcal records what the page observed, so the recorder survives interface changes underneath it.
- **Restore is a reseed event.** Izcal's renderers are forked or spawned, never snapshot-restored, so the classic identical-stream hazard does not arise in the normal path; the kernel's fork-aware interfaces (getrandom's semantics, the vDSO's `VM_WIPEONFORK` state pages, arc4random's fork reseed) are the load-bearing safety ([ER 5.1, 5.5][ER]). Any future checkpoint/restore feature must treat restore as a reseed-worthy event, mirroring what VMGenID does for guests ([ER 5.2–5.3][ER]) — a rule stated now so the feature inherits it (Q-WC-6).
- **`getRandomValues` draws directly from `Entropy::crypto()`** with the spec's 65 536-byte cap — a compatibility number the spec states without rationale; implemented exactly and explained in one sentence ([ER 4.1–4.2][ER]). Integer typed arrays only, filled in place; `crypto.randomUUID` is RFC 4122 version 4 from 16 bytes of the same source ([ER 4.3][ER]).
- **riscv64** uses the same `getrandom` interface; the RISC-V `Zkr` entropy CSR is ratified but its kernel use is immature (Medium/Low; [ER 2.5][ER]), and hardware entropy handling is kernel business in any case — the OS-interface rule (M-1 part 1). Cold-start blocking on entropy-thin embedded riscv64 is treated as a normal startup condition, surfaced, never engineered around ([ER §2][ER]).
- **`Math.random` is untouched**: the JS spec's per-realm B1 stream (JS §6.9) and the CSPRNG share no state, and a lint (G161's second clause) rejects any code path that couples them. ECMA-262's only requirement — distinct sequences per realm — is the JS spec's to meet ([ER 4.5][ER]).

### 6.5 The key model: custody without a new process (WC-D3, WC-D6)

**Where operations run.** Placement is defined by the **invoking agent**: a `SubtleCrypto` operation runs on the substrate's fork/join pool of the renderer that hosts the invoking agent (DM-D8's process for documents and dedicated workers; the worker's own renderer for shared and service workers, which DM-D8 places by the worker's (origin, container) key and which may outlive the creating page). The synchronous `getRandomValues` and `randomUUID` draw inline on the invoking thread — the script thread included — which is exactly why WC-6 bounds their overhead. Queued operations never run on the script thread, so bulk AES never blocks a task (G165). Same-agent promise ordering is preserved at resolution points, which is the only ordering the spec gives. RSA key generation (prime search, seconds-scale) is a pool job with a budget; a cancelled page's job is abandoned at the next check point. **Worklets are out**: `Crypto` is exposed `(Window, Worker)` in the pinned IDL and worklet global scopes inherit neither, so `subtle`, `getRandomValues` and `randomUUID` are absent from worklet scopes — a recorded compatibility fact, watched by a use counter in case the platform extends it, and the reason the AudioWorklet real-time-thread question (JS 6.12) never meets a blocking draw.

**Where key bytes live.** In `hg-crypto`'s secret types, outside the JS cage, in a **per-process key table** — each process that receives a cloned key holds its own secret-type entry with a custody record naming the owning (origin, container) — and zeroized when the key object is collected, including in a worker renderer that outlives the creating page ([NW §6.5][NW]). A `CryptoKey` object in script holds an ID plus metadata; the bytes are reachable only through `hg-webcrypto`'s operation entry points. The heap verifier asserts at GC-safe points in test builds that no cage-resident byte sequence equals a live key's material (WC-9).

**Extraction.** `exportKey` on a non-extractable key is `InvalidAccessError` before any byte is touched (the check is on metadata, so there is nothing to leak); on an extractable key it produces exactly the requested format and no more. `wrapKey` composes export + encrypt per spec; the AES-KW path never wraps non-key payloads with a web-reachable shortcut ([SA 2.9][SA]).

**Structured clone and workers.** `CryptoKey` rides `hg-clone-wire` (DM-D12) as new record kinds carrying the algorithm metadata plus the key bytes for extractable keys and for non-extractable keys too — cloning a non-extractable key is legal (postMessage to a worker, IndexedDB persistence), only *export to script* is forbidden ([SA 1.4][SA], [SA §4][SA]). The REC's structured clone of a `CryptoKey` carries an internal handle, not bytes ([FC 4][FC]); **carrying the bytes in the wire record is Izcal's design decision**, taken because the receiving process must be able to use the key without a round trip to the creator — a decision WC-D6's custody rules exist to make safe, and one the DM-D12 amendment owns as Izcal's. **The record kinds are accepted by exactly two sink classes** — agent messages (`postMessage`, `MessagePort`, `BroadcastChannel`, transient) and IndexedDB (persistent, under 6.5's storage rules) — and the **history and Navigation API state sink refuses them** at the generated binding, because that sink persists in the broker (DM-D12's opaque bytes), which would make the broker a key custodian — the co-location WC-D3(c) rejects. The refusal is a recorded spec divergence in the DM-D12 amendment (9.5). Within a process the clone is a handle move plus a new per-process key-table entry; across processes it is a B2 message whose payload is the wire record, one hop, same origin by the agent-cluster key (DM-D6). The format module for `spki`/`pkcs8`/`jwk` is the one DER-subset parser in the renderer (G167): definite lengths only, canonical encodings, unpadded base64url, `key_ops`/`usages` consistency enforced as the spec's table says ([SA 4.1–4.5][SA]); it is fuzzed with the Wycheproof ASN.1 cases and a grammar-derived corpus (WC-14).

**Storage posture — the explicit decision.** Key material reaches persistent web-exposed storage exactly one way: as part of a `CryptoKey` clone-wire record persisted by IndexedDB. The custody rule is that **no cross-site process ever holds plaintext key material**: the partition service (the (top-level site, container) tier that already holds the container's first-party cookie jar, NW 6.16) holds the partition's at-rest seal key and performs every seal and unseal — a key-bearing record is sealed before it reaches the storage service and unsealed only for delivery to a renderer of its own partition — so the cross-site storage service and the broker store and relay only ciphertext. The storage service stores and serves only ciphertext, never sees plaintext key material, and never indexes or logs the records. This is the explicit decision the brief demands: the feature exists because P2 requires it (E2EE clients persist identity keys through IndexedDB), the bytes never ride a plaintext path outside the partition tier, and the recording boundary excludes them (G162). Until the storage spec's (G-19, in progress) interface confirms the seal/unseal split, the IndexedDB `CryptoKey` path does not ship (9.1). `localStorage` cannot hold keys (strings only), the history and Navigation API state sink refuses key records (above), and no other storage surface accepts them.

**Placement alternatives** (WC-D3):

| Option | Verdict | Reason |
|---|---|---|
| (a) In-renderer, bytes in secret types outside the cage | **Chosen** | The page's authority already includes its keys' operations, so a renderer attacker gains no *online* capability from a crypto service; the remaining delta is offline exfiltration of non-extractable bytes, which the secret-type placement, the cage exclusion and the storage encryption bound. No IPC on the hot path (P4), no new process kind (FP-1), no new threat-model entry |
| (b) A per-(site, container) crypto/key service | Rejected, with a written trigger | Cost: a new process kind per site (≈ 2–4 MiB† and ≥ 1 thread each, FP-1/FP-32 rows), an IPC hop and payload copy per operation (bulk AEAD halves, measured at WC-M0), a new threat-model entry — against a delta limited to lifting non-extractable key bytes past the mitigations of (a). **Trigger:** measured in-the-wild exploitation that defeats (a)'s placements, or an owner decision that E2EE-class key custody is P1; Section 9.5 carries the pre-written amendment |
| (c) The broker as key custodian | Rejected outright | Co-locates cross-site key material in one address space: P1 |
| (d) Platform keystore integration (Keychain/CNG) | Out of scope | That is the WebAuthn/passkey boundary, not this spec's; a future credential spec amends this one |

**Why (a) does not go further, stated plainly.** The history's lesson — "JS-reachable memory is not a key store" ([HP §7, lesson 8][HP]) — points further than (a) does, and the difference is deliberate. A page's WebCrypto keys protect data the page already has: whatever the keys decrypt, the page renders, stores and transmits, so a renderer attacker who lifts key bytes gains offline persistence of an authority the page exercised online anyway. The credentials that must survive renderer compromise — passwords, passkeys, payment instruments — are exactly the ones the platform moved to WebAuthn's hardware boundary and the credential stores, not to `SubtleCrypto` ([HP 5.3][HP], [SR 4.2][SR]). Between those two sits the E2EE-in-a-tab case (an identity private key persisted for months), which is the one place the delta is real; it is what WC-9, the storage encryption decision (WC-D6) and WC-D3(b)'s trigger are for, and an owner who judges that case P1 moves to the service with the pre-written amendment in hand.

**Side-channel posture of (a), stated exactly.** In-renderer crypto has a same-process attacker co-tenant, in two distinct senses. **Same-thread interleaving is impossible**: an operation is one pool job, and the script thread's timers and callbacks cannot run inside it (G164's no-script rule and the substrate's job model). **Cross-thread co-tenancy is real and is not waved away**: the fork/join pool concurrently runs style, layout, paint preparation and off-thread parsing or compilation of attacker-supplied inputs (Stage 1 3.1, 3.3; JS 6.3), so hostile-influenced engine work shares the process's cores, L3 and SMT siblings with a seconds-scale RSA operation for its whole duration. What bounds that channel is the constant-time discipline itself (6.6), site isolation (the co-tenant is the same site's own work), and the cage exclusion (secret types live outside the JS cage) — not scheduling. The residual shared-cache/SMT risk is named here, carried in Section 10's risk table, and reviewed at each NW-52 audit ([SR §2, §4][SR]).

### 6.6 Constant time: the surface and its verification (WC-3, WC-4)

The secret-dependent list NW-50 names grows by the WC-D2 rows: RSA-OAEP decryption and both RSA signing schemes (blinded), ECDSA P-384 signing, ECDH P-384, Ed25519 signing, AES-CBC decryption's unpad, AES-KW's integrity check, PBKDF2's HMAC over the password, and X25519's all-zero check — already inside NW-50's verified X25519 — gains its error-path indistinguishability cases ([SR 1.8][SR]). The method is NW-50's, and it is **three gates with their promise levels named** ([SR 2.10][SR]): constant-time-by-construction arithmetic where the proof exists (`fiat-crypto`'s generated field arithmetic — proofs attach to the generated form, and this spec claims nothing about compiler output beyond what the binary gates check, the honesty Fiat-Crypto's own prose models [SR 2.7][SR]); a binary-level taint check (the ctgrind class) as the cheap per-merge gate; and Welch's t-test statistical timing as hardware-in-the-loop regression that is *qualitative* — passing it is not a proof, and its false-positive modes are triaged, not silenced ([SR 2.3, 2.9][SR]). The taint check runs on **x86-64, arm64 and riscv64** builds (the owner's 19 October 2026 ISA decision), and both gates run on **every shipped binary flavor that links `hg-crypto` into a content-facing process** — per OS and per build profile in the renderer tier, as well as the network-service binaries — because link-time optimization can change codegen, so per-binary verification is the honest form; `hg-crypto` is compiled with cross-crate LTO into it pinned off in the profiles where the flavor matrix is not enumerated, and the flavor list is a checked-in fact the gates iterate. The in-process attacker (hostile script sharing the renderer) is the strongest co-tenant the discipline must survive ([SR §4][SR]). RSA private-key operations use blinding drawn from `Entropy::crypto()` — which is also what makes recorded replays of RSA signatures bit-identical (6.7). Error-path indistinguishability (WC-4) is its own target because vectors do not test it: OAEP decrypt, CBC unpad, KW unwrap and X25519's rejection share one completion path with a randomized dummy path where the computation's shape would otherwise disclose the failure — the Bleichenbacher/Manger class is a *failure-path design flaw* that rewrites keep re-introducing (ROBOT found it live twenty years on), and only a designed single path fixes it ([SA 2.11][SA], [SR 1.2, 3.7][SR]).

### 6.7 Recording and replay: randomness is drawn values (WC-D8)

Every random byte a web-crypto operation consumes or produces is a **drawn value on the recording** — in one of two sensitivity classes, because the two classes have different blast radius ([SR 6.4][SR]):

- **Page-visible draws** — `getRandomValues` returns, `randomUUID`s — are ordinary recorded values: page content under the recording's existing rules (off by default, user-initiated, encrypted at rest, redactable on export).
- **Internal draws** — OAEP seeds, PSS salts, RSA blinding factors, hedged ECDSA nonce randomness, key-generation randomness — are recorded as **sensitive-class drawn values**: they live only inside the encrypted-at-rest recording (REC-R2), never in plaintext logs, never in `hg-export`'s outputs, and `hg-redact` treats them as credential-class. The reason is SR 6.4's inversion: a recorded internal draw plus a public signature is nonce-recovery material — the recording would be a **key-recovery archive** if kept carelessly. Recording them is still right, because the alternative — replaying signatures that differ from the recorded ones — breaks the bit-identical guarantee every other spec's replay relies on; NW §6.16 already records a sensitive draw class this way (stateless-reset tokens).

The precise invariant (G162): **engine-held** key material and derived keys are never recorded; key material the page itself exposed (a `getRandomValues` draw later imported, `exportKey` output) is page content under the recording's existing rules, because refusing to record it would break replay of legal pages.

**Scope: which agents' crypto is on the recording.** Documents and **dedicated workers** run inside the recorded renderers (DM-D8), and their draws and operations are recorded as above. **Service and shared workers run outside the dedicated processes, are recorded as IPC inputs, and are not replayed** — DT-D2's existing rule, which this spec adopts unchanged rather than amending: their crypto appears in the recording as the IPC-visible results, their entropy draws are not drawn values on the tab's recording, and WC-8's bit-identical claim is scoped accordingly. Replaying worker-side crypto is a pre-written DT-D2 amendment away (9.5, conditional row) if the DevTools owner later wants it.

**Persisted keys.** A key restored from IndexedDB — the E2EE identity-key case — enters a replay through its **sealed record**, which is ciphertext and therefore recordable under G162: the recording carries the sealed bytes as the value read, the replay host unseals with the partition's at-rest key it already holds at REC-R2 class, and a digest of the record verifies the replay used the same stored key. A key created inside the recording replays from its recorded creation draws. Either way no plaintext key material enters the recording.

What is never recorded: any engine-held key material, any derived key, any PBKDF2 output (a `deriveKey` result used as an AES key is a secret; the record carries the operation and its inputs' metadata, and replay re-executes the derivation from the recorded inputs — deterministic by construction, since HKDF and PBKDF2 are). The rule's two halves, mechanically:

- **Recorded replay never re-derives randomness from recorded inputs.** The replay host runs **under the simulation substrate**, and the recording's draw log is consumed as `hg-substrate-sim`'s `Entropy::crypto()` input — drawn values, never a seed, which keeps Q-CS-1 intact: the seeded CSPRNG exists only under the simulator, and the replay host is a simulator process (no network, no storage device, no GPU). A replay that reaches for entropy beyond the recorded log is a divergence, detected like any other (the channel's consumption is asserted, WC-8).
- **Random outputs are recorded session data.** No *seed* ever exists to record — in production there is none ([NW §6.16][NW], Q-CS-1) — and the simulation's seeded generator exists only under `hg-substrate-sim`, which is also what the interleaving explorer (DT §6.1) re-seeds: the seed is a simulation input, never a production one.

Consequence worth stating: a replayed page sees bit-identical `getRandomValues` sequences. That is the point — reproducibility — and the known trade ([GO 2.3–2.4][GO]): uniqueness-dependent code paths observe the same values the original run observed. The **fresh-randomness replay mode is a simulation-only fault-injection mode** (re-run under a new seed within the orders HTML permits), never a production replay behaviour.

### 6.8 Post-quantum direction: an oracle now, a surface later (WC-D9)

The prose base is complete: FIPS 203 (ML-KEM, 13 August 2024), SP 800-227 (KEM usage, final 18 September 2025), and RFC 10024 (X25519MLKEM768 and companions, August 2026) ([SA §3][SA]). The W3C registry has no ML-KEM entry and no engine exposes one; every deployed web ML-KEM byte is inside TLS ([SA 1.10, 3.7][SA]). Decisions:

1. **No post-quantum algorithm in the web API in Stage 1.** There is no registry entry, no interop partner among browsers, and P2 says Izcal does not invent permanent surface to preview standards. The incubation exists and is watched: the WICG *Modern Algorithms in the Web Cryptography API* Draft CG Report (14 September 2026) already drafts the `encapsulateKey`/`decapsulateKey` shape with ML-KEM, ML-DSA and SLH-DSA ([GO 6.2][GO]) — when that matures toward the registry, Izcal's exposure decision anchors to it rather than inventing a shape. The `hg-crypto` SPI is shaped so an ML-KEM binding is additive whenever that day comes.
2. **A from-prose ML-KEM reference implementation exists as a test-only differential oracle** (WC-M2, WC-15), built from FIPS 203's text only, passing the FIPS KATs and ACVP's decapsulation-failure vectors, and fuzzed differentially against the pinned `ml-kem` crate that NW-D23 trusts for TLS. The pin's own documentation states the crate **has never been independently audited** ([SR 5.5][SR]) — which is exactly why the oracle is not optional: it is the independent check that exists until NW-52's audit covers the pin, and if the pin ever fails review, the oracle is the seed of Izcal's own implementation. Its implicit-rejection path is also the constant-time case study for the no-error-path rule ([SA 3.3][SA]).
3. **The spike's deliverable is a decision memo, not an API**: constant-time decapsulation evidence, implicit-rejection test results, audit-status disclosure for every cryptography crate Izcal pins (the ml-kem lesson, [SR 5.5][SR]), and the API-shape cost against the WICG draft. Web exposure then follows the registry path (P2), or an owner decision if Izcal chooses to lead — with the no-error-path rule as the line no Izcal PQ binding crosses ([SA 3.3][SA]).

### 6.9 The permission and policy surface: none, with receipts (WC-D7)

`SubtleCrypto` is `[SecureContext]`; keys are same-origin by construction; no operation grants a capability the origin does not already have. **No permission prompt, no enterprise policy, no cross-origin-isolation requirement** in v1. The web's own threat model for `getRandomValues` is unguessable bytes, not identity: the W3C text makes no fingerprinting claim for it, and the fingerprinting literature the gaps strand surveyed studies canvas, WebGL, fonts and audio — none of it studies RNG output, an absence-of-evidence finding graded Low ([GO 3.4][GO]). What Izcal adds instead is *visibility*: the crypto journal flags per-operation policy-relevant facts — PBKDF2 below 600 000† iterations, GCM tags below 96 bits, SHA-1 digests — as DevTools warnings and use counters, never as rejections (P2; the floors are advisory † values from current guidance, [SA 2.4, 2.6][SA]). An origin that needs to *forbid* crypto (a kiosk profile) is a content-blocking-class policy, not a permission.

### 6.10 Observability: the `crypto` IIP domain (WC-D10)

`hg-webcrypto-observe` emits the domain's records (experimental tier per DT-D1's stability ladder), read by `hg-inspect-renderer`. Each record type carries a **DM-D18 cost class**, because the classes decide what is always paid for: **Operation**, **Error reason** and **Warning** are DevTools-attached journals (with the Operation outcome also in the recording class, which is what backs WC-10's recorded-session clause); **Key inventory** and **Draw** are counters-class (always computed, one increment per event, no per-event records unless DevTools is attached), and WC-12 counts their always-on cost:

| Record | Content |
|---|---|
| **Operation** | Normalized algorithm, operation, key ID (opaque), extractable, usages, input/output byte counts, pool job duration, outcome (ok / error class / reason code), agent and thread, execution point, `caused_by` |
| **Key inventory** | Per live key: ID, algorithm, extractable, usages, creating script position and task, persisted-to (IndexedDB record reference) or not |
| **Draw** | Per entropy draw by page-reachable API: byte count (values are page content; the *fact* of draws and their sizes is metadata) |
| **Warning** | Policy floors (6.9), non-standard algorithm use, weak-parameter use |
| **Error reason** | The journal's plain-language reason for every `DataError`/`OperationError`: which normalization step failed, which format check, which consistency rule ([GO §1, §4][GO]) |

The boundary is structural, not promissory: the domain's types carry **no field that can hold key bytes or derived secrets** — the same discipline as DT G11's `Redacted<T>`, applied by construction (G166). The DevTools **security panel** gains a "Web crypto" section listing the key inventory and warnings; the console surfaces the reason codes on failures. This is the observability no current engine ships ([GO §1][GO]) and the one place Izcal's from-scratch crypto code pays a UX dividend: because every check is Izcal's own anchored step, every failure has a name.

## 7. M-1 compliance

**Built new (Izcal's own, anchored).** The `SubtleCrypto`/`Crypto` surface (bindings in `hg-webapi` per the DOM spec's web-API track; semantics, normalization, key model and formats in `hg-webcrypto`, every function anchored to the pinned W3C snapshot); the SPKI/PKCS8/JWK codecs from RFC 5280/5958/5208/7517/7518; RSA private-key operations, P-384 ECDH and ECDSA signing, Ed25519 signing on `fiat-crypto`'s generated field arithmetic; the ML-KEM test-only reference from FIPS 203. No third-party engine or library code is read, linked or translated (M-1 parts 1 and 3); other engines are black-box differential signals only.

**The sanctioned secret-type boundary.** NW 6.5's secret types forbid `Debug`, `Clone` and serialization; this spec's key model needs exactly two byte-moving operations (the clone-wire writer and the export/wrap codecs), so the NW amendment (9.5) adds one named, audited capability — `expose_bytes(sink)`, admissible only at those two call sites, with a lint rejecting any other consumer. Without it, `hg-webcrypto` would quietly violate NW's rule; with it, the rule's intent (no casual copying) survives and the two legitimate paths are reviewable.

**Pinned MIT dependencies (extend NW's table, owner decision class (a)).** `ctr`, `cbc`, `aes-kw`, `pbkdf2` (RustCrypto, MIT OR Apache-2.0), each resolved alone with no `subtle` before pinning, exactly as NW 6.5's table was checked; all are generic cryptography primitives, the one class M-1 part 1 allows. Everything else this spec needs already exists in `hg-crypto`'s pin set.

**Anchors.** The registry table is generated from the pinned W3C snapshot with per-row anchors (ANC-1); every hand-written algorithm carries `// spec:` anchors to the W3C sections or the NIST/RFC texts; `hg-anchor` covers `hg-webcrypto` (G169 puts it in G9's list). Oracles: the pinned W3C WebCryptoAPI suite (WPT), Wycheproof, ACVP, RFC vectors, the differential-fuzzing rule of NW-49, and two black-box implementations per primitive as test-only peers (M-1 part 4).

**Evidence discipline.** Standards prose (W3C, NIST SP/FIPS, RFCs, IETF datatracker), papers, published audits and vendor status pages are the evidence classes used throughout ([SA][SA], [HP][HP], [ER][ER], [SR][SR]); no repository code file was opened; crates.io and licence pages were read for status and licence facts only. Values marked † are set from first principles by this document.

## 11. Open questions and flagged claims

### 11.1 Open questions

- **Q-WC-1.** When will the W3C registry admit ML-KEM (and ML-DSA), and with what parameter sets? The WICG *modern-algos* CG Report drafts the `encapsulateKey` shape ([GO 6.2][GO]); watched at each pin bump; exposure follows the registry path or an owner decision (WC-D9).
- **Q-WC-2.** The storage spec's seal/unseal interface for clone-wire records carrying key material — owned by G-19's spec; this spec's requirement (sealed before leaving the renderer's trust tier; the storage service holds only ciphertext) is stated in Section 9.5, the IndexedDB path gates on it, and the wording is coordinated with the G-19 owner before WC-M3.
- **Q-WC-3.** Do corpus measurements ever justify X448? Reviewed at each corpus refresh against the dead-surface rule.
- **Q-WC-4.** The entropy floors for DevTools warnings (PBKDF2 600 000† iterations, GCM tag 96 bits†) are advisory † values; confirm or adjust at WC-M4 with the use-counter data.
- **Q-WC-5.** Windows `ProcessPrng` availability on the oldest Windows Izcal targets: confirm at WC-M0; `BCryptGenRandom` with the system-preferred flag is the documented fallback on the same platform class ([ER §1][ER]).
- **Q-WC-6.** The reseed-on-restore rule (6.4) binds any future checkpoint/restore feature; owned jointly with the substrate and footprint specs when such a feature is proposed.

### 11.2 Claims that are single-source, unverified or conflicting

- Chrome's SubtleCrypto `CHACHA20-POLY1305` is documented on MDN as Chrome-only and non-standard ([SA 1.8][SA], Medium): no first-party release-note source was found; the name's compat value is asserted from MDN's documentation.
- The claim that all three engines' SubtleCrypto operations run off the main thread is folklore-grade (no primary source was found in any strand); this spec never relies on it (WC-D10 makes placement observable data).
- The vDSO `getrandom` bulk-draw benefit on Linux ≥ 6.11 is from kernel documentation and release notes ([ER §1][ER]); no independent benchmark was found (Medium).
- PBKDF2's 600 000-iteration floor is OWASP's current guidance, not a NIST number ([SA 2.4][SA]); it is used only as an advisory warning threshold (Q-WC-4).
- The per-site service cost estimate in WC-D3(b) (≈ 2–4 MiB†, ≥ 1 thread) is derived from the footprint spec's process-kind rows, not measured; the WC-M0 spike measures the IPC side, and the memory figure stays an estimate until a service is actually proposed.
- The 27–42-month† duration is a placeholder derived from NW 9.3's milestone months, not a measured velocity; the WC-M1 review replaces it (9.3).
- The partition-tier seal design (WC-D6) assumes the partition service is an acceptable holder of the at-rest seal key because it already holds the container's first-party cookie jar (NW 6.16); the security scope's owner should confirm that granularity reading (A-SEC rows are on an unmerged branch).
