Six web APIs let a page talk to hardware: **WebUSB**, **WebHID**, **Web Serial**, **Web MIDI**, **Web Bluetooth** and **Web NFC**. Every one of them is a direct path from page script to an operating-system device interface, and every one is implemented default-on today by one engine family (MIDI and Serial also ship behind an add-on in Firefox), under its own permission model, with its own choice of what a "device" is and when a grant persists. No Izcal document owns any of them: the DOM spec's API table has no device row, the security scope's 36-kind process map has no device service, the Stage 1 feature table has no device track, and the extensions spec's Ring C does not even name the six. The corpus has a rule for exactly this situation — the DOM spec's 6.18 sends every unclaimed web API to the amendment ledger as a gap before admission — and the ledger has no row for devices. This specification names that gap **G-26**, owns the six APIs, and closes it.

The central idea is **one device-access boundary, not six stacks**. A page does not reach a device; it holds a typed, broker-minted handle to a sandboxed **device-access service**, which exists as one process kind in two roles. The **arbiter** role is the only process in the browser allowed to call an OS device interface: it opens devices, asks the OS to pair or claim, holds every handle and file descriptor, and proxies bytes. The **session** role is per (frame site, container, device family): it parses descriptor and protocol bytes, enforces the API's semantics, and holds no OS handle at all. The broker mints a **device-access ticket** — a signed, expiring, capability-scoped token — for every open and every session, the way it mints a Local Network Access ticket for a socket (NW-D4), with one difference the design explains: the issuer and the verifier are different processes, so the ticket is signed rather than MACed. All device parsing is Izcal's own, in tier-P crates, written from specification prose and fuzzed: USB descriptors, HID report descriptors, ATT/L2CAP and GATT, NDEF, and the MIDI 1.0 wire format. Device I/O is external nondeterministic input, so device sessions record at the device-service boundary, in the shape DT-D2 already uses for renderers and NW-D2 for networks, and a replay feeds a virtual device and never opens real hardware.

The decisions that matter most:

1. **One process kind with two roles** (DV-D1): `hg-device-main` as `arbiter` (one per profile, the only OS device caller) and `session` (one per frame site, container and family). This amends the security scope's 36-kind map to 37 kinds and its 38 threat-model files to 39, with one model, `device-access.md`, covering all three configurations.
2. **Broker-signed device-access tickets** (DV-D2): the broker is the only minter; the arbiter is the only verifier; every open, transfer and configuration change carries a ticket bound to the frame origin, top-level site, container, family, device identity digest, capability set and signed scope.
3. **The OS stack is the interface for every family, Bluetooth included** (DV-D3): IOUSBHost, WinUSB/WinRT, usbfs and UsbManager for USB; IOHIDManager, HIDClass, hidraw for HID; termios/COM/SerialDevice for serial; CoreMIDI, Windows MIDI Services/WinMM, ALSA rawmidi, `android.media.midi` for MIDI; CoreBluetooth, WinRT GATT, BlueZ D-Bus, `BluetoothGatt` for Bluetooth; `NfcAdapter` for NFC. Izcal writes no HCI controller stack; the evidence for that call is in 6.7. Every parser above the interface is Izcal's.
4. **One permission model over the shell's prompt layer** (DV-D4, DV-D5): a grant is per (frame origin, top-level site, container, family, device identity digest), decided by a broker-owned chooser, recorded in the prompt ledger; `device-pairing`, `device-connection` and `device-write` are high-risk prompt classes under CON-R1 to CON-R5 and A-SH-12. Handles are per-(origin, container, device) pseudonyms; hardware serial numbers and tag UIDs are hidden unless a separate, off-by-default *expose hardware identifiers* grant is given.
5. **Device sessions record as input logs and replay virtually** (DV-D7, DV-D8): descriptors, transfers, reports, bytes, chunk boundaries, receipt times, page calls, grant and adapter decisions and typed errors are recorded; NFC tag payloads are credential-class and never recorded by default; a replay provably opens no device.
6. **Exposure follows the corpus's two-engine admission rule, applied as written** (DV-D9): no API gets general exposure in Stage 1. Web MIDI has no recorded WG resolution and only one default-on engine; Web Serial is a WHATWG standard but has only one default-on engine; all six are built and fuzzed; the five desktop-capable APIs sit behind an off-by-default, per-origin developer setting, with MIDI and Serial the first owner-exception candidates (DV-E5, DV-E6), and Web NFC is Android-only, built but not exposed, and ships only when Android support exists.
7. **The unowned-surface gap closes** (9.5): G-26 is named in the ledger, the six APIs enter the DOM spec's 6.18 table, the security scope's 3.5 gap table and process map gain their device rows, and the extensions Ring C gains the device namespaces as refused.

The cost is **23–31 engineers†** at peak, **70–110 engineer-years†** across DV-M0–DV-M5 as the team ramps from a Stage 1 device share of **9–13†** engineers inside the 59.5–84.5† Stage 1 team; the format parsers and a virtual-device oracle are the long pole, not the OS backends. Device access is the last major web platform surface Izcal owns, and the one where the difference between a browser that ships it and a browser that refuses it is measured in whether a person can flash a microcontroller, configure a keyboard, read a sensor or write a tag without installing another browser.

## 1. The problem and who has it

| User | Task, in their words | What fails today |
|---|---|---|
| **People with hardware** | "Flash this board, configure this keyboard, open my wallet, play this synth, read this sensor, write this tag" | Each task is confined to a browser family or a platform: ESP Web Tools and Trezor Suite work only in Chromium desktops; VIA is Chromium-desktop only; Web NFC is Android Chrome only; iOS users install Bluefy or a native bridge ([DV-G 1.1–1.8][DVG]); Firefox ships Serial and MIDI only behind a per-site add-on, and Safari ships none of the six ([DV-G 2.2–2.3, 2.5][DVG]) |
| **People who value privacy** | "A site should not learn what I own, or recognise me across sites by my devices" | Persisted grants silently re-expose devices on later visits ([DV-X 4.2–4.3][DVX]); Web MIDI lists every port and can identify a rig ([DV-X 4.9][DVX]); WebUSB exposes VID/PID/serial and Web NFC exposes a tag UID ([DV-F 1.1–1.6][DVF]); only Web Bluetooth even suggests per-origin IDs, and it does not require them ([DV-S 3.4][DVS]) |
| **Web developers** | "Let me test this without hardware, and show me what the device actually sent" | No stable browser has a scriptable virtual device; Chrome's Bluetooth fake is test-only and not in stable builds; Web Serial tests are manual and need hardware; no DevTools domain for USB, HID, Serial, MIDI, Bluetooth or NFC exists ([DV-G 3.1–3.6][DVG]; [DV-R 4.6–4.15][DVR]) |
| **Izcal's engineers and agents** | "One boundary to review, one parser to fuzz, one recording to replay" | Six APIs in Chromium mean six Chromium-side stacks, six permission stores and six test fakes, each with its own history of use-after-free, policy bypass and protected-class escape ([DV-X 3.2–3.4][DVX]; [DV-X 7.5][DVX]) |
| **Enterprise and education administrators** | "Allow this lab's boards on this site, block everything else, and show me what happened" | Current policy is per API, per vendor identity, with silent pre-grant allowed and no cross-API device principal ([DV-X 4.7][DVX], [DV-X 7.9][DVX]) |
| **Agents acting for a person** | "Use the device I am looking at, for this task, with my approval" | No device API has an agent model; a compromised agent or extension would inherit an ambient device grant if one were added naively ([DV-G 4.8][DVG]) |

**What Izcal's specs already decide** (full list with IDs in [H2][H2], [H3][H3] and [SS][SS]):

- **[M-1][H2] (2.3.2).** Izcal writes its own engine components; shipped code and data are MIT; standards-body data, test-only inputs, and OS interfaces are the named exceptions. No third-party project's source code is evidence (M-1 part 3, 2.3.3): this spec and its notes cite specification prose, OS documentation, registry data and black-box observation only.
- **[I-2][H2].** "A compromised renderer must not be able to open files, sockets, devices, PCIe config space or GPU MMIO. Everything goes through IPC to a broker." The one recorded exception is a broker-granted video-only device in the hardware-decode process (MD-D10). Device access therefore belongs in a broker-side service and nowhere else.
- **[P1, P2, P6][H2] and [I-1][H2].** Per-(site, container) processes and state; no ambient authority; isolation is a first-class budget, not an optimisation; privacy is a product property, not a setting.
- **[B1, B2, B9, B10, DET-1, DET-2][H3].** Engine code reaches the outside world only through the substrate; IPC is typed and generated; agents act through typed intents and person-present grants; AI off means not launched; nondeterminism enters only as recorded input.
- **[CON-R1 to CON-R5, A-SH-12][SS].** The broker decides that a user approved, on broker-observed OS input, against a broker-owned prompt template, after 500 ms† of visible and unoccluded time; security prompts are drawn by a jitless prompt renderer in a broker-owned window; the content GPU is never on the prompt pixel path; a high-risk AT-invoked approval needs person-present evidence, and until AX-D11 implements it the AT action only moves focus.
- **[DT-D2][DT] and [NW-D2][NW].** A recorded session starts at process launch in fresh dedicated processes, records inputs at the lowest boundary that holds no secret, never records credential-class values, and marks a replay "approximate from that point" after a placeholder. Replay never re-opens a socket (NW-37's dedicated replay host holds no network service).
- **[ST-D18 as applied by LY-D10][ST].** An editor's-draft feature is admitted when it has a WG resolution and WPT tests and either ships in two engines or is an Interop focus area; data structures are built general from the first milestone. This is the rule DV-D9 applies to the six APIs.
- **[SEC-24][SS] and [FP-1, FP-22][FP].** Device and descriptor parsers are Tier-1 fuzz targets for the pre-release audit; the browser's idle baseline is ≤ 64 MiB†; every feature is gated on an absolute energy measurement, not a comparison with another browser.
- **[G9][S1] and [CS][CS].** Every crate carries a `// spec:` anchor at a pinned revision; `tools/tiers.toml` is the normative tier list; new crate rules take the next free G-range (this spec registers **G210–G219**).

**Success** is measured by Section 8: zero device interfaces reachable from a renderer or a session; zero forged tickets accepted; zero parser panics or crashes reachable from device bytes; zero grants to protected classes; zero devices visible before a grant; a replay that opens zero real devices; a recorded session that replays to the end with every output digest matching; and a device service that is absent when no device API is in use.

## 2. History: what came before and why it was built that way

The six APIs were not designed together. They were proposed over seven years (2012–2019), shipped by one engine over six years (2015–2021), and standardized across four venues (W3C Audio WG, W3C Community Groups, WICG, and finally WHATWG). Their common shape — a user-chosen device, an origin-bound grant, a transport-specific API — is the residue of what survived, not a design anyone chose up front. The history matters because the failures are the requirements: every element of Section 6 is a response to a dated incident or a decade-long non-implementation.

### 2.1 Before the APIs: plug-ins, then a privileged app platform

The web's first device path was native code in the page: Java applets and NPAPI plug-ins (1995) and ActiveX (1996), carrying both the driver knowledge and the user's trust; the applet and ActiveX years are commonly given and were not checked against primary sources in this pass ([DV-H 1.1][DVH]). Chrome killed that path deliberately. Its 2013 announcement called NPAPI's "90s-era architecture … a leading cause of hangs, crashes, security incidents, and code complexity"; only six plug-ins were used by more than 5% of users, and the largest, Silverlight, by 15% ([DV-H 1.2–1.3][DVH]). NPAPI was blocked by default from January 2014 and removed with Chrome 45 in September 2015 ([DV-H 1.4][DVH]). The replacement was not a web API but a privileged app platform: Chrome Apps (2013) exposed `chrome.usb`, `chrome.serial`, `chrome.hid` and `chrome.bluetooth` inside packaged apps ([DV-H 1.5][DVH]). Chrome Apps were deprecated in January 2020 and gone from desktop by 2022 ([DV-H 1.6][DVH]). A site that needed a serial port in 2014 had a plug-in being removed, an app platform being deprecated, a native helper via Native Messaging, or nothing; the web API that replaced it shipped in Chrome in 2021 and in Firefox in 2026 ([DV-H 1.7][DVH]).

Two conclusions follow. First, **the device APIs exist because the platform removed a general native-code escape hatch, not because the web had a clean device design ready**; Izcal must not recreate that hatch (no native messaging device bridge, no extension device API, no NPAPI-shaped fallback). Second, **the absence of device access is a real capability gap with a fifteen-year tail**, and a browser that refuses all six is choosing the plug-in era's restrictions without the plug-in era's workarounds.

Three patterns are visible in the table. **First, the ship dates cluster in 2021** (three APIs in one release) because the same engine shipped them after the plug-in and app platforms were gone; they were a platform migration, not six independent bets. **Second, the second engine arrived only for the two APIs whose permission model was rebuilt around per-origin, per-port grants and an enterprise switch** — Web MIDI in 2022, Serial in 2026 — and only after a decade; USB, HID, Bluetooth and NFC have no second engine at all ([DV-H 8.1–8.5][DVH]). **Third, the venue moved without the implementation count moving**: Web Serial became a WHATWG Living Standard in October 2026, and USB, HID and Bluetooth moved their URLs to `*.spec.whatwg.org` while still rendering WICG/CG front matter ([DV-H 8.10, 11.8][DVH]).

### 2.3 Why the chooser, not a registry

WebUSB's specification records two designs considered before the chooser. One gave each device a list of allowed origins, optionally through a public registry. It failed because it required new devices built for WebUSB, product cycles are long, an Editor's Draft "does not have the clout necessary to influence product planning", and it gave third-party developers no way to use an existing device. The adopted model was a permission prompt plus Permissions Policy ([DV-H 2.2][DVH]). Web Bluetooth went further and made the chooser normative: `requestDevice()` requires transient activation, the UA must prompt, it "MUST NOT allow the user to pair entire classes of devices with a website", and it must explain what the selected services let the site do before the user chooses ([DV-H 5.2][DVH]). The chooser survived because it solves two problems at once: it limits drive-by access, and it avoids a general scan that would expose both the user's devices and the browser's own radio address.

The registry idea is worth recording because it is the road not taken. It would have made device access a property of the device (its firmware lists origins), not of the browser's permission store. It failed for adoption reasons, not security reasons. Izcal could revisit it as an *additional* constraint — a device that names allowed origins is still constrained by the browser grant — but not as a replacement for the grant. The spec does not propose a registry.

### 2.4 The decade of single-engine objections

Vendor positions are unusually consistent. Mozilla recorded WebUSB as harmful in November 2019, Web Bluetooth in June 2020, WebHID in July 2021 and Web NFC as negative in January 2020; it recorded Web Serial as harmful in May 2020, changed to neutral in May 2024, and shipped it in Firefox 151 ([DV-H 2.5, 3.5, 4.4–4.5, 5.5, 6.4][DVH]). Mozilla's 2020 reason for Serial is the sentence the whole design has to answer: "We don't believe that user consent is adequate protection for anything that provides this level of capability", and serial access is "a relic from an age where a physical connection conferred a great deal of trust" ([DV-H 4.4][DVH]). WebKit opposed WebUSB (rationale 2022, label 2025), Bluetooth (2025), NFC (2025), Serial (2026) and HID (2026); its HID rationale rejected blocklists and prompts as insufficient and argued these needs "would be better served by purpose-built, capability-level APIs" ([DV-H 2.6, 3.6, 4.7, 5.6, 6.5][DVH]). No WebKit MIDI position was found ([DV-H 7.7][DVH]).

In 2026 the W3C tried to bring the five peripheral APIs into the Devices and Sensors Working Group. W3C staff filed a formal objection on 23 July 2026 calling them "detrimental to the security and privacy of users"; a Call for Consensus to remove them on 14 August reached no consensus by 31 August, and the objection was resolved without a council on 7 October ([DV-H 8.9][DVH]). The objection's argument is the most compact statement of the problem in the record: the danger is "in the permission grant, not the byte stream"; grants are "Too broad", "Too persistent and transferable" and "Too silent"; and the specs "merely shift the responsibility of maintaining security to device vendors" ([DV-H 8.9, 10.5][DVH]). This specification's three high-risk prompt classes, per-device expiry, signed tickets and pseudonymous handles are direct answers to those three phrases. It does not claim they make the APIs safe for every device; it claims they make the grant narrower, shorter, transfer-resistant and visible.

### 2.5 The physical incidents

The security literature predates the APIs and explains why their specs are so cautious. **BadUSB** (Black Hat 2014) showed that USB controller firmware can be reprogrammed so a stick spoofs other device types; the lesson is that a USB descriptor is a claim, not an identity ([DV-H 9.1][DVH]). **MouseJack** (2016) showed that wireless keyboard and mouse dongles can be made to inject keystrokes ([DV-H 9.2][DVH]). **BlueBorne** (2017) disclosed eight Bluetooth vulnerabilities (nine related zero-days in another account) across Android, Windows, Linux, iOS and macOS, with a vendor estimate of about 5.3 billion devices and no pairing or interaction required ([DV-H 9.3][DVH]; [DV-X 2.2][DVX]). **KNOB** (USENIX Security 2019) drove Bluetooth BR/EDR key negotiation to eight bits of entropy, brute-forceable, across more than 14 chips; "all tested devices are vulnerable" ([DV-H 9.4][DVH]). **BLESA** (WOOT 2020) found two specification-level weaknesses in BLE reconnection, so "even a device implementing the BLE protocol correctly may be vulnerable to spoofing" — a prior pairing is not proof that the reconnecting peer is the same device ([DV-H 9.5][DVH]). **BrakTooth** (2021) disclosed 16 vulnerabilities across 13 devices from 11 vendors and more than 1,400 product listings, without pairing; the notes disagree on the CVE count (25 in the history note, 20 in the security note) ([DV-H 9.6][DVH]; [DV-X 2.5][DVX]). **NFC relay** research from 2005 and a phone-based software-only demonstration in 2011–12 broke the assumption that a token within range is in close proximity; no cryptography is broken, only the proximity claim ([DV-H 9.7][DVH]).

**Peripheral Instinct** (WWW '25) is the synthesis for the web: 22 device models from 15 vendors, full exploit chains through WebHID, WebUSB, Web Serial and Web MIDI — custom firmware on a Logitech Unifying Receiver, macro and key-map changes on mice and keyboards, AT-command attacks over Web Serial enabling SMS and two-factor-code interception, GPS tracking and permanent SIM lockout — and the argument that the host, not the device, is now the untrusted party ([DV-H 9.8][DVH], [DV-X 1.1–1.2][DVX]). Its strongest chain crossed the air: a page flashed a wireless receiver over WebHID, and the receiver then injected into a different machine in the room with no action by that machine's user ([DV-X 1.1][DVX]). A browser cannot prevent that with a prompt; it can refuse the device class, or refuse the write, or tell the person exactly what the grant permits.

### 2.7 The six misjudgments

1. **"The prompt is the security boundary."** The specs themselves say a compromised device can attack later hosts and "there is nothing that can be done by the UA to prevent further damage" ([DV-H 2.8][DVH]); Web Serial says host software "may be vulnerable to attack because it improperly validates input from connected devices" ([DV-H 11.9][DVH]); WebHID says a malicious page could "generate trusted input events" ([DV-H 3.7][DVH]). The prompt is a *grant* boundary; the parser, the process split and the class refusal are the security boundary.
2. **"A device is a device."** Six transports became six APIs, six permission stores and six test stories, although the grant shape is the same: site, container, device, class, interface, purpose, expiry ([DV-G 3.1–3.4][DVG]). Izcal's one boundary is the correction.
3. **"The OS will mediate."** It mediates access, not web-origin authority. Linux hidraw has no documented keyboard/mouse exclusion; udev and seccomp cannot scope a device per process; Windows gives one PDO per top-level HID collection but no origin; macOS TCC asks per application, not per site; Android has no public HID API at all ([DV-O 3.1–3.8, 7.5][DVO]). The browser must scope above the OS.
4. **"Scanning is just a chooser with more results."** Broad Bluetooth scanning was never shipped; the scanning specification was never published; Web Bluetooth's `getAvailability()` is the one ambient bit left and the spec concedes it costs fingerprinting ([DV-H 5.7–5.8][DVH]). The chooser is not a UI preference; it is the privacy model.
5. **"A tap proves presence."** NFC relay breaks the proximity assumption with no crypto break ([DV-H 9.7][DVH]). A tap is user intent to read *a* tag, not authentication of *which* tag or *whose*.
6. **"Standardization creates implementations."** Twelve years of Community Group did not produce a second Bluetooth implementation; moving four specs to WHATWG addresses did not either; only Serial's rebuilt permission model and Firefox's gate did ([DV-H 8.4, 8.10, 11.8][DVH]). Exposure decisions must follow engines, not venues.

### 2.8 What the history tells Izcal to build

| Historical fact | Design consequence | Section |
|---|---|---|
| The plug-in/app escape hatch was removed on purpose | No native-messaging device bridge, no extension device API, no general native path | 6.14, 6.19 |
| Only per-origin, per-device, revocable grants earned a second engine | One grant model with per-device identity, expiry and revocation | 6.10 |
| The 2026 objection named grants "Too broad", "Too persistent and transferable" and "Too silent" | Narrow capability sets, 90-day† expiry, tickets bound to origin/container, prompts with consequences in the ledger | 6.2, 6.10 |
| A grant can reach firmware and radios | HID keyboard/pointer/FIDO refused; USB protected classes refused; `device-write` is a distinct high-risk class | 6.3, 6.4, 6.10 |
| Device descriptors are claims; parser bugs are host bugs | Izcal-written tier-P parsers, all fuzzed; no descriptor used as identity | 6.9 |
| Bluetooth pairing is not peer identity | No pairing-as-authentication; OS bonding only; no keys or addresses exposed | 6.7 |
| NFC proximity is relayable | Tap never authenticates; NDEF payloads are credential-class for recording | 6.8, 6.12 |
| The only second engine came with a per-site gate and an enterprise switch | Policy hooks and an administrator off-switch from the first release | 6.10, 6.15 |
| No stable browser has a virtual device | Virtual device and replay are first-class, not test-only afterthoughts | 6.12, 6.13 |

## 3. Today: the landscape and its gaps

### 3.1 The six APIs in October 2026

None of the six is a W3C Recommendation. Only Web Serial is a WHATWG Living Standard; Web MIDI is a Working Draft on the Recommendation track; the other four are Community Group drafts. Apple declined all six in its 2020 list of APIs it would not implement, for fingerprinting and security reasons ([DV-G 2.5][DVG]); Mozilla's positions range from "harmful" for WebUSB and WebHID to positive for Web MIDI, with Serial moving to neutral and then shipping gated ([DV-G 2.5][DVG]); WebKit opposes USB, Serial, HID, Bluetooth and NFC and has no MIDI position ([DV-S 10.1–10.6][DVS]).

### 3.2 What users cannot do today

The tasks are real and shipped: ESP Web Tools flashes ESP8266/ESP32 boards over Web Serial; Arduino Create, Betaflight Configurator, Espruino Web IDE and MakeCode use serial; Trezor Suite for web is WebUSB-only and excludes Firefox, Safari and iOS; VIA configures QMK keyboards over WebHID and is Chromium-desktop only; Novation Components runs on Web MIDI and treats Firefox's add-on gate as unsupported; BLE sensors and medical devices push iOS users to Bluefy or WebBLE; Web NFC's documented tasks are museum cards, inventory, conference badges and provisioning ([DV-G 1.1–1.8][DVG]). Almost every one is confined to Chromium or to one platform, with a native bridge, a standalone app or a different browser as the fallback. The designers of hardware wallets, keyboards, synths, printers, receipt printers, cash drawers and barcode scanners build their own emulators because no browser offers a programmable virtual device ([DV-G 3.5][DVG]; [DV-R 4.6–4.15][DVR]).

Manufacturing shows the identity gap: a robotics company built a factory tool for 2,000 wearable units and could not tell identical units apart, because Web Serial exposes vendor and product IDs but not the USB serial number; the workaround claims the interface with WebUSB and probes whether Web Serial can open the same port ([DV-G 1.8][DVG]). The API surface that exists is not the API surface the tasks need.

### 3.3 The engine-support gap

Three of the six are Chromium-only, one is Android-only, one is cross-engine but has no Safari, and one became cross-engine only in 2026 with an add-on gate; none ships in Safari ([DV-G 2.5][DVG]). Global reach figures measure users on a supporting browser, not adoption: WebUSB 76.47%, WebHID 30.2%, Web Serial 74.58%, Web MIDI 78.96%, Web Bluetooth 76.52%, Web NFC 42.79% ([DV-G 2.1–2.4][DVG]). The developer consequence is a native fallback or a "use Chrome" interstitial, and the privacy consequence is that the only implementations are the ones whose permission model the specs themselves describe as uneven: WebHID recommends two interactions, Web Serial requires a gesture and `requestPort()`, WebUSB says the UA "may" prompt, and Web MIDI says approval "is not currently required" ([DV-X 4.1][DVX]).

### 3.4 The testing gap

No stable browser has a scriptable virtual device: Chrome offers `about://usb-internals` connection simulation, `about://device-log`, `about://bluetooth-internals` and a HID explorer; Web Serial has only manual tests; Web NFC and MIDI document no emulator ([DV-G 3.1–3.3][DVG]; [DV-R 4.12][DVR]). The Bluetooth fake adapter is test-only and is not in stable Chrome builds ([DV-G 3.1][DVG]; [DV-R 4.10][DVR]). Hosted CI has no browser-USB path; teams self-host hardware or mock the device ([DV-G 3.2][DVG]). Device code is tested by hand, on hardware, in one browser; reconnect handling is the flaky part: GATT attributes are invalid after disconnect and must be re-fetched, parallel characteristic operations may fail by platform, and a fatal serial read error makes `port.readable` null ([DV-G 3.3][DVG]).

### 3.5 The unowned-surface gap

The DOM spec's 6.18 lists 11 web API rows, none of the six, and says: "Any web API not in this table or another spec's is recorded in the ledger as a gap before it is admitted" ([DV-G 5.1][DVG]). The Phase 3 ledger has G-1 to G-25 and none names a device API, a device service or a device permission ([DV-G 5.2][DVG]). The security scope's 3.5 gap table has 23 rows and none is a device row; its process map has 36 kinds and 38 threat-model files, and device authority appears only as narrow exceptions — capture, audio, hardware decode ([DV-G 5.3–5.4][DVG]). SEC-6 requires each process's threat model to name its entry points from a surface inventory, and no device process exists to generate one ([SS] SEC-6; [DV-G 5.2][DVG] for the gap counts). The extensions spec's Ring C names `captivePortal`, `power`, `fontSettings` and `input.ime` as "OS and vendor surfaces without an Izcal owner yet", which is the corpus's admission that such surfaces can be named and refused; the six device APIs are not even named ([DV-G 5.3][DVG]). The shell has a prompt ledger and a site panel with no device grant class; DevTools has IIP domains for crypto, ML, layout, media and reputation but none for devices; no crate table names a device crate ([DV-G 5.4][DVG]).

**This spec closes the gap for the six.** Section 9.5 names **G-26** in the ledger and records its closure: the six APIs, their permissions, their process, their recording class and their threat model now have an owner. No other input surface is claimed here; this spec owns only the six device APIs and their boundary.

## 4. First principles

### 4.1 Users' real tasks

| Task | Who | What the browser must do | What it must not do |
|---|---|---|---|
| **Flash firmware on a board** | Makers, educators, firmware developers, factory tools | Move bytes to a serial port or a USB bulk endpoint, reset the board, report failure honestly | Let a firmware write be mistaken for a printer job; silently re-open a port and reset a running device |
| **Configure a keyboard, mouse or gamepad** | Enthusiasts, accessibility users, repair shops | Read and write HID reports on a specific collection | Let a page reprogram macros and then type into other applications without a person-present decision |
| **Use a hardware wallet or security key** | Ordinary users, high-risk users | Keep FIDO and wallet protocols inside the component that owns them; expose raw HID only where the protocol requires it | Hand a FIDO key or a seed-bearing device to page script |
| **Play, record and edit MIDI** | Musicians, teachers, stage technicians | Enumerate ports, move messages with timestamps, carry SysEx for device editors | Let SysEx be an unremarked capability of an ordinary MIDI grant |
| **Read a sensor or a wearable** | Health, sport, industrial, education | Connect to a granted GATT service, subscribe to notifications, survive disconnects | Scan the room ambiently, or report a stable device identity to every origin |
| **Read or write an NFC tag** | Museums, logistics, events, provisioning | Read NDEF, write NDEF, make read-only, act only in the foreground | Read tags in the background, or treat a tag UID as an identity |
| **Audit and revoke** | Everyone, administrators | See which site used which device, when, for what, and revoke in one place | Keep a grant that the person cannot find |
| **Test without hardware** | Developers, CI, Izcal's agents | A virtual device through the same chooser, scriptable and deterministic | Make the virtual path behave differently from the real one in ways the page can detect |

### 4.2 The platform primitives

| Primitive | What it gives | Where it is defined |
|---|---|---|
| **A process with a sandbox** | A boundary that survives a compromised peer; the only place an OS handle can live | Security scope 6.7; Stage 1 Section 4 |
| **Typed IPC and capability endpoints** | Messages generated from one schema; no ambient authority; a handle is a broker-minted endpoint, not a number | B2, IPC-R1 to IPC-R17, `hg-ipc-codegen` |
| **A broker-owned prompt layer** | A decision made on broker-observed input, in a window no page can cover, recorded in a ledger | CON-R1 to CON-R5, GR-D28, SH 6.4 |
| **A signed, expiring ticket** | A capability that a different process can verify without being able to mint it | NW-D4's LNA ticket, extended in DV-D2 |
| **The deterministic substrate** | Time, entropy and external input as recorded values; decision points for anything the engine would otherwise infer | B1, DET-1, DET-2, JS-D15 |
| **A virtual device** | A device-shaped input source that a replay or a test can drive without hardware | DV-D8; CDP `BluetoothEmulation` and WebUSB Testing API as evidence of shape ([DV-R 4.8–4.9][DVR]) |
| **A tier system for parsers** | A parser that handles hostile bytes cannot also panic, allocate unboundedly or run in a high-privilege process | CS tier P, CS-ER-9, SEC-24 |

### 4.3 Izcal's principles that bind this design

- **Zero ambient authority.** A page has no device until a grant says so; a session has no OS handle at all; the arbiter has no page data. Every crossing is a typed message with a ticket.
- **Isolation first.** The parser never runs where the handle lives. This is the Rule of Two applied to devices: an unsafe language is not in play, but untrusted input and high privilege are, and a process may hold at most two of the three ([DV-X 5.11][DVX]).
- **Privacy is not a setting.** Device identity is a capability, not a fact about the person; the default is a pseudonym per origin and container, and the true identifier is a separate grant.
- **The person is the authority.** The broker, not the page, the shell or an extension, decides that a person approved; a device prompt is a security prompt; an AT action is not a person unless AX-D11 says it is.
- **Determinism is free at the boundary or expensive everywhere.** Recording device events at the service boundary costs a queue and a log; retrofitting determinism into six OS-facing stacks costs six rewrites.
- **Build our own, from the specification.** Every parser, every state machine, every ticket format, every simulator is Izcal's; OS interfaces are the only borrowed behaviour.
- **No shortcut for schedule.** The six APIs are not six independent projects with six teams; they are one boundary with six front ends. The spec does not stage down the parsers, the fuzzing or the replay to save time.

### 4.4 Assumptions kept and broken

| Assumption | Status | Why |
|---|---|---|
| The OS mediates device access and can be trusted to scope it | **Kept, with a floor** | Every desktop OS has a device interface and a permission model; none scopes to a web origin, and Linux udev/seccomp cannot scope to a device per process ([DV-O 7.5][DVO]); the browser must scope above the OS |
| A user grant is adequate protection | **Broken** | A grant reaches firmware, macros and radios; Peripheral Instinct turned one WebHID grant into trusted keystrokes on 14 of 22 devices and a cross-machine radio attack ([DV-X 1.1–1.2][DVX]); the WebUSB and Web Serial specs themselves say the UA cannot prevent damage once the device is hostile ([DV-X 1.3–1.4][DVX]) |
| Per-API permission models are natural | **Broken** | WebHID may unify USB and HID permissions and no spec requires it; enterprise policy is per API; users cannot see a cross-API device principal ([DV-X 4.5][DVX], [DV-X 7.9][DVX]) |
| Bluetooth needs its own controller stack to be a browser | **Broken** | No desktop OS exposes HCI to an ordinary process; Web Bluetooth is GATT-only; the OS stack already supplies every capability the API exposes ([DV-O 9.7, 10.5–10.7][DVO]) |
| NFC is a web platform capability | **Broken on desktop** | Core NFC is absent from macOS, Windows has only a legacy proximity API, Linux has a stale neard or PC/SC; no desktop browser ships Web NFC ([DV-O 6.1–6.7][DVO]) |
| Device identity can be normalised away | **Broken** | VID/PID, names, GATT UUIDs, port names and device bytes are device model or device state; only serial numbers, UIDs and port IDs can be pseudonymised ([DV-F 8.5–8.6][DVF]) |
| Persistent grants are a usability necessity | **Kept, bounded** | Persistence helps sites and attackers alike; Web Bluetooth's spec admits it worsens the compromised-site risk ([DV-X 4.3][DVX]); 90-day† auto-revocation and visible revocation keep it bounded |
| A device can be recorded at the API boundary | **Broken** | Descriptor and protocol parsing is where the bugs are; the API boundary hides it ([DV-R 3.1][DVR]); the OS device interface is the lowest portable, secret-free boundary |
| A recorded session can reproduce the physics | **Broken** | RSSI, radio loss, tag presence, firmware and OS scheduling are below the boundary; the honest claim is bytes, order and recorded times ([DV-R 7.3–7.8][DVR]) |
| One process per device is affordable | **Broken** | A session per (frame site, container, family) and one arbiter per profile fit the footprint; per-device processes would multiply page tables and empty-process cost for no isolation gain (6.16) |

## 5. Lessons learned and how Izcal applies them

The history above is not context; it is the failure list this design is graded against. Each lesson is stated with the evidence that produced it and the rule or target that answers it.

**5.1 The permission grant is the security boundary, not the byte stream.** The W3C staff objection says the danger is "in the permission grant, not the byte stream" ([DV-H 8.9][DVH]); Peripheral Instinct demonstrates it by turning one WebHID grant into macro reprogramming on 14 of 22 devices from 15 vendors and trusted keystrokes at 5 ms on Linux and ~35 ms on Windows ([DV-X 1.1][DVX]). A parser cannot fix a grant that permits firmware writes. *Applied:* grants are per (origin, top-level site, container, family, device identity digest) and carry an explicit capability set; read, write, configure, pair, reset and sysex are separate bits; `device-write` is a high-risk class; protected classes are refused before a prompt is drawn (6.3, 6.4, 6.10, DV-4); HID input-producing collections are refused outright (6.4).

**5.2 A parser is part of the security boundary.** Descriptor and PDU parsers are where device bugs become host bugs. NVD records 121 "USB descriptor", 83 "USB HID", 29 "HID descriptor", 24 "HID parser" and 24 "HID report descriptor" entries; USBFuzz found 26 bugs and 10 CVEs across four kernels; NDEF parser fuzzing found eight application-level bugs; the WebHID CVE-2023-1529 out-of-bounds read was rated CVSS 9.8, and CVE-2026-13778 was a malicious-peripheral use-after-free ([DV-X 3.2–3.8, 6.7][DVX]). *Applied:* every parser is Izcal's, written from specification prose, tier P, allocation-capped, recursion-free, fuzzed at ≥1,000 CPU-hours/week for USB and HID and ≥500 for GATT, NDEF and MIDI, with zero open crash bugs older than 14† days (6.9, DV-3, SEC-24).

**5.3 The process that holds the handle must not parse the bytes.** The Chromium record shows the shape of the failure: compromised-renderer escapes via WebUSB and Web Bluetooth (CVE-2026-78911, CVE-2026-11236), a malicious peripheral UAF (CVE-2026-13778), an integer overflow from a compromised renderer (CVE-2020-6569), a UI-spoofing prompt bug (CVE-2020-16033), a policy-enforcement bug (CVE-2026-5276) and an extension escalation (CVE-2026-13864) ([DV-X 3.2–3.4][DVX]). None of the six specs analyses a compromised renderer; the broker model has no device rule ([DV-X 5.2, 5.6][DVX]). *Applied:* the arbiter holds every OS handle and parses nothing; the session parses everything and holds no OS handle; the renderer holds typed handles only (DV-D1, G210, G215; DV-1, DV-13).

**5.4 A stable identifier is a tracking cookie with a device attached.** WebUSB exposes vendor/product/serial and uses the serial as a permission key, conflating device models when it is absent; Web NFC's `serialNumber` is the tag UID and may be random per read; Web MIDI port IDs "should" persist across reboots; Web Bluetooth's `id` is per-origin and "suggested" but names, GATT UUIDs and advertisement payloads remain correlators; Web Serial hides the serial but exposes VID/PID or a Bluetooth service UUID ([DV-F 1.1–1.6, 8.5–8.6][DVF]). The specs admit enumeration, availability and persistence fingerprinting ([DV-H 10.1–10.5][DVH]). *Applied:* per-(origin, container, device) pseudonymous handles; serial numbers, UIDs and hardware addresses behind a separate off-by-default identifier grant; constant `getAvailability()`; defined ordering; padded first-call timing; 90-day† expiry; rotation on clear-site-data and on site-identity change (6.11, DV-6, PRIV-2).

**5.5 The chooser is a privacy control, and its second interaction is load-bearing.** WebHID recommends two separate interactions, select then confirm; Web Bluetooth forbids pairing entire classes and requires explaining what the services allow; WebUSB's chooser displaced a device-side registry ([DV-H 2.2, 3.7, 5.2][DVH]). A one-click chooser is a click-through; the WWW '25 paper cites a study in which up to 95% of users were convinced to grant permissions ([DV-H 10.6][DVH]). *Applied:* the chooser is broker-owned, has no default selection, requires select plus confirm, shows the origin, container, family, device label, capability set and consequence text, offers "this time" and "while open" before "remember", and cannot be pre-filled by the page; `acceptAllDevices` is refused (6.10, DV-7).

**5.6 A test fake that is absent from stable builds is not a test strategy.** Chrome's Bluetooth fake adapter is test-only and is not in stable Chrome builds; Web Serial has manual tests; hosted CI has no USB path; teams self-host hardware or build emulators ([DV-G 3.1–3.2][DVG]; [DV-R 4.12][DVR]). *Applied:* the virtual device is a shipped capability, reachable through the same chooser, scriptable, deterministic and usable by DevTools, CI and agents; it is the replay target (6.12–6.13, DV-D7, DV-D8).

**5.7 Recording at the API boundary records the wrong thing.** The bugs are in descriptors and PDUs, and the API boundary hides them; the OS device interface is the lowest portable boundary that holds no page secret ([DV-R 3.1–3.3][DVR]). rr's 1.49–1.79× recording cost shows that a boundary-level record is affordable; USB/IP and gadget configfs show that a typed device protocol can be virtualised ([DV-R 4.1, 4.3, 4.16][DVR]). *Applied:* record at the device-service boundary — descriptor bytes, typed transfers, report bytes, serial chunks with boundaries, MIDI bytes with receipt times, GATT operations, NFC records, adapter and grant decisions, typed errors — and replay against a virtual device that never opens hardware (6.12, DV-8, DV-9).

**5.8 The OS stack is the only portable interface, and it is not a web security boundary.** Every desktop OS exposes USB, HID, serial and MIDI to user processes; Android exposes USB host, Bluetooth and NFC but no public HID; no ordinary desktop process gets HCI; Linux hidraw has no documented keyboard/mouse exclusion; Windows HIDClass gives one PDO per collection but no origin; macOS TCC asks per application ([DV-O 3.1–3.8, 7.5, 9.7, 10.5–10.7][DVO]). *Applied:* the OS stack is the interface for every family, including Bluetooth; the browser scopes above it; no HCI stack; no libusb or libnfc dependency; protected classes and HID input usages are refused in the arbiter before a handle is opened (6.2–6.8, DV-D3).

**5.9 One engine means one permission model, and it is not a model Izcal can inherit.** The six specs mediate inconsistently: WebHID requires an explicit grant and a two-click chooser, Serial requires `requestPort()` and transient activation, WebUSB says the UA "may" prompt, MIDI said approval "is not currently required" until Chrome 124; persistence, `forget()` and Permissions API support differ per API; enterprise policy can silently pre-grant by VID/PID and override ask/block ([DV-X 4.1–4.7][DVX]). *Applied:* one grant store and one chooser for all six, per-API differences only where the API's own semantics require them (MIDI's SysEx tier, Bluetooth's filters, NFC's foreground tap), and no silent pre-grant by default (6.10, DV-D4, DV-D5).

**5.10 A device can be hostile, and the browser cannot fix it.** WebUSB: once a device is compromised there is "nothing that can be done by the UA to prevent further damage"; Web Serial: host software "may be vulnerable to attack because it improperly validates input from connected devices"; WebHID: a malicious page could "generate trusted input events" ([DV-H 2.8, 3.7, 11.9][DVH]; [DV-X 1.3–1.4][DVX]). *Applied:* the spec states the limit in the prompt and in the documentation; it refuses the classes where the damage crosses into the host's input or storage; it logs the grant so the person can revoke; it does not claim that a green prompt makes a device safe (6.3, 6.4, 6.10).

**5.11 A venue change is not an implementation.** Web Serial became a WHATWG Living Standard; USB, HID and Bluetooth redirect to WHATWG addresses while still rendering Community Group front matter; only Serial and MIDI have a second engine, and only behind an add-on gate ([DV-H 8.10, 11.8][DVH]). *Applied:* the exposure decision (DV-D9) counts engines and WPT, not venue; the standards status is recorded per API but does not substitute for the ST-D18 test (6.15).

**5.12 A promptless capability will stay promptless.** Web MIDI shipped in 2015 and got a permission prompt in 2024, nine years later ([DV-H 7.3][DVH]). *Applied:* no device API ships without a decision path from its first release; `requestMIDIAccess()` prompts for every grant, not only SysEx; no API is exposed behind a preference that silently grants (6.6, 6.10).

**5.13 An administrator switch is a feature, not an enterprise afterthought.** Firefox 151's `DefaultSerialGuardSetting` and Firefox 152's managed-profile default-off came with the API, not years later ([DV-H 4.6][DVH]). *Applied:* every family has a policy key with `ask`, `block` and `allow-once` semantics from the first release; pre-grant is off by default and requires a signed policy with a visible indicator (6.10, 6.15).

**5.14 What this spec deliberately does not do.** It does not build a native-messaging device bridge (recreates the plug-in hatch); it does not expose a raw HCI stack (unavailable and unsafe); it does not use libusb, libnfc or pcsc-lite (non-MIT or an OS-daemon dependency; PC/SC is a possible future OS interface, not a shipped library); it does not copy the allowed-origin registry (needs new firmware); it does not ship NDEF payloads in recordings by default (credential-class); it does not claim physical fidelity in replay (bytes, order and times only); and it does not expose a device to an extension or an agent without a person-present grant (6.14).

| Process | Role | Instances | Lifetime | OS access | Page data |
|---|---|---|---|---|---|
| **Device-access service** | `arbiter` | One per profile, launched on the first device request | Exits 30 s† after the last device closes; stays while a prompt or pairing is pending | **The only process allowed to call `hg-substrate-os` device backends**: opens, claims, configures, transfers, pairs, enumerates | No page content or page strings; it sees origin/container as routing fields in a ticket and transfer buffers as opaque bytes, and parses neither |
| **Device-access service** | `session` | One per (frame site, container, family), shared by that site's documents | Exits 30 s† after the last handle closes; survives navigation within the BCG | None (link-time excluded, G215) | The granted page's device traffic only; it holds no OS handle and no handle key |
| **Device-access service** | `enumerate` | At most one per profile while a chooser is open | Exits when the chooser closes | None | None; it parses bounded descriptor bytes from the arbiter and returns a fixed summary |

The arbiter and the session are the **same binary** in two link configurations, not two process kinds: one IPC schema, one threat model, one review surface, and a link-time check that the session configuration cannot name an OS backend. The enumeration configuration is the session binary with no site identity and no device channel; it exists because the arbiter must not parse the descriptor bytes it reads to decide whether a device matches a page's filters. This is the Rule of Two applied literally: the process with the OS handle does not parse attacker bytes; the process that parses has no handle; the broker has neither and decides. A session serves one frame site, container and family; same-site origins (for example `a.example` and `b.example`) share it, and it demultiplexes by frame origin on every message, refusing a message whose ticket origin does not match the endpoint it arrived on. A cross-site iframe gets its own session, grant and ticket, so a compromised session cannot read the embedder's device bytes or vice versa. The grant remains keyed by top-level site so the person sees the embedding context; the session key is the frame site because device bytes are page data. A profile caps concurrent device sessions at **8†**; a new open beyond the cap fails with `QuotaExceededError` and is recorded.

The process map amendment (9.5) adds **one** kind, from 36 to 37, and **one** threat-model file, from 38 to 39 (`device-access.md`, with three sections: arbiter, session, enumeration). The sandbox row is "utility, no network, no filesystem; arbiter additionally has the OS device interfaces its backends need; session has no OS effects". The track is `DV`.

### 6.1 One boundary, two roles, three configurations

**Launch and lifecycle.** The broker launches the arbiter on the first device request from any frame, with a broker-minted profile ticket that carries the broker's public verification key for the profile's device-ticket keypair. The arbiter registers its device table and waits. A session is launched only after a grant exists: the broker creates a session endpoint, passes the frame-site/container/family key and the session ticket, and the session waits for a device channel. The enumeration configuration is launched by the broker when a chooser needs to filter candidates, and exits with the chooser. No device process is launched at browser start; a profile that never uses a device API runs zero device processes, and FP rows charge zero (6.16).

**Authority split.**

| Function | Broker | Arbiter | Session | Renderer |
|---|---|---|---|---|
| Decides that a person approved | **Yes** (CON-R1, CON-R2) | No | No | No |
| Mints a device-access ticket | **Yes** (only) | No | No | No |
| Verifies a ticket | No | **Yes** | No | No |
| Opens an OS device handle | No | **Yes** (only) | No | No |
| Parses descriptors, reports, PDUs, NDEF, MIDI | No | No | **Yes** | No |
| Holds the page-visible handle | Derives it (only holder of the per-origin key) | No | Maps it to the digest, never exposes either | **Yes** (opaque ID) |
| Stores grants and the prompt ledger | **Yes** | No | No | No |
| Enforces feature policy and activation | **Yes** | No | No | No |
| Records device input | No | Forwards to the recorder | **Yes**, at the boundary | No |

**Request flow.** (1) Page script calls a device method with transient activation where the API requires it; the renderer checks the API's own preconditions, then sends `DeviceRequest {family, operation, args, document_token, activation_token}` to the broker over its broker-bound endpoint. (2) The broker checks the Permissions Policy token, secure context, origin, container, top-level site, activation and rate limit, then asks the arbiter for candidates matching the page's filters. (3) The arbiter reads OS metadata and, where the API needs descriptor fields, sends bounded descriptor bytes to the enumeration configuration; the enumeration configuration returns a fixed summary (vendor/product IDs, class triple, serial presence bit, BOS capability bit, collection summary, name fields as length-prefixed bytes with control characters removed). The broker hashes the enumeration configuration's canonical scope and re-checks protected classes from OS metadata and signed policy; the enumeration summary is untrusted for security labels. (4) The broker draws the chooser with sanitized labels, the origin, the container, the family, the capability set and the consequence text; it records the prompt in the ledger. (5) On approval, the broker mints a `device-access` ticket and creates the session endpoint; the ticket carries the grant, the chosen device digest, the capability set, the scope and the expiry. (6) The session opens the device by sending the ticket to the arbiter; the arbiter verifies signature, fields, expiry, sequence and policy generation, checks its arbitration table, opens the OS handle, claims the interface/collection/port within the ticket's signed scope, and returns a typed `DeviceOpenResult`. (7) All subsequent transfers carry the `session_id` and a monotonic `sequence`; the arbiter checks them against the session context, so a stolen message cannot be replayed into another session. (8) Revocation from the broker (`DeviceRevoke`) makes the arbiter close the handle and the session reject further calls; the renderer receives `NotFoundError` on the next call and the handle is dead.

**Device-access tickets.** The format is versioned, fixed-layout, and signed with Ed25519. The broker holds the private key in its key store, one keypair per profile, rotated on profile reset; the arbiter receives the public key at launch and never a private key. A ticket is:

| Field | Meaning |
|---|---|
| `version`, `ticket_id` | Format version; 128-bit unique id |
| `purpose` | `enumerate`, `open`, `configure`, `pair`, `write` and `replay` are one-shot; `transfer` is the session ticket that authorizes transfers for its lifetime |
| `role` | `arbiter`, `session`, `enumerate` |
| `profile_id`, `session_id` | Profile binding; session binding (zero for enumerate) |
| `top_level_site`, `container_id`, `frame_origin` | The authority the ticket is for; the arbiter enforces them only as routing and logging fields, the broker is the authority |
| `family` | `usb`, `hid`, `serial`, `midi`, `bluetooth`, `nfc` |
| `device_digest` | 256-bit profile-local identity digest (6.2) |
| `capabilities` | Bit set: read, write, configure, pair, reset, sysex, write-tag, identifier-exposure |
| `scope_digest`, `scope_len` | SHA-256 of the canonical signed scope and its length: USB interface/alternate-setting/endpoint sets, HID collection indices and report IDs, the serial port identity, MIDI endpoint ids, GATT service/characteristic UUIDs; NFC has an empty scope. The enumeration configuration produces the canonical bytes from the descriptors, the broker hashes them into the ticket, and the session presents the bytes at open; the arbiter verifies the hash and enforces every claim against it, so the session cannot widen its scope |
| `grant_id` | The grant this ticket derives from |
| `issued_at`, `expires_at` | Substrate time; maximum 24 h† for a session ticket, 60 s† for an open ticket |
| `nonce`, `sequence` | Replay prevention; the arbiter stores the last sequence per session |

A session ticket is renewed by the broker before `expires_at` while the grant and session are alive, without a prompt; a failed renewal closes the device with `NetworkError`. Renewal is a fresh mint: the broker re-checks the grant, policy generation and session liveness and issues a new 24 h† segment; a this-time or while-open grant that has ended is not renewed, and the device closes. A session ticket can be renewed indefinitely while the grant lives; the grant's own 90-day†/1-year† expiry bounds it. An open ticket lasts 60 s† and is consumed by the open.

Why signed rather than MACed: NW-D4's Local Network Access ticket is both issued and verified by the broker, so a MAC suffices. Here the issuer (broker) and the verifier (arbiter) are different processes, and the arbiter is the process that holds OS handles. If the arbiter held a MAC key it could mint tickets for any device after a compromise; with a signature it can verify but not mint. The cost is one Ed25519 verification per open and per capability escalation (target ≤ 100 µs† per verification, measured on the riscv64 reference at DV-M0), and none per transfer.

**What a compromised participant can do.** A compromised renderer can call only the operations its handle's capability set allows, on the one device digest, from the one origin/container, as enforced by the session and the arbiter; it cannot enumerate, open another device, or mint a ticket. A compromised session can do the same, plus it can parse maliciously and return wrong values to its own site's pages; it cannot open a device or reach another frame site or container; within its own frame site it serves same-site origins, and the per-origin ticket check stops an honest session, not a compromised one. A compromised **arbiter** can read and inject every session's device traffic in the profile: the broker's grant table is the outer boundary for new opens, not a data-plane boundary. Those residuals are recorded in 10. A compromised **enumerate** configuration can mislabel a device in the chooser summary, but it cannot grant, open or widen the signed scope; the broker re-checks protected classes from OS metadata and signed policy before drawing the prompt, and the arbiter enforces the scope. A compromised arbiter can open any device the OS lets it open (it has the handles), but it cannot mint a ticket, cannot create a session, and cannot make the broker prompt; the broker's grant table and the OS's own per-application permission remain the outer boundary. A compromised broker is game over for the profile's grants, as it is for every other permission; the ticket design does not claim otherwise.

**IPC.** All messages are typed, generated, bounded and accounted. Descriptor bytes are capped at 64 KiB‡ per read and 256 KiB‡ per device; transfer buffers use shared-memory rings with 4 MiB‡ per transfer and 16 MiB‡ in flight per device, capped at 64 MiB‡ in flight per profile; serial chunks are capped at 1 MiB‡ and HID reports at 8 KiB‡; MIDI messages at 64 KiB‡; NDEF messages at 32 KiB‡. A message that exceeds its cap is rejected with `QuotaExceededError`, recorded as a typed error, and counted against the session's rate limit. There is no untyped byte channel and no shared file descriptor between the arbiter and any other process.

### 6.2 Device identity and handles

The arbiter computes a **device identity digest** from what the OS exposes, never from device-provided strings alone:

```
digest = SHA-256("izcal-device-v1" || profile_salt || family || os_identity)
```

| Family | `os_identity` | Stability | Notes |
|---|---|---|---|
| USB | VID, PID, `bcdDevice`, serial string if the OS exposes it; otherwise the OS device instance path (macOS registry entry, Windows device instance path, Linux bus path, Android device name) | Stable across replug if serial; otherwise per port | Serialless devices of the same model share a digest — a known limitation for manufacturing (Q-DV-4) |
| HID | VID, PID, serial if present, top-level collection usage page/usage and collection index | Per collection on Windows; per device on Linux/macOS | A composite device can have several grants, one per allowed collection |
| Serial | OS port stable id (macOS `IORegistryEntryID`/port path, Windows device instance path, Linux sysfs path) plus VID/PID if the OS exposes them | Can change across replug or hub change | Web Serial exposes no serial number; the grant follows the port, not the cable. At open the session compares VID/PID and any OS-exposed USB serial with the grant inputs; if the OS cannot verify the port's identity (a generic adapter with no VID/PID), the grant is marked `port-only` and every open requires a fresh `device-connection` prompt, because a different device on the same port would otherwise inherit the grant |
| MIDI | OS endpoint unique id plus name and manufacturer | Persistent across reboots per the API's "SHOULD" | Virtual ports are devices too |
| Bluetooth | OS per-system opaque device identifier plus adapter id | Stable while bonded or cached; can change after OS reset | The address never leaves the arbiter |
| NFC | **Zero** for the grant key: Web NFC has no per-tag grant, so the grant is per origin/container; the tag UID is used only for the per-tap pseudonym and is never part of the grant key | n/a | The NDEF parser and the per-tap `serialNumber` still see the UID; the grant does not |

The digest is profile-local: the same physical device has a different digest in a different profile because `profile_salt` differs. It never leaves the broker, the arbiter and the session that owns the device; the session receives it as an opaque routing field and never exposes it to the page. The page-visible **handle** is derived by the **broker**, the only holder of the profile secret and the grant table:

```
origin_handle = HKDF-SHA-256 over (profile_handle_secret, HANDLE_LABEL || frame_origin || site_identity_generation)
handle = HMAC-SHA-256 over (origin_handle, container_id || family || digest)
```

The broker passes the handle to the session and the renderer at bind time; the session maps it to the digest and never holds the key. The handle is stable while the grant lives, including across session restarts, and is unlinkable across origins or containers because the inputs differ. On revocation, clear-site-data, 90-day† expiry, or a change to the origin's site identity, the broker increments the origin's `site_identity_generation`, so every handle for that origin changes and a re-granted device cannot be linked to the old one. The renderer sees only an opaque 128-bit handle and the API's own device attributes; it never sees the digest, the OS path, the file descriptor or the Bluetooth address.

### 6.3 WebUSB

**What the OS does.** The OS USB stack enumerates the bus, assigns addresses, reads the device, configuration, interface, endpoint and BOS descriptors, binds a driver, and performs control, bulk and interrupt transfers. On macOS the arbiter uses IOUSBHost with the `com.apple.security.device.usb` entitlement; on Windows, WinUSB for WINUSB-compatible devices or WinRT `UsbDevice` (which excludes eight classes), with the `usb` device capability in the AppContainer; on Linux, usbfs with a per-interface claim where the kernel allows it; on Android, `UsbManager` with a per-device OS consent dialog and a file descriptor to the arbiter ([DV-O 3.1–3.8][DVO]).

**What Izcal does.** The arbiter owns the device handle, selects the configuration, claims interfaces and performs transfers. The session parses the descriptors with `hg-device-usb-desc`, decides which interfaces and endpoints the page may see, enforces the API's transfer rules, and records. The renderer sees `USBDevice` with the spec's attributes; `configuration`, `configurations`, `opened`, `vendorId`, `productId`, `deviceVersionMajor/Minor/Subminor`, `deviceClass/Subclass/Protocol`, `serialNumber` (see 6.11), and `USBConfiguration`/`USBInterface`/`USBAlternateInterface`/`USBEndpoint` values parsed by us.

**Chooser and filters.** `requestDevice({filters, exclusionFilters})` is a chooser; the page's filters narrow the candidate list and can never widen it. `getDevices()` returns only devices with a live grant for this origin and container; it never lists the bus. A device is offered only if it has the WebUSB platform capability descriptor with UUID `{3408b638-09a9-47a0-8bfd-a0768815b665}`; the enumeration configuration checks the 24-byte descriptor. A device whose interfaces are all protected is shown with the reason "protected device class" and cannot be selected; a device with a mix of protected and unprotected interfaces is offered only for its unprotected interfaces, with the protected ones listed as unavailable.

**Protected classes.** The eight WebUSB protected interface classes are refused at grant time, not at `claimInterface()` time, and the refusal is stricter than the specification: Audio (0x01), HID (0x03), Mass Storage (0x08), Hub (0x09), Smart Card (0x0B), Video (0x0E), Audio/Video (0x10) and Wireless Controller (0xE0) ([DV-S 4.7][DVS]). Hubs are refused even though the spec permits the device, because a hub multiplies the attack surface and the permission model; a hub in the physical path (not the granted device) and DMA/IOMMU behaviour below the USB stack are OS and hardware responsibilities, outside the browser boundary; mass storage is refused because it is a filesystem the browser does not mediate; smart cards because they are a credential transport; HID because HID has its own API and its own input rules; audio/video because isochronous transfers are not exposed and the classes are OS-owned. `usb-unrestricted` is never enabled: Isolated Web Apps are not a Stage 1 or Stage 2 principal, and the corpus has no IWA support. A signed VID/PID/`bcdDevice` blocklist from `hg-device-policy` is applied before the chooser; it ships with the browser, is not remote code, and a device on it is shown as "blocked" with no override.

**Transfers.** Control, bulk and interrupt transfers are supported; isochronous endpoints are refused with `NotSupportedError`. This is a deliberate capability gap, not an API limitation: WebUSB exposes `isochronousTransferIn/Out`, and macOS IOUSBHost, Windows WinUSB/WinRT and Linux usbfs can support isochronous transfers; Android's support is limited, and a bounded, recordable isochronous path on all four platforms is the blocker (Q-DV-5). The compatibility cost is recorded, and the `NotSupportedError` path is tested. **A WebUSB grant is always write-capable**: the API exposes control, bulk and interrupt OUT on every claimed interface, and a page cannot be given a meaningful read-only USB grant, so the prompt class for an open is `device-write` (with `device-pairing` on the first grant), never a read-only `device-connection` prompt. A control transfer's `setup` packet is **filtered semantically**, not just range-checked. Standard requests that change device or interface state — `SET_CONFIGURATION`, `SET_INTERFACE`, `SET_ADDRESS`, `SET_DESCRIPTOR`, `SET_FEATURE`, `CLEAR_FEATURE` — are refused with `SecurityError`; `reset()`, `clearHalt()` and `selectConfiguration()` are the only paths that change those states, and each has its own ticket and consequence line. Class and vendor requests are allowed only on a claimed interface and within the ticket's signed scope. After any control transfer, the arbiter re-reads the active configuration and interface/alternate-setting map from the OS and compares it with its claim table; a mismatch closes the device with `NetworkError` and is recorded as a `claim-desync` event. The conformance suite includes raw `SET_CONFIGURATION`/`SET_INTERFACE` attempts and crafted `wIndex` values, and `fuzz_usb_claim` fuzzes the filter and the claim table. `clearHalt()`, `reset()` and `selectConfiguration()` are explicit operations; `reset()` and a configuration change require the `reset` capability, show a distinct consequence line, and are recorded with the affected interfaces. `claimInterface()` on an interface with a kernel driver bound shows "this will detach the system driver" and requires confirmation; the arbiter records `driverDetached`.

**Linux.** usbfs cannot scope a file descriptor to one interface; the arbiter opens the device and proxies every transfer, checking the claimed interface and endpoint against the ticket's signed scope in its own code. This is a security boundary in the arbiter (not the kernel), and it is why the arbiter's claim table is a target (DV-13). On Windows, a device bound to a non-WinUSB driver cannot be opened; the chooser explains the driver requirement instead of failing after selection. On macOS, the entitlement is present in the arbiter's code signature and absent everywhere else. On Android, the OS consent dialog is an additional layer under the broker prompt; both are required. If the USB permission dialog requires a broker-owned Activity (`PendingIntent`), that Activity is a broker-owned consent surface that passes the file descriptor to the arbiter; the arbiter remains the only process that uses the device fd, and the reading is recorded in 9.5 and resolved at DV-M0 (Q-DV-17).

**Disconnect and errors.** A bus disconnect invalidates every handle for that device, resolves `device.lost` with the OS error mapped to the API's error names, and records the event. A device that re-enumerates with a different descriptor is a new digest if its serial changed; otherwise it is the same grant and the session re-parses the new descriptors before any transfer, refusing a descriptor that narrows to a protected class after the fact.

### 6.4 WebHID

**What the OS does.** The OS HID stack parses the report descriptor, creates a device node, and routes input reports to the input subsystem. On Windows, HIDClass creates one physical device object per top-level collection; keyboard, mouse, pen, touch and precision touchpad collections are opened exclusively by the system and cannot be opened by an application. On macOS, IOHIDManager/IOHIDDevice expose devices and elements, and Input Monitoring TCC gates some access. On Linux, hidraw exposes a character device per HID device; there is no documented keyboard/mouse exclusion, so the kernel does not enforce what Windows does ([DV-O 4.1–4.7][DVO]). Android has no public HID API; WebHID is desktop-only.

**What Izcal does.** The session parses the report descriptor with `hg-device-hid-report` (Main, Global and Local items, Push/Pop, long items, report IDs, collections, input/output/feature items). It refuses any collection at **any depth** whose usage is an OS input source, and exposes only collections whose subtree contains none; a vendor-defined top-level collection with a nested keyboard collection is refused, not offered. The arbiter opens the device or collection and forwards reports; the session maps report IDs to allowed collections and rejects a report ID used by a refused collection at any depth, including a unique report ID inside a nested collection (a device that does either is refused entirely, because a malicious descriptor could otherwise smuggle an input report through an allowed ID or a top-level vendor collection).

**Refused collections.** Keyboard (Generic Desktop 0x06), mouse (0x02), pointer (0x01), joystick (0x04), gamepad (0x05), multi-axis controller (0x08), system control (0x80), consumer control (0x0C), digitizer/touch/pen (0x0D), precision touchpad, and FIDO (usage page 0xF1D0, usage 0x01) are refused as collections. The device may still be offered for a vendor-defined collection if it has one, but the chooser says: "This device can also type, move the pointer or act as a security key. The site will not receive those reports, but it may be able to reprogram the device." That is the VIA case: a keyboard's vendor collection is configurable while its keyboard collection is not. Any output or feature write to a device that also exposes a refused collection requires the `write` capability and the `device-write` prompt class; a read-only grant cannot reprogram it. A signed blocklist by top-level usage and VID/PID is applied before the chooser, beside the per-collection refusals.

**Reports.** Input reports are read-only. A HID grant is **read-only by default**: the first grant is `device-pairing`, a later session with a remember grant is `device-connection`, and the first `sendReport()` or `sendFeatureReport()` triggers a `device-write` escalation prompt that names the report and the device, and on approval adds the write capability to the live ticket. Report sizes come from the descriptor and are capped at 8 KiB‡; a report larger than the cap is refused. Report IDs default to 0 when absent. Boot-protocol devices that expose no report descriptor are not offered (the API requires a report descriptor); a boot subclass keyboard is refused even if it has one. Writes are recorded and rate-limited (one per 4 ms† per device, with a burst of 4†).

**Platform notes.** Windows gives per-collection handles; macOS gives elements but not a per-collection open, so the arbiter filters by usage and report ID; Linux hidraw is per device, so the arbiter filters and the session enforces the same map. The arbiter never forwards a report from a refused collection, even if the OS labels it as coming from an allowed element. On Linux, a device with no udev rule may be unreadable; the chooser explains the permission instead of failing silently, the detail is recorded as `os-permission-denied`, and the page sees a generic `NotAllowedError`.

### 6.5 Web Serial

**What the OS does.** The OS serial driver owns the UART or the USB CDC-ACM interface and exposes a character device (macOS `/dev/cu.*`, Linux `/dev/tty*` or `/dev/cu*`, Windows `COMx`), a handle (`SerialDevice` on WinRT), and termios/DCB settings. On Android there is no public serial API; a USB-serial adapter must be reached through USB host (CDC-ACM or a vendor protocol), so Web Serial on Android is a USB-host feature, not a tty feature ([DV-O 5.1–5.8][DVO]).

**What Izcal does.** The arbiter opens the port, applies the options, and holds the handle; the session applies the stream semantics, enforces read/write caps, records chunk boundaries and signal state. `requestPort()` is a chooser over OS serial ports; `getPorts()` returns only granted ports. Filters on `vendorId`/`productId`/`usbVendorId`/`usbProductId` narrow the list where the OS exposes them; for generic adapters there is no device metadata, which the spec itself admits ([DV-H 4.9][DVH]). For a port whose identity cannot be verified, the session marks the grant `port-only` and requires a `device-connection` prompt on every open; a differing VID/PID or USB serial closes the port with `NetworkError` and records `port-identity-mismatch`.

**Opening is a side effect.** Asserting DTR and RTS on open resets many boards (the Arduino auto-reset circuit is the common case). A serial grant is **write-capable by definition** (the API exposes `writable` on every port), so its prompt class is `device-write` (with `device-pairing` on the first grant), and the consequence says the site can write bytes that may reset, reconfigure or reflash the device. The chooser says "Opening this port may reset the connected device"; the grant scope "this time" is the default; the session records the initial line state and every `setSignals()` call. A reconnect after a read error never re-opens silently: the page must call `open()` again, and the session records the new open as a new segment of the recording with a `reopen` marker. This is the determinism rule from DT-D2 applied to a transport where reopening changes the device.

**Options and streams.** `SerialOptions` carries `baudRate` (required, 1 to 20,000,000‡), `dataBits` (7 or 8), `stopBits` (1 or 2), `parity` (`none`, `even`, `odd`), `bufferSize` (default 255, 1 to 1 MiB‡), `flowControl` (`none` or `hardware`). The arbiter validates the values against the OS backend and returns a typed error if the backend cannot represent them; it does not silently round. `readable` and `writable` are streams; a read returns at most the in-flight cap and preserves the arbiter's chunk boundary; a write is queued with backpressure. `getSignals()`/`setSignals()` map to modem-control lines; `setSignals` requires the `configure` capability and is recorded. `forget()` revokes the grant and closes the port.

**Refusals.** System consoles (`/dev/console`, `/dev/tty0`–`/dev/tty63`, the Windows debug port), virtual terminals, and the browser's own diagnostic ports are refused with "system console". A port whose OS path is a symlink outside the serial class is refused. A Bluetooth serial port (RFCOMM) is refused until a separate decision: Web Serial's spec has a Bluetooth service-class blocklist, but the transport is not a tty on any of our platforms and the Bluetooth API does not expose RFCOMM ([DV-S 6.2, 6.8][DVS]); it is Q-DV-7.

**Platform notes.** macOS may require no entitlement for `/dev/cu.*`, but the sandbox profile must allow the device node; this is measured in DV-M0 and is Q-DV-1. Linux needs the user to be in the `dialout` group or a udev rule; the chooser explains it. Windows needs the vendor's COM driver; a device bound to a different driver is not a serial port. Android, if it ships, uses `UsbManager` and CDC-ACM in the arbiter, with the OS consent dialog under the broker prompt.

### 6.6 Web MIDI

**What the OS does.** CoreMIDI on macOS enumerates sources and destinations, provides timestamps and virtual ports, and supports MIDI 1.0 and UMP; Windows MIDI Services (GA 17 February 2026, MIT) provides MIDI 1.0 and 2.0/UMP endpoints, with WinMM as the legacy path; ALSA rawmidi/seq on Linux provides raw and sequencer ports, including UMP via `snd_ump_open`; Android's `android.media.midi` provides inputs, outputs, virtual ports and BLE-MIDI ([DV-O 5.9–5.16][DVO]). The Web MIDI Working Draft exposes MIDI 1.0 byte messages, not UMP ([DV-S 7.1–7.6][DVS]).

**What Izcal does.** The arbiter enumerates OS endpoints and holds the handles; the session parses the MIDI 1.0 byte stream with `hg-device-midi-wire` (status bytes, running status, channel messages, system common, system real-time, SysEx with interleaved real-time bytes), maps receipt timestamps to the substrate clock, and records both the OS timestamp and the session receipt time. UMP is not exposed: an OS endpoint that delivers only UMP is configured, where the backend supports it, to translate to MIDI 1.0; if it cannot, the endpoint is not offered, with the reason "MIDI 2.0 endpoint not supported by this API". This is a deliberate capability gap, recorded in 11.

**Permission and enumeration.** `requestMIDIAccess()` prompts on every first grant, not only for SysEx. We do not require transient activation, because the Working Draft does not and many MIDI applications initialize on page load; the prompt is still a broker-owned high-risk decision, and the page gets no port list before it. The prompt lists the ports and says the site will see all of them; after approval, `inputs` and `outputs` contain every OS port. This is the one API where the spec's model is ambient enumeration after consent, and the spec's own privacy section calls enumeration a fingerprinting target ([DV-H 7.6][DVH]). We keep the API shape but make the grant explicit, visible and revocable; the all-ports choice is recorded as DV-D13, with a reversal trigger if the Working Draft gains per-port grants. `id` is a per-origin pseudonym of the OS endpoint id (6.11); `name` and `manufacturer` are the OS strings, because the API and every MIDI app depend on them, and they remain a residual fingerprint.

**SysEx.** A separate capability (`sysex`) and a separate high-risk prompt: "This site will be able to send System Exclusive messages, which can change or replace the device's firmware." The `{sysex:true}` request that is denied fails with `NotAllowedError`; without the capability, outgoing SysEx throws and incoming SysEx is masked, matching the Working Draft's two tiers ([DV-H 7.4–7.5][DVH]). The base grant **includes output**, because `MIDIOutput.send()` is synchronous and cannot await a prompt: `requestMIDIAccess()`'s prompt lists the ports, says the site can send data, and the first grant is `device-pairing` with the `device-write` consequence line (output is part of the grant from the start). There is no per-send escalation and no `NotAllowedError` from `send()`. SysEx remains a separate capability and a separate escalation from the base grant; a denied `{sysex:true}` request fails with `NotAllowedError`, and without the capability outgoing SysEx throws and incoming SysEx is masked, matching the Working Draft's two tiers. SysEx messages are recorded as sensitive values and redacted on export by default (6.12).

**Timing and hotplug.** Each `MIDIMessageEvent` carries `receivedTime`; the session records the receipt time and the OS timestamp separately. A port that disappears produces `statechange` and invalidates its handle; a port that reappears is a new endpoint id unless the OS keeps the id, in which case it is a new segment with the same handle. Virtual ports (IAC, loopMIDI, ALSA virmidi) are devices and are listed; a loop between an output and an input is detected by a per-session queue cap (1,024† queued messages, 4 MiB‡) and disconnected with `QuotaExceededError` rather than hanging the page.

### 6.7 Web Bluetooth

**The hard call: OS stack, not our own controller.** Web Bluetooth exposes GATT, not HCI: services, characteristics, descriptors, reads, writes, notifications, and a filtered chooser ([DV-S 8.1–8.9][DVS]). Every capability the API exposes is already provided by the OS stack on every platform we support: CoreBluetooth on macOS (with the Bluetooth TCC permission and usage description), WinRT GATT on Windows (with the `bluetooth` AppContainer capability), BlueZ over D-Bus on Linux, `BluetoothGatt`/`BluetoothLeScanner` on Android with runtime permissions from Android 12 ([DV-O 8.1–8.7][DVO]). An Izcal-owned controller and HCI stack would have to implement the link-layer controller, HCI, L2CAP, ATT, SMP, GATT, pairing, bonding, address privacy, coexistence and qualification on four OSes, and no ordinary desktop process can open HCI without root or `CAP_NET_ADMIN` ([DV-O 9.7][DVO]). The cost is not one stack; it is a Bluetooth silicon qualification programme and a permanent radio-coexistence team. The rejected alternative is **40–70† engineers over 5–6 years**, plus a radio lab and a qualification budget; the chosen OS-stack backend is **3–4† of the 6–8† device-boundary role** (CoreBluetooth, WinRT GATT, BlueZ D-Bus, Android BluetoothGatt), already counted in 9.3; the rest of the role is the arbiter, tickets, claims, proxy and the USB/HID/Serial/MIDI backends. The DV-D3 comparison uses the same units: 40–70† for an own controller/HCI stack versus 3–4† for the Bluetooth share. It is rejected on cost and on the absence of a user-mode HCI path, not on a preference for OS code.

**The OS radio stack is an external trust boundary.** BlueBorne, KNOB, BrakTooth and BLESA are OS, controller, firmware or bond classes that a browser cannot mediate; a malicious BLE device can compromise the OS below the arbiter. Izcal therefore requires a minimum patched OS version per platform (defined and checked at DV-M0), treats the OS ATT/L2CAP parser as an external parser it does not fuzz, and does not count `hg-device-gatt`'s fuzz hours as protection for the shipping GATT path — they protect the oracle and the promotion path. KNOB is a BR/EDR key-negotiation weakness present in the OS stack even though Web Bluetooth exposes GATT only; BLESA is a bond/reconnect weakness and is why a bond is never authentication (6.7).

**What Izcal writes.** The GATT client logic is ours: filter matching, service discovery policy, characteristic value assembly, notification and indication reassembly, descriptor access, blocklists, error mapping, disconnect and rediscovery. The **ATT/L2CAP codec** (`hg-device-gatt`) is also ours: ATT PDUs (Exchange MTU, Find Information, Read By Group Type, Read/Write, Prepare/Execute, Handle Value Notification/Indication), L2CAP framing and the fixed ATT CID 0x0004 and SMP CID 0x0006, built from the Bluetooth Core specification prose. On the shipping desktop path the OS stack performs ATT/L2CAP, so the codec is not exercised against a real controller there; it is exercised by the virtual-device oracle, by conformance tests against recorded GATT operation sequences, and by fuzzing. The shipping ATT/L2CAP parser is the OS's, and the codec's fuzz hours are not counted as protection for that path. We state this honestly rather than claiming a full GATT stack on the data path. If a platform ever exposes raw ATT PDUs, or if a future decision builds a controller stack, the codec is the piece that would be promoted; today it is a tested library and the oracle's protocol engine.

**Chooser and filters.** `requestDevice({filters, optionalServices, exclusionFilters})` requires a filter or `acceptAllDevices`; **`acceptAllDevices` is refused** with a `NotSupportedError` and a message ("choose the device type or name this site needs"). Filters can match service UUIDs, name, name prefix, manufacturer data and service data. The chooser shows the OS device name (sanitized), the matched services and the services the site requests; it does not show the address. `getDevices()` returns granted devices for the origin and container; `watchAdvertisements()` is allowed only on a granted device (connected or known to the OS), in a visible foreground page, after transient activation, and with a 30 s† cap per call; there is no passive scan, no `acceptAllDevices`, and no advertisement filter that runs while the chooser is closed.

**GATT policy.** Service discovery returns the services the page requested plus the mandatory Generic Access/Generic Attribute services. The following services are refused and filtered from the result: HID over GATT (0x1812), FIDO over Bluetooth (0xFFFD), Device Information's Serial Number characteristic (0x2A25) unless the identifier-exposure capability is granted, and any service on the signed blocklist. A connection grant is **read/notify by default** (`device-pairing` on the first grant, `device-connection` on a later session); the first GATT write, write-without-response, or descriptor write triggers a `device-write` escalation prompt and, on approval, adds the write capability to the live ticket. A read of a characteristic that the blocklist marks sensitive is refused. The session treats every characteristic value as attacker-controlled bytes and caps values at 64 KiB‡. `gatt.connect()` triggers OS pairing if the device requires it; the broker shows the `device-pairing` prompt before the call, and the OS may show its own pairing dialog underneath (GR-D28's two-layer model). A pairing passkey is shown in the broker prompt window, never in the page.

**Disconnect and rediscovery.** A disconnect invalidates GATT attributes; the session does not cache them across a reconnect and re-runs discovery, matching the platform behaviour that reconnect handling is the flaky part ([DV-G 3.3][DVG]). Notifications in flight are dropped with a recorded `disconnected` marker; a re-connect is a new segment. BLESA's lesson is recorded in the design: a prior pairing is not proof that the peer is the same device ([DV-H 9.5][DVH]); the session never treats a bond as authentication and never exposes link keys or addresses.

**Platform notes.** macOS requires the Bluetooth usage description and TCC; Windows requires the `bluetooth` capability and the radio on; Linux needs BlueZ and D-Bus, and adapter discovery is not root-only but mgmt operations are; Android needs `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT` and shows the OS permission dialog. If the adapter is off, the page gets the same `NotFoundError` and generic message as no match ("No matching device found"); the adapter state is shown in the chooser and the browser log, not in the `DOMException` text, because that text is page-visible. The page cannot turn the adapter on.

### 6.8 Web NFC

**Status, stated honestly.** Web NFC is a Chrome-for-Android capability. There is no desktop implementation in any browser; Core NFC exists on iOS and Mac Catalyst but not on macOS; Windows has a legacy proximity API and PC/SC for contactless readers; Linux has `AF_NFC`/netlink, neard 0.19 (2023) and libnfc (LGPL-3.0), none of which a desktop browser uses for Web NFC ([DV-O 6.1–6.8][DVO]). Izcal implements Web NFC **on Android only**, behind the `nfc` permission, and does not ship it until the Android backend and a second-engine or owner decision exist (DV-D9). The NDEF parser is built and fuzzed regardless, because the oracle and the conformance suite need it and because a future Android backend or a PC/SC extension would use it.

**What the OS does.** Android's `NfcAdapter` with reader mode and foreground dispatch performs RF discovery, tag activation and the tag-type protocol (Type 1–5); it may hand the app an already-parsed `NdefMessage` through the `Ndef` technology, or raw tag technologies ([DV-O 6.1–6.4][DVO]). The OS does not provide NDEF semantics beyond the message; the Web NFC model (records, TNF, `makeReadOnly`) is ours.

**What Izcal does.** The arbiter enables reader mode while a scan is active, with the tag technologies the API supports, and passes the tag's NDEF bytes and UID to the session. The session parses with `hg-device-ndef` (message begin/end, chunked records, TNF 0–5, type, id, payload, max 32 KiB‡), enforces the read/write/makeReadOnly rules, and records. If Android hands us a parsed `NdefMessage`, the session re-serialises and re-parses the records through our parser before exposing them, so the page-visible semantics are ours and the OS parse is treated as an OS interface, not trusted for structure.

**Permission and lifecycle.** `scan()` prompts once per origin/container for `nfc` (`device-pairing`); the prompt says "read and write NFC tags while this tab is in the foreground". There is no per-tag grant; each tap is a user action, but a page with focus can read any tag tapped while its scan is active. `scan()` stops when the tab is hidden, when the screen locks, or when the page navigates; no background reads. Each `write()` and `makeReadOnly()` requires a `device-write` confirmation that names the tag (a pseudonym or the UID with the identifier grant) and says "this cannot be undone" for `makeReadOnly`. The API's `serialNumber` returns a per-origin pseudonym of the UID by default and the true UID only with the identifier-exposure grant; a tag whose UID is random per read produces a new pseudonym per read, matching the device. The identifier-exposure grant has this-time/while-open/remember scopes; a remember grant (90 days† since last use, maximum 1 year†, a separate high-risk prompt with its own consequence line, visible and revocable) is the path for an inventory app that keys on the true UID across sessions. The default remains off.

**Trust.** An NFC tap is not authentication and not proof of proximity: relay attacks are live ([DV-H 9.7][DVH]). NDEF is unsigned and unencrypted by default; the spec itself says the content cannot be trusted beyond `makeReadOnly` ([DV-H 6.7][DVH]). The prompt and documentation say this; the browser does not use NFC for payments, access control or identity. The UID is not a secret and is not stable across tags. A signed historical-bytes blocklist from `hg-device-policy` is applied when the reader exposes the tag's historical bytes; a blocked tag is not offered. The `serialNumber` pseudonym is a deliberate deviation from the API's UID semantics: a site that uses the UID as a database key sees a per-origin value, and only the identifier-exposure grant restores the true UID. This is documented in the API notes and is the price of not handing every site a stable tag identifier on first tap.

**Desktop decision.** No Web NFC on desktop in Stage 1 or Stage 2. A PC/SC-based desktop backend (contactless readers through `pcscd`, an OS interface, not a shipped library) is a possible Stage 3 extension if demand and a second engine appear; it would still be NDEF-only and would need its own threat model for reader drivers. libnfc is not used: LGPL-3.0 is not MIT, and it is a raw reader library, not an OS interface (M-1).

### 6.9 Parsers

Every parser is Izcal's, written from the specification prose named in the table, in a tier-P crate, with no third-party parser, no code generation from a foreign schema, and no `unsafe` parsing loop. Each has an explicit input cap, an explicit allocation arena, no recursion (an explicit stack with a depth cap), no panics on any input (all indexing checked, all arithmetic checked, all lengths validated before use), and a fuzz target that runs in CI and in the pre-release audit.

| Crate | Format and anchor | Limits | Fuzz target | Weekly CPU-hours† |
|---|---|---|---|---|
| `hg-device-usb-desc` | USB 2.0 Chapter 9 device/config/interface/endpoint descriptors, string descriptors, BOS and platform capability; USB-IF class codes as data | 64 KiB‡ per descriptor set; 256 KiB‡ per device; depth 2; interfaces ≤ 64†; endpoints ≤ 256† | `fuzz_usb_desc` (bytes → typed descriptor or typed error) | ≥ 1,000† |
| `hg-device-hid-report` | HID 1.11 report descriptor items, HID Usage Tables 1.7 (JSON as data) | 64 KiB‡ descriptor; collection depth ≤ 32†; collections ≤ 1,024†; report count ≤ 4,096†; report size ≤ 8 KiB‡ | `fuzz_hid_report` (descriptor → collection tree or typed error) | ≥ 1,000† |
| `hg-device-gatt` | Bluetooth Core 6.0/6.1: ATT PDUs (Vol 3 Part F), L2CAP framing and fixed CIDs (Vol 3 Part A), GATT procedures (Vol 3 Part G) | PDU ≤ 64 KiB‡; MTU 23–517†; attributes ≤ 4,096† per service; notification queue ≤ 1,024† | `fuzz_gatt_pdu`, `fuzz_gatt_value` | ≥ 500† |
| `hg-device-ndef` | NFC Forum NDEF 1.0 and RTD prose; TNF 0–5; chunked records; nested messages | 32 KiB‡ message; records ≤ 256†; total decoded records ≤ 512†; nesting depth ≤ 4†; type ≤ 255 B‡; payload ≤ 32 KiB‡ | `fuzz_ndef` (nested, chunked and depth-bomb cases) | ≥ 500† |
| `hg-device-midi-wire` | MIDI 1.0 Detailed Specification (1996 revision): status, running status, channel voice, system common/real-time, SysEx | 64 KiB‡ message; SysEx ≤ 64 KiB‡; interleaved real-time allowed | `fuzz_midi` | ≥ 500† |
| `hg-device-policy` | Signed blocklist and policy document (own format, spec-anchored): USB VID/PID/class entries, HID usages, GATT UUIDs, serial classes, device names | 1 MiB‡ document; entries ≤ 16,384†; signatures verified before parse | `fuzz_device_policy` | ≥ 250† |

`hg-device-gatt` also contains the ATT client state machine the oracle needs: MTU exchange, service and characteristic discovery, read/write with and without response, prepare/execute for long writes, and notification/indication reassembly, with the L2CAP channel state (fixed CID 0x0004, MTU 23–517†) and the SMP CID 0x0006 reserved. On the shipping desktop path the OS stack owns that state; the codec and state machine are exercised by the oracle and the conformance suite, and would be promoted if a raw ATT interface appeared (6.7, DV-D12). All parsers return typed errors with offsets and never echo unbounded device strings into a page; names are length-prefixed, control characters removed, bidirectional overrides rejected, and UTF-8 validated. The HID corpus includes nested vendor/keyboard collections and report IDs shared across allowed and refused collections. The parsers are also the oracle's protocol engine: the virtual device composes bytes with the same crates, so a test can generate a descriptor or PDU that the shipping parser must reject, and a replay can compare the parser's output on recorded bytes with the live result. The corpus is built from the standards data (HID Usage Tables JSON, USB-IF class codes, Bluetooth Assigned Numbers, NFC RTD names), Izcal-authored fixtures, and test-only WPT fakes with their licences recorded in `tools/device-corpus/LICENSES.md`; no corpus is shipped as browser data (G217, FP-D13).

### 6.10 Permissions, prompts and the chooser

**One grant model for six APIs.** A grant is a record in the broker's permission store, keyed by:

```
(frame_origin, top_level_site, container_id, family, device_digest)
```

and carrying a capability set, a scope, a creation time, a last-used time, an expiry, a prompt reference and a policy source. The renderer never holds the grant; it holds a typed handle bound to a broker endpoint. The broker is the only writer of the grant table; the arbiter and session receive only the ticket that derives from it.

| Scope | Lifetime | Survives reload | Returned by `getDevices()`/`getPorts()` | Use |
|---|---|---|---|---|
| **This time** | Until the document's BCG is discarded or the device closes | No | No | Default for a first use, a shared machine, a kiosk |
| **While open** | Until the device disconnects or the page calls `forget()` | No | No | A long session with one device |
| **Remember** | 90 days† since last use, maximum 1 year†; revoked on clear-site-data, site-identity change, or manual revocation | Yes | Yes | A device the person uses repeatedly on one site |

Persistent grants are capped at **16† per origin** and **64† per profile**; a new request beyond the cap shows the oldest grant and asks the person to revoke one. Persistent grants are returned by `getDevices()`/`getPorts()` without a prompt, but **using** one still prompts: the first open or connect in each browser session is a `device-connection` prompt, and its "Don't ask again" control upgrades that grant to silent connection in later sessions. The control is off by default and appears only after the person has used the device at least twice; it is stored on the grant and is cleared by any scope change. This is deliberately stricter than the six APIs, which reconnect silently once a grant exists: listing a device is not using it, and a live channel deserves a fresh decision. Persistent grants are off by default in the chooser; the "Remember" control is a second interaction after "Connect", and the confirmation states the 90-day† expiry. Incognito windows never offer "Remember", never return prior grants, and delete the grant when the window closes. A grant is bound to the origin string, not the registrable domain; a domain that changes hands inherits nothing after the 90-day† expiry, and clear-site-data removes it immediately (6.11 states the residual risk).

**The prompt classes.** Three new high-risk classes join the shell's 6.4 table (amendment in 9.5):

| Class | When | What it says | Risk |
|---|---|---|---|
| **device-pairing** | The **first** grant for a device (any scope), or an OS pairing/bonding step. When the first grant is also write-capable, the same prompt adds the `device-write` consequence line and the ledger records both classes; an identifier-exposure grant adds its own line ("will see the hardware serial number / tag UID, which can identify the device across sites") | "Allow example.com to connect to [device]? This device can [capabilities]. The device may be able to reprogram itself or other devices." | High: it establishes the site-device relationship and may persist |
| **device-connection** | The first open or connect in a browser session for a device the site already has a remember grant for (listing it in `getDevices()` is not a connection) | "Allow example.com to connect to [device] again? It will be able to read [family] data while this tab is open." A "Don't ask again" control makes later sessions silent for this grant | High: a live channel to hardware, even with a prior grant |
| **device-write** | A grant or escalation that includes writes: every USB and Serial open; the first MIDI access (output is in the base grant); the first HID output/feature report, GATT write, or NFC write/`makeReadOnly()` | The consequence is capability-specific: *data write* — "can send data to the device; this may change its state"; *configuration write* — "can change the device's settings; this may not be reversible"; *firmware/SysEx* — "can send firmware-level messages that may replace the device's firmware; this may be irreversible"; *NFC write* — "can write this tag; makeReadOnly cannot be undone". | High: physical, possibly irreversible |

One consequence line for every write is wrong: a MIDI note does not alter firmware and a USB LED does not. The class stays high-risk, but the text is chosen by capability and device class; `sysex`, firmware-write control transfers and `makeReadOnly` get the firmware/irreversible line. This keeps the one prompt that matters from being diluted by prompts that overstate.

All three are high-risk under A-SH-12. Until AX-D11 implements person-present evidence, an AT-invoked approval is **not accepted** for any device prompt; the AT action moves focus to the prompt only. When AX-D11 ships, a high-risk device approval is accepted only with AX-D11's evidence: a broker-observed physical input in the same window within 30 s†, or an OS-attested assistive state the user turned on (VoiceOver, Switch Control, Voice Control, Narrator or Voice Access as UIAccess-signed processes). That is the non-keyboard path for voice and switch users; the chooser remains fully keyboard-operable in the meantime. Because no device API gets general exposure in Stage 1 (6.15), the gap is bounded to the per-origin setting, and DV-E5/DV-E6 are conditioned on AX-D11 shipping or an explicit owner acceptance of the gap.

**Capability escalation is a prompt, not a silent widening.** A read-only HID or GATT session that calls its first write gets a `device-write` prompt for that device and capability; on approval the broker mints a new ticket with the added capability, the arbiter re-verifies it, and the ledger records the escalation with the prompt reference. A denial leaves the session read-only and returns `NotAllowedError` to the call. USB and Serial are write-capable at open, so there is nothing to escalate; their open is `device-write` from the start, with `device-pairing` on the first grant. NFC has no per-tag grant: the grant is keyed by (origin, top-level site, container, `nfc`, digest **zero**), and each write or `makeReadOnly()` is a per-tap `device-write` confirmation that names the tag pseudonym and, for `makeReadOnly`, says it cannot be undone (6.2, 6.8).

**Prompt anatomy.** The device prompt uses the shell's **SH-D2** prompt surface, and where the OS shows its own permission dialog above it (Bluetooth pairing, Android USB consent), that is the **GR-D28** OS prompt layer; Izcal's decision is the broker prompt, not the OS dialog. The broker-owned window shows, in this order: the requesting origin and the top-level site if different; the container (normal, work, school, incognito); the device label and family; the capability list in plain language ("read data", "send data", "change settings", "send firmware-level SysEx", "write NFC tags", "make tags read-only"); the scope options; the consequence line for the class; and the "what this does not protect" line ("A device can be malicious; a grant does not make it safe"). The device label is formatted by the broker from sanitized fields; no page string appears except the origin and URL, which the broker formats itself (CON-R2). The chooser has **no default selection**, requires a selection plus a separate Connect/Allow action, and cannot be submitted with Enter from the initial focus. The window is visible and unoccluded for ≥ 500 ms† before it accepts input, and it stays until decided; there is no 30 s† low-risk expiry because every device class is high-risk.

**Chooser behaviour.** The chooser lists only candidates matching the page's filters (or all WebUSB/Serial/HID candidates if there are no filters); the page cannot add a candidate, pre-select one, or learn the list before approval. It is one prompt at a time (SH 6.4). It is broker-owned; the page cannot draw, move, resize, cover or read it. A second prompt for the same origin/family while one is open is queued, and the page receives `InvalidStateError` if it retries more than once per 2 s†. Three denials in 60 s† trigger a 30 s† cooldown for that origin/family.

**Protected classes and refusals.** The following are refused before a prompt is drawn, with a specific message:

| Family | Refused | Why |
|---|---|---|
| USB | The eight protected interface classes (0x01, 0x03, 0x08, 0x09, 0x0B, 0x0E, 0x10, 0xE0); hubs; mass storage; smart cards; wireless controllers | OS-owned, credential-bearing, filesystem-bearing, or an input path; `usb-unrestricted` is never enabled |
| HID | Keyboard, mouse, pointer, joystick, gamepad, multi-axis, system control, consumer control, digitizer/touch/pen, FIDO | OS input or credential path; the Gamepad API owns gamepads |
| Serial | System consoles, virtual terminals, the browser's own diagnostic ports, RFCOMM ports | Host console or unsupported transport |
| MIDI | Nothing at the port level; SysEx is a separate capability | The API's own two-tier model |
| Bluetooth | HID over GATT (0x1812), FIDO over Bluetooth (0xFFFD), the Device Information serial-number characteristic (0x2A25) without identifier exposure | Input, credential, and identifier paths |
| NFC | Nothing at the tag level; write and `makeReadOnly` need `device-write` | NDEF only; no HCE, no peer-to-peer, no payments |

**Enumeration gating.** Before a grant, no API returns a device list: `getDevices()` returns an empty list (not the bus), `getPorts()` the same, `requestDevice()`/`requestPort()` open a chooser, `requestMIDIAccess()` prompts and returns ports only after approval, and NFC has no enumeration at all. `getAvailability()` is constant `true` on any build with a Bluetooth backend and `false` only on a build without one, so the page cannot learn whether a radio is present or powered from it. A device count, a "no devices found" message timing, or an error code that distinguishes "no adapter" from "no match" is a fingerprint; the chooser shows "No matching devices" only after the scan window, and the error is `NotFoundError` for both.

**Policy.** The feature tokens are `usb`, `hid`, `serial`, `bluetooth` and `midi`, each defaulting to `'self'`; `usb-unrestricted` is parsed and always resolves to `'none'` (Isolated Web Apps are not a principal). NFC has no token in its specification, so it is top-level-only and requires a visible foreground page; an iframe cannot use it. A cross-origin iframe with a delegated token still gets its own chooser, its own origin in the prompt, and its own grant; the top-level site is shown, not substituted. An opaque-origin frame (sandboxed without `allow-same-origin`) is refused all six, because its origin cannot key a grant.

**Workers and lifecycle.** Device APIs are exposed to `Window` and, where the IDL allows it, dedicated workers; they are **not** exposed to service workers or shared workers, because a service worker outlives the page and would turn a device grant into a persistence and background-scan channel. A dedicated worker's device calls are attributed to its owner document's origin and container and die with the worker. A page that becomes hidden keeps its handles but receives no new events: NFC scans stop, Bluetooth advertisements stop, and a session buffers at most 256† events or 1 MiB‡ before disconnecting with `QuotaExceededError`; a frozen page receives nothing and its session exits. Device events never wake a frozen page (DV-10). A page with an open device is not eligible for the back-forward cache; a prerendered page cannot request a device until it is activated, and activation discards the prerender if a device prompt is needed.

**Site data and revocation.** The site panel gets a **Devices** section: one row per grant with the family, the sanitized label, the scope, the last use, and a Revoke action; "Forget all devices" revokes every grant for the site and rotates its handle generation. Clearing site data deletes the grants, rotates the handle generation and closes open handles; the prompt ledger retains the decision metadata for 90 days† as a security record with the device label and digest removed. `forget()` from the page has the same effect for that device. A revocation is immediate: the broker marks the grant dead, sends `DeviceRevoke` to the arbiter and session, and the next page call gets `NotFoundError`; an in-flight transfer completes or is cancelled with `AbortError`, and the cancellation is recorded.

**Permissions API.** `navigator.permissions.query()` reflects `usb`, `bluetooth`, `midi` (and `midi` with `sysex:true`) and `nfc` where the API defines a descriptor; `granted` means a live grant exists, `prompt` means a chooser is possible, `denied` means policy or a persistent denial. There is no `permissions.request()` for a device: the chooser is the only request path. HID and Serial have no descriptor in their specifications, and we add none; their state is visible in the site panel and DevTools, not through the Permissions API.

**Enterprise.** Every family has a policy key: `DeviceUsbPolicy`, `DeviceHidPolicy`, `DeviceSerialPolicy`, `DeviceMidiPolicy`, `DeviceBluetoothPolicy`, `DeviceNfcPolicy`, each with `ask`, `block` and `allow-once` values; the default is `ask`, and a managed profile's `block` wins over a page request. A signed policy may pre-grant a specific device (VID/PID or OS identity) for a specific origin only when the administrator enables `DevicePreGrantEnabled`; pre-grant is off by default, cannot cover a protected class, cannot grant identifier exposure, and is shown in the site panel and the ledger as `policy-allow` with the policy id. A pre-granted device still shows the active indicator and can be revoked by the person. Silent pre-grant by a page is impossible; only a signed policy can do it, and it is visible.

### 6.11 Identifiers, fingerprinting and linkability

The API surface exposes device attributes by specification: USB vendor/product/version/class and `serialNumber`; HID vendor/product and collections; Serial vendor/product where the OS gives them; MIDI names, manufacturers and ids; Bluetooth name, id, GATT services and advertisement data; NFC `serialNumber` (the UID). Some of these are model constants (VID/PID, GATT UUIDs, names) and cannot be normalised without breaking the API; some are unique (serial numbers, UIDs, Bluetooth addresses, MIDI endpoint ids) and can be pseudonymised. The design does the second and documents the first.

| Attribute | Exposure | Mitigation | Residual |
|---|---|---|---|
| USB VID/PID/version/class | Always, as the API requires | None; model-level only | Identifies a device model, not a person; combinations can be rare |
| USB `serialNumber` | Only with `identifier-exposure`; otherwise `null` (`""` only for an actual empty serial string) | Per-origin grant, high-risk prompt, this-time by default, remember only by explicit choice | A granted site can fingerprint the exact device; the grant is visible and revocable |
| HID VID/PID, collections | Always | Input collections refused; names sanitized | Model-level |
| Serial VID/PID, port label | Where the OS exposes them; the port label is shown in the chooser but not exposed as a stable id to the page | `id` is a pseudonym; no serial number in the API | Port label can contain a location; the chooser shows it to the person, not the page |
| MIDI `id` | Pseudonym per origin/container | HMAC of the OS endpoint id | `name`/`manufacturer` can identify a rig; the prompt lists the ports |
| Bluetooth `id` | Pseudonym per origin/container | Never the address; OS identity stays in the arbiter | Name, GATT services and advertisement payloads can identify a model or a device |
| Bluetooth advertisement | Only for a granted, connected device, foreground, 30 s† | No passive scan; no `acceptAllDevices` | RSSI is location-adjacent; payloads are device-controlled |
| NFC `serialNumber` | Pseudonym by default; true UID only with `identifier-exposure` | Per-origin HMAC; random-per-read tags produce changing pseudonyms; a remember identifier grant restores the true UID across sessions | A tag UID is stable for many tags and can identify an object or a person |
| Device names | Sanitized strings | Control chars removed, bidi rejected, length capped | Names are device-controlled and can contain arbitrary text; a malicious device can encode an identifier in its name. The chooser shows the name; the page gets it only after a grant |

**Linkability targets.** Two origins with grants to the same physical device must not be able to tell, from API-visible values, that it is the same device, except through model-level attributes that the API requires (VID/PID, names, GATT UUIDs). The handle, the `id` fields and the NFC pseudonym are per-origin and per-container. DV-6's 1% target covers the pseudonymised attributes only; the API's own model-level surface is measured and reported separately, so a passing DV-6 is not a clean bill of health for the API. A device grant is not transferable to another container or profile. Clearing site data rotates the handle generation, so a re-grant is unlinkable to the old grant; the 90-day† expiry does the same. No cross-origin device event exists: a notification is delivered only to the session that holds the grant.

**Ordering and timing.** Every API that returns a list returns it in a defined order: USB/HID/Serial/Bluetooth by the broker's opaque handle (a stable sort, not the OS enumeration order), MIDI by the OS endpoint id after pseudonymisation, NFC no list. The first call after a grant is padded to a 50 ms† floor so a fast device does not reveal its class through timing; subsequent calls are not padded. Chooser scan duration is fixed per family (2 s† for USB/HID/Serial, 5 s† for Bluetooth) regardless of how many devices are present, and the "No matching devices" message appears at the same time whether the bus is empty or filtered out. A device connect event is delivered on the substrate clock, not the OS clock, so a replay can reproduce it.

**What we do not claim.** No published study measures enumeration entropy for these APIs ([DV-F 8.7][DVF]); the target DV-6 measures our own linkability with a test corpus, not a population. The residual fingerprint is the API's own model-level surface, and the only complete fix is not shipping the API; the spec chooses the mitigations above and states the residual in 10.

### 6.12 Determinism, recording and replay

**Device I/O is external nondeterministic input.** It enters the engine as typed values at the device-service boundary, on the substrate clock, in an order the session observes. The arbiter does not make page-visible decisions: it forwards bytes, connect/disconnect events, adapter state and OS errors. The session decides what the page sees; the recorder records what the session received and what the page called, so a replay can reproduce both.

**Recorded inputs.** For every family, the recording contains: the API calls the page made (method, arguments, promise outcome), the grant and prompt decisions, the device descriptor snapshot at recording start, the typed device events (transfers, reports, chunks, messages, GATT operations, NDEF records), the OS errors, the adapter/pairing state, the session's capability set, the recording nonce and the family/OS backend version. Bytes are recorded as values; chunk boundaries and receipt times are recorded separately. The recording is at the **device-service boundary**, not the API boundary, because the parser's input is where the bugs and the semantics are ([DV-R 3.1][DVR]).

| Family | Recorded as values | Sensitive: encrypted at rest, redacted on export | Never recorded | Replay |
|---|---|---|---|---|
| USB | Descriptor bytes, control setup and data, bulk/interrupt in/out, endpoint, status, timestamps, configuration/claim/ reset events | Control OUT data that writes firmware or configuration is labelled `device-write`; redacted on export by default | Serial strings (only a presence bit), OS device paths, bus addresses | Virtual USB device with recorded descriptor and transfer schedule; no OS path |
| HID | Report descriptor, report ID, report data, direction, timestamps | Output/feature reports labelled `device-write`; health/sensor reports labelled `sensitive` | Keyboard/pointer/FIDO reports are never recorded because they are never delivered | Virtual HID device; report IDs map to recorded collections |
| Serial | Bytes with chunk boundaries, options, signal state, open/close, resets, errors | Console login text is not detectable; the export dialog warns and offers a redaction range | Port path, serial number | Virtual serial port; chunk boundaries and timing preserved |
| MIDI | Bytes, port, direction, receipt and send timestamps, OS timestamp, port state | SysEx labelled `sensitive`; export redacts by default | Device serial number if the OS exposes one | Virtual MIDI port; times replayed on the substrate clock |
| Bluetooth | GATT operations (discover, read, write, notify, indicate), values, UUIDs, disconnect/reconnect, advertisement data only if watched, RSSI labelled `hardware` | Health services (Heart Rate 0x180D, Blood Pressure 0x1810, Health Thermometer 0x1809) labelled `sensitive` | Addresses, bond keys, pairing passkeys, OS device identifiers | Virtual GATT peripheral; OS stack not opened |
| NFC | NDEF record structure (TNF, type, id length, payload length), read/write/makeReadOnly, tag presence, timing | Tag payload is **never recorded by default**; a per-session "record tag payloads" option (typed confirmation, encrypted at rest, never exported) exists for a developer who needs it | Tag UID (a pseudonym is recorded), tag payload by default | Virtual tag; payload redacted means replay shows a placeholder and marks "approximate from that point" |

**Event classes and decision points.** Connect, disconnect, reset, configuration change, adapter on/off, pairing request, pairing passkey, GATT disconnect, NFC tag enter/leave, scan start/stop, and every OS error are decision points: the session records the value and the time, and the substrate schedules the page-visible consequence at that recorded time. A transfer completion whose order depends on OS scheduling is recorded in the order the session observed; a replay that would observe a different order diverges and is flagged. Timeouts (chooser scan window, 30 s† advertisement cap, 500 ms† prompt floor) are substrate timers, recorded as decisions, not wall-clock reads.

**Recording unit and start.** A device recording is a per-process stream joined to the tab's recorded session (DT-D2) by the tab's `recording_id`: it starts at the renderer's process launch, in a fresh device session with a recording nonce, and it ends with the session. The replay group joins the renderer stream and the device stream by `(recording_id, session_id, sequence)`; ordering is by recorded substrate time, ties broken by stream order then sequence. A missing or truncated device stream is a divergence and is reported at the first missing record. If a device is already open when recording starts, the recorder captures a descriptor snapshot and a "present at start" record, then records bytes from that point; the replay starts with the device present in that state and the UI labels it "device present at start". A device session opened during a recording but not created by the recorded page (for example, another tab's) is not part of the recording; the recorder labels the boundary and the replay refuses a call that would need it.

**Placeholders.** A redacted value is a typed placeholder, not an empty value (`Redacted<DevicePayload>`, G11). Where the live page received a redacted value, the replay delivers the same typed error. Where the live page received a real value that the recording did not retain, the replay cannot supply it: it marks the point "approximate from that point" and compares the remaining recorded outputs only where they do not depend on the missing input. The UI shows a marker on the timeline at the first placeholder ([DT-D2][DT]).

**Replay.** `hg-device-replay` is a separate crate with no dependency on `hg-substrate-os` device backends (G216). It constructs a virtual device from the recording and feeds the session; it never calls an OS device interface, and a runtime probe asserts zero device syscalls during a replay (DV-8). The replay host holds no device service, the way NW-37's dedicated replay host holds no network service: a replay cannot re-open a device even if a page calls `requestDevice()` outside the recording, because the call meets the replay graph and returns `NotInRecordingError`. A page call that is not in the recording returns `NotInRecordingError`; a write whose recorded counterpart differs returns `ReplayDivergenceError` with the first differing offset and timestamp; a call to a device that was not in the recording is refused. Outgoing writes are compared by hash and length, not replayed to hardware. The DevTools UI labels the session "virtual device" and the recording's fidelity: **exact** for bytes, order and recorded times at the device-service boundary; **approximate** after a placeholder; **not claimed** for physics, RF, firmware behaviour, OS scheduling and wall-clock latency. The claims are printed in the export header so a bug report cannot overstate them.

**What is not recorded.** The prompt's pixels, the person's input, the page's keystrokes, the OS pairing dialog, the firmware's internal state, the radio environment, the device's power state, and any value below the OS interface. A replay of a Bluetooth session cannot reproduce a weak signal; it reproduces the GATT operations the OS delivered.

### 6.13 DevTools and the virtual-device oracle

**A device domain.** The Inspector protocol gets a `devices` domain with subdomains `device.usb`, `device.hid`, `device.serial`, `device.midi`, `device.bluetooth` and `device.nfc`. Commands: `enable`/`disable`; `listGrants` (origin, family, label, scope, last use); `revokeGrant` (person-present in the UI, not callable by a page); `listDevices` (real devices visible to the profile plus virtual devices; the real list is broker-filtered and shows no addresses); `attachVirtualDevice`/`detachVirtualDevice`; `setFault` (stall, nak, short packet, malformed descriptor, disconnect at offset, GATT error, NFC malformed NDEF); `exportRecording`/`importRecording`; `snapshot` (descriptor and parser tree). Events: `deviceAdded`, `deviceRemoved`, `grantChanged`, `promptShown`, `promptDecided`, `transfer`, `report`, `chunk`, `midiMessage`, `gattOperation`, `ndefRecord`, `adapterState`, `divergence`. The domain is part of IIP, not a separate protocol; cost classes are declared (`device.attach` heavy, `device.export` heavy, `device.snapshot` light), and an agent's access is scoped by DT-13: an agent may read grants and events for its task, may not revoke a grant, may not enable tag-payload recording, and may not attach a virtual device to a page it does not own.

**The virtual device.** `hg-device-sim` is a library and a CLI (tier T). It implements a virtual USB device (descriptors, endpoints, control/bulk/interrupt queues), a virtual HID device (report descriptor and reports), a virtual serial port (byte stream with configurable chunking and line states), a virtual MIDI port (bytes with timestamps), a virtual GATT peripheral (services, characteristics, ATT PDUs through `hg-device-gatt`), and a virtual NFC tag (NDEF records, UID policy). It shares the parsers with the shipping code, so a descriptor the simulator emits is parsed by the same code the browser uses. A scenario is a declarative sequence: `at t=0 present device; on open return descriptor D; on control 0x80 0x06 return bytes; on read return chunk; at t=500 disconnect`. Faults are first-class: malformed descriptors at every offset, oversized reports, short packets, stalls, NAKs, GATT errors, unsolicited notifications, tag removal mid-write, and a disconnect during a firmware write.

**Test-only bindings.** The WebUSB Testing API (`navigator.usb.test`), Web Bluetooth's `FakeBluetooth`, and Web NFC's test interfaces are **test-build-only**, never in a stable build, and never in a release binary. The stable browser's virtual device is reachable only through DevTools and the chooser's "Virtual device" entry, which is visible only when the developer setting is on; a normal page cannot detect it except by the API's presence, and the setting is constant per profile so it is not a per-site fingerprint. The CI harness is a WPT-style runner in the test build: `navigator.usb.test`, `FakeBluetooth` and `WebNFCTest` drive the shipping session and API, and the `device-smoke` job runs the virtual USB/HID/serial/MIDI/GATT/NFC devices against it on every change. No test binding exists in a release binary. This avoids the Chrome mistake of a fake that is either absent from stable or visible to pages in it ([DV-G 3.1–3.2][DVG]).

**The oracle.** `hg-device-fuzz` drives the parsers with generated and mutated inputs; `hg-device-sim` drives the session with protocol scenarios; a conformance suite drives the session with spec-derived vectors (valid and invalid) and compares typed outputs. The three are the pre-release oracle for SEC-24. Hardware-lab smoke tests run on real devices (USB, HID, serial, MIDI, Bluetooth) on a self-hosted runner, not in hosted CI, and are recorded and replayed when they fail.

**Virtual devices are not a security boundary.** A virtual device is a test source, not a trusted one: it goes through the same parser, the same capability checks and the same recording. A replay is a virtual device; it is labelled as such in the page's DevTools overlay only (not in the page), and it never satisfies a real-device presence check that the page performs through the OS (the page cannot perform one).

### 6.14 Agents and extensions

**Agents (B9).** An agent gets device access only through a typed intent: `device.request {family, purpose, label_hint, capabilities, task_id}`. The broker resolves the task principal, checks that the task has a person present, draws a `device-pairing` prompt that names the agent, the task and the requested capabilities (adding the `device-write` consequence line when the set includes writes), and lets the person choose the device in the same chooser. The resulting grant is keyed by the task id as well as the origin/container/device, expires when the task ends or after 1 h†, whichever is first, and is never persistent. An agent cannot call `getDevices()` to inherit the person's grants, cannot use a grant the person gave the page, and cannot run a device intent in an unattended task: the intent is refused with `NotAllowedError` and the refusal is recorded. Every agent device action is visible in the agent activity log and the device ledger with an `agent` badge; revoking the task grant kills the session immediately. The intent schema is the only path; there is no agent API that takes a device handle.

**Extensions.** The six device APIs are **not** exposed to extension pages, content scripts, service workers or an extension API. The extensions spec's Ring C — "OS and vendor surfaces without an Izcal owner yet" — is amended (9.5) to add the documented `chrome.*` device namespaces `usb`, `hid`, `serial`, `bluetooth`, `bluetoothSocket` and `bluetoothLowEnergy` to the refused list, beside `captivePortal`, `power`, `fontSettings` and `input.ime`, and a separate rule refuses the six web APIs (including `nfc` and `midi`) to extension pages, content scripts and workers; `nfc` and `midi` are web API names, not extension namespaces; none of the device namespaces gains an owner in this spec, and the existing `power`, `input.ime` and `captivePortal` rows stay refused and unowned. This refusal is about extension origins and extension APIs. A content script that injects a main-world script into a page with a device grant can use the page's handle: a grant is to the origin, and the person's approval covers scripts running in it. The boundary therefore relies on the extension platform's main-world injection rules and the page-origin trust model (extensions spec 6.x); if main-world injection is allowed, the broker cannot distinguish the page's own script from an injected same-origin script, and the device grant is no stronger than the page's origin. This is recorded in 9.5.8 and 10. An extension that wants device access would need a new specification, a manifest permission, a user grant and an owner decision; the default is refusal, and the Ring C rule means a namespace cannot be added by an implementation change alone.

**Protocol-owned devices stay owned.** FIDO/CTAP remains in the credential subsystem (WebAuthn), not raw HID: WebHID refuses the FIDO usage, WebUSB refuses the HID class, and Web Bluetooth refuses the FIDO service. Payments stay in Payment Request; NFC is NDEF-only, with no HCE and no peer-to-peer. Gamepads stay with the Gamepad API; WebHID refuses gamepad collections. A future "device-class" API that wraps a protocol (a firmware-update API, a MIDI 2.0 API) is a new surface with its own spec, not a widening of these six.

### 6.15 Exposure: what ships when

The corpus's admission rule, ST-D18 as LY-D10 applies it, admits an editor's-draft feature when it has a WG resolution and WPT tests and either ships in two engines or is an Interop focus area; data structures are built general from the first milestone. The six APIs are not editor's drafts in one venue, and their engine counts differ, so the rule is applied per API. Two terms are defined so the rule is applied, not interpreted: **ships** means enabled by default in a stable release for ordinary users — an implementation behind an add-on install, a developer flag or an enterprise-inactive default does not count; **WG resolution** means a recorded working-group decision (a Candidate Recommendation or an explicit resolution minute), not the existence of a Working Draft.

| API | Venue and status on 21 October 2026 | WG resolution | WPT tests | Engines | ST-D18 verdict | Stage and exposure |
|---|---|---|---|---|---|---|
| **Web MIDI** | W3C Working Draft, 20 October 2026, Audio WG, Recommendation track ([DV-S 1.4][DVS]) | Audio WG deliverable; no recorded resolution (Q-DV-16) | Yes (MIDI and SysEx IDL/API tests) | Chrome 43+; Firefox 108+ behind a site-permission add-on, not default-on ([DV-G 2.3][DVG]) | **Does not meet as written** (no recorded WG resolution; one default-on engine) | **Stage 1 experimental setting only**; general exposure only with DV-E5 |
| **Web Serial** | WHATWG Living Standard, 19 October 2026 ([DV-S 1.3][DVS]) | A standard, not an editor's draft; the rule's first limb is satisfied a fortiori | Yes, but hardware-gated (manual serial tests) ([DV-R 4.12][DVR]) | Chrome 89+ desktop; Firefox 151+ desktop behind an add-on, not default-on ([DV-G 2.2][DVG]) | **Does not meet as written** (one default-on engine) | **Stage 1 experimental setting only**; general exposure only with DV-E6 |
| **WebUSB** | WICG Draft CG Report, 5 June 2026; no WG ([DV-S 1.1][DVS]) | None | Yes, including the test API | Chrome 61+ only ([DV-G 2.1][DVG]) | **Fails** (no WG, one engine) | **Stage 1 experimental setting only**; general exposure at Stage 2 only with an owner exception (DV-E1) |
| **WebHID** | WICG Draft CG Report, 13 September 2024 ([DV-S 1.2][DVS]) | None | Yes (IDL and chooser tests) | Chrome 89+ desktop only ([DV-G 2.1][DVG]) | **Fails** | **Stage 1 experimental setting only**; Stage 2 with an owner exception (DV-E2) |
| **Web Bluetooth** | CG Draft CG Report, 3 June 2026; never on the W3C Standards Track ([DV-S 1.5][DVS]) | None | Yes, dependent on a fake adapter | Chrome 56+ only ([DV-G 2.1][DVG]) | **Fails** | **Stage 1 experimental setting only** (desktop GATT backend); Stage 2 Android GATT backend and hardening; general exposure only with DV-E3 |
| **Web NFC** | CG draft, pre-CR, undated; `w3.org/TR/web-nfc/` 404 ([DV-S 1.6][DVS]) | None | Yes, Android-only | Chrome Android 89+ only ([DV-G 2.4][DVG]) | **Fails** (no WG, one engine, one OS) | **Not shipped**; Stage 3 only if Android support and a second engine or an owner exception (DV-E4) |

**Web Bluetooth's CG status is explicit**: the Web Bluetooth Community Group has existed since July 2014, the specification is a Draft Community Group Report, it has never been a W3C Working Group deliverable, and it is "not a W3C Standard nor … on the W3C Standards Track" ([DV-S 1.5][DVS], [DV-H 5.4][DVH]). **Web NFC's W3C draft standing is explicit**: the only public copy is a headerless Community Group draft at `w3c-cg.github.io/web-nfc/`; the `w3.org/TR/web-nfc/` URL returns 404; the text says it is unstable and expected to change before Candidate Recommendation, which it has not reached ([DV-S 1.6][DVS], [DV-H 6.3][DVH]).

**The experimental setting (ED-D2 precedent, not an admission).** A developer setting, **Experimental device APIs**, off by default and unavailable in managed profiles, exposes the six APIs (Web NFC only where an Android backend exists) to a **per-origin test-site list**. The developer adds origins in settings, only those origins see the APIs, the list is capped at 20† origins and cleared on profile reset. It is not a global switch: a site the developer did not list gets `NotSupportedError`. It is a testing and dogfooding surface, not an exposure decision: each listed site still gets the full chooser and grant, the setting is visible in the toolbar and the site panel, and it cannot be enabled by a page or an extension. The setting exists because the only way to test the stack against real sites and real devices is to expose it somewhere, and because building it behind a flag from DV-M2 is how the Stage 2 decision gets evidence. It is not a ST-D18 exception: the APIs remain unadmitted for general exposure until the owner decides.

**Owner exceptions (GR-D11 precedent).** The owner may grant a named exception for an API that fails ST-D18, with conditions, for a stated period. This spec recommends six candidates, **not granted in this revision**; every exception expires 12 months† after it is granted unless it is re-decided at DV-M5:

| ID | Candidate exception | Conditions | Decision point |
|---|---|---|---|
| **DV-E1** | WebUSB general exposure at Stage 2 without a second engine | Protected classes refused; per-device grants; write is `device-write`; 90-day† expiry; identifier exposure off; review at DV-M5; revocable if a parser sev-1 or a class bypass is found; expires 12 months† after grant | DV-M4 |
| **DV-E2** | WebHID general exposure at Stage 2 without a second engine | Input collections refused; write high-risk; the VIA-style vendor-collection carve-out only with `device-write`; review at DV-M5; expires 12 months† after grant | DV-M4 |
| **DV-E3** | Web Bluetooth GATT general exposure at Stage 2 without a second engine | No `acceptAllDevices`; HID/FIDO services refused; advertisement watch only for granted devices; review at DV-M5; expires 12 months† after grant | DV-M4 |
| **DV-E4** | Web NFC exposure on Android without a second engine | NDEF only; foreground only; write per tap; UID pseudonym; no HCE; review at DV-M5; expires 12 months† after grant | DV-M5 |
| **DV-E5** | Web MIDI general exposure without a recorded WG resolution or a second default-on engine | Output in the base grant with the `device-write` consequence; SysEx separate and high-risk; all-ports prompt and per-origin ids (DV-D13); AX-D11 evidence or an explicit owner acceptance of the AT gap; review at DV-M5; expires 12 months† after grant | DV-M3 |
| **DV-E6** | Web Serial general exposure without a second default-on engine | Write-capable open with the reset warning; port-identity check (6.5); no RFCOMM; AX-D11 evidence or an explicit owner acceptance of the AT gap; review at DV-M5; expires 12 months† after grant | DV-M3 |

The recommendation in this revision is to **grant none of them yet**: no device API gets general exposure in Stage 1. MIDI and Serial are the first two candidates (DV-E5, DV-E6) because their grant models are closest to the corpus's, but neither has a second default-on engine and MIDI has no recorded WG resolution. The rule exists because a single-engine API means a single implementation's bugs and a single vendor's permission model; Izcal's own implementation does not create a second engine, and an owner exception should be a response to evidence (demand, a second engine, a security record), not to the existence of code. The per-origin setting is enough to gather that evidence in Stage 1. If the owner grants an exception, the API moves from the setting to normal exposure with the conditions above recorded in 9.4 and the ledger.

**What is built from the start.** All six data structures — the grant record, the ticket, the family enum, the capability set, the recording classes, the virtual device — are built general at DV-M0, so a later exposure decision is a flag and a review, not a schema migration ([ST-D18][ST], [LY-D10][LY]). The APIs that are not exposed still have their parsers, fuzz targets and oracle scenarios from DV-M1–DV-M2, because the parsers are the long pole and the oracle is needed to test them.

**What the person sees.** When an origin is on the list, its chooser and site panel carry an "Experimental" badge; the settings page explains that these APIs are not standardized in a second engine and may change; the enterprise policy can block the setting entirely. When an owner exception is granted, the badge changes to "Limited support" until a second engine exists. The browser never describes an API as standard when it is a Community Group draft.

### 6.16 Footprint, energy, performance, wakeups and fuzzing

FP-1's ≤ 64 MiB† idle baseline is unchanged because the device service is lazy: a profile that never calls a device API has zero device processes, zero device memory and zero device threads. The rows above are charged when a device is in use, against the tab's device budget, and are measured by the FP harness with the same private/shared accounting as the other service rows ([FP 8.2][FP]). The Windows always-on ceiling (≈ 74 MiB†, accepted by owner decision A-SH-39 on 21 October 2026) is unaffected; no device code runs in the shell.

**Energy (FP-22).** Device access is event-driven: no polling in the arbiter or the session; USB transfers are page-initiated; HID reports arrive as OS events; serial reads are page reads; MIDI events are OS callbacks; Bluetooth discovery runs only while a chooser is open or a granted advertisement watch is active; NFC reader mode runs only while a foreground scan is active. The energy budget is the measured cost of a recorded session plus 10%†, measured on the reference devices for a USB bulk transfer, a 1 kHz HID report stream, a 115200-baud serial stream, a MIDI note stream, a GATT notification stream and an NFC read. A device that streams at 1 kHz for an hour costs what the OS costs to deliver the reports; the session's parsing and recording cost is charged and reported. No device event wakes a hidden or frozen page (6.10); a suspended tab's session exits after 30 s†, and resuming re-opens through the grant, which is a recorded decision.

**Performance (DV-18).** The proxy must not turn the OS stack into a bottleneck. On DC-16, unless a row says otherwise: USB bulk ≥ 300 MiB/s† aggregate per device with p99 proxy-added latency ≤ 2 ms†; a 1 kHz HID report stream with p99 ≤ 2 ms† and zero dropped reports; serial sustained ≥ 12 Mbaud† with p99 chunk latency ≤ 5 ms†; MIDI p99 ≤ 5 ms† (Q-DV-9); GATT notification p99 ≤ 20 ms†; NFC read ≤ 100 ms† after OS delivery. A stalled transfer on one device adds ≤ 5 ms† p99 to another device's traffic; the ring benchmark runs at 4 MiB† per transfer and 16 MiB† in flight; recording adds ≤ 10%† to p99, measured by the recording probe rather than inferred from the energy budget. Every target is measured on the riscv64 reference as well as on DC-16/DC-8/DC-4.

**Fuzzing (SEC-24).** The parser targets in 6.9 run continuously in CI and in the pre-release audit: ≥ 1,000† CPU-hours per week for USB and HID, ≥ 500† for GATT, NDEF and MIDI, ≥ 250† for the policy parser. The rule is **zero open crash bugs older than 14† days** for any device parser, and zero crashes at release. The fuzz fleet is `hg-device-fuzz` on the Linux build machines; a crash is a release blocker, not a backlog item. The oracle suite (`hg-device-sim`) runs on every change and covers descriptor edge cases, PDU fragmentation, chunk boundaries, disconnect timing, malformed NDEF and SysEx interleaving. Coverage is reported per parser; a parser below 80%† branch coverage has an open task, not a waiver.

**Why these numbers.** The arbiter is a small routing process with an OS handle table; 8 MiB† with one device is generous. The session's 3 MiB† is dominated by the parser arena and the recording buffer; a 64 KiB‡ descriptor and a 1 MiB‡ ring do not need more. The six-family worst case is 34 MiB† on DC-8 and DC-16 and 38 MiB† on DC-4, charged separately so a device-heavy tab cannot hide its cost; the 64 MiB† ring cap is shared and charged only while devices stream. The eight-session cap bounds the multi-frame case that the six-family row does not cover. If measurement shows a family exceeding its row by more than 10%†, the row is raised with evidence in a revision, not silently.

The OS backends are **modules inside `hg-substrate-os`** (tier O), one per family and OS: `usb/{macos,windows,linux,android}`, `hid/{macos,windows,linux}`, `serial/{macos,windows,linux,android}`, `midi/{macos,windows,linux,android}`, `bt/{macos,windows,linux,android}`, `nfc/android`. G3 already says only `hg-substrate`/`hg-substrate-os` may perform OS effects; this spec adds the family modules and their allowlist, not a new crate class.

**G210. One device boundary.** Only `hg-device-arb` may request a device effect from `hg-substrate-os`; no renderer, session, network, media, extension or tool crate may call a device backend. The dependency allowlist in `tools/deps` enforces it, and a CI check fails on a new edge.

**G211. Tickets only.** Only the broker mints a device-access ticket; only `hg-device-ticket` encodes or verifies one; only `hg-device-arb` accepts one. No other crate holds a signing key or a private key. Every open, configure, pair and write requires a ticket whose capabilities cover the operation; every transfer is checked against the live session context created by an open ticket.

**G212. Parsers are tier P and fuzzed.** Every device parser is tier P; it caps input and allocation, uses an explicit stack with a depth cap, has no recursion, no panic path reachable from input, and a named fuzz target that runs in CI. No third-party parser is linked. The rule is zero open crash bugs older than 14† days.

**G213. The model holds no page data and no OS handles.** `hg-device-model` may hold device values, capability bits and opaque digests; it may not hold an OS handle, path, file descriptor, Bluetooth address, serial number or page string. It is serializable for recording; sensitive fields are `Redacted<T>`.

**G214. The API crate is renderer-only.** `hg-device-api` exists only in a renderer; it never sees an OS handle, path, descriptor byte or address; it receives typed handles and values over IPC; its stubs, when a family is disabled, return `NotSupportedError` and do not reveal whether an OS backend for the family is present.

**G215. One binary, two links.** `hg-device-main` builds in three configurations (`arbiter`, `session`, `enumerate`) from two link profiles: the arbiter profile links the OS backends, the session/enumerate profile does not. The session and enumerate configurations must not link `hg-substrate-os` device backends; the arbiter configuration must not link `hg-device-api`. A build-time symbol and dependency check enforces it, and a runtime probe asserts that a session cannot resolve a device backend symbol.

**G216. Replay has no device path.** `hg-device-replay` must not depend on `hg-substrate-os` device backends, directly or transitively; the dependency graph check fails a new path; a replay run asserts zero device syscalls (DV-8).

**G217. Tools and corpora are test-only.** `hg-device-sim`, `hg-device-fuzz` and `hg-device-corpus` are tier T, never linked into a shipping binary. Every corpus file records its licence and source; no third-party corpus in shipped data without an MIT-compatible licence; test-only inputs follow the licence audit's test-only class (WPT fakes are BSD-3-Clause, recorded in `tools/device-corpus/LICENSES.md`, and never shipped); no corpus is shipped as browser data.

**G218. Identifiers never leak.** Only the broker derives a page-visible handle (it is the only holder of the per-origin handle key and the grant table); the session maps the handle to the digest for its own device and never holds the key; the digest never leaves the broker, the arbiter and the session that owns the device, and is never page-visible, logged or exported; serial numbers, UIDs, addresses and OS paths are `Redacted<T>` in every export and absent from logs. A new log site that prints a device value must use the typed redaction.

**G219. Exposure is gated.** No device API is exposed to web content unless its build feature, its stage in 6.15 and an owner decision (or the ST-D18 verdict) all agree. The experimental setting cannot be enabled in a managed profile; an owner exception is recorded in 9.4 with conditions and an expiry; the CI exposure test enumerates the build's API surface and compares it with 6.15.

### 6.18 User experience and integrations

**The chooser.** One window, broker-owned, with a title that names the origin and the action; the device list on the left (name, family, a short capability summary), the details on the right (capabilities in plain language, scope, consequence, what it does not protect). The list has no default selection and no "select all". The primary action is "Connect"; the secondary is "Cancel"; "Remember this device" is off and becomes a second confirmation. For Bluetooth, the list shows name and matched services, not an address; for NFC, there is no chooser, only the tap confirmation. For a device with a protected collection, the row is disabled with the reason; for a device that needs a driver, the row says "driver required" with a help link.

**The active indicator.** A device icon appears in the toolbar while any device is open, with a per-tab count in the site panel. Clicking it lists the open devices and the site using them, with "Disconnect" for each and "Forget" for the grant. A site with a persistent grant but no open device shows a small dot, not a full indicator, so the person can see that the site can reconnect. The indicator is drawn by the shell, not the page, and cannot be spoofed by page content (CON-R3).

**The site panel.** A Devices section per site: grants (family, label, scope, last use, expiry), open devices, the "Experimental" badge where applicable, "Forget all devices", and a link to the settings page. A grant created by policy shows "Set by your administrator" and can still be revoked by the person. A grant used by an agent shows "Used by an agent task" with a link to the task.

**Settings.** A Devices page with: the per-family policy (ask/block/allow-once), the "Experimental device APIs" per-origin test-site list (maximum 20† origins, with a warning and a managed-profile lock), the identifier-exposure default (off), the list of all grants (site, family, label, last use) with revoke, and a "Clear all device grants" action. The page explains the six APIs in one paragraph and links to the prompt ledger.

**Errors and guidance.** `NotFoundError` for no device or no match; `NotAllowedError` for policy, denial or a missing activation; `InvalidStateError` for a second prompt or a closed device; `NetworkError` for a disconnect; `QuotaExceededError` for a cap; `NotSupportedError` for a refused family, protected class, isochronous endpoint, `acceptAllDevices`, or a disabled API; `SecurityError` for a non-secure context, an opaque origin, a sandboxed frame, or a policy token that resolves to none. All device `DOMException` messages are generic: adapter state, OS permission, driver binding and port identity never appear in page-visible text (the chooser and the browser log carry the detail). Each error has a short help page: "the device is in use by another application", "the driver is not installed", "the OS permission was denied", "the device disconnected; reconnect it and try again", "this device class is not available to web pages". Errors never include the OS path, the address or the serial number.

**Onboarding.** The first device request on a profile shows a one-time explanation before the chooser: what a device grant is, that a device can be malicious, how to revoke, and where the ledger is. It is a broker-owned informational surface, not a page modal, and it is dismissed once per profile (not per site). A person who never uses a device API never sees it.

**Accessibility (AX-D11).** The chooser is keyboard-navigable, focus starts on the heading, the device list is a listbox with a described-by summary, the consequence text is announced, and the two-step selection is explicit. High-risk prompts do not time out while an AT user is interacting. Because all device prompts are high-risk, AT approval is refused until AX-D11's person-present evidence exists (6.10); when it ships, the OS-attested path is the voice and switch path. The chooser remains fully usable with a keyboard or pointer. The active indicator has a text label, not only an icon; the site panel is reachable by keyboard; the ledger rows have text, not colour-only status.

**Integrations.** The shell 6.4 table gains the three classes and its Permission example loses "MIDI" (a MIDI grant is a device grant, not a generic permission). The site panel and ledger gain device fields. DevTools gains the `devices` domain (6.13). The footprint spec gains the rows in 6.16. The coding standard gains the tiers and G210–G219. The security scope gains the process row, the threat-model file, the IPC handle kind and the CON rules. The DOM spec's 6.18 table gains the six rows. The extensions Ring C gains the device namespaces. The accessibility spec's AX-D11 records the AT gap. The ledger gains G-26 and the G210–G219 registry. All are written as amendments in 9.5.

### 6.19 Alternatives considered

| Alternative | Why it was considered | Why it was rejected | Reversal trigger |
|---|---|---|---|
| **Six separate device services, one per API** | Matches the six specs and the Chromium structure; independent teams | Six permission stores, six choosers, six threat models, six test fakes, and six places to get the grant model wrong; the grant shape is identical | A family needs a process shape the shared boundary cannot give (for example, isochronous audio with a hard latency budget) |
| **One broker-internal device stack, no session** | Fewer processes; simpler IPC; the broker already owns OS effects | The broker would parse attacker bytes (Rule of Two violation) and a parser bug would compromise the permission store and every prompt | None; the session split is a security invariant (G215) |
| **A per-device process** | Stronger isolation between devices | Multiplies empty-process and page-table cost; a session already holds no OS handle, and per-device isolation adds no boundary the arbiter does not already enforce. A hub in the path and DMA/IOMMU behaviour are OS/hardware responsibilities; the browser refuses a hub as a device but cannot mediate a hub it does not see | A family with a device that can DMA or map memory into the process (none of the six) |
| **Our own Bluetooth controller/HCI stack** | Full control of pairing, privacy and timing; no OS stack bugs | No desktop OS gives an ordinary process HCI; Linux needs `CAP_NET_ADMIN`; the cost is a silicon qualification programme, coexistence and a permanent radio team; Web Bluetooth is GATT-only | A decision to ship Classic/RFCOMM or a radio-level API, with a funded qualification programme |
| **libusb/libusb-compatible backend** | Portable USB in user space | Not an OS interface; a third-party implementation with its own bugs and licence; M-1 says build our own; the OS backends are already direct | None; OS interfaces only |
| **PC/SC for desktop NFC now** | Desktop smart-card readers exist and `pcscd` is an OS service | No second engine, no demand evidence, a reader-driver threat model, and Web NFC is NDEF-only; a Stage 3 decision, not a Stage 1 shortcut | Android NFC ships and desktop demand is measured, or a second engine appears |
| **The allowed-origin registry** | Removes the prompt; device firmware names its sites | Needs new firmware and long product cycles; no path for existing devices; the chooser is the surviving model ([DV-H 2.2][DVH]) | A device-side standard emerges with broad firmware support; it would be an additional constraint, not a replacement |
| **Record at the API boundary** | Smaller recordings; no OS-specific events | Hides the parser, where the bugs and semantics are; cannot reproduce descriptor handling ([DV-R 3.1][DVR]) | A family whose OS interface cannot be recorded portably (none found) |
| **Persistent grants by default** | Usability; fewer prompts | "Too persistent and transferable" is one of the three objection phrases ([DV-H 8.9][DVH]); a compromised site inherits the device | None; 90-day† expiry with a visible revoke is the floor |
| **Expose all six in Stage 1** | Demand; developer expectation | ST-D18 as applied by LY-D10: no API has two default-on engines, MIDI has no recorded WG resolution, and an API cannot be unshipped; the five desktop-capable APIs stay behind the per-origin setting and NFC stays unshipped | A second default-on engine for an API, or an owner exception (DV-E1–DV-E6) |

### 7.3 Evidence rule (M-1 part 3)

Every claim in this spec and its research notes is sourced to specification prose, a standards-body registry, OS documentation, a release note, a mailing-list message, a published paper or a black-box observation. No third-party source file, header, commit, diff, code review or implementation was read. Where the research notes describe what an OS or a stack "does", that is black-box or documentation evidence to reason from, not a shape copied. The HID Usage Tables JSON and the USB-IF class-code list are data, not implementation; they are used as parser tables, with the source and licence recorded. This paragraph is the M-1 part 3 attestation for the spec and the seven notes.

### 7.4 Royalty-free, riscv64 and portability

All shipped code is Izcal's MIT code; the OS interfaces are royalty-free SDKs; the standards data is not royalty-bearing for implementers. The parsers and the arbiter/session logic are portable Rust with no architecture-specific code; the only per-architecture surface is the FFI to the OS backend, which is identical on riscv64 Linux (usbfs, hidraw, tty, ALSA, BlueZ D-Bus) and on the other Linux architectures. There is no JIT, no assembly, no SIMD requirement and no assumption of a 64-bit little-endian host beyond the corpus's existing assumptions. Ed25519 verification is portable and constant-time in `hg-crypto`. The Linux backend is the riscv64 reference; macOS, Windows and Android are the other first-class targets, with Android on arm64 and riscv64 where the OS supports it.

### 9.4 Decisions

**Owner decision (21 October 2026): every recommendation below is accepted** (DV-D1 to DV-D15). The six proposed owner exceptions in 6.15 (DV-E1 to DV-E6) are **not granted**: they remain proposed, each carries its 12-month† expiry after grant, and each is re-decided at DV-M5.

| ID | Decision | Recommendation | Reversal trigger | Owner decision |
|---|---|---|---|---|
| **DV-D1** | One device-access process kind in three configurations (arbiter, session, enumerate), not six stacks and not one broker-internal stack | **Adopt.** One grant model, one threat model, one parser boundary; the session cannot link the OS backends | A family needs a process shape the shared boundary cannot meet (isochronous audio, a DMA-capable device) | No |
| **DV-D2** | Broker-signed device-access tickets; the broker mints, the arbiter verifies; signed rather than MACed | **Adopt.** The issuer and verifier are different processes; a MAC key in the arbiter would let a compromised arbiter mint. **The verifier accepts an app-id-bound ticket in the same format: the principal field carries `app:<id>` where a site ticket carries the top-level site** (*Izcal app host* A20) | A cheaper verifier with the same property is found; the ticket stays | No |
| **DV-D3** | Use the OS stack as the interface for every family, including Bluetooth; no Izcal controller/HCI stack; NFC is Android-only | **Adopt.** No unprivileged HCI on desktop; an HCI stack is a qualification programme, not a feature; the OS stack already supplies every capability Web Bluetooth exposes | A funded decision to ship Bluetooth Classic/RFCOMM or a radio-level API | **Yes — the cost of the rejected alternative is an owner-visible number** |
| **DV-D4** | One grant model per (frame origin, top-level site, container, family, device digest), with this-time/while-open/remember scopes; 90-day† expiry; 16† per origin | **Adopt.** Answers "Too broad" and "Too persistent and transferable" without making the API unusable. **The chooser accepts `app://<id>` as a requesting principal, with the app id in place of the frame origin and top-level site** (*Izcal app host* A20) | A usability study shows the expiry breaks a legitimate repeated task; the expiry can move, the per-device key stays | **Yes — persistence and identifier policy** |
| **DV-D5** | Three high-risk prompt classes (`device-pairing`, `device-connection`, `device-write`), a broker-owned chooser with no default, two interactions, protected classes refused before a prompt | **Adopt.** Every device grant can reach firmware; a low-risk device class would be a mislabel | AX-D11 ships person-present evidence, which changes the AT rule, not the risk class | **Yes — all device prompts high-risk leaves an AT gap until AX-D11 ships** |
| **DV-D6** | Pseudonymous per-origin handles; serial numbers, UIDs, Bluetooth addresses and OS paths hidden; identifier exposure is a separate grant | **Adopt.** The spec's own privacy sections and the W3C objection both name persistence and identifiers | A standards change requires a true serial in the API; it would still be a separate grant | **Yes — identifier exposure is a privacy product decision** |
| **DV-D7** | Record at the device-service boundary, not the API boundary; descriptors, typed transfers, chunks, times, decisions and errors | **Adopt.** The parser is where the bugs and semantics are; a replay must reproduce them | A family's OS events cannot be captured without a secret; none found | No |
| **DV-D8** | Replay against a virtual device that never opens hardware; NFC payloads never recorded by default; tag-payload recording is an explicit, encrypted, non-exportable option | **Adopt.** A replay that can open a device is a live-device test with extra steps, and NDEF can carry credentials. **An app's device sessions replay through the same virtual device** (*Izcal app host* A20) | A developer workflow proves it needs exportable payloads; the answer is a synthetic tag, not a recording | **Yes — recording can capture credentials** |
| **DV-D9** | Apply ST-D18/LY-D10 per API as written: no general exposure in Stage 1; MIDI/Serial/USB/HID/Bluetooth behind a per-origin setting and NFC unshipped; exceptions DV-E5/DV-E6 and DV-E1–DV-E4 as candidates | **Adopt.** "Ships" means default-on; no API has two default-on engines, and MIDI has no recorded WG resolution; the per-origin setting gathers evidence without exposing an API to all sites. **App device exposure follows the same template, gated by the app host's named-app list** (*Izcal app host* A20, AH 6.15) | A second engine ships an API default-on, or the owner grants a named exception with conditions and an expiry | **Yes — the exposure decision is the owner's, and this is the starred one** |
| **DV-D10** | Agents only through typed intents with person-present, task-scoped, non-persistent grants; extensions get no device API; the six device namespaces join Ring C as refused | **Adopt.** B9 and the extension Ring rule already say it; a device grant is the last thing an agent should inherit | A future agent capability model defines a supervised device task; even then, no persistent grant | **Yes — agent device access is a product trust decision** |
| **DV-D11** | Lazy device processes, 30 s† exit, footprint rows, event-driven energy, no hidden-page wakeups | **Adopt.** Fits FP-1 because the idle cost is zero; the six-family worst case is 34–38 MiB† plus a 64 MiB† ring cap | Measurement shows a family over its row by more than 10%† | No |
| **DV-D12** | Every parser is Izcal's, tier P, fuzzed; no third-party parser; `hg-device-gatt` is built even though the OS stack is the shipping GATT path | **Adopt.** The ATT codec is the oracle's protocol engine and the promotion path if a raw PDU interface appears; its fuzz hours protect the oracle, not the OS parser; the cost is 4–5† engineers, stated | A platform exposes a trustworthy raw ATT interface and the codec is redundant; it still serves the oracle | **Yes — paying for a GATT codec that is not on the shipping path needs an owner's acknowledgement** |
| **DV-D13** | Web MIDI keeps the API's all-ports model after one consent, rather than a per-port grant | **Adopt with a documented exception.** The Working Draft has no per-port grant; the prompt lists every port, ids are per-origin, and the rig fingerprint is stated | The Working Draft gains a per-port grant, or a privacy measurement shows the rig fingerprint exceeds DV-6 | **Yes — a privacy exception the owner should see** |
| **DV-D14** | Refuse WebUSB isochronous transfers as a capability gap | **Adopt.** The API exposes them and desktop OS backends support them, but a bounded, recordable path on all four platforms (especially Android) is missing; the compatibility cost is stated | A recordable isochronous path on all four targets, or demand from a class of devices | No |
| **DV-D15** | Allow a remember-scope identifier-exposure grant (true serial/UID) with a separate high-risk prompt and 90-day† expiry | **Adopt.** The default stays off; a legitimate inventory or wallet app otherwise cannot persist across sessions; the grant is visible and revocable | A privacy review shows the persistent grant is too linkable; it can revert to this-time only | **Yes — identifier persistence is a privacy product decision** |

★ The owner-facing decisions are **DV-D3** (the cost of not building a Bluetooth stack), **DV-D4** (persistence and identifiers), **DV-D5** (all device prompts high-risk, and the resulting AT gap), **DV-D8** (recording credential-class payloads), **DV-D9** (what ships when and which exceptions to grant), **DV-D12** (paying for the GATT codec), **DV-D13** (the MIDI all-ports privacy exception) and **DV-D15** (persistent identifier exposure). The rest are engineering decisions the spec makes and the owner can review.

## 10. Risks

| Risk | Likelihood | Impact | Mitigation | Trigger |
|---|---|---|---|---|
| A parser bug becomes a host compromise | Medium | Critical | Tier P, fuzz hours, 14-day rule, SEC-24 audit, no parser in the arbiter | Any crash; a CVE in a device parser; a bypass in the conformance suite |
| A compromised arbiter reads or injects every session's device traffic | Low | Critical | The arbiter parses no page bytes and holds no page data, but its data plane is profile-wide; the broker grant table bounds new opens, not traffic. The residual is stated; a per-container split would duplicate OS access and is rejected | A sandbox escape in the arbiter; an isolation review |
| A device class bypass (protected class reached through a crafted descriptor or claim path) | Medium | Critical | Refuse before prompt; arbiter claim table fuzz; descriptor re-parse after re-enumeration; DV-4, DV-13 | A conformance failure or a researcher report |
| Cross-site leakage if a device session is compromised | Low | Medium | One session per frame site and container bounds the blast radius; same-site origins share a process by design; per-origin ticket checks; no session shared across sites or containers | A session compromise advisory or an isolation test failure |
| A different device inherits a `port-only` serial grant | Medium | Medium | At open, compare VID/PID and OS-exposed USB serial with the grant; if the port identity cannot be verified, require a fresh `device-connection` prompt and mark the grant `port-only`; the residual is stated | A port-identity mismatch report; a serial-device incident |
| A main-world extension script borrows a page's device grant | Medium | High | The device refusal is origin- and API-scoped; the extensions spec's main-world injection rules are the boundary; the grant is to the origin and the person's approval covers scripts in it | An extension-main-world device incident; an extensions-spec change |
| The OS Bluetooth stack is compromised below the arbiter (BlueBorne, BrakTooth, KNOB) | Medium | Critical | Minimum patched-OS requirement per platform; no radio-level API; Web Bluetooth exposes GATT only; the residual is an OS/controller vulnerability, not a browser parser | A patched-OS floor misses a known exploit; a BLE device compromise report |
| A hub or DMA below the USB stack attacks the host | Low | High | A hub is refused as a device; a hub in the path and DMA/IOMMU behaviour are OS/hardware responsibilities; the browser boundary starts at the OS device interface | A hub-injection or DMA report against a granted device |
| Firmware persistence or a cross-device radio attack via a granted device | Medium | High | HID input collections refused; USB protected classes refused; `device-write` high-risk; no silent pre-grant; prompt consequence text | A Peripheral Instinct-style chain; a vendor report |
| macOS serial or HID access is not possible in the sandbox without an entitlement | Medium | High | DV-M0 measurement; a narrow helper only if measured necessary; no general native bridge | DV-M0 result |
| Windows driver binding makes WebUSB unusable for common devices | High | Medium | Chooser explains the driver requirement; WinRT `UsbDevice` fallback; documentation; demand evidence | DV-M1 backends |
| Linux udev/permission fragmentation | High | Medium | Error guidance; distro packaging; no root; BlueZ D-Bus; test matrix | DV-M2 platform matrix |

**Flagged claims.** (1) No research note records any of the six as an Interop 2026 focus area; the ST-D18 verdicts do not rely on the Interop limb, only on the engine count and WPT. (2) The MIDI WG-resolution limb is inferred from the Audio WG's published Working Draft, not from a resolution minute; Q-DV-16 tracks the exact record. (3) WPT coverage counts are stated as "tests exist", not measured pass rates; the hardware-gated Serial and Android-only NFC suites are weaker evidence than USB's test API. (4) Chrome's enterprise policy names and versions for the device guard settings were not readable from the JavaScript-only policy site; the spec defines its own policy keys and does not claim parity with Chrome's names. (5) The BlueBorne 5.3-billion-device estimate is a vendor claim, not a measurement. (6) WebHID's Android milestone is listed as both 154 and 157; the spec treats Android WebHID as unshipped. (7) No published study measures fingerprinting entropy for these APIs; DV-6 is our own corpus measurement, not a population estimate. (8) The Web Bluetooth fake adapter's absence from stable Chrome is a black-box observation from Chrome's testing documentation, not a source read (M-1 part 3); no note row records the exact wording or a binary-size rationale. (9) Windows MIDI Services' GA date and MIT licence are from Microsoft's release material; it is used as an OS service, not vendored. (10) "Ships" in ST-D18 is defined here as default-on in a stable release; if the owner intends an add-on-gated or enterprise-inactive implementation to count, MIDI and Serial meet the engine limb and DV-E5/DV-E6 become unnecessary.

## Appendix A. Phase 8 disposition

Phase 8 was performed for this draft by two independent agents, each briefed separately: an independent fact-checker and an independent design critic. Neither wrote this specification. The fact-check (`research_notes/Izcal devices/factcheck.md`) returned 24 findings; the design critique (`research_notes/Izcal devices/critique.md`) returned 36. Every finding is dispositioned below, one row per finding. All 60 were accepted and fixed in this revision; none was rejected or deferred.
