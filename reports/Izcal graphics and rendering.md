*Revision 0.1 (19 October 2026): first draft, written by the synthesis author from the eight research notes.*

HGBA-2 2.3.0 drops WebRender and wgpu, and its general rule drops every library that does this work: Skia, Dawn, ANGLE, Tint, naga, Vello, tiny-skia, lyon, Pathfinder, cairo, Direct2D as the engine's rasterizer, SwiftShader and Mesa's software drivers. So Izcal builds its own renderer, rasterizer, compositor, GPU abstraction and shader compiler. The record says four things. **First, the GPU process is now where a renderer compromise becomes a system compromise.** NVD published 535 Chrome CVEs naming a graphics component between 1 January and 19 October 2026, against about 172 in 2017–2025 under the same wording ([NVD 2.0 API](https://services.nvd.nist.gov/rest/json/cves/2.0), method in [SR 1.16][SR]); 209 of them were reached from a compromised renderer, and the three GPU-driver sandbox escapes that Google's threat-intelligence group recorded in the wild in 2025 went through **vendor user-mode drivers** fed an unvalidated call sequence or size ([GTIG 2025 review](https://cloud.google.com/blog/topics/threat-intelligence/2025-zero-day-review/); [SR 1.1–1.3, 1.16–1.17][SR]). All 16 CVE-bearing bugs DarthShader found in shader pipelines were in the optimizing compiler behind the translator, not in the translator ([SR 8.1][SR]). **Second, every engine converged on the same pipeline only after paying for the wrong one.** Chrome spent 2014 (BlinkNG) to 2021 (M94) moving layerization after paint and adopting property trees and paint chunks ([HP 1.5–1.6][HP]); Firefox ran up to four rendering back ends at once and needed about four years (2017–2021) and a purpose-built software GL to delete them ([HP 3.5–3.13][HP]); Vello's GPU-only 2D design hit memory it could not size before a frame and moved path processing back to the CPU ([HP 6.4–6.6][HP]); Skia and Flutter both cured shader-compile jank by precompiling a small closed set of pipelines ([HP 2.4, 7.3–7.4][HP]). **Third, pixels differ between machines, and everyone tolerates it.** WGSL, Vulkan and Metal all allow floating-point results to differ between GPUs ([RP 7.1–7.5][RP]); one canvas sentence rendered 50 distinct ways in 300 samples, which makes canvas a fingerprint ([Mowery and Shacham 2012](https://hovav.net/ucsd/dist/canvas.pdf); [SR 6.1][SR]); WPT, Playwright and Chromatic all compare with tolerances ([RP 6.3–6.4][RP]; [GO 4.6–4.7][GO]). Only integer arithmetic is bit-identical across GPU vendors ([WGSL §15.7](https://www.w3.org/TR/WGSL/#floating-point-evaluation); [Vulkan invariance](https://registry.khronos.org/vulkan/specs/latest/html/vkspec.html#invariance); [RP 7.2, 7.4][RP]). **Fourth, a single GPU process for all sites is the one shared resource I-1 does not yet cover**: OS GPU memory isolation is per process, not per site; Metal revokes a device's access after "too many timeouts or hangs" (whether per process is not documented); Windows bug-checks the machine after more than five GPU timeouts in a minute ([TDR registry keys](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys); [SR 2.6, 3.3–3.4][SR]). **The central idea: every pixel a page can read, and every pixel of ordinary page content in the defined canonical image (6.4), is a pure integer function of the display list, computed bit-identically on the CPU and on every GPU, so the CPU path is the oracle, the fallback and the privacy defence at once; content-dependent GPU work (raster, canvas, WebGL, WebGPU, shader compilation) runs in a content GPU process keyed exactly like the renderer, and the shared compositor sees only validated tiles and surfaces that it granted once and never waits on.** The decisions that matter most: (1) a **compositor GPU service plus a content GPU process per renderer key** (site, container, or origin where FP-D8 keys renderers by origin), started with a rendering opportunity and device-less until it needs a GPU (GR-D2, OD-5), with security prompts in an OS layer the compositor cannot draw over (GR-D28); (2) **canonical pixels**: integer-only raster on CPU and GPU for page content and every readable surface (GR-D3); (3) Izcal's own **GPU abstraction on Metal, Vulkan and in-box Direct3D 12**, with its own shader IR emitting **MSL, SPIR-V and DXIL directly** and validating its own output (GR-D1, GR-D7, GR-D8); (4) the **display list is a generated, typed IPC format**, so IPC-R16's WebRender exception disappears (GR-D6); (5) **no CPU emulation of WebGL or WebGPU**, which fail cleanly without a usable GPU, following Chrome's 2025 security reasoning (GR-D10); and (6) **WebGPU on by default only where I-6 already allows high-resolution timers**, cross-origin-isolated contexts, and behind a per-site permission elsewhere (GR-D11). The work is about **99–132 engineers† at full strength for 5–7 years† to parity**, about **420–780 engineer-years†**, against Stage 1's two-engineer graphics track (Section 9).

## 1. The problem and who has it

| Who | What they need from graphics | Evidence |
|---|---|---|
| **People browsing** | Correct pixels in every colour space, smooth scrolling and animation at the display's rate, low input latency, low battery use during video and at idle, no black screens or crashes from driver bugs, and no way for a page to fingerprint their GPU or steal another site's pixels | Firefox's move to Core Animation tiles cut a spinning animation from 12.8 W to 2.9 W and an idle Google Docs tab from 7.4 W to 1.6 W, about 4.5× on one 2013 MacBook Pro ([Mozilla gfx, 2019-10-22](https://mozillagfx.wordpress.com/2019/10/22/dramatically-reduced-power-usage-in-firefox-70-on-macos-with-core-animation/); [OS 1.9][OSD]); Linux overlay planes saved 1.0–1.8 W during video ([OS 3.13][OSD]); GPU.zip stole a logged-in username across origins in 30 minutes at 97% accuracy ([SR 5.6][SR]); canvas and WebGL readback identify devices ([SR 6.1–6.3][SR]) |
| **Web developers** | "Why did this repaint?", "why is this janky?", "why is this layer here?", "why does this look different on Windows?", "why is my shader rejected or slow?", "why is my canvas blurry?" | No shipping tool links a repaint to its cause ([GO 3.15][GO]); Long Animation Frames stops before presentation and does not separate paint, raster or compositor time ([GO 3.1][GO]); Chrome said its Layers panel "might be deprecated soon due to low usage" ([GO 2.3][GO]); View Transitions and scroll-driven animations rank high on the State of CSS incompatibility lists (2025: second and third, behind anchor positioning) ([GO 1.3–1.4][GO]); high-DPI canvas scaling is the author's job ([GO 1.10][GO]) |
| **Developers' tools and agents** | Structured rendering data instead of screenshots; identical pixels on every machine for tests | A screenshot costs about 1,000–1,800 tokens and can carry prompt injection ([GO 4.1–4.3][GO]); Chrome DevTools MCP says "Prefer taking a snapshot over taking a screenshot" ([GO 4.4][GO]); visual tests survive only by pinning the environment and adding tolerances ([GO 4.6–4.8][GO]) |
| **Izcal's engineers** | A graphics stack that is deterministic where it matters (B1, DET-1, JS-D15), checkable against a reference, memory-safe outside a small audited FFI layer, inside FP-14's GPU budgets, and secure against hostile display lists, shaders and command streams | HGBA-2 5.6: "rendering paths must match pixel-for-pixel on reftests"; security scope 6.9: the GPU service is "Izcal's widest privileged surface" ([SS][SS]); Stage 1's graphics track is 2 engineers ([S1 8.3][S1]) |

**What Izcal's specs already decide.**

- **[M-1][H2] (2.3.3).** No engine libraries; everything shipped available under MIT; OS interfaces and drivers allowed; no third-party project's source code (engine, library, tool, driver or OS component) is ever evidence; other engines are black-box differential signals only. Section 4.4's WebRender-on-OpenGL plus wgpu, D3 (wgpu), P-2 (Vello versus WebRender) and the Section 3 diagram's GPU-service box are superseded and are replaced by this spec.
- **[HGBA-2 Section 5][H2] (HAL).** Device classes, never vendors; all GPU work asynchronous with fences on a monotonic timeline; no blocking map; sticky validation errors; device loss with epochs, "three losses within ten minutes" blocklists the class for the session; `PolicyDenied` indistinguishable from `Unsupported`; every internal `Op` has a CPU implementation and "rendering paths must match pixel-for-pixel on reftests"; web APIs whose specs allow failure "surface failure instead of emulating the API on the CPU"; no synchronous per-frame readback. Targets R-1 (GPU offload never hurts p95 frame time), R-2 (device-loss recovery ≥ 99%) and R-6 (calibrated cost model) stand.
- **[HGBA-3][H3].** B6 (property trees as data-oriented phase outputs), B7 (pixel-optional rendering for unobserved and agent tabs), DET-1 (display-list hash in 1,000 of 1,000 replays; GPU-dependent output out of scope), PRIV-2.
- **[Stage 1][S1].** One sandboxed GPU service launched at first paint; G7 (renderer crates reach `hg-gpu` only through generated endpoints); 3.3 (raster checked by reftests and `rr`); 5.1 (vsync arrives from the GPU service as a message); 5.7 (paint produces property trees and paint chunks; four trees; pixel-optional stops after chunk generation); D-S1 (readback surfaces get noise seeded per (site, container, session)).
- **[Security scope 0.3][SS].** IPC-R7 (copy, then validate; opaque sampled buffers exempt when the receiver fixed their size and format), IPC-R16 (entry 1: WebRender display lists, to be removed), IPC-R17 (no process trusts another), GPU-R1 to GPU-R8 and SEC-10 (sandbox, validation, fuzzing, translation checks, timer coarsening, blocklist updates within 7 days†).
- **[JS spec][JS].** JS-D15: every timing-dependent decision is a recorded B1 input. JS-D12: one implementation per math function, no FMA contraction.
- **[Footprint spec][FP].** FP-14 (GPU baseline ≤ swapchain + 16 MiB†; visible tab ≤ 2.5 × viewport px × 4 B for tiles plus visible images' textures; atlas ≤ 2 MiB† per (site, container, partition); hidden tab 0 page-owned bytes after 30 s†); FP-D14 (partitioned atlases); FP-10 (GPU service unexplained remainder ≤ 15%†); FP 6.4 (display list copied then validated; renderer keeps chunk hashes); FP 6.6 (budget from the OS API, per-site accounting, two swapchain buffers by default); FP-11's 360 B† layout-and-paint share, with layout proposing 200 B† layout and 160 B† paint until this spec co-signs.
- **[Fonts and text][TX].** No font code in any GPU process (G26); CPU integer glyph raster in the renderer (TX-D13), masks uploaded to a per-partition atlas with dimensions in the copied message; large glyphs as paths in "the graphics spec's bounded path format"; grayscale AA, with the compositing colour space for masks left to this spec (TX-D6, R21).
- **[Layout][LY].** LY-D3 (fragments in fractional CSS px; **paint snaps to device pixels**; ResizeObserver's device-pixel box uses this spec's rule); LY-D13 (scroll offsets primary in `hg-scroll`; a delta protocol with sequence numbers with the compositor); LY-D14 and LY-D22 (hit testing is the reverse of the one paint order through `hg-paint-order`; a graphics owner named before LY-M0's review); LY-7 and LY-15 (ship blockers on paint order and clips).
- **[Images and media][MD] (in progress).** `hg-colour` (MD-D28); canonical working encodings S and W (MD-D8); display conversion, tone mapping and gain maps only in the GPU service or OS compositor; readable pixels never pass through display conversion (MD-32); G56 (opaque cross-origin pixels never map into a renderer, so canvas raster of opaque sources is never in the renderer); content-dependent filter cost kept off opaque surfaces (MD-31); video layers on the audio clock; overlay promotion measured by MD-S6.

**Scope.** In: everything in the title line above. Out, with the interface stated in Section 6: layout and hit-test traversal (layout spec), style and the animation timing model (style spec and a future animation spec; this spec runs compositor animations it is handed), glyph raster and shaping (fonts and text), decoding and `hg-colour`'s numeric contract (images and media), SVG's document model and geometry APIs (a future SVG spec; this spec owns SVG painting), PDF (its own spec), WebXR and WebNN.

**Success, in measurable terms** (Section 8): WPT paint directories, the WebGPU CTS and the Khronos WebGL suite at Izcal's own floors, with **exact-match** rates published beside pass rates; bit-identical pixel hashes for canonical surfaces on the CPU and every GPU back end of every reference device; zero cross-site data observable through any GPU process; device-loss recovery ≥ 99% with no page able to crash the OS; p95 frame time and input-to-photon latency against the best shipping engine; FP-14's budgets; and answers to "why did this repaint" for every repaint on the mutation corpus.

## 2. History: what came before and why it was built that way

### 2.1 Chronology

| Assumption | Where it came from | Why it no longer holds | Evidence |
|---|---|---|---|
| OpenGL is the portable GPU API | 2009–2015 engines; ANGLE; WebRender | macOS deprecated GL; Android GLES "is no longer under active feature development"; Windows' native API is D3D12; WebGL itself is translation overhead on Metal | [GA 5.10, 7.4][GA]; [HP 4.6][HP] |

## 4. First principles

### 4.1 Users' real tasks

- **See the page correctly and smoothly**: every frame presented on time, scrolling following the finger, colour right on the display in front of them.
- **Not be tracked or robbed through rendering**: a page must learn nothing about the GPU, driver or display beyond coarse buckets, and nothing about another site's pixels.
- **Keep battery and memory**: no work when nothing changes; overlays for video; GPU memory released for hidden tabs.
- **Find out why** (developers): why this repaint, this layer, this jank, this colour, this shader error.
- **Reproduce and compare** (developers, testers, agents): the same page renders the same pixels everywhere.

### 4.2 Platform primitives

The specifications define the pixels where they define them: CSS 2.1 Appendix E (paint order), Compositing and Blending 1 (simple alpha compositing, blend modes, isolation), Filter Effects 1 and 2, CSS Masking 1, CSS Backgrounds 3 and Borders 4, CSS Images 3 and 4 (gradients, `image-rendering`), CSS Color 4 and 5 (interpolation spaces), CSS Transforms 1 and 2 (3D rendering contexts, Newell's algorithm), Scroll-driven Animations, Web Animations, View Transitions 1 and 2, SVG 2 painting, HTML canvas and OffscreenCanvas, WebGPU and WGSL, WebGL 1 and 2 with GLSL ES 1.00 and 3.00, HTML's "update the rendering" ([RP 3–5][RP]; [CS 5–6][CS]; [WG 1–9][WG]). They leave open anti-aliasing, blur algorithms within stated bounds, gradient dithering, `image-rendering: auto`, border corner transitions and dash spacing, stroke shape at tight curves, and 3D intersection numerics ([RP 6.1][RP]).

The OS interfaces fix how pixels reach the screen: Metal, Vulkan, Direct3D 12 and DXGI, IOSurface and Core Animation, DirectComposition and composition surface handles, Wayland with linux-dmabuf and presentation-time, X11 Present, Android SurfaceControl and AHardwareBuffer ([GA][GA]; [OSD][OSD]). Their published facts that shape the design: a DirectComposition target must belong to the window's process ([OS 2.9][OSD]); no Wayland client can attach buffers to another client's surface ([OS 3.1][OSD]); macOS's public cross-process route is IOSurface by Mach port ([OS 1.11–1.12][OSD]); Android's `SurfaceControl` is parcelable ([OS 5.3][OSD]); D3D12 accepts self-hashed DXIL because the hash "was never intended as a security feature" ([GA 3.1–3.3][GA]); the Agility SDK cannot be shipped under MIT ([GA 3.8–3.9][GA]); the Vulkan loader is Apache-2.0 and installed by the OS or driver ([GA 1.1–1.4][GA]).

Izcal's own architecture supplies the rest: per-(site, container) renderers (I-1), typed capability IPC (B2), the recorded substrate (B1), property trees as data (B6), the layout spec's immutable fragment store and `hg-paint-order` contract, partitioned atlases (FP-D14), G56's opaque-pixel rule and `hg-colour`'s canonical encodings.

### 4.3 Izcal's principles that bind this design

P1 outranks P4: a slower GPU path that leaks nothing beats a faster one that leaks; P1 also decides the process model (GR-D2). P2: one rendering model on every OS and device, conformance before speed. P3: every accelerated path has a correct CPU path, and in this design the two produce the same bits (GR-D3). P6: every performance claim here is either sourced or a measurement milestone (Section 9.1). M-1: no graphics library, no engine source as evidence; OS graphics APIs and drivers are interfaces.

### 4.4 Assumptions kept and broken

| Assumption from existing engines | Keep or break | Why |
|---|---|---|
| A sandboxed GPU process separate from renderers | **Keep** | Every engine converged on it ([HP 12][HP]); I-2 requires it |
| One GPU process for all sites | **Break** | Per-process OS isolation, per-process hang penalties, compiler and driver bugs reachable from any site ([SR 2.6, 3.1–3.4][SR]); GR-D2 |
| Property trees, paint chunks, layerize after paint | **Keep** | The arc Chrome finished in 2021 with measured wins ([HP 1.5–1.7][HP]); B6 |
| Rendering may differ by GPU and driver | **Break** | Fingerprinting and test flakiness; integers are exact ([RP 7.2][RP]); GR-D3 |
| GPU float raster is faster, so use it | **Break for page content, keep as measured fallback** | Unmeasured cost of integer GPU raster is a milestone (GR-S3); a device class falls back only on measurement |
| Compute-only GPU 2D | **Break** | Unbounded intermediate memory ([HP 6.4][HP]); CPU coarse raster with exact sizes, GPU fine raster |
| A high-level shader compiler between the browser and the driver | **Break** | Where the CVEs are ([SR 8.1][SR]); Izcal emits MSL, SPIR-V and DXIL directly |
| WebGL on a GL emulation layer (ANGLE) or native GL | **Break** | Excluded by M-1; native GL is deprecated or frozen; WebGL runs on Izcal's HAL |
| A CPU fallback for WebGL and WebGPU | **Break** | A JIT in a privileged process is a "high security risk" ([HP 2.8][HP]); specs allow failure; HGBA-2 5.6 already says surface failure |
| Compile shaders on first use | **Break** for internal shaders | Precompiled closed set at build time ([HP 7.3][HP]) |
| Layers derived from DOM elements and overlap | **Break** | Layer explosion ([CS 1.2–1.3][CS]); layers derived from paint chunks with a cap |
| Redraw everything every frame | **Break** | Cannot drive partial present or overlays ([CS 1.6–1.7][CS]) |
| The compositor scrolls asynchronously | **Keep** | Input latency must not depend on script ([CS 4.1–4.6][CS]); LY-D13's protocol makes it exact |
| A single swap chain per window | **Break on macOS** | Tile tree for damage ([OS 1.8][OSD]) |
| Vsync comes from the GPU process | **Break as a universal rule** | On macOS and Wayland the timing source lives in the window's process ([OS 11][OSD]); GR-D15 |
| Noise on canvas readback (D-S1) | **Break for 2D canvas, keep for WebGL and WebGPU** | Canonical pixels remove device entropy; randomization is detectable ([SR 6.8][SR]); GR-D12 |
| Driver blocklists and workarounds | **Keep** | Driver bugs are permanent ([HP 2.3][HP]); the WebGPU spec expects them ([WG 1.7][WG]) |

### 6.1 Processes and placement (GR-D2)

The GPU process is where every engine now loses: 209 of the 535 Chrome graphics CVEs NVD published in 2026 are GPU-process bugs reached from a compromised renderer, and the three in-the-wild GPU-driver sandbox escapes of 2025 went through vendor user-mode drivers ([SR 1.1–1.3, 1.17][SR]). A single GPU process for every site adds three costs on top: shader-compiler and validation bugs land in the process that holds every site's pixels ([SR 3.1, 3.7][SR]); OS GPU memory isolation is per process (WDDM 2.0 gives each process its own GPU virtual address space, [Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-virtual-memory-in-wddm-2-0)), so two sites inside one process are not isolated by the OS ([SR 2.6][SR]); and hang penalties fall on whoever submitted the work: Metal revokes access for "too many timeouts or hangs" ([`MTLCommandBufferError.Code`](https://developer.apple.com/documentation/metal/mtlcommandbuffererror-swift.struct/code); per-process scope is an inference, Q-GR-11), and Windows bug-checks after more than five TDRs in 60 s ([SR 3.3–3.4][SR]). I-1 already forbids sharing a renderer between sites for the same kind of reason. The one process that must still see every site's pixels, the compositor, is a recorded **I-1 shared-process exception** beside media's audio and capture services (9.5).

| Option | What a compromise of the GPU side reaches | Cost | Verdict |
|---|---|---|---|
| (a) One GPU service for raster, compositing, canvas, WebGL and WebGPU (every engine today) | Every site's pixels, textures, shaders and atlases; the driver | Least memory | Rejected for P1 reasons above |
| (b) Compositor GPU service plus **one shared content GPU process** for all sites' content work | The compositor is protected from shader and raster bugs; sites are not protected from each other | One extra process | Rejected: it uses isolation as a memory lever, which FP-7 and FP-D8 forbid; it exists only as HGBA-2 I-1's below-threshold reduced mode, on the same RAM measurement as renderers', never on desktop classes |
| (c) **Compositor GPU service plus a content GPU process per renderer key** (site, container; origin where FP-D8 keys renderers by origin) | That (site, container)'s pixels, textures and shaders, which its renderer could already draw, plus the driver's kernel interface; nothing of other sites | One process per visible (site, container), driver memory per process (unmeasured, [SR 3.6][SR]), cross-process texture sharing for tiles, GPU context switching | **Recommended** |
| (d) Raster in the renderer on the CPU, compositor-only GPU service | — | — | Rejected: G56 forbids opaque cross-origin pixels in the renderer, and most page images are no-cors cross-origin, so tiles containing them cannot be rastered there |

**The content GPU process** is keyed **exactly like the renderer** it serves: by (site, container), and by origin wherever FP-D8 keys renderers by origin (every desktop class today), so two subdomain renderers that FP-D8 separates never share a content GPU process, its atlases, pipeline caches or image regions, and the networking projection's "F fixed by the process lock" holds for G68. It does every piece of GPU work whose behaviour depends on page content: reading and validating that site's display lists, layerization, path processing and raster of its tiles, its glyph atlases (FP-D14, which already partitions them per (site, container, partition)), its decoded images (received from its media process into regions it fixed, FP 6.5, which satisfies G56 because the content GPU process is not a renderer), Canvas 2D backings that are tainted or accelerated, and the WebGL and WebGPU services with their shader compilers. It holds one device, never presents to a window, and writes into tile and surface textures that the **compositor allocated at a fixed size and format** and granted to it, so the compositor samples them under IPC-R7's exemption. Two kinds of shared object cross this boundary, and each has a rule. **Shared textures and memory are granted once** (G71): an OS shared handle (NT handle, IOSurface port, dmabuf fd) cannot be revoked once duplicated, so a texture granted to one content process is never re-granted to another; it is freed only when that process exits or releases it, and its bytes stay on that site's ledger while the holder keeps it, so pinning memory is charged and killed at budget. **Fences are observed, never waited on by the GPU** (G72): a shared timeline fence can be signalled to any value or never, so the compositor keeps one fence object per (content process, compositor) pair, checks each tile's fence on the CPU against the frame deadline, samples a tile only if its fence completed in time and draws the last completed tile otherwise; a hostile process can stall only its own tiles. IPC-R7's exemption is restated to name fences as mutable shared state outside it (9.5). **Start and device on demand (reconciliation 2, Q8; owner decision OD-5).** The process starts only when one of its key's surfaces has a **rendering opportunity**: a visible document with a frame intersecting the viewport plus the prepaint margin; throttled off-screen frames start none, by the same process-independent rule as GR-D15's throttling, so the rule reveals nothing about the process model. It may come from a **spare** process locked at first use (as FP's spare renderer). It starts **device-less**: canonical raster on the CPU gives the same bits as the GPU (GR-D3), so it opens a GPU device, with the common internal pipelines and the rare ones lazily from the driver cache, only when its key uses WebGL, WebGPU or an accelerated canvas, draws video under a page effect, or its visible raster work exceeds a threshold the cost model sets from GR-S2 and GR-S3, and closes the device after 30 s† without such use. Budgets: device-less ≤ **2 MiB†** charged at idle (FP-38's figure: a process with no JS agent), with a device ≤ **12 MiB†** (GR-47). The shell's content process (which rasters prompts, GR-D28) and the spare are device-less. It marks its memory volatile when its last document is hidden and exits 30 s† later (FP 6.6's grace) if no document, WebGL, WebGPU or canvas context is live (FP-38's pattern); spawn to first tile is a target (GR-27). Cross-site iframes are other keys and get their own content GPU process, as they get their own renderer. Merging a key's device-less raster into its media process (the same authority, by the media spec's own option (d) argument) is measured at GR-M0 with GR-S2 and MD-S10, not adopted.

**The compositor GPU service** does only content-independent work: validating compositor frames (tile grids, a small property-tree subset, scroll nodes, animations, surface embeds, damage), aggregating surfaces with **clip enforcement** at every embed (a child's quads are clipped to the geometry its parent drew, so LY-15 holds even against a compromised child, [CS 10.4][CS]), compositor scrolling, **transform and opacity** animations (and scroll-driven animations of those two), colour output and HDR, frame scheduling and presentation. It links no display-list reader, no path rasterizer, no shader front end and no WebGL or WebGPU crate (G63); its only shaders are Izcal's precompiled internal compositing set (GR-D7). Its page-controlled inputs are therefore tile grids, a property-tree subset of transforms, rectangular and rounded-rectangle clips in fixed point, opacity, scroll nodes, embeds and HDR metadata already validated by the media process; `clip-path` and filter animations re-raster in the content GPU process at each BeginFrame instead (6.8). A compositor compromise still reaches every site's composited pixels, so the compositor-frame IDL's size (types, variants, maximum nesting) is published as its IPC-R11 artifact with its fuzz target, and security prompts never pass through it (GR-D28).

**Security prompts (GR-D28).** The security scope requires that a permission or consent prompt be composited above page and shell content, cannot be covered, and is approved only by input the broker hit-tested while it was unoccluded (CON-R1, CON-R3, CON-R5). A compositor compromised from a content process could draw a fake prompt or cover the real one, and the broker cannot judge "unoccluded" from compositor data. So **prompt surfaces bypass the shared compositor**: the prompt renderer's tiles are rastered by the shell's own content GPU process and handed to the broker, which places them in **their own OS layer above the compositor's layers** (a sibling CALayer, a DirectComposition visual above the content visual, a Wayland subsurface placed above, an Android child SurfaceControl). The broker derives the prompt's rectangle and its unoccluded state from its own OS layer tree only. **The property is normative** (phishing spec amendment, 21 October 2026): a **broker-placed layer above the content layer, unoccludable by the page, broker-hit-tested**; the shell's separately owned prompt window is a conforming implementation where the OS requires a window, and its own layer *is* that layer. Do not read the two as competing mechanisms: GR-19 tests the property, not the window class. **The full-page phishing and malware interstitial is a prompt-renderer surface in this layer**, and GR-19's suite covers it (phishing spec PH-D6, PH-12). Input routing between sites uses the embedder renderer's hit-test regions (LY 6.14) clamped by the broker with parent-supplied geometry; the compositor supplies only its own scroll and animation offsets, which the broker cross-checks against the renderer's last acknowledged values. GR-19 probes it.

**What it costs, and what would reverse it.** Driver memory, context-switch cost and spawn time per process are unpublished for every vendor ([SR 3.6][SR]), so spike **GR-S2** measures, on every reference device and at the corpus's p50, p90 and iframe-heavy content-process counts (5–15 cross-site frames): resident memory of an empty device and of a device with one shared texture, per-process descriptor heaps, the loss of framebuffer compression on shareable tiles, GPU context-switch time, spawn to first tile with warm and cold driver caches, and the compositor's added p95 frame latency, with and without hardware-accelerated GPU scheduling. **GR-D2's acceptance** is FP-1, FP-S30 and FP-6 met with content GPU processes counted, and FP-7 met in the scope OD-5 gives it: reconciliation 2's arithmetic (Section 3) showed that, with every process holding a device at 12 MiB†, FP-1 reaches about 70.5 MiB against 64, FP-S30 exceeds 1.25 GiB by about 100 MiB when the visible tab is iframe-heavy, and FP-7's iframe-heavy limit fails by about four times; with start-on-opportunity and device-on-demand they hold on paper, and FP-7 measures renderer isolation with per-key service processes on their own line, as OD-2 did for networking ([RN2 Q8][RN2]). The thresholds serve GR-47 and the trigger: a content GPU process at idle costs ≤ **2 MiB†** charged device-less and ≤ **12 MiB†** with a device, CPU side plus driver baseline. If it does not, or the compositor's p95 frame time rises more than **1 ms†** at the iframe-heavy count, the response is to reduce per-process cost (fewer pipelines at start, lazy pipelines from a warm driver cache, smaller descriptor heaps, shorter lifetimes), never to co-locate keys; option (a) is never the fallback.

### 6.2 The GPU abstraction (GR-D1, GR-D22)

`hg-gpu-hal` is Izcal's own abstraction over three native APIs, and only three: **Metal** (macOS, iOS later), **Direct3D 12** (Windows) and **Vulkan** (Linux, Android). It is HGBA-2 Section 5's `Gpu` device class: devices advertise capabilities, never vendors; all work is asynchronous and returns fences on a per-device timeline; there is no blocking map; validation errors are sticky; device loss resolves exactly once with an epoch. No OpenGL, GLES or Direct3D 11 back end exists: macOS deprecated GL, Android's GLES "is no longer under active feature development", D3D12 runs down to feature level 11_0 hardware, and every no-GPU or blocklisted machine gets Izcal's CPU path ([GA 5.10, 7.4–7.5][GA]). Microsoft's WARP software device is never created by either GPU process kind (G66): it is a JIT software rasterizer, the class GR-D10 excludes.

**Its model is the one the native APIs are converging on**, not Vulkan 1.0's object model: resources addressed through one bindless descriptor heap with 32-bit indices where the device offers it (D3D12 resource binding tier 3 or shader model 6.6 dynamic resources; Vulkan descriptor indexing), and through **bounded descriptor tables per pass** behind the same HAL interface where it does not (tier-2 D3D12 hardware, Android devices whose descriptor-indexing limits are lower), which the render graph can build because every pass declares its resources; GR-S1 and the Android floor check measure which devices take which model; GPU buffer addresses where the API has them; render passes with explicit load and store intent (tile-based mobile GPUs need it); compute dispatch; **barriers computed by Izcal's render graph** (`hg-gpu-graph`) from each pass's declared usage, as a WebGPU implementation must derive them from the specification's usage scopes, which leave synchronization to the implementation ([WG 1.14][WG]); timeline fences shared across processes for tile handoff, observed on the CPU by their receiver and never waited on by a GPU queue of another process (G72). This is the shape published design discussions arrive at (bindless heaps, coarse stage-mask barriers, dynamic rendering), and Vulkan's own descriptor-heap and unified-layout extensions point the same way ([GA 8.4–8.5, 5.7][GA]). The HAL exposes no float-dependent fixed function that the canonical path would use (GR-D3); the compositor's final display conversion and WebGL and WebGPU content use the native rasterizer and blending.

**Memory** is Izcal's own sub-allocator (`hg-gpu-alloc`), because placement decides fragmentation, residency and per-site accounting (FP-14, FP 6.6), so allocator crates such as `gpu-allocator` are engine work, not bindings ([GA 6.22–6.23][GA]). Budgets come from the OS: DXGI `QueryVideoMemoryInfo` with its change event, Vulkan `VK_EXT_memory_budget`, and on Metal `recommendedMaxWorkingSetSize` and `currentAllocatedSize`, polled on pressure because Metal has no change event ([GA 3.18, 5.3, 4.9][GA]). Volatile and low-residency states (`setPurgeableState`, `SetResidencyPriority`) implement FP 6.6's "volatile, then release" ([GA 4.10, 3.18][GA]).

**Device loss and diagnostics**: `MTLCommandBufferError` codes, `GetDeviceRemovedReason` and DRED, `VK_ERROR_DEVICE_LOST` with `VK_KHR_device_fault` map to HGBA-2's `LossReason` ([GA 3.17, 4.11, 5.4][GA]); fault data stays local unless the user sends a crash report (GR-D19).

**Each back end's version floor** follows GR-D21's rule: Metal on macOS 14 or later, Apple silicon and Intel Macs alike while their macOS version is patched, with residency sets from macOS 15 when present ([GA 4.2–4.8, 4.13][GA]); in-box Direct3D 12 at feature level 11_0 with resource binding tier 2 (tier-1 hardware takes the CPU path), enhanced barriers where reported ([GA 3.12, 3.15][GA]); Vulkan 1.3 on Linux with `memory_budget`, external dmabuf memory and DRM format modifiers ([GA 5.2–5.6][GA]); Vulkan 1.1 with Android Baseline Profile 2022 on Android ([GA 5.9][GA]).

**Bindings and the loader (GR-D22).** The native APIs are reached through binding crates that are generic infrastructure with an MIT option: the `objc2` family (`objc2`, `objc2-foundation`, `objc2-metal`, `objc2-quartz-core`, `objc2-io-surface`, `block2`; MIT or Zlib OR Apache-2.0 OR MIT), the `windows` family (MIT OR Apache-2.0, generated from Microsoft's MIT win32metadata), `wayland-client` and siblings (MIT), `x11rb` (MIT OR Apache-2.0), `ndk`, `ndk-sys` and `jni` (MIT OR Apache-2.0) and `libc` (MIT OR Apache-2.0) ([GA 2.6–2.7, 6][GA]; [OS 10][OSD]). **Vulkan and SPIR-V bindings are generated by Izcal** from Khronos's `vk.xml` (Apache-2.0 OR MIT) and the SPIR-V grammar (MIT with Khronos's notice), because `ash`'s last release is from April 2024 and the `spirv` crate is Apache-2.0 only ([GA 2.1–2.5, 2.8, 6.1][GA]). Dynamic loading is a small Izcal wrapper over `libc` and `windows-sys`, not `libloading`, whose licence is ISC ([GA 6.21][GA]). **The Vulkan loader** is Apache-2.0, installed by GPU driver installers on Windows, by distribution packages on Linux and in the Android system image; Khronos "strongly discourages" bundling it and static linking is impossible ([Vulkan loader application interface](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderApplicationInterface.md); [GA 1.1–1.4][GA]). Izcal classifies it as an **OS interface on condition that it is loaded from the system and never shipped** (no Izcal installer, Snap, AppImage or Izcal-built Flatpak runtime contains it; a third-party runtime's loader, such as the freedesktop Flatpak runtime's, is an OS-class interface like the distribution's; G67), and disables implicit layers in both GPU process kinds so third-party overlay code never runs there ([GA 1.9–1.10][GA]). An Izcal loader written from the documented loader–driver interface stays a measured alternative (GR-S9 records which files the loader opens under the sandbox).

### 6.3 Paint: display lists, paint order and property trees (GR-D5, GR-D6, GR-D17)

**What paint produces.** `hg-paint` runs in the renderer after layout, reading `hg-fragment` and computed style only (G38). It produces, per document: four **property trees** (transform including scroll offsets, clip, effect, scroll), each node a small record keyed by a stable id; and a back-to-front sequence of **paint chunks**, each a run of display items sharing one property-tree state (four node ids), in the order CSS 2.1 Appendix E and its successors define ([RP 4.1–4.2, 4.6][RP]). This is the structure Chrome reached in 2021 after seven years ([HP 1.5–1.7][HP]); B6 and Stage 1 5.7 already chose it, and Izcal derives it from the specifications (Section 6.26).

**Stacking contexts are effect nodes.** Compositing 1 says "everything in CSS that creates a stacking context must be considered an 'isolated' group" ([RP 4.3][RP]), so the stacking-context tree, the effect tree's isolation groups and `hg-paint-order`'s stacking order are one structure. **Identities never use fragment ids** ([RN2 Q1][RN2]): a property-tree node id and a display item's identity derive from the node slot (or an anonymous box's path from its nearest node), the pseudo-element and the fragment's index within its box, never from layout's fragment-store ids or epochs (LY-D18, G45), so the display-list hash is the same after an incremental and a from-scratch pass. Every trigger (opacity, filter, transform, `isolation`, blend, clip-path, mask, `backdrop-filter`, `will-change`, `contain: paint`, fixed and sticky, z-index on flex and grid items, the top layer) is a row in a generated table carrying its spec anchor. 3D rendering contexts follow CSS Transforms 2: participants paint into planes, sorted with Newell's algorithm and split where they intersect, in **integer arithmetic** (i64 and i128 homogeneous coordinates), with each split vertex rounded to a 1/256 device px grid, half to even, immediately after its split, so bit lengths stay bounded and the result is one deterministic answer; at most **4,096† splits per 3D context**, beyond which the remaining planes are drawn in painter's order by centroid depth, a recorded deviation. No prose source for an existing engine's plane-splitting numerics exists and DET-1 needs one answer ([RP 4.4–4.5][RP]).

**Display items** are content-addressed: each item's 64-bit hash is computed from its fields, and each chunk's hash from its items and state. A repaint re-emits only chunks whose inputs changed (the style spec's "affects" mask and the layout spec's dirty boxes say which boxes), and the renderer sends **deltas**: new chunks, plus references by hash to chunks the content GPU process already holds. After the content GPU process acknowledges a frame, the renderer keeps only chunk hashes and per-box chunk membership (FP 6.4's rule), so invalidation is a hash comparison, which also is DET-1's display-list hash ([RP 4.8][RP]). **Chunk resend:** when a delta names a hash the content process no longer holds (it evicted the chunk for a hidden tab or under pressure, or it is a new process after a crash or device loss), it answers `MissingChunks` with the hashes, and the renderer repaints those boxes from its fragments at its next frame, a recorded decision point (JS-D15). Recovery from a content-process crash is therefore **one repaint, never a tab reload**, which is how this spec restates HGBA-2 5.5's "re-rasterizes from retained display lists" and R-2 (9.5).

**Content-blocking suppression is paint-only (CB-D13, CB 6.2).** When content blocking refuses a load, the affected element is **not drawn**: its display items are omitted at paint, while its box, layout and geometry are exactly what any failed load produces, so the page cannot tell "blocked" from "failed" through layout, hit testing or geometry. The blocked flag is a paint-only input; no API exposes it, IntersectionObserver v2 included. A click whose target is a link whose navigation content blocking would refuse is not followed, and the page observes the same no-op it would for any refused navigation (CB 6.9). The decision reaches paint from the partition service as that paint-only input, never as page-visible state.

**The display-list format (GR-D6)** is a generated `.hgidl` type, read by `hg-ipc-gen`'s generated reader with a Kani harness (VER-1), copied once and validated (IPC-R7). It is not an IPC-R16 exception, so **IPC-R16 entry 1 (WebRender display lists) is removed**. Generation is not enough: the Firefox "Graphics: WebRender" component (largely Rust) still had 2026 sandbox escapes for "incorrect boundary conditions" ([SR 9.1][SR]), and the advisories name a component, not the faulty code's language, so the content GPU process checks **semantic limits** before use: property-tree depth ≤ 1,024†, clip chain length ≤ 256†, filter chain ≤ 64† primitives, every referenced resource (image region, atlas entry, canvas, surface) owned by the sender's (site, container) through generation-tagged ids (IPC-R8), total painted area per frame ≤ 64× the viewport†, and paths in the **bounded path format**. Each limit has a **deterministic degradation** that the renderer applies before sending, with the same function the validator runs, so a deep but legitimate page renders and only hostile input is rejected: property-tree nodes deeper than the limit are flattened into their nearest representable ancestor (transforms composed, clips intersected), clip chains beyond the limit are intersected into one clip, and painted area beyond the limit is culled outside the prepaint region; each degradation is a logged, explainable event (GR-D24).

**The bounded path format** (asked for by TX 9.5, R21) is defined here; its **types live in `hg-display-list` (L2)**, so the text stack (L2t) can emit them without depending on L2g, while flattening, stroking and dashing live in `hg-path` (L2g) ([RN2 Q18][RN2]): segments are lines, quadratic and cubic Béziers and elliptical arcs in fixed point (24.8 in local units, ±8,388,607, relative to the path's own origin); at most **65,536† segments per path**, **4,096† paths per chunk**, subpath nesting not applicable (flat), coordinates within the range, and every count checked in G18's checked arithmetic. Large glyphs and colour-glyph vectors from the text stack use the same format (TX 6.1).

**SVG records (the SVG spec's R7, applied 20 October 2026).** An SVG display item carries, per path, a **binary exponent** (|e| ≤ 100†) chosen as a pure function of the path's coordinates and its CTM, with an f64-to-device fallback for the rare path whose exponent would overflow the fixed-point grid, so SVG user units of unbounded range (SV-D2) flatten exactly; and **one f64-composed CTM per SVG record**, relative to the nearest property-tree node, so an SVG transform list is composed once in f64 in the renderer and its integer conversion happens at the record boundary, not per segment. **Display items reference paths by content hash**, so a `use` instance and its source share one path body, and an HTML element's `url()` paint resource (clip, mask, gradient referenced from CSS) resolves through the **same resolver** as an SVG-internal reference, so `clip-path: url(#c)` means one thing everywhere. Static transform trigonometry (a `rotate(30)` in a transform attribute or CSS transform) uses `hg-interp`'s degree functions (the animation spec's amendment), so a static and an animated transform at the same angle flatten identically.

**Pixel snapping (GR-D17, LY-D3).** Layout's fragments are in 1/64 CSS px; paint maps them to device space with the recorded device scale as an exact rational p/q (q ≤ 2¹⁶; the environment snapshot records it) and snaps **each edge independently** to the nearest device pixel, rounding half to even, wherever the accumulated transform to device space is an integer translation; under any other transform nothing is snapped and anti-aliasing applies. Border widths snap to whole device pixels with a minimum of 1 for non-zero widths; text baselines snap vertically for horizontal text, while horizontal positions keep the text spec's subpixel phases (TX 6.9). ResizeObserver's `device-pixel-content-box` is the snapped right edge minus the snapped left edge (and the same vertically), computed by `hg-paint-order`'s exported function so layout and paint can never disagree. The rule is deterministic and identical on every OS; it is a black-box observation against the three engines at GR-M0 (Q-GR-4).

**The paint-order contract (`hg-paint-order`, LY-D22).** This spec **owns** the crate and supplies its production implementation; the layout spec owns the requirements it wrote (LY 6.14) and the Appendix-E reference builder, a test oracle, and a contract change needs both owners ([RN2 Q2][RN2]). The data it serves (chunk order, chunk-to-fragment map, property-tree nodes, ink overflow) stays in the renderer after acknowledgement, inside the 72 B renderer share (6.22), so `hg-hit` never waits on another process. It provides: stacking and chunk order, the chunk-to-fragment map, property-tree lookups and ink overflow. `hg-hit` walks it in reverse (LY-D14); LY-7 compares hit testing with paint order over the production implementation from GR-M1, replacing the layout track's reference builder as production while keeping it as a test oracle. **Ink overflow** (shadows, outlines, filters' expansion, `text-decoration` beyond the line box) is computed by paint and published per chunk.

**Layerization (GR-D5)** runs after paint, in the content GPU process, as a pure function `layerize(chunks, property trees, compositor-mutable nodes) → layers` (`hg-layerize`): consecutive chunks merge into one layer unless a chunk's transform, clip or effect node is **compositor-mutable** (a compositor-scrolled scroll node, a compositor-animated transform, opacity or filter, a video, canvas or iframe surface) or merging would cross such a chunk in paint order. Overlap no longer forces new layers by element: when a non-mutable chunk lies above a mutable layer, it goes into the next layer in paint order, and the number of compositor-mutable nodes is capped (**16† per document**): beyond the cap, the lowest-priority mutable nodes (priority: video and canvas surfaces and iframes first, then compositor-scrolled nodes by area, then animations by area) lose compositor mutability and animate on the main thread, an explainable, recorded event; two mutable nodes are never merged into one layer. DOM-derived layer explosion therefore cannot happen ([CS 1.2–1.3, 1.8][CS]). **A chunk that uses its backdrop** (a non-separable or non-normal blend mode, `backdrop-filter`) is placed in the same layer as everything it reads, which may demote a mutable node below it; the compositor never blends across layers except with normal source-over. Every layer carries its reason as data (GR-D24). `will-change` creates the stacking context and containing block the specification requires and is a hint to mark the node compositor-mutable until 300† of the document's own BeginFrame ticks after its last change; the expiry is counted in recorded ticks, so it is a pure function of recorded inputs (G70); it never forces a layer on its own ([CS 1.10][CS]).

### 6.4 Canonical pixels and the rasterizer (GR-D3, GR-D4, GR-D17)

**The rule (GR-D3).** Every pixel of page content (backgrounds, borders, text, images, gradients, paths, SVG, shadows, filters, masks, blending, 3D planes) and every pixel a page can read (Canvas 2D, OffscreenCanvas 2D, `createImageBitmap` from page content, `toDataURL` and `toBlob` of 2D canvases, HTML-in-canvas snapshots when admitted) is computed by **integer arithmetic only**, with one specified rounding at each step, so the result is **bit-identical on the CPU and on every GPU back end of every device**. **The canonical image** of a document at a frame is the result of rasterizing its whole display list in one integer pass at the frame's recorded scroll offsets and animation samples, with scroll offsets snapped to whole device pixels. The compositor's composition is part of it: tiles are composited by the same integer blending as `hg-raster`, at integer layer origins, with compositor scroll offsets snapped to whole device pixels at presentation and compositor opacity applied by the same integer multiply, so **for translation and opacity the composed screen equals the canonical image**. While a non-translation transform animation is in flight (rotation, scale, perspective), the layer is resampled by the compositor and that layer is labelled non-canonical for those frames; its final frame is canonical again. Canonical captures (O4, GR-51) are taken from a one-pass CPU raster of the display list, never by reading the screen. Only integer GPU arithmetic is reproducible across vendors by specification: WGSL integers wrap exactly, while WGSL, Vulkan and Metal all allow float results to differ (unspecified rounding, reassociation, fusion, flushing; Metal defaults to fast math) ([RP 7.1–7.5][RP]). Vulkan's repeatability guarantee excludes shaders with atomics or stores, so canonical GPU passes use **commutative integer accumulation only** ([RP 7.4][RP]).

**What this buys.** P1: rendering stops being a fingerprint (one canvas text test gave 3.05 bits and six canvas and WebGL tests 5.73 bits, [SR 6.1][SR]), without noise, which FP-Scanner showed 2018's countermeasures expose through their inconsistencies ([SR 6.8][SR]). P2: reftests can be exact, and Izcal reports exact-match rates beside WPT's fuzzy passes (64% of css-borders and 52% of compositing reftests are fuzzy today, [RP 6.3][RP]). P3: the CPU path is not a fallback that looks different; HGBA-2 5.6's "match pixel-for-pixel on reftests" holds by construction, and CPU or GPU placement becomes invisible, so **placement may depend on timing without being recorded** (Section 6.21). DET-1's pixel scope extends from "out of scope" to every canonical surface (GR-51). Agents and tests get identical screenshots on every machine (O4).

**What is not canonical**, by necessity, and is labelled so in every capture: WebGL and WebGPU output (WGSL and GLSL accuracy is deliberately loose, [WG 3.8][WG]), which is noised where it leaves for any script-readable surface (6.15); video frames on the display path and video drawn under page effects (their readback is canonical through the media spec's integer path, MD-32); layers during in-flight non-translation transform animations; the compositor's final display conversion and tone mapping, which no page can read (MD-D8); and `desynchronized` canvases presented through an overlay, whose canvas contents stay canonical.

**The rasterizer (GR-D4)** is `hg-raster`, written from published descriptions, never from an implementation (Section 6.26):

| Gradients | CPU builds a 1,024†-entry ramp per gradient in the specified interpolation space through `hg-colour`'s canonical integer path; GPU and CPU index it in fixed point | CSS Color 4 default Oklab, legacy colours in encoded sRGB, premultiplied; **ordered 8×8 dithering keyed by the pixel's integer coordinates in the document's device-pixel space** (layer origins are integer-aligned, so scrolling does not change a pixel's dither) instead of the random dithering the spec permits | [RP 3.6, 5.10][RP] |
| Filters | Same | Integer kernels: feGaussianBlur by the three-box approximation the specification permits for σ ≥ 2 ("within roughly 3%") and an exact integer Gaussian kernel below; box-shadow blur with σ = blur radius ÷ 2, checked against the 5% bound; feTurbulence by the specification's reference algorithm in fixed-order IEEE double on the CPU only (JS-D12 discipline), its output then canonical; no resolution reduction under pressure | [RP 5.1–5.6][RP] |
| Masks and clips | Same | Coverage masks in the same integer pipeline; luminance masks with the specification's coefficients in fixed point | [RP 5.9][RP] |

**Placement (GR-D4).** For each tile, HGBA-2's cost model (R-6) chooses CPU or GPU fine raster from the tile's measured inputs (path count, area, device class); because the bits are identical, the choice affects only time. Low-end and compute-limited GPUs (a Mali-G78 about 14× slower than an M1 Max on GPU stroke expansion, [RP 9.2][RP]) therefore get the same image. Every placement and every fallback is a logged, explainable event (GR-D24), never a silent veto ([HP 1.4][HP]).

**What decides whether canonical-everywhere holds (GR-S3).** No one has measured integer-only GPU raster against float GPU raster on real pages. GR-S3 builds both on the reference devices at GR-M1 (the float variant as a measurement prototype only) and compares MotionMark and corpus p95 frame time and energy per interaction-corpus run, because integer compute raster gives up fixed-function blending and the on-chip blending of tile-based GPUs. GR-D3's reversal trigger: if the canonical GPU path is more than **1.15×†** slower at p95, or uses more than **1.15×†** the energy (GR-43), on a device class, display-only page content on that class may use the float path with a tolerance against the CPU reference (GR-6), while every **readable** surface stays canonical. The readable-surface rule never reverses.

**UA-defined pixels (GR-D17).** Where specifications leave pixels open, Izcal writes one rule, anchors it as a recorded deviation with a WPT test, and measures the three engines black-box first (Q-GR-3): border corner colour transitions (a straight joint from the outer to the inner corner of the curve, as the ratio of the two border widths prescribes), `dotted` as round dots and `dashed` as dashes of length 2× width with gaps equal to width, both adjusted so each side starts and ends on a full dash or dot, `double` as thirds; outline on shaped corners follows `corner-shape`'s outer contour; `image-rendering: auto` as above; anti-aliasing as above; filter resolution never reduced ([RP 5.12–5.13, 6.1][RP]).

### 6.5 Colour working space and HDR output (GR-D16)

**Blending happens in gamma-encoded sRGB.** SVG 2's `color-interpolation` (initial sRGB, [SVG 2 §13.9](https://www.w3.org/TR/SVG2/painting.html#ColorInterpolationProperty)) and CSS Color 4's legacy-colour rule point to encoded sRGB; Compositing 1 itself names no colour space, so encoded blending is web-compatible practice that Izcal adopts and Q-GR-3 confirms black-box ([RP 3.3][RP]). Linear-light blending looks better but would break reftests built on encoded compositing ([RP 3.4][RP]). Filters keep their specified spaces: CSS filter functions in sRGB, SVG filter primitives in linearRGB by default ([RP 3.5][RP]).

**Two working encodings for page layers**, matched to the media spec's decode classes (MD-D8): **S8**, premultiplied 8-bit sRGB-encoded RGBA, for layers whose content lies in sRGB and SDR (class S images, legacy CSS colours); and **E16**, premultiplied signed 16-bit fixed point holding the **extended** sRGB-encoded value (the sRGB transfer function extended symmetrically below 0 and above 1, as CSS Color 4 defines extended sRGB), for layers containing wide-gamut colours, class W images or HDR content. **E16 bit for bit:** the stored integer is the encoded value × **4,080** (255 × 16), so every S8 value is exactly representable (v × 16); range −32,768 to 32,767, about −8.03 to +8.03, which holds HDR content up to the 49× reference-white headroom that encodes to about 5.3; values outside are clamped; every conversion rounds half to even. Converting an S8-representable E16 value back to S8 is exact. Because rounding at 1/4,080 differs from rounding at 1/255, blending S8-representable inputs in E16 can differ from blending them in S8 by one S8 step; so that one wide-gamut element never changes the rounding of unrelated content, **the encoding is chosen per isolated group** (each stacking context's group, 6.3) from that group's own content, never per layer, and GR-2 includes a suite proving that S8 content in an E16 group's sibling groups is unaffected. **One numeric contract for colour conversion**, owned by the media spec's `hg-colour` (MD-D28) with this spec co-signing: tables and ramps are *built* on the CPU with `hg-colour`'s IEEE f32 contract through `hg-math` (the media class W path), which G61 allows as table construction, like feTurbulence; *per-pixel* work on CPU and GPU is integer lookup and interpolation in those tables. **One contract, two forms** ([RN2 Q12][RN2]): per-pixel f32 at decode in the media process (G55), and tables built with the same contract and applied by integer lookup at raster (G61); each (source, destination) conversion has exactly one form, named in `hg-colour`'s table of conversions. A class W texel (linear FP16) enters E16 or S8 through a table indexed by its half-float bit pattern (65,536 entries per destination encoding, built once). Class W images and colours in other predefined spaces therefore reach S8 or E16 through one definition, the same in either process and on either placement, never through GPU float math. Canvas 2D uses the encoding its `colorSpace` and `colorType` select (`unorm8` or `float16`, [WG 9.3][WG]), with `float16` canvases stored as E16 internally and converted exactly at readback.

**Display conversion happens once, at the end, in the compositor**: from S8 or E16 to the window's output descriptor (format, primaries, transfer, headroom), with HDR tone mapping by the BT.2390 EETF and gain-map application at the live headroom, as MD-D8 and MD-D9 require. This is the one place float arithmetic touches page pixels, and no page can read its output (MD-32). Per OS, the compositor writes: FP16 scRGB swap chains with `SetColorSpace1` on Windows, the SDR white level scaling reference white; `rgba16Float` drawables or IOSurfaces with extended-range colour spaces and `wantsExtendedDynamicRangeContent` on macOS, honouring that EDR headroom is 1.0 until content asks for more; `color-management-v1` image descriptions on Wayland where the compositor supports them, sRGB otherwise; and `setDataSpace` with extended-range brightness or HDR headroom on Android ([OS 1.18–1.20, 2.13–2.15, 3.11, 5.9][OSD]; [CH 9][CH]). The output descriptor is a per-window HAL input that the broker derives from OS signals and sends whenever the window moves between displays or settings change, together with refresh rate and scale ([OS 8][OSD]). **The broker, not the compositor, sets the colour metadata the OS sees**: from a closed enum of parametric output descriptors (primaries, transfer and luminance from `hg-colour`'s constants), it attaches the colour space to each IOSurface, swap chain or Wayland image description itself and strips anything the compositor attached; no ICC bytes ever pass from a GPU process to WindowServer, DWM or a Wayland compositor (IPC-R15). It also checks each IOSurface's pixel format, plane count, bytes per row and size against the descriptor it requested.

**Text masks** (TX-D6's open question) are blended with the text colour in the layer's encoding, as coverage-as-alpha in encoded sRGB, with the text spec's darkening and contrast already inside the mask; shape anti-aliasing uses the same coverage-to-alpha mapping, so text and an outlined copy of the same glyph render alike ([RP 3.8][RP]).

### 6.6 Text rendering integration

Glyph masks come from the text spec unchanged: rasterized by `hg-glyph-raster` in the renderer (TX-D13), uploaded with dimensions in the copied message into regions of exactly that size, under a per-partition upload budget of 256 KiB† per frame (TX 6.1). **The atlas lives in the content GPU process** of that (site, container), with one A8 and one RGBA8 pool per partition (FP-D14, TX 6.10), so atlas partitioning is now backed by a process boundary between sites. Text draws as atlas-sampled quads composited by the canonical blending of 6.4, exact on every device. TX decides which glyphs arrive as masks and which as paths: masks up to TX's atlas limit (A8 up to 256², with TX's stem darkening and hinting inside the mask), paths only where TX sends them (TX-D13 permits, not requires, paths above 64 device px, and TX keeps darkening continuous across its own threshold). Paths go through `hg-raster` like any path, so they are canonical too; the GPU float outline path TX-D13 permits under TX-33's tolerance is **not needed** while GR-D3 holds and is built only if a device class takes GR-D3's display-only fallback. **COLRv1 glyphs** above TX's mask threshold arrive as a bounded **COLRv1 vector item**: the paint graph flattened by TX, within TX's fuel bounds, to fills, linear, radial and sweep gradients, clips and blend groups, every one of which `hg-raster` already has, carried in the same generated format with its own count limits. Canvas 2D text uses the same masks and the same compositing, and its authoritative raster runs in the renderer (6.15), as TX 6.9 says. No font code exists in either GPU process (G26).

### 6.7 Compositing, tiles, damage and cross-origin surfaces (GR-D5, GR-D18, GR-D23)

**Tiles.** Each layer is rastered into a grid of tiles covering the visible area plus a prepaint margin in the scroll direction. Tile size is a measured trade-off between per-tile overhead and invalidation waste: Chrome's published sizes (roughly 256 × 256 px for CPU raster, roughly viewport width × a quarter of viewport height for GPU raster) would re-raster up to 5,184 times the changed pixels for a 10 × 10 px change at a 1920 × 1080 viewport ([CS 2.1–2.2][CS]). Izcal starts at **256 × 256 device px† for both placements** with **sub-tile damage**: only the damaged rectangle of a tile is re-rastered, scissored, which is cheap because every raster path is the same integer code. Waste (re-rastered pixels ÷ invalidated pixels) is a target (GR-42); the size is re-chosen from corpus measurement at GR-M1. Solid-colour tiles have no texture ([CS 2.9][CS]).

**Damage.** Each compositor frame carries invalidation damage (tile contents changed) and exposure damage (layer added, removed, moved), as published designs distinguish ([CS 3.1][CS]); the compositor unions them per output buffer and presents partially wherever the OS can take it (6.10).

**Compositor frames** from content GPU processes carry, per document surface: layers (tile grids of compositor-allocated textures granted once to this process, G71, each tile with a point on the pair's fence, G72), the property-tree subset those layers use, scroll nodes with their scrollable range and snap areas, animations (6.8), embeds of other surfaces by capability id, and the frame's damage. Holding an embed id gives no access to the surface's pixels ([CS 10.1][CS]). The compositor validates every field, clamps every geometry to its surface, and **enforces the embedder's clip and transform on every embedded surface** with the same parent-supplied geometry the broker uses to clamp hit-test regions, so drawing and input can never disagree at an iframe edge ([CS 10.4][CS]; LY-15).

**Cross-origin surfaces and effects (GR-D18).** Constant-time filter code is necessary but not enough: GPU compression and frequency scaling leak pixel values through hardware (GPU.zip stole a username in 30 minutes; Hot Pixels worked with countermeasures on), and as of September 2023 no GPU vendor had committed to a fix ([GPU.zip](https://www.hertzbleed.com/gpu.zip/); [SR 5.4–5.7][SR]). Izcal's rule: **a cross-origin surface (an out-of-process iframe, an opaque image layer, a tainted canvas) is never an input to a page-controlled effect whose cost or output can depend on its pixels.** Concretely: SVG reference filters (`filter: url()`), `backdrop-filter` and non-normal `mix-blend-mode` over a cross-origin surface treat that surface's region as transparent black for the effect's input, while the surface itself is still composited above or below in paint order without the effect (Filter Effects 1 already says UAs "should not apply SVG reference filters" to cross-origin iframe pixels, [RP 5.5][RP]); CSS filter functions (`blur()`, `opacity()`, `brightness()` and the rest) apply to an ancestor of a cross-origin surface through a **fixed-cost path**: the content GPU process applies them to the group with a kernel whose work depends only on geometry. Fixed ALU work is not fixed memory traffic: GPU.zip leaks through **lossless framebuffer compression**, whose DRAM traffic depends on how compressible the pixels are, and a contrast-amplifying filter binarizes them. So two further rules apply. (1) **Every render target that holds or derives from cross-origin pixels is created with lossless compression disabled** where the API allows it (Metal `allowGPUOptimizedContents = false`; Vulkan `VK_EXT_image_compression_control` with compression disabled; on D3D12 the layouts and flags measured per vendor in GR-S7), the compositor's output buffers included where the OS lets Izcal choose; device classes where it cannot be disabled are listed with their measured channel in GR-14's results. (2) **Amplifying filter functions are clamped** over a cross-origin surface: `contrast()`, `brightness()` and `saturate()` above 1 are applied as 1, and `hue-rotate()` and `invert()` only where those clamps already hold, a recorded deviation. This extends the media spec's MD-31 (b), the enumerated timing channels, to every cross-origin surface (G69); one list of cross-origin rendering channels (filters, compression, frame timing, `requestVideoFrameCallback`, decode timing) with measured capacities is kept by this spec, with the media spec contributing the decode-timing and `requestVideoFrameCallback` rows ([RN2 Q28][RN2]). It costs some visual fidelity in rare designs and is probed with the published GPU.zip method with compression both on and off (GR-S7, GR-14).

### 6.8 Scrolling and compositor animations (GR-D13)

**Who scrolls.** The compositor GPU service owns the visual offset of every **compositor-scrollable** scroll node between frames: one with no non-passive wheel or touch listener in the event's path, no `scroll`-linked behaviour that must run first by specification, and its content rastered in tiles. The broker routes a scroll gesture to the compositor when its hit test lands on such a node, and to the renderer otherwise; the compositor applies the delta at the next frame, so scrolling never waits for script ([CS 4.1–4.6][CS]). It implements the layout spec's **delta protocol** exactly (LY-D13): it sends (scroll node, delta, gesture phase, sequence number); the renderer applies compositor deltas at its frame's scroll step as recorded inputs and returns its own changes (`scrollTo`, anchoring, re-snap, anchor-positioning shifts) tagged with the last compositor sequence it consumed. Sequence numbers make the stale-position bug WebKit hit impossible ([CS 4.7][CS]). A non-passive listener region waits for the renderer up to a **listener timeout**, then scrolls as if `preventDefault()` had not been called: a UA intervention no specification defines ([CS 4.4][CS]). Izcal does not adopt another engine's constant: the value is set at GR-M0 from a black-box observation of all three engines (Q-GR-20) and Izcal's own input-latency targets (GR-32), and the gap is filed with the UI Events and Pointer Events editors; the timeout, as the renderer sees it, is a recorded B1 input. Sticky and fixed positioning move on the compositor from layout's sticky constraints; snap selection during a gesture happens in the compositor over layout's snap areas, and the renderer re-snaps after layout (LY 6.10). Checkerboarding (scrolling past rastered tiles) is counted per frame (GR-31).

**Compositor animations.** The animation spec hands the compositor, per animation, its **bounded hand-off record** (the animation spec's 6.5, applied 20 October 2026, replacing the earlier prose list): id, property, keyframes in `hg-interp`'s integer form, timing function, start time resolved at "ready", the class (C compositor, S content GPU) and the record's byte bounds, with Web Animations' delegation hook ([CS 5.3–5.4][CS]); both sides compute current time from that start time and the shared timeline, so they never drift. The compositor **samples only at the document's recorded frame tick** — AN-D3's one tick per frame, the sample-time rule of the animation spec's 6.3 — never between ticks. Per-frame reports (sample time, class S offset, end) go to tools and target AN-6 only, never into any page-visible surface. The compositor animates **`transform` and `opacity` only**, and **scroll-driven animations** of those two, sampled from **the same scroll offset it draws** in that frame, which is stricter than the spec's permission to be inconsistent ([CS 5.5][CS]). `filter` and `clip-path` animations whose geometry needs no layout run off the main thread **in the content GPU process**, which re-rasters the affected tiles at each BeginFrame from the same start time, so the compositor never parses page filters or rasterizes page shapes. Interpolation of the two compositor properties is one integer function (fixed-point transform decomposition and opacity), in a shared L2g crate the animation spec owns from AN-M0 (`hg-interp`, split from `hg-interp-geom`; the compositor links no path data), used by both the compositor and the main thread, so their results agree bit for bit; style's f64 computed values are converted to it at the boundary (6.28, 9.5). Anything needing layout stays on the main thread.

**View Transitions.** Captured old-state elements become snapshot surfaces rastered by the content GPU process at capture, charged to the page as their own FP-14 line (not to the 2.5-viewport tile budget, which they would break, [CS 12.6][CS]), and composited under the `::view-transition` pseudo-element tree in the top layer ([CS 5.7–5.8][CS]). **Compositor-held snapshots take only opacity, transforms, rectangular and rounded clips and `plus-lighter` (if admitted in the compositor); an animation of a snapshot that needs any other effect skips the transition and animates on the main thread instead** (the animation spec's GR-D18 amendment, applied 20 October 2026), so the compositor's effect vocabulary never grows toward page-controlled pixel work.

### 6.9 Frame scheduling and the frame clock (GR-D15)

**The timing source is per OS**, because the native signal lives with the window on two platforms: macOS view and screen display links (macOS 14; `CVDisplayLink`'s creation functions deprecated in macOS 15) and Wayland frame callbacks, presentation feedback and FIFO all belong to the window's connection, i.e. the broker ([OS 1.14–1.15, 3.4–3.6, 11][OSD]). The broker forwards a **typed timing stream** (vsync time, refresh interval, presentation feedback with flags such as `zero_copy`) to the compositor over a dedicated high-priority endpoint; on Windows 11 the compositor reads `DCompositionWaitForCompositorClock` (on Windows 10, while supported, DXGI's vblank wait), which wakes at a monitor's vertical blank or on another timer and lets Windows turn the vblank interrupt off when no one waits, while DXGI "always uses the cadence of the primary monitor" ([compositor clock](https://learn.microsoft.com/en-us/windows/win32/directcomp/compositor-clock/compositor-clock); [OS 2.11][OSD]); whether it follows the window's monitor is measured in GR-S5; on Android the compositor uses `AChoreographer` frame timelines on its own looper ([OS 5.4][OSD]). Every thread here (raster workers, the compositor's scheduler, the broker presentation thread, the Android looper) comes from the substrate, and every OS callback (Metal presented handlers, `AChoreographer` frames, composition-clock waits, Wayland presentation feedback) enters through the substrate's OS-callback bridge that the media spec requests, recorded under B1 (Stage 1 G3; [RN2 Q17][RN2]). Spike GR-S5 measures the relay's added latency on macOS and Wayland, and the broker's per-frame commit cost (one Core Animation transaction or `wl_surface` commit per frame), which runs on a **dedicated broker presentation thread** that touches no other broker state.

**The compositor is the frame scheduler.** It subscribes to timing only while something changes (FP-21's "vsync requested only while something changes", as Firefox's Silk and Wayland's hidden-surface behaviour already do, [CS 6.6, 12.7][CS]); at each tick it sends BeginFrame (with the deadline and the frame's target presentation time) to the renderers and content GPU processes that asked for a frame, which is Stage 1 5.1's "vsync message", now from the compositor. Deadline scheduling follows published practice: render as late as the measured p95 render time allows, so frames are fresh ([OS 6.3][OSD]); a frame whose content misses the deadline is drawn with the previous content plus compositor-only updates (scroll, animations), and the frame record lists exactly **which updates it included**, so "partial" and "dropped" frames are computed, not estimated ([CS 6.8][CS]). Pipelining depth is one frame by default: FP 6.6's rule, two buffers, and three only while an animation misses frames, on macOS, Windows and Linux; `CAMetalLayer`'s default of 3 drawables is set to 2 and raised to 3 by the same rule ([OS 1.2][OSD]). Android may need three always, because the system compositor may hold a buffer until scanout ends ([OS 5.8][OSD]); that is measured before it is proposed to FP (Q-GR-15).

**Recorded inputs (JS-D15).** In each renderer: the BeginFrame tick (time, sequence, deadline), the compositor deltas consumed, and which of its frames were presented with which presentation time. In the compositor (recorded when recording is on): timing ticks and presentation feedback. Presentation timestamps come from the OS where it gives them (Wayland presentation-time, DXGI and composition-swapchain statistics, Metal presented handlers, Android transaction callbacks) rather than estimates ([CS 6.4][CS]).

**Throttling.** HTML lets a UA drop non-visible navigables to 4 rendering opportunities a second or fewer ([CS 6.2][CS]). Izcal's rule is a function of visibility and intersection only, identical for in-process and out-of-process frames, because throttling only cross-process frames lets a page detect site isolation ([CS 11.4][CS]); hidden documents get no rendering opportunities, and B7's pixel-optional tabs run paint to chunks with BeginFrames from the shell's agent controller, never rasterizing. **Amended 20 October 2026 (the animation spec's GR-D15 amendment): the display runs at the highest needed rate**, and each renderer's BeginFrames are **decimated to that renderer's own vote** (the animation spec's per-renderer cadence, 6.11) instead of one global rate; under battery saver the cap is **30 Hz† with user scrolling and input exempt**; the Hardened profile's 60 Hz clamp is a **ceiling**, never a target.

**Cross-site frame timing.** All sites share one compositor and one present loop, so one site's heavy compositor work could delay another's frames, observable through rAF and Event Timing. The compositor schedules its per-frame work in **fixed per-surface slices** so one surface's work cannot delay another's composition beyond a bound, and GR-44 measures the residual channel. **Refresh cadence** is exposed: rAF follows the display, because pages that adapt to 75 Hz or 165 Hz panels need it — **and, per the animation spec's amendment, a renderer's rAF cadence follows that renderer's decimated rate**; timestamps exposed to script are quantized (each document relative to its own time origin, AN-D3); the refresh rate's bits (one of about six common rates) are counted in PRIV-2, and the Hardened profile clamps rAF cadence to 60 Hz as a ceiling (GR-D15).

**Low latency.** `desynchronized` 2D canvases get their own OS layer (6.10) and present outside the page's frame where the OS allows an overlay, with tearing permitted as the specification says ([CS 7.3–7.4][CS]). Pointer prediction (`getPredictedEvents()`) and OS-delegated ink (the WICG Ink API) are admission questions under the layout spec's specification-admission rule (LY-D10's process), not designed here. No latency target is claimed without Izcal's own photodiode rig, because no current cross-browser measurement is published ([CS 7.2][CS]; GR-S10).

### 6.10 OS presentation (GR-D14)

The broker owns every window and its OS composition tree; GPU processes never hold a window or an X connection ([OS 4.6][OSD]). Prompt surfaces arrive from the shell's content GPU process and go into their own OS layer above the compositor's (GR-D28).

### 6.11 Video compositing (GR-D26)

Video frames arrive from the media process, or from the hardware-decode process of the same (site, container) where hardware decode is used (MD-D10), as OS handles (IOSurface, DXGI shared handles, dmabuf, AHardwareBuffer) with their descriptors, and never pass through a renderer (G56). **Routing**: frames go to the compositor's video layers for display, and, on demand, to the **content GPU process** of the embedding key for script-visible uses (`texImage2D`, `importExternalTexture`, `copyExternalImageToTexture`, and the display copy of `drawImage(video)`), where readable results use the media spec's integer YUV-to-RGB path (MD-32). Script-visible reads use the frame at the official playback position, which the media process supplies (media 6.7). **For an origin-clean video source the media process sends that frame as canonical RGBA to the renderer too**, because the renderer is the authoritative raster of every origin-clean canvas whatever its display placement (6.15); hardware-decoded frames are read back to the media process first. Opaque or tainting sources go only to the content GPU process (G56) ([RN2 Q21][RN2]). The compositor holds a **video layer** per playing element and, at each tick, picks **the decoded frame whose presentation interval contains the expected display time**, on the **audio clock** the media spec supplies (media 6.7's rule, owned by media and implemented here), repeating or skipping to keep the cadence (for example 2:3 for 24 fps on 60 Hz), with the chosen frame recorded and a **cadence-error** counter per second (GR-36). YUV-to-RGB conversion and scaling on this display path may use GPU float (non-canonical, display only). **A video under a page effect** (a CSS filter, mask, non-normal `mix-blend-mode`, or a rounded clip with content above it) is not a compositor layer: the content GPU process draws it into the page's tiles, labelled non-canonical, so the compositor never implements page effects. A video layer is **promoted to an OS overlay** when the compositor can prove nothing draws above it in its window region (no translucent or effect-bearing layer above, no rounded clip it cannot pass to the OS) and the OS accepts the format; protected frames (PlayReady SL3000 and equivalents) are overlay-only by construction, because their pixels never reach Izcal's GPU code ([CS 8.1–8.6][CS]). Overlay energy is measured per OS by MD-S6 with the published 15-minute battery method ([OS 3.13][OSD]). `requestVideoFrameCallback` metadata comes from the compositor's frame record, with `processingDuration` coarsened as its draft suggests ([CS 8.4][CS]).

### 6.12 Shaders (GR-D7, GR-D8)

**One IR, two web front ends, three back ends, all Izcal's own.**

| Part | Design | Evidence |
|---|---|---|
| `hg-shader-ir` | Typed SSA with structured control flow, explicit address spaces and **bounds checks as IR operations** inserted by one pass after validation, so every memory access has a dominating check that a verifier can confirm; no undefined behaviour is representable | WGSL defines almost everything the targets leave undefined ([WG 3.3–3.11][WG]) |
| `hg-wgsl` | WGSL parser (LALR(1) grammar with the template-list pass), type checker, **uniformity analysis**, alias analysis, `const` and `override` evaluation, the spec's limits; validation before any lowering, as WebGPU requires | [WG 3.2–3.13][WG]; [WG 1.3][WG] |
| `hg-glsl-es` | GLSL ES 1.00 and 3.00 with WebGL's restrictions (Appendix A loop forms, packing rules, ASCII after preprocessing, reserved prefixes), lowering GLSL's combined samplers and GL conventions | [WG 6.4–6.5][WG] |
| `hg-shader-msl` | A **minimal, fixed MSL subset** (no templates, no headers, one fixed preamble) with `mathMode = safe`-equivalent options and explicit bounds clamps (Metal has no buffer robustness mode); compiled by macOS's own Metal compiler (an OS interface, reached through the `MTLCompilerService` XPC service, a recorded sandbox grant in GR-S9's per-OS index) | [GA 4.1–4.4][GA]; [WG 5.2][WG] |
| `hg-shader-spirv` | SPIR-V binary from Izcal's generated grammar tables; `NoContraction` and RTE where available; `robustness2` used when present, explicit clamps otherwise; workgroup zeroing by `VK_KHR_zero_initialize_workgroup_memory` or an inserted clear | [RP 7.3][RP]; [WG 5.1, 5.4][WG] |
| `hg-shader-dxil` | DXIL written directly (LLVM 3.7 bitcode subset per `DXIL.rst`), container and signatures, **Izcal's own validator** for every rule `DXIL.rst` lists, and the validator hash (a "modified MD5" over RFC 1321) implemented from INF-0004's prose where that prose specifies every modification, otherwise derived black-box with `dxil.dll` as a test-only oracle (inputs and outputs only; DXC's source, where the algorithm was also published, is never read); container fields the emitter needs are each mapped to a prose source or such a black-box observation (GR-S1; gaps in 11.2); the BYPASS sentinel where the in-box runtime reports support | [GA 3.1–3.6][GA] |
| Builtin library | WGSL and GLSL ES builtins whose results vendors may compute differently (`sin`, `cos`, `exp`, `log`, `pow`, `sqrt`, division and the rest the specifications leave loose) are lowered to **Izcal's own fixed implementations** built from basic operations, with `NoContraction` and precise flags, one implementation per function as JS-D12 does for `Math`, so a builtin-evaluation probe cannot name the vendor; the residual entropy of compute output per device class is measured and published (GR-23) and the performance cost measured on the WebGPU corpus (GR-37) | P1; [SR 6.1–6.3][SR] |
| `hg-shader-check` | Re-validates every emitted module against Izcal's own target validators; translation validation that every memory access is dominated by a check; CI additionally runs vendor validators (the SPIR-V validator, DXC's validator, Metal's compiler) as **black-box test oracles** that never ship | [SR 8.2, 8.4][SR] |

**Why direct emission (GR-D7).** All 16 CVE-bearing bugs DarthShader found were in DXC, an optimizing C++ compiler that runs inside the GPU process and was reached by translator output ([SR 8.1][SR]); emitting HLSL for an OS-side or bundled compiler would put that component back. Izcal's back ends emit simple, already-optimized, bounds-checked code, and the driver's own compiler is the only one left (an OS interface Izcal cannot remove). On Metal that residual is larger: Izcal sends MSL **text**, which Apple's C++ front end and LLVM optimizer compile in the `MTLCompilerService` XPC service, the same class of optimizing compiler the DarthShader bugs were in. Izcal narrows it by emitting only the fixed MSL subset, fuzzing Apple's compiler with that subset in the device lab, and building **binary archives for content shaders too, per partition**, so a page triggers each compilation at most once. Rust prevents memory corruption in the translator but not wrong code, so validation of Izcal's own output is part of the pipeline, not a test ([SR 8.2][SR]).

**DXIL and Direct3D 12 (GR-D8).** The Agility SDK's `D3D12Core.dll` is under Microsoft's proprietary DirectX licence with indemnity terms and cannot ship under MIT-only ([Agility SDK package](https://www.nuget.org/packages/Microsoft.Direct3D.D3D12)); `dxil.dll` is a Microsoft binary distributed with DXC releases, and no Microsoft source says Windows includes it; DXC is NCSA-licensed ([GA 3.7–3.9][GA]). The validator hash "was never intended as a security feature" and its algorithm is published ([Microsoft](https://devblogs.microsoft.com/directx/open-sourcing-dxil-validator-hash/); [INF-0004](https://github.com/microsoft/hlsl-specs/blob/main/proposals/infra/INF-0004-validator-hashing.md)). So Izcal uses **only the in-box D3D12 runtime** and never redistributes any of them (G67); its D3D12 feature tier is whatever in-box D3D12 offers on Izcal's Windows floor, measured by spike **GR-S1** (highest shader model, enhanced barriers, BYPASS support, and whether a self-hashed DXIL module loads and runs on Intel, AMD, NVIDIA and Qualcomm drivers without `dxil.dll` present). Reversal: if self-produced DXIL cannot load on a vendor's driver, Izcal emits **DXBC (SM 5.1)** for that vendor, losing SM 6 features there (wave operations and 16-bit types), which removes WebGPU's `subgroups` and `shader-f16` features on that vendor only. This fallback is **unproven**: DXBC's token format is given only in a Windows Driver Kit header, which is an OS component's source and so not evidence under M-1 part 3 (HGBA-2 2.3.3), and no published description of its container checksum was found ([GA 3.14][GA], Low); the only public descriptions of the checksum are in other projects' source, which M-1 part 3 also forbids. So both the token encoding and the checksum would be derived black-box with the in-box `d3dcompiler_47.dll` as a test-only oracle (inputs and outputs only), and GR-S1 tests whether the in-box runtime accepts DXBC that Izcal encoded with a self-computed checksum; if neither path loads on a vendor, D3D12 on that vendor uses the CPU path for page content and exposes no WebGL or WebGPU.

**Internal shaders** (raster, compositing, colour output, video conversion) are written in a WGSL subset, so one front end and one validator serve both, and a lint forbids floating-point types in canonical shaders (G61). They are compiled at build time to all three back ends, and their pipelines are created at process start, so no internal shader compiles during browsing (GR-33), the cure Flutter and Skia both reached ([HP 2.4, 7.3–7.4][HP]). On Metal the build produces MSL text, and the macOS compiler builds a binary archive at first launch of each Izcal version, because the `.metallib` format is unpublished ([GA 4.4][GA]).

**Caches (GR-D20).** Izcal's pipeline caches are keyed by the networking spec's in-process projection (T, C, X, n) and live in the content GPU process of their (site, container). Driver shader caches are shared by the OS across processes, so a page could time whether another site compiled the same shader, as the WebGPU spec warns ([WG 1.11][WG]); Izcal **salts every content shader per partition** (an inert constant derived from a per-partition key, so the driver's cache key differs), and measures the residual channel (GR-S8, GR-17). Internal shaders are identical for everyone and need no salt.

### 6.13 WebGPU (GR-D11)

`hg-webgpu` implements the WebGPU specification in the content GPU process, over `hg-gpu-hal`, with WGSL through `hg-wgsl`; the renderer side (`hg-webgpu-client`) holds handles and forwards a typed command stream, buffered (Firefox's unbuffered first release was a measured bottleneck, [WG 2.7][WG]), and completion is event-driven, never polled. Validation is total, as the spec requires: every command is checked against the device's requested limits before it reaches the HAL, errors are asynchronous and contagious, and all memory is zero-initialized, workgroup memory included ([WG 1.2–1.5, 1.13][WG]). Barriers come from usage scopes through `hg-gpu-graph` ([WG 1.14][WG]). The WebGPU CTS (BSD-3-Clause, normative) is the correctness target per back end ([WG 11.1][WG]).

**Exposure (GR-D11).** WebGPU is now in every major engine and Safari prefers it to WebGL ([WG 2.5, 2.8][WG]), but it gives every page a high-resolution clock: Giner et al. build one from atomics in coherent GPU memory without timestamp queries, and "disabling shared memory would not prevent timers in WGSL" ([SR 5.8][SR]). HGBA-2 I-6 keeps high-resolution timers behind COOP and COEP cross-origin isolation. So WebGPU is **on by default in cross-origin-isolated contexts**, which already have such timers, and **behind a per-site permission elsewhere**, until GR-S6 shows on every reference device that the WGSL atomics clock is no finer than the non-isolated `performance.now()` resolution, or the owner records an I-6 exception in HGBA-2's decision log with the measured resolution (GR-22). Hardening in both cases: (1) **adapter information** is one of at most **4† buckets** (Izcal's device classes, never vendor or model; the spec's cap is 32), and each bucket fixes **limits, features and subgroup sizes** from a tier table: a feature (such as `subgroups` or `shader-f16`) is exposed in a bucket only if every device in it supports it identically, `subgroups` only where every device has the same subgroup size range, so the feature set is not a vendor bit even under the DXBC fallback ([WG 1.10, 1.12][WG]); (2) **timestamps** are coarsened to at least 100 µs, HR-Time's "100 microseconds, or a higher implementation-defined value" that the spec and GPU-R7 require ([WebGPU privacy considerations](https://www.w3.org/TR/webgpu/#privacy-considerations); [HR-Time](https://w3c.github.io/hr-time/); [SR 5.9][SR]); (3) the **Hardened profile** (S-4a) turns WebGPU and WebGL off. Whether cross-origin iframes should need an embedder's delegation is open (Q-GR-10): no such policy-controlled feature was confirmed in the specification this pass, and adding one would be a compatibility deviation. Coarsening does not stop clocks built from atomics: Giner et al. recovered inter-keystroke timing at F1 82–98% and an AES key in 6 minutes without timestamp queries, and recommend a permission ([Giner et al. 2024](https://gruss.cc/files/WebGPUAttacks.pdf); [SR 5.8][SR]). Spike **GR-S6** measures the atomics-clock resolution, the keystroke attack and the cross-process cache channel on Izcal's reference devices at GR-M0 and GR-M1, before WebGPU ships anywhere. **Compatibility mode** is offered only as a feature level on core-capable hardware, enforcing compat's stricter limits; Izcal adds no OpenGL ES or D3D11 back end for it ([WG 2.2–2.3][WG]).

### 6.14 WebGL (GR-D9)

WebGL 1 and 2 run on `hg-gpu-hal` in the content GPU process: no ANGLE, no native GL. `hg-webgl` implements the GL state machine and every WebGL restriction (initialization of all resources, out-of-range rules, no program binaries, primitive restart fixed on, query and sync results never in the issuing frame) ([WG 6.2–6.9][WG]); `hg-glsl-es` compiles shaders to the same IR as WGSL. The renderer side keeps a shadow of WebGL state so `getError` and getters answer synchronously, and the content GPU process re-validates everything (it trusts no renderer). The GL conventions modern APIs lack are emulated in the lowering, per back end, and each emulation is a listed item with a conformance test: clip-space depth range, provoking vertex, primitive restart on lists, GL line rasterization and point sprites, framebuffer origin and `gl_FragCoord`, combined samplers, and transform feedback (for which no Metal equivalent was found this pass; Medium) ([WG 7.3–7.4][WG]). Vulkan's own GL-hosting extensions are used where present. The driver never sees a GL call sequence, only Izcal's HAL commands, whose own invariants (sizes, states, fences) the HAL validates, which is the 2025 lesson ([SR 1.1–1.3][SR]). Cross-origin media never uploads to WebGL, as the spec requires ([WG 6.7][WG]). The Khronos WebGL suite (MIT) is the target ([WG 11.2][WG]).

### 6.15 Canvas 2D, OffscreenCanvas and readback (GR-D12)

**Recording and placement.** `hg-canvas` records 2D commands in the renderer and rasterizes them with `hg-raster`'s canonical integer path (6.4). Where it rasterizes is a deterministic function of declared intent and content, never a hidden heuristic ([HP 9.5][HP]). **The authoritative raster of every origin-clean canvas is in the renderer**, on the CPU: the renderer keeps the command log since its last CPU snapshot and replays it with `hg-raster` when script reads pixels (`getImageData`, `toDataURL`, `toBlob`, `convertToBlob`, `createImageBitmap`, `captureStream`), synchronously and in process, and materializes a snapshot on a background thread when the log exceeds its budget (256 KiB† of commands). Display rasterization runs in the content GPU process (GPU or CPU fine raster) from the same command stream for canvases of 256 × 256 px† or more without `willReadFrequently`, and in the renderer otherwise; its bits equal the renderer's by GR-D3, so **no readback ever crosses processes or waits for a frame** (HGBA-2 5.3). The canvas **becomes content-process-only** at the first command that draws an opaque source (a no-cors cross-origin image or video, a tainted canvas or ImageBitmap), because G56 keeps opaque pixels out of the renderer; it is then tainted and cannot be read anyway. `getImageData` latency is a target (GR-9).

**Readback is canonical, so 2D canvas gets no noise (amends D-S1; one amendment for every surface, owner decision OD-6).** Reconciliation 2 makes this paragraph the text of **one** D-S1 amendment that the fonts (TX-D4) and media (MD-D14) specs cite: noise is applied once, where pixels or samples leave for a script-readable surface, to exactly the outputs that are not canonical: WebGL and WebGPU pixels (below), audio derived from OS-decoded tolerance codecs (MD-D14), and video frames from OS decoders that have not passed MD-42's conformance-hash check for that codec and profile on that device; never to 2D canvases, canvas export (whose encoders in the media process are deterministic), `measureText`, Izcal-rendered audio or Izcal-decoded images and video ([RN2 Q14][RN2]). Stage 1's D-S1 adds seeded noise to readback surfaces. For 2D canvas that noise is now unnecessary for GPU and driver entropy, which canonical raster removes, and harmful: FP-Scanner detected 2018's countermeasures from their inconsistencies, before per-site seeded noise existed ([SR 6.8][SR]), it breaks pages that hash or compare canvases, and it makes test and agent captures differ. So `getImageData`, `toDataURL`, `toBlob`, `convertToBlob` and `createImageBitmap` of 2D canvases return canonical pixels with **no noise**. The remaining entropy comes from fonts: scripts still on the interim OS-font tier (TX-D25) render differently per OS, which TX-22 bounds; D-S1's noise stays for **WebGL and WebGPU output**, where canonical output is impossible, and is applied **once, where non-canonical pixels leave for any script-readable surface**, seeded per (site, container, session): `readPixels`, `toDataURL` and `toBlob` of WebGL and WebGPU canvases, and every transfer of their output into a 2D canvas (`drawImage`), an ImageBitmap (`createImageBitmap`, `transferToImageBitmap`), a `VideoFrame`, or a WebGPU texture with copy-out (`copyExternalImageToTexture`). A 2D canvas that receives such pixels holds the noised pixels and is otherwise canonical, so laundering through a 2D canvas returns noised pixels (GR-8). Buffer reads of compute results (`GPUBuffer.mapAsync`, WebGL transform feedback) cannot be noised without breaking GPU compute; their entropy is reduced by Izcal's builtin library and fixed tiers (6.12, 6.13) and measured (GR-23). Recordings store pre-noise pixels and the seed, so replays and captures are exact ([GO 4.10][GO]). This changes an owner-signed Stage 1 decision, so it needs the owner's signature in the Stage 1 decision log, not only an amendment line; and PRIV-2 (a), which scores linkability as identical identifiers across sites, must be restated as distinguishability (anonymity-set size or mutual information), because a surface that is the same for everyone fails it by construction (9.5).

**Every readable surface, where its pixels live and how they move** (G56, MD-32):

| Constructor or transfer | Pixels held by | Copy path | Status |
|---|---|---|---|
| 2D canvas, origin-clean | Renderer (authoritative CPU replay); display copy in the content GPU process | In process | Canonical |
| `drawImage(video)` into an origin-clean canvas | Renderer (canonical RGBA of the frame at the official playback position, from the media process); display copy in the content GPU process | Media to renderer region | Canonical; OS-decoded frames noised unless MD-42's check passed on that device (OD-6) |
| `toBlob`, `toDataURL`, `convertToBlob` | Encoded in the media process of the key from the canvas's canonical pixels (the renderer's for origin-clean canvases; tainted canvases cannot export) | Region to the media process | Deterministic bytes; no noise unless the pixels carry WebGL or WebGPU noise |
| 2D canvas, tainted | Content GPU process only | — (unreadable) | Canonical, unreadable |
| WebGL or WebGPU canvas | Content GPU process | Readback IPC, asynchronous by API (`readPixels` into a PBO, `mapAsync`) | Non-canonical; noised at exit |
| `createImageBitmap(canvas, image or video)` | Where the source lives; opaque sources in the content GPU process | Same-key regions | Canonical (video: MD-32's integer path); noised if from WebGL or WebGPU |

**OffscreenCanvas** in a worker submits frames as its own surface to the compositor, the same mechanism as iframes and video, so a busy window event loop does not delay it, as HTML encourages; HTML pushes frames to the placeholder in the worker's own update-the-rendering steps; Izcal makes the placeholder's script-visible bitmap change in the window's next rendering step (Izcal's choice within the specification's encouragement to short-circuit), recording which worker frame it used (JS-D15) ([CS 9.1–9.3][CS]). `float16` canvases, `colorSpace`, `ImageData` pixel formats and `filter` follow the HTML standard with the encodings of 6.5 ([WG 9.3–9.5][WG]). **HTML-in-canvas**, if admitted under the layout spec's admission rule, produces snapshots from the same display list with its exclusion list enforced by construction (no cross-origin surfaces, no visited state, no system colours) ([WG 9.6][WG]).

### 6.16 SVG painting

This spec owns how SVG renders: SVG elements become display items through `hg-svg-paint`, using the same paths, stroker, paint servers (gradients with `spreadMethod`, patterns), markers with `orient` and `context-fill`/`context-stroke`, `paint-order`, `vector-effect: non-scaling-stroke`, clipping, masking and filters, and SVG's own isolation rules (opacity, filters, 3D transforms, blending and masking isolate; clipping does not) ([RP 8.1–8.2][RP]). `shape-rendering` and `text-rendering` hints never turn anti-aliasing off (the specification makes them hints), so SVG stays canonical. SVG text gets its positions from the layout spec's inline layout hand-off (LY 6.5.10) and its glyphs from the text stack. The SVG document model, SMIL, the SVG DOM and geometry APIs belong to the **SVG spec** (`reports/Izcal SVG.md`, draft 0.3, owner decisions accepted 20 October 2026), whose typed render tree and reference graph this spec consumes — the record contract is the SVG spec's 6.4 and 6.5 (R7, applied 20 October 2026), replacing this spec's earlier prose list in 6.28. Ownership of the SVG pieces: `hg-svg-paint` here; outer `<svg>` sizing, `foreignObject` and the SVG text interface in the layout spec; the opaque-image host in the media spec. Opaque cross-site SVG images are rendered by the media process with these same crates (MD-D20) and arrive as pixels.

**R7's paint rules, applied 20 October 2026.** (1) The per-path exponent and the per-record f64 CTM of 6.3. (2) **Per-record taint flags**: an SVG record derived from cross-origin resources carries a taint flag, and SVG filters, masks and blends applied over a tainted record substitute **transparent black** for the tainted input — the SVG-image analogue of 6.7's cross-origin rule, recorded as a deviation from the SVG specification's silence, with **SV-16 joining GR-14's channel list** and its capacity measured there. (3) **Filter resolution is never reduced**: an SVG filter's resolution stays the canvas or surface resolution the record targets, because a reduced resolution is a page-observable difference between inline SVG and the same drawing as an image. (4) The **mask luminance-coefficient choice** (SVG 2 leaves `luminanceToAlpha`'s coefficients to implementers) is filed with the CSS WG as Q-SV-5 and until resolved uses Rec. 601 weights, recorded. (5) **Canvas origin-clean**: a same-origin or `data:` SVG image with `foreignObject` drawn to a canvas leaves the canvas origin-clean **once the SVG spec's SV-S3 proof suite passes**; until then such images taint, as MD-D20 provides.

### 6.17 No usable GPU (GR-D10)

When no GPU back end is usable (no supported driver, blocklisted, too many losses), **page rendering continues on the CPU** with identical pixels: `hg-raster`'s CPU fine raster and the compositor's CPU implementation, presenting through the same OS buffers in system memory. This is the real experience for about **21%** of Android devices under GR-D21's floor (12.67% lack Vulkan 1.1, and 86.5% of Vulkan-capable devices meet the dashboard's "AVP 2022" profile: 0.865 × 91.15% ≈ 79% qualify; dashboard snapshot of 24 November 2025, API 23+ devices only, [Android dashboard](https://developer.android.com/about/dashboards)) and for blocklisted desktops, so CPU frame time is a target (GR-35) ([GA 5.9, 7.4][GA]). **WebGL and WebGPU are not emulated on the CPU**: `getContext("webgl")` returns null and `requestAdapter()` resolves to null, which both specifications allow and HGBA-2 5.6 already prescribes; Chrome removed its SwiftShader WebGL fallback from desktop Chrome in 2025 because a JIT in the GPU process is "a high security risk", when about 2.7% of WebGL contexts (at most about 0.5% of page loads) used it ([blink-dev intent](https://groups.google.com/a/chromium.org/g/blink-dev/c/yhFguWS_3pM/m/oLrB5up_BwAJ); [HP 2.8][HP]); reports that Chrome on Windows still falls back to WARP, also a JIT, are unconfirmed (Q-GR-19), and Izcal never creates a WARP device (G66). This amends HGBA-2 4.4's "WebGL2 or CPU is the floor" to "CPU page rendering is the floor; WebGL and WebGPU fail cleanly". Reversal trigger: a measured share of Izcal's **active users** on a supported platform without a usable GPU above 5%†, together with a design for a non-JIT, separately sandboxed software path that the security owner accepts. **Android already exceeds 5% by device share** (about 21% today, a 2025 snapshot); Android is a Stage 2 platform and its Vulkan share grows each year, so the response is decided at GR-M4 from the measured active-user share then (GR-D27), with the options designed now: (a) CPU page rendering without WebGL or WebGPU, as on desktop; (b) the HAL's floor lowered to Vulkan 1.1 without the 2022 profile, using bounded descriptor tables (6.2), which recovers most of the 21% minus the 12.67% without Vulkan 1.1; (c) a GLES 3.1 back end for Android only, which reintroduces the GL driver surface GR-D9 rejects and a fourth back end.

### 6.18 Device loss, hangs and blocklists (GR-D19)

HGBA-2 5.5's rule (three losses in ten minutes blocklist the class for the session) is a second line, because Windows bug-checks the machine after more than five GPU timeouts in 60 s and Metal revokes access after too many hangs ([TDR registry keys](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys); [SR 3.3–3.4][SR]). The first lines are: **short submissions**: the HAL splits all content GPU work into submissions of at most **100 ms†** of measured GPU time (WebGL and WebGPU draws and dispatches split by the HAL; canonical raster is already per tile), with preemption granularity measured per vendor in GR-S2; **a GPU watchdog per content process** that stops any submission running longer than **500 ms†**, well under Windows' 2 s TdrDelay and Metal's timeout; **per-page suspension** after one timeout attributed to a page's WebGL, WebGPU or canvas work: that page's GPU contexts are lost (`webglcontextlost`, `GPUDevice.lost`) and stay unavailable for the session, with the page told through the site panel; and **per-process blast radius**: a content-process hang or crash affects one key, and its tiles fall back to the last presented content until a new process starts and the renderer repaints through the chunk-resend protocol (6.3), one repaint and no tab reload. **Adapter-wide resets are expected**: on most WDDM drivers a TDR resets the whole adapter and every process loses its device. Each loss is **attributed** to the content process whose submission was running, from the HAL's per-process in-flight record; that **site's** GPU APIs are suspended; a loss attributed to process X never counts against the compositor or another site. Device loss in the compositor re-creates the device with a new epoch, and every content process re-rasters its tiles (R-2); HGBA-2 5.5's class rule counts only **unattributed** losses. Crash loops degrade only towards **more** isolation: after three unattributed compositor losses in ten minutes, the compositor switches to its CPU implementation inside the same sandboxed process, and WebGL, WebGPU and accelerated canvas are disabled first; **no GPU work ever moves to the broker or to any less sandboxed process** (G66), the failure Firefox fixed in 2025 by disabling accelerated Canvas2D and WebGPU before any fallback, the same order as Izcal's ([SR 2.7][SR]).

**Blocklists and workarounds** are data, shipped through the TUF channel within 7 days† of a driver advisory (GPU-R8), keyed by (device class, driver version range, OS version) and built from Izcal's own device lab and vendor advisories. Each entry is either a workaround flag the HAL back end implements (a list of named behaviours with a conformance test each) or a block. Telemetry for blocklist maintenance reports only (device class, driver version bucket, fault kind) with user consent; device-fault dumps (DRED, `VK_KHR_device_fault`) stay local unless the user sends a crash report ([SR 4.6–4.7][SR]).

### 6.19 Security (GR-D20)

**The trust picture.** Renderer → content GPU process: same (site, container), still untrusted (IPC-R17); the content process gains the driver's kernel interface, so it is sandboxed as tightly as the driver allows. Content GPU process → compositor: untrusted, and the compositor holds every site's composited pixels, so its input is the smallest typed format, it parses no display list or shader (G63), shared textures are granted once (G71) and foreign fences are only observed on the CPU (G72). Media and hardware-decode processes → content GPU process and compositor: frames and image regions whose size and format the receiver fixed (IPC-R7). Compositor ↔ broker: typed layer updates and timing; the compositor is not trusted with the security prompt, which the broker presents in its own OS layer (GR-D28), nor with colour metadata, which the broker sets (6.5).

| Threat | Design | Target |
|---|---|---|
| Hostile display list, command stream or compositor frame | Generated readers with Kani harnesses (VER-1); semantic limits (6.3); generation-tagged ids (IPC-R8); fuzzers for every format (GPU-R4, GPU-R5); adversarial-peer simulation of each GPU process kind (IPC-R17) | GR-11 |
| Shared textures and fences used against the compositor or another site | Single grant per texture (G71); fences observed on the CPU with a deadline, one per pair (G72); adversarial peers that never signal, signal to `u64::MAX` and write after release | GR-11 |
| Compromised compositor forging or covering a security prompt | Prompts in a broker-placed OS layer above the compositor's (GR-D28); unoccluded state from the broker's own layer tree | GR-19 |
| Shader translation dropping a bounds check | Bounds checks as IR operations; translation validation; own and vendor validators in CI; metamorphic, generative and API fuzzers (GraphicsFuzz-style, WGSLsmith-style, WebGlitch-style) from GR-M1 ([WG 4.1–4.8][WG]) | GR-12 |
| Driver reached with sizes or sequences it mishandles | HAL computes every size once in checked arithmetic into typed descriptors and re-checks them against the allocation; HAL command streams validated against HAL invariants; call-sequence fuzzing on each reference driver ([SR 10][SR]) | GR-11, GR-12 |
| Uninitialized GPU memory across sites | **"Initialized" is a type state** of every resource handle: a resource that may hold old data cannot be bound for reading; pools zero on reuse; every emitted compute shader zeroes workgroup memory; nothing relies on the OS: D3D12 zeroes only memory coming from other processes, and Vulkan promises nothing about new allocations ([SR 7.4–7.8][SR]) | GR-13 |
| Cross-site caches (pipelines, driver caches, atlases) | Per-partition keys; per-partition shader salting; atlases and caches in the site's own process ([WG 1.11][WG]) | GR-17, FP-36 |
| Pixel stealing through effects or hardware | GR-D18's rule, lossless compression disabled on cross-origin targets and amplifying filters clamped; constant-time CPU filter code where filters touch tainted inputs (Filter Effects 1 §15); feDisplacementMap with a tainted map passes through ([RP 5.5][RP]) | GR-14 |
| Rowhammer and high-resolution GPU timers | No timer-query extensions exposed (`EXT_disjoint_timer_query` stays off) ([SR 5.10][SR]); WebGPU timestamps at 100 µs or coarser ([SR 5.9][SR]); WebGPU outside cross-origin isolation only with a permission until GR-S6 (GR-D11) | GR-22 |
| Sandbox loss through crashes | G66; CPU fallback inside the same sandbox | GR-15 |
| Cross-site denial of service through hangs | 100 ms† submissions, 500 ms† watchdog, loss attribution, class rule on unattributed losses only (6.18) | GR-16 |

**Sandboxes per OS** (amending the security scope's GPU row for two process kinds). Linux: the render node only, seccomp with an **ioctl-number allowlist per driver** measured from what Izcal's HAL uses (GR-S9), Landlock's `LANDLOCK_ACCESS_FS_IOCTL_DEV` (ABI 5, [kernel docs](https://docs.kernel.org/userspace-api/landlock.html)) on the render node, no network, no X connection ([SR 2.4, 10][SR]). Windows: low integrity, LPAC where the vendor's user-mode driver runs under it (Q-SEC-9, measured), no win32k lockdown, as the security scope already records; the reason given in the notes (the D3D user-mode driver submits through win32k-routed graphics syscalls) is the researcher's reasoning, not yet checked against Microsoft documentation ([SR 2.2–2.3][SR]); the compositor's composition surface handles are created before lockdown or through the broker. macOS: Seatbelt with only the IOKit user clients the GPU needs. Android: an isolated process with SELinux ioctl allowlists (Stage 2). Vulkan implicit layers are disabled in both kinds (G67). The per-process attack-surface artifact (IPC-R11) lists each kind's endpoints and ioctls.

### 6.21 Determinism (B1)

| Output | How it is deterministic | Check |
|---|---|---|
| Property trees, display list, chunk hashes | Pure function of fragments, style and the recorded environment (device scale as a rational, colour preferences) | DET-1 display-list hash (GR-50) |
| Layers | `hg-layerize` is a pure function of the display list and the recorded compositor-mutable set; `will-change` expiry counted in recorded BeginFrame ticks | Layer list hash under replay (GR-52) |
| Canonical pixels | Integer arithmetic only; CPU and every GPU back end bit-identical | Pixel hash per tile across CPU and GPU back ends on every reference device (GR-2, GR-51) |

| CPU or GPU placement, tile scheduling, raster thread count | Free to depend on timing **because outputs are identical**; not recorded | Device-lab runs randomize placement and compare tile hashes (GR-2, GR-52); simulation runs only the CPU back end, so DST alone cannot show it |

| WebGL, WebGPU, video display path, display conversion | Outside DET-1's pixel scope, as HGBA-3 already states; the command streams are recorded | `rr` and conformance suites |

Recording these inputs costs a share of **one** whole-renderer recording budget (HGBA-3 DET-1, JS-52: ≤ 1%† of p95 frame time), measured jointly with the engine, layout and media and attributed per subsystem; this spec reports its share ([RN2 Q15][RN2]). Simulation mode (Stage 1 3.2) runs both GPU process kinds with the CPU back end only, which now produces the production pixels, so DST covers rendering end to end for canonical surfaces. **Rendering why-queries replay a multi-process unit**: the tab's renderer, its content GPU process and the compositor inputs for that tab's surfaces only, which the compositor records per tab whenever that tab's recording is on, never other tabs' (DevTools DT-D3, 9.5).

### 6.22 GPU memory and footprint (GR-D23)

Every GPU allocation carries FP 6.6's ledger tag (site, container, partition, tab, kind), recorded by `hg-gpu-alloc` in whichever GPU process allocated it; the compositor's tile and surface allocations are charged to the site whose content they hold. FP-14's rows stand, with these additions (Section 9.5): **View Transition snapshots** and **OffscreenCanvas surfaces** on their own lines; a cap of 16† compositor-mutable nodes per document (6.3); prepaint tiles beyond the viewport count inside the 2.5-viewport budget, with the prepaint margin shrinking first under pressure; FP 6.6's adaptive two-or-three swapchain rule everywhere, with Android's case measured first (Q-GR-15); **shared-tile pinning** (a holder keeping a released texture is charged for it, G71). New process kind: the **content GPU process**, started with a rendering opportunity, ≤ **2 MiB†** charged at idle device-less and ≤ **12 MiB†** with a device, CPU side plus driver baseline (GR-47, the same thresholds as GR-D2's), volatile when hidden and exiting 30 s† later (FP 6.6); the shell's device-less content process joins FP-1 (≤ 2 MiB†); FP-7 measures renderer isolation and per-key service processes are reported on their own line (OD-5), and FP-27 gains a spawn row (GR-27); the compositor GPU service keeps FP-1's ≤ 12 MiB† CPU-side line. FP-10's U ≤ 15%† applies to both GPU process kinds.

**Paint's share of FP-11 (co-signing the layout spec's split), counted across processes.** FP-11 counts paint data wherever it lives, so the 160 B† share covers the renderer's paint data **and** the display items in the content GPU process, in canonical bytes **per DOM node** (boxes per node measured on the corpus; the table below is per painted box, about 1:1 for element nodes). The renderer keeps, per box after acknowledgement: chunk membership and the box's item hashes (about 1.5 items per painted box × 12 B), its property-tree state reference, amortized property-tree nodes (sparse: one per effect, transform, clip or scroll container), and paint invalidation flags.

| Item | Low | Expected | High |
|---|---|---|---|
| Item hashes and kinds (1.2 / 1.5 / 2.5 items per box × 12 B) | 14 B | 18 B | 30 B |
| Chunk membership and property-tree state reference | 8 B | 8 B | 12 B |
| Property-tree nodes (amortized; 48 B per node, one per 6 / 4 / 2 boxes) | 8 B | 12 B | 24 B |
| Chunk records (amortized) | 4 B | 6 B | 10 B |
| Invalidation flags, ink overflow for boxes that have it (amortized) | 6 B | 10 B | 20 B |
| Snapping and hit-test region cache (amortized) | 4 B | 8 B | 16 B |
| Arena slack | 6 B | 10 B | 18 B |
| **Total** | **50 B** | **72 B** | **130 B** |

The renderer's part is 50–130 B, 72 B expected. Display items live in the content GPU process after acknowledgement and count in the same share, so they get the remainder: **≤ 88 B† per node** (160 − 72), which needs a compact item encoding (items average about 1.5 per painted box, so about 58 B per item; text runs reference glyph runs by id rather than copying them). Whether that holds is measured at GR-M1 (GR-46); if it does not, the failure order shared with the layout spec applies ([RN2 Q3][RN2]): (1) representation work on the side that is over; (2) a joint re-split of the 360 B† with layout; (3) FP-11's own failure action, owned by FP, with the style spec's shares unchanged unless it agrees; never a separate ledger line. Items are dropped for hidden tabs with their tiles, and the chunk-resend protocol (6.3) restores them.

### 6.23 Observability, user experience, accessibility and integrations (GR-D24, GR-D25)

**Production counters, always on and canonical**: frames by outcome (on time, partial, late, dropped) with the stage that overran; tiles rastered, re-rastered pixels ÷ invalidated pixels, checkerboarded area; CPU and GPU placement counts; layers and their reasons; pipeline creations; device losses and their attributed cause; GPU bytes per site and kind; overlay promotions and refusals with the reason. They feed DevTools and the GR performance targets.

**Why-queries under replay** (DevTools spec DT-D3; the layout spec's decision-record model, LY-D19). Each answer comes from the production pipeline re-run with probes on, never from a second model:

| ID | Question | Answer |
|---|---|---|
| O1 | Why did this repaint? | mutation (with its JS stack and principal) → restyle or relayout → display-item change → chunk invalidation → tiles re-rastered → frame presented; no shipping tool links a paint to its cause ([GO 3.15][GO]) |
| O2 | Why is this a layer or surface? | The compositor-mutable node or cap that created it, the declaration and spec anchor behind it, its memory and raster cost, and a counterfactual replay without it |
| O3 | Can someone else see exactly what I see? | A recording replays on any machine to the same display-list hash and the same canonical pixels |
| O4 | What does the page look like, exactly? | Canonical screenshots from the CPU path for DevTools, WebDriver BiDi and (with AI on) agents; non-canonical surfaces flagged |
| O5 | What is on screen, as data? | Paint chunks, property trees, hit regions and the semantic tree joined by node id, for agents through the agent host when AI is on (B9, B10) |
| O6 | What GPU time and memory does this site use? | Per pass, layer, canvas and WebGPU device, in DevTools only, never in a page-visible API ([GO 3.6–3.8][GO]) |
| O7 | Why did this frame drop? | The frame record: which stage overran (script, style, layout, paint, raster, upload, compositor, present) and why |
| O8 | Why does this colour look like that? | Source space, conversions, working encoding (S8 or E16), tone mapping and output descriptor for a pixel |
| O9 | Is this accessible on screen? | Forced-colours and reduced-motion replays; focus-indicator area and contrast on rendered pixels (WCAG 2.4.13); flash-risk analysis per WCAG 2.3.1 from damage and luminance ([GO 5.6, 5.10][GO]) |

Every answer carries the origin and frame of what it describes; cross-origin pixels and timings are never shown beyond what the page itself could observe, and the agent path lives in an `ai`-feature crate (G4).

**Accessibility in rendering (GR-D25).** Forced colours are paint-time work in `hg-paint`: system colours, removed shadows and gradients, and **backplates** behind text, as CSS Color Adjust allows and Edge ships ([GO 5.1–5.2][GO]), reaching the hit-test and semantic planes unchanged. **Flash analysis** is rendering data: the compositor measures, per frame and only over damaged regions, the WCAG 2.3.1 general and red flash counts, and DevTools shows them (O9), its cost and false-positive rate measured by GR-S11 ([GO 5.6–5.7][GO]). User-facing interventions built on rendering (stopping compositor animations under the OS reduce-motion preference, dropping backdrop blur under reduce-transparency, a user flash-protection mode that dims a layer exceeding three flashes a second) are shell and accessibility product questions, so this spec only makes them possible and passes them to the shell UI design as proposals (9.5) ([GO 5.3–5.4][GO]). **Amended 20 October 2026 (the animation spec's GR-D25 amendment): the flash-protection mode is a motion setting the animation spec adopts** (its level system, AN-D10), and while it is on the **compositor dims the damaged region over WCAG 2.3.1's thresholds** — the dimming is compositor work in this spec, the setting and its levels the animation spec's. Focus rings use a UA default that meets WCAG 2.4.13 (2 CSS px perimeter, 3:1 contrast against both adjacent colours).

**Shell.** The site panel shows when a page's GPU contexts were suspended after a hang, when WebGPU or WebGL is unavailable on this device, and when WebGPU needs this site's permission (GR-D11); a GPU-process crash shows "graphics restarted", never a browser error.

| Rule | Statement | Why |
|---|---|---|
| **G60** | Only `hg-gpu-mtl`, `hg-gpu-vk`, `hg-gpu-d3d12` and the OS halves of `hg-present-host` and `hg-present-gpu` may call GPU or windowing APIs or contain `unsafe`; every other graphics crate is `#![forbid(unsafe_code)]` and reaches SIMD only through `hg-simd`'s safe API (the media spec's G54) | One audited FFI layer (G5); one audited SIMD layer |

| **G62** | No graphics payload from a renderer, content GPU process or media process is parsed outside generated `.hgidl` readers; graphics has no IPC-R16 entry | GR-D6 |

| **G64** | Every GPU resource handle carries its initialization state in its type; binding for read requires the initialized state; pools zero on reuse; emitted compute shaders zero workgroup memory | GR-D20 |
| **G65** | Every shader given to a driver was produced by Izcal's back ends from validated IR, passed `hg-shader-check`, and carries bounds checks on every dynamic access; no HLSL or GLSL text reaches an OS compiler; MSL text reaches only Metal's runtime compiler | GR-D7 |
| **G66** | No GPU work runs in the broker, and no fallback moves GPU work to a less sandboxed process; no process creates a WARP or other software D3D device; a loaded-module closure check (as JS G14) proves the broker's DirectComposition device loads no D3D user-mode driver | GR-D19, GR-D10 |
| **G67** | Release artifacts (installers, Snap, AppImage, and any Flatpak runtime Izcal builds) contain no Vulkan loader, `D3D12Core.dll`, `dxil.dll`, DXC, Agility SDK file or other non-MIT graphics binary; a third-party runtime's or the distribution's loader is an OS interface; GPU processes disable Vulkan implicit layers | M-1; GR-D8, GR-D22 |
| **G68** | Pipeline caches are keyed by the (T, C, X, n) projection, valid because the content GPU process is keyed like the renderer; content shaders are salted per partition before reaching a driver | GR-D20, GR-D2 |
| **G69** | A cross-origin surface is never an input to a page-controlled effect whose cost or output depends on its pixels; render targets holding or derived from cross-origin pixels are created with lossless compression disabled where the API allows | GR-D18 |
| **G70** | Any rendering decision that changes web-observable output is a pure function of recorded inputs; decisions that change only time (placement, tiling, scheduling) are allowed to vary because canonical outputs are identical, and the device lab randomizes them to prove it | GR-D3, JS-D15 |
| **G71** | A shared texture or memory object is granted to exactly one renderer key's process for its lifetime and never re-granted; it is freed only when that process exits or releases it, and its bytes stay on that key's ledger until then | GR-D2; IPC-R8 |
| **G72** | No process makes a GPU-side wait on a fence another process can signal; foreign fences are observed on the CPU against a deadline, one fence object per (producer, consumer) pair, never shared across pairs | GR-D2, GR-D19; HGBA-2 5.3 |

### 6.26 Representation choices, derived (M-1 part 3)

Every structure above is derived from the specifications and Izcal's principles. Several resemble structures other engines have described in published prose; that prose is evidence that the shape works, never a template, and no structure, constant or algorithm was read from any engine's source code.

| Structure | Derived from | Prose evidence that the shape works | Alternative considered | What decides |
|---|---|---|---|---|
| Four property trees and paint chunks | Appendix E, Compositing 1 isolation, CSS Transforms, CSS Masking, CSS Overflow scroll containers | [RenderingNG data structures](https://developer.chrome.com/docs/chromium/renderingng-data-structures) ([HP 1.7][HP]) | A layer tree as the interface | Rejected by [HP 1.5–1.6][HP] |
| Content-addressed items, chunk-hash deltas | DET-1's display-list hash; FP 6.4's "chunk hashes" | Interned items in [Firefox's rendering overview](https://firefox-source-docs.mozilla.org/gfx/RenderingOverview.html) ([RP 4.8][RP]) | Re-sending whole lists | Bytes sent per frame at GR-M1 |
| Sparse strips with exact counts | Exact area coverage; bounded GPU memory | Levien's design document and Stampfl's thesis ([RP 1.2–1.3][RP]) | Dense accumulation buffers per tile | CPU raster time on the corpus at GR-M1 |
| Hybrid anti-aliasing | Compositing 1's coverage-as-alpha with conflation as the failure case | [RP 3.1–3.2][RP] | MSAA; supersampling everywhere | GR-6 accuracy and raster time |

### 6.27 Print, capture and export

## 9. Milestones and staffing

### 9.1 What is staged, and why

The owner allows staging only for correctness, security or measurement. Nothing here is staged for schedule; every track is staffed from GR-M0, and each feature ships when its gates pass.

| Item that is ordered or held | Reason | Kind |
|---|---|---|
| The CPU canonical rasterizer, `hg-raster-ref`, the exact-match WPT runner and the paint-order contract come before GPU raster | Oracles before code (ORC-1); the GPU path is checked against the CPU path bit for bit | Correctness |
| The HAL's resource type states, the render graph and the display-list and compositor-frame formats are designed at GR-M0 with the process model | Retrofitting is costly: lazy clearing must be remembered on every path (inference from [SR 7.8][SR]), and uninitialized use is now the second-largest Chrome graphics CVE class ([SR 7.9][SR]) | Security |
| The process model (GR-D2) is frozen only after GR-S2 measures per-process driver cost and spawn time | The acceptance test (FP-7 with content GPU processes counted) needs the number | Measurement |
| WebGL ships per back end when GR-4, GR-12 and GR-16 pass; WebGPU when GR-3, GR-12, GR-16 and GR-S6 pass, by default only in cross-origin-isolated contexts until GR-22 passes | Shader and driver attack surface; I-6 | Security gate, no stage |
| Canonical GPU fine raster is enabled per device class when GR-2 and GR-34 pass; until then that class rasters on the CPU (same pixels) | GR-S3 decides the reversal | Measurement |

| Intel-Mac and Windows 10 support (GR-D21) | Decided by the vendor-security-support rule at the release decision | Security |

**Milestones are expected dates, not holds.** Every track starts at GR-M0 and each feature ships when its gates pass. The order of features across GR-M1 to GR-M3 follows dependencies only (SVG painting needs the stroker and filters; WebGPU and WebGL need the shader compiler and the HAL; OffscreenCanvas needs the canvas back ends and surface embedding; View Transitions need snapshots and compositor-side capture), and X11 presentation is built alongside Wayland from GR-M1, sharing the dmabuf path.

**Spikes** (each a measurement milestone, results recorded in the decision log): **GR-S1** in-box D3D12 tier, binding tier and SM 6.6 dynamic-resource support per vendor, BYPASS support, self-hashed DXIL on four vendors, the DXIL container fields mapped to prose or black-box observation, the DXIL hash derived black-box where prose is incomplete, the DXBC token encoding and checksum derived black-box from `d3dcompiler_47.dll` output, and whether DXBC Izcal encodes with a self-computed checksum loads; **GR-S2** per-process driver memory, descriptor heaps, compression loss on shareable tiles, context-switch cost, preemption granularity and spawn time on every reference device, at the p50, p90 and iframe-heavy process counts; **GR-S3** canonical integer GPU raster against a float prototype, in frame time and energy; **GR-S4** macOS presentation (IOSurface as layer contents against one `CAMetalLayer` per tile; scanout behaviour); **GR-S5** sandboxed presentation per OS (composition surface handles under low integrity and LPAC; the Wayland and macOS timing relay's latency; the broker's per-frame commit cost; whether the Windows compositor clock follows the window's monitor); **GR-S6** WGSL atomics-clock resolution, the published keystroke attack, builtin-evaluation entropy and cross-process cache channels, at GR-M0 and GR-M1; **GR-S7** the GPU.zip method against Izcal's compositor and content processes, with lossless compression on and off, and how to disable compression per D3D12 vendor; **GR-S8** driver shader caches as cross-site channels, before and after salting; **GR-S9** the DRM ioctl set and Vulkan loader file accesses per Linux driver, and every OS service each GPU process kind needs (including macOS's `MTLCompilerService`); **GR-S10** an input-to-photon rig; **GR-S11** flash-analysis cost and false-positive rate; **GR-S12** the Android floor: descriptor-indexing limits on Vulkan 1.1 devices with and without the 2022 profile, and the active-user share below each floor.

## 10. Risks

| Risk | Severity | Mitigation | Trigger to revisit |
|---|---|---|---|
| **Canonical GPU raster is too slow** on some GPUs | High; performance | GR-S3 early; CPU and GPU produce the same bits, so a device class can rasterize on the CPU with no visible change while the GPU path improves | GR-34 fails: GR-D3's display-only fallback for that class |
| **The CPU rasterizer is not fast enough for real pages** (Ladybird's experience) | High; performance | Rasterizer track staffed from GR-M0; MotionMark and corpus measured monthly; SIMD integer paths | GR-30's Stage 1 ratio missed at GR-M2 |
| **Per-process driver cost makes GR-D2 unaffordable** | Medium; footprint | GR-S2 before the freeze; per-process cost reduction (spare processes, lazy pipelines, smaller heaps), never co-location | GR-D2's trigger |

| **A compromised compositor** (one hop from a content process through the compositor-frame reader) | High; security | Smallest typed input (GR-18), no page filters, paths or ICC data (G63), single-grant textures and CPU-observed fences (G71, G72), prompts outside it (GR-D28), adversarial peers | A compositor-frame CVE |
