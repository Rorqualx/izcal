The evidence as of October 2026 says the *neglected* software frontier for a new browser engine is not a new language, a new GC, a GPU layout engine or a general reactive framework. It is **how an engine is built and checked**. Algorithms still matter (B5 and B6 are algorithmic and load-bearing), but the ones worth adopting are the ones that can be gated against an oracle. Code is now cheap to produce: Ladybird moved about 25,000 lines of its JS frontend from C++ to Rust in about two weeks with zero regressions on 52,898 test262 tests ([Ladybird](https://ladybird.org/posts/adopting-rust/)). Correctness is still expensive: Cursor's agent swarm produced over a million lines of Rust in a week, but JavaScript did not work and no WPT score was ever established ([Simon Willison](https://simonwillison.net/2026/Jan/23/fastrender/)). The gap between those two outcomes is the oracle. HGBA-3.0 therefore proposes an engine whose architecture is shaped so that **every component can be checked against an executable oracle, every run can be replayed deterministically, and every pipeline stage is an incremental function with immutable outputs**. The engine can also emit a semantic, provenance-tagged view of the page that AI agents can use without screenshots. **All AI integration is off by default**: nothing agent-related runs until the user, an administrator or an embedder switches it on. HGBA-2.0's constraints survive and are restated on the ground-up build (HGBA-2 2.3.0): Izcal writes its own JavaScript and WebAssembly engine, collector, DOM and bindings, parsers, style system, layout, text stack, renderer and network stack from the specifications; process-per-site isolation stands; communication is typed capability IPC; and layout stays tied to the script thread. The DOM is stored once, as node columns outside the collector's cage with lazily created JS wrappers (JS-D4). The honest answer to "don't recreate Servo" is no longer "use Servo's libraries": M-1 excludes every library that does browser-engine work, and other engines are black-box references only. What is genuinely new is the substrate under those components and the process that produces them. None of that substrate has shipped in a browser.

## 1. Vision: from hand-maintained object graph to checkable function of recorded inputs

HGBA-2.0 broke from peak-capability hardware thinking. It described hardware by what a sandboxed process can actually reach, at what fixed cost, with what failure mode. HGBA-3.0 makes the same move for software. Legacy engines are **mutable object graphs maintained by hand**. Dirty bits are walked through the tree, threads and timers are touched directly, correctness is established after the fact by tests and fuzzers, debugging relies on record-and-replay tools bolted on from outside, and automation goes through a debug port. Each of those choices was rational when engineers wrote all the code and the web was smaller. Two facts changed the economics. The web platform is now **more than 2 million WPT subtests** (Servo's denominator was 1,998,146 at the end of 2025, and Ladybird passes 2,088,677) ([Igalia](https://blogs.igalia.com/mrego/servo-2025-stats/); [Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31/)). And AI agents can now generate and translate code faster than humans can review it, provided something mechanical decides whether the output is right.

HGBA-3.0's engine is a **deterministic, incremental function from recorded inputs to outputs**. The inputs are network bytes, user input, clock ticks, random seeds and IPC messages. The outputs are DOM state, computed style, a fragment tree, a display list, a semantic tree and pixels. Determinism makes failures replayable and lets the engine be tested the way FoundationDB and TigerBeetle test distributed databases. Incrementality makes it fast without hand-maintained invalidation sprawl. Immutable phase outputs make it parallel without races on the DOM. Oracles make AI-generated code admissible. The semantic output makes the engine useful to agents, which is the one product dimension where every 2026 competitor is a Chromium fork bolting features onto a debug protocol.

What the vision does not claim matters as much. It does not claim faster page loads than Chromium, a novel JS engine or GC design, or any change to what web content can observe **through the engine's internal design**. The web platform fixes semantics. The engine controls only how it computes them. User-agent interventions that do change what content observes (content blocking, storage partitioning, anti-fingerprinting, permission gating) are policy decisions governed by the P2 scope note in Section 2, not engine design.

## 2. Principles in precedence order

When two principles conflict, the higher one wins, and any exception is recorded in the decision log (Section 9). P1, P2, P4 and P5 carry over from HGBA-2.0. P3 and P6 are new.

| Rank | Principle | Operational meaning | Evidence anchor |
|---|---|---|---|
| P1 | **Security and privacy of the user** | Web content is hostile. Process-per-site, zero ambient authority. **An AI agent is a separate principal, not an extension of the user.** | V8 concluded in-process mitigations cannot fully stop Spectre ([v8.dev](https://v8.dev/blog/spectre)); Google calls an unconstrained agent "a Site Isolation bypass" ([Google](https://blog.google/security/architecting-security-for-agentic/)) |
| P2 | **Web compatibility (unbreakable)** | HTML, CSS, JS and WPT conformance gate everything. No subsetting of the platform, however much faster a subset would be. | Gameface's data-oriented speed depends on supporting only `display: flex` and `none` ([Coherent](https://guide.coherent-labs.com/layout-assets-and-styling/laying-out-the-screen)), which a browser cannot do |
| P3 | **Reproducibility and checkability** | Every engine run can be replayed bit-for-bit in simulation mode. Every component has a named oracle before it is written or replaced. A path that cannot be replayed or checked does not ship by default. | FoundationDB's deterministic simulator replays any failing seed exactly ([FoundationDB](https://apple.github.io/foundationdb/testing.html)); Ladybird's zero-mismatch gating ([Ladybird](https://ladybird.org/posts/adopting-rust/)) |
| P4 | **Robustness and graceful degradation** | Every incremental path has a from-scratch fallback; every accelerated path has a CPU fallback. | Incremental machinery loses on bulk changes ([Spineless Traversal](https://arxiv.org/html/2411.10659v4)) |
| P5 | **Performance and energy** | p95 interaction latency, frame time, memory and energy on a published corpus. | Salsa's main production cost was memory, not time ([Salsa notes](https://hackmd.io/@salsa/SkNtN8Lv1e)) |
| P6 | **Agent-native capability, off by default** | Semantic output for agents, agent principals, tool registries and model hosting are engine features that ship **disabled**. They run only after an explicit switch (B10), are built on P1–P5 and never weaken them. Accessibility for assistive technology is not an AI feature and is never gated by the switch. | Chrome's agent stack is built on Site Isolation and a non-content-reading critic ([Google](https://blog.google/security/architecting-security-for-agentic/)) |
| P7 | **Evidence over aspiration** | Every idea carries a maturity label: **shipped** (in production somewhere), **prototype** (working code, not in production) or **research** (paper or proposal). Vendor and single-source claims are labelled. | — |

**P2 scope note: user-agent interventions.** P2 governs the engine's behavior on unmodified pages under default settings. A *user-agent intervention* (the term avoids confusion with AI agents) is any browser behavior that changes what content observes or how it behaves, on the user's behalf. Interventions are permitted in three classes only: (a) behavior the platform leaves to user-agent discretion, such as permission prompts, autoplay policy and storage partitioning; (b) overrides the user invokes explicitly, per site or globally; and (c) privacy protections on by default that carry a recorded P1 analysis in the decision log, such as content blocking and anti-fingerprinting. An intervention outside these classes is a P2 violation. Every default-on intervention publishes its compatibility cost (WPT and corpus breakage) per release.

**Method constraint M-1 applies to everything in this document.** HGBA-2.0 Section 2 defines **M-1** (original, first-principles, spec-anchored implementation) as a method constraint that is not ranked, so no principle P1–P7 can trade it away. **Original:** no code from another browser, browser engine or engine library is copied, ported or translated into Izcal, by people or by AI tools (Stage 1 design D-S10), and **Izcal does not use libraries that do browser-engine work**. It writes its own JavaScript and WebAssembly engine, collector, DOM and bindings, HTML and CSS parsers, style system, layout, text stack, renderer and network stack from the specifications (HGBA-2 2.3.0). Dependencies are generic infrastructure only, used unmodified through their public APIs, and **every dependency and data set that ships is MIT** (D-S6). **Spec-anchored:** web-visible behavior is implemented from the normative specification at a pinned revision, and every hand-written algorithm carries a spec anchor; where a specification is silent, behavior follows documented interoperability evidence recorded as a black-box observation. **First-principles:** internal architecture that no specification governs is derived from P1–P7 and measured requirements; another engine's design is cited as evidence, never as a template. **Spec-anchored oracles decide correctness:** conformance suites, formal models, spec-derived property tests and Izcal's own reference paths are primary, and other engines are black-box differential signals only; **no third-party project's source code is evidence** (HGBA-2 2.3.1, 2.3.3).

P3 sits above performance on purpose. The build method in Section 6 depends on it. A faster path that breaks replay is a path whose bugs cannot be reproduced and whose AI-generated replacements cannot be gated, so the speed is not worth having. HGBA-2.0 already applied this logic narrowly: its parallel layout must be bit-identical to the sequential path on WPT reftests. HGBA-3.0 generalizes it to the whole engine.

## 3. What the platform fixes and what the engine is free to change

The most common error in "rethink the browser" proposals is to treat platform semantics as an implementation choice. The evidence draws a sharp line.

### The platform fixes synchronous layout, one event loop per agent, and de facto behavior documented by interoperability work

The web platform requires layout to answer synchronously from script. `getBoundingClientRect`, `offset*`, `scroll*` and `getComputedStyle` all force a style and layout flush ([Paul Irish](https://gist.github.com/paulirish/5d52fb081b3570c81e3a)). Servo, the engine designed around message-passing components, **moved layout onto the script thread in February 2024** because "the web platform almost always requires layout to run synchronously with script" ([Servo](https://servo.org/blog/2024/02/28/gamepads-font-fallback-space-jam/)). The HTML event loop is serial per agent. JS semantics, DOM node identity, mutation ordering, microtask timing and same-origin synchronous access between same-site frames are all observable. Compatibility also goes beyond specs: Interop 2026 has a "web compat" area for real-world breakage such as unprefixing `-webkit-user-select` and ESM loading ([WebKit](https://webkit.org/blog/17818/announcing-interop-2026)). Where specifications are silent, web compatibility requires matching deployed behavior; Izcal takes that behavior from interoperability evidence (WPT results across engines, Interop and web-compat data), records each case in the black-box observation log (M-1), and files it upstream as a specification issue. Spectre is not a platform rule, but it fixes the process model just as firmly.

### The engine is free to change data layout, invalidation, scheduling, determinism and its outputs to embedders

None of the following is visible to web content: how the DOM's style-and-layout inputs are stored, how dirty state is tracked and traversed, whether phase outputs are immutable, how threads are scheduled, whether time and randomness are injected, how IPC is transported, and what the engine emits to its embedder beyond pixels. Chromium itself has moved a long way on these axes without changing web semantics. It has immutable LayoutNG fragments, flat inline item lists, centralized property trees and cached paint chunks ([Chrome](https://developer.chrome.com/docs/chromium/renderingng-data-structures)). That is where HGBA-3.0 innovates.

| Layer | Fixed by the platform (cannot change) | Free inside the engine (HGBA-3.0 changes it) |
|---|---|---|
| Script | JS semantics, JIT-class performance expectations, event-loop and microtask ordering | Embedding: injected clock, randomness, task scheduling and recorded decision points (Section 4, B1; JS 6.9) |
| DOM | Node identity, mutation APIs, GC-visible cycles through JS | Storage of style/layout inputs: one copy in node columns outside the cage (B4, JS-D4) |
| Style | Cascade, selectors including `:has()`, container queries | Invalidation mechanism, sharing, parallelism (Izcal's invalidation index and content-addressed style groups, B5) |
| Layout | Synchronous queries, exact geometry, every formatting context | Incremental scheduling, cache keys, immutable fragments (B5, B6) |
| Rendering | Pixels when a human looks | Whether to paint at all when nobody looks (B7) |
| Isolation | Spectre physics: one process per site | Typed capability channels, simulation transport (B2) |
| Agents | WebMCP if it standardizes; HTTP semantics | Semantic tree, provenance tags, agent principal, snapshot diffs (B8, B9) |

### B1. Deterministic runtime substrate

**What it is.** No engine code calls the OS clock, OS threads, OS randomness or sockets directly. All of them go through injectable interfaces with two implementations: production (real OS) and simulation (seeded scheduler, virtual clock, fake network that replays recorded archives with fault injection). The simulation mode runs the whole multi-process browser in one process, with renderers as simulated hosts.

**Evidence.** Deterministic simulation testing (DST) is **shipped** in distributed databases. FoundationDB runs whole clusters in a single-threaded deterministic simulator where any failing seed replays exactly ([FoundationDB](https://apple.github.io/foundationdb/testing.html)). TigerBeetle's VOPR injects network, storage and clock faults with time acceleration ([TigerBeetle](https://github.com/tigerbeetle/tigerbeetle)). Antithesis, a deterministic hypervisor for unmodified software, raised a **$105M Series A in December 2025** ([PR Newswire](https://tools.prnewswire.com/en-us/live/20813/release/20251203EN37581)). Rust has two shipped DST libraries: madsim replaces tokio and std time, network and RNG, and turmoil simulates hosts and networks in-process ([madsim](https://github.com/madsim-rs/madsim); [turmoil](https://github.com/tokio-rs/turmoil)). A multi-process browser has the same shape as a small distributed system: processes, IPC, network and timers. The HTML event loop is already specified as task queues, so a seeded scheduler can explore exactly the interleavings the spec permits.

**Maturity.** Shipped in databases. **Research for browsers**: the notes found no published case of DST applied to Servo, Ladybird, Chromium or Gecko.

**Replaces.** Direct `std::time`/thread/RNG use and after-the-fact record/replay (`rr`, which Mozilla uses heavily for Firefox debugging) ([rr](https://rr-project.org/)). `rr` stays as a tool for the parts B1 cannot cover.

**This is the document's biggest bet and its least evidenced.** No browser has done it. The engine itself is deterministic by construction: GC, tiering and other timing-dependent decisions are recorded inputs (JS 6.9, JS-D15), so the JS layer is no longer the largest unknown, and GPU, audio and media sit outside the simulator. If DST-1 fails, the thesis survives, because it rests on oracle gating, which is shipped (Ladybird) and independent of DST; B1 then remains for replay and agent snapshots. What does *not* survive is the claim that HGBA-3.0 is simulation-tested end to end, which would shrink to "replayable".

**Risk.** The notes are blunt: DST must be designed in from day one, and **retrofitting it is very hard**. That is the strongest argument for building this substrate new rather than inheriting Servo's threading. The remaining sources of nondeterminism are the GPU and compositor threads, audio and media pipelines, and OS-decoded or hardware media paths; each needs embedder hooks, a recorded hash or Antithesis-style whole-VM determinism (DET-1's exclusions). The engine's own GC, JIT and tiering no longer sit outside Izcal's control: timing-dependent decisions are recorded inputs (JS 6.9), not a platform mode the engine hopes reproduces. The indirection also has a runtime cost, which target DET-2 bounds.

### B2. Typed capability channels with a simulation transport

**What it is.** All inter-process communication uses typed, sequence-affine endpoints generated from an IDL. Holding an endpoint is the authority to call it. One transport abstraction has two backends: OS IPC with shared memory, and in-process simulated delivery under B1's scheduler. Synchronous calls are allowed only where the platform forces synchrony, and policy discourages them elsewhere. Endpoints come in two bindings: a **free endpoint** carries its capability with it, and a **bound endpoint** is tied to a principal and checks that binding on every call, so a partition service reads only the jar it was granted (IPC-R2, IPC-R17). **Per-frame endpoints** scope a frame's grant to that frame so another frame cannot replay it. A **nested-sync rule** forbids a synchronous call from inside the handling of another synchronous call. The security scope's IPC-R1 to IPC-R17 carry the complete rules, including handle kinds, bound and free endpoints and the no-trust rule between processes; B2 adopts them as they merge (A-H3-27).

**Evidence.** Chromium's Mojo is **shipped** evidence that typed capability IPC works at browser scale; it is not a template, and B2's design is derived from first principles (P1, P3) and the OS IPC documentation. Pipes and interfaces generated from `.mojom` bind to a sequence, and the docs discourage `[Sync]` calls because they block and invite re-entrancy and deadlock ([Mojo](https://chromium.googlesource.com/chromium/src/+/main/mojo/public/cpp/bindings/README.md)). Mojo endpoints are unforgeable handles, which makes Mojo capability-like ([Mojo README](https://chromium.googlesource.com/chromium/src/+/main/mojo/README.md)). OpenAI's Atlas ran Chromium out of process behind Mojo with custom Swift bindings, which shows Mojo-style boundaries also serve embedders ([OpenAI](https://openai.com/index/building-chatgpt-atlas)). The turmoil model shows the simulated-transport half ([turmoil](https://github.com/tokio-rs/turmoil)).

**Maturity.** Typed capability IPC: shipped. Simulated browser IPC: research.

**Replaces.** HGBA-2.0 originally reused Servo's constellation for navigation and pipeline management. Izcal instead implements navigation in **`hg-navigation`**: navigables, session history and the navigation algorithms, derived from the HTML specification's navigation and session-history sections, over B2's transport so that it runs under simulation. Servo's constellation (cited here as history) was "historically designed for parallel, message-passing components" ([Servo wiki](https://redirect.github.com/servo/servo/wiki/Transcription---Notes-from-Servo-Architecture-talk-in-Suwon)), not for determinism.

**Risk.** Moderate. The design is proven. The cost is building plumbing that other engines already have. The notes contain no per-message cost figures for Mojo or Servo's constellation. The security scope's IPC rules are Phase 5 input; until they merge, the two endpoint bindings, per-frame scoping and the nested-sync rule above are the design constraints B2 must satisfy.

### B3. Two schedulers: sequences for the event loop, fork/join for phases

**What it is.** I/O, navigation and the event loop run on serial *sequences*, one per agent cluster, with structured cancellation of fetches, navigations and workers. CPU-bound pipeline phases (style, layout, raster preparation, semantic tree) use Rayon-style work-stealing fork/join. The two never share executor threads.

**Evidence.** All of it is **shipped**. Chromium tells its engineers to "prefer sequences to physical threads" ([Chromium](https://chromium.googlesource.com/chromium/src/+/main/docs/threading_and_tasks.md)). Servo still parallelizes layout with worker threads after moving layout onto the script thread ([Servo](https://servo.org/blog/2024/02/28/gamepads-font-fallback-space-jam/)). Structured concurrency is mainstream in Swift, Kotlin and Python, but Java's API is still in its **sixth preview** in JDK 26 ([JEP 525](https://openjdk.org/jeps/525)). Swift 6.2 moved defaults back toward main-actor isolation because unrestricted concurrency produced too many data-race diagnostics ([InfoQ](https://www.infoq.com/news/2025/08/swift62-approachable-concurrency)). That is evidence that "concurrent by default" has costs. In Rust, async fn in traits is stable but not `dyn`-compatible, and the 2026 project goal only aims to *settle a design* ([Rust goals](https://rust-lang.github.io/goals/2026/afidt-box.html)).

**Maturity.** Shipped.

**Replaces.** Thread-per-component designs and fine-grained actors on hot paths. Actors stay coarse: process, document, agent cluster and service.

**Risk.** Low. Embedder and plugin interfaces must avoid `dyn` async traits until at least 2027, or accept a boxed allocation per call. Rayon's scheduling is nondeterministic, so determinism must come from **phase purity**: workers read immutable inputs and write disjoint outputs, so the result does not depend on interleaving. Target DET-1 tests this.

### B4. One copy of the DOM: node columns outside the cage

**What it is.** The DOM is stored **once**. Its node columns — tree links, tag, attributes, classes, state flags, the inline-style declaration reference and a stable node ID — live outside the collector's cage and are traced as `hg-heap`'s **node space** by Izcal's one collector. The JS-visible node object is a **wrapper created lazily on first script access** and held strongly once created; DOM text lives in an arena shared with JS as external strings (JS-D4). Script reaches the DOM only through `hg-dom`; style, layout and the semantic plane read the columns through tree-access traits. DOM mutations append to an **append-only log**, applied at the start of every style or layout pass, including every forced synchronous flush. Workers read the columns **only during a flush, with the script thread blocked**, never read the cage, and never trace or write. **The data-plane mirror of 3.1–3.2 retires**; there is no second copy to project.

**Evidence.** One copy is the only representation that satisfies FP-D2 while keeping workers off attacker-writable memory: H-2 treats everything read from the cage as untrusted, so the tree style and layout read cannot be written from the cage. JS-D4 records the collector's node space, the lazy-wrapper rule and the text arena as one decision, so the DOM, the collector and the bindings are designed together rather than layered. No system in the notes combines a one-copy columnar DOM with JS-visible identity in production; the JS-M0 spike builds both this design and the cage-node alternative and measures bytes per node across every copy and the node space's share of GC time. The pattern — identity in one place, dense per-subsystem storage keyed by that identity — is shipped in non-browser UI stacks. No browser in the notes runs it with JS.

**Why one copy.** Four reasons, none of them about GC. First, B1 needs a serializable boundary between script and the rendering pipeline, and the mutation log is that boundary: replaying the log reproduces style and layout without replaying JS. Second, B5 needs explicit, enumerable inputs with stable identities, and incremental computation pays only when the program supplies stable names (Nominal Adapton). Third, B8 needs stable node IDs that survive mutation, and the columns' generational IDs are exactly that. Fourth, the two-copy design's consistency bug class disappears, and the threading hazard goes with it: the script thread owns the cage, and workers see frozen columns only during a flush.

**Maturity.** The pattern is shipped in non-browser UI stacks. **Prototype** for a browser with JS: no browser in the notes runs it; the JS-M0 spike measures it.

**Replaces.** The 3.1–3.2 F1 mirror and the two-copy `cppgc` DOM. The script thread's DOM and the workers' inputs are the same columns.

**Risk.** Memory and GC time are the open quantities, and they are bounded before the design is accepted. **FP-11's budgets apply across every copy**: node columns ≤ **48 B†** per node, the DOM (columns, rare data and existing wrappers) ≤ **72 B†**, and the corpus total ≤ **512 B†** per node, with style ≤ 80 B†, layout ≤ 200 B† and paint ≤ 160 B† counted across processes (FP-11; LY 6.13; GR-D23, GR-46). JS-D4's reversal trigger is explicit: total bytes per node across every copy, or the node space's share of GC time, worse than the cage-node alternative by more than **10%†** at the JS-M0 spike or on the corpus. The 3.1 spike's **150–175 B per node** was measured on the retired two-copy design and is not this design's number; the toy-DOM figure stays as history. If a budget is missed, the failure order is FP-11's: representation work on the side that is over, a joint re-split, then this decision's reversal trigger; any representation change needs a decision-log record.

### B5. Incremental core: specialized invalidation, not a general dependency graph

**What it is.** Each pipeline stage is a pure function over explicit inputs with memoized outputs and **early cutoff**: if recomputation yields the same value, downstream work stops. Concretely:

Style **is Izcal's invalidation index** (ST-D10): feature-indexed invalidation with exact self-checks from old values, last-match flags that never accumulate, a bulk fallback, recorded causes and measured over-invalidation. Sharing is **content-addressed style groups with deterministic identities** in per-agent tables (ST-D7), with matched rules as interned match keys plus a memo (ST-D8); an independent, spec-literal **reference style engine** (ST-D12), sharing no project code with production, checks every CI flush. Layout becomes `layout(node, constraint_space) → immutable fragment`, with a **break token in and out** and a **style-version id** in the constraint space; fragments are **arena records, not `Arc`** (LY 6.13). The constraint space is derived from the CSS Sizing and CSS Fragmentation specifications (available size, percentage resolution size, fragmentainer and break state); LayoutNG is cited below as evidence that such a cache works, not as the design. Dirty layout work is scheduled through an **order-maintained priority queue** rather than a dirty-bit tree walk, as in Spineless Traversal. Inputs carry Salsa-style **durability tiers**: UA stylesheets and fonts are high, author stylesheets medium, and DOM attributes and hover state low. Validation can then skip whole subgraphs whose inputs have not changed. A **bulk fallback** switches to from-scratch parallel recomputation for initial load, large `innerHTML` writes, stylesheet swaps and lazy-load insertion bursts. Forced synchronous queries become **demand-driven**: `getBoundingClientRect` computes only the fragments the answer depends on, if the cache can prove the rest is clean.

**Evidence.** LayoutNG is the **shipped** proof that layout as a memoized function works at web scale. It stores the parent constraint space with each fragment as a cache key, and its redesign fixed under-invalidation bugs, "hysteresis" (non-idempotent layout) and exponential two-pass grid layout ([Chrome](https://developer.chrome.com/docs/chromium/layoutng)). Blink's style invalidation sets are deliberately conservative and applied lazily, because exact rule-to-element dependencies are too costly to track ([Chromium](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/core/css/style-invalidation.md)). Spineless Traversal (**research**, PLDI 2025) replaces the "double dirty bit" walk that all major engines use. It was faster on **83% of 2,216 frames** from 50 real sites, with a **1.80× mean** speedup, captured with a modified Ladybird ([PLDI 2025](https://pldi25.sigplan.org/details/pldi-2025-papers/73/Spineless-Traversal-for-Layout-Invalidation)). Salsa (**shipped** in rust-analyzer) contributes durability and backdating ([Salsa book](https://salsa-rs.github.io/salsa/reference/algorithm.html)).

**Why not a general framework.** The evidence against a general per-field dependency graph is consistent. Salsa's 3.0 migration left **a 250 MB memory regression** in rust-analyzer after optimization ([Salsa notes](https://hackmd.io/@salsa/SkNtN8Lv1e)). Classic Adapton is "sometimes orders of magnitude slower than from-scratch computation" ([Adapton](https://ar5iv.labs.arxiv.org/html/1503.07792)). Differential dataflow state grows without bound unless compacted ([Materialize](https://materialize.com/blog/managing-memory-with-differential-dataflow/)). A browser with millions of nodes and hundreds of properties per node cannot afford one tracked cell per (element, property). TC39 Signals is still **Stage 1**, and no engine uses signals internally ([TC39](https://github.com/tc39/proposal-signals)). No production browser is built on a general incremental framework.

**Maturity.** Constraint-keyed layout caches: shipped (LayoutNG). Content-addressed style with deterministic identities: research. Feature-indexed invalidation with exact old-value checks: research. Ordered dirty queues: research. Durability tiers in a browser: research (shipped in rust-analyzer). Demand-driven forced flush: research.

**Replaces.** Dirty-bit tree walks and per-feature hand-written invalidation sprawl in layout.

**Written against traits, not a store.** The driver calls `layout(node, constraint_space)` through tree-access traits and never knows which implementation backs them. The backing store — the one-copy node columns (B4), or the cage-backed alternative that JS-M0 measures against — is therefore a measurement choice, not a rewrite; the same traits carry the reference style engine (ST-D12) and the from-scratch path (INC-1). Like B1's injectable runtime, this cannot be added later.

**Risk.** High, and specific. Spineless was **slower on 17–25% of frames**, about **2× slower on bulk insertion**, and its prototype covered only about 50 layout fields in about 700 lines of a DSL, "only a subset of HTML and CSS" ([arXiv v4](https://arxiv.org/html/2411.10659v4)). Its headline numbers also differ across paper versions (1.80× and 83% at PLDI, 3.23× and 78.2% in an earlier arXiv version). The features where research coverage stops are exactly the hard ones: out-of-flow positioning, fragmentation, `:has()`, container queries and anchor positioning. Out-of-flow descendants and fragmentation break state are exactly the inputs that the CSS Positioned Layout and CSS Fragmentation specifications let escape a box's own constraints. Each has a protocol in the layout spec — LY 6.4 for out-of-flow, LY 6.7 for fragmentation and LY 6.9 for `:has()`, container queries and anchor positioning — and each therefore needs explicit non-tree edges or a conservative fallback. INC-4's published fallback rates include `:has()`-dependent restyle and container re-entry, and P2 forbids shipping the incremental path where it disagrees with from-scratch output.

### B6. Data-oriented phase outputs, content-addressed computed style

**What it is.** Data-oriented layouts go where work is homogeneous and identity is not JS-visible. That means **phase outputs**: immutable **fragment records with physical coordinates**, **flat inline item lists** and **line records** (LY 6.13), property trees, paint chunks and animation state. The property trees and their kinds are derived from the effects the specifications define: CSS Transforms (transforms and 3D contexts), CSS Masking (clips), Compositing and Blending and Filter Effects (opacity, blend, filters), CSSOM View and CSS Overflow (scrolling). Paint chunks are runs of display items in the stacking and painting order of CSS 2 Appendix E. Computed style is **content-addressed style groups with deterministic identities in per-agent tables** (ST-D7), shared only by exact inputs; the matched-rules representation is interned match keys plus a memo (ST-D8).

**Evidence.** Chromium already ships these patterns, which is evidence that they work at web scale, not a template (M-1). Fragments are immutable with no upward references. Inline formatting contexts are flat depth-first lists with descendant counts. Property trees are cheaper to send across threads and processes than DOM state ([Chrome](https://developer.chrome.com/docs/chromium/renderingng-data-structures)). The strongest data-oriented speedup on record is Coherent Labs' **6.12× on animation ticks** against Chromium 66. That is a 2018 vendor conference claim for one subsystem, in an engine that supports only flexbox ([Nikolov, Meeting C++ 2018](https://meetingcpp.com/mcpp/slides/2018/Data-oriented%20design%20in%20practice_Nikolov_MeetingCpp18.pdf)). It shows where data-oriented design helps, which is homogeneous per-frame work, and why the whole-engine version is not available to a compatible browser. Content-addressed style groups are ST-D7's answer to the same memory problem: groups are shared only by exact inputs, identities are deterministic, and each agent's table is rebuilt independently, so parallel and sequential runs produce the same bytes. Storing about 500 properties as separate columns per element would replace sharing with copies, or reintroduce sharing through interned indices, which rebuilds the group model with an extra indirection; ST-D8 keeps matching in interned keys rather than per-property cells.

**Maturity.** Fragment records, flat inline lists, property trees and paint chunks: shipped (Chromium). Content-addressed computed style with deterministic identities: research. Animation SoA: shipped in a non-compatible engine (vendor claim).

**Replaces.** Mutable per-object layout boxes and paint objects; pointer-shared computed style with per-thread caches.

**Risk.** Low for phase outputs. Content-addressed style carries ST-D7's merge cost and identity risk (Q-ST-8), bounded by ST-D12's reference engine. **Per-property SoA for computed style is rejected** (non-goal).

### B7. Rendering: canonical pixels plus pixel-optional rendering

**What it is.** Izcal's rendering is its own: **canonical integer raster** for page content and every readable surface (GR-D3), a **content GPU process per renderer key** and a **compositor GPU service**, with the canonical image defined for the composed screen (GR 6.4). There is no WebRender, Vello or wgpu. HGBA-3.0 adds **pixel-optional rendering**, in one text with Stage 1 5.7's "stops after chunk generation": a **hidden running** tab (an agent task, automation, or a tab declared hidden for a recorded reason) runs style, layout and the semantic tree, produces property trees and paint chunks, and **stops before raster and compositing** until a screenshot or a visible frame is requested. A **frozen** tab skips style and layout as well until it resumes; a visible tab paints.

**Evidence.** Canonical integer raster is the only way to make pixel hashes identical across backends and drivers: only integer arithmetic is bit-identical across GPUs, and the notes found no shipping engine that restricts page raster to it (GR 6.4, GR-51). The notes found **no product running selector matching, cascade or general layout on the GPU**. The likely reasons (this document's explanation, not a sourced finding) are that selector matching is branchy and data-dependent per element, per-node work is tiny, the cascade and layout have parent-before-child and sibling dependencies (line breaking, floats), and text shaping runs on the CPU, all of which map poorly to GPU SIMT execution. That makes it a current constraint for general CSS, which restricted subsets might relax. Demand for render-free operation is real: Lightpanda handles DOM and JS with no rendering, specifically for automation and agents, and its vendor claims about 11× speed and 9× less memory than Chrome are unverified ([linuxiac](https://linuxiac.com/?p=209081)).

**Maturity.** Canonical integer raster across CPU and GPU: research; no shipping engine does it. Pixel-optional mode in a full engine: prototype-level idea. Headless-only engines: shipped.

**Replaces.** Always-on rendering for background, frozen and agent tabs; GPU-float page rendering.

**Risk.** Low technically. The notes contain **no data quantifying wasted rendering cost for agents**, so the benefit must be measured (target AG-4); the canonical raster's cost is unmeasured until GR-34.

### B8. Semantic plane: the accessibility tree as a first-class pipeline output

**What it is.** The engine computes a semantic tree in the core pipeline, next to layout and from the same one-copy node columns. Each node carries a **stable ID across mutations**, role, name, state, bounding box, **origin and frame provenance**, and **human-visibility flags** (contrast, size, occlusion, off-screen). The tree is served as full snapshots at quiescent points and as **incremental diffs** between them. It feeds platform accessibility APIs and agents from one source.

**Evidence.** Chrome ships "DevTools for agents" that exposes accessibility trees, console and network to 20+ coding agents ([Chrome I/O 2026](https://developer.chrome.com/blog/chrome-at-io26)). That shows the a11y tree is already an agent interface, but one reached through a debug protocol. A combined accessibility tree, HTML and screenshot observation in BrowserGym can **exceed 20,000 tokens** ([arXiv 2606.06708](https://arxiv.org/pdf/2606.06708)). WebArena scores vary **20–30 points with the scaffold alone** ([benchmarkingagents](https://benchmarkingagents.com/best-benchmarks-for-browser-agents/)), so the observation interface is a first-order variable in agent success. Brave showed that text invisible to humans, such as faint text in screenshots, reaches the model as instructions ([Brave](https://brave.com/blog/unseeable-prompt-injections/)). That is the case for visibility flags.

**Maturity.** A11y tree exposed to agents: shipped (via DevTools). Stable-ID diffs, provenance tags and visibility flags: **research/proposal**. The notes found them shipped nowhere.

**Replaces.** CDP scraping of DOM snapshots plus screenshots.

**Repair overlay.** The semantic plane has two layers. The **author tree** is computed exactly as HTML-AAM and accname specify, and the reference-engine differential and WPT check it. The optional **repair overlay** is a sparse map keyed by stable node ID, holding accessibility repairs of classes R1–R4 (B10). Each entry records its class, rule, source nodes and provenance. The overlay never feeds back into the DOM, style, layout or the node columns, which target A11Y-1 checks bit for bit. A repair may draw text only from nodes with the **same origin and frame** as the repaired node (A11Y-1b). Agent observations use the author tree; a repaired value reaches an agent only with a `repaired` provenance tag, because heuristic names promote attacker-controlled strings such as file names and URLs into trusted-looking labels. A user-facing inspector lists every repair on the page, and one toggle reverts them all. No browser offers a whole repaired tree the user can switch to and from; Chrome (2019) and Edge (2022) insert generated image descriptions with an on/off control, and the Legato browser ships rule-based repairs with no published user evaluation.

**Risk.** The tree's quality depends on page authoring quality, which the engine cannot fix. Visibility heuristics will have false negatives that attackers probe. The notes found **no matched study of a11y-tree versus screenshot accuracy** in 2026. Repairs that reduce checker-detected violations can still harm users, because a wrong name is worse than a missing one; no checker-based gate is presented as evidence of benefit. The accessibility tree is security-sensitive: CVE-2026-95301 let a compromised renderer read cross-origin accessibility data while a `chrome.automation` consumer was running (fixed in Chrome 154), so repair logic runs in the renderer on renderer-local data, never as a browser-process aggregation across origins.

### B9. Agent principal, origin capabilities and a tool registry

**What it is.** An agent is a principal with its own capability set inside the browser broker. It holds per-task **read-only and read-write origin sets**, enforced by the engine, and bounded by the **container** it runs in (Stage 1 design, Section 6): a container can forbid agents entirely, or cap them at read-only. Content from origins outside the set is never placed in the agent's observation, and that rule is enforceable because B8 tags provenance. It also gets an isolated storage partition, a trusted, non-spoofable confirmation surface for payments, credentials and messages, deterministic detection of sensitive forms, and a tamper-proof action log. A native **WebMCP-compatible tool registry** lets sites declare tools, and the engine prefers declared tools, then the semantic tree, then pixels.

**Agents are not extensions, and extensions are not agents.** Extensions are a separate principal system with a three-ring compatibility surface — implemented with published conformance suites, accepted as data, refused with recorded reasons (EX-D1) — and their own process model: one component host per extension origin, content scripts as isolated worlds, extension pages in own-origin renderers, and no extension code sharing a renderer with web content except content scripts, which hold no capability tokens (EX-D3). An agent principal never gains an extension's capabilities, and an extension never gains an agent's origin sets; the agent host is not a component host.

**Agents edit only through typed edit intents.** An intent is a typed insert, replace-range or compose capability that produces the same trusted `beforeinput`/`input` a person's input would, labelled with its principal (ED-D21). `hg-edit` refuses an agent intent whose frame's origin is outside the agent's read-write set, and the IIP `editing` domain sends agent records only for origins in the agent's read set, with credential placeholders (DT 6.5). Agent intents **never mint user activation**, so they cannot unlock clipboard writes, pop-ups or the clipboard read path; clipboard writes are labelled "agent" in the provenance log.

**High-risk confirmations reject synthesized input.** Prompt acceptance is decided by the broker from real OS input that it hit-tests itself: continuously visible and unoccluded ≥ 500 ms†, focused, within a broker-owned hit rectangle, with no gesture that began before the prompt, and **no synthesized input in any class** (SH-D12). An agent, an automation client or a page cannot press its own confirmation. The security scope's AGT-R1 to AGT-R6 govern the rest of agent traffic — least privilege, per-task origin sets, typed refusals and no self-approval (SEC-18, SEC-19) — and AGT-R3 specifically refuses `file:`, `view-source:file:`, `blob:` and `data:` navigations. Every agent-initiated URL, redirect hop and download runs the phishing check in a path the agent cannot bypass (AG-3, PH-D8).

**Evidence.** Google **ships** the core of this in Chrome's agent: a User Alignment Critic that sees action metadata but never raw web content, and Agent Origin Sets split into read-only and read-write. At initial rollout **only the read-write set is enforced** ([Google](https://blog.google/security/architecting-security-for-agentic/)). Brave runs its agent in an isolated profile with a second reviewing model, and states that the safeguards "do not eliminate risks such as prompt injection" ([Brave](https://brave.com/blog/ai-browsing/)). OpenAI frames injection as an ongoing arms race ([OpenAI](https://openai.com/index/hardening-atlas-against-prompt-injection)). WebMCP is a **prototype**: `document.modelContext.registerTool`, with cross-origin frames gated by `allow="tools"`, entered a Chrome 149 origin trial ([WebMCP](https://github.com/webmachinelearning/webmcp); [Chrome I/O 2026](https://developer.chrome.com/blog/chrome-at-io26)). A federal court enjoined Perplexity's Comet from Amazon in March 2026, separating user permission from platform authorization, after Amazon alleged Comet disguised itself as ordinary Chrome ([GeekWire](https://www.geekwire.com/2026/03/10/judge-blocks-perplexitys-ai-bot-from-shopping-on-amazon-in-early-test-of-agentic-commerce/)).

**Maturity.** Origin sets and critic: shipped in Chrome (partially enforced). WebMCP: prototype. Provenance-enforced observation filtering and honest agent identification: research/proposal.

**Replaces.** Agents as privileged extensions or CDP clients with ambient access to every origin.

**Risk.** WebMCP may change or die after its origin trial, so the registry must track the spec, not get ahead of it. **Engine enforcement does not solve prompt injection.** It bounds what an injected agent can reach, the way site isolation bounds a compromised renderer.

### B10. AI integration is off by default

**What it is.** Every AI capability in B7–B9 and Section 7 ships switched off. "Off" is defined by what does not happen, so it can be tested:

- **No agent processes.** The agent host is never launched, and the ML service is not launched unless the independent `accessibility.model` grant is on. Agent code lives in separate crates and a separate service process, so "off" means not loaded, not merely hidden in the UI. With `accessibility.model` on and `ai.enabled` off, the ML service runs only S_A — image description and OCR, plus captions if Q-ML-1 is yes — and no generative or agent task module is loaded (ML-D4, ML-D5).
- **No models without a grant.** With both grants off, no model is downloaded or loaded. Built-in AI web APIs report the spec's "unavailable" state, which is an ordinary outcome sites already handle. The Stage 1 model set is the accessibility grant's S_A only; **translate, summarise, prompt and writing assistance are Stage 2 tasks under `ai.enabled`**, not Stage 1 features, and the Prompt API does not exist with AI off (ML-D2).
- **No AI network traffic.** No requests to any model or agent endpoint, and no AI-related telemetry.
- **No agent-only computation.** Provenance export, stable-ID semantic diffs, visibility flags for agents, pixel-optional agent tabs and agent-facing animation decision records are not computed; the animation parts sit behind `ai.enabled` (AN-D12). **Session-scope enforcement for automation clients is not agent-only computation**: DevTools automation and the recorded-session host are not the agent principal, and an automation client attached with AI off still gets its session-scope checks (DT 9.5).
- **Inert, not missing, web surface.** If WebMCP ships as a standard, `document.modelContext.registerTool` still succeeds but no agent ever calls the tools. Removing the API would break sites and give fingerprinters a signal that the user has AI off.
- **No AI entry points or promotions in default UI.** With the switch off, the new-tab page, address bar, menus, context menus and onboarding show no AI buttons, chips, suggestions or nudges to turn AI on. The settings page that holds the switch is the only place AI appears. This is the case Chrome's "Do more with AI" new-tab chips show: a feature can download nothing and still be an AI pain point. The published UI-surface list that AG-0 checks includes the `hg-devtools` surfaces, so a DevTools entry point cannot become an unlisted AI surface (DT-12).
- **Off survives updates.** No update, settings migration or profile sync may switch AI on or show a re-prompt. A choice is changed only by the user or by enterprise policy. Firefox's AI controls were explicitly designed so choices "persist across updates" ([Mozilla](https://blog.mozilla.org/en/firefox/ai-controls/)).

**Boundary cases, decided in advance so that AG-0 neither fails on a legitimate model nor lets a surprise through by reclassification.** Chrome justified its silent 4 GB Gemini Nano download after the fact as powering scam detection ([That Privacy Guy](https://www.thatprivacyguy.com/blog/chrome-silent-nano-install/)), which shows why the rules must exist before the first model does.

- **Security classifiers.** A non-generative ML classifier used for a security feature (for example phishing or malware detection) is **not** governed by B10 only if it meets all of the following. It ships inside the signed browser package or its normal update, and is never downloaded separately. It stays below **50 MB†**. It makes no network requests beyond the security feature's existing protocol. And it is listed in a published **ML inventory** that states its purpose, size and inputs. The inventory is empty at 3.1.0. Adding an entry needs a decision-log record and is reported in the release notes. Anything generative, anything larger, and anything downloaded on demand counts as AI and is off by default. **The phishing spec does not use this carve-out**: its reputation list is URL data compiled into a signed bundle, not an ML classifier, and the list's model is PH-D2's; a non-MIT feed is test-only (PH-D14).
- **Rule-based accessibility repairs are not AI, but not all are on by default.** No accessibility repair is gated by the AI switch (P6). The default depends on whether a repair invents content and whether content can observe it:
  - **R0, OS preferences.** Forced colors, contrast and other OS accessibility preferences follow the OS setting and are exposed to content exactly as the specs require (for example the `forced-colors` media query). They are not normalized by anti-fingerprinting, because hiding them trades usability for anonymity on behalf of the users who depend on them.
  - **R1, AT-only language hint.** A document-language hint taken only from deterministic sources (`Content-Language`, an ancestor frame's `lang`, the UI locale), exposed only to platform accessibility APIs and never written to the DOM. **On.** Language *detection* from page text uses a classifier, which makes it an ML-inventory entry, not R1.
  - **R2, heuristic names and roles** for unlabeled controls (from URLs, file names, `title`, adjacent text). They invent content and can be wrong. **Off by default**; one accessibility setting turns them on, with per-site override; they live in B8's repair overlay, are listed in the inspector and revert with one toggle. They become default-on only by a decision-log record after A11Y-3 passes.
  - **R3, structural repairs** (focus order, keyboard traps, headings). They change focus events and behavior that content observes, so they are **user-invoked per site only**.
  - **R4, model-based repairs**, as below.
- **Model-based accessibility repairs have their own opt-in.** Machine-generated alt text and similar repairs need a model. They sit behind a separate accessibility setting — **the `accessibility.model` grant, with a model set (S_A) defined by ML-D4** — not the `ai.enabled` switch, and that setting is also off by default. **S_A is image description and OCR, plus captions only if the owner answers Q-ML-1 yes, in which case ML-ASR moves under this grant.** Turning it on downloads a local, on-device model only at that moment, following Firefox's local design rather than a cloud call ([Mozilla Hacks](https://hacks.mozilla.org/2024/05/experimenting-with-local-alt-text-generation-in-firefox-nightly/embed/)), and **disabling the grant deletes every model it downloaded, unconditionally** — B10's "unless the user chooses to keep them" is replaced for this grant, because ML-9 needs the exact default state; the keep option remains for AI-grant models in Stage 2. Every generated label is recorded in the repair overlay as machine-generated and disclosed to the user by a mechanism decided under Q-10, and the user can dismiss or report it. Turning on the accessibility setting enables no agent features, and turning on the AI switch does not enable the accessibility model: **the two are independently testable** (ML-D4). The browser describes these repairs as an aid to the user, never as making a site compliant, which is the line the FTC drew in its accessiBe order ([FTC](https://www.ftc.gov/news-events/news/press-releases/2025/04/ftc-approves-final-order-requiring-accessibe-pay-1-million)). **R0–R3 are unchanged.**
- **Accessibility unaffected.** The accessibility tree for screen readers and other assistive technology works exactly the same with the switch off. B8's shared tree is computed whenever assistive technology needs it; only its agent-facing extras depend on the switch.

**How it is switched on.**

- **Users** turn it on per profile in settings (`ai.enabled`), with a plain-language description of what an agent can do.
- **Embedders** turn it on by configuration in agent-runtime builds (headless or cloud-hosted). That is the positioning Section 7 recommends, and the build records the setting in its logs.
- **Administrators** can force it off and lock it through enterprise policy, **and may force off and lock either `ai.enabled` or `accessibility.model`**; neither can be forced on (ML-D4).

Switching on does not grant an agent anything by itself. Every agent task still starts with **empty origin sets**, and the user grants origins per task (B9); **an agent navigation, document fetch or download to a phishing-listed URL is refused with a typed error, never warned and never overridable** (phishing PH-D8). Prompt acceptance and every other high-risk confirmation reject synthesized input in every class, including automation's; the broker hit-tests real OS input itself (SH-D12, AGT-R8). Switching off tears down the agent host and deletes agent storage partitions. Downloaded AI-grant models are deleted unless the user chooses to keep them; **accessibility-grant models are always deleted when that grant is disabled** (ML-D4).

**Evidence and maturity.** This is a product and policy decision, not a technology claim. Its cost is small because B9 already makes the agent a separate principal behind the broker. Maturity: design choice; the AG-0 target verifies it.

**Replaces.** AI features that load or contact services by default and are hidden behind UI toggles.

**Risk.** Agent features get less real-world use, and so less feedback, than they would if enabled by default. HGBA-3.0 accepts this: under P1, an agent that can act on the user's behalf across origins is a capability the user opts into, not one they must find and disable.

## 5. Dependencies versus built new: specifications are the oracle

Izcal has two kinds of component, and only two. **Generic infrastructure** is used unmodified through public APIs: Rust's standard library, general-purpose crates that do no browser-engine work, MIT cryptography primitives, and OS interfaces and drivers (M-1). **Every component that does browser-engine work is written new from the specifications** (WHATWG, W3C, TC39, IETF, Khronos, Unicode) at a pinned revision, with spec anchors (ANC-1): the JavaScript and WebAssembly engine, the collector, the DOM and bindings, the HTML and CSS parsers, the style system, layout, the text stack, the renderer and rasterizer, the compositor, the GPU abstraction and shader compiler, the network protocols and content blocking. There is no third kind: no other engine's code is copied, ported or translated in (Stage 1 design D-S10), and no other engine's source is evidence (HGBA-2 2.3.3).

**A replacement is written from the specification, never translated.** If Izcal ever replaces a component, the replacement is written from the specification and gated by spec oracles (pinned WPT and test262, formal models, spec-derived property tests), plus differential testing against the component it replaces as a black box. The 2026 replacements that succeeded show why the gate matters: Ladybird's Rust LibJS produced byte-identical ASTs and bytecode against the C++ one ([Ladybird](https://ladybird.org/posts/adopting-rust/)), its Rust HTML parser was checked for DOM parity on about 7,000 sites ([Ladybird May 2026](https://buttondown.com/ladybird/archive/this-month-in-ladybird-may-2026/)), and its CSS parser port deleted C++ only after zero A/B mismatches per grammar family ([Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31/)). Those were translations of Ladybird's own code, a method Izcal does not use. What carries over is the evidence that **a mechanical oracle, not the author, decides whether a replacement is right**. A new engine with no mechanical oracle is in FastRender's position.

| Component | Decision | Reason | Evidence |
|---|---|---|---|
| JS + Wasm engine | **Build new** (`hg-js`): interpreter first, JIT when its oracle exists | M-1 excludes V8; the speed gap is largest here, so the spec's staging is built around measurable milestones rather than a dependency | Ladybird SP3 ~3.9 ([Ladybird](https://ladybird.org/newsletter/2026-08-31/)); JS 9.4–9.5 |
| Collector, DOM and bindings | **Build new** (`hg-heap`, `hg-dom`): one copy, node columns outside the cage, lazy wrappers, WebIDL bindings | No dependency implements the DOM over a one-copy columnar store; the collector and bindings are designed together | JS-D4; FP-11 |
| HTML and CSS parsing, style | **Build new** (`hg-html`, `hg-css`, `hg-style`): feature-indexed invalidation, content-addressed style groups, a spec-literal reference style engine as the oracle | No library implements the style system over Izcal's tree, and using one would be engine work; the reference engine is the gate | ST-D7, ST-D10, ST-D12 |
| Layout: block, flex, grid, tables, fragmentation, writing modes | **Build new** (`hg-layout`) from CSS 2, CSS Sizing, CSS Flexbox, CSS Grid, CSS Table and CSS Fragmentation | Taffy is an engine library and cannot satisfy the one-copy tree traits; the primary oracle is the specifications plus WPT, with reference engines as a secondary differential | LY 6.4, 6.7, 6.9; [Chrome LayoutNG](https://developer.chrome.com/docs/chromium/layoutng) as evidence that memoized layout works at web scale |
| Text and inline layout, fonts | **Build new** (`hg-text`, `hg-font`): shaping, line breaking, font parsing and the font reader; OS fonts are an interim source only | Parley and HarfBuzz are engine libraries; the font reader is a Tier 1 parser with its own proofs | TX-11; LY 6.13 |
| Raster, compositor, GPU abstraction | **Build new** (`hg-gpu`): canonical integer raster, own shader compiler, content GPU process per renderer key and a compositor GPU service | WebRender, Vello and wgpu are engine libraries; canonical pixels require control of the whole backend | GR-D3, GR 6.4, GR-51 |
| Network stack | **Build new** (`hg-net`): HTTP, TLS, QUIC and DNS from the IETF specifications; MIT cryptography primitives are generic infrastructure | neqo and similar are engine libraries; crypto primitives do no browser-engine work | Networking spec; M-1 |
| Runtime substrate, IPC and navigation | **Build new** (B1, B2, `hg-navigation`) | Cannot be retrofitted; needs a simulation backend | [madsim](https://github.com/madsim-rs/madsim) as a model; Mojo as evidence that typed capability IPC ships ([Mojo](https://chromium.googlesource.com/chromium/src/+/main/mojo/README.md)) |
| Semantic plane, agent principal, tool registry | **Build new** (B8, B9) | No engine has them as core features | — |
| Extensions | **Build new on the component host** (JS-D10), one component host per extension origin | Wasmtime is excluded with the other engine libraries; extensions are a separate principal from agents | EX-D1, EX-D3 |
| Verified parsers, font and session-image readers | **Generate and verify Izcal's own**: every `.hgbits` parser, the whole font reader and the session-image reader, with Kani covering `hg-simd`'s index arithmetic | EverParse and Kani are tools, not runtime dependencies; the parsers are Izcal's code and must be proved as such | VER-1; TX-11; MD-21 |
| Crypto | MIT cryptography primitives as generic infrastructure; protocols built on them | Primitives are generic; an engine library that implements browser protocols is not | [HACL*](https://hacl-star.github.io/) as evidence that verified primitives ship |

**Where the evidence still says build new rather than depend.** The 2.3.0 direction settles the decision for every engine component, but the evidence for *why* still matters when a component is scoped. Building new wins where substrate cannot be retrofitted: determinism and simulated IPC, where the DST literature is explicit. It wins where architecture has to be designed in from the start: immutable outputs, constraint-keyed caches and stable identities. LayoutNG needed a full rewrite to fix hysteresis and under-invalidation, and Izcal derives its own from the CSS specifications ([Chrome](https://developer.chrome.com/docs/chromium/layoutng)). And it wins where no incumbent exists: the semantic plane and the agent principal, where every 2026 agent product is a Chromium fork with no published engine change except Atlas's out-of-process wrapper ([OpenAI](https://openai.com/index/building-chatgpt-atlas)).

**What the direction costs, and why the old counter-case no longer decides.** The historical record is unkind to engines that rebuild compatible commodity parts. **Opera abandoned Presto in 2013** to "focus on what's valuable rather than building something in parallel" ([TidBITS](https://tidbits.com/2013/05/30/opera-releases-chromed-preview-of-next-browser/)), and **Microsoft abandoned EdgeHTML in 2018** for web compatibility ([9to5Google](https://9to5google.com/2018/12/06/microsoft-confirms-chromium-edge/)); both had hundreds of engineers. Even FastRender's agents chose Skia, HarfBuzz, Taffy and QuickJS over writing their own ([Simon Willison](https://simonwillison.net/2026/Jan/23/fastrender/)). That record is the cost this direction accepts, not a reason to revisit it: M-1 is the owner's premise, not a cost-benefit claim, and the component specs' staffing and milestones are where the cost is accounted. What the record changes is the method: because there is no shipped library to lean on, every component must have its oracle before it is generated, and every compatibility claim must be earned against the specifications plus WPT rather than borrowed from a dependency.

## 6. How the engine gets built

### AI-assisted development: spec-to-code, gated by spec oracles

**Spec-to-code is the only route.** Izcal has no predecessor to translate and translates no other engine's code (M-1, Stage 1 design D-S10). Agents are given the pinned specification text and Izcal's own code, and generate **step-numbered skeletons** from the specification algorithm: each function carries the spec anchors of the steps it implements, and humans review and complete it. WHATWG and TC39 specifications are written as step-by-step algorithms, which suits skeleton generation with step-number comments. But no machine-readable semantics of the HTML parser or DOM exists, so **correctness must come from the oracles, not the model**.

**Why mechanical oracles matter: the 2026 evidence.** Oracle-gated work ships; ungated generation does not. Ladybird's LibJS port, a translation of its own C++, was human-directed through "hundreds of small prompts", reviewed in multiple adversarial passes by different models, and checked with byte-identical ASTs and bytecode, **0 regressions on 52,898 test262 tests and 12,461 regression tests**, and a lockstep mode comparing both pipelines during real browsing ([Ladybird](https://ladybird.org/posts/adopting-rust/)). Cursor's FastRender swarm had only screenshot diffs and the compiler as feedback, and JavaScript never worked ([Simon Willison](https://simonwillison.net/2026/Jan/23/fastrender/)). Izcal uses neither method: it cites them only as evidence that the oracle, not the generator, decides the outcome. The best controlled productivity study found experienced developers **19% slower** with AI while believing they were 20% faster ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Google's "75% of new code is AI-generated" is self-reported and "pretty impossible to fact-check" ([Semafor](https://www.semafor.com/article/04/24/2026/google-ceo-says-75-of-companys-new-code-is-ai-generated)).

**The honest risk.** Spec-to-code has weaker oracles than translation: there is no earlier implementation to compare byte for byte, and the notes found no measured public case of an agent building a conformant browser subsystem from a specification alone. That is why the **spec** oracle class is mandatory (EQ-1): every component that implements web-visible behavior is gated by a pinned conformance suite, a formal model or spec-derived property tests, and a reference-engine differential is never its only oracle.

HGBA-3.0 therefore makes the **oracle a precondition for generation**. No component is generated or rewritten until its oracle exists and runs in CI. In order of preference, the oracles are: Izcal's own earlier implementation or from-scratch reference path, in lockstep (byte, tree or fragment equality); the relevant pinned WPT and test262 subset; formal reference models where they exist; spec-derived property tests; and differential comparison against reference engines as black boxes on generated inputs (DOM serialization, computed styles, layout boxes, JS results). ESMeta extracts ECMA-262 into an executable IR and has found bugs in both the spec and engines ([ESMeta](https://github.com/es-meta/esmeta)). Cassius gives an SMT semantics for a large fragment of CSS layout, usable as an oracle on small generated cases rather than as a proof target ([MSR](https://www.microsoft.com/en-us/research/?p=610539)).

### Spec anchoring

Every hand-written algorithm carries a **spec anchor**, a comment `// spec: <URL>#<fragment> [step N[.M]]` naming the specification section and step it implements (M-1, target ANC-1). **`hg-anchor`** resolves the anchors against **pinned specification snapshots** (`specs.lock`, next to the WPT pin), joins them to WPT tests through WPT's `<link rel=help>` metadata, publishes coverage per specification, and, when a snapshot moves, lists the anchors whose section text changed. Generated code (bindings, IPC) is anchored by its generator. Commits that change web-platform behavior carry a `Spec:` trailer.

Where a specification is silent, ambiguous or contradicted by the deployed web, behavior follows documented interoperability evidence, recorded in the **black-box observation log** (`compat/observations/`): a test case, each engine's observed result and the resulting decision, never a link to another engine's source, and filed upstream as a specification issue. **No other engine's source is placed in an agent's context or checked out in an Izcal workspace.** The Stage 1 design specifies the mechanisms (crate rule G9, CI tiers, the `provenance` check).

### WPT-driven development, with its caveats

The specifications, with WPT and test262 pinned against them, are the primary oracle from day one, tracked per directory in CI as in HGBA-2.0's S-4d. Two caveats from the notes shape how targets are written. First, **percentages move with the suite**: Servo gained 188,281 subtests in one month of 2025 from new tests alone, and Servo does not run all of WPT, so its numbers differ from wpt.fyi ([Igalia](https://blogs.igalia.com/mrego/servo-2025-stats/)). Targets are therefore pinned to a WPT revision. Second, **WPT is not the whole compatibility story**. Ladybird's subtest count grows slowly once the easy tests pass, in feature-specific bursts such as about 2,500 subtests from referrer-policy in one month ([Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31/)), and Interop's "web compat" area exists because real sites depend on de facto behavior that specs and WPT do not capture ([WebKit](https://webkit.org/blog/17818/announcing-interop-2026)). A recorded real-site corpus with differential rendering against reference engines covers that gap as a secondary signal: each disagreement is triaged against the cited specification section, and where the specification is silent the decision is recorded in the black-box observation log. It is never resolved by matching an engine's output.

### Oracles for each new component

No Izcal component has a predecessor, so each needs a named oracle, and they are not equally strong. Components that implement web-visible behavior also carry the **spec** oracle class (EQ-1) in addition to the oracles below:

| Component | Oracle | Strength | Residual gap |
|---|---|---|---|
| Node columns (B4, JS-D4) | **Traversal equality (debug and Nightly):** the columns must equal a fresh traversal computed through the DOM's public API, which is the source of truth. Checked at every flush in debug builds and sampled in Nightly; the release path relies on from-scratch bit-identity (INC-1), the reference style engine and WPT | Moderate: an exact full-state check in debug, not a heuristic assertion, and not a release-path oracle | A field defined wrongly in the traversal itself is wrong on both sides and surfaces end-to-end through WPT style and rendering failures. Release builds have no in-process column check |
| One-copy DOM and bindings (B4, JS-D4) | **`hg-heap`'s heap verifier and moving-GC stress**, plus JS-10's planted-bug suite for missing write barriers and stale wrappers; CI, DST and fuzzing run the verifying collector alongside the release one | Strong when it runs: the verifier reports a single omitted barrier, and the moving collector turns a stale external pointer into a crash rather than a silent read | Release builds run the same verifier under a sampling flag, but an omitted barrier that escapes the sampled runs can still ship as a use-after-free; the planted-bug suite is the regression net |
| Incremental driver (B5) | **The engine's own from-scratch path, which is kept, not replaced** (P4): output must be bit-identical on every frame (INC-1) | Strong for correctness in every case, including the hard ones: a formatting context the driver cannot handle incrementally falls back to from-scratch | What is open for `:has()`, fragmentation and anchor positioning (Q-2) is *how often* the fallback fires, which is performance, not correctness. INC-4 publishes it |
| Semantic plane: roles, names, states (B8) | WPT's accessibility-mapping tests (computed role and name) against HTML-AAM, Core-AAM and accname, plus black-box differential testing against Chromium's accessibility tree | Spec class from WPT; the differential is moderate: Chromium's tree is a reference, not ground truth | Disagreements are triaged against the cited AAM or accname section |
| Semantic plane: provenance and stable IDs (B8) | Property tests derived from the frame tree (every node's origin equals its document's origin) and AG-3's cross-origin suite | Moderate | No external oracle exists |
| Visibility flags (B8) | None: a heuristic | Weak | Measured only by a red-team suite; false-negative rate published (AG-5) |
| Repair overlay: non-interference (B8) | Bit-identical outputs with repairs on and off under DET-1 replay (A11Y-1) | Strong | Timing is measured separately (A11Y-4) |
| Repair overlay: correctness (B8) | Human-labelled holdout and held-out checkers (A11Y-2) | Moderate | Checkers detect a minority of WCAG criteria; labels cover only the corpus |
| Repair overlay: benefit (B8) | Pre-registered screen-reader user study (A11Y-3) | The only oracle for benefit; runs per rule change, not per commit | Population and task coverage |
| Agent principal (B9) | Tier 1 verification of the broker's capability policy, AG-3's cross-origin suite, and the security scope's AGT-R1 to AGT-R6 | Strong for the policy, moderate for its use | Policy correct but applied to wrong provenance would pass; the security rules are Phase 5 input |

**The node columns' *definition* also needs an oracle, and the style and layout specs provide one.** Traversal equality catches drift between the columns and the DOM API, but not a field whose meaning is wrong on both sides. Three rules close most of that gap:

- **Trait-generic consumers (design rule).** Style, the incremental layout driver and the semantic plane read their inputs only through Izcal's tree-access traits (`hg-tree`), which `hg-dom` implements over the columns and the JS-M0 alternative implements over cage nodes. They never depend on the concrete column types. A missing field is a compile error, because the style, layout and semantic crates depend only on the traits crate, not a silent bug.
- **Reference engines as differential oracles.** The spec-literal reference style engine (ST-D12) runs on every CI flush and must produce identical computed style; the from-scratch layout path (INC-1) must produce a bit-identical fragment tree; and the semantic plane's author tree is checked against WPT's AAM and accname mappings. This replaces the retired dual `cppgc`/data-plane implementation: the second implementation is now a spec-literal reference engine over the same DOM, not a second copy of it.
- **Independent traversal.** The fresh traversal used for the equality check is computed by a separate, deliberately simple, non-incremental walk that shares no code with the mutation-log application path. This is also a non-goal (Section 10), so reusing a helper across the two paths is a violation, not an optimization.

**What each check catches, layer by layer.** There are three places a field can be wrong:

| Layer | Example | Caught by |
|---|---|---|
| Column field definition | The columns copy the wrong DOM bit into their `:hover` field | **The reference style engine and the independent traversal.** The reference engine reads element state from the DOM API, never from the columns, so the two disagree |
| Implementation drift | The column trait implementation checks the right field the wrong way, or forgets to consult it | **The reference style engine and INC-1's from-scratch path** |
| Trait semantics | Both implementations answer "does this element match `:focus-visible`?" with the same misreading of the spec | **Not the differential.** Partly caught by WPT computed-style and rendering tests, which check observable results (`display`, `visibility`, `pointer-events`, selector matching) against the spec, and by computed-style differential comparison against reference engines on generated inputs (Section 6); private state with no observable effect stays uncovered |

**Cadence and cost.** Traversal equality is cheap (one traversal compared against stored values) and runs at every flush in debug builds and sampled in Nightly; it is a debug and Nightly check, not a release-path cost. The reference style engine and the from-scratch layout path are expensive: each runs the pipeline a second time. The reference engine runs on every CI flush where its cost fits ST-D12's sampling trigger, and the from-scratch comparison runs on every DST seed against a **fixed, published sample of the corpus** per seed batch, sized in the planning pass, so that DST cost per seed does not grow with the corpus twice. Fuzzing runs both on every generated case, because fuzz cases are small.

The weakest links are visibility flags and provenance, which is why HGBA-3.0 never presents them as a prompt-injection defense, only as a bound on what an agent can see.

### Verification where it pays off

Formal verification has shipped for small, well-specified, high-value code: EverParse-generated parsers in the Hyper-V virtual switch ([MSR](https://www.microsoft.com/en-us/research/blog/everparse-hardening-critical-attack-surfaces-with-formally-proven-message-parsers/)), HACL* crypto in Firefox, Linux and CPython ([HACL*](https://hacl-star.github.io/)), and seL4 at roughly 20:1 proof-to-code ([seL4](https://sel4.systems/About/)). The Rust standard-library campaign shows the cost at scale. After about two years, **989 of about 34,000 in-scope functions** have full formal contracts. Generated "autoharnesses" covered far more shallowly, and the effort found **no previously unknown memory-safety vulnerabilities**, only specification and documentation defects ([Rust Foundation](https://rustfoundation.org/?p=120341)). Layout verification remains research that does not scale to large pages ([Troika](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-modular-oopsla2019-abstract.html)). AI proof generation is a research target (KVerus, [arXiv 2605.03822](https://arxiv.org/pdf/2605.03822)), not yet a tool.

HGBA-3.0 tiers verification accordingly. **Tier 1, generated or checked parsers** (EverParse-class generated proofs where a format spec exists, Kani-checked otherwise, matching VER-1): IPC message (de)serialization across every renderer-to-broker channel, the broker's capability policy, the URL parser, **the whole generated font reader and the session-image reader**, every `.hgbits`-generated parser, and crypto. The three proved properties are named: **no panic, no arithmetic overflow and no out-of-bounds read**. Kani covers `hg-simd`'s index arithmetic, and a **per-backend handle harness** runs the same property set against each backend implementation, not only the default one. These are all parsers of attacker-controlled bytes at a privilege boundary. The Rust std campaign's 989 fully specified functions out of about 34,000 is not the right comparison: EverParse generates verified parsers from format descriptions, so the cost scales with the number of message formats, not the number of functions. **Tier 2, bounded model checking** (Kani, ESBMC): every `unsafe` block and every FFI seam to OS libraries, drivers and the GPU, where the std campaign suggests the value is highest. **Tier 3, everything else:** fuzzing (Fuzzilli for JS, Domato-style for DOM and CSS, and LLM-generated fuzz harnesses, which found 26 new vulnerabilities across 272 projects at Google ([Google](https://security.googleblog.com/2024/11/leveling-up-fuzzing-finding-more.html))), differential testing and DST.

### Deterministic simulation testing

B1 exists so that this is possible. The simulator runs the browser, network, GPU and renderer processes as simulated hosts under one seeded scheduler. It replays recorded HTTP archives with injected resets, slow bytes and reordered resource completion, which the notes identify as the likely source of many load-order races. It explores HTML task-source interleavings the spec permits. Every failure is a seed, and every seed replays exactly. GPU, audio and media sit outside the simulator in Stage A and are covered by `rr` or whole-VM determinism. The method is shipped in databases and untested in browsers, so it has its own kill criterion (DST-1): if it does not find bugs at a competitive rate, it is demoted. DST-1 measures that rate in two additional modes: an **adversarial-peer mode**, where every process kind is driven by a hostile peer rather than a well-behaved one, and a **planted-bug benchmark**, where seeded bugs measure whether the simulator finds the defects it was built to find.

## 7. Agent-native capabilities

The agentic browsing market moved fast in 2026, and in one direction. **OpenAI shut ChatGPT Atlas down on 9 August 2026** and moved agent browsing into ChatGPT, a cloud browser and a Chrome extension ([TechCrunch](https://techcrunch.com/2026/07/09/openai-is-shutting-down-atlas-but-its-ai-browser-ambitions-are-still-growing/)). Chrome shipped Gemini auto browse in January 2026 ([blog.google](https://blog.google/products-and-platforms/products/chrome/gemini-3-auto-browse/)). Every notable agent product is Chromium-based. That has two implications. A new engine has **no competitor at the engine layer**, and its pitch must be capabilities that a Chromium fork cannot easily bolt on. And the stronger position is as an **agent runtime** (embeddable, headless, cloud-hostable, drivable by third-party agents) rather than as a consumer AI browser, a category that is shrinking. **This positioning is a bet on a market that has not formed, not a conclusion from evidence.** The agent-runtime market contracted in 2026, Chromium is free to agent builders, and Atlas and Comet ran on it. The only render-free engine aimed at agents in the notes, Lightpanda, backs its case with vendor claims. Because AI integration ships off (B10), the consumer browser does not depend on this bet.

HGBA-3.0's agent capabilities follow from B4, B7, B8 and B9, and are labelled accordingly. The **semantic plane** (research) gives compact, diffable, provenance-tagged observations instead of 20,000-token combined snapshots. **Deterministic snapshots** (research for browsers) come from B1. An agent step taken at a quiescent point under a virtual clock and seeded randomness can be replayed exactly, which addresses the poor reproducibility of live-web agent evaluation ([arXiv 2603.29020](https://arxiv.org/pdf/2603.29020)) and gives auditors a replayable log. **Pixel-optional parallel sessions** (prototype idea) make many concurrent isolated agent contexts cheap, with cheap forking of session state, served through a native automation protocol rather than a debug port. The **agent principal** (shipped in part, in Chrome) enforces origin sets in the engine, using provenance to keep out-of-set content out of the model's view. Browser-mediated credentials let agents sign in without ever seeing secrets, as Chrome's design already does ([Google](https://blog.google/security/architecting-security-for-agentic/)). The **tool registry** (prototype, WebMCP) tracks the spec and synthesizes tools from `<form>` only if that becomes part of it. **Honest agent identification**, a distinct and verifiable agent signal to sites, is an inference from the Amazon v. Perplexity injunction, **not a sourced standard**. An **on-device ML service** (ML-D1) runs the Stage 1 accessibility model set under `accessibility.model`; the Prompt API, translate, summarise and writing assistance are **Stage 2 tasks under `ai.enabled`** (ML-D2), and cheap injection classifiers can run locally when that grant is on. Agent edits go through the typed edit-intent channel and never mint activation (ED-D21); prompt acceptance rejects synthesized input in every class (SH-D12); and an agent is a principal distinct from an extension (EX-D1, EX-D3).

**All of the above is off by default (B10).** The consumer browser ships with no agent, no model and no AI traffic. Embedders building agent runtimes switch it on by configuration, and users switch it on per profile. That fits the positioning above: the agent runtime is where these capabilities earn their keep, and a user who never opts in pays nothing for them (AG-0).

The boundary with the web platform is explicit. The semantic plane, snapshots, provenance, pixel-optional mode and agent principal are **embedder-facing internals** that content cannot observe, so the engine is free to innovate on them. WebMCP and any agent-identification header are **platform surface**, so the engine follows standards there and does not invent them.

The DevTools surface follows the same rule. A recorded session starts at a navigation or a process launch in dedicated fresh processes running the recording configuration (DT-D2); the CDP compatibility profile is Izcal's own, authored from prose and black-box observations and never from another engine's source (DT-D11 (a), DT-D12); and `hg-devtools` is an automation surface with session-scope checks, not an AI feature (B10).

## 8. Staged roadmap with falsifiable targets

HGBA-3.0 overlays HGBA-2.0's roadmap rather than replacing it. HGBA-2.0's Stage 1 targets (S-1 to S-4d, including S-4d's `wasm/jsapi/` triage rule, C-1, P-1, R-1, R-6) remain in force except where they name V8, `rusty_v8`, `cppgc`, Stylo, WebRender or wgpu; those are superseded by HGBA-2 2.3.0 and the component specs' milestones, and the `cppgc` spike's results and start conditions (i)–(iii) are history, not gates. Durations are **not given**: HGBA-2.0 already marked its 18-month Stage 1 as provisional, and nothing in the new evidence supports a schedule. Team scale is the dominant unknown. Ladybird reached about 2.09M passing WPT subtests with roughly **8 paid full-time engineers** (secondary source) ([urandom.io](https://urandom.io/blog/2026-05-09-the-browser-with-no-ad-sales-department)). Servo merged **3,183 PRs from 146 contributors** in 2025, after collapsing to 65 PRs in 2022 when Mozilla withdrew ([Igalia](https://blogs.igalia.com/mrego/servo-2025-stats/)). ## 10. Non-goals

HGBA-3.0 **does** write its own JavaScript and WebAssembly engine, garbage collector, DOM and WebIDL bindings (HGBA-2 2.3.0); what it does not do is adopt a general per-field incremental dependency graph or use signals as engine internals. It does not store computed style as per-property columns. It does not run selector matching, cascade or layout on the GPU. It does not use the Component Model as an internal ABI between script, DOM and layout; the component host is for extensions (EX-D3). It does not move layout off the script thread or adopt Servo's reported script/layout re-split. It does not subset the web platform for speed, however large the gain. It does not attempt full formal verification of the DOM, style or layout. It does not copy, port or translate another engine's code, by people or by AI tools (M-1), and it does not take another engine's library as a dependency for browser-engine work. It does not let AI agents generate components that lack an oracle, and it does not accept screenshot diffs as a conformance oracle. It does not disguise agents as human browsing. It does not treat an extension as an agent or an agent as an extension. It does not synthesize input for prompt acceptance in any class (SH-D12). It does not promise a speed multiple over Chromium. The independent traversal used for the column equality check and the mutation-log application path **share no code, ever**. Style, layout and the semantic plane **never depend on the concrete node-column types**, only on tree-access traits. Both rules are enforced by the crate graph rather than by review: the traversal and the log-application path live in separate crates, and a CI check on `cargo metadata` fails if they share any non-std, project-local dependency; the style, layout and semantic crates depend only on a traits crate, so naming a concrete column type is a compile error.

## 11. "Recreating Servo is not the best": an honest answer

The framing is half right. **Recreating Servo's architecture is not the best path**, and Servo's own history says so. Servo was designed around message-passing parallel components and a separate layout thread, and the platform forced layout back onto the script thread in 2024 ([Servo](https://servo.org/blog/2024/02/28/gamepads-font-fallback-space-jam/)). Its DOM is built from SpiderMonkey GC objects, a design Izcal does not inherit; its collector and bindings are Izcal's own (JS-D4). Its multiprocess mode is optional. Its constellation was not designed for deterministic simulation, and none of its threading was designed for replay. Its organizational history is a warning on its own: activity fell by about 95% within two years of losing its corporate sponsor ([Igalia](https://blogs.igalia.com/mrego/servo-2025-stats/)). Servo's WPT score of 61.6% at the end of 2025 also shows how far a mature, well-staffed Rust engine still is from full compatibility.

But "not Servo" is no longer "not the standalone libraries from Servo's ecosystem". **HGBA-2 2.3.0 removed that middle route**: no library that does browser-engine work is a dependency, so Stylo, WebRender, html5ever, Taffy and Parley are out, as V8, wgpu and AccessKit are. The 2.2 case for them is kept here as history, not as a requirement. Stylo had shipped in Firefox since 2017 and its sharing model beat the obvious data-oriented alternative on memory; WebRender and wgpu shipped in Firefox; html5ever was used by Servo and Blitz; Taffy and Parley were shared infrastructure across a dozen projects. The evidence that they worked was real, and it is exactly why the direction had to be made explicit: the cheap route was to use them, and M-1 now forbids it. Izcal instead writes the cascade, selector matching, invalidation, layout, text stack and rendering from the specifications, and uses the reference style engine (ST-D12), the from-scratch layout path (INC-1), WPT and black-box differentials as the oracles that the dependency would otherwise have supplied.

What is genuinely new in HGBA-3.0 is everything underneath and around those components, and none of it has shipped in a browser. That means an engine that is **deterministic and simulation-testable from its first commit** (a bet: if DST-1 fails, this shrinks to "replayable"); a **one-copy DOM with stable identities** that serves threading, incrementality, replay and agents at once (JS-D4); an **incremental core** that combines an approach shipped in LayoutNG (constraint-keyed immutable fragments, derived here from the CSS specifications) with research (Spineless ordered queues, durability tiers, ST-D10's invalidation index) behind measured fallbacks; a **build process in which oracles precede code**, code is written from the specifications, and AI generates only spec-anchored skeletons that the oracles gate; and an engine whose **semantic output and agent principal are core features**, not debug-port extras. The rule for each component is: build it from the specification, prove its parser or property where the boundary warrants it, and never ship a component without a spec-anchored oracle.

## 12. Open questions and flagged claims

### Open questions

**Q-1. What does the one-copy DOM cost?** Partly answered, and re-based. The 3.1 spike measured about 150–175 B per node on a toy DOM for the retired two-copy design; that number is history, not this design's. What is still unknown is the one-copy design's bytes per node across every copy on the corpus, which JS-M0 and FP-11's 48/72/512 B† budgets divide, and its node-space GC time; no source measures the cache behavior of a one-copy columnar DOM with JS. The question is answered by JS-M0 before B4's representation is frozen.

**Q-2. Can the incremental layout core cover the hard formatting contexts?** Spineless covered a CSS subset. Out-of-flow positioning, fragmentation, `:has()`, container queries and anchor positioning (an Interop 2026 focus area) break tree-locality. Which of them get explicit non-tree edges and which get permanent from-scratch fallbacks is unresolved.

**Q-3. Can V8 run deterministically under an injected platform?** **Retired 21 October 2026.** The JS layer is Izcal's own engine, and its GC, tiering and other timing-dependent decisions are recorded inputs (JS 6.9, JS-D15); there is no V8 platform to inject. The M0 answer below is kept as history: it is why a platform flag alone was rejected as the determinism mechanism. The flags existed in V8 15.2: `--predictable` (implies single-threaded GC, no concurrent recompilation and a fixed random seed), `--single-threaded` and `--random-seed`. But `rusty_v8`'s `PlatformImpl` intercepted only foreground task posting; worker threads and both clocks stayed with V8's default platform, so `Date.now` could not be faked from Rust. A d8-style predictable platform in the project's `rusty_v8` fork was required. Whether GC-observable behavior (`WeakRef`, `FinalizationRegistry`) was then reproducible was decided by the Stage A determinism probe.

**Q-3 answered (M0, 14 October 2026; history).** Yes, under the fork's predictable platform, which takes over both clocks and all worker tasks. A probe exercising `Math.random`, `Date.now`, allocation, `WeakRef` and `FinalizationRegistry` with embedder-forced GC points gave 1,000 of 1,000 identical hashes in-process and 50 of 50 across fresh processes, in release and debug V8, on macOS arm64, Linux x86-64 and Windows x86-64. **The hashes are identical across the three OSes**, including the full finalization order. The flags alone do not suffice: with V8's stock platform and no flags the probe produced 848 (macOS), 912 (Linux) and 989 (Windows) distinct hashes in 1,000 runs; with `--predictable --single-threaded` it still diverged occasionally (3 of 1,000 debug runs on macOS, 1 of 1,000 release runs on Windows). In release builds the worker-task mode (inline or queued) changes the hash while each mode is stable, so **every recording carries the mode as a mandatory field, and the simulator refuses a recording whose mode is missing or unsupported**. Cross-OS identity is observed for this probe, not guaranteed for all programs. The measurements are retained as evidence of the flag route's limits, not as a requirement.

**Q-4. Does DST find browser bugs at a useful rate?** No browser case exists, and no measured bug-yield numbers for Antithesis or TigerBeetle were found. DST-1 tests it.

**Q-5. Will WebMCP survive its origin trial?** The trial reportedly ends around 17 November 2026 (secondary sources disagree on its start date). Its fate decides how much of B9's tool registry is platform and how much is speculation.

**Q-6. Is engine-enforced provenance filtering a meaningful injection defense?** It bounds reach, but the notes contain no attack-success-rate data from Google or OpenAI, and visibility heuristics are unproven.

**Q-7. Do AI-generated, gated components carry a different defect profile?** The notes found **no measured defect-rate data** for AI-written code in large systems. EQ-1 is designed to produce it.

**Q-8. Did Ladybird's May–August 2026 ports use AI agents and byte-level gating?** **Retired 17 October 2026: Izcal translates no code (M-1).** The newsletters do not say. Only the February LibJS port is documented as AI-assisted. The CSS parser port documents A/B zero-mismatch gating but not the tooling.

**Q-9. How does Servo's 2026 WPT figure compare, and what is its sandbox default?** No official 2026 figure was found, and HGBA-2.0's Q-2 on multiprocess defaults remains open.

**Q-10. How can a user agent disclose an inferred accessible name?** Platform accessibility APIs have no standard "inferred by user agent" property, and screen readers do not announce custom attributes. The options are a suffix on the name or description, which works everywhere but is verbose, or a new property agreed with screen-reader vendors, which is slow. A11Y-3's third arm measures what disclosure costs users.

## Conclusion

HGBA-2.0 found that hardware growth is mostly a broker and standards problem rather than an engine-core one. HGBA-3.0 finds the software analogue: the neglected engine-core frontier in 2026 is **verifiability**, and the algorithms worth adopting are the ones that can be gated. The algorithms a compatible engine needs exist in the specifications; the components that implement them are now Izcal's own. What does not exist anywhere is an engine designed so that cheap code generation can be trusted: deterministic enough to replay, structured enough to gate component by component, and incremental by construction rather than by accumulated invalidation patches. That reframes the question of how a small team can build a browser. The 2026 evidence suggests the limiting resource is no longer engineers writing code. It is oracles, replay infrastructure and reviewers' attention, and an architecture should be judged by how much of each it gives back.

The second implication is strategic. Agentic browsing consolidated onto Chromium in 2026, yet the capabilities agents most need are compact, stable, provenance-tagged observations, enforceable cross-origin limits on what an agent can read and do, and reproducible runs. Those are exactly the things a debug-port architecture struggles to provide and a deterministic, one-copy-DOM-centric engine provides almost for free. If HGBA-3.0 has a defensible reason to exist beside Chromium, it is that one design choice, deterministic and checkable internals, serves both the builders and the agents. And because all of it ships switched off, the same engine is also a browser for people who want no AI at all.
