The evidence as of October 2026 says the *neglected* software frontier for a new browser engine is not a new language, a new GC, a GPU layout engine or a general reactive framework. It is **how an engine is built and checked**. Algorithms still matter (B5 and B6 are algorithmic and load-bearing), but the ones worth adopting are the ones that can be gated against an oracle. Code is now cheap to produce: Ladybird moved about 25,000 lines of its JS frontend from C++ to Rust in about two weeks with zero regressions on 52,898 test262 tests ([Ladybird](https://ladybird.org/posts/adopting-rust/)). Correctness is still expensive: Cursor's agent swarm produced over a million lines of Rust in a week, but JavaScript did not work and no WPT score was ever established ([Simon Willison](https://simonwillison.net/2026/Jan/23/fastrender/)). The gap between those two outcomes is the oracle. HGBA-3.0 therefore proposes an engine whose architecture is shaped so that **every component can be checked against an executable oracle, every run can be replayed deterministically, and every pipeline stage is an incremental function with immutable outputs**. The engine can also emit a semantic, provenance-tagged view of the page that AI agents can use without screenshots. **All AI integration is off by default**: nothing agent-related runs until the user, an administrator or an embedder switches it on. HGBA-2.0's constraints survive: V8 via `rusty_v8`, a `cppgc`-managed DOM, process-per-site isolation, copying Component Model boundaries, and layout tied to the script thread. One is strengthened: the F1 Rust-owned mirror moves from fallback to default, because it is also the natural home for determinism, incrementality and agent snapshots. The honest answer to "don't recreate Servo" is that the evidence still favors using **Stylo, Taffy, Parley, html5ever, WebRender/wgpu and V8** unmodified, as dependencies. Everything else is written new from the specifications (M-1). What is genuinely new is the substrate under them and the process that produces it. None of that substrate has shipped in a browser.

## 1. Vision: from hand-maintained object graph to checkable function of recorded inputs

HGBA-2.0 broke from peak-capability hardware thinking. It described hardware by what a sandboxed process can actually reach, at what fixed cost, with what failure mode. HGBA-3.0 makes the same move for software. Legacy engines are **mutable object graphs maintained by hand**. Dirty bits are walked through the tree, threads and timers are touched directly, correctness is established after the fact by tests and fuzzers, debugging relies on record-and-replay tools bolted on from outside, and automation goes through a debug port. Each of those choices was rational when engineers wrote all the code and the web was smaller. Two facts changed the economics. The web platform is now **more than 2 million WPT subtests** (Servo's denominator was 1,998,146 at the end of 2025, and Ladybird passes 2,088,677) ([Igalia](https://blogs.igalia.com/mrego/servo-2025-stats/); [Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31/)). And AI agents can now generate and translate code faster than humans can review it, provided something mechanical decides whether the output is right.

HGBA-3.0's engine is a **deterministic, incremental function from recorded inputs to outputs**. The inputs are network bytes, user input, clock ticks, random seeds and IPC messages. The outputs are DOM state, computed style, a fragment tree, a display list, a semantic tree and pixels. Determinism makes failures replayable and lets the engine be tested the way FoundationDB and TigerBeetle test distributed databases. Incrementality makes it fast without hand-maintained invalidation sprawl. Immutable phase outputs make it parallel without races on the DOM. Oracles make AI-generated code admissible. The semantic output makes the engine useful to agents, which is the one product dimension where every 2026 competitor is a Chromium fork bolting features onto a debug protocol.

What the vision does not claim matters as much. It does not claim faster page loads than Chromium, a new JS engine, a new GC, or any change to what web content can observe **through the engine's internal design**. The web platform fixes semantics. The engine controls only how it computes them. User-agent interventions that do change what content observes (content blocking, storage partitioning, anti-fingerprinting, permission gating) are policy decisions governed by the P2 scope note in Section 2, not engine design.

## 2. Principles in precedence order

When two principles conflict, the higher one wins, and any exception is recorded in the decision log (Section 9). P1, P2, P4 and P5 carry over from HGBA-2.0. P3 and P6 are new.

| Rank | Principle | Operational meaning | Evidence anchor |
|---|---|---|---|
| P1 | **Security and privacy of the user** | Web content is hostile. Process-per-site, zero ambient authority. **An AI agent is a separate principal, not an extension of the user.** | V8 concluded in-process mitigations cannot fully stop Spectre ([v8.dev](https://v8.dev/blog/spectre)); Google calls an unconstrained agent "a Site Isolation bypass" ([Google](https://blog.google/security/architecting-security-for-agentic/)) |
| P2 | **Web compatibility (unbreakable)** | HTML, CSS, JS and WPT conformance gate everything. No subsetting of the platform, however much faster a subset would be. | Gameface's data-oriented speed depends on supporting only `display: flex` and `none` ([Coherent](https://guide.coherent-labs.com/layout-assets-and-styling/laying-out-the-screen)), which a browser cannot do |

**P2 scope note: user-agent interventions.** P2 governs the engine's behavior on unmodified pages under default settings. A *user-agent intervention* (the term avoids confusion with AI agents) is any browser behavior that changes what content observes or how it behaves, on the user's behalf. Interventions are permitted in three classes only: (a) behavior the platform leaves to user-agent discretion, such as permission prompts, autoplay policy and storage partitioning; (b) overrides the user invokes explicitly, per site or globally; and (c) privacy protections on by default that carry a recorded P1 analysis in the decision log, such as content blocking and anti-fingerprinting. An intervention outside these classes is a P2 violation. Every default-on intervention publishes its compatibility cost (WPT and corpus breakage) per release.
| P3 | **Reproducibility and checkability** | Every engine run can be replayed bit-for-bit in simulation mode. Every component has a named oracle before it is written or replaced. A path that cannot be replayed or checked does not ship by default. | FoundationDB's deterministic simulator replays any failing seed exactly ([FoundationDB](https://apple.github.io/foundationdb/testing.html)); Ladybird's zero-mismatch gating ([Ladybird](https://ladybird.org/posts/adopting-rust/)) |
| P4 | **Robustness and graceful degradation** | Every incremental path has a from-scratch fallback; every accelerated path has a CPU fallback. | Incremental machinery loses on bulk changes ([Spineless Traversal](https://arxiv.org/html/2411.10659v4)) |
| P5 | **Performance and energy** | p95 interaction latency, frame time, memory and energy on a published corpus. | Salsa's main production cost was memory, not time ([Salsa notes](https://hackmd.io/@salsa/SkNtN8Lv1e)) |
| P6 | **Agent-native capability, off by default** | Semantic output for agents, agent principals, tool registries and model hosting are engine features that ship **disabled**. They run only after an explicit switch (B10), are built on P1–P5 and never weaken them. Accessibility for assistive technology is not an AI feature and is never gated by the switch. | Chrome's agent stack is built on Site Isolation and a non-content-reading critic ([Google](https://blog.google/security/architecting-security-for-agentic/)) |
| P7 | **Evidence over aspiration** | Every idea carries a maturity label: **shipped** (in production somewhere), **prototype** (working code, not in production) or **research** (paper or proposal). Vendor and single-source claims are labelled. | — |

**Method constraint M-1 applies to everything in this document.** HGBA-2.0 Section 2 defines **M-1** (original, first-principles, spec-anchored implementation) as a method constraint that is not ranked, so no principle P1–P7 can trade it away. **Original:** no code from another browser or browser engine is copied, ported or translated into Izcal, by people or by AI tools (Stage 1 design D-S10); standalone libraries are used unmodified, as dependencies, through their public APIs, and when a component would otherwise come from another browser, Izcal builds its own from the specifications. **Spec-anchored:** web-visible behavior is implemented from the normative specification at a pinned revision, and every hand-written algorithm carries a spec anchor; where a specification is silent, behavior follows documented interoperability evidence recorded as a black-box observation. **First-principles:** internal architecture that no specification governs is derived from P1–P7 and measured requirements; another engine's design is cited as evidence, never as a template. **Spec-anchored oracles decide correctness:** conformance suites, formal models, spec-derived property tests and Izcal's own reference paths are primary, and other engines are black-box differential signals only.

P3 sits above performance on purpose. The build method in Section 6 depends on it. A faster path that breaks replay is a path whose bugs cannot be reproduced and whose AI-generated replacements cannot be gated, so the speed is not worth having. HGBA-2.0 already applied this logic narrowly: its parallel layout must be bit-identical to the sequential path on WPT reftests. HGBA-3.0 generalizes it to the whole engine.

## 3. What the platform fixes and what the engine is free to change

The most common error in "rethink the browser" proposals is to treat platform semantics as an implementation choice. The evidence draws a sharp line.

### The platform fixes synchronous layout, one event loop per agent, and de facto behavior documented by interoperability work

The web platform requires layout to answer synchronously from script. `getBoundingClientRect`, `offset*`, `scroll*` and `getComputedStyle` all force a style and layout flush ([Paul Irish](https://gist.github.com/paulirish/5d52fb081b3570c81e3a)). Servo, the engine designed around message-passing components, **moved layout onto the script thread in February 2024** because "the web platform almost always requires layout to run synchronously with script" ([Servo](https://servo.org/blog/2024/02/28/gamepads-font-fallback-space-jam/)). The HTML event loop is serial per agent. JS semantics, DOM node identity, mutation ordering, microtask timing and same-origin synchronous access between same-site frames are all observable. Compatibility also goes beyond specs: Interop 2026 has a "web compat" area for real-world breakage such as unprefixing `-webkit-user-select` and ESM loading ([WebKit](https://webkit.org/blog/17818/announcing-interop-2026)). Where specifications are silent, web compatibility requires matching deployed behavior; Izcal takes that behavior from interoperability evidence (WPT results across engines, Interop and web-compat data), records each case in the black-box observation log (M-1), and files it upstream as a specification issue. Spectre is not a platform rule, but it fixes the process model just as firmly.

### The engine is free to change data layout, invalidation, scheduling, determinism and its outputs to embedders

None of the following is visible to web content: how the DOM's style-and-layout inputs are stored, how dirty state is tracked and traversed, whether phase outputs are immutable, how threads are scheduled, whether time and randomness are injected, how IPC is transported, and what the engine emits to its embedder beyond pixels. Chromium itself has moved a long way on these axes without changing web semantics. It has immutable LayoutNG fragments, flat inline item lists, centralized property trees and cached paint chunks ([Chrome](https://developer.chrome.com/docs/chromium/renderingng-data-structures)). That is where HGBA-3.0 innovates.

| Layer | Fixed by the platform (cannot change) | Free inside the engine (HGBA-3.0 changes it) |
|---|---|---|
| Script | JS semantics, V8-class JIT performance expectations, event-loop and microtask ordering | Embedding: injected clock, randomness and task scheduling (Section 4, B1) |
| DOM | Node identity, mutation APIs, GC-visible cycles through JS | Storage of style/layout inputs (Rust data plane, B4) |
| Style | Cascade, selectors including `:has()`, container queries | Invalidation mechanism, sharing, parallelism (Stylo, B5) |
| Layout | Synchronous queries, exact geometry, every formatting context | Incremental scheduling, cache keys, immutable fragments (B5, B6) |
| Rendering | Pixels when a human looks | Whether to paint at all when nobody looks (B7) |
| Isolation | Spectre physics: one process per site | Typed capability channels, simulation transport (B2) |
| Agents | WebMCP if it standardizes; HTTP semantics | Semantic tree, provenance tags, agent principal, snapshot diffs (B8, B9) |

| HGBA-2.0 constraint | HGBA-3.0 position | Why |

### B1. Deterministic runtime substrate

**What it is.** No engine code calls the OS clock, OS threads, OS randomness or sockets directly. All of them go through injectable interfaces with two implementations: production (real OS) and simulation (seeded scheduler, virtual clock, fake network that replays recorded archives with fault injection). The simulation mode runs the whole multi-process browser in one process, with renderers as simulated hosts.

**Evidence.** Deterministic simulation testing (DST) is **shipped** in distributed databases. FoundationDB runs whole clusters in a single-threaded deterministic simulator where any failing seed replays exactly ([FoundationDB](https://apple.github.io/foundationdb/testing.html)). TigerBeetle's VOPR injects network, storage and clock faults with time acceleration ([TigerBeetle](https://github.com/tigerbeetle/tigerbeetle)). Antithesis, a deterministic hypervisor for unmodified software, raised a **$105M Series A in December 2025** ([PR Newswire](https://tools.prnewswire.com/en-us/live/20813/release/20251203EN37581)). Rust has two shipped DST libraries: madsim replaces tokio and std time, network and RNG, and turmoil simulates hosts and networks in-process ([madsim](https://github.com/madsim-rs/madsim); [turmoil](https://github.com/tokio-rs/turmoil)). A multi-process browser has the same shape as a small distributed system: processes, IPC, network and timers. The HTML event loop is already specified as task queues, so a seeded scheduler can explore exactly the interleavings the spec permits.

**Maturity.** Shipped in databases. **Research for browsers**: the notes found no published case of DST applied to Servo, Ladybird, Chromium or Gecko.

**Replaces.** Direct `std::time`/thread/RNG use and after-the-fact record/replay (`rr`, which Mozilla uses heavily for Firefox debugging) ([rr](https://rr-project.org/)). `rr` stays as a tool for the parts B1 cannot cover.

**This is the document's biggest bet and its least evidenced.** No browser has done it. V8's determinism, the largest unknown, is now answered for the JS layer (Q-3: deterministic under the fork's platform on all three desktop OSes), and GPU, audio and media sit outside the simulator. If DST-1 fails, the thesis survives, because it rests on oracle gating, which is shipped (Ladybird) and independent of DST; B1 then remains for replay and agent snapshots. What does *not* survive is the claim that HGBA-3.0 is simulation-tested end to end, which would shrink to "replayable".

**Risk.** The notes are blunt: DST must be designed in from day one, and **retrofitting it is very hard**. That is the strongest argument for building this substrate new rather than inheriting Servo's threading. Three sources of nondeterminism sit outside the engine's control. V8's GC and JIT tiering timing, the GPU and compositor threads, and audio and media pipelines all need either embedder hooks or Antithesis-style whole-VM determinism. Whether V8 can run reproducibly under an injected platform and clock is **not established in the notes** (open question Q-3). The indirection also has a runtime cost, which target DET-2 bounds.

### B2. Typed capability channels with a simulation transport

**What it is.** All inter-process communication uses typed, sequence-affine endpoints generated from an IDL. Holding an endpoint is the authority to call it. One transport abstraction has two backends: OS IPC with shared memory, and in-process simulated delivery under B1's scheduler. Synchronous calls are allowed only where the platform forces synchrony, and policy discourages them elsewhere.

**Evidence.** Chromium's Mojo is **shipped** evidence that typed capability IPC works at browser scale; it is not a template, and B2's design is derived from first principles (P1, P3) and the OS IPC documentation. Pipes and interfaces generated from `.mojom` bind to a sequence, and the docs discourage `[Sync]` calls because they block and invite re-entrancy and deadlock ([Mojo](https://chromium.googlesource.com/chromium/src/+/main/mojo/public/cpp/bindings/README.md)). Mojo endpoints are unforgeable handles, which makes Mojo capability-like ([Mojo README](https://chromium.googlesource.com/chromium/src/+/main/mojo/README.md)). OpenAI's Atlas ran Chromium out of process behind Mojo with custom Swift bindings, which shows Mojo-style boundaries also serve embedders ([OpenAI](https://openai.com/index/building-chatgpt-atlas)). The turmoil model shows the simulated-transport half ([turmoil](https://github.com/tokio-rs/turmoil)).

**Maturity.** Typed capability IPC: shipped. Simulated browser IPC: research.

**Replaces.** HGBA-2.0 originally reused Servo's constellation for navigation and pipeline management. Izcal instead implements navigation in **`hg-navigation`**: navigables, session history and the navigation algorithms, derived from the HTML specification's navigation and session-history sections, over B2's transport so that it runs under simulation. Servo's constellation (cited here as history) was "historically designed for parallel, message-passing components" ([Servo wiki](https://redirect.github.com/servo/servo/wiki/Transcription---Notes-from-Servo-Architecture-talk-in-Suwon)), not for determinism.

**Risk.** Moderate. The design is proven. The cost is building plumbing that other engines already have. The notes contain no per-message cost figures for Mojo or Servo's constellation.

### B3. Two schedulers: sequences for the event loop, fork/join for phases

**What it is.** I/O, navigation and the event loop run on serial *sequences*, one per agent cluster, with structured cancellation of fetches, navigations and workers. CPU-bound pipeline phases (style, layout, raster preparation, semantic tree) use Rayon-style work-stealing fork/join. The two never share executor threads.

**Evidence.** All of it is **shipped**. Chromium tells its engineers to "prefer sequences to physical threads" ([Chromium](https://chromium.googlesource.com/chromium/src/+/main/docs/threading_and_tasks.md)). Servo still parallelizes layout with worker threads after moving layout onto the script thread ([Servo](https://servo.org/blog/2024/02/28/gamepads-font-fallback-space-jam/)). Structured concurrency is mainstream in Swift, Kotlin and Python, but Java's API is still in its **sixth preview** in JDK 26 ([JEP 525](https://openjdk.org/jeps/525)). Swift 6.2 moved defaults back toward main-actor isolation because unrestricted concurrency produced too many data-race diagnostics ([InfoQ](https://www.infoq.com/news/2025/08/swift62-approachable-concurrency)). That is evidence that "concurrent by default" has costs. In Rust, async fn in traits is stable but not `dyn`-compatible, and the 2026 project goal only aims to *settle a design* ([Rust goals](https://rust-lang.github.io/goals/2026/afidt-box.html)).

**Maturity.** Shipped.

**Replaces.** Thread-per-component designs and fine-grained actors on hot paths. Actors stay coarse: process, document, agent cluster and service.

**Risk.** Low. Embedder and plugin interfaces must avoid `dyn` async traits until at least 2027, or accept a boxed allocation per call. Rayon's scheduling is nondeterministic, so determinism must come from **phase purity**: workers read immutable inputs and write disjoint outputs, so the result does not depend on interleaving. Target DET-1 tests this.

### B4. `cppgc` DOM plus a Rust data plane (F1 mirror as default)

**What it is.** The DOM, its bindings and all JS-reachable objects live in `cppgc`, exactly as HGBA-2.0 requires. The script thread maintains a Rust-owned **data plane**: dense, generational-index storage of exactly what style, layout and the semantic tree read. That covers tree links, tag, attributes, classes, state flags, the inline-style declaration reference and a stable node ID. DOM mutations append to a log. The log is applied at the start of every style or layout pass, including every forced synchronous flush. Script never reads the data plane. Workers never touch `cppgc` memory. HGBA-2.0's F1 contract (closed log during flush, atomicity by structural quiescence, debug and Nightly cross-checks) carries over unchanged.

**Evidence.** The pattern of identity in one place and dense per-subsystem storage keyed by that identity is shipped in UI stacks. Bevy splits user-set `Node` inputs from `ComputedNode` results and maps entities to Taffy node IDs through a side table (secondary source, [DeepWiki](https://deepwiki.com/bevyengine/bevy/6.1-window-system)). Taffy stores nodes in a generational `SlotMap` and exposes trait-based tree access so embedders can run its algorithms over their own tree ([Taffy](https://github.com/DioxusLabs/taffy/blob/main/src/tree/taffy_tree.rs)). Blitz runs Stylo over its own `NodeId`-indexed arena DOM, storing Stylo's `ElementData`, `SnapshotMap` and `Stylist` alongside it ([blitz-dom](https://github.com/DioxusLabs/blitz/blob/main/packages/blitz-dom/src/document.rs)). That is direct evidence that Stylo's `TElement` traits can be implemented over a non-Servo, index-based tree, which the data plane needs.

**Why promote F1 to the default.** HGBA-2.0 preferred letting workers read `cppgc` objects directly inside no-GC scopes, with F1 as a fallback. HGBA-3.0 reverses that preference for four reasons, none of them about GC. First, B1 needs a serializable boundary between script and the rendering pipeline, and the mutation log is that boundary: replaying the log reproduces style and layout without replaying JS. Second, B5 needs explicit, enumerable inputs with stable identities, and Adapton's results show incremental computation pays only when the program supplies stable names ([Nominal Adapton](https://ar5iv.labs.arxiv.org/html/1503.07792)). Third, B8 needs stable node IDs that survive mutation, and the data plane's generational IDs are exactly that. Fourth, it removes the threading risk HGBA-2.0 called its largest integration hazard. The spike has since shown that the hazard can be managed (HGBA-2.0, Section 6: items 1–2 pass under a guard of a blocked heap owner holding both GC scopes on a heap with no compactable spaces), so this fourth reason is now a simplification rather than a necessity. The first three reasons decide the default.

**Maturity.** The pattern is shipped in non-browser UI stacks. **Prototype** for a browser with JS: no browser in the notes runs it.

**Replaces.** Workers reading DOM objects directly (Servo's model and HGBA-2.0's primary path).

**Risk.** Memory and mutation cost are **measured on a toy DOM, not on a renderer**. No external study of arena versus pointer DOM memory or cache behavior was found. Spike item 6 built a corpus-shaped toy DOM (40 tags, about 4 attributes per element, 104-byte `cppgc` nodes) and measured the data plane at **about 150–175 B per node**, which is **26–28% of toy DOM plus data plane** (the toy DOM itself is about 430–440 B per node: about 130–140 B in the `cppgc` heap and about 300 B of Rust-side allocations). **Attributes are about 60% of the data plane**, even though attribute strings are shared with the DOM rather than copied; a design that copied them would cost more. A log append costs about 4.5 ns. A flush costs 42–125 ns for 1 mutation, 4.4–14 µs for 100 and 0.52–1.39 ms for 10,000. Projection plus the equality check takes 0.10, 1.46 and 21.8 ms at 1k, 10k and 100k nodes, and it caught a deliberately unlogged mutation. Target INC-3 bounds the combined overhead against total renderer memory, which the spike did not measure: the ≤10% target holds only if a real renderer uses at least about **1.5–1.75 KB per DOM node** in total. If it uses less, attribute storage is trimmed first: interned attribute arenas, or mirroring only the attributes that selectors actually read. Consistency between DOM and data plane is a new bug class, contained by HGBA-2.0's debug and Nightly cross-checks and by B1 replay.

### B5. Incremental core: specialized invalidation, not a general dependency graph

**What it is.** Each pipeline stage is a pure function over explicit inputs with memoized outputs and **early cutoff**: if recomputation yields the same value, downstream work stops. Concretely:

Style keeps **Stylo's own invalidation and sharing machinery** (rule tree, style-sharing cache, snapshot-based restyle). Layout becomes `layout(node, constraint_space) → immutable fragment`, cached by constraint space. The constraint space is derived from the CSS Sizing and CSS Fragmentation specifications (available size, percentage resolution size, fragmentainer and break state); LayoutNG is cited below as evidence that such a cache works, not as the design. Dirty layout work is scheduled through an **order-maintained priority queue** rather than a dirty-bit tree walk, as in Spineless Traversal. Inputs carry Salsa-style **durability tiers**: UA stylesheets and fonts are high, author stylesheets medium, and DOM attributes and hover state low. Validation can then skip whole subgraphs whose inputs have not changed. A **bulk fallback** switches to from-scratch parallel recomputation for initial load, large `innerHTML` writes, stylesheet swaps and lazy-load insertion bursts. Forced synchronous queries become **demand-driven**: `getBoundingClientRect` computes only the fragments the answer depends on, if the cache can prove the rest is clean.

**Evidence.** LayoutNG is the **shipped** proof that layout as a memoized function works at web scale. It stores the parent constraint space with each fragment as a cache key, and its redesign fixed under-invalidation bugs, "hysteresis" (non-idempotent layout) and exponential two-pass grid layout ([Chrome](https://developer.chrome.com/docs/chromium/layoutng)). Blink's style invalidation sets are deliberately conservative and applied lazily, because exact rule-to-element dependencies are too costly to track ([Chromium](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/core/css/style-invalidation.md)). Spineless Traversal (**research**, PLDI 2025) replaces the "double dirty bit" walk that all major engines use. It was faster on **83% of 2,216 frames** from 50 real sites, with a **1.80× mean** speedup, captured with a modified Ladybird ([PLDI 2025](https://pldi25.sigplan.org/details/pldi-2025-papers/73/Spineless-Traversal-for-Layout-Invalidation)). Salsa (**shipped** in rust-analyzer) contributes durability and backdating. Fixing one durability misconfiguration cut a query from about 64 ms to about 14 ms ([rust-analyzer](https://git.joshthomas.dev/language-servers/rust-analyzer/src/commit/be967b94e15f238a6fe806e93359e302c43d0e45); [Salsa book](https://salsa-rs.github.io/salsa/reference/algorithm.html)).

**Why not a general framework.** The evidence against a general per-field dependency graph is consistent. Salsa's 3.0 migration left **a 250 MB memory regression** in rust-analyzer after optimization ([Salsa notes](https://hackmd.io/@salsa/SkNtN8Lv1e)). Classic Adapton is "sometimes orders of magnitude slower than from-scratch computation" ([Adapton](https://ar5iv.labs.arxiv.org/html/1503.07792)). Differential dataflow state grows without bound unless compacted ([Materialize](https://materialize.com/blog/managing-memory-with-differential-dataflow/)). A browser with millions of nodes and hundreds of properties per node cannot afford one tracked cell per (element, property). TC39 Signals is still **Stage 1**, and no engine uses signals internally ([TC39](https://github.com/tc39/proposal-signals)). No production browser is built on a general incremental framework.

**Maturity.** Constraint-keyed layout caches and Stylo invalidation: shipped. Ordered dirty queues: research. Durability tiers in a browser: research (shipped in rust-analyzer). Demand-driven forced flush: research.

**Replaces.** Dirty-bit tree walks and per-feature hand-written invalidation sprawl in layout.

**Written against traits, not a store.** The driver calls `layout(node, constraint_space)` through tree-access traits and never knows which implementation backs them. The backing store (data plane, or `cppgc` DOM under D8's fallback) is therefore a configuration choice, not a rewrite, and the same property is what makes the dual-implementation oracle possible (Section 6). Like B1's injectable runtime, this cannot be added later.

**Risk.** High, and specific. Spineless was **slower on 17–25% of frames**, about **2× slower on bulk insertion**, and its prototype covered only about 50 layout fields in about 700 lines of a DSL, "only a subset of HTML and CSS" ([arXiv v4](https://arxiv.org/html/2411.10659v4)). Its headline numbers also differ across paper versions (1.80× and 83% at PLDI, 3.23× and 78.2% in an earlier arXiv version). The features where research coverage stops are exactly the hard ones: out-of-flow positioning, fragmentation, `:has()`, container queries and anchor positioning. Out-of-flow descendants and fragmentation break state are exactly the inputs that the CSS Positioned Layout and CSS Fragmentation specifications let escape a box's own constraints. Each of those features therefore needs explicit non-tree edges or a conservative fallback, and P2 forbids shipping the incremental path where it disagrees with from-scratch output.

### B6. Data-oriented phase outputs, shared-struct computed style

**What it is.** Data-oriented layouts go where work is homogeneous and identity is not JS-visible. That means **phase outputs**: the immutable fragment tree, flat inline item lists, property trees, paint chunks and animation state. The property trees and their kinds are derived from the effects the specifications define: CSS Transforms (transforms and 3D contexts), CSS Masking (clips), Compositing and Blending and Filter Effects (opacity, blend, filters), CSSOM View and CSS Overflow (scrolling). Paint chunks are runs of display items in the stacking and painting order of CSS 2 Appendix E. Computed style stays in Stylo's pointer-shared style structs.

**Evidence.** Chromium already ships these patterns, which is evidence that they work at web scale, not a template (M-1). Fragments are immutable with no upward references. Inline formatting contexts are flat depth-first lists with descendant counts. Property trees are cheaper to send across threads and processes than DOM state ([Chrome](https://developer.chrome.com/docs/chromium/renderingng-data-structures)). The strongest data-oriented speedup on record is Coherent Labs' **6.12× on animation ticks** against Chromium 66. That is a 2018 vendor conference claim for one subsystem, in an engine that supports only flexbox ([Nikolov, Meeting C++ 2018](https://meetingcpp.com/mcpp/slides/2018/Data-oriented%20design%20in%20practice_Nikolov_MeetingCpp18.pdf)). It shows where data-oriented design helps, which is homogeneous per-frame work, and why the whole-engine version is not available to a compatible browser. Stylo's memory model works through sharing at three levels: the style-sharing cache, the rule tree and shared style structs ([Mozilla Hacks](https://hacks.mozilla.org/2017/08/inside-a-super-fast-css-engine-quantum-css-aka-stylo/)). Storing about 500 properties as separate columns per element would replace pointer sharing with copies, or reintroduce sharing through interned indices, which rebuilds the struct model with an extra indirection.

**Maturity.** Shipped (Chromium). Animation SoA: shipped in a non-compatible engine (vendor claim).

**Replaces.** Mutable per-object layout boxes and paint objects.

**Risk.** Low for phase outputs. **Per-property SoA for computed style is rejected** (non-goal).

### B7. Rendering: HGBA-2.0's path plus pixel-optional rendering

**What it is.** HGBA-2.0's rendering plan stands: WebRender in Stage 1, Vello Hybrid evaluated in Stage 2, and wgpu in a GPU service. HGBA-3.0 adds **pixel-optional rendering**. A tab no human is watching runs style, layout and the semantic tree, because geometry and visibility are needed. It skips paint, raster and compositing until a screenshot is requested.

**Evidence.** Vello Hybrid is "roughly beta quality" ([Linebender Q1 2026](https://linebender.org/blog/tmil-25/)), and an open issue reports it rendering old.reddit.com slowly ([vello#1380](https://github.com/linebender/vello/issues/1380)). The notes found **no product running selector matching, cascade or general layout on the GPU**. The likely reasons (this document's explanation, not a sourced finding) are that selector matching is branchy and data-dependent per element, per-node work is tiny, the cascade and layout have parent-before-child and sibling dependencies (line breaking, floats), and text shaping runs on the CPU, all of which map poorly to GPU SIMT execution. That makes it a current constraint for general CSS, which restricted subsets might relax. Vello itself moved partly *back* to the CPU for device coverage and memory pressure ([Vello sparse strips](https://skia.googlesource.com/external/github.com/linebender/vello/+show/de2b7514d80964598a2ebc99ff209b1fbb291d92/sparse_strips/README.md)). Demand for render-free engines is real. Lightpanda handles DOM and JS with no rendering, specifically for automation and agents. Its vendor claims about 11× speed and 9× less memory than Chrome, which is unverified ([linuxiac](https://linuxiac.com/?p=209081)).

**Maturity.** Pixel-optional mode in a full engine: prototype-level idea. Headless-only engines: shipped.

**Replaces.** Always-on rendering for background and agent tabs.

**Risk.** Low technically. The notes contain **no data quantifying wasted rendering cost for agents**, so the benefit must be measured (target AG-4).

### B8. Semantic plane: the accessibility tree as a first-class pipeline output

**What it is.** The engine computes a semantic tree in the core pipeline, next to layout and from the same data plane. Each node carries a **stable ID across mutations**, role, name, state, bounding box, **origin and frame provenance**, and **human-visibility flags** (contrast, size, occlusion, off-screen). The tree is served as full snapshots at quiescent points and as **incremental diffs** between them. It feeds platform accessibility APIs and agents from one source.

**Evidence.** Chrome ships "DevTools for agents" that exposes accessibility trees, console and network to 20+ coding agents ([Chrome I/O 2026](https://developer.chrome.com/blog/chrome-at-io26)). That shows the a11y tree is already an agent interface, but one reached through a debug protocol. A combined accessibility tree, HTML and screenshot observation in BrowserGym can **exceed 20,000 tokens** ([arXiv 2606.06708](https://arxiv.org/pdf/2606.06708)). WebArena scores vary **20–30 points with the scaffold alone** ([benchmarkingagents](https://benchmarkingagents.com/best-benchmarks-for-browser-agents/)), so the observation interface is a first-order variable in agent success. Brave showed that text invisible to humans, such as faint text in screenshots, reaches the model as instructions ([Brave](https://brave.com/blog/unseeable-prompt-injections/)). That is the case for visibility flags.

**Maturity.** A11y tree exposed to agents: shipped (via DevTools). Stable-ID diffs, provenance tags and visibility flags: **research/proposal**. The notes found them shipped nowhere.

**Replaces.** CDP scraping of DOM snapshots plus screenshots.

**Repair overlay.** The semantic plane has two layers. The **author tree** is computed exactly as HTML-AAM and accname specify, and the reference-engine differential and WPT check it. The optional **repair overlay** is a sparse map keyed by stable node ID, holding accessibility repairs of classes R1–R4 (B10). Each entry records its class, rule, source nodes and provenance. The overlay never feeds back into the DOM, style, layout or the data plane, which target A11Y-1 checks bit for bit. A repair may draw text only from nodes with the **same origin and frame** as the repaired node (A11Y-1b). Agent observations use the author tree; a repaired value reaches an agent only with a `repaired` provenance tag, because heuristic names promote attacker-controlled strings such as file names and URLs into trusted-looking labels. A user-facing inspector lists every repair on the page, and one toggle reverts them all. No browser offers a whole repaired tree the user can switch to and from; Chrome (2019) and Edge (2022) insert generated image descriptions with an on/off control, and the Legato browser ships rule-based repairs with no published user evaluation.

**Risk.** The tree's quality depends on page authoring quality, which the engine cannot fix. Visibility heuristics will have false negatives that attackers probe. The notes found **no matched study of a11y-tree versus screenshot accuracy** in 2026. Repairs that reduce checker-detected violations can still harm users, because a wrong name is worse than a missing one; no checker-based gate is presented as evidence of benefit. The accessibility tree is security-sensitive: CVE-2026-95301 let a compromised renderer read cross-origin accessibility data while a `chrome.automation` consumer was running (fixed in Chrome 154), so repair logic runs in the renderer on renderer-local data, never as a browser-process aggregation across origins.

### B9. Agent principal, origin capabilities and a tool registry

**What it is.** An agent is a principal with its own capability set inside the browser broker. It holds per-task **read-only and read-write origin sets**, enforced by the engine, and bounded by the **container** it runs in (Stage 1 design, Section 6): a container can forbid agents entirely, or cap them at read-only. Content from origins outside the set is never placed in the agent's observation, and that rule is enforceable because B8 tags provenance. It also gets an isolated storage partition, a trusted, non-spoofable confirmation surface for payments, credentials and messages, deterministic detection of sensitive forms, and a tamper-proof action log. A native **WebMCP-compatible tool registry** lets sites declare tools, and the engine prefers declared tools, then the semantic tree, then pixels.

**Evidence.** Google **ships** the core of this in Chrome's agent: a User Alignment Critic that sees action metadata but never raw web content, and Agent Origin Sets split into read-only and read-write. At initial rollout **only the read-write set is enforced** ([Google](https://blog.google/security/architecting-security-for-agentic/)). Brave runs its agent in an isolated profile with a second reviewing model, and states that the safeguards "do not eliminate risks such as prompt injection" ([Brave](https://brave.com/blog/ai-browsing/)). OpenAI frames injection as an ongoing arms race ([OpenAI](https://openai.com/index/hardening-atlas-against-prompt-injection)). WebMCP is a **prototype**: `document.modelContext.registerTool`, with cross-origin frames gated by `allow="tools"`, entered a Chrome 149 origin trial ([WebMCP](https://github.com/webmachinelearning/webmcp); [Chrome I/O 2026](https://developer.chrome.com/blog/chrome-at-io26)). A federal court enjoined Perplexity's Comet from Amazon in March 2026, separating user permission from platform authorization, after Amazon alleged Comet disguised itself as ordinary Chrome ([GeekWire](https://www.geekwire.com/2026/03/10/judge-blocks-perplexitys-ai-bot-from-shopping-on-amazon-in-early-test-of-agentic-commerce/)).

**Maturity.** Origin sets and critic: shipped in Chrome (partially enforced). WebMCP: prototype. Provenance-enforced observation filtering and honest agent identification: research/proposal.

**Replaces.** Agents as privileged extensions or CDP clients with ambient access to every origin.

**Risk.** WebMCP may change or die after its origin trial, so the registry must track the spec, not get ahead of it. **Engine enforcement does not solve prompt injection.** It bounds what an injected agent can reach, the way site isolation bounds a compromised renderer.

### B10. AI integration is off by default

**What it is.** Every AI capability in B7–B9 and Section 7 ships switched off. "Off" is defined by what does not happen, so it can be tested:

- **No agent processes.** The agent host and on-device model host are never launched. Agent code lives in separate crates and a separate service process, so "off" means not loaded, not merely hidden in the UI.
- **No models.** No model is downloaded or loaded. Built-in AI web APIs such as the Prompt API report the spec's "unavailable" state, which is an ordinary outcome sites already handle.
- **No AI network traffic.** No requests to any model or agent endpoint, and no AI-related telemetry.
- **No agent-only computation.** Provenance export, stable-ID semantic diffs, visibility flags for agents and pixel-optional agent tabs are not computed.
- **Inert, not missing, web surface.** If WebMCP ships as a standard, `document.modelContext.registerTool` still succeeds but no agent ever calls the tools. Removing the API would break sites and give fingerprinters a signal that the user has AI off.
- **No AI entry points or promotions in default UI.** With the switch off, the new-tab page, address bar, menus, context menus and onboarding show no AI buttons, chips, suggestions or nudges to turn AI on. The settings page that holds the switch is the only place AI appears. This is the case Chrome's "Do more with AI" new-tab chips show: a feature can download nothing and still be an AI pain point.
- **Off survives updates.** No update, settings migration or profile sync may switch AI on or show a re-prompt. A choice is changed only by the user or by enterprise policy. Firefox's AI controls were explicitly designed so choices "persist across updates" ([Mozilla](https://blog.mozilla.org/en/firefox/ai-controls/)).

**Boundary cases, decided in advance so that AG-0 neither fails on a legitimate model nor lets a surprise through by reclassification.** Chrome justified its silent 4 GB Gemini Nano download after the fact as powering scam detection ([That Privacy Guy](https://www.thatprivacyguy.com/blog/chrome-silent-nano-install/)), which shows why the rules must exist before the first model does.

- **Security classifiers.** A non-generative ML classifier used for a security feature (for example phishing or malware detection) is **not** governed by B10 only if it meets all of the following. It ships inside the signed browser package or its normal update, and is never downloaded separately. It stays below **50 MB†**. It makes no network requests beyond the security feature's existing protocol. And it is listed in a published **ML inventory** that states its purpose, size and inputs. The inventory is empty at 3.1.0. Adding an entry needs a decision-log record and is reported in the release notes. Anything generative, anything larger, and anything downloaded on demand counts as AI and is off by default. **The phishing spec does not use this carve-out**: its reputation list is URL data compiled into a signed bundle, not an ML classifier, and the list's model is PH-D2's; a non-MIT feed is test-only (PH-D14).
- **Rule-based accessibility repairs are not AI, but not all are on by default.** No accessibility repair is gated by the AI switch (P6). The default depends on whether a repair invents content and whether content can observe it:
  - **R0, OS preferences.** Forced colors, contrast and other OS accessibility preferences follow the OS setting and are exposed to content exactly as the specs require (for example the `forced-colors` media query). They are not normalized by anti-fingerprinting, because hiding them trades usability for anonymity on behalf of the users who depend on them.
  - **R1, AT-only language hint.** A document-language hint taken only from deterministic sources (`Content-Language`, an ancestor frame's `lang`, the UI locale), exposed only to platform accessibility APIs and never written to the DOM. **On.** Language *detection* from page text uses a classifier, which makes it an ML-inventory entry, not R1.
  - **R2, heuristic names and roles** for unlabeled controls (from URLs, file names, `title`, adjacent text). They invent content and can be wrong. **Off by default**; one accessibility setting turns them on, with per-site override; they live in B8's repair overlay, are listed in the inspector and revert with one toggle. They become default-on only by a decision-log record after A11Y-3 passes.
  - **R3, structural repairs** (focus order, keyboard traps, headings). They change focus events and behavior that content observes, so they are **user-invoked per site only**.
  - **R4, model-based repairs**, as below.
- **Model-based accessibility repairs have their own opt-in.** Machine-generated alt text and similar repairs need a model. They sit behind a separate accessibility setting — **the accessibility model grant, a grant with a model set (S_A) defined by ML-D4** — not the AI switch, and that setting is also off by default. **S_A is image description and OCR, plus captions only if the owner answers Q-ML-1 yes, in which case ML-ASR moves under this grant.** Turning it on downloads a local, on-device model only at that moment, following Firefox's local design rather than a cloud call ([Mozilla Hacks](https://hacks.mozilla.org/2024/05/experimenting-with-local-alt-text-generation-in-firefox-nightly/embed/)), and **disabling the grant deletes every model it downloaded, unconditionally** — B10's "unless the user chooses to keep them" is replaced for this grant, because ML-9 needs the exact default state; the keep option remains for AI-grant models in Stage 2. Every generated label is recorded in the repair overlay as machine-generated and disclosed to the user by a mechanism decided under Q-10, and the user can dismiss or report it. Turning on the accessibility setting enables no agent features, and turning on the AI switch does not enable the accessibility model: **the two are independently testable** (ML-D4). The browser describes these repairs as an aid to the user, never as making a site compliant, which is the line the FTC drew in its accessiBe order ([FTC](https://www.ftc.gov/news-events/news/press-releases/2025/04/ftc-approves-final-order-requiring-accessibe-pay-1-million)). **R0–R3 are unchanged.**
- **Accessibility unaffected.** The accessibility tree for screen readers and other assistive technology works exactly the same with the switch off. B8's shared tree is computed whenever assistive technology needs it; only its agent-facing extras depend on the switch.

**How it is switched on.**

- **Users** turn it on per profile in settings, with a plain-language description of what an agent can do.
- **Embedders** turn it on by configuration in agent-runtime builds (headless or cloud-hosted). That is the positioning Section 7 recommends, and the build records the setting in its logs.
- **Administrators** can force it off and lock it through enterprise policy, **and may force off and lock either the AI switch or the accessibility grant**; neither can be forced on (ML-D4).

Switching on does not grant an agent anything by itself. Every agent task still starts with **empty origin sets**, and the user grants origins per task (B9); **an agent navigation, document fetch or download to a phishing-listed URL is refused with a typed error, never warned and never overridable** (phishing PH-D8). Switching off tears down the agent host and deletes agent storage partitions. Downloaded AI-grant models are deleted unless the user chooses to keep them; **accessibility-grant models are always deleted when that grant is disabled** (ML-D4).

**Evidence and maturity.** This is a product and policy decision, not a technology claim. Its cost is small because B9 already makes the agent a separate principal behind the broker. Maturity: design choice; the AG-0 target verifies it.

**Replaces.** AI features that load or contact services by default and are hidden behind UI toggles.

**Risk.** Agent features get less real-world use, and so less feedback, than they would if enabled by default. HGBA-3.0 accepts this: under P1, an agent that can act on the user's behalf across origins is a capability the user opts into, not one they must find and disable.

## 5. Dependencies versus built new: specifications are the oracle

Izcal has two kinds of component, and only two. **Dependencies** are standalone libraries used **unmodified, through their public APIs**: V8 (through the `rusty_v8` fork), Stylo, html5ever, WebRender, Taffy, Parley, wgpu and AccessKit, among others (M-1). Fixes go upstream. **Everything else is written new from the specifications** (WHATWG, W3C, TC39, IETF, Khronos, Unicode) at a pinned revision, with spec anchors (ANC-1). There is no third kind: no other engine's code is copied, ported or translated in (Stage 1 design D-S10), and Izcal has no predecessor of its own to translate.

**A dependency is never replaced step by step by translating it.** If Izcal ever replaces one, the replacement is written from the specification and gated by spec oracles (pinned WPT and test262, formal models, spec-derived property tests), plus differential testing against the dependency it replaces. That dependency is then used as a black-box oracle on the same inputs, which M-1 allows; its source is not the template. The 2026 replacements that succeeded show why the gate matters: Ladybird's Rust LibJS produced byte-identical ASTs and bytecode against the C++ one ([Ladybird](https://ladybird.org/posts/adopting-rust/)), its Rust HTML parser was checked for DOM parity on about 7,000 sites ([Ladybird May 2026](https://buttondown.com/ladybird/archive/this-month-in-ladybird-may-2026/)), and its CSS parser port deleted C++ only after zero A/B mismatches per grammar family ([Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31/)). Those were translations of Ladybird's own code, a method Izcal does not use. What carries over is the evidence that **a mechanical oracle, not the author, decides whether a replacement is right**. A new engine with no mechanical oracle is in FastRender's position.

| Component | Decision | Reason | Evidence |
|---|---|---|---|
| JS + Wasm engine | **V8 as a dependency** via `rusty_v8` (the fork's changes are written against V8's public interfaces) | Speed gap is largest here; pure-Rust engines lack JITs; V8 sandbox | Ladybird SP3 ~3.9 ([Ladybird](https://ladybird.org/newsletter/2026-08-31/)); HGBA-2.0 D2 |

**Where the evidence says build new rather than depend.** Building new wins in three places, in addition to everything no dependency covers. The first is substrate that cannot be retrofitted: determinism and simulated IPC, where the DST literature is explicit. The second is architecture that has to be designed in from the start: immutable outputs, constraint-keyed caches and stable identities. LayoutNG needed a full rewrite to fix hysteresis and under-invalidation, and Chrome did that rewrite rather than patch ([Chrome](https://developer.chrome.com/docs/chromium/layoutng)); that is evidence for designing these properties in, and Izcal derives its own from the CSS specifications. The third is capability with no incumbent: the semantic plane and the agent principal, where every 2026 agent product is a Chromium fork with no published engine change except Atlas's out-of-process wrapper ([OpenAI](https://openai.com/index/building-chatgpt-atlas)).

**Where it does not.** Building new loses on the JS engine, the cascade, flex and grid, text shaping, the HTML parser and rasterization. In each of those a shared, shipped standalone library exists that Izcal can use unmodified as a dependency, and Blitz shows the composition works ([Blitz](https://cdn.jsdelivr.net/gh/dioxuslabs/blitz@main/README.md)). History is unkind to engines that rebuild compatible commodity parts. **Opera abandoned Presto in 2013** to "focus on what's valuable rather than building something in parallel" ([TidBITS](https://tidbits.com/2013/05/30/opera-releases-chromed-preview-of-next-browser/)), and **Microsoft abandoned EdgeHTML in 2018** for web compatibility ([9to5Google](https://9to5google.com/2018/12/06/microsoft-confirms-chromium-edge/)). Both had hundreds of engineers. Even FastRender's agents chose Skia, HarfBuzz, Taffy and QuickJS over writing their own ([Simon Willison](https://simonwillison.net/2026/Jan/23/fastrender/)).

## 6. How the engine gets built

### AI-assisted development: spec-to-code, gated by spec oracles

**Spec-to-code is the only route.** Izcal has no predecessor to translate and translates no other engine's code (M-1, Stage 1 design D-S10). Agents are given the pinned specification text and Izcal's own code, and generate **step-numbered skeletons** from the specification algorithm: each function carries the spec anchors of the steps it implements, and humans review and complete it. WHATWG and TC39 specifications are written as step-by-step algorithms, which suits skeleton generation with step-number comments. But no machine-readable semantics of the HTML parser or DOM exists, so **correctness must come from the oracles, not the model**.

**Why mechanical oracles matter: the 2026 evidence.** Oracle-gated work ships; ungated generation does not. Ladybird's LibJS port, a translation of its own C++, was human-directed through "hundreds of small prompts", reviewed in multiple adversarial passes by different models, and checked with byte-identical ASTs and bytecode, **0 regressions on 52,898 test262 tests and 12,461 regression tests**, and a lockstep mode comparing both pipelines during real browsing ([Ladybird](https://ladybird.org/posts/adopting-rust/)). Cursor's FastRender swarm had only screenshot diffs and the compiler as feedback, and JavaScript never worked ([Simon Willison](https://simonwillison.net/2026/Jan/23/fastrender/)). Izcal uses neither method: it cites them only as evidence that the oracle, not the generator, decides the outcome. The best controlled productivity study found experienced developers **19% slower** with AI while believing they were 20% faster ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Google's "75% of new code is AI-generated" is self-reported and "pretty impossible to fact-check" ([Semafor](https://www.semafor.com/article/04/24/2026/google-ceo-says-75-of-companys-new-code-is-ai-generated)).

**The honest risk.** Spec-to-code has weaker oracles than translation: there is no earlier implementation to compare byte for byte, and the notes found no measured public case of an agent building a conformant browser subsystem from a specification alone. That is why the **spec** oracle class is mandatory (EQ-1): every component that implements web-visible behavior is gated by a pinned conformance suite, a formal model or spec-derived property tests, and a reference-engine differential is never its only oracle.

HGBA-3.0 therefore makes the **oracle a precondition for generation**. No component is generated or rewritten until its oracle exists and runs in CI. In order of preference, the oracles are: Izcal's own earlier implementation or from-scratch reference path, in lockstep (byte, tree or fragment equality); the relevant pinned WPT and test262 subset; formal reference models where they exist; spec-derived property tests; and differential comparison against reference engines as black boxes on generated inputs (DOM serialization, computed styles, layout boxes, JS results). ESMeta extracts ECMA-262 into an executable IR and has found bugs in both the spec and engines ([ESMeta](https://github.com/es-meta/esmeta)). Cassius gives an SMT semantics for a large fragment of CSS layout, usable as an oracle on small generated cases rather than as a proof target ([MSR](https://www.microsoft.com/en-us/research/?p=610539)).

### Spec anchoring

Every hand-written algorithm carries a **spec anchor**, a comment `// spec: <URL>#<fragment> [step N[.M]]` naming the specification section and step it implements (M-1, target ANC-1). **`hg-anchor`** resolves the anchors against **pinned specification snapshots** (`specs.lock`, next to the WPT pin), joins them to WPT tests through WPT's `<link rel=help>` metadata, publishes coverage per specification, and, when a snapshot moves, lists the anchors whose section text changed. Generated code (bindings, IPC) is anchored by its generator. Commits that change web-platform behavior carry a `Spec:` trailer.

Where a specification is silent, ambiguous or contradicted by the deployed web, behavior follows documented interoperability evidence, recorded in the **black-box observation log** (`compat/observations/`): a test case, each engine's observed result and the resulting decision, never a link to another engine's source, and filed upstream as a specification issue. **No other engine's source is placed in an agent's context or checked out in an Izcal workspace.** The Stage 1 design specifies the mechanisms (crate rule G9, CI tiers, the `provenance` check).

### WPT-driven development, with its caveats

The specifications, with WPT and test262 pinned against them, are the primary oracle from day one, tracked per directory in CI as in HGBA-2.0's S-4d. Two caveats from the notes shape how targets are written. First, **percentages move with the suite**: Servo gained 188,281 subtests in one month of 2025 from new tests alone, and Servo does not run all of WPT, so its numbers differ from wpt.fyi ([Igalia](https://blogs.igalia.com/mrego/servo-2025-stats/)). Targets are therefore pinned to a WPT revision. Second, **WPT is not the whole compatibility story**. Ladybird's subtest count grows slowly once the easy tests pass, in feature-specific bursts such as about 2,500 subtests from referrer-policy in one month ([Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31/)), and Interop's "web compat" area exists because real sites depend on de facto behavior that specs and WPT do not capture ([WebKit](https://webkit.org/blog/17818/announcing-interop-2026)). A recorded real-site corpus with differential rendering against reference engines covers that gap as a secondary signal: each disagreement is triaged against the cited specification section, and where the specification is silent the decision is recorded in the black-box observation log. It is never resolved by matching an engine's output.

### Oracles for each new component

No Izcal component has a predecessor, so each needs a named oracle, and they are not equally strong. Components that implement web-visible behavior also carry the **spec** oracle class (EQ-1) in addition to the oracles below:

| Component | Oracle | Strength | Residual gap |
|---|---|---|---|
| Data plane (B4) | **Projection equality:** the data plane must equal a fresh projection computed from the `cppgc` DOM, which remains the source of truth. Checked at every flush in debug builds, on every DST seed and every fuzzing run, and sampled in Nightly | Strong: an exact full-state check, not a heuristic assertion | A field defined wrongly in the projection itself is wrong on both sides and only surfaces end-to-end, through WPT layout and rendering failures. Release builds have no in-process check |
| `cppgc` bindings: write barriers and tracing (B4, HGBA-2.0 S-4c) | **V8's own heap verifier**, which exists only in V8 builds with heap verification compiled in. CI, DST and fuzzing therefore run a debug-V8 configuration alongside the release one | Strong when it runs: spike item 5 showed it reports a single omitted barrier | Release V8 misses an omitted barrier silently and leaves a dangling pointer, so any barrier bug that escapes the debug-V8 runs ships as a use-after-free. There is no runtime switch to turn verification on in release |
| Incremental driver (B5) | **The engine's own from-scratch path, which is kept, not replaced** (P4): output must be bit-identical on every frame (INC-1) | Strong for correctness in every case, including the hard ones: a formatting context the driver cannot handle incrementally falls back to from-scratch | What is open for `:has()`, fragmentation and anchor positioning (Q-2) is *how often* the fallback fires, which is performance, not correctness. INC-4 publishes it |
| Semantic plane: roles, names, states (B8) | WPT's accessibility-mapping tests (computed role and name) against HTML-AAM, Core-AAM and accname, plus black-box differential testing against Chromium's accessibility tree | Spec class from WPT; the differential is moderate: Chromium's tree is a reference, not ground truth | Disagreements are triaged against the cited AAM or accname section |
| Semantic plane: provenance and stable IDs (B8) | Property tests derived from the frame tree (every node's origin equals its document's origin) and AG-3's cross-origin suite | Moderate | No external oracle exists |
| Visibility flags (B8) | None: a heuristic | Weak | Measured only by a red-team suite; false-negative rate published (AG-5) |
| Repair overlay: non-interference (B8) | Bit-identical outputs with repairs on and off under DET-1 replay (A11Y-1) | Strong | Timing is measured separately (A11Y-4) |
| Repair overlay: correctness (B8) | Human-labelled holdout and held-out checkers (A11Y-2) | Moderate | Checkers detect a minority of WCAG criteria; labels cover only the corpus |
| Repair overlay: benefit (B8) | Pre-registered screen-reader user study (A11Y-3) | The only oracle for benefit; runs per rule change, not per commit | Population and task coverage |
| Agent principal (B9) | Tier 1 verification of the broker's capability policy, plus AG-3 | Strong for the policy, moderate for its use | Policy correct but applied to wrong provenance would pass |

**The projection's *definition* also needs an oracle, and Stylo's design provides one.** Projection equality catches drift between the DOM and the data plane, but not a field whose meaning is wrong on both sides. Two rules close most of that gap:

- **Trait-generic consumers (design rule).** Style, the incremental layout driver and the semantic plane read their inputs only through tree-access traits: Stylo's `TElement` family, which Izcal implements itself (Gecko and Blitz implementing it over their own DOMs is evidence that the traits are implementable; Izcal takes neither implementation), and Taffy's tree traits. They never depend on the data plane's concrete types. A missing field is then a compile error, because workers cannot reach `cppgc`, not a silent bug.
- **Dual implementation as a differential oracle.** The traits are implemented twice: once over the data plane, and once directly over the `cppgc` DOM, used only on the script thread, which owns the heap and may read it freely. CI, DST and fuzzing run style, layout and semantic-tree construction through both and require identical computed styles, fragment trees and semantic trees.
- **Independent projection.** The fresh projection used for equality checks is computed by a separate, deliberately simple, non-incremental traversal that shares no code with the mutation-log application path. This is also a non-goal (Section 10), so reusing a helper across the two paths is a violation, not an optimization.

**What each check catches, layer by layer.** There are three places a field can be wrong:

| Layer | Example | Caught by |
|---|---|---|
| Projection field definition | The data plane copies the wrong DOM bit into its `:hover` field | **The differential.** The DOM-side trait implementation reads element state directly and never goes through the projection, so the two disagree |
| Implementation drift | The data-plane trait implementation checks the right field the wrong way, or forgets to consult it | **The differential** |
| Trait semantics | Both implementations answer "does this element match `:focus-visible`?" with the same misreading of the spec | **Not the differential.** Partly caught by WPT computed-style and rendering tests, which check observable results (`display`, `visibility`, `pointer-events`, selector matching) against the spec, and by computed-style differential comparison against reference engines on generated inputs (Section 6); private state with no observable effect stays uncovered |

**Cadence and cost.** Projection equality is cheap (one traversal compared against stored values; the spike measured 1.46 ms at 10k nodes and 21.8 ms at 100k, including the projection) and runs at every flush in debug builds, on every DST seed, in every fuzzing run, and sampled in Nightly. The differential is expensive: it runs style, layout and semantic construction a second time, and the DOM-side implementation is single-threaded on the script thread. In Nightly it would block real pages, so it does not run there. In CI and DST it runs on a **fixed, published sample of the corpus** per seed batch, sized in the planning pass, so that DST cost per seed does not grow with the corpus twice. Fuzzing runs it on every generated case, because fuzz cases are small.

The weakest links are visibility flags and provenance, which is why HGBA-3.0 never presents them as a prompt-injection defense, only as a bound on what an agent can see.

### Verification where it pays off

Formal verification has shipped for small, well-specified, high-value code: EverParse-generated parsers in the Hyper-V virtual switch ([MSR](https://www.microsoft.com/en-us/research/blog/everparse-hardening-critical-attack-surfaces-with-formally-proven-message-parsers/)), HACL* crypto in Firefox, Linux and CPython ([HACL*](https://hacl-star.github.io/)), and seL4 at roughly 20:1 proof-to-code ([seL4](https://sel4.systems/About/)). The Rust standard-library campaign shows the cost at scale. After about two years, **989 of about 34,000 in-scope functions** have full formal contracts. Generated "autoharnesses" covered far more shallowly, and the effort found **no previously unknown memory-safety vulnerabilities**, only specification and documentation defects ([Rust Foundation](https://rustfoundation.org/?p=120341)). Layout verification remains research that does not scale to large pages ([Troika](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-modular-oopsla2019-abstract.html)). AI proof generation is a research target (KVerus, [arXiv 2605.03822](https://arxiv.org/pdf/2605.03822)), not yet a tool.

HGBA-3.0 tiers verification accordingly. **Tier 1, generated or checked parsers** (EverParse-class generated proofs where a format spec exists, Kani-checked otherwise, matching VER-1): IPC message (de)serialization across every renderer-to-broker channel, the broker's capability policy, the URL parser, image, font and media container headers, and crypto. These are all parsers of attacker-controlled bytes at a privilege boundary. The Rust std campaign's 989 fully specified functions out of about 34,000 is not the right comparison: EverParse generates verified parsers from format descriptions, so the cost scales with the number of message formats, not the number of functions. **Tier 2, bounded model checking** (Kani, ESBMC): every `unsafe` block and every FFI seam to V8, `cppgc` and C libraries, where the std campaign suggests the value is highest. **Tier 3, everything else:** fuzzing (Fuzzilli for JS, Domato-style for DOM and CSS, and LLM-generated fuzz harnesses, which found 26 new vulnerabilities across 272 projects at Google ([Google](https://security.googleblog.com/2024/11/leveling-up-fuzzing-finding-more.html))), differential testing and DST.

### Deterministic simulation testing

B1 exists so that this is possible. The simulator runs the browser, network, GPU and renderer processes as simulated hosts under one seeded scheduler. It replays recorded HTTP archives with injected resets, slow bytes and reordered resource completion, which the notes identify as the likely source of many load-order races. It explores HTML task-source interleavings the spec permits. Every failure is a seed, and every seed replays exactly. GPU, audio and media sit outside the simulator in Stage A and are covered by `rr` or whole-VM determinism. The method is shipped in databases and untested in browsers, so it has its own kill criterion (DST-1): if it does not find bugs at a competitive rate, it is demoted.

## 7. Agent-native capabilities

The agentic browsing market moved fast in 2026, and in one direction. **OpenAI shut ChatGPT Atlas down on 9 August 2026** and moved agent browsing into ChatGPT, a cloud browser and a Chrome extension ([TechCrunch](https://techcrunch.com/2026/07/09/openai-is-shutting-down-atlas-but-its-ai-browser-ambitions-are-still-growing/)). Chrome shipped Gemini auto browse in January 2026 ([blog.google](https://blog.google/products-and-platforms/products/chrome/gemini-3-auto-browse/)). Every notable agent product is Chromium-based. That has two implications. A new engine has **no competitor at the engine layer**, and its pitch must be capabilities that a Chromium fork cannot easily bolt on. And the stronger position is as an **agent runtime** (embeddable, headless, cloud-hostable, drivable by third-party agents) rather than as a consumer AI browser, a category that is shrinking. **This positioning is a bet on a market that has not formed, not a conclusion from evidence.** The agent-runtime market contracted in 2026, Chromium is free to agent builders, and Atlas and Comet ran on it. The only render-free engine aimed at agents in the notes, Lightpanda, backs its case with vendor claims. Because AI integration ships off (B10), the consumer browser does not depend on this bet.

HGBA-3.0's agent capabilities follow from B4, B7, B8 and B9, and are labelled accordingly. The **semantic plane** (research) gives compact, diffable, provenance-tagged observations instead of 20,000-token combined snapshots. **Deterministic snapshots** (research for browsers) come from B1. An agent step taken at a quiescent point under a virtual clock and seeded randomness can be replayed exactly, which addresses the poor reproducibility of live-web agent evaluation ([arXiv 2603.29020](https://arxiv.org/pdf/2603.29020)) and gives auditors a replayable log. **Pixel-optional parallel sessions** (prototype idea) make many concurrent isolated agent contexts cheap, with cheap forking of session state, served through a native automation protocol rather than a debug port. The **agent principal** (shipped in part, in Chrome) enforces origin sets in the engine, using provenance to keep out-of-set content out of the model's view. Browser-mediated credentials let agents sign in without ever seeing secrets, as Chrome's design already does ([Google](https://blog.google/security/architecting-security-for-agentic/)). The **tool registry** (prototype, WebMCP) tracks the spec and synthesizes tools from `<form>` only if that becomes part of it. **Honest agent identification**, a distinct and verifiable agent signal to sites, is an inference from the Amazon v. Perplexity injunction, **not a sourced standard**. An **on-device model host** compatible with the Prompt API, which is stable in Chrome 148 ([Chrome I/O 2026](https://developer.chrome.com/blog/chrome-at-io26)), sits behind HGBA-2.0's ML service and can run cheap injection classifiers locally.

**All of the above is off by default (B10).** The consumer browser ships with no agent, no model and no AI traffic. Embedders building agent runtimes switch it on by configuration, and users switch it on per profile. That fits the positioning above: the agent runtime is where these capabilities earn their keep, and a user who never opts in pays nothing for them (AG-0).

The boundary with the web platform is explicit. The semantic plane, snapshots, provenance, pixel-optional mode and agent principal are **embedder-facing internals** that content cannot observe, so the engine is free to innovate on them. WebMCP and any agent-identification header are **platform surface**, so the engine follows standards there and does not invent them.

## 8. Staged roadmap with falsifiable targets

HGBA-3.0 overlays HGBA-2.0's roadmap rather than replacing it. HGBA-2.0's Stage 1 targets (S-1 to S-4d, including S-4d's `wasm/jsapi/` triage rule, C-1, P-1, R-1, R-6) all remain in force. The `cppgc` spike has run (results in HGBA-2.0, Section 6, and D8 below). Its Stage 1 start conditions carry over: a rerun under V8's sandbox configuration and on Linux and Windows, a recorded exposure route for the `cppgc` APIs (the APIs live in the project's `rusty_v8` fork, HGBA-2.1.6 S-4e; the patch is still offered upstream), and the debug-V8 CI configuration. Durations are **not given**: HGBA-2.0 already marked its 18-month Stage 1 as provisional, and nothing in the new evidence supports a schedule. Team scale is the dominant unknown. Ladybird reached about 2.09M passing WPT subtests with roughly **8 paid full-time engineers** (secondary source) ([urandom.io](https://urandom.io/blog/2026-05-09-the-browser-with-no-ad-sales-department)). Servo merged **3,183 PRs from 146 contributors** in 2025, after collapsing to 65 PRs in 2022 when Mozilla withdrew ([Igalia](https://blogs.igalia.com/mrego/servo-2025-stats/)). Ladybird is not a direct yardstick: it writes its own JS engine, GC, CSS engine and layout, for most of which HGBA-3.0 uses dependencies, while HGBA-3.0 builds a deeper substrate (B1, B2, B4, B5, B8–B10) and must integrate many independently maintained components, which is a standing cost of its own. The research contains no basis for a multiple of Ladybird's team size in either direction, so team scale is an output of the planning pass, not an input. The planning pass must also size the **standing integration cost**, which an initial headcount estimate hides and which decides whether the project survives: V8, Stylo, Taffy, Parley, html5ever, WebRender, wgpu and Wasmtime each move on their own release cadence, with breaking changes and security fixes. HGBA-2.0's `rusty_v8` ownership rule generalizes: every upstream gets a named owner, a pinned version, and a published lag from upstream security releases. Lag escalates the fix upstream; dependencies are used unmodified (M-1), so the `rusty_v8` fork is the only fork, and an unmaintained dependency is replaced by an Izcal-built component written from the specification (HGBA-2 D1). Thresholds marked † are set by this document from first principles and are not taken from a measured source.

### Stage A: substrate and oracles before features

| ORC-1 | Oracles exist before code | 100% of components scheduled for generation or replacement have an oracle running in CI (Izcal's own reference path, pinned WPT/test262, formal model, or black-box differential) before the first generated line lands | Component is not started |
| VER-1 | Tier 1 parsers | 100% of renderer-to-broker message types use generated, proven (EverParse-class) or Kani-checked (de)serializers | Message type requires dual review and dedicated fuzzing until covered |

### Stage B: compatible engine on the new substrate

| ID | Target | Threshold / method | If missed |
|---|---|---|---|
| EQ-1 | Gated generation is not riskier | Post-landing defects per KLOC (bugs traced to code within 90 days of landing) for AI-generated, oracle-gated code are **≤** the rate for hand-written code in the same quarter, measured over two consecutive quarters, **reported separately per oracle-strength class** (spec: a pinned conformance suite, a formal model, or spec-derived property tests, **required** for every component that implements web-visible behavior; strong: byte- or bit-identical, projection equality, dual-trait differential; moderate: reference-engine differential, property tests; none). ## 10. Non-goals

HGBA-3.0 does not write its own JavaScript engine, garbage collector or WebIDL-to-GC strategy outside `cppgc`. It does not build the DOM on an arena with JS identity bolted on, because no production evidence supports it. It does not adopt a general per-field incremental dependency graph or use signals as engine internals. It does not store computed style as per-property columns. It does not run selector matching, cascade or layout on the GPU. It does not use the Component Model as an internal ABI between script, DOM and layout. It does not move layout off the script thread or adopt Servo's reported script/layout re-split. It does not subset the web platform for speed, however large the gain. It does not attempt full formal verification of the DOM, style or layout. It does not copy, port or translate another engine's code, by people or by AI tools (M-1). It does not let AI agents generate components that lack an oracle, and it does not accept screenshot diffs as a conformance oracle. It does not disguise agents as human browsing. It does not promise a speed multiple over Chromium. The data-plane projection used for equality checks and the mutation-log application path **share no code, ever**. Style, layout and the semantic plane **never depend on the data plane's concrete types**, only on tree-access traits. Both rules are enforced by the crate graph rather than by review: the projection and the log-application path live in separate crates, and a CI check on `cargo metadata` fails if they share any non-std, project-local dependency; the style, layout and semantic crates depend only on a traits crate, so naming a data-plane concrete type is a compile error.

## 11. "Recreating Servo is not the best": an honest answer

The framing is half right. **Recreating Servo's architecture is not the best path**, and Servo's own history says so. Servo was designed around message-passing parallel components and a separate layout thread, and the platform forced layout back onto the script thread in 2024 ([Servo](https://servo.org/blog/2024/02/28/gamepads-font-fallback-space-jam/)). Its DOM is built from SpiderMonkey GC objects, which HGBA-2.0 already has to rewrite for V8. Its multiprocess mode is optional. Its constellation was not designed for deterministic simulation, and none of its threading was designed for replay. Its organizational history is a warning on its own: activity fell by about 95% within two years of losing its corporate sponsor ([Igalia](https://blogs.igalia.com/mrego/servo-2025-stats/)). Servo's WPT score of 61.6% at the end of 2025 also shows how far a mature, well-staffed Rust engine still is from full compatibility.

But "not Servo" must not become "not the standalone libraries from Servo's ecosystem". The evidence still favors using several of them unmodified, as dependencies, for reasons unrelated to Servo's overall architecture. **Stylo** is the strongest case. It has shipped in Firefox since 2017, after two failed C++ attempts at parallel style. Its three-level sharing model beats the obvious data-oriented alternative on memory. And Blitz and Gecko show it runs over DOMs that are not Servo's ([Mozilla Hacks](https://hacks.mozilla.org/2017/08/inside-a-super-fast-css-engine-quantum-css-aka-stylo/); [Blitz](https://github.com/DioxusLabs/blitz/blob/main/packages/blitz-dom/src/document.rs)). Writing the cascade, selector matching and invalidation for `:has()` new would spend years reaching where Stylo already is. **WebRender** and **wgpu** ship in Firefox. **html5ever** is used by Servo and Blitz. **Taffy** and **Parley** grew from the same ecosystem and are now shared infrastructure across a dozen projects ([Taffy](https://github.com/DioxusLabs/taffy)). **Servo's layout** is not a dependency: it reads Servo's concrete DOM types and cannot run over another DOM. It is used only as a black-box reference engine, and never as source (Stage 1 design D-S10). The long-tail layout (tables, fragmentation, writing modes) is written from the CSS specifications and has a moderate differential oracle, mitigated by the spec class: spec anchors, pinned WPT, and CSS formal models such as Cassius where they exist.

What is genuinely new in HGBA-3.0 is everything underneath and around those components, and none of it has shipped in a browser. That means an engine that is **deterministic and simulation-testable from its first commit** (a bet: if DST-1 fails, this shrinks to "replayable"); a **Rust data plane with stable identities** that serves threading, incrementality, replay and agents at once; an **incremental layout core** that combines an approach shipped in LayoutNG (constraint-keyed immutable fragments, derived here from the CSS specifications) with research (Spineless ordered queues, durability tiers) behind measured fallbacks; a **build process in which oracles precede code**, code is written from the specifications, and AI generates only spec-anchored skeletons that the oracles gate; and an engine whose **semantic output and agent principal are core features**, not debug-port extras. The rule for each component is: use unmodified what has shipped as a standalone library, write everything else from the specifications, and never ship a component without a spec-anchored oracle.

## 12. Open questions and flagged claims

### Open questions

**Q-1. What does the data plane cost?** Partly answered. Spike item 6 measured about 150–175 B per node on a toy DOM, with attributes about 60% of that, and flushes of 0.5–1.4 ms per 10,000 mutations. What is still unknown is total renderer memory per node on the corpus, which INC-3 divides by, and cache behavior, which no source measures. Blitz publishes no memory figures.

**Q-2. Can the incremental layout core cover the hard formatting contexts?** Spineless covered a CSS subset. Out-of-flow positioning, fragmentation, `:has()`, container queries and anchor positioning (an Interop 2026 focus area) break tree-locality. Which of them get explicit non-tree edges and which get permanent from-scratch fallbacks is unresolved.

**Q-3. Can V8 run deterministically under an injected platform?** Partly answered by the planning pass. The flags exist in V8 15.2: `--predictable` (implies single-threaded GC, no concurrent recompilation and a fixed random seed), `--single-threaded` and `--random-seed`. But `rusty_v8`'s `PlatformImpl` intercepts only foreground task posting; worker threads and both clocks stay with V8's default platform, so `Date.now` cannot be faked from Rust. A d8-style predictable platform in the project's `rusty_v8` fork is required. Whether GC-observable behavior (`WeakRef`, `FinalizationRegistry`) is then reproducible is decided by the Stage A determinism probe. If V8 cannot be made reproducible, DET-1 needs whole-VM determinism (Antithesis-class) for the JS layer, which changes its cost.

**Q-3 answered (M0, 14 October 2026).** Yes, under the fork's predictable platform, which takes over both clocks and all worker tasks. A probe exercising `Math.random`, `Date.now`, allocation, `WeakRef` and `FinalizationRegistry` with embedder-forced GC points gave 1,000 of 1,000 identical hashes in-process and 50 of 50 across fresh processes, in release and debug V8, on macOS arm64, Linux x86-64 and Windows x86-64. **The hashes are identical across the three OSes**, including the full finalization order. The flags alone do not suffice: with V8's stock platform and no flags the probe produced 848 (macOS), 912 (Linux) and 989 (Windows) distinct hashes in 1,000 runs; with `--predictable --single-threaded` it still diverged occasionally (3 of 1,000 debug runs on macOS, 1 of 1,000 release runs on Windows). In release builds the worker-task mode (inline or queued) changes the hash while each mode is stable, so **every recording carries the mode as a mandatory field, and the simulator refuses a recording whose mode is missing or unsupported**. Cross-OS identity is observed for this probe, not guaranteed for all programs.

**Q-4. Does DST find browser bugs at a useful rate?** No browser case exists, and no measured bug-yield numbers for Antithesis or TigerBeetle were found. DST-1 tests it.

**Q-5. Will WebMCP survive its origin trial?** The trial reportedly ends around 17 November 2026 (secondary sources disagree on its start date). Its fate decides how much of B9's tool registry is platform and how much is speculation.

**Q-6. Is engine-enforced provenance filtering a meaningful injection defense?** It bounds reach, but the notes contain no attack-success-rate data from Google or OpenAI, and visibility heuristics are unproven.

**Q-7. Do AI-generated, gated components carry a different defect profile?** The notes found **no measured defect-rate data** for AI-written code in large systems. EQ-1 is designed to produce it.

**Q-8. Did Ladybird's May–August 2026 ports use AI agents and byte-level gating?** **Retired 17 October 2026: Izcal translates no code (M-1).** The newsletters do not say. Only the February LibJS port is documented as AI-assisted. The CSS parser port documents A/B zero-mismatch gating but not the tooling.

**Q-9. How does Servo's 2026 WPT figure compare, and what is its sandbox default?** No official 2026 figure was found, and HGBA-2.0's Q-2 on multiprocess defaults remains open.

**Q-10. How can a user agent disclose an inferred accessible name?** Platform accessibility APIs have no standard "inferred by user agent" property, and screen readers do not announce custom attributes. The options are a suffix on the name or description, which works everywhere but is verbose, or a new property agreed with screen-reader vendors, which is slow. A11Y-3's third arm measures what disclosure costs users.

## Conclusion

HGBA-2.0 found that hardware growth is mostly a broker and standards problem rather than an engine-core one. HGBA-3.0 finds the software analogue: the neglected engine-core frontier in 2026 is **verifiability**, and the algorithms worth adopting are the ones that can be gated. The algorithms a compatible engine needs mostly exist as shared Rust components. What does not exist anywhere is an engine designed so that cheap code generation can be trusted: deterministic enough to replay, structured enough to gate component by component, and incremental by construction rather than by accumulated invalidation patches. That reframes the question of how a small team can build a browser. The 2026 evidence suggests the limiting resource is no longer engineers writing code. It is oracles, replay infrastructure and reviewers' attention, and an architecture should be judged by how much of each it gives back.

The second implication is strategic. Agentic browsing consolidated onto Chromium in 2026, yet the capabilities agents most need are compact, stable, provenance-tagged observations, enforceable cross-origin limits on what an agent can read and do, and reproducible runs. Those are exactly the things a debug-port architecture struggles to provide and a deterministic, data-plane-centric engine provides almost for free. If HGBA-3.0 has a defensible reason to exist beside Chromium, it is that one design choice, deterministic and checkable internals, serves both the builders and the agents. And because all of it ships switched off, the same engine is also a browser for people who want no AI at all.
