No accepted Izcal spec owns editing. The Phase 3 ledger records it as **G-16** and the spellcheck question as **C-22**, which it calls "unresolved, minor" and for which it recommends keeping the text stack's utility-process placement and recording the stage and budget as this spec's ([LG][LG]); this spec departs from that placement (ED-D7) and says why; the DOM spec keeps the Selection object and event dispatch and leaves "caret movement in editable content, editing commands and `execCommand`, `contenteditable` behaviour, `beforeinput`/`input` semantics for edits, IME composition beyond the event plumbing of 6.5, spellchecking, and the visual selection painted by graphics" to this spec ([DM 6.6][DM]); the text stack keeps composition rendering and movement data and leaves "the editing commands themselves" here ([TX 6.8a][TX]). The record is unusually consistent. **The web's editing was never specified**: HTML hands `contenteditable`'s core to an execCommand draft that says it is "not expected that it will advance beyond draft status" ([SS 4.2, 5.1][SS]); a decade of attempts to fix `contenteditable` ended in 2025 with the draft published and discontinued at once ([HP 1.8][HP]). **Every serious editor therefore keeps its own model and treats the DOM as a view** (ProseMirror, Lexical, CKEditor 5 at about 42 person-years, Google Docs on canvas), and Lexical's FAQ calls `input` and `beforeinput` "hardly reliable" ([HP 4.3–4.11][HP], [GO 1.5][GO]). **Input methods fight the DOM**: cancelable composition was dropped from Input Events because an IME owns its own buffer in another process ([HP 2.2–2.6][HP]), and a large share of editors' IME bugs sit on Android ([IM 7.8][IM], [GO 2.1–2.5][GO]). **Editing and selection were a use-after-free farm** (40 of Firefox's 74 public Editor and Selection security bugs) because edits hold positions while page script runs ([SR 1.1–1.4][SR]). **The clipboard is now an attack channel at industrial scale**: ClickFix pages write a command and tell the person to paste it into Run, in campaigns "targeting thousands of … devices globally every day"; Edge's SmartScreen warns on known landing pages, but no browser is documented to warn about what a page writes to the clipboard ([SR 2.2–2.6][SR]). **Text services leak**: cloud spellcheck sent revealed passwords to vendors ([SL 4.1][SL]); 8 of 9 cloud keyboards leaked keystrokes ([IM 10.4][IM]); the Windows text-services protocol had "no access control whatsoever" for nearly twenty years ([IM 10.1][IM]). **The central idea: every change to editable text is one typed edit intent applied by one engine to one editable text model, behind a versioned, broker-mediated boundary with the input method, the clipboard and the drag source, so that no page script runs inside an edit, no renderer sees another application's data without the person's gesture, and every keystroke's effect can be recorded, replayed and explained.** The decisions that matter most: (1) Izcal writes every default action down as its own published algorithm over Input Events Level 2, with `execCommand` mapped onto the same algorithms (ED-D1); (2) one edit engine over two backings, the DOM and a piece-table value, so text controls and editing hosts behave alike (ED-D3); (3) a push-first, versioned IME protocol where the broker answers the OS's synchronous queries from a snapshot and never waits on a renderer, with third-party Windows input-method DLLs moved out of the broker into the window-owning UI host the accessibility spec already designs (ED-D4, ED-D5); (4) Izcal's own finite-state spelling engine and lexicons, offline and identical on every OS, with an interim OS tier for languages that have no Izcal lexicon yet (ED-D7, ED-D8); (5) a broker-owned clipboard with per-read paste confirmation and, for the first time in a browser, provenance and a warning when a page plants a shell command (ED-D10, ED-D11). The work is about **34–46 engineers† plus a 10–16† language-data extension** (Section 9).

## 1. The problem and who has it

| User | Task, in their words | What fails today |
|---|---|---|
| **People typing** | "Type in my language with my input method and see it at once; let me fix mistakes" | Candidate windows appear at the screen's corner or not at all when the text store cannot answer in time, across at least eight Windows input methods ([IM 4.5][IM]); a browser-engine editor averaged 49 ms of processing latency per keystroke against 0.9 ms for a native editor ([IM 9.1][IM]); no published measurement of keystroke-to-paint latency in a browser exists ([IM 9.3][IM]) |
| **Authors of editors** (ProseMirror, Lexical, CodeMirror, Slate, CKEditor, VS Code) | "Tell me what the person meant, before you change my DOM, the same way in every browser" | `input` and `beforeinput` are "hardly reliable", and spellcheck, extensions, IMEs and dictation "don't even trigger any events at all" (Lexical, [GO 1.5][GO]); about 550 issue titles across editor trackers name Android, IME, composition, Gboard or Samsung ([GO 2.5][GO]); `@codemirror/view`'s release notes carry 32 Android workarounds ([HP 4.5][HP]); the maintainer cannot reproduce a Samsung Keyboard bug because he cannot install the keyboard ([GO 2.3][GO]) |
| **Authors of forms** | "Let `input` and `textarea` keep undo, autofill and IME working" | HTML says nothing about undo after script sets `.value` ([SS 4.10][SS]); authors use the deprecated `execCommand('insertText')` because it is the only way to keep the undo history ([GO 6.2][GO]) |
| **People copying and pasting** | "Copy should work and pages should not read or poison my clipboard" | Chromium keeps a persistent read permission while Firefox and Safari ask on each read ([SR 2.8][SR]); ClickFix grew more than 500% in the first half of 2025 and is "the second most common attack vector after phishing" ([ESET](https://www.welivesecurity.com/en/eset-research/eset-threat-report-h1-2025/), [SR 2.5][SR]); copy-paste XSS bypassed browser and editor sanitizers ([SR 3.1–3.5][SR]) |
| **Assistive-technology users** | "Hear my edits and my spelling errors; dictate into any editor" | Voice control edits the DOM behind the editor and needs vendor-specific code (Lexical's `@lexical/dragon`, [GO 2.7][GO]); no specification maps a browser's own spelling marks to the accessibility APIs ([GO 8.4][GO]) |
| **People searching a page** | "Find this word, accented or not, inside collapsed sections" | Firefox's diacritics bug stayed open 16.7 years; regex find has waited since 2005; shadow-tree find bugs were filed in October 2026 ([GO 7.1–7.4][GO]) |
| **Developers, testers and agents** | "Why did this keystroke do that?", "test my editor with a real IME", "let the agent type into the editor" | WebDriver, BiDi, Playwright and Puppeteer cannot drive an IME, with requests open since 2019–2022 ([GO 4.1–4.6][GO]); no DevTools shows composition state, target ranges, the undo stack or clipboard flavours ([GO 5.1–5.4][GO]); AI agents double or drop the first letter in rich editors ([GO 10.1][GO]) |

**What Izcal's specs already decide** (the full digest is [FR][FR]):

- **M-1 (HGBA-2 2.3.3).** No library from a browser or editor project, nor any library doing engine work; MIT only for shipped code and data; no other project's source code is evidence. Hunspell and its dictionaries, LanguageTool, Harper and every editor framework are therefore out ([SL 3.1–3.8][SL]); OS interfaces (TSF, Cocoa, Wayland, Android, OS clipboards, OS spelling services) are allowed.
- **I-1, I-6.** One renderer per (site, container), origin-keyed (FP-D8, DM-D6). The clipboard and drag data are cross-application and cross-origin data.
- **HGBA-3.** B1 (recorded inputs), B2 (typed capability IPC), B4 (the mutation log), B8 (the semantic plane), B9 and B10 (agent principal; AI off by default).
- **DM ([DM][DM]).** `hg-input` turns OS input into UI Events and dispatches `beforeinput`/`input`; every input is a recorded B1 input with the broker's sequence number; user activation is minted by the broker and checked for clipboard writes (DM-D20); script points are typed (DM-D5, G91); Selection's data model, `selectionchange` and composition-event plumbing are DM's; autofill writes values from the broker through `hg-forms`; Clipboard's bindings are in `hg-webapi`.
- **TX ([TX][TX], accepted).** TX-D23: the broker owns the OS IME frameworks, no IME code in a renderer, third-party TSF DLLs in the broker inventoried; composition rendering and movement data are TX's. TX-16: no page-controlled string reaches an OS text API in the broker. TX-D14: Izcal authors its own linguistic data with a language-data track. FP-D13: every dictionary in every build.
- **AX ([AX][AX]).** AT edits go through `beforeinput`/`input` and the input-equivalence table (G106); text positions and editable-text exposure (AX 6.8); caret browsing over DM's Selection model (AX 6.12); a window-owning UI-host process on Windows if accessibility software breaks under the broker's mitigations (AX-D9 (b)).
- **LY, GR, ST, MD.** Layout supplies `caretPositionFromPoint`, line records and LY-D11's caret width; graphics supplies paint chunks, property trees, compositor opacity animation and a 16† cap on compositor-mutable nodes; style supplies `SanitizingSink`; media decodes every image byte, clipboard images included (MD-20).

**What success means, measurably.** WPT editing directories at or above the best shipping engine (ED-1); every default action written down and anchored (ED-2); the editor corpus and the IME matrix pass on every desktop OS (ED-3, ED-4); keystroke-to-paint within a frame plus 4 ms† (ED-30); no clipboard or drag data in a renderer without a routed gesture (ED-11, ED-12); spelling identical on every OS and ISA and invisible to script (ED-15, ED-51); every editing session replays exactly (ED-50).

## 2. History: what came before and why it was built that way

### 2.1 Chronology

| Year | Project | What it did | Why that way | Fate and why |
|---|---|---|---|---|
| 1999–2000 | **IE 5.0 drag and drop; IE 5.5 `contentEditable` and `execCommand`** (IE 5.5's date is a Medium-confidence row) | Seven drag events and `dataTransfer`; any element editable; a command table run by `execCommand` | One engine, one OS, one process, with no other engine to agree with (the reasons are this spec's reading of the era) | Copied "in a haphazard and imprecise fashion" by every engine ([execCommand draft](https://w3c.github.io/editing/docs/execCommand/), [HP 1.1, 7.1][HP]); the API shape survives everywhere |
| 2003–05 | **Mozilla Midas** | `designMode` rich-text editing; cut, copy and paste off unless the user set a pref | IE compatibility within Mozilla's security model | Its clipboard stance (off unless the user set a pref) was an early permission model ([HP 1.2][HP]) |
| 2006 | **Firefox 2 inline spellcheck** | The `spellcheck` attribute with a MySpell-family checker (the engine detail is a Low-confidence row) | Browsers had become where people wrote mail and posts | Every browser followed, each with different engines and data ([HP 9.5][HP]) |
| 2008–15 | **Flash clipboard (ZeroClipboard)** | An invisible Flash movie over a button copied text | Flash Player 10 required a click in the movie; the web had no copy API | Died with Flash and with gesture-gated `execCommand('copy')` (Chrome 42/43, Firefox 41, 2015) ([HP 5.2–5.3][HP]) |
| 2009 | **HTML5 drag and drop** | IE's model standardized | Compatibility | "No less than seven events" whose `dropEffect` "made no difference" ([QuirksBlog](https://www.quirksmode.org/blog/archives/2009/09/the_html5_drag.html)); the shape stayed, protected-mode data rules were added ([HP 7.1–7.2][HP]) |
| 2010–21 | **Google Docs' own surface, then canvas** | Its own layout and editing instead of `contentEditable`, then canvas rendering | For the 2021 move: "improve performance and improve consistency in how content appears across different platforms" (the 2010 motives are not documented in what was read) | Screen-reader users need a special mode ([HP 4.1, 4.9][HP], [GO 8.2][GO]) |
| 2011–14 | **HTML Editing APIs (Aryeh Gregor)** | `execCommand` specified by matching engines where they agreed | No specification existed; in June 2011 engines were not "remotely consistent" even on unsupported commands | Stalled; its status says it is "not expected that it will advance beyond draft status" (why it stalled is a Low-confidence row) ([HP 1.4–1.5][HP], [SS 5.1][SS]) |
| 2012 | **UndoManager and DOM Transaction** | `undoscope`, automatic and manual transactions | One undo history for script and UA edits | Never shipped; in 2016 seven editor projects called browser undo "useless or harmful" ([HP 8.1–8.2][HP]) |
| 2014–25 | **`contentEditable=minimal`, `cE=typing`, the Editing Task Force** | Nested subsets (events ⊂ caret ⊂ typing ⊂ true) | Fix `contentEditable` by letting script do the rest | Never shipped; published and discontinued in 2025, its chair saying it "eventually led to the EditContext API" ([w3c/editing #480](https://github.com/w3c/editing/issues/480), [HP 1.6–1.8][HP]) |
| 2015–22 | **Editor frameworks** (ProseMirror, Draft.js, CKEditor 5, Lexical) | Their own document model; the DOM as a view; edits read from events or by diffing the DOM | Browsers gave "very little control over what the user and the browser are doing to our document" ([Haverbeke](https://marijnhaverbeke.nl/blog/prosemirror.html)) | All survive except Draft.js (archived 2023 for Lexical); CKEditor 5's model took about 42 person-years ([HP 4.3–4.8][HP]) |
| 2016–26 | **Input Events Levels 1 and 2** | `beforeinput` with `inputType` and target ranges | Let editors see intent and cancel before the DOM changes | Split in 2017 when Chrome's Android team could not cancel IME commits; Level 1 discontinued 2023; Level 2 (WD 2026-10-15) keeps one non-cancelable `insertCompositionText` ([HP 2.1–2.7][HP], [SS 2.1–2.4][SS]) |
| 2018–24 | **Async Clipboard API** | Promise-based read and write, `ClipboardItem` | Clipboard access through `execCommand` "was synchronous, and could only read and write to the DOM" (web.dev) | Chrome: persistent read permission; Safari (2020) and Firefox (2024): a Paste menu per read, which the spec now requires ([HP 5.4–5.6][HP], [SS 6.7][SS]) |
| 2019–26 | **EditContext** | Text input decoupled from the DOM: a buffer, a selection, character bounds | Hidden editables "negatively impact accessibility and increase complexity" | Chrome 121 (2024); VS Code's default (2025-06); Mozilla positive with accessibility concerns; WebKit silent; one engine in October 2026 ([HP 3.1–3.9][HP]) |
| 2001–19 | **Windows CTF (Text Services Framework)** | The cross-process protocol behind TSF | Office XP's text services, extended to Windows | "No access control whatsoever" for nearly twenty years, fixed in 2019 ([Project Zero](https://projectzero.google/2019/08/down-rabbit-hole.html), [IM 10.1][IM]) |

### 2.2 Technology mismatches: assumptions that no longer hold

| Assumption (era) | Why it no longer holds | Evidence |
|---|---|---|
| The DOM is the document model (2000) | Every serious editor keeps its own model and treats the DOM or a canvas as a view | [HP 4.3–4.11][HP] |
| One engine's behaviour is the specification | IE's copies were imprecise; `plaintext-only` took about 15 years to reach a third engine | [HP 1.1, 1.9][HP] |
| Input is a desktop keyboard whose keys map to edits | IMEs, soft keyboards, autocorrect, dictation and handwriting commit from their own buffers | [HP 2.2–2.6][HP], [IM 7.1][IM] |
| The input method can query the document synchronously | The document is in another process; synchronous OS queries must be answered from a cache | [IM 1.1, 1.3, 4.1–4.3][IM] |
| The clipboard is synchronous, trusted and single-process | It is OS-owned, cross-application, snooped and weaponized | [HP 5.4–5.9][HP], [SR 2.1–2.11][SR] |
| Browser undo serves editors | It is useless once the editor intercepts any edit | [HP 8.2][HP] |
| Text services may be a cloud call | Spell-jacking; cloud keyboards leaking keystrokes | [SL 4.1][SL], [IM 10.3–10.4][IM] |
| Spellchecker code is trusted C++ in the content process | Firefox sandboxed Hunspell as untrusted code in 2021, and the bugs moved to the sandbox boundary | [SR 6.1–6.4][SR] |
| Input-method code can run in the most privileged process | CTF's protocol had no access control; third-party TIP crashes land in the host process | [IM 4.7, 10.1][IM] |
| Rendering text and receiving text are one thing | Canvas editors and EditContext separate them; AT and OS text services still assume they are joined | [HP 3.5, 3.9][HP] |

## 3. Today: the landscape and its gaps

**The specifications are thin exactly where editing happens.** The Selection API leaves caret position and affinity undefined and says of `modify()`: "We need to more precisely define what it means to extend or move selection by each granularity" ([SS 1.2, 1.4][SS]); Input Events Level 2 still names a `contentEditable=typing` state HTML does not have and disagrees with UI Events on the order and cancelability of composition events ([SS 2.5, 2.10][SS]); the Clipboard API's algorithm text says "Add definition of sanitized copy" and never says "strip scripts" ([SS 6.5][SS]); HTML requires filtering dropped HTML but "does not specify how" ([SS 8.3][SS]); CSS leaves the caret's stacking position undefined and says of highlight geometry "Not sure if this is the correct way of describing the way things work" ([SS 7.3, 7.8][SS]); HTML says nothing about the undo history ([SS 4.10][SS]).

**Interop is uneven and unprioritised.** Selection, Input Events, the clipboard and `execCommand` have never been scored Interop focus areas; only custom highlights are, in 2026 ([SS 11.1–11.3][SS]). On 2026-10-19 the best engines scored 90.5% on `editing/`, 94.3% on `selection/`, 81.8% on `input-events/`, 95.4% on `clipboard-apis/`, and the third engine 52.4% on `input-events/` and 60.1% on `clipboard-apis/` ([SS 1.9, 2.12, 5.7, 6.12][SS]).

**What no tool shows** ([GO 4–5][GO]):

| Invisible today | Evidence | What Izcal can show |
|---|---|---|
| The input pipeline of one keystroke: key or IME message → `beforeinput` with target ranges → the edit → mutations → `input` | Framework devtools see only their own model; Chrome's Recorder stores only a field's final value ([GO 4.9, 5.2][GO]) | The edit trace and explainer (6.16) from recorded inputs and the mutation log |
| What the IME sent | No automation drives a real IME; bugs need a specific phone and keyboard version ([GO 2.3, 4.1–4.6][GO]) | IME session records, replayable on any OS, and a virtual IME (6.16) |
| The undo stack | No tool; editors cannot even read the native menu's state ([GO 6.1–6.3][GO], [SS 4.11][SS]) | The history view with validation and drops (6.9) |
| What a page wrote to or read from the clipboard | Chrome's own article needs a separate macOS app to show it ([GO 5.4][GO]) | The clipboard log in the shell and DevTools (6.10) |
| Why a word is flagged | No browser explains its spellchecker | Spelling explain with the lexicon version (6.8) |

**What Izcal can do that no one does.** Record and replay editing including the input method's messages (B1); explain an edit with spec anchors (ANC-1, B4); keep the clipboard and drag data out of every renderer (I-1, B2); spellcheck identically on every OS with lexicons the project owns (TX-D14); expose spelling errors to AT but not to script (B8); give agents, AT and extensions one labelled edit channel (B9).

## 4. First principles

### 4.1 Users' real tasks

| # | Task | What it needs from the engine |
|---|---|---|
| U1 | Type text in any script, with any input method, and see it at once | One path from key or IME commit to pixels, with the caret where the person expects it and composition shown inline; keystroke-to-paint bounded (ED-30) |
| U2 | Move the caret and select, by character, word, line, paragraph, with keyboard, mouse, touch, pen and AT | Movement rules over grapheme clusters, words from the text stack's dictionaries, lines from layout, visual order from bidi, in both editable and non-editable text |
| U3 | Fix mistakes: undo, redo, spelling suggestions, autocorrect that can be undone | A per-field history that survives script, a spellchecker that works offline in the person's languages |
| U4 | Move text between places: copy, cut, paste, drag, drop, share | Faithful data in the formats both ends understand, no leakage to pages that did not get a gesture, and no page-written commands that harm the person |
| U5 | Build an editor (author) | A cancelable, complete `beforeinput` for every intent, exact target ranges, a model that does not mutate the DOM behind the editor's back, IME that does not fight the editor |
| U6 | Fill a form (author and person) | `input` and `textarea` that keep their undo history, respect `inputmode`, `autocomplete`, `autocapitalize`, `autocorrect`, `spellcheck`, and accept autofill without script tricks |
| U7 | Find text in a page | Matching that honours case and diacritics as the person chooses, across frames, shadow trees and collapsed content, without leaking results across origins |
| U8 | Debug an editor (developer and agent) | The sequence key → `beforeinput` → edit → mutations → `input`, the IME session, the undo stack and the clipboard flavours, recorded and replayable |

### 4.2 Platform primitives

- **The specifications** (anchored at pinned revisions): HTML's editing section (editing hosts, `contenteditable`, `designMode`, `inputmode`, `enterkeyhint`, `autocapitalize`, `autocorrect`, `spellcheck`, `writingsuggestions`), its text-control selection APIs and value model, its drag-and-drop model, and `execCommand`'s entry points; Input Events Levels 1 and 2; UI Events (keyboard and composition); the Selection API; the Clipboard API and events; EditContext; CSS Pseudo-Elements 4 (highlight pseudo-elements) and the Custom Highlight API; CSS UI 4 (`caret-color`, `caret-shape`, `caret-animation`, `user-select`); URL Fragment Text Directives; the VirtualKeyboard API. What they leave undefined is Izcal's to write down (Section 6.4).
- **The OS interfaces**: TSF and IMM32 on Windows, `NSTextInputClient` on macOS, Wayland `text-input-unstable-v3` with IBus or Fcitx on Linux (and XIM on X11), Android `InputConnection` and `EditorInfo`; OS clipboards (`OpenClipboard`/OLE data objects, `NSPasteboard`, Wayland `wl_data_device` and primary selection, Android `ClipboardManager`); OS drag and drop; the touch keyboards (`InputPane`, Android soft input).
- **Izcal's own data**: the text stack's grapheme, word and sentence boundaries with SA dictionaries (TX 6.6), cluster maps and bidi maps (TX 6.8); layout's fragments, line records and `caretPositionFromPoint` (LY 6.15); the mutation log (B4); the semantic plane (B8); recorded inputs (B1).

### 4.3 Izcal's principles that bind this design

P1 (security and privacy first): the clipboard and drag data belong to the person and to other applications; a page sees them only for the transfer the person made. P2 (compatibility): `contenteditable` is used by every rich-text editor on the web, and 1.19% of page loads call `execCommand` ([DM 6.12][DM]); legacy behaviour stays where the web depends on it. P3 (determinism, B1): every keystroke, IME command, paste and drop is a recorded input; every result computed from them is a function of them. P4 (performance): typing is the most latency-sensitive interaction a browser has. P5 (footprint): dictionaries are shared engine-image data, not per-process copies. P6 (openness): every UA-defined editing behaviour is written down as an Izcal algorithm and filed with the Editing WG. M-1: no library from a browser or editor project; no other project's source as evidence; MIT only for shipped code and data.

### 4.4 Assumptions kept and broken

| Assumption | Keep or break | Why |
|---|---|---|
| The editing host's DOM is the document model | **Keep, with a choice for authors** | The web's editors are built on it and P2 requires it; EditContext's model-separated input is designed in from the start so it costs little when admitted (ED-D2) |
| Editing commands are a bag of per-engine behaviours | **Break** | HTML delegates the behaviour to a draft that will not advance ([SS 4.2][SS]); every default action becomes an Izcal algorithm with an anchor, a reference test and a recorded divergence where engines differ (ED-D1) |
| Script may run in the middle of an editing operation | **Break** | DOM deprecated mutation events in 2011 and Chrome removed them in version 127; Izcal never implements them (ST-D4); Izcal's edit core is script-free by type (G140), the lesson of the Editor and Selection use-after-free record ([SR 1.1–1.4][SR]) |
| The IME talks to the document synchronously | **Break** | The document is in another process; the broker answers the OS's synchronous queries from a versioned mirror and sends commands asynchronously (ED-D4) |
| The renderer reads the OS clipboard | **Break** | The clipboard is cross-application data; only the broker touches it, and a renderer receives data only for a paste or read the person made (ED-D10) |
| A text control is a special case with its own editor | **Break** | One engine over two backings (ED-D3); text controls and editing hosts share movement, IME, undo and spellcheck |
| Spellchecking is the OS's or a cloud's | **Break** | Izcal's own engine and lexicons, offline, identical on every OS (ED-D7) |
| Undo is a stack of opaque commands | **Break** | Each entry is a validated transaction over the model, dropped safely when script changed what it covers (ED-D14) |
| Caret blinking is the renderer's timer | **Break** | The compositor blinks the caret; the renderer paints it once per change (ED-D15) |
| Arrow keys move in visual order in bidi text | **Keep, measured** | The Selection API maps left and right through the bidi level and leaves the rest to the UA ([SS 1.4][SS]); the per-OS convention is a black-box observation (ED-D16) |
| Find in page is a renderer feature | **Break** | A tab's frames live in several processes; the broker coordinates and each renderer searches only its own documents (ED-D17) |

**One engine, three doors.** Every change a person makes to editable text arrives through one of three doors: keys and pointers (DM's `hg-input`), the input method (6.5), or a broker-mediated transfer (paste, drop, AT set-value, autofill, autocorrect, a spelling suggestion, an agent's edit). Each door produces an **edit intent**: an `inputType` from Input Events Level 2, target ranges, and data. The intent is dispatched as `beforeinput` where the specification says so and, unless cancelled, applied by **`hg-edit`** as one **edit transaction** over an **editable text model** (6.1), which is either the DOM of an editing host or a text control's value. Undo, spelling, IME, caret movement, find and the accessibility exposure all work over that model, so a text control and an editing host behave alike wherever the specifications allow and differ only where they must (G141).

**What runs where.** Everything about a document's text runs in its renderer: the model, the edit engine, movement, spelling with Izcal's lexicons, find within the document, undo. Everything that touches another application or another origin runs in the broker (or, on Windows, the UI host): the OS input-method frameworks, the OS clipboard, OS drag and drop, the personal dictionary, the find session across frames. Data from those reaches a renderer only as a recorded input tied to a gesture the broker routed to that frame (G144).

### 6.1 The editable text model and edit transactions (ED-D3)

**The model.** `hg-edit-model` (L2) defines what every editing feature works over: an **editable text model** with positions, a selection, and edit operations, and nothing about the DOM or a value string. A **position** is (container, offset, affinity), where the container is a DOM node slot with its generation (for a `DomBacking`) or the text control's value (for a `ValueBacking`), and offsets are UTF-16 code units, as the DOM and HTML's selection APIs count. Every position the engine creates is **grapheme-aligned** (TX 6.8a); positions arriving from script (`setSelectionRange`, `Range` boundaries) may fall inside a cluster and are kept as given, as the specifications require, but no engine-created edit splits a cluster except the code-point backspace rule of TX 6.8a.

**Operations.** An edit is a sequence of primitive operations, each reversible: `InsertText(position, string)`, `DeleteRange(range)`, `SplitBlock(position, kind)`, `MergeBlocks(position)`, `InsertNode(position, node)` and `RemoveNode(node)` (DOM backing only), `SetAttribute`/`SetStyle` for formatting commands (DOM backing only), and `SetSelection`. A **transaction** is the operations of one edit intent, plus the selection before and after, the `inputType`, and the content fingerprints of the ranges it touched (6.9). `ValueBacking` accepts only `InsertText`, `DeleteRange` and `SetSelection`; a formatting intent on a text control is not an edit and fires no `beforeinput`, as Input Events says for unsupported types.

**Two backings (ED-D3).**
- **`DomBacking`** applies operations through `hg-dom`'s script-free core (DM G91): each operation is a DOM algorithm step (insert, remove, replace data, split text) with live-range updates and mutation records, so `MutationObserver`, live ranges and the semantic plane see exactly what a script making the same change would cause.
- **`ValueBacking`** keeps a text control's value in a **piece table** (an original buffer, an append buffer and a balanced tree of pieces with cumulative UTF-16 lengths): insert and delete cost O(log n) in the number of pieces, not O(n) in the value's length, so typing into a 10 MB `textarea` costs about the same as into an empty one (ED-31). The UA shadow tree's inner text is a **view** onto the piece table: layout reads the value's text through `hg-text` by pieces, never through a DOM Text node holding a copy (layout and accessibility amendments, 9.5). A script `value` write that changes the value **replaces** the table with a new original buffer (no append-buffer growth, so masked inputs and controlled components that set the value on every keystroke use memory proportional to the value, not to the history of writes) and clears the history (6.9). The `value` getter returns a cached external string (JS-D4's text arena), materialized once after a change, so a page that reads `value` after every keystroke of a very large value pays O(n) per read; ED-31 states that case separately.

**Layering.** The backing traits (`EditableBacking`, implemented by `hg-dom`'s adapter and by `hg-forms`' piece table) and a `CredentialPolicy` trait (implemented by `hg-forms`, G148) live in `hg-edit-model` (L2), so `hg-edit` depends only downward and `hg-forms` calls `hg-edit` for the edits it initiates (autofill, 6.6) without a cycle.

Why one engine: the text stack already supplies one set of movement rules (TX 6.8a), and the IME protocol, spelling, undo and the accessibility exposure each need one model to work over; two editors would need every rule, every IME fix and every test twice, and would drift. The usual reason for a separate text-control editor is the DOM's cost for large values, which the piece table removes. Why a piece table and not a rope: both give O(log n) edits; the piece table never copies the original value and its pieces are immutable, so a snapshot for the IME protocol or an undo inverse is a list of piece references rather than a copy of text.

### 6.2 Edit intents, `beforeinput` and the default actions (ED-D1)

**The pipeline.** For each intent: (1) compute the **target ranges** (`getTargetRanges()`; for `deleteWordBackward` the word before the caret, by `hg-caret`'s movement over the model), covering "only the code points that the user agent would normally replace, even if they are only part of a grapheme cluster", as Level 2 now requires ([SS 2.6][SS]); (2) dispatch `beforeinput` with `inputType`, `data` or `dataTransfer` and the static ranges on the editing host or text control, through DM's dispatch; (3) if not cancelled, and the intent is still valid (its target ranges are still editable and their content fingerprints unchanged, because listeners may have mutated the DOM), apply the **default action** as one transaction; (4) queue `input` with the same `inputType` and `data`; (5) the selection change schedules `selectionchange` with the per-target coalescing bit the Selection API defines ([SS 1.6][SS]).

**Composition follows Input Events Level 2 as it reads today.** Every `inputType` is cancelable except `insertCompositionText`, and the composition sequence is `compositionstart` → (`compositionupdate`, `beforeinput` `insertCompositionText`, `input`)* → `compositionend` ([Input Events Level 2, WD 2026-10-15](https://www.w3.org/TR/input-events-2/), [SS 2.3–2.4][SS]). UI Events states the opposite order and cancelability ([SS 2.10][SS]); Izcal follows Input Events, whose current text states this model and which Chromium and Gecko are reported to follow (Firefox implements Level 1's model, [HP 2.4][HP]), pending the black-box measurement Q-ED-1; it records the conflict as a divergence and files it with both groups, together with Level 2's stale `contentEditable=typing` passage ([SS 2.5][SS]). The removed commit-time types (`insertFromComposition`, `deleteByComposition`, `deleteCompositionText`) are not implemented. An editor that wants to own composition uses EditContext (ED-D2), which is the design the Editing WG converged on for exactly that need ([HP 1.8, 2.3][HP]).

**The default actions are Izcal algorithms (ED-D1).** No current specification defines what `insertParagraph`, `deleteContentBackward` across a block boundary, `formatBold` or `insertFromPaste` do to a DOM: HTML delegates the editing host's behaviour to the execCommand draft, which defines 40 commands with about a dozen open TODOs, `undo` and `redo` among them ([SS 4.2, 5.2][SS]). Izcal writes each default action as a published algorithm in its **editing companion** (the model of the text stack's shaping specification), one section per `inputType` and per command, under these rules:
1. **Where the execCommand draft defines an algorithm and the shipping engines agree with it in black-box tests**, Izcal implements the draft's algorithm and anchors to it. WPT `editing/run/` encodes the draft's expectations, and the best engine passes 96.0% of it ([SS 5.7][SS]).
2. **Where the draft is silent or the engines disagree**, the editing companion writes its own rule from first principles (the smallest DOM change that produces the intended rendering and selection, under rules 3 and 4), with a test. Editor frameworks' normalizers, run as black-box test oracles, are a **regression signal** that triggers review of a rule when they rewrite Izcal's output; they never define correct output (HGBA-2 D1: observed behaviour is a differential signal, never the definition).
3. **Minimal markup**: the draft's principles ("Keep the markup as concise as possible", [SS 5.4][SS]); formatting uses the elements the commands name unless `styleWithCSS` is set.
4. **No surprise mutations**: a default action changes only nodes inside its target ranges' block ancestors up to the editing host and never normalizes the rest of the host, because editors reconcile against the DOM they last wrote ([HP 4.11][HP]).
5. **Paragraph separator**: `div` by default, changeable by `defaultParagraphSeparator`, as the draft defines.
6. **Every algorithm is anchored** (G9, G149) to its companion section and to the `inputType` it implements; the companion is filed with the Web Editing WG as it is written, so the editing behaviour the web has never had in writing gets an implementer-backed text.

**`execCommand` (part of ED-D1).** `document.execCommand`, `queryCommandState`, `queryCommandValue`, `queryCommandEnabled` and `queryCommandSupported` map each command to the same default-action algorithms through the draft's command-to-`inputType` table (`delete` → `deleteContentBackward`, `insertText` → `insertText`, `undo` → `historyUndo`, [SS 5.3][SS]). The draft's steps fire a cancelable `beforeinput` before the command; Chrome does not, Safari does with an empty `inputType` ([SS 5.3, 4.11][SS]). Izcal follows the draft's steps, because an editor that cancels an intent should see every intent, and records the divergence; the reversal trigger is breakage in the editor corpus (ED-3). Transactions made by `execCommand` join the undo history, which is why authors use `execCommand('insertText')` to keep undo working ([GO 6.2][GO]). Commands that exist in fewer than two engines are not implemented (DM-D15's rule). 1.19% of page loads call `execCommand` ([DM 6.12][DM]); it is compatibility work, not the foundation for editors ([HP 1.10][HP]).

**`contenteditable="plaintext-only"`** uses the DOM backing with an operation filter: only text operations and line breaks (Enter is `insertLineBreak`), and paste inserts `text/plain` only. It shipped in all three engines in 2025 ([HP 1.9][HP]).

**`designMode`** makes the document's root an editing host through the same machinery, with HTML's setter steps ([SS 4.3][SS]).

**The empty-block caret.** HTML's rendering section says the caret in an empty editing host "is expected to act like an inline replaced element with the vertical dimensions of the caret and with zero width" ([SS 4.3][SS]); `hg-caret` asks layout for exactly that box (9.5, layout amendment).

### 6.3 Script points and the script-free core (G140)

Editing was one of the engines' largest sources of use-after-free bugs, and the Firefox Editor and Selection bug titles name script running inside an editing operation: a `selectstart` handler removing a table cell, clipboard events, edit rules replaced "while running scripts" ([SR 1.1–1.4][SR]); Chrome removed mutation events in version 127 because they "have been the source of many crashes and security bugs" ([SR 1.5][SR]).

**The script points.** Each is typed by DM-D5's `ScriptToken`: `keydown`, `keypress` and `keyup`; `selectstart` (cancelable, before a selection replaces an empty or collapsed one, [SS 1.7][SS]); `beforeinput`; composition events; clipboard events (`copy`, `cut`, `paste`); drag events; `beforematch`; the **post phase** of an edit (below); `input`; `select` and `change` on text controls; `selectionchange` (queued, never synchronous); focus changes caused by editing (DM 6.5). The legacy `textInput` event is decided by DM-D15's two-engine rule.

**The transaction is the core phase only.** An edit that inserts nodes (paste, drop, `insertHTML`, a paragraph split that clones elements, `formatBlock`) triggers DOM steps that may run script: post-connection steps and custom element reactions run after insertion, as DM's two-phase tree edits define (DM 6.1, 6.6). Izcal therefore splits every edit in two. (1) **Core phase**: `hg-edit` applies all operations under DM's `CoreGuard` (G91, G140), collecting post-connection steps and queued reactions without running them, and **ends the transaction** there: the selection, the undo entry and the `TextEdit` records are final. (2) **Post phase**: the collected post-connection steps and the `[CEReactions]` reaction queue run as **one declared script point**, as they would after the same insertion by script. Then the selection is revalidated by node id and generation, `input` is queued, and `selectionchange` is scheduled. A listener (in `beforeinput`, `connectedCallback` or anywhere else) that mutates the DOM can therefore never leave the core holding a dangling reference; at worst the intent becomes invalid before the core phase and is dropped, which is recorded (6.16). `execCommand('insertHTML')` passes its argument through Trusted Types at the sink, as DM generates for every HTML sink and as Chrome and Safari enforce for this command ([HP 1.10][HP], DM 6.16).

### 6.4 Caret and selection behaviour (`hg-caret`, ED-D16)

**Ownership.** The Selection API defines one selection per document with at most one range, leaves the caret undefined for non-collapsed selections, and leaves affinity unspecified and unexposed ([SS 1.1–1.2][SS]). DM owns the Selection object and its range (DM 6.6); this spec owns how the selection **behaves**: where a click, a drag, a double click, an arrow key or an AT request puts it; how it extends; where the caret is drawn; and which highlight ranges paint receives. AX's caret browsing (AX 6.12) uses `hg-caret` for non-editable text, so caret browsing and editing move identically.

**Movement.** Every movement is a function `move(position, direction, granularity, context) → position`:
- **Character**: next grapheme boundary (TX 6.8a), with the code-point backspace rule for scripts whose clusters are typed as several marks (TX 6.8a, recorded as black-box observations).
- **Word**: UAX 29 words tailored with the SA and CJ dictionaries (TX 6.6), with the platform convention for where a forward word move stops recorded per OS as a configuration value from a black-box observation at ED-M0 (Q-ED-4). The convention is visible to script through `Selection.modify()` and `getTargetRanges()` for `deleteWordBackward`; it reveals the OS family, which the environment record already exposes, and PRIV-2 counts it (expected about 0 extra bits); Izcal's full-uniformity profile (D-S1) uses one convention everywhere.
- **Line**: layout's line records (LY 6.5.2) with a **goal x** kept across consecutive vertical moves; `caretPositionFromPoint` on the target line.
- **Paragraph, page, document boundary**: block boundaries in the box tree; page by the scroll container's page size.
- **Visual movement in bidi text (ED-D16)**: left and right arrows move in visual order using TX's visual-to-logical maps; at a boundary between runs of different direction, the caret has two candidate visual places, and Izcal draws the caret at the place given by its affinity with a direction tick (6.7). Selection extension with Shift moves visually too, while the selection itself stays a logical range, which can paint as several discontiguous visual pieces. The Selection API maps `left` and `right` through the resolved bidi level and lets UAs use "additional context (such as caret affinity)" at a boundary ([SS 1.4][SS]); the per-OS convention (visual everywhere, or logical on some OSes) is a black-box observation at ED-M0 (Q-ED-3), recorded as configuration.
- **Editable boundaries**: movement never enters a non-editable island inside an editing host except to skip it as one unit, and never leaves the editing host by arrow keys (it stops at the boundary); the shipping engines' behaviour is measured at ED-M0 (Q-ED-4).

**Selection by pointer.** Click places the caret with `caretPositionFromPoint` (LY 6.15); drag extends; double click selects a word, triple click a paragraph, with the click count from DM's `detail`; `user-select` (CSS UI 4) decides what is selectable, computed by ST; selection across shadow boundaries follows `getComposedRanges` ([SS 1.5][SS]). Touch and pen selection (handles, long-press) are the shell's affordances over the same functions.

**The caret record.** After each change and at each flush, `hg-caret` publishes a **caret record**: the caret rectangle in the editing host's coordinate space (from the cluster map and the line box; width from LY-D11's caret width), its colour (`caret-color`), its direction tick, and whether it should blink. The record goes to paint (6.7), to the IME protocol as the caret rectangle (6.5), to the semantic plane (AX 6.8) and to the Windows system-caret mirror (AX 6.8).

### 6.5 IME and composition: the renderer side and the protocol (ED-D4, ED-D5, ED-D6)

**The constraint.** TX-D23 put the OS input-method frameworks in the process that owns the native window, and no IME code in a renderer ([TX 6.8a][TX]). The frameworks disagree on who asks whom. TSF and `NSTextInputClient` are **pull** models: the input method queries the text store for text, selection and rectangles at any moment and expects the answer before the call returns. Wayland's `text-input-unstable-v3` is **push**: the client sends surrounding text, cursor rectangle and content type, and the compositor answers with serial-stamped batches. Android is a pull across processes that already tolerates a slow editor for "a couple seconds" ([IM 1.1, 6.1, 7.2][IM]). The document is in another process, and the broker must never block its UI, input-routing or IPC threads on a renderer: a compromised or busy renderer would freeze every window. Mozilla answers the synchronous queries from a cache the content process pushes; Chromium's documented Mac design blocked the UI thread on a timed wait of up to 1.5 s ([IM 4.1–4.3][IM]). The failures Mozilla recorded were in what the cache held and when it was trusted ([IM 4.5–4.6][IM]).

**The design (ED-D4): one push-first, versioned protocol on every OS, shaped like text-input-v3.**

1. **Focus sessions.** The broker mints a **session id** each time it grants text-input focus to an editable in a frame (DM's focus, routed by the broker). Every snapshot, request and acknowledgement carries it; anything with a stale id is dropped and recorded. A session ends on blur, tab switch, window deactivation, navigation, renderer crash, or when the renderer has not acknowledged a request for 500 ms†; ending a session **commits** an active composition (or cancels it, where the OS convention measured at ED-M0 says so, Q-ED-1) and resets the OS context (`ITfContext` termination on Windows, `discardMarkedText` on macOS, `restartInput` on Android, `disable` on Wayland). Text typed into one field can therefore never be delivered to another, the race Mozilla's "Typed text appears in unfocused textarea when using IME" names ([IM 4.6][IM]).
2. **The snapshot.** For the focused editable (text control, editing host or EditContext), `hg-ime` publishes a `TextInputSnapshot` in two parts with one **version** (monotonic per session). The **text part**, at the end of each task that changed it: a **text window** that is the intersection of the paragraph containing the selection and ±2,048† UTF-16 code units around it, hard-capped by ED-41 (a bounded window answers Mozilla's finding that a whole-text cache "may be too big", [IM 4.3][IM]), its offset in the whole text, the selection, the composition range and clause attributes, and the input hints (`inputmode`, `enterkeyhint`, `autocapitalize`, `autocorrect`, `spellcheck`, `writingsuggestions`, input type, credential mode, private window), mapped per OS by `hg-ime-hints`. The **geometry part**, at the next rendering update after layout, so publishing never forces a layout: the caret rectangle (the caret record of 6.4), **per-grapheme rectangles** for the composition plus 64† graphemes around the caret, the editor's bounds and visible rectangle, the writing mode and direction. In credential mode the text part has **no text field at all**: the snapshot type is `Redacted` by construction (G142).
3. **The mirror and its speculative overlay.** The broker's `hg-ime-host` keeps, per window, the latest snapshot plus a **speculative overlay**: every request the input method has made and the renderer has not yet acknowledged, applied to the snapshot's text window by pure text and selection arithmetic (no layout). Every synchronous OS query is answered from **snapshot ⊕ overlay**, in microseconds: TSF `GetText`, `GetSelection`, `GetTextExt`, `GetACPFromPoint` and `GetScreenExt`; Cocoa's `selectedRange`, `markedRange`, `attributedSubstring(forProposedRange:actualRange:)`, `firstRect(forCharacterRange:actualRange:)` and `characterIndex(for:)`; Android's `getTextBeforeCursor`, `getExtractedText` and `CursorAnchorInfo`. An input method therefore reads back its own pending writes (TSF within its write lock, Cocoa right after `setMarkedText`, Android within a batch edit), which a snapshot alone cannot do. Rectangles for speculative text fall back to the caret rectangle or, on TSF, to `TS_E_NOLAYOUT`. Coordinates arrive in the frame's space; the broker converts them to screen coordinates with the frame geometry **it** placed (parent-supplied, LY 6.14's clamp rule) and clamps every rectangle to the frame's visible area, so a renderer cannot place a candidate window over the shell (UI-10).
4. **TSF locks.** Read locks are granted synchronously against snapshot ⊕ overlay. **Write locks are granted synchronously too**, against the overlay, so `TS_LF_SYNC` requests succeed and the TIP's writes become requests (rule 5) at lock release; Izcal returns `TS_E_SYNCHRONOUS` only when TSF's own rules require it (a synchronous request while a lock is held, [IM 2.2][IM]). **Snapshots arriving while any TSF lock is held are queued** and applied at release, followed by `OnTextChange`, `OnSelectionChange` and `OnLayoutChange`, because a document must not change under a granted lock ([IM 2.3][IM]).
5. **Edits are requests, not writes.** The input method's actions travel to the renderer as typed `ImeRequest`s carrying the session id and the **snapshot version they were based on**: `SetComposition(text, clauses, cursor)`, `Commit(text)`, `DeleteSurrounding(before, after)`, `SetSelection(range)`, `ReplaceRange(range, text)` (reconversion, autocorrect, dictation corrections), `FinishComposition`, `CancelComposition`. TSF write locks, Cocoa's `setMarkedText` and `insertText`, Android's `setComposingText`, `commitText`, `deleteSurroundingText` and batch edits, and a text-input-v3 `done` batch (applied in the protocol's seven-step order, [IM 6.3][IM]) all become these requests. The renderer applies each through edit intents (6.2): composition requests produce the composition events and `insertCompositionText`; a commit produces `compositionend` and the commit's `input`; `ReplaceRange` is `insertReplacementText`.
6. **Rebase or resync.** If the request's base version is current, it applies. If the renderer changed the text since (a script edit, an earlier request), it **rebases** the request's offsets through the transactions in between when they do not touch the request's range, and otherwise **rejects** it, applies nothing, and publishes a fresh snapshot; the broker drops the overlay and tells the input method the text changed (`OnTextChange` and `OnSelectionChange` on TSF, `discardMarkedText` on Cocoa, `restartInput` on Android, a new committed state on Wayland). Forced commit and cancel are emulated in the renderer from the last composition string, the only behaviour that works when the input method's answer is asynchronous ([IM 4.4][IM]).
7. **Hold notifications until acknowledged.** The broker does not report a selection or text change to the OS until the renderer has acknowledged every request sent before it, so the input method never sees a state that contradicts its own pending edits (Mozilla's ContentCache rule, [IM 4.3][IM]); an acknowledged request leaves the overlay. A missing acknowledgement ends the session (rule 1).
8. **Stale answers, per OS.** A query outside snapshot ⊕ overlay is answered honestly: TSF returns `TS_E_NOLAYOUT` only for ranges outside the cached rectangles, then sends `OnLayoutChange` when the next geometry part covers them, and never immediately after reporting a layout change (Mozilla bug 1187351, cited in [IM][IM]'s implications; candidate windows were misplaced in at least eight input methods around `TS_E_NOLAYOUT`, [IM 4.5][IM]); Cocoa receives the nearest cached answer and `invalidateCharacterCoordinates()` and, from macOS 15.4, `textInputClientDidUpdateSelection()` when the snapshot changes ([IM 5.4][IM]); Android's `InputConnection` runs on a **dedicated IME thread** of the broker (named through `getHandler()`, [IM 7.2][IM]), never the UI, input-routing or IPC threads, and that thread may wait at most 200 ms† for an out-of-window answer from the renderer before answering from the snapshot (G142); Wayland needs no queries. The snapshot's window is set from what real input methods ask for, measured at ED-M0 (Q-ED-2b), within ED-41's bound.
9. **One offset unit inside.** Offsets are UTF-16 code units inside Izcal, as the DOM, Cocoa, TSF and Android count; the broker converts to UTF-8 bytes for Wayland at the edge and never splits a surrogate pair (Android's warning, [IM 1.2][IM]); conversion is tested on astral characters and grapheme clusters.

**Keys.** The broker sends each key event, with the OS's layout information and **every request the input method produced from it**, to the renderer as one recorded input group. When the input method consumed the key, the renderer's `keydown` has `key` `"Process"` and `keyCode` 229 and is not cancelable in effect, as UI Events allows ([SS 10.1–10.2][SS], [IM 8.1–8.3][IM]); when the input method did not consume it and `keydown` is cancelled, the renderer drops the group's non-IME intents (on macOS, the `insertText:` and `doCommandBySelector:` results of `interpretKeyEvents`). `isComposing` is true inside a composition; dead keys produce composition events with `key` `"Dead"`. Where engines differ, the rule is recorded as a divergence (Q-ED-1). On Linux without an input method, Compose and dead keys are resolved in the broker from the XKB keymap and Compose tables through `xkbcommon-dl` (MIT), which loads the system's libxkbcommon (an OS library at run time, not shipped).

**Per OS.**
- **Windows**: TSF through `ITextStoreACP2` with the lock model of rule 4 ([IM 2.1–2.3][IM]); `ITfContextOwnerCompositionSink`; IMM32's `WM_IME_REQUEST` answered from the same mirror for legacy IMEs; `TS_SD_UIINTEGRATIONENABLE` and the touch-keyboard status flags set from the hints ([IM 2.6][IM]); the touch keyboard through `InputPane` and the UI Automation exposure AX provides ([IM 3.1][IM]). Where TSF runs is ED-D5.
- **macOS**: an `NSTextInputClient` view per window in the broker, with all 21 members answered from the mirror ([IM 5.1][IM]); `interpretKeyEvents` drives key handling; input sources run in their own processes, so no third-party input-method code enters the broker.
- **Linux**: Wayland `text-input-unstable-v3`, version 2 where the compositor offers it (Mutter 51, KWin 6.7; version 1 elsewhere; none in Weston, [IM 6.5–6.6][IM]), with surrounding text cut to the protocol's 4,000-byte limit ([IM 6.2][IM]); on X11, the IBus and Fcitx D-Bus front ends through `zbus` (MIT), with XIM as the fallback. No prose specification of the IBus and Fcitx D-Bus interfaces was found, and their source and repository XML may not be used (M-1 part 3), so the interfaces are derived by **black-box runtime introspection** (`org.freedesktop.DBus.Introspectable` against running daemons) and message logging on the rigs, recorded as observations (Q-ED-16). Izcal never loads GTK or Qt input-method modules (toolkit libraries, [IM 12.6][IM]).
- **Android** (with S-8): an `InputConnection` in the browser activity's view on the dedicated IME thread, with batch edits held as one request group and `CursorAnchorInfo` from the geometry part; `EditorInfo.setInitialSurroundingText` from the text part ([IM 7.1–7.7][IM]).

**Secret fields and private windows (ED-14).** In credential mode (6.6) the snapshot carries **no text** (rule 2), and the OS signal is set as each platform's documentation prescribes ([IM 10.5][IM]): on Windows, **text services are disabled** for the field, because Microsoft says "all passwords fields should have text services disabled" and `IS_PASSWORD` "is not supported" ([InputScope](https://learn.microsoft.com/en-us/windows/win32/api/inputscope/ne-inputscope-inputscope), [IM 2.7][IM]); on macOS, **secure event input** is enabled while the field has focus and released on blur, window deactivation, tab switch, window hide, navigation, renderer crash or hang, as TN2150 requires ([IM 10.6][IM]), with input sources restricted to Roman through `allowedInputSourceLocales` ([IM 5.4][IM]); on Android, `TYPE_TEXT_VARIATION_WEB_PASSWORD` with `IME_FLAG_NO_PERSONALIZED_LEARNING`; on Wayland, purpose `password` with hints `sensitive_data` and `hidden_text` ([IM 6.4][IM]). **Private windows** set the "do not learn" signals on every field (Android `IME_FLAG_NO_PERSONALIZED_LEARNING`, which names browsers' private modes as its use case; Wayland `sensitive_data`; Windows `IS_PRIVATE` where measurement shows input methods honour it, Q-ED-11). **Generative OS text tools**, both rewriting (macOS Writing Tools, Android's API 36 writing tools) and inline suggestions (macOS inline predictions), are reported off (`NSWritingToolsBehavior.none`, `setWritingToolsEnabled(false)`, `inlinePredictionType` off) unless the person has turned AI on (B10) and enabled them, whatever `writingsuggestions` says ([IM 5.6–5.7, 7.5][IM]).

**Surrounding text and TX-16 (ED-D6).** TX-16 says no page-controlled string reaches an OS text API in the broker; its target is OS **shapers** meeting hostile strings (the Telugu-class crash, [TX 6.12][TX]). An input method, however, needs the text around the caret for reconversion, prediction and autocorrect: Android input methods read it constantly, and macOS autocorrect is reported to work only when the engine owns the text ([IM 7.2][IM], [HP 3.9][HP]). This spec therefore asks TX to restate TX-16's scope: page-controlled text reaches the OS input-method interface **only** as the bounded text window of the focused, non-credential editable the person is typing in — **at most ±2,048 UTF-16 code units around the caret** (the bound is restated in the shell spec's 6.16 and 6.18), never for hidden tabs or credential fields, and only to the input-method API (never to a window title, menu, notification or other OS text surface). On macOS, Linux and Android the input methods run in their own processes; on Windows, under ED-D5 (b), the text store lives in the UI host, not the broker. TX-16's fuzzing extends to the snapshot path (9.5).

**Where TSF runs (ED-D5).** TSF loads each text input processor's DLL into the process that owns the focused window ([IM 2.9][IM]); under TX-D23 that is the broker, which holds every site's cookies, credentials and grants. Third-party TIP crashes already land in host processes ([IM 4.7][IM]), CTF had "no access control whatsoever" for nearly twenty years ([IM 10.1][IM]), and some input methods "download and upload user input on the fly" ([IM 2.9][IM]). **New evidence since TX-D23**: the accessibility spec designs a **window-owning UI-host process** for Windows that holds no grants, cookies or credentials, owns the HWNDs, receives OS input and forwards it to the broker as untrusted data (AX-D9 (b), [AX 6.10][AX]). That process is where TSF should run. The options: (a) TSF in the broker, as TX-D23 states; (b) TSF in the UI host, adopted on Windows **for input methods even if accessibility software does not need it**, with the snapshot mirror mapped read-only into the UI host and requests forwarded to the broker as untrusted, validated messages; (c) a separate low-rights input process owning a child HWND, if TSF permits a text store on a window whose top-level parent another process owns (Q-ED-2a). **Decided by the owner (21 October 2026): (b)**, measured at ED-M0 together with AX-M0's gate (input-routing latency, AT and IME behaviour, mitigations gained). If (b) fails for a specific input method or adds latency, the fix is made within (b) or by (c); falling back to (a), which would put third-party DLLs back into the process that holds every credential, is an **owner decision** that must name the assets reachable, never an automatic fallback, and the broker's code-integrity mitigations are never relaxed for input methods without that decision. Under (b) the UI host becomes an always-on process kind on Windows, with its own FP 8.2 row (9.5).

**EditContext.** An EditContext editing host publishes its snapshot from the EditContext's own state (`text`, selection, composition, control, selection and character bounds pushed by `updateText`, `updateSelection`, `updateControlBounds`, `updateSelectionBounds` and `updateCharacterBounds`), and requests become `textupdate`, `textformatupdate`, `characterboundsupdate` and composition events **at the EditContext**, as the specification requires ([SS 3.1–3.4][SS]). Because Izcal's IME protocol already speaks a buffer, EditContext is a thin surface over it (ED-D2).

### 6.6 Text controls (`input`, `textarea`)

**What HTML fixes.** A text control has a value, a dirty value flag and "either a selection or a text entry cursor position at all times"; the selection API (`select()`, `setRangeText()`, `setSelectionRange()`, `selectionStart`, `selectionEnd`, `selectionDirection`) counts code units of the relevant value (`textarea`'s API value is CRLF-normalized); `selectionDirection`'s platform behaviour is written out per OS; UI selection changes "must be implemented using the set the selection range algorithm"; the value setter moves the cursor to the end when the value changes; `maxlength` and `minlength` errors count only when the value "was last changed by a user edit" ([SS 4.8–4.9][SS]). `hg-forms` (DM) owns the value modes, validation and submission; this spec owns how the value is edited, over `ValueBacking` (6.1), with the same intents, `beforeinput`, IME, movement, spelling and undo as editing hosts. `getTargetRanges()` is empty for text controls, as Level 2 specifies ([SS 2.6][SS]); the per-control "last changed by a user edit" bit is set by `hg-edit` on every transaction and cleared by script setters.

**Credential mode (G148).** One predicate in `hg-forms`, `is_credential_field`, is true for `input type=password`, for any field that **has ever been** `type=password` in this document (the "show password" toggle that sent revealed passwords to a cloud speller, [SR 6.5][SR]), and for fields whose `autocomplete` names a credential, one-time code or payment card. In credential mode: no spellcheck, autocorrect or writing suggestions whatever the author says; the IME signals of 6.5 and no text in the snapshot; copy and cut of the value disabled for `type=password`; DevTools recordings hold placeholders (DT 6.5). Every crate asks the one predicate; none re-derives it.

**Script-set values and undo.** HTML says nothing about the undo history when script sets `value` ([SS 4.10][SS]). A script write that changes the value **clears** the control's history (and replaces the piece table, 6.1): undoing across a script rewrite would restore a state the page never saw the person create, and keeping unreachable entries would only cost memory. Edits the person makes afterwards are undoable as usual. The shipping engines' behaviour is measured at ED-M0 (Q-ED-6); the reversal trigger is breakage in the editor or form corpus.

**Autofill boundary.** Autofill data stays in the broker until the person chooses a fill in **broker-drawn UI** (DM-D20; Chromium's own threat model says a renderer-tracked gesture "can be forged", [SR 8.3][SR]). The chooser **lists every field it will fill**, and the broker sends values only for those fields, so a page that hides fields under a visible form (hidden-field phishing, [SR 8.1][SR]) receives nothing the person did not see listed. Izcal's autofill UI is never in the page's DOM, which removes the DOM-based clickjacking that defeated 11 of 11 password-manager extensions ([SR 8.2][SR]). Each fill enters `hg-edit` through the autofill door as one `insertReplacementText` transaction per field (G141), undoable as one step. A suggestion's preview is drawn by the shell in a separate, non-interactive OS window above the field and never written into the renderer; because that window lies over the page area, Section 9.5 asks the shell owner for a UI-10 amendment covering it and the Paste popup (6.10).

**Large values.** The piece table, a line-start index and the text stack's per-line shaping cache keep a 10 MB `textarea` responsive (ED-31). IME composition that would exceed `maxlength` is truncated at commit, not during composition; the shipping engines' behaviour is measured (Q-ED-7).

### 6.7 Painting the caret and the selection (ED-D15)

**The caret is a compositor-animated item.** Paint (GR 6.3) emits the caret record's rectangle as a display item in its own paint chunk under its own effect node. The caret's **blink** is an opacity animation on that effect node, run by the compositor (GR 6.8), so a blinking caret costs no renderer frame and no raster (ED-34). Blink timing comes from the OS through `hg-ax-prefs` (Windows' caret blink time and timeout, macOS's insertion-point blink periods, the GNOME and KDE settings, Android's), and blinking **stops** after the OS timeout, after 5 s† without input, under `prefers-reduced-motion`, and when the person turns blinking off in Izcal's settings, which CSS UI 4 asks UAs without a user style sheet to provide, citing WCAG guidelines 2.2 and 2.3 ([SS 7.8][SS]). The phase is a function of recorded BeginFrame ticks (GR 6.9), so captures replay identically.

**Reserved compositor node.** GR caps compositor-mutable nodes at 16† per document (GR 6.3). The caret's effect node is **reserved outside the cap** (one per document with a focused editable), because a caret that lost compositor mutability would repaint twice a second for as long as the person reads; Section 9.5 asks GR for the amendment.

**Stacking.** CSS UI 4 leaves the caret's stacking position undefined beyond "must not be hidden by the element's background" ([SS 7.8][SS]). Izcal paints the caret **last within the editing host's stacking context** (after its positioned descendants), clipped by the host's overflow clip but allowed to extend into its scrollable overflow, and records the rule in the editing companion and with the CSS WG. `caret-color` is honoured; `caret-shape` and `caret-animation` (Chrome only, [SS 7.9][SS]) wait for the admission rule (LY-D10).

**Selection and other highlights.** `hg-caret` publishes the selection's ranges, spelling and grammar results (6.8), the find matches (6.12) and the text directive's target; ST computes the highlight pseudo-elements, of which only `color`, `background-color`, text decorations, `text-shadow`, `stroke-color`, `fill-color`, `stroke-width` and custom properties apply, with highlight inheritance ([SS 7.1–7.2][SS]); paint draws one **overlay per highlight type** in CSS Pseudo 4's order (`::selection` over `::target-text` over `::spelling-error` over `::grammar-error` over `::highlight()`, with `::search-text` directly below `::selection` in Izcal), each overlay a chunk keyed by (text fragment, highlight type), so a selection change re-emits only the overlay chunks it touched and never the text ([SS 7.3][SS]). The overlay covers the em box; whether it extends to the line box is a recorded Izcal rule, since the specification is unsure ([SS 7.3][SS]). The Custom Highlight API is an Interop 2026 focus area and is implemented with it ([SS 7.5–7.6][SS]).

**Bidi caret.** At a direction boundary the caret is drawn at its affinity's position with a one-device-pixel tick pointing in the direction of the run it belongs to, so the person can see where typed text will go (Q-ED-3 measures what the shipping engines draw).

### 6.8 Spelling, grammar, autocorrect and writing suggestions (ED-D7, ED-D8, ED-D9, ED-D19)

**What is checked.** HTML's eight-step algorithm decides whether an element's text is checked (text-like `input` types, mutable `textarea`, Text children of editing hosts; user overrides beat attributes; [SS 4.4][SS]), in the language given by `lang`, else the person's languages; never in credential mode (6.6). Words are UAX 29 words tailored by TX's dictionaries; CJK and South-East Asian text is segmented by TX-D12's dictionaries and checked only where a lexicon covers it.

**Engine (`hg-spell`, ED-D7).** One engine family over **compiled lexicons**: a lexicon is a finite-state automaton with integer weights compiled by `hg-lexc` from the language-data track's sources (stems; inflection and compounding rules; an error model of keyboard adjacency, common confusions and phonetic equivalences; word frequencies). Checking a word is an automaton walk; suggestions are the k-best paths through the composition of the error model and the lexicon, ranked by integer weights. Two published families exist: Hunspell's word list with affix rules (prefix and suffix stripping, twofold suffixes, compounding flags, REP, MAP, KEY and PHONE suggestion tables, [SL 2.1–2.2][SL]) and weighted finite-state spellers built for morphologically rich languages (the GiellaLT and Divvun work for Sámi and other circumpolar languages; the finite-state research rows are Low-confidence, [SL 2.5–2.6][SL]). Izcal's language-data track writes lexicons in **Izcal's own source format** only, covering both kinds of description, and `hg-lexc` compiles them into one automaton form; third-party dictionaries and lexicons are never inputs to shipped lexicons, only test oracles loaded by `hg-spell-eval` (TX-D14). Norvig's analysis of his 68–75% result names a trivial error model, unknown words (his "more serious" source of error) and the lack of context ([SL 2.3][SL]), which is why the error model, coverage of the lexicon and a sentence-level context score are all language data authored with linguists, not constants. Word frequencies and error-model confusions come from text Izcal commissions or licenses for that purpose under terms that allow MIT distribution of derived counts; evaluation corpora are test-only (any licence). Results are bit-identical on every OS and ISA: no floating point (G146), lexicons from the engine image only.

**Where it runs.** In the renderer, on a **worker thread** of the renderer's pool, over a snapshot of the changed text. Results return to the script thread through a **registered decision point** ("spelling or grammar result applied", JS-D15 (b), DM's register and G93): applied when ready, logged when recording, enforced in replay and seeded in simulation, so recorded sessions replay to the same display list (ED-50). The text is the page's own and the lexicons are shared read-only engine-image data (FP-D13), so a renderer gains nothing from the spellchecker that it did not have. This **departs from TX 6.8a, the ledger's C-22 recommendation and Stage 1 A-S1-75**, which placed spellchecking in a utility process; the reasons: the risk Hunspell's record shows (memory bugs in its affix and suggestion paths, [SR 6.1–6.2][SR]) comes from memory-unsafe parsing of complex dictionary files at run time, while `hg-spell` is safe Rust (`forbid(unsafe_code)`) whose lexicons are compiled and validated at build time; and a separate process would add IPC for text the renderer already holds. (Firefox's own response was an in-process RLBox sandbox, for general reasons, [SR 6.3][SR].) The amendments are in 9.5. The broker is not a better place either: there is no reason to add page-text processing to the broker beyond the bounded IME window of 6.5.

**Invisible to script, including through timing.** CSS Pseudo-Elements 4 **requires** UAs to mitigate pages reading the styling of spelling and grammar highlights and pages "attempting to track performance impacts of styling highlighted segments via programatic modification of text fields", because the user's dictionary "can include the user's name and even … their address book" ([SS 7.4][SS]). Izcal therefore:
- never exposes results through the DOM, CSSOM or events, and restricts the highlight pseudo-elements to non-layout properties;
- runs checking off the script thread;
- checks a text range **only if its content arrived through a person's door** (keys, IME commit, paste, drop, an applied suggestion): `hg-edit` keeps a provenance bit on text runs, so words a script wrote are never checked, even in a field the person has typed in, and a page cannot probe a word list by writing candidates; text the page itself supplied (from markup or script, such as a saved draft) is checked word by word as the person edits it, a visible difference from other browsers accepted because CSS Pseudo 4's mitigation is normative;
- paints spelling overlays so their cost does not depend on which words are flagged (one spelling overlay chunk emitted for every line fragment of a checked field, empty or not);
- **omits spelling and grammar overlays from every capture a page can receive**: tab, region and element capture (`getDisplayMedia` with the current tab, `cropTo`, `restrictTo`, GR 6.27) composite without those overlay chunks, which is cheap because they are separate chunks (9.5, graphics), and any future element-to-pixels API excludes them and the caret and selection highlights;
- measures the residual with a timing and self-capture attack harness (ED-15).
**Autocorrect is the disclosed residual**: an autocorrection is a visible DOM change, so it reveals that the lexicon rejected the original word. Autocorrect therefore consults **only Izcal's lexicons** (never the personal dictionary and never the interim OS tier), only on text the person typed, and its signal is counted in PRIV-2 (ED-D19). Because autocorrect makes lexicon behaviour web-observable, the lexicon set belongs in FP-D13's every-build data set, which is where this spec puts it (ED-40).

**The personal dictionary.** Words the person adds are user data shared across sites, so they live in the broker (`hg-spell-user`). The renderer asks the broker only about words its lexicon rejects, and the broker answers **only for words whose characters it routed to that frame in the last 60 s†** (keys, IME commits, pastes, applied suggestions; the broker saw every one), at most 60† words a minute, near typing speed. A compromised renderer therefore learns nothing about words the person did not type there; the residual is recorded in the threat model (ED-16). "Ignore" is per document and stays in the renderer.

**Languages and the interim tier (ED-D8).** **Staged to Stage 2** (Stage 1 13.2; shell amendment, 21 October 2026): the shell's Language and writing settings group stays hidden until the feature ships, and when it does the disclosure row names the OS service and what it receives. A language ships spellchecking when its lexicon passes the **lexicon gate** (ED-6). Until then: (a) **Izcal only**: no spellchecking in that language; or (b) an **interim OS tier**, as TX-D25 did for fonts: for a language without an Izcal lexicon, a short-lived **interim spell utility**, **keyed by the renderer key it serves** ((site, container), or origin where FP-D8 keys renderers by origin; I-1), at the strictest sandbox tier and exiting when idle, asks the OS spelling service (macOS `NSSpellChecker`, the Windows Spell Checking API, Android's spell checker service, Enchant's local back ends on Linux) for ranges, **only when the provider is the OS's own local one**, never a third-party or cloud provider (Windows and Android accept third-party providers whose privacy Izcal cannot know, [SL 4.5–4.8][SL]). Results differ by OS and by the person's OS dictionary but are never script-visible (they never feed autocorrect or any other script-visible behaviour), so they add no fingerprint; they are recorded as inputs. The utility never calls OS "learn word" or replacement APIs that would write to the person's OS dictionary. **Recommendation: (b)**, with a per-language switch in settings and the shell saying which languages use the OS, because Firefox's add-on site offers about 200 dictionaries for about 170 locales (AMO API, 2026-10-20, per the fact-check; [SL 3.4][SL]) and leaving most languages without spellchecking for years is a real cost to people, while the OS interfaces are allowed. The interim ends language by language as lexicons pass ED-6. Reversal: evidence that a provider Izcal classified as local sends text off the device, or owner preference for (a).

**Grammar (ED-D9).** `hg-grammar` checks sentences with rule sets authored per language by the language-data track (patterns over tokens, lexicon tags and morphology from `hg-spell`'s automata), offline, deterministic, never cloud. **A learned grammar model is a Stage 2 feature** (ML service spec ML-D2) behind **the AI grant, the `ai` build feature, and the person's own choice** (B10); Stage 1 has rule sets and no model at all, so ED-D9's condition is not weakened. LanguageTool's rule counts give the scale: 8,251 rules for Catalan, 6,074 for English and 892 for Russian, while most of its other 31 languages have fewer than 500 ([SL 3.6][SL]). A language's grammar ships only when its rules pass a **precision gate** (ED-7), because false flags teach people to ignore the feature. `::grammar-error` paints the result.

**Autocorrect (ED-D19).** On touch devices the OS input method corrects (Android input methods through `InputConnection`), and Izcal passes `autocorrect` and `autocapitalize` as hints (6.5). On desktop, Izcal performs autocorrect only when the OS setting for the person's keyboard asks for it (macOS "Correct spelling automatically"; Windows' hardware-keyboard autocorrect) and the element's `autocorrect` state is On (HTML's states and defaults, with `password`, `email` and `url` always Off, [SL 1.5–1.6][SL], [SS 4.6][SS]): a correction is an `insertReplacementText` transaction with its own `beforeinput`, undoable in one step, using `hg-spell`'s top suggestion from Izcal's lexicons only (above), above a per-language confidence threshold (ED-8). Smart quotes and dashes follow the same OS setting.

**Writing suggestions.** `writingsuggestions` (Chrome 124, Safari 18, [SS 4.5][SS]) is passed to the OS input method as a hint for non-generative suggestions (Windows text suggestions, keyboard word predictions); generative suggestions such as macOS inline predictions follow the AI switch (6.5); Izcal itself offers none unless AI is on (B10).

### 6.9 Undo and redo (ED-D14)

**One history per editing host and per text control**, plus one for a `designMode` document. A history belongs to its element and is dropped when the element leaves the document (and kept if it is moved within the same task, which DM's move steps cover). Each entry is a transaction (6.1) with its inverse operations and **content fingerprints**: a 64-bit hash of each touched range's content and the node ids and generations of its endpoints after the transaction.

**Validation.** Before applying an undo or redo, `hg-edit` checks that the ranges the entry covers still have their recorded fingerprints. If script changed them, that entry and every older entry that depends on the changed nodes are **dropped**, the undo is a no-op that fires no `input`, and the drop is recorded for DevTools ("undo entry dropped: content changed by script in task 4182"). Undo therefore never applies a stale inverse to a DOM it no longer describes, which is why seven editors called browser undo "useless or harmful" once they intercepted any edit ([HP 8.2][HP]).

**Coalescing.** Consecutive `insertText` intents coalesce into one entry until a word boundary after 1 s† of recorded time without typing, a caret move, a different `inputType` or a composition commit; deletions coalesce likewise; each IME composition is one entry. The shipping engines' grouping is measured (Q-ED-6).

**Editors and the native history.** `historyUndo` and `historyRedo` fire `beforeinput`, cancelable, as Level 2 says. In other engines they fire only when the native history has entries, so editors that handle all input themselves never receive them (w3c/editing #509, [SS 4.10–4.11][SS]); Izcal dispatches them for **every** undo or redo gesture on a focused editing host, even with an empty native history, records this as a divergence and files it, because it is the hook editors asked for ([GO 6.1][GO]). `execCommand('undo')` and `('redo')` invoke the same intents. Script DOM changes do not enter the history; they become invalidations (above). A way for a page to tell the browser its own undo state (for the Edit menu) does not exist in any specification; Izcal files the need with the Web Editing WG rather than inventing an API (DM-D15's rule).

**Bounds.** At most 1,000† entries or 16 MiB† of inverse data per history, and 64 MiB† across all histories of a renderer, whichever comes first; the oldest entries drop first, across histories.

### 6.10 The clipboard (`hg-clipboard`, ED-D10, ED-D11, ED-D12)

**Only the broker touches the OS clipboard.** No renderer has a handle to the Windows clipboard or OLE data objects, `NSPasteboard`, the Wayland data device or primary selection, or Android's `ClipboardManager` (G143, checked by loaded-library closure and an OS-symbol lint). Compromised renderers have attacked clipboard IPC in both other engine families, up to sandbox escapes and arbitrary file reads ([SR 2.10][SR]), so every clipboard message from a renderer is validated like any IPC-R17 input: formats from a fixed set, sizes bounded, the sequence number checked.

**Copy and cut.** A copy keystroke or menu command is routed by the broker to the focused frame's renderer as a recorded input. The renderer fires `copy` or `cut`; if a listener sets data and cancels, those items are used; otherwise the default action serializes the selection into `text/html` (the one serializer over the range's fragment, with the formatting styles the receiving application needs inlined) and `text/plain` (the rendered-text serialization), as the Clipboard API's "should create alternate text/html and text/plain" says ([SS 6.2][SS]). The renderer sends a `ClipboardWrite` with the items, its origin and the input's sequence number; the broker writes only if that sequence number is a copy or cut gesture it routed to that frame, within that event. **A person's copy is defined by broker facts only**: a copy or cut keystroke or menu command the broker routed, with no listener having replaced the data, over a selection last set by a gesture the broker routed (the renderer reports the selection's last cause; a compromised renderer can lie about it, which is the recorded residual). Everything else is **script-originated**: `navigator.clipboard` writes, every `execCommand('copy')` or `('cut')` (the classic pastejacking path selects a hidden field and calls it, [SR 2.1][SR]), and every write a `copy` listener changed. `execCommand('paste')` returns false for web content; it never reads the clipboard. All HTML a renderer produces for the OS, the default serialization included, goes through the sanitizer utility (below), because the renderer may be compromised. **No source URL is written**: the Windows HTML format's `SourceURL` field and its equivalents tell every application the person pastes into which page they copied from, so Izcal omits them (a privacy choice recorded as a divergence; Q-ED-9 measures what the other engines write).

**Paste.** A paste keystroke or menu command makes the broker read the OS clipboard **once**, build a **paste bundle** (types; `text/plain`; `text/html`; images re-encoded as PNG after decoding in the media process, MD-20; files as broker-granted read handles for those files only; `web ` custom formats), and send it with the input to the focused frame's renderer. The renderer fires `paste` with a read-only `DataTransfer` over the bundle; nothing is cached for later reads, and synthetic `paste` events never touch the bundle ([SS 6.3][SS]). In the event, `getData('text/html')` returns the HTML as the source application wrote it, minus source-URL fields, and with `file:` URLs (Office-family HTML carries paths such as `file:///C:/Users/<name>/…`, which reveal the account name) rewritten to opaque placeholders whose images are offered as `File` items in the same bundle; editors need Office and Docs markup to keep formatting, which Chrome's sanitized async reads lose, and raw HTML is what Chrome and Firefox return in paste events ([HP 5.8][HP], [SS 6.6][SS]). Both rewrites are recorded divergences (Q-ED-9). The **default action** (`insertFromPaste`, when no listener cancels) parses the HTML with ST's **`SanitizingSink`** under Izcal's **paste configuration** (no script, no event handlers, no `javascript:` URLs, no `form`, `iframe`, `object`, `embed`, `meta`, `base`, `link` or `style` elements, inline styles reduced to the formatting properties the `format*` intents can produce) and inserts **the sanitized tree itself**, never a re-serialized string, so no second parse can mutate it; this closes the shape every copy-paste XSS bypass shared ([SR 3.1–3.5][SR]). Nothing referenced by pasted content is fetched or exposed (no remote images loaded, no `file:` paths), as the specification requires ([SR 3.6][SR]); remote images in pasted HTML become broken-image placeholders until the person or the editor loads them through ordinary page fetches. `text/plain` line endings are normalized to LF.

**Async reads (ED-D10).** `navigator.clipboard.read()` and `readText()` require transient activation checked against the broker's record (DM-D20), a focused document, **and** the person pressing a **Paste button drawn by the prompt renderer** in a broker-owned OS window at the pointer or caret (shell amendment, 21 October 2026: one consent surface, one security property, SH-D13), which page content cannot draw over or imitate. The Clipboard API now requires transient activation and "user interaction with a 'Paste' element created by the user agent or operating system" ([SS 6.7][SS]); Firefox and Safari additionally enable their button only after 1 s, and Izcal does the same ([SR 2.8][SR]). A press elsewhere, Escape or 5 s† without a press rejects with `NotAllowedError`, **except that the 5 s† timer is suspended while the popup has keyboard focus or pointer hover and can be extended with Enter or Space**, so the time limit never traps a person who needs longer (WCAG 2.2.1). The popup lies over the page area, so Section 9.5 proposes a UI-10 amendment for it. The button is skipped only when the OS clipboard's change counter (the Windows sequence number, `NSPasteboard`'s `changeCount`, the Wayland offer serial) still equals the one recorded at a write by the same (origin, container, tab), so a write by another application, origin or container always shows it. There is **no persistent "always allow" grant**, because the clipboard routinely holds passwords and one-time codes copied from other applications and Chromium's persistent grant turns one decision into indefinite access ([HP 5.6][HP]). An async read returns the same bundle a paste would, with `text/html` sanitized by `SanitizingSink`'s paste configuration and serialized (Chrome and Safari sanitize async reads; [SS 6.6][SS]); the `unsanitized` option (Chrome only, negative WebKit position) waits for the admission rule. `clipboardchange` (Chrome only) waits likewise.

**Async writes and ClickFix (ED-D11).** `navigator.clipboard.write()` and `writeText()` require transient activation from the broker's record and a focused document; the `clipboard-write` permission's `allowWithoutGesture` is never granted by default. Activation does not stop ClickFix, because the decoy's click is real ([SR 2.2][SR]). Izcal adds, without blocking any write:
1. **Provenance and a log.** The broker records every script-originated write (a write that is not the default serialization of the person's own selection) with origin, time and types, keeps the last 20† in the shell's clipboard panel with a preview, and shows the same records in DevTools.
2. **A quiet notice** for script-originated `text/plain` writes: "site.example copied text", for 4 s†, without focus or sound, which a person can turn off per site.
3. **A command-text warning.** If a script-originated write matches Izcal's published **command-text patterns** (shell invocations such as `powershell`, `pwsh -enc`, `cmd /c`, `mshta`, `curl … | sh`, `iex`, `bash -c` with a download, Run-dialog paths), the notice becomes a warning: "This site put a command on your clipboard. Websites never need you to paste commands into Run or Terminal." The patterns are versioned list data maintained by the lists track (NW) and matched deterministically. **ClickFix ownership is split with the phishing protection spec** (PH-D13): this spec owns command-text warnings and the pattern list, the phishing spec owns URL checks and paste-and-go, the lists track maintains both, and the same event never produces two warnings. A developer copying a command from a documentation page by selecting it never sees a warning (that is a copy of their own selection); a copy button on a documentation site shows the quiet notice. ED-17 tests both corpora.

Microsoft's ClickFix guidance offers OS-side mitigations, user awareness and SmartScreen warnings on known landing pages in Edge, and nothing about the clipboard write itself ([SR 2.3][SR]); the broker is the one component that sees the write, its origin and its activation together. The command-text patterns are authored by the lists track from published prose reports; no third-party rule set (IOC or YARA collections) is shipped.

**The clipboard log's retention.** The log and previews are kept in memory only, cleared when the window closes, never kept in private windows, and credential-shaped text is masked in previews.

**Formats, web custom formats and the OS (ED-D12).** The mandatory types map to the OS's native formats; optional `text/uri-list` and `image/svg+xml` are supported (SVG is written only as data, never rendered from the clipboard by Izcal). **Web custom formats** (`web ` prefix) are written raw under OS formats named by the specification's JSON map, capped at 100 per session as Chrome found necessary on Windows ([HP 5.7][HP]), and never interpreted by Izcal. **HTML from a renderer is sanitized before it reaches the OS**, because native applications parse it ([SS 6.4][SS]): the sanitizing runs in a short-lived **sanitizer utility process** (no grants, the strictest sandbox tier, G145) with the one HTML parser (G23), never in the writing renderer (which may be compromised) and never in the broker (which parses no page content). The utility and `SanitizingSink`'s paste configuration share one configuration as data, and CI runs a differential between them (ST's G22). **Images written by a page** are decoded in the media process and re-encoded by Izcal's PNG encoder before the OS sees them, as the specification's "may be transcoded to produce a safe version" allows ([SS 6.5][SS]).

**Linux primary selection.** Middle-click paste is supported: the primary selection is offered through the broker only after a pointer or keyboard selection gesture the broker routed to that frame, never for credential-mode fields, and a middle click in a page is a paste gesture with the primary selection's bundle. Script selection changes (`Selection` API calls) never write the primary selection, the bug Firefox fixed as CVE-2023-6208 ([SR 2.9][SR]).

**Limits.** A paste bundle is at most 64 MiB† (larger clipboard contents offer `text/plain` truncated with a notice); pasted HTML deeper than ST's tree-depth limit is flattened by the tree builder's rule; a page may write at most 16 MiB† per write. Each limit is an observable, recorded outcome, not a crash ([SR 10.1, 10.4][SR]).

### 6.11 Drag and drop (`hg-dnd`, ED-D13)

**The drag data store lives in the broker.** HTML's store is read/write only in `dragstart`, read-only in `drop`, and **protected** (types visible, data not) in every other event; UAs "must not make the data … available to scripts until the drop event" and should filter active content "using a safelist", without saying how ([SS 8.1–8.3][SS]). Firefox's drag-and-drop security record is mostly policy bugs, not memory bugs (one of its 34 titles is a use-after-free): cross-origin iframe extraction, a cross-origin iframe that "receives file stream before drop" (filed 2026-09), file-path leaks, files planted on the desktop ([SR 4.2–4.5][SR]). Izcal therefore never puts drag data in a renderer that has not received a drop:
- **Drag start in a page.** The renderer fires `dragstart`, collects the items (or the default: the selection, a link, an image) and a drag image (rastered by the content GPU process of its key), and sends them to the broker with the input's sequence number; the broker refuses drags not started by a routed pointer gesture ("not … in response to script actions", [SS 8.3][SS]). HTML and images follow the clipboard's write path (sanitizer utility, media process).
- **Drag over a page.** The broker hit-tests the pointer itself (LY 6.14's parent-supplied geometry) and routes `dragenter`, `dragover` and `dragleave` to the frame under the pointer with the store's **types and kinds only**; `dropEffect` comes back to the broker, which sets the OS cursor.
- **Drop.** The broker sends the data, once, to the renderer of the frame its own hit test found, with the input's sequence number; files become `File` objects backed by broker-granted read handles for those files only, and file paths are never exposed ([SR 4.4][SR]). A drop into an editing host is `insertFromDrop` through `beforeinput`; a move within one host is `deleteByDrag` plus `insertFromDrop` in one undo step.
- **Drag out to the OS.** Dragging an image or link out never creates an executable or shortcut file (`.url`, `.lnk`, `.desktop`) from page-provided names or data, the class of Firefox CVE-2022-22756 and its successors ([SR 4.5][SR]); file names pass the downloads checks. The Chromium-only `DownloadURL` drag type waits for the admission rule (DM-D15).
- **Drag into browser UI.** A `javascript:` URL dropped on the address bar or tab strip is ignored, and dropped text never navigates without the person pressing Enter ([SR 4.6][SR]).
- **Cross-origin drags within one tab** (a parent into a cross-origin iframe, or back) go through the broker exactly as cross-application drags do.

### 6.12 Find in page and text directives (`hg-find`, ED-D17)

**What HTML now says.** HTML's find-in-page section defines the user query, matches and the active match; closed `details` and `hidden=until-found` content becomes searchable and is skipped again "synchronously (and so is not observable)"; a new active match queues the ancestor revealing algorithm (`beforematch`, opening `details`); and HTML flags a **tracking vector**: toggle and scroll events can reveal the query character by character, which "could be addressed … by not acting on every character the user types" ([SS 9.1–9.2][SS]). Everything else (matching rules, options, frames) is the UA's.

**Coordination across processes.** A tab's frames live in several renderers (I-1). **The find bar is shell UI and owns the counts and navigation** (shell amendment, 21 October 2026; shell 6.8 and SH-32); it talks to the broker's **find coordinator**, which sends the query to every renderer holding a frame of the tab, receives per-frame match counts and the active match's frame-relative rectangle, and drives "next" and "previous" in frame-tree order. Each renderer searches only its own documents, and the coordinator never tells a renderer anything about another frame's matches ([SR 7.1–7.4][SR]).

**Matching.** `hg-find` matches the rendered text (open shadow trees and slotted content included; `display: none` and `visibility: hidden` excluded; skipped `content-visibility` and `until-found` content through layout's synchronous path, LY 6.9) with `hg-unicode`'s caseless matching and canonical equivalence (TX R6). Options, all in the shell's find bar from the start ([GO 7.1–7.3][GO]): **case** (default insensitive, with Turkish dotted and dotless i per the document's language); **diacritics** (default insensitive, with the folding rules written down from Unicode decomposition data and published, so "Match Diacritics" means one documented thing); **whole word** (UAX 29 words with TX's dictionaries, so Thai and Japanese whole-word search works); and **regular expressions** over the rendered text with a linear-time engine, which people have asked a browser for since 2005 ([GO 7.3][GO]). The engine is a shared L2 crate, `hg-regex-linear`, with Unicode-aware classes and case folding from `hg-unicode`, which content blocking's linear-time subset (CB 6.2, today in its broker-side compiler) also moves onto (9.5).

**Revealing and the tracking vector.** Matches are counted and highlighted as the person types, but the active match is **revealed** (`beforematch`, `details` opened, scrolling) only when the person presses Enter or "next", or after 500 ms† without typing, as HTML suggests, so a page cannot read the query from reveal events character by character. In a frame that is **cross-site to the top-level page**, hidden content is counted and highlighted but not revealed (no `beforematch`, no `details` toggling) unless the person moves focus into that frame, so a third-party frame seeded with hidden candidate words cannot learn the query; this is a recorded divergence.

**Highlights.** Matches paint through the highlight overlays (6.7) as `::search-text` once admitted, and as the UA's find highlight until then.

**`window.find()`** (non-standard, all engines) searches its own document only, with no cross-frame reach, and never reveals content in cross-origin frames.

**Text directives** (`#:~:text=`, three engines) use the same matcher with the constant-shape rule the specification requires (no observable early exit); the navigation-side rules (single-use activation, top-level only, opener isolation) are DM's ([SR 7.2][SR], [DM 6.9][DM]). `::target-text` paints through the overlays. The shell's "copy link to highlight" generates a directive with the same matcher, so links it makes are guaranteed to match.

### 6.13 Virtual keyboards, `inputmode` and `enterkeyhint` (ED-D18)

`inputmode` (8 keywords, `none` meaning no virtual keyboard), `enterkeyhint` (7 keywords), `autocapitalize`, `autocorrect`, the input type and credential mode are mapped into each OS's hints by `hg-ime-hints`: Windows `InputScope` (74 values) and the touch-keyboard status flags, Cocoa's input traits, `text-input-v3` content purpose and hints and, in version 2, `set_available_actions(submit)`, Android `EditorInfo.inputType` and `imeOptions` ([SS 4.7][SS], [IM 2.6–2.7, 5.6, 6.4–6.5, 7.5–7.6][IM]). The on-screen keyboard is shown when an editable element receives focus from touch or pen input, or by script focus while transient activation from a touch is present, never on page load. On desktop OSes the keyboard overlays content and the visual viewport is adjusted to keep the caret visible (layout's visual viewport, LY-D13). The **VirtualKeyboard API** and **`interactive-widget`** ship only in Chromium ([SS 10.3–10.4][SS]) and wait for the admission rule; Izcal's behaviour without them is CSS Viewport's default (`resizes-visual`).

### 6.14 Accessibility of editing (with AX)

- **Exact edit records.** Each transaction appends a `TextEdit` record (host or control, range, removed length, inserted text, `inputType`, door) to the mutation log, so the semantic thread raises insert and delete events from the edit itself rather than diffing text (AX 6.8 derives them from diffs; exact records are cheaper and never ambiguous; amendment in 9.5).
- **AT edits** arrive as AX's `SemanticAction`s and run through DM's input-equivalence entry point (G106): set-value is `insertReplacementText`; IA2 `insertText` and `deleteText`, UIA `ValuePattern.SetValue` and AT-SPI `EditableText` map to the corresponding intents with `beforeinput`; set-caret and set-selection go through `hg-caret`.
- **Spelling and grammar to AT.** Error ranges become text attributes in the semantic plane (`invalid: spelling | grammar`), mapped by AX's tables to IA2's `invalid` text attribute, UIA's spelling-error and grammar-error annotations, macOS's misspelled-text attribute and AT-SPI's `invalid` attribute, so screen-reader users hear the errors sighted users see. No specification maps a browser's own marks today ([GO 8.4][GO]); the exact attribute per platform is confirmed black-box against the shipping engines at ED-M0 (Q-ED-13). Exposure is to OS-level AT only, never to script.
- **Composition to AT.** Composition updates from the IME protocol raise UIA's composition text-edit events and the macOS and AT-SPI equivalents through AX's event layer, and the Windows system-caret mirror follows the caret record (AX 6.8).
- **Caret browsing** (AX 6.12) uses `hg-caret`, so caret browsing and editing move identically.
- **EditContext's gap.** EditContext text "is not exposed to assistive technologies"; authors must keep an accessible DOM copy in sync, and canvas editors cannot map pixels to it ([SS 3.5][SS], [HP 3.5][HP]). Izcal's EditContext inspector (6.16) compares the EditContext's text and selection with the semantic plane's and reports divergence to developers.

### 6.15 Determinism (B1)

Recorded inputs this spec adds to the renderer's list (JS-D15; the one whole-renderer recording budget, A-H3-22): key events grouped with the IME requests they produced, with session ids, base versions and the broker's sequence numbers; paste and drop bundles (placeholders for credential-mode content, DT 6.5); clipboard-read button outcomes; interim OS spelling results; personal-dictionary answers; the OS autocorrect, smart-quote and caret-blink settings (through `hg-ax-prefs`); find queries and options. Spelling and grammar **results** are a function of the text and the lexicon version, and the frame at which they are applied is a registered decision point (6.8; DM's register). Everything else (movement, default actions, undo validation, coalescing, the post phase's order) is a function of recorded inputs and engine-image data. The caret's blink phase derives from recorded BeginFrame ticks. In the broker, snapshot answers to OS queries are not recorded (they do not affect the document); the requests they lead to are.

### 6.16 Observability, the virtual IME and the agent edit channel (ED-D20, ED-D21)

**The IIP `editing` domain** (`hg-edit-observe`) gives developers, DevTools and agents (AI on, B9) what no browser shows ([GO 5.1–5.5][GO]):
- **Edit trace**: per intent, the door (key, IME, transfer, AT, agent), `beforeinput` with `inputType`, data and target ranges, who cancelled it (the listener's script position), the transaction's operations, the mutation records, `input`, `selectionchange`, each step with its spec or companion anchor. The **edit explainer** answers "why did this keystroke produce this DOM?" by walking this chain, after the fact in recordings.
- **IME session**: requests, versions, rebases, rejections and resyncs, composition ranges and clause attributes, which input method was active.
- **Undo view**: the focused history with coalescing, clears and drops.
- **Clipboard log**: per transfer, direction, origin, types and sizes, the sanitizer's removals, the notice or warning shown; contents only to the local `devtools-user` (DT 6.5).
- **Spelling explain**: why a word is flagged (lexicon and version, rule, language source), and whether the interim OS tier answered.
- **EditContext inspector**: the EditContext's text, selection, composition and bounds next to the DOM and the semantic plane, with divergence flags ([GO 3.7, 11.10][GO]).
Cost classes follow DM-D18: counters always; traces while DevTools is attached; full detail on replay. Credential-mode content is a placeholder in every record.

**A virtual IME (ED-D20).** Because the broker turns every OS input-method callback into typed `ImeRequest`s, a test can be a source of the same requests: Izcal's automation protocol offers composition with clauses, candidates, reconversion, commit and cancel, and the same shape is proposed to WebDriver BiDi, where an "IME support in actions" request has been open since 2022 and Playwright's since 2021 ([GO 4.3–4.6][GO]). IME sessions recorded on a person's device (with their consent, DT's rules) replay on any OS, which is the reproduction artifact editor maintainers lack ([GO 2.3, 11.1][GO]). Izcal's own IME tests in its WPT-style suite use it.

**One labelled edit channel (ED-D21).** Agents (B9), AT (AX 6.9) and, in Stage 2, extensions edit only through edit intents: a typed `insert text`, `replace range` or `compose` capability that produces the same trusted `beforeinput`/`input` with target ranges a person's input would, recorded with its principal. For agents: `hg-edit` refuses agent intents whose frame's origin is outside the agent's read-write origin set (B9); agent intents **never mint user activation**, so they cannot unlock clipboard writes, pop-ups or the clipboard read path (DM-D20); the IIP `editing` domain sends an `agent(task)` principal records only for origins in its read set, with credential placeholders (DT 6.5); agent clipboard writes are labelled "agent" in the provenance log. They never write the DOM directly or use a "fill" that skips `beforeinput`, which is why AI agents double or drop first letters in rich editors and why Lexical ships a package to stop Dragon editing behind it ([GO 2.7, 10.1–10.2][GO]). Clipboard access by agents goes through the same broker grants and log as a person's, with no read without the person's Paste press. A W3C issue opened 2026-10-05 asks for a sanctioned way for outside tools to edit (it proposes a common API among editors, [GO 2.9][GO]); Izcal proposes its browser-mediated channel there. **The extension client (registered 21 October 2026).** In Stage 2, content scripts of the component host are the third client of this channel and get no other door: they edit only through the same typed intents, which record an `extension` principal label alongside the extension's identity, and their clipboard writes are labelled "extension" in the provenance log exactly as an agent's are labelled "agent" (ED-D21; the extensions spec's EX-D3; the component host never writes the DOM or the clipboard directly).

### 6.21 Representation choices, derived (M-1 part 3)

No structure here is taken from another engine's or library's source. The piece table is a textbook structure chosen for O(log n) edits and free undo (6.1); the snapshot's shape follows the published `text-input-unstable-v3` protocol and the OS interfaces' documentation (6.5); the lexicon automata follow published finite-state spelling research and Hunspell's manual (6.8); the edit trace follows the Input Events and DOM specifications' event and mutation-record definitions; content fingerprints are Izcal's own. Values that only another engine's source would state (undo coalescing, the snapshot window, rate limits, the caret tick) are set here with † or are black-box measurements at ED-M0.

## 10. Risks

| Risk | Likelihood | Mitigation | Trigger to act |
|---|---|---|---|
| **IME behaviour on snapshot misses** (candidate windows misplaced, commits lost) | High at first; the documented history is long ([IM 4.5–4.6][IM]) | Snapshot sized from measurement (Q-ED-2b); the speculative overlay (6.5); the IME matrix in CI on the rigs; per-input-method expectations recorded | ED-4 failures after ED-M1 |
| **TSF in the UI host may not be possible or may add latency** | Medium (Q-ED-2a) | Options (b) and (c) designed; measured with AX-D9 at AX-M0; (a) only by owner decision | ED-D5's reversal trigger |
| **Editor frameworks depend on other engines' quirks** | High | The editor corpus (ED-3) with framework maintainers; divergences recorded and filed | ED-3 below 100% at ED-M2 |
| **Language data takes longer than planned** | High (no per-language effort figure exists, [SL Q-SP-4][SL]) | Interim OS tier (ED-D8 (b)); language waves ordered by speakers served per linguist-year | Fewer than 10† languages past ED-6 by ED-M3 |
| **Spelling timing channel** | Medium | Off-thread checking, script-placed text rule, uniform overlay chunks; ED-15 harness | ED-15 above threshold |
| **ClickFix warning false positives or evasion** | Medium | Pattern list as versioned data; the warning never blocks; the developer corpus | ED-17 |
| **EditContext's spec changes** (built under ED-D2 (c), exposed later) | Medium | Thin surface; follow the WD; tests from WPT | ED-D2's reversal trigger |
| **Clearing undo on script writes surprises authors** | Low–Medium | Measure engines (Q-ED-6); document; editor corpus | Corpus breakage |
| **Spellchecking only person-entered text surprises people** (a saved draft's errors appear only as they edit) | Medium | Documented; the shell can offer "check this field", which marks the field's text as person-entered by an explicit gesture | User reports in early channels |
| **Staffing** (IME and linguist specialists are scarce) | High | Start the IME lab and the language-data extension at ED-M0 | Tracks below 75% of staffing at month 12 |

## 11. Open questions and flagged claims

### 11.1 Open questions

- **Q-ED-1.** The real composition event order and `insertCompositionText` cancelability per engine and OS with real input methods (Microsoft Pinyin, Kotoeri, IBus-Anthy, Gboard), against Input Events Level 2 ([SS Q1][SS], [GO Q1][GO]).
- **Q-ED-2a.** Can TSF's thread manager and text store live in a window-owning process other than the broker (the UI host), and in a child-HWND process (option (c))? ([IM Q1][IM])
- **Q-ED-2b.** What text windows and rectangles do real input methods request, and how many queries per keystroke? This sets the snapshot window within ED-41 ([IM Q2–Q3][IM]).
- **Q-ED-2c.** How long does macOS tolerate a slow `NSTextInputClient` answer before flagging a hang? ([IM Q7][IM])
- **Q-ED-3.** Caret affinity at soft wraps and bidi boundaries, and the per-OS bidi movement convention, per engine ([SS Q6][SS]).
- **Q-ED-4.** Movement at editable/non-editable boundaries and `inputType`s for platform gestures (Option+Backspace, Cmd+Backspace, Ctrl+K/Ctrl+Y, Ctrl+T) per engine ([SS Q7][SS]).
- **Q-ED-5.** `getTargetRanges()` for Backspace over multi-code-point graphemes per engine ([SS Q8][SS]).
- **Q-ED-6.** Undo grouping and the effect of script `value` writes on the history, per engine ([SS Q2][SS], [GO Q2][GO]).
- **Q-ED-7.** `maxlength` with composition per engine.
- **Q-ED-8.** Whether macOS's `NSTextInsertionIndicator` must track content carets for dictation and the input-mode switcher in a broker-owned view.
- **Q-ED-9.** Formats each engine writes on copy (including `SourceURL`) and what each sanitizes on paste, across origins ([SR Q3][SR], [GO Q4][GO]).
- **Q-ED-10.** Whether `interactive-widget` reaches a second engine.
- **Q-ED-11.** What signals each engine sends to input methods in private windows and password fields, and whether Windows input methods honour `IS_PRIVATE` ([IM Q6][IM], [SR Q6][SR]).
- **Q-ED-12.** Effort per language for a production spelling lexicon with morphology ([SL Q-SP-4][SL]).
- **Q-ED-13.** How each engine exposes its own spelling marks to UIA, IA2, AX and AT-SPI ([GO Q3][GO]).
- **Q-ED-14.** Keystroke-to-paint and IME round-trip latency in the shipping engines, on the photodiode and USB-injection rig ([IM Q4][IM]).
- **Q-ED-15.** Whether `window.find()` or find in page reveals cross-origin frame matches in any engine ([SR Q5][SR]).
- **Q-ED-16.** The IBus and Fcitx D-Bus interfaces, derived by runtime introspection and message logging on the rigs (6.5, M-1 part 3).
- **Q-ED-17.** `zbus`'s dependency closure and async runtime under `tools/deny.toml`.

### 11.2 Claims that are single-source, unverified or conflicting

- **Spell-jacking's 30-site figures** (96.7% sent personal data, 73% passwords) come from news coverage; otto-js's own page no longer resolves ([SR 6.5][SR]); BleepingComputer's own test of five sites is the checked source ([SL 4.1][SL]).
- **CVE-2019-1162 as the CTF fix**: from NVD's description and recollection; Project Zero's post does not name the CVE ([IM 10.2][IM], [SR 5.1][SR]).
- **Chrome's switch to Windows TSF and to the Windows spellchecker**: no prose source was found; graded Low ([HP 9.2, 9.5][HP]).
- **Mozilla's EditContext position date**: "positive" was labelled on 2024-12-09 ([HP 3.4][HP]); the specs note dates the position to the 2019 thread ([SS 3.6][SS]). The label date is the correct one.
- **2026 CVE counts** in Chrome components look inflated for reasons not checked ([SR method notes][SR]).
- **`execCommand('insertText')` joins the undo history in all engines**: Medium, not re-tested ([SS 5.6][SS]).
- **Finite-state spelling performance figures** (Pirinen and Lindén) were not read this session ([SL 2.5][SL]).
- **No in-the-wild editing exploit** was found, a gap rather than evidence of absence ([SR 1.12][SR]).
- **Rows used with Medium or Low confidence**: IE 5.5's 2000 date; Midas as an early permission model (the researcher's reading); Firefox 2's checker (MySpell-family; the detail is recollection); Google Docs' 2010 motives; why Gregor's spec stalled; finite-state spellers' coverage and performance; the Hunspell, Nuspell and LanguageTool licences ([HP 1.1–1.5, 4.1, 9.5][HP], [SL 2.5, 3.3, 3.7][SL]).
