HGBA-2.0 defines a Rust-first browser engine that grows with new hardware by **absorbing each device through a sandboxed broker process and a standard, capability-negotiated API**. It does not couple the engine to specific silicon. Every hardware wave that has reached the web so far arrived this way: GPUs through a brokered GPU process plus ANGLE, SIMD through fixed 128-bit Wasm SIMD, and NPUs through WebNN on top of OS ML frameworks ([Chromium graphics overhaul, 2010](https://blog.chromium.org/2010/08/chromium-graphics-overhaul.html); [WebNN status](https://webmachinelearning.github.io/webnn-status/)). HGBA-1.0 broke that pattern in five ways. It treated confidential computing, MPK and Wasm as security or acceleration primitives they are not. It assumed hardware that clients do not have: CXL, Optane, on-die SRAM tiers and quantum co-processors. It let sandboxed content touch hardware directly. It ignored the microsecond-to-millisecond fixed costs of accelerator dispatch. And it ranked performance above security and compatibility. HGBA-2.0 reverses the precedence (security, then compatibility, then robustness, then performance, then hardware reach). It adopts the process-per-site and zero-ambient-authority model every shipping browser uses. It specifies a hardware abstraction layer (HAL) whose devices are asynchronous, can be lost at any time, and always have a CPU fallback. It makes an explicit engine choice: Izcal writes its own JavaScript and WebAssembly engine on a 16 GB† cage with a trusted region (Section 4.2; JavaScript engine spec JS-D1 to JS-D22), because M-1 excludes every engine library and because the engine is where the tier ceilings, the heap and the DOM representation meet (JS 6.8, JS-D17). Each roadmap target is a measurable claim that can fail. Photonic, neuromorphic, quantum, CHERI and client-CXL hardware move to a separate Research Horizon appendix with entry criteria, and none of them is a deliverable.

## 1. Vision: hardware growth comes from brokered abstraction, not silicon coupling

HGBA-2.0 is a browser engine that gets measurably faster, more efficient and more secure as client hardware improves, **without engine rewrites per device generation and without widening the attack surface web content can reach**. "Fully using hardware" means four things. First, the engine scales across CPU cores where parallelism pays. Second, it places coarse-grained work on GPUs and ML runtimes when the measured end-to-end cost, including dispatch and synchronization, beats the CPU. Third, it adopts hardware isolation features (memory tagging, protection keys, capability hardware) as defense in depth on top of process isolation, never as replacements for it. Fourth, it exposes new device classes to the web only through standards that browsers negotiate by capability.

The vision is deliberately narrower than HGBA-1.0's. A client browser in 2026 reaches NPUs only through OS ML frameworks such as Windows ML/ONNX Runtime execution providers, Core ML and LiteRT, and those frameworks make the final placement decision ([WebNN implementation status](https://webmachinelearning.github.io/webnn-status/); [AMD Ryzen AI: Windows ML EPs](https://ryzenai.docs.amd.com/en/latest/winml/winml_ep.html)). It reaches GPUs only through brokered GPU processes: a compositor GPU service and a content GPU process per renderer key. It reaches the network only through Izcal's sandboxed network services, which enforce same-origin policy, CORS, CSP, cookies, HSTS and Local Network Access ([Chrome: Local Network Access](https://developer.chrome.com/blog/local-network-access)). HGBA-2.0 treats these constraints as the architecture, not as obstacles to route around.

Izcal, the engine this spec defines, is **a new engine built from the specifications and first principles**. It is not a derivative of another browser and does not use another browser's components: Izcal writes every part that does browser-engine work itself, and depends only on generic infrastructure (M-1, Section 2).

## 2. Principles in precedence order: security and compatibility outrank speed

When two principles conflict, the higher one wins. A design proposal that trades a higher principle for a lower one needs an explicit, recorded exception in the decision log (Section 7).

| Rank | Principle | Operational meaning | Evidence anchor |
|---|---|---|---|
| P1 | **Security and privacy of the user** | Treat web content as hostile. Renderers hold zero ambient authority. Never co-locate cross-site data in one address space. | ~70% of Chromium high/critical bugs are memory-safety bugs ([Chromium Memory Safety](https://www.chromium.org/Home/chromium-security/memory-safety/)); Spectre forces process isolation ([Google Security Blog: Mitigating Spectre with site isolation](https://security.googleblog.com/2018/07/mitigating-spectre-with-site-isolation.html)) |
| P2 | **Web compatibility and correctness** | Spec conformance (WPT, test262) gates every optimization, and parallel output must be byte-identical to sequential output (ST-5, LY-4). A faster wrong answer is a regression. | Ladybird's zero-mismatch A/B gating ([Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31)) |
| P3 | **Robustness and graceful degradation** | Every accelerated path has a correct CPU fallback. Device loss, driver bugs and OOM degrade performance, never correctness. | WebGPU's uneven platform coverage ([gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)) |
| P4 | **Performance and energy efficiency** | Optimize p95 interaction latency, frame time and energy on the corpus users actually run, measured end to end. | Parallel overhead can exceed gains ([HiPC 2016](https://hpcforge.eng.uci.edu/publication/hipc16-browser/hipc16-browser.pdf)) |
| P5 | **Hardware growth** | Adopt new hardware through extension points (brokered device processes, capability queries, standard APIs) once P1–P4 are satisfied. | Past hardware waves reached the web through OS abstractions plus standard APIs ([Chromium 2010](https://blog.chromium.org/2010/08/chromium-graphics-overhaul.html)) |
| P6 | **Evidence over aspiration** | Every performance number in this spec carries a source or a measurement protocol. Vendor claims are labeled as such. | — |

Two consequences follow. Because P1 outranks P4, HGBA-2.0 accepts the **9–13% memory overhead that Site Isolation imposed in Chrome desktop** rather than sharing renderer processes across sites ([Reis et al., USENIX Security 2019](https://www.usenix.org/conference/usenixsecurity19/presentation/reis)). Because P2 outranks P4, parallel style and layout must produce byte-identical output on the corpus and WPT (ST-5, LY-4); a path that does not is a bug, not an optimization, however fast it is.

**M-1 (method constraint, not ranked): original, first-principles, spec-anchored implementation.** It sits outside the ranking: no P1–P6 trade-off or decision-log exception can override it. It has four parts:

1. **Original, from the ground up.** No code from another browser or browser engine (Servo, Chromium and Blink, WebKit, Gecko and Firefox, Ladybird, Blitz, and their forks) is copied, ported or translated into Izcal, by people or by AI tools, whatever its license (Stage 1 design D-S10). **Izcal also does not use libraries that do browser-engine work, whoever wrote them.** Izcal builds its own JavaScript and WebAssembly engine, garbage collector, DOM, HTML and CSS parsers, selector matching and style system, layout, fonts and text shaping, renderer and rasterizer, network protocols (HTTP/1.1, HTTP/2, HTTP/3 and QUIC), content blocking and the rest of the engine, from the specifications. Libraries extracted from browsers (V8, Stylo, `selectors`, `cssparser`, html5ever, WebRender, wgpu, neqo, `adblock`, Fontations) and independent engine components (Taffy, Parley, HarfBuzz and its ports) are excluded alike. **Allowed dependencies are generic infrastructure only:** the Rust standard library; general-purpose crates whose job is not browser-engine work (data structures, serialization, error handling, hashing, logging, test tooling); cryptography primitives from MIT-licensed crates (the TLS protocol itself is Izcal's own); and OS interfaces and drivers (platform SDKs, graphics APIs such as Metal, Vulkan and Direct3D 12, OS media and accessibility frameworks). **Every dependency and data set that ships must be available under MIT** (alone or as one choice of a dual licence); anything else Izcal builds itself, and it does not ask authors to relicense. **The rule covers reputation-list data as well as code.** No existing precedent authorises shipping a non-MIT phishing or malware feed: OD-L2's exception is test-only, OD-L6 covers standards data, and the licence audit's own-list rule (2.5/OD-L5) authorises Izcal-built lists, not redistributed feeds. The phishing specification's starred owner decision of 21 October 2026 (PH-D14) resolved the question as its recommendation (a): only MIT-compatible list data ships, with a NOTICE; non-MIT feeds are test-only unless the owner later grants a named exception recorded here and in the brief; and the crawl-only floor with its published coverage gap is the fallback. Exceptions: standards data published by the standards bodies themselves (the Unicode Character Database, CLDR and emoji data, WHATWG tables, IANA registries, tz, the OpenType registries, the Public Suffix List, the CT log list), used as data; test-only inputs that never ship (conformance suites such as WPT and test262, oracles, test tools), whatever their licence; and OS interfaces, drivers and the toolchain. The **test-only oracle class** accepted with JS-D9 includes the font and text oracles of TX-D9 (HarfBuzz tools, Core Text, DirectWrite, FreeType and fontTools as black-box CI oracles) and the TLS and cryptography implementations of NW-D19 and NW-D22 (rustls-webpki, rustls, BoringSSL, OpenSSL, NSS, AWS-LC, Go's TLS and the dalek crates); none is linked or shipped. The Vulkan loader is an OS interface on G67's condition, the SPIR-V grammar is standards data, and `dxil.dll` and `d3dcompiler_47.dll` are test-only black-box oracles; all three classifications are recorded with the owner's confirmation in reconciliation 2 Q31. Fonts are content Izcal designs itself; until a script has an Izcal face, OS fonts render it. A dependency whose class is unclear is decided by the owner and recorded in the Stage 1 design; the default is to build it. **When a component would otherwise come from another browser or an engine library, Izcal builds its own from the specifications**; this is the standing answer, not a case-by-case question.
2. **Spec-anchored.** Web-visible behavior is implemented from the normative specification at a **pinned revision**, and every hand-written algorithm carries a **spec anchor** (`// spec: <URL>#<fragment> [step N]`). Where a specification is silent, ambiguous or contradicted by the deployed web, behavior follows documented interoperability evidence, recorded as a **black-box observation** (test case plus each engine's observed result, never a link to its source) and filed upstream as a specification issue.
3. **First-principles.** Architecture no specification governs (data layout, scheduling, IPC, caching, invalidation, process model, tooling) is derived from P1–P6, measured requirements and verified facts. Another engine's design may be cited as **evidence** that an approach works, from a published source, **never as a template**. A published source is prose: papers, documentation and design documents, talks, blog posts, release notes, bug-tracker discussion and standards threads. **No third-party project's source code is evidence**, whether a browser engine, a library, a tool, assistive technology or an OS component: no spec or research note links to its code files, headers, commits, diffs or code reviews, and no constant, data layout or algorithm is read from them. A prose document hosted in a repository counts as prose under OD-7's three conditions: no code file, header, diff or review is opened; a copy outside the repository is cited where one exists; and no constant that appears only beside code is taken. A value only its source states is measured black-box or set from first principles (marked †).
4. **Spec-anchored oracles decide correctness.** Conformance suites (WPT, test262, pinned), formal models, spec-derived property tests and Izcal's own reference paths are the oracles. **Other engines are black-box differential signals only**: a disagreement is triaged against the cited specification section, never resolved by matching an engine's output or reading its code.

**M-1 record (21 October 2026, *Izcal app host* A3).** No text change: the app host's Section 7 shows compliance with M-1 — its component host, manifest, ticket and WASI host are Izcal's own, and its dependencies are generic crates and OS interfaces — and its Component Model and WASI conformance suites are test-only oracles in the test-only oracle class above.

## 3. Architecture overview: a capability-brokered browser kernel

The browser process is a capability broker. Every other process holds only the handles the broker grants: IPC endpoints, read-only shared memory, GPU command-buffer channels and pre-opened files. Capability systems such as Zircon handles, Capsicum and WASI preopens show this model works ([Fuchsia: handles](https://fuchsia.dev/fuchsia-src/concepts/kernel/handles); [Capsicum, USENIX Security 2010](https://www.usenix.org/conference/usenixsecurity10/capsicum-practical-capabilities-unix)). On Linux the handles map to file descriptors under seccomp-bpf and namespaces, on Windows to handles under restricted tokens, job objects and low integrity, and on macOS to Mach ports under Seatbelt ([Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md); [Chromium Linux sandboxing](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/linux/sandboxing.md)).

Data flows down as commands and up as fenced results. Renderers never see device handles. ## 4. Subsystem specifications

### 4.1 Isolation: process-per-site is the boundary, in-process mechanisms are layers

**Requirement I-1 (site isolation).** On desktop, every site gets its own locked renderer process, including cross-site iframes. Chrome made this the desktop default in 2018 as its primary Spectre mitigation, and Firefox enabled Fission by default in Firefox 95 ([Google Security Blog, Jul 2018](https://security.googleblog.com/2018/07/mitigating-spectre-with-site-isolation.html); [Mozilla Security Blog, May 2021](https://blog.mozilla.org/security/2021/05/18/introducing-site-isolation-in-firefox/)). The isolation key, the cache partition, origin keying, the reduced mode and the shared-process exceptions are one design, stated here in five parts.

**(a) Process key.** The isolation key is **(site, container)**: a container is a user-facing policy context, and the same site in two containers gets two processes and two storage partitions. **Extension origins are their own site keys**: an `ext://` origin never shares a renderer or storage key with any other origin, including in reduced-isolation mode (extensions EX-D3, EX-2; storage 6.x). A process holds one site; splits within a site happen only at agent-cluster boundaries, when a site process exceeds 1 GiB† charged or one page monopolises its script thread (FP-D3).

**(b) Partition key and caches.** All network state is partitioned by the networking spec's partition key **F, R, T, C, X, n**: frame site F, route R, top-level site T, container C, the cross-site-ancestor bit X, and the per-navigation nonce n for credentialless iframes, fenced frames and recordings (NW-D7; [Fetch: network partition keys](https://fetch.spec.whatwg.org/#network-partition-keys); [Privacy CG: Client-Side Storage Partitioning](https://privacycg.github.io/storage-partitioning/)). The partitioned state is HTTP cache, connection and socket pools, DNS cache, Alt-Svc, TLS session tickets, HSTS, revocation-check caches, reporting endpoints and service-worker registrations. Inside a renderer, every content-derived cache is keyed by the projection **(T, C, X, n)** (P18): F is fixed by the process's site lock and the process key, and n matters only to navigation requests, so neither adds a distinction inside one renderer; a cache coarser than this key would re-create by timing the leak the network key closes (FP 6.4). The static global exceptions are the broker's own state, the OS interface layer and installed immutable data sets (the Izcal font set, OS font files on integrity-protected volumes and standards data). Shared limits — quotas, connection budgets, the wake grid, cache size caps — are **bounded channels, not closed ones**, measured and published (NW 6.8, FP 6.18.1).

**(c) Origin keying.** Site keying already separates different registrable domains; origin keying stops subdomains of one site from sharing a process, the path Kilger et al. (IEEE S&P 2026) used to exfiltrate data. Origin keying is **on for every desktop device class** (FP-D8); with FP-2's 4 MiB† empty process, the cost is about F_fixed per extra subdomain process, and if FP-7 fails the lever is F_fixed and content duplication, never isolation. On memory-constrained devices the **reduced-isolation threshold is measured by FP-8 on DC-4 and DC-2**, not assumed; origin keying stays on wherever full I-1 holds.

**(d) Reduced-isolation mode.** Below the measured threshold, a documented reduced security mode applies, never silent co-location. It names the engine's duties: per-site cages and caches remain, Spectre hardening remains, and the mode is reported on `izcal://sandbox` (JS-D20). It is **never granted to a riscv64 process**, which has no speculation barrier (JS 6.18).

**(e) Shared-process exceptions.** The one-site-per-renderer rule has one short owner-decided list of shared processes, each with a threat model in the security scope (OD-8): the **compositor GPU service** (every site's composited pixels; parses no display list, path or shader, G63), the **audio service** and the **capture service** (they parse nothing; audio holds output-ready PCM, capture holds granted capture only), and the **ML service**, added on 21 October 2026 on ML 6.2's conditions (ML-D5). Content GPU, media, hardware-decode and CDM processes are keyed exactly like the renderer they serve (origin under FP-D8; GR-D2, MD-D5, MD-D10, SEC-33), and **no footprint target may co-locate them across keys**: the only reduced mode is (d)'s (FP-7, P1).

**Requirement I-2 (zero ambient authority).** A compromised renderer must not be able to open files, sockets, devices, PCIe config space or GPU MMIO. Everything goes through IPC to a broker. This matches every shipping browser's model ([Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md)) and directly removes HGBA-1.0's userspace-driver and PCIe-probing proposals (see changelog). **One recorded exception (revision 2.4.0):** a broker-granted **video-only device** in the hardware-decode process (MD-D10). It is recorded per OS, holds one (site, container)'s decode session at a time, runs no Izcal parser, is fed typed parameters and validated access units, and is listed in the security scope's grant table (MD-S1, MD-S2, MD-S4). No renderer, content GPU process, media process or network service opens a device.

**I-2 note: protected-media host (revision 2.1.3).** To play DRM content without depending on any single licensor (Stage 1 design D-S7), a tab may switch into a **protected-media host**: the operating system's licensed web engine (WebView2 on Windows, WKWebView on macOS) in a process the broker launches. That engine is outside HGBA's renderer trust boundary and keeps its own multi-process sandbox. HGBA's guarantees inside it are limited to what the host exposes: storage per (site, container), content blocking and permission mediation. Content can reach the host only through the browser-mediated switch, which fires on actual encrypted playback, never on a capability probe. Agent tabs never use it.

**I-2 note: device access (revision 2.4.2).** The device-access service is **broker-side**: the arbiter configuration is the only process that calls OS device backends, and the session and enumeration configurations hold no OS handle. No renderer, content GPU process, media process, network service or device session opens a device. Device messages are typed, bounded and accounted, and no file descriptor crosses the browser IPC schema. The MD-D10 video-only exception is unchanged and is **not** extended by device access (devices spec DV-D1 to DV-D15; security scope CON-R6 to CON-R9).

**Requirement I-3 (layered in-process defenses).** Three in-process layers stack on top of the OS process sandbox, and each covers a different bug class. The **engine cage** confines a JavaScript or WebAssembly memory corruption to a reserved virtual region: one **16 GB† cage per process** with a **trusted region** holding verified bytecode, IC programs, stack maps and typed code and buffer tables. No raw pointer to cage memory exists in the safe API (H-1), and everything the cage holds is untrusted data (H-2) (JS 6.1, JS 6.5, JS-D16, JS-D17). Its cost is accounted under JS-27's cage, trusted-region and CFI items, not a borrowed percentage. The **library sandbox** layer remains for foreign code that parses untrusted input; after M-1 2.3.0 no C or C++ codec or parser library remains in Izcal, so its practical members are OS-interface adapters behind their own process boundary, not a Wasm-to-native translator. **Memory tagging** (Arm MTE/EMTE) is applied opportunistically in synchronous mode to privileged processes and native code (I-5).

**Requirement I-4 (MPK/PKU and Arm POE are coarse, bypassable domains).** Protection keys give **16 keys per process**, and any code that gains execution can switch them with the unprivileged `WRPKRU` instruction ([Linux kernel: Memory Protection Keys](https://docs.kernel.org/core-api/protection-keys.html)). Published attacks bypass PKU sandboxes via `WRPKRU`/`XRSTOR` gadgets, `/proc/self/mem`, `mprotect` and signal handling ([PKU Pitfalls, USENIX Security 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/connor); [Garmr](https://www.arxiv.org/abs/2110.04788)). Izcal uses PKU or POE only to separate a few coarse trust domains, such as generated-code pages (writable only on compiler threads) and cage metadata. It is always paired with W^X, control-flow integrity (CET/IBT, BTI/PAC) and syscall filtering that blocks `pkey_mprotect` and `/proc/self/mem` writes ([Cloudflare: Safe in the sandbox](https://blog.cloudflare.com/safe-in-the-sandbox-security-hardening-for-cloudflare-workers/)). PKU never isolates one site from another. Arm POE is upstream in Linux 6.12 behind the same pkeys syscalls ([arm64 6.12 pull](https://lkml2.uits.iu.edu/hypermail/linux/kernel/2409.1/08571.html)). Which shipping Arm client SoCs implement it is unknown.

**Requirement I-5 (MTE is detect-and-deter, not confidentiality).** MTE uses 4-bit tags, so a blind guess succeeds with probability 1/16. TikTag showed that speculative execution leaks tags on Pixel 8, including an attack path against Chrome ([arXiv 2406.08719](https://arxiv.org/abs/2406.08719)). The engine does not rely on MTE for its heap: tags leak through side channels, and a compressed-pointer heap leaves no spare bits. Only Apple's A19-class Memory Integrity Enforcement has a vendor-documented tag-confidentiality design. It is always-on in synchronous mode for the kernel and more than 70 userland processes, and Apple reports only "minimal performance impact" with no number ([Apple Security Research: MIE](https://security.apple.com/blog/memory-integrity-enforcement/)).

**Requirement I-6 (Spectre rules).** In-process isolation protects integrity, not confidentiality, against transient execution. Shared memory across renderer processes must be read-only or same-site. `SharedArrayBuffer` and high-resolution timers stay gated on COOP+COEP cross-origin isolation ([web.dev: COOP/COEP](https://web.dev/articles/coop-coep)). One WebGPU exception is recorded: WGSL atomics are a high-resolution timer, so WebGPU is on by default only in cross-origin-isolated contexts and behind a per-site permission elsewhere, and it is off in the Hardened profile (GR-D11; GR 6.13).

**Confidential computing is out of scope as a content sandbox.** TDX, SEV-SNP and CCA protect a guest VM *from* a malicious host, hypervisor and firmware ([AMD SEV-SNP threat model](https://docs.enclaive.cloud/confidential-cloud/technology-in-depth/amd-sev/technology/threat-model)). A browser needs the opposite direction: protecting the host and user data *from* content. TDX is a Xeon feature and SEV-SNP an EPYC feature ([Intel TDX](https://www.intel.com/content/www/us/en/developer/tools/trust-domain-extensions/overview.html); [AMD SEV](https://www.amd.com/en/developer/sev.html)). Host-driven side channels still break them (TDXDown, CounterSEVeillance) ([SecurityWeek](https://www.securityweek.com/new-counterseveillance-and-tdxdown-attacks-target-amd-and-intel-tees/amp/)). Client secrets such as passkeys and DRM keys stay in the platform's existing enclaves.

**VM isolation is an optional, per-profile tier at most.** Firecracker microVMs start in about 125 ms with under 5 MiB of VMM overhead each, compared with single-digit milliseconds for a process ([Firecracker](https://firecracker-microvm.github.io/)). Microsoft deprecated Defender Application Guard for Edge and removed it in Windows 11 24H2 ([Microsoft Learn](https://learn.microsoft.com/deployedge/microsoft-edge-security-windows-defender-application-guard)). VM-per-site is a non-goal. A VM tier for an "untrusted session" profile on KVM/Hyper-V/HVF hosts remains an open question.

### 4.2 JavaScript and WebAssembly execution

**Engine (decision D2, Section 7).** Izcal ships **its own JavaScript and WebAssembly engine** (JavaScript engine spec, JS-D1 to JS-D22): one engine in every renderer; jitless in the shell, prompt surfaces and DevTools; and a DOM-less embedder for the code-cache builder, the component host, extension agents and the PAC proxy resolver (JS 6.0). Every process holds **one 16 GB† cage with a trusted region** and agent heaps in blocks (JS 6.1, JS-D16, JS-D17). The safe API is a token API — `Mutator<'h>`, `Gc<'h,'m,T>`, `Root<'h,'s,T>` and `Field<T>` — with no raw pointer to cage memory (H-1) and cage contents treated as untrusted (H-2) (JS 6.5). The engine has one precise collector, verified bytecode, stack maps, a machine-code validator, W^X and CFI (JS 6.1, 6.7, JS-10, JS-15). Conformance is identical across tier ceilings and ISAs: test262 ≥ 99.5%†, Intl, and 100% of the Wasm specification suite (JS-1, JS-2, JS-3).

**Tier ceilings.** The profiles are **tier ceilings** (JS 6.8): **Full** (T0/T1/T2, W0/W1/W2), **Baseline** (T0/T1, W0/W1) and **Jitless** (T0, W0). The Jitless ceiling ships as `hg-renderer-jitless-main`, with no code generator in the loaded-library closure (G14, checked on that closure) and OS enforcement (JS 6.8). The default tier is JS-D13's: Full by default, Jitless for Izcal-only renderers and the banking container (SEC-D5), and per-site or enterprise choices exposed as capabilities (FP-D19). Page-facing Wasm runs at the same ceiling: W0 is an in-place interpreter, W1 a baseline compiler and W2 an optimizing compiler on the same back end (JS 6.6).

**Page-facing Wasm** runs inside the engine, because web Wasm needs GC objects shared with JS, JSPI and Web IDL bindings. A separate Wasm runtime for page content would duplicate the GC and the binding layer and split the security boundary, and no independent runtime's embedding model supplies GC, JSPI, JS String Builtins and ESM integration together ([WebAssembly features.json](https://github.com/WebAssembly/website/blob/main/features.json)). Wasm compiles per ISA on the client: W0 interprets, W1 and W2 compile, and Izcal's own code cache is keyed per engine build and invalidated by every engine update (JS 6.6, JS 6.11, JS-D21). The cross-browser Wasm baseline Izcal may assume is GC, exnref exceptions, tail calls, typed function references, SIMD128, threads (behind cross-origin isolation) and JS String Builtins. It may not assume memory64, relaxed SIMD or multi-memory in Safari, or stack switching, ESM integration or shared-everything threads anywhere ([features.json](https://github.com/WebAssembly/website/blob/main/features.json)).

**Internal components** (extensions, privileged plug-ins, sandboxed utilities) run in Izcal's **component host** (the extensions spec; JS-D10), kept out of the page-facing engine. Extension background contexts are agents on the jitless embedded engine, extension pages are own-origin renderers, and content scripts are the one renderer-side exception: isolated worlds that hold no capability tokens (extensions EX-D3). The Stage 2 program, its process model and its staffing are the extensions spec's.

**Component Model semantics, stated precisely.** Calls across component boundaries are **shared-nothing with one copy per crossing**. The host lowers values into the receiver's memory via `cabi_realloc` ([Bytecode Alliance: Road to CM 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)). Zero-copy forwarding arrives only with the future *lazy ABI*, opt-in in a 0.3.x release and the default at 1.0. Async task management currently adds **roughly 3.5x overhead even on synchronous call paths** (same source). Bulk data must cross as `stream<T>` or resource handles, not large `list<u8>`. **No browser ships the Component Model natively**: it is Phase 1 in the CG, it runs in browsers only through `jco transpile` to core Wasm plus JS glue, and CM 1.0 formally needs native implementations in two browser engines ([features.json](https://github.com/WebAssembly/website/blob/main/features.json); [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)). A new engine that shipped native CM would count toward that gate. That makes native CM a possible Stage 3 contribution, not a Stage 1 dependency.

**Wasm does not run on GPUs or NPUs, and JS is not compiled to Wasm for speed.** No credible production system lowers general Wasm to GPU or NPU. The only direct attempt, W2GPU, is a "preliminary study" that generalizes poorly ([W2GPU, LMPL 2025](https://conf.researchr.org/details/icfp-splash-2025/lmpl-2025-papers/22/W2GPU-Toward-WebAssembly-to-WebGPU-Program-Translation-via-Small-Language-Models)). GPU work is written in WGSL through WebGPU, and NPU work is expressed as WebNN graphs. Tools that put JS inside Wasm embed an interpreter, and AOT specialization gains about **2x overall and 3–5x on some benchmarks over that interpreter**, while remaining beta ([cfallin AOT JS](https://cfallin.org/blog/2024/08/27/aot-js/); [NEU PL seminar](https://lists.ccs.neu.edu/pipermail/pl-seminar/2024/000986.html)). The one AOT JS-to-Wasm compiler describes itself as not yet intended for serious use and cannot support `eval`. HGBA-2.0 uses JS-in-Wasm only to *isolate* untrusted script, such as extension sandboxes. It is never a performance path.

### 4.3 Style, layout and CPU parallelism

**Style is Izcal's own** (style spec; ST-D7, ST-D10). Computed styles, style IDs and the canonical touched and committed bytes of the style arenas are **identical for 1, 2, 4 and 8 workers in 100 of 100 runs per corpus page**, including a two-agent, two-thread case of one partition (ST-5). The style system's parallel machinery is its own: feature-indexed invalidation with old-value checks and recorded causes, content-addressed sharing with deterministic identities and per-agent tables (ST-D7, ST-D10). The evidence that parallel style ships at scale is published: a browser style engine in production since 2017 after two sequential attempts, whose public results show **about 0% gain on 2011-era pages** and gains that level off at six threads (ST 2.2, ST 9.5). Parallelism is adaptive; the sequential path is the baseline.

**Layout is Izcal's own** (layout spec; LY-D6, LY-4). The only rigorous measurement of parallel *layout* remains HiPC 2016: **3.2x and 2.5x with four threads on some sites** and no gain on others, because coordination overhead can outweigh the benefit; a predictive model that chose the thread count per page improved performance by up to 94.52% and energy by up to 46.32%, both maximums ([HiPC 2016](https://hpcforge.eng.uci.edu/publication/hipc16-browser/hipc16-browser.pdf)). Layout therefore runs LY-D6's design — phase purity by types, parallel text preparation, independent formatting-context subtrees, re-entry at barriers, an adaptive threshold and a deterministic merge — and its output is byte-identical to sequential: fragment trees, ids and canonical bytes identical for 1, 2, 4 and 8 workers in 100 of 100 runs (LY-4). **P-1 is the joint ST-26 plus LY-26 target**: the sequential path meets its own target, the adaptive path is never slower than sequential by more than 2%† on any corpus page, and the heavy-page and long-text sets reach ≥1.3×† at four workers. Its failure action is LY-D6's: keep the parallel code, raise the threshold, **never demote to untested opt-in code**.

Heterogeneous CPU cores (performance and efficiency clusters) are handled through OS QoS classes and thread priorities, not by pinning. Input, script and frame-critical work run at interactive QoS. Background style and layout of hidden frames, code caching and prefetch parsing run at utility QoS.

### 4.4 Rendering and the GPU service

The GPU service is **two process kinds** (GR-D2). The **compositor GPU service**, one per browser, does only content-independent work: composition, compositor scrolling and animation, colour output and presentation. It parses no display list, path or shader, and holds no content-dependent data (G63). The **content GPU process**, one per renderer key (origin under FP-D8), reads that key's display items and does its raster, atlases, decoded-image regions, canvas, WebGL and WebGPU; it starts with a rendering opportunity, is device-less until it needs a GPU, is volatile when hidden and exits 30 s† later (GR-D2, GR-47; FP 6.6). `Gpu` is an `hg-gpu-hal` device on **Metal, Direct3D 12 and Vulkan only**, bindless where the device offers it and bounded tables per pass otherwise, with barriers from one render graph per process; there is no OpenGL, GLES or Direct3D 11 back end and no WARP or other software device (GR-D1, GR-D3, G66).

**Pixels are canonical.** Integer-only raster and composition run on CPU and GPU for the whole canonical image — snapped scroll offsets, translation and opacity on the compositor — and readable surfaces are canonical too (GR-D3, GR-D12). The CPU and GPU paths produce the same bits, so a device class may take GR-D3's display-only fallback without changing what script can read. **CPU page rendering is the floor; WebGL and WebGPU fail cleanly** where no usable GPU exists (GR-D10). A software WebGL or WebGPU is excluded: a JIT software rasterizer in a privileged process is the class GR-D10 rejects (G66).

**WebGPU exposure** follows a measured clock rule, not a coverage headline (GR-D11): WebGPU is on by default in cross-origin-isolated contexts and behind a per-site permission elsewhere; it has at most four† buckets fixing limits, features and subgroup sizes, 100 µs timestamps, Izcal's builtin library, and it is off in the Hardened profile. **WebGPU-compat means the compat feature level on core hardware**, not a second API. WGSL atomics are a high-resolution timer and are recorded as I-6's one exception (Section 4.1).

**Event-driven rendering** in HGBA-2.0 means damage-region compositing, variable refresh rate, panel self-refresh and gaze-aware foveation where the platform offers it. These features exist and ship. "Neuromorphic displays" do not: no commercial event-driven display exists ([Research Horizon appendix](#appendix-a-research-horizon-speculative-hardware-not-roadmap-deliverables)).

**Nothing in this section applies to fonts or text.** Shaping, glyph rasterization and text layout are the text spec's (TX-D4, TX-D13); the content GPU process receives only bounded glyph masks and paths, in the atlas pools of that key and partition (TX 6.1, 6.10; GR 6.3).

### 4.5 Machine learning and NPU access

**Scope (revision 2.3.5).** The ML service's process model, inference runtime, model set, settings gates and budgets are specified by the **Izcal ML service spec** (ML-D1, ML-D5, ML-D9); this section fixes only how NPUs are reached: OS ML runtimes only, opaque placement. The replacement anchor is ML-D1's, and this section states no inference design of its own.

NPUs are reached **only through OS ML runtimes, behind an ML service process**. Windows ML selects and registers an execution provider per device and accepts policies such as `PREFER_NPU` with automatic CPU fallback ([AMD Ryzen AI: Windows ML EPs](https://ryzenai.docs.amd.com/en/latest/winml/winml_ep.html)). Core ML makes its own CPU/GPU/ANE placement decision. Chromium's WebNN backends are Windows ML/ORT, Core ML and LiteRT, all still experimental, and DirectML has been dropped from the list ([WebNN status](https://webmachinelearning.github.io/webnn-status/); [Microsoft Learn: DirectML](https://learn.microsoft.com/windows/ai/directml)). The HAL therefore models the NPU as an **opaque-placement ML runtime device**, not a schedulable processor.

Vendor TOPS figures do not drive scheduling. Windows 2026 parts claim roughly 50 (Intel Panther Lake), 60 (AMD XDNA 2) and 80–85 (Snapdragon X2 Elite) INT8 TOPS, all from secondary aggregators. Apple publishes no M5 Neural Engine figure ([localaimaster](https://localaimaster.com/blog/npu-tops-list); [Guru3D](https://www.guru3d.com/story/apple-m5-soc-brings-neural-accelerators-to-every-gpu-core)). Measured behavior matters more. In a community characterization, a 0.6B draft model ran **about 3.6x slower per token on the Lunar Lake NPU than on the CPU**, which the author attributed to a high fixed per-inference dispatch cost ([OpenVINO discussion #36484](https://github.com/openvinotoolkit/openvino/discussions/36484)). The NPU won on small matrices and the GPU on large ones in a 2024 Intel study ([arXiv 2409.14803](https://arxiv.org/pdf/2409.14803)).

**Web exposure (revision 2.3.5).** WebNN is exposed only behind a flag until at least one stable browser ships it (see the WebNN reconciliation in Section 9); WebNN stays behind a flag and is not shipped in Stage 1. Browser-owned task APIs (translate, summarize, prompt, writing assistance) implement the WebML CG task-API proposals ([Translator and Language Detector APIs](https://webmachinelearning.github.io/translation-api/); [Writing Assistance APIs](https://webmachinelearning.github.io/writing-assistance-apis/); [Prompt API](https://github.com/webmachinelearning/prompt-api)), which keep the device out of the page and pages never see it. They are **Stage 2** under the AI grant, specified by the ML service spec (ML-D2, ML-M5), not a Stage 1 commitment. The browser picks GPU or CPU once against hardware thresholds. As deployment evidence, Chrome's implementation needs a GPU with **more than 4 GB of VRAM, or 16 GB of RAM and 4+ cores**, plus 22 GB of free storage. NPU use is undocumented in both Chrome and Edge ([Chrome: Get started with built-in AI](https://developer.chrome.com/docs/ai/get-started); [Microsoft Learn: Prompt API](https://learn.microsoft.com/microsoft-edge/web-platform/prompt-api)).

### 4.6 Memory and storage: advisory tiers on real client hardware

Client memory in 2026 is **unified LPDDR5X DRAM**, ranging from about 120 GB/s on mainstream 128-bit buses to **546 GB/s on M4 Max**, with Strix Halo at 256 GB/s ([Apple Newsroom](https://www.apple.com/au/newsroom/2024/10/apple-introduces-m4-pro-and-m4-max/); [Framework](https://frame.work/blog/framework-desktop-deep-dive-ryzen-ai-max)). Intel described Lunar Lake's on-package memory as a one-off ([Wccftech](https://wccftech.com/intel-reaffirms-commitment-to-arc-gpus-panther-lake-nova-lake-sticking-to-non-on-package-memory/amp/)). The tiers a browser can actually influence are: active DRAM; OS-compressed RAM; SSD-backed swap and serialized state; and discard (reload on demand).

HGBA-2.0's memory manager is **advisory**. It classifies each frame and tab as **hot, warm, cold or frozen**, mapped to the footprint spec's pressure states (FP 6.7): hot is visible and active; warm is visible idle or hidden with a declared reason; cold is hidden inside the grace period; frozen is frozen, suspended or in bfcache. The classes map to `madvise` hints (`MADV_COLD`, `MADV_PAGEOUT`, `MADV_DONTNEED`, `MADV_HUGEPAGE`), OS memory-pressure signals and the deterministic reclaim ladder of Moderate, Critical and Emergency (FP 6.7). **Reclaim never needs memory**: the control thread releases from a pre-committed reserve, allocates nothing, runs no GC on the critical path and ranks kills deterministically (FP-15).

Fast restore uses **Izcal's image inventory and its own code cache**, not another engine's snapshots (JS 6.1, 6.11; FP 6.9). Memory is measured as **charged memory per OS**: macOS `phys_footprint` minus GPU; Linux `RssAnon` plus `VmSwap` plus owned shared pages; Windows `PrivateUsage`/commit. **Resident memory is reported beside charged memory**, shared pages are charged once, and every allocation carries a ledger tag (FP 6.2). Each OS's release mapping is explicit: resident, charged and discardable are different quantities. The on-disk class is the **regenerable-cache class** (FP-D16): authenticated; bound to its format version and its writer (the engine build for engine-written members); discarded and never repaired on failure; discarded when the writing process later crashed, failed a check or was killed for a bad message; given a time-to-live per member; never the only copy of user data; and partitioned per (top-level site, container) whenever it holds user- or site-derived state. Its members are the code cache (engine build; per (T, C)), B1 checkpoints, heap export files and suspend files (engine build; per (T, C); suspend files single-use), compiled filter files (source-list hashes and compiler version; per container for user lists, CB-D11), the HTTP cache (format version and a broker-issued security epoch; keyed per NW-D7), compiled user style sheets (written by the shell renderer, mapped only where they apply, never the only copy; ST-D17) and the font-hash cache (written only by the font service; TX 6.4). A member that needs crash consistency, or becomes the only copy of user data, leaves the class for the storage service's crash-consistent store.

Shared-memory IPC is designed from I-2 and the capability model (Section 3): sandboxed processes cannot create shared regions themselves, so the broker allocates them and passes them as handles. Chromium's Mojo, whose broker does the same for sandboxed processes, is evidence that the design ships (evidence only, M-1) ([Mojo docs](https://chromium.googlesource.com/chromium/src/+/HEAD/mojo/README.md)). **io_uring is excluded** from renderer and network-service designs. Google found that 60% of kCTF VRP submissions exploited io_uring, disabled it on ChromeOS and blocks it for Android apps ([Phoronix](https://www.phoronix.com/news/Google-Restricting-IO_uring)).

### 4.7 Network and cryptography

All web-content networking goes through **Izcal's own network services** (networking spec; NW-D3): a **system service**, one per browser; a **container service** per active container; and a **partition service** per active (top-level site, container), plus spares. They speak Izcal's own **QUIC, HTTP/3, HTTP/2 and WebRTC transport**, including DTLS with hybrid key exchange, and Izcal's own **TLS on `hg-crypto`** (NW-D22, NW-D23), with **X25519MLKEM768** by default. The broker mints every socket after bad-port, route, purpose and LNA-ticket checks; the services have no socket-creation rights and hold only their own partition's state (NW-D4). There is no direct NIC, DPDK or vfio path for content: kernel bypass needs exclusive device ownership and root/IOMMU setup, and it would skip every policy check the services enforce ([DPDK Linux drivers](https://doc.dpdk.org/guides/linux_gsg/linux_drivers.html); [Chrome: Local Network Access](https://developer.chrome.com/blog/local-network-access)). All three service kinds are sandboxed on every platform (S-6).

The client accelerations that help live **inside** the services. CPU crypto instructions (AES-NI, ARMv8 Crypto) are reached through `hg-crypto`'s **per-ISA back ends**, never through a provider interface (NW-D23). UDP GSO/GRO batching for QUIC substantially cuts packet I/O overhead, yet only one of four QUIC stacks tested in 2026 used both; Izcal probes GSO/GRO per OS and device and records the result ([TUM NOMS 2026](https://www.net.in.tum.de/fileadmin/bibtex/publications/papers/spaethj-noms2026.pdf); [Cloudflare](https://blog.cloudflare.com/accelerating-udp-packet-transmission-for-quic/)). kTLS and NIC TLS offload are server features, and kTLS does not apply to QUIC.

**Post-quantum TLS runs in software on classical CPUs.** Hybrid **X25519MLKEM768** is the default in Chrome 131+ and Firefox 132+ desktop ([Google Security Blog, Sept 2024](https://security.googleblog.com/2024/09/a-new-path-for-kyber-on-the-web.html); [Cloudflare PQC support](https://developers.cloudflare.com/ssl/post-quantum-cryptography/pqc-support/index.md)), and a secondary source reports more than two-thirds of human TLS traffic to Cloudflare used it by April 2026 ([Encryption Consulting](https://www.encryptionconsulting.com/pqc-support-in-web-browsers/)). Crypto agility is met by `hg-tls`'s **group and signature registries**, not by a provider interface: hybrid by default, policy-controlled fallback, and a path for ML-DSA/SLH-DSA (FIPS 204/205) certificates once the WebPKI adopts them ([NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)). The same hybrid key exchange applies to **WebRTC's DTLS** handshakes, against record-now, decrypt-later attacks on media. Quantum hardware has no role in this.

### 4.8 Implementation language and FFI policy

Rust is the default for new engine code. The justification is narrow and evidence-based: **Rust is the only memory-safe, non-GC language with browser-engine components shipped at scale** — in Firefox's engine components, in Chrome's font stack (the default for web fonts on Linux, Android and ChromeOS since Chrome 133) and in Servo ([Chrome: Memory safety for web fonts](https://developer.chrome.com/blog/memory-safety-fonts); [Mozilla Hacks 2017](https://hacks.mozilla.org/2017/08/inside-a-super-fast-css-engine-quantum-css-aka-stylo/)). Ladybird's 2026 ports add a second engine-core data point ([Ladybird: Adopting Rust](https://ladybird.org/posts/adopting-rust/)). The claim does **not** extend to "the only production-proven memory-safe language". The research did not evaluate Ada/SPARK. Swift 6 offers compile-time data-race checking, but it can be bypassed with `@unchecked Sendable`, and Ladybird dropped Swift over C++ interop and non-Apple platform support ([Swift Package Index](https://swiftpackageindex.com/ready-for-swift-6); [Ladybird](https://ladybird.org/posts/adopting-rust/)).

Rust's guarantees cover only safe Rust. Izcal's foreign surface is the **OS interface layer** — GPU, media and accessibility frameworks and platform SDKs — not a C++ engine: the JavaScript engine, parsers, codecs and network stack are Izcal's own Rust (M-1 2.3.0). Every `unsafe` block and FFI boundary is inventoried and owned by a named reviewer (JS-14). The engine's unsafe core follows **H-1 and H-2**: no raw pointer to cage memory exists in the safe API; `Field<T>` and `Root<'h,'s,T>` carry the edges; the corruption harness treats in-cage read and write as the attacker's premise (JS-10); the machine-code validator, W^X, CFI and shadow stacks are JS-12 and JS-15. Foreign memory is tainted and every input validated, following RLBox's tainted-data discipline ([Firefox RLBox docs](https://searchfox.org/firefox-main/source/security/rlbox/docs/index.md)). C or C++ code that parses untrusted input runs inside a library sandbox or a separate process (Chromium's "Rule of 2") ([Chromium Memory Safety](https://www.chromium.org/Home/chromium-security/memory-safety/)). Fuzzing covers every FFI and unsafe surface. When Izcal replaces one of its own components, or a dependency, with Izcal-built code, the replacement uses **equivalence gating** (D7): the new code must match the old on the component's oracles before the old code is deleted. Ladybird's published results are evidence that the gating works at engine scale, not a method for porting another engine: its Rust frontend produced byte-identical ASTs and bytecode with 0 regressions across 52,898 test262 and 12,461 internal tests, and its CSS parser port required "zero mismatches" in A/B runs before the C++ code was deleted ([Ladybird: Adopting Rust](https://ladybird.org/posts/adopting-rust/); [Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31)).

## 5. HAL specification: asynchronous devices that can fail

### 5.1 Device classes and the capability graph

The HAL exposes **device classes, never vendors**. The classes are `Cpu` (thread pools with QoS classes), `Gpu` (an `hg-gpu-hal` device in a content GPU process), `MlRuntime` (an OS ML framework session in the ML service, with opaque CPU/GPU/NPU placement), `MediaCodec` (Izcal's software decoders and OS hardware decoders; hardware sessions run in the **hardware-decode process** holding a broker-granted **video-only device**, with full-decoder sessions, MD-42's asynchronous conformance check and device-loss fallback, MD-D10, and a colour-output description per window giving descriptor and headroom as a time-varying input) and `Crypto` (CPU instruction-set capabilities reached through `hg-crypto`'s per-ISA back ends, NW-D23). Each device advertises a `Capabilities` record. The **capability graph** has one node per device instance and one edge per data path between nodes. Each edge carries a fixed cost, a per-byte cost and a synchronization cost, measured at startup and refreshed in the background, so vendor peak figures never enter the graph. This follows the research finding that fixed dispatch and sync costs dominate small tasks. A native null-kernel launch costs **about 3–7 µs on Linux and 10–80 µs under Windows WDDM**. Browser WebGPU readback adds an IPC round trip and can wait behind unrelated queued work ([NVIDIA forums](https://forums.developer.nvidia.com/t/too-much-time-for-kernel-launch-latency/233645); [arXiv 2604.17861](https://arxiv.org/pdf/2604.17861); [WebKit bug 272804](https://bugs.webkit.org/show_bug.cgi?id=272804)). On unified-memory SoCs the per-byte cost approaches zero, but the dispatch and sync costs remain.

**Device backends are not a HAL class (revision 2.4.2).** Device access adds no HAL class: the USB, HID, serial, MIDI, Bluetooth and NFC backends are OS-interface adapters in `hg-substrate-os`, on the model of the media OS decoders (MD-D3), reached only by the device-access service's arbiter. They are not schedulable engine devices, carry no capability edges in the graph, and have no CPU fallback because there is nothing to fall back from: a device that is absent is simply absent (devices spec 6.7).

### 5.2 Device interface

```rust
/// Device classes are abstract; vendors never appear in the API.
pub enum DeviceClass { Cpu, Gpu, MlRuntime, MediaCodec, Crypto }

pub struct CostModel {
    pub fixed_dispatch: LatencyDist,   // measured p50/p95, includes IPC to service
    pub sync_roundtrip: LatencyDist,   // submit -> fence signaled -> observed by caller
    pub ns_per_byte_in: f64,           // ~0 on unified memory; measured otherwise
    pub ns_per_byte_out: f64,
    pub provenance: CostProvenance,    // Measured { at, samples } | Default
}

pub struct Capabilities {
    pub class: DeviceClass,
    pub tier: Tier,                    // e.g. WebGpuCore, WebGpuCompat, MlCpuOnly
    pub features: FeatureSet,
    pub limits: Limits,
    pub unified_memory: bool,
    pub cost: CostModel,
    pub epoch: u64,                    // increments on every re-creation after loss
}

pub trait Device: Send + Sync {
    fn capabilities(&self) -> &Capabilities;

    /// Allocation never blocks the caller's frame-critical thread.
    fn create_buffer(&self, desc: &BufferDesc) -> Result<Buffer, HalError>;

    /// All work is asynchronous. Returns a fence on a monotonic timeline.
    fn submit(&self, work: WorkGraph, wait_on: &[Fence]) -> Result<Fence, HalError>;

    /// Readback is only ever a future; there is no blocking map.
    fn map_read(&self, buf: &Buffer, after: &Fence) -> MapFuture; // resolves Ok(view) | Err(HalError)

    /// Resolves exactly once, when the device is lost for any reason.
    fn lost(&self) -> LostFuture;      // yields LossInfo
}

pub enum HalError {
    Validation { detail: String },               // caller bug; sticky per object
    OutOfMemory { scope: OomScope },             // allocation failed; nothing leaked
    Timeout { fence: Fence },                    // watchdog fired; device will be lost
    Unsupported { feature: Feature },            // capability absent at this tier
    PolicyDenied { reason: PolicyReason },       // blocklist, permission, enterprise policy
    DeviceLost(LossInfo),
}

pub struct LossInfo { pub reason: LossReason, pub epoch: u64 }
pub enum LossReason { Destroyed, DriverReset, ServiceCrashed, Blocklisted, PowerOrThermal, Unknown }

/// Every schedulable operation provides at least a CPU implementation.
pub struct Op { pub cpu: CpuImpl, pub gpu: Option<GpuImpl>, pub ml: Option<MlImpl> }
```

### 5.3 Synchronization semantics

Every submission is asynchronous and returns a `Fence` on a per-device monotonic timeline. Cross-device dependencies are expressed only as fences in `wait_on`. On unified memory, a shared buffer still needs a fence before another device reads it; physical sharing does not imply ordering. **No HAL call blocks the renderer main thread or the compositor thread.** Canvas 2D readback is met by in-renderer CPU replay of the canvas command log, and fences from foreign devices are observed on the CPU, never waited on GPU-side (GR-D12, G72). Results consumed by layout, script or compositing in frame *N* must come from fences signaled before frame *N*'s deadline. In practice that means pipelined use of frame *N−1* results, or a CPU result computed in parallel. Frame budgets are 16.7 ms at 60 Hz and 8.3 ms at 120 Hz. With readback round trips that cross processes and can queue behind unrelated work, synchronous per-frame readback is prohibited ([WebKit bug 272804](https://bugs.webkit.org/show_bug.cgi?id=272804)).

### 5.4 Error semantics

Validation errors are attached to the offending object and are sticky, modeled on WebGPU error scopes. They never crash the service or the renderer. `OutOfMemory` fails the allocation cleanly, and the scheduler retries on the next device in the fallback chain. `Timeout` means a service-side watchdog fired, and it is always followed by device loss for that epoch. `PolicyDenied` covers driver blocklists, permissions and enterprise policy, and content cannot tell it apart from `Unsupported`, to limit fingerprinting. Every error path is covered by fault-injection tests (Section 6).

### 5.5 Device-loss semantics

Any device can be lost at any time: through a driver reset, a content GPU or compositor crash, an ML service crash, a power or thermal event, or a blocklist update. When a device is lost, all handles from its epoch become invalid, all pending fences resolve with `DeviceLost`, and `lost()` resolves exactly once. Recovery means asking the broker for a new device of the same class. The new device gets a new epoch, and the broker applies exponential backoff. **Submissions are short (≤100 ms†), a 500 ms† watchdog runs per content process, losses are attributed to the submitting process, and a site is suspended before the class rule applies; the class rule counts only unattributed losses** (GR-D19). **After three unattributed losses within ten minutes, the device class is blocklisted for the session** and the scheduler moves to its fallback. **No fallback moves GPU work to a less sandboxed process** (G66). Web-exposed APIs map onto this model directly: a WebGPU `GPUDevice.lost` promise resolves, and the page may request a new adapter. Neither a GPU service crash nor a content GPU process crash may take down a renderer; the renderer **recovers with one repaint (chunk resend) and no tab reload** (R-2; GR-D19).

### 5.6 Fallback semantics

Every internal `Op` must provide a CPU implementation, following StarPU's multi-variant "codelet" model ([StarPU docs](https://git.microlab.ntua.gr/exa2pro/starpu-max/raw/d32e9b2e2a2bc7b2fd76a287bdf8582e5848554d/doc/doxygen/chapters/introduction.doxy)). Fallback chains are policy-driven and mirror ONNX Runtime's EP policies. `prefer-efficiency` is `MlRuntime(npu-preferred) → Gpu → Cpu`. `prefer-latency` is `Gpu → Cpu`. `hardened` is `Cpu` only. Results must match within a declared numerical tolerance; for rendering, the canonical image makes the reftest match hold **by construction** (GR-D3, GR-D12), and reftests confirm it. **Fallback never moves work to a less sandboxed process** (G66). Fallback is invisible to content except as a change in performance. Web APIs whose specs allow failure, such as a null WebGPU adapter, surface failure instead of emulating the API on the CPU.

### 5.7 Scheduling rules: coarse, batched, measured

The scheduler is **hierarchical**. The browser-level scheduler picks a device class per *task graph*, not per task. Inside the GPU or ML runtime, the native runtime does the fine-grained scheduling. On Apple platforms, for example, Core ML makes the final ANE decision. An offload is admitted only when the following holds, using measured p95 costs:

`est_cpu > fixed_dispatch + sync_roundtrip + bytes × ns_per_byte + est_device`, with a safety margin of at least 1.5x.

Small operations are batched into a single submission, in the manner of CUDA Graphs and operation fusion ([NVIDIA: CUDA Graphs](https://developer.nvidia.com/blog/cuda-graphs)). Data stays resident on the device across stages. `MlRuntime` handles only sustained, quantized model inference of meaningful size, never per-frame or latency-critical microtasks. These thresholds are **design heuristics derived from the evidence, not measured constants**, and Stage 1 must replace them with measured values (target R-6).

## 6. Roadmap with falsifiable targets

Every target below states a metric, a threshold, the measurement method and what happens if it fails. "Corpus" means a published, versioned set of recorded real-world pages plus Speedometer 3, JetStream and MotionMark, run on named reference devices: one x86-64 Windows laptop, one Apple Silicon Mac, one Linux desktop with an Intel Gen12+ GPU and one Android device with ≥4 GB of RAM. There are **no speedup targets relative to another engine before Stage 3, and none promise a multiple.** The only cross-engine ratios before Stage 3 are slowdown caps: GR-30's p95 frame-time ratio ≤1.25×† the best shipping engine at Stage 1 exit, and GR-34's canonical-GPU cost ≤1.15×† a float prototype; neither claims an Izcal speedup (graphics spec 9.4). **P-1 is the joint ST-26 plus LY-26 target**: the sequential path meets its own target, the adaptive path is never slower than sequential by more than 2%† on any corpus page, and the heavy-page and long-text sets reach ≥1.3×† at four workers. It is calibrated below the HiPC 2016 best case (3.2x) because the same study found no gain on some sites. Its failure action is LY-D6's, never an untested opt-in path.

**Why the engine decision is made before Stage 1.** The engine determines the heap boundary, the binding generator, the code-cache format, the tier ceilings and the update cadence. Changing it after Stage 1 would change every component specification at once.

- **One boundary and one representation.** JS objects, Wasm objects, inline caches, verified bytecode and the DOM's edges live in one 16 GB† cage with a trusted region; a separate page-Wasm runtime would duplicate the collector and the binding layer and split the security boundary (Section 4.2; JS 6.5, JS-D17).
- **The security claim is structural.** No raw pointer to cage memory exists in the safe API (H-1); in-cage reads and writes are assumed attacker-controlled (H-2); verified bytecode, the machine-code validator, W^X, CFI and shadow stacks are JS-10, JS-12 and JS-15; the cost is accounted in JS-27, not borrowed from another engine.
- **Measured against our own path, not another engine.** test262 ≥99.5%†, the full Wasm specification suite and WPT per-directory floors are JS-1 to JS-3; the only cross-engine ratio at Stage 1 is GR-30's ≤1.25×† slowdown cap, and no speedup is claimed before X-2.
- **The schedule is the engine track.** JS-M0 to JS-M3 is the second-longest track beside layout (Section 6); its staffing is C-6's engine line, and Ledger B stays internal (Section 6, Resourcing).
- **Updates are Izcal's own.** There is no foreign release cadence to track: every engine build invalidates the code cache (JS-D21), and the three-version update test covers the engine like every other component (JS-16, C-10).
- **The Hardened profile is a ceiling, not a second engine.** Jitless is T0/W0 with no code generator in the loaded-library closure and OS enforcement (JS 6.8, G14). C-11 was settled by the owner on 21 October 2026: JS-D13's default stands and the Jitless ceiling is unchanged.
- **The cage is defense in depth.** It confines memory corruption inside the engine; it does not stop speculative execution, so site isolation (I-1) remains the primary mitigation. Treating cage data as untrusted is the premise, not an extra.
- **What is not claimed.** No compatibility with another engine's embedding API — Izcal defines its own WebIDL bindings and host ABI — and no performance multiple before Stage 3's published head-to-head (X-2).

## 8. Non-goals

HGBA-2.0 does not use confidential-computing VMs (TDX, SEV-SNP, CCA) as a content sandbox. It does not give web content, renderers or any sandboxed process direct access to NICs, PCIe configuration space, GPU MMIO or userspace drivers. It does not offer per-site microVMs. It does not treat protection keys as a site boundary. It does not run Wasm on GPUs or NPUs, and it does not compile page JavaScript to Wasm for performance. It does not schedule individual small tasks onto accelerators, and it does not expose vendor-specific device APIs or TOPS-based scheduling. It does not provide allocatable SRAM, CXL or persistent-memory tiers on clients, and it does not persist live DOM or JS heaps. It does not put post-quantum or any other cryptography on quantum hardware. It does not commit to photonic, neuromorphic, quantum or analog-compute deliverables (see Appendix A). It makes no pre-committed speedup multiple over Chromium or any other engine. Izcal copies, ports or translates no code from another browser engine (M-1, Stage 1 design D-S10).

## Conclusion

The main correction in HGBA-2.0 is a change of method. HGBA-1.0 described hardware by its *peak* capability. HGBA-2.0 describes it by its *reachable* capability: what a sandboxed process can touch, through which OS framework, at what fixed cost, with what failure mode. Seen that way, the growth headroom for a 2026 browser lies in places HGBA-1.0 overlooked. These are adaptive CPU parallelism, one render graph per process shared by raster and WebGPU in the content GPU process and by composition in the compositor GPU service, coarse-grained ML-runtime offload with measured break-even, and hardware memory-safety features layered on process isolation. Exotic devices are not where the gains are.

The second implication is that hardware growth is now mostly a *standards and broker* problem, not an engine-core problem. A new engine contributes most by shipping the abstractions others are still waiting on: native Component Model support counts toward its two-engine gate, and a riscv64 tier with a full sandbox would put a browser on that ISA without a reduced-isolation exception. The spec is built to be proven wrong cheaply. Each target has a kill criterion, the JS engine decision states what would re-open it, and every accelerated path keeps a CPU fallback that leaves correctness intact.

## Appendix A: Research Horizon (speculative hardware, not roadmap deliverables)

Nothing in this appendix is a deliverable. A technology moves into the roadmap only when it meets all four **entry criteria**. First, it ships in volume in client devices (laptops, desktops, phones or headsets). Second, the OS exposes it through a documented framework or driver interface that a sandboxed service process can use. Third, a standard or proposed web API can express its capability, or it improves an existing one invisibly. Fourth, independent (non-vendor) measurements show a benefit on browser-relevant workloads after dispatch overhead.

**CHERI capability hardware** is the most valuable horizon item for HGBA-2.0's security goals. Chromium has been ported to Morello with about **0.045% of base LoC and 0.8% of the JavaScript engine's lines changed** (self-reported), and CHERI deterministically mitigates CVE-2023-4863 ([AsiaBSDCon 2026 slides](https://2026.asiabsdcon.org/media/entry/question_uploads/20260322-asiabsdcon-freebsd-cheri_BQqZECW.pdf)). It exists today only on research boards, as FPGA/IP (Codasip) and on CHERIoT microcontrollers, and no client CPU implements it ([Design & Reuse](https://www.design-reuse.com/news/202530469-why-codasip-went-all-in-on-cheri/); [cheriot.org](https://cheriot.org/)). *Preparation now:* keep pointer provenance clean (no integer/pointer laundering) and prefer offset-based handles, so a CHERI build stays cheap.

**Client CXL memory** fails criterion one. AMD's estimate put it 3–5 years out as of 2023–24, and the only client socket design is a 2024 proposal ([Notebookcheck](https://www.notebookcheck.net/AMD-estimates-that-CXL-technology-with-improved-storage-performance-could-come-to-consumer-platforms-in-3-5-years.664216.0.html); [FMS 2024](https://files.futurememorystorage.com/proceedings/2024/20240807_CXLT-201-1_Gervasi.pdf)). If it arrives, it will appear as a CPU-less NUMA node managed by kernel tiering, and the advisory memory policy in Section 4.6 needs no change.

**Analog in-memory compute** is the most plausible exotic client device. If it arrives, it will be one more NPU behind the OS ML runtime and reached through WebNN. EnCharge's EN100 M.2 card claims 200+ TOPS at 8.25 W (vendor claim), and no OEM laptop with it was confirmed ([DCD](https://www.datacenterdynamics.com/en/news/encharge-ai-launches-its-analog-in-memory-en100-ai-accelerator/)). IBM's 14 nm PCM chip remains research ([The Register](https://www.theregister.com/2023/08/14/ibm_describes_analog_ai_chip/)). No browser architecture change is needed beyond the `MlRuntime` device class.

**Photonic compute** fails criteria one and two. Commercial photonics is data-center interconnect: Lightmatter Passage, and Celestial AI, which Marvell acquired in February 2026 ([Lightmatter](https://lightmatter.co/press-release/lightmatter-unveils-passage-m1000-photonic-superchip-worlds-fastest-ai-interconnect/); [Marvell](https://investor.marvell.com/news-events/press-releases/detail/1005/marvell-completes-acquisition-of-celestial-ai)). Photonic matrix compute exists only as lab packages and rack servers. Lightmatter's Nature-paper system drew 78 W, and Q.ANT sells 19-inch rack units ([Q.ANT](https://qant.com/press-releases/q-ant-launches-first-commercial-photonic-processor-for-energy-efficient-high-performance-computing-and-real-time-ai-applications/)). Photonic ray-box intersection is a single-component lab demo ([Nat. Commun. 2025](https://ideas.repec.org/a/nat/natcom/v16y2025i1d10.1038_s41467-025-61234-x.html)). Browsers benefit only indirectly, through cheaper cloud inference.

**Neuromorphic hardware** runs spiking or sparse networks, not DOM, JS or rasterization. Intel's Hala Point is a 2,600 W research system ([New Electronics](https://newelectronics.co.uk/content/news/intel-builds-world-s-largest-neuromorphic-system)). Edge parts such as BrainChip Akida, Innatera Pulsar and SynSense Speck target always-on sensor pre-processing ([HPCwire](https://www.hpcwire.com/aiwire/2025/05/22/innatera-unveils-pulsar-neuromorphic-microcontroller-for-the-sensor-edge/); [ASX filing](https://announcements.asx.com.au/asxpdf/20260727/pdf/0722fx6s9yf2w9.pdf)). Their plausible web touchpoint is invisible: a gaze or gesture signal surfaced through WebXR or media APIs. Event-based *sensors* are real ([Prophesee GenX320](https://www.vision-systems.com/cameras-accessories/image-sensors/article/14300297/prophesee-launches-event-based-vision-sensor)). Event-driven *displays* exist only as patents ([USPTO](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10559247)). Loihi 3 is **unverified**.

**Quantum computing** fails every criterion. Superconducting qubits run at about 10 mK in dilution refrigerators drawing 5–10 kW, access is through cloud job queues with second-to-hour round trips against an 8–16 ms frame budget, and no known quantum speedup applies to browser workloads ([Quartz](https://qz.com/quantum-computer-data-center-architecture-explained-051126)). Fault-tolerant machines are roadmapped for 2029 as data-center systems: IBM Starling with 200 logical qubits, and Quantinuum Apollo ([IBM roadmap](https://ibm.com/roadmaps/quantum); [Quantinuum S-1](https://www.sec.gov/Archives/edgar/data/0002110105/000162828026032836/quantinuum-sx1.htm)). The browser's quantum work is classical post-quantum cryptography, which is already specified in Section 4.7. Gidney's 2025 estimate that RSA-2048 falls to under a million noisy qubits in under a week is what makes crypto agility urgent ([arXiv 2505.15917](https://huggingface.co/papers/2505.15917)).

**RISC-V** is the one item that already meets the entry criteria for a *CPU platform*. RVA23 makes RVV 1.0 mandatory ([RISC-V International](https://riscv.org/blog/risc-v-announces-ratification-of-the-rva23-profile-standard/)), and SpacemiT K3 silicon ships in boards and a Framework mainboard ([Phoronix](https://www.phoronix.com/news/Ubuntu-SpacemiT-K3)). It is therefore on the roadmap as target X-1, not in this appendix. Its remaining horizon question is width-agnostic SIMD. Wasm's flexible-vectors proposal is Phase 1, and Cranelift fully supports SIMD only on x86-64 and aarch64 ([features.json](https://github.com/WebAssembly/website/blob/main/features.json); [Cranelift README](https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/README.md)).

## Appendix B: The 2.2.x V8-era record (history, not requirement)

This appendix preserves why the 2.2.x plan chose a foreign engine, so the reasons are not silently lost. Nothing here is a requirement, a target, an anchor or a dependency of revision 2.4.0.

**What was planned.** HGBA-2.2.x chose V8 through `rusty_v8` from Stage 1, with a Standard profile (JIT and the V8 sandbox) and a Hardened profile (jitless), and with Izcal's WebIDL bindings and DOM tracing written against `cppgc`. A `cppgc` spike run on 14 October 2026 tested five behaviours: a no-GC scope across a worker phase, cross-thread access without `CrossThreadPersistent`, DOM-to-JS edges through `TracedReference`, GC objects owning Rust data, and a debug-build heap-consistency check. The spike passed on behaviour and failed on exposure: the prebuilt library exported APIs that `rusty_v8` did not wrap, so the project built a companion crate, `v8-cppgc-ext`, a C++ shim against the same headers, and prepared an upstream patch. M0 reproduced the results under the sandbox configuration on macOS arm64, Linux x86-64 and Windows x86-64.

**Why nothing transfers.** Every result is a property of that collector and that embedding API: write barriers, heap scopes, prefinalizers, `TracedReference`, unified DOM-JS tracing and a debug marking verifier. Izcal's engine has different primitives — a 16 GB† cage, a trusted region, verified bytecode, stack maps, and the token API `Mutator<'h>`, `Gc<'h,'m,T>`, `Root<'h,'s,T>` and `Field<T>` (JS 6.5, JS-D17) — so the spike is not evidence for any target in Section 6 and is not cited as such. The one durable lesson is that the embedder edge is where soundness is won or lost; Izcal answers it with the token API and the trusted region, not with a foreign heap integration.

**The fallback shapes are retired.** F1, a Rust-owned style and layout mirror over a `cppgc` DOM, existed because workers could not touch that heap; F2, single-threaded style and layout, was the escape if the mirror failed; F3, a DOM outside `cppgc` with manual tracing, was rejected because the collector could not see edges through the DOM. There is no `cppgc` DOM to mirror and no foreign collector to trace. Workers now read immutable per-agent data through token handles, and parallel style and layout are legal only when byte-identical to sequential (ST-5, LY-4).

**What was retired with it.** The `v8-cppgc-ext` companion crate, the project V8 build farm, the `RUSTY_V8_MIRROR` archive path, the upstream patch, the engine-exposure start conditions (i) to (iii), and targets S-4e and S-4f. No build, test or release depends on them; the archived code is history, not a source. The 2.2.x revision history above records the sequence, and Section 9.1 keeps the one factual disagreement (the RISC-V port) that the notes marked historical.
