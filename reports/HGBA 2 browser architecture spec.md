HGBA-2.0 defines a Rust-first browser engine that grows with new hardware by **absorbing each device through a sandboxed broker process and a standard, capability-negotiated API**. It does not couple the engine to specific silicon. Every hardware wave that has reached the web so far arrived this way: GPUs through a brokered GPU process plus ANGLE, SIMD through fixed 128-bit Wasm SIMD, and NPUs through WebNN on top of OS ML frameworks ([Chromium graphics overhaul, 2010](https://blog.chromium.org/2010/08/chromium-graphics-overhaul.html); [V8 SIMD](https://v8.dev/features/simd); [WebNN status](https://webmachinelearning.github.io/webnn-status/)). HGBA-1.0 broke that pattern in five ways. It treated confidential computing, MPK and Wasm as security or acceleration primitives they are not. It assumed hardware that clients do not have: CXL, Optane, on-die SRAM tiers and quantum co-processors. It let sandboxed content touch hardware directly. It ignored the microsecond-to-millisecond fixed costs of accelerator dispatch. And it ranked performance above security and compatibility. HGBA-2.0 reverses the precedence (security, then compatibility, then robustness, then performance, then hardware reach). It adopts the process-per-site and zero-ambient-authority model every shipping browser uses. It specifies a hardware abstraction layer (HAL) whose devices are asynchronous, can be lost at any time, and always have a CPU fallback. It makes an explicit JavaScript engine choice: V8 via `rusty_v8` from Stage 1, because it ships the only low-overhead JS heap sandbox; SpiderMonkey is re-opened only on public evidence of a comparable one. Each roadmap target is a measurable claim that can fail. Photonic, neuromorphic, quantum, CHERI and client-CXL hardware move to a separate Research Horizon appendix with entry criteria, and none of them is a deliverable.

## 1. Vision: hardware growth comes from brokered abstraction, not silicon coupling

HGBA-2.0 is a browser engine that gets measurably faster, more efficient and more secure as client hardware improves, **without engine rewrites per device generation and without widening the attack surface web content can reach**. "Fully using hardware" means four things. First, the engine scales across CPU cores where parallelism pays. Second, it places coarse-grained work on GPUs and ML runtimes when the measured end-to-end cost, including dispatch and synchronization, beats the CPU. Third, it adopts hardware isolation features (memory tagging, protection keys, capability hardware) as defense in depth on top of process isolation, never as replacements for it. Fourth, it exposes new device classes to the web only through standards that browsers negotiate by capability.

The vision is deliberately narrower than HGBA-1.0's. A client browser in 2026 reaches NPUs only through OS ML frameworks such as Windows ML/ONNX Runtime execution providers, Core ML and LiteRT, and those frameworks make the final placement decision ([WebNN implementation status](https://webmachinelearning.github.io/webnn-status/); [AMD Ryzen AI: Windows ML EPs](https://ryzenai.docs.amd.com/en/latest/winml/winml_ep.html)). It reaches GPUs only through a privileged GPU process. It reaches the network only through a trusted network service that enforces same-origin policy, CORS, CSP, cookies, HSTS and Local Network Access ([Chrome: Local Network Access](https://developer.chrome.com/blog/local-network-access)). HGBA-2.0 treats these constraints as the architecture, not as obstacles to route around.

Izcal, the engine this spec defines, is **a new engine built from the specifications and first principles**. It is not a derivative of another browser and does not use another browser's components: Izcal writes every part that does browser-engine work itself, and depends only on generic infrastructure (M-1, Section 2).

## 2. Principles in precedence order: security and compatibility outrank speed

When two principles conflict, the higher one wins. A design proposal that trades a higher principle for a lower one needs an explicit, recorded exception in the decision log (Section 7).

| Rank | Principle | Operational meaning | Evidence anchor |
|---|---|---|---|
| P1 | **Security and privacy of the user** | Treat web content as hostile. Renderers hold zero ambient authority. Never co-locate cross-site data in one address space. | ~70% of Chromium high/critical bugs are memory-safety bugs ([Chromium Memory Safety](https://www.chromium.org/Home/chromium-security/memory-safety/)); Spectre forces process isolation ([V8: A year with Spectre](https://v8.dev/blog/spectre)) |
| P2 | **Web compatibility and correctness** | Spec conformance (WPT, test262) gates every optimization. A faster wrong answer is a regression. | Ladybird's zero-mismatch A/B gating ([Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31)) |
| P3 | **Robustness and graceful degradation** | Every accelerated path has a correct CPU fallback. Device loss, driver bugs and OOM degrade performance, never correctness. | WebGPU's uneven platform coverage ([gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)) |
| P4 | **Performance and energy efficiency** | Optimize p95 interaction latency, frame time and energy on the corpus users actually run, measured end to end. | Parallel overhead can exceed gains ([HiPC 2016](https://hpcforge.eng.uci.edu/publication/hipc16-browser/hipc16-browser.pdf)) |
| P5 | **Hardware growth** | Adopt new hardware through extension points (brokered device processes, capability queries, standard APIs) once P1–P4 are satisfied. | Past hardware waves reached the web through OS abstractions plus standard APIs ([Chromium 2010](https://blog.chromium.org/2010/08/chromium-graphics-overhaul.html)) |
| P6 | **Evidence over aspiration** | Every performance number in this spec carries a source or a measurement protocol. Vendor claims are labeled as such. | — |

Two consequences follow. Because P1 outranks P4, HGBA-2.0 accepts the **9–13% memory overhead that Site Isolation imposed in Chrome desktop** rather than sharing renderer processes across sites ([Reis et al., USENIX Security 2019](https://www.usenix.org/conference/usenixsecurity19/presentation/reis)). Because P2 outranks P4, a parallel layout path that changes output on any WPT test is disabled until fixed, however fast it is.

**M-1 (method constraint, not ranked): original, first-principles, spec-anchored implementation.** It sits outside the ranking: no P1–P6 trade-off or decision-log exception can override it. It has four parts:

1. **Original, from the ground up.** No code from another browser or browser engine (Servo, Chromium and Blink, WebKit, Gecko and Firefox, Ladybird, Blitz, and their forks) is copied, ported or translated into Izcal, by people or by AI tools, whatever its license (Stage 1 design D-S10). **Izcal also does not use libraries that do browser-engine work, whoever wrote them.** Izcal builds its own JavaScript and WebAssembly engine, garbage collector, DOM, HTML and CSS parsers, selector matching and style system, layout, fonts and text shaping, renderer and rasterizer, network protocols (HTTP/1.1, HTTP/2, HTTP/3 and QUIC), content blocking and the rest of the engine, from the specifications. Libraries extracted from browsers (V8, Stylo, `selectors`, `cssparser`, html5ever, WebRender, wgpu, neqo, `adblock`, Fontations) and independent engine components (Taffy, Parley, HarfBuzz and its ports) are excluded alike. **Allowed dependencies are generic infrastructure only:** the Rust standard library; general-purpose crates whose job is not browser-engine work (data structures, serialization, error handling, hashing, logging, test tooling); cryptography primitives from MIT-licensed crates (the TLS protocol itself is Izcal's own); and OS interfaces and drivers (platform SDKs, graphics APIs such as Metal, Vulkan and Direct3D 12, OS media and accessibility frameworks). **Every dependency and data set that ships must be available under MIT** (alone or as one choice of a dual licence); anything else Izcal builds itself, and it does not ask authors to relicense. Exceptions: standards data published by the standards bodies themselves (the Unicode Character Database, CLDR and emoji data, WHATWG tables, IANA registries, tz, the OpenType registries, the Public Suffix List, the CT log list), used as data; test-only inputs that never ship (conformance suites such as WPT and test262, oracles, test tools), whatever their licence; and OS interfaces, drivers and the toolchain. Fonts are content Izcal designs itself; until a script has an Izcal face, OS fonts render it. A dependency whose class is unclear is decided by the owner and recorded in the Stage 1 design; the default is to build it. **When a component would otherwise come from another browser or an engine library, Izcal builds its own from the specifications**; this is the standing answer, not a case-by-case question.
2. **Spec-anchored.** Web-visible behavior is implemented from the normative specification at a **pinned revision**, and every hand-written algorithm carries a **spec anchor** (`// spec: <URL>#<fragment> [step N]`). Where a specification is silent, ambiguous or contradicted by the deployed web, behavior follows documented interoperability evidence, recorded as a **black-box observation** (test case plus each engine's observed result, never a link to its source) and filed upstream as a specification issue.
3. **First-principles.** Architecture no specification governs (data layout, scheduling, IPC, caching, invalidation, process model, tooling) is derived from P1–P6, measured requirements and verified facts. Another engine's design may be cited as **evidence** that an approach works, from a published source, **never as a template**. A published source is prose: papers, documentation and design documents, talks, blog posts, release notes, bug-tracker discussion and standards threads. **No third-party project's source code is evidence**, whether a browser engine, a library, a tool, assistive technology or an OS component: no spec or research note links to its code files, headers, commits, diffs or code reviews, and no constant, data layout or algorithm is read from them. A prose document hosted in a repository (a design document, a README) is prose when no code file is opened. A value only its source states is measured black-box or set from first principles (marked †).
4. **Spec-anchored oracles decide correctness.** Conformance suites (WPT, test262, pinned), formal models, spec-derived property tests and Izcal's own reference paths are the oracles. **Other engines are black-box differential signals only**: a disagreement is triaged against the cited specification section, never resolved by matching an engine's output or reading its code.

Target ANC-1 (Section 6) makes part 2 measurable.

## 3. Architecture overview: a capability-brokered browser kernel

The browser process is a capability broker. Every other process holds only the handles the broker grants: IPC endpoints, read-only shared memory, GPU command-buffer channels and pre-opened files. Capability systems such as Zircon handles, Capsicum and WASI preopens show this model works ([Fuchsia: handles](https://fuchsia.dev/fuchsia-src/concepts/kernel/handles); [Capsicum, USENIX Security 2010](https://www.usenix.org/conference/usenixsecurity10/capsicum-practical-capabilities-unix)). On Linux the handles map to file descriptors under seccomp-bpf and namespaces, on Windows to handles under restricted tokens, job objects and low integrity, and on macOS to Mach ports under Seatbelt ([Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md); [Chromium Linux sandboxing](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/linux/sandboxing.md)).

## 4. Subsystem specifications

### 4.1 Isolation: process-per-site is the boundary, in-process mechanisms are layers

**Requirement I-1 (site isolation).** On desktop, every site gets its own locked renderer process, including cross-site iframes. Chrome made this the desktop default in 2018 as its primary Spectre mitigation, and Firefox enabled Fission by default in Firefox 95 ([Google Security Blog, Jul 2018](https://security.googleblog.com/2018/07/mitigating-spectre-with-site-isolation.html); [Mozilla Security Blog, May 2021](https://blog.mozilla.org/security/2021/05/18/introducing-site-isolation-in-firefox/)). On Android and other memory-constrained devices, HGBA-2.0 tiers isolation by available RAM. The threshold is Izcal's own, measured against S-3 on the reference devices and recorded in the decision log. Chromium's shipped behavior is evidence that tiering works: it needs **about 2 GB of physical RAM for any site isolation** and isolates only some sites by default on Android ([Chromium Process Model and Site Isolation](https://chromium.googlesource.com/chromium/src/+/main/docs/process_model_and_site_isolation.md)). Below the threshold, the spec requires a documented, reduced security mode, not silent co-location.

**I-1 extensions (revision 2.1.2).** (a) The isolation key is **(site, container)**: a container is a user-facing policy context, and the same site in two containers gets two processes and two storage partitions. (b) The network service partitions **all** of its state by (top-level site, container), extending the Fetch standard's **network partition key** ([Fetch: network partition keys](https://fetch.spec.whatwg.org/#network-partition-keys)) and the Privacy CG's storage-partitioning work ([Privacy CG: Client-Side Storage Partitioning](https://privacycg.github.io/storage-partitioning/)) with the container; Chrome's shipped network-state partitioning is evidence that it is deployable. The partitioned state is: HTTP cache, connection and socket pools, DNS cache, Alt-Svc, TLS session tickets, HSTS, revocation-check caches, reporting endpoints and service-worker registrations. (c) **Origin keying is scoped to subdomains.** Site keying already separates different registrable domains; origin keying only stops subdomains of one site from sharing a process, which is the path Kilger et al. (IEEE S&P 2026) used to exfiltrate data. Chrome 142 enables it at ≥4 GB of RAM. HGBA-2.0 enables it above a RAM threshold recorded in the decision log and set by measurement against S-3, which also gets a per-container variant because containers multiply processes. (d) **Extension origins are their own site keys.** An `ext://` extension origin never shares a renderer or a storage key with any other origin, including in reduced-isolation mode (extensions EX-D3, EX-2; storage 6.x).

**Requirement I-2 (zero ambient authority).** A compromised renderer must not be able to open files, sockets, devices, PCIe config space or GPU MMIO. Everything goes through IPC to a broker. This matches every shipping browser's model ([Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md)) and directly removes HGBA-1.0's userspace-driver and PCIe-probing proposals (see changelog).

**I-2 note: protected-media host (revision 2.1.3).** To play DRM content without depending on any single licensor (Stage 1 design D-S7), a tab may switch into a **protected-media host**: the operating system's licensed web engine (WebView2 on Windows, WKWebView on macOS) in a process the broker launches. That engine is outside HGBA's renderer trust boundary and keeps its own multi-process sandbox. HGBA's guarantees inside it are limited to what the host exposes: storage per (site, container), content blocking and permission mediation. Content can reach the host only through the browser-mediated switch, which fires on actual encrypted playback, never on a capability probe. Agent tabs never use it.

**Requirement I-3 (layered in-process defenses).** Three in-process layers stack on top of the OS process sandbox, and each covers a different bug class. The **JS heap sandbox** (cage) confines a JS-engine memory corruption to a reserved region. V8's version assumes an attacker with arbitrary read/write inside the sandbox, costs **about 1% or less on Speedometer/JetStream**, and is on by default on 64-bit Chrome ([V8 blog: The V8 Sandbox](https://v8.dev/blog/sandbox)). The **library sandbox** compiles third-party C/C++ parsers and codecs to Wasm and back to native code via wasm2c, as Firefox's RLBox does for graphite, ogg, hunspell, expat, woff2 and soundtouch ([Firefox RLBox docs](https://searchfox.org/firefox-main/source/security/rlbox/docs/index.md)). **Memory tagging** (Arm MTE/EMTE) is applied opportunistically in synchronous mode to privileged processes and native code. The wasm2c layer's security depends on the translator being correct: CVE-2026-90648, a wasm2c "table flip" flaw in wabt ≤1.0.41, enables sandbox escape mainly on 32-bit platforms ([OpenCVE](https://app.opencve.io/cve/CVE-2026-90648)). HGBA-2.0 therefore counts the Wasm-to-native compiler as part of its trusted computing base and pins patched versions.

**Requirement I-4 (MPK/PKU and Arm POE are coarse, bypassable domains).** Protection keys give **16 keys per process**, and any code that gains execution can switch them with the unprivileged `WRPKRU` instruction ([Linux kernel: Memory Protection Keys](https://docs.kernel.org/core-api/protection-keys.html)). Published attacks bypass PKU sandboxes via `WRPKRU`/`XRSTOR` gadgets, `/proc/self/mem`, `mprotect` and signal handling ([PKU Pitfalls, USENIX Security 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/connor); [Garmr](https://www.arxiv.org/abs/2110.04788)). HGBA-2.0 uses PKU or POE only as V8 and Cloudflare do: to separate a few coarse trust domains, such as JIT code pages (writable only on compiler threads) and sandbox metadata. It is always paired with W^X, control-flow integrity (CET/IBT, BTI/PAC) and syscall filtering that blocks `pkey_mprotect` and `/proc/self/mem` writes ([V8 code-memory-access](https://chromium.googlesource.com/v8/v8/+/refs/heads/main/src/common/code-memory-access-inl.h); [Cloudflare: Safe in the sandbox](https://blog.cloudflare.com/safe-in-the-sandbox-security-hardening-for-cloudflare-workers/)). PKU never isolates one site from another. Arm POE is upstream in Linux 6.12 behind the same pkeys syscalls ([arm64 6.12 pull](https://lkml2.uits.iu.edu/hypermail/linux/kernel/2409.1/08571.html)). Which shipping Arm client SoCs implement it is unknown.

**Requirement I-5 (MTE is detect-and-deter, not confidentiality).** MTE uses 4-bit tags, so a blind guess succeeds with probability 1/16. TikTag showed that speculative execution leaks tags on Pixel 8, including an attack path against Chrome ([arXiv 2406.08719](https://arxiv.org/abs/2406.08719)). The V8 team rejected MTE for the JS heap because tags leak through side channels and pointer compression leaves no spare bits ([V8 blog](https://v8.dev/blog/sandbox)). Only Apple's A19-class Memory Integrity Enforcement has a vendor-documented tag-confidentiality design. It is always-on in synchronous mode for the kernel and more than 70 userland processes, and Apple reports only "minimal performance impact" with no number ([Apple Security Research: MIE](https://security.apple.com/blog/memory-integrity-enforcement/)).

**Requirement I-6 (Spectre rules).** In-process isolation protects integrity, not confidentiality, against transient execution. Shared memory across renderer processes must be read-only or same-site. `SharedArrayBuffer` and high-resolution timers stay gated on COOP+COEP cross-origin isolation ([web.dev: COOP/COEP](https://web.dev/articles/coop-coep)).

**Confidential computing is out of scope as a content sandbox.** TDX, SEV-SNP and CCA protect a guest VM *from* a malicious host, hypervisor and firmware ([AMD SEV-SNP threat model](https://docs.enclaive.cloud/confidential-cloud/technology-in-depth/amd-sev/technology/threat-model)). A browser needs the opposite direction: protecting the host and user data *from* content. TDX is a Xeon feature and SEV-SNP an EPYC feature ([Intel TDX](https://www.intel.com/content/www/us/en/developer/tools/trust-domain-extensions/overview.html); [AMD SEV](https://www.amd.com/en/developer/sev.html)). Host-driven side channels still break them (TDXDown, CounterSEVeillance) ([SecurityWeek](https://www.securityweek.com/new-counterseveillance-and-tdxdown-attacks-target-amd-and-intel-tees/amp/)). Client secrets such as passkeys and DRM keys stay in the platform's existing enclaves.

**VM isolation is an optional, per-profile tier at most.** Firecracker microVMs start in about 125 ms with under 5 MiB of VMM overhead each, compared with single-digit milliseconds for a process ([Firecracker](https://firecracker-microvm.github.io/)). Microsoft deprecated Defender Application Guard for Edge and removed it in Windows 11 24H2 ([Microsoft Learn](https://learn.microsoft.com/deployedge/microsoft-edge-security-windows-defender-application-guard)). VM-per-site is a non-goal. A VM tier for an "untrusted session" profile on KVM/Hyper-V/HVF hosts remains an open question.

### 4.2 JavaScript and WebAssembly execution

**JS engine (decision D2, Section 7).** Stage 1 embeds **V8 through the `rusty_v8` Rust bindings**, with the V8 sandbox enabled and DOM objects traced through V8's `cppgc` heap. `rusty_v8` exposes the core of `cppgc` (for example `cppgc::Ptr` since v0.98) ([rusty_v8 changelog](https://src.opensuse.org/cbus/rusty_v8/src/branch/devel/rusty_v8.changes)). The project's `cppgc` spike (Section 6) found that `rusty_v8` 152.2.0 (V8 15.2) covers allocation, `Member`/`Persistent`, `TracedReference` and wrapper wrapping, but not the no-GC and disallow-GC scopes, heap state, heap statistics, prefinalizers or the precise testing GC. The project supplies those through a companion crate and an upstream patch. No source shows `cppgc` carrying a browser-scale DOM from Rust, so the bindings and GC integration remain Stage 1's largest engineering risk. SpiderMonkey was the original choice and was rejected after the heap-cage analysis in Section 7. Pure-Rust engines are spec-conformant interpreters without a production JIT. **Boa reached 94.12% test262 in v0.21** and a mirror reports 95.60% for v0.22 (date unconfirmed) ([Boa v0.21](https://opencollective.com/boa/updates/boa-release-v0-21); [newreleases.io](https://newreleases.io/project/github/boa-dev/boa/release/v0.22)). **Nova claims about 80%** and calls interpreter performance "not yet a high priority" ([docs.rs nova_vm](https://docs.rs/crate/nova_vm/latest)). A report that Brimstone has "97% ECMAScript support" comes from an aggregator and is **unverified** ([feedbagel](https://feedbagel.com/post/brimstone-a-new-javascript-engine-written-in-rust-with-97-ecmascript-support)). The JIT is the main memory-safety liability. Microsoft's 2021 data attributed **about 45% of V8 CVEs since 2019 to the JIT** ([BleepingComputer](https://www.bleepingcomputer.com/news/microsoft/microsoft-edge-just-got-a-super-duper-secure-mode-upgrade)). Disabling the JIT costs **1.5x to 10x or more** on compute-heavy work and addresses only about half of exploited V8 bugs ([V8 blog](https://v8.dev/blog/sandbox)). HGBA-2.0 therefore ships two JS profiles. *Standard* has the JIT on, inside the V8 sandbox. *Hardened* runs V8 in jitless mode with CET, for high-risk users and enterprise policy. Jitless V8 generates no machine code at runtime, so WebAssembly runs only through the **DrumBrake** interpreter, as in Edge's enhanced security mode and Brave's JITless setting ([Privacy Guides](https://discuss.privacyguides.net/t/mention-brave-supporting-jitless-mode/33611)). Wasm keeps working but runs far slower, and the interpreter is new attack surface: an OffensiveCon 2026 talk reports 23 RCE bugs found in DrumBrake (researchers' claim, unverified) ([OffensiveCon 2026](https://www.offensivecon.org/speakers/2026/nan-wang-and-ziling-chen.html)). A tiers-off alternative (`--no-opt`) is rejected because Sparkplug and Liftoff still emit machine code at runtime, so it does not remove runtime code generation.

**Page-facing Wasm** runs inside the JS engine, because web Wasm needs GC objects shared with JS, JSPI and Web IDL bindings. Wasmtime marks JSPI, JS String Builtins and ESM integration as not applicable ([WebAssembly features.json](https://github.com/WebAssembly/website/blob/main/features.json)). Wasm compiles per ISA on the client: a baseline tier for startup, an optimizing tier for steady state, and a code cache keyed per engine version that every engine update invalidates ([V8: Wasm code caching](https://v8.dev/blog/wasm-code-caching)). The cross-browser Wasm baseline HGBA-2.0 may assume is GC, exnref exceptions, tail calls, typed function references, SIMD128, threads (behind cross-origin isolation) and JS String Builtins. It may not assume memory64, relaxed SIMD or multi-memory in Safari, or stack switching, ESM integration or shared-everything threads anywhere ([features.json](https://github.com/WebAssembly/website/blob/main/features.json)).

**Internal components** (extensions, privileged plug-ins, sandboxed utilities) run in Izcal's **component host** (the extensions spec; JS-D10), kept out of the page-facing engine. Extension background contexts are agents on the jitless embedded engine, extension pages are own-origin renderers, and content scripts are the one renderer-side exception: isolated worlds that hold no capability tokens (extensions EX-D3). The Stage 2 program, its process model and its staffing are the extensions spec's.

**Component Model semantics, stated precisely.** Calls across component boundaries are **shared-nothing with one copy per crossing**. The host lowers values into the receiver's memory via `cabi_realloc` ([Bytecode Alliance: Road to CM 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)). Zero-copy forwarding arrives only with the future *lazy ABI*, opt-in in a 0.3.x release and the default at 1.0. Async task management currently adds **roughly 3.5x overhead even on synchronous call paths** (same source). Bulk data must cross as `stream<T>` or resource handles, not large `list<u8>`. **No browser ships the Component Model natively**: it is Phase 1 in the CG, it runs in browsers only through `jco transpile` to core Wasm plus JS glue, and CM 1.0 formally needs native implementations in two browser engines ([features.json](https://github.com/WebAssembly/website/blob/main/features.json); [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)). A new engine that shipped native CM would count toward that gate. That makes native CM a possible Stage 3 contribution, not a Stage 1 dependency.

**Wasm does not run on GPUs or NPUs, and JS is not compiled to Wasm for speed.** No credible production system lowers general Wasm to GPU or NPU. The only direct attempt, W2GPU, is a "preliminary study" that generalizes poorly ([W2GPU, LMPL 2025](https://conf.researchr.org/details/icfp-splash-2025/lmpl-2025-papers/22/W2GPU-Toward-WebAssembly-to-WebGPU-Program-Translation-via-Small-Language-Models)). GPU work is written in WGSL through WebGPU, and NPU work is expressed as WebNN graphs. Tools that put JS inside Wasm embed an interpreter: ComponentizeJS embeds about 8 MB of SpiderMonkey, and Javy embeds QuickJS. AOT specialization via weval gains about **2x overall and 3–5x on some benchmarks over that interpreter**, and is still beta ([ComponentizeJS](https://github.com/bytecodealliance/componentizejs); [cfallin AOT JS](https://cfallin.org/blog/2024/08/27/aot-js/); [NEU PL seminar](https://lists.ccs.neu.edu/pipermail/pl-seminar/2024/000986.html)). Porffor, the one true AOT JS-to-Wasm compiler, calls itself "not yet intended for serious use" and cannot support `eval` ([Porffor](https://github.com/CanadaHonk/porffor)). HGBA-2.0 uses JS-in-Wasm only to *isolate* untrusted script, such as extension sandboxes. It is never a performance path.

### 4.3 Style, layout and CPU parallelism

HGBA-2.0's parallel style **uses the `stylo` crate as a dependency**, unmodified, through its public traits. Stylo is the strongest production evidence that parallel Rust engine code ships at scale. Stylo has been in Firefox since version 57, after two failed C++ attempts at parallel style ([Mozilla Hacks 2017](https://hacks.mozilla.org/2017/08/inside-a-super-fast-css-engine-quantum-css-aka-stylo/)). Its public numbers are marketing-grade. The "up to 2 or 4 or even 18 times faster" line describes scaling with core count, not a benchmark (same source).

The only rigorous measurement of parallel *layout* is HiPC 2016. It found **3.2x and 2.5x with 4 threads on some sites** and no gain on others, because "in many cases, the overhead of creating, deleting, and coordinating parallel work outweighs any of its benefits." A predictive model that chose the thread count per page improved performance by up to 94.52% and energy by up to 46.32%, both maximums ([HiPC 2016](https://hpcforge.eng.uci.edu/publication/hipc16-browser/hipc16-browser.pdf)). Servo now runs parallel table layout via Rayon by default but has published no benchmark ([Phoronix](https://phoronix.com/news/Servo-Multi-Core-HTML-Tables)). The spec therefore requires **adaptive parallelism**. A per-document work estimate selects sequential or parallel execution and a thread count. The parallel path must be bit-identical to the sequential path on WPT reftests. Small documents default to sequential.

Heterogeneous CPU cores (performance and efficiency clusters) are handled through OS QoS classes and thread priorities, not by pinning. Input, script and frame-critical work run at interactive QoS. Background style and layout of hidden frames, code caching and prefetch parsing run at utility QoS.

### 4.4 Rendering and the GPU service

The GPU service owns all GPU access. HGBA-2.0 selects **wgpu**, the Rust implementation that backs both Firefox and Servo WebGPU, as its GPU abstraction over Vulkan, Metal and D3D12. Dawn is the documented alternative ([gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)). Chromium already serves both raster (Skia Graphite) and WebGPU through one abstraction in one privileged process. Graphite gained **nearly 15% on MotionMark 1.3** on Apple Silicon Macs when it shipped there in July 2025 ([Chromium blog: Skia Graphite](https://blog.google/chromium/introducing-skia-graphite-chromes/)). HGBA-2.0 adopts the same consolidation as a goal: rasterization, compositing and WebGPU sharing one render graph, so the scheduler sees them as one GPU queue with known contention. **Stage 1 cannot reach it.** WebRender, the Stage 1 rasterizer, renders only through OpenGL; Izcal depends on the `webrender` crate (0.70), unmodified, and that crate has no wgpu backend. The Stage 1 GPU service therefore runs two stacks: WebRender on OpenGL for page raster and compositing (through ANGLE on Windows, as Firefox does, and native OpenGL on macOS and Linux), and wgpu for WebGPU, with WebGPU canvases composited through platform shared-texture handles. The scheduler models them as two queues. The single render graph becomes reachable through Vello on wgpu, so target P-2 now decides consolidation as well as raster performance. Writing a wgpu backend for WebRender is rejected for Stage 1 as open-ended work in a component the project does not own.

The Stage 1 rasterizer is WebRender, which ships in Firefox and is used by Servo ([Servo book: architecture](https://book.servo.org/design-documentation/architecture.html)). **Vello Hybrid** (sparse strips with a CPU/GPU split) is the Stage 2 candidate. Linebender rated it "roughly beta" in Q1 2026 ([Linebender 2026 Q1](https://linebender.org/blog/tmil-25/)). Its CPU/GPU split is direct evidence that the best placement for 2D raster depends on the device, which is why placement is decided at runtime by the HAL (Section 5).

**WebGPU exposure** follows real platform coverage, not "Baseline everywhere" headlines. As of 2 October 2026, Chromium ships WebGPU on Windows, macOS, ChromeOS and Android 12+ (most vendors). On Linux it ships only on Intel Gen12+ and on NVIDIA under Wayland. Firefox ships on Windows and Apple Silicon Macs, and Linux and Android are Nightly or behind a flag ([gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)). HGBA-2.0 exposes two capability tiers. **WebGPU-core** is the default. **WebGPU-compat** targets OpenGL ES 3.1-class devices and implements the WebGPU specification's opt-in compatibility mode (`featureLevel: "compatibility"`) ([WebGPU: `GPURequestAdapterOptions.featureLevel`](https://www.w3.org/TR/webgpu/#dom-gpurequestadapteroptions-featurelevel)); Chrome shipping it in 146 is deployment evidence ([Chrome: What's New in WebGPU 146](https://developer.chrome.com/blog/new-in-webgpu-146)). WebGL2 or CPU is the floor. GPU drivers stay behind a blocklist maintained by the GPU service.

**Event-driven rendering** in HGBA-2.0 means damage-region compositing, variable refresh rate, panel self-refresh and gaze-aware foveation where the platform offers it. These features exist and ship. "Neuromorphic displays" do not: no commercial event-driven display exists ([Research Horizon appendix](#appendix-a-research-horizon-speculative-hardware-not-roadmap-deliverables)).

### 4.5 Machine learning and NPU access

NPUs are reached **only through OS ML runtimes, behind an ML service process**. Windows ML selects and registers an execution provider per device and accepts policies such as `PREFER_NPU` with automatic CPU fallback ([AMD Ryzen AI: Windows ML EPs](https://ryzenai.docs.amd.com/en/latest/winml/winml_ep.html)). Core ML makes its own CPU/GPU/ANE placement decision. Chromium's WebNN backends are Windows ML/ORT, Core ML and LiteRT, all still experimental, and DirectML has been dropped from the list ([WebNN status](https://webmachinelearning.github.io/webnn-status/); [Microsoft Learn: DirectML](https://learn.microsoft.com/windows/ai/directml)). The HAL therefore models the NPU as an **opaque-placement ML runtime device**, not a schedulable processor.

Vendor TOPS figures do not drive scheduling. Windows 2026 parts claim roughly 50 (Intel Panther Lake), 60 (AMD XDNA 2) and 80–85 (Snapdragon X2 Elite) INT8 TOPS, all from secondary aggregators. Apple publishes no M5 Neural Engine figure ([localaimaster](https://localaimaster.com/blog/npu-tops-list); [Guru3D](https://www.guru3d.com/story/apple-m5-soc-brings-neural-accelerators-to-every-gpu-core)). Measured behavior matters more. In a community characterization, a 0.6B draft model ran **about 3.6x slower per token on the Lunar Lake NPU than on the CPU**, which the author attributed to a high fixed per-inference dispatch cost ([OpenVINO discussion #36484](https://github.com/openvinotoolkit/openvino/discussions/36484)). The NPU won on small matrices and the GPU on large ones in a 2024 Intel study ([arXiv 2409.14803](https://arxiv.org/pdf/2409.14803)).

**Web exposure.** WebNN is exposed only behind a flag until at least one stable browser ships it (see the WebNN reconciliation in Section 9). Browser-owned task APIs (translate, summarize, prompt) implement the WebML CG task-API proposals ([Translator and Language Detector APIs](https://webmachinelearning.github.io/translation-api/); [Writing Assistance APIs](https://webmachinelearning.github.io/writing-assistance-apis/); [Prompt API](https://github.com/webmachinelearning/prompt-api)), which keep the device out of the page. The browser picks GPU or CPU once against hardware thresholds, and pages never see the device. As deployment evidence, Chrome's implementation needs a GPU with **more than 4 GB of VRAM, or 16 GB of RAM and 4+ cores**, plus 22 GB of free storage. NPU use is undocumented in both Chrome and Edge ([Chrome: Get started with built-in AI](https://developer.chrome.com/docs/ai/get-started); [Microsoft Learn: Prompt API](https://learn.microsoft.com/microsoft-edge/web-platform/prompt-api)).

### 4.6 Memory and storage: advisory tiers on real client hardware

Client memory in 2026 is **unified LPDDR5X DRAM**, ranging from about 120 GB/s on mainstream 128-bit buses to **546 GB/s on M4 Max**, with Strix Halo at 256 GB/s ([Apple Newsroom](https://www.apple.com/au/newsroom/2024/10/apple-introduces-m4-pro-and-m4-max/); [Framework](https://frame.work/blog/framework-desktop-deep-dive-ryzen-ai-max)). Intel described Lunar Lake's on-package memory as a one-off ([Wccftech](https://wccftech.com/intel-reaffirms-commitment-to-arc-gpus-panther-lake-nova-lake-sticking-to-non-on-package-memory/amp/)). The tiers a browser can actually influence are: active DRAM; OS-compressed RAM; SSD-backed swap and serialized state; and discard (reload on demand).

HGBA-2.0's memory manager is **advisory**. It classifies each frame and tab as hot, warm, cold or frozen and maps those classes to `madvise` hints (`MADV_COLD`, `MADV_PAGEOUT`, `MADV_DONTNEED`, `MADV_HUGEPAGE`), OS memory-pressure APIs, tab freezing and discard. Userspace cannot pin data in CPU caches or control physical page placement. Hot/cold migration (TPP, DAMON) is a kernel decision ([kernel.org DAMON](https://docs.kernel.org/mm/damon/index.html); [LKML DAMON tiering RFC](https://lkml.iu.edu/hypermail/linux/kernel/2402.3/02113.html)). **On-die SRAM is not an allocatable tier.** **CXL is not a client tier.** Every shipping expander is a data-center part, the first announced cloud deployment was an Azure preview in November 2025, and around 2023–24 AMD put client CXL **3–5 years away** ([Astera Labs](https://www.asteralabs.com/news/astera-labs-leo-cxl-smart-memory-controllers-on-microsoft-azure-m-series-virtual-machines-overcome-the-memory-wall/); [Notebookcheck](https://www.notebookcheck.net/AMD-estimates-that-CXL-technology-with-improved-storage-performance-could-come-to-consumer-platforms-in-3-5-years.664216.0.html)). Even on servers, CXL adds **about 50–300% latency over local DDR5** ([arXiv 2411.02814](https://arxiv.org/pdf/2411.02814)). **Persistent memory has no target hardware.** Intel wound down Optane in Q2 2022 with a $559M write-off, and every CXL expander found is volatile ([AnandTech](https://www.anandtech.com/show/17515)).

Fast restore uses mechanisms that already ship: bfcache in all three engines ([web.dev](https://web.dev/articles/bfcache)), V8-style startup snapshots, compiled-code caches (V8 code cache and explicit compile hints, SpiderMonkey's JSBC/Stencil) ([V8 compile hints](https://v8.dev/blog/explicit-compile-hints); [Mozilla JSBC](https://blog.mozilla.org/javascript/2017/12/12/javascript-startup-bytecode-cache/)), and tab discard with `visibilitychange` state saving ([Chrome Memory Saver](https://developer.chrome.com/blog/memory-and-energy-saver-mode)). Persistent user data is persisted by Izcal's own crash-consistent storage engine (`hg-store-engine`, the storage spec's), whose commit protocol is verified by crash injection; the regenerable-cache class (FP-D16) is the exception path, and its fallback "crash-consistent embedded store" names that engine.

Shared-memory IPC is designed from I-2 and the capability model (Section 3): sandboxed processes cannot create shared regions themselves, so the broker allocates them and passes them as handles. Chromium's Mojo, whose broker does the same for sandboxed processes, is evidence that the design ships (evidence only, M-1) ([Mojo docs](https://chromium.googlesource.com/chromium/src/+/HEAD/mojo/README.md)). **io_uring is excluded** from renderer and network-service designs. Google found that 60% of kCTF VRP submissions exploited io_uring, disabled it on ChromeOS and blocks it for Android apps ([Phoronix](https://www.phoronix.com/news/Google-Restricting-IO_uring)).

### 4.7 Network and cryptography

All web-content networking goes through the **trusted network service**. There is no direct NIC, DPDK or vfio path for content: kernel bypass needs exclusive device ownership and root/IOMMU setup, and it would skip every policy check the network service enforces ([DPDK Linux drivers](https://doc.dpdk.org/guides/linux_gsg/linux_drivers.html); [Chrome: Local Network Access](https://developer.chrome.com/blog/local-network-access)). The Chromium network service still ran **unsandboxed on Android, Windows and Linux** as of the M128-era documentation ([Chromium process sandboxes by platform](https://chromium.googlesource.com/chromium/src/+/b5470ac602dd94de3fa37f35c8a2a3649c6d013d/docs/security/process-sandboxes-by-platform.md)). HGBA-2.0 sets sandboxing it on all platforms as a Stage 2 target, because its code is Rust and parsers are confined.

The client accelerations that actually help live **inside** the network service. They are CPU crypto instructions (AES-NI, ARMv8 Crypto) and UDP GSO/GRO batching for QUIC. GSO/GRO substantially cut packet I/O overhead, yet only 1 of 4 QUIC stacks tested in 2026 used both ([TUM NOMS 2026](https://www.net.in.tum.de/fileadmin/bibtex/publications/papers/spaethj-noms2026.pdf); [Cloudflare](https://blog.cloudflare.com/accelerating-udp-packet-transmission-for-quic/)). kTLS and NIC TLS offload are server features, and kTLS does not apply to QUIC.

**Post-quantum TLS runs in software on classical CPUs.** Hybrid **X25519MLKEM768** is the default in Chrome 131+ and Firefox 132+ desktop ([Google Security Blog, Sept 2024](https://security.googleblog.com/2024/09/a-new-path-for-kyber-on-the-web.html); [Cloudflare PQC support](https://developers.cloudflare.com/ssl/post-quantum-cryptography/pqc-support/index.md)). A secondary source reports that more than two-thirds of human TLS traffic to Cloudflare used it by April 2026 ([Encryption Consulting](https://www.encryptionconsulting.com/pqc-support-in-web-browsers/)). HGBA-2.0 requires crypto agility: pluggable KEM and signature suites, hybrid by default, policy-controlled fallback, and a path for ML-DSA/SLH-DSA (FIPS 204/205) certificates once the WebPKI adopts them ([NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)). The same hybrid key exchange applies to **WebRTC's DTLS** handshakes, which Chrome enabled in version 142 against record-now, decrypt-later attacks on media. Quantum hardware has no role in this.

### 4.8 Implementation language and FFI policy

Rust is the default for new engine code. The justification is narrow and evidence-based: **Rust is the only memory-safe, non-GC language with browser-engine components shipped at scale**. Those components are Stylo and WebRender in Firefox, Fontations/Skrifa in Chrome (the default for all web fonts on Linux, Android and ChromeOS since Chrome 133), and Servo ([Chrome: Memory safety for web fonts](https://developer.chrome.com/blog/memory-safety-fonts); [Mozilla Hacks 2017](https://hacks.mozilla.org/2017/08/inside-a-super-fast-css-engine-quantum-css-aka-stylo/)). Ladybird's 2026 ports add a second engine-core data point ([Ladybird: Adopting Rust](https://ladybird.org/posts/adopting-rust/)). The claim does **not** extend to "the only production-proven memory-safe language". The research did not evaluate Ada/SPARK. Swift 6 offers compile-time data-race checking, but it can be bypassed with `@unchecked Sendable`, and Ladybird dropped Swift over C++ interop and non-Apple platform support ([Swift Package Index](https://swiftpackageindex.com/ready-for-swift-6); [Ladybird](https://ladybird.org/posts/adopting-rust/)).

Rust's guarantees cover only safe Rust. HGBA-2.0 will contain large amounts of non-Rust code. V8 is C++, and so are the OS GPU and ML frameworks, codecs and platform APIs. Servo itself is "not a pure-Rust stack" for this reason ([servo/mozjs](https://github.com/servo/mozjs) *[URL not re-fetched]*). The spec therefore requires the following. Every `unsafe` block and FFI boundary is inventoried and owned by a named reviewer. FFI wrappers validate all inputs and treat foreign memory as tainted, following RLBox's tainted-data discipline ([Firefox RLBox docs](https://searchfox.org/firefox-main/source/security/rlbox/docs/index.md)). C/C++ code that parses untrusted input runs inside a library sandbox or a separate process (Chromium's "Rule of 2") ([Chromium Memory Safety](https://www.chromium.org/Home/chromium-security/memory-safety/)). Fuzzing covers every FFI surface. When Izcal replaces one of its own components, or a dependency, with Izcal-built code (for example a C/C++ library with a Rust implementation), the replacement uses **equivalence gating** (D7): the new code must match the old on the component's oracles before the old code is deleted. Ladybird's published results are evidence that the gating works at engine scale, not a method for porting another engine: its Rust LibJS frontend produced byte-identical ASTs and bytecode with 0 regressions across 52,898 test262 and 12,461 internal tests, and its CSS parser port required "zero mismatches" in A/B runs before the C++ code was deleted ([Ladybird: Adopting Rust](https://ladybird.org/posts/adopting-rust/); [Ladybird Aug 2026](https://ladybird.org/newsletter/2026-08-31)).

## 5. HAL specification: asynchronous devices that can fail

### 5.1 Device classes and the capability graph

The HAL exposes **device classes, never vendors**. The classes are `Cpu` (thread pools with QoS classes), `Gpu` (a wgpu device in the GPU service), `MlRuntime` (an OS ML framework session in the ML service, with opaque CPU/GPU/NPU placement), `MediaCodec` (OS hardware decoders and encoders) and `Crypto` (CPU instruction-set capabilities). Each device advertises a `Capabilities` record. The **capability graph** has one node per device instance and one edge per data path between nodes. Each edge carries a fixed cost, a per-byte cost and a synchronization cost. Those costs are measured at startup and refreshed in the background, so vendor peak figures never enter the graph. This follows the research finding that fixed dispatch and sync costs dominate small tasks. A native null-kernel launch costs **about 3–7 µs on Linux and 10–80 µs under Windows WDDM**. Browser WebGPU readback adds an IPC round trip and can wait behind unrelated queued work ([NVIDIA forums](https://forums.developer.nvidia.com/t/too-much-time-for-kernel-launch-latency/233645); [arXiv 2604.17861](https://arxiv.org/pdf/2604.17861); [Dawn mapAsync](https://dawn.googlesource.com/dawn/+/refs/heads/chromium/5484); [WebKit bug 272804](https://bugs.webkit.org/show_bug.cgi?id=272804)). On unified-memory SoCs the per-byte cost approaches zero, but the dispatch and sync costs remain.

### 5.2 Device interface

```rust
/// Device classes are abstract; vendors never appear in the API.
pub enum DeviceClass { Cpu, Gpu, MlRuntime, MediaCodec, Crypto }

pub struct CostModel {
    pub fixed_dispatch: LatencyDist,   // measured p50/p95, includes IPC to service
    pub sync_roundtrip: LatencyDist,   // submit -> fence signaled -> observed by caller
    pub ns_per_byte_in: f64,           // ~0 on unified memory; measured otherwise
    pub ns_per_byte_out: f64,
    pub provenance: CostProvenance,    // Measured { at, samples } | Default
}

pub struct Capabilities {
    pub class: DeviceClass,
    pub tier: Tier,                    // e.g. WebGpuCore, WebGpuCompat, MlCpuOnly
    pub features: FeatureSet,
    pub limits: Limits,
    pub unified_memory: bool,
    pub cost: CostModel,
    pub epoch: u64,                    // increments on every re-creation after loss
}

pub trait Device: Send + Sync {
    fn capabilities(&self) -> &Capabilities;

    /// Allocation never blocks the caller's frame-critical thread.
    fn create_buffer(&self, desc: &BufferDesc) -> Result<Buffer, HalError>;

    /// All work is asynchronous. Returns a fence on a monotonic timeline.
    fn submit(&self, work: WorkGraph, wait_on: &[Fence]) -> Result<Fence, HalError>;

    /// Readback is only ever a future; there is no blocking map.
    fn map_read(&self, buf: &Buffer, after: &Fence) -> MapFuture; // resolves Ok(view) | Err(HalError)

    /// Resolves exactly once, when the device is lost for any reason.
    fn lost(&self) -> LostFuture;      // yields LossInfo
}

pub enum HalError {
    Validation { detail: String },               // caller bug; sticky per object
    OutOfMemory { scope: OomScope },             // allocation failed; nothing leaked
    Timeout { fence: Fence },                    // watchdog fired; device will be lost
    Unsupported { feature: Feature },            // capability absent at this tier
    PolicyDenied { reason: PolicyReason },       // blocklist, permission, enterprise policy
    DeviceLost(LossInfo),
}

pub struct LossInfo { pub reason: LossReason, pub epoch: u64 }
pub enum LossReason { Destroyed, DriverReset, ServiceCrashed, Blocklisted, PowerOrThermal, Unknown }

/// Every schedulable operation provides at least a CPU implementation.
pub struct Op { pub cpu: CpuImpl, pub gpu: Option<GpuImpl>, pub ml: Option<MlImpl> }
```

### 5.3 Synchronization semantics

Every submission is asynchronous and returns a `Fence` on a per-device monotonic timeline. Cross-device dependencies are expressed only as fences in `wait_on`. On unified memory, a shared buffer still needs a fence before another device reads it. Physical sharing does not imply ordering. **No HAL call blocks the renderer main thread or the compositor thread.** Results consumed by layout, script or compositing in frame *N* must come from fences signaled before frame *N*'s deadline. In practice that means pipelined use of frame *N−1* results, or a CPU result computed in parallel. Frame budgets are 16.7 ms at 60 Hz and 8.3 ms at 120 Hz. With readback round trips that cross processes and can queue behind unrelated work, synchronous per-frame readback is prohibited ([WebKit bug 272804](https://bugs.webkit.org/show_bug.cgi?id=272804)).

### 5.4 Error semantics

Validation errors are attached to the offending object and are sticky, modeled on WebGPU error scopes. They never crash the service or the renderer. `OutOfMemory` fails the allocation cleanly, and the scheduler retries on the next device in the fallback chain. `Timeout` means a service-side watchdog fired, and it is always followed by device loss for that epoch. `PolicyDenied` covers driver blocklists, permissions and enterprise policy, and content cannot tell it apart from `Unsupported`, to limit fingerprinting. Every error path is covered by fault-injection tests (Section 6).

### 5.5 Device-loss semantics

Any device can be lost at any time: through a driver reset, a GPU or ML service crash, a power or thermal event, or a blocklist update. When a device is lost, all handles from its epoch become invalid, all pending fences resolve with `DeviceLost`, and `lost()` resolves exactly once. Recovery means asking the broker for a new device of the same class. The new device gets a new epoch, and the broker applies exponential backoff. **After three losses within ten minutes, the device class is blocklisted for the session** and the scheduler moves to its fallback. Web-exposed APIs map onto this model directly: a WebGPU `GPUDevice.lost` promise resolves, and the page may request a new adapter. A GPU service crash must never take down a renderer. The renderer re-rasterizes from its retained display lists on the next device or on the CPU.

### 5.6 Fallback semantics

Every internal `Op` must provide a CPU implementation, following StarPU's multi-variant "codelet" model ([StarPU docs](https://git.microlab.ntua.gr/exa2pro/starpu-max/raw/d32e9b2e2a2bc7b2fd76a287bdf8582e5848554d/doc/doxygen/chapters/introduction.doxy)). Fallback chains are policy-driven and mirror ONNX Runtime's EP policies. `prefer-efficiency` is `MlRuntime(npu-preferred) → Gpu → Cpu`. `prefer-latency` is `Gpu → Cpu`. `hardened` is `Cpu` only. Results must match within a declared numerical tolerance, and rendering paths must match pixel-for-pixel on reftests. Fallback is invisible to content except as a change in performance. Web APIs whose specs allow failure, such as a null WebGPU adapter, surface failure instead of emulating the API on the CPU.

### 5.7 Scheduling rules: coarse, batched, measured

The scheduler is **hierarchical**. The browser-level scheduler picks a device class per *task graph*, not per task. Inside the GPU or ML runtime, the native runtime does the fine-grained scheduling. On Apple platforms, for example, Core ML makes the final ANE decision. An offload is admitted only when the following holds, using measured p95 costs:

`est_cpu > fixed_dispatch + sync_roundtrip + bytes × ns_per_byte + est_device`, with a safety margin of at least 1.5x.

Small operations are batched into a single submission, in the manner of CUDA Graphs and operation fusion ([NVIDIA: CUDA Graphs](https://developer.nvidia.com/blog/cuda-graphs)). Data stays resident on the device across stages. `MlRuntime` handles only sustained, quantized model inference of meaningful size, never per-frame or latency-critical microtasks. These thresholds are **design heuristics derived from the evidence, not measured constants**, and Stage 1 must replace them with measured values (target R-6).

## 6. Roadmap with falsifiable targets

Every target below states a metric, a threshold, the measurement method and what happens if it fails. "Corpus" means a published, versioned set of recorded real-world pages plus Speedometer 3, JetStream and MotionMark, run on named reference devices: one x86-64 Windows laptop, one Apple Silicon Mac, one Linux desktop with an Intel Gen12+ GPU and one Android device with ≥4 GB of RAM. There are **no speedup targets relative to Chromium** before Stage 3, and none promise a multiple. The research contains no evidence that would support one. P-1 is not an exception: it is a floor measured against this engine's own single-threaded path, calibrated below the HiPC 2016 best case (3.2x) because the same study found no gain on some sites. Pages where parallelism is net-negative are handled by the adaptive policy and covered by P-1's ≤2% regression bound, not by the median.

**The `cppgc` spike (answers Q-1b(a); run 14 October 2026; code in `cppgc-spike/`, results in its `RESULTS.md`).** Platform: macOS arm64 (Apple M4), crate `v8` 152.2.0 (V8 15.2.124.1), against both the release and the debug prebuilt V8 library. Each item is listed as specified, in order of likely failure, followed by its result.

1. **No-GC and no-compaction held together across a worker phase.** The script thread enters a scope that blocks both GC finalization and compaction, worker threads read traced fields of script-thread-owned objects, and the scope is also entered while concurrent marking is already in progress. Run under TSAN with zero findings. Also record whether entering the scope under active marking **blocks, defers marking, asserts, or deadlocks**, and the entry latency distribution. Scope entry runs under a watchdog timeout, because TSAN does not report a hang. Blocking means worker phases can stall on GC, which then needs a P-1 latency budget; asserting or deadlocking means the spike has failed. (Workers read only inside this scope; S-4c forbids reads while GC can run.)
   *Result: PASS on behavior, with narrower semantics than this item assumed.* Entering the scope while marking was active never blocked, deferred marking, asserted or deadlocked; entry took about 2 ns (p99 42 ns, max 65 µs). But **`NoGarbageCollectionScope` does not stop a GC that V8 itself starts**: in a unified heap, 5,000 objects were finalized while the scope was held. What made worker reads safe was structural. The heap's owning (script) thread stays blocked for the whole worker phase. It holds both `NoGarbageCollectionScope` and `DisallowGarbageCollectionScope`, so any GC attempt on that thread becomes a deterministic crash instead of a silent free. And the heap has **no compactable spaces**: `rusty_v8` creates its `CppHeap` with none, so compaction cannot move objects. Under that guard the spike ran 10,244 worker phases with marking active, with 0 finalizations and 0 errors. The disallow scope turned a GC request into a crash, as intended, and a forced-compaction probe hit a debug check. S-4c now states this guard rather than "a no-GC scope".
2. **Cross-thread access without `CrossThreadPersistent`.** V8's own header marks that handle "DO NOT USE" because the graph may be moved concurrently on the owning thread ([cppgc headers](https://chromium.googlesource.com/v8/v8.git/+/main/include/cppgc)), so the spike must show the item 1 pattern works with raw pointers inside the scope instead.
   *Result: PASS on behavior.* About 16,600 worker phases read through raw pointers under the item 1 guard, with 0 errors and 0 finalizations during worker phases. TSAN (Rust nightly) ran with zero findings and caught a deliberately planted race. V8 itself was not built with TSAN, so races inside V8 are not covered.
3. **DOM-to-JS edges.** A `cppgc`-managed DOM object holds a `TracedReference` to its JS wrapper and survives a forced unified GC, and a DOM-JS cycle is collected. Rust-owned (non-GC) structs may only hold JS objects through `v8::Global` roots, which cannot break cycles, so any DOM object that can participate in a cycle must be `cppgc`-managed.
   *Result: PASS with `rusty_v8`'s public API.* The wrapper survives a precise unified GC while the DOM side roots it. A DOM–JS cycle through an expando closure is collected. A Rust struct holding a `v8::Global` leaks, as predicted. One trap: `rusty_v8`'s one-argument testing GC scans the stack conservatively, so a stray stack pointer can keep a cycle alive. Cycle tests must use V8's precise two-argument form.
4. **GC objects owning Rust data.** A `cppgc` object holds a plain field owning Rust data (`Box`/`Arc`, e.g. Stylo element data), and the Rust destructor runs on collection. `Member` is not used for this, because it can only point at garbage-collected objects.
   *Result: PASS with the public API.* Drop counts were exact, and `Drop` ran on the script thread. Prefinalizers also work, through the companion crate below.
5. **Heap-consistency checks in a debug build** catch a deliberately omitted write barrier in Rust code.
   *Result: PASS only against debug V8.* The debug build's marking verifier reports the omitted barrier ("MarkingVerifier: Encountered unmarked object"). Release V8 misses it silently and leaves a dangling pointer, because heap verification is a compile-time V8 build option with no runtime switch. A debug-V8 configuration is therefore mandatory in CI (S-4c).

A sixth item, added by HGBA-3.0's decision D8, measured the cost of the F1 data plane. Its results are recorded there.

**What the spike changed: API exposure.** Items 3 and 4 use only `rusty_v8`'s public API. The GC scopes, heap state, heap statistics, prefinalizers and the precise testing GC are exported by the prebuilt V8 library but not wrapped by `rusty_v8`. The spike reached them through mangled C++ symbol names, which is acceptable for a test and not for a product. The project has since built **`v8-cppgc-ext`** (`v8-cppgc-ext/`), a companion crate. It compiles a small C++ shim against the same V8 headers and Chromium libc++ as the prebuilt library and wraps the shim in safe Rust. Its 28 integration tests and 4 doc tests pass against both the release and the debug prebuilt on macOS arm64. The ported spike items reproduce the original results; for item 1, that was 13,302 phases with 0 finalizations. **Items 1 and 2 passed, so the primary path is available under the guard stated in item 1's result.** The fallback shapes below stay defined for two reasons: HGBA-3.0 makes F1 its default for reasons unrelated to GC, and the guard could still fail on platforms or configurations the spike did not test. The planning pass must know which shape it is estimating:

- **F1 (preferred): a Rust-owned style/layout mirror.** The DOM stays in `cppgc`, so GC stays sound and cycles are collected. The script thread maintains a Rust-owned mirror of exactly what style and layout read (tree links, tag, attributes, classes, state flags). Workers read only the mirror and never touch `cppgc` memory. Costs: memory, update work on every mutation, and a consistency risk. The mirror contract:
  - **The mirror holds element-level data only; CSS data needs no mirror.** Style's other inputs are already Rust-owned outside the JS heap in Stylo's design: stylesheet rule data and declaration blocks (including the parsed inline `style` attribute) are shared `Arc` data behind Stylo's lock, the user-agent sheet and media/viewport state live in Stylo's own structures, and CSSOM mutations (`insertRule`, `deleteRule`, `CSSStyleDeclaration` setters) write to that data and mark the stylist dirty. Workers read it directly. The mirror stores a reference to each element's inline declaration block, not a copy. *Derived from the CSSOM specification and Stylo's public API (re-derived 17 October 2026):* CSSOM defines a CSS style sheet's rules as a mutable list that `insertRule` and `deleteRule` change in place ([CSSOM: CSSStyleSheet](https://drafts.csswg.org/cssom/#the-cssstylesheet-interface)), and a `CSSStyleDeclaration` as a list of declarations whose setters update the owner node's `style` attribute ([CSSOM: CSSStyleDeclaration](https://drafts.csswg.org/cssom/#the-cssstyledeclaration-interface)). Stylo's public types hold that data outside the JS heap: a stylesheet's contents hold its rules as `Arc<Locked<CssRules>>`, guarded by the stylesheet's `SharedRwLock`, and a declaration block is an `Arc<Locked<PropertyDeclarationBlock>>` ([stylo docs](https://docs.rs/stylo/latest/style/)). Izcal's CSSOM wrappers therefore hold `Arc`s to Stylo data, write through the lock, copy shared rule data on write, and tell the stylist which stylesheet sets changed. One refinement follows: setting the `style` attribute re-parses it into the element's declarations ([CSSOM: the `style` attribute](https://drafts.csswg.org/cssom/#the-elementcssinlinestyle-mixin)), and because Stylo's blocks are shared `Arc`s, the re-parse produces a new block rather than mutating one another holder may share. Setting inline style can therefore *replace* the element's declaration-block reference, and a changed inline-style reference is an element-level mutation that goes through the mutation log like any other. Custom property values, pseudo-element styles and container-query results are style and layout *outputs*, stored in Rust-owned per-element data, not inputs to mirror.
  - **Script never reads the mirror.** Script reads DOM inputs (`classList`, attributes, tree) from the DOM, and reads outputs (`getComputedStyle`, geometry) from style and layout results after a flush. The mirror is private to style and layout workers. Routing a script read through the mirror is a bug, because a read before the next flush would return stale data and no flush-time check could see it.
  - **Mutations are logged, not applied.** Every DOM mutation that affects a mirrored field appends to a mutation log and sets dirty bits rather than recomputing eagerly, because style and layout results are observable only at the flush points below.
  - **The flush point is the start of every style/layout pass**, not a task or microtask boundary. The log is applied synchronously before workers start, on every path that runs style or layout: the rendering update and every forced synchronous flush (`getComputedStyle`, `offset*`/`client*`/`scroll*` geometry, `getBoundingClientRect`, `ResizeObserver` delivery, and custom-element reactions that read layout). A layout pass that starts without flushing is a bug, so stale reads are a conformance failure (S-4d), not only a performance one.
  - **The log is closed during a flush, so no fixpoint loop is needed inside it.** Style and layout never run script, so nothing can append to the log between the start of the flush and the end of the pass. Custom-element reactions run at `[CEReactions]` scope exits and microtask checkpoints, not inside style or layout. `ResizeObserver` callbacks run after layout, in the HTML "update the rendering" steps, and any mutations they make land in the log for the next pass. The repeat-until-settled behavior lives in the HTML spec's own `ResizeObserver` loop, which re-runs style and layout (and therefore flushes again) with a depth limit. Debug builds assert that the log does not grow during a flush.
  - **Atomicity comes from quiescence, which is structural.** Izcal runs layout on the script thread, which only spawns workers for the parallel phase. The reason is first-principles: every forced synchronous flush above is a script call that cannot return until style and layout are current, so script waits for layout anyway (P2 requires the up-to-date answer), and a separate layout thread would add a cross-thread round trip to each such call without removing the wait. With layout on the script thread, the only mutator is blocked while workers read. The mirror is never updated concurrently with a read, and no lock or copy-on-write is needed. Moving layout to its own thread would lose this property, and the mirror would have to become copy-on-write.
  - **Consistency checking is pre-release only.** Debug builds cross-check mirror against DOM after every flush. Nightly-channel builds cross-check a sampled fraction of flushes and report mismatches as crashes, to catch drift before it reaches release. Release builds have no in-process check and rely on what debug, Nightly, conformance tests and fuzzing caught earlier.
  - **Under F1, S-4c and P-1 change meaning.** S-4c becomes: workers never dereference `cppgc` pointers (allocator guard); mirror-vs-DOM consistency holds at every flush point, including forced synchronous flushes; the mirror and its flush discipline are race-free under TSAN; and the stress suite targets forced-flush interleavings rather than GC scopes. P-1 is measured on whichever shape ships, and under F1 its style+layout time includes the mirror flush. Spike item 1's outcome matters only for the primary path: under F1 workers never touch `cppgc`, the script thread (the heap's owner) is blocked during the parallel phase, and no no-GC scope is needed at all, because concurrent marking helpers only read `cppgc` memory that workers never access.
- **F2: single-threaded style and layout.** No new infrastructure, but P-1 is dropped and parallelism is limited to raster and other non-DOM work.
- **F3 (rejected): DOM outside `cppgc` with manual tracing.** A DOM outside the JS heap needs the JS collector to see edges that pass through the DOM, or cycles through JS cannot be collected. V8 offers no such hook: current V8 headers no longer define `EmbedderHeapTracer`, leaving only `EmbedderRootsHandler` for non-unified GCs ([v8-embedder-heap.h](https://chromium.googlesource.com/v8/v8.git/+/refs/heads/main/include/v8-embedder-heap.h)), so unified DOM–JS tracing goes through `CppHeap`. Without it, the wrapper is found from the DOM through a weak `v8::Global` and the DOM from the wrapper through an internal field, and any cycle that passes through JS (an expando, a closure holding a node) either leaks or loses the wrapper early. That is a correctness problem, not a cost. Making F3 sound would mean building a cycle collector that can traverse the V8 heap, or new GC hooks, against an engine whose maintainers removed the old ones. That is a research project with a third-party dependency, not a Stage 1 task.

**Why V8, and why the decision is made before Stage 1.** HGBA-2.0 originally chose SpiderMonkey because Servo, then the planned base, already integrated it, and deferred the cage question to a Stage 1 exit gate. That combination was contradictory: P1 ranks security first, S-4 made a ≤3% heap cage a ship blocker, and no SpiderMonkey mechanism can meet it.

- **Why V8's cage is cheap.** V8's sandbox reserves a 1 TiB region, stores in-sandbox pointers as offsets from its base, and reaches code and out-of-sandbox objects through code-pointer and external-pointer tables. JIT code adds SFI-style masks only on the remaining raw accesses ([V8 blog](https://v8.dev/blog/sandbox); [Mohabi, OSDI 2026](https://www.usenix.org/conference/osdi26/presentation/sharma) §7.4). This builds on pointer compression, which V8 adopted in 2020 and which the sandbox requires ([V8 pointer compression](https://chromium.googlesource.com/v8/v8.git/+/main/docs/heap/pointer-compression.md)). SpiderMonkey stores full 64-bit NaN-boxed values; no public source shows a plan to change that representation.
- **Why SpiderMonkey's options are expensive.** Without that representation, a cage needs software fault isolation on every engine memory access. Mohabi, a full SFI sandbox of SpiderMonkey inside Firefox, costs **24.43% on Speedometer and 24.82% on JetStream** on x86-64, with an incomplete boundary-sanitization layer ([Mohabi, OSDI 2026](https://www.usenix.org/conference/osdi26/presentation/sharma)). Three of its authors are Mozilla engineers, but the paper makes no upstreaming commitment. An earlier UT Austin thesis that sandboxed only the JIT compiler reported about 13.7% ([UT Austin](https://repositories.lib.utexas.edu/items/1bcc09e3-0b38-4108-959b-93e8a3a21316)). Both miss the 3% threshold by roughly 4–8x.
- **Why Mozilla's roadmap does not matter here.** Mozilla does not disclose its plans to outside projects, so a gate of the form "Mozilla commits to a date" can never be evaluated. Even if Mohabi were upstreamed tomorrow, its measured cost fails S-4b. The decision therefore does not depend on information HGBA-2.0 cannot get.
- **What it costs.** Izcal writes its WebIDL bindings and DOM tracing on `rusty_v8`/`cppgc` (target S-4c); no existing bindings serve that pairing. V8 also has no stable embedding API, so the project tracks Deno's `rusty_v8` release cadence. SpiderMonkey's integrated riscv64 JIT is lost, but V8's port is near parity (Section 6).
- **The bindings layer is V8-specific, and the spec says so.** No browser ships engine-neutral JS-DOM bindings: Blink, Gecko and WebKit each bind to their own engine. React Native's JSI runs on several engines but holds host objects by reference counting rather than GC tracing, which a DOM full of cycles cannot rely on. Izcal writes its own bindings generator (`hg-webidl-codegen`), which emits a V8 backend; parsing uses a standalone WebIDL parser crate or Izcal's own, and no Servo or Gecko code generator is used (M-1). Migrating to another engine means writing a new backend and GC integration, which is why D2's trigger is "evaluate a migration", not "swap".
- **Owning `rusty_v8`.** A browser that cannot update its JS engine cannot ship security fixes. A named owner for the project's `rusty_v8` dependency is recorded in the Stage 1 kickoff document, and Stage 1 does not start without it. Policy: track Deno's `rusty_v8` releases; ship V8 security fixes within one Chrome stable cycle of their release; if upstream `rusty_v8` lags Chrome stable's V8 security patches by more than two weeks, or Deno stops maintaining it, switch to a project-maintained fork, as Servo maintains `servo/mozjs` for SpiderMonkey. Since revision 2.1.1 the fork is the plan of record from M0 (start condition (ii)), so the two-week rule now governs how far the fork may drift from upstream, not whether it exists: past two weeks of lag, the owner rebases or backports under S-4e. The owner also owns the fork's `cppgc` commits and the upstream patch offered for them; every V8 update follows S-4e's update procedure, and that work counts against the same security-fix window.
- **Why threading is the real integration risk.** Script callbacks (custom elements, `ResizeObserver`, `getComputedStyle`) run on the script thread, so JS never executes on style or layout workers. The danger is different: on the primary path, Izcal's parallel style and layout workers read DOM nodes directly (Stylo's traversal reads elements through `TElement`), while `cppgc` heaps are thread-affine and may move objects concurrently on the owning thread ([cppgc cross-thread-persistent.h](https://chromium.googlesource.com/v8/v8.git/+/main/include/cppgc)). Workers must therefore be read-only on GC-managed objects and run while GC and compaction are excluded. The spike showed what "excluded" has to mean: the owning thread is blocked holding both GC scopes, and the heap has no compactable spaces, since compaction applies only to such spaces. A no-GC scope on its own does not exclude V8-initiated collection. S-4c tests exactly that guard. Izcal runs layout on the script thread for the reasons in F1's contract (Section 6): forced synchronous layout makes script wait for layout anyway (P2), and the owner blocked during the parallel phase is what gives the flush its structural quiescence. A separate layout thread would widen the exposure above and is not part of this design.
- **Hardened profile threat model (resolves Q-1c).** The Hardened profile's security claim is **no runtime machine-code generation**. It is not a claim of fewer bugs. DrumBrake is treated as being in the same trust class as the JIT: memory-unsafe C++ that processes attacker-controlled input, contained by the V8 sandbox and the process sandbox like the rest of V8. CVE counts are not used as the gate, because a young interpreter under new fuzzing attention and a mature JIT under years of it are not comparable per CVE. Instead: Wasm stays on by default in Hardened; an enterprise policy and a per-profile setting can turn it off; and any confirmed in-the-wild DrumBrake exploit switches Hardened's Wasm default to off, with a UI notice, until the fix ships.
- **What the cage is and is not.** V8's sandbox is a partial SFI scheme with a long record of bypasses ([Mohabi, OSDI 2026](https://www.usenix.org/conference/osdi26/presentation/sharma) §7.4). It is defense in depth behind site isolation and the process sandbox, not a primary boundary. HGBA-2.0 adopts it because it is cheap, not because it is sufficient.

## 8. Non-goals

HGBA-2.0 does not use confidential-computing VMs (TDX, SEV-SNP, CCA) as a content sandbox. It does not give web content, renderers or any sandboxed process direct access to NICs, PCIe configuration space, GPU MMIO or userspace drivers. It does not offer per-site microVMs. It does not treat protection keys as a site boundary. It does not run Wasm on GPUs or NPUs, and it does not compile page JavaScript to Wasm for performance. It does not schedule individual small tasks onto accelerators, and it does not expose vendor-specific device APIs or TOPS-based scheduling. It does not provide allocatable SRAM, CXL or persistent-memory tiers on clients, and it does not persist live DOM or JS heaps. It does not put post-quantum or any other cryptography on quantum hardware. It does not commit to photonic, neuromorphic, quantum or analog-compute deliverables (see Appendix A). It makes no pre-committed speedup multiple over Chromium or any other engine. Izcal copies, ports or translates no code from another browser engine (M-1, Stage 1 design D-S10).

### 9.2 Open questions

Q-1 (answered): SpiderMonkey has no shipped or publicly planned V8-style heap sandbox; the measured SFI alternatives cost 13.7–24.8%. D2 now selects V8. Q-1a: Does a SpiderMonkey heap sandbox, or a pointer-compression change, ship on by default in a Firefox Release build? Monitored on the D2 cadence (each stage boundary and each Firefox ESR release). Q-1b(b) (Stage 1 exit gate, feeds S-4c's soak): Can that integration carry a browser-scale DOM within a frame budget? Pass/fail on the corpus and reference devices, excluding last-resort GCs under OS memory pressure: **p99 main-thread GC pause ≤4 ms; no pause >16.7 ms; GC-attributed missed frame deadlines in <1% of frames** during normal DOM mutation. Q-5: Will any browser engine commit to native Component Model support? Mozilla's experiments showed "close to a 2x speedup" on a DOM-heavy loop from direct Wasm-to-Web-API calls, and V8 has opened an evaluation issue, but neither is a commitment ([Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)). ## Conclusion

The main correction in HGBA-2.0 is a change of method. HGBA-1.0 described hardware by its *peak* capability. HGBA-2.0 describes it by its *reachable* capability: what a sandboxed process can touch, through which OS framework, at what fixed cost, with what failure mode. Seen that way, the growth headroom for a 2026 browser lies in places HGBA-1.0 overlooked. These are adaptive CPU parallelism, a single GPU render graph shared by raster, compositing and WebGPU, coarse-grained ML-runtime offload with measured break-even, and hardware memory-safety features layered on process isolation. Exotic devices are not where the gains are.

The second implication is that hardware growth is now mostly a *standards and broker* problem, not an engine-core problem. A new engine contributes most by shipping the abstractions others are still waiting on: native Component Model support counts toward its two-engine gate, and a riscv64 tier with a full sandbox would be the first production one. The spec is built to be proven wrong cheaply. Each target has a kill criterion, the JS engine decision states the public evidence that would re-open it, and every accelerated path keeps a CPU fallback that leaves correctness intact.

## Appendix A: Research Horizon (speculative hardware, not roadmap deliverables)

Nothing in this appendix is a deliverable. A technology moves into the roadmap only when it meets all four **entry criteria**. First, it ships in volume in client devices (laptops, desktops, phones or headsets). Second, the OS exposes it through a documented framework or driver interface that a sandboxed service process can use. Third, a standard or proposed web API can express its capability, or it improves an existing one invisibly. Fourth, independent (non-vendor) measurements show a benefit on browser-relevant workloads after dispatch overhead.

**CHERI capability hardware** is the most valuable horizon item for HGBA-2.0's security goals. Chromium has been ported to Morello with about **0.045% of base LoC and 0.8% of V8 LoC changed** (self-reported), and CHERI deterministically mitigates CVE-2023-4863 ([AsiaBSDCon 2026 slides](https://2026.asiabsdcon.org/media/entry/question_uploads/20260322-asiabsdcon-freebsd-cheri_BQqZECW.pdf)). It exists today only on research boards, as FPGA/IP (Codasip) and on CHERIoT microcontrollers, and no client CPU implements it ([Design & Reuse](https://www.design-reuse.com/news/202530469-why-codasip-went-all-in-on-cheri/); [cheriot.org](https://cheriot.org/)). *Preparation now:* keep pointer provenance clean (no integer/pointer laundering) and prefer offset-based handles, so a CHERI build stays cheap.

**Client CXL memory** fails criterion one. AMD's estimate put it 3–5 years out as of 2023–24, and the only client socket design is a 2024 proposal ([Notebookcheck](https://www.notebookcheck.net/AMD-estimates-that-CXL-technology-with-improved-storage-performance-could-come-to-consumer-platforms-in-3-5-years.664216.0.html); [FMS 2024](https://files.futurememorystorage.com/proceedings/2024/20240807_CXLT-201-1_Gervasi.pdf)). If it arrives, it will appear as a CPU-less NUMA node managed by kernel tiering, and the advisory memory policy in Section 4.6 needs no change.

**Analog in-memory compute** is the most plausible exotic client device. If it arrives, it will be one more NPU behind the OS ML runtime and reached through WebNN. EnCharge's EN100 M.2 card claims 200+ TOPS at 8.25 W (vendor claim), and no OEM laptop with it was confirmed ([DCD](https://www.datacenterdynamics.com/en/news/encharge-ai-launches-its-analog-in-memory-en100-ai-accelerator/)). IBM's 14 nm PCM chip remains research ([The Register](https://www.theregister.com/2023/08/14/ibm_describes_analog_ai_chip/)). No browser architecture change is needed beyond the `MlRuntime` device class.

**Photonic compute** fails criteria one and two. Commercial photonics is data-center interconnect: Lightmatter Passage, and Celestial AI, which Marvell acquired in February 2026 ([Lightmatter](https://lightmatter.co/press-release/lightmatter-unveils-passage-m1000-photonic-superchip-worlds-fastest-ai-interconnect/); [Marvell](https://investor.marvell.com/news-events/press-releases/detail/1005/marvell-completes-acquisition-of-celestial-ai)). Photonic matrix compute exists only as lab packages and rack servers. Lightmatter's Nature-paper system drew 78 W, and Q.ANT sells 19-inch rack units ([Q.ANT](https://qant.com/press-releases/q-ant-launches-first-commercial-photonic-processor-for-energy-efficient-high-performance-computing-and-real-time-ai-applications/)). Photonic ray-box intersection is a single-component lab demo ([Nat. Commun. 2025](https://ideas.repec.org/a/nat/natcom/v16y2025i1d10.1038_s41467-025-61234-x.html)). Browsers benefit only indirectly, through cheaper cloud inference.

**Neuromorphic hardware** runs spiking or sparse networks, not DOM, JS or rasterization. Intel's Hala Point is a 2,600 W research system ([New Electronics](https://newelectronics.co.uk/content/news/intel-builds-world-s-largest-neuromorphic-system)). Edge parts such as BrainChip Akida, Innatera Pulsar and SynSense Speck target always-on sensor pre-processing ([HPCwire](https://www.hpcwire.com/aiwire/2025/05/22/innatera-unveils-pulsar-neuromorphic-microcontroller-for-the-sensor-edge/); [ASX filing](https://announcements.asx.com.au/asxpdf/20260727/pdf/0722fx6s9yf2w9.pdf)). Their plausible web touchpoint is invisible: a gaze or gesture signal surfaced through WebXR or media APIs. Event-based *sensors* are real ([Prophesee GenX320](https://www.vision-systems.com/cameras-accessories/image-sensors/article/14300297/prophesee-launches-event-based-vision-sensor)). Event-driven *displays* exist only as patents ([USPTO](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10559247)). Loihi 3 is **unverified**.

**Quantum computing** fails every criterion. Superconducting qubits run at about 10 mK in dilution refrigerators drawing 5–10 kW, access is through cloud job queues with second-to-hour round trips against an 8–16 ms frame budget, and no known quantum speedup applies to browser workloads ([Quartz](https://qz.com/quantum-computer-data-center-architecture-explained-051126)). Fault-tolerant machines are roadmapped for 2029 as data-center systems: IBM Starling with 200 logical qubits, and Quantinuum Apollo ([IBM roadmap](https://ibm.com/roadmaps/quantum); [Quantinuum S-1](https://www.sec.gov/Archives/edgar/data/0002110105/000162828026032836/quantinuum-sx1.htm)). The browser's quantum work is classical post-quantum cryptography, which is already specified in Section 4.7. Gidney's 2025 estimate that RSA-2048 falls to under a million noisy qubits in under a week is what makes crypto agility urgent ([arXiv 2505.15917](https://huggingface.co/papers/2505.15917)).

**RISC-V** is the one item that already meets the entry criteria for a *CPU platform*. RVA23 makes RVV 1.0 mandatory ([RISC-V International](https://riscv.org/blog/risc-v-announces-ratification-of-the-rva23-profile-standard/)), and SpacemiT K3 silicon ships in boards and a Framework mainboard ([Phoronix](https://www.phoronix.com/news/Ubuntu-SpacemiT-K3)). It is therefore on the roadmap as target X-1, not in this appendix. Its remaining horizon question is width-agnostic SIMD. Wasm's flexible-vectors proposal is Phase 1, and Cranelift fully supports SIMD only on x86-64 and aarch64 ([features.json](https://github.com/WebAssembly/website/blob/main/features.json); [Cranelift README](https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/README.md)).
