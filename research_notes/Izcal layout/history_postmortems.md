# Izcal layout: history and postmortems

Compiled 19 October 2026. Primary sources were preferred (specifications, papers, engine teams' own blog posts and design documents written as prose, W3C minutes, CSSWG resolutions, bug-tracker discussion text).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known date not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no engine source code was read for this note. No code files, headers, commits, diffs, code-review pages or source browsers of Blink, Gecko, WebKit, Servo, Ladybird, Taffy, Yoga, Flutter or any print engine were opened. The Chromium LayoutNG README and a Chromium code review appeared as links in search results; neither was opened or used. Where this note says what an engine "does", it is evidence to reason from, not a shape to copy.

## 1. The CSS formatting model and the engines built for it (1996–2020)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **CSS1** (1996) and **CSS2** (1998) defined layout as prose about boxes: the visual formatting model, normal flow, floats, positioning and tables. CSS2 described *results*, not an algorithm. Engines invented their own algorithms. | CSS1 REC 1996-12-17; CSS2 REC 1998-05-12 | [CSS 2.1 Tables chapter](https://www.w3.org/TR/CSS21/tables.html) (successor text); dates from W3C TR history | 1996–1998 | Medium |
| 1.2 | **CSS 2.1** became a Recommendation after 13 years of revisions. It still leaves central table behaviour undefined: the automatic table layout algorithm "is non-normative" and "UAs are not required to implement this algorithm"; "CSS 2.1 does not define how the height of table cells and table rows is calculated"; "does not define the meaning of 'height' on row groups". | §17.5.2.2, §17.5.3 | [CSS 2.1 §17](https://www.w3.org/TR/CSS21/tables.html) | 2011-06-07 | High |
| 1.3 | **Tables-for-layout era.** Before CSS positioning worked across browsers, authors built page grids from nested HTML tables and spacer GIFs. Table layout therefore became the most compatibility-critical and least specified layout mode at once. | — | Researcher recollection; consistent with 1.2 and 4.10 | 1996–2005 | Low |
| 1.4 | **IE5 Mac "Tasman"** shipped on 27 March 2000 and was seen as the most standards-compliant engine of its day. Mozilla had planned DOCTYPE switching from November 1998 and shipped it in M11 (November 1999), per David Baron's reply. | Ship 2000-03-27; Tasman 0.9 in MSN for Mac OS X, May 2003 | [Tasman (Wikipedia)](https://en.wikipedia.org/wiki/Tasman_(browser_engine)); [Baron, www-html 2003-06](https://lists.w3.org/Archives/Public/www-html/2003Jun/0130.html); [Çelik, www-html 2003-06](https://lists.w3.org/Archives/Public/www-html/2003Jun/0131.html) | 2000–2003 | Medium |
| 1.5 | **Quirks modes are a permanent layout tax.** DOCTYPE switching froze a second set of layout behaviours (box sizing, table cell heights, line-height quirks) into every engine. It was a deliberate escape hatch for incompatible fixes. | — | Same as 1.4; WHATWG Quirks Mode spec exists for this reason | 1999– | Medium |
| 1.6 | **IE "hasLayout"** was an internal Trident flag. An element that "has layout" sized and positioned itself and its children. An element without it relied on its nearest ancestor with layout. Some elements had it by default; properties like `width`, `height`, `float`, `position: absolute`, `display: inline-block` and the proprietary `zoom: 1` set it. Whether a box became a layout root changed float containment, margin collapsing and stacking. That produced IE5–7 bugs such as the "peekaboo", "three-pixel jog" and "double margin" bugs. Authors fixed them by forcing hasLayout. | Not a CSS concept; exposed as `currentStyle.hasLayout` | Researcher recollection of Ingo Chao et al., "On having layout" (2005) and Microsoft's "HasLayout Overview"; both pages were unreachable this session | 2005 | Low |
| 1.7 | Microsoft's Markus Mielke told www-style that "HasLayout will be history with IE8". IE8 (2009) shipped a rewritten standards-mode layout engine that passed CSS 2.1 tests. | Quote dated 2007-12-20 | [Ingo Chao reply quoting Mielke, www-style](https://lists.w3.org/Archives/Public/www-style/2007Dec/0155.html) | 2007-12-20 | High (quote); Medium (IE8 outcome) |
| 1.8 | **Lesson of hasLayout.** An implementation detail (which boxes are layout roots) leaked into visible behaviour because the engine's internal box boundaries did not match the spec's formatting-context boundaries. CSS later made the concept explicit as the **block formatting context**, and `display: flow-root` (2017) gives authors a clean way to create one. | — | Inference from 1.6; `flow-root` in CSS Display 3 | 2017 | Medium |
| 1.9 | **Gecko's design.** Gecko lays out a **frame tree** separate from the content tree. Some content nodes have several frames or none. Layout is `Reflow()` recursion with a parent-built **ReflowInput** and a child-filled **ReflowOutput** plus a **reflow status**. Incremental reflow uses two dirty bits (`IS_DIRTY`, `HAS_DIRTY_CHILDREN`) and **reflow roots** that promise their rect does not change when descendants change. | — | [Gecko Layout Overview (firefox-source-docs, prose)](https://firefox-source-docs.mozilla.org/layout/LayoutOverview.html) | updated 2024-05 | High |
| 1.10 | Gecko represents fragmentation (lines, columns, pages) with **continuations**: a doubly linked list of frames per element, "fluid" ones that can be rewrapped and "fixed" ones for bidi. Overflow on fixed-height content in pagination uses invisible **overflow containers**. The docs admit open debts: "scrollbars are reflow roots but don't quite obey this invariant", reframing is "an expensive operation, and we'd love to avoid it", and code still mixes physical and logical coordinates. | — | [Gecko Layout Overview](https://firefox-source-docs.mozilla.org/layout/LayoutOverview.html) | updated 2024-05 | High |
| 1.11 | Gecko's frame-lifetime rule: "Frames are not reference counted, and code must not hold on to pointers to frames." It uses arena allocation and **frame poisoning** to blunt use-after-free. The guidance is that the frame tree "should generally not store any data that cannot be recomputed on-the-fly." | — | [Gecko Layout Overview](https://firefox-source-docs.mozilla.org/layout/LayoutOverview.html) | updated 2024-05 | High |
| 1.12 | **WebKit render tree.** KHTML (1998) became WebKit (Safari, 2003). Dave Hyatt's "WebCore Rendering" Surfin' Safari series (2007) described a mutable **RenderObject** tree that holds both style-derived inputs and layout outputs, dirty bits (`needsLayout`) and layout-in-place. Blink inherited this design in 2013, and LayoutNG was later built to replace it (Section 2). | — | Researcher recollection of the Surfin' Safari series; not fetched | 2007 | Low |
| 1.13 | **Presto** (Opera 7, 2003) was a separate engine with its own layout. Opera announced its move to WebKit/Blink in February 2013. One fewer independent layout implementation meant less pressure to resolve CSS ambiguities through interop. | — | Researcher recollection | 2003–2013 | Low |
| 1.14 | **EdgeHTML** (Trident fork, 2015) reimplemented tables in 2018. Chrome's TablesNG post credits that rewrite as the origin of **CSS Table Module Level 3**, which was "written after Edge reimplemented tables in 2018". Edge moved to Chromium in January 2020, ending EdgeHTML layout. | — | [TablesNG post](https://developer.chrome.com/blog/tablesng) | 2021-06-16 | High (2018 rewrite and spec link); Medium (Jan 2020 switch) |

**Implications:** Every engine of 1998–2015 kept inputs, outputs and dirty state in one mutable tree, and every one later paid for it. Izcal should not adopt that shape. Izcal's box boundaries must equal the spec's formatting-context boundaries, so no internal "layout root" concept can leak into visible behaviour the way hasLayout did. Quirks mode must be in scope from day one as a recorded, deterministic mode flag (JS-D15).

| 2.18 | **Total duration.** Design doc 2016–17 → inline/block 2019 → legacy layout gone in Chrome 108 (late 2022). That is about six years for a staged replacement of a production engine while it stayed compatible. | ~6 years | 2.1, 2.17 | 2016–2022 | High |

**Implications:** LayoutNG is the strongest evidence for Izcal's layout shape: pure function of (node, style, constraint space) → immutable fragment, with the constraint space as the cache key and one central diffing point. That matches HGBA-3 B5 (incremental checked against from-scratch). Fragmentation must be native from the start; every engine that bolted it on had to rewrite. The 5–10x object-count estimate warns that a naive fragment tree will break Izcal's 360 B layout+paint budget. Fragments must be packed columns, not ref-counted heap objects.

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Meyerovich and Bodík (WWW 2010)** motivated parallel layout by power-limited mobile hardware. | 3.14 | **Ladybird** (SerenityOS's LibWeb, independent since 2024) writes its own layout from the specs, with formatting-context classes per CSS mode. **Implications:** The measured parallel layout gains are small: 1.4–1.8x on 4 threads in Servo 2015 and 2–4x in simulations in 2010. Floats serialize whole sections. Servo abandoned eager parallelism for correctness and maintainability. Izcal should design layout to be **parallel-capable at independent formatting-context boundaries**, scheduled deterministically (JS-D15). It must not make correctness depend on parallelism, and it should expect style, not layout, to be the main parallel win. Servo's grid friction is a further argument for Izcal owning every layout mode itself.

Grid-lanes is new enough that Izcal can design for it from the start rather than retrofit it.

## 5. Non-browser layout systems as evidence of ideas

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **TeX** models text as **boxes, glue and penalties**. Knuth and Plass ("Breaking Paragraphs into Lines", Software—Practice and Experience 11(11), 1981) choose breaks that minimize total "badness" for the whole paragraph by dynamic programming, not greedily per line. Browsers broke lines greedily for 25+ years. CSS `text-wrap: pretty` and `balance` (2023–) are the first steps toward paragraph-level optimization. | 1981 | Researcher recollection of the paper; `text-wrap` from CSS Text 4 | 1981 | Medium |
| 5.2 | **Cassowary** (Badros, Borning, Stuckey, ACM TOCHI 2001) is an incremental simplex solver for linear equality and inequality constraints with priorities. Apple **Auto Layout** (2011) is built on a Cassowary-style engine. | — | Researcher recollection; [Auto Layout write-up (secondary)](https://juejin.cn/post/6844903619360194568) | 2001 | Medium |
| 5.3 | Auto Layout's performance problems came from **constraint churn** and global solving. Apple's WWDC 2018 session "High Performance Auto Layout" advised: "never remove all the constraints and add them back, change only the necessary ones"; hide views instead of removing them; treat `systemLayoutSizeFitting` as expensive because it forces a fitting pass. iOS 12 was presented as a significant engine speedup. | — | [WWDC18 220 notes](https://wwdcnotes.com/documentation/wwdc18-220-high-performance-auto-layout/) | 2018-06 | Medium |
| 5.4 | **Flutter** chose a **single-pass** protocol for explicit performance reasons: "Some other toolkits use layout algorithms that are O(N²) or worse (for example, fixed-point iteration in some constraint domain)". Constraints go down, geometry goes up, and "each render object is visited at most twice". A child's layout "cannot depend on its position", so parents can reposition without relayout. | O(N) initial, sublinear updates | [Inside Flutter](https://docs.flutter.dev/resources/inside-flutter) | read 2026-10-19 | High |
| 5.5 | Flutter cuts off relayout in four documented cases: unchanged constraints on a clean child; parent does not use the child's size; **tight** constraints; and a child that sizes only from its constraints. Intrinsic sizes and baselines are the exception: they need an extra subtree walk with "aggressive caching" to avoid quadratic worst cases. | — | [Inside Flutter](https://docs.flutter.dev/resources/inside-flutter) | read 2026-10-19 | High |
| 5.6 | **Yoga** (Meta) is "an embeddable layout system" that implements "a familiar subset of CSS, mostly focused on Flexbox". It does no drawing and delegates text measurement to the host. It is used by React Native. Known deviations from web flexbox (for example a column default direction) are recollection only. | — | [About Yoga](https://www.yogalayout.dev/docs/about-yoga) | read 2026-10-19 | High (scope); Low (deviations) |
| 5.7 | **Taffy** is a Rust library for block, flexbox and grid used by Servo (grid), Blitz and Zed among others. It has no inline/text layout of its own. Recorded here as history only; Izcal will not use it. | — | Researcher recollection; [W3C Servo minutes](https://www.w3.org/2025/11/12-updates-on-servo-minutes.html) | 2025 | Low |
| 5.8 | **Print engines** (Prince since ~2003; Antenna House; WeasyPrint, a BSD-licensed Python engine; Vivliostyle, a JS CSS typesetter) implement CSS Paged Media and GCPM (running headers, footnotes, page floats, cross-references). Browsers mostly do not. They show that pagination-first CSS layout is feasible and that browser print layout lags behind. | — | Researcher recollection | 2003–2026 | Low |

**Implications:** Flutter's one-pass, constraints-down protocol and LayoutNG's constraint-space cache key converge on the same idea, which supports Izcal adopting it. Global constraint solving (Cassowary) gives flexible authoring but unpredictable cost and churn, so it is a poor core for a deterministic engine with per-node budgets. TeX shows that paragraph-level line breaking must be designed in with TX-D4, not added later.

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **CSS Regions removed from Blink.** Eric Seidel tried removing the Regions code and found the patch "was over 10,000 lines", against "~350,000 code lines" of Blink C++, with "around half … sprinkled across 140+ files". | 6.4 | **`position: sticky` shipped and unshipped.** It landed in WebKit in 2012. | 6.8 | **Hysteresis** (results depend on layout history) is the signature of under-invalidation in mutable-tree engines. The documented Blink example is an "infinitely growing" rectangle fixed only in Chrome 93. | Chrome ≤92 | [RenderingNG: LayoutNG](https://developer.chrome.com/docs/chromium/layoutng) | 2021 | High |
| 6.9 | **Layout thrashing** (forced synchronous layout): script that interleaves DOM writes with geometry reads (`offsetHeight`, `getBoundingClientRect`) forces a full layout per read. It exists because synchronous geometry APIs expose layout to script with no batching contract. | — | Researcher recollection | 2013 | Low |
| 6.10 | **Margin collapsing** is the most-cited source of formal complexity. VizAssert needed a finitization reducing the set of collapsing margins to six reals and one boolean. | 6.11 | **Floats** recur as the hardest feature in every source: Meyerovich (ambiguous, inconsistent, sequential dependencies), Servo (2013 float fixes broke the traversal model; 2020 floats stalled, then serialized parallelism), Blink legacy (fixed retry counts next to floats), VizAssert (needed a novel "exclusion zone" formalization). | — | 3.3–3.4, 3.8–3.9, 2.6, 7.3 | 2010–2023 | High |
| 6.12 | **Legacy fragmentation by slicing** (2.16) is a design postmortem in its own right: fragmentation at paint time cannot implement `break-*: avoid`, monolithic overflow or per-fragment effects. **Implications:** Recurring causes: features that cut across layout, scrolling and compositing without a shared model (Regions, sticky), caches without one central validity rule (hysteresis, Gecko flex), and late fragmentation. Izcal's invariant should be that layout output is a pure function of recorded inputs, with incremental results checked against a from-scratch reference (B5). That catches under-invalidation and hysteresis by construction. Sticky and scroll anchoring must be designed jointly with the scrolling/compositing spec.

## 7. Formal methods and verification of layout

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **Cassius** (Panchekha and Torlak, "Automated Reasoning for Web Page Layout", OOPSLA 2016, pp. 181–194) encoded a fragment of CSS 2.1 block layout in SMT for reasoning and synthesis. It could not handle line-height computation, margin collapsing or general floats, because the standard describes them as operations on arbitrary-sized sets. | — | As cited in [VizAssert §1, ref 39](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf) | 2016 | Medium |
| 7.2 | **VizAssert** (Panchekha, Geller, Ernst, Tatlock, Kamil; PLDI 2018) introduced "visual logic" and **finitization reductions** from the spec's unbounded sets to fixed-size summaries. It checked 14 accessibility assertions on 62 professional pages and found **64 errors with 13 false positives**. | 14; 62; 64; 13 | [VizAssert (PLDI 2018)](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf) | 2018-06 | High |
| 7.3 | VizAssert passed all in-scope W3C conformance tests for CSS 2.1 §8.3–8.3.1 (margins, collapsing), §9.5–9.5.2 (floats, clearance) and §10.8–10.8.1 (line height). 91 failures all used unsupported features (vertical-align, RTL, SVG). On **5 tests its rendering differed from Firefox's**, and Firefox's was the incorrect one. Firefox's rendering also differs from the standard by fractions of a pixel through rounding, so comparisons used 1/6 px tolerance. | 91 out-of-scope; 5 Firefox bugs; 1/6 px | [VizAssert §5](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf) | 2018 | High |
| 7.4 | VizAssert's authors call **tabular layout** a research challenge in "understanding browser implementations, developing finitization reductions, and handling various edge cases". This matches the table under-specification in 4.9–4.10. | — | [VizAssert §6](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf) | 2018 | High |
| 7.5 | **Troika** (OOPSLA 2019) adds **modular layout proofs**: per-component specifications with rely/guarantee preconditions. It verified a page 11x larger than prior work in 30 s versus up to 19 hours, a **13–1469x** speedup. | 11x; 13–1469x | [Modular Verification of Web Page Layout](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-modular-oopsla2019.pdf) | 2019-10 | High |
| 7.6 | Meyerovich's attribute grammars (3.3–3.5) are the other formal line. VizAssert's authors note that attribute-grammar formalizations cover a smaller CSS subset than VizAssert and are "not meant for verification, only rendering". | — | [VizAssert §7](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf); 3.4 | 2010–2018 | High |

**Implications:** Formal work repeatedly found real engine bugs (Firefox on 5 conformance tests) and spec gaps (floats, margin collapsing, tables, termination). Izcal can turn its deterministic, pure layout function into an executable reference: a slow, obviously-correct path per formatting context, written from the spec text, that the fast incremental path is diffed against (B5). The finitization ideas (margin struts as six values; float exclusion zones) map directly onto compact per-node layout state that fits the 360 B budget.

## 8. Cross-cutting lessons for Izcal

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | Three independent groups (Blink LayoutNG, Servo layout 2020, Flutter) converged on **box tree in → immutable fragment tree out, constraints down, sizes up**, with the constraint as cache key. | 3 designs | Sections 2, 3, 5 | 2015–2023 | High |
| 8.2 | Both large rewrites took years and shipped by stages, mode by mode, with the old engine as fallback: Blink about 6 years (2.18), Servo about 2 years from report to removal (3.11–3.12). | ~6 y; ~2 y | 2.18, 3.12 | — | High |
| 8.3 | The modes that were retrofitted (fragmentation, multicol, printing, tables, sticky) had the longest bug tails. The oldest Blink table bug was 13 years old when fixed. | 2008 → 2021 | 2.14, 2.16 | — | High |
| 8.4 | Parallel layout's measured benefit has been modest (1.4–4x), and floats limit it. Correctness and incrementality delivered larger user-visible wins (exponential → linear). | 1.4–4x vs 2^n → n | 3.2, 3.7, 2.10 | — | High |

**Implications:** Izcal should build every mode, fragmentation and print included, on one constraint-space/fragment protocol from day one. It is a new engine with no legacy fallback, so it cannot rely on gradual replacement and must reach mode-completeness through its own staged plan validated by WPT.
