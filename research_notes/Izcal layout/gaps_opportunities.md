# Izcal layout: gaps_opportunities

Compiled 19 October 2026. Primary sources were preferred (specifications, survey reports, maintainers' posts, release notes, Stack Exchange API data, the `web-features` data set).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**M-1 note.** No engine source code was opened, read or cited for this note: no code files, headers, commits, diffs, code reviews or source browsers of Blink/LayoutNG, Gecko, WebKit, Servo, Ladybird, Taffy or any other engine. Evidence is specification prose, survey reports, release notes, design documents written as prose, documentation and API data.

**Scope.** What web developers struggle with in layout, what layout keeps invisible today, where layout meets accessibility, what breaks on real pages, which new interactions Izcal's architecture could offer, and which emerging layout features the engine must plan for. It covers phases 2–3 of the first-principles-spec method. Synthesis belongs to the spec author.

**Method notes.**
- Roughly 30 web searches and fetches. Specification text was downloaded directly from `drafts.csswg.org` and `wicg.github.io` and searched locally (prose only).
- Feature status comes from the **`web-features` npm package, version 3.43.0**, fetched from unpkg on 2026-10-19 (`data.json`, Baseline status and per-browser "support" versions). This data set lists a browser only when it judges support complete, so it can disagree with vendor announcements; conflicts are flagged.
- Stack Overflow counts come from the public Stack Exchange API (`/tags/.../info`, `/questions`), queried on 2026-10-19.
- Rows that build on the earlier Izcal DevTools research note (`research_notes/Izcal DevTools spec/invisible_gaps.md`) cite the primary source it read and say so.
- No HTTP Archive or Web Almanac figure on forced synchronous layout prevalence was found. No current Mozilla webcompat statistics by category were found. Both are open questions.

**Implications:** developers ask symptom-shaped questions ("why is this box this size", "why is there a scrollbar", "why is this not sticky"), not "debug my layout". The engine data needed to answer them (min-content contributions, automatic minimum sizes, which ancestor clips or scrolls) exists inside every layout pass. Izcal's layout should record the **reason chain** for a box's size as cheap structured data, so the tools can answer the top questions directly.

**Implications:** a large part of modern layout is **stateful across frames** (last successful position option, last remembered size, remembered scroll offsets, scroll-state snapshots, scroll anchor selection). Under JS-D15 each of these is a decision that must be recorded or derivable for replay, and each is also exactly what developers cannot see today. Izcal should treat them as named, recorded layout state with stable IDs: the replay requirement and the DevTools requirement are the same data. Interleaving being undefined in the spec (3.8) means Izcal must pick and document an order and test it deterministically.

**Implications:** layout must hand the semantic plane (HGBA-3 B8) more than boxes. It needs bounding rectangles per accessible node, line boundaries and text-run boundaries for caret and screen-reader navigation, the reading-flow order of each container, and a consistent skip decision for `content-visibility: auto`. 4.8 is a hard rule for Izcal: the accessibility path must never do layout work the visual path skipped, or timing reveals AT users. A layout tool that flags "visual order ≠ DOM order" and "reflow fails at 320 px / text-spacing clips here" would turn WCAG 1.3.2, 1.4.10 and 1.4.12 into checks the engine can actually run.

**Implications:** CLS has improved but one page in five on desktop still fails it, and unsized images, fonts and non-composited animations persist. Print is the area where engines were broken longest; Izcal should build fragmentation into the fragment tree from day one rather than slice afterwards, and make break decisions explainable.

## Open questions and black-box measurements needed

1. **Forced synchronous layout prevalence.** No HTTP Archive, Web Almanac or Lighthouse figure was found. Needs a crawl measurement (e.g. count geometry reads after writes per page in Izcal's own harness, or an HTTP Archive custom metric).
2. **Webcompat layout statistics.** No current Mozilla or webcompat.com breakdown by category (layout vs JS vs UA sniffing) was found. Ask Mozilla's webcompat team or mine the public webcompat issue tracker's labels.
3. **Text-wrap: pretty behaviour per engine.** Chromium "last four lines" is a vendor statement quoted by WebKit. Black-box measurement needed: compare break positions across engines on a fixed corpus.
4. **Cost of decision records.** How large is a per-box explanation record and how often is it written during a typical relayout? Prototype measurement in Izcal; no outside data exists.
5. **Style ↔ layout interleaving order.** The spec calls it undefined (3.8). Black-box measurement needed: how many re-entry rounds Chrome, Firefox and Safari perform for nested container queries plus anchor fallback, and whether results agree.
6. **Timing of last successful position option and last remembered size** relative to ResizeObserver delivery in each engine. Black-box tests needed before Izcal fixes its event-loop placement.
7. **Grid lanes property names.** `flow-tolerance` (shipped in Safari 26.4) vs `fit-tolerance` (editor's draft): which name will survive, and does Safari alias both? Re-check before implementing.
8. **Anchor positioning Baseline status.** `web-features` says not Baseline while WebKit says interoperable; identify which subfeatures are missing (Firefox 147 support is inferred from a subfeature row, not confirmed).
9. **Firefox Grid Inspector version and date** (recollection: Firefox 52, March 2017). Verify against Mozilla release notes.
10. **State of CSS 2026 per-item percentages** are not published; the 2026 figures here were read for the DevTools note and graded Medium.
11. **Accessibility-tree geometry requirements.** Which platform APIs (UIA, AT-SPI, NSAccessibility) need per-line and per-character rectangles, and how often they query them, is not covered here. That determines whether line and glyph boundaries must be retained after layout or recomputed on demand.
12. **Demand for layout diffs and replay** is inferred from visual-test flakiness (2.13), not measured. A developer survey or Izcal opt-in telemetry is needed before ranking 7.5 above 7.1–7.3.
