# Izcal layout: incremental_parallel

Compiled 19 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only, or recollection not checked this session.

M-1 note: no engine source code was read or cited for this note (no code files, headers, commits, diffs, code reviews or source browsers). One search result returned links to a Blink header on crrev.com; it was not opened and nothing from it is used. Every value that only an engine's source states is listed in the last section as a black-box measurement.

Method: about 40 searches and fetches, run in question order (1, 3, 2, 4, 7, 6, 8, 5). Two papers were read in full text from their PDFs: Meyerovich and Bodík, WWW 2010, and Zambre et al., HiPC 2016. The rest came from the page text of blog posts, design documents, specs and mailing-list messages. "Analysis" in the Source column marks my own reasoning from the cited facts. It is not a finding of the source.

|---|---|---|---|---|---|
| 1.1 | Blink's legacy layout tree was mutable. Each layout object held both its inputs and its outputs. | 1.11 | Flutter: one layout per frame, in a single pass. Constraints go down and geometry comes back up. Each render object is visited "at most twice": once down, once up. | 1.12 | Flutter has four cut-off rules. (a) A clean child given the same constraints returns at once. (b) A parent that does not use the child's size need not relayout when that size changes. (c) Under tight constraints the child cannot change size, so the parent need not relayout. (d) A child that sizes only from its constraints ("sized by parent") does not dirty its parent. Rules (b) to (d) produce what Flutter calls relayout boundaries. | 4 rules | [Inside Flutter](https://docs.flutter.dev/resources/inside-flutter) | current | High |
| 1.13 | In Flutter, a parent that reads a child's layout output must say so (`parentUsesSize`). Doing so ties the two nodes: the parent is marked dirty whenever the child is. | — | [RenderObject.layout API reference](https://api.flutter.dev/flutter/rendering/RenderObject/layout.html) | current | Medium (API reference prose) |
| 1.14 | Flutter's intrinsic-dimension and baseline queries walk the subtree an extra time. Flutter says "aggressive caching is used to mitigate the potential for quadratic performance in the worst case", and calls such cases "surprisingly rare". | quadratic worst case | [Inside Flutter](https://docs.flutter.dev/resources/inside-flutter), footnote 2 | current | High |
| 1.15 | Servo's layout was "all-or-nothing" until mid-2025: "any change in the page, no matter how isolated, requires laying out the entire page from scratch." Servo calls incremental layout "a key performance optimization in all browser engines." | 0 incremental reuse before 2025 | [This month in Servo, June 2025](https://servo.org/blog/2025/06/18/this-month-in-servo/) | 2025-06-18 | High |
| 1.16 | Servo's incremental work covers five stages: style, box tree, fragment tree, stacking-context tree and display list. Servo now skips display-list construction when nothing would change, which shows most when the mouse moves. Script geometry queries skip up-to-date style, box-tree and fragment-tree work, and some are answered "without doing any work at all". Changes to transform, scale, rotate, translate and perspective often avoid layout. No timings were published. | 5 stages; "big perf gains" without figures | [This month in Servo, July 2025](https://servo.org/blog/2025/07/17/this-month-in-servo/) | 2025-07-17 | High |
| 1.17 | Spineless Traversal (Kirisame, Wang, Panchekha; PLDI 2025). The standard dirty-bit traversal walks the tree from the root, touching clean auxiliary nodes on the way to dirty ones, and pays cache misses and stalls for it. Spineless Traversal drives incremental layout from a cache-friendly priority queue of dirty nodes instead. The largest gains are on hovering, typing and animation. | Faster on 83.0% of 2,216 benchmarks; mean 1.80× | [arXiv 2411.10659](https://arxiv.org/abs/2411.10659); [PLDI 2025 page](https://pldi25.sigplan.org/details/pldi-2025-papers/73/Spineless-Traversal-for-Layout-Invalidation) | 2024-11-16 (v1); PLDI 2025-06-19 | High (abstract) |
| 1.18 | The CSS Layout API draft bakes caching into its processing model. A UA "may re-use the intrinsic sizes from a previous invocation" when children, edges and styleMap are equivalent. For fragments, it may reuse a previous fragment when children, styleMap, constraints and break token are equivalent. The draft lets a UA cache "an arbitrary number of previous invocations". | key = (children, style, constraints, break token) | [CSS Layout API Level 1, ED](https://drafts.css-houdini.org/css-layout-api-1/) §6.2.2 | ED 2026-02-25 | High |

**Implications:** The evidence points one way. Constraint-keyed caching on an immutable, up-pointer-free fragment tree is the shipping answer, it removes the "dirty bit plus ad-hoc diff" bug class, and Izcal should adopt it with the cache key defined in the spec rather than in code. Spineless Traversal's 1.80× mean shows that the order in which dirty work is found is itself a performance decision. Izcal's columnar DOM (JS-D4) suits a dirty-set or priority queue better than root-down spine walks.

## 2. Exponential and quadratic layout

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Layouts that need two passes over a child (measure, then layout) cost 2 visits per level without caching. Nested to depth n, that is 2^n visits of the innermost box. | 2.4 | Hysteresis bugs: non-idempotent layout let a box grow without bound when a property toggled between two values. Fixed in Chrome 93. LayoutNG prevents the class by forbidding reads of the previous layout's state. | Chrome 93 | [LayoutNG](https://developer.chrome.com/docs/chromium/layoutng) | 2021-10-08 | High |

| 2.11 | Meyerovich and Bodík proved, for their BSS0 box language as an attribute grammar, that layout terminates and is at worst linear in tree size, and log time for balanced trees. **Implications:** Every multi-pass algorithm in Izcal (flex, grid, tables, percentage resolution, intrinsic sizes) must go through one shared measure and layout cache, keyed by the full constraint input, and that cache is a correctness and complexity requirement, not an optimisation. The spec should carry a falsifiable bound: visits per box under nested-depth tests stay below a constant, checked with depth-20 nested flex and grid fixtures.

Any parallel path must produce bit-identical fragments to the serial path, checked as part of JS-D15 replay.

**Implications:** Izcal has no external per-object baseline to beat, so its 360 B layout+paint per-node budget must be checked by its own measurement. Fragment-tree double-buffering costs only the spine, not a second tree.

## 6. Incremental computation theory and correctness checking

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | Meyerovich and Bodík specify layout as attribute grammars, with inherited attributes going top-down and synthesized attributes bottom-up. ## 7. Determinism and units

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | WebKit's LayoutUnit stores positions and sizes as integer multiples of 1/64 CSS px, which allows integer math and avoids floating-point imprecision. | 1/64 px | [WebKit wiki: LayoutUnit](https://trac.webkit.org/wiki/LayoutUnit) | wiki (rev. history 2012–2014) | High |
| 7.2 | LayoutUnit was originally 1/60, "based on Mozilla's implementation". It changed to 1/64 in September 2012, to stop losing precision when converting between LayoutUnits and float-based Lengths and to avoid integer division. | 1/60 to 1/64, 2012-09 | same | 2012-09 | High |
| 7.3 | Subpixel layout's stated motivation was zoom, on desktop and mobile. | — | same | 2012 | High |
| 7.4 | WebKit's pixel-snapping rule rounds left and top edges to the nearest device pixel and derives the right and bottom edges from the precise far edge: width = round(x+w) − round(x). The snapped edges of adjacent boxes therefore line up. | — | same | 2012 | High |
| 7.5 | Subpixel layout was enabled for the Apple, Chromium and EFL ports by 2013. A 2014 WebKit meeting noted directional rounding errors in non-horizontal-tb writing modes. | — | [WebKit wiki: 2014 Meeting Subpixel Layout](https://trac.webkit.org/wiki/2014%20Meeting%20Subpixel%20Layout) | 2013–2014 | Medium (search summary) |
| 7.6 | Gecko's app units: 60 per CSS pixel, device-independent, chosen to allow subpixel positioning. They landed in Gecko in February 2007. | 1/60 px | [Robert O'Callahan, "Units Patch Landed"](https://robert.ocallahan.org/2007/02/units-patch-landed_07.html) | 2007-02-07 | High |
| 7.7 | The commonly given reason for 60 is that 1/2, 1/3, 1/4 and 1/5 px are exact. No primary design rationale was checked. | 60 = 2²·3·5 | [otsukare, CSS width in Gecko](https://www.otsukare.info/2016/05/26/css-width-gecko) | 2016-05-26 | Medium |
| 7.8 | Trade-off between 1/60 and 1/64: 64 is a power of two, so float↔fixed conversion is exact and cheap, but thirds are inexact. 60 keeps thirds and fifths exact but makes float conversion lossy. Results differ between engines at the 1/60 versus 1/64 grain, so WPT tests carry tolerances. | — | Analysis of 7.2, 7.7 | — | Medium |
| 7.9 | Chrome's LayoutNG hysteresis fix (2.4) is a determinism result: layout must be a function of current inputs only, never of previous outputs. | — | [LayoutNG](https://developer.chrome.com/docs/chromium/layoutng) | 2021-10-08 | High |

**Implications:** Izcal should lay out in integer fixed point, consistent with the integer metrics of TX-D4, and choose its denominator by stating the conversion trade-off. 1/64 matches Blink and WebKit for interop and makes float conversion exact. A fixed-point type with defined saturation is deterministic across CPUs and thread orders, which JS-D15 requires.

**Implications:** Izcal's layout output must include a scroll and sticky description in a property-tree form that a compositor can mutate without main-thread layout. That is the contract to design, not "layout on another thread". A future author-layout API inherits Izcal's purity and caching rules for free if the engine's own algorithms already obey them.

## Open questions and black-box measurements needed

1. **LayoutUnit range and saturation in Blink and WebKit.** What is the maximum representable px value, and do operations saturate? Measure: set `width` to growing powers of two and read `getBoundingClientRect` and `offsetWidth` until it clamps.
2. **Gecko app-unit range** (int32 at 1/60 px). Measure the clamp the same way in Firefox.
3. **Blink constraint-space cache contents.** Which inputs form the key (percentage-resolution size, fixed-size flags, fragmentainer state, baseline requests)? Black-box: count relayouts with DevTools layout counts while varying one input at a time.
4. **Blink "simplified layout" and the layout-root/relayout-boundary equivalents** (for example `contain: strict` or `size` acting as a layout root). Measure layout scope in traces when mutating inside contained versus uncontained subtrees.
5. **Taffy and Yoga caching.** The number of cache slots, keyed by known dimensions and available space, is documented mainly in code. No prose source was found. History only, not needed for Izcal.
6. **Per-object memory.** Bytes per LayoutObject, NG fragment and fragment item in Blink; per nsIFrame in Gecko; per fragment in Servo. Measure with heap snapshots on synthetic pages of N identical `div`s and N text runs, and take the slope of memory against N.
7. **Layout share of Speedometer 3 and MotionMark** per engine. Trace each subtest and attribute layout time.
8. **Real-world forced-layout frequency.** Collect LoAF `forcedStyleAndLayoutDuration` distributions; HTTP Archive or CrUX analyses were not found.
9. **Servo 2024–2026 parallel layout speedups** (tables and block): none published. Measure with Servo's thread-count setting on table-heavy pages.
10. **The LayoutQuickCheck paper** (venue and per-browser bug counts) was not located. The blog post gives no per-browser totals.
11. **Nested flex and grid visit counts per engine.** Depth-20 nested `display:flex` with percentage children: time one property change in each engine to confirm linear scaling, using the 50–100 ms rule.
12. **Why the Houdini Layout API stalled.** Look for the CSSWG and Houdini TF minutes after 2020, and the Blink intent threads (discussion prose only).
13. **The full text of Adapton PLDI 2014 and of Meyerovich's PPoPP 2013 schedule-synthesis paper** for their speedup numbers. Abstracts only this session.
