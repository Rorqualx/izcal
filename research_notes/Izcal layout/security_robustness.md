# Izcal layout: security_robustness

Compiled 19 October 2026. Primary sources were preferred (NVD CVE descriptions, Project Zero posts and its 0-day "In the Wild" sheet, papers, specifications, vendor blogs).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or prior knowledge not re-fetched this session; **Low** = secondary source only, or recollection.

**M-1 note.** No engine source code was read for this note (no Blink, Gecko, WebKit, Servo, Ladybird, Taffy or other code, commits, diffs or code reviews). Where a value (a depth cap, a coordinate maximum) is known to live only in source, it is listed as a black-box measurement to make.

**Method notes.**
- **CVE counts are this note's own tallies** over NVD CVE descriptions (prose), fetched through the NVD 2.0 keyword API on 19 October 2026. NVD keyword search matches words, so the counts are **lower bounds**. From about 2015 to 2020 Chrome described most renderer bugs as "Use after free in Blink", which hides the layout component; from 2021 Chrome names "Layout" or "Blink Layout". Mozilla named Bugzilla components ("the Layout: Text and Fonts component") only from about September 2025. Apple's WebKit notes name no component, so WebKit layout bugs cannot be counted from prose.
- The **Project Zero 0-day sheet** ([P0 sheet](https://docs.google.com/spreadsheets/d/1lkNJ0uQwbeC1ZTRrxdtuPLCIl7mlUreoKfSIgajnSyY/)) was exported as xlsx on 19 October 2026: 414 unique CVE rows, 2014 to 2026. Browser renderer rows outside JS engines, GPU, media and IPC were read by hand.
- The shared web-search budget ran out after 7 searches. The rest of the evidence came from direct fetches of known primary pages (about 20). Items not re-fetched are graded Medium or Low and listed in the last section.
- Chrome's yearly Chrome Releases blog prose was not tallied post by post (budget). The NVD tally stands in for it.

**Implications:** Layout bugs in C++ engines are overwhelmingly **lifetime bugs** (UAF, stale pointers, type confusion) with a tail of **index and integer arithmetic** bugs (heap overflows, boundary conditions, integer overflow). A Rust layout with no `unsafe` removes the first class by construction and turns the second into panics or wrong output. Izcal must therefore treat **panic = denial of service** and make the arithmetic class explicit: checked or saturating geometry, and index types that cannot address outside their table.

**Implications:** Every lifetime class above comes from **layout and script sharing mutable objects across a call that can run script**. Izcal's layout should never call out to script or to anything that can mutate the DOM: it reads a frozen DOM and style snapshot (node columns, JS-D4) and writes a separate immutable fragment output. Events that layout causes (resize, intersection, scroll, focus) are queued as recorded inputs (JS-D15) and delivered after layout returns. Clipping of a frame's content to its border box (2.8) must be a hit-testing and paint invariant with a test.

**Implications:** Layout bugs are found mainly by **grammar and context-aware DOM fuzzers** (crash oracle) and by **differential or metamorphic oracles** (wrong output). Izcal can make the strongest oracle built in: every incremental layout is checkable against a from-scratch layout of the same frozen input, byte for byte (the 4.6 oracle, as HGBA-3 B5 does for style), and determinism makes any mismatch a reproducible test case. A Rust panic or assertion (4.3) found by fuzzing is a DoS bug and must be triaged like a crash.

## 5. Denial of service and resource limits

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **HTML caps `colspan` at 1000** (larger values become 1000) and **`rowspan` at 65534**; `rowspan=0` spans the rest of the row group. `span` on `col`/`colgroup` is capped at 1000. Auto-fill floors track size (suggested 1px) to avoid division by zero | ±10,000 lines | [CSS Grid 2 §5.4 Limiting Large Grids](https://drafts.csswg.org/css-grid-2/#overlarge-grids) | ED 2026 | High |

| 5.10 | **Line breaking and text**: Firefox's glyph-width OOB read in text layout (CVE-2017-5447) and the 2026 "Layout: Text and Fonts" CVEs (5 of 11, 1.6) show text is the busiest layout subcomponent for bugs | 5 of 11 | row 1.6 | 2026 | High |

**Implications:** The specs give a few hard caps (colspan, rowspan, span) and permission to clamp (grid lines, numeric ranges), but no fuel or time budget. Each engine's chosen caps are observable and engine-specific. Izcal should publish **deterministic, documented limits** (grid lines ±10,000 as the spec suggests; table spans per HTML; a maximum box-tree depth with a defined fallback; a maximum fragment count per layout), store sparse table grids, and give layout **canonical fuel** in units of work. On exhaustion the result must be specified and the same on every machine (for example, deeper boxes are laid out as `display: none` or as empty boxes) so that B1 replay holds. Recursion must not use the native stack for depth that content controls.

| 6.4 | Chrome's 2024 "Integer overflow in Layout" (CVE-2024-7025) was rated High: integer overflow in layout still led to heap corruption in 2024 | 1 High | [CVE-2024-7025](https://nvd.nist.gov/vuln/detail/CVE-2024-7025) | 2024-11-27 | High |

**Implications:** Fixed point is the right base (integer, deterministic, TX-D4 integer metrics fit it), but the range must be a **specified constant** and every operation on it must **saturate** (or be checked with a defined result), never wrap. Izcal should pick its unit (for example 1/64 px in i32, or i64 if the 360 B budget allows) by design, document the maximum, and test that the same overflowing page lays out identically on every platform. Sizes used as indices (table slots, grid tracks, line counts) must be separate integer types with explicit caps.

Izcal's bundled fonts and integer metrics (TX-D4) make geometry identical across users of one build, which closes most of 7.1. Timing needs a stronger rule: layout work must not depend on cross-origin or history state (one code path, as in 7.3), and any time a page can observe should come from the deterministic clock. Fragment scrolling and lazy loading of cross-site frames are policy decisions to record, not to leave to layout.

**Implications:** Occlusion is a **layout and hit-testing guarantee**: the engine must be able to prove that the visible, hit-testable pixels of a cross-origin frame equal its own rendering, unaltered. With one deterministic fragment and paint tree, Izcal can compute "unoccluded and unaltered" exactly rather than conservatively, but should still return false whenever the proof fails. Content of a frame must never render or hit-test outside its clip (2.8).

## Design implications for Izcal (ideas, not decisions)

1. **No re-entrancy.** Layout is a pure function of (frozen DOM columns, computed style, viewport, fonts) to an immutable fragment tree. It calls no script and mutates no DOM. Observer callbacks and events are produced as a list and delivered afterwards (sections 2, 5.7).
2. **No `unsafe` in layout, and no panics on content.** Indexing uses checked typed indices; arithmetic saturates. A panic reachable from content is a security bug (4.3).
3. **Canonical fuel and published limits.** Box-tree depth, fragment count, grid lines (±10,000), table spans (HTML caps), sparse table grids, line count per block, and a work budget per layout pass, all identical on every platform, with specified fallbacks (section 5).
4. **Fixed-point geometry with a documented range** and saturating operations; overflow behaviour is part of the spec and of the conformance tests (section 6).
5. **Built-in oracle.** Incremental layout checked against from-scratch layout in debug and fuzzing builds; metamorphic checks in CI (4.6, 4.8).
6. **Side-channel discipline.** Layout work independent of history and cross-origin state; geometry from bundled fonts; observable time from the deterministic clock (section 7).
7. **Exact occlusion.** Implement IntersectionObserver v2 semantics from the fragment and paint trees (section 8).
