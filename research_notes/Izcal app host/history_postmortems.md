# Izcal app host: history and postmortems

Compiled 21 October 2026. Primary sources were preferred (official blogs, press releases, papers, specifications, vendor documentation). This strand covers the history of in-browser application platforms and sandboxed-native-code runtimes; the accepted HGBA spec already records the current Component Model status (Phase 1 in the CG, no browser ships it natively, the two-engine gate, WASI 0.3 released 11 June 2026), so those facts are referenced, not re-argued.
Evidence rule (M-1 part 3): no third-party source code was opened for this note — all claims rest on prose: papers, official blog posts, press releases, spec text and vendor docs. Mozilla's blog domains (blog.mozilla.org, hacks.mozilla.org) block this session's fetcher, so several Mozilla pages were read through archived copies or cited at Medium confidence. No email addresses appear in this note.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary page identified but only title/snippet verifiable, or a vendor claim without data; **Low** = secondary source only.

## 1. Native Client and PNaCl (2008–2021)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | NaCl was announced on 8 December 2008 as "Native Client: A Technology for Running Native Code on the Web". The original Google blog post could not be opened this session (offline, archive copies unavailable), so the announcement text is unverified; the technical design is fully covered by the 2009 paper (1.2). | — | [Google blog announcement (unreadable this session)](https://googleblog.blogspot.com/2008/12/native-client-technology-for-running.html) | 2008-12-08 | Medium |
| 1.2 | The founding paper (IEEE S&P 2009) states the motivation: ActiveX and NPAPI "allow plugins to circumvent the security mechanisms otherwise applied to web content", and the resulting non-technical trust measures "have been inadequate to prevent execution of malicious native code" — so there is "a prejudice against native code extensions for browser-based applications". NaCl separates "safe native execution from that of extending trust". | — | [Yee, Sehr, Dardyk, Chen, Muth, Ormandy et al., "Native Client: A Sandbox for Portable, Untrusted x86 Native Code" (PDF)](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/34913.pdf) | 2009-05 (IEEE S&P 2009) | High |
| 1.3 | Sandbox design from the paper: an **inner sandbox** (software fault isolation plus x86 segmented memory — 80386 segments constrain data references to a 256 MB region, and the CS segment constrains instruction fetch; a static validator enforces reliable disassembly and bans `syscall`/`int` and segment-state-modifying instructions) and an **outer sandbox** (OS system-call interception at the process boundary), plus a trusted **service runtime** in the same process with trampoline call gates. NaCl modules are loaded into "a segment-isolated 256MB region" with a 64 KB guard region and a null-pointer page. | 256 MB region; 64 KB guard | [Same paper (PDF)](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/34913.pdf) | 2009-05 | High |
| 1.4 | Architecture support at launch: "NaCl modules are 32-bit x86 executables. The more recent 64-bit executable model is not supported." | 1.9 | PNaCl launched: "developers compile their code once to run on any hardware platform… The LLVM-style bytecode is wrapped into a portable executable… Chrome fetches and translates the portable executable into an architecture-specific machine code optimized directly for the underlying device… developers don't need to recompile their applications multiple times to run across x86, ARM or MIPS devices." | 1.10 | The LLVM-bitcode problem, stated by the WebAssembly Community Group's own FAQ: LLVM IR "is not portable (the same program has different representations for different architectures) or stable (it changes over time as optimization and language requirements change)"; bitcode "was designed for temporary on-disk serialization of the IR for link-time optimization, and not for stability or compressibility". PNaCl's answer was customisation: "PNaCl defines a small portable subset of the IR with reduced undefined behavior, and a stable version of the bitcode encoding. However, each customization, workaround, and special solution means less benefit from the common infrastructure." | — | [WebAssembly FAQ, "Why not just use LLVM bitcode as a binary format?"](https://webassembly.org/docs/faq/) | ~2015 (living FAQ) | High |
| 1.11 | The same FAQ explains why Wasm instead of asm.js: binary format decodes "more than 20× faster than JavaScript can be parsed" (large mobile codes "can easily take 20–40 seconds just to parse"), and a new standard is "easier to add the features required to reach native levels of performance"; Wasm is designed to reuse the JS engine's "existing compiler backend… security sandboxing mechanisms". | 20× decode | [WebAssembly FAQ](https://webassembly.org/docs/faq/) | ~2015 | High |
| 1.12 | Deprecation, in the maintainer's own words (Brad Nelson): "running native code on the web required a browser plugin. Removal plan: PNaCl "in the first quarter of 2018 everywhere except inside Chrome Apps and Extensions". Note the post does *not* mention LLVM bitcode churn; the bitcode-format reasoning is in the FAQ (1.10). | Q1 2018 removal plan | [Chromium blog, "Goodbye PNaCl, Hello WebAssembly!"](https://blog.chromium.org/2017/05/goodbye-pnacl-hello-webassembly.html) | 2017-05-30 | High |
| 1.13 | Actual removal: the official migration guide says Google planned "to remove support for PNaCl in Q4 2019 (except for Chrome Apps)"; Chrome 76 put web-platform PNaCl behind a deprecation origin trial "scheduled to last through Chrome 78, approximately until December 2019". NaCl/PNaCl/PPAPI inside Chrome Apps survived to June 2021 per the 2020 timeline (2.5), and Chrome Apps themselves ended June 2022 (2.6). The migration target: "For the majority of (P)NaCl use cases we recommend transitioning from the NaCl SDK to Emscripten" (WebAssembly), and TCP/UDP sockets have no direct replacement (WebRTC/WebSocket/WebTransport suggested). | Ch 76→78 trial; Q4 2019 | [Chrome for Developers, "WebAssembly migration guide"](https://developer.chrome.com/docs/native-client/migration) | 2019 (updated 2020) | High |
| 1.14 | Cross-browser reality: no other browser ever shipped NaCl/PNaCl — the 2013 post says "Chrome only", and by May 2017 the situation was unchanged. Mozilla chose the asm.js route instead (announced 26 March 2013; this session could not open the post — Mozilla's domains block the fetcher). Wasm's support at the moment of the goodbye post: "Chrome and Firefox support WebAssembly natively and Edge and Safari support WebAssembly in preview versions." | 0 other browsers | [Chromium blog 2017-05-30](https://blog.chromium.org/2017/05/goodbye-pnacl-hello-webassembly.html); [Mozilla Hacks asm.js announcement (unreadable this session)](https://hacks.mozilla.org/2013/03/asm-js-in-firefox-nightly/) | 2017-05-30 / 2013-03-26 | High / Medium |
| 1.15 | The security record has two verifiable layers this session: the design claims (1.3, 1.5) and academic verification work — the RockSalt project (PLDI 2012) produced a formally verified SFI checker for x86, motivated by the difficulty of getting NaCl's validator right by hand. No primary maintainer statement about the exploit record (Pwn2Own or CVE history) was found; see Open questions. | — | [Morrisett et al., "RockSalt: Better, Faster, Stronger SFI for the x86", PLDI 2012](https://dl.acm.org/doi/10.1145/2254064.2254111) | 2012-06 | Medium |

**Implications:** NaCl's death had three independent causes, all documented in primary prose: (a) a distribution format (LLVM bitcode) that was never designed to be stable, so portability had to be patched on with a frozen subset and constant maintenance; (b) a single-vendor plugin-shaped API surface (Pepper) in a market where the *standard* (Wasm) became the product; (c) zero cross-browser adoption, which by 2017 was the deciding factor ("did not provide a solution that worked seamlessly across all browsers"). The sandbox itself was never the stated problem — SFI + segmentation + validator + outer sandbox was regarded as strong enough that Google recommended NaCl as the *safe* replacement for NPAPI. For Izcal this means: the sandbox is the easy half of the problem; the distribution format and the API surface are where these platforms die.

The killer was not the platform's quality but the *relative* cost: once the open web absorbed offline, push and installability, a parallel proprietary platform became pure maintenance burden. Any Izcal app host must answer "why not a PWA?" before it answers anything else.

For Izcal's app host: the app-ecosystem problem is not solved by the runtime — it is solved by who ships apps with you, and by choosing a niche the web platform does not already serve better.

**Implications:** Across fifteen years of platforms, installation/update/trust choices decided outcomes more than sandbox technology did. The losers (applets, Web Start, ActiveX, AIR, Chrome Apps) all depended on a *third party's* runtime or store continuing to exist; the winners (Electron, PWAs) own their update path or need no install at all. The lesson for Izcal: an app host must own its runtime, its update channel and its permission policy as one designed system — a capability sandbox alone guarantees none of the three.

**Implications:** WASI/Component Model genuinely fixes the two technical causes of NaCl's death — an unstable distribution format and a plugin API surface — by making the bytecode a W3C standard and the I/O surface imported capabilities. But it fixes none of the *platform* causes of Chrome Apps' and Firefox OS' deaths: distribution, store economics, app supply, UI integration, permission policy and cross-browser adoption remain open, host-defined problems. An Izcal app host built on WASI/CM therefore inherits a solved execution-sandbox problem and an unsolved everything-else problem.

## Lessons learned (project → what happened → the lesson → how Izcal applies it)

| Project | What happened | The lesson | How Izcal applies it |
|---|---|---|---|
| Native Client/PNaCl | Chrome-only sandboxed native code, 2008–2021; LLVM bitcode proved non-portable/non-stable; no other browser adopted | The distribution format, not the sandbox, is the fragile half; single-vendor formats die with the vendor's patience | Spec-anchor the app format so another engine could implement it; treat format stability as a requirement from day one |
| Chrome Apps | Store + packaged apps + 1B-user browser → ~1% desktop usage; 12-year wind-down (2016→2028) | A proprietary platform must beat the web's marginal cost, not just match its features | Answer "why not a PWA?" before any app-host feature; own the update/revocation path |
| Firefox OS | Web-only phone OS; low-end Android undercut it; no WhatsApp; carriers indifferent; shut down 2015–2016 | The ecosystem problem is unsolved by the runtime; picking a contested tier loses | Choose a niche the web doesn't serve; do not launch an app host without app partners |
| KaiOS | Same web-app stack on feature phones + Google/Facebook apps + carrier subsidies → 100M devices by 2019 | Same technology, different economics: partner apps and an uncontested tier | Distribution partnerships are spec-level concerns, not marketing afterthoughts |
| Java Web Start/applets | 2001-era zero-install model killed by OS vendors' bundled-runtime push and plugin removal | Runtimes that depend on a preinstalled third-party runtime die with it | The Izcal host must be self-contained, never dependent on a system JRE-style layer |
| ActiveX | 1996 in-process native controls; removed 2015, fully retired 2022, IE mode to ≥2029 | Full local power without sandboxing creates a 30-year cleanup bill | Capability-granted, least-privilege I/O from the first design (HGBA §3 broker model) |
| Electron | Bundled Chromium+Node, native installers, auto-update → won desktop apps despite size | Owning install + update + trust beats sandbox elegance | The app host owns its update channel and permission UI as one system |
| Flatpak/Snap | Sandboxed, transactional Linux apps since 2014/2016; competing models, store friction | Sandbox mechanism is necessary but the store/policy layer decides adoption | Make store, signing and permission policy part of the spec, not the ecosystem |
| PWAs | Zero-install, linkable, earned permissions — the standard that retired Chrome Apps | The web's install/permission model is now the incumbent to beat | Reuse the earned-permission pattern; never gate installs behind a store |
| WASI/Component Model | Standard bytecode + capability I/O + composition (2019→2024), but no browser ships CM natively | Fixes format and sandbox; leaves distribution, UI, ecosystem and adoption open | App host = WASI/CM for execution, Izcal-designed for distribution/UI/permission policy |

## Implications for Izcal

The five-decade record says the same thing five ways: sandbox technology is a solved, commodity problem, and platform failure comes from distribution format instability (PNaCl), single-vendor formats and APIs (NaCl, ActiveX), contested price tiers without app supply (Firefox OS), parallel proprietary platforms that the web undercuts (Chrome Apps, AIR, Web Start), and dependence on other people's runtimes (applets, Web Start). The survivors — Electron, PWAs, KaiOS, Flatpak/Snap — each own their install, update, permission and trust story as one designed system. Izcal's app host should therefore spec four things in the same document as the WASI/Component Model execution layer, because none of them comes with WASI: (1) a distribution and update channel with signing and revocation that Izcal operates and owns; (2) a permission policy and its user-facing prompts, following the earned-permission pattern the web converged on, granted as capabilities through the HGBA broker rather than as ambient OS access; (3) a UI integration story that reuses the web stack (the PWA path that retired Chrome Apps) instead of inventing a windowing world; and (4) a format governance answer — either a spec published so another engine could implement the Izcal app format, or an explicit, measured acceptance of single-engine status, knowing that single-engine status is the one failure cause every postmortem in this note shares.
