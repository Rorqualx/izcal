# Izcal app host: security capabilities

Compiled 2026-10-21. Primary sources were preferred (specifications, vendor advisories, CVE records, papers, maintainers' posts). No third-party source code was read or cited; every finding is anchored to published prose — the WASI/W3C specifications, GitHub Security Advisories (GHSA), the NVD CVE records, RustSec entries, project documentation, and published postmortems. One naming caution: the Wasmtime filesystem-sandbox escape of June 2022 is sometimes mis-cited as CVE-2022-28990; that CVE actually belongs to wasm3 (heap overflow, 2022-05-20). Wasmtime's filesystem-escape advisories are the trailing-slash GHSA entries in §2.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

This note is the evidence base for the app host's grant model: what the WASI/Component Model sandbox has actually guaranteed under attack 2019–2026, where its implementations have broken, what supply-chain controls have failed and which have held, and what that record implies for a host that grants filesystem, network and device capabilities to signed Wasm applications.

## 1. WASI's capability model: what the specification says

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | The WASI **design principles** state capability-based security explicitly: access to external resources is always represented by **handles** that are **unforgeable** (no way to coerce an arbitrary integer into a handle), and WASI "aims to have no **ambient authorities**" — no way to request a resource purely by string name. The only ways to obtain access are to be given handles or to derive new handles from existing ones. | 2 core properties (unforgeable handles, no ambient authority) | [WASI README, Design Principles](https://github.com/WebAssembly/WASI/blob/1ad15f399e45/README.md) | 2023-02-14 (text read 2026-10-21) | High |
| 1.2 | The same text is explicit that this is a **different sense of "capability" than Linux capabilities** or withdrawn POSIX capabilities, which are per-process rather than per-resource. WASI handles are per-resource objects. | — | [WASI README, Design Principles](https://github.com/WebAssembly/WASI/blob/1ad15f399e45/README.md) | 2023-02-14 | High |
| 1.3 | For linear-memory languages, references are lowered to integer **file descriptors** held in a table ("c-list"). The indices are forgeable in principle, but "a program can only access handles within the c-list it has access to", so **isolation holds by withholding table access**, including between libraries in one instance. | — | [WASI README, Design Principles](https://github.com/WebAssembly/WASI/blob/1ad15f399e45/README.md) | 2023-02-14 | High |
| 1.4 | **Preview 1's filesystem authority is the preopen**: every path-based call takes a **base directory handle plus a relative path**. The returned descriptor is randomized (not the lowest-numbered fd) to prevent descriptor-number guessing. The guest's requested rights come as *base* rights (on the descriptor itself) and *inheriting* rights (on descriptors derived from it), and the implementation may return fewer. | randomized fd, < 2^31; base + inheriting rights | [WASI preview1 spec (path_open, fd_prestat_get)](https://github.com/WebAssembly/WASI/blob/1ad15f399e45/legacy/preview1/docs.md) | 2023-02-14 | High |
| 1.5 | **Preview 2 (WASI 0.2)** launched by WASI Subgroup vote on **2024-01-25**, based on the **component model**, with two worlds: `wasi-cli` (files, sockets, clocks, random) and `wasi-http`. The capability model carries over; the filesystem world is a typed WIT interface, not raw fd syscalls. | 2 worlds at launch | [Bytecode Alliance, "WASI 0.2 Launched"](https://bytecodealliance.org/articles/WASI-0.2) | 2024-01-25 | High |
| 1.6 | The canonical **path-resolution semantics** for wasi-filesystem: all functions take a base directory handle + relative path; **absolute paths are not permitted and there is no global namespace**; resolution is constrained to the subtree of the base handle, and paths that *temporarily* step outside ("../../../stuff/here") are rejected even if the final target is inside, because the escape attempt itself leaks information. | — | [WASI filesystem path-resolution.md](https://github.com/WebAssembly/WASI/blob/main/proposals/filesystem/path-resolution.md) | read 2026-10-21 | High |
| 1.7 | The same spec models its scheme on **CloudABI** and **Capsicum**, and names the host primitives: **Linux `openat2` with `RESOLVE_BENEATH`**, **FreeBSD `O_RESOLVE_BENEATH`**, and **Windows `NtCreateFile`** with a directory handle. Where those do not exist, resolution must be implemented **manually** with `openat` + `O_NOFOLLOW` component-by-component plus `readlinkat` for symlinks. The Rust library **cap-std** implements exactly these semantics and is what Wasmtime uses. | 3 named host primitives + 1 manual fallback | [WASI filesystem path-resolution.md](https://github.com/WebAssembly/WASI/blob/main/proposals/filesystem/path-resolution.md) | read 2026-10-21 | High |
| 1.8 | **Symlink policy**: creating a symlink whose target is an absolute path fails with "not permitted"; otherwise any symlink string is allowed at creation. **Sandboxing of symlinks is performed at access time, not creation time**, and is specified to hold "even in the presence of outside processes" renaming/unlinking/creating files concurrently — the TOCTOU requirement is written into the design intent. | — | [WASI filesystem path-resolution.md](https://github.com/WebAssembly/WASI/blob/main/proposals/filesystem/path-resolution.md) | read 2026-10-21 | High |
| 1.9 | **What the spec does not provide**: preview1 and preview2 define **no standard budget or metering interface**, **no descriptor revocation operation**, and (in preview1) the sandbox strength of path resolution is delegated to the host implementation — the spec mandates the behavior, and host bugs are what break it (§2). | — | absence across [preview1](https://github.com/WebAssembly/WASI/blob/1ad15f399e45/legacy/preview1/docs.md) and [preview2](https://github.com/WebAssembly/WASI/blob/main/proposals/filesystem/path-resolution.md) | 2026-10-21 | High |

**Implications:** the capability model is real and load-bearing — but it is a *host-enforced* model with a spec-level contract that the host must implement with kernel primitives. Izcal's app host inherits the model; its security reduces to (a) never granting anything except handles, and (b) implementing path resolution on macOS without an `openat2` equivalent, which §2 shows is the historically broken part.

## 7. Grant-boundary lessons for an app host

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **Least privilege is granted by handle, not by name**: the entire WASI model (§1) grants capabilities only as unforgeable handles (preopened directories, sockets, clocks). The host's job is to grant *nothing else*. The permission-check CVEs (§2.8–2.9) show even the grant bookkeeping needs adversarial review: a missed flag (`TRUNCATE`, hard-link source perms) silently widens a grant. | — | [WASI design principles](https://github.com/WebAssembly/WASI/blob/1ad15f399e45/README.md); CVE-2026-47261, CVE-2026-58494 | 2026-10-21 | High |
| 7.2 | **Manifests as ceilings**: wasmCloud's claims are a *declared ceiling* — the runtime refuses to link capabilities not attested in the signed claims, and every capability must be declared before use (default-deny). This is the pattern Izcal's per-app manifest should copy: the manifest is the maximum, runtime grants can only shrink it. | — | [wasmCloud ADR 0005](https://wasmcloud.github.io/adr/0005-security-nkeys.html) | read 2026-10-21 | Medium |
| 7.3 | **Runtime grants below the ceiling**: WASI preview1 already separates base and inheriting rights at open time; wasmtime-wasi exposes per-preopen DirPerms/FilePerms. Grants can and should be *narrower* than the manifest, decided at instantiation (e.g., a preopen limited to one directory with read-only file perms). | — | [preview1 spec](https://github.com/WebAssembly/WASI/blob/1ad15f399e45/legacy/preview1/docs.md) (path_open rights) | 2023-02-14 | High |
| 7.4 | **Expiry exists and is proven**: wasmCloud claims carry nbf/exp; TUF metadata carries expiry (PEP 458 specifies metadata expiry times); Sigstore certificates are short-lived by design (keyless ephemeral keys). Grants without expiry (a forever preopen, a never-expiring signing key) are the failure cases in the supply-chain record (5.1–5.5). | — | [wasmCloud ADR 0005](https://wasmcloud.github.io/adr/0005-security-nkeys.html); [PEP 458](https://peps.python.org/pep-0458/) | 2026-10-21 | Medium |
| 7.5 | **Revocation**: WASI has **no descriptor-revocation operation** — a granted handle lives until the instance/store dies; the host must therefore be able to destroy the instance (or the whole app sandbox) as the revocation mechanism. At the distribution layer, TUF models revocation of trust in projects/distributions (PEP 458 "Revoking Trust in Projects and Distributions"); Rekor gives detection, not revocation. | — | [PEP 458](https://peps.python.org/pep-0458/); [Wasmtime docs](https://docs.wasmtime.dev/security.html) | 2026-10-21 | Medium |
| 7.6 | **Signed tickets, not signed code review**: the wasmCloud pattern — a signed JWT bundling the *capabilities, the artifact hash, and validity* — is a ticket the host can check at load. It cannot vouch for the code's behavior (xz was built and released through fully legitimate, signed channels for two years; §5.5). Signing should answer "who published what, when, from where" — never "is this safe". | — | [wasmCloud ADR 0005](https://wasmcloud.github.io/adr/0005-security-nkeys.html); [xz timeline](https://research.swtch.com/xz-timeline) | 2026-10-21 | High |
| 7.7 | **Install-time review vs update-channel attacks**: four of the five supply-chain incidents (5.1–5.5) were *updates* — previously trusted packages poisoned later, auto-pulled by version ranges. Install-time review is defeated by design. The controls that held or were added: ceilings the update cannot exceed (7.2), expiry (7.4), keyless identity + transparency logs at publish time (6.8), digest pinning (6.7), and update-channel protection (TUF, 6.9). | 4 of 5 incidents were poisoned updates | synthesis of §5–§6 | 2026-10-21 | High |
| 7.8 | **Precompiled artifacts are not validated artifacts**: CVE-2026-47218 shows AOT-cache bytes from a registry bypass WebAssembly validation entirely. The app host must validate (or re-derive) everything from the source module bytes; a signed precompiled cache is only safe if the signature covers bytes the host itself produced deterministically. | — | [CVE-2026-47218 (NVD)](https://nvd.nist.gov/vuln/detail/CVE-2026-47218) | 2026-10-15 | High |

**Implications:** the grant boundary for Izcal's app host is a stack, not a single check: signed manifest as ceiling → narrower runtime grants at instantiation → handle-only capability passing → budgets (fuel/epoch) as a second dimension of the grant → instance destruction as revocation → keyless identity + transparency log + digest pinning + TUF-style channel protection at distribution. Every layer above has a shipped precedent and a recorded failure mode.

## 8. Implications for Izcal

The record supports six design commitments for the app host, each tied to evidence above:

1. **Path resolution on macOS is the most exposed code in the stack.** Izcal's host has no kernel beneath-mode on macOS (no openat2/O_RESOLVE_BENEATH), so it must implement and adversarially test the manual component-wise open with access-time symlink checks, including the trailing-slash class that escaped cap-std and wasmtime-wasi in 2026 (2.1–2.3) and the rename/link permission checks that bypassed FilePerms (2.9). This is a falsifiable, spec-checkable requirement, not an aspiration.
2. **The JIT is the highest-risk component; the WASI interfaces are not.** All guest-to-host memory escapes in the 2019–2026 record are compiler or allocator bugs (3.1, 3.5); host-API bugs are permission bypasses and DoS. Izcal should start interpreter-first (or bounds-checked baseline compilation) and treat any JIT tier as requiring either a second in-process boundary (the V8-sandbox precedent, 3.13) or an explicit acceptance of that risk with a measured escape-bug budget.
3. **Budgets are part of the grant.** Fuel (deterministic, higher overhead) and epoch (wall-time, ~10%) are the proven mechanisms (4.1–4.3); WASI standardizes neither (4.4), so Izcal defines its own and must: default limits on (CVE-2026-27204), convert every host-API panic to a guest trap by policy (4.6), and audit preemption points as attack surface (4.8).
4. **Signing authenticates identity and provenance, never safety.** The xz and event-stream records (5.1, 5.5) prove review and signing do not catch poisoned updates. Izcal's signing should use the shipped pieces — keyless OIDC identity plus a Rekor-style transparency log (6.8), content-addressed/digest-pinned distribution (6.6–6.7), wasmCloud-style signed claims as the per-app capability ceiling with nbf/exp (6.11), and TUF-style protection of the update channel (6.9) — while the runtime enforces the ceiling, since that is the only layer the update cannot exceed (7.7).
5. **Never trust precompiled bytes from the registry** (CVE-2026-47218): validate from source module bytes only; if an AOT cache is used, its signature must cover bytes the host itself produced (7.8). Reproducible wasm builds remain an unsolved gap (6.10) — record it as an open question rather than a dependency.
6. **The component model is the right substrate but adds its own attack surface**: it preserves the capability model (6.2), yet its canonical-ABI transcoding and trampolines produced the 2026 CVE batch (6.4). Izcal's host must fuzz and limit exactly that boundary, and should write the threat-model document the ecosystem lacks (6.3) as part of its own spec.

Open questions carried forward: whether any WASI standardization of component signatures or budgets emerges (watch W3C WASI subgroup); a black-box measurement of fuel overhead on Izcal's own interpreter; and the deployment status of PyPI's PEP 458 (relevant only as TUF precedent, not dependency).
