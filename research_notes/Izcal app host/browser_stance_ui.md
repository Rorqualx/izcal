The two-VM Phase 4 gate means CM-on-the-web is, as of today, blocked by the absence of a second committing browser engine — which is simultaneously an argument that Izcal could matter (a second prototype breaks the gate) and a warning (until the gate breaks, CM tooling targets non-web hosts).

### A3. Why no engine ships WASI

| # | Finding | Source | Date | Conf. |
|---|---------|--------|------|-------|
| 34 | **It was never proposed for the web.** WASI is standardized in a CG subgroup whose own statements place browsers outside the target set (rows 29–30); no standards-position tracker or chromestatus entry exists because nobody asked. The web-relevant path is CM (rows 26–27), not WASI. | rows 29–30 above | — | High (synthesis of High rows) |
| 35 | **Capability/authority model.** The web grants capability per origin and per user-mediable permission; a WASI world import is ambient authority — whatever the host links is whatever the module gets, with no per-import user mediation or origin scoping in the model itself. Published discussion: in the Nov 2022 Bytecode Alliance Zulip thread on a component-based browser, Jamey Sharp argued the host should "expose only low-level APIs from the host, and let people build abstractions in untrusted third-party libraries" with components "isolated from each other except through their explicit public interfaces" — an isolation argument, notably without any origin or user-permission layer. Community threads on the same question also cite fingerprinting-surface growth as a reason WASI-style system APIs stayed out of browsers. | bytecodealliance.github.io zulip-archive thread "WASI Web Browser and Component Caching" (read); Lobste.rs/community discussion of the Mozilla Hacks post | 2022-11-20/26; 2026-02 | High (Zulip read) / Low (fingerprinting point, snippet only) |
| 36 | **API-surface and compatibility burden.** WASI 0.3 is a large, modular world surface (filesystem, sockets, HTTP, clocks, randomness, CLI…) defined in WIT, overlapping heavily with existing web APIs; a browser hosting it would maintain a parallel system-interface layer that duplicates what the web platform already does, with the browsers' own concern-tag vocabulary (WebKit labels proposals with "concerns: duplication", "concerns: portability") documenting how such duplication is treated. Luke Wagner in the CG minutes concedes WASI's scope "potentially a much bigger scope than just the web", and virtualization ("wasi-virt", ways to virtualize missing filesystems) is an open WASI-internal problem — i.e., the surface is not even self-contained yet. | CG-10.md (High); WebKit standards-positions label vocabulary (High); WASI README | 2023 | High (quotes) / Medium (the duplication-burden argument as such is synthesis) |
| 37 | **Origin-model mismatch.** WASI apps have no origin: identity, storage, network policy and permissions in browsers are all keyed to origins (or extension IDs, which are a special origin class). None of the WASI proposals defines an origin or app-identity concept, and the CM's own web interactions are explicitly "not fully designed" (row 26). | Mozilla Hacks Feb 2026 (High); WASI repo docs | 2026 | Medium (mismatch characterization is synthesis over High primaries) |
| 38 | **The CM 1.0 two-engine gate.** CM cannot reach 1.0 without two browser engines implementing natively (row 27), and Phase 4 standardization requires two Web VMs (row 28). With one prototyping engine and one evaluating engine, WASI-in-browser cannot even ride CM into existence yet. | rows 27–28 | 2026 | High |
| 39 | The only sanctioned browser path today is transpilation: jco `transpile` produces plain core Wasm + JS glue that any browser runs, deliberately "combining platform-native WebAssembly core support with the advanced features of WebAssembly Components" (jco README), with the `"use components"` telemetry marker as the influence strategy. | github.com/BytecodeAlliance/jco README; BA Road to CM 1.0 | current / 2026-06 | High |

**Implications:** WASI-in-the-browser is not "blocked by one stubborn vendor" — it was architecturally never aimed at the web, and its model (ambient capability, no origin, duplicated system surface) conflicts with the web's three invariants (origin-scoped everything, user-mediated capabilities, one platform surface). For Izcal the practical read is: do not design an app host around hosting WASI components natively; if Izcal ever wants component support, the jco-style transpile-to-core-Wasm route is the compatibility posture the ecosystem itself has chosen, and it costs Izcal nothing special.

### A4. What shipping WASI would require, and the Flash/PPAPI/extensions precedents

| # | Finding | Source | Date | Conf. |
|---|---------|--------|------|-------|
| 40 | Minimum additions a browser shipping WASI would need (synthesis, none of which exists in any WASI/CM proposal today): (a) a **permission UI** per capability class — browsers already have the permission-prompt machinery (Permissions API) but nothing maps WASI imports to prompts; (b) an **origin/identity model** for installed apps — the web has origins, extensions have IDs (special origins), WASI apps have neither; (c) a **package format** — a component binary plus its WIT interface is a distribution unit but has no signing, metadata, or versioning story; (d) an **update channel** — nothing in WASI covers delivery of new versions; (e) a **store or sideloading policy** — who reviews, signs, and revokes. | synthesis over A2/A3 rows; web permission model per MDN Permissions API docs | — | Low (design synthesis, flagged as such) |

**Implications:** browsers have twice retired "native-capability app" layers (Flash, Chrome Apps) while keeping the extension model — the dividing line is that extensions are reviewable, permission-scoped, and distribution-controlled end to end. Any Izcal app-host surface (WASI or otherwise) inherits the full checklist of row 40; the two historical survivors (extensions, and ChromeOS-kiosk apps) suggest that if Izcal hosts apps, it should either use a reviewed, signed, permission-declared package model or explicitly target a narrow OS-gap use case, not a general "run any Wasm app" surface.

And the Wayland constraints (verified in Electron's own docs) mean Izcal should design its window story around "request, don't assume" semantics from day one.

## Implications for Izcal

**Part A (WASI / Component Model):**
1. Izcal should not plan to host WASI natively. No engine does, none has a public plan to, the WASI subgroup scopes itself outside browsers, and the model conflicts with the web's origin/permission invariants. Building a WASI host would be building for a web audience that HTTP Archive measures at roughly zero.
2. Izcal should treat the Component Model as a watch-list item, not a dependency: one engine prototypes, one evaluates, and Phase 4's two-VM gate is the blocking condition — which a third engine like Izcal could theoretically help satisfy, but only once the spec's web interactions are designed (they are not, per Mozilla's own words).
3. The cheap, ecosystem-blessed compatibility posture is the jco-style transpile-to-core-Wasm route; if Izcal ever wants components, following that route (polyfill over core Wasm) costs nothing architecturally now beyond shipping rows 1–13 of the feature matrix.
4. If Izcal hosts applications at all (Part B), the capability model must be web-style — per-app grants, user-mediated, revocable, audit-logged — never WASI-style ambient imports. The Flash/PPAPI/Chrome Apps record says capability-app layers die unless reviewable, permission-scoped, and distribution-controlled end to end.

**Part B (windows, launch, automation):**
5. Do not build a window manager or a full app platform. Chrome Apps is the tombstone; Electron shows the surviving "rich window" model is a native shell, not a browser. Izcal's window contract should be PWA-grade: display modes, optionally a WCO-style title-bar overlay, own-window management, and "request, don't assume" semantics for everything Wayland refuses.
6. The obligations that decide whether Izcal's app windows are usable are accessibility and input: WCAG 2.2 conformance, OS accessibility bridges (AX/UI Automation/AT-SPI), and IME participation. Luke Wagner's checklist (accessibility, content blocking, consistency, battery, text handling, progressive enhancement) is the bar any Izcal app UI must meet — keep apps on DOM/CSS, not canvas-first.
7. For agents, adopt the converging standard (WebDriver BiDi; CDP where native) rather than inventing an automation protocol, and design the app capability model around typed, named capabilities (the OpenAI Apps SDK pattern) with per-action, expiring, person-present-confirmable grants (the 2026 permission work: short-lived authorizations, relock-on-input, signed single-use approvals). An agent acting with the user's grants must be a designed mode, not an accident.
8. Launch surfaces: ship search + pinning + OS-shortcut install + file/protocol associations; skip store-driven discovery and window-manager ambitions.
