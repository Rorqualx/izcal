# Izcal app host: WASI and Component Model specifications an app host must implement, and their standing

Compiled 21 October 2026. Primary sources were preferred (specifications and spec documents, maintainers' posts, release notes, licence texts). No third-party source code was used as evidence (M-1 part 3); where an interface's shape is stated only in WIT files, it is recorded as unverified.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Relationship to `HGBA 2 browser architecture spec/wasm_component_model.md`** (state as of 13 October 2026): that note answers browser-side questions (browser support, jco, the eager/lazy ABI story, JS-to-Wasm, embedding). This note extends it with the host-implementation side. **Additions:** WASI Preview 1 history and fate; the WASI 0.2 package set, worlds and patch line; WIT syntax and world/linking/instantiation semantics; spec-level Canonical ABI facts (flat types, `realloc`/`cabi_realloc` mechanics, handle tables, stream/future ends, size limits); a world-by-world authority and client/server analysis; conformance suites and their licences; the licences of the specifications themselves; the WARG-to-OCI registry history and `wkg`; the verbatim CG Phase 4 entry requirements. **Corrections/updates:** (a) the existing note cites `features.json` for the Component Model's Phase 1; the CG's own proposals table says the same (row 2.15 below); (b) WASI 0.3.2 shipped 13 October 2026, after the existing note's cutoff; (c) the existing note quotes CanonicalABI.md via a fork mirror; the canonical repo's text says the same (row 2.9 below). No factual error found in the existing note's 0.2.0 date (25 January 2024), 0.3.0 date (11 June 2026) or its "one copy per crossing" conclusion.

| 2.4 | **WIT** (Wasm Interface Type): "isn't a general-purpose programming language and doesn't define behaviour; it defines only contracts". A package ID is `namespace:name` with optional semver (`documentation:example@1.0.1`); a file holds interfaces or worlds. Built-in types: bool, s8–u64, f32/f64 (with a single logical `nan`), char, string, `list<T>`, `option<T>`, `result<T,E>`, `tuple<...>`, and (0.3) `stream<T>` and `future<T>`. User-defined: record, variant, enum, flags, type alias, and `resource` (constructor, methods, static functions; `borrow<T>` loans). `use` imports types from another interface; worlds `import`/`export` interfaces (per-interface direction, "A package groups definitions together; it doesn't describe a coherent set of behaviours") and can `include` other worlds. Identifiers are ASCII kebab-case; functions may be `async func`. | — | [CM book: WIT Reference](https://component-model.bytecodealliance.org/design/wit.html) | 2026-10-21 | High |
| 2.5 | **Worlds**: a world "describes the functionality a component provides, and the functionality it requires". A host supports a world "by providing implementations for all of the imports and by optionally invoking one or more of the exports". Sandboxing is structural: "if a component does not have an import for a secret store, then it cannot access that secret store, even if the store is running in the same process." | — | [CM book: Worlds](https://component-model.bytecodealliance.org/design/worlds.html) | 2026-10-21 | High |
| 2.6 | **Linking and instantiation**: a component is "a self-describing WebAssembly binary that interacts only through interfaces instead of shared memory"; "memories are never exported or imported". A component file "could include representations of one or many traditional ('core') WebAssembly modules and sub-components, composed together via their imports and exports"; "Two modules or components can be composed if the imports of one are satisfied by the exports of another", repeated arbitrarily. Instantiation means "turning a static description of a module into a dynamic structure in memory", analogous to loading an executable. | — | [CM book: Components](https://component-model.bytecodealliance.org/design/components.html); [CM book: Worlds](https://component-model.bytecodealliance.org/design/worlds.html) | 2026-10-21 | High |
| 2.7 | **Canonical ABI — flat types**: component-level types are flattened into core Wasm values; the only core value types crossing a boundary are `i32, i64, f32, f64` ("the 4 core value types"); 16-bit types flatten to `i32`. `lift_flat` "defines how to convert a list of core values into a single high-level value"; `lower_flat` "defines how to convert a value v of a given type t into zero or more core values". | 4 flat types | [CanonicalABI.md](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md) | 2026-10-21 | High |
| 2.8 | **`realloc`/`cabi_realloc`**: the canonical option `realloc` defines "how to dynamically allocate linear memory" "when lowering non-flattened values", modeled "as-if `realloc` were a component export invoked by the host"; allocation calls `reallocate(0, 0, alignment, byte_length)` and the result is checked for alignment and bounds. (This is the mechanism behind the eager `cabi_realloc` the existing note's Q3 describes; the Road-to-CM-1.0 article names it `cabi_realloc`.) | — | [CanonicalABI.md](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md); [BA: Road to CM 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0) | 2026-10-21; 2026-06-08 | High |
| 2.9 | **One copy per crossing**: the canonical ABI "uses a `realloc` approach to update the allocation size during the single copy", and "a real implementation should be able to fuse lifting and lowering into a single direct copy". Confirms the existing note's Q3 conclusion: one copy, source memory to destination memory, no shared memory. | 1 copy | [CanonicalABI.md](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md) | 2026-10-21 | High |
| 2.10 | **Resource handles**: handles are "opaque elements that are represented in Core WebAssembly as `i32` indices into the [component instance's `handles`] table". Passing an own handle transfers ownership: it is "removed from the current component instance's `handles` table", ownership "transferred to the lowering component". A handle tracks type, representation, own/borrow status, borrow scope and lend count. | — | [CanonicalABI.md](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md) | 2026-10-21 | High |
| 2.11 | **`stream<T>`/`future<T>` in the ABI**: they are "pairs of readable and writable ends linked together". A readable end is "represented in the Canonical ABI as `i32` indices into the component instance's `handles` table"; "Writable ends are never passed across component boundaries"; "each stream/future end must be uniquely owned by either the host or a single component instance". On crossing, ownership transitions (the end "becomes officially owned by the host" / "lower_async_value will transition ownership from the host into the receiving component instance"). | — | [CanonicalABI.md](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md) | 2026-10-21 | High |
| 2.12 | **Async**: a lifted async call "creates a new task/thread pair for the call"; `task.return` passes the result "to the [current task]'s caller". | 2.17 | **Minimum host surface.** Must cover: component binary decode/validation including nested modules and components; core-module instantiation; type-checked linking of imports to exports across instances; the flat-type ABI (lift/lower with the single copy); per-instance resource handle tables with ownership transfer and destructors; and, to host WASI 0.3, async lift/lower, `future`/`stream` ends and task scheduling driven by the host (rows 2.7–2.12). **Deferrable:** parsing WIT at runtime — WIT "describes the typed APIs a component imports and exports" for tooling, and WIT packages themselves travel as components ("We are packaging WIT as Wasm"); a host that links by canonical names need not consume WIT. **Implications:** Izcal's app host gets a well-bounded core: a component decoder/validator, core-module instantiation, name- and type-based linking, a flat-type ABI with one copy per crossing, handle tables, and (for 0.3) a host-driven task scheduler. WIT tooling is not in the host's runtime path. Because the Component Model has no tagged releases, Izcal's M-1 spec must anchor to document paths plus retrieval dates, and must be re-pinned when the formal spec and reference interpreter appear.

## 3. The WASI 0.2/0.3 worlds: what each import grants, and who is client and who is server

Authority reading: in the Component Model, imports are requests and the host's act of providing them is the grant (row 2.5). Client/server below means what a component targeting the world can *do*: make requests out (client), or be driven by inbound work (server).

| 3.7 | `wasi:io` (0.2 only) — `streams` (`input-stream`, `output-stream`), `poll` (`pollable`) | Async I/O primitives: byte streams and readiness polling; it "underpins all other WASI 0.2 interfaces that perform I/O". Removed entirely in 0.3 — "There is no WASI 0.3 version of `wasi:io`" — replaced by native `stream<T>`/`future<T>`/`async func` | Pollables were per-instance resources; a composed component could not forward host wake-ups through a middle component (the "sandwich problem") — the authority-analysis relevant limit that 0.3 removes | Neither; substrate for both directions | [wasi.dev: WASI 0.2](https://wasi.dev/releases/wasi-p2); [wasi.dev: WASI 0.3](https://wasi.dev/releases/wasi-p3) | High |
| 3.8 | 0.3 worlds summary: `wasi:cli/command` (exports `async func run`); `wasi:http/service` (exports async `handler`, imports clocks/random/cli-stdio/http client); `wasi:http/middleware` (service plus imported handler). "Each core proposal additionally exposes an `imports` world (`wasi:cli/imports`, `wasi:sockets/imports`, `wasi:filesystem/imports`, `wasi:clocks/imports`, `wasi:random/imports`) aggregating that package's interfaces for use by other worlds." | — | Grant granularity is per world: an Izcal host can implement exactly `wasi:cli/imports` for tools, or exactly `wasi:http/service` for web servers, without granting the rest | — | [wasi.dev: WASI 0.3](https://wasi.dev/releases/wasi-p3) | High |

**Implications:** For Izcal's app host the world list is the menu of authority: `wasi:http/service`+`middleware` (server), `wasi:cli/command` (client tools), `wasi:sockets` (both, gated at world level in 0.3), `wasi:filesystem` (only via preopens — this is the mount-point answer: preopens *are* the mounts, and there is no namespace to configure beyond them), and clocks/random (utility capabilities). The host never needs `wasi:io` for 0.3 targets.

## Implications for Izcal (overall)

1. **Target WASI 0.3 pinned to a tag** (0.3.1 or 0.3.2), not 0.2 and not Preview 1; offer Preview 1 module support only as a compatibility shim if needed. Do not plan around WASI 1.0 or CM 1.0 dates — neither has one, and WASI 1.0 waits on CM 1.0, which waits on two Web VMs.
2. **The host core is bounded and spec-anchored**: component binary decode/validation, nested instantiation, type-checked linking, flat-type ABI with the single copy, per-instance handle tables, and host-driven async scheduling. WIT stays a tooling language outside the runtime. Everything is implementable from Apache-2.0/W3C-licensed prose (M-1 compatible).
3. **Grant authority world by world**: `wasi:http/service` and `middleware` for servers, `wasi:cli/command` for tools, `wasi:sockets` (world-level network grant in 0.3) for both, `wasi:filesystem` only through preopens — preopens are the only mount mechanism, and there is no path namespace beyond them. Never implement `wasi:io` for 0.3 targets.
4. **Conformance**: pass the shared wasi-testsuite (the Wasmtime/jco bar) plus the core spec test suite; track the CM WAST suite as it grows; keep copied test fixtures under their Apache-2.0 headers and write Izcal's own tests from prose.
5. **Distribution**: adopt OCI artifact conventions (`wkg`-compatible, digest-pinned) for Izcal apps; treat WARG as dead and component signing as an open problem the Izcal design must answer itself.
6. **Standardization leverage**: a conformant native host makes Izcal one of the two Web VMs the Component Model's Phase 4 gate waits for — a first-mover position with no code dependency on anyone (D-S10).
