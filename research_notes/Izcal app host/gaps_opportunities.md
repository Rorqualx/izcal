# Izcal app host: gaps and opportunities

Compiled 21 October 2026. Primary sources were preferred (specifications, vendor documentation, release notes, surveys, issue trackers, platform-status records).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Scope: what developers and users cannot see or do today with browser-hosted applications and Wasm/WASI tooling, and what the Izcal app host's architecture could expose that no current tool does. Other strands own history, specifications and standards, security and capabilities, determinism and recording, distribution and trust, and the browser-stance and UI questions. All external products are evidence only.

An Izcal app host with per-app capability grants can lift each ceiling for one declared, reviewed, user-granted app without weakening the page model at all; that is a different product than "the web platform grows another API".

## Implications for Izcal: the five most valuable things an app host could show or do that nothing does today

1. **The recorded host-call log with reason-coded denials (AH-12).** The single most cited gap across every source — Chromium's own FSA admission, wasmCloud's "can't attach a debugger", the cryptic component traps, WebReplay's abandonment — is that no tool shows what a Wasm program asked its host for and what the host said. Izcal is the only architecture where every exercise of a capability already passes through a broker-minted ticket, so the log falls out of the trust model instead of being bolted on. It answers "why was this denied?", "which ticket covered this?", and "what did this app actually touch?"
2. **Replay that opens nothing, with divergence reporting (AH-3).** A bug report becomes a recording that runs against a virtual filesystem and network, provably opening zero real resources, and reports the first differing host call with both values. No browser, runtime or WASI vendor offers this; rr is native-only and Firefox's WebReplay is dead. This is the concrete form of the determinism the substrate already guarantees (AH-2).
3. **The install-time capability view and the live ticket list.** OS dashboards (iOS, Android, TCC) and Chrome's site settings show post-hoc, coarse, sensor-only categories with no denials and known holes, and users don't read prompts (Felt 2012). An Izcal app shows "exactly which directories, network destinations and device families it may reach" *before* it runs, then shows live tickets and per-use history — the pre-view and the audit that no permission dashboard provides.
4. **The typed intent boundary as the agent and UI channel (B9, AH-11).** Intents are grantable, deniable, versioned and recorded — the only agent path with a schema and an audit record, versus today's pixel-clicking automation. The same boundary gives the sealed `app://` UI a hard, typed answer to "what can the UI reach versus the component?", which no Electron-like stack can state.
5. **The named WASI profile with conformance numbers (AH-5).** "WASI" means different things on every 2026 host (Workers' partial syscalls, Preview 1 vs 2 vs 0.3, sockets in or out). `izcal:app@0.1` is one pinned, conformance-tested profile: a developer can read one page and know exactly which interfaces exist, which need tickets, and what a denial looks like — the missing reference point the whole "write once, run anywhere" claim currently lacks.

## Questions this strand could not answer

- What share of installed PWAs or Chrome apps would migrate to a WASI app host, and what workloads dominate? No vendor publishes install-share data by API usage, and no public crawl probes FSA/OPFS adoption.
- Does Chrome's "Recent activity" in Site Settings have a retention window and a denial record, or only a last-use flag? The UI is documented only informally.
- How much of the State of JS 21.2% Wasm usage is browser-side versus server-side Wasm, and how much is via toolchains (Blazor, Emscripten) versus hand-written WAT? The survey does not split it.
- Are any of the vendor claims in 6.4 (Fastly's 40% of edge traffic, Spin's 100k deployments, the CNCF 31%/8% pair) backed by published surveys? They circulate only in vendor blogs; treat as marketing until audited.
- Would developers actually adopt a browser that debugs Wasm *better* than their IDE, or does the app host need DAP-grade editor integration (already in DT's plan) before the recording features matter? No survey asks this.
