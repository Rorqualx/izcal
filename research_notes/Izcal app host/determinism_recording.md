# Izcal app host: determinism and record/replay for WASI applications

Compiled 21 October 2026. Primary sources were preferred (specifications, official documentation, papers, maintainers' posts and talks). No third-party project source code was read: evidence comes from rendered documentation, README prose, API reference pages, papers and talk abstracts. WIT interface-definition files were not read; interface facts come from the proposals' README prose and from wasi.dev.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Context read: JavaScript engine spec 6.9 (determinism by construction, decision points JS-D15, the Wasm 3.0 deterministic-profile commitment JS-D12) and DevTools spec DT-D2 (recorded sessions, input logs, digests, redaction, sensitive internal-draw class).

## 1. Wasm's determinism guarantees

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Wasm aims to specify a single outcome whenever it can; nondeterminism is "always done in a limited and local manner" and "only specified as a compromise" when there is no other practical way to get portability, performance or security | — | [WebAssembly design rationale, "Limited Local Nondeterminism"](https://raw.githubusercontent.com/WebAssembly/design/main/Rationale.md) | living doc, accessed 2026-10-21 | High |
| 1.2 | NaN bit patterns from floating-point instructions are nondeterministic "in most circumstances" in the Full profile; even the sign of a canonical NaN is nondeterministic; observable via `reinterpret`, stores/loads, globals, imported/exported boundaries and `copysign`. Mandatory canonicalization was rejected because "the cost of canonicalizing NaNs is believed to be greater than the benefit" | — | [WebAssembly design rationale, "NaN bit-pattern nondeterminism"](https://raw.githubusercontent.com/WebAssembly/design/main/Rationale.md) | living doc, accessed 2026-10-21 | High |
| 1.3 | The Wasm 3.0 spec defines two profiles: **Full** (FUL, the complete language, all behaviours) and **Deterministic** (DET). DET requires: "All NaN values generated by floating-point instructions are canonical and positive" and "All relaxed vector instructions have a fixed behaviour that does not depend on the implementation" | 2 profiles | [Wasm 3.0 core spec, Appendix: Profiles](https://webassembly.github.io/spec/core/appendix/profiles.html) | living doc, accessed 2026-10-21 | High |
| 1.4 | Even the DET profile leaves `memory.grow` and `table.grow` "technically nondeterministic" so that resource exhaustion can be reported. The profiles appendix says nothing about threads or shared memory: data races under Wasm 3.0 shared-everything threads are therefore not constrained by either profile | — | [Wasm 3.0 core spec, Appendix: Profiles](https://webassembly.github.io/spec/core/appendix/profiles.html) | living doc, accessed 2026-10-21 | High |
| 1.5 | API-level nondeterminism — "random number generators, date/time functions or input events" — is deliberately left to the environment, not the core language | — | [WebAssembly design rationale](https://raw.githubusercontent.com/WebAssembly/design/main/Rationale.md) | living doc, accessed 2026-10-21 | High |
| 1.6 | Izcal's JS engine spec commits the renderer's Wasm to the DET profile (JS-D12 (a)), with one relaxed-SIMD lowering per ISA and constant folding that produces the NaN the generated code would, measured before shipping | internal | `reports/Izcal JavaScript engine.md` 6.9 | 2026-10-21 | internal |

**Implications:** pure Wasm computation under DET is deterministic up to resource exhaustion, exactly what Izcal's renderer already assumes; the app host should adopt the same DET requirement for hosted apps, and treat allocation growth failure and thread races as the two remaining in-core nondeterminism sources.

**Implications:** WASI's interface layer is already designed for host virtualization — every nondeterminism source is an import the host can back with a recorded or simulated implementation. The one spec-level warning is wasi-random's: deterministic randomness must never leak into a production configuration, which Izcal's Q-CS-1/G161 rules already enforce renderer-side and the app host must repeat.

**Implications:** the public record is: one shipped post-mortem snapshot (coredump), one in-tree prototype (Wasmtime RR), one academic boundary-recording technique (Wasm-R3), and no toolchain support. The shared idea — record at the component/module boundary, replay against a synthetic host — is exactly what an Izcal app host should build, and no shipped implementation occupies the space.

**Implications:** the industry's evidence is that deterministic simulation finds real bugs cheaply (700–1000x acceleration) while whole-machine recorders pay 10–20x overhead and whole-VM determinism costs a simulated CPU without GPU or external services. A WASI boundary recorder sits between them: it pays no CPU-level tax and needs no hypervisor, because the only nondeterminism that can enter a hosted app crosses a typed interface the host owns. That is the argument the app host spec should make explicitly.

| 6.4 | Recording a CSPRNG draw is recording key material: the WASI random proposal itself says deterministic replacement of random data "should only be used for debugging, and not production use", and Antithesis documents that runtime-seeded PRNGs cannot be re-seeded mid-history ("we cannot go back just a little bit and 'change history'") — a recorded draw log must be treated as credential-class data | — | [wasi-random README](https://github.com/WebAssembly/wasi-random/blob/main/README.md); [Antithesis environment docs](https://antithesis.com/docs/configuration/the_antithesis_environment/) | accessed 2026-10-21 | High |

**Implications:** the app host's recording classes should mirror DT-D2: never record app-held key material at the boundary unless the app itself exported it; record host-injected entropy draws only in an encrypted-at-rest, never-exported class; and replay consumes recorded draw values, never seeds, so the production CSPRNG path stays unseedable (Q-CS-1).

## 7. The hash boundary: what an output digest can and cannot cover

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | What a Wasm digest can cover is exactly the state a Wasm coredump enumerates — modules, instances, **memories, globals** (and tables, in the format) — plus the host-call log: Wasm-R3's replay correctness rests on recording module-boundary interactions, the same class a WASI host-call log covers | — | [Wasmtime book: core dumps](https://docs.wasmtime.dev/examples-debugging-core-dumps.html); [Wasm-R3 paper](https://dl.acm.org/doi/full/10.1145/3689787) | accessed 2026-10-21; 2024-10 | High |

| 7.4 | Izcal's renderer-side digest discipline already defines the pattern the app host needs: per-task digests of outgoing IPC, checkpoint hashes at flush points, "100% of divergences flagged at the first mismatching task digest or checkpoint", and "nothing past a divergence is shown as exact" (DT-1(c)) | internal | DT-D2 and DT-1, `reports/Izcal DevTools spec.md` | 2026-10-21 | internal |

**Implications:** for a WASI app the hash boundary is: memory + globals at chosen checkpoints, the ordered host-call result log, stdout/stderr, and filesystem-write effects against the virtual filesystem — everything else (wall-clock values the app displays, GPU, audio, real sockets) must be listed exclusions or labelled approximate, never silently hashed.

## Implications for Izcal

**Record at the WASI boundary.** The one place every nondeterminism source crosses (clocks, random, filesystem reads and metadata, sockets, args/env at instantiation) is the host-call boundary; record each host-call result in call order with the canonical position, exactly the JS-D15 "record decisions, not waits" pattern applied to a component host. Pure computation needs no recording when hosted apps run under the DET profile (rows 1.3–1.5), the same commitment JS-D12 already makes renderer-side.

**Virtualize, don't just record.** One injected implementation per WASI source, as WasiCtxBuilder proves feasible (row 2.7): virtual monotonic clock driven by recorded values or the simulated scheduler; `insecure`/`insecure-seed` drawn from a per-app entropy stream (recorded encrypted, never a production seed); filesystem served from a content-addressed in-memory store whose reads replay from the log — the "fully controlled private filesystem" the wasi-filesystem spec itself names as the precondition for determinism (row 2.4); sockets replaced by recorded byte streams, with the "replay opens no real resource" rule (row 4.4) as an audit assertion. WASI 0.3's async-native waits (row 2.2/2.8) mean the app host's recorder must log wake-up ordering, which is a scheduler decision point in JS-D15's sense.

**Exclude and classify.** List exclusions, never open-ended (DT-1's rule): wall-clock values the app displays, GPU output, audio, thread races (row 1.4). Treat recorded entropy draws as the sensitive internal-draw class (encrypted at rest, never exported, credential-class under `hg-redact`, rows 6.4–6.6), and define the digest set as memories + globals at checkpoints, the host-call log, stdout/stderr and virtual-filesystem effects (rows 7.1–7.3).

**Open measurements.** No published numbers exist for a WASI-boundary recorder's overhead or log size (row 3.5) — the app host spec should carry a target in the JS-52 style (recording cost ≤ 1%† of frame/p95 time, log size published) with a measurement milestone, since the only published recorders are either CPU-level (TTD 10–20x, row 5.7) or whole-VM (Antithesis, no GPU, 10 GB, row 5.4), and neither is the cost model the app host wants.
