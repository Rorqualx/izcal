# Izcal content blocking: gaps and opportunities

Compiled 19 October 2026. This note covers strand (A), the extension and blocker API story, and strand (B), what is invisible today and what Izcal could do that no blocker does. Primary sources were preferred: vendor engineering blogs, API documentation, papers, maintainers' posts, release notes and issue trackers. No engine or blocker source code was read or cited (M-1 part 3). Where a value is stated only in source code, it is recorded as a question for a black-box measurement.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a claim carried from an earlier Izcal research note without being re-read; **Low** = secondary source only, or inference.

**Budget note.** The shared web-search budget ran out partway through this strand. Every source after that point is a known primary page read directly. Items that could not be checked are graded Medium or Low and say so. Several Chrome, Edge, Brave and malicious-extension facts are carried from `research_notes/Browser user pain points 2026/privacy_security.md` and `research_notes/Composable platform essay review/factcheck_A.md`, and are marked "(carried)".

**Implications:** DNR is a reasonable answer to the question "how do you let third-party code block requests without seeing them": declarative, compiled, with no per-request extension code. It fails on four points, and each is a design requirement for Izcal. **List updates are coupled to store review**, so a fix waits days. **There is no top-level context** until Chrome 145, so per-partition semantics are impossible. **Explanations are rationed**, at 20 calls per 10 minutes. **Everything that is not a network rule** (cosmetic rules, scriptlets, response inspection) falls back to arbitrary page-world JavaScript, which defeats the security rationale. Izcal's matcher (Networking 6.15) is DNR-shaped on the inside. The question for Stage 2 is which of these four failures its extension surface avoids, not whether to copy DNR.

## 2. Safari content blockers

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Design rationale.** JavaScript-based blockers cost battery and latency on every load, slow pages and use a lot of memory. Rules are declared ahead of time as JSON (a `trigger` of `url-filter` regex, `resource-type`, `load-type` first- or third-party, and `if-domain` or `unless-domain`; an `action` of `block`, `block-cookies`, `css-display-none` or `ignore-previous-rules`), compiled to bytecode and run by the engine in the network subsystem. **Privacy:** the extension "does not see the URLs of pages and resources the user browsed to", and WebKit does not record which rules ran on which URLs | — | [WebKit: Introduction to content blockers](https://webkit.org/blog/3476/content-blockers-first-look/) (Benjamin Poulain) | 2015-06-12 | High |
| 2.2 | **The regex subset is restricted on purpose.** It is a strict subset of JavaScript regex; quantifiers, especially mid-pattern, are discouraged; the compiler **rejects** rule sets that would hurt user experience | — | same | 2015-06-12 | High |
| 2.3 | **Rule caps.** 50,000 rules per content blocker, raised to 150,000 (AdGuard dates this to iOS 15, and elsewhere to 2022). Apps split rules across several blockers: AdGuard ships six, for up to 900,000 rules. Apple had argued that performance would degrade before agreeing to the raise. No Apple primary source was found | 50k → 150k per blocker | [AdGuard KB (iOS)](https://adguard.com/kb/adguard-for-ios/features/safari-protection/); [AdGuard for Safari 1.11](https://adguard.com/en/blog/adguard-for-safari-1-11.html) | 2021–2022 | Medium (vendor, dates conflict) |
| 2.4 | **The same model reached Chrome.** Ghostery built a DNR-based Safari extension first and used it to plan its Chromium migration. Safari and Firefox supported Chrome's 2023 limit increases in the WebExtensions Community Group | — | [Ghostery](https://www.ghostery.com/blog/manifest-v3-the-ghostery-perspective); [Chrome blog](https://developer.chrome.com/blog/improvements-to-content-filtering-in-manifest-v3) | 2021–2023 | High |

**Implications:** WebKit's 2015 design is the cleanest statement of the privacy argument: the blocker's author never learns where the user went. It is also the design with the least explanation, since WebKit records nothing. Izcal can keep both properties. Third-party lists are data compiled in a utility process (Networking 6.15), the list author receives nothing, and explanations are produced locally from Izcal's decision log rather than handed to an extension.

Users judge a blocker by whether the lists they trust work. Izcal's "users may add third-party lists by URL" (Networking 6.15) therefore needs a published coverage table for the syntax: which rule types are supported, which are ignored, and why.

**Implications:** The threat is not the blocking API. It is **broad read access plus silent updates**. An ad blocker is the most natural disguise, because users expect it to see every page. Three consequences for Izcal's Stage 2 extensions (Wasmtime, Stage 1 D-S3 and the Extensions row). (a) A list-only blocker must be able to exist with **zero read capability**: it supplies rules, and Izcal compiles and applies them. (b) Read access (IIP interception, Networking 6.19) must be a separate, scoped and audited capability, with **an update that widens capability re-prompting** the user. (c) A hostile list is also an attack, both on the compiler (tier P, utility process) and on the user, for example by redirecting to affiliate links. That is why Chrome caps "unsafe" dynamic rules at 5,000 (1.5).

**What no one shows** (inference from 5.1–5.6, Medium): (a) **which list version and which entry**, with a link to the entry's **published evidence** (what the tracker was observed doing); (b) the **partition** (top-level site, frame site, container) in which the rule matched; (c) the **initiator script** (which script caused the blocked request, and through which chain); (d) the **counterfactual** (what the page would have done had the rule not fired); (e) a **history** that outlives an open tool window, which uBO lacks by design. No browser tells a site operator how to contest an entry from the point where they see the failure.

**Implications:** Izcal's decision log (Networking 6.18) already holds (a)–(c). (d) is new and needs replay (Section 9). Frame success criterion 3 ("every entry explainable") becomes testable if the site panel and DevTools both resolve a `FailureReason::ContentBlocked` to (list, version, entry ID, evidence URL, partition, initiator). The page itself must still see only a generic network error (NW-22).

## 6. Behaviour-based detection with engine instrumentation

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **AdGraph** instrumented Chromium to build a graph of HTML structure, network requests and JavaScript behaviour, and trained a classifier on it. | 6.3 | **FP-Inspector** learned fingerprinting behaviour from static and dynamic script features. | 6.5 | **Production blockers do not use runtime attribution for decisions.** Lists remain URL- and host-based (Networking 6.15). **Implications:** The research lineage (AdGraph → WebGraph → FP-Inspector → PageGraph) needed a **forked, instrumented Chromium**, and PageGraph's "crash rather than guess" rule shows how hard attribution is to bolt on. Izcal's JS engine attributes time and allocation to scripts as its single accounting mechanism (JS 6.10). Extending that to "which script called which API, with which arguments' class" is a first-class engine fact, not a research fork. That makes two things possible. (1) The lab crawler can classify by **information flow**, which WebGraph shows is robust, and not only by URL. (2) A shipping browser could act on **behaviour at runtime**, for example by restricting a script that reads a canvas, a font list and audio within one task. That runtime use needs a P1 analysis, because a behaviour trigger is itself observable (Section 8).

## 7. API-level interventions versus URL blocking for fingerprinting

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 9.1 | **Breakage triage today is manual and live.** Users report a URL; maintainers reload the site, toggle lists and bisect rules by hand. The filter-list issue trackers show the volume (Section 15) | — | Issue trackers (15.1) | 2025 | Medium (inference) |
| 9.2 | **Research automates breakage detection** ("Blocked or Broken?", PETS 2022, built on PageGraph) and **reproducible capture** ("Web Execution Bundles", USENIX Security 2025), but no shipping blocker reproduces a user's breakage | — | [PageGraph wiki](https://github.com/brave/brave-browser/wiki/PageGraph) (paper list) | 2022; 2025 | Medium (papers unread) |
| 9.3 | **No browser or blocker documents deterministic replay** of a page load with and without a rule. This is an absence of evidence, checked against the vendor pages read for this note | — | — | — | Low |

**Implications:** Izcal makes every blocking decision a recorded B1 input and replays exactly (DET-1, Networking 6.16), so a breakage report can carry a **redacted recording** (DT-10's redaction, consented). Triage becomes "replay with rule R removed and diff the outputs" (DOM, semantic plane, display-list hash). Rules can be bisected automatically in a replay host. This is the strongest single thing Izcal can do that no blocker can. Its limit: replay with a rule removed diverges as soon as the unblocked request needs a network response that was never recorded. So the useful forms are (a) **lab replays** on the crawler's own recordings, where Izcal recorded both arms, and (b) **"exact until"** marking, as DT-1(c) requires, on user recordings.

## Questions for measurement

1. **Explainability cost.** What does it cost (memory per partition service, p99 match time against FP-28's 20 µs†) to keep (entry ID, list version, initiator) for every match in the decision log, always on?
2. **Replay coverage for breakage.** On the crawler's corpus, for what share of "rule R breaks page P" cases does replay with R removed reach the breakage point before diverging? That share bounds how far Opportunity 1 extends to user reports.
3. **Per-script intervention breakage.** On the corpus, compare breakage (NW-54's ≤ 1%† metric) and residual linkability (PRIV-2) for three arms: URL blocking of listed fingerprinting scripts, per-script API normalization, and D-S1 defaults only. FP-Inspector's 2× breakage result is the hypothesis to reproduce.
4. **Detectability of differing treatment.** Can a page tell, cross-site, (a) which lists a container has enabled, (b) whether a per-script intervention applied, (c) whether the user has a per-site override? Run the ITP and Privacy Badger attack classes (8.2–8.4) as a PRIV-2 test suite.
