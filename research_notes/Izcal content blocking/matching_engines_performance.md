# Izcal content blocking: matching engines and performance

Compiled 19 October 2026. Primary sources were preferred (papers, official documentation, filter-syntax documentation pages and wikis, maintainers' blog posts, release notes). Under M-1 part 3 no source code of any blocker or engine was read, linked or used (adblock-rust, uBlock Origin, Ghostery's adblocker, AdGuard CoreLibs, WebKit's content-extension compiler, Chromium's subresource filter). Where a value appeared to be stated only in source code, it is listed as a question for black-box measurement (Section 10). Search results that pointed at source snapshots of WebKit's compiler were not opened, and nothing from them is used here.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a third-party documentation page; **Low** = secondary source only, or unchecked recollection.

The shared web-search budget ran out partway through. Later items were read directly from known primary pages. Items that could not be checked are graded Medium or Low and are named in Section 10.

**Implications:** The interoperable core that Izcal's rule-syntax page (networking 6.15) names, URL patterns, anchors, `$third-party`, `$domain`, types, exceptions, `$important`, `$redirect` and `$removeparam`, is exactly the part all three list dialects and DNR share. Everything beyond it is either blocker-specific or restricted by provenance in every blocker, so Izcal can decline it without breaking common lists, and must record silent areas (1.16) as black-box observations. Syntax is very likely not protected expression, but no ad-filter-specific commentary exists; list content stays licence-encumbered.

**Implications:** Every fast published engine is a **token index with a least-frequent-token choice plus a separate hostname structure**; Bloom-filter-first designs lost because blocking is common. The big recent win (Brave, 2026) was **not** matching speed but making the compiled form a **zero-copy, mappable file**, which is exactly networking 6.15's sealed automaton. Safari shows the opposite risk of full ahead-of-time automata: seconds of compile time on phones and hard rule caps. Izcal's 20 µs p99 target is comfortably above published means (5–20 µs) but none of those engines publish a p99 on a fixed corpus, so Izcal must measure its own tail.

**Implications:** Izcal's design (per-site subset as a user-origin sheet, cascade shared per partition, ≤ 256 KiB) answers 3.1 directly. Procedural operators should be compiled into native selector features where possible (`:has()`), and text/XPath operators either declined or implemented inside the style engine rather than as page-injected script.

## 9. Design ideas for an own matcher (ideas only, never code)

1. **Two-level index, chosen by measurement.** A hostname structure (suffix-label trie or perfect hash over reversed labels) for `||host^` rules, which are the majority, and a token index for path patterns, with each rule filed under its rarest token computed over the whole compiled corpus (2.1, 2.5, 2.6). Bucket 0 (token-less rules) is a compile-time warning, and its size is reported.
2. **Compiled form is a sealed, zero-copy, position-independent file** (networking 6.15; Brave's FlatBuffers result, 2.8): offsets, not pointers; mapped read-only by every partition service; validated once in the utility process with a checksum and a structural verifier, then trusted only as data with bounds-checked reads.
3. **No general regex at match time.** Translate the URL-pattern language (`*`, `^`, anchors) into a small fixed set of match primitives; accept `/regex/` only in a linear-time subset (RE2-like guarantees, size-capped like DNR's 2 KB), compiled in the utility process; reject or quarantine the rest with a reported reason (2.13, 2.17).
4. **Option checks before pattern checks**, as bitsets: resource type, party, method and partition flags first; `$domain` as a set lookup against T and F (1.16, 2.6).
5. **Total, documented precedence**: a single ordering key (important > exception > redirect > block, then priority, then list order, then rule id) so ties never depend on hash order; this is the answer to 7.3 and DET-1.
6. **Context-complete decisions**: match over (URL, resource type, initiator, F, T, container, CNAME chain, method, service-worker route) because only the in-stack placement has all of it (6.6, 6.7).
7. **Provenance tiers in the compiled file**: rules that only block or allow are accepted from any user list; redirects only to Izcal's built-in neutral resources; header changes from a closed allowlist that never weakens security headers; script-running and body-rewriting rule kinds exist only for Izcal-authored lists, or not at all (4.5, 5.2).
8. **Cosmetic compiler emits native CSS** per site, preferring `:has()` and generic "collapse what was blocked" over generic selector sheets (3.1, 3.5); text and XPath operators are either dropped or implemented inside the style engine's matching, never as page-injected script with MutationObservers.
9. **Reference matcher as oracle**: a deliberately naive interpreter of the rule-syntax page, used to differentially fuzz the compiled automaton on random rules and URLs (Section 7).
10. **Explainability is a by-product**: each compiled rule keeps (list, line, entry id) so DevTools and the decision log can name the rule (frame, DevTools user row), at no per-match cost.
11. **Dead-rule reporting at compile time** for user lists (shadowed by a broader rule, unreachable type combination, duplicate) and evidence-based pruning for Izcal's lists (8.1–8.3).
12. **Bounded compile**: compile time and output size are budgets with a refusal path, as Safari's compiler rejects harmful rule sets (2.10), so a hostile list cannot exhaust the utility process.
