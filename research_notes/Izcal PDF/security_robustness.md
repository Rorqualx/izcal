# Izcal PDF: security_robustness

Compiled 19 October 2026. Primary sources were preferred (papers, CVE/NVD records, vendor advisories, Project Zero and researcher write-ups, vendor policy pages).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only, or the researcher's recollection.

M-1 note: no source code of any browser or PDF engine was opened (pdf.js, PDFium, Poppler, Xpdf, MuPDF, CoreGraphics, Acrobat or others). Evidence comes from CVE descriptions, vendor advisories, security write-ups in prose, papers, design documents in prose, and policy pages. One search result pointed at Chromium code reviews; they were not opened or cited. Where only engine source would state a value (a parser's recursion limit, a decompression cap), it is recorded as a question for black-box measurement.

**Method notes**
- About 30 web fetches and searches were used before the shared search budget ran out. After that only known primary pages were fetched; several planned topics (OSS-Fuzz PDF numbers, grammar-fuzzing results, Reader X sandbox history, pdf.js scripting sandbox) are graded Low and listed under "Claims not verified".
- CVE counts come from the NVD 2.0 API, queried on 19 October 2026 by keyword ("pdfium", "PDF in Google Chrome", "pdf.js", "Adobe Reader", "Acrobat Reader"). Keyword counts are **lower bounds**: many Chrome CVEs name the component only as "PDF", and Adobe advisories change wording over time. Treat them as shape, not census.
- The NDSS 2021 paper "Processing Dangerous Paths" was read in full (text extracted locally from the published PDF), so its rows are High.

**Implications:** A C/C++ PDF engine yields a steady stream of use-after-free, overflow and image-decoder bugs; a memory-safe engine trades these for logic bugs (injection, origin confusion, navigation bypass). Izcal's Rust engine removes the first class only if it has no `unsafe` decoding code; it must still design out the second class, which is where pdf.js and Chrome's 2026 PDF navigation CVEs live.

Decompression needs a per-stream **and** per-document output cap.

**Implications:** A browser viewer should show a signature as valid only for the **signed revision**, and show plainly when later incremental updates exist (and what they change). Whether Izcal validates signatures at all is a scope decision for the spec; if it does not, it must not show any "signed" badge.

**Implications:** Izcal must set its own limits from first principles (†), enforce them in the engine (structured, recoverable errors) **and** in the OS sandbox (hard memory and CPU caps), and publish them. Suggested starting points for the spec to justify or replace: decoded bytes per stream ≤ 256 MiB†, per document ≤ 2 GiB† or a fraction of the PDF process's memory budget; filter chain ≤ 8†; indirect-reference and XObject nesting depth ≤ 64†; a visited-set on every graph walk; per-page render CPU budget with cancellation; JBIG2/JPX image pixel caps tied to the images spec.

**Implications:** Running PDF JavaScript is a scope decision for the spec, not a default. If Izcal runs it, it should be a minimal, specified subset (form calculation, formatting, validation) on Izcal's own JS engine in the PDF sandbox, with no network, no file, no timers beyond a budget, and a fixed property set so it cannot fingerprint beyond "Izcal". XFA should be out of scope, with a clear fallback message.

Origin design (§2.12, §1.4) needs equal attention.
