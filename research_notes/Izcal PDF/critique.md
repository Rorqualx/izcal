# Izcal PDF: independent design critique (phase 8)

Written 19 October 2026 by a reviewer who did not write the spec. Subject: `reports/Izcal PDF.md`, draft 0.1 (line numbers below refer to that draft). Method: `.claude/skills/first-principles-spec/SKILL.md`, phase 8, and the shared phase 2c brief.

**Read against:** HGBA-2 2.3.2 (M-1 parts 1–4 and the MIT-only rule, P1–P6, I-1, I-2, S-5); Stage 1 design (Section 1 process map, 2.2 G1–G9, 8.1 M7, Section 6 PDF row, 13.2); JavaScript engine spec (JS-D12, JS-D13, JS-D15, G13–G18); resource footprint spec (FP-14, FP-27, FP-38, FP-D8, FP-D11, FP-D16, FP-D19, FP-S30, Section 8.2); HTML and CSS parsing and style spec (G19–G24); fonts and text spec 0.3.4 (TX-D2, TX-D7, TX-D13, TX-D19, TX-D23, TX-D24, TX-8, G25–G29, 6.1, 6.18); networking spec 0.3.2 (6.5 crypto table, G36, `hg-crypto`, `hg-compress`, downloads and Range); images and media spec 0.4 (6.1, 6.4, 6.5, MD-D8, MD-D28, 6.18, G50–G57, R18); graphics and rendering spec 0.4 (6.1 content GPU process keying, 6.3, 6.5, glyph atlas at line 306, G60–G72, 6.27); layout spec (6.7, LY-D8); Phase 2 reconciliation (P1 layers, G24), reconciliation 2 (Q24), licence audit (OD-L2, OD-L3, OD-L6, class 4); Phase 3 ledger (C-8, C-21, G-14, A-FUT-2, A-FUT-6); the in-progress accessibility notes (`frame.md`: tree computed in the renderer, broker exposes, G100–G109; `security_robustness.md` 4.5). All seven PDF research notes' M-1 statements were read; all 287 distinct links in the spec and notes were screened for source-code hosts.

**Overall.** The draft is strong. Its central idea (one resolved view, everything downstream typed, no PDF bytes past the PDF process) is right and well argued, and the security posture is mostly security-first: generated parsers, no script engine, no authority, a named repair grammar, actions behind consent. The weak points are where the design meets parts of the system it does not fully model:
- **The process key.** The draft keys the PDF process by (site, container). The accepted graphics and footprint specs key by the renderer's key, which is the origin on every desktop class.
- **The range-read grant.** It is the one network path the PDF process has. As specified, it is both an integrity hole (bytes can change between reads) and an exfiltration channel.
- **Encryption.** The public-key handler turns the broker into a decryption oracle. The "decrypt-only" legacy crypto rule makes filled encrypted forms unsavable.
- **Colour.** The process-colour design contradicts the media spec's accepted decode classes (MD-D8) and numeric contract (MD-D28), and no amendment is listed. Its transparency model also omits shape.
- **PD-D8's recommended option.** It does not escape the licence question it was chosen to avoid.

**Counts:** 36 findings: **6 High, 18 Medium, 12 Low**. In addition, 9 engine-source and licence items (E1–E9) and 17 reconciliation items (R1–R17).
