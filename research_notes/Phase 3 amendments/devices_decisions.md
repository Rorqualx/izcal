# Phase 3, batch 5: record of the owner's decisions of 21 October 2026

Written 21 October 2026. Most of the work lands on branch `spec/phase2c`; the security-scope amendments land on `spec/security-scope` and the coding-standard amendments on `spec/cs-amendments`, each in its own worktree and published when that branch merges. This file records what the owner decided on 21 October 2026 and where each decision is applied. It is a decision record, not a research note: it cites the documents it changes, and every change it names carries its own dated revision line in the document it lands in.

## 1. Every batch-5 recommendation is accepted

The owner accepted, in full and as written, every recommendation in `reports/Izcal devices.md` §9.4, **DV-D1 to DV-D15** (the spec is now draft 0.3, the corpus's 23rd specification). The decision section carries the stamp "**Owner decision (21 October 2026): every recommendation below is accepted**", in the form `reports/Izcal JavaScript engine.md` §9.4 uses, and the spec carries a dated Revision 0.3 line (0.2 → 0.3, a notable revision under `CONTRIBUTING.md`). Notable consequences:

- **DV-D1** creates **one device-access process kind, `hg-device-main`, in three configurations** — `arbiter` (one per profile, the only caller of the OS device interfaces), `session` (one per frame site, container and device family, capped at 8† per profile) and `enumerate` (one while a chooser is open). This takes the security scope's process map from 36 to **37 kinds** and its threat-model files from 38 to **39** (one new model, `device-access.md`, with three sections). The session holds no OS handle; the arbiter parses no page bytes.
- **DV-D2** makes device access **broker-signed tickets**: the broker is the only minter, the arbiter the only verifier, and every open, transfer and configuration change carries a ticket bound to the frame origin, top-level site, container, family, device identity digest, capability set and signed scope. The signature, not a MAC, is required because issuer and verifier are different processes.
- **DV-D3** uses the **OS stack as the interface for every family, Bluetooth included** — IOUSBHost, WinUSB/WinRT, usbfs and UsbManager for USB; IOHIDManager, HIDClass and hidraw for HID; termios/COM/SerialDevice for serial; CoreMIDI, Windows MIDI Services/WinMM, ALSA rawmidi and `android.media.midi` for MIDI; CoreBluetooth, WinRT GATT, BlueZ D-Bus and `BluetoothGatt` for Bluetooth; `NfcAdapter` for NFC. Izcal writes no HCI controller stack. The rejected alternative is a 40–70† engineer, 5–6-year controller programme plus radio qualification; the chosen Bluetooth share is 3–4† inside the 6–8† device-boundary role. Web NFC is **Android-only** and is built but not shipped until an Android backend and a second-engine or owner decision exist.
- **DV-D4** is **one grant model for all six APIs**: per (frame origin, top-level site, container, family, device identity digest), with this-time, while-open and remember scopes, a 90-day† remember expiry and a 16†-per-origin cap, decided by a broker-owned chooser and recorded in the prompt ledger. **DV-D5** makes `device-pairing`, `device-connection` and `device-write` **high-risk prompt classes**, with no default selection, two separate interactions, and protected device classes refused before a prompt appears. **DV-D6** makes handles **per-(origin, container, device) pseudonyms**; hardware serial numbers, tag UIDs, Bluetooth addresses and OS paths are hidden unless a separate, off-by-default *expose hardware identifiers* grant is given (DV-D15).
- **DV-D7** records at the **device-service boundary**, not the API boundary: descriptors, typed transfers, reports, bytes, chunk boundaries, receipt times, page calls, grant and adapter decisions and typed errors. **DV-D8** replays against a **virtual device that provably opens no hardware**; NFC tag payloads are credential-class and **never recorded by default**, and tag-payload recording is an explicit, encrypted, non-exportable option.
- **DV-D9** applies **ST-D18/LY-D10 exactly as written, per API**: no device API gets general exposure in Stage 1; Web MIDI, Web Serial, WebUSB, WebHID and Web Bluetooth are built, fuzzed and reachable only through an off-by-default, per-origin *Experimental device APIs* developer setting (at most 20† origins, locked in managed profiles), and Web NFC is built but not exposed. "Ships" means default-on in a stable release; no API has two default-on engines, and MIDI has no recorded WG resolution. The six proposed owner exceptions (DV-E1 to DV-E6) are **not granted** (Section 5).
- **DV-D10** keeps **agents and extensions off the devices**: an agent acts only through the typed intent `device.request`, person-present, task-scoped and non-persistent, never inheriting the user's device grants; the six documented extension namespaces join the extensions spec's Ring C as refused, and the six device web APIs are separately refused to extension pages, content scripts and extension workers.
- **DV-D11** makes device processes **lazy and event-driven**: 30 s† idle exit, zero idle footprint, no polling, no hidden-page wakeups; the six-family worst case is 34–38 MiB† plus the 64 MiB† ring cap. **DV-D12** makes **every parser Izcal's own**, tier P and fuzzed: USB descriptors, HID reports, GATT/ATT, NDEF and MIDI wire; `hg-device-gatt` is built and maintained even though the OS stack is the shipping GATT path, because it is the oracle's protocol engine and the promotion path if a raw PDU interface appears — a stated 4–5† cost the owner acknowledged. **DV-D13** keeps Web MIDI's **all-ports enumeration after one consent**, a documented privacy exception with per-origin ids and a stated rig fingerprint. **DV-D14** refuses **WebUSB isochronous transfers** as a capability gap (`NotSupportedError`), with the compatibility cost stated. **DV-D15** allows a **remember-scope identifier-exposure grant** (true serial/UID) only with a separate high-risk prompt, default off, 90-day† expiry and immediate revocation.
- **The eight owner-facing decisions** are flagged for attention in the spec's 9.4 and this record: **DV-D3** (the cost of not building a Bluetooth stack), **DV-D4** (persistence and identifiers), **DV-D5** (all device prompts high-risk and the resulting AT gap), **DV-D8** (recording credential-class payloads), **DV-D9** (what ships when, and which exceptions may later be granted), **DV-D12** (paying for the GATT codec), **DV-D13** (the MIDI all-ports privacy exception) and **DV-D15** (persistent identifier exposure). The rest are engineering decisions the spec made and the owner reviewed.

## 2. The C-6 correction

Revision 0.3 corrects a misstatement about C-6, recorded in the devices spec's Section 9.3, its 9.5.11 C-6 row and its Appendix F2:

- **C-6's full-strength total was not "unsupported and withdrawn".** It is about **590–778† people†**: the nine-spec base of 442–570† plus the folds from batches 2–4 (SVG, animation, editing and the language-data extension; storage, WebCrypto and extensions; the ML service, shell and phishing protection).
- **The devices track's 23–31† peak folds into it**, making the full-strength total about **613–809† people†** (590–778 + 23–31).
- **The device track's Stage 1 share is 9–13† engineers gross, 8–12† net** after 1† of shared security and fuzzing time already counted. It folds into Stage 1 8.3's track table and takes its total from **59.5–84.5†** to **67.5–96.5† engineers**; the 5.5–10.5† non-engineers stand.
- **C-6's Stage 1 statement is unchanged**: about **442–570†** for the nine component specs plus DevTools 5–6.5† and the Security track 3–4†; the device addition to that Stage 1 figure is the 8–12† net share.

The 70–110† engineer-years across DV-M0–DV-M5 are the area under the ramp (9–13† at Stage 1, 23–31† at peak for roughly half the window, winding down after DV-M5), not peak × 5.75 years.

## 5. What is left open

- **DV-E1 to DV-E6 remain proposed, not granted.** The owner's acceptance of DV-D9 is the recommendation to grant none of them yet. Each stays proposed with its conditions, gains its **12-month† expiry after grant** if ever granted, and is **re-decided at DV-M5**:
  - **DV-E1** — WebUSB general exposure at Stage 2 without a second engine (decision point DV-M4): protected classes refused, per-device grants, write as `device-write`, 90-day† expiry, identifier exposure off, revocable on a parser sev-1 or class bypass.
  - **DV-E2** — WebHID general exposure at Stage 2 without a second engine (DV-M4): input collections refused, write high-risk, the VIA-style vendor-collection carve-out only with `device-write`.
  - **DV-E3** — Web Bluetooth GATT general exposure at Stage 2 without a second engine (DV-M4): no `acceptAllDevices`, HID/FIDO services refused, advertisement watch only for granted devices.
  - **DV-E4** — Web NFC exposure on Android without a second engine (DV-M5): NDEF only, foreground only, write per tap, UID pseudonym, no HCE.
  - **DV-E5** — Web MIDI general exposure without a recorded WG resolution or a second default-on engine (DV-M3): output in the base grant with the `device-write` consequence, SysEx separate and high-risk, all-ports prompt and per-origin ids, AX-D11 evidence or an explicit owner acceptance of the AT gap.
  - **DV-E6** — Web Serial general exposure without a second default-on engine (DV-M3): write-capable open with the reset warning, port-identity check, no RFCOMM, AX-D11 evidence or an explicit owner acceptance of the AT gap.
- **Q-DV-1, Q-DV-2, Q-DV-3, Q-DV-8, Q-DV-9, Q-DV-15, Q-DV-16 and Q-DV-17 stay open.** They are measurement, standards-watch or owner questions, with the owners and needed-by dates in the devices spec's Section 11:
  - **Q-DV-1** — whether macOS allows `/dev/cu.*` serial access from the sandboxed arbiter without an entitlement, and with which sandbox profile (DV-M0, needed by DV-M1).
  - **Q-DV-2** — which IOHIDManager open options allow a non-keyboard collection without Input Monitoring, and whether they differ on macOS 15/16 (DV-M0, needed by DV-M1).
  - **Q-DV-3** — whether Windows packaged WinUSB accepts the `usb` capability for the devices WebUSB targets, or only WinRT `UsbDevice` (DV-M0, needed by DV-M1).
  - **Q-DV-8** — whether an MIT-compatible corpus of USB descriptors, HID report descriptors, GATT profiles or NDEF records exists, or every corpus must be Izcal-authored (fuzz, needed by DV-M1).
  - **Q-DV-9** — whether one session process can meet sub-5 ms† MIDI through the proxy ring, or MIDI needs a direct session handle (device, needed by DV-M2).
  - **Q-DV-15** — which second engine, if any, is likely to ship USB/HID/Bluetooth, and on what evidence the owner should grant DV-E1–DV-E3 (owner/standards, needed by DV-M4).
  - **Q-DV-16** — whether a recorded Audio WG resolution adopts the Web MIDI Working Draft as its deliverable, or the published Working Draft alone carries ST-D18's WG-resolution limb (standards watch, needed by DV-M1).
  - **Q-DV-17** — whether Android reader-mode NFC and the USB permission dialog can be driven from the arbiter, or need a broker-owned activity; if an activity is required it is broker-owned and passes an fd/`PendingIntent` to the arbiter, with the G210 reading recorded (Android, needed by DV-M1). The answer changes the Android process layout, not the boundary.
- **The other questions are answered in the spec or assigned to measurement.** Q-DV-4, Q-DV-5, Q-DV-6, Q-DV-7 and Q-DV-10 to Q-DV-14 have owners and decision points inside the spec's milestones; they are not owner decisions and do not block the batch.
- **The eight owner-facing decisions are accepted, not left open.** DV-D3, DV-D4, DV-D5, DV-D8, DV-D9, DV-D12, DV-D13 and DV-D15 are flagged for attention because they carry product, cost or privacy consequences the owner should see; their reversal triggers are stated in the 9.4 table and the ledger records them as accepted on 21 October 2026.
