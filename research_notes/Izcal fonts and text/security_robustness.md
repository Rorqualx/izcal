# Izcal fonts and text: security, robustness and privacy of font and text stacks

Compiled 19 October 2026. Primary sources were preferred: Project Zero's 0-day "In the Wild" spreadsheet and root-cause analyses (RCAs), vendor advisories, the OpenType specification, papers and maintainers' posts.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, a technical secondary source, or prior knowledge not re-fetched this session; **Low** = secondary source only (forums, press).

**Method notes.**
- Section 1's tally is this note's own count. The P0 sheet ([P0 0-day ITW sheet](https://docs.google.com/spreadsheets/d/1lkNJ0uQwbeC1ZTRrxdtuPLCIl7mlUreoKfSIgajnSyY/)) was exported as xlsx on 19 October 2026 and parsed locally (412 CVE rows, August 2014 – October 2026; corrected per the fact-check, FC-R1). Rows were selected by matching font, FreeType, TrueType, ATMFD, CFF, Type 1, CoreText, DirectWrite and HarfBuzz in the description. The sheet starts in 2014, so Duqu (2011) is not in it.
- The web search budget for this session ran out partway through (after about 15 searches). Items that could not be re-fetched are graded Medium from prior knowledge, and the gaps are listed at the end. Direct fetches of known URLs were still used.
- No source code of FreeType, HarfBuzz, OTS, Fontations or any other font library was read (M-1). READMEs, advisories, RCAs, specifications and papers were.
- The security scope notes (`../security-scope/research_notes/Izcal security scope/`) already hold the Fontations "39 bugs" figure (exploits_mitigations 4.5), Lockdown Mode (sandbox_ipc 3.11), the RLBox Graphite sandbox (HGBA 2 isolation_security) and Firefox 145's fingerprinting result (new_surfaces_privacy 6.5). This note re-checks the first one and adds font-specific detail; it does not repeat the others.

**Bug classes behind the exploited and reported font bugs** (this note's tally from 1.1–1.10 and Project Zero's 2015 kernel campaign, 2.1):

| Class | Examples | Count in this note |
|---|---|---|
| Integer truncation or wrap in a size computed from font fields | CVE-2020-15999 (16-bit truncation), CVE-2025-27363 (signed → unsigned wrap) | 2 ITW |
| Count or index read from the font, not bounded before use | CVE-2020-0938 (`num_master`), CVE-2020-27930 (negative operand count), CVE-2016-7256 (CFF name index) | 3 ITW |
| Glyph-program VM (TrueType hinting, Type 1/CFF CharStrings) | CVE-2020-27930, CVE-2023-41990, CVE-2015-2455 (TrueType `IUP`, Pwn2Own 2015) | 2 ITW + 1 contest |
| Type 1 Multiple Master dictionary parsing | CVE-2020-0938, CVE-2020-1020 | 2 ITW |
| Undocumented or legacy format feature | CVE-2023-41990 (`ADJUST`); Type 1 itself (Microsoft and Apple both later removed or sandboxed it) | 1–4 |
| Embedded foreign format (PNG in `sbix`/`CBDT`) | CVE-2020-15999 | 1 ITW |
| Variation data | CVE-2025-27363 (GX subglyphs) | 1 ITW |
| Shaping state desynchronisation (no font bug needed) | CVE-2018-4124 (Telugu) | 1 |

**Implications:** Every exploited font bug is a **numeric field from the file trusted before it was bounded**, either as a size, a count, an index or a VM stack position. A parser that cannot form a buffer access without a proven bound removes the whole table; the glyph-program interpreters (TrueType hinting, CharStrings) need the same rigor as a bytecode VM, with a bounded stack, fuel and no undocumented opcodes. Type 1 is gone from browsers and Izcal should never parse it.

**Implications:** Process placement worked exactly once on the record: the same Type 1 bug was a kernel exploit on Windows 8.1 and was not exploited on Windows 10 (1.7). Validators (OTS) catch table-structure bugs but not interpreter or rasterizer bugs, and Chrome still keeps OTS in front of a Rust parser. A memory-safe parser generated from table descriptions (2.6) has the best measured record (2.5). Izcal can make the validator and the parser **one thing**: a generated, bounds-proved reader whose acceptance set is the validation policy.

## 3. Resource exhaustion and complexity attacks

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **COLRv1 requires an acyclic paint graph, but sets no depth limit.** "The graph must be acyclic"; `PaintColrLayers` and `PaintColrGlyph` use indirect references and "provide a possibility for introducing cycles"; applications "should track paint tables within a path" (pseudo-code given). On error the sub-graph "should not be rendered"; an application that cannot recover "may ignore the color glyph entirely". Depth is "arbitrary ... to the limits inherent in the formats" | must (acyclic) / should (detection) / none (depth) | [OpenType spec: COLR](https://learn.microsoft.com/en-us/typography/opentype/spec/colr) | 2026-10 (living) | High |
| 3.2 | **HarfBuzz CVE-2023-25193**: O(n²) work in `hb-ot-layout-gsubgpos` (as the CVE text names it) when many consecutive marks force a backward search for a base; CVSS 7.5, CWE-770; fixed in HarfBuzz 7.0/8.0 era. HarfBuzz's defense is implementation-chosen: a cap on operations per input character (64, raised to 1024 for a real Duployan font, HarfBuzz issue 2707). OpenType GSUB/GPOS defines no such limits | 1 CVE; limits not in spec | [Debian tracker CVE-2023-25193](https://security-tracker.debian.org/tracker/CVE-2023-25193); [HarfBuzz issue 2707](https://github.com/harfbuzz/harfbuzz/issues/2707) | 2023-02 | High |
| 3.3 | TrueType hinting has loops (`LOOPCALL`, `JMPR`, recursion through `CALL`) and no instruction limit in the specification; rasterizers impose their own instruction and call-depth caps. Composite glyphs reference other glyphs with no depth limit in the spec (`maxComponentDepth` in `maxp` is advisory) | 0 spec limits | [OpenType spec: maxp](https://learn.microsoft.com/en-us/typography/opentype/spec/maxp) | living | Medium |
| 3.4 | WOFF2 inflates Brotli-compressed tables to a size declared in the header; a decoder must check the declared total before allocating and stop at it, or a small file becomes a large allocation (decompression bomb) | Qualitative | [W3C WOFF 2.0](https://www.w3.org/TR/WOFF2/) | 2024-08-08 | Medium |
| 3.5 | **The Telugu crash is a shaping bug, not a font bug.** Sequence ja + virama + nya + ZWNJ + aa (U+0C1C U+0C4D U+0C1E U+200C U+0C3E); generally consonant, virama, a "suffix-joining" consonant, ZWNJ, vowel; also Bengali and Devanagari. The analysis guesses that the virama's left "affinity" "confuses the algorithm that handles ZWNJs after viramas", desynchronising code point and glyph buffers | 3 scripts | [Manish Goregaokar: Picking apart the crashing iOS string](https://manishearth.github.io/blog/2018/02/15/picking-apart-the-crashing-ios-string/) | 2018-02-15 | High (sequence); Medium (cause) |
| 3.6 | Long combining sequences ("Zalgo") are legal Unicode; UAX 15's Stream-Safe Text Format bounds a run of non-starters at 30 for normalization, but nothing bounds shaping input. Layout must still handle 10⁴ marks on one base without quadratic cost (3.2) | 30 (UAX 15) | [UAX 15 §13](https://www.unicode.org/reports/tr15/#Stream_Safe_Text_Format) | Unicode 17 | Medium |

**Implications:** The specs mandate almost no limits (one "must" for acyclic COLR graphs, nothing for depth, hinting time, lookup nesting or shaping work). Every engine chooses its own caps, which makes them device- and engine-observable. Izcal should define **canonical fuel**: per font, per glyph program and per shaped run, in units of the abstract work (not time), identical on every platform (B1, FP-D19), with the result on exhaustion specified (glyph dropped to outline, run shaped without that lookup).

**Implications:** Fonts fingerprint through two channels: which fonts exist (enumeration, Local Font Access) and how they render (metrics, rasterization, 4.3). A browser that ships its own rasterizer and a fixed, bundled font set with deterministic output (B1) can make metrics identical across users of one build, which no OS-rasterizer browser can. Exfiltration (4.10) and GPU leaks (4.11) are by-spec or hardware behaviors and need partitioning and process boundaries, not parser fixes.

**Implications:** Verified generated parsers have run on hostile input at hyperscale for years at <2% cost (6.2) and safe-by-construction decoders can beat C (6.3). Font tables are the same shape of problem (offsets, counts, arrays of records), so Izcal can describe OpenType tables once in a format language, generate a zero-copy reader with proved bounds, and use the same description to drive structure-aware fuzzing and differential tests.

## Design implications for Izcal (ideas, not decisions)

1. **Process placement.** Parse and rasterize untrusted fonts only in the strictest utility process or the site's renderer, never the broker or GPU service (security scope IPC-R15). 1.7 shows the boundary turning a kernel exploit into a contained one. Outputs crossing a boundary should be normalized (outlines, bitmaps, metrics), not font bytes.
2. **One generated reader is the validator.** Replace the OTS role with a reader generated from table descriptions, proved bounds- and overflow-safe (VER-1 Tier 1), whose rejection set is the sanitization policy; never re-serialize fonts. Cover the CFF/CFF2 CharString and TrueType instruction interpreters as VMs with bounded stacks and no undocumented opcodes. No Type 1.
3. **Canonical fuel everywhere the spec is silent.** Hinting instructions, composite depth, COLRv1 graph depth and cycles, GSUB/GPOS nesting and per-run operations, WOFF2 declared sizes: abstract-unit budgets identical on every platform, with specified fallback on exhaustion, recorded as B1 inputs. Every shaping algorithm linear or bounded in run length (3.2).
4. **Regression corpus.** Each class in Section 1 (truncation, wrap, unbounded count, VM stack, PNG-in-font, variations, Telugu-class shaping desync) becomes a permanent test, plus differential tests against black-box engines (M-1 part 4).
5. **Fingerprinting posture.** Bundled, fixed font set per build with deterministic metrics; system fonts visible only through the sealed, PRIV-2-filtered session image (footprint 6.3); no Local Font Access without a strong reason; partitioned glyph and shaping caches (FP-D14, FP-36); a measurable target from 4.3 (unique-by-font-metrics fraction).
6. **Exfiltration and GPU.** `unicode-range`/ligature leaks are by-spec; partition font fetches and treat them as style-injection consequences, not parser bugs. Keep cross-origin content out of shared GPU filter paths (4.11).
7. **Unicode security data** lives in the text stack (UBA, UTS 39, normalization at the pinned UCD); shell and DevTools render bidi controls visibly where code or URLs are shown.
