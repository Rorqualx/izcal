# Izcal fonts and text: glyph rasterization, hinting, anti-aliasing and glyph caches

Compiled 19 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, a specification fact stated from the researcher's knowledge of the published spec, or a number inferred from a primary source (method stated); **Low** = secondary source only.

M-1 reading used throughout: FreeType, Skia, skrifa, swash, Vello, Pathfinder, Slug and WebRender are **evidence only**. No source code of any of them was read. Facts come from documentation, papers, blogs, theses and issue trackers. The one exception is a list of *names* in a Chromium metrics enum (5.3), which is cited as a statement of policy, not as code.

## 1. Rasterization algorithms

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Dense accumulation rasterizer (font-rs):** line segments are drawn straight into a dense array of signed area/coverage deltas, with no sorted edge list. A prefix sum (SIMD) then gives coverage. The README claims "extremely promising performance compared with Freetype". It avoids branch mispredictions and allocation. The same idea underlies fontdue, which claims "the lowest end-to-end latency for a font rasterizer". | No verified ratio | [font-rs README](https://github.com/raphlinus/font-rs); [fontdue README](https://github.com/13-Types/fontdue) | 2016; 2026-10 (read) | Medium |
| 1.2 | **Sparse strips (Vello CPU):** the canvas is cut into **4×4 tiles**. Each path becomes run-length "strips" of fixed height 4 that carry winding numbers. Fine raster has a u8/u16 path and an f32 path. The thesis presents tile size 4 as the sweet spot, measured against 1, 2 and 8. It beats most CPU renderers in Blend2D's harness. Blend2D, which uses fixed-point math, stays ahead in several tests. The thesis notes that **strips can be cached as a compact glyph representation**. An x-shift is trivial, but a **y-shift that is not a multiple of 4 is an open problem**. | tile 4×4; MT speedup up to 4.7× in one test | [Stampfl, "High-performance 2D graphics rendering on the CPU using sparse strips", ETH MSc thesis](https://ethz.ch/content/dam/ethz/special-interest/infk/inst-pls/plf-dam/documents/StudentProjects/MasterTheses/2025-Laurenz-Thesis.pdf); [vello_cpu crate](https://docs.rs/crate/vello_cpu/0.1.0) | 2025-10-10 | High |
| 1.3 | **Slug (Lengyel):** the GPU renders glyphs **straight from Bézier outlines in the pixel shader**, with no atlas texture. Curves are binned into bands. "Dynamic dilation" grows each glyph quad by half a pixel in the vertex shader so that partly covered pixels are shaded. Supersampling was removed because it only helped text that is "barely readable anyway". The stated goal is provably no artifacts despite floating-point round-off. **The patent (US 10,373,352, granted 2019) was dedicated to the public domain on 2026-03-17.** No benchmark numbers are given. | patent free from 2026-03-17 | [Lengyel, "A Decade of Slug"](https://terathon.com/blog/decade-slug.html) | 2026-03-17 | High |
| 1.4 | **Pathfinder 3:** a GPU rasterizer that computes **exact trapezoidal area coverage** ("effectively 256× AA"). It has a compute mode ("D3D11") and a hardware-raster mode ("D3D9") in which tiling runs on the CPU. It supports slight hinting, subpixel AA, stem darkening and gamma. It claims to "often match or exceed" the best CPU rasterizers, with the largest gains at large sizes. The README says "heavy development, incomplete". | no data | [servo/pathfinder README](https://github.com/servo/pathfinder) | 2026-10 (read) | Medium |
| 1.5 | **Loop–Blinn (2005):** curves are filled in the fragment shader by an implicit-function test over triangulated hulls. It is the ancestor of Slug-style approaches. An HN comment said the Microsoft patent on cubic curves would expire in March 2026; this is unverified. | — | [Loop & Blinn, "Resolution independent curve rendering using programmable graphics hardware", SIGGRAPH 2005](https://www.microsoft.com/en-us/research/publication/resolution-independent-curve-rendering-using-programmable-graphics-hardware/) | 2005 | Medium |
| 1.6 | **SDF/MSDF text:** multi-channel distance fields fix the rounded corners of single-channel SDF. The paper says a higher field resolution "only reduces" corner errors and "can never eliminate them". Distance-field fonts **do not support hinting**, so they suit large, scaled or 3D text, not 9–16 px body text. | — | [Chlumský et al., "Improved Corners with Multi-Channel Signed Distance Fields", CGF 2018](https://dcgi.fel.cvut.cz/wp-content/wpallimport-dist/publications/pdf/publications-2018-sloup-cgf-msdf-paper.pdf); [Red Blob Games, SDF fonts](https://www.redblobgames.com/articles/sdf-fonts) | 2018; 2024 | Medium |
| 1.7 | **GPU floating point is not bit-exact across implementations.** WGSL has a whole section on floating-point evaluation, with sub-sections on accuracy, reassociation and fusion, and makes even literal rounding "an implementation choice". So shader-computed coverage (Slug, Pathfinder D3D11, Vello GPU) cannot promise bit-identical pixels across vendors without integer-only arithmetic. | — | [W3C WGSL §15.7](https://www.w3.org/TR/WGSL/#floating-point-evaluation) | 2026-10 (read) | Medium (TOC and literal rules read; body not read) |

**Implications:** for B1, coverage must be computed in **integer or fixed-point arithmetic on the CPU**, with one implementation on both ISAs (JS-D12 style). The dense-accumulation and sparse-strip families both fit, and sparse strips also give a compact cache format. GPU outline rendering (Slug, now patent-free) is attractive for large and transformed text, but only if it is accepted as non-bit-exact or written with integer shader arithmetic. SDF is unsuitable for body text.

## 2. Hinting

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **FreeType v40 TrueType interpreter (default since 2.7):** it **ignores all horizontal hinting instructions** and snaps only on the y axis. Reasons given: output is close to DirectWrite/ClearType, **advance widths do not change**, spacing of poorly hinted fonts improves, and stem darkening conflicts with x-hinting. v35 (full 1990s grid fit) was the old default. v38 ("Infinality") was "very slow" and is off by default. v40 is about as fast as v35. | default from 2.7 | [FreeType, "The new v40 TrueType interpreter mode"](https://freetype.org/freetype2/docs/hinting/subpixel-hinting.html) | 2016-09-08 | High |
| 2.2 | **"Slight" hinting = vertical-only.** Native vertical snapping is used where the driver supports it; otherwise the autohinter is used. Full or medium native hinting "tends to bring out the worst" in many fonts. "Slight hinting will result in consistent font rendering." | — | [Waxweiler, "On slight hinting, proper text rendering, stem darkening and LCD filters"](https://freetype.org/freetype2/docs/hinting/text-rendering-general.html) | 2015-11-30 | High |
| 2.3 | **CFF hinting and stem darkening:** Adobe's CFF engine (in FreeType since 2013, now the default) darkens stems at small sizes by default. Control points: **+0.4 px up to 0.5 px stems, +0.275 px at 1–1.667 px, 0 at ≥2.333 px**, with linear interpolation between them. The curve comes from Adobe's "Avalon" rasterizer. Darkening assumes a gamma-correct pipeline. | 0.4 / 0.275 / 0 px | [FreeType ftcffdrv.h docs (mirror)](https://fuchsia.googlesource.com/third_party/freetype2/+/VER-2-5-3/include/ftcffdrv.h); [Waxweiler 2015](https://freetype.org/freetype2/docs/hinting/text-rendering-general.html) | 2013; 2015 | Medium |
| 2.4 | **DirectWrite rendering modes:** GDI_CLASSIC (x-only AA, GDI-compatible whole-pixel advances), GDI_NATURAL (design-like advances rounded to whole pixels), NATURAL (**subpixel positioning**, resolution-independent layout), NATURAL_SYMMETRIC (AA on both axes, larger sizes), OUTLINE (very large sizes). | 2.5 | **Hinting vs subpixel positioning:** Skia (via FreeType) forces slight hinting whenever subpixel positioning is on. Chromium stopped enabling subpixel positioning with medium or full hinting (2014). A 2018 commit says headless Linux builds were moved to full hinting because desktops resolve to full, and the result "renders differently". Cairo proposes the same rule: subpixel positioning only with at most slight hinting. | — | [Qt WebEngine patch of Chromium change](https://gitlab.linphone.org/BC/public/external/qt/qtwebengine-chromium/-/commit/bd04cc312a5bc7b454d2aba317f3357b367a6d34); [crrev 536535](https://crrev.com/536535); [cairo MR 262](https://gitlab.freedesktop.org/cairo/cairo/-/merge_requests/262) | 2014; 2018; 2023 | Medium |
| 2.6 | **Layout metrics:** a 2019 Skia change redefined a flag to mean "use linear metrics", which fixed Chromium bugs about metrics for hinted fonts. On Windows, embedded-bitmap fonts without subpixel positioning use GDI-classic measuring, a per-OS divergence. FreeType: hinted metrics make layout **depend on output resolution**; linear (unhinted) advances keep layout device-independent. | — | [Skia commit f460eee](https://skia.googlesource.com/skia/+/f460eeec99dc09408c7903b582ab90995faf2f7c); [crrev 1304363011](https://codereview.chromium.org/1304363011/); [FreeType Glyph Conventions §V](https://freetype.org/freetype2/docs/glyphs/glyphs-5.html) | 2019; 2015 | Medium |
| 2.7 | **Chrome's font back end is now skrifa (Rust, Fontations):** used for web fonts on Linux, Android and ChromeOS since Chrome 133 (2025-02) and for system fonts since 136. **FreeType was removed from Blink in Chrome 145.** Skrifa has "high level hinting virtual machines" and about 700 unit tests. It was compared with FreeType in pixel tests ("fauntlet") across AA and hinting modes; no closeness figure is published. Fuzzing found 39 bugs, none security-critical. Google's FreeType fuzzing and triage cost "≥0.25 FTE". A COLRv1 bug in FreeType "took more than 10 months" to find by fuzzing. | 700 tests; 39 bugs; 0.25 FTE | [Chrome blog, "Memory safety for web fonts"](https://developer.chrome.com/blog/memory-safety-fonts) | 2025-03-19 (updated later) | High |
| 2.8 | **The hinting VM is an attack primitive:** TrueType hinting programs alone, with no script, mount **cache-contention and L1 Prime+Probe attacks**, website fingerprinting, and tracking of the PDF page being viewed. The authors call for mitigations "beyond traditional scripting languages". | — | [Trampert & Schwarz, "Hidden in Plain Sight: Scriptless Microarchitectural Attacks via TrueType Font Hinting", uASC '25](https://ojs.ub.rub.de/index.php/uASC/article/view/12015) | 2025-03-01 | Medium (abstract) |
| 2.9 | **macOS does no hinting** (Core Text applies no grid fitting or bytecode). This is long-standing platform behaviour; no Apple primary statement was found in this pass. | — | [Waxweiler 2015 (Windows/macOS comparison)](https://freetype.org/freetype2/docs/hinting/text-rendering-general.html) | 2015 | Low–Medium |

**Implications:** the industry has converged on **x-unhinted, at most y-snapped** rendering with **linear advances for layout**. That matches B1 exactly. Layout never sees hinted advances, so metrics do not vary by OS. Hinting becomes a raster-only, per-strike choice. A full TrueType bytecode VM is both an attack surface (2.8) and a source of output variety. Izcal can choose (a) no bytecode at all, with an own vertical-only autohinter, or (b) a fuel-bounded VM limited to y-direction instructions in a sandboxed utility process. Either way the choice is a **pinned B1 input**, never OS-dependent.

## 3. Anti-aliasing, gamma and display density

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Gamma:** text must be blended linearly and then gamma-corrected. At gamma 2.2, coverage 128/255 looks too dark, and about 186 is needed for 50% perceived brightness. Windows and macOS already do this natively; X11 toolkits did not (2015). Gamma correction thins text, which is why stem darkening exists. | 128 → ≈186 | [Waxweiler 2015](https://freetype.org/freetype2/docs/hinting/text-rendering-general.html) | 2015-11-30 | High |
| 3.2 | **LCD filters** must sum to 1 (0x100). FreeType's newer default filter is normalized and colour-balanced. Subpixel rendering gives about 3× horizontal resolution before filtering, but the filter takes back part of the gain. | 3× nominal | [FreeType v40 article](https://freetype.org/freetype2/docs/hinting/subpixel-hinting.html) | 2016 | High |
| 3.3 | **macOS Mojave (10.14, 2018) turned subpixel AA off by default.** The setting can still be re-enabled with a `defaults` key, so the code appears to remain. The only stated rationale is a reported ex-Apple engineer: LCD AA needs physical subpixel geometry threaded through every graphics layer, and that is screen-dependent (multi-monitor, rotation). Retina panels make it unnecessary. | — | [angristan, "How to fix font rendering on macOS 10.14"](https://angristan.xyz/how-to-fix-font-rendering-macos-10-14-mojave/); [MacRumors thread](https://forums.macrumors.com/threads/the-subpixel-aa-debacle-and-font-rendering.2184484/) | 2018-09 | Low |
| 3.4 | **LCD text needs an opaque destination.** "Drawing LCD text into non-opaque layers is never correct", so Chromium disables it there, and Skia disables it for non-opaque save-layers. A canvas rotated by CSS can keep LCD text only in its first frame. Chromium records the reasons in `LCDTextDisallowedReason`: setting, background not opaque, contents not opaque, non-integral translation, and others. These feed UMA split by high and low DPI. Chromium promotes opaque-background scrollers to layers partly to keep LCD text. | — | [Chromium lcd_text_disallowed_reason.h (names only)](https://chromium.googlesource.com/chromium/src/+/HEAD/cc/raster/lcd_text_disallowed_reason.h); [WHATWG thread (S. White)](https://lists.whatwg.org/pipermail/whatwg-whatwg.org/2013-February/081268.html); [crrev 1826013002](https://codereview.chromium.org/1826013002/) | 2013–2026 | Medium |
| 3.5 | **Display density, Steam survey September 2026 (primary display):** 1920×1080 **47.91%**, 2560×1440 **27.04%**, 2560×1600 5.22%, 3840×2160 **4.79%**, 1366×768 1.92%. Inference: ≥75% of this (gamer, desktop-heavy) population is on panels normally run at DPR 1–1.25. Laptops at 2560×1600 or 2880×1800 are often DPR 2. Steam does not report DPR. | 47.9 / 27.0 / 4.8% | [Steam Hardware & Software Survey](https://store.steampowered.com/hwsurvey/Steam-Hardware-Software-Survey-Welcome-to-Steam) | 2026-09 | High (data); Medium (DPR inference) |
| 3.6 | **Rendering variety is a fingerprint.** Mowery & Shacham found **50 distinct renderings among 300 samples** of 18pt Arial on canvas, and **44 groups among 294 for a web font**, i.e. the *same font bytes*. That is 5.73 bits across their tests, with "differences even between computers running the same OS and browser version". The variety came from rasterizer, AA, hinting and gamma, not only font choice. | 50/300; 44/294; 5.73 bits | [Mowery & Shacham, "Pixel Perfect: Fingerprinting Canvas in HTML5", W2SP 2012](https://hovav.net/ucsd/dist/canvas.pdf) | 2012 | High |

**Implications:** low-DPI desktops are still the majority of PC screens in 2026, so **grayscale AA with good gamma and darkening matters**. LCD subpixel AA is a smaller, shrinking win, and it brings opacity rules, per-display geometry and extra variants. It is also a fingerprint source (3.6). A deterministic grayscale-only pipeline (fixed gamma and darkening tables, one implementation) removes the main source of canvas text entropy. That supports PRIV-2 directly. LCD AA, if offered at all, should be a user setting that is applied only at final composition and never readable by content.

## 4. Glyph caches and atlases

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Atlas sizes and eviction:** see the footprint notes. WebRender uses 2048² atlases, A8 4 MiB and RGBA8 16 MiB, with age-based eviction from 400 frames down to 1 frame. Skia's glyph cache defaults to 2 MB / 2048 glyphs. | 4 / 16 MiB; 2 MB | [compact_engine_data.md §7.4, §9.2](../Izcal%20resource%20footprint/compact_engine_data.md) | 2026-10 | High / Medium |
| 4.2 | **Firefox rasterizes glyphs in the GPU process**, in a Rust thread pool, during frame building. Glyphs go into a texture atlas because "GPU text rendering assumes … glyphs are already available in a texture atlas". | 4.3 | **Chrome OOP-R:** the sandboxed renderer cannot reach the GPU. Rasterization moved to the GPU process, and Skia's "Chrome remote glyph cache" (`SkChromeRemoteGlyphCache`) serializes the strikes and glyphs the renderer analyzed so that the GPU process can draw them without font access. The design doc was not found; the mechanism was confirmed only from file and API names. | — | [Intel, "Software vs GPU rasterization in Chromium"](https://www.intel.com/content/www/us/en/developer/articles/technical/software-vs-gpu-rasterization-in-chromium.html); [Skia source tree listing](https://skia.googlesource.com/skia/+/main/src/text/gpu/SkChromeRemoteGlyphCache.cpp) | 2018–2026 | Medium |
| 4.4 | **Atlas allocators:** *étagère* is a shelf packer, suited to many items of similar size such as glyphs. *guillotière* is a guillotine packer whose hard part is merging free rectangles after deallocation. It keeps neighbour links for constant-time access. Both were written for WebRender. | — | [etagere](https://github.com/hecrj/etagere); [guillotiere (Meterian listing)](https://www.meterian.io/components/rust/guillotiere) | 2024 | Medium |
| 4.5 | **Rendering side channels on shared pipelines:** *GPU.zip* leaks cross-origin pixels through iGPU **hardware compression**. Wikipedia usernames were recovered in about 30 min (AMD) and 215 min (Intel) at 97–98.3% accuracy. Chrome was vulnerable; Firefox and Safari were not. *Pixel Thief* leaks through **CPU cache access patterns of SVG filter code** at **267 bit/s**, recovering text and sniffing history. No published attack on a *glyph* cache was found in this pass. | 30–215 min; 267 bit/s | [GPU.zip](https://www.hertzbleed.com/gpu.zip/); [Pixel Thief, USENIX Sec 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/oconnell) | 2024-05; 2024-08 | High / Medium |

**Implications:** a glyph atlas holds data derived from page text, and residency (hit or miss timing) reveals which glyphs another page used. **FP-D14's per-(site, container, partition) atlases** close the cross-partition cache-timing channel by construction. Izcal still needs an FP-36 probe for it. Pixel Thief and GPU.zip show that the GPU service itself can leak through data-dependent work. Rasterizing in a per-site or utility process and passing coverage masks (Chrome's remote-cache shape, not Firefox's shared GPU-process cache) keeps font parsing out of tier-P processes. A shelf allocator fits glyphs. A 256 KiB A8 atlas is 512×512, which holds roughly 1,000–2,000 body-size glyphs (inferred: about 130–260 px each with padding), enough for Latin but not for CJK at first paint.

## 6. Variable fonts at render time

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **gvar** stores per-glyph tuple variations of point deltas. Points without explicit deltas are interpolated by **IUP** (interpolate untouched points) from neighbouring touched points. Cost is linear in points × active tuples, per glyph per instance, so outlines should be cached per (font, normalized coordinates, glyph). | — | [OpenType spec, gvar](https://learn.microsoft.com/en-us/typography/opentype/spec/gvar) | 2026-10 | Medium |
| 6.2 | **Hinting variable fonts:** **cvar** varies the TrueType control-value table per instance. The hinting program then runs on the varied outline. CFF2 hints are blended like the outlines. | — | [OpenType spec, cvar](https://learn.microsoft.com/en-us/typography/opentype/spec/cvar) | 2026-10 | Medium |

**Implications:** the variation instance (normalized coordinates, quantized to F2Dot14 as the spec does) belongs in the strike key. Interpolation must be integer or fixed-point to stay bit-identical. F2Dot14 and 16.16 arithmetic make this natural.

## 8. Design implications for Izcal (ideas only)

1. **One CPU coverage rasterizer in integer or fixed-point arithmetic**, of the dense-accumulation or sparse-strip family, written once for x86-64 and AArch64 with SIMD that gives identical results. Its output is the B1 reference. GPU outline rendering (Slug-style, patent-free since 2026-03-17) is an optional fast path for large or transformed text, verified against the reference, unless an integer shader formulation can be shown to be bit-exact.
2. **Layout uses linear (unhinted) advances only.** Hinting, if any, is vertical-only and affects raster only. This removes the largest source of cross-OS metric differences (2.5, 2.6) and keeps `measureText` deterministic before D-S1 noise is added.
3. **The hinting decision is open for the spec.** Options are (a) no TrueType bytecode, using Izcal's own vertical-only autohinter plus stem darkening; (b) a fuel-bounded y-only bytecode VM in a sandboxed utility process. Evidence: the hinting VM is an attack primitive (2.8), v40 already ignores x, and macOS ships unhinted.
4. **Grayscale AA by default, with fixed gamma and darkening tables in the build.** This removes the canvas-text fingerprint seen in 3.6. LCD AA is at most a user setting applied after composition, never visible to content.
5. **Strike key** = (font bytes hash, glyph id, size in fixed point, normalized variation coordinates, subpixel x phase, hinting mode, darkening). The number of subpixel phases is to be chosen from measurement; Chrome's value was not verified.
6. **Atlases follow FP-D14 (per site, container and partition) with a shelf allocator**, separate A8 and RGBA pools, and an FP-36 test for glyph-residency timing.
7. **Cache sparse-strip or coverage masks, not outlines, for small sizes.** Investigate vertical re-phasing of strips (1.2, open problem) as an Izcal contribution.
8. **COLRv1 runs on the general paint rasterizer, with fuel.** Bitmap emoji are scaled with a pinned filter.

## 9. Flagged claims and open questions

- **Unverified:** font-rs's speed ratio against FreeType (the 2016 post was unreachable); glyphs/s figures for any rasterizer at 12–16 px; first-text paint latency numbers.
- **Unknown:** Chrome's subpixel position count per glyph (commonly said to be 4 horizontal; not verified); Chrome's current per-OS hinting defaults; Chrome's renderer and GPU glyph cache limits.
- **Unknown:** whether any production rasterizer claims bit-exact cross-platform output. FreeType's 26.6 and 16.16 fixed point suggests it is possible, but no statement was found.
- **Not found:** a published timing attack on a browser *glyph* cache. The partitioning argument rests on the general cache-residency channel, not on a known exploit.
- **Not found:** an official Apple rationale for dropping subpixel AA in Mojave (3.3 is Low).
