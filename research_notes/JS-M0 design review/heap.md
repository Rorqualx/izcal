# JS-M0 design review: `hg-heap`

Written 31 October 2026 for JS-M0 (JS spec 9.2). It turns the JS spec's sketch of the heap (Sections 6.1 and 6.5, "names illustrative, not an interface freeze") into the decisions the first `hg-heap` implements. It changes no target and no owner decision (JS-D1, JS-D2, JS-D3, JS-D15, JS-D16, JS-D17, JS-D18 stand).

## Scope at JS-M0

JS-M0 builds the **precise, non-generational mark-region collector** that later collectors are tested against (JS spec 9.1: "the precise collector is the rooting oracle the others are tested against"). The copying nursery, concurrent marking and its barrier protocol, ephemerons and the read-only image come later. The design leaves room for each: every slot is already an atomic, every edge store already goes through one setter where the barrier will sit, and the header has room for a mark-state bit.

## Decisions

| # | Decision | Why | Reversed by |
|---|---|---|---|
| H-1 | **Every cage access goes through one inventoried module, `cage`, with the offset masked to the cage length (a power of two) and aligned to its width.** No other module computes a cage address. | H-2: under arbitrary cage contents, the worst a bad offset can do is address another part of the cage. A 16 GiB cage is 2^34 bytes, and a 31-bit offset in units of 8 also spans 2^34, so in production every decompressed reference lands inside the reservation by construction; the mask matters only for the smaller cages that tests use | A measured cost of the mask on the reference interpreter (JS-D16's spike); it is one `and` instruction |
| H-2 | **Objects are never materialised as Rust references (`&T`).** A `Gc` is a slot value. Field reads and writes are atomic loads and stores at `object + field offset`, through `cage`. | A Rust reference must point at valid, dereferenceable memory for its whole lifetime. A corrupted slot can name any offset in the cage, including uncommitted pages, so `&T` would make corruption Rust-level undefined behaviour. Raw, clamped atomic accesses keep the worst case an in-cage fault, which H-2 allows (JS-10 counts out-of-cage faults) | — |
| H-3 | **`Trace` is a safe trait. Its impls come only from `hg_heap::object!`, a declarative macro; a hand-written impl is a lint error (G5's intent, enforced by an ast-grep rule).** The spec's sketch had an `unsafe trait` implemented by a procedural-macro derive. | Because of H-1 and H-2, a wrong layout description can only make the heap trace the wrong slots, which gives wrong answers inside the cage: the same outcome the spec already accepts under corruption. Soundness does not depend on the description, so the trait need not be `unsafe`. Generated code then needs no `unsafe` in the user's crate (G5 forbids it there), and no procedural macro is needed (the graph rules ban them in L1–L3 without an exception) | A reason the layout must be trusted for memory safety, for example a future direct `&T` access path |
| H-4 | **Object layout:** a 4-byte header (a type index into the heap's type table, which lives outside the cage, plus a forwarding bit), a 4-byte length word (for variable-size objects; 0 otherwise), then the body: traced slots first, then raw words. Every object starts on an 8-byte boundary, so its offset is a slot offset. | One layout for fixed and variable objects. The type table is outside the cage, so the tracer's layout comes from a bounds-checked index (H-2), and a corrupted type index selects another valid layout, never an out-of-table read | The object model's shapes (JS-M1) may move the header to a shape reference; the type table then becomes the shape's layout descriptor |
| H-5 | **Immix geometry:** 32 KiB blocks of 128-byte lines; blocks committed in 1 MiB chunks. | The Immix paper's sizes ([PLDI 2008](https://www.steveblackburn.org/pubs/papers/immix-pldi-2008.pdf)). 1 MiB is a multiple of every page size Izcal runs on (4 KiB, 16 KiB, 64 KiB), so the heap's commits are aligned on every OS and the simulator's ledger is identical everywhere | The JS-D4 spike or corpus measurement of fragmentation |
| H-6 | **Objects larger than 8 KiB go to a large-object space:** whole blocks, never moved, freed whole. | Immix keeps medium objects out of line-sized holes; a non-moving large space is the spec's allocation row (6.5) | — |
| H-7 | **One tracing loop serves marking and evacuation.** A cycle picks a set of candidate blocks. A live object in a candidate block is copied to a fresh block, its old header records the new offset, and every slot that reached it is updated. Every other live object marks its lines. Normal cycles pick fragmented blocks (opportunistic evacuation). The **moving test collector** picks every block on every allocation, and the **GC-stress mode** at every safepoint. | One mechanism, tested hardest by the mode that moves everything (JS spec 6.5, step 8) | — |
| H-8 | **GC debt is counted in canonical allocation units, charged by the operation, never by the allocation.** `Mutator::charge(units)` is the GC point that adds debt, with the units the operation's `.hgop` description fixes; `alloc` itself charges nothing. A cycle starts when the debt reaches the trigger. | JS spec 6.9: GC triggers never depend on OS pages, real sizes, representation or time. A charge by object size would differ between a tier that boxes a number or builds a rope and one that does not; the design review's R0-B10 fixes the units per description | The footprint spec's heap knob (FP 6.20.2), when it sets the trigger |
| H-9 | **A cycle's completion, and the clearing of weak references, is one decision point:** `DecisionKind::GC_COMPLETE` at the mutator's position, with the number of weak cells cleared as the detail. The position's progress counter is the mutator's own: the interpreter advances it with each operation it runs. | JS-D15. The probe compares the decision log, so it must carry what the cycle decided | — |
| H-10 | **Weak cells:** a type may declare weak slots. Marking skips them; when the cycle completes, a weak slot whose target is dead is cleared, and one whose target moved is updated. `WeakRef.deref` adds the target to the mutator's kept-alive list, cleared by `clear_kept_objects` (ECMA-262 [ClearKeptObjects](https://tc39.es/ecma262/#sec-clear-kept-objects)). A finalization cell whose target died is queued on its registry's cleanup list; the host runs cleanup through `HostEnqueueFinalizationRegistryCleanupJob`. | ECMA-262's [WeakRef processing model](https://tc39.es/ecma262/#sec-weakref-processing-model): clearing happens together, at the end of a cycle | Ephemerons (JS-M1, with `WeakMap`) join the same pass as a fixpoint |
| H-11 | **Brands and roots follow the spec's sketch:** `Heap::enter(|m| …)` gives a fresh invariant `'h`; `Gc<'h, 'm, T>` carries the shared borrow of the mutator, so it cannot survive a GC point (`&mut Mutator`); `Root<'h, 's, T>` is an index into the mutator's root slots, valid in its generative scope `m.scope(|m, s| …)`. | JS-D18, the soundness argument's steps 1–4 and 6 | The CS-D3 re-run (below) |
| H-12 | **One cage per process, shared by its agent heaps (JS-D17).** The cage hands each heap whole 1 MiB chunks from a locked pool; a heap numbers its blocks in the order it acquired them, so its layout never depends on other agents. A slot of one heap that points into another heap's chunk is never followed. A dropped heap gives its chunks back whole, without tracing; they are decommitted and reused, and a run of chunks for a large object reuses adjacent returned ones. A chunk whose decommit the OS refused keeps the old heap's data, so it is never handed out again (I-2). | JS-D17 (a): a shared heap is more blocks in the same cage, with ordinary 32-bit references and a brand; per-agent ownership keeps heaps from mixing even under corruption (H-2), and makes release on navigation away free (JS spec 6.5) | The JS-D17 spike: address-space or allocation contention between agents on a reference device |

## Unsafe code, and its verification conditions

`hg-heap` has one inventoried module, `cage`. Its condition, stated for arbitrary cage contents: **every access it performs lies inside `[base, base + len)` of the cage reservation, is aligned to its width, and is atomic.** It holds because the module masks every offset to `len − 1` (with `len` a power of two) and rounds it down to the access width before adding `base`. An access may land in an uncommitted page and fault; that is a crash inside the cage, which H-2 allows. Everything else in the crate is safe Rust.

The copy used by evacuation (H-7) is a loop of word-sized atomic loads and stores through the same module, not a `memcpy`, so it meets the same condition.

## Tests

- **Miri** runs the heap's tests with the moving test collector on a small cage backed by an ordinary allocation (a `Memory` implementation for tests), since Miri cannot map a real reservation.
- **Kani** proves the slot encoding: `decode(encode(x)) == x` for every offset and small integer, and that every decompressed offset is inside the cage.
- **The four cross-heap cases** (store across heaps, read through the wrong mutator, root through the wrong mutator, a `Gc` of one heap written into an external traced slot through another's mutator) are compile-fail tests, in `crates/hg-heap/tests/ui/` with the rest of the brand discipline. `tools/refusals.sh` runs them and `tools/checks.sh`'s `refusals` check calls it, so a variance or signature change that quietly makes one of them legal fails CI rather than passing silently. Each case names the error code it must be refused with, and the brand cases also name the note where rustc says which of the heap's types is invariant over `'h`: without that second check, `fail-cross-heap-store` passed while being refused for an unrelated borrow, with the brand never consulted.
- **The multi-node mutation pattern** (CS-D3 criterion 4) is an `insertBefore` on the test node space with an allocating callback between the detach and the relink, run in all three collector modes: the nodes it touches are rooted in a `node_scope` for the mutation's duration, and no wrapper reference is held across a GC point. A companion test leaves the node scope out and finds the detached node on the release list, so the pattern is shown to be necessary and not decoration.
- **The in-cage corruption fuzzer** writes arbitrary words into the cage between operations and checks that nothing faults outside the cage.

## The CS-D3 re-run

The coding standard's five criteria for `TokenCell` (CS-D3) are re-run against this API in their own PR, with the compile-fail tests. That PR also settles Q-JS-10: whether `ScriptToken` stays separate from `Mutator`.
