# M1 D4 macOS IPC: Mach facts

Compiled 2026-10-25 on macOS 27.0.1 (build 26A434), Apple silicon. Primary sources were preferred: Apple Developer Documentation pages (read through their published JSON form), the Kernel Programming Guide "Mach Overview" chapter, Apple technotes, Apple man pages installed on this Mac or in the Xcode SDK's `usr/share/man` (man pages only, no `usr/include`), and the OSF/Apple *Mach Kernel Interface* reference pages (HTML man pages hosted by MIT). Secondary sources were Apple Developer Forums answers by Apple DTS engineers, one peer-reviewed paper and two prose security write-ups.

Confidence: **High** = I read and checked the primary Apple document, and it is current. **Medium** = a primary document that is old or only a snippet (for example the OSF Mach reference, which predates XNU's changes), or a reputable secondary source such as an Apple DTS forum answer. **Low** = a community or secondary source, or memory, with nothing primary behind it. Anything at Low that the design depends on appears again in the Probe list.

## 1. Sender identity per message

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | "The message carries with it the security ID of the sender, which the receiver can request in the message trailer." The receiver picks the trailer format and the number of leading elements with `MACH_RCV_TRAILER_TYPE(...)` / `MACH_RCV_TRAILER_ELEMENTS(...)`. To get element *n* it must accept elements 1…n−1. The trailer sits after the body at the next natural boundary, and its length is in `msgh_trailer_size`, not `msgh_size`. | Only `MACH_MSG_TRAILER_FORMAT_0` exists. An unsupported request returns `MACH_RCV_INVALID_TRAILER`. | OSF `mach_msg` man page | 1990s (OSF), Apple-hosted | Medium |
| 1.2 | Apple's kernel reference lists `mach_msg_audit_trailer_t` (macOS 10.3+), `mach_msg_security_trailer_t`, `mach_msg_mac_trailer_t`, `mach_msg_max_trailer_t` (= mac trailer) and `audit_token_t` (10.3+). The pages give no fields. | none | developer.apple.com/documentation/kernel/mach_msg_audit_trailer_t, …/audit_token_t | current (pages say "current 15.4") | High (existence only) |
| 1.3 | KPG: a message may contain "kernel implicit attributes, such as the sender's security token". | none | Kernel Programming Guide, Mach Overview | updated 2013-08-08 | Medium |
| 1.4 | Unforgeability: the kernel fills in the trailer itself. `MACH_SEND_TRAILER` (a sender-supplied trailer) is accepted only from "tasks with a security ID of KERNEL_SECURITY_ID". | 1.5 | Apple DTS (Quinn, accepted answer) recommends exactly our pattern. Spawn the child with `POSIX_SPAWN_START_SUSPENDED` so "the PID you get back can't be reused and … it can't have done any IPC yet". Get its audit token with `task_name_for_pid` and `task_info(TASK_AUDIT_TOKEN)`. "You can then compare that to the audit token you get from the Mach message trailer." | 1.6 | "The canonical identifier for this sort of comparison is the audit token." "Protecting against PID reuse is one of the primary reasons that audit tokens exist." The supported pattern is to "retrieve the audit token of some existing object/connection (like a Mach port or an XPC connection)". | none | Forums 842442, 850777, 824760 (DTS: Quinn, Kevin Elliott) | Apr–Oct 2026 | Medium |
| 1.7 | The audit token holds audit UID, effective and real UID/GID, PID, audit session ID and a **PID version** "used for when the PID wraps around". | 1.8 | The pidversion is bumped on `execve`. A 2019 advisory (macOS < 10.14.4) showed the increment let two processes share (pid, pidversion). The bug was fixed. | PIDs wrap at about 100 000 (secondary). | exploit-db 46648 (Jann Horn advisory), via search summary only | 2019 | Low (probe P3) |
| 1.9 | The `es_process_t` doc says you extract PID/UID/GID "from the `audit_token` field by using functions defined in `libbsm.h`". | 1.10 | The kernel stamps each received message with the port's sequence number (`MACH_RCV_TRAILER_SEQNO`). The number is reset when the receive right moves. | none | OSF `mach_msg` | 1990s | Medium |

**Implications:** Per-message, kernel-attested sender identity exists. The receive call must request the audit trailer on every receive (FORMAT_0, elements up to AUDIT). The IO thread compares the token's (pid, pidversion) with the token it recorded for the peer at spawn: from a suspended spawn, or from the first message on the bootstrap channel. A violation is attributed to the trailer token, never to anything in the payload. Struct layout, the trailer element count for "audit", and the pid/pidversion accessors are not in prose docs, so P1–P4 must settle them. Notifications the kernel sends carry a kernel token (P4), and the IO thread must check this so a peer cannot pose as a kernel notification.

## 2. Who created or holds the receive right

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Ports have no system-wide names. Only one task holds a port's receive right, and the receive right can be moved by message. Nothing in the docs gives a send-right holder a query for "which task holds the receive right" or "which task created this port". | none | KPG Mach Overview; OSF `mach_msg` | 2013 / 1990s | High (absence in docs read) |
| 2.2 | `mach_port_get_attributes` / `MACH_PORT_RECEIVE_STATUS` need the **receive** right (`KERN_INVALID_RIGHT` otherwise), so a send-right holder cannot use them. | none | OSF `mach_port_get_attributes` | 1990s | Medium |
| 2.3 | `mach_port_kobject` (10.6+) and `mach_port_kobject_description` (10.15.4+) exist, with only signatures documented. They describe **kernel** objects and have no stated meaning for user-owned ports. | none | developer.apple.com kernel/1578702, /3516847 | current | High (existence) / probe P8 |
| 2.4 | A peer can relay rights it received. When a receive right moves, its make-send count and seqno reset and no-senders requests are cancelled, but "send rights for the port remain unchanged and continue to function". | none | OSF `mach_msg`, `mach_port_request_notification` | 1990s | Medium |

**Implications:** **No documented way exists.** "Bound sender sent only by its creator" therefore cannot be checked as a property of the port. It has to be checked as a property of the **message that carries it**: accept a bound-sender handle only when that message's audit-trailer token equals the token of the process that created the channel. The receiving side already knows that token, because it was told the creator's identity when the channel was announced, or because it *is* the broker that issued the channel. An optional stronger check is to send a challenge over the received send right with a send-once reply right. The reply's trailer token identifies the process that dequeued it, which is the receive-right holder unless that holder forwarded the send-once right. P6 checks that nothing better exists.

## 3. Classifying a received right

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | `mach_port_type(task, name, &ptype)` returns a bitmask of the rights held under that name: `…_SEND`, `…_RECEIVE`, `…_SEND_ONCE`, `…_PORT_SET`, `…_DEAD_NAME` and `…_DNREQUEST`. It returns `KERN_INVALID_NAME` if the name denotes nothing. It does **not** say what object the port represents. | Bit values are not in prose (P7). | OSF `mach_port_type`; Apple kernel/1578714 (signature) | 1990s / current | Medium |
| 3.2 | Receiving a send right for a port the task already holds **reuses the existing name** and adds a user reference. A receive right arriving where send rights exist joins the same name. Each send-once right gets its own name. | none | OSF `mach_msg` (MACH_MSG_TYPE_PORT_SEND/RECEIVE) | 1990s | Medium |
| 3.3 | A port in transit can die. The receiver then gets `MACH_PORT_DEAD` in place of the right, and `MACH_PORT_NULL` if a resource shortage stopped the right from being received. "A task never receives port rights or memory for which it is not told." | none | OSF `mach_msg` | 1990s | Medium |
| 3.4 | The kernel is the receiver for kernel-object ports. Task, thread and host ports are "control" or "name" ports. A send right to a task control port gives control of that task, and send rights to a thread port "give you complete register control". | none | KPG Mach Overview; Project Zero "task_t considered harmful" | 2013; Oct 2016 | Medium |
| 3.5 | Apple (2026): "An attacker who gains access to a Mach port for your app … potentially gains a lot of privileges". With `com.apple.security.hardened-process.platform-restrictions` ≥ 1, the system raises `EXC_GUARD` / `GUARD_TYPE_MACH_PORT` for these: **ILLEGAL_MOVE** (moving a send right to its own task or thread control port to another process, which "gives the receiving process complete control over your process"), **OOL_PORT_ARRAY** ("insecure descriptor layout … change your MIG interface so that it doesn't send arrays of Mach ports"), **REQUIRE_REPLY_PORT_SEMANTICS** (launchd-service messaging), **KOBJECT_REPLY_PORT_SEMANTICS** (kernel messaging), **THREAD_SET_STATE** and **SET_EXCEPTION_BEHAVIOR**. The entitlement also makes "additional checks … on Mach messages your app or extension receives from other processes". | Entitlement value "2". macOS 26.4+. | developer.apple.com/documentation/xcode/conforming-to-mach-ipc-security-restrictions; …/enabling-enhanced-security-for-your-app; …/com.apple.security.hardened-process.platform-restrictions-string | 2026 (current) | High |
| 3.6 | Integrity warning for OOL memory: "Integrity-conscious receivers should exercise caution when dealing with out-of-line memory from un-trustworthy sources", because a virtual copy may involve the sender's memory manager. | none | OSF `mach_msg` | 1990s | Medium |

**Implications:**
- **Receive rights verify themselves.** A receive right cannot be a kernel object, since the kernel keeps those. If `mach_port_type` reports RECEIVE (and not PORT_SET) and `mach_port_get_attributes(MACH_PORT_RECEIVE_STATUS)` succeeds, it is a plain IPC queue.
- **Send rights need `mach_port_kobject[_description]`** to reject task, thread, host, memory-entry and IOKit ports. Only the signatures are documented, so P8 must show it works on a release kernel and inside the child sandbox, and what it returns for a plain port. Fallback if it is unusable: carry only *receive* rights across processes and mint send rights locally (`MAKE_SEND`). Any handle that arrives as a raw send right is then treated as untrusted and validated by a challenge (§2).
- **Alias dedupe (3.2):** two handle slots in one message can resolve to the same name. The decoder must detect this and treat it as a protocol violation.
- **Never use OOL port arrays.** Up to 16 individual port descriptors are fine, and the arrays would crash under platform restrictions.

## 4. Message format

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | A message is a fixed header, then an optional body (`MACH_MSGH_BITS_COMPLEX`) holding a descriptor count and descriptors (port, OOL memory, OOL ports), then inline data, then the kernel-appended trailer. In a received message the header's destination and reply are reversed. | Struct sizes are not in prose (P11). | OSF `mach_msg`, `mach_msg_descriptor`, `mach_msg_header` | 1990s | Medium |
| 4.2 | Send dispositions: `MAKE_SEND` (from a receive right; increments make-send count), `COPY_SEND` (no uref change), `MOVE_SEND` (decrements urefs), `MAKE_SEND_ONCE` (only from a receive right), `MOVE_SEND_ONCE`, and `MOVE_RECEIVE` (resets mscount and seqno, cancels no-senders with a send-once notification, keeps queued messages). Received values are `PORT_SEND`, `PORT_SEND_ONCE` and `PORT_RECEIVE`. `MACH_PORT_NULL`/`DEAD` are valid in descriptors. | Numeric values: P12. | OSF `mach_msg` | 1990s | Medium |
| 4.3 | Header rights are processed atomically. Body rights and OOL memory are not: "front-to-back, back-to-front, in some random order". | none | OSF `mach_msg` | 1990s | Medium |
| 4.4 | OOL memory: a logical copy, possibly copy-on-write. `deallocate` turns the copy into a move. `VIRTUAL_COPY` and `PHYSICAL_COPY` are available ("a (fairly large) limit" on physical copy). The receiver must `vm_deallocate` the region. "Regions of memory up to 4 gigabytes". | 4 GB | OSF `mach_msg` | 1990s | Medium |
| 4.5 | The maximum inline message size is **not stated** in any prose I found. | none | none | n/a | none (P13) |
| 4.6 | Receive: a message larger than `receive_limit` is **dequeued and destroyed** unless `MACH_RCV_LARGE`. With it, the message stays queued and `MACH_RCV_TOO_LARGE` reports the size. The receive buffer must also hold the trailer. | none | OSF `mach_msg` | 1990s | Medium |
| 4.7 | Received rights and memory "should be consumed or de-allocated in some fashion". A resource shortage destroys the affected rights (`MACH_RCV_HEADER_ERROR`/`BODY_ERROR` with `MACH_MSG_IPC_SPACE`/`VM_SPACE` bits). | none | OSF `mach_msg` | 1990s | Medium |
| 4.8 | `mach_msg_destroy` (user-space) has **no** Apple documentation page. Only `mach_msg_destroy_from_kernel_proper` is listed. | none | developer.apple.com kernel/mach index | current | High (absence) |
| 4.9 | A failed send with `MACH_SEND_TIMED_OUT`/`INTERRUPTED` triggers a "pseudo-receive" that returns rights and OOL memory to the sender. Names and OOL addresses may change. Errors such as `MACH_SEND_INVALID_RIGHT`/`MEMORY`/`TYPE` mean "some or all of the message was destroyed". | none | OSF `mach_msg` | 1990s | Medium |
| 4.10 | KPG says "the mach_ipc calls are preferred … The mach_msg calls are supported for legacy code but deprecated". The `mach_ipc` family never shipped. This is aspirational text from 2002–2013, but Apple's prose does say it. | none | KPG Mach Overview | 2013 | Medium (doc quirk) |

**Implications:**
- **Carrying 64 KiB:** prefer inline if P13 shows the limit is comfortably above 64 KiB + header + 16 descriptors + trailer. Inline avoids a new VM mapping per message and the OOL integrity caveat (3.6), and keeps a single buffer for the receive. P14 measures the cost.
- **Rejected messages:** release every right, using `mach_port_deallocate` for send and send-once rights and `mach_port_mod_refs(RECEIVE, −1)` for receive rights, and `vm_deallocate` any OOL. Do this in our own code; do not rely on the undocumented `mach_msg_destroy`. P22 confirms nothing leaks.
- **Outbox replay:** after `MACH_SEND_TIMED_OUT`, re-read the descriptor names (4.9) before re-queuing.

## 5. Queue semantics and notifications

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | A new port's queue limit is `MACH_PORT_QLIMIT_DEFAULT`. The limit is read and set with `mach_port_get/set_attributes(MACH_PORT_LIMITS_INFO)` (`mach_port_limits.queue_limit`) by the receive-right holder, and `MACH_PORT_RECEIVE_STATUS` reports qlimit, msgcount, mscount, srights, seqno and sorights. | Default and maximum values are not in prose (P16). | OSF `mach_port_allocate`, `mach_port_limits`, `mach_port_status` | 1990s | Medium |
| 5.2 | Full queue: send-once destinations ignore the limit. Other senders **block** "unless the MACH_SEND_TIMEOUT option is used". "A zero timeout is legitimate." The result is `MACH_SEND_TIMED_OUT`, with the message returned by pseudo-receive. | none | OSF `mach_msg` | 1990s | Medium |
| 5.3 | Delivery is reliable and in order **per sending task** ("or a single kernel"). Messages to send-once rights are unordered. | none | OSF `mach_msg` | 1990s | Medium |
| 5.4 | Notifications are requested with `mach_port_request_notification` (an atomic swap, previous right returned, sent to a send-once right): `PORT_DESTROYED`, `DEAD_NAME` (bumps the dead name's urefs; becomes port-deleted if the name is freed), `NO_SENDERS` (needs the receive right; `sync` = make-send-count threshold, fires immediately if already satisfied; carries mscount). Send-once rights guarantee "either a message … or … a send-once notification". | none | OSF `mach_port_request_notification`, `do_mach_notify_*` | 1990s | Medium |
| 5.5 | The OSF page says ports from `mach_port_allocate` refuse no-senders requests and to use `mach_port_allocate_full`. Modern Apple practice contradicts this, so treat it as unverified. | none | OSF `mach_port_allocate` | 1990s | Low (P20) |
| 5.6 | `mach_send_possible_notification_t` exists (macOS 10.7+). **No prose** describes when it fires, whether it is one-shot, or how it interacts with qlimit. | none | developer.apple.com kernel/mach_send_possible_notification_t | current | High (existence only) |
| 5.7 | `mach_port_peek` (10.9+) and `mach_port_construct` with `mach_port_options_t` (10.9+), `mach_port_guard`/`unguard`/`swap_guard` (10.9/10.15) and `mach_msg_guarded_port_descriptor_t` (10.15) exist, with signatures only. | none | developer.apple.com kernel/mach | current | High (existence) |

**Implications:**
- **Credit-counted capacity stays ours.** Set each channel port's qlimit to the documented-settable maximum (P16) so that kernel-queue-full is rare. Always send with `MACH_SEND_TIMEOUT` and timeout 0, so `send` never blocks (P17). Push `MACH_SEND_TIMED_OUT` messages to the outbox.
- **Flushing the outbox without polling** needs `MACH_NOTIFY_SEND_POSSIBLE` delivered to a port in the IO thread's port set. Its semantics are undocumented, so P19 must establish them. Fallback: a credit-return message from the receiver. The receiver already acks credits, and the flush can trigger on those acks.
- **Notification ports never get send rights handed out.** Combined with the trailer check (P4), this stops forged notifications.

## 6. Waiting

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | A receive on a port set takes a message from any member. The set may be empty, and "ports may be added and removed while a receive from the port set is in progress". `msgh_local_port` says which member it came from. A port may be in at most one set, and members cannot be received from directly (`MACH_RCV_IN_SET`). | none | OSF `mach_msg`; KPG "Port sets permit one thread to wait on a number of message and event sources" | 1990s / 2013 | Medium–High |
| 6.2 | With no `MACH_RCV_TIMEOUT` the receive blocks indefinitely ("MACH_MSG_TIMEOUT_NONE"). Without `MACH_RCV_INTERRUPT`, interrupted calls are retried automatically. | none | OSF `mach_msg` | 1990s | Medium |
| 6.3 | Port-set names cannot be sent in messages. | none | OSF `mach_msg` | 1990s | Medium |

**Implications:** Use one IO thread per process: `mach_msg(MACH_RCV_MSG | trailer opts, no timeout)` on a single port set that holds every channel receive port, the notification port and a dedicated **wake port**. Other threads (or `send` handing work to the outbox) wake it by sending a zero-body message to the wake port with timeout 0. The wake port's qlimit is 1, and `MACH_SEND_TIMED_OUT` there means "already pending", which coalesces wakes. Zero idle wakeups need confirming (P23).

## 7. Closed detection

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | Last send right gone, so the receiver learns: a no-senders notification (requested on the receive right) carries the mscount at generation time. A send right inside an in-flight message is still extant. | none | OSF `mach_port_request_notification`, `do_mach_notify_no_senders` | 1990s | Medium |
| 7.2 | Receive right destroyed, so senders learn: send and send-once rights "turn into dead names", queued messages are destroyed (releasing their rights and OOL), and registered dead-name requests fire. Sending to it gives `MACH_SEND_INVALID_DEST` ("msgh_remote_port value was invalid"). | none | OSF `mach_msg`, `mach_port_destroy` | 1990s | Medium |
| 7.3 | `MACH_RCV_PORT_DIED`: the caller lost the receive right during the receive. | none | OSF `mach_msg` | 1990s | Medium |
| 7.4 | No prose says how a kernel-generated no-senders notification is **ordered** relative to data messages already queued on the channel port. The ordering guarantee is only per sender (5.3). | none | none | n/a | none (P20) |

**Implications:**
- **Closed on the receiver side:** the no-senders notification comes from the kernel (checked by trailer token) for the channel's receive port. Send it to the notify port in the same port set, and deliver `Closed` only after the channel port has been drained. To be safe without depending on P20's answer, on no-senders do a non-blocking drain of the channel port (pull it out of the set, `MACH_RCV_TIMEOUT` 0 until empty), then report `Closed`. P20 checks whether that is even necessary.
- **Closed on the sender side:** a send that returns `MACH_SEND_INVALID_DEST` (or a dead-name notification) means the peer is gone. Report `Closed` to the sender and drop the outbox.
- **No-senders sync argument:** use the make-send-count threshold so a request made after rights were handed out cannot fire early.

## 8. Bootstrap without lookups

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | `posix_spawnattr_setspecialport_np(attr, port, which)` sets a special port in the child "as if the new process had called task_set_special_port()". This is documented and current. `posix_spawnattr_setexceptionports_np` is its exception-port counterpart. | Errors: EINVAL, ENOMEM. | `man posix_spawnattr_setspecialport_np` (SDK) | 2007 page, ships in SDK 27 | High |
| 8.2 | Task special ports include `TASK_BOOTSTRAP_PORT` ("used to send messages requesting return of other system service ports") and `TASK_KERNEL_PORT`. A child reads its own with `task_get_special_port`/`task_get_bootstrap_port`. "All processes inherit a reference to the bootstrap service from their parent." | none | OSF `task_get/set_special_port`; TN2083 | 1990s; TN2083 no longer updated | Medium |
| 8.3 | `mach_ports_register`/`mach_ports_lookup`: up to `MACH_PORTS_SLOTS_USED` registered send rights, inherited by children of `task_create`. The OSF page says these are "intended … only for task initialization … by run-time support modules". Nothing in Apple prose says whether they survive `posix_spawn` or whether current macOS restricts them. | none | OSF `mach_ports_register` | 1990s | Low (P28) |
| 8.4 | `bootstrap_check_in` returns a receive right only for a service named in the job's `launchd.plist` `MachServices` (`BOOTSTRAP_UNKNOWN_SERVICE` otherwise). Apple documents no dynamic registration. Deactivated namespaces refuse registration with `BOOTSTRAP_NOT_PRIVILEGED` (1100). | 1100 | `man bootstrap_check_in` (launch(3)), 2014; TN2083 | 2014 | High |
| 8.5 | `POSIX_SPAWN_START_SUSPENDED` creates the child "as if it immediately received a SIGSTOP". | none | `man posix_spawnattr_setflags` | current SDK | High |
| 8.6 | Apple and TN2083 consistently advise against raw Mach ("Apple has consistently recommended that third party developers avoid them"). | none | TN2083; Forums 845644 | 2007–2026 | High |

**Implications:**
- **The documented, lookup-free route** is `posix_spawnattr_setspecialport_np(TASK_BOOTSTRAP_PORT)`, which gives the child a send right to a broker port as its bootstrap port, combined with `POSIX_SPAWN_START_SUSPENDED` to record the child's audit token. The child's first act is to read `task_get_bootstrap_port` and send its hello (carrying a reply receive right) to the broker.
- **Catch:** the child's libSystem may send its own bootstrap traffic (logging, notifyd and so on) to that port. The broker must refuse it, and the child must tolerate the refusals. P27 observes which messages arrive.
- **A launchd-looked-up broker service** would need a `MachServices` plist entry: a LaunchAgent or an embedded XPC service. That is a packaging decision, not something the transport can do alone.
- **Hiding launchd from the child:** if we replace the bootstrap port, the child has no launchd connection at all. That is stronger than "no lookups except the broker's", and it makes `mach-lookup` irrelevant.

## Probe list

Black-box tests to run on this Mac (macOS 27.0.1, Apple silicon). Each fact the design needs but the prose does not settle. Constant **values** cannot come from headers under M-1, so each value is found by behaviour or by a documented query, noted per item.

1. **P1 Audit trailer layout.** Receive with trailer type FORMAT_0 and increasing element counts 0…N. Record `msgh_trailer_size` at each step, and find the count at which the size stops growing or `MACH_RCV_INVALID_TRAILER` appears; that maximum is the audit/mac trailer. In the trailer bytes, find the words equal to the sender's `getpid()`, `geteuid()` and `getuid()` (from a known sender), and compare with `task_info(TASK_AUDIT_TOKEN)` of the sender. This gives the offsets of pid and pidversion, and whether libbsm `audit_token_to_pid`/`…pidversion` agree.
2. **P2 Trailer forgery.** An unprivileged sender sets the send-trailer option bit (found by scanning option bits on a test port) with a fabricated trailer, then separately appends fake trailer bytes beyond `send_size`. Expect `MACH_SEND_INVALID_TRAILER` or the bytes ignored. The receiver must see the kernel's token.
3. **P3 pidversion behaviour.** (a) Record the token, `exec` the same binary (`POSIX_SPAWN_SETEXEC`), record again: does pidversion change? (b) Spawn and reap children in a loop until a pid repeats (or across a long run), and check that (pid, pidversion) never repeats.
4. **P4 Kernel-originated messages.** Receive a no-senders and a dead-name notification with the audit trailer, and record the token (expect pid 0). Confirm a peer holding a send right to a test port cannot make a message carrying that token.
5. **P5 Port-set trailers.** Messages received through a port set carry the correct per-member seqno and sender token.
6. **P6 Receive-holder discovery.** For a plain port whose receive right is held by process B, call `mach_port_kobject`, `mach_port_kobject_description`, `mach_port_type` and `mach_port_get_attributes` from A, which holds a send right. Confirm none of them reveals B. Run the challenge/reply pattern from §2 and check that the reply trailer identifies B.
7. **P7 Right-type bit values.** Create one name of each kind (receive, send, send+receive, send-once, port set, dead name, plus a dead-name request), call `mach_port_type` and tabulate the bitmasks.
8. **P8 Kernel-object classification.** Call `mach_port_kobject` and `mach_port_kobject_description` on: our task self port, task name and inspect ports, a thread port, host port, a memory-entry port, a semaphore, an IOKit connection, a plain port, a dead name, and a task port received from another process. Record return codes, type numbers and description strings, and repeat inside the deny-default child sandbox. The question is whether a plain port returns a distinguishable "none".
9. **P9 Receiving task and thread ports.** Peer sends `COPY_SEND` of its `mach_task_self()`, its task name port and a thread port. Observe sender-side failures or `EXC_GUARD` ILLEGAL_MOVE (with and without the hardened-process entitlement), and what the receiver gets.
10. **P10 Receive-right verification.** A received `MOVE_RECEIVE` right: `mach_port_get_attributes(RECEIVE_STATUS)` succeeds. Check the qlimit, mscount and seqno resets claimed in 4.2. Check whether `mach_port_construct` options can mark our receive rights immovable or guarded, and how a guarded right behaves when moved.
11. **P11 Struct sizes on arm64.** Send messages with 0…16 port descriptors and 0…2 OOL descriptors, and observe the received `msgh_size` and inline-data offset. This derives the header, body, port-descriptor and OOL-descriptor sizes as received by a 64-bit task, and whether sent and received descriptor sizes differ.
12. **P12 Disposition and option values.** Find the numeric values of `MAKE_SEND`, `COPY_SEND`, `MOVE_SEND`, `MAKE_SEND_ONCE`, `MOVE_SEND_ONCE` and `MOVE_RECEIVE`. Do it by sending each candidate value with a receive right or send right and checking with `mach_port_type` and urefs (`mach_port_get_refs`) what the receiver got and what the sender lost. Map the `mach_msg` option bits (SEND, RCV, SEND_TIMEOUT, RCV_TIMEOUT, RCV_LARGE, trailer encodings) and return codes the same way. If any value cannot be pinned black-box, record it as a decision for the lead.
13. **P13 Maximum inline size.** Binary-search `send_size` of a simple message until the send fails, and record the error code. Repeat with 16 port descriptors. Confirm that a 64 KiB payload with 16 descriptors fits.
14. **P14 Inline vs OOL at 64 KiB.** Round-trip latency and CPU for 1 KiB, 16 KiB and 64 KiB inline against OOL (`VIRTUAL_COPY`, `PHYSICAL_COPY`, `deallocate`), including the receiver's `vm_deallocate`. Use `rig check local --kind exclusive`.
15. **P15 OOL time-of-check/time-of-use.** After the send returns, the sender writes to its OOL source pages. Does the receiver ever see the change, before or after reading? Also: does the receiver's mapping arrive writable?
16. **P16 Queue limits.** `mach_port_get_attributes(LIMITS_INFO)` on a fresh port gives the default qlimit. Raise `mach_port_set_attributes(LIMITS_INFO)` until it errors to find the maximum. Check whether qlimit 0 is allowed, and whether there is a per-port byte limit (fill with 64 KiB messages).
17. **P17 Non-blocking send on a full queue.** With `MACH_SEND_TIMEOUT`=0 on a full port: record the return code and latency distribution (never blocks?). Confirm that descriptor names and OOL are restored by pseudo-receive and that resending works. Repeat with a receive right inside the message, and under signal storms without `MACH_SEND_INTERRUPT`.
18. **P18 Send-once and queue limits.** A send-once right ignores qlimit (5.2). Confirm, and measure how many messages the kernel queues past qlimit this way. This bounds memory a peer can force through notifications.
19. **P19 Send-possible.** Register `MACH_NOTIFY_SEND_POSSIBLE` (msgid found by behaviour or the documented struct's msgh_id at receipt) on a send right to a full port. Does it fire when the receiver dequeues one message? Is it one-shot? Does it fire immediately if the queue is not full? What happens when the port dies (dead-name instead?), and what does `sync` do?
20. **P20 No-senders behaviour.** (a) Do ports from `mach_port_allocate` accept a no-senders request (5.5)? (b) Ordering: the sender sends N messages, then deallocates its only send right. With the notification aimed at a separate port in the same set, does the IO thread ever see no-senders before all N data messages? Run 10⁶ trials. (c) A send right in flight blocks the notification until it is received or destroyed. (d) The `sync` and mscount race.
21. **P21 Dead destination.** The receiver destroys its receive right while messages carrying rights and OOL are queued. Record the sender's exact error on the next send, the dead-name notification, and the release of rights inside the destroyed messages (cascading no-senders on those ports).
22. **P22 Rejected-message cleanup.** Receive messages with every right kind and OOL, release them with manual deallocation, and compare `mach_port_names` counts and VM usage before and after. Check whether `mach_msg_destroy` is equivalent.
23. **P23 Idle wakeups.** An IO thread blocked in `mach_msg` with no timeout on a port set holding 1 000 idle channels, the notify port and the wake port: 0 wakeups/s over 10 min (`top -stats pid,idlew`, powermetrics). Wake-port coalescing with qlimit 1. Adding and removing members while blocked.
24. **P24 Oversized receive.** Without `MACH_RCV_LARGE`, confirm that an oversize message's rights are destroyed (and that the peer sees no-senders or dead name). With it, the message stays queued and the size is reported.
25. **P25 Deny-default sandbox and Mach.** Apply a `(version 1)(deny default)` profile with no `mach-*` allows, applied after the IO thread is set up, and with the bootstrap port replaced. Test `mach_port_allocate`/`construct`, `mach_msg` send and receive on held rights, port sets, `request_notification`, `get/set_attributes`, `mach_port_kobject`, `task_get_bootstrap_port`, `mach_make_memory_entry_64`, `mach_vm_map` and audit trailers. Compile-test which operation names exist on macOS 27 (`mach-lookup`, `mach-register`, `mach-bootstrap`, `mach-per-user-lookup`, `mach-priv-host-port`, `mach-priv-task-port`, `mach-task-name`, `mach-kernel-endpoint`, `syscall-mach`, `syscall-mig`, and any `mach-task-special-port-*`) by checking whether the profile compiles, and which ones a deny-default profile denies. Log the deny reports.
26. **P26 Sandbox entry under SDK 27.** Built against SDK 27, does `sandbox_init(custom_profile_string, 0, &err)` still work, fail, or kill the process (9.2)? Is there an SDK-27-safe documented path?
27. **P27 Bootstrap replacement.** Spawn a child with `posix_spawnattr_setspecialport_np(TASK_BOOTSTRAP_PORT = broker port)` and `START_SUSPENDED`. Log every msgh_id and size the broker port receives during child startup (libSystem, os_log, notifyd and so on). Check whether the child runs normally when the broker refuses them or does not reply, and whether `task_get_bootstrap_port` in the child returns the broker port. Compare the child's audit token from `task_name_for_pid` with its first message's trailer.
28. **P28 mach_ports_register.** Is it permitted on macOS 27 (return code)? Do registered ports survive `posix_spawn` and `exec`? Also check which other `which` values `posix_spawnattr_setspecialport_np` accepts.
29. **P29 Dynamic registration.** From an unprivileged process: does `bootstrap_check_in` with an unlisted name, or a legacy register call, fail? Record the codes. Check whether a LaunchAgent `MachServices` entry or an embedded XPC service lets the broker be looked up by name.
30. **P30 Platform restrictions.** Sign the broker and child with `hardened-process` + `platform-restrictions-string` "2" + `enhanced-security-version-string`. Run the whole channel suite: one-way messages without a reply port, 16 port descriptors, receive-right moves, OOL data, memory entries, and send-possible and no-senders notifications. Confirm there is no `EXC_GUARD`. Confirm OOL port arrays do trigger `OOL_PORT_ARRAY`.
31. **P31 Received-message checks under the entitlement.** With the entitlement on the receiver, send it messages from an un-entitled peer that carry odd dispositions (send-once reply, dead names, `MACH_PORT_NULL` descriptors). Record which messages the system rejects or turns into crashes, so a hostile peer cannot crash the broker on purpose.
32. **P32 Alias and uref limits.** One message carries the same send right in 16 descriptors: the receiver gets one name with urefs +16 (3.2). Find the uref overflow point (`KERN_UREFS_OVERFLOW`) and what the receiver gets then.
33. **P33 Read-only memory entry.** Create an entry with READ only and send it. The receiver tries `mach_vm_map` with cur and max READ|WRITE, then READ, and calls `mach_vm_region` to read `max_protection`. The creator writes after mapping: is the change visible (shared, not copy-on-write)? Can the receiver make a writable child entry from it (`parent_entry`)?
34. **P34 Name-space exhaustion.** A peer floods rights (16 per message at qlimit max). Record when the receiver hits `MACH_RCV_*_ERROR | MACH_MSG_IPC_SPACE` and the per-task port-name limit, so the per-process handle cap can be sized.
35. **P35 Token after sender exit.** The sender queues a message and exits before the receiver dequeues it. The trailer still carries the sender's original (pid, pidversion), and a new process reusing the pid gets a different pidversion.
36. **P36 Send-once replies for challenges.** `MAKE_SEND_ONCE` reply right in a challenge. If the peer destroys it, the challenger gets a send-once notification (5.4) carrying the kernel token. If the peer forwards it, the reply's token is the forwardee's.
37. **P37 Receive-right move semantics.** Moving a channel's receive end to another process cancels its no-senders request with a send-once notification (4.2). The new owner must re-arm, and the move must not lose queued messages.
38. **P38 Wake-port send under contention.** Many threads send to the wake port with timeout 0 while the IO thread is blocked. Check that no sender ever blocks and that exactly one wake is observed per drain.

**Count: 38 probe items.**

### Unresolved or not run

- `mach_port_construct` option flag values (immovable receive rights, P10): no permitted source; only all-zero options tested.
- Discoverability of a name claimed with `bootstrap_check_in` (P29) and LaunchAgent/XPC-service bootstrap: no documented lookup signature; installing a launchd job was out of scope.
- `mach_msg_destroy` equivalence (P22): undocumented.
- libbsm `audit_token_to_pid/pidversion` (P1): no documented signature; offsets come from `task_info` equality and exec behaviour instead.
- Physical vs virtual copy option *names* (P14): inferred from cost only.
- Exact uniqueness of (pid, pidversion) across a pid wrap (P3b, P35): would need ~10⁵ spawns.
- 10⁶ ordering trials (P20b: 1 800 run), 10-minute idle and powermetrics (P23: ~1 min, top only), name-space ceiling above 250 000 (P34), uref behaviour beyond saturation in the *receiver* of a hostile peer (P32: same-process only).
- All timings (P14, P17, P38) were taken beside another session's heavy job; an exclusive window is needed before relying on them.
