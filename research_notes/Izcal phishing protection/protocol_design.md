## 1. Google Safe Browsing v5: local-list mode

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **v5 local-list mode keeps the threat list on the device.** The client maintains a local database of SHA-256 hash prefixes of host-suffix/path-prefix URL expressions and checks every URL locally; it contacts the server "if and only if there is a match". A separate local cache, which need not be persistent, holds full hashes returned by the server. This is the v4 Update API's shape with the v5 API surface. | Local list; server contacted only on a local match | [Local List Mode](https://developers.google.com/safe-browsing/reference/Local.List.Mode) | 2025-12-10 | High |
| 1.2 | **The local check procedure.** Generate the URL's expressions; SHA-256 each; take the first 4 bytes; consult the cache (expired entries removed; a cached match compares the full hash and returns `UNSAFE`); look each surviving prefix up in the local database and drop misses; send the survivors to `SearchHashes`/`hashes.search`; cache returned full hashes with the server's expiry; return `UNSAFE` if a returned full hash equals one of the URL's full hashes, else `SAFE`. **Any error, including network or HTTP failure, returns `SAFE`.** | 4-byte prefixes; fail-open on error | [Local List Mode](https://developers.google.com/safe-browsing/reference/Local.List.Mode) | 2025-12-10 | High |
| 1.3 | **Expression generation is bounded and scheme-blind.** The client forms up to **30** host-suffix/path-prefix combinations using only host and path; scheme, username, password and port are discarded. Host: at most **5** strings, the eTLD+1 from the Public Suffix List plus successive leading components, and the exact host. Path: at most **6** strings, the exact path with query, the exact path without query, and four prefixes built from `/` by appending components with trailing slashes. At least one combination includes the full path and query. For `a.b.com/1/2.html?param=1`, `a.b.com` is checked for `/1/2.html?param=1`, `/1/2.html`, `/1/` and `/`, and `b.com` for the same four. | ≤30 expressions; 5 host strings; 6 path strings | [URLs and Hashing](https://developers.google.com/safe-browsing/reference/URLs.and.Hashing) | 2025-05-23 | High |
| 1.4 | **v5 lists carry one hash length each: 4, 8, 16 or 32 bytes.** The length is encoded in the list name (`se-4b`, `gc-32b`); "all hashes in a list now have a single length" and additions are uniform. Only the network search method is fixed at 4 bytes: "Currently each hash prefix is required to be exactly 4 bytes long", because "sending additional bytes in this request will compromise user privacy." | 4/8/16/32-byte lists; 4-byte search | [URLs and Hashing](https://developers.google.com/safe-browsing/reference/URLs.and.Hashing); [v5 RPC reference](https://developers.google.com/safe-browsing/reference/rpc/google.security.safebrowsing.v5); [Local Database](https://developers.google.com/safe-browsing/reference/Local.Database) | 2025-05-23 / read 2026-10-21 | High |
| 1.5 | **Updates are versioned whole-list deltas.** `GetHashList`/`BatchGetHashLists` return a `HashList` with an opaque `version` ("The client MUST NOT manipulate those bytes"; empty on first request), `partial_update`, `compressed_removals`, `compressed_additions`, `sha256_checksum`, `minimum_wait_duration` and metadata. List names are stable and "will never be renamed"; obsolete lists become empty but continue to exist. | Opaque version; stable names | [v5 RPC reference](https://developers.google.com/safe-browsing/reference/rpc/google.security.safebrowsing.v5); [Local Database](https://developers.google.com/safe-browsing/reference/Local.Database) | read 2026-10-21 | High |
| 1.6 | **Removals are indices; additions are values.** `compressed_removals` is a `RiceDeltaEncoded32Bit` of removal indices into the sorted list; `compressed_additions` is exactly one of 4-, 8-, 16- or 32-byte Rice-encoded addition sets. `partial_update=true` means "apply an incremental update by applying removals and then additions"; `false` means delete the local copy and take the response as complete, with removals empty. | Indices + values; removals first | [v5 RPC reference](https://developers.google.com/safe-browsing/reference/rpc/google.security.safebrowsing.v5) | read 2026-10-21 | High |
| 1.7 | **Rice-Golomb coding of sorted hashes.** Entries are taken in lexicographic order; adjacent differences are encoded with a unary quotient and a k-bit remainder; `first_value` holds the first value and `entries_count` is zero when only one value is encoded. In v5 "the encoded data are now treated as big-endian so as to avoid a costly sorting step." Allowed `rice_parameter` ranges: 3–30 (32-bit), 35–62 (64-bit), 99–126 (128-bit), 227–254 (256-bit). | k ranges 3–30 / 35–62 / 99–126 / 227–254 | [v5 RPC reference](https://developers.google.com/safe-browsing/reference/rpc/google.security.safebrowsing.v5) | read 2026-10-21 | High |
| 1.8 | **Integrity and pacing.** `sha256_checksum` is "the sorted list of all hashes, hashed again with SHA256" after applying the update; on a mismatch the documented client behaviour is "perform a full update". `minimum_wait_duration` is a floor; when it is zero or omitted the client "SHOULD fetch immediately" because the server has more updates. `max_update_entries` must be at least **1024** when set. | 1024-entry minimum constraint; SHA-256 over sorted list | [v5 RPC reference](https://developers.google.com/safe-browsing/reference/rpc/google.security.safebrowsing.v5); [Local Database](https://developers.google.com/safe-browsing/reference/Local.Database) | read 2026-10-21 | High |
| 1.9 | **No list sizes are published.** The docs name the lists (`gc-32b` global cache, `se-4b` social engineering, `mw-4b` malware, `uws-4b`, `uwsa-4b`, `pha-4b`) but give no entry counts, byte sizes or expected sizes; the only count on the Local Database page is `entries_count: 2` in a coding example. | No published N or bytes | [Local Database](https://developers.google.com/safe-browsing/reference/Local.Database) | read 2026-10-21 | High |

**Implications:** v5's local-list format is a complete, documented, adoptable design for a locally matched list: sorted truncated hashes, index-based removals, value additions, a whole-list checksum, a server-set minimum wait, and four supported hash widths. The 4-byte width is a network-privacy choice, not a local-matching requirement; Google itself ships 8-, 16- and 32-byte lists for local use, which is evidence that a locally matched list should choose its width from its false-positive budget (Section 5).

## 2. v5 real-time, no-storage and the OHTTP relay

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Real-time mode adds a benign global cache in front of the local list.** The client stores a Global Cache of SHA-256 hashes of likely-benign expressions plus the usual threat lists. If any URL hash is in the global cache it returns `UNSURE` and runs the local-list procedure; otherwise it sends 4-byte prefixes to the server. A network/HTTP error returns `UNSURE` (not `SAFE`). | Global cache of full hashes; error → UNSURE | [Real Time Mode](https://developers.google.com/safe-browsing/reference/Real.Time.Mode) | 2026-02-18 | High |
| 2.2 | **The request ceiling is 30 prefixes, and decoys are explicitly allowed.** The protocol leaves batching to the client and says it is "acceptable for the client to send unrelated or randomly generated hash prefixes together with the hash prefixes", "as long as the number of hash prefixes sent in a single request does not exceed 30." | 30 prefixes/request; random decoys allowed | [Real Time Mode](https://developers.google.com/safe-browsing/reference/Real.Time.Mode) | 2026-02-18 | High |
| 2.3 | **`hashes.search` limits and caching.** `GET https://safebrowsing.googleapis.com/v5/hashes:search`; "Clients MUST NOT send more than 1000 hash prefixes", "SHOULD NOT need to send more than 30", each exactly 4 bytes. The response is an unordered `fullHashes[]` (each 32 bytes) with threat details and a `cacheDuration` that applies to every queried prefix, including negatives; the client may extend it to at most **24 hours** only when `fullHashes` is empty, and the server may vary durations between responses. | 1000 hard / 30 recommended; 4 bytes; 24 h cap | [hashes.search](https://developers.google.com/safe-browsing/reference/rest/v5/hashes/search) | read 2026-10-21 | High |
| 2.4 | **No-Storage mode keeps no persistent database.** The client "need not maintain any persistent local database" but still keeps a local cache that "may be cleared in case of memory pressure"; it sends the same ≤30 4-byte prefixes, decoys allowed, and **on any network or HTTP error returns `SAFE`**. It never returns `UNSURE`, because there is no local list to fall back to. | No persistent DB; error → SAFE; ≤30 prefixes | [No Storage Real Time Mode](https://developers.google.com/safe-browsing/reference/No.Storage.Real.Time.Mode) | read 2026-10-21 | High |
| 2.5 | **The OHTTP gateway is v5-only and takes encapsulated Binary HTTP.** Public key: `GET https://safebrowsingohttpgateway.googleapis.com/v1/ohttp/hpkekeyconfig?key=<API key>`; requests: `POST .../v1/ohttp:handleOhttpEncapsulatedRequest` with `Content-Type: message/ohttp-req`. The inner request is Binary HTTP (RFC 9292), typically `/v5/hashes:search`. "Google Safe Browsing V4 APIs cannot be accessed via this service." Clients should refresh the key **once per day**; keys rotate regularly. The relay must use OAuth 2.0 with scope `https://www.googleapis.com/auth/3p-relay-safe-browsing`, and Fastly is the named example relay. | Daily key refresh; RFC 9458 + RFC 9292; v5 only | [Safe Browsing Oblivious HTTP Gateway API](https://developers.google.com/safe-browsing/ohttp/reference) | read 2026-10-21 | High |
| 2.6 | **What OHTTP hides, and from whom (RFC 9458).** The relay sees the client's network origin, the gateway endpoint, TLS boundaries, ciphertext lengths, timing and the key identifier, but not plaintext. The gateway decrypts and sees the target URI, headers and body, but not the client's IP; transport does not reveal which requests come from the same client absent per-client keys, although content, cookies or identifiers can still link them. The security assumption is that relay and gateway "cannot be operated by the same entity"; if they share views, identity and plaintext join. Protection is client-to-gateway, not client-to-target. There is **no forward secrecy** during a key's lifetime, response post-compromise security is not provided, and "traffic analysis … is outside the scope of this document." | Relay sees IP+metadata; gateway sees plaintext; collusion breaks it | [RFC 9458](https://www.rfc-editor.org/rfc/rfc9458.html) | 2024-07 | High |
| 2.7 | **Google's public description matches the split.** Chrome encrypts 4-byte prefixes with a Safe Browsing public key and sends them through a Fastly-operated OHTTP relay that removes identifiers; "Safe Browsing sees the hash prefixes of your URL but not your IP address, and the privacy server sees your IP address but not the hash prefixes. No single party has access to both." On repeated request failure Chrome "will enter a back-off mode and downgrade the checks to hash-based checks." | Fastly relay; fail to local-list checks | [Google Security Blog, "Real-time, privacy-preserving URL protection"](https://security.googleblog.com/2024/03/blog-post.html) | 2024-03-14 | High |
| 2.8 | **Configuration hygiene is part of the privacy model.** A key configuration "MUST be authenticated and have integrity protection"; acquisition is unspecified, and applications "MUST provide accommodations to mitigate tracking using Client configurations." Each active configuration partitions the client anonymity set, unique configurations and trial decryption narrow it, and cookies or other identifiers can correlate requests even through OHTTP. | Config partitions anonymity set; trial decryption | [RFC 9458](https://www.rfc-editor.org/rfc/rfc9458.html) | 2024-07 | High |

**Implications:** The real-time and no-storage modes exist to shrink the update-to-detection window at the cost of a per-URL request and a trust split between relay and gateway. A local full list removes the request entirely, so it has a strictly smaller privacy surface at browse time; it pays instead in list size, update bandwidth and a longer worst-case reaction time (bounded by the refresh interval).

**Implications:** v4's protocol was structurally sound but its economics were wrong for fast phishing: a 20–50 minute local refresh misses the majority of short-lived sites. v5 keeps the local-list option, adds a real-time option and a privacy relay, and fixes the update format (big-endian, variable hash width, simpler diff semantics). Izcal should take v5's update semantics, not v4's, and should not assume a 30-minute freshness rule exists anywhere in the published protocol.

## 4. Alternative set-membership structures and published trade-offs

Let ε be the target false-positive probability per membership query and f = log2(1/ε) the fingerprint width in bits.

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Bloom filter.** With n items, m bits and k hashes, ε ≈ (1 − e^(−kn/m))^k; the optimum is k = (m/n)·ln2, giving m/n = 1.44·log2(1/ε) bits per item. At ε = 1% that is 9.57 bits/item ("about 9.6 bits per element"); each tenfold error reduction costs about 4.8 bits/item. No deletion, no enumeration. | 1.44·log2(1/ε); 9.57 bits at 1% | [Bloom filter](https://en.wikipedia.org/wiki/Bloom_filter); original: [Bloom, CACM 1970](https://doi.org/10.1145/362686.362692) | 1970-07 / page read 2026-10-21 | Medium (secondary formula page; primary paywalled) |
| 4.2 | **Blocked Bloom filter.** Each item is stored in one small Bloom filter sized to a CPU cache line; every query then costs at most one cache miss. The trade-off is a higher false-positive rate from imbalanced load across blocks, and deletion remains unsupported. The cuckoo-filter paper's comparison table gives blocked Bloom 1 cache miss per lookup versus k for standard Bloom. | 1 cache miss; FP higher than standard Bloom | [Cuckoo Filter, CoNEXT 2014](https://www.cs.cmu.edu/~dga/papers/cuckoo-conext2014.pdf), Table 1 and Section 2.1 | 2014-12-02 | Medium (blocked-Bloom numbers are as reported by the cuckoo paper, not Putze et al. directly) |
| 4.3 | **Cuckoo filter.** Stores only fingerprints in a cuckoo hash table with two candidate buckets per item; supports insertion and deletion dynamically; "no false negatives"; bucket occupancy can reach about 95%; uses less space than a space-optimized Bloom filter when the target false-positive rate is less than 3%. Deletion is limited to items known to have been inserted, and insertion can fail and require rehashing. | <3% FP crossover; 95% occupancy; 8-bit fingerprints | [Cuckoo Filter, CoNEXT 2014](https://www.cs.cmu.edu/~dga/papers/cuckoo-conext2014.pdf) | 2014-12-02 | High |
| 4.4 | **Cuckoo filter size formula.** ε ≤ b/2^(f−1) for bucket size b, so f ≥ log2(b/ε) + 1; storage is (log2(1/ε) + 1 + log2 b)/α bits per key at load factor α, with α up to 95.5%. Fingerprints need at least about (log n)/b bits, so very large sets cannot use arbitrarily small fingerprints. | (log2(1/ε)+1+log2 b)/α; α ≤ 95.5% | [Cuckoo filter](https://en.wikipedia.org/wiki/Cuckoo_filter) | read 2026-10-21 | Medium |
| 4.5 | **Xor filter.** "Xor filters can be faster than Bloom and cuckoo filters while using less memory"; the compact xor+ variant "can use even less space" than Golomb-compressed sequences, with query speeds competitive with Bloom filters. Published in the Journal of Experimental Algorithmics 25(1), 2020. | Qualitative abstract only; no bits/key stated | [Xor Filters](https://arxiv.org/abs/1912.08258) | 2019-12-17 (JEA 2020) | Medium (abstract only) |
| 4.6 | **Binary fuse filter.** Within **13%** of the storage lower bound, versus **23%** for xor filters and **44%** for Bloom filters; an **8%** variant trades query speed for space; construction "can be more than twice as fast as the construction of xor filters." At the same bound that is about 8% smaller than xor filters. | 13% / 23% / 44% above lower bound; 8% slower variant | [Binary Fuse Filters](https://arxiv.org/abs/2201.01174) | 2022-01-04 (JEA 2022) | High |
| 4.7 | **Derived widths per fingerprint bit.** Xor uses 1.23·f bits/key, binary fuse 1.13·f (or 1.08·f in the slower variant), Bloom 1.44·f (with f = log2(1/ε)); the information-theoretic lower bound is f. These relations follow directly from 4.1, 4.4 and 4.6. | xor 1.23f; fuse 1.13f; Bloom 1.44f; bound f | Calculation from 4.1, 4.4, 4.6 | 2026-10-21 | High (arithmetic) |
| 4.8 | **Golomb-coded sets (GCS).** Store the sorted hashes and Rice-code the gaps; the structure is near-entropy. Published summaries claim 20–30% smaller than a Bloom filter at the same false-positive rate, at roughly an order of magnitude slower queries; one measured implementation reports **33.6 bits/item at P = 2^−32** and **5.6 bits/item at P = 1/16**. | 20–30% smaller than Bloom; 33.6 bits at 2^−32 | Search-result summary of GCS READMEs and [Kragen's GCS page](https://canonical.org/~kragen/sw/inexorable-misc/golomb.py); not opened in this pass | undated / read 2026-10-21 | Low |
| 4.9 | **GCS arithmetic for this design.** For N entries mapped into a 2^b universe, mean gap λ = 2^b/N; optimal Rice parameter k ≈ log2(λ·ln2); expected length is k + 1/(1 − e^(−2^k/λ)) bits, about **2 bits above log2(1/ε)** (1.9–2.5 bits in the cases computed here, the upper end from rounding b up to a whole bit). With up to 30 expressions per URL and a target of 1e−9 per URL (ε = 3.33e−11 per expression), b = 53 bits and GCS costs **36.9 bits/entry = 0.92 MB** for 200k entries; b = 59 and **37.2 bits/entry = 46.5 MB** for 10M. At a 1e−6 per-URL target the same arithmetic gives 0.67 MB and 34.0 MB. | 53/59-bit prefixes; 0.92 / 46.5 MB at 1e−9 per URL | Calculation (this note), Rice model as in 1.7 | 2026-10-21 | High (arithmetic) |
| 4.10 | **Sorted truncated-hash array with binary search.** Store b-bit hashes in ascending order; lookup is log2(N) probes (18 at 200k, 24 at 10M). No extra structure and no additional false positives beyond truncation; diff-friendly because insertions and removals are positional. At the same 1e−9 per-URL target: 53 bits/entry (1.33 MB) at 200k and 59 bits (73.8 MB) at 10M. | 18/24 probes; 1.33 / 73.8 MB | Calculation from 4.9's b values | 2026-10-21 | High (arithmetic) |
| 4.11 | **Prefix trie over host labels.** A reversed-label trie matches host suffixes in O(labels) with no false positives and supports enumeration; memory is proportional to the number of label nodes, not entries, so it suits host-only lists but not millions of distinct URL paths. uBlock Origin documents a compressed trie for pure-hostname filters, with lookup cost scaling in hostname length and "no measurable performance hit" for tens of thousands of filters (prose description, no code read). | O(labels); no FP; tens of thousands of hosts | [uBO wiki, Filter performance](https://github.com/gorhill/uBlock/wiki/Filter-performance) | last edited 2024-10-27 | Medium |
| 4.12 | **Comparison at the 1e−9-per-URL target (30 expressions).** Bits per entry and total size: GCS 36.9/37.2 bits (0.92 MB at 200k, 46.5 MB at 10M); binary fuse 39.3 bits (0.98 / 49.1 MB); cuckoo 39.6 bits (0.99 / 49.4 MB); xor 42.8 bits (1.07 / 53.5 MB); Bloom 50.1 bits (1.25 / 62.6 MB, and about 35 hash functions); sorted array 53/59 bits (1.33 / 73.8 MB). At a 1% per-query target instead, xor and fuse win (about 10–12 bits/entry) and GCS is roughly tied with Bloom. | See cell | Calculation from 4.1–4.10 | 2026-10-21 | High (arithmetic) |

**Implications:** For a phishing list that must run locally with a near-zero false-warning rate, **GCS is the best fit at both 200k and 10M entries**: 0.9 MB and 46.5 MB at 1e−9 per URL, with a simple sorted-delta format that matches v5's Rice coding and can be block-indexed for random access. Binary fuse and cuckoo are the right choice only if the target is a coarse 1% filter and lookup speed dominates; a plain sorted array is the fallback when implementation simplicity and positional diffs matter more than 35–40% space; a trie is for host-suffix lists, not URL lists.

## 5. Hash choice and truncation

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **v5 uses SHA-256 exclusively.** Every expression is hashed with SHA-256; the full hash is 32 bytes and is truncated to 4, 8 or 16 bytes depending on the list. | SHA-256 only; 32-byte full hash | [URLs and Hashing](https://developers.google.com/safe-browsing/reference/URLs.and.Hashing) | 2025-05-23 | High |
| 5.2 | **A 4-byte prefix has a false-positive probability of N/2^32 per lookup.** For N = 200,000 that is **4.66e−5** (1 in 21,475); for N = 10,000,000 it is **2.33e−3** (1 in 429). | 4.66e−5 / 2.33e−3 per lookup | Calculation: N/2^32 | 2026-10-21 | High (arithmetic) |
| 5.3 | **A URL performs up to 30 lookups, so the per-URL false-warning bound is up to 30·N/2^32.** At 200k that is **1.40e−3** (about 1 in 716 URLs); at 10M it is **6.99e−2** (about 1 in 14 URLs). The union is smaller than the sum because expressions overlap, but the sum is the safe bound. | 0.14% / 7.0% of URLs | Calculation: 30 × 5.2 | 2026-10-21 | High (arithmetic) |
| 5.4 | **Birthday collisions inside a 4-byte list.** Expected colliding pairs = N(N−1)/2^33: **4.66** at 200k and **11,642** at 10M; P(at least one collision) is **99.05%** at 200k and effectively 1 at 10M. | 5.5 | **Longer prefixes buy the false-positive budget a local list needs.** Per-URL bounds at 10M with 30 expressions: 5 bytes **2.73e−4**; 6 bytes **1.07e−6**; 8 bytes **1.63e−11**. The published bypasses (userinfo/`@`, backslashes, `%2e` dot segments, IDN homographs, trailing dots) all exploit a mismatch between "the string that was checked" and "the string that was fetched"; one parser removes the class.

**Implications:** Izcal can anchor the format on freely implementable published specifications (v5 prose, TUF, RFC 9458/9292, WHATWG URL, RFC 4648) while shipping only its own MIT-licensed code and its own or MIT-licensed list data. The Safe Browsing service and data are non-commercial and attribution-bound, so they are a design reference and a benchmark, not a data source.
