# Izcal phishing protection: list production, operations and governance

Compiled 21 October 2026. Primary sources were preferred (operators' terms pages, specifications, standards, regulators, papers, maintainers' prose). **M-1 note:** no third-party project's source code, commit, diff or code review was opened. Repository READMEs and terms pages were read as prose; where a fact is visible only in a commit history, the note says so and does not use it.

Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only, or a claim I could not check today.

This note builds on the source selection and five feed samples in [SEC-D7][SECD7] (18–19 October 2026). It does not redo that measurement. It covers the operations and governance side: licences, quality practice, aggregation, the TUF channel, staffing and cost, legal exposure, and what Izcal should measure about its own list. References to CB-D16 are to the [Izcal content blocking spec](../../reports/Izcal%20content%20blocking.md), whose governance rules this strand should reuse rather than reinvent.

**Implications:** The allowlist is the main false-positive control, and Phishing Army's **candidate-not-auto-replaced, human-diffed monthly workflow** is the practice to copy. Izcal should publish evidence and a correction route for every entry, use "suspected/reported" language where the source is not verified, and set a **much shorter re-validation clock for phishing than CB-D16's 12 weeks**. DNSSEC and domain age can rank review candidates; neither can justify an entry on its own.

| # | Finding | Numbers / exact terms | Source | Date | Conf. |

| 3.1 | **The strongest published evidence says reputation lists barely overlap and should be combined.** ICANN's 2023 evaluation of reputation block lists measured overlap at "less than five percent in most cases" and recommended combining two or more, because "the strengths of one will often compensate for the weaknesses of another." Deduplicate on registrable domain plus URL, exclude aggregates and stalled feeds, and budget reviewer time per unique entry rather than per feed. Keep phishing and malware as separate tiers with separate matching semantics.

## 4. Update channel operations: TUF, diffs, CDN cost, mirrors and witnesses

| # | Finding | Numbers / exact terms | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **TUF 1.0.37 defines four mandatory top-level roles plus an optional mirrors role, with threshold signatures and offline key custody.** Root delegates trust; targets signs which files are trusted; snapshot prevents mix-and-match; timestamp signs the snapshot hash. Root private keys "MUST be kept very secure and thus should be kept offline"; all keys except timestamp and mirrors "should be stored securely offline." | "There are four fundamental top-level roles": root, targets, snapshot, timestamp; mirrors optional; "All roles can use one or more keys and require a threshold of signatures"; root keys offline | [TUF specification 1.0.37 §2.1, §4.3, §6.1](https://theupdateframework.github.io/specification/latest/) | 2026-10-08 | High |
| 4.2 | **Expiry is mandatory and a missed signature is a client-visible freeze.** Clients "MUST NOT trust an expired file"; an expired timestamp, snapshot or targets file causes the update cycle to abort and a possible freeze to be reported. | "Clients MUST NOT trust an expired file"; expired timestamp: "discard it, abort the update cycle" and report a possible freeze; fixed update start time | [TUF specification 1.0.37 §4.3, §5.4–5.6](https://theupdateframework.github.io/specification/latest/) | 2026-10-08 | High |
| 4.3 | **Rollback and mix-and-match are blocked by monotonic versions and hash pinning.** Clients must not replace metadata with a lower version; root updates advance exactly one version at a time; snapshot records all targets metadata versions and hashes; timestamp pins snapshot by hash/version, so a combination that never existed together is rejected. | "Clients MUST NOT replace a metadata file with a version number less than the one currently trusted"; root version N+1; "An attacker cannot trick clients into using a combination of metadata that never existed together" | [TUF specification 1.0.37 §1.5.2, §5.3–5.6](https://theupdateframework.github.io/specification/latest/) | 2026-10-08 | High |

The cost table shows why that is not only a privacy choice but the only scalable one. | daily full + 15-min diffs: $4,080/month B2, $34,680/month CloudFront at 1M clients; 5-min diffs: $9,840 / $83,640 | Derived; [content blocking spec §6.9, CB-D17](../../reports/Izcal%20content%20blocking.md) | 2026-10-21 | Medium |

| Update mode | Per client/day | 1M clients TB/day | B2 at $0.01/GB per month | CloudFront at $0.085/GB per month | R2 egress |
|---|---:|---:|---:|---:|---:|
| Daily full sync | 4.00 MB | 4.00 | $1,200 | $10,200 | $0 |
| 15-min diffs + daily full | 13.60 MB | 13.60 | $4,080 | $34,680 | $0 |
| 5-min diffs + daily full | 32.80 MB | 32.80 | $9,840 | $83,640 | $0 |
| 5-min full fetch | 1,152 MB | 1,152 | $345,600 | $2,937,600 | $0 |

†The 4 MB and 100 KB figures are **planning assumptions, not measurements**. SEC-D7 measured churn of tens of new phishing domains and about 20 malware URLs per hour; a diff carrying that churn is kilobytes, so 100 KB is conservative. At 10M clients, multiply every cost by ten.

**Implications:** TUF gives **rollback, freeze and mix-and-match protection but no diff format**, so Izcal must define its own version-addressed diff (GSB's additions/removals model is the published precedent) and test it against TUF's expiry and consistent-snapshot rules. **Do not poll a 200k-entry full list every 5–15 minutes**: use a daily full sync, small diffs, and the emergency channel for fast-moving security entries. A zero-egress CDN (R2) plus a request budget is the only configuration where 5-minute diffs remain inexpensive at scale.

## 5. Governance precedents

| # | Finding | Numbers / exact terms | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **CRLSets are the closest precedent for a browser-pushed security list.** Chrome replaced online CRL/OCSP checks with a pushed revocation list delivered through its existing update mechanism, because online checks soft-fail, add a median ~300 ms (mean near 1 s) and leak browsing to the CA. Admission is criteria-based: a contributing CRL must be crawlable, valid under RFC 5280, free of negative serial numbers; EV CRLs are preferred and revocation reasons allow size filtering. | "list of revoked certificates" via the update mechanism; soft-fail "seat-belt that snaps when you crash"; median OCSP ~300 ms; mean near 1 s; "valid by RFC 5280"; EV "taken in preference" | [ImperialViolet, CRLSets](https://www.imperialviolet.org/2012/02/05/crlsets.html) | 2012-02-05 | High |
| 5.2 | **CRLs use a publisher deadline, not a client revalidation rule.** `thisUpdate` is the issue date; `nextUpdate` is the date by which the next CRL will be issued; issuers MUST include it. RFC 5280 does not say a client must reject an expired CRL, which is why browsers added their own policy. | "This field indicates the date by which the next CRL will be issued"; "Conforming CRL issuers MUST include the nextUpdate field"; no required client action after expiry in the text | [RFC 5280 §5](https://www.rfc-editor.org/rfc/rfc5280) | 2008-05 | High |
| 5.3 | **The CA/Browser Forum is a multi-stakeholder body with formal ballots.** It is a "voluntary gathering" of certificate issuers and certificate consumers (browsers and other software); changes go through discussion and voting periods, with 2026 ballots and reviews documented on the site. | "voluntary gathering"; CAs and "Certificate Consumers"; ballots with discussion and voting; Server Certificate Requirements SC100 dated 2026-09-07; ballot SMC020 posted 2026-10-05 | [CA/Browser Forum](https://cabforum.org/) | 2026-10-21 (site; ballots 2026-09/10) | High |
| 5.4 | **Google publishes scale but not the operational numbers a small team needs.** Safe Browsing "protects over five billion devices every day", reaches "half the world's online population", and has run since 2005. No team size, budget, false-positive rate or review throughput is published. Its transparency report exists, but the overview page is JavaScript-rendered and yielded no figures to this fetch. | "over five billion devices every day"; "half the world's online population"; launched 2005 against phishing; transparency page title only | [Google Safe Browsing](https://safebrowsing.google.com/); [Google Transparency Report](https://transparencyreport.google.com/safe-browsing/overview) | accessed 2026-10-21 | High (scale), Medium (transparency extract) |
| 5.5 | **APWG is a membership-funded clearinghouse, not a regulator.** eCX has operated since 2004, is agreement-based and closed, and its tiers are priced from $1,500 to $15,000 a year. It is a multi-stakeholder data-sharing model, but one whose terms are contractual and unpublished. | "since 2004"; "not public open feeds"; tiers $1,500–$15,000; "data sharing agreement" | [APWG eCX](https://apwg.org/ecx/); [APWG membership](https://apwg.org/membership/) | accessed 2026-10-21 | High |
| 5.6 | **CB-D16 already sets stricter governance than any external precedent reviewed here.** It requires behaviour criteria, two-person review, an entry record, MIT publication of the list as data, 12-week re-validation, exceptions as entries, published appeals, published legal demands, and a funding rule free of listed parties. The same spec's delivery design requires a witness-cosigned log: the client refuses a bundle without k-of-n cosine and a consistency proof. The funding rule is the hardest constraint for a small browser: Google and Microsoft can fund lists from general advertising; Izcal cannot. | "two people"; "Every entry carries evidence, two reviews and a last-fired date"; "re-validated every 12 weeks†"; "No payment, ever"; funding "must not include revenue from a party the lists name in a way that could shape them"; search-revenue deal "ruled out"; "checkpoint cosigned by k of n independent witnesses" | [Content blocking spec §6.8–6.9, CB-D16, CB-22](../../reports/Izcal%20content%20blocking.md) | 2026-10-19 | High (internal) |

**Implications:** Copy **CRLSets' pushed-list architecture, CABF's published-ballot habit and CB-D16's no-payment/two-review rules**. The funding rule is the binding constraint: Izcal must publish who funds the list and must refuse revenue from listed parties, which rules out the advertising-funded model that sustains Google's and Microsoft's lists. Plan for **witness recruitment as a governance dependency**, not a late engineering task.

## 8. Measurement plan for Izcal's own list

| # | Finding | Numbers / exact terms | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | **Adopt ICANN's seven dimensions as the list scorecard.** Volume, overlap, timeliness, churn, liveliness, purity and accuracy give Izcal a published vocabulary that is independent of any vendor and covers both coverage and hygiene. | "volume", "overlap", "timeliness", "churn", "liveliness", "purity", "accuracy" | [ICANN](https://www.icann.org/en/blogs/details/icann-publishes-paper-on-defense-mechanisms-against-harmful-internet-content-18-12-2023-en) | 2023-12-18 | High |
| 8.2 | **PhishTime is the published method for measuring list speed and coverage with ground truth.** It launched and reported 2,862 harmless test phishing sites over six rounds in nine months, then measured how quickly and consistently each blacklist listed them. SEC-D7 records GSB coverage at 92.9% with a median of about 56 minutes, and SmartScreen at 93.2% with about 3 h 47 min; the USENIX page itself gives no per-list figures, so those numbers are a secondary reading. | 2,862 test sites; six rounds; nine months; GSB 92.9%, ~56 min; SmartScreen 93.2%, ~3 h 47 min; mobile lower; cloaking drops coverage | [PhishTime, USENIX Security 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/oest-phishtime); [SEC-D7 §3.2][SECD7] | 2020-08; SEC-D7 2026-10-19 | Medium |
| 8.3 | **The Tranco-based popularity proxy is a cheap false-positive screen, and URL-level matching is mandatory.** SEC-D7 counts listed hosts that equal a registrable domain in the Tranco top 100k and hosts under top-10k domains. It is a review flag, not proof. Whole popular domains were listed at host level, so blocking a host would break google.com, github.com, dropbox.com and others; URL feeds must match host-suffix and path-prefix expressions, with an allowlist. | CERT Polska 2 popular apex (lookalikes); PhishTank 165 (google.com, linkedin.com); URLhaus 13 (github.com); Phishing.Database 74 (bit.ly, nflxvideo.net); allowlist workflow in Phishing Army README | [SEC-D7 §4.6][SECD7]; [Phishing Army README](https://github.com/drego85/PhishingArmyCore) | 2026-10-18/19; README accessed 2026-10-21 | High |
| 8.4 | **Appeals and takedowns must be measured as product metrics, not only handled.** CB-D16 sets a seven-day response target and publishes the decision and reason, plus a quarterly report of entries, exceptions, appeals, outcomes and legal demands. Izcal should record appeals per 10k entries, time to first response, overturn rate, repeat appellants, and takedowns received and complied with. The same report should publish entry age distribution and the share of entries not re-validated on time. | "a named reviewer answers within 7 days†"; decision and reason published; quarterly report | [Content blocking spec §6.8](../../reports/Izcal%20content%20blocking.md) | 2026-10-19 | High (internal) |
| 8.5 | **Freshness should be measured as first-observed-to-client time, not feed build time.** SEC-D7's cross-feed lag method (host first seen in A, then when B had it) is the measurement Izcal can reuse against its own list and an independent feed. | lag measured in 26/60/60/60-minute intervals; CERT Polska led PhishTank on Polish phishing; OpenPhish's new hosts were absent from PhishTank and CERT Polska | [SEC-D7 §4.4][SECD7] | 2026-10-18/19 | High |
| 8.6 | **Coverage needs an independent ground truth; measuring a list against its own inputs is circular.** PhishTime's test-site method is the strongest published option; a cheaper proxy is a held-out independent feed that is never an input to the list. | hold out one source; test sites; do not use a shipped input as ground truth | [PhishTime](https://www.usenix.org/conference/usenixsecurity20/presentation/oest-phishtime) | 2020-08 | Medium |
| 8.7 | **No published false-positive rate exists for phishing lists, so Izcal must publish its own, and the SEC-D7 scripts already implement the feed-side measurements.** None of the operators reviewed publishes a rate; the popularity proxy is the only measured screen in this strand. `fetch_once.sh`, `poll.sh` and `analyse.py` produce the sample, churn, lag, overlap and popularity tables; a list-health harness should reuse them rather than build a second path. | no published FP rate from Google, Microsoft, APWG, CERT Polska or the open feeds; scripts in SEC-D7; results in `report.json` and `report_interim.json` | [SEC-D7 §4.1, §4.6, files][SECD7] | 2026-10-19 | High (absence) |

**Implications:** Publish a **quarterly list report** using ICANN's seven dimensions, PhishTime-style ground-truth tests and the SEC-D7 popularity proxy. Track **appeals, overturns and takedowns** as first-class metrics, and publish the first false-positive rate in the field. Reuse the SEC-D7 scripts for feed-side measurement; add a client-side test that no URL check produces a network request.
