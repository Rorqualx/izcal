**Why it was built that way.** In 2004–2008 no browser vendor had both a global crawler and a phishing feed, and users would not install toolbars. A **free, centrally curated list** let every browser ship protection on day one. The unit of protection was the URL, because that was the only signal every browser could check before loading a page.

**Implications:** Izcal must ship default-on URL protection from its first release; a browser without it is the Atlas case in Section 6. But the history also shows that a free list is a dependency, not a strategy: the vendor can retire a protocol (v1 in 2008, v4 in 2027) and leave the browser unprotected. Izcal should own its list format and its update path, and treat any external feed as replaceable.

## 2. Protocol evolution: from v1 lists to v5 real-time

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **GSB v2 ("shavar")** distributed only a **32-bit prefix** of each URL's SHA-256 digest. A local prefix match was not proof: the client queried the server for the full 256-bit digests matching that prefix and compared locally. Lists were split into **add chunks** and **sub chunks**, identified by chunk ID, so a client could update by sending the chunk IDs it already had. | 32-bit prefixes; add/sub chunks | [Inria research report RR8686](https://inria.hal.science/hal-01120186v1/file/RR8686.pdf) | 2014–2015 (report) | High |
| 2.2 | Early Chromium stored prefixes in a **Bloom filter** with 20 Jenkins hash functions, a minimum of 25,000 bytes and a maximum of 3 MB. It was **discontinued in September 2012** because a Bloom filter is static: entries cannot be deleted, and blacklist churn requires deletion. The replacement, a **delta-coded prefix table**, used 1.3 MB for the same 32-bit prefixes versus 2.5 MB raw (1.9× compression). | 20 hashes; 25 KB–3 MB; Sept 2012; 1.3 MB vs 2.5 MB | [Inria RR8686](https://inria.hal.science/hal-01120186v1/file/RR8686.pdf) | 2014–2015 (report) | High |
| 2.3 | The report's snapshot of GSB lists shows **317,807 malware prefixes** and **312,621 phishing prefixes**; the Yandex mirror used the same shavar scheme, with only 195 phishing prefixes in common with Google's list. That overlap figure is evidence that "the list" was never one universal list. | 317,807; 312,621; 195 shared | [Inria RR8686](https://inria.hal.science/hal-01120186v1/file/RR8686.pdf) | 2014–2015 (report) | High |
| 2.4 | **GSB v4 (May 2016)** replaced chunk IDs with a state-based update API: `threatListUpdates.fetch` returns a full or partial update, the client stores `newClientState`, and a checksum mismatch forces the client to clear the database and re-request from empty state. Prefixes are normally **4 bytes**; `fullHashes.find` confirms matches and accepts **up to 500 threat entries** per request. | 2016-05; 4 bytes; 500 entries | [Google Safe Browsing v4 Update API](https://developers.google.com/safe-browsing/v4/update-api); [The Register](https://www.theregister.com/security/2016/05/23/google-releases-v4_safe_browsing_api/1238154) | 2016-05 | High |
| 2.5 | **There is no 30-minute freshness clause in the v4 update documentation.** The server may impose a minimum wait; the documented example is **593.44 seconds (9.89 minutes)**. In practice Chrome updated its local list **every 30 to 60 minutes**, which is the real basis of the "30-minute" folklore. | 593.44 s; 30–60 min | [v4 Update API](https://developers.google.com/safe-browsing/v4/update-api); [Google Security Blog, 2024](https://security.googleblog.com/2024/03/blog-post.html) | 2024-03-14 | High |
| 2.6 | **GSB v2 and v3 were turned down on 1 October 2018**, announced on 24 January 2018, forcing all clients to v4. | 2018-01-24; 2018-10-01 | [Google Security Blog](https://security.googleblog.com/2018/01/announcing-turndown-of-deprecated.html) | 2018-01-24 | High |
| 2.7 | **GSB v5 (March 2024)** moved Chrome's Standard mode to a server-side list checked in real time. Chrome hashes the URL to 32-byte full hashes, truncates to **4-byte prefixes**, encrypts them with a Safe Browsing public key, and sends them through an **Oblivious HTTP privacy server operated by Fastly**. Google sees prefixes but not the IP; Fastly sees the IP but not the prefixes. On failure Chrome falls back to hash-based checks. | 2024-03-14; 4-byte prefixes | [Google Security Blog, 2024](https://security.googleblog.com/2024/03/blog-post.html) | 2024-03-14 | High |
| 2.8 | Google's stated reason for v5 is that **the majority of unsafe sites exist for less than 10 minutes**, so a 30–60-minute local list misses them; the server-side list can include sites as soon as they are discovered and can grow beyond device limits. | <10 min; 30–60 min | [Google Security Blog, 2024](https://security.googleblog.com/2024/03/blog-post.html) | 2024-03-14 | High |
| 2.9 | The **v5 API** documents three modes: **Real-Time**, **Local List**, and **No-Storage Real-Time**. `hashes.search` sends only a 4-byte prefix and returns full matching hashes; `urls.search` sends raw URLs and is labelled "No URL Confidentiality". OHTTP is optional; without it Google sees the request content and the IP, which it says it uses only for networking and anti-DoS. v5 is "check-by-default instead of the allow-by-default protocol previously available in V4", aided by a likely-benign Global Cache. | 3 modes; 4-byte prefix | [Google Safe Browsing reference](https://developers.google.com/safe-browsing/reference) | read 2026-10-21 | High |
| 2.10 | **Firefox 147 (13 January 2026)** "now supports the Safe Browsing V5 protocol and is migrating from Safe Browsing V4 to the local list mode of Safe Browsing V5 protocol." This is a protocol migration, not a move away from Google. | 2026-01-13 | [Firefox 147 release notes](https://www.firefox.com/en-US/firefox/147.0/releasenotes/) | 2026-01-13 | High |
| 2.11 | Google has told developers that **v4 support ends on 31 March 2027**; the API "may remain accessible beyond this date", but clients should move to v5 or Web Risk. Commercial use is restricted to Web Risk. | 2027-03-31 | [Chrome Enterprise release notes](https://support.google.com/chrome/a/answer/10314655) (notice reproduced in vendor forums) | read 2026-10-21 | Medium |

**Why it was built that way.** Bandwidth and memory drove the design: a 2014 list was hundreds of thousands of prefixes, and mobile devices could not hold full URLs. Hashing on the client hid browsing history from the vendor. Bloom filters were the obvious space-efficient answer until deletion made them wrong; delta-coded tables traded query speed for mutability. Real-time lookup only became affordable once the privacy relay (OHTTP) made sending prefixes acceptable.

**Implications:** Izcal should implement the **prefix + full-hash confirmation** model, because it is the only shape that survives both privacy review and list size, and should support both a local list and a server-side real-time mode. Freshness must be a **measured SLO** (time from list publication to client check), not an assumed 30 minutes: the v4 docs never promised it, and the 30–60-minute figure is Chrome's client cadence, not the protocol. Izcal should also plan for feed-version churn; the v1→v2 and v4→v5 transitions each left old clients unprotected for months.

**Why it was built that way.** Each source solved a different constraint. PhishTank was **crowd verification** before vendors had global sensors. eCX was **industry reciprocity** for brands and banks. URLhaus was **malware distribution**, where the URL is the payload delivery point. CERT Polska was a **national regulator** response to Polish-language targeting. Netcraft/OpenPhish were **commercial feeds** selling coverage. None of them alone covered fresh, regional, builder-hosted and malware cases; browsers that looked good (PhishTime's Opera 60.5%) inherited the gaps of their partners.

**Implications:** Izcal cannot rely on one feed. It should combine a global list, a malware feed, at least one regional feed and a commercial or crawler-derived source, and record **provenance, licence, retention and refresh interval per entry**, because those determine whether a warning is defensible. The PhishTank case is the warning about community governance: a feed that cannot accept new reporters or review disputes decays into a static archive even while it stays online.

## 4. Warning design history and the studies that changed it

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Akhawe & Felt (USENIX Security 2013)** measured **over 25 million** real warning impressions in Firefox and Chrome in 2013. Users continued through **about 10%** of Firefox malware/phishing warnings, **about 25%** of Chrome malware/phishing warnings, **about 33%** of Firefox SSL warnings and **70.2%** of Chrome SSL warnings. Their conclusion: warnings can be effective, and the user experience of a warning has a significant effect on behaviour. | 25M+; 10%; 25%; 33%; 70.2% | [USENIX Security 2013](https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/akhawe) | 2013-08 | High |
| 4.2 | **Sunshine et al. (USENIX Security 2009, "Crying Wolf")** surveyed 400+ users and ran a 100-participant lab study on SSL warnings. Redesigned warnings performed better, but far too many participants still proceeded; many held a backwards mental model (a warning meant the site was untrustworthy, so a trusted site was safe to proceed). The authors argued warnings are "fundamentally broken" and recommended blocking unsafe connections instead. | 400+ survey; 100 lab | [USENIX Security 2009](https://www.usenix.org/conference/usenixsecurity09/technical-sessions/presentation/crying-wolf-empirical-study-ssl-warning) | 2009-08 | Medium |
| 4.3 | **Chrome's 2013 interstitial redesign** simplified the malware and phishing warning pages, removed cartoon imagery and made the warning look serious; the variants were A/B tested in the field before rollout. The press account credits Adrienne Porter Felt's team; the measured field click-through after the redesign was still around a quarter. | 2013; ~25% | [ZDNet](https://www.zdnet.com/article/google-changing-chrome-malware-phishing-warnings/) | 2013 | Medium |
| 4.4 | **Felt et al. (CHI 2015)** redesigned Chrome's **SSL** warning: a prominent blue "Back to safety" button, with "Proceed" demoted behind "Advanced". Adherence rose from **37%** (Chrome 36, 24.7M impressions) to **62%** (Chrome 37, 20.2M impressions) and stayed near 61%; a controlled experiment moved **31% → 58%**. Text-only changes improved adherence by only **1.2%**, and comprehension did not improve. **This was an SSL certificate warning, not a phishing warning**; the two are often conflated. | 37%→62%; 31%→58%; +1.2% | [CHI 2015, DOI](https://dl.acm.org/doi/10.1145/2702123.2702442); [Help Net Security](https://www.helpnetsecurity.com/2015/02/02/browser-security-warning-redesigned-with-partial-success/) | 2015-04 | Medium |
| 4.5 | **Reynolds et al. (CHI 2020, "Measuring Identity Confusion with Uniform Resource Locators")** found participants identified **real URLs 93%** of the time but correctly identified only **40%** of obfuscated look-alike URLs. Users rely on URL-parsing strategies that fail against typosquatting and homographs. | 93% vs 40% | [CHI 2020, DOI](https://dl.acm.org/doi/10.1145/3313831.3376298) | 2020-04 | Medium |
| 4.6 | **Habituation is measurable in the field.** A CMU SOUPS 2014 analysis of Chrome malware warnings found users were **twice as likely** to ignore a warning when the blocked site was already in their browsing history. Familiarity, not just warning frequency, predicts bypass. | 2× | [SOUPS 2014 proceedings](https://www.cs.cmu.edu/afs/cs/Web/People/kiesler/publications/2014/2014_SOUPS-14-proceedings.pdf) | 2014 | Medium |
| 4.7 | **HTTPS is no longer a trust signal.** Zimperium's March 2024 analysis of **88,014** phishing URLs found **87.1% used HTTPS** and only 12.9% used HTTP; about **60%** of newly registered phishing domains obtained an SSL certificate within two hours. A separate 2024 figure puts HTTPS at **76%** of phishing sites. | 88,014; 87.1%; 60% in 2 h; 76% | [Zimperium](https://zimperium.com/blog/deep-dive-into-phishing-chronology-threats-and-trends) | 2024-03 | Medium |
| 4.8 | Google's 2024 design keeps **two levels**: Standard mode warns only for sites Safe Browsing has already confirmed unsafe; Enhanced mode uses additional signals and machine learning for unconfirmed or cloaking sites. Google explicitly says real-time Standard protection cannot catch a site that is too new or is cloaking to its detection systems. | 2 modes | [Google Security Blog, 2024](https://security.googleblog.com/2024/03/blog-post.html) | 2024-03-14 | High |
| 4.9 | The **"safe action prominent"** pattern survived because it was measured, not because it was stylistically preferred: the same study that produced 37%→62% found that changing only the words did almost nothing. Warning design is layout and default action first, copy second. | +1.2% for text only | [CHI 2015, DOI](https://dl.acm.org/doi/10.1145/2702123.2702442) | 2015-04 | Medium |

**Why it was built that way.** Early phishing protection copied the SSL warning: a modal page with two symmetric choices. Field measurement showed users treated the risky choice as normal, and that familiarity and repetition increased bypass. The redesigns made the safe action visually dominant and the risky action harder to reach. They did not, and could not, fix comprehension; the CHI 2015 authors called that result disappointing.

**Implications:** Izcal's interstitial should be **full-page, with the safe action as the only prominent control** and the bypass behind a deliberate second step, and its effect must be measured in the field (continue-through rate by warning type), not assumed from a lab. A padlock or "HTTPS" cue must never appear as a safety signal in the warning, because 87% of phish now use HTTPS. Look-alike domains need a separate, explainable indicator: users identify only 40% of them even when shown the URL.

**Implications:** Izcal's success metric should be **time-to-warn for a URL that is already live**, measured from first observation, not list membership at some later time. The historical baseline is 56 minutes for GSB desktop and 3 h 47 for SmartScreen; a new browser that only downloads a list every 30–60 minutes cannot beat that. Izcal needs a real-time path plus client-side signals, and it must measure mobile separately, because the historical mobile gap (57.8% coverage) is where users are most exposed.

| 6.5 | The scale is corroborated by two other vendors: Mimecast reported a **500% increase** in ClickFix attacks within six months, and Microsoft's Digital Defense Report 2025 attributed **47%** of initial-access compromises handled by its Defender Experts to ClickFix, ahead of traditional phishing at **35%**. | 500%; 47% vs 35% | [Mimecast 2025 report](https://www.mimecast.com/resources/infographics/2025-global-threat-intelligence-report-key-findings/); [CTM360 via The Hacker News](https://thehackernews.com/2026/09/17000-urls-reveal-how-clickfix-turns.html) | 2025–2026 | Medium |

**Why this chapter matters.** The historical model protects a **navigation**: the browser checks a URL, then shows a page. Agentic browsers act on pages, and ClickFix asks the user to act outside the browser. In both cases the malicious content can be a legitimate domain, a freshly built page, or an instruction rather than a URL. A list of bad URLs has nothing to match.

**Implications:** Izcal should treat the **action** as the protection unit alongside the URL: clipboard writes, command paste, file launch and agent-initiated navigation need their own policy and consent surface. For agentic browsing, the browser must be able to say which principal (user or agent) initiated a navigation and which page content influenced it; a URL list alone reproduces Atlas's 5.8% result. ClickFix also argues for clipboard mediation as a browser-owned capability rather than a page permission users reflexively grant.

|---|---|---|---|---|---|

The asymmetry pushes vendors toward caution, which is exactly what slows fresh-phish coverage. | — | [PhishTime](https://www.usenix.org/system/files/sec20-oest-phishtime.pdf) | 2020-08 | High |

| 7.8 | **Availability and security were explicitly traded.** If real-time requests fail repeatedly, Chrome enters a back-off mode and downgrades to hash-based checks; if the privacy server is unreachable, it also downgrades. **Why these failures persist.** The ecosystem's economics reward **precision** (don't break the web) over **recall** (catch every fresh phish). PhishTank shows what happens when intake governance collapses. Safari shows that even a working integration can create a privacy story that outlives the feature. The 2017 false-positive record is thinner than folklore suggests, but the individual cases show the mechanism: a shared hosting or release-asset pattern gets flagged, and every site using it is affected at once.

**Implications:** Izcal needs an explicit **false-positive appeal path with a named owner and a response target**, published like a security policy, because a feed without one becomes PhishTank. Real-time lookups should default to a relay design and must **show when protection has degraded** rather than silently falling back. The trust copy should say what is sent and to whom before the first lookup, not after a privacy article.

## 8. What survived and why

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | **Hash-prefix lists with full-hash confirmation survived** from v2 (2008) through v4 (2016) to v5 local-list mode (2026). The reason is unchanged: prefixes hide browsing history, and full-hash confirmation removes collisions. | 2008–2026 | [Inria RR8686](https://inria.hal.science/hal-01120186v1/file/RR8686.pdf); [v5 docs](https://developers.google.com/safe-browsing/reference) | 2008–2026 | High |
| 8.2 | **The full-page interstitial survived** as the warning surface because it measured better than toolbars and passive indicators; the "safe action prominent, risky action demoted" pattern survived because the 37%→62% result was reproduced in the field. | 37%→62% | [CHI 2015](https://dl.acm.org/doi/10.1145/2702123.2702442) | 2015 | Medium |
| 8.3 | **Default-on protection survived; opt-in did not.** GSB became the default in Chrome, Firefox and Safari; SmartScreen shipped in IE; Opera enabled Fraud Protection by default. The browsers that required users to install a toolbar lost the protection argument. | 2006–2009 | [Google 2017](https://blog.google/innovation-and-ai/technology/safety-security/safe-browsing-protecting-more-3-billion-devices-worldwide-automatically/); [LWN, Opera](https://lwn.net/Articles/279608/) | 2017-09-11 | High |
| 8.4 | **Multi-source, not one list, survived.** The working services combine a global list, malware feeds, regional lists and commercial data: Quad9 uses 19 feeds; Opera used PhishTank, Netcraft and Yandex; DuckDuckGo uses Netcraft; CERT Polska feeds Quad9 and NextDNS. | 19 feeds | [Quad9](https://www.securityweek.com/group-launches-secure-dns-service-powered-ibm-threat-intelligence/); [CERT Polska](https://cert.pl/en/warning-list/) | 2017–2026 | Medium |
| 8.5 | **What did not survive:** GSB v1, v2 and v3; Bloom filters (abandoned September 2012); open PhishTank registration (closed 2020); toolbar-only phishing filters; and the assumption that HTTPS means safe (87.1% of phish use it). | 2012; 2020; 87.1% | [Inria](https://inria.hal.science/hal-01120186v1/file/RR8686.pdf); [PhishTank register](https://phishtank.org/register.php); [Zimperium](https://zimperium.com/blog/deep-dive-into-phishing-chronology-threats-and-trends) | 2012–2024 | High/Medium |
| 8.6 | **What is not yet settled:** whether agentic browsers will adopt URL lists at all, and whether clipboard/action mediation becomes a browser primitive. Atlas's vendor-measured 5.8% block rate is the only public data point, and it is disputed in part. | 5.8% | [The Register](https://www.theregister.com/2025/10/27/atlas_vulnerability_memory_injection/) | 2025-10-27 | Medium |

**Why these survived.** Each survivor reduced one of the three costs that killed its alternatives: **bandwidth** (prefixes), **user attention** (interstitial with a dominant safe action), and **trust** (default-on, multi-source, relayed lookups). What did not survive either could not delete entries (Bloom), could not accept new evidence (PhishTank registration), or protected the wrong object (toolbar indicators and, now, URL-only protection against agentic and ClickFix attacks).

**Implications:** Izcal should build on the survivors rather than reinvent them: its own prefix-based list format with full-hash confirmation, a full-page interstitial with a dominant safe action, default-on behaviour, multiple feeds with per-entry provenance, and a relayed real-time path. The open design space is the one history leaves empty: **action-level protection** for agentic browsing and clipboard-mediated execution, which no surviving design covers.
