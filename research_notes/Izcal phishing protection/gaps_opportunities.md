# Izcal phishing protection: gaps, opportunities and interfaces

Compiled 21 October 2026. Primary sources were preferred: vendor documentation, published help pages, policy documents, standards documentation, news reports that quote the people involved, and Izcal's own accepted specifications. No third-party project's source code, commits or diffs were read or cited (M-1 part 3); where a value is stated only in source code, it is recorded as a question for a black-box measurement. Repository documents were read read-only at the cited sections.

Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a news report quoting a vendor test; **Low** = secondary source only, or inference.

**Budget and access note.** The shared web-search budget was limited, so the most load-bearing questions were researched first and the rest of the evidence is from known primary pages read directly. Three fetches failed: the Google Security Blog post on real-time Safe Browsing (HTTP 404 at the guessed address), the People Alchemy incident PDF (network error), and the Google Transparency Report page (empty render). Claims that depend on them are graded Medium or Low and say so. Chromium policy definitions surfaced by search are source code and are **not** cited; the enterprise-policy finding is graded Medium and relies on vendor documentation and benchmark descriptions, not on the YAML file.

# Part A. Gaps and opportunities

## 1. No explanation: the blocked page does not say what it knows

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Chrome's phishing interstitial names a detector, not a fact.** The documented wording is: "Deceptive site ahead … Google Safe Browsing recently detected phishing on example.com … You can report a detection problem or, if you understand the risks to your security, visit this unsafe site." It gives no list name, list version, entry ID, detection date, evidence, or the URL that was checked. "Recently" is the only time reference | — | [Matomo: troubleshoot a Chrome warning](https://matomo.org/faq/on-premise/troubleshoot-chrome-warning-on-matomo-domain/) | 2023-12-14 | High |
| 1.2 | **Google's own help page offers users no source, evidence or appeal record.** The user's options are "Details" then "Visit this unsafe site"; site owners are directed to request a review. | 1.3 | **A documented false positive shows the explanatory vacuum from the operator's side.** Developer Bogdan Chadkin found his site behind a full-screen "Deceptive site ahead" banner with "no phishing, no malware". He said: "The error message remained frustratingly vague, something about 'detected phishing activity.'" Google cleared it in about two hours, but he "never got an exact answer as to why his website was flagged" | 2 h to clear with Google; ~3 weeks for other vendors | [Cybernews](https://cybernews.com/security/google-ban-causes-cascade-of-blacklists-across-internet/) | 2026-03-05 | High |
| 1.4 | **Microsoft SmartScreen's "unrecognized app" is a reputation verdict with no explanation.** WinSCP reported an installer false positive; Microsoft replied that Defender found the files clean but SmartScreen showed "no known reputation". Separate Microsoft Q&A threads describe no working false-positive path and boilerplate answers about buying an Authenticode certificate and building reputation | — | [WinSCP forum](https://winscp.net/forum/viewtopic.php?t=28537); [Microsoft Q&A](https://learn.microsoft.com/en-gb/answers/questions/2751586/no-way-to-report-false-positives-for-various-micro) | accessed 2026-10-21 | Medium |
| 1.5 | **A false positive can cascade across vendors with no shared evidence trail.** In the People Alchemy incident report, a Netcraft false-positive phishing classification of an NHS customer subdomain cascaded into Google Safe Browsing labelling the whole domain "deceptive"; browsers blocked it (Edge excepted, because it uses a different list) until Google approved a review | — | [People Alchemy incident report (PDF)](https://community.sophos.com/cfs-file/__key/communityserver-discussions-components-files/2/People_2D00_Alchemy_2D00_Final_2D00_Incident_2D00_Report_2D00_2026_2D00_08_2D00_08.pdf) | 2026-08-08 | Medium (search snippet; PDF fetch failed) |
| 1.6 | **No browser documents the per-navigation check to the user.** Brave's user-visible surface is a database-manager page showing list status and last update; Chrome's is an internal debug page. **Implications:** The gap is not that a block happens; it is that the block is **unfalsifiable to the person seeing it**. Izcal already has the pieces for the opposite: the content-blocking decision log records list ID, version, entry ID and rule ID (CB §6.13), and networking attaches a typed `FailureReason` (NW §6.7). The phishing spec should make the interstitial a view over one recorded check: list name and version, entry, source, observation date, the exact URL and canonical form checked, the local result, and a contest action. That is a different product from "deceptive site ahead".

## 2. No transparency or audit for the list

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|

| 2.2 | **Chrome's equivalent is an internal diagnostic page, not a user surface.** A 2026 issue about reaching `chrome://safe-browsing/#tab-preferences` through a fragment shows the page exists but is gated as an internal debug page; triage treated access as working as intended. Nothing in normal settings shows list state | — | [Chromium issue 433295196](https://issues.chromium.org/issues/433295196) | 2026 | Medium |
| 2.3 | **The Safe Browsing protocol has list state but no user-visible version.** The v4 Update API carries `clientState`, checksums, partial updates, `minimumWaitDuration` (593.44 s in the example) and backoff on non-200 responses. The client knows its state; no browser publishes it to the user | ~9.89 min minimum wait in the example | [Safe Browsing v4 Update API](https://developers.google.com/safe-browsing/v4/update-api) | page current 2026-10 | High |
| 2.4 | **Enterprise control is a protection level, not a list audit.** Chrome Enterprise exposes a Safe Browsing protection-level policy with No protection, Standard and Enhanced values; when set as mandatory, users cannot change it. No per-list selection, list version, or last-check report is described | 3 values | [Chrome Enterprise policy list](https://chromeenterprise.google/policies/#SafeBrowsingProtectionLevel); CIS/DISA benchmark descriptions | accessed 2026-10-21 | Medium |
| 2.5 | **Per-navigation audit does not exist for developers either.** Safe Browsing checks are browser-level; the documented way to observe them is `chrome://net-export/` with the Netlog viewer, not the DevTools Network panel. There is no verdict, list version or entry in the exported page view | — | [Chrome network bug-triage documentation](https://chromium.googlesource.com/chromium/src/+/main/net/docs/bug-triage-labels.md); Stack Overflow note on net-export | accessed 2026-10-21 | Medium |

**Implications:** Izcal's list machinery is already more auditable than any browser's: TUF metadata, version-addressed diffs, a witness-cosigned transparency log with consistency proofs (CB-22), and a per-decision log. The phishing spec can expose, in ordinary UI, what only Brave exposes in an internal page and Chrome hides entirely: list version and hash, last successful update, next scheduled check, signature and witness checkpoint, and the last check for this navigation. The transparency log is the strongest answer to "which list do I have"; it should cover the phishing list too (Section 19).

**Implications:** False positives are not an edge case; they are a routine operating cost of URL reputation, concentrated on new domains, shared hosting and redirects. Izcal's content-blocking governance already commits to published appeals and legal demands (CB-D16) and to entries with evidence and revalidation (CB-21). The phishing spec should extend both to reputation entries, publish per-entry outcomes, and set a response target. It must also confront volume: a feed with ~124,500 domains rebuilt every five minutes cannot have two human reviewers per entry (Section 19). The honest design is source-level vetting, an automated allowlist of popular and shared-hosting domains, sampling, and a fast removal path, with the weaker per-entry guarantee published.

## 4. Privacy: what a check sends, and who can see it

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Chrome Standard protection sends a 4-byte hash prefix, not the URL, and only after a local miss.** The URL is SHA-256 hashed and truncated to 32 bits; prefixes are encrypted and sent through a privacy server (an Oblivious HTTP relay operated by Fastly) that strips the IP before forwarding to Google. Google sees the prefix but not the IP; the relay sees the IP but not the prefix | 4-byte prefix; 1,000 prefixes per request in v5 | [9to5Google](https://9to5google.com/2024/03/14/chrome-standard-safe-browsing/); [The Hacker News](https://thehackernews.com/2024/03/google-introduces-enhanced-real-time.html); [Safe Browsing v5 reference](https://developers.google.com/safe-browsing/reference/rpc/google.security.safebrowsing.v5) | 2024-03-14 | Medium (news); High (v5 field: `hash_prefixes`, 4 bytes) |
| 4.2 | **Chrome Enhanced protection sends far more.** Google's help page says Enhanced sends the visited site's URL, "a small sample of page content, extension activity, and system information", and performs "in-depth scans of suspicious downloads". Standard sends "an obscured URL portion" through privacy servers and sends "full URLs and bits of page content" only when a site behaves suspiciously | — | [Google Chrome Help: Enhanced protection](https://support.google.com/chrome/answer/9890866) | page current 2026-10 | High |
| 4.3 | **Brave proxies desktop checks and says URLs are never sent.** Only a prefix is sent, and only on a local prefix hit; desktop requests route through a Brave-operated proxy so Google never sees the user's IP. Android uses the OS SafetyNet service directly, so "your IP address may be seen (and logged) by Google"; iOS uses WKWebView, requests are initiated by the OS provider and cannot be proxied by Brave, and the IP "may be seen (and logged) by Apple, Google, or Tencent" | 4-byte prefix | [Brave: Safe Browsing](https://support.brave.app/hc/en-us/articles/15222663599629-Safe-Browsing-in-Brave) | 2024-05-03 | High |
| 4.4 | **Safari uses Google, and Tencent in mainland China, with Apple proxying.** Apple's 2019 statement said the actual URL is not shared and Tencent checks are limited to mainland China; from iOS 14.5 Apple began proxying Safe Browsing requests so the provider sees Apple's IP, not the user's | — | [MacRumors](https://www.macrumors.com/2019/10/14/apple-tencent-fraudulent-website-warning-check/); [The Hacker News](https://thehackernews.com/2021/02/apple-will-proxy-safe-browsing-requests.html) | 2019-10-14; 2021-02 | Medium |
| 4.5 | **Firefox keeps lists locally but still sends a prefix on a hit, and a file hash for some downloads.** Mozilla's answers say the lookup "does not include the complete address … only contains partial information derived from the address"; for downloads, Firefox submits "a cryptographic hash of the contents" for non-common binaries, which can be disabled in `about:config` | 4-byte prefix; SHA-256 file hash | [Mozilla Support Q&A 1220219](https://support.mozilla.org/questions/1220219); [Mozilla Support Q&A 1400401](https://support.mozilla.org/da/questions/1400401) | accessed 2026-10-21 | Medium |
| 4.6 | **DuckDuckGo is the closest to zero lookup traffic, but not zero.** The browser downloads a feed of the first eight characters of each malicious domain's SHA-256 hash and matches on-device. When a domain misses the common-threat list but its eight-character prefix matches, the browser sends "the first four characters of the domain's SHA-256 hash" to DuckDuckGo, which returns a refined candidate list; the page says these requests are not logged or stored | 8-char local prefix; 4-char lookup | [DuckDuckGo: Scam Blocker](https://safe.duckduckgo.com/duckduckgo-help-pages/threat-protection/scam-blocker) | page current 2026-10 | High |
| 4.7 | **No shipping browser offers a full local list with zero lookup traffic for every check.** Chrome, Brave, Firefox and Safari all send a prefix on a local hit; DuckDuckGo sends one only in a rare collision case; Android and iOS hand the check to an OS service the browser cannot proxy | — | 4.1–4.6 (inference) | — | Medium |
| 4.8 | **A 32-bit prefix is a membership signal.** An IACR ePrint analysis notes that a hit causes prefixes of URL components to be sent, which can identify small domains; Firefox mixes the true query with four random 32-bit hashes as masking, and Google can still often infer the visited unsafe URL | 32-bit | [IACR ePrint 2021/345](https://eprint.iacr.org/archive/2021/345/1615995468.pdf) | 2021 | Medium (abstract/paper) |

**Implications:** The privacy bar is now clear. A full local list is the only design with no lookup traffic in the common case; every browser that ships one still sends a prefix on a hit, and mobile hands the whole check to the OS. Izcal's SEC-D7 already chooses a v5 local-list design filled with Izcal's own data, and its privacy analysis covers "any later prefix check through a non-colluding relay". The phishing spec should make zero lookup the default, state in the UI exactly what a lookup would send if enabled, and treat a prefix lookup as an opt-in mode with its own consent and audit. That is a first among browsers, and it follows from owning the list and the network stack.

| 5.4 | **Platform dependence removes the protection without saying so.** Brave on Android cannot enable Safe Browsing on devices without Google Play Services, and on iOS the feature is an OS service the browser neither controls nor proxies | — | [Brave: Safe Browsing](https://support.brave.app/hc/en-us/articles/15222663599629-Safe-Browsing-in-Brave) | 2024-05-03 | High |
| 5.5 | **List age is visible only in an internal page.** Brave's `brave://safe-browsing/#tab-db-manager` shows status and last update; there is no site-panel row, warning, or settings label for "protection last updated at…" | — | same | 2024-05-03 | High |

**Implications:** Izcal's update system already has the primitives for the opposite: TUF metadata with expiry, rollback and freeze protection (UPD-R1), and SEC-17's requirement that "stale state [be] shown to the user". The phishing spec must define what happens at expiry (fail closed with a labelled interstitial, or fail open with a visible warning), show list age and next check in the site panel, and make enterprise-sourced lists and ages visible on `izcal://policy`. The content-blocking daily check (CB §6.9) is too slow for a phishing feed; the phishing list needs its own cadence and expiry (Section 19).

**Implications:** URL reputation keyed to the top-level navigation misses the surfaces where phishing actually arrives: an in-app WebView, a PWA in standalone mode, a saved `.hta`, a download, a QR code scanned by another device, an extension-initiated navigation, and an external protocol handoff. Izcal's advantage is that every one of these crosses an Izcal-owned boundary (navigation commit, download completion, external-protocol launch, extension `ext://` origin, installed-app launch). The phishing spec should define a **surface taxonomy** and require a check and a record at each boundary, including surfaces with no URL. The PWA and local-file cases also need a visible "what is this?" label, because the address bar is gone by design.

## 9. What no browser can show, and what Izcal can

The pattern across Sections 1–8: every browser can block, and almost none can **account** for the block. The record is split between a vendor's server, an internal debug page, and an expert netlog. No browser binds a verdict to the list version, the entry, the evidence, the exact URL, the surface, and the person or agent affected.

Izcal's existing decisions already supply the substrate:

- a per-decision log with list ID, version, entry ID and rule ID (CB §6.13);
- typed failure reasons that reach the shell and DevTools, never the page (NW §6.7);
- one URL parser and one canonicalization point (`hg-url`, NW §6.2);
- TUF-signed data channels and a witness-cosigned transparency log (UPD-R1, CB-22);
- deterministic recordings that replay every decision (DT-D2, CB §6.14);
- an agent principal with scoped capabilities and an audit log (B9, DT §6.5).

The phishing spec's opportunity is to make those five things one user-visible object: **a check record**. It is the unit the interstitial, the site panel, the DevTools view, the agent audit, the contest form and the replay all read. That is not a better interstitial; it is a different data model for reputation.

# Part D. The five gaps Izcal can uniquely close

1. **An evidence-bearing block.** Name the list, version, entry, source, observation date, checked URL and result, and offer a contest with an ID and a status. No browser does this; Chrome's own wording is "recently detected phishing".
2. **A per-navigation check record for people, developers and agent operators.** One record, read by the interstitial, the site panel, the IIP view, the agent audit and replay. No browser documents the check; Brave shows list state, not decisions.
3. **A genuinely local list with honest disclosure.** Izcal's own list, matched on-device, zero lookup by default; if a prefix lookup is ever enabled, show exactly what it would send. DuckDuckGo is closest but still sends a four-character prefix in rare cases; every other browser sends one on a hit.
4. **Visible freshness and defined stale behaviour.** Signed list, visible age, next check, expiry action and a labelled fail-closed or fail-open state. Brave documents a 45-minute validity and then silently ignores the list; no browser shows the user.
5. **Deterministic replay of a blocked navigation and an offline URL test.** Replay with and without the entry and diff the outcomes; test a URL against the pinned list offline with the exact canonical form. No browser or reputation service offers either.

The binding constraints on all five are in Part C: SEC-D7's mandate, M-1's no-source rule and MIT-only data rule, CB's uniform-list and witness-log constitution, the per-navigation consent model, the one URL parser, the per-hop Fetch checks, the prompt layer, and the DevTools recorded unit. Those are the interfaces the phishing spec must satisfy, not invent.
