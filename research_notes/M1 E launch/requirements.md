# M1 phase E (remainder): requirements and conflicts

Compiled 2026-10-26 from `reports/` at the branch's base (Stage 1 0.14.x, security scope 0.3.7, footprint, networking, distribution 0.4.1, OS integration 0.4.1, coding standard), the approved plan (`~/.claude/plans/m1-finish.md`, phase E) and the code on `substrate/m1e-launch`. The phase-E-pure items (BuildId, RecordingHeader/PolicyDigest, OsPort, hg-launch-wire, install device) are done on `substrate/m1e-pure` and are not repeated here.

## 1. Requirements

## 2. Conflicts and gaps

| # | Between | Conflict | Recommendation |
|---|---|---|---|
| **C1** | DU 13 item 1 ("the spawner opens O_PATH at its own start") vs probe E4/E4b | On a host with Ubuntu's AppArmor userns restriction, exec of an fd opened outside the child's new mount namespace is refused ("disconnected path"), and a procfs reopen does not help | E-R4: open the executable's fd inside the child's mount namespace from a directory fd the spawner holds; or skip the mount namespace on the restricted tier. Propose a DU amendment; don't edit the spec |
| **C2** | Stage 1 D-S5 (Windows launch at M5) vs the approved M1 plan (all three OSes) | The owner approved three OSes for M1, and D5 already ships the Windows IPC | Follow the approved plan: Windows launch in E at the FP-M0 sandbox level. The full 6.7 Windows set (alternate desktop, win32k lockdown, CIG) stays at M5. Propose a D-S5 note |
| **C3** | NW-M0 (sandboxed system, container and partition services with spares, socket broker with LNA tickets, OS adapter) vs M1 phase E | NW-M0 is a spec milestone that starts at M1, and its contents are networking-track work | E delivers the `hg-net-service` library and `hg-net-main` with the three configurations as **launch kinds** in the netns/no-socket sandbox, plus the round trip. Sockets, LNA and spares belong to NW-M0's own plan |
| **C4** | Approved plan ("six threat-model files") vs SEC-26 and security 9 (39 created, 6 filled) | The plan undercounted | Create all 39 from the template; fill the 6 |
| **C5** | Security 9 (`izcal://sandbox` at M1) vs M1 having no page renderer | The page cannot render until the renderer draws (M4) | M1 records the tier in `ready` (a `SandboxReport`), in the broker's log, and in a text dump the broker prints on request. The page shows the same record from M4. Propose a note |
| **C6** | Security 6.7 full rows vs what M1 can build | Empty root (Linux restricted hosts, E2), alternate desktop and win32k lockdown (Windows, M5), Landlock UDP (ABI ≥ 10; hueyj has 4) | Each gap is a **named reduced tier** in the SandboxReport (SEC-8), never silent |
| **C7** | hg-dst holds both the runner and `dst-smoke`; F's Q-CS-1 rule names `hg-dst` as a linker | The runner itself doesn't need the simulator | Move `dst-smoke` and the new scenarios to a `hg-dst-sim` package; `hg-dst` (the runner) stops linking `hg-substrate-sim`; F's rule names `hg-dst-sim` |
| **C8** | D3's `creator_pid` bootstrap check and D6's "writer only from the broker" by pid vs probe E12/E13 | In a PID namespace every outside process reads as pid 0 | E-R6: the child attests the broker by its bootstrap channel, not by pid |
| **C9** | Security 6.3 spawner row ("the broker re-checks the returned PID and namespace") | No mechanism is named | The spawner returns a pidfd plus the outer pid; the broker reads `NSpid` from the pidfd's fdinfo (E16) |
| **C10** | Footprint FP-D1 ("the child applies its seccomp filter and execve's") vs today's sandbox (the process applies seccomp after exec) | Before-exec filtering is stronger; after-exec allows the binary's own start-up first | Both: a small **launch filter** before exec that allows exactly the exec; the process's full filter after start-up (filters stack) |
| **C11** | Spawner IPC form | The spec gives "a fixed request struct", no protocol | A fixed-layout binary request and reply over one SEQPACKET socketpair, not `.hgidl` (G-rule: the spawner links no hg-ipc), with a Kani-proved decoder |
| **C12** | The plan's `process.hgidl` kinds (Browser, Renderer, Network×3, Spawner) | The broker is the browser and launches itself, and the spawner speaks no `.hgidl` | `ProcessKind`: Renderer, NetworkSystem, NetworkContainer, NetworkPartition. Browser and Spawner are not child kinds of this protocol |
| **C13** | Stage 1 2.1 layer list vs the M1 crates | `hg-browser`, `hg-renderer`, `hg-net-service` (the libraries S1-M1a requires), `hg-spawner-main` (FP-D1's spawner), `hg-launch-plan` and `hg-dst-sim` are not named in 2.1 | Propose the layers in the plan's E-R1 (L5, L4, L5, L6, L2, tools) as a 2.1 amendment |
