# Izcal animation: history and postmortems

Compiled 20 October 2026. Primary sources were preferred (specifications, W3C minutes and mailing lists, blink-dev threads, engine teams' blog posts, release notes, bug-tracker prose, Chrome use-counter data, MDN browser-compat-data).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known date not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no source code of any browser, engine or third-party project was read for this note. No code files, headers, commits, diffs or code-review pages of Blink, Gecko, WebKit, Servo, jQuery, GSAP, Lottie, Motion, Rive or web-animations-js were opened. Two search results pointed to Chromium commit mirrors (a `CompositeClipPathAnimations` change); they were not opened or used. The web-animations-js README and `docs/experimental.md` were read as prose; repository metadata (last push, release dates) came from the GitHub API. Where this note says what an engine "does", it is evidence to reason from, not a shape to copy.

## 1. Script-driven animation: DHTML, timers and jQuery (1996–2011)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **DHTML animation** moved elements by changing style properties from `setTimeout`/`setInterval` callbacks. The era had no compositor, no frame callback and no shared clock. Every script picked its own interval and the browser painted whenever it could. | — | Researcher recollection; problem statement confirmed in 1.4 and 5.1 | 1997–2010 | Low |
| 1.2 | **jQuery `.animate()`** stepped all running animations from one global timer. `jQuery.fx.interval` (added 1.4.3) defaulted to **13 ms**. It was deprecated in 3.0 and removed in 4.0 because it "has no effect in browsers that support the requestAnimationFrame method". | 13 ms | [jQuery API: jQuery.fx.interval](https://api.jquery.com/jQuery.fx.interval/) | 2010–2024 | High |
| 1.3 | jQuery 1.6 adopted `requestAnimationFrame` and **1.6.3 removed it**. Animations started in a hidden tab "stack" up and do not run until the tab regains focus, and then play all at once. Code that queued animations from timers assumed frames always arrive. | 1.6 → 1.6.3 | [jQuery 1.6.3 released](https://blog.jquery.com/2011/09/01/jquery-1-6-3-released/) | 2011-09-01 | High |
| 1.4 | Robert O'Callahan stated the timer problem plainly: "there is no 'right' timeout value". Authors cannot know the frame rate, which changes moment to moment, and timers keep sampling when nothing is visible. | — | [O'Callahan, mozRequestAnimationFrame](https://robert.ocallahan.org/2010/08/mozrequestanimationframe_14.html) | 2010-08-14 | High |

**Implications:** Timer-driven animation failed because it had no knowledge of frames or visibility. Its successor, rAF, broke code that assumed time and frames move together (1.3). Izcal must keep the HTML timer clamps and the rAF hidden-document semantics exactly as specified, since deployed libraries depend on both.

## 2. Declarative timing: SMIL, HTML+TIME and SVG animation (1998–2026)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **SMIL 1.0** (W3C Recommendation, June 1998) defined timed multimedia presentations with time containers (`par`, `seq`) for synchronizing media. It targeted standalone players such as RealPlayer, not HTML browsers. | REC 1998-06-15 | W3C TR history; HTML+TIME (2.2) calls it "the SMIL Recommendation" in Sept 1998 | 1998 | Medium |
| 2.2 | **HTML+TIME** (W3C Note, 18 Sept 1998) proposed bringing SMIL timing into HTML. Authors were from Microsoft, Compaq/DEC and Macromedia, with review from Digital Renaissance. It "is not intended to supplant SMIL" and added an object model, which SMIL lacked. Internet Explorer 5 and 5.5 shipped it as "behaviors" (later "HTML+TIME 2.0"). | Note 1998-09-18 | [NOTE-HTMLplusTIME](https://www.w3.org/TR/NOTE-HTMLplusTIME) | 1998 | High (Note); Low (IE ship) |
| 2.3 | **SMIL Animation** (REC, 4 Sept 2001) is "a true subset of SMIL 2.0" for XML hosts, with **no time containers**. It defined the **sandwich model**: a running animation "does not actually change the attribute values in the DOM"; it writes a separate presentation value over an unchanged base value. Web Animations kept this model (7.1). | REC 2001-09-04 | [SMIL Animation](https://www.w3.org/TR/smil-animation/) | 2001 | High |
| 2.4 | **SVG 1.0/1.1** adopted SMIL Animation (`<animate>`, `<set>`, `<animateMotion>`, `<animateTransform>`). It could animate **any attribute**, including path data (morphing), and could run inside SVG used as an image, where script cannot. | SVG 1.1 REC 2003 | BCD: `svg.elements.animate` Chrome 2, Firefox 4, Safari 3.1 | 2001–2011 | Medium |
| 2.5 | **Internet Explorer never implemented SMIL in SVG.** At the SVG WG on 30 April 2015, Microsoft's Rossen Atanassov, asked when IE would implement it, answered "Never", and said Edge would be considered separately. | — | [SVG WG minutes 2015-04-30](https://www.w3.org/2015/04/30-svg-minutes.html) | 2015-04-30 | High |
| 2.6 | **Blink "Intent to deprecate: SMIL"** (Philip Rogers, with Eric Willigers, 29 April 2015): "deprecate SMIL animations in favor of CSS animations and Web animations". Reasons: "SMIL was never implemented in all major browsers which limited its use" and "SMIL adds significant complexity to Blink". It asked only for a console warning, not removal. Usage was "low but stable at **0.0403%** of pageviews", and **0.006%** for SMIL inside images, where polyfills cannot run. | 0.0403%; 0.006% | [blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/5o0yiO440LM/m/59rZqirUQNwJ) | 2015-04-29 | High |
| 2.7 | Replies the same day gave three LGTMs. Chris Harrelson proposed removal in **M45**. Elliott Sprehn asked how authors would embed animated `.svg` files without inline SVG. Tobi Reif objected that existing content would break. | — | Same thread | 2015-04-29/30 | High |
| 2.8 | The SVG WG reacted the next day. Participants listed gaps CSS and Web Animations could not fill: declarative **path animation** ("really unhappy to lose"), several independent animations on one element, **chaining**, and **event-driven begin** beyond CSS pseudo-classes. Brian Birtles noted Web Animations had **no declarative syntax**. Resolution: "Move the SVG Animation features to a separate spec." | — | [SVG WG minutes 2015-04-30](https://www.w3.org/2015/04/30-svg-minutes.html) | 2015-04-30 | High |
| 2.9 | Chrome shipped the warning: by October 2015 developers saw "SVG's SMIL animations (`<animate>`, `<set>`, etc.) are deprecated and will be removed" in the console. | — | [www-svg, Mulder](https://lists.w3.org/Archives/Public/www-svg/2015Oct/0033.html) | 2015-10-26 | High |
| 2.10 | **The deprecation was suspended in 2016**, after developers showed that SMIL features such as path morphing and animation inside SVG images had no CSS or Web Animations equivalent. The suspension message itself was not found; secondary sources disagree on the month (August vs late 2016). | — | Secondary pages summarized in search results; [ZKM "Format Obsolescence"](https://extinction.zkm.de/events/smil-browser-support-collapse) | 2016 | Low |
| 2.11 | **SMIL survived** in all three engines. BCD lists `<animate>` in Chrome, Firefox and Safari, and Edge inherited it when it moved to Chromium (2020). | — | BCD 8.1.6 | 2026-10 | High |
| 2.12 | **Usage grew after the reprieve.** Chrome's `SVGSMILElementInDocument` counter went from **0.047%** of page loads (1 Jan 2015) to **2.90%** (18 Oct 2026). `SVGSMILAnimationInImageRegardlessOfCache` is **1.67%**. Caveat: Chrome's counting changed around 2017–2018 (the unprefixed rAF counter jumps from 5.5% to 27% in the same period), so the ratio is indicative only. | 0.047% → 2.90% | [chromestatus feature popularity data](https://chromestatus.com/data/featurepopularity) | 2015–2026 | High (values); Medium (trend) |

**Implications:** SMIL is a case of the "never break the web" rule plus missing replacements. A deprecation driven by code complexity was reversed because the replacements could not express path morphing, syncbase chaining or script-free animation inside images. Izcal must implement SVG SMIL animation on the same timing core as CSS and Web Animations, not as a side engine, because it is used on about 3% of page loads.

## 3. Flash and plug-in animation (1996–2020)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Flash** (Macromedia, then Adobe) supplied vector animation, a timeline authoring tool, scripting (ActionScript) and video when browsers had none of these. It ran in a plug-in with its own renderer and clock, outside the page's layout, accessibility and event model. | — | Researcher recollection | 1996–2010 | Low |
| 3.2 | Apple refused Flash on iPhone and iPad. Steve Jobs's "Thoughts on Flash" (29 April 2010) gave reasons: closed and proprietary, reliability, security and performance, **battery life** (no hardware video decoding), **touch** (Flash content relied on mouse rollovers), and a third-party layer between developers and the platform. It named HTML5, CSS and JavaScript as the replacement. | 6 reasons | "Thoughts on Flash" (apple.com page now 404; not re-read) | 2010-04-29 | Medium |
| 3.3 | **Adobe announced Flash's end** on 25 July 2017: it would stop updating and distributing Flash Player at the end of 2020, because "open standards like HTML5, WebGL and WebAssembly have matured" and browser vendors were moving plug-in functionality into browsers. | EOL end of 2020 | [Adobe, "Flash & the future of interactive content"](https://blog.adobe.com/en/publish/2017/07/25/adobe-flash-update) | 2017-07-25 | High |
| 3.4 | **What survived:** timeline-based vector animation authored in a design tool survives as **Lottie** (After Effects to JSON) and **Rive** (13.1, 13.5). The plug-in boundary did not survive. | — | Section 13 | — | Medium |

**Implications:** Flash's fate shows that power, touch input and security, not visual capability, decided animation technology on mobile. Izcal's animation design should treat **energy per animated frame** and **input latency** as first-class targets, and should make design-tool animation formats (Lottie, Rive) cheap to run through the platform's own primitives (canvas, WebGPU, Web Animations) rather than through any special runtime.

## 4. CSS Transitions, Animations and Transforms (2007–2026)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | Dave Hyatt introduced **CSS Transitions** on the WebKit blog on 31 October 2007, as "implicit animations" that run when a property value changes. Existing scripts and stylesheets work unchanged, and the feature "degrade[s] gracefully". The same post showed animated `-webkit-transform` and promised a "more detailed proposal" for transforms, animation and other effects. | — | [WebKit blog: CSS Animation](https://webkit.org/blog/138/css-animation/) | 2007-10-31 | High |
| 4.2 | The proposals came from Apple's iPhone work, where WebKit drew transforms and opacity with Core Animation on the GPU. 3D transforms "have been supported on iPhone since 2.0" and reached Mac WebKit in July 2009. | iPhone OS 2.0 (2008) | [WebKit blog: 3D Transforms](https://webkit.org/blog/386/3d-transforms/) (Fraser) | 2009-07-16 | High (3D dates); Medium (Core Animation link) |
| 4.3 | **Prefixed shipping:** `-webkit-transition` in Safari 3.1, `-webkit-animation` in Safari 4 and Chrome 3, `-moz-` versions in Firefox 4–5. Unprefixed: Firefox 16, Safari 9, Chrome 26 (transitions) and 43 (animations). Firefox 49 also accepts `-webkit-` aliases, a compatibility cost of the prefix era. | 2008 → 2015 | BCD 8.1.6 | 2008–2016 | High |
| 4.4 | The WebKit editors (Jackson, Hyatt, Marrin) handed the specs to the CSSWG. **CSS Transitions 1 was still a Working Draft on 8 January 2026**, edited by L. David Baron (Google) and Brian Birtles (Mozilla). It defines **before-change** and **after-change style**; a transition starts only when values are neither "not animatable" nor "discrete". | WD 2026-01-08 | [CSS Transitions 1](https://www.w3.org/TR/css-transitions-1/) | 2026-01-08 | High |
| 4.5 | **Limit of the transition model:** a transition needs a previous computed style. An element inserted, or switched from `display: none`, has none, so it cannot transition in, and `display` itself is discrete. That gap stayed open until 2023 (section 11). | — | 4.4; [Chrome: entry/exit animations](https://developer.chrome.com/blog/entry-exit-animations) | 2007–2023 | High |
| 4.6 | **Interop:** Compat 2021 and Interop 2022–2023 carried a **Transforms** area; Interop 2023 added **Motion Path** ("now supported in all three engines. **Implications:** CSS animation was designed around one platform's GPU compositor (Core Animation) and around implicit, stateless triggers. The style-change-event model that defines when transitions start is subtle and still a Working Draft. Izcal's style engine must compute before-change and after-change styles as defined, deterministically, and test them against WPT, since that is where engines historically diverged.

## 5. requestAnimationFrame and background throttling (2010–2026)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **`mozRequestAnimationFrame`** landed in Firefox 4 beta 4. Its design goals: let the browser choose the frame rate; give all animations started in the same frame **the same start time**, shared with CSS transitions and SMIL; and let hidden pages drop to about **1 frame per second** (not yet implemented then). | ~1 fps hidden | [O'Callahan](https://robert.ocallahan.org/2010/08/mozrequestanimationframe_14.html) | 2010-08-14 | High |
| 5.2 | Paul Irish popularised it with a shim covering `webkit` and `moz` prefixes. Arguments: hidden tabs stop the loop, saving CPU, GPU, memory and battery; the browser batches concurrent animations into one reflow and repaint. By March 2013 the `ms` and `o` prefixes were no longer needed. | — | [Irish, rAF for smart animating](https://www.paulirish.com/2011/requestanimationframe-for-smart-animating/) | 2011-02-22 | High |
| 5.3 | **Shipping:** prefixed in Firefox 4, Chrome 10, Safari 6; unprefixed in Chrome 24, Firefox 23, Safari 7. Unprefixed rAF is hit on **65.1%** of Chrome page loads; the prefixed form on 0.036%. | 65.1% | BCD 8.1.6; [chromestatus popularity](https://chromestatus.com/data/featurepopularity) | 2026-10-18 | High |
| 5.4 | **HTML's model** today: a navigable has a "rendering opportunity" according to "hardware refresh rate constraints and user agent throttling"; "This specification does not mandate any particular model". Its example: 60 Hz, dropping to 30 to avoid irregular drops, and "4 rendering opportunities per second, or even less" when hidden. Hidden documents are filtered out of update-the-rendering, so rAF does not run. | 16.7 ms example | [HTML: event loop processing model](https://html.spec.whatwg.org/multipage/webappapis.html#rendering-opportunity) | 2026 | High |
| 5.5 | **Timer throttling** grew in steps. Chrome 88 (Jan 2021) added "intensive throttling": timers in pages hidden over 5 minutes, silent for 30 s, with chain count ≥ 5, run **once per minute**. rAF "waits for the page to become visible". | 4 ms; 1 s; 1 min | [Chrome: timer throttling in Chrome 88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88) | 2021-01 | High |
| 5.6 | Chrome 52 added an intervention throttling the rendering pipeline of off-screen cross-origin frames; Firefox and Safari also ship such throttling per chromestatus. An effort to standardise iframe throttling is marked "No active development". | Chrome 52 | [chromestatus 4514713492783104](https://chromestatus.com/feature/4514713492783104); [5175574929080320](https://chromestatus.com/feature/5175574929080320) | 2016; 2022 | Medium |
| 5.7 | **Long Animation Frames** (LoAF) timing shipped in Chrome 123 to attribute slow frames to scripts; Firefox "Positive", Safari "No signal". | Chrome 123 | [chromestatus 6118675067699200](https://chromestatus.com/feature/6118675067699200) | 2024 | Medium |

**Implications:** rAF moved the clock from the page to the browser, but HTML left frame selection, throttling and hidden-state policy to each user agent. These are observable (frame timestamps, callback counts) and are fingerprinting surfaces. Izcal must pick them deliberately: one documented frame-scheduling policy, deterministic under replay (B1), with timestamps coarsened like other timers.

## 6. Compositor-driven ("accelerated") animation in each engine (2008–2026)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **WebKit on iPhone and Mac** handed `transform` and `opacity` animations of composited layers to **Core Animation**, which interpolated them in the OS's render server. This is the origin of the "only transform and opacity are cheap" folklore: those were the properties Core Animation could apply to a layer without repainting. | — | Researcher recollection; consistent with 4.2 and 6.9 | 2008– | Low |
| 6.2 | **Chrome's compositor (cc)** document (Wiltzius, Kokkevis, last updated May 2014) traces the path from software painting to a compositor on the main thread, then its **own thread**, then impl-side painting and the übercompositor. "Thus far CSS animations and CSS filters are the only other major compositor-driven page updates" besides scrolling. Layer triggers include an animated `opacity` or `transform` and accelerated filters; overlap causes "layer explosion", mitigated by squashing. | — | [GPU Accelerated Compositing in Chrome](https://www.chromium.org/developers/design-documents/gpu-accelerated-compositing-in-chrome/) | 2014-05 | High |
| 6.3 | **Firefox OMTA** (off-main-thread animation) of `transform` and `opacity` shipped on desktop and Android in **Firefox 41** (Sept 2015), after running in Firefox OS since 1.0. Limits: no 3D transforms in a `preserve-3d` scene; transform animations stay on the main thread if the same animation also changes geometry (to avoid drift); no SVG transforms. On `getComputedStyle()` the main thread recomputes the current value. | Firefox 41 | [Baron, compositor animations](https://dbaron.org/log/20150916-compositor-animations) | 2015-09-16 | High |
| 6.4 | **Why the restriction:** in each engine the compositor holds layers, not layout boxes. Only properties that change a layer's matrix, opacity or filter can be applied without paint. Baron describes the mechanism (send keyframes and timing functions to the layer), not a policy. | — | 6.2, 6.3 | 2014–2015 | High |
| 6.5 | Chrome later composited more: **SVG** animations in Chromium 89, **percentage translate** when the box size is not changing each frame. `background-color` and `clip-path` "will soon join the list"; Chrome chose them by measuring which properties are animated most. | Chromium 89 | [Chrome: hardware-accelerated animation updates](https://developer.chrome.com/blog/hardware-accelerated-animations) (Kravets) | 2021-02-22 | High |
| 6.6 | **Composited `background-color` result:** Chrome's animation team saw "more animations being composited" but **no improvement in PercentDroppedFrame**, possibly because such animations are "mostly applied on small buttons", and a **memory regression** (crbug 1210221). | —  A later stable-channel trial on 1% of users reported \"very good results on throughput metrics\" with about 1.5% more memory on Windows ([October 2021](https://www.chromium.org/teams/animations/highlights-archive/october-2021---2-sprints-worth-of-highlights); CF 1.7), so the two trials conflict (added in phase 8). | [Chromium animations highlights, June 2021](https://chromium.org/teams/animations/highlights-archive/june-2021---new-features-stability-fixes-interop-fixes-and-more) | 2021-06 | High |
| 6.7 | Whether composited `background-color` and `clip-path` then shipped by default was not confirmed from prose this session. Motion's Matt Perry (Nov 2025) lists `transform`, `opacity`, `filter` and `clip-path` as compositor-capable. | — | [Motion: Web animation performance tier list](https://motion.dev/blog/web-animation-performance-tier-list) | 2025-11-05 | Medium |
| 6.8 | **Two engines per browser.** Perry: the compositor engine "doesn't have to be spec-complete"; when it lacks a feature the browser **silently** falls back to the main thread. He calls Safari "the biggest offender": no dedicated compositor animation engine, reliance on Core Animation, and `playbackRate ≠ 1` loses acceleration. Changing a CSS variable always triggers paint; one site restyled 1,300+ elements at about 8 ms per frame by animating a global variable. | ~8 ms/frame | [Motion tier list](https://motion.dev/blog/web-animation-performance-tier-list) | 2025-11-05 | Medium (vendor claim) |
| 6.9 | **WebKit's scroll-driven animations are not accelerated.** Antoine Quint (Apple), 1 April 2025: no hardware acceleration in Safari yet; that work depends on "threaded animation resolution" (WebKit bug 250970). | — | [WebKit bug 222295](https://bugs.webkit.org/show_bug.cgi?id=222295) | 2025-04-01 | High |
| 6.10 | Chrome counts `SyntheticKeyframesInCompositedCSSAnimation` on **28.1%** of page loads: most pages run at least one composited CSS animation that needed a synthesised keyframe. | 28.1% | [chromestatus popularity](https://chromestatus.com/data/featurepopularity) | 2026-10-18 | High (value); Medium (reading) |

**Implications:** Every engine built two animation engines, a complete one on the main thread and a partial one beside the compositor, and the boundary between them is invisible to authors and differs per engine. Izcal should have **one** animation sampler that is a pure function of (timeline time, effect, base style) and can run on any thread. The renderer decides per frame whether the result needs paint or only a layer update. Fallbacks must be visible in DevTools, not silent.

## 14. Technology mismatches: assumptions that no longer hold

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 14.1 | **Fixed 60 Hz.** Timers of 13 ms (jQuery) or 16.7 ms assumed 60 Hz. Displays now run at 90–144 Hz or vary (VRR, ProMotion 10–120 Hz). HTML uses 60 Hz only as an example and leaves the rate to the user agent (5.4). | 13 ms; 16.7 ms | 1.2; [HTML rendering opportunity](https://html.spec.whatwg.org/multipage/webappapis.html#rendering-opportunity) | 2026 | High |
| 14.2 | **Safari still caps page rendering near 60 fps on ProMotion by default**, via a "Prefer Page Rendering Updates near 60fps" feature flag that users can switch off; reports say Chrome and Firefox do not cap. | ~60 fps | [WebKit bug 294338](https://bugs.webkit.org/show_bug.cgi?id=294338) and third-party guides (via search summary) | 2025–2026 | Medium |
| 14.3 | **One main thread.** CSS and SMIL were specified as if style, layout and animation sampling all run on one thread. Every engine then moved a subset off-thread (6.2–6.3), creating two engines with silent fallbacks (6.8). | — | Section 6 | 2012– | High |
| 14.4 | **GPU layers as the unit of cheap animation.** The transform/opacity rule follows the layer model of 2008–2014 compositors. Composited `background-color` gave no smoothness gain and cost memory (6.6). With GPU rasterization and display lists, the cost of re-rasterizing small areas has changed, and the layer boundary is not the only possible line. | — | 6.1, 6.6 | 2008–2021 | Medium |
| 14.5 | **Time as the only clock.** Animation timing assumed wall-clock time. Scroll and view timelines (section 9) and navigation-driven transitions (section 10) now drive animations from position and navigation state. | — | Sections 9, 10 | 2023– | High |
| 14.6 | **Always-visible page.** Early timer animation assumed frames always arrive; hidden-tab throttling broke that (1.3, 5.5). Battery-powered devices made throttling permanent. | 1 min timers | 1.3, 5.5 | 2011– | High |
| 14.7 | **Mouse input.** Hover-driven animation assumed a pointer; touch removed rollovers (Jobs, 3.2). Animation Worklet's V2 aimed at touch and gesture input but never shipped (8.2). | — | 3.2, 8.2 | 2010– | Medium |

**Implications:** Izcal should not hard-code a frame period, a thread or a layer rule into animation semantics. The sampler takes a timestamp from the frame scheduler, which reads the display's actual (possibly variable) refresh, and its result must be identical whichever thread computes it.

## 15. Cross-cutting lessons for Izcal

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 15.1 | **Removal fails without full replacement.** SMIL's deprecation was reversed (2.10), and its usage then rose about 60x (2.12). | 0.047% → 2.90% | 2.6–2.12 | 2015–2026 | Medium |
| 15.2 | **Unification costs a rewrite if done late.** WebKit spent over two years rebuilding on Web Animations (7.5). | > 2 years | 7.5 | 2020 | High |
| 15.3 | **Imperative extension points stalled; declarative features shipped.** Animation Worklet stayed in origin trial with 0% use (8.3), while `@property`, `linear()`, `@view-transition` and scroll timelines shipped and spread (8.5, 11.3, 10.6). | 0% vs 12–19% | Sections 8, 10, 11 | 2018–2026 | High (data); Medium (inference) |
| 15.4 | **Off-main-thread animation is per-engine and partial**, and authors cannot see when it falls back (6.3, 6.8, 6.9). | — | Section 6 | 2015–2026 | High |
| 15.5 | **Scope cuts to ship sooner stay cut.** Groups were deferred in 2015 "to iterate more quickly" and were still unshipped eleven years later (7.2–7.3), which keeps JS sequencing libraries in use (13.5). | 11 years | 7.2, 7.3 | 2015–2026 | High |

**Implications:** Izcal should (1) build one timing core for CSS Transitions, CSS Animations, SMIL, Web Animations, scroll/view timelines and View Transitions; (2) make the animation sampler a deterministic pure function that can run on the main thread or beside the compositor with bit-identical results (B1), so the "two engines" problem never arises; (3) choose what to update without repaint from measured cost, not from the inherited transform/opacity list; (4) schedule frames from the actual display refresh, with documented, privacy-reviewed throttling; (5) expose every animation, its timeline, its thread and any fallback in DevTools.
