**Implications:** Animation code has had memory-safety bugs at roughly the density of layout code, and a much higher share of **in-the-wild exploits** (section 3). The bugs are almost all lifetime bugs. Animation code lives on a graph (timeline → animation → effect → target element → style → frame), that graph is torn down by DOM mutation, GC and cycle collection, and it is walked every frame. A Rust animation engine with typed handles and no `unsafe` removes the class. The design must still make **"walk the graph while script runs"** impossible (section 2), or the bug comes back as a logic bug (a stale handle that is valid but points at the wrong thing).

**Implications:** Three rules close nearly every class. (1) **No script runs while the animation graph is being walked.** The timeline tick computes a list of state changes and promise settlements. Those are applied, and microtasks run, only after the walk ends, exactly at the spec's checkpoint. (2) **Animations, timelines and effects are owned by one arena per document**, addressed by generational handles, and are never freed while a tick holds a handle. (3) **Refresh-driver registration is idempotent by type** (a set, not a list), so CVE-2019-9796's double registration cannot exist.

**Implications:** The animation system is the **clock** that most rendering-timing attacks use. Coarsening `performance.now()` does not help, because the attacker counts frames. The working defences cut the dependence of render time on secret state: partitioned `:visited` (4.6), no filters or effects that read pixels of cross-origin content at data-dependent cost (4.3, 4.7), and visited and unvisited links on identical paint paths. For Izcal this means **constant-work paint of cross-origin content** (an iframe is composited as an opaque surface the embedder's filters cannot sample, or the filter cost cannot depend on its pixels) and **frame cadence that does not depend on secret-dependent work in another origin's process**.

**Implications:** View Transitions are the one animation feature that **copies pixels across a navigation**. Izcal should treat the snapshot as an opaque, process-local texture that is never readable by script, never sent to another origin's process, and dropped when the transition ends. Old and new documents are same-origin and so share a renderer process under FP-D8 site keying, but **cross-origin iframes inside the captured element** are other processes' surfaces. They must be composited by reference, never read back into the transition's image. Every limit (maximum snapshot size, maximum named elements, timeout) should be a **published constant** so behaviour is deterministic.

**Implications:** The specs allow unbounded inputs everywhere (infinite iterations, any number of keyframes, any number of animations, open SMIL cycles) and leave resources to the UA. Izcal needs **published, deterministic budgets**: a cap per document on live animations, keyframes per effect, SMIL instance times and intervals generated per tick, with defined, testable fallbacks (for example, extra SMIL intervals are dropped in document order). Time arithmetic must be **saturating fixed-point or checked f64** with defined handling of ∞ and NaN. Iteration index computation must never wrap. Event dispatch must coalesce to at most a fixed number of events per animation per frame.

**Overall implications.** Animation needs the same no-re-entrancy, arena-handle design as layout. It also needs three things layout does not: (a) **promise and event deferral** at exactly the spec's checkpoints, since the in-the-wild exploits all freed a graph node from script during a tick; (b) the **frame clock treated as a security boundary**, with render time kept independent of cross-origin and history state; and (c) **published resource budgets and a flash detector**, which no other engine provides and which Izcal's ownership of the compositor makes possible.
