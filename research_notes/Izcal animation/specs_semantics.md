## 2. Web Animations 1: timelines, time and the frame procedure

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | A **time value** is a real number that "nominally" represents milliseconds, or **unresolved**. In the API it is a `double`, with `null` for unresolved. | ms; `double?` | [WA1 §4.2](https://drafts.csswg.org/web-animations-1/#time-value-section), [§6.1](https://drafts.csswg.org/web-animations-1/#time-values-in-the-programming-interface) | 2026-10-08 | High |
| 2.2 | A timeline is **inactive** when its time is unresolved. A **document timeline**'s time is a fixed offset (its **origin time**) from the `now` timestamp passed to each "update animations and send events". It is inactive before the document's time origin is established and whenever its Document is not active, and monotonically increasing once active. The **default document timeline** has origin time 0 and survives `document.open()`. | origin time 0 | [WA1 §4.3](https://drafts.csswg.org/web-animations-1/#timelines), [§4.3.1](https://drafts.csswg.org/web-animations-1/#document-timelines), [§4.3.1.1](https://drafts.csswg.org/web-animations-1/#the-documents-default-timeline) | 2026-10-08 | High |
| 2.3 | `document.timeline.currentTime` **does not change between calls to update animations and send events**, so it is constant within a task, and it equals the `requestAnimationFrame` callback argument for the same frame. | difference = 0 | [WA1 §6.13](https://drafts.csswg.org/web-animations-1/#model-liveness), [§4.3.1.2](https://drafts.csswg.org/web-animations-1/#document-wallclock-time) | 2026-10-08 | High |
| 2.4 | **Update animations and send events(doc, now)**: (1) update the current time of every timeline associated with doc, which updates each animation's current time, runs "update an animation's finished state" and queues animation events; (2) **remove replaced animations**; (3) **perform a microtask checkpoint** (so promise reactions run before events); (4) copy and clear doc's **pending animation event queue**; (5) **stable-sort** by scheduled event time (unresolved times first), ties by composite order; (6) dispatch. Each run establishes a new **animation frame**; API changes only update the current frame. | 6 steps | [WA1 §4.4](https://drafts.csswg.org/web-animations-1/#update-animations-and-send-events) | 2026-10-08 | High |
| 2.5 | An **animation** has a timeline, an associated effect, a **start time** and a **hold time** (both initially unresolved), a playback rate (initially 1), an optional **pending playback rate**, and a **previous current time**. **Current time** = hold time if resolved; else unresolved if no timeline, inactive timeline or unresolved start time; else `(timeline time − start time) × playback rate`. Animations are appended to a **global animation list** in creation order. | formula | [WA1 §4.5](https://drafts.csswg.org/web-animations-1/#animations), [§4.5.1](https://drafts.csswg.org/web-animations-1/#the-current-time-of-an-animation) | 2026-10-08 | High |
| 2.6 | **Play states** derive from start time × hold time plus pending tasks: idle (both unresolved, no pending task), paused (pending pause task, or unresolved start without a pending play task), finished (resolved current time at or past the boundary for the effective playback rate), else running. "Paused wins over finished." A playback rate of 0 gives a running animation whose time never changes. | 4 states | [WA1 §4.5.17](https://drafts.csswg.org/web-animations-1/#play-states) | 2026-10-08 | High |
| 2.7 | **Pending tasks and "ready".** `play()` and `pause()` do not take effect synchronously: they schedule a **pending play task** or **pending pause task** that runs "as soon as animation is ready", i.e. when the UA has done any setup "including rendering the first frame of any keyframe effect" and the timeline is active. The play task sets the start time to `ready time − hold time / playback rate`. The UA "may schedule the above task as a microtask … but it must not perform the task synchronously". This is the spec's hook for starting a compositor or other-process animation without a first-frame jump. | async, ≥ microtask | [WA1 §4.5.6](https://drafts.csswg.org/web-animations-1/#waiting-for-the-associated-effect), [§4.5.8](https://drafts.csswg.org/web-animations-1/#playing-an-animation-section), [§4.5.9](https://drafts.csswg.org/web-animations-1/#pausing-an-animation-section) | 2026-10-08 | High |
| 2.8 | The **current ready promise** starts resolved, is replaced when a pending task is queued with none outstanding, and is shared by play and pause requests. Canceling (via "reset an animation's pending tasks") rejects it with `AbortError`, marks it handled and replaces it with a resolved promise. | — | [WA1 §4.5.7](https://drafts.csswg.org/web-animations-1/#the-current-ready-promise), [§4.5.14](https://drafts.csswg.org/web-animations-1/#canceling-an-animation-section) | 2026-10-08 | High |
| 2.9 | **Auto-rewind.** `play()` passes auto-rewind = true: with rate ≥ 0 and current time unresolved, < 0 or ≥ end, it seeks to 0; with rate < 0 and time unresolved, ≤ 0 or > end, it seeks to the end, throwing `InvalidStateError` if the end is +∞. An idle animation always plays from 0 regardless of the flag. On a timeline that is not monotonically increasing ("has finite timeline", i.e. scroll), the seek sets the **start** time instead of the hold time. | — | [WA1 §4.5.8](https://drafts.csswg.org/web-animations-1/#play-an-animation) | 2026-10-08 | High |
| 2.10 | **Finished state** is recomputed on every model change and in each frame by "update an animation's finished state(did seek, synchronously notify)". Without a seek, the hold time is clamped to max(previous current time, end) (or min with 0 in reverse), so a finished animation "sticks" at its boundary. Notification (resolve the finished promise, queue `finish` with scheduled time = effect end converted to origin-relative time) runs in a **microtask** unless `finish()` was called, which notifies synchronously. The finished promise is replaced every time the animation leaves the finished state. | — | [WA1 §4.5.12](https://drafts.csswg.org/web-animations-1/#updating-the-finished-state), [§4.5.13](https://drafts.csswg.org/web-animations-1/#finishing-an-animation-section) | 2026-10-08 | High |
| 2.11 | **`updatePlaybackRate()`** sets a pending playback rate that is applied after "any necessary synchronization" with another thread or process, so a compositor animation can change speed without a jump. `reverse()` negates the effective rate and plays with auto-rewind. | — | [WA1 §4.5.15.2](https://drafts.csswg.org/web-animations-1/#seamlessly-updating-the-playback-rate-of-an-animation), [§4.5.16](https://drafts.csswg.org/web-animations-1/#reversing-an-animation-section) | 2026-10-08 | High |
| 2.12 | **Animation events**: playback events are `finish`, `cancel` (entering idle from another state) and `remove`. Each Document keeps a pending animation event queue with a **scheduled event time** ("when the event would ideally have been dispatched were animations updated at an infinitely high frequency"), unresolved for scroll timelines. CSS animation and transition events share this queue and sorting. Playback events fire even when the effect is absent. | 3 types | [WA1 §4.5.18](https://drafts.csswg.org/web-animations-1/#animation-events-section), [§4.5.18.1](https://drafts.csswg.org/web-animations-1/#sorting-animation-events) | 2026-10-08 | High |

**Implications:** the timing model is a small, closed state machine (start time, hold time, pending tasks, pending rate, previous current time) whose transitions are fully specified, so Izcal can implement it as a pure, recorded function of `now` (B1) and property-test it against the spec's invariants. The "ready" moment is the only point where Izcal chooses a time, and it must be a recorded decision point.

## 3. Web Animations 1: effects, keyframes, composition and the cascade

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Active duration** = iteration duration × iteration count, defined as 0 if either is 0 (to avoid ∞ × 0). **End time** = max(start delay + active duration + end delay, 0). Intervals are **endpoint-exclusive** `[begin, end)`, except that a fill that begins exactly at an iteration end holds that endpoint. | — | [WA1 §4.6.5.2](https://drafts.csswg.org/web-animations-1/#the-active-duration), [§4.6.5.3](https://drafts.csswg.org/web-animations-1/#the-end-delay), [§4.6.9.3](https://drafts.csswg.org/web-animations-1/#interval-timing) | 2026-10-08 | High |
| 3.2 | **Phases** (before, active, after, idle) use the before-active boundary `max(min(delay, end), 0)` and active-after boundary `max(min(delay + active duration, end), 0)`; at an exact boundary the phase depends on the **animation direction** (playback rate sign) unless the endpoint-inclusive flag is set (used by `commitStyles()`). Derived states: **in play**, **current**, **in effect** (resolved active time). | — | [WA1 §4.6.6](https://drafts.csswg.org/web-animations-1/#animation-effect-phases-and-states) | 2026-10-08 | High |

| 3.5 | **Keyframe values are computed against the target element** ("compute a property value"), which creates ordering dependencies (e.g. `em` after `font-size`), and computed keyframes are "**live**": recreated every time the effect value is calculated. Shorthands expand to longhands; logical properties map to physical by the target's writing mode; conflicts resolve longhand > fewer-longhand shorthand > physical > IDL-name order. | 4 tie-break rules | [WA1 §5.3.2](https://drafts.csswg.org/web-animations-1/#computing-property-values), [§5.3.3](https://drafts.csswg.org/web-animations-1/#calculating-computed-keyframes), [§5.3.4](https://drafts.csswg.org/web-animations-1/#the-effect-value-of-a-keyframe-animation-effect) | 2026-10-08 | High |

| 3.8 | **Applying to the cascade**: the composited value enters the cascade as a specified value at the level of the class of the **top** effect: the Animation Origin by default, the Transition Origin if the top effect is a CSS transition. | — | [WA1 §5.4.5](https://drafts.csswg.org/web-animations-1/#applying-the-composited-result) | 2026-10-08 | High |

| 3.10 | **Side effect:** any property targeted by a current or in-effect, non-removed effect behaves as if listed in `will-change`, so e.g. a transform animation creates a stacking context through its before phase and forwards fill. | — | [WA1 §5.6](https://drafts.csswg.org/web-animations-1/#side-effects-section) | 2026-10-08 | High |
| 3.11 | **`getAnimations()`** (Element, Document, ShadowRoot; `subtree`, `pseudoElement` options) returns **relevant** animations (current or in effect, not removed) in composite order and **triggers a style change event**, so pending CSS animations and transitions exist before it returns. **Implications:** the effect pipeline is deterministic arithmetic over computed values, but it reads computed style (live keyframes, `em`, `var()`), so animation sampling sits inside style resolution, not after it. Izcal's style engine must expose "base value" and "compute a property value against element E" as first-class operations, and sampling must happen at a defined point in each style pass.

## 15. Implications for Izcal (summary)

1. **One timing kernel, many front ends.** CSS Transitions, CSS Animations, scroll-driven animations, view transitions (whose pseudo-tree runs CSS animations) and, optionally, SMIL all reduce to Web Animations' animation and effect model (sections 2–3). Izcal should build that model once (timing state machine, effect stack, composite operations) and express each front end as a generator of `Animation` objects with its own class, owning element and composite order.
2. **Animation lives inside style.** Keyframes compute against the element (live), the stack folds from a base value, results enter two cascade origins with unusual precedence, and custom properties carry animation taint (3.5, 7.1, 7.10). The style engine must expose base value, origin slots and "compute ignoring animation origins" as primitives, which is an amendment candidate for the HTML and CSS parsing and style spec.
3. **The frame is a fixed, recorded sequence.** HTML orders every step and leaves only cadence and the timestamp open (11.1–11.4). Izcal can make the timestamp, the "ready" decision, the style-change-event points and the stale-timeline re-run explicit recorded inputs, satisfying B1 without diverging from the spec.
4. **Time values need a type.** Milliseconds as `f64` with microsecond resolution (14.1) and percentages on progress timelines (4.2) argue for an exact representation (for example integer nanoseconds for time, a separate fixed-point type for progress) with conversion at the IDL boundary, so model arithmetic is exact and reproducible on x86-64, arm64 and riscv64.
5. **Shared interpolation functions.** Transform decomposition, slerp, premultiplied Oklab and the per-type rules (section 8) must be one crate used by style and by the compositor (graphics spec GR-D13 already asks for an integer function for transform and opacity), with golden vectors per type.
6. **Choose, record and test where specs are open or broken** (13.1–13.9): stale timeline policy, display-transition edge cases, step-easing before-flag semantics, view-transition timeouts and size limits, hidden-document timeline behaviour.
7. **View-transition snapshots are sensitive pixels.** They can contain cross-origin and visited-link data (10.11), and cross-document transitions carry them across navigations. Izcal's isolation rule (I-1) requires the snapshot to stay outside any renderer that could read it, which the animation spec must specify jointly with the graphics spec.
8. **Reduced motion is Izcal's own policy.** No spec says what to do (14.5), and the media query is a fingerprinting signal (11.5). Izcal should decide its behaviour (for example, whether user-level reduced motion also shortens animations) and its exposure under the privacy rules (P2).
