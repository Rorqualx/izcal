# Izcal animation: determinism_math_replay

Compiled 20 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Evidence rule.** No source code of any browser, engine or other project was read or cited (M-1 part 3, extended by the owner on 19 October 2026 to every third-party project). The evidence below is specifications, papers, prose documentation, protocol definitions, black-box test files and Izcal's own numeric experiments. A value that only some project's source states is listed in Section 10 as a black-box measurement. The experiments marked **(Izcal exp.)** were run on 20 October 2026 with CPython 3 on macOS arm64. They are first-principles arithmetic, not measurements of any engine.

**Izcal context.** The JS spec owns `hg-math`, one implementation of the implementation-approximated math functions on every tier and ISA, never the platform libm, with no FMA contraction ([JS 6.9](../../reports/Izcal%20JavaScript%20engine.md), JS-D12). It sits in L2s with a tier-P build, and the style spec uses it for `calc()` and colour ([ST 6.9, G24](../../reports/Izcal%20HTML%20and%20CSS%20parsing%20and%20style.md)). The images and media spec asks for `hg-math` f32 entry points, defined as the f64 function rounded once to f32 (MD R11). The graphics spec gives this spec `hg-interp`: an **integer** interpolation of transform and opacity, used by the compositor and the main thread so that they agree bit for bit, with no floating point (G61), and with style's f64 values converted at the boundary ([GR 6.8, 6.28, G61](../../reports/Izcal%20graphics%20and%20rendering.md)). DET-1 requires bit-identical replay hashes. JS-D12 (a) asks for identity across ISAs, and the owner made riscv64 a target on 19 October 2026. M0 found the forked V8's hashes identical across macOS arm64 and Linux and Windows x86-64 ([M0](../../m0/determinism_crossplatform.md)). M0 did not test floating-point maths across ISAs.

**Implications:** On x86-64, arm64 and riscv64, Rust's scalar `+ − × ÷ sqrt mul_add` give identical bits for non-NaN results, provided FTZ is off, no `algebraic_*` or SIMD reduction is used, and the evaluation order is fixed. NaN bits and anything libm computes are not identical. Izcal should assert MXCSR, FPCR or fcsr at frame start in every process that does canonical float work, because a GPU driver or OS library can change them.

**Implications:** A cross-ISA identity contract cannot route through any platform libm, through Rust std's transcendental methods or through the `libm` crate, because none of them promises bits. `hg-math` should implement **correctly rounded** binary64 functions. Correct rounding is the only specification that is both implementation-independent and checkable against MPFR. CORE-MATH's published algorithms and worst-case lists show it is achievable at low cost. Under the extended evidence rule, Izcal writes its own implementation from the papers and the IEEE definition, and uses MPFR (through `rug`, test-only) and CORE-MATH's published worst cases as oracles. A fixed-algorithm implementation that is not correctly rounded would also give identical bits, but its result would be "whatever this code computes", which nothing outside Izcal can check.

**Implications:** The full set of transcendentals animation needs is **acos, sin, cos, atan2, pow, cbrt, plus sqrt**, all of which are in JS's `Math` and the style spec's `hg-math` list. The ownership is clean: animation adds no new function to `hg-math`. It does add the requirement that `hg-math`'s acos and atan2 are correctly rounded too, and a **degree-based** sin, cos and atan2 (sinpi, cospi and atan2pi in CORE-MATH's naming) is worth adding. CSS angles are degrees, so `rad2deg(atan2(...))` and `sin(deg2rad(θ))` round twice and break symmetry (for example, sin(180deg) ≠ 0 in radians). `sinpi(θ/180)` gives an exact zero at multiples of 180°.

**Implications:** Store timeline and animation times internally as **i64 nanoseconds** (exact for decimal CSS times to 6 places of ms; ±292 years). Then derive progress as an exact rational `local / duration`, rounded once to the easing input. This removes accumulation drift by construction, decides step and iteration boundaries exactly, and keeps WPT's ±1 µs tolerance trivially. Exposure to script stays f64 ms, coarsened per HR-Time.

The cost is about 24 integer iterations per sample, or a per-curve table built once, which is then also exact. The precision chosen (output grid of 2⁻²⁴ progress†, for example) must be finer than any observable step: 2⁻²⁴ of a 10⁵ px translation is 0.006 px, below the 24.8 fixed-point raster unit.

## 11. First-principles recommendation: a deterministic numeric contract for animation

1. **Time.** Internally, i64 nanoseconds for timeline, start, hold and local times. API doubles convert by one round-half-even, and script sees HR-Time-coarsened f64 ms. The local time `(timeline − start) × playbackRate` is computed exactly in i128 and rounded once. Nothing is accumulated across frames. The frame timestamp is a **recorded B1 input**, like layout's scroll deltas.
2. **Progress.** Iteration progress, the current iteration and step boundaries are computed as exact rationals of integer times, so `% 1.0` and `floor` boundaries are exact (row 4.8). The progress handed to easing and interpolation is fixed point (for example 2⁻³² units†).
3. **Easing.** cubic-bezier is solved by integer bisection on dyadic control points with one final rounding (5.5). `linear()` and `steps()` are exact integer arithmetic. There is no Newton iteration and no epsilon that depends on duration.
4. **Interpolation.** Compositor-eligible properties go through `hg-interp` in integers (GR G61): fixed-point decomposition with exact integer sqrt, and correctly rounded **fixed-point** acos, sin and cos for slerp. Other properties use the spec's `(1 − p)·A + p·B` form, in style's f64 or in fixed point, chosen per value type and stated once. Colour mixing goes through `hg-math`'s correctly rounded `pow`, `cbrt`, `atan2`, `sin` and `cos` (and degree variants), and then into `hg-colour`'s contract (MD-D28).
5. **Transcendental policy.** Only `hg-math`, and every function **correctly rounded** in binary64. f32 entry points are the f64 result rounded once (MD R11). Everything is written from published algorithms and IEEE definitions, with MPFR (`rug`, LGPL, test-only) and published worst-case lists as oracles. No platform libm, no Rust std transcendental, no `libm` crate on any observable path.
6. **Arithmetic hygiene.** No FMA except explicit `mul_add`. No `algebraic_*`, no SIMD float reductions, no estimate instructions. NaN is canonicalized wherever its bits could be observed (JS-D12 (a)). The FP control register (MXCSR, FPCR or fcsr) is checked at each frame start in the renderer, the compositor and the content GPU process, and a check that fails is a crash report, not a silent fix.
7. **Cross-ISA identity tests.** For each `hg-math` function, run the correctly rounded oracle on 10⁷† random inputs plus the published worst cases, on x86-64, arm64 and riscv64 hardware, with identical bits required. For animation, run a corpus of animations sampled at fixed timeline times (including steps boundaries, near-parallel slerp, near-singular matrices, and hue wrap at 0° and 360°), hash `getComputedStyle` values and `hg-interp` outputs, and require the same hash on all three ISAs in CI on every change (the Box2D pattern). Compare against browsers only within WPT's tolerances.

**Implications for Izcal:** Animation needs no new transcendental, but it raises `hg-math`'s bar from "one implementation" to **correctly rounded**, and it asks `hg-interp` for fixed-point acos, sin, cos and sqrt. The JS owner (`hg-math`) and the graphics owner (G61) must co-sign this. The frame timestamp must join the consolidated B1 decision-point and input list (RN2 Q15). The open risk is cost: correctly rounded binary64 acos and sin, and per-sample integer bisection, have not been measured in Izcal, so measuring them is a milestone, not an assumption.
