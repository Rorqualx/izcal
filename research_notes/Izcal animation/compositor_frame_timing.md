**Implications:** every engine started from `transform` and `opacity`, each widening only where the off-thread path needs no layout and either no paint or a paint it can do away from script (Chrome's paint-worklet route for `background-color`). WebKit's move away from Core Animation shows the cost of borrowing an OS animator: its feature set, not the web's, limits what can be accelerated. Izcal should own its threaded sampler and use one interpolation code path on both sides (as GR-D13 already requires).

## 2. Paint-dependent animations off the main thread: cost and benefit

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Chrome's composited `background-color` re-paints the element off the main thread through a paint-worklet path (1.6) rather than animating a compositor quad colour, because a background can be a painted region with borders, radii and images under it. The cost was one extra memory line and eligibility bugs. | +1.5% memory (Windows) | 1.6, 1.7 | 2021 | High |
| 2.2 | Eligibility must be decided once, from one snapshot: Chrome's double check (paint vs compositing) disagreed when property-tree nodes changed between stages, and a missed input (`time_offset`) crashed. | — | 1.6 | 2021-04 | High |
| 2.3 | Values that resolve late (system colours, `currentcolor` by inference) cannot be pre-resolved for the off-thread sampler, so they must fall back or be resolved at hand-off. | — | 1.7 | 2021-10 | High |
| 2.4 | Measured power on an M1 MacBook (powermetrics, 10 s, median of 3): most CSS and SVG animations draw about **200 mW** in Chrome, Safari and Firefox against **25 mW** idle; Firefox's layered semi-transparent gradient animation drew about **500 mW** because it repaints; an SVG turbulence-filter animation spiked in Safari and Firefox while Chrome used "barely 5%" of their energy. Single machine, chart-derived numbers. | 25 / 200 / 500 mW | [Torchbox, How much power do web assets use?](https://torchbox.com/blog/how-much-power-do-web-assets-use) | 2025-02-18 | Medium |
| 2.5 | WebKit: "Painting often triggers GPU work, which can significantly increase power use"; spinner GIFs and CSS animations "that continually trigger painting, even if you can't see them" are the main risk. | — | [WebKit blog, power usage](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/) | 2019-08-27 | High |
| 2.6 | Chrome's throughput metric (2020): when a compositor animation and a main-thread animation run together, the old metric reported the worse one; a transform animation at **~98%** with a `width` animation at **~10%** was reported as 10%, and after the change as **~65%** (compositor throughput used while no main frame is expected). | 98 / 10 / 65% | [Chromium animations highlights, March 2020](https://www.chromium.org/teams/animations/highlights-archive/march-2020---web-animations-scroll-linked-animations-throughput-metrics-and-more) | 2020-03 | High |

**Implications:** moving a paint-dependent property off the main thread means moving *raster* off the main thread, not just interpolation; the work then scales with the painted area per frame, so the power benefit is smaller than for transform and opacity and must be measured. GR-D13's placement (filter and `clip-path` re-rastered in the content GPU process, never in the compositor) matches what Chrome had to do for `background-color`.

**Implications:** two jank modes are documented: a **start delay** (pending until the first frame, by design) and a **phase skew** of one vsync between threads (Firefox 1208411). **Implications:** the spec frame timestamp is the rendering-opportunity time; engines feed it the vsync or BeginFrame time. Refresh-rate choice should follow ARR's model (per-animation votes, normal ≈ 60 Hz unless motion needs more), not "always maximum" and not Safari's blanket 60 Hz cap.

## 5. Scroll-driven animations off the main thread

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | Scroll-driven Animations: written so effects need no script per sample; UAs with async scrolling "are allowed (but not required) to sample such effects asynchronously as well"; during a composited frame whose scroll has not propagated to layout or script, the UA "may likewise choose not to sample", so "the rendered scroll offset and the state of a scroll-driven animation may be inconsistent". | — | [Scroll-driven Animations 1 (ED)](https://drafts.csswg.org/scroll-animations-1/) §1.2, §5 | 2026-09-25 | High |
| 5.2 | Chrome moved scroll-linked animations to the compositor in 2020 (demo: main-thread version janks under artificial load, composited version smooth); "scroll snapshotting" was added to keep timeline invalidation correct and avoid layout cycles, called "a ship-blocker". | — | [Chromium animations highlights, March 2020](https://www.chromium.org/teams/animations/highlights-archive/march-2020---web-animations-scroll-linked-animations-throughput-metrics-and-more) | 2020-03 | High |
| 5.3 | Chrome 115 shipped scroll-driven animations "run off the main thread"; no property list or fallback rules are published; the docs steer authors to `transform` instead of `width`. | 5.4 | WebKit: "Threaded Scroll-driven Animations" built on the threaded-animation work in late 2025 and early 2026 (reported in Safari 26.4); bugs found: animations stopped at 100%, dropped from the remote layer tree on completion, scroll sources that are not composited, JS-created animations forcing resolution every update, and **continuous rendering updates while the page is idle** (bug 304412, fixed 2025-12-19). | — | [WebKit bug 304412](https://bugs.webkit.org/show_bug.cgi?id=304412); other bug titles from a search listing | 2025-12 | High (304412) / Medium (rest) |
| 5.5 | Safari 26 shipped scroll-driven animations; WebKit's guide uses `width`, `transform` and `opacity` with no performance guidance. | Safari 26 | [WebKit, guide to scroll-driven animations](https://webkit.org/blog/17101/threaded-scroll-driven-animations/) | 2025-06-20 | High |

**Implications:** the hard part is not sampling but invalidation: timeline ranges depend on layout (scrollable overflow, view-timeline subject position) and must be snapshotted once per frame from layout, while the offset comes from the compositor. GR-D13 already chooses the stricter rule (sample from the offset the compositor draws). Izcal needs a test that an idle page with a scroll-driven animation produces zero frames (WebKit 304412).

## 6. Animation Worklet

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | Origin (2016): "Compositor Worklet" ran user code on the compositor thread; the redesign as Animation Worklet moved it off: "code doesn't run on the compositor thread anymore", but in sync with it on a best-effort basis, and allowed to "slip"; v1 outputs limited to fast properties (opacity, transform, scroll offsets). All four vendors expressed interest. | — | [Surma, Animation Worklet](https://surma.dev/things/animworklet/) | 2016-09-26 | Medium |
| 6.2 | Spec: **stateless** animators are pure functions (recommended); **stateful** ones return `state()` which is passed to a recreated instance so the UA can tear down or migrate global scopes; animators set the effect's **local time** directly; the UA "is not required to run animations on every visual frame"; main-thread script "may see a stale value"; local-time sync must happen before rAF in the lifecycle. | — | [CSS Animation Worklet 1 (ED)](https://drafts.css-houdini.org/css-animation-worklet-1/) | 2026-02-25 | High |
| 6.3 | Chrome: Canary behind a flag, origin trial planned for Chrome 71; the article admits Chrome did none of the slipping/thread-migration yet. Roadmap: MVP to animate all properties with slow ones in sync with the main thread; V2 for gesture input. | Chrome 71 OT | [Chrome blog, Animation Worklet](https://developer.chrome.com/blog/animation-worklet); [status.md](https://drafts.css-houdini.org/css-animation-worklet-1/status.md) | 2018-10-06 | High |
| 6.4 | Fate: no engine ships it. In February 2024 `CSS.animationWorklet` was undefined even in Chrome Canary 124 with experimental features. Its scroll use case was absorbed by declarative scroll-driven animations (Section 5). No published post-mortem was found. | — | [public-houdini-archive, issue #1123](https://lists.w3.org/Archives/Public/public-houdini-archive/2024Feb/0005.html) | 2024-02-29 | Medium |

**Implications:** Animation Worklet's lasting idea is the **contract**: a pure function of (time or scroll input) → local time, which a UA may run anywhere. Izcal's off-thread sampler can be specified the same way internally (pure, migratable) without exposing script on that thread; it should not run author JavaScript in the compositor (G63 boundary).

## 8. Derived classification: what can run off the main thread deterministically

The derivation uses three tests, each from the evidence above. **(L) Layout independence**: the sampled value must not change box geometry, or the compositor result goes out of step with layout (1.2, 1.10, 1.11). **(P) Paint independence**: either the value changes only how existing rasters are composed, or the repaint can be done off the main thread from a recorded display list with no script and no style resolution (1.6, 2.1). **(D) Determinism of sampling**: the value is a pure function of (start time resolved at ready, frame time, keyframes resolved at hand-off, timing function), with no late-resolved inputs (1.7, 2.2, 3.6).

| Class | Properties (examples) | L | P | D | Where it can run | Data the off-thread side needs |
|---|---|---|---|---|---|---|
| **A. Compose-only** | `transform`, individual `translate`/`rotate`/`scale`, `opacity`, `filter` on an isolated surface, `offset-*` when the path is resolved to absolute units | yes | yes: only how rasters combine | yes, when keyframes are absolute (percentages resolved against a box size frozen for the animation, 1.2) | compositor | property-tree node id, resolved keyframes in the shared integer encoding, timing (delay, duration, iterations, direction, fill, playback rate, easing incl. `steps()` and `linear()` stops), start time at ready, timeline id (document or scroll node), composite mode and the underlying value, the frame time the main thread used |
| **B1. Paint, uniform** | `background-color` on a simple box, `color` of a solid run, `box-shadow` colour, `outline-color` | yes | repaint of the element's own display items | yes, after colours are resolved at hand-off (system colours and `currentcolor` excluded or pre-resolved, 1.7) | content raster (GPU) process | as A, plus the element's recorded display items and their tile coverage; interpolation in the colour space the spec mandates |
| **B2. Paint, geometric** | `clip-path`, `mask-position`/`mask-size`, `box-shadow` offsets and blur, `border-radius`, `background-position`, `filter` with blur on a non-isolated element | yes, if the reference box is frozen | re-raster of an area that can change per frame | yes, if the reference box and path vertex counts are fixed at hand-off | content raster process (GR-D13), never the compositor (G63) | as B1, plus the reference box, the path or shape in a resolved form, and a damage bound per frame |
| **B3. Paint, text or content dependent** | `color` of text with decorations, `text-shadow`, gradient stops over large areas | yes | repaint may need shaping or large re-raster | yes in principle | main thread unless measured otherwise | — |
| **C. Layout** | `width`, `height`, `top`/`left`, `margin`, `padding`, `font-size`, `grid-template-*`, percentage transforms on a resizing box | no | — | — | main thread only; anything composited on the same element must join it (1.10, 3.7) | — |
| **S. Scroll-driven of A** | class A on a scroll or view timeline | as A; ranges snapshot from layout once per frame | as A | yes, if the compositor samples from the offset it draws (5.1's permission made strict) | compositor | as A, plus scroll-node id, range start and end in pixels snapshotted at the last layout, axis, and for view timelines the subject's position at that layout |

Three rules follow. (1) **Group rule**: all animations of one element on the same composited node must run on one side, or class C on that element forces the others to the main thread (Firefox's geometry rule generalised). (2) **One time, one function**: the off-thread side receives the frame time the main thread used for that frame and samples with the same integer function, so a main-thread read and the displayed value agree bit for bit (3.6, 3.8, 1.15). (3) **Hand-off snapshot**: eligibility and resolved inputs are decided once, at the commit that hands the animation over, and any later change (keyframes, box size for percentages, system colour, timeline range) re-commits rather than patching (2.2).

## 10. Implications for Izcal

1. **Adopt the classification of Section 8 as the animation spec's eligibility table**, with class A on the compositor, B1 and B2 in the content GPU process (as GR-D13), C on the main thread, and the group, one-time and snapshot rules as normative engine rules with tests.
2. **Own the threaded sampler, never an OS animator.** WebKit spent 2023–2026 leaving Core Animation because its feature set capped acceleration (1.14–1.15); Izcal's sampler must support every timing function, composite mode and playback rate the main thread does, from the same L2g crate.
3. **Share one frame time.** Define frameTimestamp as the BeginFrame tick time, send it with each commit, and have the compositor sample class A and S at that time for frames that include the main frame, and at its own tick for compositor-only frames, with the rule written down; Q-9.3 sets the acceptance bound.
4. **Refresh rate by vote, power by default.** Follow ARR: each running animation votes (Normal ≈ 60 Hz unless it moves geometry or is scroll- or input-driven), the compositor requests the highest vote from the OS frame-rate API, low-power mode halves it, and the Hardened profile keeps GR-D15's 60 Hz clamp. This replaces a blanket cap (Safari) or always-maximum.
5. **Zero frames when nothing visible changes.** Off-thread animations whose target is clipped out, hidden, in a throttled frame or in a hidden document stop requesting BeginFrames; a CI test asserts zero frames on an idle page with a scroll-driven animation (WebKit 304412) and on a page whose only animation is off-screen.
6. **Metrics in frame records.** GR-D15's frame records already list which updates a frame included; the animation spec should define dropped and partial frames exactly as the smoothness metric does (4.13) and expose them in DevTools, together with LoAF.
7. **No Animation Worklet.** Keep its pure-function contract as an internal property of the sampler; do not run author script off the main thread.
