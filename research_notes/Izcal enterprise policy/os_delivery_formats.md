**Implications:** On Windows, Izcal should read `HKLM` and `HKCU\Software\Policies\<Vendor>\Izcal`, with a `Recommended` subkey, numbered list subkeys, and JSON-string dictionaries. These are the conventions admins and tools already emit. Refresh should run on `RegisterGPNotification` (machine and user), backed by a re-armed, thread-agnostic `RegNotifyChangeKeyValue` on the policy keys, because MDM and script writes may not raise the GP event. Whether Izcal copies Chrome and Edge in gating raw-registry or sensitive policies on domain join or MDM enrolment is a design decision. Their stated motive, from old secondary sources, is malware writing the key. The HKCU ACL is undocumented and is a **black-box measurement** (`Get-Acl` on a standard-user account, rig253).

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | The ADMX format, introduced with Vista, is "one language neutral file (.admx) and associated language resource files (.adml)". One error case is documented: two ADMX files declaring the same target namespace fail with "Namespace … is already defined". | — | [Create and manage Central Store](https://learn.microsoft.com/en-us/troubleshoot/windows-client/group-policy/create-and-manage-central-store) | 2026-02-12 | High |

| 2.5 | The `list` element's attributes (`valuePrefix`, `additive`, `explicitValue`) were not confirmed. The archived per-element page returned 404. | — | — | — | open |

**Implications:** Izcal must publish an ADMX/ADML pair: one target namespace with a version in its name (see 3.5), an `en-US` ADML first, a separate category tree for recommended policies, and `class` set per policy. The template is generated from Izcal's own policy schema, never adapted from another vendor's ADMX.

**Implications:** Izcal's ADMX must ingest cleanly. On MDM-only devices ingestion writes the same registry keys GPO would, so one registry reader covers GPO, Intune ADMX and scripts. Whether Izcal treats "enrolled in MDM" as equivalent to "domain-joined" for any gate must be decided from the CSP enrolment state, not inferred. The detection API is still open.

**Implications:** On Linux, Izcal should read `/etc/<izcal>/policies/{managed,recommended}/*.json`. It should define a **deterministic** merge, for example lexical file order with a conflict reported as an error, instead of Chrome's "undefined". It should also **check** that each file and its directory are root-owned and not group- or world-writable, rejecting and reporting files that fail, rather than only advising it. Sandboxed packages need a documented host path. Accepting a user-writable Flatpak extension path (`$XDG_DATA_HOME`) for mandatory policy would let users override policy, so only `/var/lib/flatpak/extension/...` should count as managed.
