# Izcal enterprise policy: history and postmortems

Compiled 2026-10-24. Primary sources were preferred (vendor documentation, security bulletins, protocol specifications, vendor and maintainer blog posts). No third-party source code, header, commit, code review or in-repository data file (ADMX, JSON schema) was opened or cited (M-1 part 3).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a summary of a primary page, or a vendor claim without data; **Low** = secondary source only.

The search budget for this session ran out before strands 6–7 were finished. Claims gathered after that point rest on pages already found, and the gaps are listed at the end.

## 1. Windows: NT 4.0 system policies, Group Policy, ADMX, and the GPP password leak

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **NT 4.0 system policies wrote anywhere in the registry and stayed there.** Microsoft: "Windows NT 4.0 policies do not respect these special trees, and they can write to any part of the registry. After such a policy is applied, it persists until the value is intentionally reversed, either by a counteracting Windows NT 4.0 policy or by editing the registry." The industry name for this is **tattooing**. | — | [Windows NT 4.0 system policies (Windows Server 2003 docs)](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2003/cc728021(v=ws.10)) | doc dated 2009-10-08 | High |
| 1.2 | Removing the NT 4.0 policy file from the domain controller did nothing, because the client registries had already been changed; the admin had to push a reversing policy. | — | TechNet "Controlling the User" (snippet only) | n.d. | Medium |
| 1.3 | **Windows 2000 Group Policy confined policy to four reserved, ACL-protected trees**: `HKLM\Software\Policies`, `HKCU\Software\Policies` (preferred), and the two `…\CurrentVersion\Policies` keys. "When Group Policy changes for any reason, these trees are wiped clean and the new policies are rewritten." | 4 keys | [cc728021](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2003/cc728021(v=ws.10)) | 2009-10-08 | High |
| 1.4 | The Windows 2000 developer guide states the same rule: "The keys are created when the GPO is applied. If the GPO that applied the keys is ever removed, the registry keys associated with it will also be removed." Standard users cannot change the keys. | — | [Implementing Registry-Based Group Policy for Applications](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-2000-server/bb742499(v=technet.10)) | Windows 2000 era; archived 2009-12-09 | High |
| 1.5 | **Policy and preference are kept in separate keys on purpose.** "Although Group Policy settings take priority over a preference, they *do not* overwrite or touch the registry key used by the preference. If both a policy and preference are present, the preference will be successfully restored if the policy is removed or disabled." Apps must read the policy key first, then the preference, then a built-in default. | 4-row resultant-behaviour table | [bb742499](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-2000-server/bb742499(v=technet.10)) | Windows 2000 era | High |
| 1.6 | The escape hatch kept tattooing alive: custom `.adm` files could still write outside the approved trees, and Microsoft warned that "installing Windows NT 4.0 .adm files can lead to undesirable persistent registry settings". | — | [cc728021](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2003/cc728021(v=ws.10)) | 2009-10-08 | High |
| 1.7 | **ADMX/ADML (Windows Vista / Server 2008)** replaced the ADM language with an XML format. ADMX is language-neutral and ADML holds per-language strings. "Unlike ADM files, ADMX files are not stored in individual GPOs"; a domain can host one **central store**. | — | [Managing Group Policy ADMX Files Step-by-Step Guide](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-vista/cc709647(v=ws.10)) | 2008-07-25 | High |
| 1.8 | Why: the old model copied ADM files into every GPO in SYSVOL. Microsoft says the new model means "domain controllers don't store or replicate redundant copies of .adm files", and that SYSVOL is no longer auto-updated, "to reduce network load and disk storage requirements" and to avoid cross-locale conflicts. The central store is `\\domain\SYSVOL\domain\policies\PolicyDefinitions`. | — | [Create and Manage Central Store](https://learn.microsoft.com/en-us/troubleshoot/windows-client/group-policy/create-and-manage-central-store); [cc709647](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-vista/cc709647(v=ws.10)) | 2026-02-12; 2008-07-25 | High |
| 1.9 | Known central-store failure: mixing ADMX/ADML generations causes namespace collisions and missing-string errors. Microsoft's fix is to build a clean PolicyDefinitions folder for each OS release and swap folders. | 2 named known issues | [Create and Manage Central Store](https://learn.microsoft.com/en-us/troubleshoot/windows-client/group-policy/create-and-manage-central-store) | 2026-02-12 | High |
| 1.10 | **MS14-025 / CVE-2014-1812 (Group Policy Preferences passwords).** GPP could store passwords for local users, mapped drives, services, scheduled tasks and data sources. An authenticated domain user "could retrieve and decrypt the password". Rated Important. It was publicly disclosed and exploited in targeted attacks. | 8 GPP extensions | [MS14-025](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2014/ms14-025) | 2014-05-13 | High |
| 1.11 | Root cause: the encryption key was published. MS-GPPREF says "All passwords are encrypted using a derived Advanced Encryption Standard (AES) key" and prints the 32-byte key in the specification. Any domain user can read SYSVOL, so encryption with a public key was no protection. | 32-byte static key | [MS-GPPREF: Password Encryption](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gppref/2c15cbf0-f086-4c74-8b70-1f2fa45dd4be) | spec page updated 2024-04-23 | High |
| 1.12 | The fix removed the feature but did not clean up existing data: "the update does not remove any existing GPOs that were configured prior to the application of this security update." KB2962486 disables the password fields, ships a detection script, and tells admins to Delete/Disable each affected preference and wait for refresh cycles. | — | [MS14-025](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2014/ms14-025); [KB2962486](https://support.microsoft.com/kb/2962486) | 2014-05-13 | High |

**Implications:** Izcal's policy store must be **non-tattooing by construction**. Effective policy is a pure function of the sources present now, held apart from user preferences, and it vanishes when its source is removed. Policy must **never carry secrets**: any channel that every managed principal can read will leak them. A fix to the format must also find and remove the bad data already deployed.

It should show the policy source to the user, and keep the trust tiers ordered and explicit as Chrome's precedence table does.

**Implications:** Kiosk escapes come from **browser features that hand off to the OS**: file dialogs, protocol handlers, downloads that can then execute, and a legacy engine. The defaults should be closed, not left for the admin to switch off.

## Cross-cutting lessons (for phase 5)

| Project | What happened | Lesson | How Izcal applies it |
|---|---|---|---|
| NT 4.0 system policy | Wrote anywhere, persisted after removal (tattooing) | Policy must be removable state, separate from preference | Effective policy recomputed from live sources; never written into user prefs |
| Win2000 Group Policy | Reserved ACL'd keys, wiped and rewritten on change | Separate namespace + reset-on-change works | Separate policy layer; full recompute on any source change |
| GPP / MS14-025 | Published AES key, SYSVOL world-readable, passwords leaked; fix left old data | No secrets in policy; fixes must purge deployed data | Schema forbids secret-typed values; secrets come from an OS credential store or enrollment |
| ADM → ADMX | Per-GPO template copies bloated SYSVOL; XML + language split + central store | Separate definitions from values, and strings from definitions | One versioned schema with localisable strings, shipped once |
| Chrome 2014–2015 | Store-only rule exempted "enterprise policy"; malware moved to policy keys | Local admin-writable ≠ managed | Gate high-impact policies on a verifiable management relationship; show the source |
| AutoConfig → policies.json | Executable JS config replaced with declarative engine; AutoConfig sandboxed | Policy is data, not code | No script evaluation in policy |
| Apple MDM → DDM | Imperative and polled → declared state, atomic activations, status channel | Desired state plus status beats commands | Atomic apply plus per-policy status reporting |
| ADMX ingestion | Registry contract carried over OMA-DM, with path restrictions | Transport and schema must be separate | One schema, many transports, one normaliser |
| IE mode | Site list outlived the engine; LOB/ActiveX keeps it alive to ≥2029 | Compatibility lists last for decades | Policy-driven "open in other browser" list |
