**What the security scope already settles (and this note does not reopen).** UPD-R1 (every data channel is a TUF target), UPD-R2 (fetch in the network service, opaque bytes through the broker, verify and apply in the network-less updater), UPD-R3 (root offline 2-of-3†, a delegated `releases` role, online timestamp and snapshot keys), UPD-R4 (emergency release class), UPD-R5 (emergency mitigation switches), SEC-13 to SEC-17 (artifact chain, dependency review, reproducible engine images, signing and rotation drills, the TUF attack-class suite with a 3-day† timestamp ceiling), SEC-D14 (per-user install, no elevated component, Stage 1). This note covers what those rules leave open: how a running multi-process browser survives its files being replaced, deltas, cadence and channels, staged rollout without telemetry, pinning, background and metered behaviour, and the state of the supply-chain frameworks.

**Three patterns, one constraint.** (a) **Versioned directories** with the swap of a small launcher at next launch (Chrome on Windows and macOS). Children always come from the running build's directory, so the old one must outlive the old parent. (b) **Pre-forked or pre-opened children** (Chrome's zygote, Firefox's fork server on Linux). They work while every file a child needs is already open, and break as soon as a child needs a file by path (FreeBSD case). (c) **Detect and refuse** (Firefox's build-ID check and `about:restartrequired`). It is safe, but the user sees broken tabs. Firefox shows both what happens when (c) is the only defence (2026 bug) and how far (b) reaches.

**Implications:** Izcal's IPC already refuses a child from another `BuildId`, so Izcal needs (a) on every OS, so that the refusal never fires in normal operation. (1) **Install into `<root>/versions/<BuildId>/`, never over a running build.** Each child is launched by absolute path from the parent's own version directory, or on Linux by `execveat` on an fd opened at startup (1.10). A small per-user launcher (or `Current` symlink on macOS and Linux) selects the newest *complete, verified* version at the next launch. (2) **The updater deletes an old version directory only when no process of that build is alive.** A per-build lock file held by the parent works for this, and on Windows it removes the need for boot-time renames, which per-user installs cannot use (1.7). (3) **On macOS, each version is a separately signed, notarized nested bundle** (or the whole `.app` is replaced while closed), and nothing writes into a signed bundle (1.11). (4) **Linux system packages** must install into the same versioned layout, because distribution packages replace files in place (1.3). The tarball's TUF updater gets this for free. (5) Keep a **user-facing `restart required` state** for the case where the refusal fires anyway, with a test that it never fires in the normal update path.

**Patterns.** Every scheme has a **full-payload fallback** (2.4, 2.5, 2.6, 2.8), and every scheme that patches against the files on disk **verifies them first**: hashes in protocol v4, size and CRC in MARs, the manifest in Windows. Server cost grows with the number of version pairs. Mozilla caps it at four; Windows removed pairs altogether by diffing against a common baseline. Executable-aware diffing (Courgette, Zucchini) gives about an order of magnitude over bsdiff, but it is a disassembler for every ISA and format, run on attacker-reachable input in the client.

**Implications:** (1) **Deltas are optional TUF targets keyed by (from-BuildId, to-BuildId)**. Each lists its length and hashes and names the full target it must produce; `hg-update` applies it into a fresh version directory and **verifies the result against the full target's hashes** before switching. A mismatch or any error means: fetch the full target. The full target is always published and signed. (2) Because Izcal installs into versioned directories (Section 1), the **base is the previous version directory, read-only and verified**, which avoids Mozilla's modified-install failure. (3) The **patch format parser runs in the network-less updater** under SEC-17's fuzzing and gets its own fuzz target. A Courgette-class disassembler is a large parser surface, so start with a dictionary-style format (zstd-like, Izcal's own implementation under M-1) and measure before adding an executable-aware stage. (4) Cap the pairs (last N† releases per channel, plus a weekly or baseline delta), and measure on Izcal's own binaries the size of a full download versus a dictionary delta versus an ISA-aware delta, at per-release granularity.

| 4.8 | **Firefox refuses to open a profile last used by a newer version** (downgrade protection, Firefox 67, May 2019), with an override flag; the fix for a bad release is a new release. | Fx 67 | Mozilla SUMO article (failed to load this session) | 2019 | Medium |
| 4.9 | **Fix-forward is the norm**: Play has no rollback (4.2); Mozilla's practice is a dot release; Chrome's rollback is an enterprise policy with snapshots (4.7). | — | 4.2, 4.7 | — | High |

**What gates widening, and what Izcal can use without per-user telemetry.** Apple, Play and Balrog widen on **crash and stability data the vendor already collects**; CrowdStrike now bakes each ring with telemetry. Izcal has no account and only opt-in telemetry, so it cannot copy that. What is left: (a) **pre-release populations** (Nightly and Beta users who opted in, plus opt-in crash reports from every channel) as the canary rings; (b) **time-based widening with a halt**, with the bake time set by how fast opt-in crash reports and public bug reports arrive; (c) **client-side buckets that are never sent**: each install draws a random number once and keeps it locally, the signed metadata publishes a rollout fraction (or a start time and ramp), and the client compares locally. The server learns nothing per user. The cost is that the server cannot halt a single bucket, only lower the fraction for everyone not yet updated; (d) per-request rather than per-client dice (Balrog) gives no stable identity at all but makes a client flip in and out, which matters if a rollout is halted mid-download.

**Implications:** (1) Put the **rollout fraction (or ramp schedule) inside the signed TUF targets metadata** for the release (a `custom` field), so that a halt is a new signed snapshot that reaches the client within the timestamp expiry, without an online server that knows who is who. A ramp schedule also keeps rolling out if the release keys are offline over a weekend. (2) **The local bucket is a per-install random value that never leaves the device**: it is not telemetry and not a tracking ID. Record it in the privacy inventory and reset it on profile reset. (3) **Manual "check now" bypasses the ramp** (as Apple and Balrog do), and security releases use a short ramp or none (UPD-R4). (4) **Rollback is fix-forward** by default: a halted release is superseded by a higher version. TUF forbids version rollback, so a "rollback" is always a re-signed old build under a new version, and the profile schema needs **forward-compatible migrations or snapshots** (Chrome's 4.7) before any downgrade is allowed. (5) The CrowdStrike lesson applies to **every UPD-R1 data channel**, not only binaries: a data-channel update needs a canary and ramp too. UPD-R5's emergency switches are the exception, and Section 6 of the spec should say so explicitly.
