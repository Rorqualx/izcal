# Izcal distribution and updates: history and postmortems

Compiled 24 October 2026. Primary sources were preferred (vendor postmortems, maintainers' posts, advisories, official documentation, release notes, mailing lists, bug-tracker discussion).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract, snippet or summary, or a vendor claim without independent data, or a press report quoting the primary; **Low** = secondary source only, or a claim from background knowledge that could not be checked this session.

**M-1 part 3.** No third-party source code, header, commit, diff or code review was read, linked or cited. Every source is prose. Several searches surfaced code-viewer links (Chromium `registration.cc`, Searchfox pages for Firefox's update docs, a `docker-cli` commit patch); none was opened or used. Two Chromium prose documents hosted in the source repository (the component updater README and the Chromium Updater design document) are cited from search snippets only, under OD-7: no code file was opened, no outside copy was found, and the one constant quoted (a six-minute first-check delay) appears in the prose, not beside code. It is still flagged for black-box measurement. Where a value seems to live only in code (Chrome's Windows in-use swap, the Linux zygote behaviour after a package upgrade, Firefox's restart-required trigger), it is recorded as a black-box question.

**Search budget.** About 22 web searches, then primary pages fetched directly (CrowdStrike's RCA PDF read in full; Chromium Blog posts read via the Blogger feed). Unchecked claims are graded Medium or Low and say why.

**Scope.** Software distribution and update systems, 2006–2026, as they bear on a browser: installers, per-user installs, update protocols, delta updates, background updaters, data/content channels, Linux distribution packaging, signing, update-channel and build-system compromises, staged rollout, and the frameworks (TUF, Uptane, reproducible builds, binary transparency) built in response.

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Chrome's installer goals were stated in January 2009: keep users "free from the burden of checking for security updates"; "allow users who are not administrators to install"; update "automatically in the background even when Google Chrome is in use. | 1.3 | Google Update was reused because it already handled **update channels** "each with its own update schedules", silent background updates, **proxy support**, and one updater instance for several Google programs. | 1.5 | Google built Google Update in **2007** as "a common background automatic updater for all of its products on Windows" and open-sourced it as **Omaha**. **Omaha 3** added a COM state-model API, richer logs (text or ETW), queued result pings for unreliable networks, and **elevation-optional installs** that try per-machine or per-user from a single installer. | 2007; Omaha 3 2011 | [Google Open Source Blog, "Omaha 3"](https://opensource.googleblog.com/2011/09/omaha-3-modernizing-automatic-software.html) | 2011-09 | High |
| 1.6 | **Courgette**: Google wrote an executable-aware diff because bsdiff was still too large. Rationale: "We want smaller updates because it narrows the window of vulnerability. If the update is a tenth of the size, we can push ten times as many per unit of bandwidth." The 190.1→190.4 dev update: full **10,385,920 B**, bsdiff **704,512 B**, Courgette **78,848 B**. | 132× vs full; 9× vs bsdiff | [Chromium Blog, "Smaller is Faster (and Safer Too)"](https://blog.chromium.org/2009/07/smaller-is-faster-and-safer-too.html) | 2009-07-15 | High |
| 1.7 | **Keystone incident (macOS)**: Google said a Chrome update "may have shipped with a bug that damages the file system on macOS machines with System Integrity Protection (SIP) disabled", and paused the release. Keystone **1.2.13.75** tried to remove the `/var` symlink to `/private/var`, which macOS needs to boot; SIP normally prevents this. Victims were mostly video professionals (Avid users) who disable SIP for third-party GPUs; Google eventually advised reinstalling macOS from Recovery. | v1.2.13.75 | [TidBITS](https://tidbits.com/?p=41630); [The Register](https://www.theregister.co.uk/2019/09/25/macwoes_google_chrome_update/); [iMore](https://www.imore.com/google-says-chrome-update-might-be-killing-some-macs-0) (all quote Google's support-forum statement, not retrieved) | 2019-09-24/25 | Medium |
| 1.8 | **Component updater**: a Chrome subsystem in the browser process that uses the Omaha protocol to fetch and register "components" (for example the Widevine CDM) separately from Chrome. The stated benefit is faster or desynchronized release cadences, lower bandwidth and a smaller installer; the stated cost is that "they require Chrome to tolerate their absence in a sane way". It registers components at startup and checks for updates about **six minutes** later. | ~6 min delay | Chromium `components/component_updater/README.md` (prose doc in the source repo; search snippet only, OD-7) | snapshot ~2019 | Medium |
| 1.9 | **Chromium Updater** (the rewrite): described as "a drop-in replacement for Google Update/Omaha/Keystone" that third parties such as Edge can customize; written for Windows, macOS and Linux with mostly platform-independent behaviour, and platform modules for IPC (COM on Windows, XPC on macOS). Goals: cut duplicated per-platform code and implement checking, applying, metrics and **load shedding** consistently. Rollout dates on Windows and macOS were not found in prose. | 3 OSes | Chromium `docs/updater/design_doc.md` (prose doc in the source repo; search snippet only, OD-7) | ~2020–2023 | Medium |
| 1.10 | **Windows versioned install directory and in-use swap**: Chrome installs each version under `Application\<version>\`; when an update lands while Chrome runs, the new launcher is staged (commonly observed as `new_chrome.exe`) and swapped on the next launch, and the old version directory is removed later. No Google prose document describing this was retrieved this session. | — | Background knowledge; user-visible file layout | — | Low |
| 1.11 | **Linux**: Google's Chrome `.deb`/`.rpm` installs add Google's own APT/YUM repository, and Chrome is then updated by the system package manager, not by Omaha. When the package replaces files under a running Chrome, the running browser keeps working (the Linux **zygote** process forks renderers from the already-loaded old image) and the UI asks for a relaunch. No Google prose source for the zygote detail was found within budget. | — | Forum and guide reports only, e.g. [itslinuxfoss](https://itslinuxfoss.com/update-google-chrome-linux/) | — | Low |

**Implications:** Chrome's 2009 goals (silent, per-user, background, small, clean uninstall) still match Izcal's Stage 1. Keystone shows that a root-capable updater is an OS-wide risk; Izcal's per-user-only Stage 1 removes that class. The component updater is the precedent for Izcal's data channels and its central lesson, "tolerate their absence", is a design rule. The zygote trick (keep a pre-loaded image to fork from) is the mechanism that lets a package upgrade not break new tabs; Izcal, whose IPC refuses a child from another `BuildId`, needs an equivalent: launch children only from its own versioned directory, never from a shared path, and measure what happens under a running `.deb` upgrade.

## 2. Firefox update service

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **MAR (Mozilla ARchive)** is the update package format, "basically a series of files with an index tacked on to the end", whose content is bzip2-compressed files or binary diffs. A MAR may carry several signatures; the updater accepts it if **at least one** verifies. Firefox 10–56 accepted only RSA-PKCS1-SHA1 (2048-bit); SHA-384 (4096-bit) support was added for Firefox 56. | 2.6 | **"Armagadd-on"**: the intermediate certificate used to sign nearly all add-ons "expired just after 1AM UTC on May 4" 2019, disabling "the vast majority of add-ons" (over 15,000 add-ons exist). | 2.7 | **Armagadd-on post-mortem**: the signing team knew the certificate was expiring but believed Firefox ignored expiry (a confusion rooted in an earlier decision about end-entity checks); QA did not test certificate expiry or behaviour at future dates ("a fundamental oversight in our test plan"). The Studies system, built for experiments not fixes, was tied to Telemetry, so some users had to enable Telemetry, and Mozilla over-collected and later deleted data. Balrog checked for updates every 12 h (possibly 24) versus Normandy's 6 h. Eight system add-on versions and **six dot releases** followed. Lesson stated: "we need a mechanism that allows fast updates that isn't coupled to Telemetry and Studies." | 6 dot releases | [Mozilla Hacks, post-mortem result](https://hacks.mozilla.org/2019/07/add-ons-outage-post-mortem-result/) | 2019-07-12 | High |
| 2.8 | **Profile downgrade protection (Firefox 67)**: each installation gets a dedicated profile; a profile last used by a newer version triggers a warning that the older version can corrupt bookmarks and history, with an offer to create a new profile (`--allow-downgrade` overrides). The motivating case: Firefox 63 changed storage in a way 61 could not read, so running 63 once damaged 61's data. | Fx 67 (2019-05) | [SUMO, Dedicated profiles](https://support.mozilla.org/kb/dedicated-profiles-firefox-installation); [gHacks](https://www.ghacks.net/?p=148442) | 2019 | Medium |
| 2.9 | **Firefox on Linux, distro package replaced under a running browser**: when the distro's package manager replaces Firefox's files while it runs, a newly started content process may be incompatible with the running parent, and Firefox shows an `about:restartrequired` page ("Sorry, just one more thing to keep going" / "Sorry, there's just a little thing we need to do first"). Firefox's own updater does not trigger it because it stages updates and applies them at restart. A Fedora report found the page's restart button sometimes failed after a `dnf` reinstall; Flatpak avoids the problem because the running app's image is not replaced. The bug that introduced the page and its Firefox version were **not found** within budget. | — | [Mozilla bug 1536150](https://bugzilla.mozilla.org/show_bug.cgi?id=1536150); [Red Hat bug 1876214](https://bugzilla.redhat.com/show_bug.cgi?id=1876214) | 2019–2020 | Medium (mechanism); Low (version) |

**Implications:** Izcal faces exactly Firefox's Linux problem: a `BuildId` mismatch between a running parent and a new child. Firefox's answer (detect, then force a restart page) is the fallback; the better answer is never to launch a child from files that can change (versioned directories that the package manager adds beside, not over, the running one). Armagadd-on is the core lesson for any expiring credential: test the browser at future dates, and keep an emergency channel that does not depend on telemetry consent. MFSA 2013-83 is the time-of-check/time-of-use lesson: verify the bytes you actually apply, in a location only the updater can write.

**Implications:** Sparkle's history repeats TLS-only trust: transport security does not survive a compromised server; the archive and the feed must be signed with a key the server never holds, which is what Izcal's TUF client gives. ShadowHammer and Notepad++ targeted a few users, so transparency logs or a consistent-snapshot check against other clients matter. CrowdStrike is the staged-rollout lesson: **every** update, including data and config, goes through rings.

## 7. TUF and Uptane

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **TUF** ("Survivable Key Compromise in Software Update Systems", Samuel, Mathewson, Cappos, Dingledine, ACM CCS 2010) separates responsibilities into roles (root, targets, snapshot, timestamp), uses signature thresholds and expiring metadata, and defends against rollback, freeze, mix-and-match and endless-data attacks, so that a single stolen key does not compromise clients. It grew from earlier work on package-manager attacks (Cappos et al., 2008) and Tor's Thandy updater. | 4 roles | [TUF paper (PDF)](https://theupdateframework.io/papers/survivable-key-compromise-ccs2010.pdf) | 2010-10 | Medium (not re-read) |
| 7.2 | **PEP 458** (TUF for PyPI, created 27 September 2013) is **Accepted**, not Final. It was deferred in early 2019 "until appropriate funding could be secured"; the page does not state that PyPI publishes TUF metadata in production. | 13 years since creation | [PEP 458](https://peps.python.org/pep-0458/) | read 2026-10-24 | High (status); Medium (deployment) |
| 7.3 | **Docker Notary v1 / Docker Content Trust**: Docker began retiring DCT for Docker Official Images on 29 July 2025 (certificates expiring from 8 August 2025) because "the upstream Notary codebase is no longer actively maintained" and **fewer than 0.05%** of Docker Hub pulls used DCT. Azure Container Registry and Harbor had deprecated it earlier; Docker points to Sigstore or Notation. | <0.05% | [Docker, Retiring Docker Content Trust](https://www.docker.com/blog/retiring-docker-content-trust/); [Docker, migration guidance](https://www.docker.com/blog/docker-content-trust-retirement-and-migration-guidance/) | 2025-07-29 | Medium |
| 7.4 | **Sigstore** distributes its root of trust (Fulcio and Rekor keys) through a TUF repository signed in a public key ceremony by several keyholders. | — | Sigstore blog post returned 404 this session; background knowledge | 2021– | Low |
| 7.5 | **Uptane** (2016, Kuppusamy, Cappos et al., with automotive partners) adapts TUF to vehicles: an image repository (what exists, offline keys) and a director repository (what this vehicle should install, online keys), with full and partial verification for small ECUs. It became a Linux Foundation Joint Development Foundation project and an IEEE-ISTO standard in 2019. | 2 repositories | Background knowledge; [uptane.org](https://uptane.org/) not read | 2016–2019 | Low |

**Implications:** TUF is the right foundation (Izcal already has a client), but adoption history is a warning: Notary v1 died because verification was **opt-in** and almost nobody opted in, and PyPI stalled for funding. Izcal's TUF check must be mandatory and invisible. Uptane's split between "what exists" (offline keys) and "what this client should install now" (online, per-cohort) is the shape a staged rollout needs.

## 8. Reproducible builds and binary transparency

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | **Tor Browser deterministic builds**: Mike Perry argued that malware targeting "the software development and build processes themselves" could reach tens or hundreds of millions of machines through one signed update, that air gaps and signing keys do not stop states ("I don't believe it is possible to keep software signing keys secure any more"), and that "deterministic, distributed builds are perhaps the only way we can reliably prevent these types of targeted attacks." Ideas included multiple independent signatures and publishing package hashes in the Tor consensus. PGO is non-deterministic because profile data varies by machine. | — | [Tor Blog, Deterministic Builds Part One](https://blog.torproject.org/deterministic-builds-part-one-cyberwar-and-global-compromise/) | 2013-08-20 | High |
| 8.2 | **Mozilla binary transparency (2017)**: build a Merkle tree (RFC 6962) over each release's SHA256SUMS, encode the tree head in a domain name under `fx-trans.net`, get a certificate and log it in Certificate Transparency. Balrog would carry the certificate, SCT and an inclusion proof (~300 bytes vs ~500 kB for SHA256SUMS); "the Firefox updater should not accept an update unless it comes from a logged release." The page (last edited 2 March 2017) leaves CA, log and Balrog choices open; whether the updater ever enforced it was **not established**. | ~300 B proof | [Mozilla wiki, Binary Transparency](https://wiki.mozilla.org/Security/Binary_Transparency) | 2017-03-02 | High (proposal); Low (fate) |
| 8.3 | **Debian reproducible builds** (from 2013) made most of the archive reproducible and the term standard; independent rebuilders verify. | — | [reproducible-builds.org](https://reproducible-builds.org/) not read this session | 2013– | Low |

**Implications:** Izcal builds its own toolchain-adjacent stack, so reproducibility is achievable early, and it is the only defence in this note against a SUNSPOT-style build implant. A binary-transparency log (Izcal-run or CT-anchored) with the updater refusing unlogged releases turns ShadowHammer-style targeting into a detectable event; Mozilla's proposal stalled on operational choices, not on the idea.

## 10. Technology mismatches

| Assumption baked into older updaters | Who assumed it | Why it no longer holds for Izcal |
|---|---|---|
| **Single-process browser**: replace files, and the running process is unaffected until restart | Early Firefox, distro packaging habits | Izcal launches child processes continuously; a child from a new build fails the `BuildId` check. Files must never change under a running build: versioned directories plus a switch at relaunch (Chrome, Squirrel) or a pre-loaded image (zygote). |
| **An admin-elevated service is acceptable** to avoid prompts | Mozilla Maintenance Service (2012), Omaha per-machine, Keystone | A privileged updater widens the blast radius (Keystone 2019, MFSA 2013-83). Stage 1 is per-user only. |
| **HTTPS (or code signing) is sufficient trust** | Sparkle pre-2016, Notepad++ WinGUp, M.E.Doc | Server or hosting compromise defeats transport security; validly signed malware (CCleaner, ShadowHammer, 3CX) defeats signing alone. Needs TUF metadata with offline keys, plus transparency. |
| **Vendor build machines are trusted implicitly** | Almost everyone pre-2020 | SUNSPOT, 3CX and xz showed the build is an attack surface. Needs reproducible builds and an independent rebuilder before signing. |
| **One global rollout**, or rollout only for code | CrowdStrike's Rapid Response Content | Data and configuration can crash clients too. Every channel (binary, components, lists, config) uses staged rings with automatic halt. |
| **Rollback is free** | Implied by "pull the release" | Profile migrations are one-way (Firefox 67). Roll forward with a fixed build, or make migrations reversible for one version. |
| **Expiring credentials are someone else's problem** | Armagadd-on | Every certificate and metadata expiry must be tested by running the browser at future dates. |
| **The emergency path can reuse an experiments channel** | Normandy in 2019 | Emergency fixes need their own channel, independent of telemetry or study consent. |
| **The OS package manager owns the files** but not the running process | Linux distros | The package manager will replace files under a running Izcal; the install layout must make that harmless. |
| **Patch level is invisible to the web** | Apple RSR "(a)" | Anything web-visible (UA, client hints) changed by an update breaks sites; keep it tied to the major version. |

## 11. Lessons

| Project | What happened | Lesson | How Izcal applies it |
|---|---|---|---|
| Chrome 2009 installer | Per-user, silent, background updates by design | Removing the admin prompt is what made automatic updates universal | Stage 1 per-user only, no elevation |
| Courgette | 132× smaller than full updates | Smaller updates are a security property | Ship deltas; measure size per release |
| Component updater | Data shipped apart from the binary | Components must be optional at runtime | Every data channel has a safe "absent" state |
| Keystone 2019 | Root updater deleted `/var` | An updater bug is an OS bug | No privileged updater; updater touches only its own directory |
| Firefox on Linux | Package replaced files; new content processes mismatched | Never launch children from mutable paths | Versioned install directories; children from the parent's own directory; restart prompt as fallback |
| MFSA 2013-83 | MAR changed after signature check | Verify what you apply | Verify then apply from an updater-only location, or verify per file during apply |
| Armagadd-on | Expired intermediate disabled add-ons | Test at future dates; fast path independent of telemetry | Clock-skew tests in CI; an emergency channel independent of telemetry |
| Firefox 67 | Newer profile data corrupted by older builds | Rollback is hard | Roll forward; schema changes reversible for one release |
| Flame | Licensing CA could sign code; MD5 forged | Scope keys narrowly, retire weak hashes early | Separate keys per role (TUF), modern algorithms only |
| Sparkle 2016 | HTTP feeds; injected release notes | Transport security is not authenticity | TUF-signed metadata; release notes are not rendered as active content |
| Apple RSR (a) | UA change broke sites | Fast patches must not change identity | Security patches never change the UA |
| SUNSPOT, 3CX, xz | Build or source tampering, signed output | The build is part of the TCB | Reproducible builds, independent rebuilder, isolated build hosts |
| CCleaner, ShadowHammer | Valid signatures on malware; targeted payload | Signatures prove origin, not intent | Binary transparency; clients reject unlogged releases |
| M.E.Doc, Notepad++ | Update server controlled by attackers | Clients must not trust the server | Offline-rooted TUF; server holds no release key |
| CrowdStrike 291 | Unstaged content update crashed 8.5M machines | Stage every update, including data | Rings, canaries, automatic halt and rollback for all channels |
| Codecov | One customer's checksum caught it | Publish hashes; make verification default | Verification mandatory in the client |
| Notary v1 | Opt-in signing, <0.05% use, retired | Optional verification is unused | No opt-out of TUF verification |
| Iceweasel | 10-year rename over trademarks | Distro policy must be planned for | Publish a clear policy for distro-built Izcal |
| Ubuntu snaps | Cold start ~2× slower, then fixed | Packaging costs are measurable | Cold-start target for every package format |
| Mozilla APT repo | Vendor repo inside APT | Users keep the package manager; the vendor keeps the build | Izcal's own signed APT/YUM repos |
