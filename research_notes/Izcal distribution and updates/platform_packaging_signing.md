**Implications:**
- **SmartScreen reputation is the critical path to launch on Windows.** Neither EV nor Artifact Signing gives instant trust. Reputation builds on the *publisher certificate identity* and on each *file hash*, and Microsoft's own estimate is "several weeks and hundreds of clean installs". Izcal must start signing public builds (nightly or beta) with the **same identity it will launch with** at least one to two months before launch, and must spread them across a wide audience.
- **Keep the signing identity stable.** Changing the certificate "affects the publisher trust signal". The 460-day validity cap means re-issuance at least every ~15 months, and Artifact Signing rotates certificates every ~3 days under the same validated identity. Microsoft's guidance implies reputation follows the validated publisher identity, not one certificate. Measure that before relying on it (Q7.1).
- **Who holds the identity.** An individual outside the US or Canada cannot use Artifact Signing. Izcal needs a legal entity in a listed region, or a CA-issued OV certificate on an HSM or cloud HSM. Organisation validation can take up to 20 business days and is part of the lead time.
- **Sign every PE file**, including DLLs and helper executables, not just the installer. SAC checks every executable the loader maps, and an unsigned helper (crash reporter, GPU process DLL) will be blocked.
- **Never let a build that resembles a PUP be signed** (a bundled offer, a silent default-browser change). Doing so can give the identity negative reputation.

**Implications:**
- **The Microsoft Store is closed to Izcal under today's policy 10.2.1**, whether as MSIX or as a 10.2.9 linked installer. Do not plan Store distribution or Store-granted reputation. Track the policy, because the rule is a Store policy, not a law, and EU DMA pressure could change it.
- **Stage 1 per-user install in `%LocalAppData%`** needs no UAC and no admin rights, so `MOVEFILE_DELAY_UNTIL_REBOOT` is unavailable to it. The updater must use **side-by-side versioned directories** (`…\Izcal\<version>\`) plus a small stable launcher or pointer. It must never overwrite a running image. Old version directories are deleted after the last process from that build exits, by a deferred clean-up on next launch. Register under `HKCU\…\Uninstall`.
- **Version skew is safe this way.** Izcal's IPC rejects a child process from a different build, so the browser process must spawn children from *its own* version directory by absolute path, never from a "current" alias. Then an update landing mid-session never breaks new tabs.
- **MSIX for Stage 2** depends on proving that a full-trust packaged process can create AppContainer or restricted-token children with Izcal's own sandbox profile (Q7.3). Until that is proven, plan MSI (per-machine, `Program Files`, silent `msiexec /qn`) for enterprise.
- **Ship native Arm64, not Arm64EC.** Izcal has no x64 plug-ins to host, and Arm64 is the cleaner ABI. Windows-on-Arm support can be Windows 11 only, matching Chrome.

**Implications:**
- **Sequoia makes notarisation mandatory in practice.** An un-notarised Izcal cannot be opened without a trip to System Settings. Every build that reaches a user, nightlies included, must be Developer ID signed, use the Hardened Runtime with `allow-jit` (Izcal's own JIT), and be notarised and stapled. Stapled tickets matter for first launch offline. The notary round trip belongs in CI (Q7.5 covers its latency).
- **The Account Holder is a single point of failure.** Only that person can mint Developer ID certificates, and there are five of each type. An organisation account (D-U-N-S) is needed for the publisher name to read "Izcal" rather than a person's name.
- **The Mac App Store is out:** the WebKit rule (2.5.6) on top of 2.4.5 (App Sandbox for the whole process tree, no own updater, no downloaded code). Ship a DMG for Stage 1 and a Developer ID Installer-signed `.pkg` for MDM in Stage 2. The `.pkg` must be re-signed when the Installer certificate expires.
- **Update model:** install new versions as sibling versioned bundles, or as a versioned inner framework (`Versions/<n>/`) behind a stable outer `.app`, then relaunch. Children are spawned from the running version's own path, never re-resolved through the outer bundle, for the same IPC version-check reason as on Windows.
- **Support window:** follow the three-releases practice. Edge and Chrome currently require macOS 13 or later.

**Implications:**
- **Izcal APT repository:** a deb822 `.sources` file with `Signed-By: /usr/share/keyrings/izcal-archive-keyring.pgp`, a binary key, and an `izcal-archive-keyring` package that rotates the key. SHA-256+ binding signatures, and no SHA-1 anywhere in the key, because sqv has rejected SHA-1 bindings since 1 Feb 2026. Sign `InRelease`. Test every key change with `sqv` (Debian/Ubuntu) and `rpm-sequoia` (RHEL 10/Fedora) in CI.
- **RPM repository:** `gpgcheck=1` and `repo_gpgcheck=1`, an Ed25519 or RSA-3072+ key with SHA-256+ signatures, and packages that pass RHEL 9/10's DEFAULT crypto policy. Expect RPM 6 enforcement to become the default in later Fedora releases.
- **Versioned install directories give Linux a clean upgrade.** Install to `/opt/izcal/<version>/` with a stable symlink or launcher. dpkg/rpm then *add* a directory rather than overwrite files. A running browser keeps exec'ing children from its own absolute version path, so the IPC build check never fires mid-session. A post-install hook signals the running browser to offer a relaunch, and the old directory is removed at the next upgrade, or at next launch if no process holds it. Never let the browser re-exec through `/usr/bin/izcal` to spawn a child: after the rename it resolves to the new build.
- **Ship an AppArmor profile** granting `userns` for the Izcal binary in `.deb` packages for Ubuntu 23.10+. Without one, the namespace sandbox fails on stock Ubuntu. The tarball install cannot install a profile, so the tarball either documents the need or falls back to a reduced sandbox and says so in the UI (Q7.7).
- **Flatpak (Stage 2) runs at reduced isolation:** Izcal's namespace layer is replaced by the Flatpak spawn portal sandbox. Document this in the UI and the docs, and verify the publisher on Flathub.
- **riscv64:** Debian 13 is the only major distribution with official riscv64 as of October 2026. Ubuntu requires RVA23, and Fedora's port is still an alternative architecture. Ship riscv64 `.deb` from Izcal's own repository targeting Debian 13 (rv64gc baseline, or RVA23 if Izcal's JIT needs the vector or bit-manipulation extensions), plus the tarball. Treat Ubuntu riscv64 as RVA23-only and Fedora riscv64 as best effort.
