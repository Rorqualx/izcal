**Implications:** Izcal's shell 6.11 ("Later" respected for 7 days, then restart at a safe moment) fits the CRA's "option to temporarily postpone". The CRA also requires two things 6.11 does not yet have. First, a **clear, easy opt-out of automatic security updates**, with instructions (Annex II 8(e)). Izcal needs a real Settings switch, documented, rather than only an enterprise policy. Second, **security-only updates "where technically feasible"**. An evergreen browser that ships fixes only inside 4-weekly feature releases must either build a security-only path (a patch release on the current version, as point releases already are) or document why one is not feasible. Every security release needs a **public advisory** (Part II (4), (8)), and actively exploited bugs need a **user notice** (Art. 14(8)). The download page and About must show the **support end date as month and year** (Art. 13(19)). Every security update must stay downloadable for **≥ 10 years** (Art. 13(9)), and any archive must warn about unsupported builds (Art. 13(11)). Art. 13(10) lets Izcal patch only the latest version, but only while users can move to it **without extra hardware or software cost**. Dropping an OS that users must pay to replace may therefore keep a security-fix duty alive for the last build on that OS until the support period ends (see 6.x). Annex I (2)(b) and (2)(m) make **reset** and **permanent data removal** product requirements, not just conveniences.

**Implications:** The evidence points the same way across studies. **Silent background install plus a restart that costs nothing** is what moves the version share (2.1). What drives avoidance is **restart cost, unclear value and fear of unwanted change** (2.2, 2.6, 2.8). Izcal's SH-24 (every tab, window and ledger entry survives; zero prompts re-asked) directly attacks the largest measured cost. The row text should answer the "information problem": what the update fixes (security or features), how long the restart takes, and what will be restored. Because negative experiences cause later avoidance, **feature updates must never ride with security fixes in a way that forces unwanted UI change**, which also matches CRA Part II (2). The **opt-out** that the CRA requires should be honest but not the default. The people who use it are often the more security-aware ones (2.7), so it should show what they give up rather than hide the switch. Windows' 7-day-then-engaged-restart model matches 6.11's 7 days. A learned "safe moment" (2.10) is an idea, but Izcal's no-telemetry rule means any such model must stay on the device.

| 3.7 | **Firefox's uninstaller leaves a scheduled task behind.** The background-update task (2.12) is one of the artefacts a full uninstall must remove. Others Izcal should expect are services, protocol and file-association registrations, AUMID/notification registrations, launch agents, and OS keychain items (Keychain, DPAPI-protected blobs, Secret Service collections). No vendor document describing a complete cleanup was found this session. | — | — | — | Low (no source; measurement question 8.4) |
| 3.8 | **Uninstall surveys.** Firefox is widely reported to open an exit-survey page after uninstall on Windows. Mozilla's privacy notice (effective 4 May 2026) mentions surveys only generally. Not verified. | — | [Firefox Privacy Notice](https://www.mozilla.org/en-US/privacy/firefox/) | 2026-05-04 | Low |

**Implications:** CRA Annex I (2)(m) and Annex II 8(d) make permanent removal of data and settings, and documented "secure decommissioning", product requirements. No mainstream desktop browser meets that by default on every OS: Chrome's checkbox is Windows-only, and Mac and Linux need manual folder deletion. Izcal should ship the **removal inside the product**, so the same flow works on all three OSes and needs no OS uninstaller: Settings > "Remove Izcal and all its data". It should list each item (profiles, OS-keychain entries, scheduled tasks, launch agents, protocol and file registrations, notification registrations, caches, crash dumps), delete them, and then hand off to the OS uninstaller or Trash. The Windows uninstaller should offer the same checkbox, **unchecked by default**, so data loss is never the accident. A **reset** that keeps user data (CRA (2)(b)) is already the recovery window's "Reset profile settings". No exit survey, because it is a network call after the person has said goodbye (FI-D12 spirit).

## 7. Release notes and transparency practice

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **Chrome Releases, Chrome 156 stable (20 October 2026).** "This will roll out over the coming days/weeks." Each security fix is listed as `[reward][bug id] Severity CVE-ID: summary. Reported by X on date`. "Access to bug details and links may be kept restricted until a majority of users are updated with a fix", and restrictions are kept for unfixed third-party library bugs. This release lists **353 security fixes**, many reported by AI-assisted researchers. | 353 fixes | [Chrome Releases](https://chromereleases.googleblog.com/2026/10/stable-channel-update-for-desktop_02018666648.html) | 2026-10-20 | High |
| 7.2 | **Mozilla Foundation Security Advisories.** Numbered `MFSA YYYY-N` (sequential per year). Impact is rated Critical, High, Moderate or Low; for example, Critical means code can run "with no user interaction beyond normal browsing". There is one advisory per product line and release, and ESR gets its own: on 20 October 2026, MFSA 2026-111 covered Firefox 158.0.1 and MFSA 2026-112 covered ESR 153.5.1. | 7.3 | **The CRA requires advisories.** "Advisory messages" must accompany security updates (Annex I Part II (8)). Public disclosure must include the affected product, impact, severity and remediation (Part II (4)), and users must be informed of actively exploited bugs, ideally machine-readably (Art. 14(8)). | — | Rows 1.10, 1.12, 1.20 | 2024-10-23 | High |

**Implications:** Izcal should publish **one advisory per security release**, numbered and dated, in a human page plus a **machine-readable feed** (CSAF or OSV-style JSON is the obvious candidate; the format choice belongs to the spec). Each advisory should give a severity on a published scale, the affected and fixed versions per channel and OS, CVE IDs, and a line saying whether the bug was actively exploited (which ties to the Art. 14 clock). The in-product update row can link to the advisory, which answers the "information problem" in 2.6. Restricting bug details until most users are updated is compatible with Part II (4)'s delay clause. Without telemetry, though, Izcal cannot measure "a majority of users", so it needs a time-based rule (for example, N days after release) stated in the disclosure policy.
