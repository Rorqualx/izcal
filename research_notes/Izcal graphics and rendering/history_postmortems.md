## 1. Chrome: GPU process, compositor and the paint pipeline (2010–2022)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Chromium "graphics overhaul"** introduced a GPU process that receives graphics requests from the sandboxed renderer and forwards them to OpenGL or, through **ANGLE**, Direct3D, in a modified sandbox. Stated motivation: "New APIs and markup like WebGL and 3D CSS transforms are a major motivation for this work"; it also put page compositing on the GPU because doing that last step on the CPU would cancel the gain. | — | [Chromium Blog, "Chromium Graphics Overhaul"](https://blog.chromium.org/2010/08/chromium-graphics-overhaul.html) (body read only as search snippet) | 2010-08-27 | Medium |
| 1.2 | Chromium's compositing design document: "The GPU process exists primarily for security reasons"; the sandboxed renderer "cannot directly issue calls to the 3D APIs provided by the OS"; "A GPU process crash (e.g. due to faulty drivers) doesn't bring down the browser." The command buffer is "patterned closely after the GL ES 2.0 API". | — | [GPU Accelerated Compositing in Chrome (prose design doc)](https://www.chromium.org/developers/design-documents/gpu-accelerated-compositing-in-chrome/) | updated 2014-05 | High |
| 1.3 | **Threaded compositing**: the compositor "can produce frames without needing to ask the main thread for anything". **Impl-side painting** gave the compositor control of "when paints occur", which "isolates rasterization from the rest of the frame production flow". Content layers are split into **tiles** and rastered per tile. A legacy **software path** that paints RenderLayers back to front was "still lingering as of May 2014". | — | Same as 1.2 | 2014-05 | High |
| 1.4 | **GPU rasterization** arrived in Chrome 37: "some paint workloads can go from 100ms/frame to 4-5ms/frame". It was gated by a device allow-list and a viewport trigger, and **content could veto it** (example: many SVGs with non-convex paths). DevTools exposed on/off and the veto reason. | 100 ms → 4–5 ms per frame (claim) | [How to get GPU rasterization (prose)](https://www.chromium.org/developers/design-documents/chromium-graphics/how-to-get-gpu-rasterization/) | 2014–2015 | High |
| 1.5 | **Slimming Paint** re-implemented Blink→cc recording around "a global display list rather than a tree of cc::Layers". Phases: SPv1 display items (M45); paint invalidation and property trees in Blink (M58); SPv175 paint chunks and raster invalidation (M67); BlinkGenPropertyTrees, layer list instead of tree (M75); **CompositeAfterPaint** (M94). It "fixed a fundamental compositing bug". | ~22,000 lines of C++ removed; Chrome CPU −1.3%; p99 scroll update +3.5%; p95 input delay +2.2% | [Slimming Paint (chromium.org)](https://www.chromium.org/blink/slimming-paint/) | 2015–2021 | High |
| 1.6 | **Why CompositeAfterPaint.** BlinkNG: layerization ran before paint, which "more or less required that there were circular dependencies in the code, which is a big problem for a rendering pipeline". Pre-paint (a post-layout walk) now issues invalidations, builds **property trees** and records pixel-snapped paint offsets; before it, invalidation was spread across phases, producing under- and over-invalidation bugs. Rule: "Once a stage has finished, its outputs should be immutable for the remainder of the rendering update." | BlinkNG began 2014 | [BlinkNG (developer.chrome.com)](https://developer.chrome.com/docs/chromium/blinkng) | 2022-04-19 | High |
| 1.7 | **Property trees**: four trees (transform, clip, effect, scroll); every element has a 4-tuple property-tree state; "it's much easier and faster to send property trees around to different threads and processes than full DOM state". **Paint chunks** group consecutive display items with the same state and are the input to layerization; merge by default, but not where state changes on the compositor thread (scrolling). | 4 trees | [RenderingNG key data structures](https://developer.chrome.com/docs/chromium/renderingng-data-structures) | 2021 | High |
| 1.8 | **Compositor frames** are lists of render passes of **quads** (tile, solid colour, texture); a render pass holds no pixels. Cross-process embedding uses **surface IDs**: a surface draw quad holds only the ID, and Viz substitutes the referenced frame during aggregation. | — | Same as 1.7 | 2021 | High |
| 1.9 | **RenderingNG** pipeline: Animate, Style, Layout, Pre-paint, Scroll, Paint, Commit, Layerize, Raster/decode/paint worklets, Activate, Aggregate, Draw. Viz is "good for stability in the face of bugs in GPU drivers or hardware"; the display compositor runs on its own thread because it "needs to be responsive at all times" and must not block on slow driver calls on the GPU main thread. | 12 stages | [RenderingNG architecture](https://developer.chrome.com/docs/chromium/renderingng-architecture) | 2021-07-26 | High |
| 1.10 | RenderingNG's own summary: work spanned "more than eight years"; reliability is "the single most important part"; CompositeAfterPaint "disentangles compositing from style, layout and paint". Timeline items: 2011 threaded scroll and animation; 2015 layer squashing; 2016 universal overflow scrolling, GPU raster on Mac; 2017 "GPU is used on over 60% of Android page views", image decodes on the compositor thread; 2020 "Always composite fixed-position". | >8 years; >60% of Android page views (2017) | [RenderingNG](https://developer.chrome.com/docs/chromium/renderingng) | 2021-06-22 | High |

**Implications:** Chrome spent about 2014–2021 undoing two early choices: compositing decided before paint, and a cc::Layer tree as the interface between paint and compositing. Izcal should start where Chrome finished: immutable per-phase outputs, property trees plus paint chunks as the only paint→compositor contract (already B6 and Stage 1 5.7), and layerization as a pure function after paint. Content-dependent GPU-raster "vetoes" (1.4) are a warning: every path the GPU raster cannot do becomes a hidden mode switch, which must be visible as data.

**Implications:** Chrome's arc is GL-centric Skia (Ganesh) → a portable modern-API layer (Dawn) under a rewritten rasterizer (Graphite) that uses depth testing and a closed, precompiled pipeline set. Izcal's own HAL on Metal, Vulkan and D3D12 matches where Chrome ended up, without the GL era. The SwiftShader removal shows that a **JIT in the GPU process** was judged a high security risk. Izcal's CPU fallback for WebGL/WebGPU must be interpreted or AOT-compiled, or placed in a separate sandbox, and the HGBA-2 "WebGL2 or CPU as the floor" needs re-deciding (see Open questions).

**Implications:** Firefox ran up to four rendering paths at once (Basic, D3D11/Advanced Layers, OpenGL layers, WebRender) and needed about four years (2017–2021) and a purpose-built software GL to delete the old ones. The lesson for Izcal is to have **one** paint/composite model with one CPU implementation of the same ops (HGBA-2 Section 5 already says this) from day one, and to make the CPU path a first-class back end of that model, not an emulation of a GPU API. OS-feature floors (Windows 7 without DirectComposition) can block a design for years, so Izcal's OS minimums are a design input.

**Implications:** WebKit's GPU Process is the clearest published statement of the security case: the content process loses all GPU/kernel driver access, and drawing crosses IPC as a recorded display list. Izcal's design (renderers never see device handles, I-2; display lists copied then validated, IPC-R7) is the same principle, which WebKit adopted late and incrementally over about 2020–2023. Apple's own argument that WebGL is translation overhead on Metal supports building WebGL on Izcal's HAL rather than on a GL emulation.

## 12. What survived, and why

| Survivor | Where it appears | Why it survived |
|---|---|---|
| **A separate, sandboxed GPU process** | Chrome 2010 (1.1–1.2), Firefox compositor/GPU process 2017 (3.5), WebKit GPU Process 2020–23 (4.2–4.3) | Driver crashes and kernel-driver attack surface; every engine converged on it, WebKit last. |
| **Threaded compositor with async scroll and animation** | Chrome 2011 (1.3), Firefox APZ (3.7), Android RenderThread (7.2), DirectComposition (5.3) | Input and animation latency must not depend on script. |
| **Property trees + paint chunks + layerize after paint** | Chrome Slimming Paint/CAP (1.5–1.7) | Removed circular dependencies; measurable CPU and latency wins. |
| **Display lists recorded in one process and replayed in another** | Android 2011 (7.1), WebKit GPU Process (4.2), Chrome OOP-R (2.1), WebRender (3.9) | Isolation and re-raster without re-running paint. |
| **Surface/quad compositor frames with ID references** | Chrome Viz (1.8), Fuchsia Flatland (7.5) | Cross-process embedding (iframes, video, canvas) without copying pixels. |
| **Modern explicit APIs (Metal, Vulkan, D3D12) behind one abstraction** | Graphite on Dawn (2.4), Firefox wgpu (8.9), Vello on wgpu (6.3), WebGPU itself (8.3) | GL-centric designs could not use modern GPUs well (2.4, 4.6). |
| **Closed, precompiled pipeline sets** | Impeller (7.3–7.4), Graphite (2.4) | First-use shader compilation causes jank. |
| **Driver blocklists and staged rollouts** | SwiftShader 2012 (2.7), WebRender filters (3.11) | Driver bugs are permanent (2.3). |
| **What did not survive** | Layer trees as the paint/composite interface (Chrome cc::Layer tree, Gecko Layers), multiple coexisting back ends (Firefox), JIT software GL in the GPU process (SwiftShader for WebGL), vendor-only path extensions (NVPR), engine-owned 2D rasterizers that lost on speed (LibGfx), compute-only 2D without bounded memory (Vello classic, not yet production) | |

**Implications:** Izcal's frame already assumes most survivors (GPU service, property trees, paint chunks, typed IPC). The new constraints from this history are: one back-end model with no second legacy path; a closed internal pipeline set compiled at build time; bounded GPU memory per frame for path rasterization; no JIT in the GPU process; and OS floors chosen with the compositor features they imply.

## Open questions

1. **CPU floor for WebGL/WebGPU.** HGBA-2's "WebGL2 or CPU as the floor" conflicts with Chrome's 2025 decision to fail context creation rather than fall back to a JIT software GL (2.8). Decide: no WebGL without a GPU, an interpreter-based CPU path, or a CPU path in its own sandboxed process. Measure the share of Izcal's target devices with no usable GPU.
2. **OOP-R benefits.** No published numbers for Chrome's OOP-R security or performance benefit were found (2.1). Measure black-box: renderer memory and GPU-process memory with raster in and out of process.
3. **WebRender shader compile time and crash rates by driver** were not found in prose (3.16). Measure first-frame time and pipeline creation counts black-box in Firefox on a cold shader cache.
4. **Canvas GPU↔CPU switching heuristics** in Chrome, Firefox and Safari (9.5). Measure black-box with repeated `getImageData` and timing.
5. **WebKit remote layer tree** and UI-process compositing (4.7): find prose (WWDC sessions, webkit.org docs).
6. **Graphite rollout** beyond Apple Silicon (2.6) and the measured MotionMark effect on other platforms.
7. **Vello Hybrid/CPU** production readiness and memory bounds (6.4–6.6): what exact bound does sparse-strip binning give? Relevant to Izcal's own design, read as research only.
8. **Slug patent status** and any other patents on outline-in-shader glyph rendering (10.3) before TX-D13's GPU outline path is fixed.
9. **ANGLE origin reason** (missing vs buggy GL drivers on Windows, 8.2): find the 2010 project announcement.
10. **Dates to re-check**: Chrome 113 stable date, Safari 26 release date, Firefox 105 OffscreenCanvas, Firefox 46 APZ on desktop, Firefox OMTC/OMTA versions, Opera Vega, the 2017 NXT and Obsidian proposals (8.4).
11. **Windows OS floor**: WebRender was blocked on Windows 7 lacking cross-process window painting features (3.11). Confirm Izcal's Windows minimum against DirectComposition and flip-model swap chains (os_surfaces_display strand).
