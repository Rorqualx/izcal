# Izcal graphics and rendering: compositing and scheduling

Compiled 19 October 2026. Primary sources were preferred (specifications, engine teams' prose design documents and blog posts, OS vendor documentation, bug-tracker discussion text).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known fact not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no engine source code was read for this note. No code files, headers, commits, diffs, code-review pages or source browsers of Chromium, Skia, Gecko, WebRender, WebKit, Servo or any other engine were opened. Two Chromium Markdown design documents under `docs/` ("How cc Works" and "Life of a frame") were read as prose, as the common brief allows. Several web-search summaries surfaced engine source files (WebRender's `picture.rs` documentation, Chromium's `main_thread_scrolling_reason.h` and viz `hit_test_region_list.h`, WebKit's `RemoteLayerTree` directory listings, Chromium code reviews). None was opened, and no value from them is used here (see "Sources not used and why"). Where this note says what an engine "does", it is evidence to reason from, not a shape to copy.

## 1. Why browsers composite, layerization, layer explosion and `will-change`

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Chrome's published rationale for GPU compositing: the GPU is "far more efficient" than the CPU for operations over many pixels; content already on the GPU (video, accelerated canvas, WebGL) avoids readbacks; CPU and GPU work in parallel. | — | [GPU Accelerated Compositing in Chrome](https://www.chromium.org/developers/design-documents/gpu-accelerated-compositing-in-chrome/) (Wiltzius, Kokkevis) | updated 2014-05 | High |
| 1.2 | That design listed eight **compositing reasons**: 3D or perspective transforms, accelerated video, accelerated canvas, composited plugins, CSS animation of opacity or transform, accelerated filters, a composited descendant, and **overlap** with a lower-z composited sibling. The last one is the source of **layer explosion**: any element painted above a composited layer must itself be composited to keep paint order correct. | 8 reasons | same | 2014-05 | High |
| 1.3 | Chrome's answer to explosion was **squashing**: multiple overlapping layers without direct reasons are merged into one backing store. Each layer "could be quite wasteful in terms of memory (VRAM especially)". | — | same | 2014-05 | High |
| 1.4 | Mozilla's published case against layers: they "take up a lot of memory and can actually make things slower"; too many layers fill memory and are slow to transfer; a repainted layer composited unchanged touches every pixel twice; animating `background-color` repaints the whole layer anyway. These are **performance cliffs**. | — | [Lin Clark, "The whole web at maximum FPS"](https://hacks.mozilla.org/2017/10/the-whole-web-at-maximum-fps-how-webrender-gets-rid-of-jank/) | 2017-10-10 | High |
| 1.5 | WebRender's published alternative: remove the paint/composite distinction, stop guessing layers, redraw every pixel each frame on the GPU from a retained display list, with culling, a render task tree to minimise intermediate targets, batching, and opaque/alpha passes with depth culling for overdraw. Claimed: pages at 15 fps in Chrome or Firefox ran at 60 fps (vendor claim, no data). Guidance cited: ≤ 100 draw calls per frame on desktop. | 60 fps; ≤ 100 draw calls | same | 2017-10-10 | High (claims as stated); Medium (performance) |
| 1.6 | WebRender later **reintroduced retained surfaces** as "picture caching". Glenn Watson's 2019 bug proposes that "all content drawn by WebRender is drawn into a picture cache surface", accepting extra GPU memory (to be reduced by detecting solid-colour tiles) because it gives **exact dirty rects for the full screen** and starts drawing directly into **OS compositor surfaces**. Landed for Firefox 71 after three attempts; one linked regression (tart/tscrollx) was WONTFIX. | Firefox 71 | [Bugzilla 1584439 (discussion text)](https://bugzilla.mozilla.org/show_bug.cgi?id=1584439) | 2019-10 | High |
| 1.7 | **Lesson from 1.4–1.6**: both extremes failed. Many DOM-derived layers wasted memory and fell off cliffs; "redraw everything every frame" wasted power and could not drive OS partial present or overlays, so it gained cached tiles back. The durable design is retained raster in coarse tiles, keyed by what changed, plus OS-compositor surfaces for whatever moves independently. | — | inference from 1.2–1.6, 3.6 | — | Medium |
| 1.8 | **CompositeAfterPaint**: layerization used to run before paint, which created circular dependencies (invalidation depended on past layerization). Chrome's lesson: "DOM elements are not a good 1:1 representation of an efficient or complete layerization scheme"; layerization now runs after paint, on paint chunks and property trees. Moving it off the main thread is named as future work; no numbers given. | Completed 2021 | [RenderingNG deep-dive: BlinkNG](https://developer.chrome.com/docs/chromium/blinkng) (Zager, Harrelson); [RenderingNG](https://developer.chrome.com/docs/chromium/renderingng) | 2022-04-19 | High |
| 1.9 | Chrome's data model: four **property trees** (transform including scroll offsets; clip; effect: opacity, filters, masks, blend modes, clip-path; scroll: chaining for compositor scrolling); **paint chunks** group display items sharing one property-tree state and are the input to layerize. Updates are O(interesting nodes), not O(layers). | 4 trees | [RenderingNG data structures](https://developer.chrome.com/docs/chromium/renderingng-data-structures); [How cc Works (prose)](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md) | 2021-08-24 | High |
| 1.10 | **CSS Will Change**: a hint with no direct visible effect except that a property whose non-initial value creates a stacking context or containing block must do so under `will-change` (so `will-change: opacity` creates a stacking context at opacity 1). The spec warns against `* { will-change: transform, opacity }`, says overuse can slow or crash a page, and tells authors to toggle it from script around the change and remove it afterwards. Status: CR Draft (5 May 2022); ED dated 29 Apr 2022. | — | [CSS Will Change 1 (ED)](https://drafts.csswg.org/css-will-change/) | 2022 | High |
| 1.11 | Developer guidance (Chrome, 2015): "every layer you create requires memory and management"; promote with `will-change` or `translateZ(0)`; aim for 4–5 ms compositing budget during scrolls; "only two properties" (transform, opacity) animate without layout or paint. This guidance is why `translateZ(0)` became a folk hack and why authors over-promote. | 4–5 ms | [Paul Lewis, web.dev](https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count) | 2015-03-20 | High |
| 1.12 | **Layer memory (derived)**: one viewport-sized RGBA8 surface at 1920×1080 is 7.9 MiB; at 2560×1600 it is 15.6 MiB. FP-14's visible-tab tile budget (2.5 × viewport px × 4 B) is 19.8 MiB at 1080p, i.e. about 2.5 full-viewport layers. No engine publishes per-layer memory statistics from the field. | 7.9 / 15.6 / 19.8 MiB | arithmetic; [frame.md FP-14](frame.md) | — | High (arithmetic) |

**Implications:** Izcal should layerize after paint from paint chunks and property trees (B6 already says so), treat `will-change` as a stacking-context rule plus a bounded hint, and make "overlap forced this layer" a recorded, explainable decision. The design must avoid both the DOM-derived layer explosion and WebRender's original no-retention model; FP-14's budget allows only about 2.5 viewport-sized surfaces, so layer count needs a hard cap with merging.

## 2. Tiling, raster scheduling and invalidation waste

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Chrome tiles each painted layer per raster scale (a sparse regular tiling). Published tile sizes: software raster "roughly 256x256 px"; GPU raster "roughly viewport width x one quarter viewport height". | 256² px; vw × vh/4 | [How cc Works](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md) | current | High |
| 2.2 | **Tile memory (derived)**: a 256² RGBA8 tile is 256 KiB; a GPU-raster tile at a 1920×1080 viewport is 1920×270×4 B ≈ 1.98 MiB. A 10×10 px change re-rastered at whole-tile granularity costs 655× (CPU tile) or 5,184× (GPU tile) the changed pixels. Chrome's documents do not publish whether or how partial-tile raster limits this. | 256 KiB; 1.98 MiB | arithmetic from 2.1 | — | High (arithmetic) |
| 2.3 | Chrome's TileManager rasters, in priority order: tiles needed to draw the active tree, tiles needed to activate the pending tree, prepaint tiles near the viewport, and offscreen image decodes. GPU memory is given to tiles by priority until the budget is full. Image decode is "the most expensive part of raster, especially relative to comparatively speedy gpu raster". | — | [How cc Works](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md); [GPU Accelerated Compositing](https://www.chromium.org/developers/design-documents/gpu-accelerated-compositing-in-chrome/) | current; 2014 | High |
| 2.4 | **Pending tree and activation**: changes from one JavaScript callstack must appear atomically, so commit copies main-thread state into a pending tree, raster completes, then activation swaps it in. The active tree keeps scrolling and animating meanwhile. If raster misses the deadline the old active tree is drawn. | — | [How cc Works](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md); [Life of a frame](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/life_of_a_frame.md) | current | High |
| 2.5 | Commit blocks the main thread while it copies (Chrome's commit is a blocking copy, not IPC). A Non-Blocking Commit prototype existed in March 2022. | — | same; [BlinkNG](https://developer.chrome.com/docs/chromium/blinkng) | 2022 | High |
| 2.6 | Chrome raster modes: software bitmaps in workers (zero-copy into GpuMemoryBuffers/IOSurface, or one-copy uploads), or GPU raster by serialising paint ops. GPU raster is "limited to one worker thread at a time" due to context locks. Paint ops are serialised partly to handle **TOCTOU** from a malicious renderer writing shared memory while the GPU process reads it. | 1 GPU raster thread | [How cc Works](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md) | current | High |
| 2.7 | GPU raster coverage history: over 60% of Android page views in 2017; Windows, ChromeOS, Android Go in 2018; remaining Android 2020. Out-of-process raster (in Viz, not the renderer) shipped 2018 (Android, Mac, Windows), everywhere except canvas 2019, canvas 2021. | >60% (2017) | [RenderingNG](https://developer.chrome.com/docs/chromium/renderingng) | 2021-06-22 | High |
| 2.8 | Firefox's displayport: APZ sizes the area painted beyond the viewport from panning velocity and direction, bounded for memory. Scrolling past it shows **checkerboarding** (unpainted content). | 2.9 | Solid-colour layers or tiles need no raster and no texture; both Chrome (solid colour layers) and WebRender (solid-colour "clear" tiles, 1.6) special-case them. | — | [How cc Works](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md); 1.6 | — | High |

**Implications:** tile size is a measured trade-off between per-tile overhead and invalidation waste; Izcal should publish its choice and measure waste (re-rastered px ÷ invalidated px) as a target, with sub-tile dirty-rect raster from the start. Commit must not copy on the main thread (Izcal's paint output is immutable and content-hashed, FP 6.4), and serialised paint data must be copied then validated (IPC-R7), which Chrome adopted for the same TOCTOU reason.

## 3. Damage tracking, partial present and energy

**Implications:** every Izcal platform backend needs a damage path: `eglSetDamageRegion`/buffer age (Android and EGL Linux), `Present1` dirty rects or DirectComposition surfaces (Windows), `damage_buffer` (Wayland), and on macOS **a CALayer tree of IOSurface tiles**, because a single CAMetalLayer cannot express damage. FP 6.6's "two swapchain buffers by default" is legal on all three APIs (CAMetalLayer must be set to 2 explicitly; its default is 3).

## 4. Threaded and asynchronous scrolling

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | Chrome's compositor thread (one per renderer) processes input, scrolls and animates; scroll deltas applied on the compositor that the main thread does not yet know about travel in BeginFrameArgs and are applied to Blink at BeginMainFrame. **Implications:** LY-D13's delta protocol is consistent with every engine's published shape (Chrome's deltas in BeginFrameArgs, APZ's generation counters, WebKit's stale-position bug as the failure case), and Izcal's explicit sequence numbers are stricter than any of them. Izcal's input regions should be built from the paint order (as WebKit's "fake paint" and LY-D14 do), must over-approximate and never under-approximate, and should treat 400/600 ms as the published precedent for a `preventDefault` timeout, recorded as a B1 input.

## Open questions

1. **Tile size and invalidation waste**: measure black-box (paint-flashing traces, GPU memory counters) Chrome's and Firefox's effective tile sizes and partial-raster behaviour; Firefox's picture-cache tile sizes are stated only in source and must be measured, not read.
2. **Layer memory in the field**: no engine publishes per-layer or per-tab GPU memory distributions; Izcal needs its own corpus measurement to set FP-14's layer cap.
3. **Partial-present energy on Windows, Wayland and Android**: only macOS (Firefox 70) has a published before/after; measure `Present1` dirty rects vs full present on an idle blinking cursor and a spinner.
4. **Input-to-photon**: build a camera or photodiode rig; obtain Casiez et al. (UIST 2017) through a library to see whether it has browser numbers.
5. **Compositor-animated properties in shipping engines today** (does Chrome composite `background-color` and `clip-path` by default now?): black-box test with a blocked main thread.
6. **Scroll snap on the compositor**: which engines choose the snap target off the main thread, and how they reconcile with a re-snap after layout; no prose source found.
7. **APZ displayport multipliers and Chrome prepaint extents**: source-only values; measure checkerboard rate vs memory.
8. **Render-blocking timeout** and **View Transition timeout**: both implementation-defined; measure engines and choose Izcal's values as recorded inputs.
9. **Iframe throttling margins**: take part in whatwg/html #10333; Izcal's rule must be process-model-independent.
10. **Presentation timestamps per OS**: which APIs give exact scanout time (DXGI frame statistics, `wp_presentation`, Metal `addPresentedHandler`, Android `Choreographer`/`SurfaceFlinger` timestamps) is for the OS-surfaces strand, but frame metrics here depend on it.
11. **`commit()` removal**: date and reason of removal from HTML not found this session.
