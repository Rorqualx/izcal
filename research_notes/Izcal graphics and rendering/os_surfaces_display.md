Compiled 19 October 2026. Primary sources were preferred (vendor documentation, protocol specifications, WWDC sessions, maintainers' posts, release notes).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, a single-author measurement, or a third-party table; **Low** = secondary source only, or the researcher's inference not checked against a source this session.

**Implications:** On macOS the sandboxed GPU service can present only through **IOSurfaces passed by Mach port or XPC** to the browser process, which owns the window, the layer tree and the display link (1.11–1.14); `CALayerHost` is private and `CARemoteLayer*` is legacy. Because `CAMetalLayer` has no damage API (1.8), Izcal's damage-region compositing on macOS must be **a tree of IOSurface-backed tiles and layers** the browser process updates, and whether IOSurface-as-`contents` (undocumented, 1.10) or one `CAMetalLayer` per tile owned by the browser process is the stable public route must be measured (Q1).

**Implications:** Because a DComp target can only be created by the window's own process (2.9) and cross-process HWND parenting couples input queues (2.10), the clean public design is: **the browser process owns the HWND and the DirectComposition tree; the GPU service renders into DXGI or composition-swapchain buffers bound to composition surface handles that the broker duplicates into it** (2.8). Timing should come from the compositor clock where available (Windows 11), not DXGI vblank, which follows the primary monitor (2.11).

## 11. Findings that bear on the frame's assumptions

- **"Vsync arrives from the GPU service as a message" (Stage 1 3.1/5.1).** On macOS (view display links, `CVDisplayLink` deprecated, 1.14) and Wayland (frame callbacks, presentation feedback, FIFO on the browser's connection, 3.4–3.6) the native timing signal lives **in the process that owns the window**, i.e. the browser process. Only Windows' compositor clock (2.11) and Android's Choreographer (5.4, if the GPU service holds a looper thread) can be read inside the GPU service. The design must either relay vsync from the browser process or give the GPU service a timing-only capability; this is a decision, not a given.
- **FP 6.6 "two swapchain buffers by default".** `CAMetalLayer` defaults to 3 (2 allowed, 1.2); Android needs 3 for smoothness (5.8); Windows needs ≥ 2 with latency 1 (2.1, 2.4). Two is achievable on macOS and Windows; Android likely needs an FP-14 exception.
- **HGBA-2 4.4 "damage-region compositing".** macOS has no per-layer damage API (1.8): damage there means a **layer/tile tree** in the browser process, which interacts with FP-14's tile budget.
- **GPU service sandbox (GPU-R1, win32k).** DirectComposition targets must be created by the HWND's owner (2.9): either the browser process owns the DComp tree (recommended by the evidence) or the GPU service owns a cross-process child HWND with the input-queue coupling of 2.10.
- **MD-S6 overlay energy.** Only Linux (3.13) and macOS partial compositing (1.9) have published numbers; Windows MPO has none (7.3).

## Open questions

- **Q1 (macOS, measure):** Is `CALayer.contents = IOSurface` (undocumented, 1.10) stable and as efficient as a `CAMetalLayer` drawable, including for direct-to-display promotion of video? Compare energy and `presentsWithTransaction` atomicity with resize, on Apple-silicon and Intel Macs.
- **Q2 (macOS, measure):** When does Core Animation scan out a layer directly (full-screen video, `AVSampleBufferDisplayLayer`, IOSurface contents, EDR)? Apple publishes no rules (1.21). Black-box with power readings and the Metal HUD (1.22).
- **Q3 (Windows, measure):** Can a sandboxed (low-integrity or LPAC) GPU service create composition surface handles, DXGI swap chains on them and the composition-swapchain presentation manager, and does `DCompositionWaitForCompositorClock` work there? Does MPO/Independent Flip still engage for a swap chain bound through a duplicated surface handle?
- **Q4 (Wayland, decide + measure):** Relay presentation feedback and FIFO waits from the browser process to the GPU service, or give the GPU service its own Wayland connection with a surface it owns (impossible without cross-client surfaces, 3.1)? Measure the relay's added latency.
- **Q5 (all, measure):** Input-to-photon latency per OS for a composited page, a scrolled page and an overlay-promoted canvas, with a photodiode rig in the style of 6.2, against the OS floors in 6.6.
- **Q6 (Windows, measure):** Energy of MPO and Independent Flip for video in a browser window vs composed, with the 3.13 method; no published numbers exist (7.3).
- **Q7 (Android, check):** Can a GPU service in an isolated process use `AChoreographer` and submit `ASurfaceTransaction`s on a parcelled `SurfaceControl`, and what does the system charge it for (ADPF sessions, frame-rate votes)?
- **Q8 (Android/FP):** Is a third buffer needed on Android for smoothness under Izcal's pacing (5.8), and should FP-14 carry that exception?
- **Q9 (Wayland, check):** wayland.app lists Weston 15 as lacking `color-management-v1`, which conflicts with Weston's announced colour work; read Weston's release notes and test before relying on the table (3.11).
- **Q10 (decide):** Use the composition swapchain (Windows 11, timed presents, statistics) as the primary Windows path and DXGI flip as the fallback, or DXGI everywhere? Windows 10 share at the planned ship date decides it.
- **Q11 (latency literature):** Retrieve Ng et al. 2012 and Jota et al. 2013 thresholds and the full Casiez 2017 results (6.2, 6.7) for the latency targets.
