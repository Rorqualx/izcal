# Izcal graphics and rendering: security and robustness

Compiled 19 October 2026. Primary sources were preferred (vulnerability advisories and the NVD records behind them, threat-intelligence reviews, papers, specifications, vendor documentation, bug-tracker discussion text).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a citation inside another primary source, secondary coverage that quotes the primary, or a vendor claim without data; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no engine source code was read for this note. No code files, headers, commits, diffs, code-review pages or source browsers of Chromium, Skia, ANGLE, Dawn, Tint, Gecko, WebRender, wgpu, Naga, WebKit, DXC, Mesa or any GPU driver were opened. Project Zero root-cause-analysis pages contain code excerpts, so only their titles (from the RCA index) are used. Where this note says what an engine "does", it is evidence to reason from, not a shape to copy.

This note **extends** the security scope's Sections 6.6 (IPC-R1 to IPC-R17), 6.7 (sandboxes per OS) and 6.9 (GPU-R1 to GPU-R8). It does not repeat them. Where a finding changes one of those rules, the implication line says so.

**Method notes**
- The shared web-search budget ran out after 7 searches from this strand. Later rows were checked by fetching known primary pages directly (W3C specifications, Khronos and Vulkan documentation, learn.microsoft.com, Apple's documentation JSON, kernel.org, Mozilla advisories, Bugzilla, papers as PDF read with `pdftotext`).
- **CVE counts** (Section 1.B) come from the NVD 2.0 API on 19 October 2026, with exact-phrase keyword searches such as `"in ANGLE in Google Chrome"` and `"Graphics: WebGPU component"`. NVD's *publication* year is used, which can lag the fix by days to weeks. A CVE whose description names two components can appear in two lists; the unique-ID totals de-duplicate. Counts are as of that date and will change.

**Implications:** the GPU process is now the place where a renderer compromise becomes a system compromise, and since 2025 the step out of it is a **vendor user-mode driver** reached by a call sequence or size the browser passed through unvalidated. Izcal's own WebGL and WebGPU validation (GPU-R2, GPU-R3) must therefore model **driver-visible state machines** (transform feedback active, fences, sizes passed to the driver), not only API validity. The 2026 volume (535 CVEs, 209 renderer-to-GPU) means the GPU service will receive a continuous stream of reports and must be designed so that a bug in validation does not reach the driver of another site (Section 3).

**Implications:** the security scope's Windows row ("Low integrity; LPAC if drivers allow; win32k lockdown not possible") stands, and row 2.7 adds a rule it lacks: **no fallback may ever move GPU work to a less sandboxed process** (the broker, or an unsandboxed in-process path); after repeated GPU-service crashes Izcal falls back to CPU raster in a sandboxed process and disables WebGPU, WebGL and canvas acceleration first. Because render nodes and WDDM isolate processes, not sites, any cross-site isolation inside the GPU service must be built by Izcal or obtained by splitting processes (Section 3).

## 3. Splitting GPU work across processes

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | In Chrome, the **Dawn wire server, Tint and DXC run in the GPU process** that also composites (DarthShader's architecture figure and text: dxc runs "in the GPU process of the browser"). | 3.7 | Firefox moved Canvas2D into the GPU process (remote canvas) and the move created a new renderer-to-GPU parser that yielded at least four sandbox escapes in seven months (row 1.10). **Implications:** Stage 1's "GPU service 1" puts the compositor, every site's WebGL/WebGPU, shader compilers and the driver in one process. Three published facts argue for a split: shader-compiler and validation bugs land in the compositor (3.1, 3.7), content-induced hangs revoke the GPU or crash Windows for everything in that process (3.3, 3.4), and the OS isolates GPU memory only per process (2.6). The spec should present **(a) one GPU service** versus **(b) a compositor GPU process plus content-GPU processes per (site, container) or per site group** as a real alternative, with per-process driver memory and context-switch cost as a **black-box measurement milestone** (3.6).

## Open questions

Black-box measurements (none of these values is published; each becomes a milestone):
1. **Per-process and per-context driver memory** on each reference device (Metal, D3D12, Vulkan on NVIDIA, AMD, Intel, Apple, Qualcomm, Mali): resident bytes for an empty device, a device with one swapchain, and N contexts. This decides whether content-GPU processes per (site, container) fit FP-14 (Section 3).
2. **Context-switch cost** between GPU processes with and without hardware-accelerated scheduling, measured as added frame latency for the compositor while a content process runs compute work.
3. **Scope of Metal `accessRevoked`** (per process, per device, per app bundle) and how many timeouts trigger it; the same for Windows TDR attribution when two processes share a GPU.
4. **Which DRM ioctls** each Linux driver (amdgpu, i915/xe, nouveau/nova, msm, panfrost/panthor, asahi) needs for Izcal's HAL, to size the seccomp ioctl allowlist; and whether Landlock `IOCTL_DEV` alone is usable on the reference kernels.
5. **LPAC for the GPU service on Windows**: which vendor UMDs load and run under LPAC (security scope Q-SEC-9); driver DLLs that read registry or files outside ACL'd locations.
6. **Whether each reference GPU zeroes** D3D12 placed resources, Vulkan allocations and Metal textures within one process (to size the cost of Izcal's own zeroing, not to rely on it).
7. **GPU.zip on Izcal's compositor**: does a page-controlled effect stack over an Izcal cross-origin iframe produce a measurable DRAM-traffic or render-time difference? Run the published PoC method against Izcal's own pipeline.
8. **Atomic-counter timer resolution** reachable from WGSL on each reference GPU (Giner et al.'s method), to decide whether WebGPU needs a permission or engagement gate.

Decisions for the spec:
9. One GPU service versus a compositor GPU process plus content-GPU processes (Section 3); what evidence reverses the choice.
10. WebGPU exposure: always, behind engagement, or behind a permission (Giner et al. recommend permission).
11. Crash-fallback policy: after N GPU-service crashes, CPU raster in which sandboxed process, and which APIs go away first.
12. Blocklist telemetry content and consent (device class, driver bucket, fault kind; no device-fault dumps by default).

Unverified and unknown in this note: Pwn2Own GPU entries (1.15); crash-rate data for Firefox WebRender and Chrome's GPU process (4.11); AmIUnique's exact entropy figures (6.4); Firefox's current canvas protections (6.9); any Chrome or Firefox design prose on per-site GPU processes (3.6); row 2.3's win32k reasoning against a Microsoft page.
