# Izcal graphics and rendering: frame

Written 19 October 2026 (phase 1 of the first-principles-spec method, `.claude/skills/first-principles-spec/SKILL.md`).

## The problem and who has it

Izcal needs its own renderer and graphics stack. HGBA-2 2.3.0 (M-1 part 1) excludes WebRender and wgpu by name, and its general rule excludes every library that does this work: Skia (Ganesh and Graphite), Dawn, ANGLE, naga, Tint, Vello, tiny-skia, lyon, Pathfinder, cairo, Direct2D used as the engine's rasterizer, SwiftShader, Mesa components (llvmpipe, lavapipe, Zink), glslang, SPIRV-Cross, DXC used as a library, and their kind. HGBA-2 Section 4.4 (WebRender on OpenGL plus wgpu for WebGPU; Vello as the Stage 2 candidate; one render graph as a P-2 outcome), decision D3 (wgpu), target P-2 (Vello versus WebRender) and Stage 1 design 5.7's "two GPU stacks" are superseded and are what this spec replaces. The layout spec's LY-D22 asks for a graphics owner to be named before LY-M0's design review and lists what that owner must implement (`hg-paint-order`'s read contract, the browser-side hit-test region message, the scroll delta protocol, pixel snapping, the device-pixel box for ResizeObserver, a co-signed paint share of FP-11's 360 B† per node).

The owner's direction (19 October 2026): engine work is all ours; OS graphics APIs (Metal, Vulkan, Direct3D 12, DXGI, IOSurface, Core Animation layers, DirectComposition, Wayland and X11 protocols, Android surfaces) and GPU drivers are OS interfaces and allowed; the Vulkan loader must be classified honestly; everything shipped must be available under MIT; no shortcuts for time or complexity; staging only for correctness, security or measurement reasons; cost is a planning fact; the GPU process and shader compilers are a top attack surface, designed for security from first principles; another engine's source code is never evidence (M-1 part 3).

**Scope of this spec** (from the layout spec's fragment tree to photons):
- **Paint**: display list (paint ops) from the fragment tree, CSS 2 Appendix E paint order, stacking contexts, property trees (transform, clip, effect, scroll), paint chunks, ink overflow, pixel snapping, paint invalidation, and the `hg-paint-order` contract layout reads.
- **2D rasterizer**: paths, strokes, dashes, gradients, images and image filtering, clips, masks, CSS and SVG filters, blend modes, group opacity, anti-aliasing, text (glyph masks from atlases, the GPU outline path for large glyphs), GPU and CPU paths, determinism.
- **Compositing**: layers and layerization, tiling, damage tracking, partial present, compositor (threaded) scrolling with the layout spec's delta protocol, compositor-driven animations (transform, opacity, filter, scroll-driven) under contract with the future animation spec, out-of-process iframe surfaces, video layers, overlays and direct scanout.
- **GPU process and GPU abstraction**: Izcal's own abstraction directly on Metal, Vulkan and Direct3D 12 (a "graphics HAL" under HGBA-2 Section 5's `Gpu` device class), memory allocation and budgets, synchronization, device loss, driver workarounds and blocklists, GPU process sandboxing.
- **Shaders**: Izcal's own shader language and IR for internal shaders, WGSL front end for WebGPU, GLSL ES front end for WebGL, back ends to MSL, SPIR-V and DXIL (or what each API requires), validation, robustness (bounds checks), pipeline caching.
- **Web APIs**: WebGPU (core and compatibility mode), WebGL 1 and 2 (implemented on Izcal's abstraction, no ANGLE, no native GL), Canvas 2D and OffscreenCanvas, ImageBitmap, `createImageBitmap`, canvas readback, `VideoFrame` drawing.
- **SVG rendering** (paint side; the layout spec owns the SVG boundary: outer `<svg>` sizing, `foreignObject`, SVG text positioning hand-off).
- **Colour management and HDR output** (with the images and media spec: `hg-colour` is media's crate (MD-D28); media requires display conversion, tone mapping and gain-map application in the GPU service, MD-D8 and MD-D9).
- **Text rendering integration** (fonts and text spec: TX-D13 CPU integer raster in the renderer, masks to the partitioned atlas, GPU outline path above 64 device px† under TX-33's tolerance, the bounded path format, compositing colour space for text masks, CPU compositing of canvas 2D text).
- **Video frame compositing** (frame selection on the audio clock, YUV planes and descriptors, zero-copy OS handles from the media process).
- **Frame scheduling and vsync**, display and OS surface integration on macOS, Windows, Linux (Wayland and X11) and Android.
- **GPU memory budgets** (footprint spec FP-14, FP-D14, Section 6.6), GPU process robustness, and **observability** (DevTools and agents).

**Not in scope**: layout (layout spec), style (style spec), text shaping and glyph raster (fonts and text spec), image and video decode and `hg-colour`'s numeric contract (images and media spec), the animation engine's timing model (future animation spec; this spec runs compositor animations it is handed), PDF (its own spec), WebXR (named as a future consumer only), WebNN and ML (HGBA-2 4.5).

## Who has the problem

- **People browsing**: pages that render correctly, scroll and animate smoothly at the display's rate, with low input-to-photon latency, correct colour on wide-gamut and HDR displays, low battery use (video playback, idle pages), no crashes or black screens from driver bugs, and no way for a page to fingerprint their GPU or read another site's pixels.
- **Web developers**: "why did this repaint?", "why is this janky?", "why is this layer here?", "why does this look different on Windows?", "why is my WebGPU shader slow or rejected?", "why does canvas readback differ between machines?". Graphics features (WebGPU, `backdrop-filter`, colour spaces, View Transitions) are uneven across engines.
- **Developers' tools and agents**: structured rendering data instead of screenshots; deterministic pixels for testing.
- **Izcal's engineers**: a graphics stack that is deterministic where web-observable (B1, DET-1, JS-D15), checkable against a reference rasterizer, memory-safe outside a small audited FFI layer, within FP's GPU budgets, and secure against hostile display lists, shaders and command streams.

## What Izcal's specs already decide or constrain (IDs that apply)

- **HGBA-2 2.3.2**: P1–P6 precedence (security > compatibility > robustness > performance > hardware reach); **M-1** parts 1–4 (MIT-only shipped code and data; OS interfaces and drivers allowed; engine source never evidence; other engines black-box only; spec anchors at pinned revisions); I-1 (renderer per (site, container)); I-2 (zero ambient authority; renderers never see device handles); I-6 (timer coarsening); Section 3 architecture (one GPU service, broker-mediated); **Section 5 HAL**: device classes not vendors, `Capabilities` with tiers (WebGpuCore, WebGpuCompat), measured `CostModel`, all work async with fences, no blocking map, sticky validation errors, `DeviceLost` with epochs, three losses in ten minutes blocklists the class for the session, `PolicyDenied` indistinguishable from `Unsupported`, every `Op` has a CPU implementation, rendering fallback must match pixel-for-pixel on reftests, no synchronous per-frame readback; **Section 4.4** event-driven rendering (damage-region compositing, VRR, panel self-refresh); WebGPU exposure tiers WebGPU-core and WebGPU-compat (`featureLevel: "compatibility"`), WebGL2 or CPU as the floor, driver blocklist in the GPU service; targets **R-1** (GPU offload never hurts p95 frame time), **R-2** (device-loss recovery ≥ 99%, no renderer crash, no tab reload), **R-6** (cost model calibrated), S-7 (MTE in the GPU process where present); superseded: D3, P-2, the Section 4.4 WebRender and wgpu text.
- **HGBA-3**: B1 (deterministic substrate), B2 (typed capability IPC), B5 (incremental with from-scratch reference), **B6** (property trees as data-oriented phase outputs), **B7** (pixel-optional rendering for unobserved and agent tabs), B9, B10 (AI off), **DET-1** (display-list hash in 1,000 of 1,000 replays; GPU-dependent output out of scope), PRIV-2 (fingerprinting).
- **Stage 1 design**: process map (GPU service 1, sandboxed, launched at first paint); G1–G9 (G5 `forbid(unsafe_code)` unless inventoried; G7 renderer crates use only generated IPC endpoints of `hg-gpu`; G9 anchors); 3.3 ("GPU, audio, media: out of scope for simulation; paint checked as display-list hash; raster by reftests and `rr`"); 3.1/5.1 (vsync arrives from the GPU service as a message; in simulation a scheduled event); 5.7 (paint produces property trees and paint chunks; four trees; pixel-optional stops after chunk generation); D-S1 (readback surfaces get seeded noise per (site, container, session)); Graphics track was 2 engineers (8.3).

- **JavaScript engine spec 0.3 (accepted)**: JS-D15 (every timing-dependent decision is a recorded B1 input: production applies when ready, logged when recording, enforced in replay); JS-D19 (CET/GCS/PAC: no return address written outside prologues); JS-D12 (one math implementation per function, no FMA contraction); G13–G18 (G18 checked arithmetic on untrusted sizes); tier P (never panics on any input) for shared processes.

## What success looks like (measurable)

Candidate target dimensions, to become GR- targets:
- **Correctness**: WPT reftests in the paint-related directories (`css/css-backgrounds`, `css/css-borders`, `css/css-images`, `css/filter-effects`, `css/compositing`, `css/css-masking`, `css/css-transforms`, `css/css-color`, `svg/`, `html/canvas/`, `webgl/` via the Khronos CTS, the WebGPU CTS) at Izcal's own floors; GPU raster equals the CPU reference within a stated tolerance on every reference device; hit testing equals paint order (LY-7).
- **Determinism**: display-list hash in DET-1; readable pixels (canvas, `toDataURL`) identical across GPUs, OSes and drivers wherever Izcal chooses to make them canonical; CPU raster bit-identical across ISAs.
- **Security**: GPU service sandboxed on every platform; no renderer-supplied payload parsed outside generated `.hgidl` readers; every shader validated and bounds-checked; fuzzing of display lists, command streams and shader compilers; device-loss and hang recovery.
- **Performance and energy**: p95 frame time and dropped frames on the corpus and MotionMark relative to the best shipping engine; input-to-photon latency; scroll and animation smoothness under main-thread load; idle wakeups; video playback energy against the OS player.
- **Footprint**: FP-14's GPU rows; FP-10's U ≤ 15%†; paint bytes per node within the share co-signed with layout.
- **Robustness**: R-2 device-loss recovery; driver workaround coverage; crash rate per device class.
- **Observability**: "why did this repaint", layerization reasons, per-frame timelines, GPU memory by site, delivered to DevTools and agents as data.

## Research strands (phases 2 and 3)

1. `history_postmortems.md`: browser rendering and GPU history, what each design did, why, its limits and fate.
2. `gpu_apis_platforms.md`: Metal, Vulkan, D3D12 and their shader binary formats as OS interfaces; licences of the loader, registries and Rust binding crates; minimum OS and driver coverage.
3. `os_surfaces_display.md`: window surfaces, presentation, vsync and frame pacing, overlays, HDR and colour output, per OS (macOS, Windows, Wayland, X11, Android).
4. `rasterization_paint.md`: 2D rasterization research, paint order, display lists, effects, determinism of raster.
5. `compositing_scheduling.md`: layers, tiling, damage, threaded scrolling, compositor animations, frame scheduling, latency, video compositing, OffscreenCanvas.
6. `webgpu_webgl_shaders.md`: WebGPU, WGSL, WebGL, shader translation, validation, robustness, conformance suites and their licences.
7. `security_robustness.md`: GPU-process exploits, sandboxing, driver bugs, device loss, blocklists, side channels, fingerprinting, GPU memory isolation.
8. `gaps_opportunities.md`: what developers and agents cannot see, DevTools history, accessibility in rendering, energy, cost and team-size evidence.
