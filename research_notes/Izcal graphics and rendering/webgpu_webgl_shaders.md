# Izcal graphics and rendering: WebGPU, WebGL and shaders

Compiled 19 October 2026. Primary sources were preferred (W3C and Khronos specifications at their current revisions, Apple and Microsoft language and API specifications, peer-reviewed papers, browser teams' own release posts, licence files of test suites).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a well-known fact not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no engine source code was read for this note. No code files, headers, commits, diffs, code-review pages or source browsers of Chromium, Dawn, Tint, ANGLE, Gecko, wgpu, naga, WebKit, Servo, Mesa, SwiftShader or DXC were opened. Search results that pointed to ANGLE commits on android.googlesource.com and chromium.googlesource.com, and to a Tint Markdown file on dawn.googlesource.com, were not opened or used. The DarthShader, ICST 2023 and PLDI 2023 papers print shader test inputs and name engine commits; only their prose findings and tables are used here. Where a value is stated only in an engine's source, it is listed under **Open questions** as a black-box measurement.

## 1. WebGPU security and privacy model (the spec's own text)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Status.** WebGPU is a W3C **Candidate Recommendation Draft** dated 15 September 2026; the Editor's Draft is dated 16 October 2026. Editors are from Google and Mozilla; Apple editors are listed as former editors. | CRD 2026-09-15 | [WebGPU (TR)](https://www.w3.org/TR/webgpu/); [Editor's Draft](https://gpuweb.github.io/gpuweb/) | 2026-09-15 | High |
| 1.2 | **The general approach is total validation**: "strictly validating all the commands before they reach GPU, ensuring that a page can only work with its own data." Native APIs leave invalid usage undefined, so "the range of allowed WebGPU behaviors is defined for any input" and the implementation "only reach[es] the driver with the valid workloads." | — | [WebGPU §2.1.1 CPU-based undefined behavior](https://www.w3.org/TR/webgpu/#security-cpu-ub) | 2026-09-15 | High |
| 1.3 | **Shaders are validated before any translation**: "the WebGPU implementation has to validate it before doing any translation (to platform-specific shaders) or transformation passes." The shader instruction set and its behaviours are defined by WebGPU itself. | — | [WebGPU §2.1.2](https://www.w3.org/TR/webgpu/#security-gpu-ub) | 2026-09-15 | High |
| 1.4 | **All memory is conceptually zeroed**, including shader variables and **workgroup memory**. If the native API cannot clear workgroup memory, the implementation "transforms the compute shader to first do a clear across all invocations, synchronize them, and continue". Because initialization status is only known at enqueue, some implementations need an "unoptimized late-clear at enqueue time", and all implementations "should issue a developer console warning" about it. | — | [WebGPU §2.1.3 Uninitialized data](https://www.w3.org/TR/webgpu/#security-uninitialized) | 2026-09-15 | High |
| 1.5 | **Out-of-bounds shader access** may be prevented by the driver's "robust buffer access" mode **or** by inserting manual bounds checks; manual checks are needed only for array indexing because `minBindingSize` validation covers fixed struct fields. Allowed outcomes for an OOB **load**: a value from elsewhere in the same resource, `(0,0,0,X)`, or partially discarding the draw/dispatch. For an OOB **store**: write elsewhere in the resource, discard the write, or partially discard the call. | 3 load outcomes, 3 store outcomes | [WebGPU §2.1.4 Out-of-bounds access in shaders](https://www.w3.org/TR/webgpu/#security-shader) | 2026-09-15 | High |
| 1.6 | **NaN and infinity** may only affect arithmetic results, never cause "other side effects". | — | [WebGPU §2.1.5](https://www.w3.org/TR/webgpu/#security-invalid-data) | 2026-09-15 | High |
| 1.7 | **Driver bugs**: the WG will ask vendors to run the WebGPU CTS in driver testing "like it was done for WebGL"; implementations are "expected to have workarounds" and to "disable WebGPU on drivers with known bugs that can't be worked around." | — | [WebGPU §2.1.6](https://www.w3.org/TR/webgpu/#security-driver-bugs) | 2026-09-15 | High |
| 1.8 | **Timing.** Timestamp queries return the result of HR-Time's **coarsen time** with `crossOriginIsolatedCapability` false, i.e. the non-isolated resolution. The spec says cross-origin isolation "never applies" to device/queue timelines because the device timeline "typically runs in a process that is shared by multiple origins", and GPUs may lack Meltdown-style isolation. Writable storage buffers can also build high-resolution timers; no mitigation is specified for those. Chrome documents the quantization as **100 µs**. | 100 µs (Chrome) | [WebGPU §2.1.7.2](https://www.w3.org/TR/webgpu/#security-timing-device); [Chrome "New in WebGPU 121"](https://developer.chrome.com/blog/new-in-webgpu-121) | 2026-09-15; 2024-01 | High |
| 1.9 | **Denial of service**: an implementation "may" limit GPU memory per application and "may set up 'watchdog' timer" for GPU time "for more than a few seconds". Row hammer: no specific mitigation. Workload identification and VRAM-exhaustion probing (§2.1.10–2.1.12) are acknowledged and **not mitigated**. Abuse (mining) cannot be prevented; UAs may throttle background tabs and warn on power. | "a few seconds" (unquantified) | [WebGPU §2.1.8–2.1.13](https://www.w3.org/TR/webgpu/#security-dos) | 2026-09-15 | High |
| 1.10 | **Privacy cap**: "A user agent must not reveal more than **32 distinguishable configurations or buckets**." Hardware limits may be binned; default limits are "deliberately high enough" so most apps never request more; validation runs against requested limits, so real hardware limits are not exposed "by accident." Privacy-critical UAs "should utilize software implementations" to remove rasterization and precision artifacts. | 32 buckets | [WebGPU §2.2, §2.2.1–2.2.3](https://www.w3.org/TR/webgpu/#privacy-considerations) | 2026-09-15 | High |
| 1.11 | **Compilation caches are a cross-origin channel**: a cached `createComputePipelineAsync()` resolves measurably faster, which "can leak information across origins (like 'did the user access a site with this specific shader')", so UAs "should follow the best practices in storage partitioning". The driver's own shader cache is named too: UAs "may want to disable these when at all possible, or add per-partition data to shaders" so the driver treats them as different. | — | [WebGPU §2.2.4 User Agent State](https://www.w3.org/TR/webgpu/#privacy-user-agent-state) | 2026-09-15 | High |
| 1.12 | **Adapter identifiers**: when exposed by default they "should be as broad as possible", for example vendor and general architecture without the specific adapter. A proxy adapter may be reported. Full detail may be revealed with user consent. `GPUAdapterInfo` has `vendor`, `architecture`, `device`, `description`, `subgroupMinSize`, `subgroupMaxSize`, `isFallbackAdapter`; any string may be empty. `device` "may be a PCI device ID". | 7 attributes | [WebGPU §2.2.6](https://www.w3.org/TR/webgpu/#privacy-adapter-identifiers); [GPUAdapterInfo](https://www.w3.org/TR/webgpu/#gpuadapterinfo) | 2026-09-15 | High |
| 1.13 | **Errors are asynchronous and contagious**: an object created from an invalid object is invalid and never becomes valid. After device loss, validation need not run, errors stop, and most operations "appear to succeed" except `mapAsync()`, so whether work ran is unobservable. `GPUDeviceLostReason` has only `"unknown"` and `"destroyed"`. | 2 loss reasons | [WebGPU §3.2.1 invalidity](https://www.w3.org/TR/webgpu/#invalidity); [§22.1 Fatal Errors](https://www.w3.org/TR/webgpu/#fatal-errors) | 2026-09-15 | High |
| 1.14 | **Implicit synchronization**: the implementation, not the page, tracks resource state. Each compute dispatch and each render pass is a **usage scope**; within a scope a subresource's usages must be compatible, checked during encoding. Barriers are therefore derived by the implementation from usage scopes (an implementation inference: the specification defines usage scopes and their validation and never says "barrier"; phase 8). | — | [WebGPU §3.4.4 Synchronization](https://www.w3.org/TR/webgpu/#programming-model-synchronization) | 2026-09-15 | Medium |
| 1.15 | **Why the API is shaped this way (explainer)**: it "must be implementable and efficient in browsers that use a GPU-process architecture"; GPU processes "are typically shared between multiple origins" and "must validate all messages". A content-side `GPUBuffer` "can use maybe 150 bytes" yet hold "a 1GB allocation". Synchronous errors are "prohibitively expensive" across processes, hence error scopes. Mapping needs a shared-memory staging copy because driver mappings live only in the GPU process. | 150 B vs 1 GB example | [WebGPU Explainer §2.1, §2.2, §3.3](https://gpuweb.github.io/gpuweb/explainer/) | 2026 (living) | High |
| 1.16 | **Why not "WebGL 3"**: WebGL's OpenGL lineage "doesn't match the design of modern GPUs" and makes WebGL "increasingly hard to implement" on modern APIs. **WebGL 2.0 Compute was abandoned** because "the impedance mismatch with native APIs made the effort incredibly difficult." Non-goals include hardware that cannot do general compute. | — | [Explainer §1.3](https://gpuweb.github.io/gpuweb/explainer/) | 2026 | High |

**Implications:** WebGPU's security model is "validate everything in the GPU process, define every shader behaviour, zero all memory", which fits HGBA-2's HAL rules (sticky errors, epochs, device loss) closely. The spec itself names pipeline caches and driver caches as cross-origin channels, so Izcal's pipeline cache must be keyed by the networking spec's partition key from day one (P18), and Izcal needs its own answer for driver caches.

## 3. WGSL: the language's guarantees

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Status.** WGSL is a CRD dated 21 September 2026; editors from Google plus one independent; the Test Suite field points to the WebGPU CTS `shader/` tree. | CRD 2026-09-21 | [WGSL (TR)](https://www.w3.org/TR/WGSL/) | 2026-09-21 | High |
| 3.2 | **Three error times**: shader-creation (source only), pipeline-creation (entry point plus overrides), and **dynamic** errors during execution, which "may or may not be detectable" (e.g. data races). An "uncategorized error" may occur even for a valid shader ("too complex" or an implementation defect). Only code reachable from the chosen entry point is compiled per pipeline. | 3 phases | [WGSL §2.1 Shader Lifecycle, §2.2 Errors](https://www.w3.org/TR/WGSL/#shader-lifecycle) | 2026-09-21 | High |
| 3.3 | **Recursion is forbidden**: "It is a shader-creation error if any module scope declaration is recursive"; the declaration graph "must not have a cycle", so functions cannot recurse directly or indirectly. The uniformity analysis relies on this ("There is no risk of being trapped in a cycle, as recurrence is forbidden"). | — | [WGSL, Declaration and Scope](https://www.w3.org/TR/WGSL/); [§15.2.2](https://www.w3.org/TR/WGSL/#uniformity) | 2026-09-21 | High |
| 3.4 | **Minimum complexity limits** an implementation must accept: 1023 struct members; nesting depth 15 for composite types and 127 for brace-enclosed statements; 255 function parameters; 1023 switch case selectors; 8192 B private, 8192 B function-scope, 16384 B workgroup; 64 B immediate; 2047 elements in an array value constructor. Shaders beyond them "should" get an error. | values as listed | [WGSL §2.4 Limits](https://www.w3.org/TR/WGSL/#limits) | 2026-09-21 | High |
| 3.5 | **Integers wrap**: `i32` is two's complement and concrete integer overflow is "modulo 2^bitwidth". **Division by zero** and `INT_MIN / -1` are defined at run time: the result is `e1`; they are a shader-creation error if operands are const-expressions and a pipeline-creation error if override-expressions. | — | [WGSL §6.2.3 Integer Types](https://www.w3.org/TR/WGSL/#integer-types); WGSL arithmetic expressions (`e1 / e2`) | 2026-09-21 | High |
| 3.6 | **Out-of-bounds access is a dynamic error** with a bounded set of outcomes: trap (invocation terminates, stage outputs zero), an invalid load returning a value from anywhere in the bound buffer (or the originating variable), the zero value, or `(0,0,0,x)` with x in {0, 1, max int} or {0.0, 1.0}; an invalid store may write anywhere in the bound buffer or variable, or not execute. | — | [WGSL §6.5.7 Out-of-Bounds Access](https://www.w3.org/TR/WGSL/#out-of-bounds-access) | 2026-09-21 | High |
| 3.7 | **Floating point**: no rounding mode is specified; no FP exceptions; signaling NaNs may become quiet; the sign of zero may be ignored; subnormals may be flushed for listed operations only. **Finite-math assumption**: overflow, infinity or NaN in a const-expression is a shader-creation error and in an override-expression a pipeline-creation error; at run time an implementation may assume none occur, and if one does the result is an **indeterminate value** (so `min`/`max` may misbehave). `fma` may be split into multiply and add. | — | [WGSL §15.7.2 Differences from IEEE-754](https://www.w3.org/TR/WGSL/#differences-from-ieee754) | 2026-09-21 | High |
| 3.8 | **Accuracy is a table, not "correctly rounded"**: `+ - *` and comparisons correctly rounded; `x / y` 2.5 ULP for \|y\| in [2^-126, 2^126] (f32); `atan` 4096 ULP (f32) and 5 ULP (f16); `acos`/`asin` absolute error ~6.8×10^-5 (f32). Results therefore legitimately differ between GPUs. | values as listed | [WGSL §15.7.4 Floating Point Accuracy](https://www.w3.org/TR/WGSL/#floating-point-accuracy) | 2026-09-21 | High |
| 3.9 | **Uniformity analysis** is a static, call-graph-ordered analysis (leaves first) that rejects collective operations (barriers, derivatives, subgroup ops) outside uniform control flow. The spec states its properties: **sound**, stable under inlining and outlining, and able to give a chain of implications for error messages. It assumes no dynamic errors. Subgroup uniformity triggers a `subgroup_uniformity` diagnostic whose severity is controllable. | — | [WGSL §15.2 Uniformity](https://www.w3.org/TR/WGSL/#uniformity) | 2026-09-21 | High |
| 3.10 | **Alias analysis**: each memory view has a statically determinable root identifier; at each call site it is a shader-creation error if two root identifiers alias and one access is a write. This rules out the aliasing patterns that MSL, HLSL and SPIR-V back ends would otherwise have to assume. | — | [WGSL §11.4.1 Alias Analysis](https://www.w3.org/TR/WGSL/#alias-analysis) | 2026-09-21 | High |
| 3.11 | **`discard` is demote**: it "converts the invocation into a helper invocation and throws away the fragment output"; only earlier statements have observable effects. This matches SPIR-V `OpDemoteToHelperInvocation`, not GLSL's terminate semantics (row 5.5). | — | [WGSL §9.4.11 Discard Statement](https://www.w3.org/TR/WGSL/#discard-statement) | 2026-09-21 | High |
| 3.12 | **Memory model**: "In general, WGSL follows the **Vulkan Memory Model**", which the spec notes is "a textual version of a formal Alloy model". | — | [WGSL §14.5 Memory Model](https://www.w3.org/TR/WGSL/#memory-model) | 2026-09-21 | High |
| 3.13 | **Grammar**: specified "in a form suitable for an **LALR(1)** parser", with one customization: **template list discovery** (disambiguating `<`) runs as a separate pass before parsing (or on demand during tokenization). A recursive-descent form is also given (§18). | — | [WGSL §3 parsing; §18 Grammar for Recursive Descent Parsing](https://www.w3.org/TR/WGSL/#grammar-recursive-descent) | 2026-09-21 | High |
| 3.14 | **Language extensions** are feature-detected through `navigator.gpu.wgslLanguageFeatures`, e.g. `readonly_and_readwrite_storage_textures`, `packed_4x8_integer_dot_product`, `unrestricted_pointer_parameters`, `pointer_composite_access`, `uniform_buffer_standard_layout`, `subgroup_id`, `subgroup_uniformity`, `texture_and_sampler_let`, `linear_indexing`, `immediate_address_space`, `fragment_depth`, `swizzle_assignment`. | 12+ named | [WGSL language extensions](https://www.w3.org/TR/WGSL/#language-extensions-sec) | 2026-09-21 | High |
| 3.15 | No **mechanized (proof-assistant) semantics of WGSL** was found this session; the search budget ran out before a dedicated search. The only formal anchor found is the Vulkan Memory Model's Alloy model (row 3.12). | — | — | — | Low |

**Implications:** WGSL defines almost every behaviour that MSL, HLSL and SPIR-V leave undefined (division, OOB, aliasing, recursion, discard), so Izcal's WGSL front end can be a typed, total, checkable translator with no UB at its input. The deliberately loose accuracy table means readable WebGPU output cannot be canonical across GPUs; DET-1 already scopes GPU-dependent output out.

## 4. Published shader-compiler testing and the bug classes it found

| # | Finding | Numbers | Source | Date | Conf. |

## Open questions (measure black-box or decide)

1. **DXIL signing.** Can a D3D12 runtime and driver load DXIL that was not produced or hashed by Microsoft's DXC/dxil validator, on the Windows versions Izcal supports? This decides whether Izcal can emit DXIL directly (removing DXC, row 4.6) or must ship HLSL through DXC as an OS-adjacent tool. Read Microsoft's DXIL and Agility SDK documentation, then test.
2. **MSL to metallib.** Does Izcal compile generated MSL with the OS's runtime compiler (`newLibraryWithSource`, an OS interface), and what are the cold-compile times? Measure on reference Macs and iOS devices.
3. **Driver shader caches as cross-site channels** (row 1.11). Measure whether Metal, Vulkan (per driver) and D3D12 driver caches make a second compile of an identical shader measurably faster across sites; decide between disabling them and salting shaders per partition.
4. **Robustness cost.** Measure frame-time cost of explicit bounds clamps versus `VK_EXT_robustness2` on the reference devices, per the spec's warning that robustness2 "may be expensive".
5. **Workgroup zero-init cost** with and without `VK_KHR_zero_initialize_workgroup_memory`, and on Metal and D3D12, where no equivalent exists.
6. **Other engines' adapter-info buckets** (Chrome, Firefox, Safari), timestamp resolution in Firefox and Safari, and whether they partition pipeline caches: black-box tests in each browser.
7. **Compatibility mode on Izcal's HAL.** Decide whether "WebGPU-compat" in HGBA-2 means only the feature level on core hardware (cheap), or a reason to add a D3D11 or GLES 3.1 backend (large).
8. **WebGL usage in 2025–26** (Chrome Platform Status counters, HTTP Archive) and **WebGPU usage**: retrieve when search is available.
9. **Separate GPU queue or device per site for WebGPU versus the compositor**: measure hang-isolation and copy costs.
10. **GLSL ES mismatches per back end** (row 7.4): confirm `gl_FragCoord` origin handling and point-size and transform-feedback emulation from Metal and D3D12 documentation.
11. **Mechanized semantics of WGSL**: search the literature when budget allows (row 3.15).
12. **D3D12 root-descriptor bounds behaviour** (row 5.3): confirm from Microsoft's D3D12 specifications.
