### Must-fix list

- **FC-M1. Engineer-years do not match the hiring ramp** (summary; 9.3). The spec says "25–30 engineers at GR-M0 … about 60 by month 12; full strength by month 24–30", then counts "about 28 in year one, 75 in year two, then 96–128 a year". A linear ramp from 25–30 to 60 averages **about 43–45** engineers in year one, not 28 (28 is the starting headcount). Year two runs from 60 to full strength at month 24–30, about 78–83, and when full strength arrives only at month 30, year three is not a full year at 128 either. Recomputed: low (96 by month 24) 42.5 + 78 + 3 × 96 ≈ **409**; high (128 by month 30) 45 + 83 + 122 + 4 × 128 ≈ **762**. So **about 410–760 engineer-years†**, not 390–745. Either use these totals in the summary and 9.3, or change the ramp so the year sums agree with it. The arithmetic as written (28 + 75 + 3 × 96 = 391; 28 + 75 + 5 × 128 = 743) is correct; its inputs are not.
- **FC-M2. The media spec's staffing and version are stale** (header; 9.3). 9.3 says "before the media spec's 55–72†". The media spec is now revision 0.2 (19 October 2026), and its full strength is **56–73†** (`Izcal images and media.md` 9.3, "Full strength … 56–73†"). The header also cites "images and media spec draft 0.1". Update both. The other cross-references checked (MD-D8, MD-D9, MD-D20, MD-D28, MD-31, MD-32, MD-S6, G56) still mean what this spec says.
- **FC-M3. GR-D8's DXBC fallback rests on a claim its note contradicts** (6.12, GR-D8). The spec says Izcal would emit DXBC "from Microsoft's published format and checksum". GA 3.14, the only row cited, says DXBC's token format is "published only as a WDK header" and that the checksum is an "MD5-variant" from recollection (confidence Low). No Microsoft prose describes the DXBC checksum. Correct statement: "DXBC's token format is given only in a Windows Driver Kit header, and no published description of its container checksum was found (GA 3.14, Low)." GR-S1 should also test whether the in-box runtime accepts DXBC with a self-computed checksum, or the reversal path should be listed as unproven in 10's risk row.
- **FC-M4. "the three browser-reachable sandbox escapes of 2025 went through vendor user-mode drivers"** (summary; 6.1; it supports GR-D2). Google's [2025 zero-day review](https://cloud.google.com/blog/topics/threat-intelligence/2025-zero-day-review/) lists three "Device-Specific Sandbox Escapes" (CVE-2025-27038 Adreno, CVE-2025-6558 Mali, CVE-2025-14174 Metal; SR 1.1–1.3 are accurate) and also "Operating System-Based Sandbox Escapes" such as CVE-2025-2783 (Chrome through ipcz handles on Windows). Correct statement: "the three GPU-driver sandbox escapes that Google's threat-intelligence group recorded in the wild in 2025 went through vendor user-mode drivers".
- **FC-M5. The CVE comparison "535 … against 173 in all earlier years together"** (summary; 2.1). The 535 reproduces exactly; the comparison does not mean what it says. NVD began wording Chrome CVEs "in X in Google Chrome" only in 2017: older records ("Skia, as used in Google Chrome", 35; "the GPU process in Google Chrome", 5; "WebGL implementation in Google Chrome", 6) are not counted, and descriptions naming two components ("in ANGLE and GPU in Google Chrome", CVE-2025-6558) match no query. The re-run gives **172** before 2026, not 173 (and 707 in all, not 708). These are NVD publications, not "Chromium published". Correct statement: "NVD published 535 Chrome CVEs naming a graphics component between 1 January and 19 October 2026, against about 172 in 2017–2025 under the same wording ([NVD 2.0 API](https://services.nvd.nist.gov/rest/json/cves/2.0); method in SR 1.16)". Add both gaps to SR 1.16's method notes.
- **FC-M6. "5.73 bits from one canvas test"** (2.2; 6.4, where it argues GR-D3). [Mowery and Shacham 2012](https://hovav.net/ucsd/dist/canvas.pdf) give 5.73 bits for all six canvas and WebGL tests together (294 experiments, 116 unique); the single Arial text test produced 50 groups in 300 samples and **3.05 bits**. SR 6.1 is accurate; the spec merged two numbers. Correct statement: "5.73 bits from six canvas and WebGL tests, 3.05 bits from one text test".
- **FC-M7. Firefox bug 1987906's fix is described wrongly** (2.1 "Fixed in Firefox 145 by capping fallback to start-up"; the lesson behind G66 and GR-15). [Bug 1987906](https://bugzilla.mozilla.org/show_bug.cgi?id=1987906) is right about the problem (fallback after "crashing the GPU process 6 times" moved WebRender and WebGL to the parent). Capping the restart count to start-up was only an option (comment 3). What shipped in 145: after start-up the parent process crashes instead of falling back, enabled on Nightly only ("we've elected to not ship parent process crashing on anything but nightly", comment 11); release builds are protected because accelerated Canvas2D and WebGPU are disabled before the GPU process is dropped (bugs 1992430 and 1992856, comment 12). SR 2.7 carries the same error. Correct both; the lesson (never fall back to a less sandboxed process) stands, and Mozilla's release behaviour, disabling GPU web APIs first, matches GR-D19's order.
- **FC-M8. TDR and Metal limits** (summary; 6.1; 6.18; GR-D19; GR-16). Microsoft's [TDR registry keys](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys) give `TdrLimitCount` (default 5) as the number of TDRs allowed within `TdrLimitTime` (60 s) "without crashing", so the bug-check comes after **more than five**, not after five. 6.18 cites **SR 4.11** for these limits; SR 4.11 is about missing crash-rate data; the rows are SR 3.3–3.4. Apple's `accessRevoked` text ("responsible for too many timeouts or hangs") does not say the revocation is per process (SR 3.3 marks this Medium), so "can revoke Metal access for all rendering" is an inference, which Q-GR-11 already asks about; say so in 6.1.
- **FC-M9. The Android CPU-path share is about 21%, not 12.7%** (6.17; GR-D10's and GR-D21's costs). 12.67% of Android devices lack Vulkan 1.1 ([Android dashboard](https://developer.android.com/about/dashboards): "None 8.85%, 1.0.3 3.82%", 28 days to 24 November 2025, API 23+ only). But the floor in 6.2 and GR-D21 is Vulkan 1.1 **plus** Android Baseline Profile 2022, which covers 86.5% of Vulkan-capable devices: 0.865 × 91.15% ≈ 78.8% of all devices meet it, so **about 21%** would render on the CPU and have no WebGL or WebGPU. State this share, the snapshot date and the API 23+ scope, or lower the Android floor. (The dashboard labels the profile "AVP 2022"; that it is the Android Baseline Profile 2022 was not confirmed.)
- **FC-M10. GR-D10's precedent and Izcal's own use of WARP** (6.17; GR-D10; 6.25; Section 7). The [blink-dev intent](https://groups.google.com/a/chromium.org/g/blink-dev/c/yhFguWS_3pM/m/oLrB5up_BwAJ) is quoted correctly and the share is "2.7% of WebGL contexts" (Byers put the upper bound at about 0.5% of page loads); deprecation warnings began in Chrome 130 and removal targeted desktop Chrome 137. Secondary reports, and a Chrome engineer in a [related blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/TvNk-PJO2Sk/m/hTEi9pYvAQAJ) ("still suffers from continuing to run JITed code"), say Chrome on Windows falls back to Microsoft's **WARP**, itself a JIT software rasterizer, so "Chrome removed its software WebGL fallback" holds only off Windows. Separately, this spec lists WARP as an OS interface it may use (6.25 "D3D12 is in-box with WARP"; Section 7's runtime-interface row) without saying whether a GPU process may load it. GR-D10's own reason ("no JIT in a privileged process") then needs a rule: state that neither GPU process kind ever creates a WARP device (and add it to G67 or G66), or justify WARP as an exception. Check Chrome's Windows behaviour on chromestatus before citing it.
- **FC-M11. GR-D16's basis: "Compositing 1 and SVG 2's `color-interpolation` (initial sRGB) put simple alpha compositing in encoded space"** (6.5). Compositing 1 defines no colour space and has no `color-interpolation` property; RP 3.3 itself says it "never names a colour space". SVG 2's `color-interpolation` has initial value sRGB ([SVG 2 §13.9](https://www.w3.org/TR/SVG2/painting.html#ColorInterpolationProperty)), and CSS Color 4 keeps legacy colours in encoded sRGB; that browsers composite in encoded space is an observation, not a requirement. Correct statement: "SVG 2's `color-interpolation` (initial sRGB) and CSS Color 4's legacy-colour rule point to encoded sRGB; Compositing 1 does not name a space, so encoded blending is web-compatible practice that Izcal adopts (Q-GR-3 measures it black-box)".
- **FC-M12. Firefox 70's power ratios** (2.1 "3× or more"; 5 and 6.10 "3–4×"). The cited numbers, 12.8 → 2.9 W and 7.4 → 1.6 W ([Mozilla gfx, 2019-10-22](https://mozillagfx.wordpress.com/2019/10/22/dramatically-reduced-power-usage-in-firefox-70-on-macos-with-core-animation/); OS 1.9), are **4.4× and 4.6×**. Write "about 4.5× (two workloads, one 2013 MacBook Pro)" in all three places.
