# Izcal OS integration, draft 0.1: independent design critique (phase 8)

Date: 24 October 2026. Status: phase 8 critique of draft 0.1. I did not write the specification.

**Method.** I read the `first-principles-spec` skill and the devices critique for format, then `reports/Izcal OS integration.md` (draft 0.1, 794 lines) in full, and judged the design on its own and against the corpus at 3b183d1. I did not fact-check dates, links or note-row citations, because a separate fact-checker does that. I did not read or cite any third-party source code. I did not edit the specification or any other document, and this file is the only file I created.

## What the design gets right

- **The central idea is right.** Treating the OS as one more untrusted, recorded peer, with typed inputs in and typed commands out, is the correct reading of DET-1. It is also the better of the two patterns the audit offered in §8.2. The rejected alternative fails for exactly the reason given: on macOS and Linux, Apple Events, window messages and power notifications arrive in the window-owning process, and an adapter process cannot see them.
- **Only one cross-build message.** The design keeps VER-1 intact for everything else and makes the launch hand-off the single versioned exception. The TLV format, the sender-set critical bit, refusal on an unknown major version, golden vectors and a skew matrix answer §8.3 in the right shape. The rule that the hand-off "never carries an endpoint" is exactly right.
- **Argument injection gets a structural fix, not a per-bug one.** In `--os-open` mode no switch is honoured, every registration ends in an end-of-options marker, Windows must deliver exactly one operand, and the parser refuses anything else. The 500-case corpus (OI-4) is the right enforcement. The history table earns this decision.
- **The default-browser stance is honest and stable.** Izcal registers only the types it really handles, asks only through the OS's own surface, reads status as an input, shows the truth per type, never writes UserChoice, never runs an agent and never re-asks. This matches R19 and UP3 and needs no change when the OS changes its rules again.
- **The outbound design closes the scheme-flooding signal at the browser's edge.** Outcomes the page cannot tell apart, a prompt even when no handler exists, one external launch per 5 s† and no `file:` or UNC from web content. The OS-side residual is stated rather than hidden.
- **Placement by what each call has to trust is the right principle.** Third-party shell extensions and antivirus code leave the credential-bearing broker for a medium-IL helper, which is the correct analogue of SH-D3 for dialogs. Speech outside the ML service satisfies FI-D5 and AG-0 without a special case.
- **Privacy defaults are good.** Recent items are off, no page title reaches a jump list or Dock menu, private windows send anonymised media metadata, default status goes nowhere (D-S4), background mode is opt-in and visible, preloading is refused, and scripting that runs page JavaScript is refused.
- **Portals have a deadline.** Portals are the primary API with feature detection, every first reply has a 1 s† timeout with a stated fallback, and diagnostics are shown in `about:diagnostics`. This turns a documented 25 s hang class into a target (OI-19).
- **One registration record serves the browser and FI-9.** Exact artifact lists, removal of only what Izcal wrote, and no silent re-creation of artifacts the person removed is the right model for clean uninstall (OI-11) and for FI-D8's full PWA platform.
- **The spec is honest about the open points.** It does not guess the answers to Q-OI-1 (cross-process HWNDs), Q-OI-4 (speech under the sandbox) and the conflicting Microsoft share documentation. It schedules them as measurements and names reversal triggers.

## Findings

| ID | Area | Finding | Severity | Why it matters | Recommendation |
|---|---|---|---|---|---|
| **C1** | Security / I-2 | The sandboxed **OS-integration service is given a raw session-bus connection** (6.9; amendment "Utility sandbox with only its D-Bus, SSIP and audio-service endpoints"). On systemd desktops the session bus is the user bus, so the service can reach `org.freedesktop.systemd1` (`StartTransientUnit` runs any command as the user), `org.freedesktop.secrets` (the login collection is normally unlocked, so the service can read every stored secret, Izcal's own profile key included), the portals (OpenURI launches handlers) and the broker's own `org.freedesktop.Application.Open`. The "no network, no files, no process creation" probes in OI-14 therefore test nothing that matters. This is the process the spec chose *because* it parses untrusted D-Bus data from other programs. | **Critical** | I-2 (zero ambient authority) is broken by a single file descriptor. G235's "holds no credential" is false in effect, because one method call reaches the user's credentials. The same pattern recurs in AX-D12's bridge (which also needs the session bus to find the a11y bus) and in MD's capture service (portals, RTKit). | Never give a sandboxed process an unfiltered bus socket. Specify an Izcal **D-Bus filter**: a broker-held connection or a tiny trusted proxy that parses headers only, with tier P code and Kani proofs. It allows only the (destination, interface, member) tuples each role declares, refuses `BecomeMonitor`, eavesdropping and name ownership outside the role, and drops everything else. Add OI-14 cases that call `systemd1`, `secrets` and `Application.Open` from the service and expect denial. Apply the same rule to the AX bridge and the capture service, and record that in the AX and MD amendment rows. |
| **C2** | Architecture / §8.2 adoption | As written, `OsPort` cannot be built under the corpus's layer rules. The trait goes into `hg-substrate` (L1), but its types are generated into `hg-os-types` at **L2**, so L1 would depend on L2. `hg-os-win`, `hg-os-mac` and `hg-os-linux` are given "tier O", but tier O is "`hg-substrate-os` only", the one crate allowed ambient OS effects under G3. `hg-os-service` (tier R) and `hg-launch-main` call OS APIs, and G231 forbids the launcher from linking the substrate, so under G3 it cannot name `std::process` at all. `hg-launch-wire`, `hg-dbus` and `hg-xdg` are placed in L1, the substrate layer, rather than among the leaf parsers. The amendments table has no coding-standard row. | **High** | Appendix C is offered "for adoption" at M1 exit, but the graph lint and the tier table would reject it. That is precisely the precision §8.2 asks for. | Follow the code as built. The `Ipc` trait carries bytes and handles, and the typed layer sits above it. So either (a) `OsPort` carries encoded `os.hgidl` frames and a typed wrapper lives in an upper layer, or (b) the few OS types are hand-written in `hg-substrate`. Make the per-OS halves inventoried modules of `hg-substrate-os`, as batch 5 did for the device backends. Give the launcher a recorded G3 exception or a minimal substrate-os entry. Move the three pure crates to L2s. Add the coding-standard amendment (tier table, G3). |
| **C3** | Determinism / scope of the boundary | The `OsInput` set does not cover the OS inputs the corpus already reads in the broker, so "the OS edge has one boundary" and G234 ("no production code reads an OS setting … except through `OsPort`") cannot both hold. Missing: **enterprise policy**, the first item in audit §8.2 (registry, managed preferences, `/etc`); the amendment row says FI-3's policy "arrives through `OsPort`", but no `Policy` kind exists and Appendix C omits it. Also missing: **locale, preferred languages and regional formats**, **time zone and its changes**, and `hardwareConcurrency` and `deviceMemory` (DM 6.16's environment record). Several AX 6.11 fields are missing too (inverted colours, caret width, focus-ring width, Apple's image and flash settings), although 9.5 says `hg-ax-prefs` takes its raw values from `Settings` "unchanged". | **High** | §8.2 is an M1-exit input. A boundary that leaves policy, locale and time zone outside it gives DET-1 a hole exactly where enterprise bug reports start, and G234 as written would forbid reads that the corpus already makes. | Add an inventory table: every OS-sourced value, the process that reads it, the owning spec and how it is recorded. Add `Policy`, `Locale`, `TimeZone` and `Hardware` kinds, or state who owns each and through which boundary it is recorded. Make `Settings` a superset of AX 6.11's sources. Put `Policy` into Appendix C's M1 types. |
| **C4** | Architecture / Windows window owner | Under SH-D3, on Windows the **UI host**, not the broker, owns content HWNDs and their message loop. `WM_DPICHANGED`, `WM_SETTINGCHANGE`, `WM_DISPLAYCHANGE`, per-window display moves, `WM_POINTER` (6.12) and the session-end messages therefore arrive in a least-privilege process. The design never says how they reach `OsPort` (broker only), or that they are UI-host-reported and untrusted (IPC-R17). The OI-D1 rationale ("arrive in the broker's own process") is false on Windows. | **High** | Without this, the Windows half of `Displays`, `Settings` and `Power` has no defined path or trust level, and a compromised UI host can forge display or settings inputs that the broker records as OS truth. | State the Windows path explicitly: UI-host typed messages, validated by the broker and recorded as `OsInput` tagged with the reporting process. Prefer windowless sources in the broker where they exist (`RegisterSuspendResumeNotification`, UISettings events, display enumeration) and cross-check the UI host's reports against them. Add an IPC-R17 suite for these messages. |
| **C5** | Determinism / production recording | Stage 1 3.4 records **per tab, after "Reload to record", in a fresh renderer**, and SEC's REC-R6 records per process and joins by IDs. A recording "that began with an OS launch" (OI-7, and the "I clicked a link in Outlook" case) cannot be produced under that model. The broker's `OsPort` stream is browser-wide: launches into other tabs, profiles and containers, display layout, default status and chosen file paths. FI-11's amendment ("recordings include the `OsPort` stream") would put all of it into one tab's recording. | **High** | The DET-1 claim is either unachievable under the recording model as specified, or a cross-container privacy leak in every shared recording. | Split the claim. (a) DST and simulation cover the whole `OsPort` stream, as the spec designs. (b) A production tab recording carries only the derived values that tab consumed (its environment record, its own launch, its own dialog answers), joined by ID under REC-R6. A broker-wide OS recording, if wanted, is a separate opt-in mode with its own privacy statement. Restate OI-7 accordingly and add a SEC/REC amendment row. |
| **C6** | Isolation / shared process | The OS-integration service is site-less and shared, yet it receives **page payloads from every site**: speech utterance text (Web Speech and read aloud), Media Session metadata and notification text (G235). It also runs third-party SAPI 5 voice DLLs and speech-dispatcher's protocol, and on Linux it holds the bus (C1). I-1 part 3 allows exactly four shared services (OD-8), each receiving "never page payloads". The spec calls the new service "site-less like the audio service", but the audio service receives PCM, not page text. | **High** | One exploit in a voice engine through crafted utterance text yields every site's utterances and media titles plus the bus. Placing this as a fifth shared exception without an owner decision contradicts I-1 and P1. | Split the roles into separate instances: a per-(site, container) **speech** instance, or one per utterance source with an idle exit, and a **desktop-bus** instance that holds the C1-filtered connection. Alternatively, record the service as a fifth OD-8 shared exception with its own FP-7 line, threat model and owner decision. Make G235 name the role, not the process. |
| **C7** | Text safety / TX-16 | TX-16, as ED-D6 restated it, says page-controlled text reaches an OS text interface only as the IME snapshot, "never any other OS text surface". The spec sends page strings from the broker to SMTC and Now Playing (title, artist, album), `UNUserNotificationCenter`, the share sheet (`navigator.share` title and text), and file-dialog type descriptions and suggested names. G233's formatter is a good control, but no TX-16 amendment is proposed, and the broker threat model's "no page-controlled string reaches an OS text API in this process" is contradicted. The shell's window title already does this, so the tension predates this spec, but this spec widens it to the lock screen and other processes. | **High** | TX-16 exists because hostile strings crash OS shapers; the Telugu-class bug spread through notifications. An accepted rule silently broken by a new spec is a reconciliation failure. | Add a TX-16 amendment: a closed list of OS display surfaces, each receiving only G233-formatted, length-bounded, script-checked strings, fuzzed with TX-12a (OI-15), and owned by TX. Note that the shell's window title falls under the same rule. Update the broker threat-model text in SEC 6.5. |
| **C8** | Security / broker parsing | 6.0 justifies the service with "IPC-R15 keeps such parsing out of the broker, as AX-D12 already does", and then puts in the broker (a) a session-bus connection that receives and parses `org.freedesktop.Application` calls from any same-user bus client, including a compromised service, (b) the Secret Service client's replies, and (c) the IZLH listener. On Linux there are also **two rendezvous paths** into the broker, D-Bus and a socket. The `DBusActivatable=true` cold start is not specified: there is no `.service` file, nothing says what the bus starts, and nothing says the launcher must not hand off in that mode. | **High** | This is the brief's central question, and the spec does not acknowledge the contradiction. A tier P codec makes the parsing defensible, but that is a decision to record, not to leave implicit. | Record a narrow exception in SEC: the broker parses D-Bus headers plus the closed `Application` and Secret Service bodies, and the IZLH frame, all tier P, with Kani proofs, fuzz targets and an adversarial suite. Alternatively, move `org.freedesktop.Application` behind the filter of C1 and forward typed `Launch` records. Consider dropping `DBusActivatable` in Stage 1, which leaves one Linux rendezvous; if it is kept, specify the activation file and the cold path. |
| **C9** | Security / inbound URLs and paths | Only `javascript:` and `data:` are refused on the inbound path, and Q-OI-3 defers the rest to a black-box reading of other browsers. Nothing is said about Izcal's internal pages (settings, `about:` pages with actions, DevTools, extension and `app://` schemes), `view-source:`, `blob:`, or inbound **UNC paths and `file://host/` URLs**. Opening `\\attacker\share\a.html` from a mail client makes Izcal authenticate over SMB, which is the same leak 6.5 blocks in the other direction. | **High** | The hand-off and `Application.Open` are the only channels any local program, sandboxed apps included, can use to make Izcal navigate. "External launch to a privileged internal page" and "remote file path leaks credentials" are well-known bug classes. | Decide from first principles rather than by imitation. Make inbound an **allowlist**: `http`, `https`, local-volume `file:` (with the `file:` origin rules), and `about:blank`. Refuse internal and privileged schemes or open them without any URL-encoded action. Refuse or prompt for UNC, SMB and other remote paths. Apply the same rule to dropped URLs (ED's drag-in path) and to D-Bus `Open`. Add these cases to OI-4. |
| **C10** | Targets / hand-off | 6.2 processes ≤ 20† hand-offs per second and **refuses the rest** as `rate-limited`, with a 2 s† launcher timeout. OI-5 requires 1,000 concurrent launches with "every URL delivered exactly once", and so does Appendix C's M1 test. The two cannot both hold. Refusal also means a multi-select "Open" in Explorer or a script that opens 50 links produces dozens of failures and error messages. | **High** | One target is unpassable as written, and the user-facing behaviour under a burst is wrong. | Replace refusal with **bounded queueing and backpressure**: `busy-retry` with a retry-after, a per-sender and global queue bound, and coalescing of `activate`. Refuse only beyond a large bound (for example ≥ 1,000† queued). Say how the launcher reports a refusal (one message, not one per launch). Make OI-5 and Appendix C use that rule. |
| **C11** | §8.3 / macOS and update layout | 6.2 says the launcher "is the app bundle's main executable for command-line launches", while the broker "is the bundle's `NSApplication`". Only one of them can be `CFBundleExecutable`, and Launch Services, Dock identity, notification authorisation and keychain groups attach to that process. A broker run from a versioned directory outside the bundle loses that identity. If the broker runs from inside the bundle, an in-place bundle update brings back §8.3's `BuildMismatch` for children. FI-D10's versioned directories are a decision for Linux packages only, so "this also answers the audit's update problem" is asserted for macOS and Windows without a layout. | **High** | §8.3 is an M1-exit input that M5 depends on. On the platform with the strictest bundle model, the proposed answer is internally contradictory. | Per OS, state which binary is the OS-registered app, where the versioned engine binaries live (for example, versioned helper bundles inside the app bundle that the running broker pins), how a cold command-line launch starts the app (through Launch Services, not `exec`, on macOS), and what the updater may replace while the browser runs. Hand that layout to FI-2 as a requirement, not an assumption. |
| **C12** | Footprint / Linux | The service is "on demand, 0 when not running, exits ≤ 10 s†". On Linux, though, it holds the subscriptions that must be live whenever the browser runs: the Settings portal's `SettingChanged` (live theme and contrast changes), logind's `PrepareForSleep` and delay lock, the Inhibit portal's session state, and MPRIS while media plays. It is therefore always on. FP-1's line budgets on Linux already sum to **63 of 64 MiB** (FP 8.2), so another 2 MiB breaks the line arithmetic even though the 3.5 MiB of idle headroom would absorb it. Separately, the colour scheme is needed before the shell's first paint, while 6.9 says "no portal call is ever on the startup path", so the first frame paints with the wrong theme. | **High** | "FP-1 unchanged" and OI-12's "0 when not running" are false on Linux, and SH-1's first paint gets a theme flash. | Either budget an always-on Linux line in FP 8.2 and re-derive FP-1, or keep the long-lived subscriptions on the broker's filtered connection (C1, C8) and start the service only for portal requests, MPRIS and speech. Read the theme at startup within a bounded wait (≤ 50 ms†, or cache the last known value and reconcile later). |
| **C13** | Windows / SH-D3 honesty | The fallback for window-scoped calls (taskbar progress, per-window AUMIDs, SMTC `GetForWindow`, `ShowShareUIForWindow`) is that "the UI host gains a typed endpoint". The UI host is least-privilege, though, and SEC's 6.5 model requires denial tests proving it has no OS API "beyond TSF's content-window interface". Whether a low-integrity or AppContainer process can call these COM and WinRT APIs is itself unknown. If both the broker (cross-process) and the UI host (sandbox) fail, there is no plan, and Q-OI-1 is scheduled at M5. | **High** | A negative answer could reopen SH-D3, an accepted starred decision, three milestones after the shell's window platform is built (SH-M2 at M3). | Move Q-OI-1 into **SH-M0** (the M1 gate before M2, which already measures UI-host behaviour). Measure the broker path, the UI-host path under its real token, and a third option: a broker-owned top-level frame window with the UI host's content as a child. Pre-record which option changes SH-D3 and what the security amendment would be. |
| **C14** | `hg-dbus` / scope and schedule | `hg-dbus` is described as a client: "typed proxies". Its consumers mostly need the **server side**: AT-SPI exports thousands of objects with properties and signals, and MPRIS, StatusNotifierItem and `org.freedesktop.Application` are exported interfaces. That means object export, `Properties`, `PropertiesChanged`, `Introspectable` output, name ownership, fd passing and, per C1, filtering. The 1–1.5† estimate covers none of that explicitly. The schedule also conflicts: AX-M0 already includes "the AT-SPI bridge prototype" before M5, ED's X11 IME and MD's portals are earlier consumers, and `hg-dbus` lands at OI-M1 (M5). "MD's … PipeWire calls" are not D-Bus. | **Medium** | The decision itself holds: CS-AS-4 and Q-CS-2's precedent apply, and build-our-own is the standing rule. But its cost and timing are understated, and AX is the consumer most hurt by a slip. | Specify server-side features and the filter. Re-estimate (I would expect 2–3† at the peak of the codec, server and filter work). Land a header-and-marshalling core at AX-M0's date. Make the reversal trigger fire at AX-M0, not OI-M1. Correct the PipeWire wording. |
| **C15** | M-1 / interface sources | `hg-dbus`'s proxies are "generated from the published interface definitions (portal docs, freedesktop specs; never from another project's source)". The machine-readable XML for portals and AT-SPI lives in the projects' source repositories; the published documentation is rendered prose. ED already ruled that "their source and repository XML may not be used" for IBus and derived interfaces by black-box introspection. | **Medium** | Generating code from repository XML would be an M-1 part 3 violation. The current wording invites it. | State that Izcal hand-writes its own interface descriptions from the prose documentation, or from black-box `Introspect` output of running services as ED does, and records the evidence chain for each interface. Never vendor the repository XML. |
| **C16** | Substrate / sans-IO I/O | The sans-IO D-Bus codec says "the owning process's substrate sequence drives the socket", but no substrate trait, built or planned (Clock, Entropy, Executor, Memory, Ipc, CodeMemory, NetTransport, Storage), offers a pre-opened local stream with readiness events and `SCM_RIGHTS`. The same gap applies to the SSIP socket and the IZLH listener. | **Medium** | Every consumer (broker, service, AX bridge, ED front ends, capture service) will otherwise invent its own I/O inside tier-O code, outside the simulator. | Add a small substrate primitive, a local-stream handle with readiness delivered as tasks and handle passing, to Appendix C or to the M5 substrate additions, with a simulated implementation. |
| **C17** | Launcher / lifecycle | Several launcher behaviours are left open. (a) The cold-start race (two launchers, no broker yet) has no stated algorithm: who takes the lock, when the endpoint exists, and how the loser waits. (b) SH 6.14 makes the launcher start the **recovery window** "when the broker cannot start", which needs the launcher to wait for a broker ready signal; 6.2 has it exit immediately, and OI-12 allows ≤ 50 ms† alive. (c) A v2 launcher must "still be able to send v1", but there is no downgrade-on-refusal rule. (d) "N−3 … N+3 against a running N" cannot be run for future versions. | **Medium** | Single-instance races are the bug class OI-5 exists for, and the recovery path is a shell requirement. | Specify the algorithm. One option: the launcher creates or takes the per-channel endpoint and lock and passes the listening handle to the broker it starts, then waits for a "started" reply up to a deadline before launching recovery. Add a v2→v1 retry rule. Restate the matrix as "this release's launcher against the last three brokers, and this release's broker against the last three launchers". |
| **C18** | Security / rendezvous authentication | Only the server checks the client. The launcher never verifies that the pipe or socket server is Izcal's broker, yet it sends URLs (which can be magic-login or password-reset links) and, on Windows, calls `AllowSetForegroundWindow` for that PID **before sending**. Pipe-name squatting by a same-user, lower-privilege process would receive both. On Windows the pipe namespace is global while the tie-breaker mutex is per session (`Local\`), so two sessions of one user collide inconsistently. Sandboxed Izcal processes, AppContainer and low-IL callers rely on implicit OS defaults. | **Medium** | ATK-7 is same-user, but sandboxed same-user apps are a lower trust level that the design should keep out explicitly. | Make the launcher verify the server (`GetNamedPipeServerProcessId` plus image path, token user and integrity; `getpeereid` and `SO_PEERCRED` plus executable checks). Grant foreground rights only after an `accepted` reply. Include the session ID in the Windows name. Add OI-14 probes: renderer, service, AppContainer and low-IL callers cannot connect. |
| **C19** | Windows / taskbar identity | Registrations and shortcuts target the stable launcher, but the running windows belong to a broker in a versioned directory. Without `PKEY_AppUserModel_RelaunchCommand`, `RelaunchDisplayNameResource` and a relaunch icon on each window, a person who right-clicks a running window and picks "Pin to taskbar" pins the versioned `broker.exe`, and that pin breaks at the next update. "Set on the process and every window" is not possible for several per-profile AUMIDs in one broker, because a process has one explicit AUMID. | **Medium** | The spec rightly avoids programmatic pinning, so the person's own pin is the main path, and that path breaks. | Set the relaunch properties on every window, pointing at the launcher with `--profile`. Use per-window AUMIDs, and give the process the default profile's ID. Add the case to OI-11 and the update test. |
| **C20** | Registration journal | The journal is "one store per profile root, in the storage service", but FI-D17 gives **each profile its own storage-service instance**, so it is unclear which instance holds a per-profile-root journal. The uninstaller (FI-2) must run every removal without the browser, which would mean linking Izcal's store engine. The installer's own records are "the installer's", so the system has two sources of truth for OI-11. | **Medium** | Clean removal (OI-11, a ship blocker) depends on a store the uninstaller cannot read. | Make the journal a small, versioned, plain file per install and per profile root, with a tier-P reader that the uninstaller and broker share. Have the installer write its records into the same journal. Add a storage-spec row only if it stays in the store. |
| **C21** | Downloads / SH-R6 and PO-8.9 | On Windows, `IAttachmentExecute::Save` in the helper "applies the zone mark", but SH-R6 says "the broker sets the mark itself, because the save flow is itself a documented way to strip it". No SH-R6 amendment is proposed. The antivirus row PO-8.9 is closed by OI-14, a sandbox probe, so no target checks that a scan actually runs and blocks. | **Medium** | Two specs disagree about who owns the origin mark, and a ship-relevant row has no functional target. | Keep the broker's mark as the authority and use IAE for the scan, or amend SH-R6 to accept IAE's mark with a broker verification afterwards. Add a target: the EICAR test file is blocked with the "blocked by your antivirus or policy" verdict 100% of the time, and the zone mark is present on every saved file (on Windows and macOS). |
| **C22** | `OsPort` / synchronous OS callbacks | The model is "commands never block; inputs arrive as tasks". ## The five findings that most change the design

1. **C1, the bus is ambient authority.** A sandbox with a raw session-bus socket is not a sandbox. The fix is an Izcal D-Bus filter, which changes `hg-dbus`'s scope (C14), the service's sandbox row, and the AX and MD bridges.
2. **C2 and C3, `OsPort` must be adoptable and complete.** As written, the trait breaks the layer rules and G3, and its input set omits policy, locale, time zone and AX fields. These two findings decide what can be merged at M1's exit.
3. **C6 and C7, page text in shared and OS surfaces.** The service receives every site's utterances and media titles. The broker sends page strings to OS text surfaces that TX-16 forbids. Both need either a structural change (split the roles) or a recorded owner exception and amendment.
4. **C11 and C13, the two platform contradictions.** macOS's bundle identity contradicts the launcher and versioned-broker split. Windows' window-scoped APIs may work neither from the broker nor from the sandboxed UI host. Both should be resolved at SH-M0 and in FI-2's layout, before M5 builds on them.
5. **C8, C9 and C10, the inbound channel.** The broker's D-Bus and hand-off parsing needs a recorded exception, the inbound URL rule must be an allowlist, and the rate limit must queue rather than refuse.
