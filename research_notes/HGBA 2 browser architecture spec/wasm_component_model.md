# WebAssembly, the Component Model and WASI in Browsers (state as of October 13, 2026)

Scope: what Wasm and the Component Model can and cannot do inside a browser, to ground the HGBA-2.0 spec. Each claim has a source. Older data is labeled with its date.

## Q1. WASI 0.3 (P3): ratification, features, runtime support, CM 1.0 / WASI 1.0 timeline

### Takeaway
WASI 0.3.0 was released June 11, 2026. It moves async into the Component Model's Canonical ABI (async functions, `stream<T>`, `future<T>`). Wasmtime 46 is the first runtime to implement the final spec, and 0.3.1 followed on Aug 11, 2026. Component Model 1.0 has **no date**. It formally requires native implementations in at least two browser engines, and WASI 1.0 depends on CM 1.0.

### Cited Findings
- "WASI 0.3.0 was released on June 11, 2026." — [WASI.dev: WASI 0.3](https://wasi.dev/releases/wasi-p3)
- Features: async functions in WIT ("Functions can now be declared as asynchronous in WIT"), `stream<T>` ("a typed, asynchronous data channel"), and `future<T>` ("a single-value async completion"). — [WASI.dev](https://wasi.dev/releases/wasi-p3)
- Async I/O moved into the Component Model. Work that `wasi:io` did in WASI 0.2 is now part of the Canonical ABI. WASI 0.3 passed the WASI Subgroup vote, and the 0.3.0 spec is stable. — [Bytecode Alliance: WASI 0.3 Launched](https://bytecodealliance.org/articles/WASI-0.3)
- Wasmtime 46 is "the first release to implement the final WASI 0.3.0 specification" and enables WASI 0.3 plus `component-model-async` by default. Wasmtime 43–45 implement the 0.3.0-rc-2026-03-15 snapshot and Wasmtime 41–42 an earlier snapshot; both need the flags `-Sp3 -W component-model-async=y`. Wasmtime 44 added initial `wasi:tls@0.3.0-draft`. — [WASI.dev](https://wasi.dev/releases/wasi-p3)
- jco is listed as WASI 0.3 tooling and runtime for JavaScript environments. The page says nothing about native browser support. — [WASI.dev](https://wasi.dev/releases/wasi-p3)
- Patch cadence: "WASI 0.3 patch releases ship every two months on the release train". 0.3.1 was released Aug 11, 2026. — [WASI.dev](https://wasi.dev/releases/wasi-p3)
- Some third-party articles say WASI 0.3 arrived in Feb 2026. They are describing the preview snapshots in Wasmtime 37+, not the final spec. — e.g. [progosling digest (Feb 2026)](https://progosling.com/en/dev-digest/2026-02/wasi-0-3-wasmtime-37-native-async); conflicts with [WASI.dev](https://wasi.dev/releases/wasi-p3) (final = June 11, 2026)
- "The Road to Component Model 1.0" (Bytecode Alliance, June 8, 2026) gives no 1.0 date and says sequencing depends on use cases and resources. The 1.0 spec will be a narrower "good parts" subset of P3. "WASI 1.0 will follow from and depend on the Component Model reaching 1.0 first." Some WIT features may come in 1.x. — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- "The Component Model can't formally reach 1.0 without native implementation in at least two browser engines." — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- The post names five work areas for 1.0:
  1. ABI improvements: the lazy ABI, multivalue returns with error context, a GC ABI option, and zero-overhead sync calls.
  2. A browser path.
  3. Easier implementation: a simplified spec, C ABI headers generated by wit-bindgen, and a proposed `lower-components` tool that turns a component into a single core module.
  4. Ecosystem growth.
  5. WIT expressivity: optional imports, callbacks, subtyping, a map type, runtime instantiation, getters and setters.
  — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- Cooperative threads are slated for a follow-up WASI P3 minor release. Shared-everything threads come "later", with no timeline. — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- On the WebAssembly CG proposals tracker, the Component Model is listed at **Phase 1**. — [WebAssembly/website features.json](https://github.com/WebAssembly/website/blob/main/features.json) (last commit 2026-09-29)

### Inferences
- The spec should treat WASI 0.3 / CM async as stable for **out-of-browser hosts** (Wasmtime ≥46, jco) and should not assume WASI 1.0 or CM 1.0 before 2027.
- The CM is still Phase 1 in the W3C CG, and 1.0 is gated on two browser engines shipping it. A browser spec that requires "native CM" is betting on something that is not yet a standard.

### Gaps
- No official date for WASI 1.0 or CM 1.0. One third-party claim says "late 2026 / early 2027", but it is unsourced and should not be used.
- I did not verify the Wasmtime 46 release date or the current Wasmtime major version as of October 2026. features.json references Wasmtime 47 for GC and exceptions.

## Q2. Browser support: Component Model, jco, ESM integration, JSPI, and per-feature shipping status

### Takeaway
**No browser ships the Component Model natively.** Mozilla has run experiments and V8 has opened an evaluation issue; neither is a commitment. Components run in browsers only through **jco transpile**, which produces core Wasm plus JS glue. Most core-Wasm post-MVP features have now shipped in all three engines, with these exceptions:
- Safari: memory64, relaxed SIMD and multi-memory are flag-only or missing.
- Stack switching: flag-only in Chrome.
- ESM integration: shipped only in Deno, not in any browser.
- Shared-everything threads: Phase 1.

### Cited Findings
- No native CM in any browser. Mozilla (Ryan Hunt) shows "close to a 2x speedup" on a DOM-mutation-heavy Wasm VDOM loop from direct Wasm-to-Web-API calls that bypass JS glue, and presented the results at a CG meeting. The V8 team opened an issue "for evaluating Component Model implementation". The post says: "These aren't commitments, but they're meaningful signals." Apple/WebKit is not mentioned. — [Bytecode Alliance, June 8, 2026](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- `jco transpile` "already converts any component into equivalent core Wasm and JavaScript glue", so components run in browsers without native support. Since jco 1.16.8 the glue emits a `"use components"` marker (renamed from `"use jco"`), modeled on asm.js's `"use asm"`, as telemetry to build the case for native support. — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- Feature phases per the CG tracker:
  - **Phase 5 (standardized):** JSPI, GC, exception handling (exnref, "exceptionsFinal"), memory64, multi-memory, relaxed SIMD, tail calls, typed function references, JS String Builtins, branch hinting.
  - **Phase 4:** threads, wide arithmetic, compact import section.
  - **Phase 3:** stack switching, ESM integration, custom page sizes, custom descriptors.
  - **Phase 1:** shared-everything threads, Component Model, type imports, stringref.
  — [features.json](https://github.com/WebAssembly/website/blob/main/features.json); rendered at [webassembly.org/features](https://webassembly.org/features/)
- Shipping versions per browser (stable unless noted). Same source as above, last updated 2026-09-29:

- Non-browser runtimes:
  - Wasmtime: exceptions, GC and typed function references since 47; memory64 since 30; multi-memory, relaxed SIMD and threads since 15. JSPI and ESM integration are N/A.

### Inferences
- A cross-browser HGBA baseline (Chrome, Firefox and Safari stable) can assume: GC, exnref exceptions, tail calls, typed function references, SIMD128, threads (SharedArrayBuffer still needs cross-origin isolation), JSPI (Safari only from 27), and JS String Builtins.
- It **cannot** assume memory64, relaxed SIMD or multi-memory in Safari, or stack switching, ESM integration, shared-everything threads or a native Component Model anywhere.
- If HGBA defines its own engine, the "two browser engines" gate for CM 1.0 is an opening: a new engine shipping native CM would count toward standardization.

### Gaps
- I did not independently confirm the Safari 27 JSPI and Firefox 153 JSPI entries against WebKit or Mozilla release notes; they come only from features.json.
- I found no Chrome Platform Status or Firefox bug tracking a native CM implementation timeline.

## Q3. Canonical ABI: lift/lower, copying vs zero-copy, overhead

### Takeaway
Today's Canonical ABI is **copy-based, or "eager"**. Values crossing a component boundary are lifted out of one linear memory and lowered into the other: the host calls the receiver's `cabi_realloc` and copies the data. There is no shared memory between components. A "lazy ABI" that enables zero-copy forwarding is planned as an opt-in in 0.3.x and becomes the default at 1.0. Async plumbing currently adds measurable overhead even on sync paths.

### Cited Findings
- **Eager semantics today:** when a callee returns, e.g., a list of strings, "the host calls the calling component's `cabi_realloc` to allocate memory for each element" and copies everything into the caller's memory before returning. Known problems: heap fragmentation, poor handling of large allocation failures, one host-to-guest call per list value, and conflicts with custom allocators. — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- **Lazy ABI:** the callee returns opaque `i32` handles. The caller then invokes a statically known built-in with a destination address, which can be inlined like an instruction. This enables zero-copy forwarding, dropping unused values, and moving string transcoding into guest code. It ships as an opt-in in a 0.3.x minor release, becomes the default at 1.0, and comes with an adapter to convert eager components. One dependency is LLVM C-ABI multivalue support, which is "potentially the longest lead time". — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- **Overhead:** per Nick Fitzgerald's Plumbers Summit measurements, async task management across component boundaries adds "roughly 3.5x overhead even on purely synchronous call paths." The recursion check has already been removed, and the rest of the refactor is planned for after P3 ships. — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)
- The CanonicalABI.md explainer defines lift and lower as executable Python. It notes the Python appears to copy data out of linear memory during lift, but "a normal implementation should never need to make this extra intermediate copy". In other words, there is one copy, source memory to destination memory, not two. — [CanonicalABI.md (fork mirror)](https://github.com/phyBrackets/component-model/blob/main/design/mvp/CanonicalABI.md); canonical repo [WebAssembly/component-model](https://github.com/WebAssembly/component-model)
- In browsers today, every CM call goes through jco's JS glue, so it pays for both the JS boundary and the copy. Mozilla's ~2x VDOM gain from direct Web API calls measures how much that glue costs. — [Bytecode Alliance](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)

### Inferences
- HGBA should not describe component boundaries as zero-copy. The accurate wording is: "shared-nothing, one copy per crossing; zero-copy forwarding only with the future lazy ABI; bulk data should use `stream<T>` or resource handles rather than large `list<u8>` values."
- Resources (handles) are the only way to pass a reference rather than a copy across components today.

### Gaps
- I found no published cross-engine microbenchmark (ns per call, GB/s per copy) for Canonical ABI crossings. The only overhead figure found is the relative 3.5x.

## Q4. Compiling JavaScript to Wasm: ComponentizeJS/StarlingMonkey, Javy, Porffor

### Takeaway
ComponentizeJS (StarlingMonkey/SpiderMonkey) and Javy (QuickJS) **embed an interpreter** inside the Wasm module. They pre-initialize the heap but do not natively compile JS. ComponentizeJS can optionally AOT-specialize the interpreter via weval, a partial evaluator, for a roughly 2–5x gain over the interpreter. Porffor is a true AOT JS-to-Wasm/C compiler, but it is pre-alpha and incomplete. None of these approaches matches a native JIT (V8/SpiderMonkey/JSC) on hot code. That comparison is my inference, because no head-to-head benchmark was found.

### Cited Findings
- ComponentizeJS takes a JS source file plus a WIT world and produces a component by embedding SpiderMonkey via StarlingMonkey. It is marked experimental, and the embedding is about 8 MB. — [ComponentizeJS GitHub](https://github.com/bytecodealliance/componentizejs)
- It uses Wizer pre-initialization and optional AOT via weval (`npm run build:weval`). — [ComponentizeJS GitHub](https://github.com/bytecodealliance/componentizejs)
- weval AOT (Aug 2024) is built on SpiderMonkey's Portable Baseline Interpreter plus weval partial evaluation. It is available via `--aot` in StarlingMonkey, reports a 3–5x speedup, is "beta"/experimental, and passes the SpiderMonkey JIT and JS test suites and runtime-level WPT. — [Chris Fallin, "Compiling JS to Wasm, Part 3: AOT" (2024-08-27)](https://cfallin.org/blog/2024/08/27/aot-js/)
- A more conservative figure: about 2x overall and about 4x on some microbenchmarks. — [NEU PL seminar abstract (2024)](https://lists.ccs.neu.edu/pipermail/pl-seminar/2024/000986.html); also [PLDI 2025 weval slides](https://cfallin.org/pubs/pldi2025_weval_slides_public.pdf)
- Fastly js-compute-runtime measured about 30% on a Markdown renderer, up to about 3.5x on Octane crypto, and a 1.83x geomean, and described it as "not yet production-worthy". — [fastly/js-compute-runtime PR #541](https://github.com/fastly/js-compute-runtime/pull/541)
- Javy "principally relies on QuickJS' interpreter". A late-2025 proof of concept that compiles QuickJS bytecode to Wasm reported about 1.2x on function calls and about 1.5–3.5x on closure creation using Wasm GC, on a "very small sample". — [Igalia, "Five years of JavaScript on WebAssembly" (2026-05-25)](https://blogs.igalia.com/compilers/2026/05/25/five-years-of-javascript-on-webassembly/)
- Javy module size: 1–16 KB with dynamic linking, where a shared QuickJS plugin is instantiated once, versus at least 869 KB with static linking. — [Javy README (mirror)](https://gitee.com/mirrors_Shopify/javy); background [Shopify Engineering](https://shopify.engineering/javascript-in-webassembly-for-shopify-functions)
- Porffor describes itself as an "experimental AOT optimizing JS/TS → Wasm/C engine/compiler/runtime", "not yet intended for serious use". It claims to be fast versus interpreters and JIT-less engines, but says JIT engines "can catch up". Async/Promise support is limited, and `eval`/`new Function` are "infeasible". — [Porffor GitHub](https://github.com/CanadaHonk/porffor)
- The project's own claim of "10–30x smaller and faster" than other JS-to-Wasm projects is unverified. — [project PDF summary](https://read.jamesst.one/1755458650.pdf)

### Inferences
- In a browser, JS-to-Wasm only makes sense for isolation or portability, e.g. running untrusted JS in a Wasm sandbox. It is not a performance path: the page's own JIT is faster, and an embedded engine adds MBs per instance.
- Full ECMAScript semantics, including `eval`, need an embedded interpreter. Pure AOT (Porffor) cannot support the full web.

### Gaps
- No independent 2026 benchmark comparing StarlingMonkey+weval, Javy or Porffor against V8/SpiderMonkey JIT.

## Q5. Wasm on GPU/NPU; Wasm SIMD and RISC-V RVV

### Takeaway
I found **no credible production system that lowers general Wasm to GPU or NPU**. The only direct attempt is a preliminary research study that uses small language models to translate WAT to WGSL. In practice GPU and NPU work goes through WebGPU/WGSL (shaders) or WebNN (graphs), with Wasm as host/CPU code. Wasm SIMD is fixed-width 128-bit. On RISC-V, Cranelift's vector support is partial, and Chromium's RVV build flag defaults to off (2023 data).

### Cited Findings
- W2GPU (ICFP/SPLASH 2025 LMPL workshop) is labeled a "preliminary study". It fine-tunes small LMs on 14,547 WAT↔WGSL pairs; the models learn vectorization patterns but generalize poorly to longer sequences. — [W2GPU, LMPL 2025](https://conf.researchr.org/details/icfp-splash-2025/lmpl-2025-papers/22/W2GPU-Toward-WebAssembly-to-WebGPU-Program-Translation-via-Small-Language-Models); [github.com/w2gpu](https://github.com/w2gpu)
- Apache TVM (2020) compiles ML models into a Wasm host plus WebGPU kernels. GPU code is generated separately (WGSL/SPIR-V lineage), not lowered from Wasm. — [TVM blog, 2020-05-14](https://tvm.apache.org/2020/05/14/compiling-machine-learning-to-webassembly-and-webgpu)
- WebNN is in a Chrome origin trial for M145–147 (desktop, Android, WebView). It targets NPUs and OS ML services. The Intent says Edge plans to ship alongside Chrome and Firefox plans to implement. — [Intent to Experiment: WebNN](https://groups.google.com/a/chromium.org/g/blink-dev/c/5CWKSChYo98); [Phoronix, Chrome 146 beta](https://www.phoronix.com/news/Chrome-146-Beta)
- A secondary source claims WebNN reached W3C Candidate Recommendation Draft in Aug 2026; not verified. — [Refonte Learning](https://www.refontelearning.com/blog/webnn-ai-features-no-server-round-trip)
- Wasm SIMD is shipped everywhere and relaxed SIMD in Chrome and Firefox (see Q2 table). Flexible vectors, a length-agnostic SIMD design that would map to RVV/SVE, is only Phase 1. — [features.json](https://github.com/WebAssembly/website/blob/main/features.json)
- Cranelift README: all four backends (x86-64, aarch64, s390x, riscv64) support the Wasm MVP, but only x86-64 and aarch64 "fully support SIMD". — [Cranelift README](https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/README.md)
- riscv64 SIMD began in April 2023 as an initial 128-bit implementation using RVV. — [wasmtime PR #6240](https://github.com/bytecodealliance/wasmtime/pull/6240)
- Chromium's build has `riscv_use_rvv = false` by default, with VLEN options 128–1024 (2023 config). — [Chromium riscv.gni (Cobalt mirror)](https://cobalt.googlesource.com/cobalt/+/refs/heads/master/build/config/riscv.gni)

### Inferences
- HGBA should not claim Wasm "runs on GPU/NPU". The correct model is: Wasm on CPU, WGSL via WebGPU for GPU, WebNN graphs for NPU, with Wasm (or a future component interface) orchestrating them.
- Fixed 128-bit SIMD leaves wide-vector hardware (AVX-512, SVE, RVV with VLEN>128) underused until flexible vectors advances.

### Gaps
- No current (2026) status found for V8 or SpiderMonkey Wasm SIMD on riscv64 with RVV.
- No primary source found for WASI-WebGPU (wasi-gfx); the only coverage is a secondary [article](https://ecosistemastartup.com/?p=88503).

## Q6. Portability: per-ISA compilation (Cranelift, Liftoff/TurboFan, SpiderMonkey tiers), code caching

### Takeaway
Wasm is portable bytecode but is always compiled to native code per ISA on the client, either tiered (V8: Liftoff baseline, then TurboFan) or AOT (Cranelift in Wasmtime). Browsers cache optimized machine code keyed by URL, and the cache is invalidated on engine upgrades.

### Cited Findings
- V8: Liftoff is the fast baseline compiler. TurboFan is the optimizing compiler shared with JS and runs in the background; for large modules it can take "30 seconds to a minute or more". (2019) — [V8 blog: Code caching for WebAssembly developers, 2019-06-17](https://v8.dev/blog/wasm-code-caching)
- Code caching (2019):
  - Applies only to `compileStreaming` and `instantiateStreaming`.
  - Chrome stores TurboFan output in a code cache keyed by resource URL, and any URL change forces a recompile.
  - The cache is invalidated when the `.wasm` changes or V8 updates (roughly every 6 weeks).
  - Modules under 128 kB are not cached.
  - Compiled code is 5–7x the `.wasm` size.
  - On desktop the cache is capped at about 150 MB for Wasm.
  - Works in workers and service workers.
  — [V8 blog](https://v8.dev/blog/wasm-code-caching)
- Dynamic tiering (2021, Chrome 96 trial): only hot functions are tiered up to TurboFan. There is no OSR for Wasm, so long loops may stay in Liftoff code. Only TurboFan code is cached, so cold functions are recompiled with Liftoff even on a cache hit. — [V8 blog: Dynamic Tiering, 2021-10-29](https://v8.dev/blog/wasm-dynamic-tiering)
- Cranelift (Wasmtime's code generator) has backends for x86-64, aarch64, s390x and riscv64. — [Cranelift README](https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/README.md)
- Safari/JSC added a JIT-less Wasm in-place interpreter in 2025 (secondary source). — [Platform Uno report](https://platform.uno/?p=52451)

### Inferences
- "Compile once, run anywhere" applies only at the bytecode level. HGBA must budget for client-side compilation (baseline tier for startup, optimizing tier for steady state) and a per-engine-version, per-ISA code cache. Shipping precompiled native code is not portable across engine versions.

### Gaps
- I did not fetch current docs on SpiderMonkey's tiers (Wasm baseline, then Ion), so they are not cited here. The V8 caching numbers date from 2019 and may have changed.

## Q7. Wasm-based library sandboxing (RLBox in Firefox)

### Takeaway
Firefox ships RLBox: selected C/C++ libraries are compiled to Wasm, translated back to C with wasm2c, and linked natively, so memory-safety bugs stay inside a sandbox with low overhead. The libraries are graphite, ogg, hunspell, expat, woff2 and soundtouch. Its security rests on wasm2c being correct; a 2026 CVE in wasm2c is a reminder of that.

### Cited Findings
- Each library is compiled to Wasm, translated by wasm2c and linked into Gecko. The sandboxed set is graphite, ogg, hunspell, expat, woff2 and soundtouch, controlled by a build flag and on by default on little-endian targets. Big-endian targets or opt-out builds use a "noop sandbox" that runs native code. — [Firefox source docs: security/rlbox](https://searchfox.org/firefox-main/source/security/rlbox/docs/index.md)
- Callback pitfall: per-object callback state (graphite, expat) is safe. A global setter such as `RegisterHunspellCallbacks` is a trap. — [Firefox RLBox docs](https://searchfox.org/firefox-main/source/security/rlbox/docs/index.md)
- Firefox 95 (Dec 2021) shipped Graphite, Hunspell and Ogg sandboxed; Expat and Woff2 followed in Firefox 96. — [Mozilla Hacks, 2021-12](https://hacks.mozilla.org/2021/12/webassembly-and-back-again-fine-grained-sandboxing-in-firefox-95/); [Mozilla Attack & Defense](https://blog.mozilla.org/attack-and-defense/2021/12/06/webassembly-and-back-again-fine-grained-sandboxing-in-firefox-95/)
- CVE-2026-90648: a wasm2c "table flip" flaw in wabt ≤1.0.41 can enable sandbox escape, mainly on 32-bit platforms. — [OpenCVE record](https://app.opencve.io/cve/CVE-2026-90648)

### Inferences
- RLBox shows that Wasm can act as an in-process software-fault-isolation layer without a Wasm runtime at execution time (wasm2c compiles ahead of time). HGBA can adopt the same pattern for parsers and codecs. The trusted computing base then includes the Wasm-to-native compiler and the tainted-data API discipline.

### Gaps
- I did not verify whether Firefox has picked up a patched wabt for CVE-2026-90648, or whether soundtouch is enabled in current release builds.

## Q8. Rust Wasm engines (Wasmtime/Cranelift, Wasmer) for browser embedding; Servo's Wasm handling

### Takeaway
Wasmtime is the reference CM/WASI implementation and the first with final WASI 0.3. It is written in Rust with a Cranelift backend, but it has **no JS/Web integration**: JSPI, ESM integration and JS String Builtins are N/A on features.json. Servo gets Wasm from SpiderMonkey (C++) through the mozjs bindings, not from a Rust engine. A browser could embed Wasmtime for components and extensions, but web-page Wasm requires JS-engine-integrated Wasm (GC objects shared with JS, JSPI, Web IDL bindings).

### Cited Findings
- Wasmtime feature coverage, per the Q2 table: GC, exceptions and typed function references since 47. JSPI, JS String Builtins and ESM integration are null (not applicable). — [features.json](https://github.com/WebAssembly/website/blob/main/features.json)
- Wasmtime 46+ implements final WASI 0.3 with component-model-async on by default. — [WASI.dev](https://wasi.dev/releases/wasi-p3)
- Wasmer: stack switching since 7.0, relaxed SIMD and tail call since 7.1, no GC listed. — [features.json](https://github.com/WebAssembly/website/blob/main/features.json)
- Servo uses SpiderMonkey for script execution, and SpiderMonkey also implements the Wasm JS API and core Wasm. — [spidermonkey_servo write-up](https://github.com/gterzian/spidermonkey_servo)
- StarlingMonkey (SpiderMonkey compiled to Wasm) runs inside CM-aware hosts such as Wasmtime. This is the reverse direction: a JS engine inside Wasm. — [ComponentizeJS GitHub](https://github.com/bytecodealliance/componentizejs)

### Inferences
- In an HGBA design, a two-engine split is plausible:
  - Page-facing JS and Wasm in one integrated engine (V8, SpiderMonkey or JSC class).
  - A separate Rust Wasmtime instance for privileged or extension components (WASI 0.3, CM), which would also get native CM.
- The cost is two code generators, two GC heaps, and no shared GC references between them.

### Gaps
- I found no primary source showing Servo integrating Wasmtime, or any browser shipping Wasmtime in production for web content.
- I did not verify Wasmtime's current major version, or whether its security and fuzzing posture is documented as suitable for hostile web content.
