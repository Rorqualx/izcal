# Izcal ML service: security and robustness

Compiled 21 October 2026. Scope: the sandboxed, network-less on-device ML service and its declarative model container, plus the Stage 2 agent boundary. Primary sources preferred (papers, specifications, standards prose, vendor documentation, security advisories). No third-party project's source code was read; documentation pages, specification text, abstracts and advisories were used.

Confidence: **High** = primary text read and the claim checked in it; **Medium** = official page or abstract read but not the detailed text, or a vendor claim without data; **Low** = secondary source, search summary or recollection.

**Method notes**
- The shared web-search budget was exhausted after roughly ten searches in this strand. Everything after that was read from known primary URLs directly; no search engine was queried by other means.
- Several primary pages would not render their body text (IEEE CSDL, NVD, some PDFs). Where a claim rests on the title, abstract snippet or recollection rather than checked text, it is graded Medium or Low and repeated under "Claims not verified". The note is about classes of failure and published evidence, not about reproducing any exploit.

## 1. Threat model and trust boundaries

The service is a **shared trusted process** that sees content from every site. That makes a compromise a cross-site disclosure, not a single-site bug: whatever the process can read, the attacker can read for every tab the service has served. The browser's answer to the same problem is site isolation, and the ML service sits outside it by design, so it must earn the trust with stricter rules than a renderer.

## 2. Model-file parsing and container safety

A model file is a parser input with attacker-controlled lengths, ranks, offsets and cross-field invariants. It is the same class as an image codec, with a shorter disclosure history and a worse tooling baseline. The published record says the bug is rarely one bad length; it is two fields that disagree.

**Validate before mmap.** The principle that follows is not "mmap is unsafe"; it is that the header must be read through a bounded, checked reader, every cross-field invariant proved, and only then may the data region be mapped read-only and handed to kernels. A parser that maps first and validates lazily has already exposed the address space to a hostile length.

## 3. Supply chain and integrity

Integrity has three separate questions: is this the artifact the publisher signed, is it the version the client should accept, and what produced it. Content addressing answers the first, rollback protection answers the second, provenance answers the third. None of them is a substitute for the others.

## 4. Privacy attacks

"On-device" removes the network observer, not the inference channel. The published attacks divide into membership inference, model inversion, model extraction and unintended memorisation; each assumes some query access, and the first question for the ML service is who has it.

## 5. Denial of service and resource exhaustion

The service is a single process shared by every site, so an unbounded job is a browser-wide outage. The controls are: bound every quantity before allocating, cap the job, cap the process, and make cancellation kill work rather than ask it to stop.

## 6. Prompt injection and agent-specific risks (Stage 2 only)

Stage 1 has no page-triggered inference and no page-visible output, so the indirect-injection channel does not exist: there is no path by which page content can become an instruction to a model, because no page can invoke one. Stage 2 creates that path deliberately, and the published record says it cannot be closed by prompting alone.

## 7. Sandbox implementation evidence

The primitives exist on all three targets and differ in what they can express. The design should use each OS's native mechanism, prove the capability set empty at launch, and test the denials rather than the configuration.

## Implications for Izcal

1. **Keep Stage 1 page-blind.** No page-triggered inference and no page-visible output is the single strongest control in this note: it removes the timing oracle, the fingerprinting signal and the indirect-injection channel at once. Any Stage 2 API must be a new, separately argued surface (6.6).
2. **The shared service needs a written empty-state contract.** No per-site state, no content-keyed cache, inputs dropped at completion, outputs only to the caller, one job at a time. If a future API makes the service page-facing, it splits per site or does not ship (1.7-1.9).
3. **Build the loader as a parser, not a deserialiser.** Declarative container, bounded reader, validate-before-mmap, checked dimension products, no pickle, no code, no external paths, per-tensor and whole-file SHA-256, operator allowlist (2.13-2.14).
4. **Fuzz semantically and run sanitizers in CI.** Byte-level fuzzing will not construct the cross-field disagreement that causes the bug. A seed corpus of valid containers plus a semantic mutator plus ASan is the minimum (2.2-2.4, 7.8-7.9).
5. **Sign the manifest, not the blob.** Content address every file, sign the list, verify before the loader sees it, reject non-increasing versions, and treat a verification failure as fatal (3.1-3.12).
6. **Plan for key compromise.** Offline root, threshold signing, short-lived workload credentials, a documented rotation and revocation path. A stolen release key must not be able to substitute a model silently (3.10).
7. **Do not rely on hub scanning.** A model from a hub is untrusted input regardless of its scan badge, and a clean repository can still ship a malicious artifact (8.2-8.3).
8. **Bound quantities before allocation and kill on overrun.** Dimension products, sample counts, download sizes and job durations each need an explicit cap, backed by cgroups, job objects or rlimits, with a supervisor that kills the tree (5.3-5.8).
9. **Keep provenance and privacy records structural.** No input content in journals, a machine-generated marker on every output, and a data ledger for weights. The weights can memorise; the ledger is how that risk is argued (4.5-4.7, 4.11).
10. **Test the sandbox by denial, per OS.** seccomp/Landlock on Linux, App Sandbox on macOS, AppContainer plus job objects on Windows, each with a connect/open-for-write/create-process negative test and a syscall trace (7.1-7.7, 7.12).
