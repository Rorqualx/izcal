# Izcal ML service: specifications and standards

Compiled 21 October 2026. This strand records what the published specifications actually require, so the ML service spec can anchor to them and can tell where no standard exists. It is the one strand authored by the synthesis author rather than an independent researcher, after the shared web-search budget was exhausted; primary specification pages were read directly where reachable, and every row not read at the source is graded Low.

M-1 note: only specification prose, standards documents and published papers are used. No third-party project's source code was opened. A specification describes required behaviour; it is evidence for a contract, not a shape to copy from an implementation.

Confidence: **High** = the specification text was read at the source; **Medium** = the status or date is from an official page or a reliable secondary summary; **Low** = recollection or an inaccessible primary source.

|---|---|---|---|---|---|
| 1.1 | **WCAG 2.2, SC 1.1.1 Non-text Content (Level A)** | Every non-text element needs a text alternative that serves the equivalent purpose; a brief alternative or a brief plus a longer one, as the content requires; decorative images may be marked as such. It sets no character limit and no quality metric. | W3C Recommendation, 5 October 2023 | ML-IMG must produce a short default and a longer form on request; ML-1/ML-2 measure adequacy, not length ([MA 5.6][MA]) | High |
| 1.2 | **WCAG 2.2, SC 1.3.2 Meaningful Sequence (Level A)** | When the sequence of content affects meaning, a correct reading sequence must be programmatically determinable. | W3C Recommendation, 5 October 2023 | ML-OCR's text runs must carry reading order, not just boxes; the PDF integration consumes `order` (6.12) | High |

It has no property that means "this text was generated by a machine". | W3C Recommendation, 6 June 2023 | The Q-10 disclosure cannot be a standard ARIA flag; it is a text suffix, an object attribute, or both, chosen by A11Y-3 (ML-14) | High |
| 1.4 | **HTML Accessibility API Mappings (HTML-AAM)** and **Core-AAM** | Map HTML elements and ARIA to platform accessibility APIs; define how names and descriptions reach assistive technology. | W3C specifications, continuously revised | The generated description must reach the accessibility tree through the existing mapping path, not a new one | Medium |
| 1.5 | **PDF/UA-1 (ISO 14289-1:2014)** | Defines accessible PDF: tagged content, reading order, alternative text for figures, language. | ISO, 2014 | The OCR output must fit a tagged-PDF structure the PDF spec already targets | Medium |
| 1.6 | **PDF/UA-2 (ISO 14289-2)** | Extends PDF/UA to PDF 2.0; reported published in 2024. | 1.7 | **ISO 32000-2:2020 (PDF 2.0)** | The PDF format, including tagged content and structure elements. | ISO, 2020 | The raster-in, text-runs-out contract is a PDF-layer integration, not a format change | Medium |
| 1.8 | **WCAG 3.0** | A future accessibility standard; still a Working Draft in this period. | W3C Working Draft, date unverified | No dependency; the spec targets WCAG 2.2 conformance vocabulary | Low |

**What this means.** Accessibility standards say what a description must achieve, not how to produce or mark one. Every machine-description decision in this spec — short default, longer form, reading order, generated marker — has a WCAG or PDF/UA anchor, and the marker itself has none: it is Izcal's Q-10 mechanism, not a standards feature ([AX][AX]).

## 2. Numerics and model-format specifications

| # | Instrument | What it fixes | Status and date | Relevance to this spec | Conf. |
|---|---|---|---|---|---|
| 2.1 | **IEEE 754-2019 for floating-point arithmetic** | Formats, rounding modes, operations, exceptions and special values; defines correctly rounded results for the basic operations. It does **not** require a particular reduction order across a vector or a thread count, so it does not by itself make a model's output reproducible. | IEEE, 22 July 2019; also ISO/IEC 60559:2020 | The canonical mode's contract (6.4) is built on 754's per-operation guarantees plus Izcal's fixed reduction trees; the gap is exactly why ML-D6 exists ([IK 1.3][IK]) | High |
| 2.2 | **IEEE 754-2019 fusedMultiplyAdd** | Defines the fused operation as one rounding. | IEEE, 2019 | Canonical mode forbids contraction; fast mode allows FMA ([IK 1.4][IK]) | High |
| 2.3 | **ISO/IEC 60559:2020** | The ISO adoption of IEEE 754-2019; the same arithmetic contract under an ISO name. | ISO/IEC, 2020 | Cited alongside 754 where an ISO reference is needed | Medium |
| 2.4 | **ONNX IR specification (prose)** | Defines a graph of nodes, initializers, opsets and typed tensors; a model is a protobuf with an optional external-data mechanism. It has no mandatory checksum. The format is Apache-2.0. | Open standard, continuously revised; read as prose only ([IK 7.1–7.4][IK]) | A checklist for what a graph must carry, and a counterexample for validation: `.hgmodel` adds mandatory hashes and cross-field checks (6.6) | High |
| 2.5 | **safetensors format specification** | A header length, a JSON header describing dtype/shape/offsets, and a data region; designed so loading does not execute code. | Open specification, Apache-2.0; version not verified | Its offset/shape validation problem is the same class `.hgmodel` must solve; no dependency ([IK 7.5][IK]) | Medium |
| 2.6 | **No standard model container** | No ISO, W3C or IETF standard defines a signed, declarative, cross-runtime model container with provenance and quantisation metadata. | — | `.hgmodel` is Izcal's own (ML-D7); the spec says so rather than implying a standard | High |
| 2.7 | **SPDX licence expressions** | A machine-readable syntax for licence identifiers and expressions (`MIT`, `Apache-2.0 OR MIT`). | SPDX 3.0, April 2024; 2.3 still widely used | Every ledger row and model manifest carries an SPDX expression; the training gate parses it (6.7) | Medium |
| 2.8 | **BCP 47 (RFC 5646) language tags** | Identifies languages and scripts for OCR/ASR packs, model cards and caption metadata. | IETF Best Current Practice | The model manager, the OCR language parameter and the ASR language id use BCP 47 tags | High |
| 2.9 | **Unicode Standard** | Character encoding, normalization and segmentation; the tokenizer's input is Unicode text. | Version current at implementation | The tokenizer and OCR text runs must state the Unicode version they assume | Medium |

**What this means.** Numerics has a standard for operations but not for reproducibility; model files have formats but no container standard with integrity and provenance; licensing has a syntax (SPDX) but no standard for weight provenance. The three absences are the space this spec fills.

## 3. Provenance, licensing and AI-governance instruments

| # | Instrument | What it fixes | Status and date | Relevance to this spec | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Model Cards for Model Reporting (Mitchell et al.)** | A short model document: intended use, factors, metrics, evaluation data, training data, ethical considerations. | Paper, 2019; widely adopted | The card in 6.7 follows it, with the data-ledger digest added ([MA 5.1][MA]) | High |
| 3.2 | **Datasheets for Datasets (Gebru et al.)** | Documents a dataset's motivation, composition, collection, preprocessing, uses, distribution and maintenance. | Paper, 2018; CACM 2021 | Required per training corpus ([DL 7.1][DL]) | High |
| 3.3 | **Data Statements for NLP (Bender and Friedman)** | Documents language, speaker and annotator demographics, provenance and curation. | TACL 2018 | Required per speech and text corpus ([DL 7.2][DL]) | High |
| 3.4 | **NIST AI Risk Management Framework 1.0** | Voluntary risk framework in four functions: Govern, Map, Measure, Manage. | NIST, 26 January 2023 | The governance section (6.7, ML-D12) maps to it without claiming certification ([MA 5.3][MA]) | High |
| 3.5 | **EU AI Act, Regulation (EU) 2024/1689, Article 50(2)** | Providers of AI systems generating synthetic audio, image, video or text must mark outputs in a machine-readable format and detectable as artificially generated. | In force 1 August 2024; applies from 2 August 2026 | Generated descriptions and captions carry provenance; ML-14 and Q-ML-5 ([MA 5.4][MA]) | Medium |
| 3.6 | **EU AI Act, Article 53** | General-purpose model providers must have a copyright policy honouring Article 4(3) TDM reservations and publish a sufficiently detailed training-content summary. Applies from 2 August 2025; the AI Office template was published on 24 July 2025. | Regulation; template 2025 | The Article 53 summary is generated from the model manifest (6.7) ([DL 6.6][DL]) | Medium |
| 3.7 | **EU AI Act, Article 4(3) of Directive (EU) 2019/790 (DSM)** | Machine-readable reservations of rights for text and data mining. | Directive, 2019 | The data programme honours reservations; crawled data is not a training source (6.7) | Medium |
| 3.8 | **US Copyright Office, Part 3 pre-publication report** | Training is prima facie reproduction; commercial use of vast copyrighted troves to produce competing expressive content, especially via illegal access, is beyond established fair use; licensing markets should develop first. | 9 May 2025 | Izcal does not rely on fair use for crawled data ([DL 6.5][DL]) | High |
| 3.9 | **FTC Act Section 5** (unfair or deceptive acts) as applied in the accessiBe order | An accessibility vendor may not claim that a widget makes a site compliant without support. | Final order 21 April 2025; $1M, 20 years | Generated descriptions are an aid, never a compliance claim; the card says so (6.7) ([H3][H3]) | Medium |
| 3.10 | **C2PA Content Credentials 2.1** | A provenance manifest for media: who made it, with what tools, what edits; it can carry assertions about generated outputs. It does **not** record training-data licences. | Specification 2.1; publication date not shown | Optional output assertion where the shell supports it; never used as a training-data record ([DL 7.4][DL]) | Medium |
| 3.11 | **Dataset Providers Alliance, AI Data Licensing Position Paper** | Favours direct licensing, robust opt-in for people's data and likeness, and rights metadata such as IPTC. | DPA formed 26 June 2024; paper 4 September 2024 | Contributor terms follow its opt-in principle ([DL 7.3][DL]) | High |
| 3.12 | **IPTC photo metadata** | Rights and creator metadata embedded in images. | Industry standard | A rights-metadata field in the per-item ledger for commissioned photography | Low |

**What this means.** The governance instruments are voluntary frameworks and disclosure duties, not a model licence. None of them makes an MIT weight file's training data MIT, which is why the data ledger (6.7) is the operative control.

## 4. Platform ML interfaces

| # | Instrument | What it fixes | Status and date | Relevance to this spec | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Windows ML** | The Windows runtime that selects an execution provider (CPU, GPU, NPU) for a model; HGBA-2 4.5 records that an app may express `PREFER_NPU` and receive CPU fallback. Placement is the runtime's decision. | Windows component, current | The only permitted NPU path later (ML-D9); the opaque-placement rule is HGBA-2 4.5's ([H2][H2]) | Medium |
| 4.2 | **Core ML** | Apple's on-device ML framework; it chooses compute placement itself and does not publish the policy. | Apple OS framework | Same class as Windows ML for a future NPU path; not a Stage 1 runtime ([IK 6.3][IK]) | Low |
| 4.3 | **Android NNAPI** | Android's neural-networks API; deprecated as of Android 15. | Deprecated 2024–2025 | No dependency; a lesson that an OS ML abstraction can be withdrawn ([IK 6.4][IK]) | Medium |
| 4.4 | **W3C WebNN** | A web API for neural-network inference across CPU, GPU and NPU backends. Requires at least two independent interoperable implementations to reach Proposed Recommendation. | Candidate Recommendation Draft, 10 October 2026; one engine family; Safari and Firefox do not implement it | Not a foundation for Izcal's runtime; stays behind a flag per HGBA-2 ([HP 9.2–9.3][HP]) | High |
| 4.5 | **W3C WebGPU** | A portable GPU compute and rendering API; usable for ML but not an NPU API. | Shipped in all major engines by late 2025; not Baseline in 2026 | A possible Stage 2 GPU path for large models; not in Stage 1 (ML-D9) | Medium |
| 4.6 | **No standard "model host" process contract** | No specification defines a browser's model host, its settings semantics, its file inventory, or its privacy contract. | — | The contribution of this spec; B10 and AG-0 define the off-state in prose, ML-D4/ML-D5 make it testable | High |

**What this means.** The platform interfaces Izcal may use for acceleration are OS frameworks with opaque placement, or web APIs that are not yet portable. The CPU path is the only one that is standard, portable and reproducible, which is why Stage 1 is CPU-only.

## 5. Security and supply-chain standards

| # | Instrument | What it fixes | Status and date | Relevance to this spec | Conf. |
|---|---|---|---|---|---|
| 5.1 | **NIST SSDF (SP 800-218)** | A set of secure software development practices: prepare, protect, produce, respond. | NIST, February 2022 | The loader and service development follow it; the audit (ML-21) is the external check | Medium |
| 5.2 | **SLSA** | A supply-chain integrity framework with provenance attestations and build levels. | SLSA 1.0, 2023 | The model build and release pipeline records provenance; the browser's existing signing chain is reused (6.6) | Medium |
| 5.3 | **in-toto** | A framework for attesting the steps and materials of a supply chain. | Specification, current | Optional for the model build pipeline; not required for the runtime | Low |
| 5.4 | **Sigstore / transparency logs** | Keyless signing and public transparency logs for artefacts. | Open standard and service | A candidate for model-release transparency; the browser's release key remains the trust root (6.6) | Low |
| 5.5 | **ISO/IEC 42001:2023** | An AI management-system standard: organisational governance, risk and lifecycle. | ISO/IEC, 2023 | Reference for the data and model governance process, not a certification claim | Low |
| 5.6 | **No standard for a signed model container** | No standard defines a signed, content-addressed model file with per-tensor hashes and a declarative graph. | — | `.hgmodel` is Izcal's own; its validation list is anchored in the published vulnerability literature, not a standard ([IK 7.7–7.14][IK]) | High |

**What this means.** Supply-chain frameworks describe how to attest a build; none of them makes a model loader safe. The loader's safety comes from its own validation contract and fuzzing (6.6, ML-19), not from conformance to a provenance format.

## 6. What no standard covers

These absences are load-bearing; each is owned by a decision in this spec.

1. **A model container with mandatory integrity, provenance and quantisation metadata.** ONNX and safetensors are formats, not signed containers; neither mandates a checksum ([IK 7.2–7.3][IK]). Owned by ML-D7.
2. **A reproducible numerical contract for inference.** IEEE 754 fixes operations, not reductions or thread counts ([IK 1.3][IK]). Owned by ML-D6.
3. **A machine-readable "generated by a model" flag in the accessibility tree.** ARIA has no such property; Q-10 is a text and attribute mechanism ([AX][AX]). Owned by ML-14 and the accessibility spec.
4. **A standard for weight provenance or training-data licensing.** SPDX names a licence; it does not prove the data behind a weight. Owned by ML-D3 and the D-class ledger.
5. **A testable definition of an AI off-state.** B10 and AG-0 define it for one browser; there is no standard vocabulary for "no model process, no model file, no download". Owned by ML-D4 and ML-9/ML-10.
6. **A portable NPU API with published placement.** WebNN has one implementation family; OS runtimes do not publish their placement policy ([HP 9.2–9.3][HP], [IK 6.17][IK]). Owned by ML-D9.
7. **An accessibility-quality benchmark for generated descriptions.** CIDEr, SPICE and CLIPScore measure reference overlap or image-text similarity, not task adequacy ([MA 1.17–1.21][MA]). Owned by ML-1/ML-2 and the evaluation rubric (6.7).

## 7. Implications for Izcal

- **Anchor to what the standards actually say.** WCAG 1.1.1 gives the purpose test, PDF/UA and WCAG 1.3.2 give reading order, IEEE 754 gives the operation semantics, SPDX gives the licence syntax, and the AI Act gives the marking duty. Everything else is Izcal's own contract.
- **Do not invent a standards claim.** `.hgmodel`, canonical mode, the two grants and the D-class ledger are Izcal specifications; the document says so. A reader must never think a W3C or ISO document backs them.
- **The absences are the design.** The most valuable parts of this spec are the gaps no standard fills: model container safety, reproducible numerics, generated-content provenance in the accessibility tree, weight provenance, and a testable off-state.
- **Cite the standards in code.** Every operator, loader check and disclosure mechanism carries a `// spec:` anchor to the clause or paper it implements (G189). Where the anchor is Izcal's own spec, it names the section.

## 8. Claims not verified

- **PDF/UA-2's ISO part number and publication date** — the ISO catalogue returned 403 and the PDF Association page was unreachable ([MA 5.7][MA], Low).
- **WAI-ARIA 1.2's exact publication date and whether `aria-description` is the right vehicle for a generated marker** — the recommendation date is Medium; the property list should be re-read before the accessibility spec's Q-10 work.
- **WebGPU's exact standards status in October 2026** — shipped in all major engines, not Baseline; the W3C snapshot was not read in this pass ([HP 9.1][HP], Medium).
- **SPDX 3.0's release date and the tooling's support for it** — from recollection, not read here (Low).
- **SLSA 1.0 and in-toto specification dates** — from recollection, not read here (Low).
- **ISO/IEC 42001:2023's exact scope** — from recollection, not read here (Low).
- **Unicode version current at implementation** — deliberately not pinned here; the model card records it (Low).
- **NIST AI RMF's mapping to this spec's governance** — the framework's functions are cited, but no formal mapping was performed (Medium).
- **The AI Act Article 50(2) application date and the "provider" question for a browser's generated descriptions** — the date is from the models strand; the legal classification is Q-ML-5 (Medium).
- **Whether any standard body is working on a model-container or weight-provenance standard** — no evidence was found either way in this pass (Low).
