# Izcal security scope: software supply chain, build integrity, release and update security

Compiled 18 October 2026. Primary sources were preferred (incident postmortems by the affected project, registry and security-team advisories, specifications, platform changelogs, and Izcal's own workflows and build script, read directly).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Scope: the attacks that shaped today's practice (phase 2 of the first-principles method), the defenses and their evidence (phase 3), and an audit of Izcal's present pipeline: `.github/workflows/checks.yml`, `CONTRIBUTING.md`, `.githooks/`, `tools/checks.sh`, the fork's `izcal-v8-build.yml` and `izcal-checks.yml`, and the fork's `build.rs` at `v152.2.0`. The plan read is Stage 1 design Sections 7.1, 7.7, 7.8 and 13.2 (Updates, Security response, Packaging).

Search budget note: the incidents and the 2025–2026 platform changes were researched first. Items marked "(not re-checked)" come from the researcher's prior knowledge of well-documented events and are graded Medium or Low.

## 1. Attacks on the source and build: the long-con and the build-server implant

| 1.6 | **ua-parser-js.** The maintainer's npm account was hijacked; three versions shipped a Monero miner (all platforms) and a credential stealer (Windows) for about four hours | 0.7.29, 0.8.0, 1.0.0; 6–8 M weekly downloads | [CERT-EU advisory 2021-057](https://cert.europa.eu/publications/security-advisories/2021-057/); [Rapid7](https://blog.rapid7.com/2021/10/25/npm-library-ua-parser-js-hijacked-what-you-need-to-know/) | 2021-10-22 | Medium |

| 1.10 | **s1ngularity (Nx, August 2025).** A `postinstall` payload ran the victim's own **AI coding CLIs (Claude, Gemini, Q) with permission-bypass flags** (`--dangerously-skip-permissions`, `--yolo`, `--trust-all-tools`) to search the disk for secrets. **Implications:** the attacks that hurt most did not break cryptography: they owned a person (xz, event-stream, chalk), a credential (ua-parser-js, Shai-Hulud) or a build machine (SUNSPOT). For Izcal, with one maintainer and self-merge allowed, the maintainer's GitHub account and workstation are the single largest supply-chain asset. An installed AI CLI on a developer machine is now an attack tool a payload can borrow (1.10).

Malicious yanks mean "yanked" is not a trustworthy signal on its own.

## 4. Platform defenses that now exist (GitHub, SLSA, Sigstore, Scorecard)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **SHA-pinning enforcement and blocklists** in the allowed-actions policy (enterprise, org and repository level): a workflow using an action not pinned to a full SHA fails; `!owner/action@ref` blocks a known-bad one | — | [GitHub changelog](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/) | 2025-08-15 | Medium |
| 4.2 | **Immutable releases (GA).** Once published, assets cannot be added, modified or deleted and the tag cannot be moved or deleted, even if the repository is deleted and recreated; publishing creates a **signed release attestation** over tag, commit and assets. Recommended flow: draft → attach all assets → publish. Only releases created while the setting is on are immutable | — | [GitHub changelog](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/); [docs](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) | 2025-10-28 | Medium |
| 4.3 | **Workflow lockfiles (public preview, 14 October 2026)**: `.github/workflows/actions.lock`, made by `gh actions-lock`, records the SHA every action and **transitive** action resolved to; a "Require lockfile" policy exists. **Enterprise Cloud only** in preview, so not yet available to a free public repository. GitHub notes locking does not make a dependency safe | — | [GitHub changelog](https://github.blog/changelog/2026-10-14-github-actions-workflow-lockfiles-in-public-preview/) | 2026-10-14 | Medium |
| 4.4 | GitHub's **2026 Actions security roadmap** names tj-actions, Nx and trivy-action, and plans: event and actor rules (e.g. forbid `pull_request_target`), **scoped secrets** bound to branch/workflow, removing secret management from plain write access, an **egress firewall** outside the runner VM ("remains immutable even if an attacker gains root"), and an execution data stream | previews 3–9 months from 2026-03-26 | [GitHub blog](https://github.blog/security/supply-chain-security/whats-coming-to-our-github-actions-2026-security-roadmap/) | 2026-03-26 | High |
| 4.5 | **Artifact attestations** (`actions/attest-build-provenance`) give **SLSA Build L2**; moving the build into a **reusable workflow** isolates it from the calling workflow and reaches **L3**. `gh attestation verify` checks the signer workflow identity (`--signer-repo`, `--cert-identity`) and works offline with `--bundle` | — | [GitHub docs: SLSA Build L3 with reusable workflows](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-and-reusable-workflows-to-achieve-slsa-v1-build-level-3); [gh manual](https://cli.github.com/manual/gh_attestation_verify) | 2024–2026 | Medium |
| 4.6 | **SLSA v1.2** keeps the Build track (L1 provenance exists; L2 signed by a hosted platform; L3 hardened, isolated build) and adds a **Source track** (L2 history and provenance; L3 continuous technical enforcement such as branch protection) | approved about November 2025 | [SLSA v1.2 what's new](https://slsa.dev/spec/v1.2/whats-new); [Build track basics](https://slsa.dev/spec/v1.2/build-track-basics) | 2025-11 | Medium |
| 4.7 | **Sigstore Rekor v2 GA**: tile-backed log on Trillian-Tessera, one write endpoint, yearly log shards, keys distributed via TUF; entries carry no signed timestamp, so bundles need an RFC 3161 timestamp | cosign ≥ 2.6.0 | [Sigstore blog: Rekor v2 GA](https://blog.sigstore.dev/rekor-v2-ga/) | 2025-10-10 | Medium |
| 4.8 | **OpenSSF Scorecard** automates the checks that matter here: Dangerous-Workflow (script injection, `pull_request_target` misuse), Token-Permissions, Pinned-Dependencies, Branch-Protection, Signed-Releases. No ecosystem-wide effectiveness study was found | — | [Microsoft NuGet blog on Scorecard](https://devblogs.microsoft.com/nuget/openssf-scorecard-for-net-nuget/); [scorecard repo](https://github.com/ossf/scorecard) | 2024 | Low |

**Implications:** most of the fixes Izcal needs are settings and a few workflow lines, not new infrastructure: SHA pins (enforced by policy), immutable releases, attestations from a reusable workflow, and no caches in release jobs. Lockfiles and scoped secrets are not yet available to a free public repository, so SHA pins plus a pin-updater (Renovate or Dependabot) stay the Stage 1 answer.

## 5. Rust dependency controls: cargo-vet, cargo-deny, RustSec, lockfiles, vendoring

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **cargo-vet** (Mozilla) fails the build unless each dependency version is covered by an audit from the project or an entity it trusts; it supports **delta audits** between versions, **imported audits** from other organizations, and an exemptions list "ratcheted down over time" | — | [cargo-vet book](https://mozilla.github.io/cargo-vet/) | current | High |
| 5.2 | Its built-in criteria: **safe-to-run** ("can be compiled, run, and tested on a local workstation or in controlled automation" without harm) and **safe-to-deploy** (no serious vulnerability "to production software exposed to untrusted input"; unsafe code and powerful imports examined; build deps and proc macros held to the same standard) | — | [cargo-vet: built-in criteria](https://mozilla.github.io/cargo-vet/built-in-criteria.html) | current | High |
| 5.3 | Firefox's `supply-chain/config.toml` imports audits from **Mozilla, Google and the Bytecode Alliance**. Those organizations audit much of the dependency set Izcal shares with Firefox and Servo (Stylo, WebRender, wgpu, neqo). cargo-vet does not verify reviewer identity: an import is full trust in that organization | — | [Firefox supply-chain/config.toml](https://searchfox.org/mozilla-central/source/supply-chain/config.toml) | current | Medium |
| 5.4 | **cargo-deny** checks advisories (RustSec vulnerabilities, unmaintained, yanked), bans (named crates, duplicates), licenses, and **sources** (which registries and git repositories are allowed) | 4 checks | [cargo-deny book](https://embarkstudios.github.io/cargo-deny/checks/index.html) | current | Medium |
| 5.5 | RustSec now records malicious-crate removals as advisories (2.3, 2.4), so `cargo-deny advisories` and `cargo-audit` detect a known-malicious version already in `Cargo.lock`; they are **after-the-fact** controls (arrayref's advisory came after the versions were removed) | — | [RustSec](https://rustsec.org/advisories/) | 2026 | Medium |
| 5.6 | `Cargo.lock` records a SHA-256 for each registry crate, checked on download; `--locked` refuses to change the lockfile. Already-extracted sources under `~/.cargo/registry/src` are not re-hashed on each build (not re-checked), which matters when that directory is restored from a CI cache (Section 10, L8) | — | [Cargo book: Cargo.lock](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html) | current | Medium |
| 5.7 | **Vendoring** (`cargo vendor`) protects against registry outages, deletions and silent yanks and makes the reviewed bytes the built bytes; it does not catch a malicious version that was vendored. It is a substrate for review, not a review | — | [Cargo book: cargo vendor](https://doc.rust-lang.org/cargo/commands/cargo-vendor.html) | current | Medium |

**Implications:** for Izcal the cheapest high-value step is cargo-vet with Mozilla's, Google's and the Bytecode Alliance's audits imported, criteria safe-to-deploy for the browser and safe-to-run for dev tools, and an exemption list that must shrink. A **dependency-update cooldown** (no version younger than N days†, e.g. 7) would have avoided arrayref (removed in under 2 hours), faster_log was live four months, so cooldown is not a substitute for review.

## 6. Reproducible builds and binary transparency

| # | Finding | Numbers | Source | Date | Conf. |

| 6.1 | **Tor Browser** has shipped reproducible builds since 3.0 (2013): "anyone [can] produce byte-for-byte identical binaries to the ones we release". ## 7. Update systems: design rationale and the failures that justify it

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **TUF** (spec 1.0.37, modified 2026-10-08) protects against arbitrary installation, endless data, extraneous dependencies, fast-forward, indefinite freeze, malicious mirrors, mix-and-match, rollback, key compromise below threshold, and wrong software | 10 named attacks | [TUF specification](https://theupdateframework.github.io/specification/latest/) | 2026-10-08 | High |
| 7.2 | TUF's design: **four roles** (root delegates trust; targets describes files; snapshot fixes the set of metadata versions against mix-and-match; timestamp is a short-lived signature over snapshot that limits freeze), **threshold signatures** per role, **expiry** ("Clients MUST NOT trust an expired file"), and keys other than timestamp "should be stored securely offline" | — | same | 2026 | High |
| 7.3 | **Root rotation**: the client walks root versions one by one; version N+1 must be signed by a threshold of N's keys **and** of its own. After timestamp or snapshot key rotation the client deletes cached timestamp/snapshot metadata to recover from fast-forward attacks. Rotation is therefore a designed, tested path, not an emergency improvisation | — | same | 2026 | High |
| 7.4 | Why TUF looks the way it does: it came from the observation (Cappos et al., 2008–2010) that package managers signed packages but not the **freshness and consistency** of the index, so mirrors could replay old vulnerable versions; the design goal is **compromise resilience** (survive the loss of some keys) rather than compromise prevention (not re-checked) | — | [TUF security page](https://theupdateframework.io/security/) | 2010 | Medium |
| 7.5 | **Uptane** (automotive) splits TUF across an **Image repository with offline keys** and a **Director repository with online keys** that tells each device what to install, so a compromised online server cannot ship an image the offline keys never signed | 2 required repositories | [Uptane design](https://uptane.org/learn-more/design); [Uptane Standard 2.1.0](https://uptane.org/docs/2.1.0/standard/uptane-standard) | current | Medium |

| 7.8 | Updater bugs are real even with signatures: **MFSA 2013-83**, the updater did not lock the MAR after checking its signature (time-of-check/time-of-use), fixed in Firefox 24. **CVE-2026-41431**: the Firefox fork Zen Browser **removed MAR signature verification** from its updater | — | [MFSA 2013-83](https://www.mozilla.org/security/advisories/mfsa2013-83/); [Debian tracker CVE-2026-41431](https://security-tracker.debian.org/tracker/CVE-2026-41431) | 2013 / 2026 | Medium |

Signing the binary alone would not stop rollback or freeze | — | same; 7.1 | 2026 | High |
| 7.11 | **Signed but malicious updates** from a compromised vendor build or update system: ASUS Live Update (ShadowHammer, 2019, signed with ASUS's key), CCleaner (2017), M.E.Doc/NotPetya (2017), 3CX (2023, itself a cascade from a compromised X_Trader download) (not re-checked) | — | e.g. [Kaspersky: Operation ShadowHammer](https://securelist.com/operation-shadowhammer/89992/) | 2017–2023 | Medium |

**Implications:** the plan's choice of a TUF client (13.2) is well supported. What the evidence adds: the **timestamp key is the only key that should be online**; the **targets and root keys must be offline and threshold-held** even with one maintainer (two hardware keys in separate places); and the update metadata must be served from infrastructure Izcal's keys protect end to end, because hosting will be compromised at some point (Notepad++). ## Lessons for Izcal

| Project / incident | What happened | The lesson | How Izcal applies it |
|---|---|---|---|
| xz-utils | Backdoor only in release tarballs, not git; maintainer was the attacker | Artifacts must be reproducible from reviewed source; trust in a person is an attack surface | V8 archives rebuilt by two independent builders with matching hashes before a tag ships (SC-11); release built only from a tagged commit, never from uploaded files |
| SolarWinds SUNSPOT | Build server altered source during compilation; signed output | Signatures prove origin, not integrity of the build | SLSA Build L3 (isolated reusable workflow, ephemeral hosted runners) plus independent rebuild |
| event-stream, ua-parser-js, chalk, Shai-Hulud | Maintainer handover, account takeover, TOTP phishing, token theft | The weakest point is the person and their tokens | Passkey/hardware-key-only GitHub account for every maintainer; no long-lived publish tokens; review every new dependency version (cargo-vet) |
| arrayref (2026) | Compromised crate maintainer; build script fetched payload at `cargo build` | Rust builds execute dependency code; minutes are enough | cargo-vet audits plus a cooldown on new versions; builds run with no secrets present; dependency bumps only by reviewed PR |
| tj-actions, Trivy, actions-cool | Tags moved to malicious commits | A tag is a mutable pointer | Pin every action to a full SHA; enable GitHub's SHA-pinning policy; Renovate/Dependabot for updates; minimize third-party actions in write-scoped jobs |
| Ultralytics, Clinejection | Low-privilege workflow poisoned the cache used by release jobs | Caches cross trust boundaries | Release and publish jobs restore no caches and build clean |
| Clinejection, PromptPwnd, s1ngularity | AI agents with shells acted on untrusted text; malware borrowed local AI CLIs | An agent with tools is a code-execution primitive | No CI agent with shell or secrets on untrusted input; keep the local reviewer read-only; treat it as advisory |
| PyTorch runners | Fork PRs ran on persistent self-hosted runners | Public PRs must never reach your hardware | Self-hosted (huey, laptop) only for `push`/`workflow_dispatch` on protected refs, ephemeral, or not at all for the public repo |
| Notepad++ | Hosting compromise redirected unsigned update checks for six months | Signed binaries are not enough; metadata, freshness and hosting compromise must be designed for | TUF client: offline threshold root and targets keys, online timestamp only, short expiry, pinned root in the binary |
| Zen CVE-2026-41431, MFSA 2013-83 | Verification removed in a fork; TOCTOU after check | Updater code is security-critical code | Updater verification in a small, fuzzed crate (`hg-update`), verify-then-apply on a locked file, test vectors for every TUF attack |
| Storm-0558 | Key rotation stopped; old key stayed live | Rotation that is not rehearsed stops happening | Scheduled key-rotation drills for TUF and code-signing keys; alert on key age |
| Chrome Omaha, Firefox MAR | Signed update responses and packages independent of TLS | Do not rely on TLS or the CDN for update integrity | TUF metadata is the integrity root; TLS is only a privacy layer |

## Open questions and flagged claims

- **Unverified repository settings**: whether the fork already has immutable releases, branch rulesets, required signatures or the upstream workflows disabled was not checked (settings are not in git).
- **Bit-for-bit reproducibility of the V8 archive** is not known to be measured; M0's determinism work concerns runtime behavior and rebuild logs (6.5).
- **Toolchain downloads inside the V8 build** (`rust_toolchain.py`, clang `update.py`, CIPD for gn/ninja) showed no hash check in a grep; CIPD instance IDs are content hashes, so gn/ninja may be verified implicitly. Needs a read of each script.
- Counts for Shai-Hulud 2.0, Trivy, chalk and slopsquatting come from vendor blogs (Low); the arrayref, Clinejection, Notepad++, TUF, pull_request_target and GitHub roadmap claims were read in the primary text (High).
- Workflow lockfiles (4.3) are Enterprise Cloud only in preview; availability for free public repositories is unknown.
- crates.io has not stated how the arrayref maintainer was compromised or announced registry changes in response.
