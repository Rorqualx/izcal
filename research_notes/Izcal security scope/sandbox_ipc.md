# Izcal security scope: OS sandboxing primitives and IPC security

Compiled 18 Oct 2026. Primary sources were preferred: OS vendor documentation, kernel documentation, browser design documents and security blogs, vulnerability advisories, exploit write-ups by the people who analysed them, and papers. Per M-1, browser *design documents* are cited and browser source files are not.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a well-known fact recalled but not re-fetched this session; **Low** = secondary source only.

**Method note.** The web-search budget was spent first on the questions that carry the design: how IPC-boundary escapes actually happen, the macOS sandbox API status, and the Linux user-namespace situation. Several facts (Landlock kernel versions, seccomp history, App Sandbox dates) are recalled from stable documentation and graded Medium. Section 14 lists the gaps.

**Izcal context this note serves.** HGBA-2 Section 3 makes the browser process a capability broker; I-2 requires zero ambient authority for renderers; I-3 stacks the V8 cage, RLBox-style wasm2c and MTE on top of the OS sandbox. Stage 1 Section 1 lists the process types (broker, per-(site, container) renderer, GPU, network, storage, pooled utility, protected-media host, shell renderer, ML service, agent host). Stage 1 Section 4 specifies `.hgidl` IDL, endpoints as capabilities, a fixed little-endian wire format (VER-1) with a generated Kani harness per message, an allowlist for sync calls, and in-house OS transports (Unix sockets + `SCM_RIGHTS` + `memfd`; Mach ports; named pipes + `DuplicateHandle`).

## 1. History: how browsers came to rely on OS sandboxes

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **The broker/target model came from Windows constraints.** Chromium's Windows sandbox is a user-mode library: the browser process is always the broker; it spawns targets, hosts the policy engine and an IPC service, and performs allowed actions on their behalf. Targets drop from an initial token to a lockdown token with `LowerToken()`, which cannot be undone. The sandbox is considered compromised "once execution passes a few early calls in `main()`". | 7 token levels; ~4 MB per alternate desktop | [Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md) | living doc, read 2026-10-18 | High |
| 1.2 | **Interceptions are for compatibility, not security.** Hooked Windows APIs are forwarded over sandbox IPC to the broker, which re-issues or denies them. Policy checks in the target are "only a speed optimization". | — | Same | living doc | High |
| 1.3 | **The 2010 view: retrofitted sandboxes were large and porous.** Capsicum's authors counted Chromium's sandbox code per OS: Windows ACL/SID sandbox 22,350 lines (mostly syscall forwarding to the broker), Linux setuid chroot helper 605, Mac Seatbelt 560, SELinux policy 200, the old Linux seccomp sandbox 11,301 (with "over a thousand lines of hand-crafted assembly" for a trusted-thread design), Capsicum 100. They found "significant vulnerabilities in all of these sandbox models due to inherent flaws or incorrect use". | 22,350 / 605 / 560 / 200 / 11,301 / 100 lines | [Watson et al., Capsicum, USENIX Security 2010 (PDF)](https://www.usenix.org/legacy/event/sec10/tech/full_papers/Watson.pdf) | 2010-08 | High |
| 1.4 | **Why the old sandboxes leaked.** Windows DAC could not protect non-securable objects (FAT volumes, TCP/IP sockets in that era); the setuid chroot left System V shared memory (hence the X server) and network open, and needed a root binary; Seatbelt and SELinux put policy in a separate file from the code ("dual-coding"), which "can lead to inconsistencies". The current Chromium Windows doc still lists FAT volumes and anonymous shared memory as unprotectable. | — | Same; [Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md) | 2010 / living | High |
| 1.5 | **Capsicum made Chromium sandboxable in ~100 lines only because the browser was already message-passing.** "Would not have been possible without existing sandbox support in the design": fonts already passed as fds, shared memory for output, RPC marshalling everywhere. The only real change was System V → POSIX shared memory. | ~100 lines vs 4.3 M lines in tree | [Capsicum paper](https://www.usenix.org/legacy/event/sec10/tech/full_papers/Watson.pdf) | 2010 | High |
| 1.6 | **Fate of Capsicum.** It shipped in FreeBSD (capability mode, `cap_enter`). The Linux port was never merged, so no mainstream desktop OS offers capability mode. What survived is the idea: Fuchsia, WASI preopens and Landlock all express "start empty, receive handles". | — | Recalled; FreeBSD capsicum(4) | — | Medium |
| 1.7 | **Linux moved from setuid + legacy seccomp to user namespaces + seccomp-bpf.** seccomp mode 1 (read/write/exit only) arrived in Linux 2.6.12 (2005); seccomp-bpf in Linux 3.5 (2012), which Chromium adopted soon after. Chromium's current README: setuid sandbox "everywhere" as a fallback, namespaces and seccomp-bpf "where supported"; SELinux and AppArmor "previously used, no longer used"; Landlock: "We currently don't use Landlock, but we'd like to." | — | [Chromium Linux sandbox README](https://chromium.googlesource.com/chromium/src/+/HEAD/sandbox/linux/README.md); dates recalled | living | High (README) / Medium (dates) |
| 1.8 | **Firefox reached comparable isolation only after a multi-year re-architecture.** Win32k lockdown in Firefox 100 required moving all drawing to WebRender in the GPU process (Firefox 92), remoting Canvas 2D and WebGL with "a robust validating API between child and parent", non-native form theming, IPC-remoted line breaking for Thai/Lao/Tibetan/Khmer, and blocking third-party DLLs that pull in user32. macOS WindowServer access was cut in Firefox 95 (process start-up 30–70% faster); the X11 connection from content processes was removed in Firefox 99. | ~4 years of work; ~15% faster new tabs from not loading DLLs | [Mozilla Hacks: Improved Process Isolation in Firefox 100](https://hacks.mozilla.org/2022/05/improved-process-isolation-in-firefox-100/) | 2022-05-12 | High |
| 1.9 | **Edge (EdgeHTML) moved the JIT out of process to get ACG.** Code Integrity Guard (Windows 10 1511) plus Arbitrary Code Guard (Creators Update, 2017) make content processes unable to map or modify code pages. Because a JIT needs exactly that, "we moved the JIT functionality of Chakra into a separate process", which maps code into the content process. Child-process creation was also blocked (1607). | — | [Microsoft Edge blog, Mitigating arbitrary native code execution](https://blogs.windows.com/msedgedev/2017/02/23/mitigating-arbitrary-native-code-execution/) | 2017-02-23 | High |

**Implications:** Every successful sandbox in this history worked because the application was already decomposed into message-passing processes with pre-opened resources. Izcal starts from that position, so its sandbox code should be small and policy should be expressed next to the code that needs it, not in a separate per-OS profile file wherever the OS allows.

## 2. Linux primitives

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **seccomp-bpf is not a sandbox.** The kernel doc says: "System call filtering isn't a sandbox." It reduces kernel exposure; behaviour and information-flow policy must come from elsewhere (namespaces, an LSM). Filters cannot dereference pointers, so only register arguments are checked, which avoids a TOCTOU class. Installation requires `NO_NEW_PRIVS` or `CAP_SYS_ADMIN`. A seccomp sandbox must not allow `ptrace`. The main pitfall is filtering syscall numbers without checking the architecture. | — | [Linux kernel: Seccomp BPF](https://docs.kernel.org/userspace-api/seccomp_filter.html) | living | High |
| 2.2 | **User notification (`SECCOMP_RET_USER_NOTIF`) has caveats.** Notifications carry no memory pointers; a supervisor must copy tracee memory before deciding, or it has a TOCTOU bug. The notifying process can be pre-empted, aborting the notification. | — | Same | living | High |
| 2.3 | **Landlock: unprivileged, stackable access control, 11 ABI versions.** ABI 1 (Linux 5.13) filesystem rights; 2 `REFER` (cross-directory rename/link); 3 `TRUNCATE`; 4 TCP bind/connect; 5 `IOCTL_DEV`; 6 scoping of abstract Unix sockets and signals; 7 logging flags; 8 `RESTRICT_SELF_TSYNC` (all threads); 9 `RESOLVE_UNIX` for pathname sockets; 10 UDP bind/send; 11 `RESTRICT_SELF_NO_NEW_PRIVS`. | 11 ABIs; max 16 stacked layers | [Linux kernel: Landlock](https://docs.kernel.org/userspace-api/landlock.html) | read 2026-10-18 | High |
| 2.4 | **Landlock kernel versions** (not given in the doc): ABI 2 = 5.19, 3 = 6.2, 4 = 6.7, 5 = 6.10, 6 = 6.12, 7 = 6.15. The kernels that added ABIs 8–11 were not checked. | — | Recalled from release notes | 2022–2025 | Medium |
| 2.5 | **Landlock limits.** It cannot yet restrict `chdir`, `stat`, `flock`, `chmod`, `chown`, `setxattr`, `utime`, `fcntl`, `access`; it cannot restrict pipes/sockets reached via `/proc/<pid>/fd/*` or nsfs paths; ioctl control is coarse and applies only to newly opened device files; network rules need `CONFIG_INET`. | 16-layer limit | [Linux kernel: Landlock](https://docs.kernel.org/userspace-api/landlock.html) | living | High |
| 2.6 | **Kernel attack surface through allowed syscalls is the dominant Linux escape route.** In Google's kCTF VRP, 60% of submissions in the year to June 2023 exploited `io_uring`, and `io_uring` was used in every submission that bypassed Google's mitigations. Google disabled it on ChromeOS and production servers, and Android's seccomp filter makes it unreachable to apps; Google considers it "safe only for use by trusted components". | 42 exploits; 60%; ~US$1 M paid for io_uring alone | [Google Security Blog: Learnings from kCTF VRP's 42 Linux kernel exploits](https://security.googleblog.com/2023/06/learnings-from-kctf-vrps-42-linux.html) | 2023-06-14 | High |
| 2.7 | **Unprivileged user namespaces are an exploit enabler.** Canonical cites a Google report that 44% of the exploits Google saw required them, and calls them "broadly used as a step in several privilege escalation exploit chains". | 44% | [Ubuntu blog: Restricted unprivileged user namespaces in 23.10](https://ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces) | 2023-10-09 | High (citation) / Medium (underlying stat) |
| 2.8 | **Ubuntu restricts them per application via AppArmor.** From 23.10 (opt-in) an unprivileged process may create a user namespace only if its AppArmor profile has a `userns,` rule (or it has `CAP_SYS_ADMIN`). Canonical added a `default_allow` profile mode; its example is a profile for `/opt/google/chrome/chrome`. Sysctls: `kernel.apparmor_restrict_unprivileged_userns`, `kernel.apparmor_restrict_unprivileged_unconfined`. Applications installed at other paths are blocked until someone writes a profile. Ubuntu 24.04 enabled it by default. | — | Same; default in 24.04 per [Qualys advisory](https://www.qualys.com/2025/three-bypasses-of-Ubuntu-unprivileged-user-namespace-restrictions.txt) | 2023-10 / 2024-04 | High (mechanism) / Medium (24.04 default) |
| 2.9 | **The restriction was bypassed three ways.** Qualys (reported 15 Jan 2025): `aa-exec` into a permissive preinstalled profile (e.g. `chrome`, `flatpak`, `trinity`); `busybox`, whose profile allows namespaces; and `LD_PRELOAD` into a permissive program such as Nautilus. Canonical treated them as defence-in-depth weaknesses, not vulnerabilities. | 3 bypasses | [Qualys advisory](https://www.qualys.com/2025/three-bypasses-of-Ubuntu-unprivileged-user-namespace-restrictions.txt) | 2025-03 | Medium |
| 2.10 | **Flatpak breaks the browsers' namespace layer.** Flatpak's own seccomp filter blocks nested namespace and chroot creation. Chromium in Flatpak uses Zypak, which `LD_PRELOAD`s a shim so Chromium believes its setuid sandbox exists and delegates to Flatpak's sandbox; the seccomp layer stays because filters stack. Reports say Firefox's Flatpak build simply loses its namespace layer. Replacing `fork` with `flatpak-spawn` also loses copy-on-write zygote memory sharing. | — | [Fedora Discussion thread](https://discussion.fedoraproject.org/t/security-problems-with-flatpak-browsers-firefox-chromium-bubblejail-seccomp-user-namespaces/121109); [Privacy Guides thread](https://discuss.privacyguides.net/t/does-flatpak-weaken-chromium-firefoxs-sandbox/13373) | 2024–2025 | Low |
| 2.11 | **Firefox's Linux content sandbox is cumulative levels.** Level 1 blocks many syscalls including process creation; 2 adds filesystem write restrictions; 3 adds read restrictions; 4 (Firefox 60) adds a chroot and, where available, unprivileged user namespaces, but still allows network and System V IPC in some GPU-driver configurations. Access goes through a file broker in the parent. | — | [MozillaWiki: Security/Sandbox](https://wiki.mozilla.org/Security/Sandbox) | last edit 2024-10-11 | High |

**Implications:** On Linux the honest residual risk of any sandboxed Izcal process is "every kernel bug reachable from the syscalls, ioctls and files we allow". The filter must deny `io_uring`, `bpf`, `userfaultfd`, `keyctl`, `ptrace`, `perf_event_open` and namespace creation after setup, and check the architecture. User namespaces cannot be assumed: Izcal needs a measured fallback path for Ubuntu without an AppArmor profile, Flatpak and hardened distributions, and that fallback must be listed as a reduced mode rather than silently weaker.

Izcal must measure, on the macOS 27 SDK, whether a custom deny-default profile still applies, and evaluate Enhanced Security helper extensions as the fallback for utility, storage and possibly renderer processes.

That is a measurable trade-off for the security owner, not a default.

## 7. IPC as the boundary: Mojo, IPDL and the rules they learned

| # | Finding | Numbers | Source | Date | Conf. |

| 7.1 | **Mojo** is a set of runtime libraries over message pipes, data pipes and shared buffers, with `.mojom` IDL generating C++, JS, Java and Rust bindings. ## 10. Capability systems: lessons for a broker

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 10.1 | **Fuchsia starts processes empty.** "A newly created process is empty. It cannot access any kernel objects, allocate memory, or execute code." | 10.2 | **Zircon rights attenuate.** Rights travel with handles; `zx_handle_duplicate`/`zx_handle_replace` can only reduce them; a handle needs `ZX_RIGHT_TRANSFER` to be sent over a channel and `ZX_RIGHT_DUPLICATE` to be copied. | — | [Fuchsia: Rights](https://fuchsia.dev/fuchsia-src/concepts/kernel/rights) | living | High |
| 10.3 | **Capsicum** joins capability mode (`cap_enter`: no global namespaces) with per-fd rights limits, and puts policy in the program instead of a separate MAC policy, at the cost of no separate policy artefact for static analysis; the authors call the two approaches complementary. | — | [Capsicum paper](https://www.usenix.org/legacy/event/sec10/tech/full_papers/Watson.pdf) | 2010 | High |
| 10.4 | **WASI/Wasmtime**: capability-based filesystem access ("only the files and directories they've been given access to"), plus 2 GB guard regions, zeroed instance memory, and Spectre hardening of `call_indirect` and `br_table`. | 2 GB guard | [Wasmtime security](https://docs.wasmtime.dev/security.html) | living | High |
| 10.5 | **Chrome's agent design extends origin isolation to the agent.** A "user alignment critic" model, isolated from untrusted content, vets proposed actions; "origin sets" split read-only from read-write origins, the planner can't add origins without a gating function, and a deterministic check restricts model-generated URLs to known public ones. **Implications:** None of the desktop OSes give Izcal kernel-enforced attenuation for its own handles, so attenuation must live in `hg-ipc`: an `Endpoint<T>` carries a rights set, the broker can only narrow it, and the transport refuses to carry a raw OS handle whose kind and rights the broker did not mint. That is exactly the check CVE-2025-2783 lacked.

## 11. The broker as a single point of failure

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 11.1 | **Rule of 2**: "Pick no more than 2 of" untrustworthy inputs, an unsafe implementation language, high privilege. | 11.3 | **The browser process is the funnel.** A full chain usually needs a renderer bug plus either an OS bug or a browser-process bug, and the browser process "fundamentally *has* to be all-powerful"; Google's strategy is to narrow both the OS slice and the browser-process slice. | — | [Google Security Blog: MiraclePtr](https://security.googleblog.com/2022/09/use-after-freedom-miracleptr.html) | 2022-09-13 | High |
| 11.4 | **Hardening the broker itself.** CET was prioritised for the browser process because Windows maps libraries at the same address in every process, so any renderer-side read reveals ROP gadgets in the browser process. | — | [Google Security Blog: cetcompat](https://security.googleblog.com/2021/05/enabling-hardware-enforced-stack.html) | 2021-05-04 | High |
| 11.5 | **Privileged script in the broker is a liability.** Both Firefox escapes in 6.7 and 6.8 ran in privileged JavaScript in the parent; the fix direction was allowlisting and moving checks to the parent, and Firefox still had to accept renderer-sent principals until site isolation. | — | [ZDI 2022](https://www.zerodayinitiative.com/blog/2022/8/23/but-you-told-me-you-were-safe-attacking-the-mozilla-firefox-renderer-part-2); [Mozilla A&D 2021](https://blog.mozilla.org/attack-and-defense/?p=217) | 2021–2022 | High |

Izcal's shell renderer (D-S2) is the WebUI case of 11.6: its endpoints are the most powerful any renderer holds, so a compromise of it is close to a broker compromise and its endpoint set must be the smallest the UI needs.

## 15. Lessons for Izcal

| Project | What happened | Lesson | How Izcal applies it |
|---|---|---|---|
| Chromium CVE-2025-2783; Firefox CVE-2025-2857 | Broker duplicated a pseudo-handle relayed by a renderer and returned a real thread handle; exploited in the wild; same pattern found in Firefox within two days | Handle transfer is the most dangerous IPC operation, and validation must be in the transport, not in each interface | `hg-ipc` OS backends accept only handles of a declared kind; the broker never duplicates a handle it did not mint; sentinel and pseudo-handle values are rejected; one Kani harness per backend proves it |
| Firefox CVE-2019-11708, CVE-2022-1529 | Parent trusted renderer-sent URL and origin; privileged JS turned them into chrome execution | Identity and authority-bearing values must never come from the sender | Origin, site, container and frame identity are properties of the endpoint binding, not message fields; `.hgidl` has no `Origin` parameter type on renderer→broker messages |
| FORCEDENTRY / NSXPC | Subclass-accepting deserialization made the whole class library reachable | The reachable surface must be "minimal, enumerable and reviewable" | Closed type universe in `.hgidl`: no `any`, no inheritance, no self-describing payloads, no embedded expressions; CI publishes and diffs the per-process interface inventory |
| Chrome FileWriter UAF; GHSL review | Renderer controlled lifetime of broker objects across async callbacks | Lifetime is part of the protocol | Broker-side objects are owned by the endpoint; pending replies hold weak references; endpoint closure is a simulator fault injected against every in-flight call |
| Mojo best practices | Many rules (no CHECK on untrusted input, return after ReportBadMessage, unions over optionals) depend on reviewers | Rules a generator enforces cannot be forgotten | `hg-ipc-codegen` enforces them; handlers return `Result`, and a bad message closes the endpoint and kills the sender, never panics the broker |
| Edge 2017 ACG; Chrome CET | Strongest Windows mitigations are incompatible with an in-process JIT | JIT placement is a sandbox decision | Non-JIT processes get the full stack; renderer JIT vs ACG/CET is an explicit, measured trade-off (jitless tier for high-security containers) |
| Firefox Win32k lockdown | Retrofit took ~4 years: remote canvas/WebGL, own form theming, IPC line breaking | Designing for no-OS-UI-in-renderer from day one is cheap; retrofitting is not | Renderers never link OS UI, font-rendering or text-shaping system libraries; everything goes through Izcal's own stacks or a broker service |
| Ubuntu userns restriction; Qualys bypasses; Flatpak | Namespaces may be unavailable, and their restriction is itself bypassable | Never assume a Linux primitive; detect, record, degrade visibly | Probe at startup; report the achieved sandbox tier per process in an `izcal://sandbox` page and in telemetry-free local logs; reduced tier is a documented mode |
| Apple SBPL status; BrowserEngineKit | The OS vendor owns the sandbox API and is moving third parties to extensions | Per-OS sandbox backends must be replaceable | `hg-sandbox` has a backend trait; macOS has a Seatbelt backend and an Enhanced-Security-extension backend under evaluation |
| kCTF io_uring | 60% of kernel exploits through one new subsystem | Deny new kernel surface by default | seccomp allowlists, not denylists; new syscalls are denied until reviewed |
| Capsicum on Chromium | 100 lines because the app already passed fds | Pre-opened, passed resources make sandboxing small | Processes receive all files as pre-opened handles from the broker; no process opens a path after start-up |
| Mozilla Nyx; MojoLPM | IPC fuzzing needed deterministic resets and call sequences | Izcal's simulator is an IPC fuzzing platform | Adversarial-renderer DST target per endpoint, with sequences and endpoint-closure races, measured under DST-1 |

## 17. IPC design rules (evidence-backed)

Each rule names the evidence that motivates it. Rules marked **[gen]** are enforced by `hg-ipc-codegen` or the transport, not by review.

1. **Handles are typed, minted and attenuated by the broker.** A message field carries a handle of a declared kind (`Endpoint<T>`, read-only shared memory, read-only file, write file in a granted directory). The transport rejects any OS handle not of that kind, rejects pseudo-handles and sentinel values (`-1`, `-2`, `INVALID_HANDLE_VALUE`, fds ≤2 unless declared), and the broker never `DuplicateHandle`s or forwards a handle on a renderer's behalf without checking its kind and rights. Rights can only shrink. Evidence: 6.4, 6.5, 4.10, 10.2. **[gen]**
2. **Identity comes from the endpoint, never from the message.** Site, origin, container, frame and process identity are bound to the endpoint when the broker creates it; renderer→broker messages cannot carry them. Evidence: 7.4, 6.7, 6.8. **[gen]**
3. **Closed type universe.** No `any`, no inheritance or subtype acceptance, no self-describing nested payloads, no strings that are later parsed as URLs, paths, JSON or expressions on the privileged side. URLs and paths are dedicated validated types. Evidence: 6.9, 7.6, 7.11. **[gen]**
4. **Every value valid by construction.** Closed enums (unknown discriminant = bad message), unions instead of optional-field combinations, no parallel arrays, explicit maximum lengths, checked arithmetic in generated size calculations. Evidence: 7.6, 7.9. **[gen]**
5. **A bad message closes the endpoint and terminates the sender; it never panics the broker.** Handlers return `Result`; `panic`, `unwrap` and `expect` on message-derived values are lint errors in broker crates; the Kani harness proves "no panic for any byte string". Evidence: 7.5, 9.4. **[gen]**
6. **Round-trip property.** For every message type, a parsed message re-serializes to the identical byte string (parse ∘ serialize = id), so no two components can disagree about a message. Evidence: 9.3. **[gen]**
7. **Copy, then validate, shared memory.** Data in shared memory from a less-privileged process is copied once into private memory before validation and use; the generated reader never reads shared memory twice. Evidence: 7.7, 9.1 (double-fetch freedom). **[gen]**
8. **Lifetime belongs to the broker.** Broker objects reachable from an endpoint are owned by the endpoint's state; in-flight async work holds weak references; endpoint closure cancels it. Endpoint closure during every pending call is a standard simulator fault. Evidence: 6.1, 6.2, 12.4.
9. **Policy only in the privileged process; feature gates on the privileged side.** The broker decides; renderers request. An unshipped feature's endpoints are not bound at all for processes that should not have them. Evidence: 7.3, 7.7.
10. **No interpreter on the privileged side.** No script engine, template evaluator or expression language runs on IPC-derived data in the broker, network or storage service. Evidence: 6.7, 6.8, 6.9, 11.5.
11. **The attack surface is an artefact.** CI generates, per process type, the list of interfaces and methods it can reach, with whether each is sync and which handle kinds it can send; the security owner reviews the diff on every PR. Evidence: 6.9 ("minimal, enumerable and reviewable"), 8.4.
12. **Privileged endpoints are bound to a kind of content.** Shell and DevTools endpoints are granted only to the shell renderer and to DevTools panes for a specific inspected target; no general renderer can request them. Evidence: 11.6.
13. **Sync calls stay on the reviewed allowlist, and nested sync is forbidden.** Evidence: 7.9; Stage 1 Section 4.1.
14. **Fuzz the protocol, not only the parser.** Every renderer-reachable endpoint gets a sequence fuzzer (create, call, close, interleave) driven through the simulator from a compromised-renderer harness that can send anything the renderer's endpoint set allows, and its yield is measured under DST-1. Evidence: 8.1, 8.3, 8.4, 8.6.
15. **No parsing of web formats in the broker** even though it is written in Rust: parse in a site-locked renderer or utility, and send normalised results. Evidence: 11.1, 11.2, 6.13.
