# Izcal security scope: new attack surfaces and privacy

Compiled 18 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, vendor documentation, advisories).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Scope.** The surfaces Izcal adds that most browsers do not have, or that are new code in Izcal: the agent principal and semantic plane (HGBA-3 B8, B9, B10; AG-0 to AG-5), recordings and deterministic replay (B1; DevTools spec DT-D2, Section 6.5, DT-1, DT-10 to DT-13), the inspection protocol and its CDP, BiDi, DAP and MCP adapters, the protected-media host (Stage 1 design 13.1a, D-S7), anti-fingerprinting, partitioning and GPC (Stage 1 design Section 6, D-S1), telemetry and crash reports (D-S4), and the Stage 1–2 feature code in 13.2 (PDF viewer, password manager and passkeys, importers, service workers, push, Wasm extensions).

**Relation to earlier notes.** Vendor agent architectures (Chrome's User Alignment Critic and Agent Origin Sets, Brave's isolated profile), the first Comet disclosure, Claude for Chrome's launch numbers, WASP, EIA, CaMeL, Invariant's MCP tool-poisoning and GitHub MCP findings, the MCP Inspector and Playwright MCP CVEs, and Chrome 136's remote-debugging change are already recorded in [agentic_browsing.md](../Future%20software%20browser%20engine/agentic_browsing.md) Section 3 and [agents_integrations.md](../Izcal%20DevTools%20spec/agents_integrations.md) Section 3. This note cites them where it builds on them and adds what those notes lack: the 2025–2026 attack record, adaptive-attack evidence, recordings, the DRM host, privacy and the Stage 1–2 feature code.

**Search budget.** About 40 web searches and 12 page reads were used. Agentic attacks, infostealers and the DRM host were researched first. Items that were only seen in search summaries are graded Medium or Low.

**Implications:** Every 2025–2026 attack entered through a channel the vendor treated as trusted: the agent's own invocation URL (1.1), the address bar (1.3), persistent memory (1.2), local files and a password-manager extension (1.4), and an extension's access to the AI panel (1.5). Izcal's B9 enforcement covers web origins, so it must also treat those channels as untrusted. Enforcement has to be on parsed targets, not string filters (1.4).

## 2. Defenses and what engine enforcement can guarantee

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **"The Attacker Moves Second."** Authors from OpenAI, Anthropic and Google DeepMind ran adaptive attacks (gradient descent, RL, random search, human red-teaming) against **12 recent jailbreak and injection defenses**. Most fell at **>90% attack success**, although most had reported near-zero rates against static attacks. Classifier and prompting defenses do not hold against an attacker who adapts | 12 defenses; >90% | [arXiv 2510.09023](https://arxiv.org/abs/2510.09023); [USENIX Security 2026](https://www.usenix.org/conference/usenixsecurity26/presentation/nasr) | 2025-10-10 | Medium |
| 2.2 | **Meta's "Agents Rule of Two".** Until injection can be detected reliably, a session should hold at most two of three properties: processing untrusted input, access to sensitive data or systems, and changing state or communicating externally. If all three are needed, the session needs human approval or a fresh context. Willison points out that untrusted input plus state change, which the diagram marks "safe", can still do harm | — | [Simon Willison on Meta's post](https://simonw.substack.com/p/new-prompt-injection-papers-agents) | 2025-10-31 | Medium |
| 2.3 | **CaMeL and design patterns.** CaMeL derives control flow from the trusted query and attaches capabilities to data. It solves 77% of AgentDojo tasks with provable security, against 84% undefended. The design-patterns paper gives patterns with provable resistance and their utility cost | 77% vs 84% | [arXiv 2503.18813](https://arxiv.org/abs/2503.18813); [arXiv 2506.08837](https://arxiv.org/abs/2506.08837) | 2025 | Medium (from earlier note) |
| 2.4 | **Chrome's deployed version** of a CaMeL-style split: the critic sees action metadata only; read-only and read-write origin sets; data may flow only from read-only to writable origins; at rollout **only the writable set was enforced**. Google calls an unrestricted agent "effectively a Site Isolation bypass" | — | [Google](https://blog.google/security/architecting-security-for-agentic/) | 2025-12-08 | High (earlier note) |
| 2.5 | **Brave on its own agent:** an isolated profile, a second reviewing model and explicit invocation, and "these safeguards do not eliminate risks such as prompt injection" | — | [Brave](https://brave.com/blog/ai-browsing/) | 2025-12 / 2026-05 | High (earlier note) |
| 2.6 | **What origin sets cannot stop (analysis).** (a) **In-set misuse.** An agent with read-write on a mail origin can be told to forward mail to the attacker *through that origin*. No cross-origin flow happens, so origin sets never fire. (b) **Read-only to writable laundering.** An injection on a read-only origin steers writes on a writable one, which Chrome's flow rule explicitly allows. (c) **Encoded exfiltration in URLs** (1.1's base64) to any writable origin, or to any navigation the planner can propose. (d) **Wrong-but-allowed actions** (buying the wrong item). Engine enforcement bounds **reach**, not **intent**. That is HGBA-3's own statement in B9, and AG-3 tests only reach | — | Inference from 1.1–1.4, 2.4 | — | Medium (analysis) |
| 2.7 | **What engine enforcement can guarantee, if built as specified.** (a) Content from out-of-set origins never enters the observation (B8 provenance). (b) No navigation or request to an out-of-set origin. (c) No access to non-web schemes (`file:`, `view-source:`, internal pages, extension pages) when the checks are on the **parsed URL in the broker**, unlike 1.4's string filters. (d) Credentials, passkeys and payment instruments never reach the model. (e) Every write is logged. (f) With AI off, none of the agent surface exists (AG-0). Each holds even when the model is fully compromised, which is why AG-3 and DT-13 test with model defenses disabled | — | HGBA-3 B9, B10; DevTools spec 6.5 | — | Medium (analysis) |

**Implications:** The evidence puts model-side defenses (classifiers, RL training, critics) as risk reduction measured in percentages, which an adaptive attacker raises (2.1, 1.7). Engine enforcement is the only layer that can be tested to 100%, and it covers reach only. Izcal should add **Rule-of-Two task policies**: a task that reads untrusted origins and holds a read-write sensitive origin needs per-write confirmation. It should also describe in-set misuse as an accepted residual risk.

## 3. Recordings and replay

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Session-replay scripts exfiltrate what users type.** Seven replay services (Yandex, FullStory, Hotjar, UserReplay, Smartlook, Clicktale, SessionCam) ran on **482 of the Alexa top 50,000** sites. They captured page content and keystrokes, including health and prescription data on Walgreens.com. A registration password reached SessionCam **even when the form was never submitted**. Redaction differed by vendor (masking all input vs excluding fields by type), and some served replays over plain HTTP | 482 / 50k; 8,000-site list released | [Princeton CITP](https://blog.citp.princeton.edu/2017/11/15/no-boundaries-exfiltration-of-personal-data-by-session-replay-scripts) | 2017-11-15 | Medium |
| 3.2 | **Password leaks to analytics.** A 2018 follow-up examined passwords that analytics and session-replay scripts captured by accident (prompted by Mixpanel collecting typed passwords). It found "seemingly well-intentioned safeguards fail". Selector-based exclusion (`input[type=password]`) misses fields the site built differently | — | [FTC-hosted slides](https://www.ftc.gov/system/files/documents/public_events/1223263/panel04_no_boundaries.pdf) | 2018-02 | Medium |
| 3.3 | **Debugging artifacts are credentials.** The October 2023 Okta breach accessed support-case files of **134 customers** (28 September – 17 October 2023). Some were **HAR files containing session tokens**, which hijacked sessions at 5 customers, among them 1Password, BeyondTrust and Cloudflare. Okta then recommended sanitizing HAR files before sharing them | 134 customers; 5 hijacks | [BleepingComputer](https://www.bleepingcomputer.com/news/security/okta-breach-134-customers-exposed-in-october-support-system-hack/) | 2023-11 | Medium |
| 3.4 | **Izcal's recording contents (from its spec).** A recording holds the B1 input log, meaning every network response, timer reading and input event, plus DOM, display-list and semantic-tree hashes. Credential, one-time-code and card fields are never recorded (DT-D2). **Every other keystroke is recorded with timestamps**, and so is every response body, including `Set-Cookie` and bearer tokens unless redacted at export | — | [DevTools spec DT-D2, 6.5](../../reports/Izcal%20DevTools%20spec.md) | 2026-10-18 | High |
| 3.5 | **Keystroke timing is sensitive in itself.** The WebGPU cache attack (9.1) recovered inter-keystroke timing with F1 of 82–98% as a side channel, which shows that timing alone carries information. A recording keeps exact timestamps for every non-credential key event, so it holds typing rhythm, a known behavioural biometric. No published study of replay bundles and keystroke dynamics was found | F1 82–98% (side channel) | [Giner et al., ASIA CCS 2024](https://www.gruss.cc/files/WebGPUAttacks.pdf) | 2024 | Medium (inference for recordings) |
| 3.6 | **Crafted recordings as input: no published attacks were found** against DevTools trace, Perfetto or HAR importers. The nearest class is import-file XSS in other products, such as a crafted **trace file** that runs script in a device's diagnostics UI (CVE-2025-40943, CVSS 4.0 9.4). An Izcal bundle is worse than a trace, because replay **executes** the recorded scripts against recorded responses: an imported bundle is an attacker-authored page plus an attacker-authored input log | CVSS 9.4 (other product) | [NVD CVE-2025-40943](https://nvd.nist.gov/vuln/detail/cve-2025-40943) | 2025 | Medium (analogy) |
| 3.7 | **Encryption at rest with the profile key** (DevTools spec 6.5 rule 10) protects against disk theft, not same-user malware. Chrome's cookies were DPAPI-encrypted for years, and infostealers decrypted them as the logged-in user. That is why Chrome added App-Bound Encryption (5.3). A saved bundle under a user-scoped key is exposed to the same malware that steals cookies | — | [Google Security Blog](https://security.googleblog.com/2024/07/improving-security-of-chrome-cookies-on.html) | 2024-07-30 | Medium |
| 3.8 | **Replay as an oracle (analysis).** Deterministic replay lets anyone holding a bundle re-run the session with probes, including retroactive logpoints that read any JS value at any past point. A leaked bundle therefore exposes every value the page computed, not only what was displayed: decrypted messages, tokens in memory, and values that redaction never saw because they were never on the wire. Redaction by placeholder (6.5 rule 6) covers only recorded inputs | — | Inference from DevTools spec 6.1, 6.5 | — | Medium (analysis) |
| 3.9 | **The entropy stream is in the bundle.** Anti-fingerprinting noise is drawn from the substrate's `Entropy` stream, seeded per (site, container, session) (Stage 1 design §6), and DET-1 replays it exactly. A shared bundle therefore contains that session's farbling seed and the page's real readback results. The seed is per session, so the damage is limited to that session's linkability | — | [Stage 1 design §6](../../reports/HGBA%20Stage%201%20architecture%20design.md) | 2026-10 | Medium (analysis) |

**Implications:** Recordings are a session-replay script built into the browser, with a stronger replay than any vendor's, and the Okta case shows debugging artifacts being shared and then stolen. Izcal's controls (never-recorded credential fields, DT-10 canaries, memory-only until saved, export redaction) target the right risks. Five gaps remain: typing rhythm, in-memory values reachable by replay, imported bundles as hostile input, user-scoped keys, and no retention limit on saved bundles.

**Implications:** Izcal's design already closes the ports: no listener by default (DT-11), pipe launch only into ephemeral containers, and a grant naming the user container. Command-line flags must never reach a user container, and the consent prompt should resist synthetic OS input where the platform allows it. Stage 2 Wasm extensions must have no debugger-class capability (4.5, 4.6).

## 5. Protected-media host: WebView2 and WKWebView

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **WebView2 is Edge's Chromium process model.** One browser process per **user data folder**, plus renderer, GPU and utility processes. Every WebView2 instance on the same folder shares that browser process, and a renderer can serve frames from several instances that use one folder. Separate folders give separate process groups | — | [Microsoft Learn: process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model) | updated 2026-06-12 | High |

| 5.3 | **Host objects stay reachable after removal.** Removing a host object blocks new access, but script that already holds a reference keeps it. **Implications:** D-S7 gives each (site, container) its own user data folder or data store, which by 5.1 also gives each its own WebView2 process group. That is the right isolation, at a memory cost. The host must expose **no bridge** (5.2, 5.3), must restart the host on runtime updates (5.4), and must check the runtime and OS WebKit version before switching (5.4, 5.7). It should also tell users that this mode inherits Edge's or Safari's patch level and exposure.

## 6. Fingerprinting

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **How unique fingerprints are at scale.** In 2,067,942 fingerprints from a top-15 French site, **33.6% were unique**, against over 80% in earlier studies with smaller, self-selected samples. Removing plugins sharply cut unique desktop fingerprints | 33.6% | [Gómez-Boix et al., WWW 2018](https://www.doc.ic.ac.uk/~maffeis/331/docs/EffectivenessOfFingerprinting.pdf) | 2018 | Medium |
| 6.2 | **Tor Browser chooses uniformity.** "Striving for uniformity has generally proved to be a better strategy for Tor Browser". "Randomization (especially incomplete randomization) may also provide a false sense of security". New windows are rounded to 200×100 multiples, capped at 1000 px. User configuration ranks as the most severe source of fingerprints: "Each option that detectably alters browser behavior can be used as a fingerprinting tool" | — | [Tor Browser design](https://2019.www.torproject.org/projects/torbrowser/design/) | (design doc) | High |
| 6.3 | **Brave chooses farbling plus uniformity.** "Best-effort". It makes values uniform where it can and adds per-session, per-site noise elsewhere. The seed "changes per session, per site (eTLD+1) and per storage area", and third-party frames share the top-level site's seed. Brave: "fingerprinting attacks will always be possible" | — | [Brave wiki](https://github.com/brave/brave-browser/wiki/Fingerprinting-Protections) | (wiki) | High |
| 6.4 | **Randomization has been broken.** Nguyen and Vadrevu (WWW 2025) tested canvas defenses in 18 extensions and in Chrome, Firefox, Brave, Tor and Safari. Randomization was the most common technique (Brave and nine extensions), and they show attacks that **predict or remove the noise in every randomization mechanism tested**. They conclude no fully deployable canvas defense exists. An earlier paper notes that noised output can itself be a fingerprint | 18 extensions, 5 browsers | [chatpaper summary of WWW 2025 paper](https://chatpaper.com/paper/129963); [arXiv 2008.04480](https://arxiv.org/abs/2008.04480) | 2025-01 | Medium (abstract only) |
| 6.5 | **Firefox 145 measured a reduction.** Fingerprinting protections cover graphics rendering, fonts, math precision, core count, touch points and taskbar dimensions. They "cut the percentage of users seen as unique by almost half". They ship in Private Browsing and ETP Strict first. Mozilla gives the time zone used by calendar and conferencing tools as a reason not to go further. | 6.6 | **Ad tech may now fingerprint under Google's rules.** Google's ban on fingerprinting by advertisers ended on **16 February 2025**. Google said in 2019 that fingerprinting "subverts user choice and is wrong" | — | [ICO](https://ico.org.uk/about-the-ico/media-centre/news-and-blogs/2024/12/our-response-to-google-s-policy-change-on-fingerprinting) | 2024-12-19 | Medium |
| 6.7 | **GPU timing identifies devices.** DRAWNAPART (NDSS 2022) identifies devices from GPU execution-unit timing. **Implications:** D-S1's hybrid (normalize discrete surfaces, add noise to readbacks, uniformity as opt-in) matches Brave's design and inherits its documented weakness, that noise can be predicted or removed (6.4). Izcal should measure PRIV-2 against **adaptive de-noising attacks**, not only naive hashing. It should also add GPU and NPU timing (6.7, 9.3) to the surface list, and keep its few user-facing options per Tor's warning (6.2).

## 13. Gaps and unverified items

- **Crafted recordings and trace importers:** no published attack was found (3.6). The risk analysis rests on analogy.
- **Measured Tor-vs-Brave comparison:** no study compares uniformity and farbling head-to-head on linkability. 6.4 is from an abstract.
- **WebView2 storage encryption:** whether WebView2 user data folders get App-Bound-style protection was not found (5.5).
- **WebView2 two-week cadence from version 153**, VoidStealer, Gray Swan's numbers and NeuralTrust's omnibox finding are single secondary sources.
- **Chrome password ABE:** whether Chrome's passwords (not only cookies) are App-Bound in 2026 was not confirmed. It decides whether Izcal can import Chrome passwords from disk on Windows at all.
- **Session-replay measurement after 2018:** no 2024–2026 measurement study was found.
- **Push (autopush) and service workers:** no new-surface research was done in this pass. Service workers are standard Chromium/Gecko-class surface. Self-hosted push adds a server that holds subscription endpoints, which belongs in the threat model.
- **Number in 7.1** is from recall and needs checking against the paper.

## 14. Lessons for Izcal

| Project or event | What happened | The lesson | How Izcal applies it |
|---|---|---|---|
| CometJacking (1.1), Atlas omnibox (1.3) | The agent took tasks from a URL parameter and from a failed URL parse | The agent's **entry points** are an injection channel, not only page content | Agent tasks start only from the trusted agent UI. No URL scheme, deep link, query parameter or address-bar fallback creates or extends a task. Add these to AG-3's suite |
| Atlas Tainted Memories (1.2) | A CSRF wrote persistent agent memory | Persistent agent state is a write target for the web | Agent memory is per task by default. Anything persisted needs user confirmation in trusted UI and is never writable through a web request. Add to AG-3 |
| PleaseFix (1.4) | `file://` reached through `view-source:` and `#.pdf` bypasses; password-manager extension driven by the agent | String denylists fail; adjacent privileged tools become the target | The broker checks the **parsed** scheme and origin of every agent navigation and fetch: only `https:` origins in the set. Extensions are not reachable by agent tasks. The built-in password manager never fills for an agent without B9's confirmation |
| Gemini Live hijack (1.5) | An extension took over the AI panel | AI surfaces become privileged targets for other local code | The agent host and its UI accept no extension messages. With AI off they do not exist (B10) |
| Attacker Moves Second (2.1), MCPTox (1.9) | Adaptive attacks beat 12 defenses; stronger models were more susceptible | Model-side defenses give percentages, not boundaries | Keep AG-3 and DT-13 testing **with model defenses disabled**. Never present classifiers or visibility flags as boundaries (AG-5 already says so) |
| Rule of Two (2.2), in-set misuse (2.6) | Injection succeeds when untrusted input, sensitive data and outbound capability meet | Origin sets bound reach, not intent | Add a task policy: if a task reads any origin outside its writable set **and** holds a read-write sensitive class, every write needs confirmation. Document in-set misuse as a residual risk |
| Okta HAR (3.3), session replay (3.1) | Debug artifacts and replay scripts carried tokens and typed data | Recordings will be shared and stolen | Saved bundles: redact by default (DT-10), add a **retention limit**, use an **OS-bound key** (Keychain, or a TPM/App-Bound-style key on Windows) rather than a user-scoped profile key, and **quantize input timestamps** in exported bundles unless the user keeps exact timing |
| Replay as oracle (3.8), crafted inputs (3.6) | Replay can read any past value; imported bundles run attacker code | A bundle is both secret data and hostile input | Imported bundles replay in a replay host with an opaque origin, no network, no user container and no write capability; the bundle parser is fuzzed (Stage 1 7.5). An agent never gets a bundle (already in 6.5 rule 10) |
| Infostealers and debug ports (4.1–4.3) | Hidden debug-mode launches stole cookies after ABE | Same-user malware will launch the browser itself | No flag, environment variable or project file can attach to a user container. A user-container grant needs the trusted-region prompt. Monitor for and refuse automation launches against a profile that is in use |
| Extension supply chain (4.5, 4.6) | A debugger API and hijacked updates exfiltrated sessions | Extension capabilities must assume a malicious update | Stage 2 Wasm extensions get no debugger, cookie-jar, WebAuthn or DOM-injection capability. Add per-update capability diffs and an OS sandbox per extension |
| WebView2 and WKWebView (5.1–5.7) | Shared processes per data folder; host bridges; patch lag; WebKit zero-days | The DRM host is a second browser engine with its own patch level | One user data folder per (site, container) (as designed). Zero host objects, web messages or injected scripts. Restart the host when the runtime updates. Refuse protected media mode below a minimum runtime or OS WebKit version. Label the mode's patch source |
| Tor vs Brave (6.2–6.5) | Uniformity lowers exposure most; randomization can be removed | Farbling is not enough on its own | PRIV-2 must include adaptive de-noising attacks. Add GPU and NPU timing to the surface list. Keep privacy options few |
| Privacy Sandbox retirement (7.5, 7.6) | Ten APIs retired; CHIPS and FedCM kept | Do not build on Chrome-only privacy APIs | Implement CHIPS and FedCM. Skip Topics, Protected Audience, Related Website Sets and IP Protection. Partition connection pools by the storage key (7.2) and ship bounce-tracking mitigation on by default |
| GPC (7.7, 7.8) | ~12 states; AB 566 from 1 January 2027; real penalties | GPC by default is now legally grounded | Keep `Sec-GPC: 1` on by default. Correct Stage 1's "three states" wording after legal review |
| Minidumps (8.1, 8.2) | Stacks hold private data; Mozilla restricts access | Crash data is private data | Filtered-stack dumps for renderer and replay-host processes. Access rules and a 30-day retention limit in the privacy policy |
| PDF.js (10.1, 10.2) | Code generated from PDF data executed | Viewers must not generate code from documents | No `eval`-style code generation in the PDF path. Output in an opaque-origin renderer, not the shell |
| Wasmtime (11.1, 11.2) | aarch64 sandbox escape; guest-triggered panics | A Wasm runtime is one layer, not the boundary | OS-sandboxed process per extension, Wasmtime defaults kept, LTS tracking |
| Password managers and passkeys (12.1–12.3) | DOM-injected autofill clickjacked; WebAuthn proxied; UA-based downgrade | Credential UI must be out of the page's reach | Autofill and passkey UI drawn by the browser outside the DOM. WebAuthn not interceptable by extensions. UA-1 should note FIDO-downgrade risk if sites misdetect Izcal |
| ABE and importers (12.4, 12.5) | Third-party decryption of Chrome data needs infostealer techniques | An importer must not behave like malware | No cookie import. Chrome passwords only from a user-made CSV. Bookmarks and history from disk are fine. Document the behavior for EDR vendors |
| Atlas phishing exposure (1.2) | Weak anti-phishing protection made the AI browser riskier | An agent navigates to whatever it is told | **Stage 1 has no Safe Browsing-class phishing and malware URL protection.** The specs mention only download reputation checks and B10's security-classifier carve-out. Agent tasks should require it |
