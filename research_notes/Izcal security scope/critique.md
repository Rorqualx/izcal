# Izcal security scope: design critique

Independent design review (method phase 8) of `reports/Izcal security scope.md`, draft 0.1, 18 October 2026. Reviewed against the first-principles-spec method and template, the Stage 1 design (Sections 1, 2.2, 3, 4, 7, 8, 10, 13), HGBA-2 (D2, S-2, S-4a, S-4e, S-5), HGBA-3 (B9, B10, VER-1, DST-1, AG-3), the DevTools spec (6.1, 6.5, DT-10/11/13), the shell UI design (UI-5, UI-9, UI-10) and the five research notes. Sources are not fact-checked here; another agent does that. The fork's workflow files were read only to check one state claim (finding M6).

Severity: **high** means the rule is unsound, conflicts with another Izcal decision, or leaves a major surface without a model, and should be fixed before the spec is adopted. **Medium** means a target or rule that does not bite, cannot be enforced as written, or misses a research finding with real weight. **Low** means wording, consistency or a small gap.

Counts: **8 high, 20 medium, 11 low.**

---

## High

### H1. The "trusted region" is drawn by an untrusted renderer that reads every site's strings
**Location:** 6.3 (shell renderer row), 6.5 (shell renderer model), 6.12 (Rule-of-Two confirmations, consent prompt), 6.14 (autofill "after a trusted-UI gesture"), SEC-19, SEC-20, SEC-23; shell UI design UI-10 ("everything above the double line is drawn by the shell"); D-S2 (shell is sandboxed web content).
**Problem:** Every consent and confirmation the spec relies on (automation attach, agent per-action confirmation, B9's credential and payment confirmation, permission prompts, the protected-media switch, the autofill gesture) is drawn by, and clicked through, the shell renderer. That renderer runs JS and takes page titles, favicons, URLs and notification text from every site. It is the one renderer that is cross-site by design. One bug triggered by a page title gives ATK-1→ATK-2 inside the process that holds the most powerful endpoints and that "clicks Allow". The broker re-check in 6.5 ("a permission grant must match a pending prompt the broker issued") does not help: a compromised shell can approve a real pending prompt with no user present. The residual row understates this ("UI spoofing and any action its endpoints allow"). In practice, the shell's integrity is the integrity of every consent decision in Izcal.
**Change:** Add a rule (call it TB-12a or IPC-R16): **the broker, not the shell, decides that a user approved.** Options to state and choose from: (a) the broker routes OS input itself and accepts an approval only for a real OS input event that it hit-tested against the prompt rectangle it asked the shell to draw, while the prompt is unoccluded and has been visible for a minimum time; (b) security prompts are drawn by a separate prompt renderer that receives no page-derived strings except the broker-formatted origin, with no JS or only project JS; (c) the native recovery-window code path (D-S2) draws the critical prompts. Recommend (a) plus (b) for credential and agent confirmations. Add the shell to ATK-2's examples. Raise "shell compromise" to "equivalent to approving any pending consent" in its threat model. Add a target: a compromised-shell harness in the simulator tries to approve every pending prompt type without broker-observed input, and 0 succeed. Also state that autofill shows only usernames in the shell, and that the broker writes the password into the target renderer directly, so the shell never holds secrets.

### H2. The sandbox table puts two processes in a tier that contradicts what they do
**Location:** 6.7 table, row "Utility, replay host, automation gateway, agent host"; 6.5 replay-host and automation-gateway models; DevTools spec 6.1 (replay host runs `hg-substrate-sim` with **one recorded process**, that is, a renderer with V8 under the recorded engine configuration), DevTools 6.5 rule 4 and DT-11 (loopback listener).
**Problem:** (1) **Replay host.** It runs V8 on page JS, and for imported bundles that JS is attacker-written (6.13). The spec still gives it "no filesystem, no network, pure computation" plus **ACG and CET** on Windows. ACG forbids V8's JIT. Running it jitless changes the engine configuration that the recording carries (DevTools DT-D2: "V8 flags" and the worker-task mode are mandatory recording fields). It also changes allocation patterns, and so GC timing and `WeakRef`/`FinalizationRegistry` results, which is exactly what M0 showed the predictable platform must hold fixed. So either the replay diverges or the policy breaks V8. On macOS the "pure computation" profile has no `allow-jit` either. (2) **Automation gateway.** The gateway is the endpoint for an optional loopback listener (DevTools 6.5 rule 4, DT-11), but the row gives it "no network". Windows AppContainer without capabilities also blocks loopback by default.
**Change:** Move the replay host to the renderer row (Standard tier, JIT allowed where the recording used it), keyed per (site, container) like a renderer, with "imported bundle" as an ATK-1 entry point equal to opening a page. Add a rule that replay uses exactly the recorded engine configuration, so a jitless replay is available only for recordings made jitless. For the gateway, follow the spec's own principle that "every process opens what it needs before lockdown, then receives pre-opened handles": the broker (or the network service) owns the listening socket and passes each accepted connection to the gateway as a handle. The gateway keeps "no network". State this in 6.7 and in DT-11's amendment.

### H3. SEC-1 cannot be met as designed, and its clock can be gamed
**Location:** 6.8 "Patch latency", SEC-1, SEC-2, SEC-D1, Q-SEC-1; HGBA-2 D2 ("track Deno's `rusty_v8` releases") and S-4e (backport onto "the currently pinned V8").
**Problem:** (1) **Branch support.** The backport path cherry-picks V8 security commits "onto the pinned V8". Chrome backports security fixes only to the current stable branch and, every other milestone, the extended-stable branch. Izcal pins whatever V8 version Deno's `rusty_v8` last tagged, which can lag Chrome stable. When the pinned branch is no longer maintained upstream, cherry-picks stop applying cleanly, and Izcal does V8 security engineering itself. No staffing row covers that, and a 72-hour bound is not credible for it. (2) **Clock start.** The clock starts at the first Chrome stable release, "or an earlier public V8 commit **if Izcal identifies it**". That makes the metric self-reported: not noticing a commit improves the score. (3) **Pipeline evidence.** The 17.5–46 minute build figures were measured on the M4 Mac, huey and the Windows laptop. SEC-27 forbids those machines as CI runners, so releases build on GitHub-hosted runners, whose V8 build time and disk headroom have not been measured. (4) **Failure action.** "An advisory recommends the Hardened profile" barely bites. Jitless covers about half of exploited V8 bugs (6.18), and few users act on an advisory.
**Change:** Add a rule to SEC-1 and to D2 and S-4e: **the fork's pinned V8 is always on a branch Chrome still patches** (stable or extended stable). If upstream `rusty_v8` has not tagged that branch, the fork rebases its own commits onto the V8 branch directly. This is also a missing owner decision (see M15). Restate the clock as "the earliest of the first public V8 commit containing the fix (found afterwards from the fix commit's history) and the first Chrome stable release", measured after the fact so it cannot be gamed. Make SEC-2's drill run on the actual release runners and record per-stage times, and derive the 72 h† from the sum of measured stages, not from M0 local builds. Give SEC-1 a failure action that bites: when an exploited-bug window is missed, a signed, TUF-delivered emergency configuration switches Standard renderers to jitless for all users until the fix ships. That needs its own owner decision (M15).

### H4. Three release-chain targets block the emergency path that SEC-1 requires
**Location:** SEC-15 ("the tag is not published until the difference is explained and fixed"), SEC-16(b) and 6.16 (TUF root **and targets** keys offline, 2-of-3† hardware keys "in separate places"), SEC-D4 (two-person approval for release tags and targets signing), SEC-1 (72 h†).
**Problem:** On a Saturday with an exploited V8 bug, a 72-hour release needs: (a) bit-for-bit agreement between a GitHub-hosted and an independent build of a 160–240 MB V8 archive, which has never been measured (11.2) and fails easily on Windows (PDB GUIDs, timestamps) and with unpinned LLVM (M6); (b) two offline hardware keys stored in separate places, all held by the one maintainer, to sign targets metadata; (c) after SEC-D4, a second person's approval. Each is sound alone. Together they put the least-proven controls on the most time-critical path. The spec does not reconcile them. Separately, a 2-of-3 threshold held entirely by one person protects against losing a key, not against compromise or coercion of that person. The spec should say so.
**Change:** Split TUF roles the way the TUF specification allows. **Root** stays offline with a threshold. **Targets** delegates release signing to a `releases` role whose keys are hardware keys that release managers carry, usable within hours. The **timestamp and snapshot** keys are online. For SEC-15, define an **emergency release class**: a security release may publish with a verified provenance attestation (SEC-13) and the reproducibility comparison running in parallel, which must be green within 7 days†, or the release is re-issued. Record each use. Say plainly in 6.16 that, until SEC-D4 is met, the key threshold protects only against key loss.

### H5. The attacker model has only one compromised process, so the IPC rules cannot be applied between services
**Location:** 6.1 ATK-2 ("compromised renderer"), IPC-R2 ("messages from a **less-privileged** process"), 6.6 adversarial mode ("a simulated renderer"), SEC-3(c), SEC-5.
**Problem:** The GPU, network, storage and utility services are all sandboxed and all parse hostile input (ATK-3, ATK-5). The 6.5 models assume each can be compromised. But no rule says how services treat **each other**, and "less-privileged" is undefined between, for example, the network service and the storage service. A compromised network service, which talks to the storage service about cookies, can ask for any partition unless the storage service treats it as hostile. 6.5 hints at this ("partition checks must live here, not only in the broker"), but the IPC rules, the oracles and SEC-3 test only the renderer.
**Change:** Define ATK-2 as "code execution in **any** sandboxed process", and add a short **privilege lattice**: the broker trusts no other process; every service trusts no other process; identity on a service-to-service endpoint is bound by the broker at creation (IPC-R2 for every edge, not only renderer→broker). Extend the adversarial harness and SEC-3(c) and SEC-5(a) to "each sandboxed process kind as the compromised peer", starting with the network service and the GPU service.

### H6. IPC-R2 is incomplete: endpoints that carry identity can be transferred, and frames are not endpoints
**Location:** IPC-R2, SEC-3; Stage 1 4.1 ("A `Remote<T>` can only be obtained by being sent one"); B2.
**Problem:** Identity is bound to an endpoint, and endpoints are transferable capabilities. Nothing stops a renderer from forwarding an identity-bearing endpoint, or the broker from relaying one (MessagePort transfer, worker creation, `window.open` handoffs). Then a process acts with an identity it was never assigned. Second, a renderer hosts several frames of its site. If identity is per endpoint, frame identity is sound only with **one endpoint per frame (and per worker)**, and the spec does not state that. Third, SEC-3(a) bans origin and site types on renderer→broker messages, but some messages legitimately carry an origin as **data** (`postMessage` `targetOrigin`, a navigation target URL). A blanket type ban either breaks them or gets bypassed with strings.
**Change:** Add to IPC-R2: (a) endpoints are declared in `.hgidl` as `bound` (identity-bearing, non-transferable, enforced by the generator and the transport) or `free` (data channels with no identity); (b) the broker creates a separate bound endpoint per frame and per worker; (c) separate `CallerIdentity` (constructible only by `hg-ipc` from the binding) from data types such as `TargetOrigin` and `NavigationUrl`, which are allowed and never used for authorization. SEC-3(b) then becomes checkable by type: no handler can construct `CallerIdentity`. Add identifier reuse to IPC-R8: frame, request and object IDs carry a generation and are never reused, so a stale ID cannot reach a new object (the Rust version of a use-after-free).

### H7. WebRTC ships in Stage 1 with no process, boundary, threat model or target, and the native PlayReady path is also missing
**Location:** 6.1–6.5 (absent); Stage 1 M7 ("PQC for WebRTC DTLS"), 13.2 (OpenH264 for WebRTC); SEC-D3 cites WebRTC's in-the-wild exploits as a reason for SEC-12 but gives it no design. The native PlayReady path (Stage 1 13.1a item 2, M7, Media Foundation CDM and protected media path) is also absent.
**Problem:** WebRTC has an in-the-wild record (CVE-2022-2294, CVE-2023-7024, in exploits_mitigations ranking 4). It parses peer-controlled RTP, RTCP, SCTP, STUN and DTLS over UDP, holds peer and IP information (ICE candidates, local-address leaks), and needs codecs on the encode side. The spec does not say which process runs it, which stack is used and whether that stack is browser code (M-1), how UDP sockets are granted, or how ICE candidates are filtered (mDNS obfuscation). Native PlayReady brings a vendor CDM and the Windows protected media path into Izcal's own engine. Neither appears in the 15-process map or the threat models.
**Change:** Add a WebRTC row to 6.3 and 6.5: placement (network service for transport, utility for codecs, a dedicated sandboxed process if the stack is C++), UDP socket grants as broker-minted handles, ICE candidate policy, and a fuzz target for the RTP, SCTP, STUN and DTLS parsers. Add a target (for example SEC-29) covering that placement and fuzzing, and include WebRTC dependencies in SEC-25. Record the stack's M-1 classification in Section 7. If it would come from another browser, the standing answer applies and Izcal builds its own, so this is a note, not a question. Add a "media CDM" row covering native PlayReady: which OS processes it runs in, what Izcal exposes to it, and its residual risk.

### H8. The GPU plan overstates what Izcal must write, and leaves out its largest parser
**Location:** 6.9, SEC-10(b), 9.2 (9 engineer-months); Stage 1 5.7 (WebRender on GL, wgpu for WebGPU).
**Problem:** (1) SEC-10(b) requires Izcal to validate **every** WebGL and WebGPU command against the specification "before ANGLE, wgpu or a driver sees it". For WebGPU, that validation is wgpu-core's job, built to the WebGPU specification. Duplicating it is months of work and a second source of disagreement. For WebGL, no Izcal spec says where the WebGL implementation lives or which shader translator macOS and Linux use. Validating in front of ANGLE effectively means writing a WebGL implementation, which 9 engineer-months does not cover. (2) **WebRender display lists**, sent by every renderer into the GPU service, are a serialized format of WebRender's own. They do not go through `.hgidl`, so IPC-R3, R4, R6 and R7 and VER-1 do not cover the largest renderer-to-privileged-process parser. The spec does not name it as an exception.
**Change:** Restate SEC-10(b): wgpu-core is the WebGPU validator, and Izcal adds resource-ownership checks per renderer, size and limit clamps, and fuzzing. The WebGL implementation's location and translator are an open question with a recommendation (validation in the GPU service, within Izcal's WebGL implementation, measured with the Khronos WebGL conformance suite's negative tests as SEC-10(b)'s metric). Add an explicit **IPC-R exception list** with WebRender display lists as entry 1: a fuzz target that deserializes them in the GPU service, a size cap, copy-then-validate, and an owner. Any other non-`.hgidl` payload (V8 inspector JSON, L11) joins that list.

## Medium

### M1. The Rule-of-Two policy misses injection from inside the writable origin
**Location:** 6.12 "Rule-of-Two task policy", SEC-19.
**Problem:** The trigger is "has read any origin **outside** its writable set **and** holds a sensitive read-write origin". The most common injection is attacker text **inside** the sensitive writable origin: an incoming email in the mail origin, an issue comment on the code-hosting origin. Meta's rule counts any untrusted input. The spec's own residual ("an agent allowed to write to a mail origin can be told to forward mail through it") is a case the policy was meant to cover. SEC-19 also passes trivially: it measures only that the defined condition fires, not that the condition is the right one, and nothing measures confirmation fatigue.
**Change:** Treat content in sensitive-class origins that third parties can write (mail, messages, issues, comments) as untrusted input by default, so writes in such tasks need per-action confirmation unless a site policy or B8 provenance marks the content as first-party. Add SEC-19(b): the median confirmations per task on a published task corpus, published per release with a ceiling†, because a policy users click through is not a control.

### M2. SEC-25 has no exploited-bug tier for Izcal's own code and covers only crates
**Location:** SEC-25, 6.11 ("RustSec advisories against ... any shipped crate"), SEC-1.
**Problem:** An exploited V8 bug must ship in 72 h†, but an exploited critical bug in Izcal's own broker gets 14 days†. Advisories for shipped **C and C++** dependencies (libvpx, whose CVE-2023-5217 was exploited in the wild; dav1d; ANGLE; SQLite; the wasm2c translator) and for the Cisco OpenH264 binary have no response target, because SEC-25 says "shipped crates".
**Change:** Add a tier for bugs known to be exploited in the wild, in any shipped component, at SEC-1's 72 h†. Extend SEC-25 to "every shipped dependency, including C and C++ libraries and vendor binaries", with the upstream advisory sources listed per dependency in the 7.7 table.

### M3. The staffing math does not match the recommendation, and "security owner approves" is self-approval for now
**Location:** 9.2 (83 engineer-months, "about 2.3–3.5 engineers", recommended 2–3†), SEC-6, IPC-R11, SEC-9 ("security-owner review"), Stage 1 4.1 (sync allowlist), SEC-D2, SEC-D4.
**Problem:** 83 engineer-months over 24 months is 3.5 engineers, so 2–3 understaffs the spec's own estimate unless the contracted audit share is quantified. SEC-1's 72-hour bound with one `rusty_v8` owner and one backup is a two-person on-call rotation all year, and that is not counted. Several gates (SEC-6, SEC-9, the sync allowlist, the threat-model review in SEC-26) are "approved by the security owner". Today that is the same person as the author, so the gates exist only on paper until the role is staffed.
**Change:** Either recommend 3–3.5† or state how many engineer-months are contracted (SEC-D10) to close the gap. Add on-call as a row. Add one line to 6.4 or 9.2: until a security owner distinct from the maintainer exists, these approvals are recorded as "self-approved" in the PR and listed in the quarterly report, so the gap is visible rather than hidden.

### M4. SEC-8 can always be passed by declaring a reduced tier
**Location:** SEC-8 ("matches the floor **or** reports a named reduced tier ... 100%"; failure: ship blocker "unless a reduced tier is recorded in the decision log").
**Problem:** Reporting a reduced tier satisfies the metric, and a decision-log entry clears the failure, so nothing forces the floor to be reached anywhere.
**Change:** Make the Section 6.7 floor **non-waivable for the renderer, shell renderer and GPU service on the four reference devices**. Allow reduced tiers only for configurations that are not reference devices (Flatpak, kernels without namespaces), and publish the number of waivers and affected platforms in each release report. If macOS SDK 27 forces a reduced renderer tier, that becomes an owner decision (SEC-D6), not a log entry.

### M5. The Windows broker mitigations conflict with IMEs, accessibility tools and file dialogs
**Location:** 6.7 broker row (Windows: "CET, CFG, CIG; extension points disabled"), 6.5 broker "Open".
**Problem:** Code Integrity Guard and disabled extension points block third-party DLLs. Third-party TSF IMEs (M6 makes platform IME integration a Stage 1 requirement), screen-reader and accessibility hooks, shell extensions in common file dialogs, and some security products load exactly that way, into the process that owns the native window. The table states these mitigations as decided, while the "Open" row says they are unmeasured.
**Change:** State which process owns the top-level native window, IME integration and file pickers. If it is the broker, mark CIG and extension-point blocking as "to be measured at M5 against the IME and assistive-technology compatibility list" rather than as decided. Consider a separate, unsandboxed but non-broker UI-host process if they prove incompatible.

### M6. The pipeline state table overclaims that CI downloads are fixed
**Location:** 6.16 "CI tool downloads verified: **Fixed**"; research note L5.
**Problem:** The V8 release build still downloads Chromium `tools/win` from a `+archive` URL with no hash, and installs LLVM through `apt.llvm.org` and `brew install llvm@21` with unpinned versions (`m0/rusty_v8/.github/workflows/izcal-v8-build.yml`, lines 93–128). libclang's version shapes the bindgen output, so these downloads affect the binding file that SEC-13 hashes and the reproducibility that SEC-15 compares. The spec's fix covers only the checker tools.
**Change:** Change the row to "Partly fixed", and add a P0 control: hash-pin `tools/win`, and pin LLVM to an exact version (or a hashed archive) in the release build. Q-SEC-11, the toolchain downloads inside V8's own build, becomes a P0 item, because SEC-15 depends on it.

### M7. The updater's privilege and the other data channels are not modeled
**Location:** 6.3 (update client in the broker), Q-SEC-6, SEC-17, 6.9 (blocklist "through the update service"), 13.2 (CRLs pushed by the update service).
**Problem:** On Windows, a per-machine install needs an elevated updater service or task, and macOS may need a privileged helper. Chrome-class updaters have a long local-privilege-escalation record, yet no updater process appears in the process map or the threat models. The broker parses TUF metadata (JSON from the network) unsandboxed, which strains IPC-R15's intent. Content-blocking lists, CRLs, the GPU blocklist and a future phishing list are update channels too (history note lesson: "treat every update channel as TUF-class"), and the spec does not say they are TUF targets.
**Change:** Answer Q-SEC-6 in the spec. Download in the network service, verify signatures in a small updater component, and apply the update in a separate updater process whose privilege depends on the install model, which becomes an owner decision: per-user install (no elevation) recommended for Stage 1. Add an updater row to 6.3 and 6.5. State that **every** data channel the browser fetches is a TUF target with expiry, under SEC-17's tests.

### M8. IPC-R5's lint cannot be enforced as written, and the panic strategy conflicts with SEC-28
**Location:** IPC-R5 ("`panic`, `unwrap` and `expect` on **message-derived values** are lint errors"), SEC-7(a), SEC-28 ("a panic in one connection never ends the service").
**Problem:** Clippy cannot track which values are message-derived. Kani proves "no panic" for the generated parser, not for handlers. SEC-28 needs `panic = "unwind"` with `catch_unwind` boundaries, while a security-oriented broker usually wants `panic = "abort"`. Neither choice is stated.
**Change:** In broker and service handler crates, deny `clippy::unwrap_used`, `expect_used`, `panic`, `indexing_slicing` and `arithmetic_side_effects` outright, with an allowlist file reviewed like the `unsafe` inventory. State the panic strategy per process: abort in the broker, unwind with per-connection `catch_unwind` in the network service. Say that SEC-7(a) covers parsers only, and add handler fuzzing (SEC-5) as the handler-side evidence.

### M9. Copy-then-validate and "read-only shared memory" need per-OS definitions
**Location:** IPC-R1 ("read-only shared memory"), IPC-R7; Stage 1 4.1 ("Bulk data crosses as read-only shared memory").
**Problem:** Copying all bulk data before use is unaffordable for video frames and textures. And "read-only" from a less-privileged **creator** is meaningless unless the OS enforces it: the renderer keeps its writable mapping unless the region is a sealed memfd (`F_SEAL_WRITE`/`F_SEAL_GROW`/`F_SEAL_SHRINK`), a Windows section duplicated without write access, or a Mach memory entry made with read-only protection.
**Change:** Limit IPC-R7 to data the privileged side **parses or interprets**. Opaque pixel or sample buffers that are only sampled are exempt if their size and format are fixed at creation by the receiver. Define the read-only handle kind per backend (memfd seals, section access mask, memory-entry protection), and add a test to SEC-4(a) that a writable mapping cannot cross as the read-only kind.

### M10. IPC-R1 does not say how the Windows broker, which is the transport, checks handles
**Location:** IPC-R1 ("never duplicates or forwards a handle on a sender's behalf unless it minted it"); Stage 1 4.2 (Windows: "Named pipes plus `DuplicateHandle` brokered by the browser process").
**Problem:** On Windows the broker **is** the handle relay: sandboxed processes cannot duplicate handles into each other, so every handle crossing renderer→GPU or renderer→utility goes through the broker's `DuplicateHandle`. That is exactly the CVE-2025-2783 code path. "Unless it minted it" either forbids all renderer-created shared memory, which is workable if stated, or does not describe the check.
**Change:** State the Windows mechanism: the broker duplicates **from** the source process (with its own `PROCESS_DUP_HANDLE` right) into its own table, determines the kind **from the object** (`GetFileType`, `NtQueryObject` type name), never from the message, compares it with the declared kind, and duplicates onward with an **explicit, narrowed access mask**, never `DUPLICATE_SAME_ACCESS`. Alternatively, require every shared region to be broker-minted on request. Give macOS the matching rule: reject task, thread and host ports by kernel-object type, and accept only port kinds the broker created. These rules are what SEC-4(b)'s Kani harnesses should prove.

### M11. SEC-20 does not stop the attack it cites, and the residual risk from same-user malware is unstated
**Location:** 6.12 "Local malware launching Izcal", SEC-20; ATK-7.
**Problem:** Infostealers usually **kill** the browser and relaunch it in debugging mode. "Refuse automation against a profile another instance holds" does not apply when nothing holds the profile. The first clause (no flag attaches to a user container) is the real control. More broadly, same-user malware can read process memory or inject into a medium-integrity broker on Windows, and App-Bound Encryption was bypassed by injection within months (Elastic, cited). Linux has no app-bound key store at all (Secret Service is user-scoped), which SEC-21(c) skips.
**Change:** Drop the profile-in-use clause or reframe it as defense in depth. State in ATK-7 that against same-user code execution Izcal **raises cost and leaves evidence**; it does not prevent theft. Name the Linux residual for SEC-21(c) and the password manager.

### M12. Timestamp quantization breaks replay fidelity
**Location:** 6.13 "Typing rhythm", SEC-21(d); DevTools DT-D2, 6.5 rule 6; B1.
**Problem:** A recording is an input log, so moving input timestamps by up to 100 ms† changes how they interleave with timers, which changes what the replay computes. The spec presents the change as privacy-only. Also, 100 ms is about the size of typical inter-key intervals and still keeps digraph-level timing, and no rationale is given.
**Change:** Run quantized exports through DevTools rule 6's redact-and-replay divergence check, and label them "approximate from the first divergence". Quantize only the **intervals between keystrokes in text-entry fields**, not all input. Justify the bucket size from the keystroke-biometrics literature in the research note, or mark it † with a measurement plan.

### M13. Processes that run only Izcal's code should be jitless by default
**Location:** 6.7 ("Shell renderer: As renderer"; DevTools workspace and pane "as renderer"), SEC-D5.
**Problem:** The shell renderer, the DevTools workspace and the panes run only project JS (D-S2, DevTools 6.5 rule 7), and the shell is the highest-value renderer (H1). JIT buys them little, and on Windows it costs them ACG and CET.
**Change:** Run these processes jitless with the full Windows mitigation set (ACG, CET), and seccomp-deny `PROT_EXEC` mappings on Linux, measured against the shell's UI-* latency targets. It is cheap, and it narrows H1's entry route.

### M14. Several components have no stated provenance under M-1
**Location:** Section 7; 6.10 (PDF), 6.5 crash handler, 6.9 (driver blocklist), 6.10 and 6.18 ("RLBox-style"), 6.11 ("CORB-class").
**Problem:** The spec is careful about SBPL and importers but leaves gaps where the obvious candidates are another browser's code. **PDF:** PDF.js (Firefox) and PDFium (Chromium) are both browser components, and the spec names no engine. **Crash handler:** Crashpad and Breakpad are Chromium projects. **GPU driver blocklist:** the obvious data source is Chromium's software-rendering list. **WebRTC** (H7). **RLBox** is Firefox's C++ framework; "RLBox-style" implies Izcal writes its own tainted-type wrapper, but Section 7's "built new" list omits it. CORB is obsolete; the Fetch standard's mechanism is **ORB** (opaque-response blocking).
**Change:** Add each item to Section 7, either as an unmodified non-browser dependency or as built new by Izcal from its specifications (the minidump format from Microsoft's documentation; the blocklist from Izcal's own device testing and vendor advisories). This applies the standing answer and asks the owner nothing. Rename "CORB-class filtering" to ORB, written from the Fetch standard.

### M15. Decisions are missing, and three listed ones are not real choices
**Location:** 9.3.
**Problem:** Missing real choices: (1) **an emergency mitigation channel**, meaning a TUF-signed remote configuration that can force jitless or disable WebGPU or a codec during an exploited window (H3). It has privacy and B10-style "no surprise changes" implications, so the owner should decide it. (2) **the V8 tracking source**: Chrome's maintained branch directly, or Deno's tags (H3). (3) **S-6 network-service sandbox in Stage 1** on Linux and macOS: it holds every cookie, and the spec only reports "best effort". (4) **image and font decoders**: 6.10 says the choice "should be" made but gives it no ID. (5) **WebGPU on by default** per platform (the GPU model's "Open" row). (6) **the updater install model** (M7). Weak entries: SEC-D8 option (a), decrypting Chrome's data with infostealer techniques, is not a choice anyone would make; SEC-D9 and SEC-D10 are near-obvious; SEC-D6 option (c), "wait for Apple", is a strawman; SEC-D4 and SEC-D10 have no reversal trigger.
**Change:** Add decisions for (1), (2), (3) and (6). Make (4) and (5) open questions with recommendations. Fold SEC-D8 and SEC-D9 into the design as settled rules, with the legal-review trigger kept as a note. Give SEC-D4 a trigger (for example, "D-S8 funds a second person: the date moves forward").

### M16. No trust boundary covers web content reaching the local network and localhost
**Location:** 6.2 (TB list); Stage 1 Section 1 (network service enforces LNA); DevTools 6.5 rule 4.
**Problem:** Pages attacking routers, printers and localhost services (local network access, DNS rebinding) are a standing attacker route. The DevTools loopback listener is an instance of the same boundary. The network service already enforces LNA (Stage 1 Section 1), but the threat model has no TB, no ATK mapping and no target for it.
**Change:** Add TB-13, "web content ↔ local network and loopback", enforced in the network service from the endpoint's context (IPC-R2), with a target: 100% of a published LNA and DNS-rebinding suite blocked without a permission grant.

### M17. Downloads, external protocol launches and File System Access have no rules
**Location:** 6.5 broker entry points ("OS integration (file associations, protocol handlers ...)"), Stage 1 13.2 (downloads manager "with file-type and reputation checks", File System Access permission).
**Problem:** Delivering a malicious file and launching an external protocol handler (the Follina-style `ms-msdt:` class) are among the most common real-world browser-assisted compromises of ordinary users, who are this spec's main population (Section 1). The spec has no rule on Mark-of-the-Web or `com.apple.quarantine` tagging, on dangerous-type handling, on external-scheme launch prompts (user gesture, per-origin, no auto-launch from iframes), or on the write handles File System Access hands to renderers. The "reputation check" needs a data source, which is the same question as SEC-D7.
**Change:** Add a short 6.14 subsection with these rules and one target. Tie download reputation to SEC-D7.

### M18. SEC-5 sits on M6's critical path, cannot exercise the OS transports, and its metric is undefined while yields are low
**Location:** SEC-5(a) ("blocks M6"), SEC-5(b); 6.6; Stage 1 3.2 (simulation transport is in-memory queues); Stage 1 8.2 (M6 is on the critical path).
**Problem:** (1) A tool with no precedent, by the spec's own account, gates a critical-path milestone. (2) In simulation, handles are not OS handles, so the adversarial mode cannot test IPC-R1 or IPC-R7 at the transport, where CVE-2025-2783 lived. (3) "Unique bugs per CPU-hour versus `cargo-fuzz`" is undefined when both are near zero, as they will be early. (4) Endpoints keep arriving after M6 (the storage service and media at M7), so "100% by M6" is a snapshot.
**Change:** Gate M6 on "every endpoint has a generated sequence fuzzer, run under either the simulator or `cargo-fuzz`", and make it a T0 rule (no new endpoint merges without its generated harness). Add a **per-OS multi-process transport fuzzer** for handle passing, separate from the simulator. Make SEC-5(b) falsifiable early with a **planted-bug benchmark**: seed known IPC bug classes (a pseudo-handle relay, an identity taken from the message, closure during a pending reply, a double fetch) into a test build, and measure time-to-find for both tools.

### M19. SEC-27's Scorecard criterion is undefined and partly unachievable
**Location:** SEC-27 ("Scorecard and zizmor clean at medium severity or above").
**Problem:** OpenSSF Scorecard reports 0–10 scores per check, not severities, and its Code-Review and Branch-Protection checks will fail while one maintainer self-merges.
**Change:** List the Scorecard checks that must score 10 (Pinned-Dependencies, Dangerous-Workflow, Token-Permissions, Binary-Artifacts) and the known exceptions until SEC-D4 is met (Code-Review), with zizmor at "no findings of medium or higher".

### M20. The spec does not work yet as the overarching document an engineer reads first
**Location:** whole document; header "Relates to" line; 6.5; 6.6–6.17; 8; 11.1.
**Problem:** An engineer who owns one process must read 6.3, 6.5, 6.7, the relevant subsection of 6.8–6.17, IPC-R, and about a third of the 28 targets to learn what applies to them, and no index links them. Rules are numbered (IPC-R), but the 6.12–6.14 rules are prose bullets with no IDs, so they cannot be cited from code or PRs. Q-SEC items have no owner or milestone. ATK and TB have no matrix.
**Change:** (1) Add a **per-process index** right after 6.3: process × (ATK classes, TBs, IPC-R rules, sandbox row, SEC targets, threat-model file, owning track). (2) Give the agent, recording, shell-feature and network rules IDs (AG-R, REC-R, SH-R, NET-R) so they can be cited the way IPC-R is. (3) Add a **"by role" reading guide**: IPC author, FFI author, release maintainer, DevTools and agent author. (4) Add owner and "answered by" milestone columns to 11.1. (5) Shorten the header "Relates to" line to a pointer to the 6.4 map. (6) Add an ATK × TB matrix to 6.2.

JIT tiers need separate binaries on macOS, and the Linux jitless tier can do more.** *Location:* 6.7, SEC-D5. *Problem:* `allow-jit` is a Hardened Runtime entitlement on the executable, not an SBPL rule, so a jitless renderer needs its own helper binary without the entitlement to gain anything. *Change:* State the per-tier helper executables. ## What the spec does well (keep these through revision)

- **The central framing is right and evidence-led.** Risk moves to code Izcal does not own (patch latency and containment) and to logic at boundaries Izcal does own, with V8 measured at 57% and three logic bugs that all escaped the sandbox.
- **IPC rules enforced by the generator** (the [gen] tags). Rules no reviewer must remember is the correct response to the Mojo record, and IPC-R1, R2, R3, R7 and R11 target the real escapes.
- **Using the simulator as an adversarial peer**, with a stated comparison against `cargo-fuzz` and an honest note that there is no precedent.
- **The current-state supply-chain audit** read from the repositories (archive and binding hashes not verified, `SHA256SUMS` detecting only corruption, PR-sourced checker, client-side tag protection). It is concrete, cheap to fix, and prioritized P0, P1 and P2 with costs.
- **Reduced sandbox tiers are visible, never silent** (`izcal://sandbox`), and **pre-opened handles** with no path opening after start-up.
- **Agent entry points, memory and schemes as injection channels**, and the broker checks **parsed** URLs, not strings. Testing with model defenses off is preserved.
- **The protected-media host rules** (no bridge, own process, restart on runtime update, minimum version, label naming whose patch level applies).
- **M-1 discipline** on SBPL, importers, the TUF client and IPC backends. Other browsers appear only as evidence. No owner question asks build versus reuse, and the TUF alternative is resolved by the standing answer.
- **Honest residual-risk statements** per process, and a thorough flagged-claims table (11.2) and cross-spec contradictions list (11.3).
- **Per-process threat models delivered now**, including the seven process kinds Stage 1's list omitted, with a template tied to the generated surface inventory (SEC-26), so the models cannot go stale silently.
