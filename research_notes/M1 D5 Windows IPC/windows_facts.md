**Implications:** No document says that an Untrusted-IL, lockdown-restricted, no-capability AppContainer process can create and connect to its own pipe. Every hint points the other way: the 1709 note, the restricted-token double access check, and the unlabelled-means-Medium rule. A design that needs the sandboxed child to create pipes therefore rests on probes P1–P4. The design that needs no such probe is **broker-created pairs**. The broker calls `CreateNamedPipe` in its own context with a random 128-bit name and `FILE_FLAG_FIRST_PIPE_INSTANCE | PIPE_REJECT_REMOTE_CLIENTS`, sets `nMaxInstances = 1`, and supplies an explicit DACL that grants only the broker's own SID or logon SID. It connects with `CreateFile`, and then duplicates one or both ends into the children. Children request new channels from the broker with a control message. This matches "the broker relays every handle", and it makes the broker the recorded creator of every channel, so "bound sender" ownership is tracked by the broker on the requester's behalf. Use FILE_READ_DATA/FILE_WRITE_DATA, never FILE_GENERIC_WRITE (finding 1.4).

## 2. Message mode, overlapped I/O, buffer-full behaviour

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|

| 2.2 | In message-read mode, a read succeeds only when the whole message has been read. If the buffer is smaller, ReadFile returns FALSE with **ERROR_MORE_DATA**, and later reads (or PeekNamedPipe) return the rest. | — | Type/Read/Wait Modes; ReadFile | 2025 | High |
| 2.3 | A **client handle from CreateFile always starts in byte-read mode**. Switch it with `SetNamedPipeHandleState`, which needs FILE_WRITE_ATTRIBUTES on the handle. | 2.5 | **Buffer sizes are advisory.** The reserved size is the system default, the system minimum or maximum, or the request rounded up to an allocation boundary. GetNamedPipeInfo: "If the buffer size is zero, the buffer is allocated as needed." | — | CreateNamedPipe; GetNamedPipeInfo | 2025 | High |
| 2.6 | **What a write does when the buffer is full.** The system first charges the write against the pipe's write quota. If the quota covers the write, it "completes immediately". So an overlapped write to a full pipe **pends** (returns FALSE with ERROR_IO_PENDING) and completes once the reader drains it. It does not fail. | — | CreateNamedPipe Remarks; WriteFile "Pipes" | 2025 | High (text); exact thresholds **Low** → probe |
| 2.7 | PIPE_NOWAIT (0x1) "is supported for compatibility with Microsoft LAN Manager version 2.0 and should not be used to achieve asynchronous I/O". In other words it reports **success with 0 bytes written**, not an error. | 0x1 | Type/Read/Wait Modes | 2025-04-15 | High |
| 2.8 | A nonblocking empty read returns FALSE with ERROR_NO_DATA. | — | Type/Read/Wait Modes | 2025-04-15 | High |
| 2.9 | A successful read of 0 bytes on a pipe means the peer wrote a zero-length message. | — | ReadFile | 2025-07-22 | High |
| 2.10 | Overlapped ReadFile/WriteFile can fail with ERROR_INVALID_USER_BUFFER or ERROR_NOT_ENOUGH_MEMORY when "too many outstanding asynchronous I/O requests" exist, and with ERROR_NOT_ENOUGH_QUOTA when the buffer cannot be page-locked. A file opened for async I/O "can also behave synchronously". | — | ReadFile; WriteFile | 2025 | High |
| 2.11 | PeekNamedPipe returns total bytes available and the bytes left in the current message without removing data. It is unaffected by wait mode, and on an async handle it does not block. | — | PeekNamedPipe | 2024-02-22 | High |
| 2.12 | GetNamedPipeInfo flags report PIPE_SERVER_END (0x1) or client end (0x0) and PIPE_TYPE_MESSAGE (0x4). | — | GetNamedPipeInfo | 2024-02-22 | High |

**Implications:** The kernel buffer cannot supply the exact `Full` that D3 requires. Buffer sizes are advisory, and a full pipe pends a write rather than refusing it. So capacity must be **credit-counted in user space**, as on Linux: the receiver returns credits when it consumes messages, and the sender refuses with `Full` at exactly N unacknowledged messages. "send never blocks" then follows from overlapped I/O. The IO thread issues at most one overlapped write per pipe and keeps an outbox of encoded messages behind it. A write that returns ERROR_IO_PENDING means "the kernel buffer is full below capacity", which is the outbox case; its completion packet means "drained". PIPE_NOWAIT is not used (Microsoft says not to, and its 0-bytes-written success is easy to misread). Each message is one WriteFile, so boundaries come from the kernel. The receiver posts reads into a 64 KiB + header buffer, and ERROR_MORE_DATA is a protocol violation by the sender (a message larger than the maximum), not a case to handle by reading on. The client end must be switched to PIPE_READMODE_MESSAGE, so the broker must hold FILE_WRITE_ATTRIBUTES while setting the mode and **drop it when it duplicates the end onward** (see §6).

## 3. Close semantics and the "Closed is eventual" window

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | "An instance of a named pipe is always deleted when the last handle to the instance … is closed." "an instance of a named pipe may have more than one handle associated with it." "The pipe exists as long as a server or client process has an open handle". | — | CreateNamedPipe; DisconnectNamedPipe | 2024–2025 | High |
| 3.2 | **Anonymous** pipe: once the write handle is closed, ReadFile returns FALSE with **ERROR_BROKEN_PIPE**. Once the read handle is closed, WriteFile returns FALSE with ERROR_BROKEN_PIPE. ReadFile also returns "if all write handles to the pipe have been closed". | — | ReadFile; WriteFile; Anonymous Pipe Operations | 2025 | High |
| 3.3 | For **named** pipes, the reference pages do not say whether messages queued before the writer closed can still be read, or which error comes after them (ERROR_BROKEN_PIPE, presumably). | — | ReadFile, WriteFile | — | Low → probe |
| 3.4 | **DisconnectNamedPipe** on the server end forces the client end closed, and "any unread data in the pipe is discarded". FlushFileBuffers waits until the client has read everything. | — | DisconnectNamedPipe | 2024-02-22 | High |
| 3.5 | ConnectNamedPipe reports **ERROR_PIPE_CONNECTED** when the client connected between Create and Connect. That counts as a good connection. It reports **ERROR_NO_DATA** if the previous client closed and the server has not disconnected. | — | ConnectNamedPipe | 2024-11-20 | High |
| 3.6 | What the **writer** of a named pipe sees after the reader closes (ERROR_NO_DATA "pipe is being closed", or ERROR_BROKEN_PIPE) is not stated on the reference pages. | — | — | — | Low → probe |
| 3.7 | Inherited and duplicated handles "refer to the same object". An inherited handle "has the same value and access privileges" in the child. | — | Inheritance; Handle Inheritance | 2025 | High |

**Implications:** An end stays open while *any* handle to it exists, in any process, including a copy the broker still holds for relay or a copy inherited into a child. So "Closed" is reported only after the last handle to the peer end closes, and the broker must not keep relay copies longer than the duplication takes. During process creation, an inheritable handle in the broker can be picked up by *any* concurrent `CreateProcess(bInheritHandles=TRUE)` that lacks a handle list. The documented fix is PROC_THREAD_ATTRIBUTE_HANDLE_LIST, but the handle still has to be inheritable. Duplicating into a suspended child (§8) avoids inheritable handles entirely. Never call DisconnectNamedPipe on a channel. It discards unread data, which breaks in-order delivery up to `Closed`. Close with CloseHandle only, and confirm by probe (P9) that CloseHandle does not discard queued data the way Disconnect does.

**Implications:** Windows pipes cannot give D3's "kernel-attested sender identity" per message, and since ends move between processes, connect-time PIDs do not name the current sender either. Use the **broker as the attesting authority**. The broker knows which process it duplicated each end into, because every handle move passes through it (IPC-R1), so it knows the single process that held a sender end when a violation was observed. Holding is not proof of sending, though: the holder could duplicate the end within its own process, but it cannot hand it to another sandboxed process without the broker, since sandboxed processes have no PROCESS_DUP_HANDLE on each other. So "only that sender could have caused it" holds exactly when the broker's ledger shows one holder process for that sender end since the violating message was written. The design needs an end-transfer ledger, plus the rule that the broker never leaves the same end in two processes at once (move = DUPLICATE_CLOSE_SOURCE from the source). Do not depend on ALPC, which is not documented for third-party use.

| 5.6 | **CVE-2025-2783**: a sandboxed renderer sent the value returned by GetCurrentThread (**−2**) through a relay message. | 5.7 | DuplicateHandle: "If hSourceHandle is a pseudo handle returned by GetCurrentProcess or GetCurrentThread, hSourceProcessHandle should be a handle to the process calling DuplicateHandle … DuplicateHandle converts it to a real handle." **Implications:** The broker must not trust any handle value that arrives in a message. A value is only an index into the *source child's* handle table. The broker then:
1. Rejects every value whose top bits make it negative as a pointer-sized integer, and 0. This covers −1, −2 and any other undocumented pseudo-handle without enumerating them (probe P14 checks which small negatives are live).
2. Duplicates the handle **from the child into the broker** with DUPLICATE_SAME_ACCESS. This is the one place SAME_ACCESS is allowed, because the handle stays inside the broker; P15 checks that it never widens access.
3. Classifies the broker-side copy. A channel end must have GetFileType = PIPE, pass GetNamedPipeInfo with the expected flags, and **match one of the broker's own registered pipe ends under CompareObjectHandles**. The last test is the strongest: the broker created every pipe, so it can identify exactly which channel and which end it received, independent of anything the message claims. For a shared-memory section, the NtQueryObject TypeName and GrantedAccess must match.
4. Compares the result with the declared kind.
5. Duplicates onward (§6).

CompareObjectHandles costs one call per registered end, which is linear in the number of ends. The broker can index by an expected channel ID taken from the message and compare just that one, because a mismatch is then a violation.

**Implications:** Onward duplication uses explicit masks and never DUPLICATE_SAME_ACCESS:
- **Receiver end:** FILE_READ_DATA \| SYNCHRONIZE, plus FILE_READ_ATTRIBUTES if the child must call GetNamedPipeInfo or PeekNamedPipe. P16 checks whether ReadFile also needs READ_CONTROL or EA rights.
- **Sender end:** FILE_WRITE_DATA \| SYNCHRONIZE only. No FILE_APPEND_DATA, because that value is also CREATE_PIPE_INSTANCE.
- Neither end gets FILE_WRITE_ATTRIBUTES. The broker sets PIPE_READMODE_MESSAGE before handing an end over, so the child cannot change the mode or switch the end to NOWAIT.
- **Section:** FILE_MAP_READ only.

Use DUPLICATE_CLOSE_SOURCE when pulling from the sender, so the end moves rather than being copied. Because that flag closes the source even on error, the pull is irreversible, and a failure must be reported as a closed or violated end, never retried. Never give a child a process handle carrying PROCESS_DUP_HANDLE (finding 6.2).

**Implications:** There are two documented routes.
- **(a) Handle list:** create the two ends inheritable, list them in PROC_THREAD_ATTRIBUTE_HANDLE_LIST, and pass the two values on the command line. FP-M0 used this route for one handle.
- **(b) Duplicate into a suspended child:** create the child with CREATE_SUSPENDED and no inheritable handles, DuplicateHandle the two ends into it with explicit narrowed masks, write the two values into the child (on the command line is impossible after creation, so they go into a small bootstrap message on the already-inherited stdout pipe), then ResumeThread.

Route (b) avoids inheritable handles in the broker entirely, and with them the concurrent-CreateProcess leak window, and it applies narrowed masks at the first hop, which route (a) cannot do because inheritance copies access. A hybrid is the minimum change from FP-M0: inherit only a single bootstrap pipe through the handle list, then hand all channel ends over that pipe using the normal relay path. Probe P21 checks that DuplicateHandle into a suspended AppContainer child succeeds before the process has initialized.

**Implications:** Turn on strict handle checks in **sandboxed children**, so a forged or stale handle value is a crash rather than a silent failure. Whether to turn them on in the **broker** needs thought: the broker deliberately calls DuplicateHandle with *child-supplied* values whose source is the child's table, and P26 must show whether a bad value in the *source* process raises in the broker. The **FSCTL disable policy needs a probe (P27) before use**, because pipe mode changes and ConnectNamedPipe may be FSCTLs underneath. **Summary for the design.**
1. **Broker-created pairs are confirmed.** A child cannot create global pipes (P1). It can create pipes in its own AppContainer namespace (P2, P3), but nothing requires that.
2. **Close semantics match Linux.** Queued data survives the writer's close; a write after the reader closes gives 232 (ERROR_NO_DATA); a write pending at close reports *success*.
3. **GetNamedPipeClientProcessId is connect-time only**, so the end-transfer ledger is required.
4. **The pseudo-handle filter must reject every value ≤ 0**, including −1 (P14).
5. **Every object handed to a child needs an explicit DACL** (P23/P24). An unnamed section has no SD and is widenable by its holder.
6. **Strict handle checks** are safe in the broker (P26) and already on in the children (P26x).
7. **The FSCTL policy is harmless to the transport** (P27).

**Unresolved:** the P12 two-thread race (only the deterministic form was run); which launch ingredient turns strict handle checks on in the child; behaviour from an interactive session-1 broker with the real filtered token; why an unlabelled pipe with an AC ACE was writable by an Untrusted child (P5).

**Round-2 summary for the design.**
- **Move protocol (W3) is the sharpest result:** an end must be moved only after the source has cancelled and drained its outstanding I/O. DUPLICATE_CLOSE_SOURCE alone lets the old holder keep stealing messages.
- **Ledger keys (W2, W5, W1):** mask the low two bits of any child-supplied handle value; key on the pipe name and the server/client bit; HandleCount gives a cross-process check that no extra copy survives a move.
- **One AppContainer SID per child (W4)**, created ahead of time (~5 ms each), or siblings can reach each other's pipes directly.
- **Bootstrap over one inherited pipe (W7) and batched handoff (W6)** are confirmed cheap and leak-free.
