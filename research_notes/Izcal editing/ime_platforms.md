## 1. The core tension: who asks whom, and when

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | The four platforms split into two models. **Pull (synchronous query)**: TSF and `NSTextInputClient` let the input method ask the text store for text, selection and rectangles at any moment and expect an answer before the call returns. **Push (client-reported state)**: Wayland text-input-v3 never queries; the client sends surrounding text, cursor rectangle and content type, and the compositor replies with events stamped by a serial. **Android** is a pull model across a process boundary: the IME calls `InputConnection` over IPC, and the platform already tolerates a slow editor ("given a couple seconds", then `null`). | 2 pull, 1 push, 1 cross-process pull | Rows 2.1–2.4, 5.1, 6.1, 7.1–7.2 | 2026-10-20 | High |
| 1.2 | **Offset units differ per platform.** Wayland offsets are **UTF-8 bytes**; Android lengths are "in code unit" (Java UTF-16); Cocoa `NSRange` and TSF ACPs are UTF-16 positions. A renderer-side text model must convert all three without drift, especially around surrogate pairs (Android warns IMEs "not to delete only half of a surrogate pair"). | 3 unit systems | [text-input-v3](https://wayland.app/protocols/text-input-unstable-v3); [InputConnection](https://developer.android.com/reference/android/view/inputmethod/InputConnection) | fetched 2026-10-20 | High (Wayland, Android); Medium (TSF, Cocoa UTF-16: well known, not re-checked) |
| 1.3 | Mozilla answers synchronous IME queries in the browser process from a **cache pushed by the content process**; Chromium's documented Mac design (c. 2010) instead blocked the UI thread on a **timed wait of up to 1.5 s** for the renderer's answer. Neither lets the browser block indefinitely on a renderer (corrected after the fact-check) | — | Section 4 | 2013–2026 | High |

**Implications:** Izcal's IPC should be push-first everywhere: the renderer publishes a versioned **text-input snapshot** (text window, selection, composition range, rectangles) to the broker, and the broker answers pull-model OS queries from it. Section 4 shows what goes wrong at the edges.

**Implications:** a broker-side text store can satisfy TSF from a cached snapshot: read locks served from the cache, write locks turned into typed edit requests to the renderer, and `TS_E_SYNCHRONOUS` or `TS_E_NOLAYOUT` as the honest answers when the cache is stale. Section 4 shows that `TS_E_NOLAYOUT` is where IMEs misbehave. Because TIP DLLs load into the broker, every third-party TIP is code running in Izcal's most privileged process (section 10).

## 4. How out-of-process browsers answered synchronous queries (prose and bug-title evidence)

| # | Finding | Numbers | Source | Date | Conf. |

## 6. Linux: Wayland text-input, input methods, IBus and Fcitx

| # | Finding | Numbers | Source | Date | Conf. |

## Implications for Izcal

1. **One push-first protocol on every OS.** The renderer owns a per-focused-editable **text-input snapshot**: a bounded text window around the selection (Wayland caps at 4000 bytes; Android trims; Mozilla's whole-text cache was "too big"), selection, composition range, caret rect, per-character rects for the composition and a margin around it, editor bounds, content type, and a **version**. The broker answers TSF, Cocoa and Android queries from it. Model the IPC on text-input-v3: double-buffered state, versioned batches, and the 7-step apply order (rows 6.1–6.3).
2. **Stale-answer policy, per OS.** TSF: serve read locks from the snapshot; return `TS_E_NOLAYOUT` only for ranges outside the cached rects, then send `OnLayoutChange` when the renderer catches up. Never return it right after notifying a layout change (Mozilla 1187351). Cocoa: answer from the snapshot and call `invalidateCharacterCoordinates()` / `textInputClientDidUpdateSelection()` on update. Android: forward asynchronously with a budget well under "a couple seconds". No unbounded broker wait on a renderer, ever.
3. **Hold OS notifications until the renderer acks** every composition and selection event the broker sent (Mozilla ContentCache, row 4.3). That is what keeps the snapshot from contradicting the IME.
4. **Edits are requests, not writes.** IME commits, deletions and replacements travel to the renderer as typed edit requests with the snapshot version they were based on. The renderer turns them into `beforeinput`/`input` (DM 6.5) and replies with a new snapshot. Forced commit and cancel are emulated in the renderer (row 4.4).
5. **Offsets in one internal unit** with exact UTF-8 and UTF-16 conversion at the broker edge, tested on astral characters and grapheme clusters (row 1.2).
6. **Secret fields** (password, `autocomplete=one-time-code`, private mode): Windows: no TSF context (`IS_PASSWORD` is invalid); macOS: secure event input on focus and off on blur, Roman-only `allowedInputSourceLocales`; Android: web-password type plus `IME_FLAG_NO_PERSONALIZED_LEARNING`; Wayland: purpose `password` with `sensitive_data` and `hidden_text`. Private tabs set the "no learning" signals for all fields. AI writing tools (macOS Writing Tools, Android API 36) are off by default (B10).
7. **IME code isolation.** TIP DLLs run in whatever process hosts TSF (row 2.9), and CTF showed the framework itself is a cross-process attack surface (10.1). Inventory TIPs (TX-D23), and test whether TSF can be hosted in a separate low-rights input process that owns the focused HWND.
8. **Device matrix and harness from day one**: the frame's IME matrix plus Samsung, AOSP-based keyboards and Heliboard on Android (row 7.8), and ATOK, Japanist and Sogou on Windows (rows 4.5, 4.7).

## Open questions (black-box measurements)

1. **TSF hosting**: can a TSF thread manager and text store live in a separate low-rights process that owns the focused child HWND, with the broker owning the top-level window? Measure the TIP behaviour and candidate placement.
2. **Snapshot size**: what text window do common TIPs, Cocoa input methods, Gboard and Fcitx/Rime actually request (reconversion, prediction)? Log `GetText`/`attributedSubstring`/`getTextBeforeCursor` ranges per IME against a test page.
3. **Query frequency**: how many synchronous queries per keystroke do MS-IME Japanese, Microsoft Pinyin, Kotoeri and Apple Pinyin make? This sets the cache-hit target.
4. **Latency budget**: keystroke-to-paint and IME round trip (OS → broker → renderer → broker → OS) in Chrome, Firefox and Safari, by camera or a USB-injecting rig (Dan Luu method), idle and under main-thread load.
5. **`TS_E_NOLAYOUT` today**: which current TIPs still misplace candidate windows on `TS_E_NOLAYOUT` on Windows 11 24H2/25H2? (Mozilla's last bug is from 2020.)
6. **What Chrome and Firefox send** for private windows on each OS (`IME_FLAG_NO_PERSONALIZED_LEARNING`, `IS_PRIVATE`, `sensitive_data`): observe with a logging IME or the OS's IME debug tools, not source.
7. **macOS timeout**: how long will the Cocoa text input system wait on a slow `firstRect`/`attributedSubstring` before the UI is flagged as hung? Measure with an instrumented test app.
8. **Writing Tools on an `NSTextInputClient`-only view** without `NSWritingToolsCoordinator`: what text, if any, does macOS 15+ read?
9. **text-input-v3 v2 adoption**: do GTK and Qt already bind v2, and how do IBus and Fcitx use `preedit_hint` and `language`? Test on Mutter 51 and KWin 6.7.
10. **AltGr and dead keys** on Windows: record the `WM_*` sequence for AltGr+key and dead-key combinations on 5 European layouts and compare with WPT `uievents` expectations.
