# Izcal editing: specifications and semantics

Compiled 20 October 2026. Primary sources were preferred: the W3C TR and editor's drafts and the WHATWG HTML living standard (all downloaded on 2026-10-20 and searched as text), MDN browser-compat-data 8.1.6 (timestamp 2026-10-15), wpt.fyi run summaries (aligned stable runs of 2026-10-19), the Interop dashboard data, and prose discussion in spec and standards-position issue trackers.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known fact not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked this session.

**M-1 note.** This note uses no code from any engine or other project. No code files, headers, diffs, code reviews or source browsers were opened, whether from Chromium, Gecko, WebKit, Servo, Ladybird, an editor framework, a spellchecker or an IME framework. One web search result was a WebKit commit page ("Support (insertFrom|deleteBy)Composition … inputTypes"); it was not opened and is not cited. Under the owner rule update (HGBA-2 2.3.3) this note also cites no commits. To date when the Input Events composition inputTypes were removed, it compares two published spec versions (the 2019-05-30 WD and the 2026-10-15 WD). Only the commit titles of the w3c/input-events spec repository were listed, to find which versions to compare, and none of them is cited. Implementation status comes from MDN browser-compat-data (CC0 data), the browser columns in the WHATWG spec, standards-position issues (prose) and WPT results (black-box). Where only engine source would settle a behaviour, it is listed under "Open questions".

**Method notes**
- The specs were fetched as HTML and converted to text with pandoc. ReSpec editor's drafts (Input Events, EditContext, Selection) render on the client, so the TR versions, which are pre-rendered, were used for quotes. Each TR and its ED were checked to have the same normative text for the rows cited.
- **WPT numbers were computed this session.** They come from the wpt.fyi `summary_v2` files of the aligned stable runs on 2026-10-19 (Chrome 155.0.8059.84, Firefox 158.0, Safari 27.0, all on the same WPT revision `0f26972422`). The "test score" is the mean over tests of the fraction of subtests passed (Interop-style), and a reftest or crashtest counts 1 for PASS or OK. A test that a browser did not run counts 0 for that browser. "All-pass" counts tests that pass completely. The directory scores are this researcher's arithmetic, not a wpt.fyi dashboard figure. Firefox and Safari scores in `html/editing/dnd/` and `virtual-keyboard/` partly reflect test automation (testdriver drag actions, Chromium-only APIs), not only the feature.
- Only 5 web searches were used. Everything else was fetched directly: spec URLs, the GitHub REST API for issue prose, unpkg for BCD, and storage.googleapis.com for WPT summaries.

## 1. Selection API

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **One selection per document, one range.** "Every document with a browsing context has a unique selection associated with it." "This one selection must be shared by all the content of the document (though not by nested documents), including any editing hosts in the document." "Each selection can be associated with a single range." The spec says it "follows non-Gecko engines in restricting selections to at most one range". It explains that `removeRange()`/`getRangeAt(index)` are leftovers of Netscape's multi-range design and that "multi-range selections proved to be an unpleasant corner case". | ≤1 range | [Selection API WD](https://www.w3.org/TR/selection-api/) §2, notes after §4 | 2026-06-11 | High |
| 1.2 | **The caret is defined only when collapsed.** "When the selection is not collapsed, this specification does not define the caret position; user agents should follow platform conventions." The spec also never says how the caret is drawn or where it goes at line wraps or bidi boundaries. Open issues [#32](https://github.com/w3c/selection-api/issues/32) ("tell if the caret is displayed at the beginning or the end of the line", 2014, updated 2025-09-12), [#51](https://github.com/w3c/selection-api/issues/51) (affinity argument for `collapse`, updated 2025-09-18) and [#57](https://github.com/w3c/selection-api/issues/57) (expose the caret's bidi level) show that **caret affinity is unspecified and not exposed**. | 3 open issues | Same §2; issue titles | 2014–2025 | High |
| 1.3 | **Direction** is forwards, backwards or directionless. A user selection is "directionless if the start and the end cannot be ordered due to the platform convention". `direction` returns `"none"`/`"forward"`/`"backward"`. It is new API: Chrome 137, Firefox 126, Safari 17. | 3 states | Same §2, §6; BCD `api.Selection.direction` | 2026 | High |
| 1.4 | **`modify(alter, direction, granularity)` is now specified, but only as a hook.** It takes direction values `forward`/`backward`/`left`/`right` and granularities `character`, `word`, `sentence`, `line`, `paragraph`, `lineboundary`, `sentenceboundary`, `paragraphboundary`, `documentboundary`. `left`/`right` map through "the resolved text direction at this selection's focus" (the UAX #9 embedding level), and "at a bidi boundary … user agents may use additional context (such as caret affinity …)". The movement itself is "as if the user had requested to extend/move selection by granularity", and a note says "**We need to more precisely define what it means to extend or move selection by each granularity.**" Open issues [#179](https://github.com/w3c/selection-api/issues/179) (`paragraphboundary`), [#175](https://github.com/w3c/selection-api/issues/175) and [#346](https://github.com/w3c/selection-api/issues/346) (optional arguments). | 9 granularities | Same §4 `modify()`; issue titles | 2026-06-11 | High |
| 1.5 | **`getComposedRanges({shadowRoots})`** returns at most one `StaticRange`. Each endpoint inside a shadow tree that is not listed is re-scoped to the host's parent: the start goes to the host's index, the end to the index + 1. It is static and never live. The selection's anchor and focus "need not to be in the document tree. It could be in a shadow tree", but `getRangeAt` throws and `anchorNode` returns null when that happens. Shipping: Safari 17, Chrome 137, Firefox 142. | 1 StaticRange | Same §4; BCD | 2026 | High |
| 1.6 | **`selectionchange` on text controls.** Each Document, `input` and `textarea` has a "has scheduled selectionchange event" flag (a coalescing bit). A text-control selection change schedules the event **on the element**, and it bubbles. A document selection change schedules it on the document, and it does not bubble. Both use the user-interaction task source. The spec does not say whether a text-control change also notifies the document. Shipping on elements: Firefox 92, Chrome 127, Safari 18. | 1 coalescing flag per target | Same §6.2; BCD | 2026 | High |
| 1.7 | `selectstart` fires (bubbles, cancelable) only when a new range replaces an **empty or collapsed** selection. A user action must never empty a non-empty selection ("e.g. clicking on a non-editable region"). The privacy section allows emulating mouse and keyboard events so that AT-driven selection is not detectable. | — | Same §6.1, §6, privacy | 2026-06-11 | High |
| 1.8 | `containsNode` depends on "visually equivalent" boundary points, which the spec does not define. The stringifier returns "the concatenation of the rendered text". Both depend on layout, outside the spec. | — | Same §4 | 2026-06-11 | High |
| 1.9 | WPT `selection/` (193 tests): Chrome 94.3%, Firefox 94.2%, Safari 80.0%. `selection/shadow-dom/` (23 tests): Chrome 99.5%, Firefox 90.6%, Safari 66.9%. Subtests total 34,420, mostly generated `addRange`/`collapse` permutations. | see text | wpt.fyi summaries, computed | 2026-10-19 | High |

**Implications:** Izcal's caret model (affinity, bidi level, visual or logical movement for each granularity) must be its own spec text. The Selection API only gives the hook (`modify`) and the data model. `selectionchange` coalescing per target is cheap and should be one bit per target, as specified.

**Implications:** Izcal should implement Level 2 as it reads today: a single non-cancelable `insertCompositionText` and cancelable everything else, with code-point target ranges. It should resolve the UI Events order conflict in favour of Input Events L2, which matches the Chromium/Firefox behaviour the WPT tests encode (to be confirmed by measurement, see the open questions). The stale `typing` state should be filed upstream rather than implemented.

## 3. EditContext

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Model.** An `EditContext` holds text (a string), selection start and end, a composition range, control bounds, selection bounds and character bounds (`characterBoundsRangeStart` plus `DOMRect`s). Authors push state with `updateText`, `updateSelection`, `updateControlBounds`, `updateSelectionBounds` and `updateCharacterBounds`. The UA fires `textupdate`, `textformatupdate` (IME decoration: underline style and thickness per range), `characterboundsupdate` (the IME asks for rects for a range), `compositionstart` and `compositionend` **at the EditContext**, not at the element. | 5 update methods, 5 events | [EditContext WD](https://www.w3.org/TR/edit-context/) §1–4 | 2026-09-10 | High |
| 3.2 | **Which elements.** The `editContext` setter throws `NotSupportedError` unless the element's local name is "a valid shadow host name" or `canvas`. An element can have at most one EditContext. The element becomes an *EditContext editing host* only if its parent is not editable. If both contenteditable and EditContext are set, "the EditContext behavior 'wins'". An EditContext "keeps its associated element alive". | shadow-host names + canvas | Same §1.2, §5 setter steps | 2026-09-10 | High |
| 3.3 | **What the UA still does and what it stops.** It still does focus, caret navigation and selection inside a DOM host, key events and `beforeinput`. Which positions to cache is platform-dependent ("Different platforms may require different positions to be cached"). | — | Same §1.2.1, §1.2.4 | 2026-09-10 | High |
| 3.5 | **Accessibility is the author's job.** The EditContext text "is not exposed to assistive technologies", so the editor "must also render its contents in an accessible format to the DOM". | 3.6 | **Implementation status.** Chromium only, since 121 (Chrome and Chrome Android). Firefox and Safari: no. EditContext was **not selected** for Interop 2025 (#819). | 1 of 3 engines | BCD; [WebKit/standards-positions#243](https://github.com/WebKit/standards-positions/issues/243); [interop#819](https://github.com/web-platform-tests/interop/issues/819) | 2024–2026 | High |

**Implications:** EditContext is the cleanest boundary between Izcal's IME broker (TX-D23) and an author's editor: plain text, offsets, rects, and IME decoration as data. It is single-engine and its accessibility story is weak. Izcal can implement it as a thin surface over the same renderer-side text-input state that contenteditable and text controls use. It should not become the core model.

## Implications for Izcal

1. **The spec gaps are concentrated, and Izcal must close them in its own spec text:** caret position for non-collapsed selections and affinity (1.2); `modify()` movement per granularity (1.4); contenteditable behaviour, which HTML delegates to an unofficial draft (4.2, 5.1); undo history scope and the effect of script `.value` on it (4.10); clipboard "sanitized copy" (6.5); DnD filtering (8.3); highlight overlay geometry and caret stacking (7.3, 7.8).
2. **Pick the Input Events L2 composition model** (one non-cancelable `insertCompositionText`, everything else cancelable, code-point target ranges) and file the UI Events order conflict (2.10) and the stale `typing` state (2.5) upstream.
3. **Clipboard policy:** sanitize `text/html` from other origins through the one parser plus ST's `SanitizingSink`; re-encode images on write in the media process; gate reads on a broker-drawn paste affordance plus transient activation (the spec's current read rule); and decide the `unsanitized` option deliberately (Chrome yes, Firefox defaults to unsanitized, Safari concerned).
4. **DnD protected mode = I-1:** only types and kinds cross into renderers the drag passes over; data goes only to the drop target's renderer after a user-ended drop.
5. **Spellcheck results must be invisible to script, including through timing** (7.4 is normative). This supports C-22's "results invisible to script" goal and constrains how spell marks are painted (no layout effect, no observable timing).
6. **WPT targets for "best shipping engine":** `editing/` ≈ 90.5% (Chrome), `editing/run/` 96.0% (Firefox), `selection/` 94.3%, `input-events/` 81.8%, `clipboard-apis/` 95.4%, `edit-context/` 74.8%, `css-highlight-api/` 92.9%, `html/editing/` 93.0% (all Chrome except as noted; 2026-10-19). The Chrome-only scores on dnd and virtual-keyboard partly reflect automation support.
7. **EditContext** is worth implementing as a thin view onto the same text-input state used by text controls and contenteditable. It should not be the core model (single engine; accessibility concerns from Mozilla).

## Open questions (black-box measurements)

1. In Chrome, Firefox and Safari, which order does a real IME produce: `compositionupdate`/`beforeinput`/`input`, or the UI Events order? Is `beforeinput` `insertCompositionText` cancelable in practice? Measure with Microsoft Pinyin, Kotoeri, IBus-Anthy and Gboard.
2. Undo after script `.value =` in `input`/`textarea`: does the native stack clear, merge or survive, per engine? Does `execCommand('insertText')` create one undo step per call or coalesce?
3. Does `historyUndo` `beforeinput` fire with an empty native stack in any engine? Does it fire for Edit-menu undo versus Ctrl+Z versus `execCommand('undo')` (w3c/editing#504)?
4. Clipboard HTML sanitization per engine: which elements and attributes survive `copy` → `paste` across origins (`<script>`, `on*`, `javascript:`, `<style>`, `<meta>`, comments, `<input type=hidden>`)? Do Firefox and Safari re-encode PNG on `write()`?
5. `selectionDirection` and `Selection.direction` after Shift+arrow on macOS versus Windows versus Linux; check against HTML's platform text (4.8).
6. Caret affinity at soft wraps and bidi boundaries: where each engine draws the caret after End and Home and after clicking past the line end. Inputs for TX's movement rules.
7. Which `inputType`s each engine actually emits for platform gestures (Option+Backspace = `deleteWordBackward`; Cmd+Backspace = `deleteSoftLineBackward` or `deleteHardLineBackward`?; Emacs Ctrl+K/Ctrl+Y = `insertFromYank`; Ctrl+T = `insertTranspose`).
8. `getTargetRanges()` for Backspace over a multi-code-point grapheme ("é" decomposed, emoji ZWJ sequences, Devanagari conjuncts) per engine, against the L2 code-point rule.
