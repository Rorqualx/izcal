# Izcal editing: gaps and opportunities

Compiled 20 October 2026. Primary sources were preferred (survey result pages, specifications, editor-framework documentation in prose, maintainers' forum posts, issue-tracker titles and prose discussion, standards-position threads, OS and browser vendor documentation).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, a count whose query could miss items, or a well-known fact not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no source code of any project was opened or cited. No code files, headers, commits, diffs or code reviews of Chromium, Gecko, WebKit, ProseMirror, Lexical, Slate, CodeMirror, CKEditor, Tiptap, VS Code/Monaco, Playwright, Puppeteer, browser-use, rrweb or NVDA were read. Only these were used: prose READMEs and documentation pages (Lexical `testing.md`, `faq.md` and the `@lexical/dragon` README; Slate `faq.md`; the `prosemirror-dev-tools`, Lexical DevTools and rrweb READMEs); issue and forum **titles and prose posts**, with code blocks stripped before reading (ProseMirror discuss topics 3810, 1823 and 5246 were fetched as JSON and every `<pre>` block was replaced with "[code omitted]"); standards-position threads; and specifications. The Chrome DevTools Protocol `browser_protocol.json` was read only for the Input domain's command names, parameter names and descriptions. It is the published interface definition of the protocol, which the brief counts as an interface specification. MDN browser-compat-data JSON files (CC0 data) were read for version numbers. The Playwright issue #5777 body links a Chromium mojom file, which was not opened.

**Method notes**
- **Web search was not available.** The session-wide WebSearch budget was already spent when this strand started; the one search attempted returned nothing. All rows come from known primary URLs fetched directly, the GitHub REST API (issue search by title and label, issue and comment bodies), the Bugzilla REST API, and the ProseMirror Discourse JSON API (`/search.json`, `/t/<id>.json`). These are the trackers' own query interfaces, the same kind of title query the brief asks for, not general search engines.
- **Issue counts** (section 2) are GitHub search `total_count` values fetched on 2026-10-20, "is:issue" with the term **in the title** or with the named label. Title search misses issues that do not name the term in the title, and Slate closes stale issues in bulk, so open counts are lower bounds on live problems. A first run of the Slate title query hit GitHub's search rate limit, and the rerun returned only the open count.
- **State of HTML** numbers come from the published result pages (2023, 2024, 2025). The pages hide some rows behind "Show all", so features or pain points that are absent may be hidden rather than missing. Where a row was not visible, it is not reported.
- Could not fetch: Medium's "Why ContentEditable is Terrible" (HTTP 403); Chrome's blog post on unsanitized async-clipboard HTML (404 at the guessed URL); the CKEditor 5 "future of rich text editing" post (404). No row depends on them.

## Implications for Izcal

1. Make every editing input a typed B1 record that carries the full IME payload (composition string, clauses and attributes, selection, replacement range, commit or cancel), not just the resulting text. Replay and the virtual IME (11.1, 11.2) depend on it, and nothing else on the web offers it.
2. Expose a **virtual IME** in Izcal's automation protocol and push the same shape to WebDriver BiDi. That also gives Izcal's own WPT-style IME tests, which no engine can write today (4.4).
3. Ship an **edit explainer** and **undo-stack view** in DevTools, built on the mutation log and spec anchors, and keep them in recordings.
4. Mediate the clipboard in the broker with a visible per-origin **write and read log** and a command-like-content warning. ClickFix shows the cost of silence.
5. Give agents, extensions and AT one sanctioned edit channel that produces trusted `beforeinput`/`input` with target ranges and is labelled by principal. Never let them edit through DOM surgery.
6. Expose native spelling and grammar marks to AT through the semantic plane, and keep them invisible to script.
7. Design find in page with diacritics, regex and whole-word options and shadow-tree coverage from the start.
8. Treat EditContext as a one-engine API whose accessibility burden falls on authors. If it is implemented, ship the inspector with it.
