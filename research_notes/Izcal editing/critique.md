# Izcal editing: design critique

*Phase 8 independent design critique of `reports/Izcal editing.md` draft 0.1 (20 October 2026), by a critic who did not write the spec or its research notes. Date: 20 October 2026. Read against: the first-principles-spec method and its references; the phase 2c brief (binding owner direction); HGBA-2 2.3.3 (M-1 parts 1–4, I-1, D1, OD-7); HGBA-3 (B1, B9, B10, DET-1, PRIV-2); DOM, bindings and event loop 0.2 (6.2 rules 1–3, 6.5, 6.6, 6.7 decision-point register, 6.12, 6.17, G90–G99, DM-D15, DM-D20); accessibility 0.2.1 (6.8–6.12, AX-D9, G106, staffing 9.3); fonts and text 0.3.4 (6.1, 6.8a, TX-D14, TX-D23, TX-D25, TX-16, 9.3, 9.5 R6); graphics and rendering (6.3, 6.8, 6.9, 6.27, GR-D5); layout 0.4 (LY-D10 and its two exceptions, LY-D11, LY-D13, 6.14, 6.15); parsing and style (6.5 `SanitizingSink`, G22, G23, ST-8); resource footprint 0.4 (FP-25, FP-D13); DevTools (6.5); shell UI design (UI-10, R11, R17); PDF (G114, PD 6.x AcroForm, 6.19 boundary); content blocking (6.2, `hg-cb-compile`); JavaScript engine (JS-D15); Phase 3 ledger (G-16, C-22, A-S1-75, A-H3-22). Model: `research_notes/Izcal accessibility/critique.md`. No third-party source code was opened for this critique.*

**Counts: 41 findings: 6 High, 18 Medium, 17 Low.** Plus 9 engine-source and licence items and 20 reconciliation items below.

The spec is strong on history, on the threat record, on the clipboard's broker-only design and on M-1 hygiene in the notes. Its central idea (one typed edit intent, one engine, a versioned broker-mediated boundary) is sound. Its weak points are where the idea meets real protocols: **the IME mirror has no model of the input method's own pending writes**, which is exactly the class of bug the notes document (IM 4.6); **the "no script inside an edit" claim ignores the DOM steps that run script after insertion** (custom element reactions, post-connection steps), which an edit that inserts nodes triggers; **the spelling engine is said to be a pure function of recorded inputs but returns on a worker thread at an unrecorded time**; and **the spelling privacy rule has three bypasses** (script-written words after one keystroke, autocorrect, and tab or element self-capture). The rest are fixable precision, enforceability and reconciliation gaps.

| 1 | **High** | **"No script runs between `beforeinput` returning and `input` being queued" is false for edits that insert nodes.** `InsertNode` (paste, drop, `insertHTML`, `insertParagraph` cloning, `formatBlock`) runs DOM insertion. DM 6.1 splits insertion into a script-free core phase and a **post phase** that "may run script" (post-connection steps, e.g. `iframe` loading), and `[CEReactions]` reactions (custom element `connectedCallback`, `attributeChangedCallback`) run when the reaction scope ends. G140 says the transaction holds `CoreGuard` throughout, so either these steps are skipped (an HTML conformance bug: custom elements pasted into an editor never connect) or they run inside the transaction (the UAF class the spec exists to close). The spec never mentions reactions, post-connection steps, or Trusted Types for `insertHTML` (HP 1.10 notes Chrome and Safari enforce it). | 6.3, 6.2 pipeline, G140, ED-10 | DM 6.1 phases 1–2; DM 6.6 (reactions stack); HTML CEReactions | Define the transaction as **core phase only**: apply all operations under `CoreGuard`, collect post-connection steps and the reaction queue, end the transaction (selection, undo entry, `TextEdit` records), then run the post phase and reactions as **one declared script point** before `input` is queued; revalidate the selection by id after it. | 2 | **High** | **The IME mirror cannot serve an input method's reads of its own pending writes, and its TSF lock semantics are wrong.** Rule 4 makes every write a request answered later; rule 2 answers every read from "the latest snapshot". Against a mirror that has not seen the write, each read contradicts the IME's own edit.
