## 2. Input Events: `beforeinput`, and the composition dispute

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Why it exists:** to let authors see an edit's *intent* (`inputType`) and cancel it before the browser mutates the DOM, so frameworks can apply edits to their own model. Level 2's rule: "all beforeinput events apart from those being emited within an IME composition process are cancelable". `insertCompositionText` is not cancelable; `historyUndo`/`historyRedo` are cancelable, with empty `getTargetRanges()` and null `data`/`dataTransfer`. | — | [Input Events Level 2 ED](https://w3c.github.io/input-events/) | fetched 2026-10-20 | High |
| 2.2 | **The split (~2017-02):** "the Android team objected to an impedance mismatch" (proposal by Alexandre Elias of Chromium). "Shortly before 2017-02, Apple implemented both Level 1 and 2; shortly after 2017-02, Google implemented only Level 1." In 2018 Wilm said Chromium "did not have anyone responsible for contenteditable at the time" and could not commit to Level 2. | 2 levels | [w3c/input-events #78](https://github.com/w3c/input-events/issues/78) (discussion) | 2018-02-03 | High (as reported in the issue) |
| 2.3 | **The technical root:** an IME on Android (and elsewhere) keeps its own copy of the text around the caret and commits on its own schedule. If the page cancels the commit, the IME's and the page's text diverge. Microsoft's Bo Cupp later put it: "The challenge as I see it isn't in implementing the events, but in supporting a relocatable selection when composition starts." | — | [w3c/input-events #122](https://github.com/w3c/input-events/pull/122) discussion | 2021-10-15 | High (quote); Medium (Android generalisation) |
| 2.4 | **Firefox:** Mozilla shipped `beforeinput` only in **Firefox 87** (2021-03), following Level 1, because "Level 2 is still unstable around event order with composition events"; Mozilla did not plan Level 2 "due to concerns about backwards compatibility with existing IME software" (issue #86: `beforeinput` before `compositionstart` breaks old expectations). | Chrome 60, Safari 10.1, Firefox 87 | BCD; [Bugzilla 1447239](https://bugzilla.mozilla.org/show_bug.cgi?id=1447239) (snippet); [#78 comment 2019-06-24](https://github.com/w3c/input-events/issues/78) | 2019–2021 | High (versions); Medium (bug text via snippet) |
| 2.5 | **Effect on frameworks:** Slate's author: "Level 1 is not really useful for IME-based editing … Safari (on desktop and mobile) works beautifully for compositions because of the presence of the Level 2 [commit-time] input type … Right now Chrome is degraded with no easy way to fix things." | — | [#78 comment](https://github.com/w3c/input-events/issues/78) | 2019-12-18 | High |
| 2.6 | **Resolution by deletion:** Microsoft (Bo Cupp) proposed in PR #122 (2021-09-09) to eliminate `insertFromComposition`, `deleteByComposition` and `deleteCompositionText`, leaving composition as `compositionstart` → (`compositionupdate`, `beforeinput insertCompositionText`, `input`)* → `compositionend`. Wilm objected (WebKit had implemented them; they "solve a fundamental problem of containerizing IME input") and asked that they be optional; the PR was closed 2022-03-11. The current ED defines none of the three types. | 3 types removed | [PR #122 discussion](https://github.com/w3c/input-events/pull/122); [ED](https://w3c.github.io/input-events/) | 2021-09 to 2022-03 | High (proposal, ED text); Medium (that the removal came from this PR) |
| 2.7 | **Status today:** Level 1 is a W3C **Discontinued Draft** (2023-09-28): "no longer intended to advance or to be maintained". Level 2 is a Working Draft (latest TR 2026-10-15, corrected after the fact-check) in the Web Editing WG; its ED now carries EditContext notes for `getTargetRanges()`. Open issues remain on composition (e.g. #176, 2025-09: `insertCompositionText` cannot tell the commit event from in-progress events). | — | [Input Events Level 1 TR](https://www.w3.org/TR/input-events-1/); [Level 2 TR](https://www.w3.org/TR/input-events-2/); [issue #176](https://github.com/w3c/input-events/issues/176) | 2023-09-28; 2025 | High |

**Implications:** The composition fight is a mismatch between a *synchronous, cancelable DOM event* model and an *IME that owns its own text buffer in another process*. No amount of event naming fixes it; only an API where the IME's buffer is first-class (EditContext's `text`, `updateText`) does. Izcal's IME protocol with the broker (TX-D23) should be built around a shared text-buffer model, with `beforeinput` derived from it, not the reverse.

**Implications:** EditContext is the only standards-track design whose model matches how OS text services actually work (a text buffer, a selection, character bounds), and it is where the editing TF's decade of work ended. But it is single-engine, its accessibility story for canvas is unsolved, and its first adopters logged a stream of implementation bugs. Izcal should design its internal editing model as an EditContext-shaped buffer (so EditContext is nearly free to expose) and treat the canvas-accessibility gap (3.5) as a requirement, not an afterthought.

**Implications:** The web's editing customers voted with their architecture: model–view separation, intent events, and reconciliation. Izcal's job is to be a good input source (accurate `beforeinput`, stable composition, accurate caret geometry, EditContext) and a good view host, more than to have a clever DOM-mutating command engine.

## 10. Technology mismatches: assumptions that no longer hold

| # | Assumption baked in (era) | Why it no longer holds | Evidence |
|---|---|---|---|
| 10.1 | **The DOM is the document model** (IE 5.5, 2000) | Every serious editor keeps its own model and treats the DOM or canvas as a view | 4.3–4.11 |
| 10.2 | **One engine's behaviour is the spec** (IE, then WebKit for `plaintext-only`) | Copies were "haphazard and imprecise"; `plaintext-only` took ~15 years to reach Firefox | 1.1, 1.9 |
| 10.3 | **Input is a desktop keyboard; keys map to edits** (keyCode era) | IMEs, Android soft keyboards, autocorrect, dictation and handwriting commit text asynchronously from their own buffers; cancelling breaks them | 2.2–2.6, 4.5 |
| 10.4 | **Events are synchronous and cancelable** | The IME lives outside the page (another process, often another app); Level 2 cancelation could not be implemented on Android | 2.2, 2.3 |
| 10.5 | **Single process, synchronous clipboard** (`execCommand`, `clipboardData`) | Clipboard is OS-owned, cross-app and needs consent UI; async API replaced it | 5.4–5.6 |
| 10.6 | **Clipboard content is trusted** | Silent reads (iOS apps), hijacking writes, native-decoder RCE risk drove gestures, prompts, sanitizing and the `web ` prefix | 5.2, 5.7, 5.9 |
| 10.7 | **Browser undo serves editors** | Useless once the editor intercepts any edit | 8.2 |
| 10.8 | **Text services can be a cloud call** | Password leakage via Enhanced Spell Check | 9.6 |
| 10.9 | **Rendering text and receiving text are one thing** | Canvas editors (Docs) and EditContext separate them; AT and OS text services still assume they are joined | 3.5, 3.9, 4.9 |

## Implications for Izcal

1. **Model the edit target as a text buffer, not a DOM.** Make Izcal's internal editing core an EditContext-shaped buffer (text, selection, composition range, character bounds) that `<input>`, `<textarea>`, `contentEditable` and EditContext all map onto; the broker's IME protocol (TX-D23) speaks only this buffer (rows 2.3, 3.1–3.3, 10.4).
2. **Ship EditContext**, but treat Mozilla's accessibility objection (3.5) as a design input: require a way to tie AT-visible nodes to rendered geometry for canvas editors, or document the gap.
3. **`beforeinput`:** implement Level 2 with non-cancelable composition, matching the current ED's single `insertCompositionText` sequence; do not reintroduce the three removed types (2.6).
4. **`contentEditable`/`execCommand`:** compatibility work against WPT and the execCommand draft; no innovation there (1.4, 1.10).
5. **Clipboard:** gesture for writes, broker-shown per-paste consent for cross-origin reads (Firefox/Safari model), sanitization by the one parser, `web ` custom formats with a per-session cap, no raw native formats (5.5–5.8).
6. **Undo:** built-in stack for text controls and plain `contentEditable`; a page-declared undo state for frameworks; no DOM-transaction recorder (8.1–8.3).
7. **Spellcheck and text services stay on-device;** never through a cloud service; script cannot read results (9.6).
8. **Android** needs its own test matrix from day one; it is where every framework's bug list concentrates (4.5).

## Open questions (black-box measurements)

1. How Chrome, Firefox and Safari group typed characters into undo steps in `contentEditable` and `textarea` (time-based? word-based?), measured by scripted typing and `historyUndo` counts.
2. Exact composition event order per engine and OS for a fixed IME script (Microsoft Pinyin, Kotoeri, IBus-Anthy, Gboard), compared with the Level 2 ED sequence.
3. Whether Google Docs uses EditContext in Chrome today (observable by feature-detecting `editContext` on its input element).
4. Whether Chrome's Windows text input uses TSF on all supported Windows versions (observable via the touch keyboard and emoji panel behaviour), and when it switched (needs a prose source).
5. When Chrome and Edge began using the Windows spellchecker and on which Windows versions (needs a prose source; black-box: compare suggestions with the OS's).
6. Chrome's persistent `clipboard-read` permission vs Firefox/Safari per-paste UI: measure which reads succeed without UI after a first grant, cross-origin vs same-origin.
7. WPT pass rates for `editing/`, `input-events/`, `edit-context/`, `clipboard-apis/` per engine (wpt.fyi), to set Izcal's targets.
