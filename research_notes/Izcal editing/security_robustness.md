# Izcal editing: security and robustness

Compiled 20 October 2026. Primary sources were preferred (the NVD database, Bugzilla metadata, vendor release notes and security advisories, specifications, OS vendor documentation, security researchers' write-ups, papers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a count whose method has a known bias (stated); **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no source code of any project was opened for this note. No code files, headers, commits, diffs, code reviews or source browsers of Chromium, Gecko, WebKit, Hunspell, wasm2c/RLBox, IBus, Fcitx, Sogou or any rich-text editor were opened. NVD descriptions that name a source file (for example `editing/markup.cpp`, `EditingStyle.cpp`) are quoted as CVE text only; no file was opened. Mozilla evidence uses bug **titles and metadata** from the Bugzilla REST API; no bug body, patch or attachment was opened. The Chromium "Post-Spectre Threat Model Re-Think" is a prose markdown document and was read as prose. Hunspell's own repository was not opened (not even the README). Where only source code would state a value (undo-stack depth, paste size limits, nesting limits, IME update throttles), the value is listed under "Open questions" for a black-box measurement.

**Method notes**
- The session-wide web-search budget ran out after **2 searches** by this researcher (the shared cap of 200 was hit by other agents). Everything else was checked by fetching known primary pages directly: NVD API, Bugzilla REST, mozilla.org advisories, chromereleases.googleblog.com, projectzero.google, citizenlab.ca, microsoft.com security blog, proofpoint.com, welivesecurity.com, marektoth.com, xsleaks.dev, w3c.github.io, wicg.github.io, html.spec.whatwg.org, developer.mozilla.org, developer.chrome.com, developer.apple.com, developer.android.com, learn.microsoft.com, usenix.org, mysk.blog, github.com READMEs.
- **CVE counts were computed this session** from the NVD 2.0 API (`keywordSearch`, all words must appear), fetched 20 October 2026, then filtered by regular expression on the English description. Chrome adopted the "*Bug class* in *Component* in Google Chrome" description format around 2018; older Chrome CVEs often say only "Use-after-free … related to …", and Apple's WebKit descriptions almost never name the editing component. **All NVD counts are lower bounds.**
- **Mozilla security-bug counts** come from the Bugzilla REST API, product Core, by component, keywords `sec-critical|sec-high|sec-moderate|sec-low`, fetched 20 October 2026. Only bugs public today are counted.
- **Not fetchable:** Michał Bentkowski's original write-up (`research.securitum.com/the-curious-case-of-copy-paste/` now redirects to the company home page) and the Daily Swig coverage (redirects to PortSwigger's home page); Krzysztof Kotowicz's 2011 blog post (connection closed twice); the otto-js disclosure (page now a product landing page). Rows that depend on them use the vendor advisories and Bugzilla titles instead, or are graded Medium/Low.
- **2026 counts look inflated.** Chrome CVE descriptions with component names show a surge in 2026 (46 of 89 Autofill CVEs, all 7 "in Editing" CVEs). The accessibility note saw the same surge. Read per-year trends with care; the cause (for example AI-assisted bug finding) was not checked this session.

**Implications:** In shipping engines, editing and selection are a memory-safety bug farm (Firefox: 40 of 74 Editor+Selection security bugs are UAFs) because edit code holds positions across script and layout re-entry. Rust removes the UAF class but not the logic class: a stale `EditorDOMPoint` becomes a wrong edit or a panic instead of a UAF. Izcal's editing commands should take no script re-entry mid-command (queue events, run them after the edit commits) and validate every held position after any point that can run script. The 2026 Chrome editing CVEs are all **information leaks**, which Rust does not prevent.

**Implications:** Paste is untrusted cross-origin HTML entering an editing host. CSS inside pasted `<style>` and SVG are the historically broken parts and need explicit test corpora. Pasted content must never fire handlers or fetch resources before or during sanitization.

## Implications for Izcal

1. **No script inside an edit.** Editing commands run to completion before any page script (`beforeinput` before, `input`/`selectionchange`/mutation records after). Every held position is revalidated after any point that can run script or layout. This is the root cause of the Firefox Editor/Selection UAF record (1.1–1.4) and still matters in Rust (logic errors, panics).
2. **Broker-owned clipboard and drag data**, renderers see types only until a user-ended paste/drop on their own frame; broker hit-tests the drop target; drag images, file names and outgoing types from a renderer are hostile (2.10, 4.1–4.7).
3. **Clipboard reads only through a broker-drawn Paste element** (Firefox/Safari model, with the 1 s enable delay), no persistent `clipboard-read` permission (2.7, 2.8). **Clipboard writes are logged and inspectable** in the broker; consider a visible "this site put text on your clipboard" indicator, and for text that looks like a shell command written without a copy gesture, a stronger cue (ClickFix, 2.2–2.5). Write must require a broker-minted transient activation (DM-D20).
4. **Paste = sanitized tree, not string.** Pasted HTML goes through the one parser with `SanitizingSink` and is inserted as a tree; no re-serialize/re-parse; `<style>` CSS and SVG get dedicated adversarial corpora; nothing fires or fetches during sanitization (3.1–3.7).
5. **Password fields:** disable text services on Windows, Secure Event Input on macOS while focused, `IME_FLAG_NO_PERSONALIZED_LEARNING` on Android; spellcheck off for any field that is or was `type=password`; same for private windows (5.7–5.9, 6.5).
6. **Spellchecker** is Izcal's own Rust code, offline only, outside the renderer behind a typed interface whose counts and offsets are validated (6.1–6.4).
7. **Find and text fragments** answer per frame, top-level only, with no observable early exit (7.1–7.3).
8. **Autofill UI is broker UI**, never in page DOM; fill only after a broker gesture; refuse fills into fields the broker judges invisible (8.1–8.3).
9. **Input timing:** per-renderer input queues in the broker; coarsened `Event.timeStamp` (9.2, 9.4).
10. **Explicit limits** on paste size, tree depth, undo depth, IME rate, each with an observable failure mode (10.4).

## Open questions (black-box measurements to make)

1. Paste size and depth: largest `text/plain` and `text/html` paste each shipping engine accepts, time to insert, and the nesting depth at which pasted HTML is flattened or rejected (WPT-style harness with synthetic clipboard contents).
2. Undo-stack depth and memory per engine for `contenteditable` and `textarea` (type N edits, count undo steps).
3. Whether Chrome, Firefox and Safari strip or keep `<style>`, SVG, `<math>`, comments and hidden inputs on cross-origin paste today (Bentkowski's 2020 vectors re-run as black-box tests).
4. Whether any shipping browser warns on clipboard writes without a copy gesture or on shell-command-like text (ClickFix); behaviour of `writeText` from a cross-origin iframe with and without Permissions-Policy.
5. Whether `window.find()` and find-in-page reveal cross-origin iframe matches through focus, scroll, timing or selection changes.
6. Which spellcheck and IME settings each engine applies to `type=password`, to fields toggled from password to text, and in private windows (observe TSF input scope, `IsSecureEventInputEnabled`, Android `imeOptions` with OS tools).
7. Rate of IME composition updates an engine tolerates before dropping or coalescing, and behaviour under a hostile IME (fuzzed TSF/`NSTextInputClient` ranges).
8. Keystroke-timing observability across sites in the same browser (Loophole-style probe against Izcal's broker input path).
9. Hunspell OSS-Fuzz issue count and the Project Zero 0-day sheet / ZDI Pwn2Own records for editing bugs (needs search budget).
