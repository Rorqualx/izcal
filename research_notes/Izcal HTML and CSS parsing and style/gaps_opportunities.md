# Izcal HTML and CSS parsing and style: gaps and opportunities

Compiled 19 October 2026. Primary sources were preferred (surveys' own result pages, specifications, engine and DevTools source, protocol definitions, release notes, issue trackers, papers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Provenance note (phase 8, 19 October 2026).** The design critique ([critique.md](critique.md), finding 1) found that HGBA-2 M-1 parts 2–4 do not allow engine source files as evidence, even for constants or comments. Rows below whose source is an engine source file (a `.h`, `.cc`, `.cpp`, `.rs`, `.ts`, `.java`, `.json5` or `.toml` file in an engine's or browser project's repository) are kept as a record of what was read, but **must not be used as design input or as a number**: the report `reports/Izcal HTML and CSS parsing and style.md` (draft 0.2) cites none of them and replaces them with published sources, black-box tests planned at ST-M0, or † values. Published documentation (design documents, READMEs), bug trackers, commit messages, blogs and papers remain usable evidence.

**Scope.** This strand covers phase 3 of the first-principles-spec method for HTML parsing, CSS parsing, selectors, cascade, computed values and invalidation: what developers struggle with, what engines and tools keep invisible, which construction and verification approaches the evidence supports, and what an engine Izcal owns could do that no shipping engine does. Each section ends with what Izcal could expose or do, tied to the capabilities in `.claude/skills/first-principles-spec/references/izcal-capabilities.md` (deterministic substrate B1, mutation log with old values B4 / Stage 1 design 5.4, from-scratch reference path B5, spec anchors ANC-1 / G9, own UI renderer D-S11).

**Relation to other notes.** The DevTools strand already covers page-level tooling gaps: [invisible_gaps.md](../Izcal%20DevTools%20spec/invisible_gaps.md) (**[IG n]**), [visualization_ux.md](../Izcal%20DevTools%20spec/visualization_ux.md) (**[VU n]**), [protocols_standards.md](../Izcal%20DevTools%20spec/protocols_standards.md) (**[PS n]**). This note does not repeat them. It adds the **style-engine layer**: what only the parser and style system know (invalidation sets, parser recovery decisions, cascade steps), how other engines build these parts, and the formal and incremental research that applies. The DevTools spec 0.3 already plans why-queries (DT-D3), a Style domain (M3) and a contingent cascade explainer (Q-DT-4). With the style system now Izcal's own (M-1), Q-DT-4 is answered: the explainer is the cascade itself, not a separate model.

**M-1 note.** Everything here is evidence: ideas, numbers and the reasons behind other engines' choices. Engine source (Stylo, Blink, Chrome DevTools frontend, Ladybird, Gecko's parser translator) was read only to verify claims about how those systems are organised; nothing is a template, and no code from them may be copied, ported or translated (HGBA-2 M-1, Stage 1 design D-S10). Other engines remain black-box differential signals only (M-1 part 4).

Izcal's cascade can record, per element and property, every candidate declaration and the criterion that eliminated it (Section 4), and link that criterion to its CSS Cascade step through spec anchors.

**Implications:** today's tools expose either cost (selector stats) or a capped list of invalidations from an experiment, and the protocol forces the frontend to re-derive the cascade. Izcal can do what none does:
- **Cascade trace as engine output.** The cascade records, for each (element, property), the ordered candidates and the criterion (origin/importance, context, style attribute, layer, specificity, scope proximity, order) that eliminated each one. The Styles pane renders it; no second cascade exists. Requirement: the explainer is the production cascade on the reference path (B5), and a test checks its winner equals the computed value on every element.
- **Restyle causality from the mutation log.** Every restyled element points to the B4 mutation (with old value) and the selector or invalidation-set entry that dirtied it; over-invalidation becomes measurable ("restyled, no property changed") because the from-scratch reference shows which recomputes were needed. Run the expensive probes on a B1 replay, so they cost nothing in the live page ([IG 16] lesson on "(slow)" probes).

## 4. Cascade semantics that are easy to get wrong

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | Cascade sort order (descending): origin and importance; context (shadow encapsulation); style attribute; **layers**; **specificity**; **scope proximity**; order of appearance. Specificity is compared **before** scope proximity, so a more specific unscoped rule beats a closer scoped one | 7 criteria | [CSS Cascade 6 WD](https://www.w3.org/TR/css-cascade-6/) §2.1 | 2024-09-06 | High |
| 4.2 | Layer order **reverses** for `!important` (earlier layers win), and inner-context `!important` beats outer. Each reversal is a separate surprise for developers | — | same | 2024-09-06 | High |
| 4.3 | Cascade 6 is an "Exploratory Working Draft" and tells implementers to use Level 5; `@scope` semantics come from Level 6 | — | same | 2024-09-06 | High |
| 4.4 | Free-form requests for features that exist (nesting, parent selector, scoping) and "many complaints about the cascade" (1.3–1.4) show that the rules are learned by trial and error | — | 1.3–1.4 | 2024–2025 | Medium (interpretation) |

**Implications:** a cascade explanation must name the **criterion** ("lost on layer order: `@layer base` is before `@layer theme`", "lost on specificity before scope proximity was considered") with the spec step, since the counter-intuitive cases are exactly the ordering rules. Izcal's spec anchors (ANC-1) make this a lookup: each comparison in the cascade carries the anchor of the CSS Cascade step it implements, pinned to a revision (M-1 part 2).

**Implications:** every engine converged on **generating property boilerplate from a data table**, and each table is a private dialect mixing spec facts (syntax, initial, inherited) with engine facts (storage group, invalidation scope, `affects`). The spec facts now exist upstream in webref. Izcal can do something no engine does: a build step that **imports webref's `syntax`, `initial`, `inherited`, `animationType`, `longhands` and `href`** at a pinned version (spec anchor by construction, M-1 part 2), overlays an Izcal-owned file for engine facts and for the computed-value rules webref leaves as prose, and **fails the build** when webref and the overlay disagree. The 169 computed-value texts are small enough to classify by hand into a closed set of computed-value kinds. For HTML, the precedent (Gecko's translator, Taylor's OCaml model) supports writing the tokenizer state machine as **data plus a generator** with one `// spec:` anchor per state, and an emitted parse-decision log (Section 5). Using webref data as input is spec data, not browser code, so it is M-1-clean; using CSSTree or any other parser as a dependency is not.

**Implications:** two research results become product features in an engine that owns its selector representation. (1) **Static selector analysis**: with selectors as a typed IR, Izcal can answer "can this rule ever match in this document?" (unused-CSS that is sound for the current DOM plus recorded mutations, not a coverage guess), "which elements could this rule affect?" and "do these two selectors overlap?" (the 7.4 reduction is NP-complete in general, so expose it as a bounded, budgeted query with an "unknown" answer). (2) **Style as a checked function**: computed style = f(rules, element state, parent style, container sizes); the B5 from-scratch reference turns every incremental restyle into a testable claim, which no shipping engine runs in CI. The research gap in 7.8 is an opportunity and a risk: Izcal would be first, so INC-style targets for restyle must be measured, not assumed.

## 8. Determinism and replay of style

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | **rr** gets determinism by emulating a single core: parallel programs pay the single-core slowdown, "an inherent feature of the design"; Firefox test suites record at ≤ 1.2× | ≤ 1.2× | [rr-project.org](https://rr-project.org/) | read 2026-10-19 | High |
| 8.2 | **Replay.io** relies on browsers being "largely deterministic" and on "effective determinism", which allows some behaviour to vary on replay; the post does not discuss style or layout | — | [How Replay works](https://www.replay.io/blog/how-replay-works) | read 2026-10-19 | Medium |
| 8.3 | **Stylo's style-sharing cache is per thread**: an LRU of 32 candidates (`SHARING_CACHE_SIZE`) stored in thread-local context, up to 8 levels. Which elements share a `ComputedValues` allocation therefore depends on how the parallel traversal splits work across threads; the values are equal, the sharing (pointer identity, memory) is not. A `DISABLE_STYLE_SHARING_CACHE` switch exists | 32 entries; 8 levels | [Stylo sharing/mod.rs](https://github.com/servo/stylo/blob/main/style/sharing/mod.rs); [context.rs](https://github.com/servo/stylo/blob/main/style/context.rs) | read 2026-10-19 | High (code read); consequence is inference |
| 8.4 | Correctness of sharing rests on an invariant the code comments call "very important": any selector that could distinguish two candidates that pass the up-front checks must be in the "revalidation selectors" set. A missed one is a silent wrong-style bug | — | same | read 2026-10-19 | High |
| 8.5 | Izcal's Stage 1 design 3.3 already requires that the style-sharing cache must not make results depend on thread assignment (phase purity) | — | frame.md | 2026-10-19 | High |

**Implications:** value-equality is not enough for Izcal: DET-1 hashes, FP-11 memory budgets and "discard and rebuild bit-identical" all observe sharing. The opportunity is a sharing scheme whose **sharing decisions are a deterministic function of the tree** (for example, keyed by a content hash of the cascade inputs and resolved in a fixed order after the parallel phase), so parallel equals sequential **including memory layout**. The 8.4 invariant should become a checked property: the from-scratch reference path with sharing disabled must produce identical computed values on every CI frame.

**Implications:** agents need **answers, not dumps**: "which properties differ from initial/inherited on these nodes, and why" is a few hundred bytes from a cascade trace (Section 3), and a per-node style diff between two execution points falls out of B4 + B1. User styles are an accessibility feature with a dead UI: Izcal can support the **user origin as a first-class, per-site and global, capability-scoped style sheet** edited in its own UI (D-S11), loaded from memory with no startup I/O (the reason Firefox gave in 9.4), and shown in the cascade trace as "user origin". This also gives forced-colours-style and reduced-motion overrides a principled home in the cascade.

## 11. Lessons learned

| Project | What happened | Lesson | How Izcal applies it |
|---|---|---|---|
| Chrome DevTools cascade in TypeScript (3.9) | The protocol gives rules, not outcomes, so the frontend re-implements the cascade | Explanations computed outside the engine drift from it | The engine emits the cascade trace; the UI only renders it |
| Chrome invalidation tracking (3.3–3.4) | Exists for years as an experiment, capped at 20 events, two style reasons | Causality bolted onto a conservative invalidator yields little | Record causes in the mutation log and reference path from the start |
| Firefox View Source parse errors (5.2) | Shows some errors in a view few open; tree-builder text errors omitted | Parser data needs a place in the normal workflow | Put parse decisions on the element in the inspector and in why-queries |
| Gecko Java→C++ translator; Blink json5; Stylo TOML (6.1–6.7) | Everyone generates parser and property code, from private sources | Generation is right; private, unanchored inputs are the weakness | Generate from spec data (webref) plus an Izcal overlay; fail the build on disagreement |
| Stylo per-thread sharing cache (8.3–8.4) | Equal values, thread-dependent sharing; correctness rests on a manual invariant | Sharing must be deterministic and checked | Deterministic sharing keys; CI compares with sharing disabled |
| User style sheets (9.3–9.4) | Removed in Chrome; spec requirement deleted; Firefox gated for startup I/O | The feature died of UI and I/O cost, not semantics | Keep the user origin; serve it from memory with a real UI |
| Cassius, SatCSS, Hague et al. (7.1–7.4) | Sound CSS analyses stayed research tools outside browsers | Analyses need the engine's own data and a user surface | Typed selector IR exposes bounded static queries in DevTools |

## 12. Unverified and open items

- **Chrome's "First invalidated" field** on Recalculate Style events: not found in documentation; whether Blink emits more style-recalc reasons than the frontend's two-value enum (3.4) was not checked in Blink source.
- **WebKit Web Inspector**: whether it shows style invalidation causes or parse errors was not checked (search budget exhausted).
- **`:has()` invalidation cost**: WebKit says it built ":has-specific caching and filtering" ([WebKit blog](https://webkit.org/blog/13096/css-has-pseudo-class/)); no tool reporting per-rule `:has()` invalidation cost was found, but Chrome's invalidation count column (3.2) may partly cover it.
- **Chrome user stylesheet removal**: version 33 comes from the CSSWG issue, not a Chrome announcement.
- **Meyerovich 2010, Medea 2023, Cassius/VizAssert venues and numbers**: from abstracts or search snippets only.
- **Johns and Klein 2024**: venue not stated on the page read.
- **Processing instructions in HTML**: html5lib-tests added PI tokenizer tests (2026-10-01) and the WPT tree format describes PI nodes; whether the HTML standard now creates PI nodes in HTML documents, and since when, must be checked against the pinned HTML revision before the spec relies on it.
- **9.2 size estimate** is a † order-of-magnitude figure, not a measurement; measure CDP `getComputedStyleForNode` payloads on corpus pages if a target depends on it.
- **Open, unmeasured**: the cost of recording a full cascade trace per element (memory and time) on corpus pages; whether deterministic sharing keys lose sharing hit rate against a per-thread LRU; the share of restyles that change no property (over-invalidation) in Izcal's design.
