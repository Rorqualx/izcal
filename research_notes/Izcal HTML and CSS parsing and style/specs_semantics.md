# Izcal HTML and CSS parsing and style: specifications and semantics

Compiled 19 October 2026. Primary sources were preferred (specifications at their current editor's drafts or living standards, WPT, spec issue trackers). Counts marked "counted" were computed by this researcher from the primary file named in the row, on the date given. Spec text was read from the published multipage HTML Standard (`html.spec.whatwg.org/multipage/`, built from whatwg/html commit [`26f733f9`](https://github.com/whatwg/html/commit/26f733f9) of 19 October 2026) and the CSSWG editor's drafts at `drafts.csswg.org` (dates per spec below). Every `#fragment` cited for the HTML Standard was checked against its published [`fragment-links.json`](https://html.spec.whatwg.org/multipage/fragment-links.json); every CSS fragment was checked against the downloaded draft.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, issue title or status data, or a claim not checked in the spec text itself; **Low** = secondary source only.

**Provenance note (updated 0.3.1, 19 October 2026).** HGBA-2 2.3.1 M-1 part 3: another engine's source code (code files, headers, commits, diffs, code reviews) is never evidence. At phase 8 the rows read from engine source files were only marked; in the 0.3.1 source-evidence pass they were **replaced** by published prose (documentation, bug-tracker discussion, blogs, papers, mailing lists), **turned into black-box measurements** planned at ST-M0, or **removed**. The per-row log is [source_evidence_pass.md](source_evidence_pass.md). Prose design documents hosted in a repository (for example a `docs/*.md` page or a README) remain usable; commit messages and code reviews do not.

M-1 note: the specifications, WPT, html5lib-tests and spec-derived data (the HTML Standard's `entities.json`, `@webref/css`, the W3C property index, webstatus.dev and wpt.fyi results) are oracles and data, not engine code. Engine behaviour reported here (for example the 512-element depth cap) is a black-box fact to be observed, recorded so Izcal's differential tests can expect it. It is not a design template. Recent whatwg/html commits are cited because the parser changed a great deal in 2025–2026; the spec anchors for Izcal (M-1 part 2) must therefore pin a whatwg/html **commit**, not "the living standard".

**Implications:** the decoder sits in front of the tokenizer and can restart the whole parse once (a navigation). The ~9-step sniffing order is a deterministic function of headers, bytes and the parent document; Izcal's locale default is a B1 input that must be recorded.

## 3. Re-entrancy: scripts, `document.write`, `document.open` and custom elements

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **The tree builder is re-entrant.** "While the tree construction stage is handling one token, the tokenizer might be resumed." Control state: the parser's **script nesting level** (starts at 0), the **parser pause flag**, and the **insertion point** (where `document.write` text goes; can be "undefined"). At a `</script>` the parser saves the old insertion point, increments the nesting level, prepares the script (which "might cause the tokenizer to output more tokens, resulting in a reentrant invocation"), decrements the level, and clears the pause flag when the level returns to 0. **Implications:** the parser calls into JS at three points (script end tags, custom element constructors and callbacks, microtask checkpoints), and JS can call back into the parser (`document.write`) or mutate the tree the parser holds pointers into. In Izcal the tree builder must hold **node IDs with generation checks** (JS-D4's 32-bit slot plus generation), never raw references, across every call-out, and must re-validate its insertion target after every call-out, as the 2026 spec text now requires. A recursion cap for `document.write` is Izcal's choice and must be recorded as a deviation.

**Implications:** the computed-value phase is no longer "look up and convert". Izcal should treat that interpreter as a component with its own spec anchors and fuzz target. The property table (~760 entries plus types and functions) should be generated from spec-extracted data, used as data (allowed by M-1), with every grammar anchored to its spec.
