# Izcal HTML and CSS parsing and style: history and postmortems

Compiled 19 October 2026. Primary sources were preferred (specifications and their W3C history pages, maintainers' blog posts, commit messages read from the commits themselves, Bugzilla and WebKit Bugzilla records read through their REST APIs, Chromium code reviews, in-tree design documents, and source-file doc comments). Shipping versions come from the MDN browser-compat-data file (`@mdn/browser-compat-data` 8.1.6, built 2026-10-15) and its browser release table.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a summary of a primary source that could not be read in full, or a vendor claim without data; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

**Provenance note (phase 8, 19 October 2026).** The design critique ([critique.md](critique.md), finding 1) found that HGBA-2 M-1 parts 2–4 do not allow engine source files as evidence, even for constants or comments. Rows below whose source is an engine source file (a `.h`, `.cc`, `.cpp`, `.rs`, `.ts`, `.java`, `.json5` or `.toml` file in an engine's or browser project's repository) are kept as a record of what was read, but **must not be used as design input or as a number**: the report `reports/Izcal HTML and CSS parsing and style.md` (draft 0.2) cites none of them and replaces them with published sources, black-box tests planned at ST-M0, or † values. Published documentation (design documents, READMEs), bug trackers, commit messages, blogs and papers remain usable evidence.

M-1 note: ideas, measurements and reasons only; no code and no design template from any engine. Where this note says what an engine "does", that is evidence to reason from, not a shape to copy. Source files were read only for their prose (doc comments, commit messages, README text).

## 1. HTML parsing before and after the HTML5 algorithm

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Before HTML5, no specification said how to turn bytes into a DOM. HTML was nominally SGML, but parsing of invalid documents (most of the web) was undefined, and some SGML constructs were never implemented. Browser developers **reverse-engineered the market leader** (Mosaic, then Netscape, then IE) when in doubt, which produced "unwritten common rules" and divergent behaviour. | — | [Sivonen, "Firefox 4: the HTML5 parser" (Mozilla Hacks)](https://hacks.mozilla.org/2010/05/firefox-4-the-html5-parser-inline-svg-speed-and-more/) | 2010-05 | High |
| 1.2 | The HTML5 algorithm took its **tokenizer closer to IE's** (sites had been tested against IE's tokenizer, the majority browser) and its **tree builder closer to WebKit's** ("the most reasonable tree building solution prior to HTML5"). The approach survived 16 years, but every change crosses two languages and a custom translator. | — | [Firefox `parser/html/java/README.txt`](https://github.com/mozilla-firefox/firefox/blob/main/parser/html/java/README.txt); [validator/htmlparser](https://github.com/validator/htmlparser) | read 2026-10-19 | High |

**Implications:** A complete, error-handling parsing algorithm plus a shared test corpus (html5lib-tests) is what ended fifteen years of reverse-engineering. Izcal should implement the WHATWG algorithm directly from the spec text in Rust, with html5lib-tests and WPT as oracles, and should not introduce a second source language or translator: Gecko's Java route worked but costs every maintainer a cross-language round trip.

## 2. Speculative, threaded and incremental parsing

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **The preload scanner** (WebKit, Antti Koivisto): "Parsing can't proceed before the script is fully loaded and executed", so "a series of script tags essentially loads serially". When a script blocks the main parser, a **side parser** scans the rest of the source for resources to fetch, and scripts and stylesheets are prioritized over images. | WSJ front page with 50 ms added latency: 6.3 s → 3.5 s; at 512 kbit/s: 23.8 s → 17.9 s | [WebKit blog, "Optimizing Page Loading in the Web Browser"](https://webkit.org/blog/166/optimizing-page-loading-in-web-browser/) | 2008-03-23 | High |
| 2.2 | **IE8** downloaded scripts in parallel while keeping execution order, and raised connections per host from 2 to 6. (The post does not describe IE8's lookahead mechanism.) | 2 → 6 connections per host | [Souders, "IE8 speeds things up"](https://www.stevesouders.com/blog/2008/03/10/ie8-speeds-things-up/) | 2008-03-10 | High |
| 2.3 | **Gecko off-main-thread parsing** (2010): the HTML5 parser "parses network streams off the main thread", which Sivonen attributed to the new code base being more maintainable than the old one. | 2.5 | **WebKit/Chromium threaded HTML parser** (Adam Barth meta bug, 2013-01-04). Two hoped-for gains: a more responsive main thread, and faster loads from doing other work in parallel. | 2.8 | **Blink deleted the background HTML parser** on 2022-02-02 (Mason Freed): ForceSynchronousHTMLParsing had been on by default since M96 (Finch M96–M98, in code from M99), so "the background html parser and all of its associated machinery is no longer being used". Blink parsed in the background for about 8 years (2013–2021). | M96 = Chrome 96, 2021-11-15 | [Chromium commit 4dbb35444daf](https://github.com/chromium/chromium/commit/4dbb35444daf) | 2022-02-02 | High |
| 2.9 | **innerHTML fast path** (Chrome, 2023): "`innerHTML` is a very common way of updating the DOM via JavaScript so we added specialized fast paths for parsing"; WebKit adopted the approach too. Later extended to `DOMParser` for a further 1% on Speedometer 3. The motive was benchmark weight: in Speedometer 2.1 innerHTML took ~14% of time, in Speedometer 3.0 ~4.5%. | 14% → 4.5% of Speedometer time; +1% from the DOMParser extension | [Chromium blog 2023-04-13](https://blog.chromium.org/2023/04/more-ways-were-making-chrome-faster.html); [2024-03-11](https://blog.chromium.org/2024/03/speedometer-3-building-benchmark-that.html); [2024-06-06](https://blog.chromium.org/2024/06/how-chrome-achieved-highest-score-ever.html) | 2023–24 | High |

**Implications:** Moving the whole parser off the main thread paid 8–14% in 2013 on a single-core-bound phone, but Blink later judged the cross-thread machinery (simulation, checkpoints, rewind on `document.write`) not worth it compared with a budgeted, yielding parser on the main thread. Izcal should measure both before choosing. What survived everywhere is the **preload scanner**, which does not have to be right to be useful. Fragment parsing (innerHTML, DOMParser) is hot enough to justify a dedicated fast path. That path must match the general algorithm exactly, so it needs a differential oracle.

## 3. `document.write`

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | The HTML standard calls `document.write` behaviour idiosyncratic: it can insert into the parser stream, clear the page as if `document.open()` were called, be ignored, or throw, and can depend on **network latency**. "For all these reasons, use of this method is strongly discouraged." The spec now states: "User agents are explicitly allowed to avoid executing script elements inserted via this method." | — | [HTML §8.4 Dynamic markup insertion](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html) | read 2026-10-19 | High |
| 3.2 | The standard has two counters for re-entrancy: an **ignore-destructive-writes counter** (so external scripts cannot use `document.write` to blow away the document through an implicit `open()`), and a **throw-on-dynamic-markup-insertion counter** (so custom element constructors run by the parser cannot call `open`/`write`/`close`). | — | [HTML §8.4](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html) | read 2026-10-19 | High |
| 3.3 | **Chrome's 2016 intervention** (Paul Kinlan): from Chrome 55 (warnings from Chrome 53), Chrome skips a `document.write`-inserted script only when **all** hold: the user is on 2G; top-level document; parser-blocking script; not same site; not in the HTTP cache; not a reload. | Field trial 28 days, 1% of stable users on 2G: 7.6% of 2G page loads had such a script; those pages were "typically twice as slow"; blocking gave +10% loads reaching FCP, +25% reaching fully parsed, −10% reloads, mean FCP −21% (>1 s), mean parse time −38% (~6 s) | [Chrome blog, "Intervening against document.write()"](https://developer.chrome.com/blog/removing-document-write) | 2016-08 | High |
| 3.4 | `document.write` is the main reason parser speculation fails (2.4) and why threaded parsers needed rewind machinery (2.6). It is also a classic re-entrancy surface: script runs inside the parser, which then resumes on mutated state. | — | Sections 2.4, 2.6 | — | High (mechanism) |

**Implications:** Izcal must implement `document.write` exactly, including both counters, but should treat it as a **recorded decision point** (JS-D15): whether a write-inserted script runs, and where speculation restarts, must be B1 inputs. The spec's explicit permission to skip such scripts gives Izcal room for an intervention policy. That policy has to be a deterministic, recorded input, never a hidden network heuristic.

## 4. CSS parsing: from bison grammars to CSS Syntax 3

Gecko used a hand-written scanner and parser. | — | [Firefox Style System Overview](https://firefox-source-docs.mozilla.org/layout/StyleSystemOverview.html); WebKit commits citing `css/CSSGrammar.y.in` (2013) | — | Medium |

In October 2026 it is still a Candidate Recommendation Draft (latest 10 October 2026). | — | [W3C history](https://www.w3.org/standards/history/css-syntax-3/); [CSS Syntax 3 ED §1.1](https://drafts.csswg.org/css-syntax-3/) | 2013, 2026 | High |

| 4.5 | **WebKit adopted Blink's parser:** a preference for "new CSS parsing" was added 2016-08-23 (bug 161095), tokenization landed 2016-08-24, and the new parser was turned on 2016-12-06 (bug 165213), closing the 2010 meta bug after six years. WebKit's `CSSTokenizer.cpp` today carries "Copyright 2015 The Chromium Authors" above Apple's line, so the parser was ported from Blink. | 6 years from meta bug to switch | [WebKit bug 161095](https://bugs.webkit.org/show_bug.cgi?id=161095); [bug 161174](https://bugs.webkit.org/show_bug.cgi?id=161174); [bug 165213](https://bugs.webkit.org/show_bug.cgi?id=165213); [WebKit CSSTokenizer.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/css/parser/CSSTokenizer.cpp) | 2016 | High |

| 4.7 | **Grammar changes still reach the parser:** relaxed CSS nesting (Chrome 120) depended on a parser technique. **Implications:** Error recovery is the part of CSS parsing that matters most, and generated grammars got it wrong; every engine now follows the Syntax 3 algorithm by hand. Izcal should implement Syntax 3 directly and keep the generic layer (tokens, blocks, rules, declarations) separate from the per-property value grammars, so that changes like nesting's restart rule touch one place. The CSSWG still edits Syntax 3, so its revision must be pinned (M-1 part 2).

## 5. Selector matching and style resolution

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **Right-to-left matching and indexing:** Blink indexes each rule by the right-most compound selector (by id, class, tag and so on), so an element looks only in the buckets for its own features. Matching then walks ancestors from the subject outwards. | — | [Blink "CSS Style Calculation" doc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/css/style-calculation.md) | read 2026-10-19 | High |
| 5.2 | **Descendant-selector Bloom filter** (WebKit, Antti Koivisto, bug 53880, 2011-02-06): "Bloom filter is faster than a hash set in this kind of use". The filter holds the ancestors' ids, classes and tags, so most descendant selectors can be rejected without walking up. Stylo has the same idea (a style Bloom filter kept in thread-local storage and reused across traversals). | Profiler estimate ~30% faster style matching on descendant-heavy sites | [WebKit bug 53880](https://bugs.webkit.org/show_bug.cgi?id=53880); [Stylo `bloom.rs` doc comment](https://github.com/servo/stylo/blob/main/style/bloom.rs) | 2011-02 | High |
| 5.3 | **Why browsers long refused a parent selector:** matching runs right to left; pages are styled as a stream, so a parent rule cannot be resolved until its children arrive; and every descendant insertion could force re-evaluation of ancestors. | No benchmark figures | [Snook, "Why we don't have a parent selector"](https://snook.ca/archives/html_and_css/css-parent-selectors) | 2010-10-10 | High (article); Low (the attribution to Hyatt is secondhand) |
| 5.4 | **WebKit CSS selector JIT** (Benjamin Poulain): the old `SelectorChecker` was a generic interpreter; the JIT compiles each selector to machine code. Unsupported pseudo-classes fall back to the interpreter. Compile cost is "within one order of magnitude of a single execution". | Microbenchmark ~1100 ms → <500 ms; "a gain of 2x is generally what we expect on common selectors" | [WebKit blog, "Overview of WebKit's CSS JIT Compiler"](https://webkit.org/blog/3271/webkit-css-selector-jit-compiler/) | 2014-03-26 | High |
| 5.5 | **JIT history:** enabled by default on x86_64 on 2014-01-14 (bug 126953); ARM64 enabled 2014-05-30 (bug 133246). Within a month, WebKit used its speed to **check selectors exactly when invalidating style** (2014-02-07: "Selectors are now really fast to match with the JIT"). | — | WebKit commits for [bug 126953](https://bugs.webkit.org/show_bug.cgi?id=126953), [133246](https://bugs.webkit.org/show_bug.cgi?id=133246), [128321](https://bugs.webkit.org/show_bug.cgi?id=128321) | 2014 | High |
| 5.6 | **Still in use (October 2026):** `PlatformEnable.h` enables the selector JIT on x86_64 and ARM64 whenever the JIT is enabled. In 2025 WebKit added an internal flag "to compare selector matching results between the SelectorChecker and the SelectorCompiler", and fixed a bug where `:not(:hover)` failed to invalidate **only when the JIT was disabled** (bug 301090). | — | WebKit commits for [bug 297655](https://bugs.webkit.org/show_bug.cgi?id=297655) and [bug 301090](https://bugs.webkit.org/show_bug.cgi?id=301090) | 2025-08, 2025-10 | High |
| 5.8 | Neither Blink nor Gecko/Stylo has a selector JIT. Both rely on indexing, the Bloom filter and caching. | — | Absence in the Blink style docs and the Stylo module list | — | Medium (absence of evidence) |

**Implications:** The ideas that survived are cheap rejection (bucketed rule indexes and an ancestor Bloom filter), not faster per-selector execution. A selector JIT doubles matcher implementations and has produced divergence bugs. That is the G1 dual-implementation pattern without a built-in oracle, and runtime code generation also conflicts with Izcal's security posture. If Izcal ever specializes selectors, it should be a data-driven compiled form checked against the reference matcher in CI.

## 11. Technology mismatches: assumptions no longer true

| Assumption baked into older designs | Where | Why it no longer holds | Evidence |
|---|---|---|---|
| One core; parsing and styling are inherently sequential | Gecko's pre-2017 style system, the first HTML parsers | Every target device has 4–16+ cores, but measured parallel gains depend on page weight | 7.5, 7.6 |
| Scripts are synchronous and block parsing; the network is slow | The preload scanner, threaded parsers, `document.write` | Parser-blocking scripts are now an anti-pattern; `async`/`defer`/modules dominate, so the main thread is less often idle waiting | 2.1, 3.3 |
| Pages are mostly parsed from the network once | Background parser designs | Single-page apps build DOM via innerHTML/DOMParser and frameworks, so fragment parsing became hot | 2.9 |
| Pages are small, with little styling | Parallel-style skepticism of 2017 | TP5's 2011-era pages "don't have that much styling"; modern design systems have thousands of rules | 7.6 |
| Stylesheets rarely change after load | Coarse stylesheet invalidation (2012) | CSS-in-JS and constructable sheets mutate rules at runtime | 8.1 |
| Selectors match right to left, and only ancestors matter | Pre-`:has()` invalidation | `:has()`, `:is()`, nesting and `@scope` require upward and sideways invalidation | 8.5–8.7 |
| Style does not depend on layout | All classic pipelines | Container queries create a style↔layout loop; anchor positioning adds more | 9.3 |
| Values are static per declaration | The pre-2020 cascade | `var()`, `@property`, typed `attr()` and `if()` make values computed from the cascade and the DOM | 9.8–9.10 |
| Runtime code generation is acceptable | Selector JIT (2014) | Lockdown modes, JIT-less policies and W^X make a JIT-only path a liability | 5.7 |
| One source language per component is a luxury | Gecko's Java→C++ parser | Memory-safe systems languages now cover both the validator and browser use cases | 1.7 |

## 12. What survived, and why

| Idea | Origin | Survived because | Evidence |
|---|---|---|---|
| A spec-defined, error-handling parsing algorithm (HTML5, CSS Syntax 3) | Hickson 2006–08; Atkins/Sapin 2013 | Interoperability on invalid input; removed the need to reverse-engineer | 1.1, 4.3 |
| A shared, engine-neutral test corpus (html5lib-tests, WPT) | html5lib 2006 | Lets independent implementations converge cheaply | 1.4 |
| The preload scanner | WebKit 2008, IE8 | Large latency wins and allowed to be wrong | 2.1 |
| Rules indexed by the right-most compound, plus an ancestor Bloom filter | WebKit 2011, all engines | Most rules are rejected without matching | 5.1, 5.2 |
| Rule tree and struct/group sharing with copy-on-write | Gecko, kept by Stylo; Blink groups | Memory and recompute savings that come from the data model, so they are deterministic | 6.1, 6.6 |
| Invalidation compiled from selectors, plus dynamic flags, plus a broad fallback | Blink 2014, WebKit 2016–22 | Precise in common cases, bounded in pathological ones | 8.3–8.5 |
| Lazy, batched invalidation (pending sets applied when style is read) | Blink | Coalesces mutation bursts | 8.3 |
| Sequential-first, adaptive parallel traversal | Stylo | Avoids overhead on small trees; scales on large ones | 7.7 |
| Property tables as data, with generated storage code | Blink json5 + generator | ~950 properties cannot be hand-maintained consistently | 6.5 |
| Gone: background HTML parsing thread (Blink) | 2013–2022 | Complexity versus a yielding foreground parser | 2.8 |
| Gone: opportunistic style sharing (Blink) | to 2017 | Unpredictable, blocked other work | 6.4 |
| Gone: generated CSS grammars | bison, to 2016 | Error recovery and extensibility | 4.2 |
| Gone: `document.write` scripts on slow networks (Chrome) | 2016 | 21% faster FCP on 2G; now explicitly allowed by the spec | 3.1, 3.3 |

**Implications:** The survivors have one thing in common: they are **deterministic, data-driven, and verifiable against a spec or a reference**. The casualties depended on timing, thread assignment or a second implementation that could disagree. That is the strongest historical support for Izcal's B1/B5/DET-1 approach to style.

## Open questions and flagged claims

- **Blink invalidation sets start date:** the earliest commits found are from March–April 2014, and the original design doc (a short link) was not readable. The start is probably late 2013 (Medium).
- **Blink's new CSS parser enable date:** the plan dates from ~September 2014 (code review 566483002) and WebKit's port carries a 2015 Chromium copyright. The exact milestone at which Blink switched off bison was not found (search budget exhausted).
- **Why Blink generated ComputedStyle:** no postmortem found. The rationale here (maintaining ~950 properties, memory grouping by usage) is inferred from the in-tree doc and generator comments.
- **Style-dev thread on style sharing** was read through a summarizer. The proposal doc's Wikipedia analysis and its numbers were not seen.
- **WebKit's reason for removing the threaded parser (2014)** is not stated in bug 127225.
- **Gecko speculative parsing origin** (believed Firefox 3.5, 2009) was not verified this session.
- **Gecko's pre-Stylo CSS parser being hand-written** comes from the style-system doc's "CSS scanner"/"CSS parser" wording and recollection (Medium).
- **Single-source claims:** the 30% Amazon speedup (7.5), the ~30% Bloom-filter estimate (5.2, a profiler estimate in a bug comment), the 2× selector JIT gain (5.4, a vendor microbenchmark) and the Nexus 7 threaded-parser numbers (2.5) each rest on one source.
- **Not covered for lack of budget:** Presto's style system and parser, Trident's lookahead downloader internals, Ladybird's parser, "style recalc share of main-thread time" on modern corpora (no primary figure found), and Gecko's current `:has()` invalidation design.
