# Izcal HTML and CSS parsing and style: security and robustness

Compiled 19 October 2026. Primary sources were preferred (specifications at their current editor's drafts, Project Zero's 0-day "In the Wild" sheet, vendor blogs and advisories, peer-reviewed papers, maintainers' bug reports and security reviews).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, a technical secondary source, or prior knowledge not re-fetched this session; **Low** = secondary source only (forums, press, aggregators).

**Method notes.**
- **M-1.** No engine source code was read (Blink, WebKit, Gecko, Stylo, html5ever). Specifications, papers, blogs, advisories, bug reports, rustdoc pages of public items and one Mozilla test file's comment were read. Where a fact about another engine's internals comes only from a write-up of its code (for example a commit summary), it is marked Medium and used only as a black-box signal about a bug class, never as a design to copy.
- Section 1's in-the-wild tally is this note's own count from the Project Zero sheet ([P0 0-day ITW sheet](https://docs.google.com/spreadsheets/d/1lkNJ0uQwbeC1ZTRrxdtuPLCIl7mlUreoKfSIgajnSyY/)), exported on 19 October 2026 (the same export the JS-engine security note used). **Implications:** The in-the-wild record says the parser and cascade are rarely the exploited link, but the one exploited CSS bug (1.1–1.2) is exactly the class Rust's borrow rules remove: a reference into a container held across a call into script that mutates it. Mozilla's own count (1.6) says about three quarters of style-system security bugs are memory-safety bugs that safe Rust removes. Izcal should therefore treat **"no `unsafe` in `hg-style` and the HTML parser" as a hard rule** and spend its security effort on what Rust does not remove: logic and privacy bugs (1.7), re-entrancy semantics (section 6), allocation failure and stack depth (sections 4 and 8). The 1.7 lesson is already SEC-24 in the security scope; it applies first to `:visited`.

**Implications:** Every mXSS and sanitizer bypass above comes from **two parsers, or two parses, disagreeing**: sanitizer vs browser, context-free vs contextual, scripting on vs off, fast path vs full parser, old parser vs new. Izcal's engine-side rules follow directly: **one HTML tokenizer and tree builder for every entry point** (document, `innerHTML`, `setHTML`, `parseHTMLUnsafe`, `DOMParser`, preload scanner tokenization included); **one parser per micro-grammar** (URLs, namespaced attribute names, CSS values), with no "fast path" that can disagree with the full parser; sanitization done **in the tree builder** as the standard now specifies; and a CI **round-trip differential suite** (parse, serialize, re-parse in every context, with scripting on and off) that must reach a fixed point or be on a recorded list of spec-known mutations.

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|

**Implications:** CSS can read the DOM and make requests; it cannot run code, so its threats are **exfiltration and history leaks**, and the spec answers are structural: taint (3.4), hidden nonce (3.7), partitioned history (3.10–3.11), origin-clean (3.12). Izcal should ship **triple-keyed `:visited` from the first release** (Appendix C), and still keep the 2010 property restrictions until partitioning is the only source of `:visited` state, since the visited store is per-profile and the renderer must never hold history it could not observe. `attr()` taint must be a **type-level property** of substituted token streams in `hg-style`, and Izcal should raise the implicit-flow gap (3.5) with the CSSWG rather than invent a non-standard fix.

Each call is another substitution layer for 4.7's limit | — | [CSS Mixins 1 §3](https://drafts.csswg.org/css-mixins-1/) | read 2026-10-19 | High |
| 4.14 | Deep-tree recursion crashes recur in engines: a recursive WebKit style-reset routine (`resetStyleForNonRenderedDescendants`) "can stack overflow on very deep DOM trees", fixed by rewriting it iteratively | 1 example | [WebKit bug 243957](https://bugs.webkit.org/show_bug.cgi?id=243957) | 2022 | Medium |

**Implications:** The specs either say nothing about limits (HTML) or require a UA-defined limit without a number (substitution). Izcal should set **every limit as a named, recorded constant with a spec-conformant overflow behaviour**, and test both sides of each: parser depth (the depth at which elements become siblings, matching the WebKit-observed 512 unless measurement says otherwise), substitution output length, `calc()` terms and nesting (≥ 32, the spec floor), custom-function call depth, `@import` depth. Because a parser cap does not stop script-built trees (4.3), **no style or layout algorithm may recurse on DOM depth** on a native stack; they must be iterative or carry an explicit depth budget. Selector cost needs a **work budget per style pass** (a measured target, not a spec rule), with `:has()` invalidation bounded per mutation.

The style pass itself must be **script-free**: nothing in matching, cascade or computed values can call out. Izcal should not implement mutation events at all; their removal is now web-compatible in Chromium.

## 8. Robustness lessons from Rust rewrites

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | **Stylo's dominant crash class at launch was OOM, not memory corruption**: bug 1404633, "stylo: Crash in OOM", signature `OOM \| unknown \| alloc::oom::oom \| style::properties::StyleStructRef<T>::mutate<T>`, a failed 16-byte allocation on 32-bit and 64-bit Windows during Firefox 57 beta. Engineers judged that fixing one call site would just move the OOM, and closed it WONTFIX (dup of 1415151) | 16-byte allocations | [Bugzilla 1404633](https://bugzilla.mozilla.org/show_bug.cgi?id=1404633) | 2017 | High |
| 8.2 | **Stylo manages native stack explicitly**: the style thread pool has a minimum stack size (8,192 KB, "Servo requires a bigger stack in debug builds", larger under ASAN), and a `STACK_SAFETY_MARGIN_KB` at which "recursive optimizations are skipped" | 8,192 KB | [Servo docs: style::parallel](https://doc.servo.org/style/parallel/index.html); [STYLE_THREAD_STACK_SIZE_KB](https://doc.servo.org/style/parallel/constant.STYLE_THREAD_STACK_SIZE_KB.html) | read 2026-10-19 | High (rustdoc) |
| 8.3 | **Stylo turns concurrency misuse into panics**: DOM state touched by parallel styling is behind `AtomicRefCell`, "which panics on misuse"; the only `unsafe` in the parallel traversal is wrapping nodes to send across threads | 1 unsafe site | [Servo docs: style::parallel](https://doc.servo.org/style/parallel/index.html) | read 2026-10-19 | High |
| 8.4 | Mozilla's lesson from the rewrite: "While Rust makes it easier to write better code, it's not foolproof" (see 1.7: a logic regression and a disabled test) | — | [Mozilla Hacks 2019](https://hacks.mozilla.org/2019/02/rewriting-a-browser-component-in-rust/) | 2019-02-28 | High |
| 8.5 | Firefox builds its Rust with panics that abort the process (a panic is a crash report, not unwinding); a panic in a content process loses the tab's process, not the browser | — | prior knowledge; not re-fetched | — | Medium |

**Implications:** A Rust style system moves failures from exploitable corruption to **denial of service by crash**: OOM, panics from runtime borrow checks, and stack exhaustion. Izcal should design for these explicitly: **fallible allocation** in the parser, substitution and rule-index paths, with a defined outcome (stop parsing, treat declaration as invalid, evict a regenerable cache per FP-D16); **no recursion on attacker-controlled depth** (section 4) rather than larger thread stacks; and **no runtime-checked sharing on the hot path** (use the phase-purity discipline of the Stage 1 design so parallel style needs neither `AtomicRefCell` panics nor locks). A panic must abort only the site process (I-1), and every panic site in `hg-style` should be fuzz-reachable and counted.

## 10. Open questions and gaps in this research

- **Current depth caps of Blink and Gecko** (4.3) were not verified; WebKit's 512 is from its test expectation. A black-box test (nest N elements, read `parentNode` depth) on each shipping engine would settle it and is allowed under M-1 part 4.
- **CVE-2026-2441's root cause** comes from one technical write-up (Wiz); the Chromium tracker entry was not read.
- **Chrome's VRP or advisory counts by component** (CSS, HTML parser, style) for 2023–2026 were not found; the share of style bugs among non-exploited Chrome security fixes is unknown.
- **`:has()` crash or security bugs**: no public CVE tied to `:has()` was found; its invalidation complexity is a correctness and DoS concern, not an evidenced security one.
- **Final removal of mutation events** in Chromium (after the deprecation trial) and their status in WebKit and Gecko were not verified.
- **Fuzzing statistics** for Chrome's CSS and HTML fuzzers, Mozilla's Grizzly/Domino, FreeDom and later DOM fuzzers were not re-fetched (search budget exhausted); 5.4 is Low.
- **Stylo stack-overflow history** (specific bugs where deep trees overflowed style threads) was not found; 8.2 shows the mitigation, not the incident record. Firefox's panic strategy (8.5) is from prior knowledge.
- **Safari's fingerprinting behaviour** for media queries and its Lockdown Mode effect on the CSS Selector JIT were not checked.
- **Implicit-flow leak through `if()`** (3.5) is this note's inference; whether the CSSWG considers it in scope for the attr() taint is not known.
