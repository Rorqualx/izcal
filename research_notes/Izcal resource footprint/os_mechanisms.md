# Izcal resource footprint: OS and hardware mechanisms per platform

Compiled 19 October 2026. Primary sources were preferred (OS documentation, kernel docs, man pages, vendor engineering blogs, papers, and Chromium source read at `HEAD` on 2026-10-19 as evidence only).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Scope.** This strand covers what each operating system and its hardware give a browser for keeping memory, CPU wake-ups, energy, GPU memory and disk low: per-process base cost and fork servers, shared read-only mappings, copy-on-write, memory compression, `madvise` and purgeable memory, memory-pressure signals, allocators, huge pages and page size, threads, timers and QoS, GPU budgets, disk caches and binary layout. Platforms: macOS, Linux, Windows, and Android/iOS as future targets. It covers phases 2–3 of the first-principles-spec method; synthesis belongs to the spec author.

**Izcal constraints that apply.** HGBA-2 **P1** (security) outranks **P4** (performance and energy); **I-1** process per site is the boundary, so no two sites' data may share a process; **Section 4.6** already names the advisory tiers (hot/warm/cold/frozen), `madvise` hints, discard, bfcache, snapshots, broker-allocated shared memory, and excludes io_uring. **M-1/D-S10**: everything below is evidence; no code or template is taken from Chromium, Firefox or any OS sample.

**Method note.** The shared web-search budget was used for the hardest questions (Instagram COW numbers, macOS spawn cost, Windows process-creation cost, allocator RSS data, memory-compression ratios, dedup attacks). Everything else was read directly from known primary pages. The Instagram engineering blog refused connections (2026-10-19), so its numbers are graded Medium from search snippets. No primary measurement of **macOS `posix_spawn`** or **Windows `CreateProcess`** cost for a sandboxed browser child was found; this is an open measurement (Section 14).

**Implications:** A process's fixed cost is dominated by what each process must *write* at start-up (relocations, library init, heap set-up), not by code. Linux and Android can share that work through a zygote, at an ASLR cost that conflicts with P1 unless the zygote is re-randomised (Morula's ~13 MB/app is the price data point). macOS and Windows cannot fork; there the lever is making start-up produce **no dirty pages** (position-independent data, page-in linking, read-only snapshot mappings). Izcal should budget per-process cost per platform, not one number, and measure spawn cost itself.

## 2. Shared read-only mappings

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|

**Implications:** Izcal's broker-allocated shared memory (HGBA-2 4.6) maps cleanly to sealed memfds on Linux and to section handles with read-only access on Windows; on macOS the equivalent is a Mach memory entry passed over IPC (not researched in depth here). A **read-only, position-independent snapshot** of engine start-up state, mapped shared into every site process, gives zygote-like sharing on every OS without sharing layout or writable state. Content-based deduplication across sites must never be used (P1, I-1).

## 3. Copy-on-write and its pitfalls

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Refcount and GC writes break COW.** At Instagram, reading a Python object writes its refcount, and the cyclic GC writes `gc_refs` on every tracked object; perf traces showed most COW faults came from the GC. Disabling GC raised shared memory per worker from **140 MB to 225 MB** and freed about **8 GB per host**; an earlier GC-disable gave ~10% more capacity. | 140 → 225 MB/worker | [Instagram: COW-friendly Python GC](https://medium.com/instagram-engineering/copy-on-write-friendly-python-garbage-collection-ad6ed5233ddf); [Instagram: Dismissing Python GC](https://instagram-engineering.com/dismissing-python-garbage-collection-at-instagram-4dca40b29172) | 2017 | Medium (blog unreachable; numbers from search snippets) |
| 3.2 | **`gc.freeze()`** (CPython 3.7) moves all tracked objects into a permanent generation. Recipe: `gc.disable()` early in the parent, `gc.freeze()` just before `fork()`, `gc.enable()` in the child; also avoid freed "holes" in parent pages. | 3.7 | [Python docs: gc](https://docs.python.org/3/library/gc.html) | read 2026-10-19 | High |
| 3.3 | **Immortal objects (PEP 683, Python 3.12)** fix the refcount on shared objects so reads never write. Cost of a naive implementation: **2%** slowdown (3% MSVC; the abstract says ~4%), recovered to roughly neutral with mitigations. The PEP notes refcount semantics "drastically reduce the benefits" of fork sharing and that every refcount change invalidates a cache line. | 2–4% | [PEP 683](https://peps.python.org/pep-0683/) | 2022–2023 | High |
| 3.4 | **ASLR-shared zygote children** keep COW sharing only while nobody writes; any per-process re-randomisation (Morula) or per-process relocation (Linux PIE `.data.rel.ro`) turns shared pages private. | ~6–8 MB/process in Chromium's measurement (1.1) | [Chromium zygote doc](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/linux/zygote.md) | read 2026-10-19 | High |

**Implications:** COW sharing survives only if the shared data is **truly immutable at the machine level**: no refcounts, mark bits, inline caches, lazy-initialised fields or GC metadata inside shared pages. Izcal's JS engine and style system should keep mark bits and mutable metadata in side tables, and put shared start-up state in a mapping that is read-only by protection, not by convention, so an accidental write faults instead of silently un-sharing.

## 4. Memory compression

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **macOS Compressed Memory** (OS X 10.9) compresses least-recently-used pages with the dictionary-based **WKdm** algorithm, in parallel across cores, before swapping; compressed objects are what get swapped. | ">50%" size reduction; a page in "a few millionths of a second" | [Apple: OS X Mavericks Core Technologies Overview (PDF)](https://www.apple.com/media/us/osx/2013/docs/OSX_Mavericks_Core_Technology_Overview.pdf) | 2013-10 | High |
| 4.2 | **WK-family compressors** were designed for in-memory data: word-aligned integers and pointers, which general compressors handle poorly. | — | [Wilson, Kaplan, Smaragdakis, USENIX ATC 1999](https://www.usenix.org/conference/1999-usenix-annual-technical-conference/case-compressed-caching-virtual-memory-systems) | 1999 | Medium (abstract not read) |
| 4.3 | **Windows memory compression** (Windows 10, 2015): under pressure the memory manager compresses unused pages into a **compression store** in the System process's working set instead of writing them to the page file; a store hit is a "soft compression fault". | ~30–40% of original size (secondary) | [Windows Insider build 10525](https://blogs.windows.com/windowsexperience/2015/08/18/announcing-windows-10-insider-preview-build-10525/); [Petri](https://petri.com/memory-compression-in-windows-10-threshold-2/) | 2015-08-18 | High (mechanism); Low (ratio) |
| 4.4 | **Linux zram** is a compressed RAM block device (lzo, lz4, zstd, …) with up to three secondary recompression algorithms, writeback of idle or incompressible pages, and `same_pages` stored with no memory. Sizing guidance assumes **2:1**. | 2:1 assumed; 0.1% overhead when unused | [kernel.org: zram](https://docs.kernel.org/admin-guide/blockdev/zram.html) | read 2026-10-19 | High |
| 4.5 | **Linux zswap** is a compressed cache in front of a swap device (zsmalloc pool, LRU writeback, same-filled pages stored as a pattern; shrinker off by default). cgroup v2 has `memory.zswap.max` and `memory.zswap.writeback`. | — | [kernel.org: zswap](https://docs.kernel.org/admin-guide/mm/zswap.html) | read 2026-10-19 | High |
| 4.6 | **What compresses:** Meta's TMO assumes a **3×** average ratio for production workloads, but quantized ML model bytes compress only **1.3–1.4×** and go to SSD instead. Zero and same-filled pages cost nothing in zram/zswap. | 3× avg; 1.3–1.4× quantized | [Meta: Transparent Memory Offloading](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/) | 2022-06-20 | High |

**Implications:** Every target OS compresses cold anonymous memory, so a browser's "cold" tier is already partly handled by the OS, and **what matters is compressibility and access pattern**: pointer-rich heaps and zeroed pages compress well; decoded images, compressed media, JIT code with random constants and encrypted data do not. Izcal should zero freed pages it keeps (or release them), keep incompressible caches (decoded images) discardable rather than resident, and measure compressed-footprint per tab on macOS and Windows, where the OS charges compressed pages to the process.

**Implications:** "Release" has three meanings Izcal must keep apart: **resident** (working set / RSS), **charged** (commit on Windows, phys_footprint on macOS, memcg on Linux) and **discardable** (OS may drop contents). Only decommit/unmap reduces Windows commit; only `MADV_FREE_REUSABLE`-style calls reduce macOS footprint; `MADV_FREE` hides real savings from RSS. Izcal's advisory tiers should map to these per OS and its attribution must report charged memory, not RSS alone.

**Implications:** The best pressure signal available is **PSI** (stall time, i.e. measured user harm) on Linux and Android; macOS gives three coarse levels; Windows gives either a coarse system event or self-computed commit headroom. ## 14. Lessons, open questions and flagged claims

| Project → what happened | Lesson | How Izcal applies it |
|---|---|---|
| Chromium Linux zygote saves ~8 MB/process but shares ASLR layout (1.1, 1.2) | Sharing by fork trades security entropy for memory | Prefer read-only snapshot mappings that share bytes, not layout; if a zygote is used on Linux/Android, re-randomise or pool templates and budget the Morula-style cost |
| Instagram, PEP 683 (3.1–3.3) | Hidden writes (refcounts, GC bits) silently un-share COW pages | Keep all mutable metadata out of shared pages; map shared state read-only so writes fault |
| Go 1.16 reverted `MADV_FREE` (5.2) | Lazy release hides savings from users' tools | Choose release calls by what the OS *charges*, and report charged memory |
| Chromium Windows commit gotcha (5.4) | Working-set reduction is not commit reduction | Decommit on Windows for real savings; budget commit separately |
| Dedup Est Machina (2.8) | Content dedup across security domains is exploitable from JS | Never enable cross-site dedup; share only data Izcal itself chose to share |
| Chrome M87 throttling (10.9) | Timers dominate background work | Wake-ups per background site are a budgeted, tested metric |
| Chromium no Linux pressure evaluator (6.9) | Incumbents leave the best signal (PSI) unused on desktop Linux | Use PSI triggers and per-site cgroups where available |

**Open questions (need Izcal measurement, Stage 1 milestones):**
1. **Spawn cost per OS** for a sandboxed, empty Izcal site process: `posix_spawn` + sandbox init on macOS, `CreateProcess` + job/AppContainer on Windows, clone from a zygote vs fresh exec on Linux. No primary numbers were found.
2. **Private dirty bytes of an empty site process** per OS, split into relocation, allocator metadata, thread stacks, engine heap and GPU client state.
3. **Compression ratio of Izcal's own heaps** under the macOS compressor, Windows store and zram (lz4/zstd), and how much of a cold tab ends up compressed vs on disk.
4. **macOS public-API path** for per-child background policy (Chromium relies on `task_policy_private.h`).
5. **macOS shared-memory sealing equivalent** (Mach memory entry with read-only rights) and its cost — not researched here.

**Flagged claims:** Instagram numbers (3.1) are from search snippets of an unreachable blog. Windows compression ratio (4.3) is secondary. Windows process-creation cost (1.8) is anecdotal. Morula's 13 MB (1.4) is from the abstract. All Chrome "up to" percentages (5.7, 7.1, 10.9, 12.2) are vendor best cases without published distributions. EcoQoS's 90% (10.5) is Microsoft's initial assessment, not independently measured.
