# Izcal resource footprint: compact engine data structures and lazy/discardable data

Compiled 19 October 2026. Primary sources were preferred (bug trackers, engine design docs, maintainers' blog posts). Since the 0.3.1 source-evidence pass, engine source files, commits and code reviews are not evidence (HGBA-2 M-1 part 3): rows that rested on them were re-sourced, turned into black-box measurements or removed ([source_evidence_pass.md](source_evidence_pass.md)). The JS heap is covered by a separate strand; it appears here only where an idea crosses over (pointer compression, per-process fixed cost).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a number this researcher inferred from a primary source (the method is stated); **Low** = secondary source only.

M-1 reading used throughout: everything below is an idea or a measurement. No structure, layout or algorithm is to be copied from another engine's code; other engines are cited only through published prose and black-box observation, as **evidence of what a choice costs**, not as templates. Stylo, WebRender and the other unmodified dependencies named in Stage 1 Section 5.5 are covered as dependencies whose footprint Izcal inherits.

Local measurements in Section 15 were made by this researcher on 19 October 2026 on this Mac (macOS 27.0.1, Apple silicon) with `size -m`, `dyld_info -segments`, `ls` and `unzip -l`. No browser was running, so no live per-process numbers were taken.

**Implications:** Izcal's node exists **twice** (Stage 1 §5.2 `cppgc` node header with five links, wrapper reference, 64-bit stable ID; and §5.4 `DataPlane` columns). That is ≈95–115 B per node **before** payload (other engines' per-node cost is measured black-box at FP-M0, 1.2). Every field must be justified against a size assertion (CS-PF type-size budgets), and whether the fork's `cppgc` has pointer compression on is an unmeasured, high-leverage question (Section 11).

## 3. Strings, atoms and text storage

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **`string_cache::Atom` (used by `markup5ever`, Stage 1 §5.2) is always 8 bytes.** The low two bits select **static** (index into a compile-time perfect-hash set), **inline** (≤7 bytes packed in the word) or **dynamic** (pointer to a refcounted entry in a global hash set, freed when the last atom drops). Equality is a 64-bit compare. | 8 B; inline ≤7 B | [string_cache 0.11 `Atom` docs](https://docs.rs/string_cache/latest/string_cache/struct.Atom.html) | 2026-10 | High |
| 3.2 | **Latin-1 ("8-bit") strings:** WebKit's original estimate was that storing non-wide strings in 8-bit buffers would save **500 kB–2 MB, 3–5 % of WebCore memory** on pages such as espn.com (Annie Sullivan, 2011). JavaScriptCore turned 8-bit strings on in November 2011; in November 2012 Michael Saboff measured that unwanted **up-conversions to 16-bit** fell from 10.73 % of strings (864,350 bytes) to 1.08 % after fixing `TextIterator` — the saving is lost wherever an API forces the wide form. | 3–5 % of WebCore; up-conversions 10.7 % → 1.1 % | [webkit-dev, Aug 2011](https://lists.webkit.org/pipermail/webkit-dev/2011-August/017699.html); [webkit-dev, Nov 2011](https://lists.webkit.org/pipermail/webkit-dev/2011-November/018621.html); [bug 103295](https://bugs.webkit.org/show_bug.cgi?id=103295) | 2011-08; 2012-11 | Medium |
| 3.3 | V8, JavaScriptCore, Blink's `WTF::String` and Gecko's text fragments all keep a **one-byte representation** where content allows; V8 and SpiderMonkey also use **ropes/cons strings** for concatenation and **external strings** that point at engine-owned buffers without copying. (JS-heap details belong to the JS strand.) | — | [V8 blog: pointer compression context](https://v8.dev/blog/pointer-compression) and engine docs | — | Medium (not re-read for this note) |

**Implications:** Rust `String` is UTF-8, which is 1 byte per char for ASCII and avoids WebKit's up-conversion problem, but DOM and JS APIs index in UTF-16 code units. Izcal needs one **text-buffer representation shared by DOM text, JS strings and layout** (no copies at the binding boundary) with a cheap UTF-16 index map; this is a cross-strand decision with the JS engine. For tags and attribute names, a **16-bit static index** (HTML has a few hundred known names) would shrink the `tag` column from 8 to 2 bytes, keeping `Atom` only for unknown names.

## 5. Layout tree and fragment memory

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **LayoutNG's immutable fragment tree:** fragments have no parent pointers, children never read parents, so the previous tree can be reused and usually only the "spine" is rebuilt. **Inline content is a flat list per inline formatting context** of (item, descendant count) tuples instead of a box tree — described as "fast, memory efficient". | — | [Key data structures in RenderingNG](https://developer.chrome.com/docs/chromium/renderingng-data-structures) | 2021-08-24 | High |
| 5.2 | **The cache key is the constraint space** stored with each fragment; a diff of old vs new constraints decides relayout. Both measure and layout results are cached, which keeps two-pass flex/grid linear. **No memory number for LayoutNG has been published**; the posts discuss only correctness and speed. | none published | [RenderingNG deep-dive: LayoutNG](https://developer.chrome.com/docs/chromium/layoutng) | 2021-10-08 | High (absence checked in text) |

**Implications:** Stage 1 §5.6 caches `Arc<Fragment>` by constraint space; this keeps **two copies** of geometry during an incremental relayout and one fragment per (box, constraint space) in the cache. The cost is unmeasured anywhere in public; Izcal should measure fragment bytes per DOM node on the corpus and adopt **flat, index-addressed inline item arrays** (an idea, not Blink's layout). Fragments for offscreen, unchanged subtrees are a candidate for **discard-and-recompute** under pressure (layout is a pure function, so recomputation is always correct).

## 6. Display lists, paint data and property trees

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **Display item reuse:** unchanged layout objects copy their display items from the previous list; an unchanged stacking context is copied whole. **Paint chunks** group items with the same property-tree state; property trees are sparse (one node per effect, not per element), so updates are O(interesting nodes) not O(layers). | — | [RenderingNG data structures](https://developer.chrome.com/docs/chromium/renderingng-data-structures); [How cc Works](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md) | 2021-08-24; 2026-10 | High |
| 6.2 | **Layerization is a GPU-memory trade:** one layer per chunk "would quickly exhaust GPU memory"; one layer for everything forces re-raster on scroll. The default merges chunks except those that change on the compositor (scroll, transform animation). | — | [RenderingNG data structures](https://developer.chrome.com/docs/chromium/renderingng-data-structures) | 2021-08-24 | High |

**Implications:** Izcal's display list goes to WebRender over shared memory (§5.7). It should be held **once** (in the shared segment, not copied into the GPU service) and the renderer should drop its copy for background tabs; pixel-optional mode (B7) already stops after paint chunks.

Izcal writes its own decoders (M-1), so codec memory is a design choice: streaming/tiled decode for AVIF and JPEG XL should be measured before the decoders are specified.

| 12.2 | **Site isolation cost Chrome 9–13 % total memory** in practice (≈10–13 % per Reis), with 2.25 % page-load change; Chrome 63's early estimate was up to 20 %. | 9–13 % | [Reis, Moshchuk, Oskov, USENIX Security 2019](https://www.usenix.org/conference/usenixsecurity19/presentation/reis) | 2019-08 | Medium (paper not re-read; figures via slides and press) |

**Implications:** The per-site process baseline is the number this spec most needs to budget. Firefox's path shows a **≈11 MB** Windows content-process floor is reachable with shared read-only data (UA sheets, font list, atoms tables, JS self-hosted code) and allocator tuning; Izcal should set its per-process budget from a line-item list (Section 4.5, 9.1, 11.5, 15) rather than from Chrome.

Firefox 93 says act **before** the pressure cliff.

## 14. What to recompute vs what to store

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 14.1 | Engines treat as discardable: decoded images (Section 8), tiles and raster (Section 7), image caches on navigation (>50 MB), background-tab purge (17–43 MB/tab). They treat as non-discardable the DOM, JS heap and computed style. No engine publishes a measured "bytes saved vs ms to rebuild" curve for style, fragments or display lists. | — | sections above | — | Medium |
| 14.2 | Recompute cost references: LayoutNG treats a 50–100 ms layout after a small change as a bug signal; style sharing makes most restyles cheap. Raster is the costliest step to redo ("image decoding is the most expensive part of raster"). | 50–100 ms | [LayoutNG](https://developer.chrome.com/docs/chromium/layoutng); [How cc Works](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md) | 2021; 2026 | High |

**Implications:** Izcal's derived data is a **pure function of the DOM and style sheets** (DET-1, §5.6), which makes every derived layer safely discardable. The spec should require each derived store to report (bytes, rebuild time) so the memory manager can discard the best bytes-per-millisecond first; this is new measurement work, with no public baseline.

## 16. Flagged claims and open questions

- **Inferred sizes:** the Izcal per-node estimate in Section 1 was computed from member lists, not measured; confirm with `sizeof` in Izcal's own build. Other engines' inferred sizes (1.2, 1.3, 4.4) were removed at 0.3.1 and are measured black-box at FP-M0.
- **Unknown:** whether Izcal's V8 fork builds `cppgc` with pointer compression (`cppgc_enable_pointer_compression`); it decides whether the five DOM links cost 20 or 40 bytes per node.
- **Unknown:** whether Stylo's crate API lets UA sheets and their cascade data live in cross-process shared memory without modifying Stylo.
- **Unknown:** LayoutNG/fragment memory per node; AVIF and JPEG XL decoder peak memory; Chrome's renderer glyph cache limit; in-memory HTTP and code cache budgets.
- **Single-source or secondhand:** Stylo +12/+10 MB (4.3), Zig DOD percentages (11.3), Memory Saver revisit rate (13.3), site-isolation 9–13 % (12.2, figures not re-read in the paper).
- **Old data:** WebKit string numbers are from 2011–2012 on one page; treat as direction, not magnitude.
