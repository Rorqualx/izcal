# Izcal resource footprint: where browser memory and CPU go, and how to measure it

Compiled 2026-10-19. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, OS documentation). Engine source code is not evidence (HGBA-2 M-1 part 3); the row that rested on it was re-sourced in the 0.3.1 pass ([source_evidence_pass.md](source_evidence_pass.md)). One section (3) adds a small first-hand measurement made for this note on the local rig (booking b-5ddbf7, light, 2026-10-19).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Research only (M-1): this note records ideas and evidence. It contains no code and no template from any browser.

## 1. What "memory" means: OS metrics and how browsers define footprint

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Chrome's telemetry metric is **private memory footprint (PMF)**, reported per process type (1.2). Its per-OS arithmetic was first read from engine source; that reading is removed (0.3.1 source-evidence pass, HGBA-2 M-1 part 3). Each OS exposes a different native quantity: macOS `phys_footprint` (1.6), Windows commit charge (`PrivateUsage`, 1.3), Linux anonymous resident plus swap (1.4). | 1.2 | Chrome's field dashboards use UMA histograms `Memory.{Total,Renderer,Browser,Gpu,Extension}.PrivateMemoryFootprint`; memory-infra is the tool for attribution. | 5 histograms, split by process type only | [Chromium docs/memory/README.md](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/memory/README.md) | read 2026-10-19 | High |
| 1.3 | Chromium's own primer says a uniform cross-platform answer to "how much memory is Chromium using" is hard; per-OS source of truth is VMMap (Windows), vmmap (Darwin), `/proc/<pid>/smaps` (Linux). "Accounting for shared memory is poorly defined"; Chrome counts each anonymous shared-memory region toward exactly one process. PSS "is context dependent" (a process's PSS falls when more processes map the same library). On Windows, `MEM_RESET`-style discards do not release commit, so they do not prevent OOM. | — | [Key concepts in Chrome memory](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/memory/key_concepts.md) | read 2026-10-19 | High |
| 1.4 | Linux kernel definitions: **Rss** = resident pages of the mapping; **Pss** = each page divided by the number of processes sharing it; `smaps_rollup` gives Pss_Anon/Pss_File/Pss_Shmem; a page is "private" if mapped exactly once; `VmRSS = RssAnon + RssFile + RssShmem`; `VmSwap` excludes shmem swap. Reading full smaps is "slow but very precise"; rollup exists because smaps is expensive; RSS counters are updated asynchronously and "may not be very precise". | — | [Linux kernel docs, The /proc filesystem](https://docs.kernel.org/filesystems/proc.html) | read 2026-10-19 | High |
| 1.5 | Consequence of 1.4 (analysis): a footprint built from `RssAnon + VmSwap` excludes **RssShmem**, so memfd/shmem buffers (IPC, GPU transfer, shared images) are charged to no process; whether any incumbent's metric has this gap is checked black-box at FP-M0. `VmSwap` reports the uncompressed size of swapped pages, so on zram systems it overstates real RAM used. | — | derived from 1.4 | 2026-10-19 | Medium |
| 1.6 | Apple: an app's **footprint** is dirty + compressed memory; "clean memory doesn't really count"; iOS has no swap, it uses a memory compressor (since iOS 7); swap/compressed sizes are reported pre-compression; the termination limit (EXC_RESOURCE / jetsam) is graded on footprint and varies by device. | — | [WWDC 2018 session 416, iOS Memory Deep Dive](https://developer.apple.com/videos/play/wwdc2018/416/) | 2018-06 | High |
| 1.7 | Windows: `PrivateUsage` = `PagefileUsage` = **commit charge**, "the total amount of private memory that the memory manager has committed for a running process" (resident or not). Private working set is a different number (resident private pages). | — | [PROCESS_MEMORY_COUNTERS_EX](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex) | doc 2018-12-05 | High |
| 1.8 | Firefox `about:memory`: **explicit** = memory from explicit heap and non-heap (mmap/VirtualAlloc) allocations, as reported by memory reporters; **heap-unclassified** = heap not measured by any reporter, "typically 10–20% of explicit"; **resident** is the best single summary; vsize matters mainly on 32-bit. | heap-unclassified 10–20% of explicit | [about:memory docs](https://firefox-source-docs.mozilla.org/performance/memory/about_colon_memory.html) | read 2026-10-19 | High |
| 1.9 | Chrome memory-infra separates **size** (allocated by a subsystem) from **effective size** (what it is responsible for); summing effective sizes gives the total without double counting (e.g. Skia's 10 MB from PartitionAlloc appears in both sizes but only in Skia's effective size). Columns: Blink GC, CC, Discardable, Font caches, GPU, GPU memory buffer, LevelDB, Malloc, PartitionAlloc, Skia, SQLite, V8, Web Cache; OS columns: resident, PSS, private dirty, swapped. Tracing overhead is reported separately. | — | [memory-infra README](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/memory-infra/README.md) | read 2026-10-19 | High |
| 1.10 | The web-exposed `performance.measureUserAgentSpecificMemory()` (Chrome/Edge 89+) reports JS + DOM of all frames and dedicated workers in the process; needs cross-origin isolation (COOP+COEP); measured during GC (forced after 20 s); recommended sampling is a Poisson process with a 5-minute mean. Precise or cross-browser-comparable results are a non-goal; cross-origin iframes are attributed to the top-most cross-origin frame. The older `performance.memory` was used on ~20% of Chrome page loads and can grossly over- or under-estimate. | 5 min mean sampling | [web.dev article](https://web.dev/articles/monitor-total-page-memory-usage) (2020-04-13); [WICG explainer](https://github.com/WICG/performance-measure-memory) | 2020–2026 | High |

**Implications:** Every browser's "footprint" number is a different quantity per OS, and none of them attributes shared memory, GPU memory or compressed memory consistently. Izcal should define one footprint per OS for its budgets (the frame already lists PSS/USS, phys_footprint, private working set/commit), state what it excludes, and add its own byte attribution (site, component, cause) so that the OS number and the attributed sum can be reconciled, with the residual (Firefox's "heap-unclassified") as a tracked quality metric.

**Implications:** The JS heap is the largest single item but not the majority; images/layers and allocator slack together are of the same order. Three levers have published double-digit effects: heap object layout (pointer size), allocator design, and keeping decoded pixels only for what is on screen. Izcal's attribution must cover allocator slack and decoded pixels explicitly, because these are invisible in a JS-only view.

**Implications:** Roughly half of an empty renderer's private memory on macOS is the **binary's own writable/relocated data**, not web content; this is a design input (fewer pointer-bearing globals, position-independent read-only tables, a zygote/fork model where the OS allows sharing), and it multiplies by the process count that I-1 requires. RSS overstates per-process cost 3–4× versus footprint on macOS; budgets must never be set in RSS.

**Implications:** Per-site processes cost ~10% more memory in practice, not 50%, because the workload is split, not duplicated. The fixed cost per process (section 3) times the site count (p99 ≈ 42 sites) is the term to minimise: at 27 MB × 42 sites ≈ 1.1 GB of fixed cost at the p99 user, which is why the fixed cost matters more than any per-page optimisation for heavy-tab users.

## 8. Measurement pitfalls (synthesis of sections 1–7)

| # | Pitfall | Evidence | Conf. |
|---|---|---|---|
| 8.1 | RSS counts shared clean pages (binary text, dyld shared cache, mapped fonts) in every process, so summing RSS over many processes double-counts; on macOS RSS was 3.5–4.6× footprint for empty renderers. | 3.4, 3.5 | High |
| 8.2 | PSS depends on how many other processes map the page, so it changes when unrelated tabs open or close. | 1.3, 1.4 | High |
| 8.3 | USS/private excludes shared memory, so IPC and GPU shared buffers fall out of every process's total unless attributed by policy. | 1.3, 1.5 | High / Medium |
| 8.4 | Compressed and swapped memory: macOS footprint and Linux VmSwap count pages at uncompressed size; actual RAM use is lower, energy cost of compression is not shown. | 1.5, 1.6 | Medium |
| 8.5 | Windows commit counts reserved-and-committed but untouched memory and is not reduced by `MEM_RESET` discards; working set can be trimmed by the OS without memory being freed. | 1.3, 1.7 | High |
| 8.6 | GPU memory is attributed differently per OS (macOS charges IOSurface/graphics to the owning process footprint; elsewhere it may be driver memory outside any process); it drifts strongly over time. | 3.3, 7.5 | Medium |
| 8.7 | One dump after forced GC understates real use; time-series sampling is needed. Telemetry sampling must avoid observer effect (measureMemory forces GC after 20 s). | 1.10, 7.3 | High |

## 9. Open questions and gaps

- No published, per-category breakdown of renderer memory over a real-site corpus (fonts, style, layout, IPC, canvas, media, network cache) exists that we found; Izcal will have to produce its own with full attribution (a milestone, not an assumption).
- Empty-process cost on Linux and Windows for current Chrome and Firefox was not measured; it should be measured on `hueyj` and `rig253` with the same method as 3.3 (book the rigs; read-only process inspection).
- What owns Chrome's "App-Specific Tag 14/16" regions on macOS (likely Chromium allocator/V8 tags) was not identified.
- Safari/WebKit WebContent fixed cost was not measured (to avoid disturbing the user's Safari); WebKit publishes no per-process figures that we found.
- The JS 35% / DOM 10% split attributed to the V8 team (2.4) has no located primary source.
- No modern per-subsystem energy split for desktop browsing; Izcal would need its own power-rail or OS energy counters (RAPL on Linux, `powermetrics` on macOS, E3/EMI on Windows).
