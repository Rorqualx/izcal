# Izcal resource footprint: gaps and opportunities

Compiled 19 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers, code review records).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Strand: how users experience browser resource use, what browsers show and hide today, what developers can and cannot measure, the platform levers that let sites cooperate, and ideas that no shipping browser implements. M-1 applies: everything below is ideas and evidence, not code or templates. The web-search budget ran out before every item could be checked against a primary source; those items are graded Medium or Low and listed in Section 11.

## 1. What users experience: tab hoarding, crashes, complaints

**Implications:** The evidence that resource use hurts users is real but thin: crashes from tab overload (25% of one small sample), vendor-framed battery claims, and forum anecdotes. No browser publishes tab-count or footprint distributions. Izcal should publish its own measured distributions (opt-in telemetry or corpus runs) rather than repeat vendor numbers, and should design for the long tail (100+ tabs), which is where crashes happen.

**Implications:** Users outsourced footprint control to extensions, and the most popular one became malware; that is an argument for footprint control being a first-party, engine-level feature. Every vendor's mitigation is a policy layered on top of an engine not designed for it (discard = reload, thresholds unpublished, savings unpublished). Izcal can publish thresholds and measured effects, which no vendor does.

## 4. What no browser shows (the user-facing gap)

| # | Gap | Evidence it matters | Conf. |
|---|---|---|---|
| 4.1 | **Attribution to third-party scripts and ads inside a page.** No browser UI says "this tab is heavy because of script X from origin Y". Cross-site iframes are visible only as separate processes | Ads are **>15% of page-load workload, ~88% of it JavaScript**, and two ad domains cause 35% of ad cost ([adPerf, arXiv 2002.05666](https://arxiv.org/abs/2002.05666), 2020-02-06). 92% of pages load third parties; median 27 per page (top 1M), 66 for top 1k ([Web Almanac 2024](https://almanac.httparchive.org/en/2024/third-parties)) | High |
| 4.2 | **Why a tab is heavy** (cause, not total): leaked detached DOM, retained images, timers firing in background, an animation that never stops, a worker spinning | Chrome found timers are >40% of background-tab work (1.6) but shows users no per-tab wakeup count | High (Chrome finding) / Medium (gap) |
| 4.3 | **Per-site energy.** No browser reports measured energy per site to users; Firefox and WebKit use CPU as a proxy | 3.4, 3.7 | Medium |
| 4.4 | **Cost over time.** Hover cards and task managers are instantaneous; none shows "this site cost N mWh / N GB-hours today" or a history | No counterexample found | Medium |
| 4.5 | **What the browser did about it.** Discard, freeze and throttle decisions are invisible, or a single "tab was discarded" badge; Chrome's `chrome://discards` is a debug page. The heavy-ad "Ad removed" frame is the one place a user is told why | [Heavy ad interventions](https://developer.chrome.com/blog/heavy-ad-interventions) | High |
| 4.6 | **Extensions' share.** Shown as separate processes in task managers, but content scripts' cost inside a page is not attributed | No counterexample found | Low |

**Implications:** The highest-value missing feature is **causal attribution**: bytes, CPU time, wakeups and energy charged to (site, frame, script URL, cause), shown in the browser UI. Because it is browser UI and not a web API, it does not leak cross-origin information to pages (see 5.6), so it is not limited by the privacy constraints that limit developer APIs.

## 6. Web platform levers that let sites cooperate

| # | Lever | Status and evidence | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **Page Lifecycle** (`freeze`/`resume`, `document.wasDiscarded`) | States active, passive, hidden, frozen, terminated, discarded. **Chrome 68+/Edge 79+ only; not Firefox or Safari.** Guidance: in frozen, close IndexedDB, BroadcastChannel, WebRTC, WebSocket; release Web Locks; hidden is the last reliably observable state | [Chrome for Developers](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) | updated 2026-10-16 | High |
| 6.2 | **bfcache** | All major engines have one; a cached page is a full in-memory snapshot including the JS heap and is evicted "after a period". `unload` deprecated in Chrome; Firefox desktop makes `unload` pages ineligible; `no-store` work "underway" in Chrome, unshipped. Blockers: `unload` on 20% of top-1k mobile pages, `no-store` on 23% of sites | [web.dev bfcache](https://web.dev/articles/bfcache); [Web Almanac 2025](https://almanac.httparchive.org/en/2025/performance) | 2026-10-16 | High |
| 6.3 | **Background throttling** | Chrome M87: timer wake-ups in background tabs limited to **once per minute**; "up to 5x" less CPU and "up to 1.25 hours" more battery in internal tests; occlusion tracking: up to 25% faster start, 7% faster loads | [Chromium Blog](https://blog.chromium.org/2020/11/tab-throttling-and-more-performance.html) | 2020-11-17 | High |
| 6.4 | **scheduler.postTask / yield** | Chrome 94/129, Firefox 142; not Safari | `research_notes/Browser user pain points 2026/performance_compat.md` (MDN BCD 2026-10-08) | 2026-10-08 | High |
| 6.5 | **content-visibility, lazy loading, priority hints (`fetchpriority`)** | Let sites skip rendering/fetching off-screen work; all are hints the browser may honour. Not re-checked for this note | MDN (not fetched) | — | Low |
| 6.6 | **Battery Status API removal** | Olejnik, Acar et al. ("The leaking battery", 2015) showed battery level, and (on Linux) high-precision capacity, could link identities over short intervals. Mozilla found no "legitimate use cases" and removed it from web content in **Firefox 52 (March 2017)**; Safari never shipped it; MDN lists it as limited availability, secure context only | [Olejnik blog](https://blog.lukaszolejnik.com/battery-status-not-included-assessing-privacy-in-w3c-web-standards/); [Bugzilla 1313580](https://bugzil.la/1313580); [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Battery_Status_API) | 2015–2017 | Medium |

**Implications:** The cooperation levers that exist are mostly Chromium-only (Page Lifecycle, measureUserAgentSpecificMemory, Compute Pressure, crash reports), and the one energy signal that was cross-engine (battery) was removed for privacy. A site today cannot learn "you are over budget" or "the device is on battery" without a fingerprinting cost. Izcal should support the standard levers (bfcache, lifecycle, scheduler) and treat any new signal as a privacy design problem first: coarse, rate-limited, and preferably one-way (browser tells site to shed load; site learns nothing about the device).

## 7. Prior art: browser-enforced budgets and interventions

| # | Attempt | What it did | Fate and real reason | Source | Conf. |
|---|---|---|---|---|---|
| 7.1 | **Chrome heavy ad intervention** (Chrome 85, Aug 2020) | Unload an ad frame (with descendants) the user has not interacted with when it exceeds **4 MB network, 15 s CPU in any 30 s, or 60 s total CPU**. Thresholds set at the **99.9th percentile** of ads; **0.3% of ads exceed them but use 27% of ad network data and 28% of ad CPU**. Frame replaced by "Ad removed"; report to the site | **Shipped and still live.** It succeeds because it is narrow: only ad-tagged frames (Chrome's ad tagging), only non-interacted, only extreme outliers, with noise for privacy and months of notice to the ad industry | [Chromium Blog](https://blog.chromium.org/2020/05/resource-heavy-ads-in-chrome.html) (2020-05-14); [Chrome for Developers](https://developer.chrome.com/blog/heavy-ad-interventions) | High |
| 7.2 | **Never-Slow Mode** (Alex Russell, 2019) | Per-interaction budgets reset on interaction: per-script 50 KiB, total script 500 KiB, images 1 MiB each / 2 MiB total, stylesheets 100 / 200 KiB, fonts 100 KiB, 10 connections, long tasks >200 ms pause page execution; wire sizes; behind a flag | **Prototype, never shipped; no published outcome.** Press reported the author's warning that the flag could silently break content. Lesson, from first principles rather than a postmortem: bytes map poorly to user-visible cost, and enforcement without UI or opt-in has no constituency. (Details first read from the code review, an engine source record, were removed (0.3.1 source-evidence pass, HGBA-2 M-1 part 3).) | [BleepingComputer, 2019](https://www.bleepingcomputer.com/news/google/google-working-on-chrome-never-slow-mode-for-faster-browsing/) | Medium |
| 7.3 | Background timer throttling (Chrome 87), freezing on Energy Saver (Chrome 133), Firefox tab unloading, Edge sleeping tabs | See 2.2–2.5, 6.3 | All shipped. Common limits: thresholds unpublished or vague ("CPU-intensive"), savings unpublished except the 2020 Chrome numbers, opt-outs via origin trials | — | High |
| 7.4 | Opera GX user-set RAM/CPU limits | User budget for the whole browser, not per site | Shipped in a niche product; internals undocumented | 2.6 | Low |
| 7.5 | Feature-Policy "performance policies" (oversized-images, unoptimized-images, sync-xhr etc.) | Site-declared self-limits | Only `sync-xhr` survived in Permissions Policy; image policies were not shipped (from memory, not re-checked) | — | Low |

**Implications:** The successful intervention (heavy ads) is narrow, outlier-targeted, privacy-noised, announced months ahead and explained to the user. The failed one (Never-Slow Mode) was broad, byte-based, broke content and had no UI. A per-site budget in Izcal should follow the first pattern: charge **user-visible cost** (CPU time, wakeups, memory-time, energy) not bytes, act on outliers, tell the user what was done and why, and give the site a report and a way to cooperate (lifecycle events) before enforcement.

## 8. Ad and tracker blocking as a footprint lever

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | Independent study of 15 Android browsers: **ad blocking saves 20–40% battery** depending on browser; dark mode adds ~10% on AMOLED | 20–40% | [Varvello & Livshits, arXiv 2009.03740](https://arxiv.org/abs/2009.03740) (Brave Research authors) | 2020-08-06 | High (abstract) |
| 8.2 | Brave's test (Galaxy S9, 20 sites, ~1 h per browser, ADB over Wi-Fi): Chrome 124 mAh, Edge 132, Firefox 164 (likely overstated by ~15 mAh), **Brave 80**; ad-blocking browsers ~90–100; Firefox+uBO ~90. ~40% less bandwidth; user CPU time about half | mAh | [Brave blog](https://brave.com/blog/brave-saves-batteries/) | 2019-02-27 | Medium (vendor) |
| 8.3 | adPerf: ads are >15% of page-load workload, ~88% of ad cost is JS; Adblock Plus itself adds 32% median overhead from rule matching even while net load time falls | 15% / 88% / 32% | [arXiv 2002.05666](https://arxiv.org/abs/2002.05666); overhead figure from search snippet | 2020-02-06 | High / Medium |
| 8.4 | Ad blockers cut data use significantly but load-time gains are limited (news sites, five blockers in Chrome) | — | [Garimella et al., arXiv 1705.03193](https://arxiv.org/abs/1705.03193) (WebSci 2017) | 2017-05-09 | Medium |
| 8.5 | The blocker's own cost matters: Brave's Rust ad-block engine rewrite cut its memory ~75% (~45 MB) | ~45 MB | [Brave](https://brave.com/privacy-updates/36-adblock-memory-reduction) (via `reports/Browser user pain points 2026.md`) | 2026-01 | Medium |

**Implications:** Blocking is the largest single footprint lever with independent evidence (20–40% battery on mobile). It is also a source of overhead if implemented as extension-side rule matching. Izcal owns its network stack (HGBA-2 4.7) and style pipeline, so blocking can run in the network service with a compiled matcher, and its saving can be **measured per site** and shown to the user, which no blocker does with measured data.

Causal resource attribution** (bytes, CPU ns, wakeups, energy estimate, memory-time charged to site → frame → script URL → cause) shown in browser UI | 4.1, 4.2: ads >15% of workload; 92% of pages carry third parties; timers >40% of background work | Process-level task managers (3.1–3.4); LoAF script attribution is lab/field and partial (5.3); `measureUserAgentSpecificMemory` breakdown is coarse and Chromium-only | Own JS engine (spec in progress) can tag allocations and tasks by realm and script at the source; data plane and semantic tree already carry **origin and frame provenance** (HGBA-3 B8); own network service gives exact bytes per (site, frame, request initiator); B2 typed IPC can charge shared-memory and IPC to the requesting principal; engine-drawn UI (D-S2) can overlay attribution on the page itself | Cost of tagging on hot paths (CS-PF budgets); attribution of shared structures (strings, shapes, code caches) needs a stated rule (proportional, first-allocator, or "shared" bucket) |
| **B. Per-site resource budgets enforced by the browser** | Heavy ads: 0.3% of ads → 27–28% of ad cost (7.1); outliers dominate | Heavy-ad intervention shipped (narrow); Never-Slow Mode abandoned (broad, byte-based, broke pages) | Same as A; plus B1 virtual clock and scheduler make budgets on wakeups and CPU exactly enforceable and testable; per-site process (I-1) gives an OS-level backstop (cgroups/job objects) | Breaking sites; who sets defaults; privacy if limits are observable (noise as Chrome does) |
| **C. User-set budgets** ("this site may use at most X while in background"; "on battery, cap everything at Y") | Opera GX demand signal (2.6); Edge/Chrome expose only modes, not numbers | Opera GX (whole-browser, undocumented) | Per-site attribution (A) is the prerequisite; shell is HTML rendered by Izcal so per-site settings live beside permissions | Users cannot reason about MB; must be phrased as outcomes (battery, "keep this tab alive") |
| **D. Energy labels per site** (A–G style, from measured cost per visit or per hour) | Battery is a vendor marketing axis (1.9); EcoIndex A–G labels exist but score proxies (DOM size, requests, bytes), not measured energy ([EcoIndex example](https://www.spie.com/en/environmental-statement)) | EcoIndex (proxy-based, site-published); WebKit energy rating from CPU (3.7) | Measured per-site energy model from A; DST corpus runs give reproducible labels for a fixed corpus | Energy models from counters are platform-specific (RAPL, Apple power metrics, Windows EMI); labels may be gamed; legal/branding issues |
| **E. Snapshot-to-disk suspend** (serialize a frozen page's JS heap, DOM/data plane and layout to disk; restore without reload) | Every shipping discard reloads and loses state (2.7); discarding is how browsers survive tab hoarding (2.2) | **No shipping browser restores a live web page heap from disk** (search found none); bfcache keeps the snapshot **in memory** only (6.2); V8 startup snapshots serialize only engine-controlled heaps (known, not re-checked) | Own JS engine can design a serializable heap; B1 already requires a serializable boundary (mutation log) and a virtual clock, so "time passed while suspended" is a defined input; frozen-state semantics (6.1) already say connections close, which matches bfcache eviction rules | Unmeasured; open sockets, GPU contexts, workers, SharedArrayBuffer, cross-process references; disk is user data → must be encrypted and tied to profile; disk wear; restore latency vs reload |
| **F. Deterministic footprint measurement in CI** (allocation counts, peak live bytes, wakeups, instruction counts per corpus page, bit-identical across runs) | Field APIs are noisy and privacy-limited (5.1–5.6); wall-clock and energy benchmarks are noisy | Lab tools (Lighthouse budgets) measure bytes/timings with noise; no browser gates PRs on deterministic memory | **HGBA-3 B1 DST**: seeded scheduler and virtual clock make allocation and wakeup counts reproducible; M0 found V8 deterministic under the predictable platform on three OSes; CS-PF already has allocation and instruction-count gates. Energy itself is not deterministic, but its drivers (wakeups, instructions, bytes) are | DST covers JS/engine, not GPU, audio, media (HGBA-3 B1 caveat); counts must be validated against real PSS/energy on reference devices |
| **G. Footprint report for site developers** (same attribution as A, offered to a site about itself in DevTools and in deterministic replays) | 5.2–5.5: no cross-engine field tools; WebKit OOMs invisible to developers | LoAF, measureUserAgentSpecificMemory, crash reports (Chromium only) | `hg-devtools` (D-S11) plus B1 replay: a developer can replay a recorded session and get exact allocation and wakeup attribution; crash/OOM reports can carry the same cause classes | Must not expose other origins' data; replay excludes GPU/media |
| **H. Sharing between same-site tabs** | Many tabs per site is the hoarding pattern (1.5) | Chrome reuses same-site processes only over a soft process limit or for OOPIFs ("aggressive reuse"); Chrome **turns site isolation off on Android <2 GB** to save memory ([Chromium process model](https://chromium.googlesource.com/chromium/src/+/main/docs/process_model_and_site_isolation.md)) | I-1 permits same-site documents in one process; Izcal's engine can share immutable data (parsed stylesheets, compiled code, decoded images, fonts) across same-site documents by design rather than heuristically; broker-allocated shared memory (HGBA-2 4.6) can share read-only data across processes of the same site | Same-site is not same-origin; sharing must not cross the site boundary (P1); one heavy tab can starve its siblings in a shared process |
| **I. Built-in blocking as a measured footprint lever** | 8.1–8.3 | Brave (native, Rust); extensions (MV3 limits) | Own network service and style pipeline (HGBA-2 4.7); per-site measured savings from A | Breakage; list governance; site retaliation (anti-adblock) |
| **J. One-way "shed load" signal to sites** (browser tells a page it is over budget or the device is constrained, revealing nothing precise) | Battery API removed for fingerprinting (6.6); Compute Pressure is coarse (5.4); Chrome's freeze opt-out waits on a "Progress Notification API" (2.5) | Battery Status (removed), Compute Pressure (Chromium only), Page Lifecycle (Chromium only) | B1's injectable randomness makes coarse, noised signals replayable and testable | Any new signal is a fingerprinting surface; needs a privacy budget analysis |

**Implications:** A (attribution) is the foundation for B, C, D, G and I; without it the others repeat other browsers' unexplained thresholds. F is the clearest case where Izcal can do something no browser can, because it depends on B1. E is the most novel and least evidenced; it should be a measured spike, not a commitment.

## 10. Lessons for the synthesis

| Project | What happened | Lesson | How Izcal applies it |
|---|---|---|---|
| Chrome heavy ad intervention | Narrow, outlier thresholds at the 99.9th percentile, noised, announced, explained to the user; shipped and still live | Enforcement works when it targets outliers, explains itself, and gives the site a report | Per-site budgets act on outliers, show the user why, and report to the site |
| Never-Slow Mode | Broad byte budgets with task pausing, no UI, no opt-in; abandoned 2021 | Byte budgets do not equal user cost, and silent breakage has no constituency | Budget user-visible cost (CPU, wakeups, memory-time, energy), never raw bytes alone |
| Chrome M87 throttling | Measured that timers are >40% of background work and published the result | Measure first, then pick the lever | Publish measured causes and savings for every Izcal intervention |
| The Great Suspender | Users relied on an extension for footprint control; it was sold and became malware | Footprint control is too important to leave to third-party code | First-party suspend/attribution in the engine and shell |
| Battery Status API | Removed for fingerprinting | Device and resource signals to pages are privacy surfaces | Prefer browser-side action and UI over web-exposed numbers; any signal is coarse, noised, one-way |
| measureUserAgentSpecificMemory / LoAF | Useful but Chromium-only, COI-gated, partial attribution | Field APIs are constrained by privacy; lab determinism is not | Put precise attribution in DevTools and DST replay, not in a web API |
| Firefox tab unloading | Crash reductions reported but not quantified | Unpublished results cannot be built on | Izcal publishes thresholds and before/after numbers |
