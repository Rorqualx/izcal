# Izcal coding standard: testing and performance as code-level practice

Compiled 2026-10-18. Primary sources were preferred (papers, project documentation, maintainers' posts, policy pages, tool documentation). Where another browser is cited, the source is its public documentation or policy page, never its code (M-1, D-S10). Ideas and practices only; nothing here is a template.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a well-known fact not re-fetched this session; **Low** = secondary source only.

Scope: this strand covers **testing and performance at the level of the code a contributor writes and the rules a PR must meet**. Error handling, type design, async, concurrency structure and module layout belong to the other two strands. The system-level strategy is already decided and is not reopened here: CI tiers T0–T3, oracles as infrastructure, the DST farm, fuzzing campaigns and the performance lab (Stage 1 design §7), simulation mode (§3.2), resource targets RES-1 to RES-5 (§13.3), B1, B5, ORC-1, VER-1, EQ-1, DST-1 and DET-1 (HGBA-3), P-1 and M-1 (HGBA-2). This note supplies the code-level rules that make those work.

Clippy lint names and groups in this note were checked locally against **clippy 0.1.99 / rustc 1.99.1 (2026-10-13)** with `clippy-driver -W help` and `cargo clippy --explain`.

## 0. Frame

**Problem.** Izcal has architecture specs and repository hooks (rustfmt, gitleaks, the `security` and `provenance` checks, AI review) but no rule for what a test must look like, when one is required, what to do with a flaky test, or how a contributor shows that a change does not slow the engine down. Most of Izcal's code will be written with AI help (Stage 1 §7.2, HGBA-3 §6), so EQ-1 (gated generation is not riskier) depends on the tests being real oracles and not echoes of the implementation.

**What the specs already fix.**
- **G3**: only `hg-substrate-os` may name `std::time`, `std::thread`, `std::net`, `std::fs`, `std::process`, `rand::thread_rng`, `getrandom` or `Instant::now`, enforced by `hg-graph-lint` and `clippy::disallowed_methods`/`disallowed_types`. Tests outside that crate therefore cannot use a real clock, real threads or a real network, *provided clippy also runs on test targets*.
- **T0** (≤20 min per PR) already contains unit and property tests, Kani harnesses for changed IPC messages, WPT smoke, and 200 DST seeds. T1 adds full WPT and 10k seeds; T2 adds fuzzing and corpus performance.
- **G5**: `#![forbid(unsafe_code)]` except crates in `unsafe-inventory.toml`. **VER-1**: Tier 1 parsers are generated, proven or Kani-checked.
- **Performance lab**: an A/B run per merge on one device, nightly on four; metrics are p95 interaction latency, frame time, style and layout time (P-1), memory (INC-3, RES-3), energy.

**Success, measurably.** Every PR rule below is either checked by a machine (lint, hook or CI job, named) or explicitly marked review-only; the flake rate of the T0 gate stays below a stated bound; and perf regressions in hot kernels are caught per PR by a deterministic metric rather than waiting for the nightly lab.

## 1. Chronology at a glance

### 1.1 Testing practice

| Year | Step | Driving constraint | What survived |
|---|---|---|---|
| 1990s–2000s | WebKit layout tests: a page plus a checked-in `-expected.txt` dump, with a `TestExpectations` file for known failures | Rendering output is too large to assert by hand; many ports with different results | Golden output plus an expectations file, now in every engine |
| 2000s | SQLite's TH3 harness reaches 100% branch and 100% MC/DC coverage | Embedded in avionics-class products; no second chance after shipping | Anomaly testing (OOM, I/O error, crash) and asserts as a debug-only oracle |
| ~2009 onward | FoundationDB builds its database inside a single-threaded deterministic simulator before writing the database | Distributed bugs cannot be reproduced on real clusters | Seeded DST, replayable failures |
| 2010 | Google publishes test sizes (small, medium, large) by allowed resources, not by scope | Thousands of engineers sharing one CI; nondeterministic tests poison it | Hermeticity enforced by the runner, not by convention |
| 2010s | Firefox: Treeherder, OrangeFactor, a written test-disabling policy with numeric thresholds, sheriffs | Thousands of intermittent "oranges" per week | Numeric quarantine thresholds plus an escalation clock |
| 2013 | WPT (web-platform-tests) becomes the shared cross-engine suite | Each engine had its own incompatible tests | Spec-anchored tests shared by all engines; per-engine expectation files |
| 2014 | Inozemtseva & Holmes: coverage is not strongly correlated with test effectiveness | Coverage targets were being used as quality gates | Coverage as a locator of untested code, not a target |
| 2016 | Google: 1.5% of test runs flaky, 16% of tests have some flakiness | Scale of TAP | Flakiness treated as a budgeted, measured cost |
| 2016–2017 | Firefox test-verify: new or changed tests run 10 + 5 times, then again in chaos mode, before they count | New tests were the main source of new intermittents | Pre-merge repetition of new tests |
| 2017 | V8 retires Octane: optimizing for it hurt real pages | Microbenchmark overfitting | Real-world workloads over microbenchmarks |
| 2018 | Google surfaces mutants in code review for 6,000 engineers | Coverage said nothing about assertion quality | Diff-based, review-time mutation testing |
| 2019–2023 | Rust tooling matures: proptest, cargo-fuzz with `arbitrary`, Miri in std CI, loom, shuttle (ShardStore: 16 issues stopped before production, SOSP 2021), Kani (Firecracker CI), nextest | Rust gives memory safety but not logic, UB-in-`unsafe` or interleaving safety | Layered checkers, each for one class of bug |
| 2020s | TigerBeetle VOPR and TIGER_STYLE: assertion density ≥2 per function, static allocation, DST as "final line of defense" | Financial database; correctness first | Assertions as the fuel for fuzzing and DST |
| 2023 | Chromium CI study: LUCI retries a failing test up to 5 times; flaky tests revealed over one third of regression faults | Retry-based flake handling hides real bugs | Treat flaky *failures*, not flaky *tests*, as the unit |
| 2024 | LLM-generated test oracles tend to encode actual, not expected, behaviour | AI-written tests | Tests must come from the specification, not from the code |
| 2025–2026 | Rust 2024 merges doctests into one binary; Miri paper at POPL 2026 (>100,000 crates evaluated); iai-callgrind renamed gungraun | Test build cost; UB at ecosystem scale | Cheaper doctests; deterministic instruction-count benchmarks |

### 1.2 Performance-regression practice

| Year | Step | What it taught |
|---|---|---|
| 2000s | WebKit "zero-tolerance policy for performance regressions": back the patch out or drop everything and fix it | A rule only works if the default action (backout) is cheap and pre-agreed |
| 2009 | Mytkowicz et al., "Producing wrong data without doing anything obviously wrong!" (ASPLOS): setup changes such as environment size and link order bias results; none of 133 surveyed papers accounted for it | Wall-clock A/B on one binary layout can be wrong in sign |
| 2010s | Firefox Talos and Perfherder: alert on a sustained change (original point plus 12 future points), sheriffs triage within 3 days, `regression-backedout` tags | Change-point detection plus a human sheriff |
| 2016 | Chrome adopts PGO on Windows (M53): up to 15% faster; 2020, PGO with Clang on Mac and Windows (M85): up to 10% faster page loads | Build configuration is a performance feature worth CI time |
| 2017 | V8 retires Octane | Benchmark overfitting causes real regressions |
| 2018 | Firefox moves to clang + LTO on all tier-1 platforms, plus PGO on Linux: Talos >5% better on most tests, up to 18% on some | Same |
| 2018 | Chromium android-binary-size trybot becomes a mandatory CQ bot (16 KB arm32 / 64 KB arm64 per CL) with a `Binary-Size:` override footer | Size budgets enforced per CL, with an explicit, visible override |
| ~2019 | rustc-perf makes `instructions:u` its default metric: changes of about 0.3% detectable vs about 1% for wall time | Deterministic proxies make per-PR perf gates feasible |
| 2020s | Chromium perf dashboard auto-starts Pinpoint bisects on alerts; sheriffs may revert culprits | Automate bisection, keep humans for judgement |
| 2021 | Mozilla perf sheriffs report 3–7% of regression alerts invalid | Even good change detection needs triage |
| 2024 | Speedometer 3.0 released jointly by Apple, Google, Microsoft and Mozilla under consensus governance | Shared, real-app-shaped benchmarks |

Izcal's medium tier is the simulation substrate (§3.2): many simulated processes in one OS process, which is stricter than Google's medium. Real OS access belongs only to `hg-substrate-os`'s own tests and the perf lab.

## 3. Flakiness: rates, costs and policies

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|

| 3.2 | Google's later figure: flake rate "hovers around **0.15%**", which still means thousands of flakes a day. "As you approach **1% flakiness**, the tests begin to lose value." | 3.3 | Chromium CI (LUCI) reruns a failing test up to **5 times**; a test that passes after a failure in the same build is labelled flaky. | 3.4 | Chromium web tests: a test judged "truly flaky" is suppressed in `TestExpectations` by listing several allowed results (e.g. `[ Failure Pass ]`) with a `crbug.com/` reference; the file is "in theory" for temporary marks. LUCI Analysis lists top flake clusters with bug and failure counts | — | [Chromium web test expectations](https://chromium.googlesource.com/chromium/src/+/81.0.4044.122/docs/testing/web_test_expectations.md); [gtest flake tips](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/testing/gtest_flake_tips.md) | 2020 snapshot; live | Medium |
| 3.5 | Firefox test-disabling policy: a test is escalated when it is in the top 20 intermittents, fails **≥8%** of runs, or has **>100 instances in 30 days**; at **≥30%** it is disabled first. Escalation clock: bug and needinfo to the author (2 business days), then the module owner (2 days), then disable | 8%, 100/30 d, 30% | [Mozilla wiki, Test Disabling Policy](https://wiki.mozilla.org/Sheriffing/Test_Disabling_Policy) | last edited 2017-05-30 | High (page is old; current practice may differ) |
| 3.6 | Firefox **test-verify (TV)**: an added or modified mochitest runs 10 times, then 5 more in fresh browser instances, then the sequence repeats in chaos mode (`MOZ_CHAOSMODE`); a separate TVw job does this for WPT. Chaos mode found many more failures than normal mode, and its overhead can itself cause timeouts | 10 + 5 runs ×2 | [Firefox test verification docs](https://firefox-source-docs.mozilla.org/testing/test-verification/index.html); [bug 1390884](https://bugzilla.mozilla.org/show_bug.cgi?id=1390884); [bug 1812236](https://bugzilla.mozilla.org/show_bug.cgi?id=1812236) | live; 2017; 2023 | Medium |
| 3.7 | Servo marks known-intermittent results so try-run logs can ignore them; expectations reflect CI machines, and running all WPT locally is discouraged | — | [Servo book, testing](https://book.servo.org/contributing/testing.html) | live | High |
| 3.8 | cargo-nextest runs **each test in its own process**: no shared global state, a crash or memory corruption in one test does not take down others; timeouts kill only the slow test (SIGTERM, then SIGKILL after 10 s). It can retry failures and mark a test flaky if a retry passes. Cost: shared in-memory fixtures are harder, and process creation is slow on Windows and can be on macOS | — | [nextest, why process-per-test](https://nexte.st/docs/design/why-process-per-test/) | live | High |

**Implications:** retries hide real bugs (3.3) and erode trust past about 1% (3.2). Izcal's simulation substrate removes the usual causes (time, thread scheduling, network), so a flaky test outside `hg-substrate-os` is evidence of a determinism bug, which DET-1 treats as a ship blocker. The gate should therefore not retry. Detection belongs in a separate repetition job (3.6).

**Implications:** Miri cannot run code that calls V8 or other FFI, so for Izcal it covers only the pure-Rust parts of `unsafe` crates (unit tests with fake backends). ## 16. Lessons for Izcal: candidate rules

| PF-3 | **Allocation budgets as tests.** Key operations (restyle of N nodes, layout of a cached subtree, IPC encode/decode, a frame with no DOM change) have deterministic tests that count allocations with a counting global allocator or `dhat` and assert an upper bound. "No allocation in a clean frame" is a target the test checks | 14.6, 13.6, INC-3 (counting allocator already planned) | CI job (T0, deterministic) |
| PF-4 | **Deterministic per-PR perf gate.** Hot CPU-bound kernels (selector matching, style cascade, layout driver, display-list build, IPC codecs, URL and HTML-adjacent parsers) have gungraun instruction-count benchmarks on Linux CI. An increase above 1%† on any benchmark fails unless the commit carries a `Perf: <reason>` trailer (Chromium `Binary-Size:` model). Wall-clock benchmarks (criterion/divan) are for local work, not gates | 13.1, 13.2, 12.5 | CI job + hook (`commit-msg` validates trailer) |
| PF-5 | **Backout-first for lab regressions.** A sustained regression in a lab metric (P-1, RES-*) on the merge A/B run is attributed by automatic bisection, and the default action is revert; the author may instead land a fix within 2 business days†. Alerts are triaged within 3 days | 12.1–12.4 | CI job (bisection bot) + process |
| PF-6 | **No microbenchmark-only justification.** A PR that adds complexity or `unsafe` for speed must show the gain on a corpus workload or on an instruction-count benchmark of a real call path, not only on a synthetic loop | 13.3–13.5 | review only |
| PF-7 | **Inlining policy.** No `#[inline(always)]` without a benchmark in the PR (`clippy::inline_always` warns); `#[inline]` only on small non-generic functions called across crates in hot paths, since rustc already infers the trivial cases; `#[cold]` and `#[inline(never)]` on error and slow paths | 14.3, 14.4 | lint + review |
| PF-8 | **Generics in hot loops, `dyn` at boundaries.** Hot inner loops use generics (or concrete types); embedder, plugin and agent-tool boundaries use `dyn`. Generic functions keep their non-generic body in an inner function. Per-crate `cargo llvm-lines` and binary size are reported per PR; installer size growth above 256 KB†/PR needs a `Binary-Size:` trailer (RES-4) | 14.7, 12.5, RES-4 | CI job (report + threshold) + hook |
| PF-9 | **Bounds checks through structure, not `unsafe`.** Use iterators, slice-then-index and length assertions. `get_unchecked` and SIMD intrinsics are `unsafe`, so they fall under G5's inventory and Tier 2 Kani harnesses, and need an instruction-count benchmark showing the gain | 14.5, G5 | lint (G5 `forbid(unsafe_code)`) + review |
| PF-10 | **Reproducible PGO.** Release PGO profiles are collected by running the recorded corpus in simulation mode, so the profile, and therefore the binary, is reproducible from the corpus archive plus seed | 15.1–15.4, §3.2, DET-1 | CI job (release pipeline) |
| PF-11 | **Allocator choice by measurement.** The global allocator is chosen per platform in the perf lab (system vs mimalloc†) on RES-3 and P-1, not by default. Safe Rust gets no UAF protection benefit from the allocator; hardening effort goes to the heaps that still have manual memory (V8, `cppgc`, C libraries) | 15.5, 15.6 | review only (decision record) |
| PF-12 | **Back-of-the-envelope sketch for hot-path designs.** A design or PR that changes a per-node, per-frame or per-message path states its expected cost in CPU, memory and IPC bytes before measuring | 5.3 (TigerBeetle) | review only |
