# Izcal extensions: distribution and signing

Compiled 20 October 2026. Primary sources were preferred (vendor docs, security blogs, transparency reports, news quoting primaries).
Confidence: **High** = primary source read and checked; **Medium** = snippet/vendor claim; **Low** = secondary only.

| 5 | Enforcement outcomes are tiered: approve / reject (email explanation) / warning with a fix deadline (typically 7–30 days) / takedown; for "extreme violations" (malware, review evasion) the takedown is immediate with no advance notice, possibly permanent account suspension, and the extension is disabled on users' devices with no re-enable option. | 7–30 day warning windows | developer.chrome.com/docs/webstore/review-process | current | High |

| 8 | Off-store installation is forbidden on the channels that matter: since Chrome 33 (Windows) and Chrome 44 (macOS) no external installs from local CRX files are allowed, and on those platforms the install `update_URL` must point to the Chrome Web Store. | Chrome 33 / Chrome 44 | developer.chrome.com/docs/extensions/how-to/distribute/install-extensions | current | High |
| 9 | Linux is the documented exception: a preferences JSON can point to an external `update_url` (XML update manifest), or a local CRX via `external_crx`, and installs happen automatically with no confirmation prompt. | — | developer.chrome.com/docs/extensions/how-to/distribute/install-extensions | current | High |

**Implications:** Google's design bets everything on one chokepoint — the store — and pays for it with a review queue whose tail latency (3+ weeks) is the community's top grievance and a reputational attack surface for the vendor. Nothing about the fee, verification, or appeal record is published in machine-checkable form. Izcal should treat "store-only + opaque review" as the anti-pattern: keep a store, but make review state, timings and decisions published artifacts.

| 11 | Mozilla's stated rationale was that blocklisting was reactive — users were harmed before malicious add-ons were identified — so validation moved to before-install signing; Mozilla simultaneously committed to automation and reviewer headcount, targeting ~5 days for new listed reviews and 1–2 days for updates. | targets: 5 d new / 1–2 d updates | blog.mozilla.org/addons | 2015-08-21 | High |

| 13 | Self-distribution of signed XPIs is a first-class path: host the signed `.xpi` with `Content-Type: application/x-xpinstall`, installable via plain link (top-level frame only) or from file; `InstallTrigger` was deprecated and removed in Firefox 144. | InstallTrigger removed FF 144 | extensionworkshop.com self-distribution | current | High |
| 14 | Unlisted add-ons get a documented update mechanism: if the manifest declares an `update_url`, Firefox installs any higher version found there; if there is no `update_url`, Firefox falls back to checking AMO for a newer listed version. The prose does not document key-pinning or how update signatures are validated in this path — a documentation gap. | — | extensionworkshop.com self-distribution | current | High |
| 15 | The "Recommended Extensions" program is Mozilla's curated tier: staff review for functionality, safety, UX and broad relevance; status carries an explicit Mozilla endorsement badge; it is maintained by automated checks, post-publish monitoring and periodic manual re-review, with removal possible at any time (abandonment, quality decay, better alternatives). Developers commit to active maintenance as a condition. | deliberately small curated set | extensionworkshop.com recommended-extensions | current | High |
| 16 | Enterprise installs bypass the store entirely via policy (`ExtensionSettings`, force-install by URL, or bundling add-ons with a custom build); the consumer release still refuses unsigned code everywhere except dev channels with the pref flipped. | — | extensionworkshop.com; mozilla policy-templates | current | High (paths) / Medium (unsigned-via-policy detail) |

**Implications:** Firefox proves a hybrid model: mandatory vendor signing (trust root = Mozilla) combined with self-distribution of the signed artifact, so the store is a discovery/curations service, not an install monopoly. Its weakest documented point is the update path for self-distributed add-ons — the docs describe behavior but not the cryptographic guarantees, and the one time the signing infrastructure itself failed (see §6) every extension broke at once. Izcal should design the signature scheme so the signer never becomes a single point of failure for already-installed software.

Izcal can borrow the invariant (users can only run bytes that were reviewed) without the wrapper, if the signature/transparency-log design below preserves it.

## 4. Update mechanisms and the update-server attack surface

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 21 | Chrome's update path is store-mediated: the Web Store's update URL is `clients2.google.com/service/update2/crx`; on Windows/macOS the install `update_URL` must point there; self-hosted XML update manifests are documented only for the Linux external-install path. | — | developer.chrome.com install-extensions doc | current | High |
| 22 | Firefox's unlisted update path is developer-hosted: manifest `update_url`, Firefox pulls any higher version; the fetched prose documents no pinning/verification details for that URL. | — | extensionworkshop.com self-distribution | current | High |
| 23 | Copyfish (Jul 2017): phished the developer team's Google account, pushed a malicious update through the Web Store to >30,000 users (ad injection); the same campaign (Proofpoint, Aug 2017) hijacked multiple extensions and attempted to harvest SteemIt users' private keys; Google disabled the infected versions remotely. | >30,000 users, Copyfish | ui.vision postmortem, Proofpoint, Ars Technica, press | 2017-07/08 | Medium |
| 24 | "Web Developer" (reported Sep 2016): the extension (~1M users) turned malicious after its ownership/account changed hands and a spyware update was pushed through the store; coverage differs on whether the author's account was compromised or the extension was sold. Sources conflict on the exact mechanism. | ~1M users | press coverage; arXiv 2503.04292 catalog | 2016-09 | Low |
| 25 | The Great Suspender (Feb 2021): original developer sold the extension; new owners added tracking/credential-grabbing code; Google removed it from the store and force-disabled it on users' machines — some users lost saved suspended-tab sessions. | ~2M users | The Hacker News, BleepingComputer, The Verge | 2021-02 | Medium |
| 26 | The documented pattern across incidents: the compromise is almost never of the review process — it is of the *publisher identity or update channel* (phished account, sold account, hijacked update server), and auto-update then converts a clean reviewed artifact into malware within hours of approval. | — | synthesis of rows 23–25 | — | Medium |
| 27 | Chrome's mitigations when things go wrong: remote disable of infected versions (Copyfish 2017) and store-wide disable with no re-enable for malware-designated items (Great Suspender 2021, review-process doc) — i.e., the same kill switch that makes updates dangerous also makes recovery possible. | — | developer.chrome.com review-process; press | current | High |

**Implications:** Update servers are the single most exploited component in extension distribution history. Every major incident is "trusted artifact + hijacked channel." Izcal should therefore (a) sign updates with keys independent of any web-account credential, (b) make update manifests verifiable and externally auditable (transparency-log style), and (c) plan the kill switch — but also plan *recovery of user state* when a kill switch fires (Great Suspender users lost tab sessions).

## 5. Governance published-ness (the root-program gap)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 28 | Google publishes enforcement episodically, not systematically: the Oct 2018 "Trustworthy Chrome Extensions, by default" post is the canonical example — obfuscation/minification banned, extension code review required for new submissions. | — | blog.chromium.org/2018/10/trustworthy-chrome-extensions-by-default.html | 2018-10-01 | High (URL/title verified; body Medium) |
| 29 | Google's own statistics from that post (per search snippet; body unrendered): over 70% of malicious/policy-violating extensions blocked contained obfuscated code; review data cited ~5% of obfuscated submissions found malicious vs ~0.3% of non-obfuscated — the clearest published rationale Google ever gave for a signature-adjacent policy. | 70% obfuscation; 5% vs 0.3% | blog.chromium.org (snippet) | 2018-10-01 | Medium |
| 30 | Neither Google nor Mozilla publishes a routine enforcement ledger: Google's numbers surface in occasional blog posts; Mozilla communicates via add-ons blog notices and has a public add-on blocklist, and its formal transparency reports cover government requests, not store enforcement. There is no equivalent of a CA/Browser Forum audit report or CT log for either store. | — | vendor sites; Mozilla transparency reports | current | Medium |
| 31 | The precedent Izcal's root-program model would import: CA/Browser Forum root programs require publicly published audit evidence and consistent decisions, and Certificate Transparency made issuance an append-only public log — neither extension vendor offers anything comparable; enforcement decisions are individual emails and dashboard states, invisible to third parties. | — | CA/B Forum / CT as analogy | — | Medium |

**Implications:** This is the widest open gap in the entire ecosystem and Izcal's clearest differentiation opportunity: publish every enforcement decision (with evidence hashes and policy citations) in an append-only, third-party-auditable log, so "why was this removed" is a URL, not an email thread. CT's lesson also applies negatively: public logs expose *reviewers'* mistakes too, which is exactly the consistency pressure stores lack.

## 6. Store review failures with published numbers

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 32 | June 2023: Google confirmed removing ~32–34 malicious extensions with roughly 75 million combined installs (ad injection / search-result tampering); press-cited vendor confirmation, no Google blog post with the analysis. | 32–34 extensions, ~75M installs | TechRadar / press citing Google | 2023-06 | Medium |
| 33 | Dec 2019 Avast/AVG: after Wladimir Palant published data-collection analysis, Mozilla removed the extensions from AMO within about a day and later reinstated them after fixes; Google's parallel removal lagged noticeably (Palant's own headline: "…What will Google do?"). | removal within ~24 h (Mozilla) | palant.info; BleepingComputer; BornCity | 2019-12 | Medium |
| 34 | May 2019 Firefox signing-certificate expiry: an intermediate signing certificate expired and disabled effectively all extensions on all desktop channels at once — the strongest single demonstration that vendor-keyed signatures are a systemic single point of failure. Mozilla shipped the fix via the Studies system in under 9 hours (Normandy at 02:44 UTC; 6–12 h to propagate), shipped 66.0.4 on May 5, permanent fix May 8, back-ports to Firefox 47–65 by May 14, and committed to deleting telemetry the hotfix collected. | all desktop channels; hotfix <9 h; full fix timeline 4→11 days | blog.mozilla.org/addons "Update regarding add-ons in Firefox" | 2019-05 | High |
| 35 | No vendor publishes upload-to-takedown latency as a metric; the closest documented data points are incident reconstructions (e.g., Copyfish: malicious update pushed within ~1 day of account compromise; Avast: Mozilla action within ~1 day of publication, after years of the behavior live). | — | incident coverage cited above | — | Medium |

**Implications:** Published takedown counts exist only sporadically and always vendor-narrated. Two distinct failure classes emerge: (1) *review misses* — malware lives for years (Avast) or ships in bulk (2023 removals); (2) *infrastructure failure* — the 2019 Firefox outage, where the trust mechanism itself, not any attacker, broke every extension simultaneously. Izcal's design must budget for both: independent verification so a review miss is containable, and distributed/threshold signing plus a documented revocation-and-recovery path so the signer is never a mass-brick trigger.

| 38 | Historical precedent: in 2014–2015 Google removed popular ad-blocking extensions from the store citing policy, later reinstating some amid developer outcry (widely reported at the time; the primary coverage was not reachable for this note). | 39 | Documented due-process structure in all three stores: rejection/takedown email + one appeal channel (Chrome), manual review + AMO blocklist with public notice posts (Mozilla), App Review with guideline citations and an appeals board (Apple). **Implications:** Lock-in events (MV2) and category purges (ad blockers) show that control over *distribution* converts into control over *product direction*, and developers' only leverage is exit. A new browser should commit contractually to published, versioned policies; decisions that cite the policy version in force; an independent appeal path whose outcomes are themselves published; and deprecation timelines long enough (Google's 3.5-year MV2 runway is actually the defensible part of that episode) that porting, not protest, is the rational response.

**Implications:** Enterprise is where the "one distribution path" ideology bends — and Firefox's policy-installed self-hosted XPIs are the best documented model for organizations that need to know exactly what they run. ## 9. Cryptographic verification as documented

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|--------|------|-------|
| 44 | Chrome prose describes the guarantee at the boundary, not the format: only extensions "hosted on and signed by the Chrome Web Store" can be directly installed on Windows/macOS; the store holds the keys and re-signs uploads; the vendor prose page for the CRX3 container (what is signed, algorithms, failure UX) was not locatable in the current developer.chrome.com doc tree (two candidate URLs 404). Verification happens at install/update inside the browser; a failed signature results in install refusal or silent disable, with user messaging documented only in incident coverage ("disabled because it contains malware"). | Chrome 33/44 boundaries | developer.chrome.com install-extensions; 404 on /docs/crw/format | current | High (boundary) / Low (CRX3 detail) |
| 45 | Firefox prose describes signing as an AMO service: every submitted artifact is validated and signed by Mozilla's key (both listed and unlisted), the browser checks the signature at install on release/beta, and unsigned code requires dev channels plus a pref. Update-time checks for self-distributed XPIs and key-pinning semantics are not documented in the fetched prose — the docs specify *behavior* (install higher versions from update_url) without specifying *verification*. | ~24 h to signature | extensionworkshop.com | current | High (install) / Low (update-time checks) |
| 46 | Safari's verification is inherited from the app sandbox: code signature + notarization ticket (Developer ID path) or App Store receipt (store path), verified by the OS before the extension can be enabled; the browser itself performs no extension-specific signature check. | — | Apple docs (Medium, SPA not rendered) | current | Medium |
| 47 | Across all three, the user-facing story on verification failure is poor: no vendor documents a distinct, actionable message for "signature invalid" vs "removed by policy" vs "corrupt download"; incident coverage shows users discover breakage from generic disabled-extension UI. | — | vendor docs + incident coverage | current | Low |

**Implications:** All vendors verify at install; none documents the update-time trust chain in user-facing prose — the exact spot where the worst incidents (§4) happened. Izcal should invert this: publish the full verification contract (what is signed, by which key, checked when, and the exact user-facing message per failure mode) as a spec, and give users distinguishable UI for "signature invalid" (verify/re-fetch), "revoked by policy" (kill switch), and "signer key rotated."

## Open questions

- What is the current, documented Chrome Web Store registration fee and the exact scope of the 2021+ developer-account verification (email/phone/ID)? Neither was on the pages fetched.
- Does Chrome still publish any CRX3 format prose outside source code, and precisely what is covered by the CRX3 signature (ZIP bytes, manifest, ID derivation)? Could not be established from vendor prose.
- How exactly does Firefox verify updates fetched from a self-distributed `update_url` (detached signature over new XPI? new-signature-by-AMO? key pinning)? The prose documents behavior, not guarantees.
- Upload-to-takedown latency: no vendor publishes it; are there academic measurements (e.g., the arXiv 2503.04292 catalog) that quantify how long malicious extensions survive post-review?
- Is there any documented case 2020–2025 of a *hijacked update server* (as opposed to hijacked developer account) pushing malware through an extension store — the GrammaTech/2019-style incidents need a verifiable primary before citing.
- Would any CA/B-Forum-style audit regime be acceptable to a vendor with Chrome's install base, i.e., is the blocker economics or legal exposure of publishing enforcement evidence?
- What did Mozilla change in its signing infrastructure after the 2019 certificate-expiry post-mortem (Rescorla's technical write-up), and is the current scheme tolerant of signer-key compromise?
- 2014–2015 Chrome ad-blocker removals: need a reachable primary (contemporaneous press or Google statement) to replace the Low-confidence row.
