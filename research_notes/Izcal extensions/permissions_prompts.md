# Izcal extensions: permission models

Compiled 20 October 2026. Primary sources were preferred (vendor docs, roadmap posts, papers).
Confidence: **High** = primary source read and checked; **Medium** = snippet/vendor claim; **Low** = secondary only.

## 1. Chrome's model (install-time list, optional permissions, the 2021 host-permission reform)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1 | Chrome's original model (2010 gallery era) is install-time, all-or-nothing: "The extension gallery prompts the user with a warning that indicates what privileges the extension has requested" — one Install dialog listing warnings (e.g. "Your data on all websites", "Your browsing history"); the user accepts everything or nothing. | — | Felt et al., "The Effectiveness of Application Permissions", USENIX WebApps '11 (paper PDF read) | 2011 | High |
| 2 | Warnings are dense in practice: of the 500 most popular Chrome extensions, 91.4% ask for at least one security-relevant permission; ~75% trigger the window-manager/history warning; 82.0% request web access, of which 51.6% request all domains. Only 43 of 500 request no security-relevant permission. "Nearly all popular extensions (91% of the top 500) generate at least one security warning. This degrades the value of the warnings." | 91.4%; 75%; 82.0%; 51.6%; 43/500 | Felt et al. 2011 | 2011 | High |
| 3 | Warning generation is mechanical and deliberately minimal: "Most permissions have an associated warning string… Chrome tries to show as few warnings as possible, while ensuring they are still accurate." Messageless permissions (e.g. `storage`) generate no warning; permission collapsing suppresses redundant warnings (`*://*.google.com` subsumes `https://maps.google.com`; `history` subsumes `topSites`). | — | Chromium design doc `extensions/docs/permissions.md` (prose doc read) | current | High |
| 4 | Optional permissions: `optional_permissions` / `optional_host_permissions` are "granted by the user at runtime, instead of at install time", via `chrome.permissions.request()`. Chrome keeps three sets — granted (ever granted, never revoked), active (currently held), runtime-granted — and after a user removes an optional permission and re-requests it, "the user will not be prompted again because the permission is present in the granted permissions." | — | Chromium permissions.md; developer.chrome.com declare-permissions | current | High |
| 5 | The 2021 reform (runtime host permissions) withholds required host permissions at install: "Withheld permissions are the set of permissions that were listed as required permissions by the extension, but were withheld as part of the runtime host permissions feature." The user then chooses per-site access through dedicated UI — context-menu/extension-menu controls and the chrome://extensions page. (Dated blog announcements of the Chrome 88–92 rollout could not be fetched — see method notes.) | — | Chromium permissions.md; blog post 404 | 2021 | High / Medium for dating |
| 6 | The user-facing site-access choice is three-way per extension — grant on click, on specific sites, or on all sites — surfaced in the extensions menu and the extension details page. | 3 modes | developer.chrome.com declare-permissions (per-site access model) + search snippets | 2021–current | Medium |
| 7 | The user can grant more than the extension asked for, but the extension never gets it: runtime-granted sets may "extend beyond what is explicitly requested", yet current permissions are computed as intersection(active, union(required, optional)) — "we don't want to have extensions privileged beyond what they should need." Overlapping grants are intersected to the exact requested pattern. | — | Chromium permissions.md | current | High |
| 8 | Two capabilities are exempt from install-time grant even in MV3: "users must give the extension access on its details page" for `file://` URLs and for incognito; detectable via `extension.isAllowedIncognitoAccess()` / `isAllowedFileSchemeAccess()`. | — | developer.chrome.com declare-permissions | 2024 | High |

**Implications:** Chrome's decade shows a system migrating from one big install dialog toward per-origin runtime grants, but by retrofit (three overlapping permission sets, withheld permissions, intersection rules) rather than redesign — the retrofitting itself is the lesson: a new browser should define host access as per-origin runtime state from day one. The mechanical warning generator + collapsing is worth keeping; the three-set bookkeeping is not.

## 2. Firefox's model

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 9 | Firefox generates install warnings from permission categories into fixed strings (e.g. "Access your data for all websites" for broad host patterns; "Access browser tabs"; "Access browsing history"; "Exchange messages with programs other than Firefox" for nativeMessaging). The canonical list page (support.mozilla.org "Permission request messages for Firefox extensions") could not be fetched — client challenge — so exact current strings are Medium. | — | support.mozilla.org article (blocked); MDN permission pages | current | Medium |
| 10 | In Manifest V3, Firefox treats host permissions as optional by default: "Users can grant or revoke host permissions on an ad hoc basis. Therefore, most browsers treat `host_permissions` as optional." Extensions must call `permissions.contains` / `permissions.request` and are advised to onboard before asking. | — | MDN `host_permissions` doc | current | High |
| 11 | Install-prompt content changed in mid-2024: "Until Firefox 126, a Manifest V3 extension's requested host permissions weren't displayed in the install prompt. From Firefox 127, host permissions listed in `host_permissions` and `content_scripts` are displayed in the install prompt. However, if an extension update requests new host permissions, these are not shown to the user." (bug 1893232) | Firefox 126→127 | MDN `host_permissions` | 2024 | High |
| 12 | Firefox's historical update rule: an update that adds a warning-triggering permission requires user re-approval before the extension keeps running (extension disabled until approved), mirroring Chrome but without Chrome's warning-collapsed comparison. Primary prose (Extension Workshop "update your extension") 404'd on compile day — grading Medium. | — | Extension Workshop (404); Mozilla add-on docs | current | Medium |
| 13 | Firefox can silently grant host access only through explicit user action in about:addons (Permissions tab toggles for optional permissions including host patterns); there is no default "on all sites at install" for MV3. | — | MDN; support.mozilla.org extensions-button docs (snippets) | current | Medium |
| 14 | The Add-on Recommendations program curates which extensions are promoted on about:addons and in the store UI, i.e. Mozilla pairs its warning system with a trust/vetting layer rather than only warnings. | — | AMO / Extension Workshop prose (not fetched; snippet) | current | Low |

**Implications:** Firefox's MV3 position — host permissions are optional until the user grants them, per-origin, revocable ad hoc — is the closest existing analogue to web-platform permission semantics, and its 126→127 install-prompt change shows even "optional" hosts eventually migrate into a visible install prompt. Izcal should copy the semantics (optional-by-default hosts, ad-hoc revoke) while fixing the discoverability gap Firefox created (updates adding host permissions silently — bug 1893232 is an acknowledged hole).

## 3. Safari's model (per-website, App-Store-mediated)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 15 | All Safari extensions come through the App Store: "All extensions in the App Store are reviewed, signed, and hosted by Apple for your security, and they're automatically kept up to date." Installation is not a permission event; the permission moment is per website. | — | support.apple.com HT102343 (read) | 2026 | High |
| 16 | Access is configured per website, not at install: in Settings → Extensions, "Click the Edit Websites button to view the extension in Websites settings. From there you can allow access, deny access, or require that websites ask you for access" — a three-state Ask/Allow/Deny model per site, matching Apple's developer docs ("can change the permission status for a selected website to Ask, Allow, or Deny"). | 3 states | support.apple.com 102343; developer.apple.com "Managing Safari web extension permissions" (title/snippet) | current | High |
| 17 | Privacy defaults are tightened per context: "When browsing in a private window in macOS Sonoma 14 or later, all extensions that require website access are turned off by default," with an explicit "Allow in Private Browsing" opt-in per extension; extensions are off by default in each new Safari profile. | Safari 17 (macOS 14) | support.apple.com 102343 | 2023– | High |
| 18 | Safari does not show requested host permissions in the install prompt at all (MDN cross-browser note), and on iOS the per-site grant has a time-boxed variant — "Allow For One Day" — shown via the extension toolbar button. | — | MDN `host_permissions`; Apple Tech Talks 110148 (snippet) | current | High / Medium (iOS detail) |
| 19 | No enterprise force-install: in WECG discussion a Safari engineer states "Safari doesn't support enterprise or force-installed extensions," making Safari the only major platform where the admin/abuse surface below does not exist. | — | w3c/webextensions issue #260 discussion | 2022 | High |
| 20 | Managed configuration exists only as app-level managed app configuration (MDM key/value into the containing app, read by the extension) rather than an install/permission-forcing policy. | — | Apple developer docs (not fetched; snippet) | current | Low |

**Implications:** Safari demonstrates the purest site-access model: no install-time host grant at all, three states per site, plus context-scoped opt-outs (private windows, profiles, one-day grants). Its weakness is UX discoverability — the controls live in Settings, not in the browsing flow — and the fact that "Ask" default still lets an extension prompt on every site. Izcal should adopt per-site Ask/Allow/Deny with defaults, and extend Safari's time-boxed grant idea.

## 4. UX research on permission prompts

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 21 | The founding empirical result: install-time warnings are so frequent that users stop reading them. "Warninging literature indicates that frequent warnings desensitize users… Users are therefore not likely to pay attention to or gain information from install-time permission prompts in these systems." | — | Felt et al. 2011 | 2011 | High |
| 22 | Anomalies are the signal, not lists: because history/all-domain warnings are requested by "more than half of extensions; users have no reason to be suspicious of extensions with these permissions because they are not anomalous. However, warnings about plug-ins are rare and therefore potentially notable." Warnings only work where the request is rare. | >50% baseline | Felt et al. 2011 | 2011 | High |
| 23 | Developers over-request because the platform makes it easy and there is no feedback: >10% of extensions request unneeded permissions — 14.7% of the top-1000 request browser-manager permissions they never use; 41 of 50 sampled extensions over-request domain access; the platform shipped no tools to detect overprivilege. | >10%; 14.7%; 41/50 | Felt et al. 2011 | 2011 | High |
| 24 | Update friction shapes behavior both ways: Chrome/Android auto-updates "do not proceed for applications whose updates request more permissions," which "incentivizes developers to request unnecessary permissions in case later versions require the permissions" — users commenting on permissions (15% of sampled extensions had permission complaints) pressure developers toward fewer prompts. | 15% | Felt et al. 2011 | 2011 | High |
| 25 | Vendor guidance now internalizes the research: "Users are more likely to trust an extension with limited warnings or when permissions are explained to them"; docs push optional permissions "wherever the functionality of your extension permits" and runtime request with onboarding context. | — | developer.chrome.com declare-permissions / permission-warnings; MDN | 2024 | High |
| 26 | Recent academic work continues the theme ("Understanding Users' Knowledge about the Privacy and Security of Browser Extensions," 2021 — recommendations for clearer extension permission dialogues; a 2024 ACM study of sensitive-data access by extensions proposing browser-level alerts). Neither was read in full — secondary snippets. | — | search snippets | 2021/2024 | Low |

**Implications:** A decade of evidence says per-permission install lists are read once and then ignored; the only warnings that inform are anomalies. Izcal should not try to write better warning sentences — it should restructure so that a request is inherently rare and contextual (runtime, per-origin, attached to a user action), which is both the Felt recommendation and where all three vendors drifted.

## 5. Update-time permission growth

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 27 | Chrome's documented rule: "When a new permission that triggers a warning is added, the extension will be disabled until the user accepts the new permission." The extension is "re-enabled only after the user agrees to accept the new permission." | — | developer.chrome.com permission-warnings (read) | 2024 | High |
| 28 | Chrome compares warning messages, not raw permissions, to decide "privilege increase": additions that are messageless or collapse into already-granted permissions do not disable; re-adding a previously-granted permission does not disable; adding optional permissions never disables. | — | Chromium permissions.md | current | High |
| 29 | Known sync hazard: Chrome syncs disable-reasons, not granted permissions, so a device joining late can have an extension disabled "even if no new permissions are added… Chrome cannot know whether version 2 added new permissions or not, and behaves conservatively" (crbug 809797). Silent-update infrastructure therefore produces false positives, not silent escalations. | — | Chromium permissions.md | current | High |
| 30 | Firefox has the mirror-image hole: update-time additions of host permissions "are not shown to the user" (bug 1893232, as of Firefox 127-era docs), i.e. the risk direction is silent grant, not false-disable. The two vendors fail in opposite directions. | — | MDN `host_permissions` | 2024 | High |
| 31 | Firefox's general update rule requires re-approval for warning-triggering additions (extension disabled until approved), like Chrome's, but primary prose could not be fetched — Medium. A documented Firefox 128-specific change to update prompting was not found; see Open questions. | — | Extension Workshop / Mozilla docs (404) | current | Medium |

**Implications:** Every auto-update pipeline needs a defined rule for permission growth, and both shipped rules have documented failure modes: Chrome over-prompts (sync false-disables), Firefox under-prompts (silent host-permission additions). Izcal should make the update contract explicit: capability growth is impossible without user action; capability shrinkage is silent; and the decision should be per-origin so that only genuinely new origins need consent.

## 6. Enterprise / administration surfaces and the abuse record

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 32 | Chrome's admin model: `ExtensionInstallForcelist` installs extensions silently with no user consent and users cannot remove them; `ExtensionInstallBlocklist`/`ExtensionInstallAllowlist` gate installation; `ExtensionSettings` adds per-extension `installation_mode` (`force_installed`, `normal_installed`, `blocked`). Enterprise docs on developer.chrome.com and chromeenterprise.google could not be fetched (404/rate-limit) — grading Medium; the policy names and semantics are long-standing and unambiguous in vendor prose. | — | Chrome enterprise docs (blocked); search snippets | current | Medium |
| 33 | Chromium's enterprise scope for hosts: `runtime_blocked_hosts` denies extensions access to given hosts regardless of grants; `runtime_allowed_hosts` exempts listed hosts from that block — it does not itself grant anything; the extension still must request. | — | w3c/webextensions #260 discussion (Chrome-side description) | 2022–2024 | High |
| 34 | WECG #260 exposes the dispute: the proposer (Aug 2022) wants admins to "pre-grant optional host permissions without user action"; Firefox's Rob--W (Jun 2024) rejects the framing — the policy "is a way for enterprise to declare exceptions to the restrictions specified in `runtime_blocked_hosts`", not a pre-grant; grants are invisible to `permissions.contains`/`getAll`, so extensions must probe empirically. | 35 | Abuse record of force-install: on Windows, force-install policies were long abused by adware writing registry keys to force-install extensions silently; the mechanism is the reason enterprise force-install is repeatedly restricted and audited. Specific vendor fixes and any 2024+ Chrome Safety Check handling of policy-installed extensions were not retrievable on compile day — Low/Medium; the underlying policy surface and its abuse are well attested in secondary prose. | — | secondary prose/snippets (not fetched) | — | Low |
| 36 | Chrome's documented hygiene response: Desktop Safety Check "will continue to notify you if you have any Chrome extensions installed that may pose a security risk" and brings the user to "the extensions page and show[s] a summary panel with quick controls to remove them." It does not auto-remove extensions. Background Safety Check auto-revocation targets site permissions (unused sites, deceptive notification prompts), not extension host grants. | — | blog.google Chrome safety update (read) | Sep 2024 | High |
| 37 | Earlier Chrome Safety Check also surfaces "Potentially harmful extensions" among its checks (support doc snippet); whether it distinguishes policy-installed from user-installed extensions is not documented in fetched prose. | — | support.google.com Chrome safety doc (snippet) | 2023– | Medium |

**Implications:** Enterprise policy is simultaneously the largest legitimate deployment channel and the historically worst abuse channel; Safari's refusal to support force-install is the cleanest answer but breaks real deployments. Izcal should allow admin policy to restrict (block, cap hosts) silently, but require any admin *grant* of host access to remain visible to the user in the same UI as user-granted access — resolving the #260 dispute in Firefox's direction — and should let Safety-Check-style hygiene remove or flag policy-installed extensions exactly like user-installed ones.

## 7. Revocation and hygiene

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 38 | Chrome exposes per-site revocation everywhere host access exists (extensions menu site-access controls, chrome://extensions details), and `chrome.permissions.remove()` drops an optional permission from the active set — but removal never erases the *granted* set, so a re-request is silently approved with no prompt. Revocation in Chrome is therefore reversible without user knowledge. | — | Chromium permissions.md | current | High |
| 39 | Firefox's revocation is ad hoc and user-facing: "Users can grant or revoke host permissions on an ad hoc basis" via the extensions toolbar button / about:addons website-permissions UI; MV3 host permissions live in the optional set, so revoke is a genuine removal of the only grant. | — | MDN `host_permissions`; support.mozilla.org (snippet) | current | High |
| 40 | Safari revokes per site (Ask/Deny per website), plus context-level revocation by default (private windows, new profiles), and the App Store auto-updates extensions — there is no mechanism for an update to add ungranted site access because access is never granted in bulk. | — | support.apple.com 102343 | current | High |
| 41 | No fetched vendor prose documents automatic expiry of extension host grants (contrast the web platform: Chrome Safety Check "removes permissions from sites you haven't used recently" — web site permissions only). Extension-level auto-expiry appears to exist nowhere; it is an open design space. | — | support.google.com safety doc; blog.google | 2024 | High (for the negative) |

**Implications:** The granted-vs-active split is Chrome's quiet flaw: revocation that can be silently re-activated by the extension is not revocation. Izcal should make revoke destructive and durable (re-request always prompts, like a fresh grant), and should consider applying the web platform's unused-permission expiry to extension host grants — no vendor does it, which is an opportunity, not evidence against it.

## 8. Site-access model vs capability model — standards debate

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 42 | Convergence, from opposite directions: Chrome (capability model at install, retrofitted to per-site runtime access) and Firefox MV3 + Safari (per-site runtime grants by default) now both present users with per-origin, revocable host access. MDN's neutral summary: "most browsers treat `host_permissions` as optional." The install-time capability list survives only as a *request ceiling* over the per-origin state. | — | MDN; Chromium permissions.md | 2021– | High |
| 43 | The remaining standardization gap is exactly the edge cases: who may pre-grant (enterprise #260), what the install prompt must show (Chrome shows, Safari never does, Firefox since 127), and how extensions discover their actual grants (invisible enterprise grants; `permissions.contains` unreliable). WECG issues on the permissions topic were still being triaged in May 2026 with no agreed model. | — | w3c/webextensions #260; MDN compat notes | 2026 | High |
| 44 | Chromium's own design sentence is the sharpest statement of the site-access philosophy: runtime host permissions "allows the user to install an extension that requests permission to multiple hosts, but have a choice over if it runs" — install expresses intent; running expresses grant. | — | Chromium permissions.md | current | High |

**Implications:** For Izcal the debate is settled empirically: the end state every vendor reached is per-origin runtime grant with install-time declaration as a ceiling. The capability model should be kept only as (a) the declared maximum the extension can ever be granted (Chrome's intersection rule, worth keeping) and (b) the review/store signal for over-privileged manifests (Felt's defense-in-depth finding). The prompt UX should be web-platform-shaped: request at time of use, per origin, with anomaly-based warnings.
