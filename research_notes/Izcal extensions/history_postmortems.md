# Izcal extensions: history and postmortems

Compiled 20 October 2026. Primary sources were preferred (vendor blogs, announcement threads, maintainers' posts, incident write-ups, papers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage quoting the primary, or a well-known fact not re-checked this session; **Low** = secondary source only.

M-1 note: no source code of any project was read or cited (no code files, diffs, or commits); prose documents, issue discussions and vendor docs only.

## 1. Firefox XUL/XPCOM add-ons → WebExtensions (Firefox 57)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Mozilla's own announcement framed the rebuild around three named causes: multiprocess (Electrolysis/e10s) incompatibility of the old model, security ("protecting users from spyware and adware" — blocklisting was reactive and being worked around), and cross-browser API compat ("largely compatible with the model used by Chrome and Opera"). The old permissive model "gives add-ons complete access to internals" and was blocking engine progress; CPOW shims were "slow and somewhat unreliable." | 471 comments on the announcement post | [The future of developing Firefox add-ons](https://blog.mozilla.org/addons/2015/08/21/the-future-of-developing-firefox-add-ons/) | 2015-08-21 | High |
| 1.2 | XUL/XPCOM deprecation was given a 12–18 month horizon in Aug 2015, but the hard cutoff slipped to Firefox 57 in Nov 2017 — a ~26-month runway total, with the final ESR (52) carrying legacy add-ons into mid-2018 as the only sanctioned stopgap. | — | [The future of developing Firefox add-ons](https://blog.mozilla.org/addons/2015/08/21/the-future-of-developing-firefox-add-ons/); release notes | 2015-08-21 | High/Medium |
| 1.3 | At the cutoff, the surviving WebExtensions ecosystem was ~5,000 add-ons; "nearly 5,000" WebExtensions were counted just before Firefox 57, against a legacy catalogue of 10,000+ (some coverage says ~14,000 total add-ons existed on AMO) — i.e. roughly two-thirds to three-quarters of the catalogue was lost overnight. Popular casualties: NoScript (ported shortly after), Tab Groups, Classic Theme Restorer, FireGestures. | ~5,000 survivors vs ~10,000+ lost | [BleepingComputer: Upgrading to Firefox Quantum](https://www.bleepingcomputer.com/news/security/upgrading-to-firefox-quantum-expect-some-add-ons-to-no-longer-work); Mozilla Hacks (Oct 2017) | 2017-11-14 | Medium |
| 1.4 | Maintainers' stated reasons for not porting cluster on: the WebExtensions API not expressing what their add-on did (deep UI modification, tab management, privacy tools needing chrome-privileged hooks), and single-maintainer burnout — porting was a rewrite, not a migration, because the old XUL/XPCOM surface shared nothing with the new JS API surface. Community workarounds (`extensions.legacy.enabled`, ESR 52 forks, Pale Moon as a XUL refuge) captured a small but vocal user base. | — | BleepingComputer coverage; community threads | 2017–2018 | Medium |
| 1.5 | What survived and thrived after 57 was content-level extension (ad blockers, privacy, password managers) — exactly the API surface WebExtensions exposes. Deep UI/behavior modification add-ons (themes beyond CSS, tab-group UI, full keyboard remaps) largely died or were rebuilt as separate products. Legacy listings were purged from AMO around Nov 2018. | — | BleepingComputer; AMO purge reporting | 2018-11 | Medium |

**Implications:** The Firefox rebuild shows that a platform ABI/API break is survivable if the replacement reaches capability parity for the majority use-case *before* the cutoff — Mozilla did not, and paid for it in catalogue and goodwill. Any Izcal extension API should be designed so the common classes (content filtering, privacy, passwords) are expressible from day one, and any future capability-culling should be additive deprecation, not a flag-day.

## 2. Chrome's extension platform origins and security model

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Chrome enabled extensions by default on its developer channel on 2009-09-09 with sample extensions; the extensions gallery beta opened Dec 2009 with ~300 extensions; the "official" gallery launched 2010-01-25 alongside Chrome 4 with ~1,500 extensions. | ~300 → ~1,500 extensions | [Wikipedia: Google Chrome extension](https://en.wikipedia.org/wiki/Google_Chrome_extension) | 2009-09-09 | Medium |
| 2.2 | The Chrome Web Store was announced 2010-05-19 and opened 2010-12-07, folding extensions into the same storefront as hosted web apps — a single store became the default (and later on Windows/Mac, effectively forced) install path. | — | [Wikipedia: Google Chrome extension](https://en.wikipedia.org/wiki/Google_Chrome_extension) | 2010-12-07 | Medium |
| 2.3 | Chrome's security model from the start: install-time permission prompt (all host permissions granted up front), sandboxed content/utility processes, and Web Store hosting. From 2014–2015 Google blocked Windows (then Mac) users from installing extensions not hosted in the Web Store after reporting a ~75% drop in customer-support requests for uninstalling unwanted extensions — the store itself was the anti-abuse mechanism, not the permission model. | ~75% support-request drop | [Wikipedia: Google Chrome extension](https://en.wikipedia.org/wiki/Google_Chrome_extension) | 2015 | Medium |
| 2.4 | The install-time, bundle-of-all-hosts permission model was the load-bearing weakness that later incidents exploited: anything granted `<all_urls>` at install time could exfiltrate every page (DataSpii), and any update could change behavior within the granted scope without re-prompting (Great Suspender). Both postmortems below trace back to this design. | — | Synthesis of sections 4.1–4.2 | — | High |

**Implications:** Install-time all-or-nothing host permissions created the "read everything forever" class of abuse; Izcal should grant per-origin at runtime (Chrome later moved partway there with optional host permissions in MV3). The 2014–15 hosting lock-in shows store control is also a censorship/fragmentation lever — plan for user-approved non-store installs from day one.

## 3. Manifest V2 → Manifest V3: the dated record

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | MV3 was announced by Google in October 2018: replace persistent background pages with service workers, replace blocking webRequest with declarativeNetRequest, prohibit remotely hosted code, promise-based APIs. Stated motivations: security (less remotely loaded, reviewable code), privacy (declarative rules evaluated before requests reach extension), performance (no always-resident background). | — | [Wikipedia: Google Chrome extension](https://en.wikipedia.org/wiki/Google_Chrome_extension) (checked text); developer.chrome.com MV3 docs | 2018-10 | Medium |
| 3.2 | Web Store cutoffs: new Public/Unlisted MV2 submissions blocked Jan 2022; new Private MV2 submissions blocked Jun 2022. | — | [MV2 support timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline) | 2022-01/2022-06 | High |
| 3.3 | Phase-out in browser: 2024-06-03 warnings in Beta/Dev/Canary + Featured badges revoked; 2024-10-09 gradual disabling begins in stable (temporary re-enable allowed); 2025-03-31 disabled by default for all users; 2025-07-24 (Chrome 138) disabled everywhere, re-enable removed. | — | [MV2 support timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline) | 2024→2025 | High |
| 3.4 | Enterprise escape hatch: `ExtensionManifestV2Availability` policy exempted enterprises "until June 2025"; the policy itself was removed in Chrome 139 (2025-06). Long runway, but the deadline still moved on Google's schedule, not customers'. | — | [MV2 support timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline) | 2025-06 | High |
| 3.5 | End state: 2026-08-31 all remaining MV2 extensions removed from the Web Store; installs on Chrome ≤138 keep running but cannot be updated or reinstalled. Full timeline Jan 2022 → Aug 2026 = 4.5 years. | 4.5-year tail | [MV2 support timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline); [ublockorigin.com/chrome](https://ublockorigin.com/chrome) | 2026-08-31 | High |
| 3.6 | Public backlash: EFF's December 2021 statement — "The changes in Manifest V3 won't stop malicious extensions, but will hurt innovation, reduce extension capabilities, and harm real world performance"; MV3 is "a fundamentally user-hostile move"; the rule cap means "it will be permanently tipping the scales in favor of ads and trackers." EFF conceded Google is "right to ban remotely hosted code" but objected to bundling that with the rest. Google later raised the rule-count limits, which EFF called "arbitrary limits" raised rather than the model fixed. | — | [EFF: Google's Manifest V3 still hurts privacy, security, innovation](https://www.eff.org/deeplinks/2021/12/googles-manifest-v3-still-hurts-privacy-security-innovation) | 2021-12-14 | High |
| 3.7 | The concrete casualty: uBlock Origin (MV2, blocking webRequest) — "Full uBlock Origin no longer works in current Chrome"; removed from the Web Store as MV2 support ended; uBlock Origin Lite (MV3, declarativeNetRequest, three permission modes) is the official Chrome path, and the project's page steers desktop/Android users to Firefox for the full blocker. | — | [ublockorigin.com/chrome](https://ublockorigin.com/chrome) | 2025–2026 | High |
| 3.8 | Firefox's response: kept MV2 alongside MV3 indefinitely; its own MV3 differs from Chrome's — non-persistent background *event pages* instead of service workers, and blocking webRequest retained in MV3 (declarativeNetRequest exists but is optional). Firefox 106+ event pages apply to both manifests. | — | [extensionworkshop MV3 migration guide](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/) | 2022+ | High |
| 3.9 | Safari adopted MV3 concepts but diverged: service-worker-style background handling per WebExtensions compat, webRequest non-blocking, and its own native-app packaging (section 6). Safari's MV3-conversion support is documented but with no published deprecation of its own MV2-era APIs at the granularity Chrome used. | — | [Apple Developer News](https://developer.apple.com/news/?id=kuswih5l); Apple docs | 2020+ | Medium |

**Implications:** MV3 is the clearest modern precedent that a platform owner will remove *capability* (blocking interception) for supply-chain and performance reasons over a 4.5-year managed decline, and that the API an ad blocker needs is the API most at risk. Izcal should treat content-blocking as a first-class declarative capability with a fast, dynamic path — not a bolt-on — and should publish deprecation dates as policy, with enterprise-style exemptions time-boxed but visible.

## 4. Documented abuse incidents and why review missed them

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | The Great Suspender: original developer sold the extension (reported June 2020); new versions 7.1.8/7.1.9 added the ability to execute arbitrary code from a remote server (ad fraud, tracking). Microsoft blocked 7.1.8 on Edge Nov 2020; Google removed it from the Web Store and force-disabled it in users' browsers 2021-02-04 ("This extension contains malware"), an "unusual step" Google rarely takes. The benign version had 2M+ installs. Clean 7.1.6 was recoverable from GitHub in developer mode. | 2M+ users; versions 7.1.8/7.1.9 malicious | [The Hacker News](https://thehackernews.com/2021/02/warning-hugely-popular-great-suspender.html) | 2021-02-04 | High |
| 4.2 | Why review missed it: the malicious capability arrived in an *update* to a well-established, previously clean extension whose review had long passed. Install-time review cannot see future updates; Google's remediation was remote kill (store removal + in-browser disable) — which is itself the proof that store review is not the safety boundary; the kill switch is. | — | [The Hacker News](https://thehackernews.com/2021/02/warning-hugely-popular-great-suspender.html) (analysis) | 2021-02 | High |
| 4.3 | DataSpii (Jul 2019): SpeakIt!, Jupiter and SuperZoom exfiltrated complete browsing histories (including URLs behind logins at Apple, Tesla, Blue Origin) to a service reselling them as "Nacho Analytics"; ~4 million people affected. The mechanism was visible-but-obfuscated (URL params, one-second-delayed payloads); Ars's deep dive describes how the extensions hid the data grab. Google's store did not act on the extensions for an extended period; the data remained reachable via Google Analytics even after the extensions were pulled. | ~4M users | [Ars Technica deep dive](https://arstechnica.com/information-technology/2019/07/dataspii-technical-deep-dive/); Ars main story 2019-07-18 | 2019-07-18 | Medium |
| 4.4 | 2020 clickfraud wave: researcher Jamila Kaya, using Duo's CRXcavator, surfaced 70 related extensions that had evaded review for up to a year by copying each other under renamed internal functions; Google used fingerprinting to expand the takedown to 500+ extensions, 1.7M total installs — click fraud, silent domain contact, malware/phishing redirects. Detection came from an outside researcher scanning the store corpus, not from Google's review. | 500+ extensions, 1.7M installs | [Sophos](https://www.sophos.com/en-us/blog/google-pulls-500-malicious-chrome-extensions-after-researcher-tip-off) | 2020-06 | High |
| 4.5 | Parallel Mozilla action (Jan 2020): 197 Firefox add-ons banned for executing remote code (129 from one B2B developer, 2Ring) — enforcement of the self-containment policy hardened around Firefox 72. | 197 banned | [Sophos](https://www.sophos.com/en-us/blog/mozilla-bans-firefox-extensions-for-executing-remote-code) | 2020-01-28 | High |
| 4.6 | Oct 2021: Mozilla blocked malicious Firefox proxy add-ons installed by ~455,000 users (proxy abuse for traffic resale). | 455K users | [BleepingComputer](https://www.bleepingcomputer.com/news/security/mozilla-blocks-malicious-add-ons-installed-by-455k-firefox-users) | 2021-10-25 | Medium |
| 4.7 | Honey/PayPal (Dec 2024–): MegaLag's exposé alleged Honey rewrites creators' affiliate links at checkout, redirecting commissions to PayPal; class actions filed Jan 2025 (GamersNexus v. PayPal, 2025-01-03, N.D. Cal. 5:25-cv-00114; consumer suit consolidated as In Re PayPal Honey Browser Extension Litigation). PayPal had acquired Honey for ~$4B (Jan 2020). Not malware — a perfectly "clean" extension whose *business model* is invisible expropriation that neither store review nor permission models flag. Also triggered copycat claims against Capital One Shopping. | $4B acquisition; multiple consolidated suits | [Johnson//Becker case page](https://www.johnsonbecker.com/class-action/paypals-honey-browser-extension-referral-fees-class-action-lawsuit) | 2025-01 | Medium |
| 4.8 | Mozilla's own signal-systems claim (May 2019, Kris Maglione, "The state of malicious extensions," Mozilla Add-ons blog): roughly 70% of malicious add-on reports came to Mozilla through its own detection systems rather than user reports — Mozilla's framing that automated/telemetry signals, not human review, do most of the catching. **Note: the primary post could not be relocated this session (URL not found); figure recollected from the post and period coverage.** | ~70% | Mozilla Add-ons blog (May 2019) | 2019-05 | Low |
| 4.9 | Neither Google nor Mozilla has published a store-review postmortem explaining how the DataSpii, Great Suspender, or 2020 clickfraud waves passed review; public record consists of takedown notices and researcher write-ups. (Mozilla's 2019 malicious-extensions post and 2021 proxy-add-on block are the closest to vendor self-analysis.) | — | Absence across searched sources | — | Medium |

**Implications:** Every major incident is an *update-channel* or *business-model* failure, not an install-time one: sold extensions turning malicious, updates adding remote code, clean permissions hiding affiliate theft. Izcal needs (a) a remote-kill switch with user-visible disclosure, (b) update re-review / behavioral scanning, (c) signals-based (telemetry+reporting) detection treated as the primary defense rather than pre-publication review, and (d) an explicit stance on monetization abuse, which permissions models cannot catch.

## 5. Firefox add-on signing (2015) and the 2019 certificate single-point-of-failure

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | Mandatory Mozilla signing was announced as part of the Aug 2015 package (Firefox 41+ blocks unsigned on release); backlash was immediate — 471 comments on the announcement, users threatening to move to Pale Moon/Vivaldi. Mitigations: a preference in Nightly/Dev Edition, and unsigned "unbranded" builds that don't enforce signing; enforcement began in earnest Firefox 42 (Nov 2015). | 471 comments | [The future of developing Firefox add-ons](https://blog.mozilla.org/addons/2015/08/21/the-future-of-developing-firefox-add-ons/); enforcement rollout coverage | 2015-08→11 | High |
| 5.2 | The signing certificate expiry (2019-05-04, ~1AM UTC): the shared intermediate that signed "the vast majority" of 15,000+ add-ons expired; Firefox verified validity on a ~24h staggered cycle, so add-ons died progressively over the weekend of May 4–5. Every signing user was affected simultaneously — one credential, one ecosystem-wide failure. | 15,000+ add-ons; ~1AM UTC May 4 | [Mozilla Hacks technical details](https://hacks.mozilla.org/2019/05/technical-details-on-the-recent-firefox-add-on-outage/) | 2019-05-09 | High |
| 5.3 | The fix and its lessons: a replacement intermediate with the same subject name and public key (accepted by existing chain-building, no re-signing) delivered as a system add-on through Normandy/Studies in under 9 hours; a dot release covered users Studies couldn't reach. Side effect: some users lost add-on data (multi-account containers). Mozilla's commitments: inventory every "time bomb" (expiring credential) in the product, build an emergency update channel that works "even when — especially when — everything else is down," separate opt-out fixes from Studies participation, and review the add-on security architecture to reduce single-point breakage. | <9 hours to fix deployment | [Mozilla Hacks](https://hacks.mozilla.org/2019/05/technical-details-on-the-recent-firefox-add-on-outage/) | 2019-05-09 | High |

**Implications:** Signing is necessary (spyware-era Mozilla said so explicitly in 2015) but creates a cryptographic single point of failure with a physical expiry date. Izcal should: treat signing keys/certificates as product-level infrastructure with monitored expiry, support recovery distribution independent of the main update channel, and never couple emergency fixes to an opt-in telemetry system.

## 6. Safari's WebExtensions port (2020–2021)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | Apple announced Safari Web Extensions at WWDC 2020 (Safari 14 / macOS Big Sur): "the same WebExtensions API used in other browsers, such as Chrome, Firefox, and Edge" — Apple's stated goal was importability of the existing ecosystem (user demand / developer demand), replacing its own abandoned Safari App Extension model. | — | [Apple Developer News](https://developer.apple.com/news/?id=kuswih5l) | 2020-08-27 | High |
| 6.2 | Packaging changed fundamentally: an extension is part of a native (Catalyst) app, converted by `safari-web-extension-converter` (Xcode 12), signed/notarized, and distributed through the Mac App Store — Apple's model binds extensions to app review and the $99/yr developer program. iOS 15/iPadOS 15 (2021) extended it to mobile; a Jan 2021 SixColors piece documented that adoption remained thin ("so where are the extensions?"), citing conversion friction and App Store gating. | $99/yr developer fee | [Apple Developer News](https://developer.apple.com/news/?id=kuswih5l); [SixColors](https://sixcolors.com/post/2021/01/safari-14-added-webextensions-support-so-where-are-the-extensions) | 2020→2021 | Medium |
| 6.3 | Later: WebKit moved WebExtensions support into WebKit itself so "all WebKit-based browsers can align on a unified implementation" (Safari 18.4, 2025) — the API surface became engine-level rather than browser-level. | — | [WebKit blog, Safari 18.4 notes](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/) | 2025-03-31 | Medium |

**Implications:** Safari is the experiment in "extensions as apps": strongest tamper-resistance and monetization, weakest catalogue. Apple's late-2020s move of the API into WebKit shows the endgame of consolidation: one engine-level extension API, browser-independent. Izcal should aim its API at that level of stability from the start.

## 7. Chromium-fork extension-store fragmentation

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | Chromium Edge (stable Jan 2020) supports Chrome extensions directly and launched its own Microsoft Edge Add-ons store; Microsoft accepted Chromium-Edge add-on submissions from Dec 2019 and pitches "publish... with minimal code changes." | — | [Microsoft Learn overview](https://learn.microsoft.com/en-us/microsoft-edge/extensions); [TheNextWeb](https://thenextweb.com/news/microsoft-wants-devs-to-submit-chromium-edge-add-ons-ahead-of-its-launch) | 2019-12→2020-01 | Medium |
| 7.2 | The Edge store's catalogue lag: ~1,000 add-ons by Mar 2020 versus the Chrome Web Store's ~150K+ — every Chromium fork that runs its own store starts with a near-empty catalogue and the same extensions re-reviewed N times. | ~1,000 vs ~150K+ | [ghacks](https://www.ghacks.net/2020/03/02/the-microsoft-edge-extension-store-is-finally-getting-some-traction) | 2020-03-02 | Medium |
| 7.3 | Because Chromium extension code is portable, each fork runs its own review, its own signing, and its own MV2/MV3 rollout timing (Google disabled MV2; forks retained it longer where policy allowed) — distribution becomes N parallel trust decisions over one codebase. Opera (also Chromium) has its own catalog in the same pattern. | — | Synthesis; [MV2 timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline) (policy scope) | — | Medium |

**Implications:** Store fragmentation is the cost of forking the engine: the extension *format* is portable but trust is not. If Izcal ships extensions, the signing/review/kill-switch layer should be designed as a separate, replaceable component so downstream builds can reuse it rather than each re-inventing review over the same packages.
