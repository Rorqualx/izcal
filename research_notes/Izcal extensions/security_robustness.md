# Izcal extensions: security and robustness

Compiled 20 October 2026. Primary sources were preferred (vendor docs, Project Zero, papers, CVE prose).
Confidence: **High** = primary source read and checked in its text; **Medium** = snippet/vendor claim; **Low** = secondary only.

M-1 note: no source code of any project was read or cited; prose documentation only.

## 1. Isolated worlds / isolated content scripts

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 1.1 | Chrome documents content scripts as living in an "isolated world": "a private execution environment that isn't accessible to the page or other extensions." "JavaScript variables in an extension's content scripts are not visible to the host page or other extensions' content scripts." Isolation is mutual: "none of these (web page, content scripts, and any running extensions) can access the context and variables of the others." | — | developer.chrome.com, Content scripts | current (2026) | High |
| 1.2 | The isolation covers prototype/expando tampering: Chrome's doc demonstrates both the page and the content script setting the same custom property on the same DOM element and each seeing its own value — the documented defense against page prototype poisoning and expando snooping. | — | developer.chrome.com, Content scripts | current | High |
| 1.3 | Firefox documents the same guarantee as "Xray vision": "If a page script redefines a built-in DOM property, the content script sees the original version of the property, not the redefined version"; redefined `window.confirm` reverts to the original in the content script. In Firefox content scripts `globalThis` is "a distinct object inheriting from `window`". | — | MDN, Content scripts | current | High |
| 1.4 | The DOM itself is shared and unisolated in both browsers. Chrome: environments "share access to the page's DOM," and page↔extension communication "must do so through the shared DOM" (e.g. `window.postMessage`). Firefox: "Content scripts can access and modify the page's DOM, just like normal page scripts can. They can also see any changes that were made to the DOM by page scripts." So all DOM writes a content script makes are visible (and detectable) by the page. | — | developer.chrome.com; MDN, Content scripts | current | High |
| 1.5 | Both vendors document `world: "MAIN"` as the escape hatch that drops isolation: Chrome defaults to `ISOLATED` and warns "When a content script is injected into the main world, the CSP of the page applies" (and MAIN-world scripts get no extension APIs). Firefox documents `window.eval()` vs `eval()` as running code with page vs. content-script privileges, with the warning that the page can redefine objects the injected code calls. MDN also warns broadly: "Extensions are privileged code which can have powerful capabilities and hostile web pages can easily trick them into accessing those capabilities." | — | developer.chrome.com; MDN | current | High |
| 1.6 | Firefox-only opt-in sharing primitives: `cloneInto()` and `exportFunction()` deliberately cross the Xray boundary; Chrome has no equivalent (its isolated worlds share nothing). | — | MDN, Content scripts | current | High |

**Implications:** Isolation of JS state is cheap, proven, and uniform; DOM cohabitation is the irreducible shared channel (timing/UI cues, postMessage protocol confusion). Izcal should treat DOM writes as public-by-construction, keep `world: MAIN` rare and review-flagged, and consider Firefox's cleaner model (fresh globals, no shared prototypes) rather than Chrome's V8-context trickery.

## 2. Privilege separation: where extension code runs

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 2.1 | Chrome's Site Isolation doc states web sites "do not share processes with extensions, which are more highly privileged than web sites" — extension pages and service workers are separated from content renderers by process boundaries. | — | Google Security Blog, "Protecting more with Site Isolation" | 2021-07 | High |
| 2.2 | Chrome 92 extended this: "As of Chrome 92, we will start extending this capability so that extensions can no longer share processes with each other. This provides an extra line of defense against malicious extensions, without removing any existing extension capabilities." Cross-extension process separation is a late (2021) hardening, ~12 years after the extension platform shipped. | Chrome 92 | Google Security Blog | 2021-07 | High |
| 2.3 | Site Isolation on desktop (per-site renderer processes) has been default since Chrome 67 per Chromium security docs; on Android it remains heuristic (high-value sites, 2 GB RAM floor, OAuth/COOP triggers added in Chrome 92) — so the extension/content process wall is weaker on Android. | Chrome 67 | Chromium security docs; Google Security Blog | 2018 / 2021 | High |
| 2.4 | MV3 replaced persistent background pages with service workers that "run only when needed" — documented as a resource change; the privileged event-driven context survives only while dispatched, which shrinks the always-on attack window but complicates security tooling (no long-lived context to inspect). | — | developer.chrome.com, What is MV3 | current | High |
| 2.5 | Firefox's WebExtension implementation is documented (its own implementation guide) as splitting API code between "the main process" and "the child process" under e10s, with separate code paths for built-in vs. privileged/experimental APIs — i.e., the privileged extension machinery concentrates in the browser (parent) process, unlike Chrome's renderer-hosted extension pages. | — | firefox-source-docs.mozilla.org, WebExtensions implementation guide | current | High |
| 2.6 | Firefox's signing/Discourse documentation records a 2025–2026 change of signing root with Firefox 128 ("starting with Firefox 128, Mozilla switched signing approaches"), breaking verification in older versions — evidence that the privileged add-on trust chain itself is a live hardening surface. | Firefox 128 | Mozilla Discourse (snippet) | 2025-09 | Medium |
| 2.7 | Chrome documents MV3 "split" incognito behavior as the default for MV3 extensions (extension incognito runs in a separate, non-incognito-context process), reducing cross-context data bleed compared to MV2's default "spanning". | — | developer.chrome.com, incognito | current | Medium |

**Implications:** The historical lesson is that "extension = more privileged than the web" was accepted for a decade before process separation caught up. Izcal should design extension code into its own process class from day one — separate from both web content and from other extensions — and treat the parent/browser process as the only place signed, built-in privileged code may run.

## 3. Native messaging

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 3.1 | Chrome's documented model: a JSON host manifest (`name`, `description`, `path`, `type`, `allowed_origins`) registered via a registry key on Windows under `HKLM/HKCU\...\Google\Chrome\NativeMessagingHosts\<name>` (32-bit queried before 64-bit) or fixed filesystem locations on macOS/Linux; on Linux/macOS `path` "must be absolute"; on Windows it "can be relative to the directory containing the manifest file." | — | developer.chrome.com, Native messaging | current | High |
| 3.2 | Transport: "Chrome starts each native messaging host in a separate process and communicates with it using standard input (stdin) and standard output (stdout)"; JSON/UTF-8 messages length-prefixed with a 32-bit native-order length; host→browser messages max 1 MB, browser→host max 64 MiB. The host receives the caller's origin (extension ID) as its first argument. | 1 MB / 64 MiB | developer.chrome.com | current | High |
| 3.3 | Access control is manifest-mediated: the extension declares `"nativeMessaging"`; the host manifest's `allowed_origins` (Chrome) / `allowed_extensions` (Firefox) lists permitted extension IDs and "can't contain wildcards". Firefox's MDN page confirms no connect-time user prompt — permission is purely the pair of manifest declarations. Chrome's page likewise documents no user-confirmation dialog at connect time. | — | developer.chrome.com; MDN, Native messaging | current | High |
| 3.4 | Firefox differences documented on MDN: `allowed_extensions` vs Chrome's `allowed_origins`; registry keys under `Software\Mozilla\NativeMessagingHosts\<name>` on Windows; browser→app message cap 4 GB (Chrome 64 MiB); the add-on ID is passed as a second argument since Firefox 55. | 4 GB | MDN, Native messaging | current | High |
| 3.5 | The structural risk is installation, not the pipe: whoever can write one registry key or one file in a user directory can register a native host that any matching extension can drive to arbitrary OS code execution. Chrome's docs implicitly acknowledge this (installation "requires writing a registry key (Windows) or a file to system/user directories") and require `nativeMessaging` per-extension, but neither vendor documents an install-time user prompt for native hosts. | — | developer.chrome.com; MDN | current | High |
| 3.6 | Chrome's docs document the content-script boundary: native messaging APIs "are not available inside content scripts"; the service worker "must validate `sender.origin`... and sanitize the message payload before forwarding" — i.e., the documented pattern requires the privileged side to treat page-influenced messages as hostile input to the OS bridge. | — | developer.chrome.com, Native messaging | current | High |
| 3.7 | Documented abuse in the wild: a 2024 GitHub Security Lab write-up ("Attacking Browser Extensions", Oct 2024) shows extension-input injection yielding UXSS; a 2026 SpecterOps post documents Chromium extension C2 persistence using native messaging as the bridge between a planted extension and a local OS process. Historical malware families (e.g. Stantinko) used installed extensions plus native hosts for persistence. | — | GitHub Security Lab; SpecterOps (snippets); ESET write-ups | 2024–2026 | Medium |

**Implications:** Native messaging is the single most dangerous extension feature because it converts a browser-content bug into OS code execution with no additional user gesture. Izcal should either omit it or make it the most heavily gated capability: explicit per-host user pairing ceremony at first connect, system-vs-user registration tiers, no wildcards, and host processes sandboxed away from user credentials.

## 4. Signing and verification

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 4.1 | Chrome documents that "Windows and Mac installs must come from Chrome Web Store": "As of Chrome 33, no external installs are allowed from a path to a local CRX file on Windows"; on Mac, as of Chrome 44; external installs' `update_URL` must point at the Web Store. Local-CRX external install survives on Linux only (preferences JSON, auto-installed without prompt). | Chrome 33 / 44 | developer.chrome.com, Install extensions | current | High |
| 4.2 | Chrome's install model uses signed CRX packages served from the Web Store (the store is the only trusted `update_url` on Win/Mac); the practical effect documented by Google is that self-hosted, self-signed or repacked extensions cannot silently install on the two dominant desktops. | — | developer.chrome.com | current | High |
| 4.3 | Firefox's signing model: add-ons "need to be signed before they can be installed into release and beta versions of Firefox," signed by Mozilla (AMO/Autograph) regardless of listing; verification chains to a Firefox root CA shipped with the browser ("the signing cert chains back to the Firefox Root CA"), with the end-entity cert's "subject CN must match the add-on ID" and a PKCS7 detached signature over `META-INF/mozilla.sf`. | — | Mozilla Wiki, Add-ons/Extension Signing | current | High |
| 4.4 | Mandatory signing arrived gradually: Firefox 40–42 warn; Firefox 43 enforces with an override preference; Firefox 48 "Release and Beta... will not allow unsigned extensions to be installed, with no override." Override (`xpinstall.signatures.required=false`) survives only on Nightly/Developer/ESR/unbranded builds. | Firefox 40–48 | Mozilla Wiki | 2015–2016 | High |
| 4.5 | Mozilla signs both listed and unlisted add-ons — unlisted add-ons are "automatically signed" after automated review via `web-ext sign` or a signing API, without public hosting. Rationale documented: "the purpose of this is to protect users from malicious add-ons"; Mozilla concedes "No, there is no perfect solution for this. Fighting malware requires defenses on many levels." | — | Mozilla Wiki; Extension Workshop | current | High |
| 4.6 | Stolen-key/compromise asymmetry: Chrome's model ties validity to the store's own signing key (Google-operated, never shipped to developers); Firefox's model makes Mozilla the sole signer (developer keys never exist). Both mean a store/signing-infrastructure compromise, not a developer key leak, is the catastrophic case — and Firefox additionally keeps its root private-PKI root in-product. | — | Mozilla Wiki; developer.chrome.com (synthesis) | current | High |
| 4.7 | The Firefox intermediate-signing-certificate expiry (early May 2019) disabled essentially all extensions across Firefox 52–65 worldwide; users saw add-ons "could not be verified and were disabled." Mozilla pushed a fix via its Studies (shield-studies) hotfix system and follow-up updates to old ESR branches; criticism focused on the lack of any user-side fallback for release builds. | May 3–4, 2019; Firefox 66.0.4/66.0.5 | ghacks coverage (primary Mozilla posts now 404) | 2019-05 | Medium |
| 4.8 | No comparably public incident of a Chrome CRX signing-key compromise exists in the prose record; the store-centralization incident class instead shows up as policy/enforcement failures (see §5). | — | (absence of evidence, searched prose record) | 2026 | Low |

**Implications:** A signing chain is a single point of global failure — the 2019 incident shows an *expiry*, not an attack, was enough to disable every extension at once. Izcal should plan for verification infrastructure failure: validity windows with overlap, offline grace periods, and a last-resort user-visible trust decision, rather than silent mass disablement.

## 5. Store review effectiveness

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 5.1 | Google's own USENIX Security 2015 paper: over three years, 9,523 malicious extensions found — "roughly 10% of all extensions submitted to the Chrome Web Store." Their WebEval system reached a "detection rate of 96.5%," and "half of malware [was removed] within 25 minutes of creation" — yet "fewer than 100 evasive extensions still infected more than 50 million Chrome users." | 9,523; 96.5%; 25 min; 50M+ users | Jagpal et al., USENIX Security 2015 | 2015 | High |
| 5.2 | Hulk (USENIX Security 2014) dynamically analyzed 48,000 Web Store extensions against 1M+ URLs using HoneyPages and identified multiple malicious extensions, "one of which had 5.5 million affected users" — evidence that review-time analysis missed broadly-installed malware. | 48,000 extensions; 5.5M users | Kapravelos et al., USENIX Security 2014 | 2014 | High |
| 5.3 | Chrome's documented review process is automated-first: "a combination of manual and automated systems"; closer human review triggered by "new developers, new extensions, dangerous permission requests, significant code changes"; "for most extensions, review is completed within a few days, but it can take up to a few weeks"; obfuscation is disallowed; enforcement tiers are rejection / warning (7–30 days) / takedown (404, later disabled, re-enableable) / malware takedown (immediate, unre-enableable). | — | developer.chrome.com, Review process | current | High |
| 5.4 | Documented enforcement numbers: June 2023 — Google removed 32 malicious extensions with 75 million total installs (BleepingComputer); February 2020 — 500+ malicious adware extensions removed (Guard.io). | 32/75M (2023); 500+ (2020) | BleepingComputer; Guard.io (snippets) | 2020–2023 | Medium |
| 5.5 | Independent assessment of review effectiveness (Wladimir Palant, Jan 2025): of a June 2023 cluster report of 108 extensions, "96 were still active in January 2025"; a Jan 2025 report covered 920 spammy extensions; ~150,000 extensions total, ~60% abandoned; fake reviews trivially reachable (19 five-star reviews in a day on a 10,000-user extension); Google's DDPRP bug/enforcement program ended August 2024. Google confirmed two 2024 reports were "being worked on" while the items stayed live. | 96/108 still live; 920 spam; ~150k extensions | palant.info, "Chrome Web Store is a mess" | 2025-01 | High |
| 5.6 | MV3 itself functions as a review-surface policy tool: "Manifest V3 removes the ability for an extension to use remotely hosted code" because remote code "presents security risks by allowing unreviewed code to be executed in extensions" — bundling all code makes store review authoritative. | — | developer.chrome.com, What is MV3 | current | High |
| 5.7 | Mozilla's model accepts slower, deeper review (automated validation "within up to 24 hours," longer if flagged, plus "manual code review at any time after submission" for all signed add-ons, listed or not) — trading scale for review depth. | — | Extension Workshop, Signing and distribution overview | current | High |
| 5.8 | Academic follow-ups: DeKoven et al. (CSET 2017) scanned real users' browsers and found an "observational gap" — malware live in the field beyond what store scans see; a 2024 Georgia Tech study found thousands of privacy-compromising extensions with hundreds actively exfiltrating data. | — | CSET 2017; Georgia Tech 2024 (snippets) | 2017–2024 | Medium |

**Implications:** Store review is a latency reducer, not a gate: even at Google's published 96.5% detection and 25-minute median removal, a sub-1% evasion reach 50M users. Izcal must assume some malicious extensions are installed and design containment (permission transparency, runtime observability, fast kill-switch) rather than relying on review alone.

## 6. CSP for extension pages

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 6.1 | Chrome MV3 documents a fixed default: `"extension_pages": "script-src 'self'; object-src 'self';"` — inline JavaScript blocked, strings can't be evaluated, WebAssembly disabled by default. | — | developer.chrome.com, Manifest CSP | current | High |
| 6.2 | Chrome enforces a non-relaxable floor: minimum `"script-src 'self' 'wasm-unsafe-eval'; object-src 'self';"`. "You can't add sources like 'unsafe-eval' to script-src"; violations fail at install time ("Insecure CSP value "'unsafe-eval'" in directive 'script-src'"). | — | developer.chrome.com, Manifest CSP | current | High |
| 6.3 | Chrome's sandbox escape valve: `"sandbox"` pages get `"script-src 'self' 'unsafe-inline' 'unsafe-eval'; ..."` and are customizable, "because they lack access to extension APIs and direct access to non-sandboxed pages" — the documented way to run eval-ful legacy code. | — | developer.chrome.com, Manifest CSP | current | High |
| 6.4 | MV2 (per MDN's cross-browser doc) defaulted to the same `script-src 'self'; object-src 'self'` but allowed developers to relax it (remote scripts, `'unsafe-eval'`) — the relaxation channel MV3 removes. Firefox MV2 likewise allowed relaxations, though "a CSP allowing remote script injection gets the extension rejected from AMO during review" — policy, not engine, enforced the same end. | — | MDN, Content Security Policy; developer.chrome.com | current | High |
| 6.5 | Firefox MV3 documents a different default: `"script-src 'self'; upgrade-insecure-requests;"` — Firefox does not document Chrome's hard floor; relaxations remain possible (localhost sources permitted for development in Firefox 147+), so CSP strength is engine-specific, not spec-uniform. | Firefox 147 | MDN, CSP | current | High |
| 6.6 | Documented CSP limits: MDN notes MV2 content scripts "had no CSP" and MV3 content scripts inherit the extension's default CSP with no way to declare a separate one; CSP does nothing against DOM-injection XSS (the injection of data-as-markup), which remains the dominant extension-page XSS class (Carlini et al. 2012: most of their 70 vulnerabilities were content-injection bugs that CSP cannot see). | — | MDN, CSP; Carlini et al. USENIX 2012 | 2012–current | High |

**Implications:** A strict CSP with no relaxation channel (Chrome MV3's model) is worth copying, but Izcal must not treat it as XSS protection: it blocks remote-code inclusion and eval, not data-injection into the extension's own DOM. The sandbox-page escape valve should exist but be API-less by construction, as Chrome documents.

## 7. webRequest's documented danger surface

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 7.1 | Chrome frames MV3's headline privacy change declaratively: declarativeNetRequest "lets extensions modify network requests without intercepting them and viewing their content, thus providing more privacy." Blocking webRequest "required extensions to proxy all network traffic to provide filtering capabilities, which came at a performance and privacy cost" and is "deprecated" in MV3. | — | developer.chrome.com, declarativeNetRequest; What is MV3 | current | High |
| 7.2 | The observational path is not removed: MV3 extensions can still ship non-blocking `webRequest` (headers, URLs, timing), `webNavigation`, and content-script DOM observation with host permissions; MV2-era tools (header readers, credential watchers) remain writable. Critics noted this at the time — "the observational capabilities of WebRequest aren't being deprecated, so malicious extensions can still spy" (Ghostery/press objections). | — | developer.chrome.com; Ghostery/Lapcat commentary | current | Medium |
| 7.3 | Firefox never adopted the restriction: "in Firefox, both MV2 and MV3 extensions can use blocking webRequest and/or declarativeNetRequest" (Lapcat, Oct 2026) — documented divergence, so MV3 does not itself reduce network-observation capability platform-wide. | — | Lapcat Software (snippet); MDN browser-compat notes | 2026 | Medium |
| 7.4 | DNR rule ceilings are documented and small relative to real blockers: 100 static rulesets declared, 50 enabled, "at least 30,000 guaranteed" static rules; 30,000 dynamic "safe" rules vs 5,000 unsafe (Chrome 121+); 5,000 session rules; regex rules ≤1,000 per type, ≤2 KB compiled. Redirect actions additionally require `web_accessible_resources`. | 30k/5k/1k | developer.chrome.com, declarativeNetRequest | current | High |
| 7.5 | DNR's permission tiers are documented: `declarativeNetRequest` alone grants allow/block/allowAllRequests with an install warning and "avoid[s] needing to request full access to hosts"; `declarativeNetRequestWithHostAccess` shows no warning but requires host permissions — meaning the model still permits zero-warning, broad-visibility configurations. | — | developer.chrome.com, declarativeNetRequest | current | High |
| 7.6 | Credential exposure in practice: a Firefox security advisory documented a WebExtension bug where rewriting `Host` request headers via `webRequest` allowed "bypass[ing] domain restrictions through domain fronting" (CVE-2018-12395, moderate) — header-level API confusion turning a filter extension into an origin-boundary breaker. | CVE-2018-12395 | MFSA 2018-27 | 2018-10 | High |
| 7.7 | An arXiv 2025 study of developer experience found MV3's webRequest removal "causes some extensions to unintentionally and unnecessarily hinder functionality" — the documented cost side of the trade. | — | arXiv 2025 (snippet) | 2025 | Medium |

**Implications:** The real privacy lever is read-access to request bodies/headers, not blocking-vs-declarative. Izcal should separate "filter" (declarative, no read) from "observe" (explicit read grant, visible badge, per-site) as two different capabilities, rather than one `webRequest` umbrella with an opt-out.

## 8. Sandbox escapes and API-confusion bug classes

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 8.1 | Carlini et al. (USENIX Security 2012) reviewed 100 Chrome extensions: "70 vulnerabilities across 40 extensions." Architecture verdict: Chrome's mechanisms (site-extension isolation, privilege separation, permissions) "largely succeed at stopping web-based attacks," but "new security mechanisms are needed" against network attacks, website-metadata attacks, and vulnerabilities extensions introduce into sites they modify. Banning HTTP scripts and inline scripts "would eliminate 47 of the 50 most severe vulnerabilities." | 100 / 70 / 40; 47 of 50 | Carlini, Felt, Wagner, USENIX Security 2012 | 2012 | High |
| 8.2 | The same paper's descendants keep finding the same class: GitHub Security Lab (Oct 2024) documents page-controlled input flowing into extension-executed JS yielding UXSS — "code execution across arbitrary websites" — in modern Chrome MV3 extensions; the OWASP Browser Extension cheat sheet catalogs permission overreach, data leakage, XSS, and insecure messaging as standing classes. | — | GitHub Security Lab; OWASP cheat sheet | 2024 | Medium |
| 8.3 | Firefox's documented WebExtension CVE set (MFSA 2018-27, all Rob Wu): CVE-2018-12395 (webRequest `Host`-header rewrite → domain-fronting bypass), CVE-2018-12396 (content scripts executing in disallowed contexts — "potential privilege escalation by the WebExtension"), CVE-2018-12397 (missing permission prompt for local file access — content scripts in `file://` pages "without permission warnings"). All moderate; the class is API-contract confusion, not memory corruption. | 3 CVEs, moderate | MFSA 2018-27 | 2018-10 | High |
| 8.4 | A Chromium issue tracker report documents bypassing "Chrome Cloud/Enterprise managed policy" — i.e., allow/deny-list and packed-extension restrictions — showing that the enforcement layer between policy and the extension loader is itself bug-prone. | — | Chromium issue tracker (snippet) | current | Medium |
| 8.5 | Eunomia.dev's 2025 bug study of browser extensions and IDE plugins documents how extension vulnerabilities "undermine browser sandbox assumptions, turning add-ons into attack vectors" — extensions as the soft entry into the browser's trust boundary. | — | eunomia.dev (snippet) | 2025 | Medium |
| 8.6 | Hulk's HoneyPages technique (2014) demonstrated the mirror-image attack: malicious extensions probing and adapting to expected page structure to elicit malicious behavior — dynamic-analysis evasions that static review cannot see. | 48,000 extensions | Kapravelos et al., USENIX 2014 | 2014 | High |

**Implications:** Fifteen years of evidence says the vulnerability class is *contract confusion at the API boundary* (header rewrite, context checks, prompt presence), not sandbox memory corruption. Izcal's extension API design should be small, typed, and deny-by-default on every multi-condition check (permission + context + timing), since that conjunction is exactly where Firefox's documented CVEs live.

## 9. Enterprise policy abuse

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 9.1 | `ExtensionInstallForcelist` is documented by Google as an enterprise Windows-registry/JSON policy (`HKLM\Software\Policies\Google\Chrome\ExtensionInstallForcelist`) that force-installs extensions and makes them non-removable — "installed by enterprise policy," uninstallable by the user. | — | Chrome Enterprise policy docs; developer.chrome.com install docs | current | High |
| 9.2 | Documented abuse: adware and malware writing that same policy on personal machines to force-install extensions, producing the notorious "Managed by your organization" banner; removal requires registry cleanup or Google's policy-remover tool (GridinSoft and other anti-malware vendor write-ups; a Dec 2025 case study details consent bypass via the policy; the JSCEAL campaign used registry policy modification including `ExtensionInstallForcelist`). | — | GridinSoft blog; sealkisnotklaes.fr case study (snippets) | 2020–2026 | Medium |
| 9.3 | Persistence asymmetry: because the policy re-applies at startup, "user-initiated uninstalls effectively blocklist the extension so it won't reinstall" (documented for the preferences-file path) does not help against policy installs — the documented mitigation is machine-level, not browser-level. | — | developer.chrome.com; GridinSoft | current | High |
| 9.4 | Chrome's documented compensations are disclosure-oriented: enterprise-installed extensions are labeled, `chrome://policy` exposes the forcing policy, and Chrome's install restrictions (§4.1) removed the older silent-CRX path that complemented policy abuse. Firefox has no force-install policy equivalent (add-ons require signing + explicit install), which structurally closes this class. | — | Chrome Enterprise docs; Mozilla signing docs | current | High |

**Implications:** Any enterprise/fleet management feature Izcal offers will be weaponized as a persistence mechanism on consumer machines. Force-install should require an admin-level, separately-verifiable trust anchor (not just a writable policy file), and consumers should always see and be able to break the "managed" state.

## Open questions

- Does any vendor document a user-confirmation prompt for native-messaging host *installation* (vs. first connect), and is there a published census of how many Web Store/AMO extensions use `nativeMessaging`? (Determines how heavy Izcal's gate can be without breaking the ecosystem.)
- What is the documented detection-latency distribution for Chrome Web Store takedowns after 2023 (Google stopped publishing the 25-minute-median style numbers after the 2015 paper)? Independent measurement post-MV3 is missing.
- Are there published MV3-era equivalents of Carlini 2012 (systematic review of MV3 extensions under the fixed CSP) to confirm whether DOM-injection XSS in extension pages is now the dominant residual class?
- Firefox's parent-process concentration of privileged extension machinery: is there public prose on the planned "out-of-process extensions" work and its threat-model rationale, to compare against Chrome's Chrome-92-style cross-extension process split?
- What exactly changed in Firefox 128's signing root (new root CA enrollment vs. key rollover), and what is the documented revocation story if the AMO/Autograph signing infrastructure is compromised — the Firefox-side analogue of the 2019 expiry incident class?
- Does Chrome document any runtime attestation for enterprise-forced extensions (so a fleet admin can distinguish a genuine admin install from registry-squatting adware)?
