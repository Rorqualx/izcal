## 1. Extension enumeration and fingerprinting: the academic record

|---|---------|---------|--------|------|-------|

| 9 | The vector inventory a new browser must defend against: (a) fetching `chrome-extension://` WAR URLs; (b) probing `chrome.runtime.id`-derived resource paths; (c) content-script DOM side effects; (d) extension message eavesdropping; (e) Resource Timing on extension-fetched resources; (f) simulated user actions; (g) CSS-style/layout shifts from injected nodes. | — | Carnus + Solomos papers (technique sections) | 2020–2022 | High |
| 10 | Chrome's countermeasure, `use_dynamic_url` on `web_accessible_resources` (introduced with the MV3 manifest format): resources are then served under a *per-session* dynamic package ID, "regenerated when the browser restarts or the extension reloads", instead of the permanent `chrome.runtime.id`. The docs' stated reason WARs are opt-in at all: otherwise a malicious page could "fingerprint extensions that a user has installed" or "exploit vulnerabilities (for example XSS bugs) in installed extensions". | Per-session randomization; restart/reload re-randomization | developer.chrome.com, "Manifest — Web Accessible Resources" (read) | docs current 2026 (key shipped with MV3-era manifest format, ~Chrome 88–103) | High (mechanism), Medium (date) |

**Implications:** Extension enumeration is a solved attack: every vector family has a working academic demo, and the defense side has only one shipped countermeasure (per-session WAR IDs) that covers exactly one vector (WAR probing) and none of the behavioral/user-action vectors. Any browser that allows third-party extensions must assume the *installed set* is public to every page it visits. Therefore: (1) Izcal should default to installing zero third-party extensions on privacy-hardened profiles and treat each install as an explicit fingerprinting opt-in, the way Tor does; (2) any Izcal analogue of WARs must be default-deny, origin-checked, and session-randomized per install (not just per session — per *install* randomization plus rotating identifiers is strictly stronger); (3) content-script DOM injections should be randomized (tag names, attribute ordering) or run in a shadow tree the page cannot observe, because Carnus-class behavior signatures survive WAR defenses.

**Implications:** Izcal's extension platform should (a) log installs only in the store's server access logs, never emit install or "first launch" events, (b) make update checks identifier-free (batched list requests or download-URL-based fetches with no client ID), and (c) if Izcal ever wants usage statistics, collect them via explicit opt-in and publish the schema. The Firefox model — telemetry carries add-on identity but is switchable, and removal from the default environment shows the data was recognized as over-collected — is the closest shipped precedent; Izcal should start one step stricter (nothing on by default).

## 3. Permission-breadth data

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|

| 17 | Chrome's permission model distinguishes API permissions from host permissions; host permissions can be requested at install time or at runtime via the optional-permissions flow, and Chrome displays distinct warning strings per dangerous permission group. | — | developer.chrome.com, "Declare permissions" (surfaced in search; full page not re-read) | docs current 2024+ | Medium |
| 18 | Since the 2021-era "site access" rework, extensions with broad host permissions expose a per-extension site-access dropdown (on click / on specific sites / on all sites), i.e. Google's own mitigation for breadth is a runtime narrowing control rather than store-level rejection of `<all_urls>`. | — | Chrome issue tracker discussion of optional host permissions + Chrome settings UI (secondary descriptions) | 2023–2024 | Medium |
| 19 | What fraction of popular extensions trigger the most severe warnings ("Read and change all your data on all websites") could not be verified from primary sources this session; widely-cited store-crawl figures exist in secondary sources only. | Unverified | Open — see Open questions | — | Low |

**Implications:** The permission-breadth data is the weakest part of the public record — one peer-reviewed compliance number (39.8%) and a set of store-crawl claims of varying quality. For Izcal the defensible conclusions are structural: (1) default-install grants of `<all_urls>` should not exist; every host grant is runtime, per-site, and revocable from the toolbar; (2) the install dialog should show *data-type* warnings ("can read everything you do on these sites") not URL-pattern text, because rows 4–5 show the underlying risk is inference of sensitive attributes; (3) Izcal's store should measure and publish permission-breadth distribution as a first-class metric, since the incumbents' data here is embarrassingly thin.

## 5. Incognito / private-browsing behaviour

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 28 | Chrome documents two extension modes for private windows: "spanning" (one profile-spanning extension instance sees both normal and private tabs) and "split" (separate instances); the API surface includes `chrome.extension.isAllowedIncognitoAccess()` / `browser.extension.isAllowedIncognitoAccess()` (MDN documents the cross-browser form). Extensions do not run in incognito unless the user opts in per-extension. | — | developer.chrome.com incognito docs (URL 404 at fetch time — page moved); MDN `extension.isAllowedIncognitoAccess()` (read) | docs current 2026 | Medium (Chrome specifics), High (API exists) |
| 29 | The leak is structural: in spanning mode a user-authorized extension's content scripts run *inside* private tabs, so the extension vendor receives private browsing data — the browser cannot distinguish "extension telemetry" from "incognito telemetry" once the user flips the toggle. The opt-in dialog does not say this to users in those words. | — | Mode descriptions as above + Carnus/Solomos demonstrations that extension↔page interaction is observable | — | Medium |
| 30 | Firefox's default is the opposite direction: extensions are disabled in private windows unless the user explicitly grants access per add-on (post-Firefox 55 model). | — | Mozilla support documentation (SUMO page behind client challenge at fetch time; long-standing documented behavior) | 2017+ | Medium |
| 31 | There is no shipped "split with separated storage" story in either browser: both eventually expose one extension's view across contexts once granted, differing only in whether the grant exists by default. | — | Synthesis | — | Medium |

**Implications:** Izcal should not copy spanning. A first-principles private-mode design is: extensions are absent from private contexts by default; a per-extension grant creates a *separate, storage-isolated extension instance* whose cookies/storage/history access is walled from the normal instance and whose network traffic is tagged so the user's own DevTools can show "this request came from your extension while in private mode"; and the grant dialog must state the consequence plainly ("this extension's publisher will see your private browsing"). Default-off (Firefox) plus isolation (no shipped browser has both) is the defensible combination.

|---|---------|---------|--------|------|-------|
| 32 | Google's stated rationale for replacing blocking `webRequest` with `declarativeNetRequest`: webRequest "can also be — and has been — abused"; declarative rules let the browser enforce blocking without giving each extension a per-request code hook into all traffic. | — | blog.chromium.org, "Web Request and Declarative Net Request" (Jun 12, 2019; body not retrievable this session — snippet-graded) | Jun 2019 | Medium |
| 33 | DNR's quantitative shape (post-Chrome 120): up to 100 static rulesets with 50 enabled at once, a guaranteed minimum of 30,000 static rules; before Chrome 120, 50 rulesets / 10 enabled. | 34 | EFF's core critique (Dec 2021): a declarative API makes content blockers unable to adapt — "If your extension needs to process requests in a way that isn't covered by the existing rules, you just can't do it"; and Google's performance justifications for MV3 were asserted without published evidence ("Google has provided no evidence to back these claims"). | — | EFF, "Google's Manifest V3 Still Hurts Privacy, Security, and Innovation" (read in full) | Dec 14, 2021 | High |
| 35 | EFF documents a concrete capability gap: CNAME uncloaking (mapping requests to a site's real first-party infrastructure) existed in Firefox's extension API for years while Chrome's DNR could not express it — i.e., the declarative surface froze anti-tracking capability at the browser vendor's implementation pace. | Firefox ahead by 3+ years per EFF | same | Dec 2021 | High |
| 36 | Cross-vendor dynamics: Mozilla kept blocking `webRequest` while also implementing DNR; Mozilla floated "limited event pages" to restore web-platform APIs to extension background contexts; Apple expressed support; "Google said no." | — | same | Dec 2021 | High |
| 37 | Early technical assessment that EasyList-class filter lists cannot be ported faithfully onto a permission-less DNR blocker — the rule-count and rule-semantics limits bite before the lists finish converting. | — | uBlock Origin issue #338 discussion | Dec 2018 | Medium |
| 38 | Where the privacy rationale has real content: MV3's remote-code ban (bundled with, though separable from, the DNR change) is the one piece EFF endorsed — remotely hosted extension code is the mechanism behind most update-time trojanization (rows 22, 25). | — | same EFF piece (row 34) | Dec 2021 | High |

**Implications:** MV3 conflated two separable moves: (a) banning remote code — genuinely protective, and cheap for Izcal to adopt as a store requirement with reproducible builds; and (b) de-capability-izing content blockers — which transfers trust from the extension author (auditable, replaceable, competing) to the browser vendor (monolithic, slow, conflicted when the vendor's ads are the target). Izcal should keep powerful blocking APIs but attach the *audit* burden to the store: any extension requesting intercept-all-traffic capability gets mandatory review, signed reproducible builds, and automatic re-review on ownership change — getting Google's abuse-control goals without freezing anti-tracking capability at vendor pace.

**Implications:** The defence-side record splits into two honest strategies — Tor's (no third-party extensions, ever) and Safari's (make the top use cases native, then require per-site grants for the rest) — and one incoherent one (allow everything and warn). Izcal should pick Safari's shape with Tor's honesty: native-first for content blocking, password fill, and dark mode (the categories that keep appearing in rows 22 and 39), per-site grants for everything else, and a visible "N of your M extensions are enumerable by every site you visit" indicator, because the fingerprinting cost of each install is real and currently invisible to users.

## 8. The privacy cost of NOT having extensions

| # | Finding | Numbers | Source | Date | Conf. |
|---|---------|---------|--------|------|-------|
| 43 | When extension-level blocking is weakened (MV3), the vendor-documented fallback channel is DNS/network-level filtering — a *worse* privacy trade (traffic handed to a resolver/proxy operator, coarser rules, no per-site user control) for the same user goal. | — | BlueCat Networks, "Manifest V3 doubts? Try a DNS-based solution" (secondary) | Feb 2023 | Low |
| 44 | The userscript escape hatch carries its own collection risk: widely-used userscript managers have shipped third-party analytics (e.g., Tampermonkey's Google Analytics, enabled by default, reported by users in 2017) — i.e., users pushed off the extension platform land on a channel with full host access and *less* disclosure structure than a store listing. | — | Community reports (Reddit r/firefox, 2017); no peer-reviewed quantification found | 2017 | Low |
| 45 | Tor's own guidance routes users who need blocking to the *built-in* uBlock Origin and forbids further add-ons — evidence that a browser can eliminate the third-party extension channel without leaving users defenseless, provided the built-in capability is real. | — | Tor forum guidance (moderator prose) | 2021–2025 | Medium |

**Implications:** Row 6's arithmetic cuts both ways: if Izcal ships no extension capability at all, users who need blockers or password fill will reach for OS proxies, DNS filters, or userscript managers — channels with strictly worse privacy properties than a well-designed in-browser extension (the browser at least sandboxes and audits what an extension does; nothing audits a system proxy). The record supports "native-first + tightly-reviewed minimal extension platform" over both extremes.

## Open questions

1. **Firefox's countermeasure set.** What exactly Firefox does against WAR enumeration (per-install `moz-extension` UUID behavior, `web_accessible_resources` `matches` enforcement) could not be verified from prose docs this session. A focused read of MDN's `web_accessible_resources` and Mozilla's hardening blog posts is needed before Izcal fixes its WAR design.
2. **XHOUND's exact fraction.** What percentage of the ~10,000 extensions XHOUND analyzed were actually fingerprintable (and how many users affected) — Semantic Scholar and author sites were unreachable. Worth one library visit; it is the anchor number for the 2017 baseline.
3. **Agarwal RAID 2024 user-impact figure.** The paper reports the affected user count alongside the 2,747 extensions; the number was truncated in every accessible snippet. Fetch the ACM page (bot-check permitting) or the authors' copy.
4. **Popular-extension `<all_urls>` breadth.** The often-cited store-crawl percentages ("X% of the most popular extensions can read all data on all sites") have no primary source this session. Either crawl the current CWS/AMO ourselves for the spec, or cite Picazo-Sánchez's 39.8% least-privilege figure alone.
5. **Chrome install-side signals.** Whether Chrome still sends extension IDs to Google outside update checks (Safe Browsing CRX lookups, enterprise policy checks), and where the Privacy Whitepaper's current text lives. Needed for the "no phone-home" spec section.
6. **Brave's actual position.** Does Brave apply any fingerprinting defense to extension enumeration (e.g., WAR filtering)? Its privacy-features page yields nothing; a support-forum or blog search would settle it.
7. **MV3's measured effect on tracker prevalence.** Is there a post-deprecation measurement comparing tracking-request prevalence under MV2 vs MV3 content blockers? If none exists, Izcal's spec should commission one — it is the falsifiable version of the EFF/Google dispute.
8. **Quantified "extension-less" costs.** No study measures how many users move to DNS proxies or userscripts when extension platforms are restricted. If Izcal restricts extensions, this is the number to justify the native-first investment; no one has produced it.
