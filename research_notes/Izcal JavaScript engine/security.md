# Izcal JavaScript engine: security of JS and Wasm engines

Compiled 19 October 2026. Primary sources were preferred: Project Zero's 0-day "In the Wild" spreadsheet and root-cause analyses (RCAs), engine teams' blogs, vendor documentation, peer-reviewed papers (read in full text where marked High), and security advisory databases.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, a technical secondary source, or prior knowledge not re-fetched this session; **Low** = secondary source only (forums, press).

**Method notes.**
- Section 1's tallies are this note's own count. The Project Zero sheet ([P0 0-day ITW sheet](https://docs.google.com/spreadsheets/d/1lkNJ0uQwbeC1ZTRrxdtuPLCIl7mlUreoKfSIgajnSyY/)) was exported as xlsx on 19 October 2026 and parsed locally. It has tabs for 2014–2026. Its Introduction tab still says "Last updated: 2023-04-20", but the year tabs run to September 2026. Rows were assigned to an engine from the description; where the description names only "WebKit", the JavaScriptCore (JSC) attribution is marked Medium.
- The sheet's descriptions are vendor advisory titles ("Type confusion in V8"). Root causes come from the P0 RCA index ([RCA list](https://googleprojectzero.github.io/0days-in-the-wild/rca.html)), which covers 18 JS-engine entries from 2019–2022 and none after 2022.
- The security scope's research note (`research_notes/Izcal security scope/exploits_mitigations.md`, in PR #8) already holds the 2022–2026 Chrome tally, MiraclePtr, MTE, MIE, VRP and Pwn2Own data. This note does not repeat it; it extends the window to 2018, adds the other engines, and asks the engine-design questions: which bug classes an implementation choice removes, and what each mitigation and verification technique costs and buys.
- No engine source code was read (M-1). Papers, blogs, advisories and RCAs were.

**Implications:** Every in-the-wild JS-engine row in the sheet (2018–2026) is typed memory corruption, and every one with a published root cause (Project Zero's RCAs, 2019–2022) was memory corruption reached through an engine **logic** error (type assumption, side effect, GC tracking, bounds); V8 says its exploited bugs are "rarely 'classic' memory corruption" (1.7). The 2023–2026 rows carry advisory titles only, with no published root cause, so the logic-error share after 2022 is not established (corrected per the fact-check, `factcheck.md` FC-M1). Izcal's engine will be judged on exactly this class. The legacy-engine rows (1.4) also show that an engine kept reachable for compatibility stays a target; Izcal should ship one engine and no legacy mode.

## 2. The bug classes behind the exploits, with root causes

| # | Class | What goes wrong | Exploited examples (root cause from RCA or write-up) | Source | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Side-effect modeling errors in the optimizing JIT** | The compiler assumes an operation cannot run user JS (a getter, `valueOf`, a Proxy trap) and keeps a type check eliminated across it; user code changes the object's shape in between | CVE-2020-6418, "Chrome incorrect side-effect modelling issue in Turbofan leading to type confusions". | 2.2 | **Speculation/dependency invalidation errors** | Optimized code depends on a fact about an object layout (a map, a global property cell) and is not invalidated when that fact changes | CVE-2020-16009, "Turbofan Type Confusion after Map Deprecation"; CVE-2021-30632, "Turbofan Type confusion in Global property access" | [P0 RCA list](https://googleprojectzero.github.io/0days-in-the-wild/rca.html) | High |
| 2.3 | **Typer / range-analysis errors leading to bounds-check removal** | The compiler computes a wrong value range, then folds a bounds check as always true. | 2.4 | **GC root-tracking and write-barrier bugs** | A live object is not visible to the collector (missing root, wrong ephemeron handling) or a JIT elides a write barrier, so the GC frees or fails to trace a live object | CVE-2021-37975, "v8 garbage collector logic bug causing live objects to be collected"; CVE-2021-4102, "incorrect node elision in Turbofan leads to unexpected WriteBarrier elision"; the four JScript "not tracked by the garbage collector" bugs (1.5) | [P0 RCA list](https://googleprojectzero.github.io/0days-in-the-wild/rca.html); [P0 Déjà vu](https://projectzero.google/2021/02/deja-vu-lnerability.html) | High |
| 2.5 | **Deoptimization and object materialization** | When optimized code bails out, escaped-analysis objects are rebuilt inconsistently with what the interpreter expects | CVE-2022-1364, "Inconsistent Object Materialization in V8" | [P0 RCA list](https://googleprojectzero.github.io/0days-in-the-wild/rca.html) | High |
| 2.6 | **Runtime/builtin and IC errors (not JIT)** | Builtins or inline caches that re-read state after calling user code (TOCTOU), interceptors, or leaked internal sentinels | CVE-2022-1096, "Type Confusion in Property Access Interceptor"; CVE-2021-38003 (V8 "inappropriate implementation", the internal hole sentinel leaking to script); the canonical public example is JSC's `Array.prototype.slice` reading a length, then calling `valueOf`, then copying with the stale length (CVE-2016-4622, Phrack 2016). | 2.7 | **Front-end: parser and bytecode generator** | The bytecode generator emits code whose register/scope assumptions the interpreter trusts | CVE-2022-4262, "Incorrect Bytecode Generation by JavaScript Parser" | [P0 RCA list](https://googleprojectzero.github.io/0days-in-the-wild/rca.html) | High |
| 2.8 | **Wasm validation and Wasm codegen** | A limit check that was correct for Wasm 1.0 became insufficient when Wasm GC added recursive type groups: types after a group of 1,000,000 types got index `kV8MaxWasmTypes`, aliasing an internal heap type; the compiler then elided `ref.cast` as always-succeeding, giving "a universal type confusion". | 2.9 | Wasm codegen in a Rust engine | Wasmtime/Cranelift's worst bugs are instruction-selection and lowering errors that drop or mis-form the sandbox check | CVE-2023-26489 (x86-64 guest-controlled out-of-bounds read/write, CVSS 9.9), CVE-2021-32629, CVE-2026-34971 (aarch64), CVE-2026-34987 (Winch). 12 of Wasmtime's 75 advisories are miscompiles or codegen sandbox breaks | [Wasmtime advisories](https://github.com/bytecodealliance/wasmtime/security/advisories) (tally via GitHub API, 2026-10-19); [Arrival, OOPSLA 2025, §1](https://www.contrib.andrew.cmu.edu/~bparno/papers/arrival.pdf) | High |
| 2.10 | **Fixes are part of the attack surface.** A TurboFan induction-variable typing bug was patched assuming the loop increment cannot change in the body; a variant trigger still worked, and the later conservative patch "introduced an additional security vulnerability". CVE-2019-1429 exists because the CVE-2019-1367 patch did not fix the original proof-of-concept | 2 documented incomplete-fix chains | [P0 Déjà vu](https://projectzero.google/2021/02/deja-vu-lnerability.html) | 2021-02 | High |

**Root-cause share of the 10 V8 RCAs that name a component (2020–2022):** 6 in the optimizing-compiler pipeline (side effects, dependencies, write-barrier elision, materialization, a TurboFan logic bug), 1 GC, 1 runtime/IC, 1 bytecode generator, 1 not stated in the title. This matches V8's "roughly half in compilers" over a longer window (1.7). Confidence: High for the titles; the bucket assignment is this note's.

**Implications:** The exploitable bugs are **disagreements between two parts of the engine about an invariant** (the JIT's model of side effects vs. the runtime; the GC's root set vs. the code; the validator's limit vs. the type encoding). A design that states each invariant once, in a machine-checkable form, and derives both sides from it attacks the class rather than the instance. Wasm validation needs the same rigor as JS, because Wasm GC made it as type-rich as a JIT's type system.

## 3. What a memory-safe implementation language removes, and what it does not

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | V8's team: "memory safety cannot be guaranteed by the compiler if a compiler is directly part of the attack surface". Its exploited bugs are logic bugs that become memory corruption through generated code and through the engine's own heap manipulation | Qualitative | [V8: The V8 Sandbox](https://v8.dev/blog/sandbox) | 2024-04-04 | High |
| 3.2 | **Wasmtime is the best evidence for a Rust engine, and its memory-safety failures are exactly the classes Rust does not cover.** Of 75 advisories (2021–Oct 2026): ~12 codegen/miscompile sandbox issues (2.9); **7 GC-reference memory-corruption bugs** (externref use-after-free and invalid free at GC safepoints, 2021–2022; "Rooting for GC values live across `try_call` may be missing, causing GC heap corruption" and "Mis-typed WebAssembly tag imports can lead to GC heap corruption", October 2026); 1 native stack buffer overflow in unvalidated component-model data (critical, October 2026); the rest are panics (19 mention "panic"), WASI capability logic bypasses (~15) and resource exhaustion | 75 total, 51 in 2026 | [Wasmtime advisories](https://github.com/bytecodealliance/wasmtime/security/advisories) (tally) | 2026-10-19 | High |
| 3.3 | Rust's soundness depends on `unsafe` library code being correct; RustBelt (POPL 2018) gave the first machine-checked safety proof for a realistic Rust subset and states, per `unsafe` library, the verification condition for it to be a safe extension. The work found that `MutexGuard<Cell<i32>>` was wrongly `Sync` (Rust issue #41622) | 1 std soundness bug found | [RustBelt, POPL 2018](https://plv.mpi-sws.org/rustbelt/popl18/paper.pdf) | 2018-01 | High |
| 3.4 | Memory-safe new code works where the attacker's bug would be "classic" memory corruption: Android's Rust has ~0.2 memory-safety vulnerabilities per MLOC against ~1,000 for historical C/C++ | ~1000x | [Google: Rust in Android](https://blog.google/security/rust-in-android-move-fast-fix-things/) (via the security-scope note 6.3) | 2025-11-13 | High |
| 3.5 | Deno's two memory bugs sat at the Rust↔engine boundary (`v8::External` lifetimes; a resizable ArrayBuffer shrunk under an async Rust borrow). With an own engine the boundary moves inside the engine, between safe Rust and the GC heap | 2 | security scope note `exploits_mitigations.md` 9.10–9.11 (PR #8) | 2023–2024 | High |

**Classes, by what removes them** (this note's synthesis of Sections 1–3):

| Bug class | Removed by a memory-safe implementation language? | What else is needed |
|---|---|---|
| Classic buffer overflow / UAF in the runtime, parser, builtins written in safe code | **Yes** | — |
| TOCTOU in builtins (stale length after user callback) | **Partly**: safe indexing turns it into a panic or wrong result, not corruption, *if* the builtin's storage is a bounds-checked safe structure. Not if the builtin is emitted as machine code or uses raw element pointers | Builtins written in a safe language, or verified when generated |
| GC root tracking, write barriers, moving-GC pointer updates | **No** by default. Every tracing GC in Rust needs `unsafe` at the heap boundary (Wasmtime 3.2) | A GC API whose types make un-rooted references unrepresentable, plus proof or exhaustive checking of the `unsafe` core |
| JIT-emitted code (type checks elided, bounds checks folded, barriers dropped, wrong lowering) | **No.** The output is machine code | Verified or validated compilation (Section 6), in-process sandboxing of generated code (Section 7), tier limits (Section 4) |
| Wasm validation logic errors (limits, type indices) | **No**: a logic error yields a well-typed but wrong program | Validator derived from or checked against a mechanized spec (6.6) |
| Spectre | **No** | Process isolation (Section 5) |
| Panics and resource exhaustion | **No**: they become DoS instead of RCE | Panic-free paths in the hot engine, quota limits |

**Implications:** Rust removes the minority of engine exploits that were classic memory bugs and turns some TOCTOU bugs into panics. It does not touch the majority (JIT and GC logic). Izcal's engine security must therefore rest on **verification of generated code and of the GC interface**, plus containment, not on the language alone.

| 4.11 | **MTE / Apple MIE** | Stops spatial and temporal heap bugs in allocator-managed memory; Apple could not rebuild any of 6 mercenary chains under MIE (vendor claim). **Implications:** Turning the JIT off is the single most effective lever (about half of exploited bugs) and costs 2x–12x on compute benchmarks but little on typical browsing (6%–17%). Apple already requires engines to be correct without a JIT. A from-scratch engine can do better than "JIT on/off": a **fast interpreter and a baseline tier that are verified or trivially checkable**, an optimizing tier only where it pays, code pages never RWX, and CFI/PAC designed in, not retrofitted.

## 5. Spectre and the move to process isolation

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | V8 found "software mitigation of all possible leaks due to Spectre was infeasible". LFENCE-style barriers and retpolines cost 2–3x on Octane; masking ("poisoning") cost under 20%; variant 4 was judged infeasible in software. Conclusion: "the only effective mitigation is to move sensitive data out of the process's address space"; site isolation was deployed "for as many platforms as possible by May 2018"; Chrome no longer assumes language-enforced confidentiality within a renderer | 2–3x; <20% | [V8: A year with Spectre](https://v8.dev/blog/spectre) | 2019-04-23 | High |
| 5.2 | Timers were coarsened (5 µs → 100 µs plus jitter) and SharedArrayBuffer was disabled until cross-origin isolation (COOP/COEP) existed | — | same | 2019 | High |
| 5.3 | Spectre-hardened Wasm (Swivel): randomized designs under 10.3% on SPEC 2006 (Wasm subset); deterministic designs 3.3%–240.2%; 9–36.3x lower than fence-based defenses | 10.3%; up to 240% | [Swivel, USENIX Security 2021](https://www.usenix.org/conference/usenixsecurity21/presentation/narayan) | 2021-08 | High (abstract) |

**Implications:** No in-process engine mechanism provides confidentiality against Spectre. Izcal already has site-per-process (I-1); the engine must not reintroduce cross-site data into one isolate or heap (for example, shared caches of compiled code or interned strings across sites).

## 10. Open questions and gaps in this research

- The P0 RCA index stops in 2022; root causes for 2023–2026 V8 bugs (19 rows) are only advisory titles. Chrome's bug tracker entries would settle the JIT/non-JIT split for that period.
- JSC component attribution (1.6) is unverified per CVE.
- No primary measurement of Chrome's V8-optimizer setting or of Lockdown Mode on current hardware was found; Izcal should measure its own tiers instead.
- Costs of per-thread W^X toggling and PKU switching on JIT-heavy workloads were not found in primary sources.
- TurboTV's V8 bug yield is not in its abstract; the full evaluation was not read.
- "JIT-Picking" (differential JIT fuzzing, CCS 2022) was not read; its results are not cited.
