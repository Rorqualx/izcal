# Izcal JavaScript engine: history and postmortems

Compiled 19 October 2026. Primary sources were preferred (engine blogs, papers, maintainers' posts, release notes, commit messages and issue trackers). Bugzilla records were read through its REST API, and commit messages from the commits themselves. Conformance figures come from the live test262.fyi data file.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, or a vendor claim without data; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: this file records ideas, measurements and reasons. It contains no code and no design template from any engine. Where it says what an engine "does", that is evidence to reason from, not a shape to copy.

## 1. Origins: Mocha, SpiderMonkey, JScript, Rhino (1995–2007)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Mocha** was prototyped by Brendan Eich in ten days. Hand-written lexer, recursive-descent parser that **emitted bytecode directly, no parse tree**; "simple and slow" bytecode interpreter; values as a large discriminated union; **reference counting**. | 10 days (believed 6–15 May 1995) | [Wirfs-Brock & Eich, "JavaScript: The First 20 Years", HOPL IV, §2.2](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf) | 1995-05 (paper 2020-06) | High |
| 1.2 | **Why bytecode in 1995:** a requirement of Netscape's LiveWire server team, who wanted bytecodes "rather than source parsing, for faster server application loading". The constraint was load time for an embedder, not execution speed. | — | [HOPL §2.2](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf) | 1995 | High |
| 1.3 | JavaScript 1.1 (Netscape 3.0, Aug 1996) was still mostly the 10-day prototype. Eich then rewrote the engine in two weeks to "pay down the technical debt": **tagged pointers with immediate primitives replaced the discriminated union; mark/sweep GC replaced reference counting**. The result was named **SpiderMonkey**. He insisted on reimplementing before writing a specification, "to correct original design mistakes before enshrining them in a specification." | 2 weeks | [HOPL §5](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf) | 1996 | High |
| 1.4 | **JScript** (Microsoft, from Oct 1995): a simple bytecode interpreter, later improved, joined to a separate parser and a GC by Patrick Dussud. Lack of a specification made compatibility a guessing exercise, which drove standardization. | — | [HOPL §4](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf) | 1995–96 | High |
| 1.5 | **Rhino**: JavaScript in Java, started at Netscape (Norris Boyd hired onto the JS team, per HOPL). It has both an interpreter and a compiler to JVM bytecode. Still maintained: release 1.9.1 on 2026-02-15. | GitHub repo pushed 2026-10-15 | [HOPL §5](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf); [mozilla/rhino](https://github.com/mozilla/rhino) | 1997–2026 | Medium (design detail from recollection; release date High) |
| 1.6 | Until 2007, browser engines were interpreters tuned for short scripts. **SunSpider** (WebKit, 2007), small tests derived from web code, made speed a public competitive axis, because "browser game theory" stopped vendors competing on language features. | — | [HOPL §19](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf) | 2007 | High |

**Implications:** JavaScript's two oldest engine decisions (direct-to-bytecode compilation for fast loading, and a precise tracing GC instead of reference counting) were made for embedding and correctness and have outlived every later tier. Writing the engine before the specification left quirks in the specification for good, so Izcal should do the opposite: anchor to the spec text first (M-1) and treat the spec as executable (Section 9).

## 2. The 2008 performance war

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **SquirrelFish** (WebKit) replaced an AST-walking interpreter. The post names three costs of tree-walking: visiting nodes that do no work, a virtual call and return per node, and passing state between nodes. The new engine was "a **register-based, direct-threaded**, high-level bytecode engine", citing Shi et al. "Virtual Machine Showdown" for register machines. | 1.6× SunSpider over the old interpreter | [webkit.org/blog/189](https://webkit.org/blog/189/announcing-squirrelfish/) | 2008-06-02 | High |
| 2.2 | **SquirrelFish Extreme** added a context-threaded JIT (about 4,000 lines, x86-32 only at first), **polymorphic inline caches keyed on StructureID** (credited to Self), and a regex JIT (WREC). | SunSpider runs/min: Safari 3.0 5.4 → SquirrelFish 29.9 → SFX 63.6 | [webkit.org/blog/214](https://webkit.org/blog/214/introducing-squirrelfish-extreme/) | 2008-09-18 | High |
| 2.3 | **V8** (Chrome, Sept 2008, led by Lars Bak with Self/Smalltalk/Java VM experience) published three design pillars: **hidden classes** with transitions (crediting Self's maps), **inline caches** patched into machine code, and **"no intermediate byte codes, no interpreter"**: source was compiled straight to machine code on first run. Also a precise generational GC. | ~10× Firefox's SpiderMonkey on Google's benchmark, ~2× on SunSpider (contemporary report quoted in HOPL) | [V8 "Design Elements" (2008, archived)](https://web.archive.org/web/2008/http://code.google.com/apis/v8/design.html); [HOPL §19](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf) | 2008-09 | High |
| 2.4 | **TraceMonkey** (Firefox 3.5), from Andreas Gal's PhD work: interpret, count loop iterations, **record a trace** of the hot path with observed types, compile it with nanojit, and side-exit back to the interpreter on a failed guard. | Example loop: 990 ms (Firefox 3) → 45 ms; object-heavy code only 2–5× | [Mandelin, "An overview of TraceMonkey"](https://hacks.mozilla.org/2009/07/tracemonkey-overview/); Gal et al., PLDI 2009 | 2009-07-17 | High |
| 2.5 | TraceMonkey's own documentation listed its limits at launch: **trace aborts** on unsupported constructs (eval, arguments, getters/setters, with, most closures, recursion, DOM property access), a cap of **32 traces per loop** ("trace explosion"), and slowdowns on branchy or type-changing code. | 32 traces/loop | [hacks.mozilla.org 2009-07](https://hacks.mozilla.org/2009/07/tracemonkey-overview/) | 2009-07-17 | High |
| 2.6 | **Opera Carakan** moved from stack to **register bytecode** ("fewer instructions need to be executed, and less data needs to be copied"), added **automatic object classification** (classes shared by objects with the same prototype and property set, with cached lookups), and native code generation from static type analysis plus speculation. Its predecessor Futhark had been designed "to minimize code footprint and memory usage, rather than to achieve maximum execution speed", which the post calls the right trade-off for Opera's devices until then. | 2.5× SunSpider with switch dispatch alone; 5–50× on the few tests the JIT handled | [Lindström, "Carakan", Opera Core blog](https://web.archive.org/web/2009/http://my.opera.com/core/blog/2009/02/04/carakan) | 2009-02-04 | High |
| 2.7 | **Chakra** (IE9) argued past benchmarks: scripts took 10–30% of page load on typical sites and 30–90% in apps like Gmail. It added a new interpreter for ordinary pages and **background compilation on a separate core**, because "the time needed to [compile and optimize] may offset the savings of running optimized code." | 10–30% / 30–90% of time in script | [IE Blog, "The new JavaScript engine in Internet Explorer 9"](https://web.archive.org/web/2010/http://blogs.msdn.com/b/ie/archive/2010/03/18/the-new-javascript-engine-in-internet-explorer-9.aspx) | 2010-03-18 | High |

**Implications:** Every 2008-era engine converged on two ideas within a year: **shape-based object layout plus inline caches** (all crediting Self) and **getting out of the AST walker**. Both are still in every fast engine in 2026. The ideas that diverged (V8's no-interpreter stance, TraceMonkey's traces) were later reversed (Sections 3 and 5). Izcal should treat shapes and ICs as settled and the tiering structure as the open question.

## 3. SpiderMonkey: traces, methods, type inference, and Warp

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **JägerMonkey**, a whole-method JIT, was added to cover code TraceMonkey could not trace stably. It shipped in Firefox 4. | — | [hacks.mozilla.org 2010-03](https://hacks.mozilla.org/2010/03/improving-javascript-performance-with-jagermonkey/) (listed in [SpiderMonkey bibliography](https://github.com/mgaudet/SpiderMonkeyBibliography)) | 2010–11 | Medium |
| 3.2 | **Why tracing was abandoned (maintainers' words):** before JägerMonkey, performance was **bimodal** (interpreted or traced), so "huge amounts of effort" went into tracing code that should not be traced, making TraceMonkey "really complicated". With both JITs, the mode-switching heuristics were "quite hairy". **Type inference made JägerMonkey alone faster on average than JägerMonkey plus TraceMonkey**, and "TraceMonkey was actively getting in the way of various additional JaegerMonkey and type inference improvements." Tracing still suited "very tight, non-branchy loops". | 67,000 lines removed | [Nethercote, MemShrink report wk 23](https://blog.mozilla.org/nnethercote/2011/11/23/memshrink-progress-report-week-23/); [bug 697666 (disable, 2011-10-31)](https://bugzilla.mozilla.org/show_bug.cgi?id=697666); [bug 698201 "Remove tracer", fixed 2011-11-23, mozilla11](https://bugzilla.mozilla.org/show_bug.cgi?id=698201) | 2011-11-23 | High |
| 3.3 | **IonMonkey** (Firefox 18) added what JägerMonkey and TraceMonkey lacked: an **IR** to optimize over (LICM, sparse GVN, linear-scan register allocation, DCE, range analysis for bounds-check elimination). It relied on Hackett & Guo's hybrid **type inference** (PLDI 2012). | Kraken 2602 → 1921 ms; V8 bench +7% over Firefox 17 | [IonMonkey in Firefox 18](https://blog.mozilla.org/javascript/2012/09/12/ionmonkey-in-firefox-18/); [Hackett & Guo 2012](https://dl.acm.org/citation.cfm?id=2254094) | 2012-09-12 | High (TI link Medium) |
| 3.4 | **Baseline** (Firefox 23) replaced JägerMonkey because, once TI was added, JM had become an optimizing JIT it "was not designed for". The post names the conflicts: an optimizing JIT *uses* type information while a baseline JIT should *collect* it; JM code was **invalidated** when types changed, while Baseline code never is; JM used a heap interpreter stack and Ion the C stack, making cross-JIT calls expensive; TI and JM used a lot of memory; JM was "really complex and hard to work with". Baseline: no IR, IC stub chains that feed type data, Ion's calling convention. | 10–100× over the interpreter; compiles after 10 iterations vs JM's 40; +5–10% on suites | [The Baseline Compiler Has Landed](https://blog.mozilla.org/javascript/2013/04/05/the-baseline-compiler-has-landed/) | 2013-04-05 | High |
| 3.5 | **CacheIR**: Baseline and Ion each had their own IC code with "a lot" of duplication and features in one tier missing from the other. CacheIR is a **linear, branch-free IR of guards and operations**, with shape pointers and slot offsets stored as separate stub fields, compiled to machine code by a simple allocator. One emitter serves all tiers; identical stubs share code. | "Thousands of lines" of boilerplate removed | [de Mooij, "CacheIR"](https://jandemooij.nl/blog/cacheir/) | 2017-01-25 | High |
| 3.6 | **Baseline Interpreter** (Firefox 70): big sites (Docs, Gmail) spent real time in Baseline JIT compilation; the C++ interpreter was too slow and collected no type data. The new tier is **generated from the Baseline JIT's own code generator**, shares its ICs, profiling data (JitScript) and **frame layout**, and adds only a bytecode PC to the frame. Ion now deoptimizes into the interpreter, which simplified Baseline JIT and Ion. | Google Docs load 901 → 676 ms (633 with Baseline JIT); Speedometer 31 → 52 (69); Baseline JIT threshold raised 10 → 100 | [de Mooij, hacks.mozilla.org](https://hacks.mozilla.org/2019/08/the-baseline-interpreter-a-faster-js-interpreter-in-firefox-70/) | 2019-08-30 | High |
| 3.7 | **Warp** (Firefox 83) replaced IonBuilder: Ion now builds MIR by **transpiling the CacheIR** recorded in the baseline tiers, instead of consulting **global Type Inference**. TI was dropped because of its memory use, the engine-wide tracking code it needed, and its GC overhead. Warp adds trial inlining (per-call-site specialization) and off-thread MIR building. | Google Docs load ~20% faster; Speedometer +10–12%; tp6 memory −8%; slower than Ion on Octane/Kraken, which the authors attribute to years of Ion tuning | [de Mooij, "Warp"](https://hacks.mozilla.org/2020/11/warp-improved-js-performance-in-firefox-83/) | 2020-11-13 | High |
| 3.8 | IonBuilder and TI were deleted in [bug 1673553 "Remove IonBuilder and TI"](https://bugzilla.mozilla.org/show_bug.cgi?id=1673553), resolved 2020-12-15 with target milestone 85 (the bibliography says Firefox 84: conflict noted). | — | Bugzilla REST | 2020-12-15 | High |
| 3.9 | SpiderMonkey's 64-bit **value representation** is NaN-boxing (PUNBOX64): non-number values live in the NaN space, with a 5-bit tag next to a 47-bit payload. It depends on user-space pointers fitting in 47 bits; 57-bit (5-level paging) addresses are "opt-in, and we simply don't use them". The 32-bit form (NUNBOX32) keeps the tag in the high word. NaNs must be canonicalized wherever untrusted doubles enter. | 47-bit payload, 5 tag bits | [js/public/Value.h comment](https://github.com/mozilla/gecko-dev/blob/master/js/public/Value.h) | current | High |

**Implications:** SpiderMonkey's 15-year arc is one lesson repeated. **Global or speculative machinery that every tier must honour (trace selection, global TI) became the bottleneck. Per-site, recorded, tier-shared data (CacheIR) won.** The Warp results show this also cut memory and won on real pages while losing on old synthetic suites. For Izcal, a single recorded IC language that is the profile, the baseline code and the optimizer's input is also a natural unit for determinism (it can be logged and replayed) and for DevTools visibility.

## 4. JavaScriptCore: four tiers, LLVM to B3, Riptide

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **FTL** added a fourth tier on **LLVM** for "aggressive C-like optimizations". Tiers: **LLInt** (low-latency interpreter) → **Baseline** (after a statement runs more than 100 times or more than 6 calls) → **DFG** (more than 1000 times / 66 calls) → **FTL** (only from DFG code; functions running more than ~10 ms). | FTL over DFG: Richards +40%, asm.js +35% avg | [Pizlo, "Introducing the WebKit FTL JIT"](https://webkit.org/blog/3362/introducing-the-webkit-ftl-jit/) | 2014-05-13 | High |
| 4.2 | **Why FTL left LLVM for B3:** LLVM took **about three quarters or more of FTL compile time**, which on some workloads outweighed the gain; LLVM IR needs much memory per function and causes cache misses; LLVM was built for C-like languages, and its **patchpoints need predetermined sizes and its speculation checks split basic blocks**, weakening optimization. B3 has two IRs (B3 SSA, Air machine-level), compact by-value objects, and first-class `Patchpoint` and `Check`. | LLVM 4.7× slower to compile JetStream hot functions (goal was 10×); MacBook Air: JetStream +4.5%, Kraken +11.6%, Octane +5.2%; Mac Pro: no change on JetStream/Octane, Kraken +8.2% | [Pizlo, "Introducing the B3 JIT Compiler"](https://webkit.org/blog/5852/introducing-the-b3-jit-compiler/) | 2016-02-15 | High |
| 4.3 | **Measured tier economics** (JetStream 2, author's machine): cost per bytecode LLInt 3.97 ns, Baseline 1.71 ns, DFG 0.349 ns, FTL 0.225 ns. Baseline ~2× LLInt; DFG ~5× Baseline at ~4× Baseline's compile time; FTL ~1.5× DFG at ~6× DFG's compile time. A failed speculation costs ~2,499 ns (DFG) or ~9,998 ns (FTL) against ≤~1.48 ns of benefit, so the DFG must be right more than ~99.94% of the time. | Thresholds LLInt→Baseline 500, Baseline→DFG 1,000, DFG→FTL 100,000 execution points | [Pizlo, "Speculation in JavaScriptCore"](https://webkit.org/blog/10308/speculation-in-javascriptcore/) | 2020-07-29 | High |
| 4.4 | JSC prefers **OSR exit** over "diamond" fast/slow paths, and **watchpoints** (the runtime notifies the compiler; code is jettisoned) over emitted checks. | — | [Speculation in JSC](https://webkit.org/blog/10308/speculation-in-javascriptcore/) | 2020-07-29 | High |
| 4.5 | **Why LLInt is in offlineasm:** in C++ it would need a second native frame per JS call and make OSR between tiers hard to maintain; in raw assembly it would need a rewrite per CPU. Offlineasm is a portable macro assembler that shares the JIT's frame and register conventions and can also compile to C++ (for no-JIT targets). | ~5,000 lines | [Speculation in JSC](https://webkit.org/blog/10308/speculation-in-javascriptcore/) | 2020-07-29 | High |
| 4.6 | **Riptide GC:** concurrent, **non-moving**, **conservative stack scanning**, generational through **sticky mark bits** rather than copying, reusing the existing generational barrier ("retreating wavefront"). It still stops the world for stack scanning and most DOM constraint solving. WebKit first had to do "the painful work of removing WebKit's previous use of copying". | JetStream splay-latency 5×; Octane SplayLatency 2.5×; JetStream +5%; Splay pauses >10 ms → <3 ms; barrier ~5% during GC, 0% otherwise | [Pizlo, "Introducing Riptide"](https://webkit.org/blog/7122/introducing-riptide-webkits-retreating-wavefront-concurrent-garbage-collector/) | 2017-01-20 | High |
| 4.7 | JSC's 64-bit values are NaN-boxed with a twist: doubles are stored **offset by 2^49**, so pointers have the top 16 bits zero and integers carry a fixed `NumberTag`. | `NumberTag = 0xfffe000000000000` | [JSCJSValue.h](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/runtime/JSCJSValue.h) | current | High |
| 4.8 | **Spectre (2018):** WebKit added **index masking** on all array-like accesses and **pointer poisoning**, cut timer precision to 1 ms and disabled SharedArrayBuffer. | Index masking: no measurable impact on Speedometer/ARES-6, <2.5% on JetStream | [Pizlo, "What Spectre and Meltdown mean for WebKit"](https://webkit.org/blog/8048/what-spectre-and-meltdown-mean-for-webkit/) | 2018-01-08 | High |

**Implications:** JSC gives the only published per-tier cost table in this survey. It shows the top tier buys only ~1.1–1.6× for ~6× the compile cost, while each lower tier buys about 2× or more. The LLVM episode is the clearest **technology-mismatch** postmortem: a general-purpose C backend did not model speculation or patching and spent most of the compile budget. Izcal should own its optimizing backend and design deopt and patching into the IR from day one. Riptide's non-moving, conservative design was chosen to fit C++ and JIT frames. That constraint is weaker for a Rust engine with precise roots, but it is evidence that a non-moving concurrent collector can meet browser latency.

## 5. V8: from no interpreter to five tiers

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | 2008 V8 compiled everything to machine code with no interpreter (2.3). Full-codegen (baseline) and **Crankshaft** (optimizing, from 2010) followed. | Crankshaft date from recollection | [Launching Ignition and TurboFan](https://v8.dev/blog/launching-ignition-and-turbofan) | 2010 | Medium |
| 5.2 | **Why Ignition + TurboFan replaced Full-codegen + Crankshaft:** Crankshaft optimized only a subset of JS (e.g. not try/catch/finally); new features needed hand-written code for **nine architectures**; Crankshaft had over ten thousand lines per architecture and a performance ceiling; **Full-codegen's machine code took almost one third of Chrome's JS heap**; generating it was slower than generating bytecode. | Baseline code memory 9× smaller on ARM64 low-RAM devices; Speedometer +5–10%; Node AcmeAir +10%; V8 memory −5–10% | [v8.dev, Launching Ignition and TurboFan](https://v8.dev/blog/launching-ignition-and-turbofan) | 2017-05-15 | High |
| 5.3 | **Ignition** is a **register machine with an implicit accumulator** (shorter bytecodes, fewer loads and stores). Its handlers are generated by TurboFan's backend from architecture-independent macro-assembly, avoiding hand-written assembly per port. It was first enabled on Android devices with ≤512 MB RAM. | Bytecode 25–50% the size of baseline machine code; ~5% less memory per tab | [v8.dev, Firing up the Ignition interpreter](https://v8.dev/blog/ignition-interpreter) | 2016-08-23 | High |
| 5.4 | **Sparkplug** fills the gap between interpreter and optimizer: a **single-pass, no-IR compiler from bytecode** that keeps the **interpreter's frame layout** (so the debugger, profiler, unwinding and OSR barely change) and calls the same builtins. | 5.5 | **Maglev**: many functions on real pages run too briefly to pay for TurboFan. Maglev is an **SSA CFG** optimizer with few passes that specializes on feedback during graph building. | ~10× slower to compile than Sparkplug, ~10× faster than TurboFan; Sparkplug alone +45% JetStream / +41% Speedometer over Ignition; energy −3.5% JetStream, −10% Speedometer | [v8.dev, Maglev](https://v8.dev/blog/maglev) | 2023-12-05 | High |
| 5.6 | **Why TurboFan's Sea of Nodes was abandoned** (Turboshaft, a CFG IR, from about 2022): effect and control chains were **too complex** (a wrong-chain bug went unnoticed for months); **too limited**, because most JS nodes sit on effect or control chains anyway, so little floats, and adding control flow during lowering is hard; **too slow**, with nodes changing only once per ~20 visits, ~3× more L1 d-cache misses (up to 7× in some phases), and Load Elimination bailing out on large graphs. Sea of Nodes was inherited from HotSpot C2. | Compile time roughly halved; CFG load elimination up to 190× faster | [Mercadier, "Land ahoy: leaving the Sea of Nodes"](https://v8.dev/blog/leaving-the-sea-of-nodes) | 2025-03-25 | High |
| 5.7 | Migration status in March 2025: the whole TurboFan JS backend and the entire Wasm pipeline were on Turboshaft. Builtins were still Sea of Nodes (being replaced slowly), and the **JS frontend was being replaced by Maglev's graph builder**. The post dates Crankshaft's replacement by TurboFan to 2013, while the launch post shows it shipping in 2017; 2013 is probably the project start. | — | [same](https://v8.dev/blog/leaving-the-sea-of-nodes) | 2025-03-25 | High (dates conflict flagged) |
| 5.8 | **Orinoco GC**: generational with an intermediate generation; **parallel scavenger**; **concurrent marking and sweeping** with write barriers; incremental slices; idle-time GC. | Scavenge main-thread time −20–50%; WebGL game pauses −50%; Gmail idle heap −45% | [v8.dev, Trash talk](https://v8.dev/blog/trash-talk) | 2019-01-03 | High |
| 5.9 | **Pointer compression**: 64-bit Chrome (2014) doubled pointer size, and tagged values were ~70% of the V8 heap. V8 stores 32-bit offsets in a 4 GB cage and gave up 32-bit Smis (now 31-bit) and unboxed double fields. | Heap −43%; renderer memory −20% on desktop; Octane regression went from ~35% to ~4% residual | [v8.dev, Pointer compression](https://v8.dev/blog/pointer-compression) | 2020-03-30 | High |
| 5.10 | **V8 sandbox**: 60% of Chrome in-the-wild exploits 2021–2023 were in V8, and many V8 bugs are **logic bugs** (e.g. a JIT trusting bounds after a callback), which memory-safe languages do not prevent. Raw pointers in the heap become **offsets inside a 1 TB reservation**, and external objects go through a **pointer table**. About half of exploited V8 bugs were in compilers, so disabling JITs would fix only part of the problem and cost 1.5–10× on compute-heavy work. | ≤~1% overhead on Speedometer/JetStream; in the Chrome VRP since Chrome 123 | [Groß, "The V8 Sandbox"](https://v8.dev/blog/sandbox) | 2024-04-04 | High |
| 5.11 | **Jitless mode** (for iOS, consoles, smart TVs and attack-surface reduction) runs only Ignition and a regex interpreter. | Speedometer 2 −40%; Web Tooling −80%; YouTube TV JS −6%; heap −1.7% | [v8.dev, jitless](https://v8.dev/blog/jitless) | 2019-03-13 | High |

**Implications:** Each V8 redesign reacted to a **measured** cost: memory (Full-codegen code in the heap), porting cost (nine architectures), compile latency (Sparkplug, Maglev), compiler engineering cost (Sea of Nodes) and exploitability (sandbox). By 2025, V8's surviving shape was **register bytecode plus a no-IR baseline with the interpreter's frames, then CFG SSA optimizers**. The sandbox postmortem matters most for a Rust engine: **memory safety in the host language does not cover JIT logic bugs**, so Izcal needs a containment boundary for engine-heap corruption as well as safe Rust.

## 12. What survived, and why

| Idea | Origin | Survived because | Evidence |
|---|---|---|---|
| Shapes/hidden classes + inline caches | Self → 2008 V8/JSC/Carakan | Real programs are structurally regular; one memory load per access | 2.2, 2.3, 2.6 |
