# Izcal JavaScript engine: gaps, the invisible, and what no engine does

Compiled 19 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers, engine source).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Scope.** This strand covers phase 3 of the first-principles-spec method for the engine: what developers struggle with when JavaScript and WebAssembly run, what engines keep invisible, and what an engine Izcal owns could do that no shipping engine does. For each idea it records the evidence that it matters, the prior attempts and their fate (with the stated reasons), and what Izcal's architecture makes possible. It is research only (M-1): ideas and evidence, never code or templates.

**Relation to the DevTools notes.** The DevTools strand already covers page-level gaps, surveys and record/replay products in depth: [invisible_gaps.md](../Izcal%20DevTools%20spec/invisible_gaps.md) (cited below as **[IG n]**), [history_postmortems.md](../Izcal%20DevTools%20spec/history_postmortems.md) (**[HP n]**), [visualization_ux.md](../Izcal%20DevTools%20spec/visualization_ux.md) (**[VU n]**), [protocols_standards.md](../Izcal%20DevTools%20spec/protocols_standards.md) (**[PS n]**) and the [fact-check](../Izcal%20DevTools%20spec/factcheck.md). This note does not repeat them. It adds the **engine-level** layer: what only the engine knows (tiering, deopts, GC, hashing, heap layout) and the engine-level precedents (TARDIS/JARDIS, V8 predictable mode, xsnap, taint-aware engines).

**Izcal constraints that apply.** HGBA-2 P1–P6 and M-1 (own engine, spec-anchored); I-1 (one renderer per site, never two sites in one process); HGBA-3 **B1** (deterministic substrate: injected clock, entropy, scheduler; DET-1, DET-2, DST-1), **B4** (data plane and mutation log), **B9** (agent principal, origin sets), **B10** (AI off by default); Stage 1 design 3.3 (determinism with an own engine becomes Izcal's requirement); DevTools spec 0.3 (IIP, recorded sessions, recording starts at a navigation boundary per the design critique's finding 1). Izcal's own measurement: V8 needed the fork's **predictable platform**, not just flags, to make GC-observable behaviour deterministic ([m0/determinism_crossplatform.md](../../m0/determinism_crossplatform.md)).

**Method note.** The shared web-search budget was used for the questions that carry design weight (determinism sources, engine-level time travel, safety controls, snapshots). The rest came from direct reads of known primary pages (ECMA-262 2027 draft, the CDP protocol documentation, two papers read as full PDFs). Rows built only from search summaries are graded Medium or Low and say so. Rows that first rested on engine source were re-sourced to published prose or black-box observation, or removed, in the 0.3.1 source-evidence pass (HGBA-2 M-1 part 3; [source_evidence_pass.md](source_evidence_pass.md)).

**Implications:** the engine is the only component that knows *why* code is slow (which IC went megamorphic, which guard failed, which tier ran it), and every engine keeps that behind internal flags whose format changes with each release. Izcal can make "why did this deopt / why is this not optimized" a **stable, versioned engine event stream** that its own DevTools consume, with plain-language reasons tied to source (and to the shape transition that caused them), and can show every tier change, including those the debugger causes.

## 2. Memory: heap snapshots, retaining paths and leaks

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Node's own documentation: a heap snapshot "requires memory about twice the size of the heap", risks the OOM killer, and "blocks the event loop". It covers one isolate only, not workers | ~2× heap | [Node.js v8 module](https://nodejs.org/api/v8.html) | read 2026-10-19 | High |
| 2.2 | Bloomberg's 500 MB snapshot took **over 30 minutes**. After fixes (numeric-string hash collisions, uncached line positions in minified code) a 100 MB snapshot fell from ~10 min to ~6 s | >30% of time in `ComputeStringHash()`; 100× | [Speeding up V8 heap snapshots (v8.dev)](https://v8.dev/blog/speeding-up-v8-heap-snapshots) | 2023-07-27 | High |
| 2.3 | Snapshots are needed most when the heap is near its limit, which is exactly when taking one can fail: V8 reports a heap snapshot of a demo page aborting with OOM on stable Chrome, and notes DevTools itself runs on an ordinary V8 heap | — | [One small step for Chrome, one giant heap for V8](https://v8.dev/blog/heap-size-limit) (search summary) | 2017 | Medium |
| 2.4 | Built-in tools show a moment (snapshot) or candidates (allocation timeline), never a confirmed leak. MemLab and BLeak diff snapshots across repeated loops to find leaks | Facebook OOMs −50%; BLeak −94% heap growth | [IG 7.3, 7.5, 7.6](../Izcal%20DevTools%20spec/invisible_gaps.md) | 2018–2022 | High/Medium |

**Implications:** heap inspection today is a stop-the-world copy of the whole heap into a second representation. An engine designed for it can keep the metadata a snapshot needs (object-to-source allocation site, retainer edges, per-realm ownership) incrementally, answer **retaining-path queries in place** without a full copy, and, under B1 replay, compare the heap at the same execution point across two runs. Leak finding becomes "replay the loop N times under the same seed and diff", which is exact rather than heuristic.

## 4. Time travel and omniscient debugging at the engine level

The product history (Web Replay, Replay.io, rr, Microsoft TTD, Pernosco, Timelapse, Elm, Redux) is in [HP 10.1–10.4], [VU 3.1–3.14] and [IG 15.9–15.17]. This section adds the precedents built **inside a JS engine**.

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **TARDIS** (Barr and Marron) showed that a managed runtime can make time travel the *default* debugger: snapshots of the managed heap plus a log, and it can "debug optimized code using time-travel to reconstruct state" | 7% average overhead; 0.6 MB/s log; worst-case 0.68 s time-travel latency | [TARDIS, OOPSLA 2014](https://www.microsoft.com/en-us/research/publication/tardis-affordable-time-travel-debugging-in-managed-runtimes/) | 2014-10 | Medium (abstract) |
| 4.2 | **JARDIS** shipped TARDIS's design in ChakraCore and Node-ChakraCore, with VS Code support. Record-replay-snapshot: inputs logged at the JsRT host API boundary (e.g. `Date.now` results), the PRNG **seed stored in each snapshot** "obviates recording each value", snapshots taken when the JS stack is empty (event-loop turns), letting a recording start at any point | ~20 kloc in ChakraCore, <100 lines in Node; runtime overhead under 2%; memory overhead up to 56%; 4.5–7.3 MB compressed log per 2–4 s | [Time-Travel Debugging for JavaScript/Node.js, FSE 2016 (PDF)](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/09/TTNode.pdf) | 2016-11 | High |
| 4.3 | **Fate:** it died with its engine, not on its merits. Node-ChakraCore was archived on 15 October 2020 and called itself "not an officially supported Node.js branch"; a 2019 SAP post notes V8-based Node has no time-travel debugging. Microsoft moved Edge to Chromium (announced December 2018) | archived 2020-10-15 | [nodejs/node-chakracore](https://github.com/nodejs/node-chakracore); [SAP blog](https://blogs.sap.com/2019/05/22/sit-belgium-2019-recap-debugging-node.js-applications-in-scp-cf.-part-4-time-travel-debugging/) | 2020-10-15 | High (archive) / Medium (cause) |
| 4.4 | **Omniscient debugging** (record every event, then query) dates to EXDAMS (1969). TOD made it scale for Java with a distributed event database, scoped capture and partial traces; trace volume is the central obstacle | ~15 MB/s, 10–115× slowdown (secondary table) | [Pothier and Tanter, IEEE Software 2009](https://pleiad.cl/papers/2009/pothierTanter-software2009.pdf); [TOD](https://pleiad.cl/tod) | 2007–2009 | Medium |
| 4.5 | Chrome's DevTools **Recorder** records and replays user flows (exportable to JSON and Puppeteer). | 4.6 | Chromium has **virtual time** for headless use: `Emulation.setVirtualTimePolicy` (experimental) replaces real time with a synthetic source for all frames, with policies `advance`, `pause`, `pauseIfNetworkFetchesPending`, a budget, an `initialVirtualTime` and a task-starvation cap "to prevent deadlock". **Implications:** every engine-level time-travel debugger (JARDIS) or browser-level one (Web Replay, Replay.io) died for **organisational** reasons: the engine was abandoned, the author left, or the product lacked a business. None died because the technique did not work; JARDIS reached <2% runtime overhead. Izcal owns the engine and makes B1 the substrate its own CI runs on, which removes the organisational failure mode. JARDIS's design choices are directly relevant evidence: log at the host-API boundary (Izcal's equivalent is the WebIDL bindings and B1 interfaces), store seeds rather than values, and snapshot at empty-stack points (HTML event-loop task boundaries), which also answers the DevTools critique's "recording must start somewhere" finding.

## 5. Deterministic execution of JavaScript and Wasm (for B1)

### 5.1 Sources of non-determinism, by layer

| # | Source | What the specification allows | Source | Conf. |
|---|---|---|---|---|
| 5.1 | `Math.random` | "chosen randomly or pseudo randomly … using an implementation-defined algorithm", and each realm's `Math.random` "must produce a distinct sequence" — so a seeded design needs **per-realm seeds** derived from one root seed | [ECMA-262 (2027 draft) §21.3.2.28](https://tc39.es/ecma262/#sec-math.random) | High |
| 5.2 | `Date.now`, `performance.now` | Returns the time "of the occurrence of the call". HR-Time coarsens to ≥100 µs (≥5 µs when cross-origin isolated) and allows implementation-defined **jitter** | [ECMA-262 §21.4.3.1](https://tc39.es/ecma262/#sec-date.now); [HR-Time](https://w3c.github.io/hr-time/) | High |
| 5.3 | GC timing, `WeakRef`, `FinalizationRegistry` | Objects "may be released after long periods of time, or never at all"; "Implementations may omit FinalizationRegistry callbacks for any reason"; scheduling of `ClearKeptObjects` and cleanup is deferred to the host | [WeakRefs proposal text](https://tc39.es/proposal-weakrefs/); ECMA-262 §9.9 | High |
| 5.4 | Breadth of latitude | The current draft uses "implementation-defined" 55 times, "implementation-approximated" 46 times and "host-defined" 47 times (count by this note over the rendered text) | [ECMA-262](https://tc39.es/ecma262/) | High (count is the note's own) |
| 5.5 | Shared memory and `Atomics` | Sequential consistency is guaranteed only for data-race-free programs; racy programs may observe any of a set of values. Embeddings may deactivate agents "without the agent's knowledge" | ECMA-262 §29 (memory model), §9.7–9.8 | High |
| 5.6 | Property-key hashing | Engines seed string hashes against HashDoS. A heap snapshot that contains seeded hash tables fixes the seed unless the tables are rehashed on load: Node's startup snapshots froze the hash seed (CVE-2017-11499) | [Red Hat bug 1475327](https://bugzilla.redhat.com/show_bug.cgi?id=1475327) | Medium (re-sourced at 0.3.1) |
| 5.7 | JIT tiering and background compilation | V8's predictable mode must switch off concurrent recompilation, lazy compile dispatching, parallel compile tasks, background Maglev work and concurrent cache deserialization; Wasm tier-up becomes synchronous | same | High |
| 5.8 | GC heuristics | Predictable mode disables the **memory reducer** (timer-driven GC) and forces single-threaded GC; a separate `--predictable_gc_schedule` fixes semispace size and heap growth "and memory reducing behavior" | same | High |
| 5.9 | Wasm | The deterministic profile canonicalizes NaNs and fixes relaxed-SIMD results, but `memory.grow` and `table.grow` stay non-deterministic so they can report exhaustion | [Wasm spec, profiles appendix](https://webassembly.github.io/spec/core/appendix/profiles.html) | High |
| 5.10 | Izcal's measurement | With stock V8 the GC-observable channel (finalization order, WeakRef liveness) diverges on every OS; `--predictable --single-threaded` alone was "almost" stable with real outliers (2/200 on macOS debug); the forked predictable platform was bit-identical across macOS, Linux and Windows | [m0/determinism_crossplatform.md](../../m0/determinism_crossplatform.md) | High (Izcal's own) |

Other sources the host owns, recorded here for completeness: event-loop task-source selection ("implementation-defined manner", [IG 4.6]), network timing, worker scheduling, locale and time zone, `Intl` data versions, and Array sort stability (now specified; ECMA-262 notes it narrowed "the amount of cases that result in an implementation-defined sort order").

**Implications:** the engine is where most non-determinism is *created* (GC heuristics, background compilation, hash seeds, PRNG), not only where it is observed. Retrofits (V8 flags, CDP virtual time, Hermit) control one layer each and cost speed or coverage. Izcal can make determinism a **property of the engine's design**: every heuristic driven by an injected clock and seed; GC and tier-up decisions taken at deterministic points (allocation counts, safepoints, task boundaries) rather than on background-thread completion; background compilation allowed in production but with results **installed** only at deterministic points so tiering stays replayable; per-realm PRNG seeds derived from the B1 root; hash seeds from B1 entropy; finalization callbacks scheduled as ordinary host tasks under the seeded scheduler. Whether background work can run concurrently while installation stays deterministic, and what it costs against DET-2's ≤1%†, has not been measured anywhere and is a milestone question.

## 6. Live programming and hot code reload

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | V8's live edit (`Debugger.setScriptSource`) generally cannot edit a function that is on the stack; the exception is the top-most frame when it is the function's only activation (`allowTopFrameEditing`, experimental: "the function on top of the stack as long as the top-most stack frame is the only activation of that function"; failures are reported as `BlockedByActiveFunction` and similar). The same documentation now marks `setScriptSource` deprecated: "Live edit is no longer supported and this command always fails" | — | [CDP Debugger domain documentation](https://chromedevtools.github.io/devtools-protocol/tot/Debugger/#method-setScriptSource) | re-read 2026-10-19 | High |
| 6.2 | JavaScript hot reload therefore lives in bundlers: Vite HMR needs modules to opt in with `import.meta.hot.accept`, propagates to the nearest "HMR boundary", keeps state only in `import.meta.hot.data`, and falls back to a full reload | — | [Vite HMR API](https://vite.dev/guide/api-hmr) | read 2026-10-19 | High |
| 6.3 | The Dart VM does hot reload **in the engine**: it reloads libraries from new kernel files, keeps the heap, and the framework rebuilds. Documented limits: enum↔class changes, generic type declaration changes, and lazily initialized globals and statics, which are "treated as state" and not re-run; stateful reloads can differ from a fresh start | "Reloaded 1 of 448 libraries in 978ms" (example) | [Flutter hot reload](https://docs.flutter.dev/tools/hot-reload) | read 2026-10-19 | High |
| 6.4 | Erlang keeps two versions of a module (current and old); fully qualified calls switch to new code; when old code is purged, processes still in it are terminated | 2 versions | [Erlang code loading](https://www.erlang.org/doc/system/code_loading.html) | read 2026-10-19 | High |
| 6.5 | Elm cut showy time travel, kept import/export, and its compiler explains why an exported history no longer fits changed code | — | [VU 3.7](../Izcal%20DevTools%20spec/visualization_ux.md) | 2016 | High |

**Implications:** hot reload works when the runtime defines precisely what is "code" and what is "state" (Dart, Erlang). JavaScript engines never did, so the job fell to bundlers, which can only swap whole modules. An engine Izcal owns could offer **engine-level module and function replacement** with explicit rules: closures and object shapes migrate, top-level bindings are state, and a change that cannot be applied says why (as Elm does). Combined with B1, a developer could edit code and **re-run a recorded interaction against the new code**, which is a stronger form of live programming than any shipping tool offers. Semantics for module records, class fields and private names under replacement are open and need their own design.

**Implications:** per-site JIT control exists in three browsers, but always as a **process-wide** switch exposed late (enterprise policy first) and with Wasm collateral damage, because a JIT is a property of the process's memory permissions. Izcal's process per (site, container) makes per-site engine policy natural: tier ceilings (interpreter only, baseline only, full), Wasm tiers, and memory and CPU budgets can be **capabilities of the site's renderer** set by the browser process. With an engine designed for it, "JIT off" need not mean "Wasm off" (an interpreter or ahead-of-time Wasm tier). CPU caps today are frame-level and coarse (7.6); an engine that attributes execution to the script that runs it (Section 8) could cap or deprioritise a *script*, not only a frame.

| 10.2 | V8 startup snapshots capture only "V8's heap"; context creation fell from ~40 ms to <2 ms (desktop), ~270 ms to 10 ms (mobile). | 10.3 | Node's user-land snapshot API (stable in v24.0.0/v22.17.0) needs serialize/deserialize callbacks to release and reacquire resources; a deserialized app "cannot be snapshotted again" | — | [Node.js v8.startupSnapshot](https://nodejs.org/api/v8.html) | read 2026-10-19 | High |
| 10.4 | **Snapshots and seeds collide.** CVE-2017-11499: Node v4.0–v8.1.3 used a constant hash seed because building with V8 snapshots "caused the initially randomized seed to be overwritten on startup", enabling HashDoS. | 10.6 | xsnap (Agoric, on XS) snapshots a running JS worker and resumes it, "possibly on a different machine" | restarts up to 260× faster (23 min → 6 s) | [xsnap README](https://github.com/Agoric/agoric-sdk/blob/master/packages/xsnap/README.md); [Agoric stress test](https://dev.agoric.com/blog/newsletter/stress-test-completed) | 2021 | High (README) / Medium (speed-up) |
| 10.7 | Wizer pre-initializes a Wasm instance and saves the state as a new module; init cannot call imports; now part of Wasmtime | 1.35–6× faster startup; larger data segments | [Wizer](https://github.com/bytecodealliance/wizer) | read 2026-10-19 | High |
| 10.8 | bfcache keeps "a snapshot of the entire page in memory, including the JavaScript heap", but only in the same process and only for a while; ~1 in 10 desktop and 1 in 5 mobile navigations are back/forward. Ineligibility reasons include `unload`, `no-store`, open IndexedDB connections, in-flight fetches and open WebSocket/WebRTC | 10% / 20% | [bfcache (web.dev)](https://web.dev/articles/bfcache) | 2026-10-16 | High |
| 10.9 | JARDIS snapshots were serializations at empty-stack points with type layouts and PRNG seed (4.2) — a portable heap format inside a JS engine | — | [FSE 2016 PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/09/TTNode.pdf) | 2016 | High |

**Implications:** whole-heap snapshot and resume works in narrow forms (startup snapshots, bfcache in memory, xsnap, Wizer), and every form trips over the same thing: **state that must not be copied** (entropy, hash seeds, unique IDs, OS handles). Izcal's B1 already routes all entropy and time through injected interfaces, so it knows exactly which state is "external" and can re-seed it on resume, the problem that caused CVE-2017-11499 and SnapStart's rules. A serializable, versioned heap format at task boundaries would serve four uses at once: B1 checkpoints for replay, bfcache that survives process discard (tab restore with live state), fast renderer start for frequently visited sites, and agent snapshots (HGBA-3 Section 7). Constraints: a heap snapshot holds one site's data and must stay within that site's process and storage partition (I-1, P1); snapshots on disk are sensitive user data; cross-version portability needs an explicit format version. Per-site isolate cost matters because Izcal forbids sharing a process across sites: Cloudflare's 3 MB per isolate is the shared-process figure, not Izcal's.

## 13. Lessons learned

| Project | What happened | The lesson | How Izcal applies it |
|---|---|---|---|
| JARDIS / Node-ChakraCore TTD | Worked at <2% overhead; archived in 2020 when its engine was abandoned (4.2–4.3) | An engine feature lives or dies with the engine and its owner | Izcal owns the engine and makes replay a CI dependency, not an optional tool |
| V8 `--predictable` | Determinism by switching off concurrency and heuristics (5.11) | Retrofitted determinism costs performance and still leaks (5.10) | Design heuristics around injected time and seeds from the start; measure DET-2 |
| Node CVE-2017-11499; SnapStart | Snapshots silently copied seeds and RNG state (10.4–10.5) | Anything restored from a snapshot must re-derive its entropy | Classify all engine state as internal or external (B1); re-seed external state on every resume |
| Firefox JIT Optimizations view; Deopt Explorer | Expert views over unstable internals were hidden or built outside (1.2, 1.5) | Optimization data is useless without stable format and plain-language reasons | A versioned event schema and explanations tied to source |
| Edge SDSM; Chrome JIT policy | JIT-off lost Wasm and arrived as enterprise policy (7.1, 7.3) | Safety controls must not remove platform features as a side effect | Per-site tier ceilings, with a Wasm path that does not need a JIT |
| Taint-aware Chromium; Foxhound | Found thousands of real bugs; stayed in forks (9.1–9.3) | Cross-cutting instrumentation dies outside the main tree | Build taint as an opt-in engine mode in the main tree, from the generated bindings |
| Dart VM, Erlang | Hot reload works because the runtime defines code vs state (6.3–6.4) | Live programming needs runtime semantics, not bundler tricks | Specify replacement semantics in the engine; explain refusals |
| Cloudflare Workers | Freezing `Date.now` during execution served Spectre defence (5.12) | Controlled time is a security tool as well as a testing tool | Use B1's clock to keep timers coarse for content while DevTools sees exact values locally |
