# Izcal JavaScript engine: specifications, formal semantics and conformance oracles

Compiled 19 October 2026. Primary sources were preferred (specification sources on GitHub, TC39 meeting notes, the test262 and test262.fyi data repositories, papers, maintainers' READMEs). Where a number was computed by this researcher from a primary file (for example counting algorithm steps in `ecma262/spec.html`), the method is stated and the date is the date of the file.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

M-1 reading used throughout: specifications, conformance suites (test262, the Wasm spec tests, WPT) and standards data (Unicode, CLDR, IANA tz) are oracles and data. Spec-derived tools (ESMeta, SpecTec, the Wasm reference interpreter, engine262) are oracles and evidence; none of them is engine code, and none is a template. ICU, ICU4X, `temporal_rs` and similar libraries do engine work and are excluded.

**Implications:** ANC-1 can pin `tc39/ecma262` by commit and resolve anchors against the published biblio. Its coverage denominator is about 14.5k steps across about 800 typed operations. Because the spec is typed and checked in CI, Izcal can treat the algorithm headers (parameter and return types, abrupt-completion sets) as a contract that the engine's internal API must refine.

## 2. TC39 process and proposal status (as of October 2026)

The stages are 0, 1, 2, **2.7** (spec text approved, waiting for tests), 3 (implement and ship-ready) and 4 (finished, merged into `main`). The 2.7 stage was introduced in 2023–24. Stage 4 needs test262 tests merged and two shipping implementations ([process document](https://tc39.es/process-document/)).

**Implications:** the module-loading surface (import attributes, JSON and text modules, source phase, `import defer`, deferred re-exports) is the fastest-moving part of the language and is co-designed with HTML and Wasm. Decorators and ShadowRealm are not shipping targets for Izcal's first edition.

## 3. ECMA-402 (Intl) and ECMA-404 (JSON)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | ECMA-402's `main` draft is titled "ECMAScript 2027 Internationalization API Specification". It is split into per-chapter ecmarkup files and is released yearly alongside ECMA-262. | — | [ecma402 spec/index.html](https://github.com/tc39/ecma402/blob/main/spec/index.html) | 2026-10 | High |
| 3.2 | **ECMA-402 does not require CLDR.** Its text says "implementations are not required to use Unicode Common Locale Data Repository (CLDR) data", and that the set of supported locales is implementation-defined. It **does** require the IANA Time Zone Database (clause 6.5, "Use of the IANA Time Zone Database", with AvailableNamedTimeZoneIdentifiers and related operations), and it requires BCP 47 / UTS 35 locale identifiers. Output strings (date patterns, number formats) are not specified; test262's `intl402` tests check structure and invariants, not exact localized text. | 9 mentions of CLDR; 31 of the IANA tz database | [tc39.es/ecma402](https://tc39.es/ecma402/) | 2026-10 | High |
| 3.3 | **In practice the interoperable web needs CLDR data.** Every shipping engine derives its locale data from CLDR, through ICU4C (V8, SpiderMonkey, JSC) or ICU4X (Boa, and newer engines). Matching user-visible output (for example `toLocaleString`) across browsers therefore means using CLDR data and UTS 35 algorithms. Under M-1, Izcal uses **CLDR, UCD and the IANA tz database as standards data**, and writes its own formatting, collation (UTS 10/UCA), segmentation (UAX 29), normalization and calendar code. ICU4C, ICU4X and `temporal_rs` are excluded. | — | [CLDR](https://cldr.unicode.org/); [ICU4X](https://github.com/unicode-org/icu4x) | 2026-10 | Medium |
| 3.4 | **ECMA-404** (The JSON Data Interchange Syntax, 2nd edition, December 2017) is a grammar-only standard and agrees with [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259). ECMA-262's `JSON.parse` is normative for the engine and is stricter in places (for example duplicate keys: last one wins). Since ES2019, JSON text is a syntactic subset of ECMAScript (the "JSON superset" proposal). ES2026 added source-text access (`JSON.rawJSON`, reviver `context.source`), and "JSON.parse options" is at Stage 2.7. | — | [ECMA-404](https://ecma-international.org/publications-and-standards/standards/ecma-404/) | 2017-12 | Medium |

**Implications:** Intl is a second engine-sized project: collation, segmentation, plural rules, calendars, time zones and number and date formatting, all from UTS/UAX specifications and CLDR data. It should be its own crate family with its own data-build pipeline (CLDR → Izcal's compact format). Pass rates should be reported separately from the language, as test262.fyi does.

**Implications:** the history is decisive. Hand formalizations (JSCert, KJS) were excellent and then **froze at ES5** because they could not follow a yearly language. Izcal's engine should therefore be **checked against a spec-extracted model**, not a hand-maintained one: ESMeta's interpreter as an executable oracle, its coverage to measure Izcal's tests, and its typed operation signatures to check Izcal's internal API.

The `.wast` format scripts module definitions, invocations and `assert_return` / `assert_trap` / `assert_invalid` / `assert_malformed` checks, so a new engine needs a `.wast` runner. | 258 core `.wast` files | [WebAssembly/spec](https://github.com/WebAssembly/spec) (tree) | 2026-10-13 | High |

**Implications:** a 2026 web engine has to target Wasm 3.0 plus Threads, JSPI, JS String Builtins and the CSP integration from the first edition. JSPI and Stack Switching need the engine to suspend and resume Wasm stacks, which constrains the stack design of both the JS and Wasm tiers (one stack model, or segmentable stacks). The Wasm 3.0 deterministic profile is a ready-made spec for DET-1 on the Wasm side.

Because HTML allows several window event loops on one thread and requires dedicated threads only for `[[CanBlock]]` agents, the scheduler design (HGBA-3 B3) has spec-sanctioned freedom.

## 10. How far can an engine be generated from, or checked against, the spec?

| # | Finding | Evidence | Conf. |
|---|---|---|---|
| 10.1 | **Proven possible: a slow, complete reference interpreter extracted from the spec.** JISET/ESMeta (about 95% of steps compiled automatically, the rest hand-completed; passes applicable test262) and SpecTec (100% of the applicable Wasm 2.0 suite). | 5.4, 5.5, 7.3 | Medium–High |
| 10.2 | **Proven possible: checking the spec itself.** ESMeta's type checker runs in TC39 CI with 16 known exceptions. SpecTec checks rule consistency, and WasmCert proves soundness for the 2.0 subset. | 1.9, 7.5 | High |
| 10.3 | **Proven possible: spec-derived test generation and coverage.** JEST synthesized programs that covered 97.78% of syntax and 87.70% of semantics (ES11), and found 44 engine bugs and 27 spec bugs. Feature-sensitive coverage (PLDI 2023) refined this. | 4.8 | Medium |
| 10.4 | **Not shown by anyone: generating a production-speed engine.** Spec algorithms specify observable results through spec-only data structures (Lists, Records, property descriptors, environment records). A production engine replaces them with shapes and hidden classes, inline caches, bytecode, register allocation, NaN-boxing, rope strings and compiled tiers. No published work derives those from the spec. The gap is not the algorithms' meaning but **representation and optimization**, which belong to Izcal's first-principles design (M-1 part 3). | absence of evidence in the ESMeta, SpecTec and KJS literature reviewed | Medium |
| 10.5 | **Not shown: proof that an optimizing JIT refines the spec.** The verified Wasm interpreters (WasmRef-Coq, Isabelle) are interpreters. Verified compilation of JS or Wasm to native code in a browser engine is not available at 3.0 scale. Partial routes: translation validation per compiled function against the reference semantics, differential fuzzing against the spec interpreter, and verified validators. | 7.5 | Medium |
| 10.6 | **What is left for hand design, anchored but not generated:** the object representation, the GC (the spec is silent except for WeakRef and FinalizationRegistry liveness and the `[[KeptAlive]]` list), the bytecode and tiers, the parser's error recovery and speed (the spec grammar with cover grammars and early errors is a specification, not an efficient parser), RegExp compilation (the spec gives a backtracking matcher semantics), Intl data handling, scheduling, and the embedding API. | 1.5, 3.2, 8.2 | High |

**Implications:** the realistic, high-value position is **spec-extracted oracles plus a hand-designed engine with anchors**. Izcal can (a) run an ESMeta-extracted reference model and the SpecTec interpreter as differential oracles in CI and in DST; (b) use their spec-coverage maps to measure, for ANC-1, which algorithm steps Izcal's tests exercise, and not only which steps have comments; (c) check that Izcal's internal operation signatures refine the typed spec headers; and (d) aim for verified Wasm validation. Generating the production engine itself is unproven and would conflict with the performance requirements, so it should not be a goal; generating **test oracles** should be.
