# Izcal JavaScript engine: execution techniques and performance evidence

Compiled 2026-10-19. Primary sources were preferred (papers, engine team blogs, benchmark announcement pages, maintainers' posts, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only, or recalled and not re-read this session.

**Method note.** This strand follows phase 2 and 3 of `.claude/skills/first-principles-spec/SKILL.md` for the frame in `frame.md`. It records ideas and measured evidence only (M-1): no code and no template is taken from any engine. The most design-relevant questions were researched first: where real pages spend engine time, what the benchmarks reward, tiering numbers, IR choice, and new ways to build interpreters and baseline JITs. The web-search budget is shared, so many items come from known primary pages fetched directly. Every number carries the **hardware era** it was measured on where the source states it; many engine blogs do not state hardware, and that is noted. Engine blog figures are vendor measurements on vendor benchmarks; treat them as evidence of direction and size, not as independent results.

**Implications:** Izcal must design for the long tail: most shipped code is cold, functions are short, and work is event-driven. Fast lazy parsing, a compact and fast first tier, and cheap feedback collection matter more on real pages than peak optimized-code speed. Izcal should build its own **engine-wide time accounting** (the RCS idea, designed fresh and exposed to DevTools), because the field has no public, current breakdown and Izcal will need one to steer every later decision.

## 3. Value representation

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | Three families: **pointer tagging with small integers** (V8: low-bit tag, 31-bit Smi, doubles boxed on heap), **NaN-boxing, pointer-favoring** (JSC: pointers have leading zeros, doubles offset), **"nun/pun-boxing", double-favoring** (SpiderMonkey: doubles stored raw, pointers inside NaN space). Trade-offs: NaN-boxing avoids heap doubles (less GC/cache pressure) but depends on 48-bit address layouts and is costly on 32-bit targets; high-bit tags hurt conservative GC. | — | [Wingo: Value representation in JavaScript implementations](https://wingolog.org/archives/2011/05/18/value-representation-in-javascript-implementations) | 2011-05-18 | Medium (secondary for JSC/SM internals) |
| 3.2 | **Pointer compression** (32-bit tagged values in a 4 GB cage): V8 heap **−43%**, Chrome renderer memory **−20%** on desktop browsing tests; less GC time. Costs: Smis drop to 31 bits (~−1% Octane), double field unboxing removed (~−3%); an initial ~35% Octane gap was tuned close to parity. Hard 4 GB heap limit. | Windows 10 desktop; x64 Octane; low-end Arm64 tested (branchless vs branchful decompression no difference) | [V8: Pointer compression in V8](https://v8.dev/blog/pointer-compression) | 2020-03-30 | High |
| 3.3 | **Static roots**: with a fixed read-only heap at the start of every cage, core objects have compile-time-known compressed addresses (`undefined` = 0x61), and type checks become **address range checks** on maps (e.g. "is string" = map address in 0xdd–0x49d). | ~+1% Speedometer 2 on Apple M1 | [V8: Static roots](https://v8.dev/blog/static-roots) | 2024-02-05 | High |
| 3.4 | The **V8 sandbox** replaces raw pointers with 40-bit offsets in a 1 TB region and external pointers with table indices; cost **~1%** on Speedometer and JetStream. | Hardware not stated | [V8: The V8 Sandbox](https://v8.dev/blog/sandbox) | 2024-04-04 | High |

**Implications:** Compressed, cage-relative references are a measured win for memory (P5 hardware) and double as a security boundary (offsets cannot name memory outside the cage). Izcal should decide value representation, compression, sandbox addressing and read-only root layout **together**, from the start, rather than retrofit them as V8 did over 2020–2024.

**Implications:** An IC system described as **data (an IR of guards)** rather than hand-written stubs is the measured route to sharing one source of truth across interpreter, baseline and optimizing tiers, and it is also the natural thing to expose to DevTools ("why is this access megamorphic?"). ## 5. Interpreter design

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **Register vs stack bytecode**: a register VM executed ~46–47% fewer VM instructions with ~25–26% larger bytecode; ~32% less time with switch dispatch, ~26.5% with threaded dispatch (Pentium 4); AMD64 speedup 1.48 (switch), 1.15 (inline-threaded). | Pentium 4 / AMD64 era (2005–2008), JVM bytecode | [Shi, Gregg, Beatty, Ertl: VM Showdown, VEE 2005](https://usenix.org/legacy/events/vee05/full_papers/p153-yunhe.pdf); TACO 2008 | 2005, 2008 | Medium |
| 5.2 | V8 **Ignition** is a register machine with an implicit **accumulator**, introduced to cut memory: bytecode is 25–50% the size of the old baseline machine code; ~5% less memory per tab on ≤512 MB Android. | Chrome 53 | [V8: Firing up the Ignition interpreter](https://v8.dev/blog/ignition-interpreter) | 2016-08-23 | High |
| 5.3 | **Tail-call ("musttail") interpreters** keep hot state in registers because each handler is a small function; big switch loops defeat register allocation. Protobuf parsing reached >2 GB/s, "more than double" prior state of the art (tail calls one of several techniques). | Clang `musttail` | [Haberman: Parsing protobuf at 2+GB/s](https://blog.reverberate.org/2021/04/21/musttail-efficient-interpreters.html) | 2021-04-21 | High |
| 5.4 | **Benchmark trap**: CPython 3.14's tail-call interpreter was announced as 10–15% faster, but most of the gain came from an LLVM 19 regression that had collapsed computed-goto dispatch (332 → 3 indirect jumps). Against clang-18 the real gain was ~1–5%. | i5-13500 (Raptor Lake), Apple M1; clang 18/19, LTO+PGO | [Elhage: Performance of the Python 3.14 tail-call interpreter](https://blog.nelhage.com/post/cpython-tail-call/) | 2025-03-09 | High |
| 5.5 | **Rust `become` (explicit tail calls)** is still unstable: feature-gated since 2023, RFC 3407 not accepted, LLVM support uneven (win64 issue), by-move argument semantics open; no stabilization date. Third-party reports (2026-07) show ~8% wall-time gains with `become` + `preserve_none`, and Wasmi tail-call dispatch beating loop dispatch. | — | [rust-lang/rust#112788](https://github.com/rust-lang/rust/issues/112788) | 2023-06-19 → 2026-07 | High (status) / Low (benchmarks) |
| 5.6 | V8's regexp interpreter moved to **threaded dispatch** and a peephole pass: up to 2×, ~1.45× average over the old interpreter. | V8 v7.8 | [V8: Improving V8 regular expressions](https://v8.dev/blog/regexp-tier-up) | 2019-10-04 | High |

**Implications:** Izcal's interpreter is written in Rust, which today cannot *guarantee* tail calls on stable. The choice is: (a) depend on nightly `become` (blocked on stabilization, a P3 robustness risk), (b) a match-loop interpreter and accept register-allocation losses, or (c) **generate the interpreter** (Section 6) so dispatch is not left to the Rust compiler. Every interpreter speed claim must be checked against compiler-version effects (5.4).

## 6. Building execution tiers from one semantic description

| # | Finding | Numbers | Source | Date | Conf. |

**Implications:** The strongest new idea in this strand is **one formal description of each operation's semantics from which the interpreter, the baseline JIT and the IC fast paths are all generated** (Deegen's measured results beat a hand-written assembly interpreter). It fits Izcal's M-1 spec anchoring (the description can be traced to ECMA-262 steps), its DST needs (one source of truth for every tier) and a small team. Truffle-style partial evaluation reaches near-V8 peak but at a warm-up cost that real pages (Section 1) punish; tracing is ruled out by evidence.

## 8. Optimizing-compiler IR

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | **V8 left sea of nodes** for a CFG IR (Turboshaft). Reasons: effect/control chains caused subtle bugs; in JS most nodes have effects, so "only pure nodes actually float"; nodes change only once per ~20 visits; graph scattering costs cache misses; SoN destroys the schedule of already-scheduled Wasm. Results: **compile time halved**; SoN had ~3× (up to 7×) more L1d misses; CFG load elimination up to **190× faster**. By 2025 the whole JS backend and the whole Wasm pipeline used Turboshaft; the JS frontend is moving to Maglev's CFG IR; builtins still migrating. | Hardware not stated | [V8: Land ahoy: leaving the Sea of Nodes](https://v8.dev/blog/leaving-the-sea-of-nodes) | 2025-03-25 | High |
| 8.2 | **Cranelift's acyclic e-graph ("aegraph")**: effectful ops stay in a CFG skeleton; pure ops are hash-consed with union nodes; rewrites (written in **ISLE**) fire eagerly at node creation; elaboration re-schedules pure nodes (GVN, LICM, DCE, rematerialization fall out). Full equality saturation rejected: extraction with sharing is NP-hard and an egg round-trip alone added 23% compile time. Result: ~2% better code that repeated classical passes could not reach, at **+7–8% compile time**; multi-representation adds ~0.1% speed for ~0.005% compile cost. | Sightglass suite | [Fallin: The acyclic e-graph](https://cfallin.org/blog/2026/04/09/aegraph/) | 2026-04-09 | High |
| 8.3 | **JSC B3/Air** and **MLIR** were not re-read this session; no measured comparison for a JS engine found. | — | — | — | — |

**Implications:** Evidence points to **CFG + SSA with pure-node freedom only where it pays** (aegraph-style) rather than a full sea of nodes. Rewrite rules as a DSL (ISLE) are also the natural place for Izcal to attach machine-checkable correctness arguments for JIT optimizations (security P1).

## 9. Speculation, deoptimization, OSR

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 9.1 | Pizlo's model: an **OSR exit costs ~2,499 ns (DFG) / ~9,998 ns (FTL)**, while the benefit of a speculation is ≤~1.48 ns per bytecode, so a DFG speculation pays only if it holds with p > 0.9994: "speculation is a bet with tiny benefit and enormous cost." JSC recompiles after 100×2^R exits. Value profiles feed an intentionally unsound abstract interpreter (40-bit SpeculatedType sets). | — | [Pizlo: Speculation in JavaScriptCore](https://webkit.org/blog/10308/speculation-in-javascriptcore/) | 2020-07-29 | High |
| 9.2 | V8 Wasm does **no OSR**: a running Liftoff frame stays on Liftoff code; later calls get Turbofan code. | — | [V8 docs: Wasm compilation pipeline](https://v8.dev/docs/wasm-compilation-pipeline) | current | High |
| 9.3 | JIT bugs are a large share of engine exploits: ~45% of V8 CVEs after 2019 were JIT-related; "roughly half" of exploited V8 bugs were in compilers. | — | [Edge: Super Duper Secure Mode](https://microsoftedge.github.io/edgevr/posts/Super-Duper-Secure-Mode/); [V8 Sandbox](https://v8.dev/blog/sandbox) | 2021-08-04; 2024-04-04 | High |

**Implications:** Speculation must be governed by measured exit cost and confidence, with deopt as a first-class, recorded event (for DST replay and DevTools). Every optimization pass that removes a check is also a security surface (9.3), which argues for a small, verified set of check-removal rules.

## Cross-cutting lessons on hardware eras

- Most decisive numbers come from **2016–2026 x86 desktops and Apple M1–M5 laptops**; mobile evidence is mostly from Moto G4/Pixel-class phones (2019) and Pixel Tablet/Snapdragon (2024–2026).
- Hardware changes reversed decisions: embedded builtins (2018) were partly undone for M1's branch predictor (2021); pointer compression traded ~4% Octane for 20–43% memory when memory, not ALU, became the constraint.
- Compiler-version effects can fake interpreter wins (CPython 3.14 tail-call, 5.4); Izcal's benchmarking must pin toolchains and report them.

## Gaps and flagged claims

- No public, current cross-site breakdown of engine time by component (1.6); no IC-state distribution for the web (4.4); no per-tier energy study (14.4). Izcal must measure these itself.
- Not re-read this session (graded Low/Medium): Ryu's speed claims, SpiderMonkey Latin-1 savings, JSC B3/Air, MLIR in engines, SpiderMonkey Stencil off-thread parsing, GraalJS warm-up numbers, Winch compile speed, Static Hermes performance numbers.
- Vendor-only claims: Speedometer–INP correlation −0.8 (2.4), Chrome's Speedometer percentages, Safari's subtest gains.
- Third-party Rust `become` benchmarks (5.5) are unverified comments on the tracking issue.
