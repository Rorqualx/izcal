# Izcal DevTools spec: history and postmortems of web developer tools

Compiled 2026-10-17. Primary sources were preferred (maintainers' posts, release notes, Mozilla/Chromium/WebKit/Microsoft documentation, issue trackers, specifications).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Method note.** This strand follows phase 2 of `.claude/skills/first-principles-spec/SKILL.md`. The session's web-search budget ran out partway through. After that, only known primary URLs were fetched directly. As a result, a few items (IE Developer Toolbar's 2005 launch post, Opera's own Dragonfly end-of-life statement, the Firefox OS shutdown, Edge's 2020 move to Chromium DevTools, Vue DevTools v7's stated rationale) rest on secondary sources or were left out. They are listed under **Gaps** at the end.

## 1. Origins: debuggers and inspectors before Firebug (1997–2005)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Browser debugging started as **separate debugger products** bolted onto the browser. Netscape shipped a JavaScript Debugger for Communicator, and Microsoft shipped a Script Debugger for IE 4. | Netscape debugger 1997-12; MS Script Debugger 1998-02 | [Karl Dubost, "Browser developer tools timeline"](https://www.otsukare.info/2020/08/06/browser-devtools-timeline) (cites mozilla.org and archived MSDN pages) | 2020-08-06 | Low |
| 1.2 | **Venkman** (Mozilla's JavaScript debugger, by Robert Ginda, started April 2001) was built on **js/jsd**, a mid-level debugging API that John Bandhauer wrote in 1998 for the Netscape 4.x debugger, exposed as an XPCOM component. It shipped in the Mozilla install from 3 October 2001. | jsd 1998; Venkman 2001-04 / 2001-10-03 | [Mozilla archive: Venkman project page](https://www-archive.mozilla.org/projects/venkman/) (snippet) | 2001– | Medium |
| 1.3 | Venkman **died when the engine API it depended on was removed**, not because anyone decided to retire it: "as of Firefox 33, Venkman no longer works, as the APIs which it needs have been removed." Its last release was 0.9.89 (20 March 2012). | Firefox 33 (2014) | [addons.thunderbird.net: JavaScript Debugger listing](https://services.addons.thunderbird.net/It/seamonkey/addon/javascript-debugger) (snippet) | 2014 | Medium |
| 1.4 | **DOM Inspector** was written by Joe Hewitt and bundled with the Mozilla Suite and early Firefox. From November 2003 it was an optional "Custom" install component on Windows, and it was later split out into an add-on. The tree-of-nodes view it introduced became the template for every later Elements panel. | ~2001; optional from 2003-11 | [Wikipedia: DOM Inspector](https://en.wikipedia.org/wiki/DOM_Inspector); [PortableApps forum quoting MozillaZine](https://portableapps.com/node/2354) | 2006 | Low |
| 1.5 | The first **network debuggers were proxies outside the browser**: Fiddler (Eric Lawrence, first release 6 October 2003, for IE). The browser exposed nothing, so the network was observed from outside it. | 2003-10-06 | [Dubost timeline](https://www.otsukare.info/2020/08/06/browser-devtools-timeline) (cites Telerik release history); [zh.wikipedia mirror: Fiddler](https://zhwiki.oracleblog.org/wiki/Fiddler) | 2003 | Low |
| 1.6 | The **IE Developer Toolbar** was announced at PDC in September 2005 as a separate add-on for IE6 and IE7. Microsoft built it because of heavy demand for toolbar features like those in Firefox. It was "not compatible with Internet Explorer 8," which built the tools in instead. | 2005-09 | [Dubost timeline](https://www.otsukare.info/2020/08/06/browser-devtools-timeline) (cites archived IEBlog post); [sympmarc: IE8 and the IE Developer Toolbar](https://sympmarc.com/?p=10152) | 2005–2009 | Low |

**Implications:** The first tools were add-ons on private engine APIs (jsd, XPCOM), and they died when those APIs changed. A tool is only as durable as the interface it is built on, so Izcal's tools must consume a published, versioned engine interface, never engine internals.

## 2. Firebug (2006–2017): why it dominated and why it ended

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Firebug was Joe Hewitt's Firefox extension. Firebug 0.2 (January 2006) was a single-tab console with AJAX logging. 0.4 (May 2006) added a JavaScript debugger tab. It was open-sourced in December 2006, and 1.0 shipped in January 2007. | 2006-01 → 2007-01 | [Odvarko, "Saying Goodbye to Firebug," Mozilla Hacks](https://hacks.mozilla.org/2017/10/saying-goodbye-to-firebug/) | 2017-10-24 | High |
| 2.2 | **Why it dominated:** it was "the first tool to let programmers inspect, edit, and debug code right in the Firefox browser," on any live page, and it put HTML, CSS, JS and network in one place at the moment AJAX apps appeared. Mozilla credits it with having "ushered in the Web 2.0 era." John J. Barton: "Now every browser has a debugger inspired by our work." | — | [Saying Goodbye to Firebug](https://hacks.mozilla.org/2017/10/saying-goodbye-to-firebug/) | 2017-10-24 | High |
| 2.3 | Firebug became a **platform**. Its extension ecosystem grew from about 10 extensions in 2008 to more than 60 in 2011 (YSlow, FireQuery, Pixel Perfect, FirePHP and others). Yahoo!'s YSlow (July 2007) was first built as a Firebug extension. | ~10 (2008) → 60+ (2011) | [Saying Goodbye to Firebug](https://hacks.mozilla.org/2017/10/saying-goodbye-to-firebug/); [Dubost timeline](https://www.otsukare.info/2020/08/06/browser-devtools-timeline) for YSlow | 2007–2011 | High (counts) / Low (YSlow) |
| 2.4 | Firebug's lasting contributions were **formats and ideas, not code**. The **HAR** (HTTP Archive) format came out of the Net panel's export feature in October 2009, with Steve Souders and Simon Perkins (HttpWatch). The team also invented "dynamic and graphical web page breakpoints" (April 2010), which survive as Break on XHR and Break on DOM mutation. | HAR 2009-10; breakpoints 2010-04 | [Saying Goodbye to Firebug](https://hacks.mozilla.org/2017/10/saying-goodbye-to-firebug/) | 2017-10-24 | High |
| 2.5 | **Root cause of the end: multiprocess Firefox (e10s).** In e10s, "the add-on's code will run in a different process (browser chrome process) from web page content." "Direct access is no longer possible," and "many of the existing synchronous APIs will turn into asynchronous APIs." Firebug 2 assumed synchronous, same-process access to the page. | — | [Odvarko, "Firebug 3 & Multiprocess Firefox (e10s)," Mozilla Hacks](https://hacks.mozilla.org/2014/12/firebug-3-multiprocess-firefox-e10s/) | 2014-12-03 | High |
| 2.6 | The answer was **Firebug 3 ("Firebug.next")**, "built on top of Firefox native developer tools," using the message manager and the remote debugging protocol for cross-process work. By 2015 it was "a thin layer built on top of DevTools," mainly a Firebug theme, with its features to be ported into DevTools. | — | [Firebug 3 & e10s](https://hacks.mozilla.org/2014/12/firebug-3-multiprocess-firefox-e10s/); [Odvarko, "Firebug & DevTools Integration"](https://hacks.mozilla.org/2015/10/firebug-devtools-integration/) | 2014-12, 2015-10-28 | High |
| 2.7 | **Stated reasons for discontinuing:** "Firebug wasn't designed with multiprocess in mind"; "The Firebug Working Group agreed they didn't have enough resources to implement such a massive architectural change"; and the built-in tools had improved, so "it made sense to base the next version of Firebug on these tools instead." | — | [Penadés, Odvarko, Brosset, "Firebug lives on in Firefox DevTools"](https://hacks.mozilla.org/2016/12/firebug-lives-on-in-firefox-devtools/) | 2016-12-20 | High |
| 2.8 | **Small volunteer team.** The Firebug project had been in maintenance mode since Firebug 2.0 (June 2014), and unification work officially began in 2016. The last release was Firebug 2.0.18 (7 October 2016). | 2.0.18, 2016-10-07 | Odvarko's account via [ghacks](https://www.ghacks.net/?p=127321) (snippet) | 2016 | Medium |
| 2.9 | **What the merge kept:** the DOM panel, the Firebug theme, server-side log messages, the HTTP inspector (XHR Spy), FireQuery, HAR export and PixelPerfect, plus more than 40 bug fixes to close the gaps. | 40+ bugs | [Firebug lives on](https://hacks.mozilla.org/2016/12/firebug-lives-on-in-firefox-devtools/) | 2016-12-20 | High |
| 2.10 | **What the merge lost (at the time):** Break on XHR, Break on DOM mutations, an events side panel, better CSS and console autocompletion, live preview of inspector edits, validating CSS as you type, a DOM-properties side panel, and adding cookies (tracked in bug 991806). It also lost the **third-party extension ecosystem**: Firebug extensions did not carry over to DevTools. | 11 listed gaps | [Firebug lives on](https://hacks.mozilla.org/2016/12/firebug-lives-on-in-firefox-devtools/) | 2016-12-20 | High |
| 2.11 | **Fate:** end of life with Firefox Quantum (57) in November 2017, when "more than a million loyal fans still use it today." Mozilla claimed that "all the capabilities of Firebug are now present in current Firefox Developer Tools." | >1,000,000 users at end of life | [Saying Goodbye to Firebug](https://hacks.mozilla.org/2017/10/saying-goodbye-to-firebug/) | 2017-10-24 | High |

**Implications:** Firebug did not lose to a better tool. It lost because a process-model change broke its core assumption (synchronous, same-process access to the page), and a small team could not afford the rewrite. Izcal is multiprocess from day one, with site isolation and typed IPC (B2). Its tools must treat every page as remote and every query as asynchronous, even when they run inside the browser.

## 4. Opera Dragonfly (2008–2013) and the first cross-browser protocol

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | Dragonfly was Opera's integrated debugger for Opera 9.5 and later, written as a web app and BSD-licensed "from its inception in 2008." It moved to Bitbucket as a fully open project on 10 February 2010. | 2008; 2010-02-10 | [The Register, "Opera open sources Dragonfly"](https://www.theregister.com/2010/02/19/opera_dragonfly_open_source/) | 2010-02-19 | High |
| 4.2 | It was **designed for remote debugging from the start**. Through the **Scope** protocol (STP/0, later STP/1, "faster and more efficient"), Dragonfly could debug Presto 2.1+ on non-PC devices: "You can use your desktop keyboard and display, for instance, to debug a site running on Opera Mobile 9.5." That was years before Chrome or Safari offered remote debugging. | STP/1 by 2010 | [The Register](https://www.theregister.com/2010/02/19/opera_dragonfly_open_source/) | 2010-02-19 | High |
| 4.3 | Opera published the Scope specification (July 2009) and proposed it as a shared protocol for all browser tools. **Browser makers did not agree to converge.** | 2009-07 | [Dubost timeline](https://www.otsukare.info/2020/08/06/browser-devtools-timeline) (cites Opera Dev blog and scope-interface spec); the original [Opera Dev blog post](https://dev.opera.com/blog/opera-scope-protocol-specification-released/) now redirects | 2009 | Low |
| 4.4 | **Fate:** in February 2013 Opera announced it would drop its Presto engine for WebKit/Chromium (with a "300 million users" announcement). CTO Håkon Wium Lie said WebKit supported the standards Opera cared about and gave the performance it needed. Opera also cited engineering time spent fixing sites for Android and iOS. Dragonfly was tied to Presto through Scope, so it ended with the engine. Opera 15+ shipped Chromium's DevTools. | 2013-02 | [Computing, "Opera reaches 300 million users, drops Presto for WebKit"](https://www.computing.co.uk/news/2243645/opera-reaches-300-million-users-drops-presto-for-webkit); [AlternativeTo: Dragonfly discontinued](https://alternativeto.net/software/opera-dragonfly/about/) | 2013 | Medium (switch) / Low (Dragonfly end) |
| 4.5 | Users preferred Dragonfly to Chrome's inspector: Opera forum users said they kept using Opera 12 for development because of it. Quality did not save it, because its fate was tied to its engine. | qualitative | [Opera forums](https://forums.opera.com/post/27456) | 2013– | Low |

**Implications:** Dragonfly had remote debugging, an open protocol and a web UI years early, and it still died when its engine died. A tool bound to one engine's private protocol has that engine's lifespan. Izcal's tools should speak standard protocols (WebDriver BiDi, DAP, CDP for compatibility) as well as Izcal's own, so the tools are useful beyond Izcal.

**Implications:** IE's tools were shaped by an expensive debugger (refresh to start it, scoped to one process) and by legacy engine modes. Both constraints are gone for Izcal, whose deterministic substrate (B1) can make recording always-on and cheap. The source-versus-DOM gap of 5.4 is still open, and source maps (ECMA-426) and editor integration are the way to close it.

**Implications:** Chrome won through a protocol (CDP), a headless and automation ecosystem built on it, and a steady release cadence. It also shows the costs: the protocol mirrors one engine's internals and is not stable, and agent access shipped without a threat model. Izcal can offer a CDP subset for existing clients, but its canonical interface should be typed, versioned and capability-gated (B2, B9).

## 7. Firefox Developer Tools (2010s–today): removed features and why

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **3D View (Tilt)** was removed in Firefox 47 (bug 1245875, fixed 4 March 2016). | 7.3 | The **Shader Editor** was removed for lack of use, backed by telemetry. ## Lessons for Izcal

Ideas and evidence only. No code and no template is taken from any project (M-1).

- **Firebug → a process-model change (e10s) broke synchronous, same-process access to the page, and a volunteer team could not afford the rewrite (2.5–2.8).** Lesson: design every tool as a remote client of an asynchronous, typed interface from day one, even when it runs in the same window. Izcal's multiprocess and site-isolated design (B2) makes this mandatory.
- **Dragonfly, WebIDE and F12 → each was tied to one engine or platform and died with it, however good it was (4.4, 7.7, 5.5).** Lesson: speak standard protocols (WebDriver BiDi, DAP, source maps, HAR) as well as Izcal's own, and publish Izcal's inspection schema, so the tools and the ecosystem do not depend on Izcal's market share.
- **Scope, RemoteDebug, Valence and Firefox CDP → 13 years of attempts to share one engine's inspection protocol failed; only automation was standardised (8.3–8.6).** Lesson: offer CDP as a compatibility layer for existing clients (Puppeteer, the MCP server, VS Code) but never as Izcal's model. Design the canonical interface around Izcal's own data planes and spec anchors.
- **Tilt, Shader editor, Canvas debugger → removed because usage was tiny (1,800 opens against 4.5M), maintenance was costly and they bypassed the shared protocol (7.1–7.4).** Lesson: every view needs a named user task, an owner and opt-in usage measurement from launch. It must also run on the same interface as the core tools, so it costs nothing extra under process changes.
- **Performance Insights, Edge Layers → standalone "simple" panels lost; their best ideas survived inside the expert tool (6.10, 5.5).** Lesson: put plain-language explanations ("this layout shift happened because…") inside the main views through progressive disclosure, not in separate beginner panels.
- **HAR, SSLKEYLOGFILE, Firefox Profiler links → formats and shareable artifacts outlived the tools that made them (2.4, 10.13, 7.10).** Lesson: make every recording, trace and report an exportable, documented artifact (HAR, Perfetto/qlog, OpenTelemetry) that can be shared by link with redaction. Design the artifacts before the panels.
- **Venkman, Firebug extensions → tools and extensions built on private engine APIs disappeared when those APIs changed. Firebug's 60+ extensions did not survive the merge (1.3, 2.3, 2.10).** Lesson: if Izcal lets others extend the tools (framework devtools, Wireshark-style dissectors), the extension interface must be versioned and stable on purpose. Wireshark's dissector ecosystem (10.12) shows the payoff.
- **Redux DevTools and Replay → time travel worked when a framework constrained the program (Redux) or when a company forked browsers to record non-determinism (Replay, now stuck on Chromium 108) (9.3, 10.1, 10.3).** Lesson: Izcal's deterministic substrate (B1) can offer time travel natively for any page, with no fork. That is a real gap only Izcal can fill.
- **Replay → "a solution searching for a problem." Developers would not pay for root-cause analysis of flaky tests. The technology found a market as context for AI agents (10.2, 10.4).** Lesson: launch record and replay tied to concrete tasks (a bug report that reproduces, CI failure triage, agent debugging), and measure adoption by task, not by technical capability.
- **Chrome DevTools MCP → agent access shipped with no security section and an unpinned `@latest` install (6.12).** Lesson: agent access is a first-class client, but it must go through the agent principal, origin capabilities, consent and audit (B9). It is off by default (B10), and page content is treated as untrusted input to the agent.
- **Chrome AI assistance → it is opt-in, region- and age-gated, needs sign-in, and its training use depends on enterprise policy. It warns that it "may generate inaccurate" output (6.11).** Lesson: any AI in Izcal's tools must make clear what leaves the machine, run locally where possible, and ground its answers in engine data and spec anchors so claims can be checked.
- **IE8 debugger → debugging was expensive (refresh to start, one process only), and edits lived only in the DOM, cut off from the source files (5.2, 5.4).** Lesson: always-on, low-cost recording and a direct round trip between DOM edits and source files (source maps, editor integration over DAP or LSP) are still unsolved, and they are worth designing for.
- **Edge DevTools for VS Code → it works and is maintained, but it embeds a second copy of one engine's DevTools in a webview, while debugging uses a separate VS Code debugger. The webhint sibling died (11.1–11.3).** Lesson: integrate with editors through standard protocols so any editor gets Izcal support, and do not ship and maintain per-editor copies of the UI.
- **Polypane, Responsively, Sizzy → developers want many viewports at once, so third parties wrapped Chromium to provide it. Single-founder products are fragile (10.5–10.8).** Lesson: since Izcal renders its own UI (D-S2, D-S11), it can offer several synchronised viewports as a native workspace without a wrapper. The multi-viewport need is proven.
- **mitmproxy, Fiddler, Wireshark → network visibility below HTTP needs MITM certificates, ECH stripping or key-log files that "MUST NOT be used in production" (10.9–10.13).** Lesson: Izcal owns its network stack (rustls, neqo), so it can show TLS, QUIC, DNS and partitioning from the inside, with consent and per-origin scoping. It does not need to weaken the protocols to show them.

## Technology mismatches

Assumptions built into today's tools that no longer hold.

| Assumption | Where it is built in | Why it no longer holds | Evidence |
|---|---|---|---|
| **The tool can reach into the page synchronously** | Firebug 2, Tilt, early extensions, many panels that "evaluate in page" | Browsers are multiprocess and site-isolated. Each frame may be in another process, so every query is remote and asynchronous | 2.5, 7.1, 7.11 |
| **One page, one tab, one tool window, one viewport** | Every vendor's docked panel; single-viewport responsive mode | Developers test many viewports and many frames, origins and workers at once. Third parties built whole browsers to fix this | 10.5–10.8 |
| **The protocol is the engine's internals, serialized** | CDP (Blink domains), Scope (Presto), WebKit inspector protocol, Firefox RDP | Several engines need common tooling. Bridges between engine-shaped protocols failed, and BiDi standardised only automation | 8.3–8.6, 6.4 |
| **Only one client attaches at a time** | CDP before Chrome 63; IE8's per-process debugger | DevTools, IDE, test runner and AI agent now attach at once | 6.3, 5.2, 6.12 |
| **Inspection is live only; history is lost on reload** | All built-in panels; IE8 edits "lost on refresh" | Hard bugs (races, flaky tests, failures that do not reproduce) need recordings. Replay had to fork browsers to provide them | 5.4, 10.1–10.3 |
| **The developer is a human at a keyboard** | Panel UIs; AI added as a chat side panel | Coding agents are now primary users ("programming with a blindfold on"), and they need structured, permissioned access | 6.12, 10.4 |
| **Debugging is expensive, so it is switched on explicitly** | IE8 "Start Debugging"; profilers you start and stop | A deterministic runtime can record continuously and cheaply, then debug after the fact | 5.2; Izcal B1 |
| **The network is observed from outside the browser, or at the HTTP level** | Fiddler, Charles, mitmproxy, Wireshark; HAR (HTTP only) | HTTP/3/QUIC, ECH and partitioning hide the important data from outside observers. External tools now have to weaken privacy to see it | 10.11, 10.13 |
| **Framework semantics are invisible to the browser** | React, Vue and Redux devtools each building their own tree, bridge and replay | Most pages run on component frameworks, and every framework rebuilds the same tooling machinery | 9.1–9.4 |
| **Mobile and remote debugging is vendor-paired** (Safari ↔ Mac, Chrome ↔ Android) | Safari remote inspection; Chrome remote debugging | Developers use many devices and engines. weinre and Valence existed to cut these pairings and were abandoned | 3.5, 8.1, 8.2, 8.4 |
| **Tools are an integrated browser feature, not a product with an API** | Panels without exportable artifacts | The parts that lasted were exportable formats and separable projects (HAR, Lighthouse, Firefox Profiler) | 12.4 |
| **AI output can stand on its own** | AI chat panels with "may be inaccurate" disclaimers | Claims about engine behaviour can be grounded in engine data and spec anchors, and checked | 6.11; Izcal ANC-1 |
