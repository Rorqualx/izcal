# Izcal DevTools spec: agents and integrations

Compiled 17 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Scope.** This strand covers how developer tools connect to AI agents, editors, test runners, CI, observability systems and design tools: what each connection does, why it was built that way, what breaks, and its status in October 2026. It ends with lessons and a table of integration surfaces for Izcal's DevTools. It covers phases 2–3 of the first-principles-spec method; synthesis (phases 4–7) belongs to the spec author.

**Izcal constraints that apply** (read before using this note): HGBA-3 **P1** (an AI agent is a separate principal, not an extension of the user), **P6** and **B10** (AI off by default; "off" means no agent processes, no models, no AI traffic, no agent-only computation, no AI entry points in default UI, off survives updates), **B9** (agent principal with per-task read-only and read-write origin sets bounded by the container, provenance-filtered observations, trusted confirmation surface, tamper-proof action log, WebMCP-compatible tool registry), **B8** (semantic plane with stable IDs, provenance and diffs), **AG-0** to **AG-5**, Stage 1 **D-S11** (own `hg-devtools` frontend; backend implements CDP domains from the published protocol definition; remote-debugging port off by default), and **M-1**/**D-S10** (no code from another browser).

**Method note.** The session's web-search budget ran out partway through this strand. Later findings come from direct fetches of known primary URLs. Where only a search-result summary was available, the finding is graded **Low** or **Medium** and says so. Sentry's documentation could not be fetched (connection refused).

## 1. How we got here: debug protocols, fragmentation and the standards response

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Firebug**, the first widely used in-page web debugger, was retired as a separate add-on because "Firebug wasn't designed with multiprocess in mind". Firefox's multiprocess redesign (Electrolysis) would have needed a rewrite the Firebug Working Group could not resource. Its DOM panel, theme, XHR Spy, server-side logs and the FireQuery, **HAR export** and PixelPerfect add-ons were merged into Firefox DevTools. | 40+ bugs fixed to close the gap | [Mozilla Hacks](https://hacks.mozilla.org/2016/12/firebug-lives-on-in-firefox-devtools/) | 2016-12-20 | High |

| 1.5 | **WebDriver BiDi is still a W3C Working Draft** (8 October 2026), not a Recommendation. | 1.6 | **BiDi has an accessibility locator.** `browsingContext.locateNodes` accepts `browsingContext.AccessibilityLocator` with optional `role` and `name`, so a standard automation protocol can already find nodes by role and name. | 1.7 | **WebDriver (classic, "Level 2") is also a Working Draft** (2 July 2026). | 1.8 | **Agent frameworks went the other way, from Playwright down to raw CDP.** browser-use left Playwright because of a second network hop through a Node.js relay, hangs where the relay waited "indefinitely", poor cross-origin iframe handling, and problems with dialogs, downloads, tall screenshots and crashed tabs (about **1% of runs**, compounding over many steps). The costs they took on: about ten tab-crash paths to handle themselves, thin bindings, and Chromium-only support, because BiDi "is not yet feature complete". | ~1% of runs hit relay edge cases | [browser-use blog (Sweeting)](https://browser-use.com/posts/playwright-to-cdp) | 2025-08-20 | High |
| 1.9 | **Stagehand v3 (Browserbase) dropped its Playwright dependency for CDP**, because actionability checks and auto-waiting "add overhead" in automation, and because it needed CDP-level control of iframes and multiple tabs. It caches discovered actions, so the LLM is called only when a workflow breaks ("self-healing"). | "44.11% faster" on iframe/shadow-root interactions (vendor benchmark) | [Browserbase](https://browserbase.com/blog/stagehand-v3) | 2025-10-29 | Medium (vendor data) |

**Implications:** Engine-specific protocols fragmented because no protocol had a public specification. BiDi fixes that for automation, but agent builders still pick CDP for speed and depth. Izcal needs a CDP-compatible endpoint (already D-S11) *and* BiDi, both built from published definitions, and should expect agents to want lower-level, frame-aware access than test tools do.

**Implications:** By 2026, the agent's way into a browser is a debug protocol (CDP), an extension bridge or an embedded web view, each wrapped in MCP. Agents get accessibility snapshots with refs that go stale on every change, full snapshots after each action, and tool catalogs large enough to cost context. That is the gap the semantic plane (B8) and the agent principal (B9) are designed to fill.

## 9. Lessons for Izcal

| Project | What happened | The lesson | How Izcal applies it |
|---|---|---|---|
| Firebug (1.1) | Built on Firefox internals; could not survive the multiprocess redesign | A tool coupled to one engine architecture dies with it | DevTools speaks a typed protocol generated from Izcal's IPC schemas (B2), never engine internals; external surfaces are adapters over it |
| CDP in Firefox (1.2–1.4) | Partial reimplementation of an unspecified protocol, removed in Firefox 141 | Implementing another engine's private protocol is a permanent compatibility debt | CDP endpoint is a **compatibility adapter** for existing clients (D-S11), scoped to documented stable domains, never the source of truth |
| WebDriver BiDi (1.3–1.6, 6.1) | Standard, cross-engine, has accessibility locators; WPT's testdriver needs it | The standard protocol is where tests and, increasingly, automation live | Implement BiDi (and classic) as the primary automation surface; extend it upstream (for example semantic-plane queries) rather than inventing private commands |
| browser-use, Stagehand (1.8–1.9) | Left Playwright for raw CDP for speed, frames and tab control | Agents need low-level, frame-aware, low-latency access, and pay for it with crash handling | Izcal's agent surface offers frame-aware stable handles natively (B8 IDs carry frame provenance), so agents need not rebuild them |
| Chrome DevTools MCP (2.1–2.5) | 59 tools, ambient profile access, telemetry and CrUX lookups on by default, per-attach dialog added later | Disclaimers do not replace enforcement; defaults leak data | MCP server runs only under B9 with empty origin sets; **no telemetry, no external lookups**; per-task consent; slim tool set by default |
| Playwright MCP (2.6–2.7, 3.12) | Refs die on any change; origin allowlist not a boundary; DNS-rebinding CVE | Unstable IDs waste tokens; localhost servers are reachable from pages | Stable-ID snapshots plus diffs (AG-1); local transports are stdio or OS IPC with tokens; HTTP listeners validate `Origin` and `Host` |
| Claude Code, VS Code browser (2.8, 2.10) | Projects cannot enable browser access; agent pages ephemeral; explicit "share with agent" | Consent must come from the user, not from files in a repository; isolation by default | Agent access is enabled only by the user or by embedder configuration (B10); agent sessions get an isolated partition (B9); sharing a user tab is an explicit, revocable grant |
| Copilot coding agent (2.11), GitHub MCP (3.11) | Tools run with no approval; "Always Allow" enabled exfiltration | Blanket approval removes the last human check | No "always allow" across origins; write actions on read-write origins go through the trusted confirmation surface for sensitive classes (B9) |
| Comet, Fellou (3.1–3.2) | Page text treated as instructions; full-session privileges | Untrusted content and user intent must be separated structurally | Observations carry provenance; out-of-set origins never reach the model; agent actions logged; AG-3 tests this with model defenses off |
| Chrome agent architecture, CaMeL (3.5, 3.9) | Critic sees metadata only; origin sets; capability-checked data flow | Defense by architecture beats defense by model | Origin sets and capability checks live in the broker, verified (HGBA-3 Section 6), not in a prompt |
| MCP tool poisoning, mcp-remote (3.10, 3.13) | Tool descriptions and server metadata are injection and RCE channels | Treat every string from a server or page as untrusted, including tool metadata | WebMCP tool descriptions shown to agents carry origin provenance; DevTools displays the full description to the human; never shell-open URLs |
| Chrome 136 debug-port change (3.16) | Infostealers used remote debugging to steal cookies | A debug port on the real profile is a credential-exfiltration API | Remote debugging off by default (D-S11), and never on the user's main profile without an explicit, per-session, in-browser consent; prefer separate profiles |
| VS Code browser debugging (5.5) | Attach needs a debug port and separate profile; source maps fetched with page cookies | Editor attach forces users to weaken their setup | Izcal's editor attach uses a consented local IPC channel; source-map fetches are labelled and use the debuggee's partition only |
| DAP (5.1–5.2) | One adapter serves every editor; has reverse-execution requests | Standard adapters beat per-editor extensions | Ship a DAP adapter that exposes Izcal's replay (B1) as `stepBack` and `reverseContinue` |
| Edge DevTools for VS Code (5.7) | Embedded DevTools in the editor with CSS mirror editing; still maintained | Write-back to source is the valued feature, not embedding | Offer source write-back through source maps and DAP/LSP-style workspace mapping, not an embedded copy of the frontend |
| Vite HMR and Vite DevTools (5.9–5.10) | Dev servers built their own protocols and their own DevTools | Browser DevTools are blind to the build graph | Show HMR boundaries and module swaps from engine data (module records, mutation log), with an optional link to the dev server |
| HAR and Okta (7.3–7.5) | Unstandardized export; session tokens leaked via support uploads; redaction default added in 2024 | Exports are data flows; the default must be safe | Every export is redacted by default, shows what it contains, and needs a second explicit step to include secrets |
| OTel browser, Trace Context (7.1–7.2) | Browser OTel experimental; Trace Context stable | Integrate with the stable standard, not the moving SDK | DevTools reads and correlates `traceparent`; OTLP export is opt-in and local; the engine never injects tracing headers by default (P2) |
| devtools.* and chrome.debugger (7.11, 3.17) | The safe API is too narrow, so extensions take the broad debugger grant | A gap in the safe API pushes developers to the dangerous one | Offer a richer read-only extension API over the native protocol, so full debugger access is rarely needed |

## 10. Integration surfaces

Derived from first principles: every external surface is an **adapter over one native, typed Izcal inspection protocol** (`hg-devtools` backend, generated from B2 schemas). Each connection is a **principal** under the broker. The broker cannot tell a human-driven client from an agent-driven one on a CDP or BiDi socket, so the rule is that **any automation connection is treated as untrusted until the user consents in browser UI**. Only the MCP surface is an AI feature under B10. CDP, BiDi and DAP are not AI features, but they are the bypass route: Chrome DevTools MCP is CDP underneath. They therefore default to **separate, isolated profiles**, and reach the user's real profile only through an explicit per-session grant.
