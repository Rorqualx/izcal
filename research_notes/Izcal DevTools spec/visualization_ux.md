# Izcal DevTools spec: visualization and user experience, beyond the side panel

Compiled 17 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Scope: how developer tools are laid out and visualized, what attempts to break the docked-panel model achieved, and what that implies for Izcal's DevTools frontend (`hg-devtools`, an HTML application rendered by Izcal under Stage 1 D-S11). This strand covers phases 2–3 of the first-principles method. No code and no UI template is taken from any of these projects (M-1, D-S10). They are evidence only.

---

## 1. Origins of the docked-panel, tab-per-tool layout

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Firebug started from frustration with fragmented tools.** Hewitt called existing tools "awful" and said it "was always my plan to support all facets of web development" in one place. He designed for extensibility so others could add their own tabs and buttons, which planted the tabbed-plugin model. No primary statement was found of *why* he docked it at the bottom of the window. | — | [FOSDEM 2007 interview: Joe Hewitt](https://archive.fosdem.org/2007/interview/joe%2bhewitt.html) | 2007-02 | High (quotes); layout rationale not found |
| 1.2 | **Firebug grew one panel at a time.** 0.2 was a single console tab (January 2006), 0.4 added a JS debugger (May 2006) and 1.0 shipped in January 2007. Add-on panels grew from about 10 to over 60. Its end came when Firefox 57 dropped legacy extensions. | >1M users at end of life; 10 → 60+ extensions (2008 → 2011) | [Saying goodbye to Firebug (Mozilla Hacks)](https://hacks.mozilla.org/2017/10/saying-goodbye-to-firebug/) | 2017-10-24 | High |
| 1.3 | **Firebug died at a process-model change, not from lack of demand.** "Firebug wasn't designed with multiprocess in mind." Adapting it to e10s needed a rewrite the Firebug Working Group could not resource. Its features (DOM panel, theme, XHR spy, HAR export) and its developers moved into Firefox DevTools. | 40+ parity bugs fixed; 11 priority features | [Firebug lives on in Firefox DevTools](https://hacks.mozilla.org/2016/12/firebug-lives-on-in-firefox-devtools/) | 2016-12-20 | High |
| 1.4 | **Docking squeezed the layout as early as 2008.** WebKit's "Inspector UI refresh" had four stated goals: integrate the JS debugger (replacing the standalone Drosera), "utilize screen real estate better, especially when docked", separate DOM and source views, and remove redundant UI. | Landed 2008-04-14 | [WebKit bug 17773](https://bugs.webkit.org/show_bug.cgi?id=17773) | 2008-03/04 | High |
| 1.5 | **Safari's attempt to leave the tab row.** Safari 6's Xcode-style inspector "alienated some web developers familiar with the old Web Inspector". Safari 7 (WWDC 2013) used five regions running general to specific from left to right: toolbar, navigation sidebar, content browser, quick console and details sidebar. It could dock bottom or right, or be undocked. This is the clearest attempt to replace the tab row with linked columns, and it was revised after developers pushed back. | 5 regions | [State of Web Inspector (Hatcher, webkit.org)](https://webkit.org/blog/2518/state-of-web-inspector/) | 2013-06-11 | High |
| 1.6 | **Flexibility inside the docked model.** Chrome 87 let any tool move between the top panel and the bottom drawer "so you can view any two tools at once". Edge found moving the Console repeatedly "was cumbersome" and restored its dual placement in Edge 96. Edge's Focus Mode and vertical Activity Bar aimed to "reduce distractions and clutter", but the Activity Bar is no longer supported as of Edge 144. | — | [New in DevTools 87](https://developer.chrome.com/blog/new-in-devtools-87); [Edge DevTools 96](https://learn.microsoft.com/en-us/microsoft-edge/devtools/whats-new/2021/11/devtools) | 2020-10; 2021-11 | High |
| 1.7 | **DevTools are already web apps.** In Firefox (Browser Toolbox) and Chromium ("DevTools on DevTools") the tools are web applications you can inspect from a second, undocked window. No usage data was found. | — | [Browser Toolbox](https://firefox-source-docs.mozilla.org/devtools-user/browser_toolbox/); [DevTools on DevTools](https://chromium.googlesource.com/devtools/devtools-frontend/+/main/docs/cookbook/devtools_on_devtools.md) | current | High (existence) |

**Implications:** the docked pane came from one tool adding panels to an extension host, and screen space has been a struggle ever since. Nothing in the record says a docked pane is the right shape for the task. It was the cheapest shape for a browser add-on. Izcal's frontend is rendered by its own engine (D-S11), so it does not inherit that constraint.

| 2.9 | **Developers ask for layout debugging, not WYSIWYG.** In Mozilla's MaxDiff survey of 23 design challenges, CSS layout debugging ranked first "by far", then cross-browser compatibility. | 2.10 | **Chrome Recorder** records, replays and measures user flows (preview in Chrome 97). | 2.11 | **A 2017 prototype essay** criticised fixed panels ("can't show Performance and Sources side by side") and proposed an infinite canvas and time scrubbing. Nothing shipped from it. | — | [Prototyping the future of DevTools (Dzwinel)](https://www.freecodecamp.org/news/prototyping-the-future-of-devtools-f54ba4d51891/) | 2017-09 | Medium (opinion piece) |

**Implications:** visualizations died at architecture changes (Tilt, Firebug: e10s) or because they answered no specific question. They survived when they answered a precise one (z-index in 3D, a mirrored viewport per breakpoint). Every consolidation since 2019 has been driven by context switching between panels that answer one question. Izcal should build each visualization as a client of the same data protocol, and organize views by question, not by feature.

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Replay.io's retroactive logging.** You click a line and type an expression, and the Console shows its value at *every* time that line ran, "as if the log statement had always been there". Conditions filter the output, and each message jumps replay to that moment. A "focus window" limits logs, hit counts and events to a time range. | — | [Replay DevTools: time travel tools](https://docs.replay.io/reference/replay-devtools/time-travel-tools) | n.d. | 3.5 | **Replay pivot 3: the recording becomes AI context.** Nut.new, an AI app builder, records the app and sends the model an explanation built from console, network, dataflow and control-dependency analysis of the recording. | 3.6 | **Redux DevTools worked because the architecture forced replayable state.** Abramov turned stores into "stateless Stores… (now we call them reducers)" over immutable data, to "replay actions for hot reloading". The Redux style guide states the rules as time-travel requirements: mutation "will also break time-travel debugging"; reducers must have no side effects, randomness or `Date.now()`; state must be serializable. | — | [SurviveJS: Redux interview](https://survivejs.com/blog/redux-interview/); [Redux style guide](https://redux.js.org/style-guide/) | 2015-09-14; n.d. | High (React Europe 2015 talk not viewed) |
| 3.7 | **Elm cut its showy time-travel features in 0.18 and kept import/export.** The 2013 debugger "made for a great demo, but it was never quite right for large projects". The compiler explains *why* an exported history no longer fits changed code. | — | [The perfect bug report (Elm 0.18)](https://elm-lang.org/news/the-perfect-bug-report) | 2016-11-14 | High |
| 3.8 | **rr** records and replays unmodified Linux programs in user space, with reverse execution through gdb (watchpoint plus reverse-continue finds the last write). Fork-based checkpoints usually take under 10 ms. | Recording <2× slowdown on the paper's workloads except `make`; Firefox tests ≤1.2× (project site) | [Engineering record and replay for deployability (ATC '17)](https://arxiv.org/abs/1705.05937); [rr-project.org](https://rr-project.org/) | 2017-07 | High |
| 3.9 | **Pernosco: an omniscient database instead of stepping.** All program states are precomputed, so moving in time is instant. A **notebook** makes debugging state persistent where it is normally "invisible and transient". Sessions are shareable URLs, and multiprocess is first-class. | — | [Pernosco overview](https://pernos.co/about/overview/); [Explaining dataflow](https://pernos.co/about/dataflow/) | n.d. (read 2026-10) | High |
| 3.10 | **O'Callahan: omniscience beats reverse stepping.** Print-debugging fans are right that step debuggers, rr included, show "one point in time". The aim is that developers never step to build a mental model. Pernosco offers "interactive print debugging" plus backward dataflow, which print debugging cannot do. | — | [Print debugging should go away](https://robert.ocallahan.org/2021/04/print-debugging-should-go-away.html); [Your debugger sucks](https://robert.ocallahan.org/2019/11/your-debugger-sucks.html) | 2021-04-27; 2019-11 | High |
| 3.11 | **Why Pernosco's adoption is slow, in its founder's words.** "Only been modestly successful so far", though customers "love the product and keep subscribing". | 3.12 | **WinDbg Time Travel Debugging** records user-mode processes, shares traces and positions, and lets you query a trace with LINQ (all exceptions, module loads) and view timelines of calls and memory access. Microsoft lists "large overhead at record time" and large files as cons, and warns traces may hold personal or security data. | ~10–20× recording slowdown; traces of several GB within minutes; index ≈ 2× trace | [Time Travel Debugging overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/time-travel-debugging-overview) | updated 2025-11-05 | High |
| 3.13 | **Earlier omniscient debuggers.** Bil Lewis's Omniscient Debugger (Java) recorded every state change and paired it with event search; it reports only "small user studies". Undo UDB (C/C++) is commercial, with reverse watchpoints and portable recordings, and publishes no overhead figure. | — | [Debugging backwards in time (Lewis)](https://arxiv.org/abs/cs/0310016); [Undo UDB](https://undo.io/products/udb/) | 2003-10; current | Medium |
| 3.14 | **Timelapse/Dolos: web record and replay inside WebKit** at the platform API boundary, about 7.6K lines added to 1.38M. In a study of 14 developers it made **no significant difference** to speed or success. Developers just reproduced more. Methodical developers used replay to bisect; ad-hoc ones got distracted. UIST Best Paper honourable mention. | <1.1× interactive, ≤1.65× benchmark slowdown; reproduction 8–25% of task time; N=14 | [Burg et al., Interactive record/replay for web application debugging (UIST '13)](https://homes.cs.washington.edu/~mernst/pubs/record-replay-uist2013.pdf) | 2013-10 | High |

**Implications:** recording is solved engineering (rr, TTD, Timelapse). What decides whether anyone uses it is the UI on top. Replay alone did not speed anyone up (3.14). What people value is query-style omniscience (3.1, 3.9), sharing (3.2, 3.7) and "where did this come from" (3.9). Replay.io retreated because everyday bugs were already well served (3.4), and Pernosco because time travel was a separate, last-resort tool (3.11). So Izcal's substrate (B1) should feed the *default* tools, so that time travel is not a mode developers have to enter.

## 4. Causality and "why" explanations

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Whyline (Alice).** You ask "why did / why didn't" about the program's output. The design came from Natural Programming studies showing programmers phrase questions that way. | Debugging time cut by "nearly a factor of 8"; 40% more tasks completed | [Ko & Myers, Designing the Whyline (CHI '04)](https://hci.rwth-aachen.de/materials/conferences/CHI2004/1p151.pdf) | 2004-04 | High |
| 4.2 | **Whyline for Java.** You pick a question about output (a pixel, console text, an exception), and it answers with static and dynamic slicing. Developers' first guesses were wrong almost 90% of the time. Experts did *worse* without it, because they asked about their guess rather than the visible symptom. One task, small sample. | Median 4 min (1–12) with Whyline vs 10 min (3–38) without, p<.05, n=9 users; >2× faster than experts; tracing 1.7–15.3× slowdown | [Ko & Myers, Debugging reinvented (ICSE '08)](https://faculty.washington.edu/ajko/papers/Ko2008JavaWhyline.pdf) | 2008-05 | High |
| 4.3 | **Scry** lets you pick an element; at each change it saves DOM/CSS inputs and a screenshot, diffs any two states and names the JS lines responsible. It had case studies, no user study. Stated limit: what you see does not map one-to-one to the DOM, so changes outside the selected element go unexplained. | — | [Burg, Ko, Ernst, Explaining visual changes in web interfaces (UIST '15)](https://homes.cs.washington.edu/~mernst/pubs/dom-tracing-uist2015.pdf) | 2015-11 | High |
| 4.4 | **Unravel and Telescope** link a page's visible behaviour to the code behind it. Unravel (UIST '15, a DevTools extension that records DOM changes and JS calls) cut time to the first key source by 53% and time to understand how to recreate a feature by 32%. Telescope (UIST '16) found that in 6 of 7 popular sites, under 150 lines out of tens of thousands described the interaction. | 53% / 32% (N=13); <150 LOC | [Unravel project page](https://dtr.northwestern.edu/projects/rec0iUQDDzXcX4p4g); [Zhang CV](https://users.eecs.northwestern.edu/~hq/hq_cv.pdf) | 2015-11; 2016-10 | Medium |
| 4.5 | **Ply** hides CSS properties that have no visual effect, found by deleting each one and diffing screenshots ("visual relevance testing"). Novices finished milestones about 50% faster than with Chrome DevTools, and 3.5× faster on the first one (p=.01); the third was not significant (p=.06). Its screenshot method fails on JS animation and live content. | 16.7 vs 24.8 min; N=12 | [Lim, Hibschman, Zhang, O'Rourke, Ply (UIST '18)](https://par.nsf.gov/servlets/purl/10109034) | 2018-10 | High |
| 4.6 | **Inactive CSS (Firefox 70)** greys out valid CSS that has no effect (e.g. `flex` on a child of a non-flex container). A hover icon explains why, suggests a fix and links to MDN. It is deterministic and needs no account or network. Ply's research is reported as its origin (not confirmed in Mozilla's post; flagged). Chrome added an equivalent in Chrome 108. | — | [Firefox 70 (Mozilla Hacks)](https://hacks.mozilla.org/2019/10/firefox-70-a-bountiful-release-for-all/); [New in DevTools 108](https://developer.chrome.com/blog/new-in-devtools-108) | 2019-10-22; 2022-10 | High |
| 4.7 | **"Why did this render" tools are inferences.** The 2018 React Profiler let you infer a cause only by comparing props and state between commits. | 4.8 | **Chrome Performance "Insights" move explanations onto the timeline.** Lighthouse findings came into the trace because Lighthouse "lacks the timeline context". Selecting an insight highlights the related events and overlays explanations. Insights include LCP and INP by phase, forced reflow, and layout-shift culprits with the DOM elements and an animated screenshot of the worst CLS cluster. | LCP in 4 phases | [Insights sidebar](https://developer.chrome.com/blog/devtools-insights-sidebar); [Performance insights](https://developer.chrome.com/docs/performance/insights) | 2025-04-02 | High |

**Implications:** the strongest effects in this whole strand (Whyline ~8×, Ply ~50%, Unravel 53%) come from **asking from the visible output backwards**. Each of these research tools had to *reconstruct* causes by tracing, patching or screenshot diffing, with false positives and big slowdowns. Izcal's mutation log (B4) and from-scratch reference path (B5) can give exact answers instead. That is the clearest place where Izcal can do what no one else does.

## Lessons for Izcal

| Project | What happened | The lesson | How Izcal applies it |
|---|---|---|---|
| Firebug, Tilt | Both died at the e10s process-model change, not from lack of demand (1.3, 2.1) | Visualizations tied to engine internals die when the architecture changes | Every view is a client of the DevTools data protocol over capability IPC (B2), never a reach into engine internals |
| Firefox panel removals, Chrome consolidation | 0.02% vs 70% usage; niche panels removed; Insights panel folded back in after context switching (2.3–2.5) | A panel per feature does not scale. Organize by question and summon specialist views by context | Few permanent surfaces; specialist views open from a selection or a question, not from a tab row |
| Safari 7, Edge Activity Bar | New layouts were revised or withdrawn after pushback (1.5, 1.6) | Layout changes need a familiar entry path and testing with real users | Keep a familiar docked layout as one arrangement among several, and test new ones in lab studies before shipping |
| Debugger Canvas | Helped on long call paths, but some abandoned it; its authors recommended a mode, not a replacement (10.11) | New paradigms should be modes inside the familiar tool | Workspaces and canvases are optional arrangements of the same views |
| Timelapse, Replay.io, Pernosco | Recording was cheap, but replay alone gave no speed-up; time-travel tools stayed niche and "last resort" (3.4, 3.11, 3.14) | Time travel pays off only when it feeds the everyday tools | Use B1 recording as the backing store of the default console, network and elements views, not as a separate "replay mode" |
| Replay.io, Pernosco | Retroactive logging and one-click dataflow are what users valued (3.1, 3.9, 3.10) | Start from print debugging, then reach provenance | Logpoints that apply across the whole recording; "where did this value come from" on any value |

| Whyline, Scry, Unravel, Ply | The largest measured gains came from asking backwards from visible output (4.1–4.5) | Answer "why" from the symptom, not from the developer's guess | Why-queries on pixels, boxes, nodes and values, answered from the mutation log (B4) and invalidation records (B5) |

| Moldable Inspector, Smalltalk | ~9 lines per custom view made custom inspection routine (5.3, 5.5) | Make author-level views a cheap platform feature | A small, stable view-registration API in `hg-devtools` for framework components and custom elements |

## Candidate paradigms

Each paradigm is derived from a user task, not from an existing panel. They can be combined: a paradigm is a way of arranging and querying the same data, not a separate tool.

| # | Paradigm | User task it serves | Evidence for | Evidence against | Needs which Izcal capability |
|---|---|---|---|---|---|
| CP-1 | **Recording-backed everyday tools.** Every session is recorded by default within a budget. **Strongest five, on current evidence:** CP-2 (why-queries), CP-1 (recording-backed everyday tools), CP-3 (spec-linked explanations), CP-10 (text and table equivalents) and CP-9 (agent surface). CP-2 and CP-3 have the largest measured effects in this strand, and Izcal is uniquely placed to answer them exactly. CP-1 is where Izcal's substrate differs most from other browsers, but the evidence says it pays off only through CP-2 and retroactive logging, not as a separate mode. CP-4 and CP-5 should ship as optional arrangements, following the Debugger Canvas and Safari lessons.
