# Izcal DevTools spec: protocols and standards

Compiled 17 Oct 2026. Primary sources were preferred: specifications, W3C, IETF and Ecma pages, maintainers' posts and release notes. Where a protocol definition is published as machine-readable data, I read the data (counts below), but I cite the published definition, not engine source files (M-1).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Method note.** This session's web-search budget ran out partway through. After that I used only direct fetches of known primary URLs. Claims I could not re-check that way are marked Medium or Low, and the gaps are listed in section 12.

## 1. Chrome DevTools Protocol (CDP)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Origin: CDP began as the "WebKit Remote Debugging Protocol"**, a JSON-RPC 2.0-style protocol carried over a WebSocket. The browser acts as a server on `--remote-debugging-port=9222`, and `/json` lists the inspectable targets. The API is split into **domains** of commands and events. It was defined by `Inspector.json` in WebKit. Chrome's own Web Inspector frontend used the same protocol, so third-party tools could too. | v1.0 public domains in Chrome 17: CSS, Console, DOM, DOMDebugger, Debugger, Network, Page, Runtime, Timeline (9). Hidden domains, "not guaranteed to be backwards-compatible": ApplicationCache, DOMStorage, Database, FileSystem, IndexedDB, Inspector, Memory, Profiler, Worker (9). | Sharma (Adobe), "Better Web Development with WebKit Remote Debugging", WWW2012 Dev Track. https://archives.iw3c2.org/www2012/proceedings/nocompanion/DevTrack_041.pdf | Apr 2012 | High |
| 1.2 | **Design rationale.** The protocol was the wire between Chrome's own frontend (itself a web app) and the engine. That made it powerful and complete for Chrome, and documentation for outsiders was an afterthought: "Tutorials and documentation available about the API have been scarce." The **public/hidden split** was its first stability mechanism. | — | Same | Apr 2012 | High |
| 1.3 | **Today's size.** The published definition (version field "1.3" in the tip-of-tree JSON) has **59 domains**: 53 browser domains plus 6 JS domains (Console, Debugger, HeapProfiler, Profiler, Runtime, Schema). It has **677 commands and 232 events**. **40 of the 59 domains are flagged experimental.** New domains in 2026 include `WebMCP`, `FedCm`, `DigitalCredentials`, `SmartCardEmulation` and `PWA`. | 53+6 domains; 596+81 commands; 210+22 events; 39+1 experimental domains | Published definition, ChromeDevTools/devtools-protocol (`json/browser_protocol.json`, `json/js_protocol.json`), viewer at https://chromedevtools.github.io/devtools-protocol/ | read 17 Oct 2026 | High (counted) |
| 1.4 | **Versioning and stability policy.** The viewer publishes three views: **Tip-of-Tree**, **Stable (1.3)** and **V8 Inspector (Node.js)**. ToT is what Chrome ships and changes continuously. "Stable 1.3" is a frozen subset, and tools in practice target ToT anyway. The repository is regenerated daily from Chromium. Protocol issues are filed against the Chromium bug component, not the repository. So there is **no external governance**: Chromium changes the protocol when Chromium needs to. | Generated "daily"; 1.3 frozen long ago (I recall it was tagged at Chrome 64 but could not re-verify) | https://github.com/ChromeDevTools/devtools-protocol (README) ; https://chromedevtools.github.io/devtools-protocol/ | 2026 | High (process) / Low (Chrome 64 tag) |
| 1.5 | **License.** The published protocol definition is **BSD-3-Clause** ("Copyright 2014 The Chromium Authors"). A clean-room implementation built from the published definition is therefore legally simple. The constraint is technical: the semantics are defined by Chromium's behavior, not by prose. | — | https://github.com/ChromeDevTools/devtools-protocol (LICENSE) | 2014– | High |
| 1.6 | **CDP already exposes some deep network data per request.** `Network.SecurityDetails` carries protocol, key exchange (and group), cipher, MAC, certificate subject, SANs, issuer, validity, the **SCT list**, **CT compliance**, the server signature algorithm and an **`encryptedClientHello`** flag. `Response` carries `remoteIPAddress`, `connectionId` and `alternateProtocolUsage`, and `ResourceTiming` includes DNS timings. It has **no QUIC-level events** (packets, loss, congestion, streams) and no DNS-resolution events (resolver, records, HTTPS RR). | 15 SecurityDetails fields | Published definition, Network domain. https://chromedevtools.github.io/devtools-protocol/tot/Network/ | read 17 Oct 2026 | High (counted) |
| 1.7 | **Chrome's QUIC and DNS internals live in a separate format, NetLog**, not in CDP. NetLog is "an event logging mechanism for Chrome's network stack": a JSON event stream with source IDs and BEGIN/END phases, covering DNS, socket pools, proxy and cache. It is explicitly "subject to change", and its viewer was removed from Chrome in 2018 and moved to an external repository. | — | https://www.chromium.org/developers/design-documents/network-stack/netlog/ | living doc | High |
| 1.8 | **Security cost of a debugging port.** From **Chrome 136**, `--remote-debugging-port` and `--remote-debugging-pipe` are ignored for the default profile and need a non-default `--user-data-dir`. The reason: "we've seen an increase in attackers using Chrome Remote Debugging to extract cookies" after App-Bound Encryption shipped. An unauthenticated localhost protocol with full power is an attack surface. | Chrome 136 | https://developer.chrome.com/blog/remote-debugging-port | 17 Mar 2025 | High |
| 1.9 | **Firefox implemented a partial CDP and then removed it.** It shipped in Firefox 86 (Feb 2021) with **82 APIs**, "a subset" for Puppeteer. Deprecated in Firefox 129, disabled by default and moved to limited maintenance. Fully removed in **Firefox 141**, and the `remote.active-protocols` preference went with it. Mozilla's reasons: BiDi is "a superset of the features that were provided by Firefox's CDP implementation", and clients (Selenium, Browsertime, Puppeteer) had moved to BiDi. | 82 APIs (out of the hundreds in 1.3); deprecated FF129; removed FF141 | Skupin, "Deprecating CDP Support in Firefox". https://fxdx.dev/deprecating-cdp-support-in-firefox-embracing-the-future-with-webdriver-bidi/ ; "CDP Retirement in Firefox" https://fxdx.dev/cdp-retirement-in-firefox/ ; Firefox WebDriver newsletter 141 https://fxdx.dev/firefox-webdriver-newsletter-141/ | 28 May 2024; 2025 | High (deprecation) / Medium (141 from newsletter snippet) |
| 1.10 | **Why the Firefox CDP subset failed.** "Since Firefox only implemented a subset of CDP, Puppeteer could never guarantee its full API to work with Firefox, creating confusion for users." A protocol whose semantics are one engine's internals cannot be implemented partially in a way clients can rely on. Selenium removed CDP-for-Firefox in Selenium 4.29.0. | — | Chrome for Developers, "WebDriver BiDi production-ready in Firefox, Chrome and Puppeteer". https://developer.chrome.com/blog/firefox-support-in-puppeteer-with-webdriver-bidi ; https://www.selenium.dev/blog/2025/remove-cdp-firefox/ | Aug 2024; 2025 | High |
| 1.11 | **CDP remains the de facto debugging protocol.** Google says BiDi is not a replacement for debugging: "Chromium-based browsers will continue to use CDP for debugging purposes." Puppeteer still defaults to CDP for Chrome "since not all CDP features are supported by WebDriver BiDi yet." | — | https://developer.chrome.com/blog/webdriver-bidi ; https://pptr.dev/webdriver-bidi | 2021; 2026 | High |

**Implications:** CDP is the protocol that existing clients speak: Puppeteer, Playwright's Chromium path, VS Code's JS debugger, Lighthouse, Chrome DevTools for agents. But it is one vendor's evolving internal API, and Firefox showed that a subset implementation disappoints. If Izcal offers CDP at all, it should be a bounded, documented compatibility profile (for example, the JS domains plus a named subset) generated from the published BSD-licensed definition. It should never be Izcal's native protocol, and it must sit behind authentication and an explicit opt-in profile.

## 2. Other engine-specific debugging protocols

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Firefox Remote Debugging Protocol (RDP)** is an **actor** protocol. Every server entity is an actor in a tree (root, then tabs, then threads, then frames), and closing an actor closes its descendants. Packets are JSON objects with `to`/`from` and `type`. Debuggee values are **grips**: either JSON values or references to actors. The transport is pluggable (`length:JSON` framing over TCP or USB, an in-memory transport in-process), and it has **bulk data packets** for large payloads such as profiles. | Thread actor states: Detached, Running, Paused, Exited | Firefox source docs, "Remote Debugging Protocol". https://firefox-source-docs.mozilla.org/devtools/backend/protocol.html | living doc | High |
| 2.2 | **RDP limits.** RDP is documented as prose, with **no machine-readable schema**. Its compatibility rule is "Clients should silently ignore packet properties they do not recognize." The page still has open TODOs ("What about objects with many properties?"). Firefox now exposes **Marionette** (internal, and geckodriver's backend for WebDriver Classic) and **WebDriver BiDi** for automation. RDP stays as the private DevTools wire. | — | Same; https://firefox-source-docs.mozilla.org/remote/index.html | living doc | High |
| 2.3 | **WebKit Inspector Protocol.** It forked from the same `Inspector.json` lineage as CDP (1.1), after Chromium left WebKit in 2013. Remote inspection uses JSON over a WebSocket or platform channel. I found **no public stability or versioning statement**, and domains are moved or removed in practice. Safari Web Inspector keeps adding features over it (for example LCP entries in Timelines, Safari 26.2). | — | WWW2012 paper (1.1); WebKit Bugzilla 200384 https://bugs.webkit.org/show_bug.cgi?id=200384 ; https://webkit.org/blog/17640/webkit-features-for-safari-26-2/ | 2012–2025 | Medium |
| 2.4 | **Opera Scope / STP.** Opera Dragonfly (from May 2008, BSD and later Apache-2.0) talked to Presto over the **Scope Transfer Protocol**. STP/0 was XML and "too slow for large structures like DOM trees". STP/1 added JSON and **Protocol Buffers**, with services, commands and events described in `.proto` files and code generated by the `hob` tool. Opera published the spec and said it hoped other browsers would adopt it, possibly through a standards body. | Dragonfly shipped in Opera 9.5–12.18 | Opera dev blog, "Opera Scope Protocol Specification Released" (now redirected; content via search snippet) https://dev.opera.com/blog/opera-scope-protocol-specification-released/ ; hob https://pypi.org/project/hob/ ; https://en.wikipedia.org/wiki/Opera_Dragonfly | 2009–2010 | Medium (primary blog no longer resolves) |
| 2.5 | **Scope's fate.** It ended with Presto. When Opera moved to Chromium/Blink in 2013, "subsequent versions included Chromium's DevTools instead", and no other browser adopted Scope. A typed, schema-first protocol did not survive because its engine did not, and no second implementer had joined. | — | https://en.wikipedia.org/wiki/Opera_Dragonfly | 2013 | Low (secondary) |
| 2.6 | **V8 Inspector protocol.** This is the CDP subset that V8 itself implements (Runtime, Debugger, Profiler, HeapProfiler, Console, Schema). Embedders pass JSON through `dispatchProtocolMessage` and get `sendResponse`/`sendNotification` back. Node.js exposes it via `--inspect` on 127.0.0.1:9229, with a per-process UUID WebSocket URL. The **legacy V8 Debugging Protocol** (port 5858) was deprecated in Node 7.7 and "is no longer maintained or documented". | 6 JS domains, 81 commands, 22 events (1.3) | https://v8.dev/docs/inspector ; https://nodejs.org/en/learn/getting-started/debugging | living docs | High |
| 2.7 | **Inspector security model: anyone who connects is root.** Node's docs say a client that connects "may be able to execute arbitrary code". Binding to 0.0.0.0 lets any reachable client connect "without any restriction". Even on 127.0.0.1, "any applications running locally on your machine will have unrestricted access". Node's only defense against DNS rebinding is a check that `Host` is an IP or `localhost`. | — | https://nodejs.org/en/learn/getting-started/debugging | living doc | High |

**Implications:** Every engine built its own protocol because the protocol was really the RPC layer of its own DevTools frontend. Two design ideas are worth carrying forward as ideas: RDP's **actor tree with lifetimes**, and Scope's **schema-first protobuf services with code generation**, which matches Izcal's typed IPC (B2). The failure to avoid is a protocol that has a single implementer and no stability tiers. All of these protocols also have a "localhost equals trusted" security model, which Izcal should reject.

## 3. WebDriver Classic and WebDriver BiDi

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **WebDriver (Classic) became a W3C Recommendation on 5 June 2018**: "a remote control interface that enables introspection and control of user agents", over HTTP REST with strict command/response. **WebDriver Level 2** is still a Working Draft (2 Jul 2026). | — | https://www.w3.org/TR/2018/REC-webdriver1-20180605/ ; https://www.w3.org/TR/webdriver2/ | 2018; 2026 | High |
| 3.2 | **Safari's driver shows a safe automation UX.** `safaridriver` (Safari 10) runs tests in separate **Automation windows** (orange Smart Search field), always from a clean slate with no access to history or AutoFill. A **"glass pane"** blocks stray user input, and the user can "break the glass" to cut the test off. Only one session runs at a time. | — | Burg, "WebDriver Support in Safari 10". https://webkit.org/blog/6900/webdriver-support-in-safari-10/ | 26 Aug 2016 | High |
| 3.3 | **WebDriver BiDi status.** It is a **W3C Working Draft dated 8 Oct 2026** (Browser Testing and Tools WG). The editors are James Graham (Mozilla), Alex Rudenko and Maksim Sadym (Google). It "extends WebDriver by introducing bidirectional communication" over WebSocket, and events stream from the browser. It is not yet a CR. | Modules: session, browser, browsingContext, emulation, network, script, storage, log, input, webExtension | https://www.w3.org/TR/webdriver-bidi/ | 8 Oct 2026 | High |
| 3.4 | **Why BiDi was made.** It aims "to combine the best of both WebDriver 'Classic' and CDP". Classic lacked events, and CDP "with its Chrome- and DevTools-specific elements, cannot be directly replicated" in a standard. CDP-based tools (Puppeteer, Playwright, Cypress) were the reason cross-browser automation fragmented. | — | https://developer.chrome.com/blog/webdriver-bidi | 2021 | High |
| 3.5 | **What BiDi covers (2026 spec text).** Navigation and history events; realms and script evaluation with structured remote values and preload scripts; **network interception** (`addIntercept`, `continueRequest/Response`, `provideResponse`, `failRequest`, `continueWithAuth`), body capture (`addDataCollector`, `getData`), `setCacheBehavior` and `setExtraHeaders`; cookies with **partition keys**; user contexts (profiles); input actions; downloads; screenshot, print and **screencast**. **Emulation** covers geolocation, locale, timezone, network conditions, media features, forced colors, screen, touch, UA, scripting-enabled and viewport-meta. | ~10 modules; network has ~13 commands and 7 events | https://www.w3.org/TR/webdriver-bidi/ (CDDL definitions) | 8 Oct 2026 | High |
| 3.6 | **What BiDi does not cover.** There is **no tracing, profiling, heap, coverage, CSS/style inspection, DOM-mutation stream, layer/paint or accessibility-tree** module. Accessibility appears only as a locator (`name`, `role`). Network responses carry `protocol` (the ALPN string) and `FetchTimingInfo` (Resource Timing fields such as `tlsStart`), but **no certificate chain, cipher, QUIC or DNS detail**. A spec note still says "CDP has LogEntryAdded types xml, …" that BiDi lacks. | — | Same | 8 Oct 2026 | High |
| 3.7 | **Who ships BiDi.** **Firefox** ships it natively, and it is the default for Puppeteer since 23 and for Cypress with Firefox 135+. **Chrome** ships it through **chromium-bidi**, "a JavaScript layer translating between BiDi and CDP, running inside a Chrome tab", served by ChromeDriver, with `goog:cdp.*` escape hatches. **Safari/WebKit**: Selenium marks Safari BiDi as experimental, and Igalia presented work on WebKit BiDi at SeleniumConf 2025. I found no WebKit statement that it has shipped. | — | https://developer.chrome.com/blog/firefox-support-in-puppeteer-with-webdriver-bidi ; https://github.com/GoogleChromeLabs/chromium-bidi ; https://www.selenium.dev/selenium/docs/api/rb/Selenium/WebDriver/Safari/Options.html ; https://www.igalia.com/downloads/slides/lauromoura-advancingwebdriverbidisupportinwebkit.pdf | 2024–2026 | High (FF, Chrome) / Low (Safari) |
| 3.8 | **Gaps measured from a client.** Puppeteer lists as **unsupported over BiDi**: Accessibility, Coverage, Tracing, CPU throttling, vision-deficiency emulation, `metrics()`, `queryObjects()`, response `securityDetails()`, service-worker bypass and drag interception. It lists partial support for screenshots, PDF, viewport and navigation options. | ~30 Puppeteer APIs listed | https://pptr.dev/webdriver-bidi | 2026 | High |
| 3.9 | **BiDi convergence worked because it was test-driven and multi-vendor.** Status is tracked on wpt.fyi rather than in vendor docs, and the editors come from two vendors. Mozilla's milestone page shows active 2026 work aimed at Playwright. | Mozilla Milestone 19 completed 29 Mar 2026 (wiki snippet) | https://wiki.mozilla.org/WebDriver/RemoteProtocol/WebDriver_BiDi | 2026 | Medium |

**Implications:** Izcal should implement **WebDriver Classic and WebDriver BiDi natively from the W3C specs**, with WPT as the conformance test. BiDi is the only cross-engine automation protocol with real momentum, and it brings Puppeteer, Selenium, WebdriverIO and Cypress for free. It is deliberately not a debugging protocol, so Izcal still needs its own protocol for everything in 3.6. Copy Safari's glass-pane and isolated-session UX as an idea.

## 4. Editor protocols: Language Server Protocol and Debug Adapter Protocol

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **LSP was announced 27 Jun 2016** by Microsoft, with Red Hat and Codenvy (Eclipse Che) adopting it. It is "an open, JSON-based protocol", JSON-RPC between an editor and a language server, so "a server can be implemented in any language". The aim was to stop repeating language support per tool: the M×N problem. | — | VS Code blog, "A Common Protocol for Languages". https://code.visualstudio.com/blogs/2016/06/27/common-language-protocol | 27 Jun 2016 | High |
| 4.2 | **LSP current version is 3.18**, with **3.19 under development**. The spec is still hosted and edited by Microsoft (GitHub repository). It has no foundation governance. | 3.18 current | https://microsoft.github.io/language-server-protocol/ ; https://microsoft.github.io/language-server-protocol/specifications/lsp/3.18/specification | 2026 | High (version) / Medium (governance, inferred from hosting) |
| 4.3 | **DAP** standardizes "the abstract protocol" between a tool's generic debugger UI and a **debug adapter**, because "it is unrealistic to assume that existing debuggers or runtimes adopt this protocol any time soon". The adapter translates a runtime's native API, such as CDP for JS, into DAP. Messages are JSON with a `Content-Length` header, over stdio (single-session) or a port (multi-session). | — | https://microsoft.github.io/debug-adapter-protocol/overview | living doc | High |
| 4.4 | **DAP history.** It came out of VS Code, and its JSON was **modeled on the obsolete V8 Debugging Protocol**: "similar to but not compatible with the JSON-RPC used in the LSP". It got its own site and repository in **Aug 2018**, explicitly to show it was not VS Code-specific. | — | Weinand, "New home for the Debug Adapter Protocol". https://code.visualstudio.com/blogs/2018/08/07/debug-adapter-protocol-website/ | 7 Aug 2018 | High |
| 4.5 | **DAP adoption.** 16 client entries (15 distinct tools) are listed: VS Code, Visual Studio, VS for Mac, Eclipse (LSP4E), Emacs (dap-mode, dape), ecode, Theia, Vim/Neovim (vimspector, nvim-dap), Cloud Studio, JCIDE, OpenSumi, IntelliJ (LSP4IJ), **Zed**, Kate. A long list of adapters is also maintained. | 16 client entries | https://microsoft.github.io/debug-adapter-protocol/implementors/tools/ | 2026 | High |
| 4.6 | **What DAP cannot express.** It models threads, stack frames, scopes, variables, breakpoints and stepping, which is the classic debugger model. It has **no DOM, network, rendering, timeline or time-travel model** beyond optional `stepBack`/`reverseContinue` capabilities (I recall these but did not re-check them this session). So it is the right protocol for *JS/Wasm source debugging in an editor*, and the wrong one for browser inspection. | — | Same overview; DAP specification https://microsoft.github.io/debug-adapter-protocol/specification | — | Medium |

**Implications:** Izcal should ship a **DAP adapter for its JS and Wasm debugger** (`hg-*` crate), built from the DAP spec, so that VS Code, Zed, Neovim, JetBrains and others debug Izcal pages without CDP. LSP has no direct runtime role. Its lesson is the M×N decoupling, plus the warning that a Microsoft-hosted spec without a foundation still became universal, because it was simple, versioned and documented.

## 5. Agent protocols: MCP, WebMCP and Chrome DevTools for agents

| # | Finding | Numbers | Source | Date | Conf. |

| 5.14 | **WebMCP** lets *pages* offer tools to agents: `document.modelContext.registerTool/getTools/executeTool`, gated by a **Permissions Policy "tools"** feature (default `'self'`). It is a **Draft Community Group Report (16 Oct 2026, W3C Web Machine Learning CG), not on the standards track**. Editors are from Microsoft and Google. **Implications:** MCP is the agent-tool interface that matters in 2026, now under neutral governance and moving fast: four breaking revisions in 20 months. Izcal should **expose its DevTools as an MCP server** that follows the current spec, but it must enforce what MCP leaves to implementers. Use **stdio or an authenticated local channel only**, never an open port; pass every call through the **B9 agent principal** with origin-scoped capabilities; **pin and hash tool descriptions** against rug pulls; label page-derived content as untrusted; and keep AI off by default (B10). Track WebMCP, but do not ship it while it is a CG draft.

## 6. Source maps (ECMA-426) and DWARF for WebAssembly

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **ECMA-426, 1st edition, December 2024** ("Source map format specification") standardized the de facto "Revision 3" Google doc format under **TC39-TG4** (formed July 2023). The live draft is dated 11 Sep 2026. | 1 edition published | https://ecma-international.org/publications-and-standards/standards/ecma-426/ ; https://tc39.es/ecma426/ | Dec 2024; Sep 2026 | High |
| 6.2 | **What it expresses.** `version` (must be 3), `file`, `sourceRoot`, `sources`, `sourcesContent`, `names`, VLQ `mappings`, **`ignoreList`** (formerly `x_google_ignoreList`, for hiding framework code), and **index maps** (`sections` with offsets). | 6.3 | **Debugging extensions in progress.** **Scopes (Stage 3)**: original scope trees, generated ranges, inlined-function **callsites**, and **bindings** given as JS expressions to recover original variable values. **Range Mappings (Stage 2)**, **Debug ID (Stage 2)**, **Env (Stage 1)**. | 6.4 | **Why scopes matter.** Without them source maps are "generally insufficient to reconstruct the original frames, scopes and bindings". Inlined functions leave no frame, and renamed or eliminated variables cannot be shown. This is the single largest gap between "it maps lines" and "it debugs the original program". | — | scopes proposal (6.3) | 2026 | High |
| 6.5 | **DWARF for WebAssembly** is a convention, not a W3C standard. | 6.6 | **Chrome's C/C++ debugging is an extension, not a protocol.** It requires the "C/C++ DevTools Support (DWARF)" extension. Chrome chose DWARF over source maps for future variable, type and expression support. | Docs last updated 7 Jun 2023 | https://developer.chrome.com/blog/wasm-debugging-2020 ; https://developer.chrome.com/docs/devtools/wasm | Dec 2020; Jun 2023 | High |

**Implications:** Izcal should consume **ECMA-426 natively, including Scopes and Debug ID** as they reach Stage 3–4, and should treat on-demand, memory-bounded map loading as a requirement (see 5.13). For Wasm, read **DWARF per the Wasm convention** inside the engine's debugger, without a browser extension, and expose it through DAP. Debugging must not change execution tier silently: Izcal should show when it does.

## 7. Network data formats: HAR and qlog

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **HAR was never standardized.** The W3C Web Performance draft (Odvarko, Jain, Davies) "was never published … and has been abandoned", and it is marked "DO NOT USE". ## 10. Why protocols fragmented, and why some converged

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 10.1 | **Fragmentation pattern.** Each debugging protocol (WebKit/CDP, Firefox RDP, Opera Scope, WebKit Inspector) was the private RPC of a vendor's own frontend, shaped by that engine's internals. None had a second full implementer. Attempts to adopt another vendor's protocol (Firefox's CDP subset) or to offer one's own (Opera Scope) failed. | 4 engine protocols, 0 successful cross-engine adoptions | Sections 1–2 | 2008–2025 | High (synthesis) |
| 10.2 | **Convergence pattern.** The protocols that converged (WebDriver, BiDi, LSP, DAP, MCP, Trace Context, ECMA-426) were designed **for an external client from day one**, had **prose specs plus a schema** (CDDL, JSON Schema, TypeScript), had **multiple implementers before freezing**, and had a **conformance suite** (WPT for WebDriver) or a reference SDK. Source maps converged *de facto* first and were then standardized from existing practice. | — | Sections 3–8 | 2016–2026 | High (synthesis) |
| 10.3 | **Scope split.** Standards cover automation (BiDi) and editor debugging (DAP), and none covers *inspection* of DOM, CSS, layout, paint, network internals or memory. That part stays per-engine. No working group currently charters a cross-engine inspection protocol. | — | 3.6, 4.6 | 2026 | Medium (absence of evidence) |
| 10.4 | **Every local debug endpoint became an attack vector.** Chrome's remote-debugging port (cookie theft, Chrome 136), Node's inspector (local unrestricted access), MCP Inspector (CVE-2025-49596) and MCP local servers (DNS rebinding, so the spec requires an `Origin` check). | 4 cases | 1.8, 2.7, 5.8, 5.11 | 2025 | High |

**Implications:** Izcal's own protocol needs the convergence traits from day one: an external-client design, a schema, a prose spec with stability tiers, a conformance suite and authentication. It also needs a public pledge of which parts are stable.

## Lessons for Izcal

| Project | What happened | Lesson | How Izcal applies it |
|---|---|---|---|
| WebKit Remote Debugging → CDP | The frontend's private RPC became the world's de facto protocol; 40 of 59 domains are still experimental, and semantics are defined by Chromium behavior | A protocol designed for your own frontend becomes everyone's API whether you plan it or not | Design Izcal's protocol for external clients from day one, with stability tiers stated per domain |
| Firefox partial CDP (FF86–FF141) | 82-API subset; Puppeteer "could never guarantee its full API"; removed | A partial clone of a vendor protocol disappoints users and costs maintenance | If Izcal offers CDP, publish an exact compatibility profile tested by a suite, and refuse what it does not support with a clear error |
| Opera Scope (STP/1) | Schema-first protobuf, published spec, hoped for standardization; died with Presto | Good design without a second implementer does not converge | Generate Izcal's protocol from one schema (as B2 does for IPC), and seek outside clients early: DAP, BiDi, MCP adapters |
| Firefox RDP | Actor tree with lifetimes; prose-only spec | Object lifetimes on the wire prevent leaks; prose without a schema prevents tooling | Keep the lifetime idea (handles scoped to sessions), and always ship a machine-readable schema |
| WebDriver BiDi | Multi-vendor, WPT-tested, CDDL schema; converging | Standards win where they are test-driven and deliberately scoped | Implement BiDi natively and run WPT; do not stretch BiDi into an inspection protocol |
| LSP / DAP | Solved M×N with simple JSON protocols, adapters for legacy runtimes | Adapters let old runtimes join, and editors adopted widely | Ship an Izcal DAP adapter; editors get JS/Wasm debugging with no CDP |
| MCP 2024→2026 | Four revisions, now stateless; security left to implementers; tool poisoning, rug pulls, CVEs | The agent wire will keep changing, and security must be enforced by the host, not the protocol | Thin MCP layer over Izcal's own capability-checked tool registry (B9); pin tool descriptions; untrusted-content labels; AI off by default |
| Chrome remote-debugging port, Node inspector, MCP Inspector | Localhost debug endpoints exploited (cookie theft, RCE) | "Localhost = trusted" is false | No unauthenticated listening port. Use pipes, stdio or OS-authenticated channels, plus per-session tokens and visible "being controlled" UI (Safari glass pane) |
| HAR / Okta | Unstandardized format; HAR files leaked session tokens | Export formats are data-exfiltration paths | Sanitize by default; explicit, logged opt-in for secrets; warn on share |
| qlog / NetLog | IETF format exists; Chrome keeps QUIC detail in a private log | Owning the stack lets you log in the open format | neqo emits qlog natively; tools read qlog; export for qvis |
| Trace Event JSON → Perfetto TrackEvent | Unversioned Google Doc format became universal; Perfetto moved to protobuf with flows and interning | Causality (flows) and size (interning) matter more than human-readable JSON | Internal causal trace model; export Perfetto protobuf and Chrome JSON |
| Source maps → ECMA-426 + Scopes | De facto format standardized in 2024; scopes reach Stage 3 | Position mapping is not debugging; scopes and bindings are | Consume ECMA-426 with Scopes and Debug ID, loading maps on demand |
| DWARF-for-Wasm via Chrome extension | Works, but needs an extension and tiers down silently | Source-level Wasm belongs in the engine, and observer effects must be visible | Native DWARF reading; show tier changes; expose via DAP |
| Chrome DevTools for agents | 50k-line traces overwhelmed agents; moved to summaries, CLI and skills | Agents need summarized, queryable data, not raw dumps | Izcal's protocol offers queries and summaries (SQL-like over traces) as well as streams |
