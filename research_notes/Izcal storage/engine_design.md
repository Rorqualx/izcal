# Izcal storage: engine design evidence

Compiled 20 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers). Papers were read from primary PDFs or landing pages; vendor and project documentation was read as prose. **No third-party source code was read** (M-1 part 3): where a project's design facts come only from its on-disk format or code, they are recorded as open questions for black-box measurement instead.

Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Scope: evidence for choosing between a **log-structured (LSM-style)**, **copy-on-write B-tree**, and **B-tree + WAL** architecture for a from-scratch engine that must store IndexedDB object stores and indexes, versioned snapshots mapped read-only into other processes, transactions with atomic multi-store commits, crash consistency, per-key (site, container) partitioning, quota accounting, and deterministic replay.

## 1. LSM (log-structured merge-tree) literature

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | The original LSM-tree paper derives its advantage from **two batching effects**: (a) multi-page block I/O (COSTπ) is much cheaper than a random page I/O (COSTp), and (b) entries accumulate in the memory component C0 so that M entries merge into each C1 leaf page per merge. Insert-cost ratio: COST_LSM-ins/COST_B-ins = K1·(COSTπ/COSTp)·(1/M), "typically ... a cost ratio improvement of nearly two orders of magnitude". Example 3.2 uses a ratio of 0.02 = 1/50. | M = (Sp/Se)·(S0/(S0+S1)); typical S1 = 40·S0, ~200 entries/page → M = 5. If M < K1·COSTπ/COSTp (e.g. large entries, tiny C0), "we would do better to use a normal B-tree" | [O'Neil, Cheng, Gawlick, O'Neil, "The Log-Structured Merge-Tree (LSM-Tree)"](https://www.cs.umb.edu/~poneil/lsmtree.pdf) | 1996 | High |
| 1.2 | The same paper prices everything with the **five-minute rule** (Gray & Putzolu 1987): keep a page in memory if it is accessed more often than once per amortization interval (~60 s); the paper notes the interval "is now often 30 minutes or more than when defined in 1987 when it was five minutes" as hardware shifted. This is the origin of LSM's premise: tune the memory component so hot writes stay cheap. | interval grew 5 min → 30+ min from 1987 to 1996 | same | 1996 | High |
| 1.3 | **WiscKey** separates keys (kept in the LSM) from values (appended to a value log), explicitly because LSM write amplification wastes SSD endurance and because SSDs are fast at random reads. Results vs LevelDB: loading 2.5x–111x faster; random lookups 1.6x–14x faster; outperformed LevelDB and RocksDB "in all six YCSB workloads". Its cost: garbage collection of the value log rewrites surviving values (the GC problem). | 2.5x–111x load; 1.6x–14x lookups | [WiscKey (FAST '16) landing page](https://www.usenix.org/conference/fast16/technical-sessions/presentation/lu) | 2016-02 | High |
| 1.4 | Dostoevsky (SIGMOD 2018) formalizes the LSM compaction design space: **leveling** minimizes space and read amplification at the cost of write amplification O(T²); **tiering** minimizes write amplification at the cost of read amplification. **Lazy leveling** (tiering everywhere, leveling in the largest level) roughly halves worst-case read amplification versus leveling while cutting write amplification; FluidKV reported up to 25% lower tail read latency and 8x lower storage overhead than RocksDB on some workloads. | ~25% tail read latency; 8x storage overhead (reported figures) | [Dostoevsky (SIGMOD '18)](https://dl.acm.org/doi/10.1145/3183713.3196902), figures via [LSM compaction design-space survey](https://www.researchgate.net/publication/358488953_Constructing_and_Analyzing_the_LSM_Compaction_Design_Space) and course summaries | 2018-06 | Medium |
| 1.5 | Documented **write-stall behavior** (RocksDB wiki): writes are throttled "when flush or compaction can't keep up with the incoming write rate"; otherwise space and read amplification grow without bound. Writes are fully stopped when memtables waiting to flush hit `max_write_buffer_number`; slowed/stopped at L0 file-count triggers (example log: stalled at 4 L0 files, stopped at 20); slowed at `soft_pending_compaction_bytes` and stopped at the hard limit. A stalled write is reduced to `delayed_write_rate`, and **a stall in one column family stalls the entire DB**. | example triggers: slow at 4 L0 files, stop at 20; 1 ms sleeps for no_slowdown | [RocksDB wiki: Write Stalls](https://github.com/facebook/rocksdb/wiki/Write-Stalls) | current (accessed 2026-10-20) | High |
| 1.6 | LevelDB documents the read-side cost directly: "a single `Get()` call may involve multiple reads from disk", and its optional Bloom-filter policy "will reduce the number of unnecessary disk reads needed for Get() calls by a factor of approximately a 100" at 10 bits/key. Its default asynchronous write is "often more than a thousand times as fast as synchronous writes" (durability is a separate dial, not part of the structure). | ~100x fewer disk reads with 10-bit Bloom filters; >1000x async vs sync write | [LevelDB doc/index.md](https://github.com/google/leveldb/blob/master/doc/index.md) | current | High |
| 1.7 | Space amplification is visible in a practitioner benchmark published by the redb author: same 1 GB-equivalent workload, uncompacted on-disk size: LevelDB-derived RocksDB 893 MiB vs LMDB 2.61 GiB vs redb (COW) 4.00 GiB vs sled 2.13 GiB. LSM stores reclaim space by rewriting; in-place structures carry free-space fragmentation or COW garbage until a full compaction/vacuum. | 893 MiB / 2.13 / 2.61 / 4.00 GiB uncompacted, same benchmark | [redb README benchmark table](https://github.com/cberner/redb) | accessed 2026-10-20 | Medium |

**Implications:**
(a) **Architecture**: LSM wins when writes dominate and the value/entry ratio makes batching effective (O'Neil's M); it loses on point-read cost (per-level probes + Bloom filters), on tail latency predictability (compaction storms, write stalls — 1.5), and on a browser's constraint that a stalled write path blocks a page's JS. Key–value separation (1.3) exists precisely because browser-style workloads have very large values (IndexedDB blobs to hundreds of MB); but it adds a GC subsystem.
(b) **Durability**: LSM durability is a WAL-plus-memtable policy, independent of the tree (1.6); an async-write-first design with batched sync is standard practice.
(c) **Snapshot mapping**: immutable sorted-string-table files are inherently page-granular, immutable, and mappable — the LSM's one structural advantage for cross-process read-only views.
(d) **Determinism**: compaction scheduling is a large source of nondeterministic timing behavior that must be abstracted or made deterministic in simulation (see §10).

## 2. B-tree / B+-tree and copy-on-write B-trees

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | The B-tree side of O'Neil's model: a B-tree insert in the steady state costs a leaf-page read plus a leaf-page write, COST_B-ins = 2·COSTp (a random I/O each way), with no batching — but also **no reorganization, no GC, and bounded read cost** (the tree is the index). The LSM trade is exactly the M-batching and COSTπ/COSTp ratios of §1.1 against this flat, predictable cost. | COST_B-ins = 2·COSTp | [O'Neil et al. 1996](https://www.cs.umb.edu/~poneil/lsmtree.pdf) | 1996 | High |
| 2.2 | **LMDB** documents a memory-mapped **copy-on-write B-tree**: "Data pages use a copy-on-write strategy so no active data pages are ever overwritten, which also provides resistance to corruption and **eliminates the need of any special recovery procedures after a system crash**." And: "Unlike other well-known database mechanisms which use either write-ahead transaction logs or append-only data writes, LMDB requires no maintenance during operation... LMDB tracks free pages within the database and re-uses them for new write operations, so the database size does not grow without bound in normal use." | zero; no WAL, no checkpoint, no compaction step at all | [LMDB documentation](https://lmdb.tech/doc/) | current (accessed 2026-10-20) | High |
| 2.3 | LMDB's concurrency model: "Writes are fully serialized; only one write transaction may be active at a time, which guarantees that writers can never deadlock. The database structure is multi-versioned so readers run with no locks; writers cannot block readers, and readers don't block writers." Reads are zero-copy out of the map ("no malloc's or memcpy's occur during data fetches"), and a read-only map "provides total immunity to corruption" from stray pointer writes. Caveats documented in the same page: long-lived read transactions "prevent reuse of pages freed by newer write transactions, thus the database can grow quickly"; do not fork while an environment is open; do not use it on remote filesystems; stale readers must be checked. | single writer; unlimited lock-free readers | [LMDB documentation](https://lmdb.tech/doc/) and [intro.doc prose](https://github.com/LMDB/lmdb/blob/master/libraries/liblmdb/intro.doc) | 2011–2021 | High |
| 2.4 | redb (a pure-Rust store "loosely inspired by lmdb") documents the same structure with the invariants spelled out: "Except for the database metadata, all other data structures are copy-on-write"; "Committed pages are never modified in-place"; read transactions "make a private copy of the root of the b-tree" and pages freed by writes are reused only "after all read transactions that could reference it have completed" (epoch-based reclamation); isolation is serializable via MVCC; single writer, multiple concurrent readers. | savepoint allocator snapshot ≈ 64 kB per 1 GB of data at 4 KB pages | [redb design doc](https://github.com/cberner/redb/blob/master/docs/design.md) | current | High |
| 2.5 | Filesystem COW evidence: Btrfs is documented as "a copy on write filesystem" whose writing of new data to fresh locations underpins "Checksums on data and metadata", "Writable snapshots", and reflink/deduplication — snapshots are cheap because they share extents. This is shadow paging at filesystem scale: the tree of blocks is rebuilt on write and the root reference is swapped atomically. | snapshot creation is an extent-tree reference, not a copy | [Btrfs kernel documentation](https://docs.kernel.org/filesystems/btrfs.html) | current | High |
| 2.6 | The cost COW pays: every write of one logical record dirties the whole path from root to leaf (path copying), and freed old pages can only be reused after the oldest reader departs (2.3, 2.4) — a long-held snapshot grows the file. redb's benchmark table (1.7 row) shows a COW store at ~4.5x the footprint of an LSM store on the same workload before compaction. | ~4.5x uncompacted footprint vs LSM in one benchmark | [redb README](https://github.com/cberner/redb) | 2026 | Medium |

**Implications:**
(a) **Architecture**: a COW B-tree gives flat, predictable read cost, single-write serialization with lock-free readers, and **crash consistency for free** (no WAL, no recovery pass) — at the cost of write amplification on deep trees, garbage until old readers finish, and needing explicit free-space/compaction management to avoid growth.
(b) **Durability**: durability is reduced to making one small, atomic "commit record" durable (root pointer + checksums); see §5.
(c) **Snapshot mapping**: a committed root is a page number that never mutates — exactly the handle a publisher needs to hand another process (§8).
(d) **Determinism**: no background rewriter means fewer asynchronous decision points; the remaining nondeterminism is in page allocation and reader-reclamation timing.

## 3. B-tree + WAL

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | SQLite's rollback-journal atomic commit is built from the weakest usable primitives, stated pessimistically: "It is not possible to modify any part of the disk smaller than a sector"; "SQLite does always assume that a sector write is linear... We do not know if this assumption is always true"; since 3.7.9 (2011) it assumes **powersafe overwrite** because "the standard sector size increasing from 512 to 4096 bytes... has become necessary to assume powersafe overwrite in order to maintain historical performance levels"; it "assumes that the file size is updated before the file content" and that "a file deletion is atomic". The **commit instant is the deletion of the journal**: before it, recovery rolls back; after it, everything appears applied. | sector = 512 B historically, 4 KB standard now; two fsyncs per commit | [How SQLite does atomic commit (atomiccommit.html)](https://www.sqlite.org/atomiccommit.html) | doc current 2026 | High |
| 3.2 | For **multi-file atomic commit** SQLite uses a super-journal listing every participating journal, flushed before any database changes and deleted last — the multi-database commit instant. This is the direct precedent for an engine committing across several stores (or site partitions) atomically. Note SQLite's WAL mode explicitly does **not** offer this: multi-ATTACH transactions "are atomic for each individual database, but are not atomic across all databases as a set". | 1 super-journal per multi-DB transaction | same, and [WAL documentation](https://www.sqlite.org/wal.html) | 2010–2026 | High |
| 3.3 | **WAL mode** inverts the journal: "The original content is preserved in the database file and the changes are appended into a separate WAL file. A COMMIT occurs when a special record indicating a commit is appended to the WAL." Benefits: "WAL is significantly faster in most scenarios"; "Write transactions are very fast since they only involve writing the content once... and because the writes are all sequential"; "WAL provides more concurrency as readers do not block writers and a writer does not block readers" — but "there can only be one writer at a time". Readers need the **wal-index**, a shared-memory structure ("rarely exceeds 32 KiB... never synced"), which is why "WAL does not work over a network filesystem" and requires all processes on one host. | auto-checkpoint at 1000 pages (~4 MB); 1–2% read penalty vs rollback mode for read-mostly | [WAL documentation](https://www.sqlite.org/wal.html) | 2010 (WAL added 3.7.0), doc current | High |
| 3.4 | WAL's structural costs, documented: checkpointing is "slower than write transactions"; "read performance deteriorates as the WAL file grows"; **checkpoint starvation** — "if a database has many concurrent overlapping readers and there is always at least one active reader, then no checkpoints will be able to complete and hence the WAL file will grow without bound"; page size cannot change once in WAL; a freshly created WAL file historically could not be opened read-only without extra files. With `synchronous=NORMAL` "transactions are no longer durable and might rollback following a power failure or hard reset" — the commit record survives in the WAL only until the next checkpoint's barrier. | checkpoint every 1000 pages; WAL grows unbounded under continuous readers | same | 2010–2026 | High |
| 3.5 | PostgreSQL's WAL rationale (prose): "changes to data files... must be written only after those changes have been logged"; "only the WAL file needs to be flushed to disk to guarantee that a transaction is committed... The WAL file is written sequentially, and so the cost of syncing the WAL is much less than the cost of flushing the data pages"; "when the server is processing many small concurrent transactions, one `fsync` of the WAL file may suffice to commit many transactions"; WAL also enables replay-forward recovery and point-in-time replay. PostgreSQL additionally protects against torn pages with `full_page_writes` (whole-page image into WAL on first modification after a checkpoint) — quote not verified from the page (the fetched chapter page was a table of contents); recorded as Medium. | 1 fsync can commit many transactions | [PostgreSQL docs ch. 28.3 WAL](https://www.postgresql.org/docs/current/wal-intro.html) | current (PG 18) | High (Medium for full_page_writes wording) |

**Implications:**
(a) **Architecture**: B-tree + WAL keeps in-place B-tree read economics and adds sequential durable logging; SQLite's WAL shows reader/writer non-blocking concurrency is achievable but needs shared-memory coordination between processes and a checkpoint policy, and multi-database atomicity must come from a super-journal-style construct, not from WAL alone.
(b) **Durability**: WAL decouples the durability dial (sync every commit vs group sync vs async) from the data structure — the same dial SQLite, PostgreSQL, and LevelDB all expose.
(c) **Snapshot mapping**: WAL itself gives readers nothing page-granular to map; cross-process readers must either share the wal-index in OS shared memory (SQLite's answer) or fall back to locking and cache invalidation (the rollback-mode change-counter scheme, atomiccommit.html).
(d) **Determinism**: recovery = replay of a deterministic log prefix, which is friendly to replay testing; but checkpoint timing is asynchronous and must be driven deterministically in simulation.

## 4. mmap vs read/write syscalls

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | The CMU-position paper states: "There are, however, severe correctness and performance issues with mmap that are not immediately apparent"; "several popular DBMSs initially used mmap to support larger-than-memory databases but soon encountered these hidden perils, forcing them to switch to managing file I/O themselves after significant engineering costs"; "mmap is not a suitable replacement for a traditional buffer pool"; conclusion prescribes limited uses. | — | [CMU DB blog, mmap](https://db.cs.cmu.edu/mmap/) and paper below | 2022 | High |
| 4.2 | The paper (Crotty, Leis, Pavlo, CIDR 2022) enumerates the pathologies: unplanned **I/O stalls** ("accessing any page could result in an unexpected I/O stall" because the OS transparently evicts); **TLB shootdowns** ("Since current CPUs do not provide coherence for remote TLBs, the OS has to... TLB shootdown", "thousands of cycles", IPI to every core); **loss of eviction control**; **error handling** — I/O failure during access "produce[s] a SIGBUS that the DBMS must deal with via cumbersome" handlers; page-table pressure. | experiment: 2 TB data, 100 GB page cache → 95% of accesses page-fault; fio sustained ~900K reads/s at ~100 µs NVMe latency; mmap with MADV_RANDOM matched fio for 27 s, dropped to ~zero for ~5 s when the cache filled, then recovered to only ~half of fio | [Are You Sure You Want to Use MMAP in Your Database Management System? (CIDR 2022)](https://db.cs.cmu.edu/papers/2022/p13-crotty.pdf) | 2022 | High |
| 4.3 | Industrial confirmation in the same paper's prose: MongoDB "deprecated MMAPv1 and then completely removed it in 2019" after moving to WiredTiger in 2015 (and reintroduced an mmap option in WiredTiger in 2020); RDF-3X "abandoned its original" mmap design. | — | same | 2022 | High |
| 4.4 | The counter-case that survives: LMDB's design is built on a **read-only** mmap of a COW file, where the map is stable (committed pages never change, no eviction control needed for correctness) and the writer uses ordinary read/write syscalls — the CMU paper's prescription ("prescription for when DBMS developers might consider using MMAP") is consistent with this split. SQLite likewise keeps the wal-index in `shm_open` shared memory but reads/writes data through the VFS. | — | [LMDB documentation](https://lmdb.tech/doc/), [SQLite WAL docs](https://www.sqlite.org/wal.html) | — | High |

**Implications:**
(a) **Architecture**: mmap as a general page cache is contraindicated; mmap of **immutable committed state** (COW snapshot) is the surviving pattern and is precisely the shape Izcal's cross-process snapshot feature wants.
(b) **Durability**: writing through pointers in an RW mmap gives no ordering and no error reporting; durable writes should go through explicit syscalls with explicit flushes.
(c) **Snapshot mapping**: reader-side mapping is safe when the mapped state is immutable by construction (COW committed pages); writer-side mapping is the dangerous half.
(d) **Determinism**: OS page-cache eviction and kswapd behavior are nondeterministic inputs; avoiding mmap for the write path removes them from the engine's decision space (macOS/Windows-specific mmap page-cache behavior was not separately documented in these sources — open question).

## 5. fsync and durability costs

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | SQLite's durability ladder, rollback-journal mode: two flushes per commit (journal content, then journal header with page count flipped non-zero only after content is flushed) — if power dies early, "the process doing the rollback will see that the journal contains zero pages and will thus make no changes". With `synchronous=NORMAL` only one flush happens, so "as a second line of defense, SQLite also uses a 32-bit checksum on every page of data in the rollback journal... If an incorrect checksum is seen, the rollback is abandoned" — checksums are probabilistic, "there is a small but finite probability that the checksum might be right even if the data is corrupt". | 2 flushes (FULL) vs 1 (NORMAL); 32-bit journal checksums | [atomiccommit.html](https://www.sqlite.org/atomiccommit.html) | current | High |
| 5.2 | Flushes can lie: "We are told that the flush and fsync primitives are broken on some versions of Windows and Linux... there is nothing that SQLite can do to test for or remedy the situation"; "the IDE disk control lies and says that data has reached oxide while it is still held only in the volatile control cache"; macOS `PRAGMA fullfsync` (F_FULLFSYNC) "will guarantee that data really does get pushed out... But... not only is it profoundly slow, it also slows down other unrelated disk I/O. So its use is not recommended." | — | same | current | High |
| 5.3 | redb documents the minimum assumptions a store can make about media: (1) "single byte writes are atomic"; (2) "following an `fsync` operation writes are durable"; (3) powersafe overwrite (citing SQLite's psow.html). On those alone it implements a **1-fsync commit** (1PC+C): write all pages + checksums + a monotonically increasing transaction id, flip one byte choosing the primary commit slot, single fsync; on crash, verify id and checksums, else roll back to the secondary slot. A 2-fsync (2PC) variant defends against adversarial collision of the non-cryptographic checksum. | 1 fsync per durable commit; 2 for the adversarial mode | [redb design doc](https://github.com/cberner/redb/blob/master/docs/design.md) | current | High |
| 5.4 | Torn-page protection: PostgreSQL writes a full page image into WAL on the first modification after each checkpoint so recovery never rebuilds from a half-written page (documented as `full_page_writes`; wording Medium per §3.5). SQLite handles the same hazard in reverse in journal mode: "whenever any page within a sector is written into the journal file, all pages in that same sector are stored with it" — a torn sector write cannot corrupt untouched neighbor pages. | journal stores all pages sharing a sector | [PostgreSQL docs](https://www.postgresql.org/docs/current/wal-intro.html) (Medium), [atomiccommit.html](https://www.sqlite.org/atomiccommit.html) (High) | current | High / Medium |
| 5.5 | fsync latency and device behavior literature (abstract level): fsync latency depends on how much must be flushed and on journal design [Fine-Grained Journaling, USENIX ATC 2017]; commodity NVMe drives already deliver sub-10 µs device I/O, shifting the durability cost to the kernel path [i10, USENIX ATC 2019]; commodity NVMe latency is highly variable, with tail reductions of 2.7x–62x achievable [FusionRAID, FAST 2021]. **No controlled consumer-SSD fsync latency distribution was captured in this strand** — Izcal must measure its own (see Open questions). | device I/O sub-10 µs (2019-era enterprise NVMe); no fsync distribution captured | [ATC'17 paper](https://www.usenix.org/conference/atc17/technical-sessions/presentation/park), [ATC'19 paper](https://www.usenix.org/system/files/atc19-lee-gyusun.pdf), [FAST'21 paper](https://www.usenix.org/conference/fast21/presentation/jiang) | 2017–2021 | Medium |
| 5.6 | Crash-consistency research line (for the durability policy, not to be imitated): NoFS ("Consistency Without Ordering", FAST 2012) achieves crash consistency without ordering metadata writes using back-pointers, with a formal model proof; OptFS (SOSP 2013) adds optimistic consistency (`dsync-batched`) and notes NoFS cannot implement atomic rename; Verma et al. (FAST 2015) provide multi-file failure-atomic commits via per-file writable snapshots. The recurring lesson: **every ordering you assume between two separate writes is an assumption the filesystem may not honor**. | — | [NoFS FAST'12](https://www.usenix.org/conference/fast12/consistency-without-ordering), [Verma FAST'15](https://www.usenix.org/conference/fast15/technical-sessions/presentation/verma) | 2012–2015 | Medium |
| 5.7 | "RIFS" (named in the strand brief among atomicity-guarantee studies) **could not be identified** in public literature after multiple searches; recorded as an open question. Likewise "sanakemura" returned no public key-value-store project. | — | (searches, 2026-10-20) | — | Low |

**Implications:**
(a) **Architecture**: durability policy must be an explicit, configurable dial separate from the data structure (LevelDB's `sync`, SQLite's `synchronous`, PostgreSQL's `synchronous_commit` all expose it); a COW design can collapse the durable-commit problem to one atomic byte (redb's god byte) — the smallest commit surface of the three architectures.
(b) **Durability policy**: default to a 1-fsync group commit with checksum-verified commit slots (5.3), assume powersafe overwrite but nothing stronger, and treat torn writes as detected-then-rolled-back rather than prevented.
(c) **Snapshot mapping**: unaffected by the durability dial — but publishing a snapshot to another process must be ordered after the commit that produced it (one barrier at publish).
(d) **Determinism**: the crash-consistency literature's testing lesson (SQLite's quote below, §9) is that crash behavior must be exercised deterministically — a simulated disk model with configurable torn-write behavior, not real fsync timings.

**Implications:**
(a) **Architecture**: the Rust embedded-store ecosystem splits exactly along the three candidate architectures (sled = log-structured, redb = COW B-tree, fjall = LSM), and each documents the weaknesses of its own choice (sled's space/GC rewrite, redb's footprint, fjall's maturity churn) — strong evidence that all three are viable but none is free.
(b) **Durability**: every one of them makes durability a background-policy dial (sled's 500 ms flusher, redb's 1PC+C/2PC switch), not a structural property.
(c) **Snapshot mapping**: none of the Rust stores documents read-only mapping of committed state into other processes — this is the gap Izcal's feature actually targets (§8).
(d) **Determinism**: none documents deterministic simulation as a design constraint; adopting it would be novel, following FoundationDB/TigerBeetle (§10) rather than any embedded store.

## 7. Variable-length record storage

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | SQLite's **slotted pages**: "A b-tree page is divided into regions in the following order: [header]... The cell pointer array... Unallocated space... The cell content area"; "SQLite strives to place cells as far toward the end of the b-tree page as it can, in order to leave space for future growth of the cell pointer array". Table B-trees take 64-bit integer keys with all data in leaves; index B-trees take arbitrary keys and no data — the natural mapping for an object store (rowid tree) plus secondary indexes (index trees). | two B-tree variants | [SQLite file format](https://www.sqlite.org/fileformat2.html) | current | High |
| 7.2 | **Overflow pages** for large values: "When the payload of a b-tree cell is too large for the b-tree page, the surplus is spilled onto overflow pages. Overflow pages form a linked list." Thresholds X/M/K are defined in terms of usable page size U; large index keys are split so "no single key uses more than one fourth of the available storage space on the page and hence every internal page is able to store at least 4 keys". Free space is a freelist of trunk pages (each holding a page-number array) plus zero-content leaf pages; SQLite "avoids reading or writing freelist leaf pages in order to reduce disk I/O". | ≥4 keys per internal page guaranteed; min usable page 480 B | same | current | High |
| 7.3 | PostgreSQL's **TOAST** documents the out-of-line-chunks alternative: fixed ~8 KB pages, tuples cannot span pages; values are compressed and/or moved out-of-line once a row exceeds ~2 KB; chunks of ~2000 B ("four chunk rows will fit on a page"), each a row with `(chunk_id, chunk_seq)` under a unique index; 18-byte on-disk pointer; 1 GB per-value limit; "During an UPDATE operation, values of unchanged fields are normally preserved as-is" (no rewrite of a changed row's big blobs); measured example: HTML-page table stored at ~half raw size with the main table only ~10% of the data. | ~2 KB trigger; ~2 KB chunks; 18 B pointer; 1 GB cap | [PostgreSQL TOAST docs](https://www.postgresql.org/docs/current/storage-toast.html) | current (PG 18) | High |
| 7.4 | Space reclamation: SQLite tracks a freelist and VACUUM rebuilds the whole file (coarse, all-or-nothing); LSM stores reclaim incrementally at every compaction but pay write amplification; WiscKey's value log needs an explicit GC that rewrites surviving values (§1.3); redb (COW) only reuses freed pages once no reader can see them, and its footprint in 1.7 shows what deferred reclamation costs. No source found documents an incremental vacuum for in-place B-trees — SQLite's vacuum is a full rebuild. | — | [atomiccommit.html](https://www.sqlite.org/atomiccommit.html), [fileformat2.html](https://www.sqlite.org/fileformat2.html), [WiscKey](https://www.usenix.org/conference/fast16/technical-sessions/presentation/lu), [redb design doc](https://github.com/cberner/redb/blob/master/docs/design.md) | — | High |

**Implications:**
(a) **Architecture**: both shapes handle bytes→hundreds-of-MB values only via an out-of-line mechanism (overflow chain or blob log); the blob store should be log-structured-with-offset-table or chunked-TOAST-style regardless of the main index architecture, because either way a multi-hundred-MB blob must never be rewritten to update a neighbor.
(b) **Durability**: large values argue for key–value separation (write the blob once, mutate the small index entry in place) — WiscKey's whole premise.
(c) **Snapshot mapping**: blob chains and overflow pages are immutable once committed under COW/LSM, mappable like any committed page; under B-tree+WAL they move on update, so readers need the WAL indirection instead.
(d) **Determinism**: GC/vacuum triggers are timing-dependent; a deterministic engine needs reclamation driven by explicit deterministic events (transaction boundaries), not wall-clock heuristics.

## 8. Snapshots mapped into other processes

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | LMDB is the existence proof: "The entire database is exposed in a memory map, and all data fetches return data directly from the mapped memory"; "It is read-only by default as this provides total immunity to corruption"; multi-process access is native ("supports concurrent read/write access from multiple processes and threads"); an open read-only transaction pins a consistent version of the tree with no locks on data; and "when the memory map is read-only, the database integrity cannot be corrupted by stray pointer writes from application code." The cost is the documented caveat list: lock-file coordination, no fork, no remote filesystems, stale-reader checks, and long-lived readers growing the file. | unlimited readers, 1 writer | [LMDB documentation](https://lmdb.tech/doc/) | current | High |
| 8.2 | The same page states the publication mechanism implicitly: committed data pages are never overwritten (COW), so a committed root page number **is** the snapshot handle; the new root becomes visible by updating the map's metadata, and readers that started earlier keep referencing old pages, which LMDB cannot reuse until they finish. Page-granular, copy-free, consistent — no copy of data occurs at publish time. | — | same | current | High (mechanism), Medium (exact publication ordering — not spelled out in prose) |
| 8.3 | SQLite's WAL achieves cross-process consistency differently: readers agree on an "end mark" in the WAL at transaction start and find pages via the wal-index in **shared memory** — all processes must be on one host and share that memory ("WAL requires all processes to share a small amount of memory"). A reader maps only the database file, never the in-progress WAL; but the *committed* view it sees is assembled from two regions (main file + WAL prefix), so it is not a single immutable mapped range. Read-only WAL access additionally needs the -shm/-wal files to exist or the `immutable` flag. | wal-index ≈ 32 KiB, never synced | [SQLite WAL docs](https://www.sqlite.org/wal.html) | 2010–2026 | High |
| 8.4 | LSM stores publish snapshots via **immutable files**: LevelDB documents `GetSnapshot()` as "consistent read-only views over the entire state"; the implementation reads immutable sorted files (the docs describe block-based immutable table files and version sets). FDB's storage servers likewise read committed immutable log/checkpoint data. An immutable-file snapshot is mappable read-only by construction, but the *view* is the union of many files plus a manifest — publishing one consistent view means publishing a manifest that names a set of files, and those files must be retained (deleted only when no reader holds the view). | — | [LevelDB doc/index.md](https://github.com/google/leveldb/blob/master/doc/index.md) | current | High (API and immutability), Medium (manifest mechanics from prose only) |
| 8.5 | redb documents the same COW pinning primitive as LMDB inside one process — read transactions copy the root and register so "no pages that root references are freed" — but **does not document** exposing that root as a cross-process read-only map; the mechanism generalizes (a committed root + epoch-delayed reclamation is exactly LMDB's model) and is the natural design for Izcal's localStorage snapshot regions in OS shared memory. | savepoint state 64 kB/GB | [redb design doc](https://github.com/cberner/redb/blob/master/docs/design.md) | current | High (mechanism), Medium (cross-process extension is unproven in these sources) |

**Implications:**
(a) **Architecture**: for the "versioned snapshots mapped read-only into other processes" requirement, the evidence favors a design where **committed state is immutable at page granularity and one small handle (root page + generation) is atomically published** — LMDB/redb's COW model, or equivalently a manifest-of-immutable-files LSM model. B-tree+WAL is structurally worst here: the committed view is spread across the base file plus a mutable WAL, and SQLite needs shared-memory coordination to even read consistently.
(b) **Durability**: publish = fsync the new snapshot state, then atomically swap the published handle (one byte or one small slot) — redb's god byte generalized.
(c) **Snapshot mapping**: readers mmap only committed ranges (never the write path), satisfying the CMU paper's condition for safe mmap (§4.4); retention must be epoch-based so a slow reader cannot grow the store unboundedly (LMDB's documented failure mode).
(d) **Determinism**: snapshot publication is a discrete, recordable event — a replayable storage layer can log "publish generation N at logical time T" and reproduce reader-visible history exactly.

## 9. Checksums and verification

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 9.1 | redb checksums everything with "a non-cryptographic Merkle tree with XXH3_128": each page's checksum is stored in its parent (branch pages carry a 16-byte checksum per child), the roots' checksums and a slot checksum live in the commit slots, and "All data is checksumed when written... The docs also state the security limit honestly: because XXH3 is not collision-resistant, an attacker with control over flush order could in theory make a partial commit look complete — hence the optional 2-fsync 2PC mode. | 16-byte (128-bit) checksums per page and per slot | [redb design doc](https://github.com/cberner/redb/blob/master/docs/design.md) | current | High |
| 9.2 | SQLite uses checksums as a *probabilistic second line*, not a primary guarantee: 32-bit checksums on rollback-journal pages guard the single-flush `synchronous=NORMAL` path ("there is a small but finite probability that the checksum might be right even if the data is corrupt"). WAL frames are likewise checksummed so recovery can find the last valid frame — this is documented in the WAL material but was not captured verbatim in this strand's fetch (Medium). SQLite's atomic-commit doc also records the negative result worth keeping: "SQLite does not add any redundancy to the database file for the purpose of detecting corruption" — its main file historically relies on ordering alone. | 32-bit journal checksums | [atomiccommit.html](https://www.sqlite.org/atomiccommit.html) | current | High (Medium for WAL-frame checksum wording) |
| 9.3 | LevelDB documents checksum discipline at block granularity ("leveldb associates checksums with all data it stores"), but defaults to **not verifying on read** (`verify_checksums` false) and `paranoid_checks` off — reliability knobs exposed rather than enforced. RocksDB's block-based table format carries a per-block trailer (compression byte + 4-byte checksum) plus a footer checksum; a "context checksum" feature salts each block's checksum so a block relocated to another offset cannot pass validation (per project documentation summaries; Medium). | 4-byte checksum + 1 type byte per block | [LevelDB doc/index.md](https://github.com/google/leveldb/blob/master/doc/index.md) (High), [RocksDB wiki-derived summaries](https://github.com/facebook/rocksdb/wiki) (Medium) | current | High / Medium |
| 9.4 | Filesystem precedent: Btrfs checksums "data and metadata" with multiple algorithms and runs on-line verification (scrub); the same COW structure that makes checksums cheap (never overwrite → always write checksum next to fresh data) is what makes whole-tree Merkle placement natural (redb). Torn-write detection falls out of per-page checksums: a partially written page fails its checksum and is treated as absent/rolled back rather than replayed. | — | [Btrfs kernel docs](https://docs.kernel.org/filesystems/btrfs.html) | current | High |
| 9.5 | The testing lesson SQLite attaches to this: crash-test VFSs "simulate incomplete sector writes, pages filled with garbage data... and out of order writes", and "any other database system that does not use a similar crash test system likely contains undetected bugs that will lead to database corruption following a system crash or power failure." | — | [atomiccommit.html](https://www.sqlite.org/atomiccommit.html) | current | High |

**Implications:**
(a) **Architecture**: per-page checksums stored in the parent (Merkle-in-the-tree) are the pattern that serves both crash detection and future corruption audits; a checksum strategy must be chosen per architecture (page-tree Merkle vs per-record log checksums).
(b) **Durability policy**: checksums make 1-fsync commits safe against torn writes (detect-and-roll-back), but a 128-bit non-cryptographic hash is not adversarially safe — Izcal's threat model (malicious site data, same-process attacker) should pick the 2-phase variant or a collision-resistant hash for commit slots.
(c) **Snapshot mapping**: checksums in the tree let a *consumer* process verify a mapped snapshot independently of the publisher.
(d) **Determinism**: a simulated disk that corrupts/torn-writes per SQLite's crash-test design makes checksum paths deterministically exercisable.

**Implications:**
(a) **Architecture**: rank by number of asynchronous, timing-dependent subsystems: COW B-tree (allocation + reclamation only) ≤ B-tree+WAL (replay is deterministic, checkpoint timing is not) < LSM (continuous compaction scheduling). If Izcal wants FDB-grade replayability, background work must be driven by logical events, not wall-clock.
(b) **Durability policy**: model the disk as a deterministic simulated device (corrupt unsynced writes on reboot, torn sectors, reordered writes) so durability logic is tested by construction, per SQLite and FDB.
(c) **Snapshot mapping**: publication as a discrete logged event ("generation N visible at logical time T") makes cross-process snapshot history replayable — this also serves debugging of the localStorage snapshot feature.
(d) **Determinism**: require an injectable I/O seam from day one (LevelDB `Env`-style) and forbid wall-clock-driven decisions in the engine core; budget for independent black-box testing anyway (TigerBeetle/Jepsen).

## Summary comparison (evidence-based, recommendation-neutral)

| Axis | LSM (log-structured) | COW B-tree | B-tree + WAL |
|---|---|---|---|
| Point read cost | Multiple levels probed per lookup; Bloom filters cut disk reads ~100x (10 bits/key) but add CPU/memory (§1.6) | One root-to-leaf descent; flat, predictable; zero-copy possible from map (§2.2–2.4) | One root-to-leaf descent; in-place pages, standard caching |
| Write amplification | Batching makes cheap writes possible (O'Neil cost ratio example 1/50), but compaction rewrites data repeatedly; KV-separation exists to fix exactly this (§1.1, 1.3) | Path copying per write + garbage until reclamation; ~4.5x uncompacted footprint in one benchmark before compaction (§2.6) | Each commit writes the log (once, sequentially) + eventual dirty-page rewrite; rollback mode writes data twice (§3.1, 3.3) |
| Space reclamation | Incremental and automatic at compaction; unbounded growth risk under write stalls (§1.5) | Deferred until no reader references freed pages; long-lived snapshots grow the file (LMDB documented caveat, §2.3) | Freelist reuse in place; VACUUM-style full rebuild for deep fragmentation (§7.4) |
| Snapshot mapping | Immutable SST files + manifest; view = set of files, retention-coupled (§8.4) | Best documented model: committed root = snapshot handle; page-granular, copy-free, read-only map immune to corruption (§8.1–8.2) | Weakest: committed view spans base file + WAL; needs shared-memory wal-index coordination (§8.3) |
| Crash recovery time | Replay WAL + possibly scan/validate levels; immutable files limit blast radius | None needed by design — "eliminates the need of any special recovery procedures after a system crash" (§2.2); worst case a checksum-guided root/slot roll-back (§5.3) | Replay log since checkpoint; recovery time scales with log length since last checkpoint (§3.4–3.5) |
| Implementation complexity | High: compaction scheduler, Bloom filters, levels/tiering, write stalls, optional KV separation and value-log GC (§1, 6.1, 6.3) | Moderate: COW page management, epoch reclamation, commit slots; no WAL, no recovery, no compaction (§2.2, 2.4, 5.3) | Moderate-high: WAL, checkpointing, starvation avoidance, multi-DB super-journal, shared-memory reader coordination (§3.2–3.4) |
| Determinism fit | Hardest: continuous background compaction is the largest nondeterministic subsystem (§10.5) | Best: no background rewriter; allocation + reclamation driven at transaction boundaries (§2.4, 10.5) | Good: replay is a deterministic prefix; checkpoint timing must be logically driven (§10.2, 3.5) |

The evidence does not dictate a single choice: the snapshot-mapping requirement and determinism fit favor the COW family's committed-immutable-handle model, large-value handling and write-heavy ingest favor log-structured elements (which all three architectures can adopt for blobs, §7), and every production system in the evidence ends up exposing durability as a policy dial rather than baking it into the structure.
