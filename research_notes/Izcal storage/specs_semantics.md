# Izcal storage: specs and semantics

Compiled 20 October 2026. Primary sources were preferred: the WHATWG Storage, File System, HTML (Web storage, Structured data) standards, the W3C IndexedDB and File API specifications, the W3C Service Workers specification, the WICG Storage Buckets and File System Access drafts — all read directly from the editors' published pages on 19–20 October 2026, with normative sentences quoted in the findings. No third-party project's source code was read (M-1 part 3).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source or prior knowledge, not re-checked.

**Pinning.** WHATWG standards are living documents; the Storage and File System standards self-report "last updated" dates of 19 October 2026, and HTML is read at 20 October 2026. The IndexedDB and File API citations are to the current W3C/TR snapshots of the editors' drafts (the IndexedDB text already contains IndexedDB 3.0 material: `databases()`, `getAllRecords()`, `IDBRecord`). The Storage Buckets draft is a W3C Draft Community Group Report dated 19 December 2023. Service Workers is the w3c.github.io editors' draft at 20 October 2026.

**A structural finding up front.** The old mental model ("origin quota box; localStorage limited to 5 MB; sessionStorage lives two hours") no longer matches the normative text. The WHATWG Storage standard now defines a **shed → shelf → bucket → bottle** hierarchy; the 5 MiB quota is a per-endpoint *recommended* value; and the historic "two-hour" sessionStorage language is **absent** from both HTML §11 and the Storage standard (rows 2.1, 3.3).

## 1. HTML Web Storage (WHATWG HTML §11, Web storage)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Web storage lives in [HTML §11](https://html.spec.whatwg.org/multipage/webstorage.html) as a thin layer over the [Storage standard](https://storage.spec.whatwg.org/). `localStorage` is "designed for storage that spans multiple windows, and lasts beyond the current session"; `sessionStorage` is per-window session-scoped. Both getters are flagged as tracking vectors in the spec's own machinery. | — | [HTML webstorage](https://html.spec.whatwg.org/multipage/webstorage.html) | 2026-10-20 | High |
| 1.2 | The `Storage` interface is exactly: `length`, `key(index)`, `getItem(key)`, `setItem(key, value)`, `removeItem(key)`, `clear()`. `getItem` returns `null` for an absent key; the bracket getter returns `undefined` instead. `setItem` returns early (no event) if the key exists **with the same value**; `removeItem` and `clear` are no-ops when nothing changes. | — | [HTML webstorage](https://html.spec.whatwg.org/multipage/webstorage.html) | 2026-10-20 | High |
| 1.3 | **Key order is not defined.** The spec: "iteration order is not defined and can change upon most mutations", and re-ordering after insertion/removal is done "in an implementation-defined manner". There is no sorted-key requirement. | — | [HTML webstorage](https://html.spec.whatwg.org/multipage/webstorage.html) | 2026-10-20 | High |
| 1.4 | **Cloning rules.** `window.localStorage` returns the `Storage` object for the window's origin's *local* storage area (shared across same-origin windows). For session storage: "After creating a new auxiliary browsing context and document, the session storage is copied over." Session storage is held in the *traversable navigable's* shed, not the user agent's shed, so each top-level session gets its own copy. | — | [HTML webstorage](https://html.spec.whatwg.org/multipage/webstorage.html); [Storage §4.3](https://storage.spec.whatwg.org/#storage-shed) | 2026-10-20 | High |
| 1.5 | **Session lifetime.** The historic "two hours" language is **gone**. The current normative text: "Session storage buckets must be cleared as [traversable navigables] are closed" (Storage §7.1), with a note that on revival ("reopening navigables or continuing after restart") "clearing necessarily involves a more complex set of heuristics". No duration is specified anywhere. | no duration | [Storage §7.1](https://storage.spec.whatwg.org/#storage-pressure) | 2026-10-20 | High |
| 1.6 | **The `storage` event.** Fired via a "broadcast" to *all other* same-origin `Storage` objects — the changing document is excluded ("all `Storage` objects excluding storage"). For `localStorage` all same-origin documents receive it; for `sessionStorage` only documents whose node navigable's traversable navigable is the same as the source's. `key`, `oldValue` (null for a new key), `newValue` (null on removal/clear), `url` ("the serialization of thisDocument's URL"), `storageArea` (the receiving remote `Storage`). Delivery is a "global task on the DOM manipulation task source"; events for non-fully-active documents are ignored until active again. | — | [HTML webstorage](https://html.spec.whatwg.org/multipage/webstorage.html) | 2026-10-20 | High |
| 1.7 | **Quota.** No numeric limit in HTML §11. `setItem` throws `QuotaExceededError` "if value cannot be stored", e.g. "if, e.g., the user has disabled storage for the site, or if the quota has been exceeded". On failure the map-set step is never reached: the change is discarded and no event is broadcast. The per-bottle recommended quota is 5 MiB (row 3.1). | 5 MiB recommended | [HTML webstorage](https://html.spec.whatwg.org/multipage/webstorage.html); [Storage §4.1](https://storage.spec.whatwg.org/#storage-endpoints) | 2026-10-20 | High |
| 1.8 | **UA latitude (HTML's own list).** User agents may: restrict `localStorage` to scripts from the top-level document's domain; "automatically delete stored data after a period of time" (possibly user-configured); allow session storage unrestricted while requiring user authorization for local storage; record third-party origin usage; allow users to share persistent-storage blocklists. Should: present clearing interfaces coherently, "treat persistently stored data as potentially sensitive", and ensure that "when deleting data, it is promptly deleted from the underlying storage". | — | [HTML webstorage](https://html.spec.whatwg.org/multipage/webstorage.html) | 2026-10-20 | High |

**Implications:** Izcal must implement `Storage` as an ordered-map-with-undefined-order abstraction whose ordering is a free policy choice (a deterministic, e.g. insertion-order, choice is allowed and testable). The `storage` event's "other documents only" fan-out is a genuine cross-document notification path that Izcal's process model must route, and the no-self-event rule plus no-op-on-same-value rule are conformance-critical details tests check. The absence of a mandated lifetime means Izcal may define session persistence across restart as policy — but must clear per closed traversable by default.

## 2. IndexedDB (W3C IndexedDB 3.0)

### 2a. Databases, versions, upgrade transactions

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | `IDBFactory.open(name[, version])` returns an `IDBOpenDBRequest`. Steps: "If version is 0 (zero), throw a `TypeError`"; storage key is obtained (failure → `SecurityError`); the "opening a database connection" algorithm runs in parallel. Without a version, an existing database opens unchanged and a new one gets version 1. Opening with a **lower** version than existing fails (`VersionError`); a higher version triggers an upgrade. **There is no options argument on `open()`** — the durability hint is per-transaction (row 2.4). | version 1 for new DBs | [IndexedDB §4.3](https://www.w3.org/TR/IndexedDB/#idbfactory-interface) | 2026-10-20 | High |
| 2.2 | **Upgrade transaction.** Created automatically when "a version greater than the current version is specified"; mode is `versionchange`; script cannot create one manually; it is active inside the `upgradeneeded` handler. "The `upgradeneeded` event isn't fired … until all other connections to the same database are closed"; while the upgrade transaction is live, "attempts to open more connections to the same database are delayed". `blocked` fires on the open request "if other clients still hold a connection … after their `versionchange` events have fired". Object stores and indexes "can't be added or removed" outside it. | — | [IndexedDB §2.7.3](https://www.w3.org/TR/IndexedDB/#upgrade-transaction-construct) | 2026-10-20 | High |
| 2.3 | **Abort of an upgrade transaction** rolls back "any changes made to the database", which "for upgrade transactions … includes changes to the set of object stores and indexes, as well as the change to the version"; a throwing `upgradeneeded` callback aborts. `deleteDatabase` resolves its success event with `null` and can also be `blocked`. `databases()` resolves with a snapshot of `IDBDatabaseInfo {name, version}` objects, skipping version-0 databases. | — | [IndexedDB §5.5](https://www.w3.org/TR/IndexedDB/#abort-a-transaction) | 2026-10-20 | High |
| 2.4 | **Durability.** `IDBDatabase.transaction()` takes `IDBTransactionOptions { durability: "default" | "strict" | "relaxed" }`. `strict`: the transaction may be treated as committed "only after verifying that all outstanding changes have been successfully written to a persistent storage medium". `relaxed`: "as soon as all outstanding changes have been written to the operating system, without subsequent verification". `default`: "the user agent should use its default durability behavior for the storage bucket". The commit algorithm says: "Attempt to write any outstanding changes made by transaction to the database, considering transaction's durability hint"; if writing fails, the transaction aborts (e.g. `QuotaExceededError`, `UnknownError`). Apps are "encouraged" to use `relaxed` for caches and `strict` where data-loss risk outweighs performance/power cost. | — | [IndexedDB §2.7](https://www.w3.org/TR/IndexedDB/#transaction-durability-hint), [§5.4](https://www.w3.org/TR/IndexedDB/#commit-transaction) | 2026-10-20 | High |
| 2.5 | **Commit trigger.** The implementation "must attempt to commit an inactive transaction when all requests placed against the transaction have completed and their returned results handled, no new requests have been placed against the transaction, and the transaction has not been aborted". A transaction is "active" at creation and during dispatch of a request's event; new requests can only be placed while active. "Cleanup Indexed Database transactions" steps deactivate transactions when the invoking task completes. The exact text does not use the phrase "microtask checkpoint"; the trigger is request-completion plus inactivity. | — | [IndexedDB §2.7.1](https://www.w3.org/TR/IndexedDB/#transaction-lifetime-concept) | 2026-10-20 | High |
| 2.6 | **Scheduling.** Read-only transactions start when no earlier transaction with overlapping scope is unfinished; read/write transactions additionally wait for all earlier overlapping transactions. Multiple read-only transactions may run concurrently on overlapping scopes. Modes are exactly `readonly`, `readwrite`, `versionchange` — **no `readwriteflush` or `cleanup` modes exist in this edition**. | — | [IndexedDB §2.7.2](https://www.w3.org/TR/IndexedDB/#transaction-scheduling-concept) | 2026-10-20 | High |
| 2.7 | **Connection close.** `close()` makes the connection close-pending (no new transactions) and waits for started transactions; closing unblocks queued upgrades/deletes. The `close` event "only fires if the connection closes abnormally"; an explicit `close()` fires nothing. A user agent may close a connection "in exceptional circumstances, for example due to loss of access to the file system, a permission change, or clearing of the storage key's storage"; a forced close aborts all its transactions with `AbortError`. | — | [IndexedDB §5.2](https://www.w3.org/TR/IndexedDB/#close-a-database-connection) | 2026-10-20 | High |

### 2b. Keys, key paths, generators, values, stores, indexes

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.8 | **Valid keys** have one of five types: *number* (any ECMAScript Number "except NaN. This includes Infinity and -Infinity"), *date* (a Date whose `[[DateValue]]` is not NaN; stored as its time value), *string*, *binary* (ArrayBuffer or a view such as Uint8Array), *array* (every item defined, itself a valid key, and not directly or indirectly containing itself — a cycle rule, not a numeric depth limit). Booleans, null, undefined, RegExp and everything else fail conversion (`DataError`). | 5 key types | [IndexedDB §2.4](https://www.w3.org/TR/IndexedDB/#keys) | 2026-10-20 | High |
| 2.9 | **Key ordering** is a total order: **array > binary > string > date > number** (the compare steps return 1/−1 exactly in that precedence). Binary members compare "as unsigned byte values (in the range 0 to 255 inclusive)", byte-wise. Arrays compare element-wise recursively, then by length. "Negative infinity is the lowest possible value"; "there is no highest possible key value" (a longer array is always higher). | array > binary > string > date > number | [IndexedDB §2.4](https://www.w3.org/TR/IndexedDB/#key-order) | 2026-10-20 | High |
| 2.10 | **Key paths**: an empty string; an identifier (ECMAScript IdentifierName); two or more identifiers separated by U+002E; or a non-empty list of such strings. "Spaces are not allowed within a key path." Evaluating a key path against a value can address Blob (`size`, `type`), File (`name`, `lastModified`), Array (`length`), String (`length`). | — | [IndexedDB §2.5](https://www.w3.org/TR/IndexedDB/#key-path-construct) | 2026-10-20 | High |
| 2.11 | **Key generators.** `generate a key` returns the current number then increments; "if key is greater than 2⁵³ (9007199254740992), then return failure". `possibly update the key generator` considers only number keys: floored and clamped to 2⁵³; "if value is greater than or equal to generator's current number, then set generator's current number to value + 1" — so explicit numeric keys advance the generator; date/array/binary/string keys have no effect. "If an insertion fails due to constraint violations or IO error, the key generator is not updated"; aborted transactions roll generator increases back. Exhaustion past 2⁵³ throws `ConstraintError`. | 2⁵³ ceiling | [IndexedDB §2.11](https://www.w3.org/TR/IndexedDB/#key-generator-construct) | 2026-10-20 | High |
| 2.12 | **Values** are any structured-cloneable value: `put`/`add` take "a clone of value in targetRealm during transaction" (structured serialize/deserialize, row 8). In-line keys: `createObjectStore(name, {keyPath, autoIncrement})` — `keyPath` must be null or a valid key path else `SyntaxError`; "if autoIncrement is true and keyPath is an empty string or any sequence", throw `InvalidAccessError`. With in-line keys and no key argument, the key is extracted via the key path; if extraction fails but the store has a generator, a key is generated and injected. Out-of-line stores without a generator require an explicit key (`DataError`); giving a key argument to an in-line-key store throws `DataError`. | — | [IndexedDB §4.8](https://www.w3.org/TR/IndexedDB/#idbobjectstore) | 2026-10-20 | High |
| 2.13 | **Index parameters**: `createIndex(name, keyPath, {unique = false, multiEntry = false})` — upgrade-transaction only; duplicate name → `ConstraintError`; invalid key path → `SyntaxError`; "if keyPath is a sequence and multiEntry is true, throw `InvalidAccessError`". No `locale` option appears in this edition. Creating a unique index over data that already violates it does not throw at the call: the transaction "will be aborted when the index is created and the constraint fails". | — | [IndexedDB §4.9](https://www.w3.org/TR/IndexedDB/#idbindex) | 2026-10-20 | High |
| 2.14 | **Index updating on store.** In "store a record into an object store": an existing record with the same key is removed first; then for each index referencing the store, "let index key be the result of extracting a key from a value using a key path"; **"If index key is an exception, or invalid, or failure, take no further actions for index, and continue"** — the record is stored *without* an index entry and "an exception thrown in this step is not rethrown". For `multiEntry`, an array key stores one record per subkey (nested arrays are used directly, not flattened); an empty array adds no records. A unique-constraint violation fails the operation with `ConstraintError` (which, being a request failure, aborts the transaction unless handled — note the abort semantics of row 2.3 apply to *request* errors only when the script does not handle them; uncaught errors abort). Deletion removes the record and its index records. | — | [IndexedDB §6.1](https://www.w3.org/TR/IndexedDB/#store-a-record-into-an-object-store) | 2026-10-20 | High (skip-on-failure verbatim; request-abort nuance Medium) |
| 2.15 | **Cursors.** Records are "sorted in ascending key order"; for an index source, "secondarily sorted in ascending value order". Directions: `next` (key ≥ given key, with primary-key tie-breaking on indexes), `prev` (mirror), `nextunique` (no position/primary-key conditions — duplicate index keys are skipped entirely), `prevunique` (lands on the earliest record sharing the key; note: "Iterating with 'prevunique' visits the same records that 'nextunique' visits, but in reverse order"). `advance(count)` defaults count to 1; range membership is checked against the cursor's range. When exhausted, cursor key becomes undefined and the request resolves with null. | 4 directions | [IndexedDB §6.7](https://www.w3.org/TR/IndexedDB/#iterate-a-cursor) | 2026-10-20 | High |
| 2.16 | **IndexedDB 3.0 additions present in this edition**: `IDBFactory.databases()`; `IDBTransaction.commit()` and `abort()` in the IDL (explicit early commit); `getAllRecords()` and the `IDBRecord {key, primaryKey}` shape with `IDBGetAllOptions` (noted as supported in Chrome/Edge 141); batch retrieval with count defaulting to infinity and unique-variant dedupe by comparing adjacent keys. | — | [IndexedDB §4](https://www.w3.org/TR/IndexedDB/) | 2026-10-20 | High (IDL/method presence); Medium (`commit()` algorithmic detail not re-read) |
| 2.17 | **Defined exceptions** (§3 table): `VersionError`, `NotFoundError`, `ConstraintError`, `DataError`, `InvalidAccessError`, `InvalidStateError`, `ReadOnlyError`, `TransactionInactiveError`, `SyntaxError`, `QuotaExceededError`, `UnknownError`, `AbortError`, `SecurityError` — each with a one-line condition in the spec's exceptions table. | — | [IndexedDB §3](https://www.w3.org/TR/IndexedDB/#exceptions) | 2026-10-20 | High (list read; per-name conditions read in part) |
| 2.18 | **Persistence latitude.** Privacy §8.1: user agents "may automatically delete stored data after a period of time", with the warning that "this also puts the user's data at risk". §8.3: agents "should treat persistently stored data as potentially sensitive" and "should ensure that when deleting data, it is promptly deleted from the underlying storage". §9.3 stresses that "strictly following the storage key partitioning model … is important for user security". §9.2 notes shared-host authors "all share one set of databases" with no pathname restriction — a same-origin (not per-user) scoping model. | — | [IndexedDB §8–9](https://www.w3.org/TR/IndexedDB/#privacy) | 2026-10-20 | High |

**Implications:** IndexedDB is the largest normative surface in web storage: Izcal must implement a write-ahead transaction engine with total key ordering (array > binary > string > date > number), generator bookkeeping with the exact 2⁵³ rules, silent index-entry skipping on key-path failure, and the durability tri-state whose `strict`/`relaxed` distinction maps directly onto an fsync-or-don't policy at commit. The commit trigger ("all requests completed and handled, no new requests") means Izcal's scheduler can auto-commit at a well-defined point without event-loop coupling. Partitioning by storage key is a security requirement the spec states explicitly, not a nice-to-have.

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Registered endpoints** (§4.1 table): `caches` «"local"» quota null; `indexedDB` «"local"» null; `localStorage` «"local"» 5 × 2²⁰; `serviceWorkerRegistrations` «"local"» null; `sessionStorage` «"session"» 5 × 2²⁰. | 3.3 | **Hierarchy** (§4.3–4.7): a *shed* is "a map of storage keys to storage shelves" — the UA's shed holds all local storage data; each traversable navigable's shed holds its session storage. A *shelf* exists per storage key and holds a bucket map whose only current key is `default`. A *bucket* holds a bottle map per endpoint; a *local* bucket has a **mode** — "'best-effort' or 'persistent' … initially 'best-effort'" — a *session* bucket has none. A *bottle* holds the endpoint's actual data plus a proxy map and quota. The old "box" concept is gone. | — | [Storage §4.3–4.7](https://storage.spec.whatwg.org/#storage-shed) | 2026-10-20 | High |
| 3.4 | **Pressure and eviction** (§7, §7.1): "Whenever a storage bucket is cleared by the user agent, it must be cleared in its entirety"; UAs "should avoid clearing storage buckets while script that is able to access them is running, unless instructed otherwise by the user". Under pressure, a UA "should clear network state and local storage buckets whose mode is 'best-effort', ideally prioritizing removal in a manner that least impacts the user"; if pressure continues, it "should inform the user and offer a way to clear the remaining local storage buckets". "Storage pressure" is not formally defined; eviction ordering is UA latitude. | — | [Storage §7](https://storage.spec.whatwg.org/#management) | 2026-10-20 | High |
| 3.5 | **Persistence permission** (§5): the powerful feature name is `persistent-storage`. When granted, "the user agent cannot clear storage marked as persistent without involvement from the origin or user"; if the permission is later not granted, the shelf's default bucket mode resets to `best-effort`. `persist()` steps: obtain a local storage shelf (`TypeError` on failure); in parallel request `persistent-storage`; if not persisted and granted, "set bucket's mode to 'persistent'"; a note encourages UAs "to not let the user answer this question twice for the same origin around the same time". No clause permits always-true/always-false outright, but permission *policy* is UA-defined in the Permissions spec. | — | [Storage §5](https://storage.spec.whatwg.org/#persistence), [§8](https://storage.spec.whatwg.org/#api) | 2026-10-20 | High |
| 3.6 | **Usage and quota** (§6): usage and quota are "implementation-defined" rough, conservative estimates; the quota "should be less than the total storage space on the device" and **"must not be a function of the available storage space on the device"**. Flagged as a tracking vector: "Directly or indirectly revealing available storage space can lead to fingerprinting and leaking information outside the scope of the origin involved." | 3.7 | **`StorageManager` API surface** (§8): exactly `persisted()`, `persist()` (Window-only), `estimate()`; `StorageEstimate { usage, quota }` — **no `usageDetails` member exists**. UAs may use "deduplication, compression, and other techniques" that make the byte counts approximate. `getDirectory()` is not defined here; it lives in the File System standard (row 7.2). `estimate()` resolves with the shelf's usage and quota. | — | [Storage §8](https://storage.spec.whatwg.org/#dom-storagemanager-estimate) | 2026-10-20 | High |
| 3.8 | **UI guidelines** (§7.2): UAs "should offer users the ability to clear network state and storage for individual websites", "should not distinguish between network state and storage in their user interface", while credentials and permissions "are best separated". | — | [Storage §7.2](https://storage.spec.whatwg.org/#ui-guidelines) | 2026-10-20 | High |

**Implications:** Izcal's storage layer should be built directly on the shed/shelf/bucket/bottle model — it is the spec's own architecture, it cleanly separates quota accounting (shelf) from endpoint data (bottle), and it gives the future per-bucket work (Storage Buckets) a home. "Must not be a function of available device space" forbids naive free-disk-space quotas; Izcal must pick a fixed-per-shelf or heuristics-based quota and accept the fingerprinting cost of revealing it. Eviction priority ("least impacts the user") is wholly Izcal's policy to define.

**Implications:** Buckets are the direction of travel but not yet normative; Izcal can design its internal storage layout bucket-first (the Storage standard's `default` bucket keeps today's behavior) so named buckets become a natural extension rather than a rewrite. The draft's unresolved eviction/deletion semantics are exactly the kind of under-specified area where a first-principles engine can define and publish a better policy.

## 5. Cache API (Service Workers §5)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|

**Implications:** The Cache API is author-managed storage wearing an HTTP-shaped API; Izcal must keep it strictly partitioned from its HTTP cache (row 6 of the networking strands) and must preserve opaque responses byte-opaquely while enforcing CORP at retrieval. The `put` full-clone semantics is an explicit invitation to stream to disk — a natural fit for Izcal's storage layer.

## 7. File System / OPFS (WHATWG File System standard + WICG File System Access)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **Handles**: `FileSystemHandle` has `kind` (`"file"`/`"directory"`) from the locator, `name` ("the last path component of handle's locator's path"), and `isSameEntry` (true iff locators are "the same locator as" each other). The WHATWG standard defines internal "query access"/"request access" algorithm hooks (defaulting to `denied`) that dependent specs implement; implementations of only this standard "do not need to bother" implementing them. Handle deserialization throws `DataCloneError` unless the serialized origin is same origin with the new context. | — | [File System §4](https://fs.spec.whatwg.org/#filesystemhandle) | 2026-10-19 | High |
| 7.2 | **Origin-private (bucket) file system**: `navigator.storage.getDirectory()` "makes it possible for websites to get access to a file system directory without having to first prompt the user". A handle "is in a bucket file system" when its path's first item is the empty string. The standard ties the bucket FS to Storage-standard buckets and quota; physical location is not pinned ("the actual physical location of the corresponding file system entry is implementation-defined"). Note the WHATWG page uses the term "bucket file system"; the marketing term "origin private file system" (OPFS) is used in prose elsewhere. | — | [File System §9](https://fs.spec.whatwg.org/#origin-private-file-system) | 2026-10-19 | High (API/anchor semantics); Medium (exact "origin-private" partitioning sentence not located on page — see Open questions) |
| 7.3 | **Locking model**: a file entry's `lock` is exclusively "`open`", "`taken-exclusive`", or "`taken-shared`", plus a shared-lock count. Exclusive succeeds only from `open`; shared succeeds from `open` or increments when already `taken-shared`; releasing decrements to zero → `open`. WritableFileStreams "requires a shared lock"; SyncAccessHandles "requires an exclusive one". Lock failure → `NoModificationAllowedError`; sync handles outside the bucket FS → `InvalidStateError`; calling methods on a closed handle → `InvalidStateError`. | — | [File System §3](https://fs.spec.whatwg.org/#locks) | 2026-10-19 | High |
| 7.4 | **`createSyncAccessHandle` is worker-only and bucket-FS-only**: the `FileSystemSyncAccessHandle` interface is `[Exposed=DedicatedWorker, SecureContext]`, and "this method will only succeed when the fileHandle is in a bucket file system". | — | [File System](https://fs.spec.whatwg.org/#filesystemsyncaccesshandle) | 2026-10-19 | High |
| 7.5 | **Writable model**: "Any changes made through stream won't be reflected in the file entry … until the stream has been closed"; the spec's own note: "this is typically implemented by writing data to a temporary file, and only replacing the file entry … with the temporary file when the writable filestream is closed" — close "atomically updates the contents of the file on disk". `keepExistingData: true` copies existing contents into the buffer first. `write()` supports `write`/`seek`/`truncate`; writing past EOF pads NUL bytes; quota failure → `QuotaExceededError` leaving the buffer unmodified. Close runs "implementation-defined malware scans and safe browsing checks" (failure → `AbortError`). The buffer "can get arbitrarily large, so it is expected that implementations will not keep this in memory, but instead use a temporary file". Multiple writables can coexist (shared locks re-entrant), which blocks sync handles until close. `getFile()` returns a snapshot; if the file later changes, "the returned File object will likely be no longer readable". | — | [File System](https://fs.spec.whatwg.org/#createwritable) | 2026-10-19 | High |
| 7.6 | **Picker grant model** (WICG File System Access): all three pickers verify "if global does not have transient activation, then throw a `SecurityError`" (opaque origins and non-same-origin iframes also `SecurityError`). Well-known directories: `desktop, documents, downloads, music, pictures, videos` with implementation-defined paths; UA "remembers the last directory a file or directory was picked from" if no `startIn`. Post-picker: "the fact that the user picked the specific files … should be treated by the user agent as the user intending to grant read access" (readwrite for save). `requestPermission()` also needs user activation. | 16 well-known-dir map entries minimum | [File System Access §3.1–3.2](https://wicg.github.io/file-system-access/#api-showopenfilepicker) | 2026-10-20 | High |
| 7.7 | **Grant persistence is UA latitude**: a handle "retrieved from IndexedDB is also likely to return `prompt`"; UAs "are encouraged" to "automatically expire permission grants except for particularly well trusted origins"; clearing browsing data "is expected to revoke all permissions". Bucket-FS entries always have permission state `granted`. Sensitive-directory restriction (browser dirs, `C:\Windows`, `/dev`, `/sys`, `/proc`, whole home dir, …) is "encouraged", not required. Picker prompt appearance "is implementation-defined". File System Access writes are not subject to storage quota (§6.3), with mitigation latitude. No encryption anywhere in the spec. | — | [File System Access §5–6](https://wicg.github.io/file-system-access/#permissions) | 2026-10-20 | High |

**Implications:** The bucket file system gives Izcal a spec-sanctioned place to build its best storage: a private, per-origin, lock-disciplined tree with atomic close semantics — the swap-file-on-close rule is a *typical* implementation hint, and Izcal can implement transactional copy-on-write natively. The lock tri-state (exclusive/shared with counts) is small enough to test exhaustively. Grant persistence and sensitive-directory policy are Izcal's to set.

## Open questions

1. **Partitioned storage keys.** Storage §4.2 says the origin-only key "is expected to change; see Client-Side Storage Partitioning". Which partitioned-key text is current (the Privacy CG's proposal vs. text folded into the Storage standard) was not verified — Izcal's storage layer should be key-abstracted so a third tuple element is a one-line change. (Medium)
2. **`IDBTransaction.commit()` semantics.** Confirmed present in the IDL (row 2.16), but its algorithmic text (what happens on commit() with pending requests) was not read. (Medium)
3. **"blocking"/"closed" events on databases.** `blocked` on `IDBOpenDBRequest` is confirmed; any "closed" event on `IDBDatabase` beyond the connection `close` event (an IndexedDB 4.0 idea) was not found in this edition — likely absent, unverified. (Low)
4. **OPFS "origin-private" sentence.** The File System standard calls it the bucket file system and ties it to storage buckets/quota; the explicit "not enumerable by the user" phrasing lives (if anywhere) in the WICG File System Access spec or explainer prose and was not located. Partitioning scope (origin vs storage key) for OPFS needs one more targeted read. (Medium)
5. **IndexedDB TR publication date.** The exact snapshot date of the consulted TR page was not recorded; content identity (contains `getAllRecords`, Chrome/Edge 141) pins it to a late-2026 edition. (Low)
6. **`readwriteflush`/`cleanup`.** Confirmed absent from the W3C edition (row 2.6); whether any living spec still defines them was not checked — treat as non-normative legacy. (Low)
7. **Clear-Site-Data `storage:bucket-name`** integration status (draft-only per row 4.5) — track if Izcal implements Clear-Site-Data. (Low)
