# Izcal storage: security, privacy and robustness

Compiled 20 October 2026. Primary sources were preferred (specifications, Privacy CG documents, vendor security blogs, paper PDFs, the SQLite documentation, forensic literature, issue-tracker titles and discussion text).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known fact not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no engine source code was read for this note. No code files, headers, commits, diffs, code-review pages or source browsers of Chromium, Gecko, WebKit or any library were opened. Read as prose only: the Privacy CG storage-partitioning README (fetched through the GitHub API as a document), the Chromium Site Isolation page, Chromium issue **titles** surfaced by search, and the README (documentation prose) of a third-party decryption research tool. Papers were read as papers (the ALFS paper PDF was downloaded and its text extracted locally). Where only source code would state a value (storage-service sandbox rules, fd-passing policy), it is listed under "Open questions" for a black-box measurement.

**Method notes**
- The shared web-search budget was tight: 6 searches succeeded this session (2 more were rejected with rate-limit errors). Everything else was fetched from known primary URLs. Several URL guesses 404'd (developer.chrome.com storage-partitioning, privacysandbox bounce-tracking page, xsleaks.dev nesting-browsers page, USENIX paper pages for ALFS and BOB, Mozilla Support pages, The Register article): rows that would have relied on them are graded Medium or Low or moved to "Open questions".

| 1.9 | The SAA spec itself concedes the criticism: the API "comes with a risk of abuse by third parties for tracking purposes"; silent grants/denies (allowed to avoid prompt fatigue) "weakens the privacy guarantees of this proposal" by an implementer-chosen amount; denied requests consume user activation to block re-prompting. | — | [Storage Access API spec, §6 Privacy Considerations](https://privacycg.github.io/storage-access/) | fetched 2026-10-20 | High |

**Implications:** Any state Izcal exposes to script is a tracking oracle unless its key includes the top-level site *and* its observability is timing-insulated. Izcal should treat "which storage exists, and how fast can you probe it" as part of the threat model from day one — evercookie's 17 vectors are just the enumeration of web-exposed state, and every later partitioning scheme is an amendment to that list, not a replacement for auditing it. Heuristic-based escape hatches (SAA) are a standing tracking risk: they re-create unpartitioned state on the browser's word that a relationship is legitimate, and their silent-grant paths are explicitly weaker than prompting.

**Implications:** Partitioning is a keying decision Izcal must make once, in the storage broker, and apply to *every* state class in the README's list — not just the APIs labelled "storage". Popups are a known soft spot for partitioning and need their own analysis.

**Implications:** For Izcal, "storage bytes never map into the wrong origin's process" must be enforced twice: at the IPC boundary (the broker only ever returns bytes for origins the caller's process is allowed to render) and at data placement (a process hosts one site's documents only). Given 5–15 exploitable renderer bugs per milestone in a single engine's history, the storage broker must assume every renderer is hostile and validate every request's origin against process capability, not against renderer-supplied origin strings. Private mode needs a design answer at the storage layer (separate ephemeral volume, deleted on session end) rather than hoping file deletion is clean.

| 4.6 | **Threat-model mapping (analysis, not a source claim):** OS-level full-disk encryption answers device theft only; profile-level encryption with a key in the OS user key store (DPAPI/Keychain) answers other local users and, partially, malware running *as a different user*; per-profile or per-container keys limit blast radius of one profile's compromise; nothing at this layer answers malware running as the user, because ABE's own failure (row 4.3) shows any in-context key use is reachable by the attacker. | — | Synthesis of 4.1–4.5 | 2026 | Medium |

**Implications:** At-rest encryption for Izcal's storage answers a strictly weaker adversary than the renderer-compromise model of section 3: its real target is *other local principals* (theft, other users, offline image of the disk), and its ceiling is malware already running as the user. Chrome's ABE is the instructive failure: it tried to stretch the boundary to infostealers using a *path*-based trust check, and fell to injection into the trusted process — a lesson for Izcal's broker (section 9). Izcal should use per-profile keys unwrapped from the OS key store, document honestly that user-context malware is out of scope, and keep the unlock path free of identity checks that can be spoofed from inside the browser's own process.

## 5. Secure deletion and data clearing

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | Forensic literature consistently recovers "deleted" browser data: deleted records remain in database files; private and portable modes leave Registry/Prefetch traces (row 3.6); the 2024 survey treats cache, cookies, history and local storage as recoverable artifact sources across modes. | — | Row 3.6 sources | 2013; 2024 | Medium |
| 5.2 | SQLite WAL mode keeps old page images in the main database and appends changes to a WAL file; a commit "can happen without ever writing to the original database". | 5.3 | On flash storage, overwrite-in-place is not guaranteed: wear leveling and remapping mean logical deletion rarely erases the physical cell; the standard reference (NIST SP 800-88 media sanitization; Wei et al., FAST 2011 on SSD erasure) argues only crypto-erase or full-volume sanitization is reliable. Not re-checked this session. | — | NIST SP 800-88; Wei et al. FAST'11 (recollection) | 2006; 2011 | Low |
| 5.4 | What browsers promise operationally: Chrome's "Clear cookies and site data when you close all windows" shrinks the storage quota to about 300 MB; persistent (non-best-effort) storage "isn't auto-cleared; the user must remove it manually"; Chrome's quota accounting drops Incognito origins to ~5% of disk. **Implications:** "Clear site data" in Izcal should be specified as a *durability and remnant* contract, not a file-unlink call: checkpoint or vacuum after clearing, rotate the WAL, and for private mode prefer an encrypted ephemeral volume whose key is destroyed (crypto-erase) — the only reliable erasure on wear-leveled flash. Anything less should be documented as "unlinked, not unrecoverable".

## 6. Crash consistency and corruption

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | SQLite's WAL design is the reference durability trade-off: WAL "uses many fewer fsync() operations and is thus less vulnerable to problems on systems where the fsync() system call is broken"; writes are "sequential" and once per transaction versus twice for rollback journal. `synchronous=FULL` syncs the WAL per commit; NORMAL omits it, so "transactions are no longer durable and might rollback following a power failure or hard reset". | 6.2 | ALFS (OSDI **2014**, Pillai et al.): ALICE analysed 11 applications' update protocols — key-value stores **LevelDB, GDBM, LMDB**; relational **SQLite, PostgreSQL, HSQLDB**; Git, Mercurial; HDFS, ZooKeeper; VMware — and found **60 crash vulnerabilities**, "several … with severe consequences such as data loss or application unavailability"; "roughly half" manifest on current ext3/ext4/btrfs. 7/11 applications misbehave when syscall ordering is not persisted, 10/11 expect atomicity of filesystem updates, 7/11 fail to meet expected durability (often directory operations not flushed). ext4's delayed-allocation introduction "broke several" applications. | 11 apps; 60 vulnerabilities; 7/11, 10/11, 7/11 | [All File Systems Are Not Created Equal (PDF)](http://research.cs.wisc.edu/adsl/Publications/joint/alice-osdi14.pdf) | 2014 | High |

| 6.5 | The brief's named test tools "TornPage" and "PowerCut" do not appear in the ALFS OSDI paper text; if they are from the journal version or other papers, that is unverified this session. | — | [ALFS PDF text](http://research.cs.wisc.edu/adsl/Publications/joint/alice-osdi14.pdf) | 2014 | Low |
| 6.6 | Wider crash-consistency context from the same research group (listed on its publications page, titles only): CCFS (FAST'17), "Optimistic Crash Consistency" (SOSP'13), CACM 2015 "Crash Consistency", "Fault-Tolerance, Fast and Slow" (OSDI'18). | — | [ADSL publications page](https://research.cs.wisc.edu/adsl/Publications/) | fetched 2026-10-20 | Medium |

**Implications:** A browser storage engine is exactly the class of application ALFS shows gets crash consistency wrong (LevelDB and SQLite are both in its study set), on consumer filesystems where ordering and atomicity assumptions routinely fail. Izcal should design its on-disk format around an explicit, *verified* persistence model — append-only log + periodic checkpoint, sync discipline stated per operation — and test it with a crash-explorer-style harness under simulated torn writes and reordering, not rely on the filesystem's reputation. Corruption of one origin's store must be containable: per-origin or per-bucket files so one torn write cannot take down the whole profile.

## 7. Quota exhaustion as DoS

| 7.1 | Quota shapes, per web.dev's survey: Chrome allows the browser up to **80% of total disk** and an origin up to **60% of total disk**; Incognito ~**5%**; with "clear on close" enabled, ~**300 MB**. | 7.2 | Writes can still fail at quota ("You must catch over-quota errors"; `QuotaExceededError` DOMException from IndexedDB/Cache API), and "in some cases the reported quota may exceed real available storage" — so quota enforcement is approximate and per-write. Eviction under pressure is LRU by origin (Chromium, Firefox). | — | Same | fetched 2026-10-20 | High |
| 7.3 | `navigator.storage.persist()` exempts data from best-effort eviction; "Persistent storage isn't auto-cleared; the user must remove it manually". **Implications:** Izcal's quota model needs three properties: per-site keys (so one site cannot fill the disk for others), an eviction order that is not attacker-steerable (see section 8), and a persist() analogue that is rare, revocable, and surfaced to the user — otherwise "persistent" storage becomes a free DoS reservation. The Safari prompt-and-grow model is a defensible baseline for exceeding a generous default.

| # | Finding | Numbers | Source | Date | Conf. |

| 9.1 | The general rule Chromium's own docs state for sibling surfaces: renderer-supplied data must be treated as hostile in the privileged process, and the privileged side "can detect and terminate a misbehaving renderer process" — containment, not trust. | — | [Chromium Site Isolation](https://www.chromium.org/Home/chromium-security/site-isolation/) | fetched 2026-10-20 | High |

**Implications:** Izcal's storage broker should hold **capabilities to per-origin/per-bucket files**, never resolve attacker-influenced paths, and make every renderer request carry an unforgeable origin grant checked against the connection, not the message. All untrusted-byte parsing (log replay, quota metadata) happens in the broker with memory-safe tooling plus explicit format validation; "trusted process path" style checks are disallowed by policy.
