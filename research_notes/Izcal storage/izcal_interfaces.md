## 2. What the storage spec must HONOUR (interface contracts)

### 2.1 The localStorage snapshot protocol (DM-D11)

[DM 6.13, verbatim]: "when a document of a storage key first touches `localStorage`, the storage service maps a **read-only snapshot** of the key's area into the renderer (shared memory, versioned); reads are local; writes apply to a local overlay at once, so a script reads its own writes, and are sent asynchronously to the storage service, which orders all writers of the key (documents of one origin can live in two processes after an FP-D3 split) with **last-writer-wins per key in its sequence order**. An overlay entry is retired only when the snapshot version that contains its acknowledgment is installed, so a value never reverts. A new version is installed only at a task boundary, as a recorded input (6.7's register); other contexts receive `storage` events when it lands. The first touch waits for the snapshot (a recorded blocking point, like sync XHR), but **the snapshot is requested at navigation commit** for documents whose key has a non-empty area, so the wait is usually zero. **Quota is enforced by the storage service**; the renderer's check against the overlay is advisory and only decides when to throw `QuotaExceededError` early."

Sub-contracts the storage spec must satisfy:

- read-only, versioned, shared-memory snapshot mapped into renderers; writes asynchronous; the service is the sole ordering point for all writers of a key; last-writer-wins per key in sequence order; version-acknowledged overlay retirement (no value reverts); installs at task boundaries only, as recorded B1 inputs; `storage` events on install; quota enforced service-side. [DM 6.13]
- The snapshot is requested at navigation commit for keys with a non-empty area. [DM 6.13]
- [DM 9.4 DM-D11 options]: "(a) read-only snapshot plus local overlay, async writes, events through the broker; (b) synchronous IPC per access \| **(a)**: removes `localStorage` from the sync-IPC allowlist, as NW-D10 did for cookies \| … \| Web Storage WPT or NW-D10-style ordering cases fail under (a)". Reversal trigger: "Web Storage WPT or NW-D10-style ordering cases fail under (a) and cannot be fixed". [DM 6.19 localStorage row] states the same trigger.
- [DM 9.5, Stage 1 4.1 row]: "Remove `localStorage` reads from the synchronous-IPC allowlist once DM-D11's cases pass; sync XHR stays, as a blocked scheduler state."
- `sessionStorage` is **not** the storage service's: [DM 6.13] "`sessionStorage` is per top-level traversable and cloned on the navigations HTML names, **kept in the broker as opaque bytes per traversable**." (See 5.5.)
- The pattern's precedent is NW-D10's cookie view region: [NW 6.9] a "producer-writable, consumer-read-only shared memory" handle (memfd sealed `F_SEAL_FUTURE_WRITE` on Linux; section duplicated without `FILE_MAP_WRITE` on Windows; read-only Mach memory entry on macOS), sequence-lock reads, no double fetch (IPC-R7), version-ordered visibility with responses, local-overlay read-your-writes with async writes. [DM 9.5] and [NW 9.5] both amend Stage 1 4.1's allowlist on this pattern. | High

### 2.2 `hg-clone-wire` opaque bytes and the forever decoder (DM-D12)

[DM 6.11]: "`hg-clone-wire` defines one versioned, little-endian, length-prefixed record format for every serialized value that leaves an agent: … `history.state` and navigation API state (stored by the broker as opaque bytes), **IndexedDB values (stored by the storage service as opaque bytes)**, and `structuredClone()` itself. … **Stored values outlive releases**, so the decoder reads every published version of the format forever, and **a corpus of values written by each release is a CI fixture** (DM-12)."

Obligation on storage: IndexedDB values are stored and returned as bytes; the storage spec must never encode, decode, migrate or interpret them, and must keep them byte-stable across releases so that the forever-backwards-compatible decoder can read every stored version. [DM 6.11] "Its decoder is the only parser of the format (G95), uses checked arithmetic on every size (JS G18's rule), has a Kani harness per record kind … and is fuzzed (DM-12)." | High

### 2.3 Service-worker registration storage and placement (DM-D8)

- Registrations keyed (storage key, scope), stored by the storage service; job queue and lifetime in the broker's `hg-agents`; fetch routing in the partition service; `InstallEvent.addRoutes` static routes (at most 1,024 conditions and depth 10) allocated to the partition service by DM 9.5's NW amendment. [DM 6.10]
- [NW 6.7]: "it looks up the registration in the client's storage key" — the partition service reads registrations; the storage service holds them.
- Worker placement: [DM 6.8 DM-D8]: "a shared or service worker runs in the renderer of its (origin, container) key. Among that key's processes it prefers one that already holds documents of the worker's **storage key** (a third-party worker partitioned under top-level site A goes where A-partition documents of that origin already are), and otherwise starts a new one, **so no partition's data enters a process only because a worker was placed there**." The storage spec's snapshot-mapping and quota behaviour must respect this: a partition's storage data reaches a process only through documents of that partition. | High

### 2.4 Partition keys come from broker-minted capabilities (G99)

[DM 6.17 G99]: "Every DOM-side object that touches state shared across documents (`Storage`, `BroadcastChannel`, `SharedWorker`, service-worker registrations, Web Locks, Blob URLs) takes its partition key from the broker-minted capability, **never computes it in the renderer** \| Partition keys cannot be forged by a compromised renderer ([SR 9.3][SR], [NA 6.2][NA]); partitions already mapped into a process remain I-1's residual risk (6.16)." The storage spec's API must take the partition key from the capability the broker minted, never from renderer-supplied data. [DM 6.16 residual-risk table]: "G99 makes keys unforgeable; it does not stop a compromised renderer from reading partitions already mapped into it, which is I-1's accepted residual risk." | High

### 2.5 FP-1 and the footprint model's storage line

[FP 8.2 FP-1 row]: "Baseline browser, idle, no tab content: broker ≤ 20, shell renderer ≤ 14, compositor GPU service CPU side ≤ 12, the shell's device-less content GPU process ≤ 2, network line ≤ 8 (system service ≤ 4 and spare ≤ 1.5 at idle; the default container service ≤ 2 from the first navigation), **storage ≤ 4**, crash handler ≤ 2, Linux spawner ≤ 1 MiB†" — total "≤ 64 MiB†", all three device classes. [FP 6.1 model term B] lists "storage service" among baseline services with levers "Lazy start, shared image, small allocator, exit when unused". [RN2]: the FP-1 sum "storage 4" appears in the reconciliation's arithmetic ("**Breaks as written; holds with OD-5** (3.5 MiB left)"). FP model terms the storage spec must use when stating its own numbers: charged memory per OS (FP 6.2), canonical touched and committed bytes, the ledger categories, and † marking of first-principles thresholds (FP 8 preamble). | High

### 2.6 FP-D16: the regenerable-cache class — what must NOT live in persistent storage

[FP-D16 (a), accepted 19 October 2026]: members are "authenticated, bound to the engine build, discarded and never repaired on failure, discarded when the writing process later crashed, failed a check or was killed for a bad message, time-to-live per member, **never the only copy of user data**, partitioned per (top-level site, container)". *0.4* members and bindings: code cache (engine build; per (T, C)); B1 checkpoints, heap export files and suspend files (engine build; per (T, C)); compiled filter files (source-list hashes and compiler version; not per (T, C) except user-added lists' files, kept per container, CB-D11); HTTP cache (format version and a broker-issued security epoch, keyed per NW-D7; NW-D11); compiled user style sheets (ST-D17, source in the storage service); font-hash cache (TX 6.4). [FP-D16 reversal trigger]: "A member needs crash consistency or is the only copy of user data: it **leaves the class and moves to a crash-consistent embedded store**."

Obligation on storage: anything that is the only copy of user data (IndexedDB, Cache API, localStorage, cookies, history, attribution history, the user sheet source, the interaction record) is **not** a regenerable-cache member and needs crash-consistent persistence; and FP-D16's fallback phrase "a crash-consistent embedded store" is precisely where the storage spec's own engine sits (Section 3.3). | High

### 2.7 FP-D18 and FP-37 retention/clearing

See 1.10/1.11. The storage spec must implement retention (24 h† / 7 days†), the three clearing paths (history with time ranges, site data, container removal), private-window memory-only behaviour, and the FP-37 storage-test gate ("Storage tests; shell renderer inspection in DST"). The interaction record inherits FP-D18's rules (CB 6.5). | High

### 2.8 Suspend files and SEC-34 keying

[FP 6.9]: encrypted and authenticated "with the **profile's OS-bound key** (SEC-34, the REC-R2 rule for recordings)", single-use, discarded on writer crash/check failure/bad-message kill, bound to the engine build, 7-day† TTL, restore only into a fresh process locked to the same (site, container), "the broker never parses it". [FP 9.4 security-scope row]: "Suspend files and attribution history under REC-R2's key rule." The storage spec's at-rest encryption must fit SEC-34's key discipline: one profile key and, for cookies, per-container keys the broker unwraps from the OS key store (NW 6.9). The security scope itself (SEC-*) lives outside `reports/` — "security scope 0.3 (in review, PR #8)" per [NW header] — so its exact text was not read here. | High (quotes); Medium (SEC text unread)

### 2.9 NW cookie persistence contract

[NW 6.9] (quoted at 1.14): jars live in the container service (first-party, per site) and the partition services (partitioned third-party, keyed (T, C, X) matching CHIPS's ancestor bit; Storage Access grants keyed (T, C, embedded site)); both persist **through the storage service**, encrypted under per-container keys. The storage service therefore serves two network-service kinds with different jar scopes, and jar access is broker-bound: [NW 6.1] "A partition service for T receives, from the broker, a bound endpoint that can read and write **only site T's jar**, plus the jar of each site S that holds a Storage Access grant under T (IPC-R2; the container service checks the binding on every call, IPC-R17)." Clearing interfaces the storage service participates in: Clear-Site-Data within one container (NW-D18), bounce-tracker first-party deletion in this container (CB-D8), and the 7-day† no-interaction backstop (NW 6.9). | High

### 2.10 DevTools scoped principals, redaction and storage views

[DT 6.5 rule 1]: "Every session is a scoped principal. Each session … gets a container, an **origin set** (read-only and read-write) and **sensitive classes** (**cookies and storage**, bodies, form values, TLS secrets). Out-of-set content never reaches it (out-of-set frames are opaque); every command is checked against the grant; every write goes in a hash-chained **session log**." [DT 6.5 rule 5]: "Sensitive classes are masked at the IIP boundary for every principal except `devtools-user` unless granted. Exports drop `Cookie`, `Set-Cookie`, `Authorization`, `Proxy-Authorization`, credential-shaped values in URLs and bodies, **form and storage values**, qlog connection IDs and tokens, and TLS secrets; each carries a **redaction manifest** …" [DT 6.5 rule 6]: `hg-redact` substitutes "a **consistent placeholder** of the same length and type across the bundle (the same token in a response, the request echoing it, and **storage**)". [DT 6.5 rule 8]: "A replay host runs one recorded process; … **no network, storage service or GPU device**." [DT 8 DT-10]: seeded-canary suite proves "0 canaries in default exports … **storage values**" among the classes. [DT 6.2/other views]: "**storage keys**" listed among Stage 2–3 views; [DT 3.2 table]: "Process and isolation boundaries; **storage keys**" is today's invisible data. Any storage-view IIP domain the storage spec exposes must enforce the grant check at the IIP boundary. | High

### 2.11 MD-31 opaque responses through the Cache API

[MD 6.1]: "neither the encoded bytes nor the decoded pixels or samples of an opaque response map into the renderer's address space. … A service worker that forwards an opaque response passes the handle, never the body; **the Cache API stores it in the storage service**." [MD 8 MD-31(a)]: "A probing suite finds 0 bytes of opaque encoded data, pixels or samples mapped into any renderer, including through service workers and the Cache API" — ship blocker. [DM 6.10]: "**Opaque responses** that pass through a service worker or the Cache API are non-readable handles that never map into the renderer, as the media spec requires for opaque media (MD-31, G56)." The storage spec's Cache API store must accept opaque bodies as non-readable handles and must never deliver their bytes to a renderer. | High

### 2.12 The Stage 1 IPC model

[S1 4.1]: interfaces declared in `.hgidl` (methods, typed messages, handle-carrying fields); `hg-ipc-codegen` generates endpoint types, serializers and a Kani harness per message; "**Endpoints are capabilities.** A `Remote<T>` can only be obtained by being sent one. Renderers start with exactly one endpoint, to the browser process, and receive the rest from the broker"; "**Sequence affinity.** An endpoint is bound to one sequence"; "**Synchronous calls** are an explicit IDL attribute with an allowlist reviewed by the security owner. Expected Stage 1 users: `document.cookie`, `localStorage` reads, and sync XHR."; serialization VER-1 fixed little-endian length-prefixed; bulk data as read-only shared memory.

Two of the three expected sync users were since removed by decision: `localStorage` by DM-D11 ([DM 9.5] "Remove `localStorage` reads from the synchronous-IPC allowlist once DM-D11's cases pass") and `document.cookie` by NW-D10 ([NW 9.5] "Remove `document.cookie` from the sync allowlist once NW-2's ordering cases pass"). The storage spec's IPC surface must be typed `.hgidl` endpoints minted by the broker, sequence-bound, with sync calls confined to what an amended allowlist still permits. [S1 2.2 G7]: "Renderer-side crates never depend on `hg-net`, `hg-storage` or `hg-gpu` internals, **only on their generated IPC endpoints**." | High

### 2.15 Container semantics and key projections

- Isolation key: [S1 1]: "Renderer processes and **all browser-side state** are keyed by **(site, container)**"; [H2 4.1 I-1 (a)]: "a container is a user-facing policy context, and the same site in two containers gets two processes and **two storage partitions**." [FP-D8, accepted]: origin keying "On for every desktop class, regardless of FP-7 … None [no reversal trigger] that turns it off". [DM 6.8]: "the key is **(origin, container)** on every desktop class (FP-D8) and (site, container) only where I-1's reduced-isolation mode applies."
- Network partition key: [S1 1]: "The network service partitions **all** of its state by **(top-level site, container)** … The key extends the Fetch standard's **network partition key** with the container, and its scope follows the Privacy CG's storage-partitioning work …: HTTP cache, connection and socket pools, DNS cache, Alt-Svc, TLS session tickets, HSTS, revocation-check caches, reporting endpoints and service-worker registrations."
- **What F, R and n mean** [NW 6.8 key notation]: "T top-level site (schemeful), C container, F frame site, X cross-site-ancestor bit, N cross-site-main-frame-navigation bit, R route identity, n per-navigation nonce (credentialless iframes, fenced frames, recordings), O origin, Cr credentials flag." F is the frame site; R is the route identity (a route change restarts the container's services with fresh state); n is the per-navigation nonce.
- **Do storage keys use the same projection? No.** [NW 6.8 table]: "Service-worker registrations, Cache Storage \| **Storage key (T, C, X) + O**, as the storage partitioning work defines." Storage keys carry T, C, X and O — not F (the frame site is already the origin's own site for first-party storage; X carries the third-party ancestor bit), not R, not n. The (T, C, X, n) projection is the key for **in-process renderer caches** only: [NW 6.8]: "A renderer's in-process caches (parsed style sheets, attribute sets, decoded images, parsed fonts, shaped text, raster entries) and its glyph atlas key by the projection **(T, C, X, n)**: F is fixed by the renderer's site lock (origin under FP-D8), and N concerns only navigation requests." The same projection is restated in [FP 6.4 "Sharing, within a site, keyed by partition"] and adopted into H2 I-1 by [FP 9.4]: "in-process caches keyed by the (T, C, X, n) projection of NW-D7 (P18), extending I-1 (b)". The storage spec must honour the storage-partitioning key (T, C, X) + O for persisted state and must not confuse it with the (T, C, X, n) renderer-cache projection. (Boundary case: recorded sessions run with a recording nonce in the *network* key, NW 6.16; whether recorded sessions get a distinct storage key is unstated — 5.6.) | High

### 2.16 Recorded sessions and the storage service (NW-D2)

[NW 6.16]: a recording runs "that tab's top-level site in a **dedicated, freshly launched partition service** with a recording nonce in its key (n)"; "Reads from state that outlives the recording (the first-party cookie jar in the container service, HSTS, Alt-Svc, the HTTP cache, the authentication cache, Storage Access grants) are recorded as **the values read**, so replay needs no snapshot of those stores; writes to them are re-executed in replay and compared." The storage-side analogue — what a recorded renderer's IndexedDB/Cache/localStorage interactions record — is not stated in NW; DT owns recorded renderers ("DT-D2 does for renderers by starting at process launch"), and [DM 6.8]: "**Recorded sessions** follow the DevTools spec instead: the recorded browsing context group runs in dedicated, freshly launched processes and its service and shared workers outside them (DT)." [DT 6.5 rule 8]: replay hosts hold "no network, storage service or GPU device", cross-process answers stitched in the broker. The storage spec must define what a recorded unit reads and writes when no storage service exists in the replay host (5.6). | High (quotes); Low (storage-side recording semantics unstated)

### 2.17 bfcache/freeze interplay

[DM 6.9 freezing-exemption table]: "Open IndexedDB connections that block another context; Web Locks held \| Cached while no other context is waiting on them; evicted when one starts waiting." **Summary for the synthesis author.** The local contract is unusually complete on *boundaries* and almost silent on *engine*: eight accepted documents hand the storage service its clients (DOM bindings, network services, broker, shell, DevTools, content blocking), its keys (storage key (T, C, X) + O for persisted state, distinct from the (T, C, X, n) renderer-cache projection and the network key), its protocols (DM-D11's versioned snapshot, DM-D12's opaque bytes, CB's write notifications, FP-D18/FP-37 retention and clearing), and its budgets (FP-1's ≤ 4 MiB† line, FP 6.12's disk budgets). What it inherits as stale text is one idea in five places — SQLite in WAL mode (H2 3 diagram, H2 4.6, S1 process map, S1 13.2, NW diagram + NW 6.9) — already contradicted by M-1 2.3.0, HGBA-2 2.3.2's MIT-only rule and the accepted FP-D16/NW-D11 decisions. What nobody has written: an engine, a schema, a quota-charging key, and owners for OPFS, Web Locks persistence, browsing history, bookmarks, and the estimate behind `navigator.storage.estimate()`.
