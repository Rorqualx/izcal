# Izcal SVG: rendering, text and geometry

Compiled 20 October 2026. Primary sources were preferred (specifications, maintainers' posts, issue trackers, black-box test results).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only, or the researcher's recollection.

M-1 note: **no source code of any browser, engine, library or tool was opened or cited**. That covers Chromium/Blink, WebKit, Gecko, Servo, Ladybird, Vello, Pathfinder, lyon, librsvg, resvg, Batik, Skia and every other project. Under the owner rule of 20 October 2026, no third-party code of any kind counts as evidence. The feTurbulence C code is cited because it is normative specification text. This note cites no code-file links, so none had to be removed.

## 0. What the existing Izcal decisions leave open

| # | Finding | Source | Conf. |
|---|---|---|---|
| 0.1 | **The graphics spec decides SVG painting.** It covers `hg-svg-paint` (paths, the stroker, paint servers, markers, `paint-order`, `non-scaling-stroke`, clip, mask and filters) and SVG's isolation rules. It treats `shape-rendering` and `text-rendering` as hints that never turn anti-aliasing off. | 0.3 | **The fonts spec (TX-D4) quantizes font size in local user units** to the finer of 1/64 unit and 2⁻¹⁶ em. Advances are integers derived linearly from font units, and values handed to script are integers converted exactly to doubles. | `reports/Izcal fonts and text.md` 6.8 | High |

**Implications:** the SVG spec must give each geometry query a numeric contract in the same style as TX-D4 and GR-D3. Without one, the two neighbouring specs' determinism ends at the SVG DOM.

## 1. SVG text layout

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Two-stage model.** The CSS renderer lays out `<text>` as a block (with `tspan`, `textPath` and `a` as inlines) "as if absolutely positioned" and returns typographic characters with positions. The SVG algorithm then adjusts them. The used values of `margin`, `padding`, `border-style`, `float`, `position` and `text-align` are forced to their initial values. Non-text descendants get `display: none`. | — | [SVG 2 §11.5](https://www.w3.org/TR/SVG2/text.html#TextLayoutAlgorithm) | CR 2018-10-04 | High |
| 1.2 | **Output per DOM character:** a global index, (x, y), an angle, and the flags *hidden* (fell off a textPath), *addressable*, *middle* (second or later character of a typographic character) and *anchored chunk*. Collapsed white space, soft hyphens, bidi controls and trimmed characters are **not addressable**, so `x="100 200 300"` skips them. | — | [§11.5](https://www.w3.org/TR/SVG2/text.html#TextLayoutAlgorithm) | 2018 | High |
| 1.3 | **Ligature rule.** Attribute arrays are indexed by addressable characters but applied to typographic characters. For a ligature, extra `x`/`y` values are skipped, extra `dx`/`dy` values accumulate onto the next typographic character, and `rotate` carries forward. Positions therefore do not depend on whether a font has the ligature. | — | [§11.5](https://www.w3.org/TR/SVG2/text.html#TextLayoutAlgorithm) | 2018 | High |
| 1.4 | **Order of steps:** resolve positioning recursively ([ResolveGlyphPositioning](https://www.w3.org/TR/SVG2/text.html#ResolveGlyphPositioning); descendants override ancestors; inside a textPath, `y` is ignored for horizontal text and `x` for vertical) → apply `dx`/`dy` cumulatively → apply `textLength` (children before parents, [ResolveTextLength](https://www.w3.org/TR/SVG2/text.html#ResolveTextLength)) → apply absolute `x`/`y` (each starts a chunk) → apply anchoring per chunk using min/max extents (advances are negative in RTL) → position on the path. | — | [§11.5](https://www.w3.org/TR/SVG2/text.html#TextLayoutAlgorithm) | 2018 | High |
| 1.5 | **The algorithm text has defects.** It reads `new_check_count` for `new_chunk_count`. It sets `resolve_dx` from `dy[i]`. It writes `lrt` for `ltr`. The x/y loop starts at "index = 1", which would never apply `x` to the first character. The textPath loop uses undefined `i` and `k`. A literal implementation is therefore wrong, and the intent has to be reconstructed and filed. | 5 defects | [§11.5](https://www.w3.org/TR/SVG2/text.html#TextLayoutAlgorithm) (text as published) | 2018 | High |
| 1.6 | **`textLength`:** a node with a forced line break is not adjusted. Otherwise delta = `textLength` − (b − a), and the UA "is required" to shift the last character by delta; intermediate characters are "free" to be adjusted. `spacing` spreads delta / n with each resolved descendant counted as one character. `spacingAndGlyphs` has no algorithm. | — | [§11.5](https://www.w3.org/TR/SVG2/text.html#ResolveTextLength), [textLength](https://www.w3.org/TR/SVG2/text.html#TextElementTextLengthAttribute) | 2018 | High |
| 1.7 | **textPath placement.** mid = x + advance/2 + startOffset (scaled by `pathLength`). On an open path, a character is hidden if mid < 0 or mid > length. A **single closed subpath** wraps one full circuit: hidden windows depend on the anchor and direction, then mid mod length is taken. Position = point − o·t + y·n, and angle += the tangent angle. `side="right"` reverses the path. Characters after a textPath continue from the path's end point. | — | [§11.5 "Position on path"](https://www.w3.org/TR/SVG2/text.html#TextLayoutAlgorithm), [§11.8](https://www.w3.org/TR/SVG2/text.html#TextLayoutPath) | 2018 | High |
| 1.8 | **The spec leaves `method="stretch"` and `spacing="auto"` to the UA.** "The user agent is free to make any additional adjustments". Stretch warps glyph outlines along the path, and straight segments "should be converted to Bézier curves". There is no algorithm, so there is no interop target. | — | [method](https://www.w3.org/TR/SVG2/text.html#TextPathElementMethodAttribute), [spacing](https://www.w3.org/TR/SVG2/text.html#TextPathElementSpacingAttribute) | 2018 | High |
| 1.9 | **The spec itself records startOffset interop.** "Chrome and Safari both do not handle offsets outside the range 0% to 100%" (an editor's note in the CR). | — | [startOffset](https://www.w3.org/TR/SVG2/text.html#TextPathElementStartOffsetAttribute) | 2018 | High (as a 2018 note) |
| 1.10 | **Auto-wrapped text (`inline-size`).** The text is laid out in a CSS content box of that inline size with unconstrained block size. Each line box is shifted by `text-anchor`, and "no further post-processing" applies, so `x`/`y`/`dx`/`rotate` are ignored except for the first character's `x`/`y`, which set the start. Percentages are relative to the SVG viewport's width (or its height for vertical text). `shape-inside`: the first line moves down until it fits, and broken lines share one height (agreed at Sydney 2016). | — | [§11.4](https://www.w3.org/TR/SVG2/text.html#InlineSize), [§11.7](https://www.w3.org/TR/SVG2/text.html#TextLayoutAuto) | 2018 | High |
| 1.11 | **No major engine implements wrapping, as of 2026-10-19.** All three fail every WPT `text-inline-size-*` (8), `text-multiline-*` (3) and `text-shape-inside-*` (2) reftest, as well as `textpath-side-001/003/005`. Safari alone fails 13 of the textPath `path`-attribute reftests and most of the textPath scripted tests. | 13 + 3 reftests fail in all three | [wpt.fyi svg/text](https://wpt.fyi/results/svg/text?label=stable) (API query, Section 8) | 2026-10-19 | High |
| 1.12 | **`glyph-orientation-vertical` is an alias.** It is obsolete, but must be supported as a shorthand for `text-orientation`: `auto`→`mixed`, `0`/`0deg`→`upright`, `90`/`90deg`→`sideways`. Anything else is invalid. Vertical text uses `writing-mode`, and the full glyph cell is the em box by the vertical advance (or by the em height when the font has no vertical advance). | — | [§11.10.1.3](https://www.w3.org/TR/SVG2/text.html#GlyphOrientationVerticalProperty), [full glyph cell](https://www.w3.org/TR/SVG2/coords.html#TermFullGlyphCell) | 2018 | High |
| 1.13 | **`text-rendering` is a hint.** `geometricPrecision` "will usually cause the user agent to suspend the use of hinting so that glyph outlines are drawn with comparable geometric precision to the rendering of path data". `optimizeSpeed` "will sometimes" turn anti-aliasing off. | — | [SVG 2 §13.10](https://www.w3.org/TR/SVG2/painting.html#TextRenderingProperty) | 2018 | High |
| 1.14 | **Selection and find are conformance requirements.** In web-browser environments a viewer "must have the ability to search and select text strings within SVG content". Selection runs in logical order between the start and the nearest glyph cell in the same `<text>`, "regardless of position on the canvas". | — | [conform §2.5.5](https://www.w3.org/TR/SVG2/conform.html#ConformingSVGViewers), [§11.12](https://www.w3.org/TR/SVG2/text.html#TextSelection) | 2018 | High |
| 1.15 | **Firefox's design history.** In July 2013, Firefox's SVG text was reworked to "reuse the same text layout and rendering code that it uses for HTML". It took 50 patches (bug 655877) and about 40 follow-ups, and brought text-decoration, find and selection, correct bidi across child nodes, `white-space`, `line-height` and `::first-letter`. In 2011 the same engineer called positioned, anchored bidi SVG text "greatly non-interoperable and somewhat underspecified". | 50 patches; ~40 follow-ups | [McCormack, "Firefox SVG text improvements"](https://mcc.id.au/blog/2013/07/firefox-svg-text-improvements); www-svg, [2011-08](https://lists.w3.org/Archives/Public/www-svg/2011Aug/0017.html) | 2013-07-01 | High (blog); Medium (2011 quote, from a snippet) |
| 1.16 | **Blink's prose is not usable.** Blink's SVG text is said to run its inline layout first and then a separate SVG pass, but the only prose found was third-party summaries derived from source. They were not used. No first-party Blink design document on SVG text was found this session. | — | — | — | Low |

**Implications:** Izcal should implement §11.5 as a **pure function** from (the inline layout's per-character records, the attribute lists, path geometry) to per-character records, entirely in integer user-space units. It should have its own corrected pseudo-code, with the five defects filed upstream. `inline-size` and `shape-inside` are an interop gap that no engine fills today: Izcal's layout library call (LY 6.5.10) makes them nearly free, but the visible result cannot be checked against another browser.

## 2. Path geometry

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Path errors render up to the error.** Rendering stops before the command that contains the first error, and a command with a bad parameter count renders its complete segments ("M 10,10 L 20,20,30" draws 10,10→20,20). The UA "shall report all errors". | — | [SVG 2 §9.5.4](https://www.w3.org/TR/SVG2/paths.html#PathDataErrorHandling) | 2018 | High |
| 2.2 | **Out-of-range arc parameters.** An arc whose endpoint equals the current point is omitted. rx or ry = 0 is a line. Negative radii take their absolute values. Radii that are too small are scaled up by √Λ, where Λ = x1′²/rx² + y1′²/ry². The endpoint-to-center conversion is SVG 2 **Appendix B.2.4** (it was F.6 in SVG 1.1). | — | [§9.5.1](https://www.w3.org/TR/SVG2/paths.html#ArcOutOfRangeParameters), [B.2.4](https://www.w3.org/TR/SVG2/implnote.html#ArcConversionEndpointToCenter), [B.2.5](https://www.w3.org/TR/SVG2/implnote.html#ArcCorrectionOutOfRangeRadii) | 2018 | High |
| 2.3 | **Distance along a path is UA-defined.** "Exact mathematics exist … but the formulas are highly complex". UAs should be "as precise as possible", and `pathLength` exists so authors can calibrate. A moveto has zero length. `pathLength="0"` means an infinite scale (0 stays 0). Negative values are errors, and `pathLength` has no effect on percentage distances. | — | [§9.6](https://www.w3.org/TR/SVG2/paths.html#DistanceAlongAPath), [§9.6.1](https://www.w3.org/TR/SVG2/paths.html#PathLengthAttribute) | 2018 | High |
| 2.4 | **The length APIs are float32 and ignore `pathLength`.** In the IDL, `float getTotalLength()` and `getPointAtLength(float distance)` both ignore `pathLength`, and the distance is clamped to [0, length]. `isPointInFill` implicitly closes open subpaths, counts points on the path as inside, and returns false for NaN or ∞. `isPointInStroke` uses width, caps, joins, miter limit, **dash array and offset** and `vector-effect`. A non-rendered element whose geometry the UA cannot compute throws InvalidStateError. | — | [SVG 2 §4.4.3](https://www.w3.org/TR/SVG2/types.html#InterfaceSVGGeometryElement) | 2018 | High |
| 2.5 | **Arc-length results differ between engines.** Bug 1507603 reports that Firefox 63 gave about 145.8 for a five-decimal path and about 147.1 after rounding, while Chrome gave about 147.1 for both (open as of the snippet). A 2020 SVG WG thread reports Firefox and Chrome about 0.1% apart on a long cubic spiral. A library documents that native results differ between all three engines and uses Legendre–Gauss quadrature itself. | ≈0.9% (bug); ≈0.1% (WG) | [Mozilla bug 1507603](https://bugzilla.mozilla.org/show_bug.cgi?id=1507603); [public-svg-issues 2020-01](https://lists.w3.org/Archives/Public/public-svg-issues/2020Jan/0030.html) (a third-party library's claim that engines disagree is not cited: its repository is code, phase 8 FC-R1) | 2018–2020 | Medium (snippets) |
| 2.6 | **WPT length tests are coarse, and still fail.** Safari fails `getPointAtLength-04/05` and `getTotalLength-02`, and Chrome and Safari fail 2 of 6 `getTotalLength-01` subtests. The CSS `path-length` property (`tentative`) fails in all three. Only Firefox passes the new `getPathData`/`setPathData`/`getPathSegmentAtLength` tests. | — | [wpt.fyi svg/types, svg/path](https://wpt.fyi/results/svg/path?label=stable) | 2026-10-19 | High |
| 2.7 | **Bounding-box rules.** A bounding box is the tightest box in user space. **Control points that are not on the curve must not contribute**, while parts of the curve outside the control hull must. The four flavours are object, stroke, decorated (with markers) and clipped. `getBBox` options default to fill true and the others false. Opacity, visibility, fill, fill-rule, **dasharray and dashoffset have no effect**. A zero-size element still has a box. Elements that are not rendered (`defs`, `display:none`) still answer `getBBox` but do not contribute to their ancestors. Text uses full glyph cells. A `use` that points nowhere has its x, y and 0×0. | — | [SVG 2 §8.10](https://www.w3.org/TR/SVG2/coords.html#BoundingBoxes), [getBBox](https://www.w3.org/TR/SVG2/types.html#__svg__SVGGraphicsElement__getBBox) | 2018 | High |
| 2.8 | **getBBox interop is poor beyond the basic case.** Chrome fails subtests in `getBBox-03, 05, 06, 07, 08, 09`, for example 3/12 in 03 and 33/49 in 07. Safari fails in `02, 05, 06, 07, 09, 10`. Firefox passes all ten files. | — | [wpt.fyi svg/types/scripted](https://wpt.fyi/results/svg/types/scripted?label=stable) | 2026-10-19 | High |
| 2.9 | **Markers.** An `orient="auto"` marker bisects the end direction of the incoming segment and the start direction of the outgoing one; at the ends of an open subpath it follows the path. Directions "move past" zero-length segments, and the direction of an all-zero path is +x. A marker is drawn on every vertex, including zero-length segments and consecutive movetos. `auto-start-reverse` adds 180° at the start only. Markers are not interactive, take no inherited properties, and are clipped to their viewport by the UA stylesheet's `overflow: hidden`. | — | [§13.7.4](https://www.w3.org/TR/SVG2/painting.html#RenderingMarkers), [§9.4](https://www.w3.org/TR/SVG2/paths.html#PathDirectionality), [§9.5.3](https://www.w3.org/TR/SVG2/paths.html#ZeroLengthSegments) | 2018 | High |
| 2.10 | **Marker interop.** `marker-path-022/023` fail in all three. Safari fails 8 other marker reftests, and all fail `marker-005/006/007` except Safari. | — | [wpt.fyi svg/painting](https://wpt.fyi/results/svg/painting?label=stable) | 2026-10-19 | High |
| 2.11 | **`non-scaling-stroke`.** The path is transformed to the host space (the viewport of the furthest ancestor SVG viewport), stroked there, and the outline transformed back. Paint stays in user space. The other `vector-effect` values (`non-scaling-size`, `non-rotation`, `fixed-position`) are **at risk** "due to a lack of implementations", and none affects 3D rendering contexts. Seven non-scaling-stroke reftests are split between engines (`-precision-loss` and `-non-uniform-scale` fail in Safari). | — | [§13.6 non-scaling-stroke](https://www.w3.org/TR/SVG2/painting.html#non-scaling-stroke), [§8.13](https://www.w3.org/TR/SVG2/coords.html#VectorEffectProperty), [issue 31](https://www.w3.org/TR/SVG2/coords.html#issue31) | 2018; 2026-10-19 | High |

**Implications:** the spec should **name one arc-length algorithm**: a fixed segment subdivision, a fixed Gauss–Legendre order, a fixed summation order and integer or fixed-point output. That gives `getTotalLength`, textPath, dashes and markers one answer each, which no engine does today (2.5). Bounding boxes must use curve extrema, not control hulls. Because dashing does not change the stroke bounding box, a box can be computed from geometry alone.

## 3. Units, coordinates and precision

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **The viewBox → viewport transform is an explicit algorithm.** scale = e/vb per axis. `meet` takes the smaller scale and `slice` the larger, unless `align` is `none`. The translation is e − vb·scale, plus half (Mid) or all (Max) of the leftover space. The result is translate·scale, with no rotation. | — | [SVG 2 §8.2](https://www.w3.org/TR/SVG2/coords.html#ComputingAViewportsTransform) | 2018 | High |
| 3.2 | **Percentage lengths.** Lengths that are not horizontal or vertical use the **normalized diagonal** √(w² + h²)/√2 of the viewBox, or of the viewport if there is no viewBox. | — | [§8.9 Units](https://www.w3.org/TR/SVG2/coords.html#Units_viewport_percentage) | 2018 | High |
| 3.3 | **Precision floors.** Coordinate conversion needs "at least single-precision", but CTM generation, including the nested ScreenCTM, "must" use at least double precision. A high-quality viewer needs double precision for all coordinate transformation. Informative B.3 states "The real number precision of SVG is single-precision" and tells authors to tile large maps under per-tile double-precision transforms. | — | [conform §2.5.5](https://www.w3.org/TR/SVG2/conform.html#ConformingSVGViewers), [§2.5.6](https://www.w3.org/TR/SVG2/conform.html#ConformingHighQualitySVGViewers), [B.3](https://www.w3.org/TR/SVG2/implnote.html#NumericPrecisionImplementationNotes) | 2018 | High |
| 3.4 | **The DOM types mix float32 and double.** `SVGNumber.value`, `SVGLength.value`, `SVGAngle`, `currentScale`, `getComputedTextLength`, `getSubStringLength`, `getRotationOfChar` and `getTotalLength` are IDL `float`. `getBBox`, `getCTM` and `getPointAtLength` return SVGRect, SVGMatrix and SVGPoint, which are aliases of Geometry Interfaces' DOMRect, DOMMatrix and DOMPoint (unrestricted double). SVG 2 "requires complete support" for Geometry Interfaces 1. | — | [SVG 2 §4.3–4.5](https://www.w3.org/TR/SVG2/types.html#InterfaceSVGNumber) | 2018 | High (IDL); Low (alias detail, not re-read) |
| 3.5 | **Engines show precision-loss bugs.** The fact that a `non-scaling-stroke-precision-loss` reftest exists and fails in Safari (2.11) shows that precision loss is still observable today. How each engine stores path coordinates is stated only in source, so it is not recorded here and goes to black-box measurement (Q-SVG-T4). | — | [wpt.fyi svg/painting](https://wpt.fyi/results/svg/painting?label=stable) | 2026-10-19 | High (test); — |
| 3.6 | **What Izcal already fixes.** Style's IEEE matrices are converted once to i64 fixed point with 32 fractional bits and composed in i128, and raster coordinates are 24.8 relative to an integer layer origin (GR-D3). Text advances are integers in a quantum of user units (TX-D4). | — | `reports/Izcal graphics and rendering.md` §6.3 table | 2026-10-19 | High |
| 3.7 | **A feasible deterministic approach (first principles, not published practice).** (a) Parse numbers to a canonical fixed point, for example 1/2¹⁶ user unit in i64, after correctly rounded decimal-to-binary conversion. (b) Compose CTMs in 32.32 as the graphics spec does. (c) Compute curve extrema (roots of quadratics) and arc length with integer or fixed-order IEEE double arithmetic that uses only correctly rounded operations (+ − × ÷ √), so results are bit-identical on every ISA if FMA contraction is disabled. (d) Implement sin, cos and atan2, which arcs and `rotate` need, as Izcal's own correctly rounded or fixed-point functions, never the OS libm. (e) Convert to double exactly at the IDL boundary, then round to float32 where the IDL says `float`. | — | Derived from 3.3–3.6; IEEE 754 requires correct rounding only for basic operations and √ | — | Medium (reasoning) |

**Implications:** SVG's own floors (single precision for coordinates, double for CTMs) leave room for a fixed-point design that meets or exceeds them. The one place this needs care is very large coordinates (maps), where 1/2¹⁶ in i64 still spans ±1.4×10¹⁴ units. The spec should state the quantum, the range and the overflow behaviour, and test them with tiled-map content.

## 4. Paint servers, clipping, masking and filters

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Radial focal handling, SVG 2.** The focal circle (fx, fy, fr) may lie outside the end circle, which forms a cone, and the area outside the cone is transparent black (this aligns with Canvas). If the start circle fully overlaps the end circle, nothing is drawn. When the focal point lies on the circle with `repeat`, the area is painted with the **offset-weighted average of the stops**. That deliberately differs from Canvas, for SVG 1.1 compatibility. | — | [SVG 2 §14.2.3.2](https://www.w3.org/TR/SVG2/pservers.html#RadialGradientNotes) | 2018 | High |
| 4.2 | **Paint-server templates.** `href` templates copy undefined attributes and children, may cross files in SVG 2, and must guard against recursive references. An invalid paint reference without a fallback now paints nothing; in SVG 1.1 it put the document in error. Six `*-transform-*-attr` and template-inheritance reftests fail in Safari only. | — | [§14.1.1](https://www.w3.org/TR/SVG2/pservers.html#PaintServerTemplates), [painting §13.2](https://www.w3.org/TR/SVG2/painting.html#SpecifyingPaint); wpt.fyi svg/pservers | 2018; 2026-10-19 | High |
| 4.3 | **`clipPath` content.** A clip may contain shapes, text and `use`, but only a `use` that **directly** references a shape or text; for indirect references the clip "must be ignored". An editor's issue in the spec says "No browser ignores clipPath on use with indirect reference", and that Firefox stops rendering elements whose clipPath breaks the content model. Silhouettes are combined with OR as 1-bit coverage (except anti-aliasing). "Raw geometry" for text is undefined ([csswg-drafts #170](https://github.com/w3c/csswg-drafts/issues/170)). | — | [CSS Masking §6.1](https://www.w3.org/TR/css-masking-1/#ClipPathElement) | 2014 CR | High |
| 4.4 | **Missing resources fail in different ways.** An invalid clipPath means **no clipping**. An invalid mask is a **transparent-black layer, so the element disappears**. An invalid filter means the **whole chain is ignored**. An invalid marker draws no marker. An invalid paint uses its fallback or nothing. A circular `use` is not rendered. | — | [Masking §5.1](https://www.w3.org/TR/css-masking-1/#the-clip-path), [§7.1](https://www.w3.org/TR/css-masking-1/#the-mask-image); [Filter Effects §5](https://www.w3.org/TR/filter-effects-1/#FilterProperty); [SVG 2 §5.5.1](https://www.w3.org/TR/SVG2/struct.html#UseShadowTree) | — | High |
| 4.5 | **Mask luminance coefficients conflict between specs.** CSS Masking defers to "feColorMatrix … [SVG11]", whose `luminanceToAlpha` row is **0.2125, 0.7154, 0.0721**. Filter Effects 1's feColorMatrix uses **0.2126, 0.7152, 0.0722** (Rec. 709). The difference is under 0.03% per channel, but it can change an 8-bit result. Conversion to linearRGB happens only if `color-interpolation` on the `<mask>` is `linearRGB` (initial sRGB), and luminance is computed from non-premultiplied values, then multiplied by alpha. | 2 coefficient sets | [CSS Masking §7.10.1](https://www.w3.org/TR/css-masking-1/#MaskValues); [SVG 1.1 filters](https://www.w3.org/TR/SVG11/filters.html#feColorMatrixElement); [Filter Effects 1 §9.6](https://www.w3.org/TR/filter-effects-1/#feColorMatrixElement) | — | High |
| 4.6 | **`filterRes` is removed** ("was removed from the specification"). Primitives operate in a device-dependent **operating coordinate space** that scales `primitiveUnits` values, and "User agents may reduce the resolution of filter primitives on limited platform resources". Undefined pixels are transparent black. | — | [Filter Effects 1 §8](https://www.w3.org/TR/filter-effects-1/#FilterEffectsRegion) | 2018 WD | High |
| 4.7 | **feGaussianBlur.** The Gaussian is separable. For σ ≥ 2.0, three box blurs of size d = floor(σ·3·√(2π)/4 + 0.5) may be used ("within roughly 3%"), with the even-d case specified as two offset boxes plus one box of size d+1. | — | [§9.14](https://www.w3.org/TR/filter-effects-1/#feGaussianBlurElement) | 2018 | High |
| 4.8 | **feTurbulence is exact C code.** The spec's C code is normative ("shows the exact algorithm"). It uses a Park–Miller generator (a = 16807, m = 2³¹−1, with the 10,000th value 1043618065 from seed 1 as a self-test) and double-precision lattice and noise math, stitching through floor/ceil frequency adjustment. R, G, B and A lattices are generated in that order, and output is in `color-interpolation-filters` space. | — | [§9.21](https://www.w3.org/TR/filter-effects-1/#feTurbulenceElement) | 2018 | High |
| 4.9 | **Primitive details.** feDisplacementMap uses `in` premultiplied and `in2` un-premultiplied, and `color-interpolation-filters` applies only to `in2`. feDropShadow is defined as blur(alpha) → offset → flood → composite → merge. feImage renders an external file like `<image>` and an element like `use`; failures give transparent black. Lighting uses 3×3 Sobel kernels on an implicit grid set by `kernelUnitLength`, which is otherwise resolution-dependent. | — | [§9.11](https://www.w3.org/TR/filter-effects-1/#feDisplacementMapElement), [§9.12](https://www.w3.org/TR/filter-effects-1/#feDropShadowElement), [§9.15](https://www.w3.org/TR/filter-effects-1/#feImageElement), [§9.10](https://www.w3.org/TR/filter-effects-1/#feDiffuseLightingElement) | 2018 | High |
| 4.10 | **Tainted primitives must run in constant time.** feFlood, feDropShadow and lighting with `currentColor`, feImage over no-CORS or element references, and SourceGraphic, SourceAlpha, BackgroundImage, BackgroundAlpha, FillPaint and StrokePaint are tainted, and taint propagates. Filtering with any tainted input "must" take the same time whatever the pixel values. | — | [§15.1](https://www.w3.org/TR/filter-effects-1/#tainted-filter-primitives) | 2018 | High |
| 4.11 | **Filter and masking interop.** Of 395 `css/filter-effects` tests, Chrome passes 371, Firefox 351 and Safari 300; 271 pass in all three. Of 566 `css/css-masking` tests, Chrome and Firefox pass 521 and Safari 480; 433 pass in all three. `display-none-mask.html` and `inline-svg-resize-viewport-dependent-mask.html` fail in all three. | — | wpt.fyi API (Section 8) | 2026-10-19 | High |

**Implications:** the SVG spec must choose one luminance coefficient set and file the conflict. The graphics spec's "specification's coefficients in fixed point" cannot be implemented until that choice is made. The table in 4.4 should go into the render tree as an explicit **resolution outcome** per reference: applied, ignored, or element hidden.

## 5. GPU and CPU vector rendering: what belongs where

| # | Finding | Source | Conf. |
|---|---|---|---|
| 5.1 | **The algorithms are already covered.** Signed-area coverage, sparse strips (Levien, 2024 design document) and the CPU and hybrid variants, piet-gpu/Vello's compute sort-middle design, Li–Hou–Zhou's GPU scanline rasterization (SIGGRAPH Asia 2016), shortcut trees, random-access vector graphics, stencil-then-cover (Kilgard and Bolz, NV_path_rendering), Loop–Blinn (2005), Slug, Pathfinder 3's trapezoidal coverage, and strokers (Nehab 2020; Levien and Uguray 2024) are all in the graphics research, which picked sparse strips plus an integer fine raster (GR-D3, GR-D4). | [GR-RP 1.1–1.12, 2.1–2.7](../Izcal%20graphics%20and%20rendering/rasterization_paint.md) | High (as cross-reference) |
| 5.2 | **SVG adds a different stress: many small, independently animated elements.** Data visualization means thousands of circles, rects and short paths, each with its own transform, fill and events. Path-heavy maps stress dashed strokes ([GR-RP 8.3]). Per-element costs dominate: style, geometry building, flattening, the render-tree record and hit-test structure, not raster throughput. No published benchmark of SVG element-count scaling across engines was found this session. | [GR-RP 8.3]; no source | Low (no measurement) |
| 5.3 | **The split, derived from 0.1–0.2.** The graphics spec owns flattening, stroking, coverage and blending. The SVG spec owns (a) **granularity**: one render-tree record per graphics element, with geometry in the bounded path format cached per element and keyed by the geometry attributes plus the `vector-effect` host transform; (b) **invalidation**: which records a DOM, style or resource change dirties (Section 6); (c) **reuse**: a `use` instance and a marker instance share their source geometry, and only transform and context paint differ. | Reasoning from §6.16 and §6.28 | Medium |
| 5.4 | **Marker and pattern instancing.** The spec defines rendering as if the marker's contents were "deeply cloned into a separate non-exposed DOM tree for each instance" ([§13.7.4](https://www.w3.org/TR/SVG2/painting.html#RenderingMarkers)). That is a semantic statement, not an implementation requirement, so instancing by transform is allowed whenever the result is identical. WebKit's LBSE notes caching image buffers "per resource client" for masks and patterns (2024). | [SVG 2 §13.7.4]; [WPE WebKit LBSE update](https://wpewebkit.org/blog/status-of-lbse-in-webkit.html) | High (spec); High (blog) |

**Implications:** the SVG spec should not choose a rasterizer. It should define the render-tree record, its cache key and its dirty bits, and set targets for element-count scaling (for example frame time at 10⁴ and 10⁵ animated circles†) measured by GR-S3's harness.

## 6. Invalidation and incremental update

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **The dependency graph is many-to-many and crosses documents.** Clients (shapes, text, `use`, groups) reference resources (gradients and patterns with `href` templates, clipPath, mask, filter, marker, feImage, textPath, `use` targets, `mpath`). **Implications:** Izcal should make the resource graph an **explicit, acyclic-checked index** built at render-tree construction. Edges should be typed (paint, geometry, bbox-dependent, external document). A change should yield a **dirty set computed in one pass**, independent of DOM order. Cycles should be detected when an edge is inserted, and a cycle should resolve to the spec's error outcome (4.4). The five bug classes in 6.5 make a ready-made regression list.

## 7. Hit testing and `pointer-events`

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **The values.** `visiblePainted` (the initial value via `auto`) hits fill where fill ≠ none and stroke where stroke ≠ none, if `visibility` is visible. `visibleFill`, `visibleStroke` and `visible` ignore the paint values. `painted`, `fill`, `stroke` and `all` ignore visibility (`fill` and `stroke` also ignore paint). `bounding-box` hits the element's bounding box. `none` never hits. | 11 values | [SVG 2 §15.6](https://www.w3.org/TR/SVG2/interact.html#PointerEventsProperty) | 2018 | High |
| 7.2 | **Text and images are tested by area.** Text is hit-tested **per character cell**, and `fill`/`stroke`/`all` are equivalent there. Raster images are hit-tested over the whole image rectangle. Markers are never hit. The outermost `svg` is not a graphics element and is never a target in standalone files. Its behaviour when embedded is "implementation-specific". | — | [§15.6](https://www.w3.org/TR/SVG2/interact.html#PointerEventsProperty), [§15.5.1](https://www.w3.org/TR/SVG2/interact.html#hit-testing), [§13.7.4](https://www.w3.org/TR/SVG2/painting.html#RenderingMarkers) | 2018 | High |
| 7.3 | **`use` and events.** Shadow-tree instances can be targets, and events are **retargeted** to the `use` element when they leave the shadow tree (new in SVG 2, matching Shadow DOM). | — | [SVG 2 §5.5.5](https://www.w3.org/TR/SVG2/struct.html#UseEventHandling) | 2018 | High |
| 7.4 | **Interop.** Firefox passes 17 of 31 `svg-pointer-events-bbox` subtests, and Chrome and Safari pass all. Firefox fails `ellipse-hittest` and `rect-hittest-002`. Safari fails `pointer-events-fill-stroke-hittest`, `text-hittest-002/003` and `use-instance-hover`. | — | [wpt.fyi svg/interact](https://wpt.fyi/results/svg/interact?label=stable) | 2026-10-19 | High |
| 7.5 | **Hit-test geometry is not tied down.** `isPointInStroke` includes dashes (2.4), but pointer-events says only "perimeter (stroke)". The spec does not say whether dash gaps hit, whether hit testing uses the anti-aliased coverage or the exact outline, or how clip-path and mask (which CSS Masking says limit hit testing) combine with `bounding-box`. | — | [§15.6](https://www.w3.org/TR/SVG2/interact.html#PointerEventsProperty); [types §4.4.3](https://www.w3.org/TR/SVG2/types.html#InterfaceSVGGeometryElement) | 2018 | High (that it is unspecified) |

**Implications:** hit testing should reuse the **exact** fill and stroke outline in fixed point, with no coverage threshold, and be the same function as `isPointInFill` and `isPointInStroke`. ## Open questions for the spec

- **Q-SVG-T1:** Izcal's corrected §11.5 pseudo-code. File the five defects (1.5) with the SVG WG, and decide what to do meanwhile.
- **Q-SVG-T2:** whether to implement `method="stretch"` and `spacing="auto"`, which no algorithm defines. Ship `align`/`exact` only and record it?
- **Q-SVG-T3:** the arc-length method: a named algorithm, its tolerance and its integer representation, shared by `getTotalLength`, textPath, dashes, markers and motion paths.
- **Q-SVG-T4:** black-box measurement of each engine's coordinate precision (large-coordinate path tests, float32 versus float64 behaviour), because engine storage types are stated only in source.
- **Q-SVG-T5:** which mask luminance coefficients to use (4.5), to be filed with the CSS WG.
- **Q-SVG-T6:** the hit-test rule for dash gaps and for clip/mask combined with `bounding-box` (7.5).
- **Q-SVG-T7:** whether `vector-effect` values other than `non-scaling-stroke` (at risk) are implemented.
- **Q-SVG-T8:** a published or measured element-count scaling benchmark for SVG data visualization (5.2), to be added to the graphics GR-S3 harness.
- **Q-SVG-T9:** how §11.5 applies inside `inline-size` text that also has `textLength` or `rotate` (the spec says no post-processing; WPT has a tentative textLength + anchor test that fails in Firefox and Safari).
- **Q-SVG-T10:** whether find-in-page and selection on SVG text (a conformance must, 1.14) use the same semantic-plane hooks as HTML text (TX 6.14).
