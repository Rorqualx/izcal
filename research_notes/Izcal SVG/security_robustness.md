# Izcal SVG: security and robustness

Compiled 20 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

M-1 note: no source code of any browser, engine or library was opened or cited (Chromium/Blink, WebKit, Gecko, librsvg, resvg, Skia, Cairo and others). Search results surfaced a librsvg source file holding resource limits and two Chromium commits; they were not opened, and every limit below comes from librsvg's prose security document or its release notes. Paul Stone's 2013 slides show a short excerpt of Firefox filter code; that excerpt was not used. The note was checked against the wider owner rule, under which no third-party code (libraries such as librsvg, resvg, ImageMagick or DOMPurify, tools, OS components) counts as evidence. No code file, header, commit, diff or code review is linked, so nothing had to be removed. The issue-tracker links (librsvg #323, AngularJS #11290, Cairo #292) point to prose discussion. Prose only: papers, vendor blogs, release notes, CVE records, mailing lists, W3C drafts.

| 1.7 | **Root-cause classes, as a synthesis of 1.1–1.5 and the wider record.** (a) Cloned **`<use>` instance trees** whose lifetime is tied to the referenced element, which a mutation can destroy while it is being rebuilt. **Implications:** Izcal's SVG code is written in Rust, which removes most raw use-after-frees. The same five classes still return as **logic bugs**: stale node handles, iterating a list while a callback mutates it, and cycles in the reference graph. The spec should require (1) generation-checked node handles for `<use>` shadow instances and resource clients, (2) that animation sampling builds the list of changes first and applies it afterwards, with no DOM mutation during iteration, and (3) a reference graph rebuilt or checked once per frame, with cycle detection, not ad-hoc client lists. Fuzz each class directly.

**Implications:** Izcal should not copy librsvg's posture: no total budget, with fixed counters only. It should define a **per-document budget** that is deterministic and part of the spec, because GR-D3 requires the cut-off point to be bit-identical. The budget should cover: expanded instance count (a counter on `<use>` and pattern expansion, cutting off the subtree beyond it), reference depth, nesting depth (iterative traversal, not recursion), filter work units (sum of pixels × kernel cost per primitive), intermediate-surface bytes, and path segment count. When a limit is reached, the result must be defined (the element renders as if it were in error) and reported to DevTools. Fuzzers will produce extreme coordinates; the integer-only rasterizer needs saturating or checked arithmetic and a coordinate clamp defined in the spec.

## 3. Side channels: timing and pixel stealing

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Stone, "Pixel Perfect Timing Attacks with HTML5"** (Context IS, Black Hat USA 2013). SVG filters can be applied to HTML content, including cross-origin iframes. `feMorphology`'s running time depended on pixel values, and `requestAnimationFrame` timing exposed it. Each pixel was thresholded to black or white and read one at a time; text was recovered with an OCR-style binary tree (n reads for 2ⁿ characters). The same work timed redraws to sniff `:visited` history at 13–20 URLs per second in Firefox and IE, and up to 30 per second in Chrome. | 13–30 URLs/s | [Stone slides](https://wiki.owasp.org/images/1/10/HackPra_Allstars-Browser_Timing_Attacks_-_Paul_Stone.pdf); [The Register](https://www.theregister.com/2013/08/05/html5_timing_attacks/) | 2013-08 | High |
| 3.2 | Stone's slides: "Mozilla have fixed feMorphology in Firefox 22". Suggested fixes included always redrawing links (visited or not), not applying filters to iframes or links, and rendering iframes as blank and links as unvisited when a filter applies. Sites could defend themselves with X-Frame-Options. | Firefox 22 | same | 2013 | High |
| 3.3 | **Kotcher, Pei, Jumde, Jackson, "Cross-origin pixel stealing: timing attacks using CSS filters"**, CCS 2013. Timing attacks with the default CSS filters worked in several browsers and on several devices. They could test whether a user has an account on a site, sniff history, and read text tokens. | n/a | [CCS 2013 PDF](https://static.aminer.org/pdf/20170130/pdfs/ccs/es7k2n6jxrlhnkeo1yagfgzhwpruu3ci.pdf); [Wikipedia](https://en.wikipedia.org/wiki/Pixel_stealing_attack) | 2013-11-04 | Medium |
| 3.4 | **Andrysco et al., "On Subnormal Floating Point and Abnormal Timing"**, IEEE S&P 2015. On x86, floating-point add and multiply can take up to about 100 times longer on subnormal operands. SVG filters applied to web content in Firefox 23–27 could be timed from JavaScript; filters moved to the GPU in Firefox 28. The paper proposes a constant-time fixed-point library. | ~2 orders of magnitude | [Paper PDF](https://web.eecs.umich.edu/~genkin/teaching/fall2019/EECS598-12_files/07163051.pdf) | 2015-05 | Medium |
| 3.5 | **Kohlbrenner and Shacham, USENIX Security 2017**: "Google Chrome, Mozilla Firefox, and Apple's Safari have insufficiently addressed the floating-point side channel". The paper shows cross-origin pixel extraction through SVG filters in each, and concludes "floating point is simply too variable to use in a timing security sensitive context." | 3 browsers | [USENIX abstract](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/kohlbrenner) | 2017-08 | High |
| 3.6 | **GPU.zip** (Wang et al., IEEE S&P 2024; disclosed March 2023). GPU lossless compression of framebuffers makes rendering time depend on the data. SVG filters applied to a cross-origin iframe produce data whose compressibility depends on a secret pixel. **Chrome** was vulnerable because it (1) loads cross-origin iframes with cookies, (2) allows SVG filters on iframes, and (3) renders on the GPU. Firefox and Safari did not meet all three conditions. As of September 2023 no GPU vendor had committed to a patch and Google was "still deciding". The proof of concept read a logged-in Wikipedia username. | n/a | [GPU.zip site](https://www.hertzbleed.com/gpu.zip/); [BleepingComputer](https://www.bleepingcomputer.com/news/security/modern-gpus-vulnerable-to-new-gpuzip-side-channel-attack) | 2023-09-26 | High |
| 3.7 | Google's response pointed to frame-blocking headers and to SameSite=Lax cookies by default. In other words, the mitigation is that the site refuses to be framed, not a fix in the renderer. | n/a | [BleepingComputer](https://www.bleepingcomputer.com/news/security/modern-gpus-vulnerable-to-new-gpuzip-side-channel-attack) | 2023-09 | Medium |
| 3.8 | The common pattern across 3.1–3.6: **any filter or compositing work whose cost depends on pixel values, applied to pixels the page cannot read, is an oracle**. Fixing one primitive (feMorphology in 2013) did not close the class. Floating point (2015, 2017) and hardware compression (2023) reopened it. | n/a | synthesis | n/a | Medium |

**Implications:** Izcal's integer-only rasterizer removes the subnormal floating-point channel (3.4, 3.5), but only if filters never fall back to floats or to data-dependent fast paths. Do not count on constant-time code alone. Make it a structural rule instead: **an SVG or CSS filter, mask or blend that reads backdrop or content pixels is never applied over cross-origin content**, meaning cross-site iframes, `:visited`-styled content or cross-origin images that are not CORS-clean. The renderer must treat those pixels as opaque, or not run the filter on them. Per-site process isolation already keeps cross-site iframe pixels outside the attacker's renderer. The compositor that applies effects across that boundary is where the rule must hold. Give each filter primitive a cost that does not depend on the data (no early exits on zero, transparent or uniform tiles) when its input may be secret.

**Implications:** Izcal's HTML parser and serializer must make namespace changes on a round trip impossible or detectable. Add WPT and mXSS corpora (DOMPurify's bypass vectors) as conformance tests, and expose a native sanitizer that knows SVG. Do not support `data:` in `<use>` (follow the current spec). Keep `data:image/svg+xml` out of any top-level `data:` exemption.

## 5. SVG as an image: restrictions and canvas taint

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | The SVG Integration draft defines processing modes. Images (`img`, CSS `<image>`) use **secure animated** mode (no script, no external references, SMIL and CSS animation allowed, no interactivity), or **secure static**. **Resource documents** (external `use`, `filter`, `mask`, `pattern`, `fill` and so on) are also secure animated. So are **font documents** (OpenType `SVG ` table). An external reference must be "treated as if a network error occurred". The document is still a 2014 First Public Working Draft. | 5 modes | [SVG Integration](https://www.w3.org/TR/svg-integration/) | 2014-04-17 | High |
| 5.2 | Why images may not fetch: an image that could load subresources would be a tracking pixel inside every `<img>`. It would also turn an image in email or a third-party context into a network beacon, and leak whether cross-origin resources are present. Script is banned because the image would otherwise run code in a context that never agreed to host it (4.1). The rationale is stated in the 2011 paper; the network-error rule in 5.1 is the mechanism. | n/a | Crouching Tiger, ACM CCS 2011 proceedings (cited by title); synthesis | 2011 | Medium |
| 5.3 | **`foreignObject` and canvas taint**: a page placed a cross-origin iframe in `<foreignObject>` inside an SVG and drew the SVG to a canvas, trying to read it back. A 2013 Chromium change let single-origin SVG images be drawn without tainting the canvas, but kept SVGs containing `foreignObject` tainting, along with external `<image>` and `<feImage>`. | n/a | [Christian Schneider, "Chrome SOP bypass with SVG"](https://christian-schneider.net/blog/chrome-sop-bypass/) | 2013 | Medium |
| 5.4 | Chrome release notes: all browsers tainted the canvas for an SVG with `foreignObject` loaded over HTTP. For `blob:` URLs, Chromium and WebKit tainted and Gecko did not, and Chromium then aligned with Gecko. WebKit discussion treated `foreignObject` as a leak mainly because of the HTML it can hold (`:visited` links, for example). | n/a | [chromestatus release notes](https://chromestatus.com/release-notes/170); [WebKit bug 119492](https://bugs.webkit.org/show_bug.cgi?id=119492) | 2013–2023 | Medium |
| 5.5 | `foreignObject` content in an image can still render **`:visited` styles, form autofill colours, system colours and fonts, and spelling marks**. Each is a read-back leak if the canvas stays clean. This is inferred from 5.3 and 5.4 and the history in §3. | n/a | synthesis | n/a | Low |

**Implications:** Make the processing mode a type-level property of an SVG document in Izcal: the scriptless media-process crates (MD-D20) cannot run script at all, which enforces "no script" by construction. The spec still needs: (1) the external-reference rule for image, resource and font documents (a network error, no fetch); (2) a rule that SVG-as-image renders `:visited` as unvisited, ignores autofill and uses no user-specific state, so that drawing it to a canvas leaks nothing and **the canvas need not be tainted even with `foreignObject`**. That is better than current browsers, and must be argued and tested before it is claimed; until then, taint with `foreignObject` as all browsers do. Same-origin SVG images render in the renderer; the same no-user-state rule must hold there.

**Implications:** The browser is the payload engine for these attacks. This is a product decision for the spec, and it should be measured against a corpus (what share of real `.svg` files on disk contain `<script>`, event handlers or `foreignObject`).

**Implications:** A Rust rewrite moved librsvg's bugs from memory corruption to **logic bugs** (path traversal, parser disagreement) and to its C dependencies. Izcal has no C dependencies, so the remaining risk is logic. Izcal must resolve every SVG URL once with the single URL parser it already has, and decide fetch policy on the parsed URL. MD-D20's media process for cross-site SVG images goes further than any browser documented here. The spec should state what that process may read (no file system, no network; resources are passed in by the renderer) so that a 7.3-style read is impossible by construction.

## Open questions for the spec

1. Black-box: what limits do Chrome, Firefox and Safari apply to `<use>` expansion count and depth, pattern recursion, filter region pixels, blur standard deviation, `feConvolveMatrix` order and path segment count? What happens when a limit is hit: blank element, whole image blank, or a crash or hang? Build a WPT-style stress corpus and time it.
2. Is there any published count of browser security bugs by component, showing the share in SVG and animation code? If not, can Izcal compute one from public bug-tracker prose (CVE descriptions that name SVG)?
3. Who owns blocking `javascript:` in animated `href`: the SVG spec or the animation spec? What is the behaviour for SMIL `values` lists?
4. Can SVG-as-image with `foreignObject` be made provably free of user state, so that canvas tainting can be dropped (§5)? What is the full list of user-specific inputs to rendering?
5. Policy for top-level SVG from `file:` and downloads: script off by default? Measure on a corpus of real-world `.svg` files first.
6. Do the cross-site filter rules in §3 also need to cover `backdrop-filter` and `mix-blend-mode` over cross-site iframes? This is shared with the graphics and compositing specs.
7. A deterministic budget for denial-of-service limits: which units (instance count, work units), and are they exposed to authors or only to DevTools?
8. Do SVG favicons and SVG cursors use the media process? Which processing mode does a favicon use?
