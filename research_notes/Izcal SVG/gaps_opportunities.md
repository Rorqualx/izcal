# Izcal SVG: gaps and opportunities

Compiled 20 October 2026. Primary sources were preferred (specifications, W3C charters and minutes, maintainers' posts, vendor documentation, issue trackers, papers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only, or the researcher's recollection.

M-1 note: no source code of any browser, engine or library was opened or cited (Chromium/Blink, WebKit, Gecko, Servo, Ladybird, librsvg, resvg, Skia and others). Bug-tracker rows cite prose discussion only. One search result was a third-party write-up describing Chromium's internal "SVG as image" structure; it appears to summarise source code, so it was not used, and the engine-internal claim in 3.5 rests on W3C prose and is marked as a question for black-box measurement. Where a row says what an engine "does", it is evidence to reason from, not a shape to copy.

**Method notes**
- 25 searches and fetches were used (the shared budget). Read in full or in substantial part: Scott O'Hara's 2019/2021 SVG accessibility test write-up; Léonie Watson's 2013 TPGi (now Vispero) ARIA-for-SVG article; the 2026 draft SVG WG charter; the February 2024 SVG WG continuation notice; the Firefox and Chrome animation-inspector documentation; Playwright's snapshot documentation.
- Other rows rest on search snippets of primary pages and are graded Medium. Rows from recollection are Low and repeated under "Claims not verified".
- "Idea" columns are ideas for the spec author, not designs.

## 1. Developer tooling gaps

| # | Finding | Evidence / numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **SMIL animation is invisible to both major animation inspectors.** Firefox: "It displays animations created using CSS transitions, CSS @keyframes rules, or the Web Animations API." Chrome: "The Animations panel supports CSS animations, CSS transitions, web animations, and the View Transitions API." Neither mentions SMIL (`<animate>`, `<animateTransform>`, `<animateMotion>`, `<set>`). | 0 of 2 inspectors list SMIL | [Firefox: Work with animations](https://firefox-source-docs.mozilla.org/devtools-user/page_inspector/how_to/work_with_animations/index.html); [Chrome: Animations panel](https://developer.chrome.com/docs/devtools/css/animations) | read 2026-10-20 | High |
| 1.2 | SMIL bugs reported by developers are timing and state bugs that a timeline would expose: animations inside masks never starting, `beginElement()` working twice then failing, inline-SVG SMIL not starting while standalone works, intermittent opacity animation. | 4 reports, 2010-2015 | [WebKit 38836](https://bugs.webkit.org/show_bug.cgi?id=38836), [WebKit 44382](https://bugs.webkit.org/show_bug.cgi?id=44382), [WebKit 139775](https://bugs.webkit.org/show_bug.cgi?id=139775), [Mozilla 1163875](https://bugzilla.mozilla.org/show_bug.cgi?id=1163875) | 2010-2015 | Medium |
| 1.3 | **Box model for SVG nodes was missing in the DevTools protocol.** Puppeteer issue 1247: `DOM.getBoxModel` returned no usable geometry for SVG elements; a 2018 Chromium change "teach DOM.getBoxModel to work with SVG nodes" closed it, but users later reported undefined width/height on visible SVG elements. The CSS box model (margin/border/padding) does not apply to SVG graphics elements; what developers need is the bbox, stroke bbox, CTM and viewport, which no panel shows. | 1 protocol gap; follow-up reports | [puppeteer#1247](https://github.com/puppeteer/puppeteer/issues/1247), [puppeteer#1357](https://github.com/puppeteer/puppeteer/issues/1357) | 2017-2018 | Medium |
| 1.4 | **Geometry APIs disagree and are hard to reason about without a view.** `getBBox()` ignores the element's and ancestors' transforms; `getBoundingClientRect()` is viewport-relative. Engines disagreed on nested `<use>` bboxes (a 2012 WebKit thread explains `<use>` acts as a `<g>` with x/y turned into a transform) and on `<textPath>`/`<tspan>` boxes; SVG 2 merged `getStrokeBBox()` into `getBBox()` options, which are unevenly implemented. A 2026 WebKit bug still disputes empty-container bboxes. | ≥3 interop disputes | [MDN getBBox](https://developer.mozilla.org/en-US/docs/Web/API/SVGGraphicsElement/getBBox); [www-svg 2016-01](https://lists.w3.org/Archives/Public/www-svg/2016Jan/0016.html); SVG WG action ACTION-3581 (recorded in the WG tracker; the repository changeset was not used, phase 8 FC-R1); [WebKit 323707](https://bugs.webkit.org/show_bug.cgi?id=323707) | 2012-2026 | Medium |
| 1.5 | `<use>` instances live in a closed, engine-generated shadow tree. DevTools in Chromium-based browsers show it as a user-agent shadow root only when a setting is enabled; no tool shows which referenced element and which re-cloning (after a mutation of the referenced subtree) produced a given instance, or the CSS cascade that applied inside it. | n/a | researcher recollection | n/a | Low |
| 1.6 | No mainstream inspector shows a **resolved paint server** (which `<linearGradient>` after `href` template inheritance, which stops, which `gradientUnits`/bbox it resolved against), a **filter region** or **primitive subregions**, or the **intermediate result of each filter primitive**. Developers debug filters by bisecting markup. | n/a | researcher recollection; implied by 1.1 docs listing no SVG views | n/a | Low |
| 1.7 | **Third-party tools fill the gaps the browser leaves.** SVGOMG (a GUI for SVGO) for minification and cleanup; svg-path-editor for editing `d` path commands visually. Their existence implies that browsers offer no path editing, no "what does this attribute cost" view and no "this markup is redundant" lint for SVG. | 2 widely used tools | [SVGOMG](https://jakearchibald.github.io/svgomg/); [svg-path-editor](https://yqnn.github.io/svg-path-editor/) | n/a | Low |

**Implications:** Izcal can own the SVG view nobody has: a SMIL timeline on the same clock as Web Animations (Izcal's virtual clock makes it scrubbable and replayable), a geometry overlay (bbox, stroke bbox, CTM, viewport, `viewBox` mapping), resolved paint servers, a per-primitive filter graph with each intermediate image, and `<use>` instance provenance from the mutation log. Each view can link to the `// spec:` anchor that produced it.

## 2. Accessibility gaps in practice

| # | Finding | Evidence / numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Without ARIA, SVG `title`/`desc` were almost unsupported in 2013.** Only IE10 exposed both `title` and `desc` and the SVG role; Firefox 25 swapped name and description; Chrome 30 and Safari 6 exposed none; VoiceOver and TalkBack ignored the SVG. With `role="img"` plus `aria-labelledby` pointing to `title` and `desc` IDs, the name was exposed in every tested browser. Children were hidden with `role="presentation"`. Commissioned by Adobe, tested by Steve Faulkner. | ~6 browsers, 4 screen readers | [Watson, Using ARIA to enhance SVG accessibility (TPGi/Vispero)](https://vispero.com/resources/using-aria-enhance-svg-accessibility/) | 2013-12-19 | High |
| 2.2 | **Inline SVG pattern that works everywhere (2019-2021 test):** `<svg role="img" focusable="false">` with a `<title>` child "will properly announce the SVG as an 'image' or 'graphic' in all tested screen reader and browser pairings." Decorative SVG needs `aria-hidden="true"`; otherwise some screen readers announce an unnamed "group". `<desc>` was not tested. Exported titles like "Created by Sketch" pollute names. | all pairings tested | [O'Hara, Contextually marking up accessible images and SVGs](https://www.scottohara.me/blog/2019/05/22/contextual-images-svgs-and-a11y.html) | 2019-05-22, upd. 2021-09-03 | High |
| 2.3 | **`<img src=*.svg>` was mis-exposed by Safari/VoiceOver** ("group" on macOS, skipped on iOS) until a fix confirmed in Safari 14.1.2 (macOS 11.5.2, iOS 14.7.1). | fixed by 2021-09 | same | 2021-09-03 | High |
| 2.4 | **SVG inside links and buttons is the weak spot.** `role="img"` + `aria-label` failed in buttons on legacy Edge and in links with IE11+NVDA and Edge+JAWS; JAWS could not reach the link at all with IE11 or Chrome. O'Hara's advice: make the SVG decorative and name the control. | several pairings | same | 2019-05-22 | High |
| 2.5 | **Graphics ARIA exists but charts rarely use it.** The WAI-ARIA Graphics Module (FPWD 2015) adds `graphics-document`, `graphics-object`, `graphics-symbol`, with Graphics-AAM mappings. MDN documents `graphics-document` for flowcharts, maps and diagrams. No survey of adoption or screen-reader behaviour was found this session. | 3 roles | [W3C blog, Graphics Module published](https://www.w3.org/blog/2015/12/wai-aria-graphics-module-published); [MDN graphics-document](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/graphics-document_role); [Graphics-AAM](https://w3c.github.io/aria/graphics-aam/) | 2015-12; read 2026-10-20 | Medium |
| 2.6 | **Forced colors and SVG are inconsistent.** Chrome and Edge on Windows apply a UA style `forced-color-adjust: none` to SVG, while Firefox forces `currentColor` to the text colour; the CSS WG moved forced colours to used-value time, which stopped inherited values being forced and broke icons that relied on it. Guides now advise `@media (forced-colors: active)` rules with system colours. | 2 behaviours | [csswg-drafts#6310](https://github.com/w3c/csswg-drafts/issues/6310); [WWU forced colors guide](https://marcom.wwu.edu/accessibility/guide/support-forced-colors) | 2021-05; n/a | Medium |
| 2.7 | **SVG text is often not text to the user.** Wikimedia's SVG Translate tool fails on nested `<tspan>` and CSS ID selectors; WordPress translation tools refuse SVG text as "basically images". Whether browser find-in-page, selection and machine translation reach inline SVG `<text>` consistently was not found in published tests. Text converted to outlines carries no text at all. | n/a | [Wikimedia T231143](https://phabricator.wikimedia.org/T231143); WPML forum thread (link dead at phase 8) | 2019-2021 | Medium (tools); Low (browsers) |
| 2.8 | **Focus in SVG:** SVG 2 adds `tabindex` on SVG elements; `focusable` is an IE-only legacy attribute that authors still add. | n/a | [O'Hara](https://www.scottohara.me/blog/2019/05/22/contextual-images-svgs-and-a11y.html); [Watson](https://vispero.com/resources/using-aria-enhance-svg-accessibility/) | 2013, 2019 | Medium |

**Implications:** Izcal's semantic plane can show the author tree, the repaired tree and why, for SVG specifically: "this `<svg>` has no name, its `<title>` is 'Created by Sketch'", "this decorative SVG would be announced as an unnamed group", "this chart has 500 `graphics-symbol` nodes with no names". Forced colours behaviour must be chosen and documented per SVG-AAM and CSS Color Adjust, and Izcal should make SVG `<text>` participate in find, selection and translation like HTML text, with a black-box test against other engines.

## 3. Footprint and performance

| # | Finding | Evidence / numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Practical SVG ceilings are thousands of marks.** ApexCharts puts the SVG ceiling at "a few thousand individual marks" and auto-switches to canvas above 8,000 points. | ~8,000 points | [ApexCharts blog](https://apexcharts.com/blog/svg-vs-canvas-charts); [ApexCharts canvas renderer](https://apexcharts.com/docs/canvas-renderer/) | 2026 | Medium |
| 3.2 | Horak et al. (TU Dresden poster): D3 node-link graphs lost interactivity from about 400 nodes (~8,000 graphical elements), and SVG and canvas performed about the same, against the common assumption. | ~400 nodes / ~8,000 elements | [Horak 2018 poster](https://mt.inf.tu-dresden.de/cnt/uploads/Horak-2018-Graph-Performance-Poster.pdf) | 2018 | Medium |
| 3.3 | JointJS handled 11,000+ DOM elements unoptimised and 100,000 only by switching to canvas at extreme zoom. A 2019 micro-benchmark (Chrome 73) drew 1,000 objects in ~10 ms with SVG vs ~1 ms with canvas. | 11k; 100k; 10 ms vs 1 ms | [JointJS](https://www.jointjs.com/blog/jointjs-performance-overview-testing-diagrams-with-100-000-nodes); [LogRocket](https://blog.logrocket.com/when-to-use-html5s-canvas-ce992b100ee8) | 2019-2024 | Medium |
| 3.4 | **No published bytes-per-SVG-element figure** for any engine was found. | none | n/a | n/a | n/a |
| 3.5 | **SVG as image is defined as script-free and fetch-restricted.** The W3C SVG Security wiki: an SVG fetched as an image must not run scripts or fetch resources, and SVG resources get the same restrictions. SVG 1.2 Tiny defines a "secure static" mode. Anne van Kesteren (2014) noted that "SVG as image" is "not very well defined". Whether engines share one parsed document across `<img>` instances of one URL, or cache rasters at several scales, is not stated in prose found this session. | n/a | [W3C SVG Security wiki](https://www.w3.org/wiki/SVG_Security); [Restricted SVG fetching model](https://www.w3.org/Graphics/SVG/WG/wiki/Proposals/Restricted_SVG_fetching_model); [public-webappsec 2014-04](https://lists.w3.org/Archives/Public/public-webappsec/2014Apr/0033.html) | 2014 | Medium |
| 3.6 | Icon sprites (`<symbol>` + `<use href="sprite.svg#id">`) are the common way to share icon geometry, but cross-origin sprites fail (see 6.3), which pushes sites to inline the same paths hundreds of times. | n/a | [svgwg#707 discussion](https://lists.w3.org/Archives/Public/public-svg-issues/2019Jul/0064.html) | 2019 | Medium |

**Implications:** Izcal can publish what others do not: a measured bytes-per-element budget for SVG nodes (DOM columns plus SVG geometry), shared immutable parsed documents for repeated SVG images (MD-D20's scriptless media process already has no JS heap), and a canvas-class threshold target (for example, 10,000 animated marks at 60 fps) measured on the reference rig. A DevTools view "memory and paint cost per SVG subtree" would answer the "should this be canvas?" question with data.

## 4. Privacy and side channels

| # | Finding | Evidence / numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Font metrics fingerprinting.** Fifield and Egelman measured glyph bounding boxes in over 1,000 browsers: 34% were unique; 43 code points captured all variation; a standard-font whitelist was estimated to cut unique users below 10%. Any API that returns text geometry (`getBBox`, `getComputedTextLength`, `getExtentOfChar`, `getBoundingClientRect` on `<text>`) is the same surface. | 34% unique; 43 code points; <10% with whitelist | Fifield and Egelman, "Fingerprinting Web Users through Font Metrics", Financial Cryptography 2015 proceedings (cited by title; the Berkeley page was dead at phase 8) | 2015 | Medium |
| 4.2 | **Tor Browser's defence** was a font whitelist (`font.system.whitelist`) and then bundled fonts only (TBB 5.5, January 2016); Tor noted the whitelist still lets OS and OS-version be distinguished. No SVG-specific fingerprinting paper was found; SVG text APIs are not treated separately in the sources read. | TBB 5.5, 2016-01 | [Tor #18097](https://archive.torproject.org/websites/lists.torproject.org/pipermail/tbb-bugs/2016-January/006042.html); [arXiv 1605.08664](https://arxiv.org/pdf/1605.08664) | 2016 | Medium |
| 4.3 | **SVG filter timing attacks.** Paul Stone (2013) read cross-origin pixels by timing SVG filters; the `feMorphology` fast path made solid regions faster. Firefox fixed it in Firefox 22 (MFSA 2013-55); a full constant-time fix took about two years. Later work still cites data-dependent SVG filter timing for pixel stealing. | Firefox 22; ~2 years | [MFSA 2013-55](https://www.mozilla.org/security/advisories/mfsa2013-55); [Stone, Pixel Perfect Timing Attacks](https://wiki.owasp.org/images/1/10/HackPra_Allstars-Browser_Timing_Attacks_-_Paul_Stone.pdf); [Kohlbrenner, subnormal slides](https://homes.cs.washington.edu/~dkohlbre/papers/subnormal-slides.pdf) | 2013-2017 | Medium |
| 4.4 | **SVG clickjacking (December 2025).** Lyra Rebane showed that `feColorMatrix`, `feDisplacementMap` and `feComposite` form logic gates and can read colours from a framed cross-origin page inside a filter, enabling interactive clickjacking (demo against Google Docs). The Register called it "yet to be fully mitigated". | n/a | [lyra.horse, SVG clickjacking](https://lyra.horse/blog/2025/12/svg-clickjacking/); [The Register](https://www.theregister.com/2025/12/05/css_svg_clickjacking/) | 2025-12 | Medium |
| 4.5 | The "Deterministic Browser" paper argues for removing timing channels by making the browser's clocks deterministic. | n/a | [arXiv 1708.06774](https://arxiv.org/pdf/1708.06774) | 2017 | Medium |

**Implications:** Izcal's integer-only, deterministic rasterizer should be specified as **constant-time with respect to pixel content** for filters (no data-dependent fast paths observable through frame timing), and SVG text geometry APIs should use the same font-visibility policy as CSS and canvas. Rebane's attack is a cross-origin data flow through filters on framed content; the spec should state whether filters may sample cross-origin frame pixels at all.

## 5. New interactions and opportunities

| # | Finding | Evidence / numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **LLMs read SVG charts from markup, unreliably.** GPT-4-turbo pulled values from labelled SVG plots but dropped in accuracy without labels and invented data points. | 10 task types | [Xu and Wall, arXiv 2404.19097](https://arxiv.org/abs/2404.19097) | 2024 | Medium |
| 5.2 | A multi-agent pipeline (Socratic Chart) that extracts bar heights, line coordinates and pie proportions from SVG beat GPT-4V and Gemini 2.0 Pro on ChartQA-type benchmarks; a York thesis deconstructed 93.4% of 800 SVG charts. | 93.4% of 800 | [arXiv 2504.09764](https://arxiv.org/html/2504.09764v1); [York thesis](https://yorkspace.library.yorku.ca/bitstreams/614e149e-a4e3-49f5-8af8-db8957bb8118/download) | 2024-2025 | Medium |
| 5.3 | **Visual regression is non-deterministic across machines.** Playwright: "Browser rendering can vary based on the host OS, version, settings, hardware, power source (battery vs. power adapter), headless mode, and other factors"; baselines must come from the same environment, and snapshot names carry browser and platform. | n/a | [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots) | read 2026-10-20 | High |
| 5.4 | Printing SVG to PDF keeps vectors for simple shapes, but filters, masks and some blend modes are rasterised in common engines. | n/a | researcher recollection | n/a | Low |

**Implications:** Izcal can offer agents (through the agent principal, with consent) the **resolved scene** of an SVG: final geometry in user space, resolved fills, text, and accessibility roles, instead of raw markup to guess from. GR-D3's bit-identical output makes SVG snapshot tests portable across OS, CPU architecture and machine, which no current browser can promise. A vector PDF path (Izcal PDF) can state per feature whether it stays vector or is rasterised, and DevTools could show that before printing.

## Open questions for the spec

1. SMIL: does the SVG spec or the animation spec own it, and will both share one timeline so DevTools can show SMIL next to CSS and WAAPI (1.1)?
2. Bytes per SVG element and per `<use>` instance in Izcal: what budget, and a black-box measurement of other engines (heap snapshots with 10k/100k `<rect>`) to compare (3.4).
3. Do other engines share one parsed SVG document across `<img>` instances of the same URL, and cache rasters per scale? Black-box: memory growth for 1 vs 1,000 `<img>` of one SVG at several sizes (3.5).
4. Do find-in-page, selection and translation reach inline SVG `<text>` in Chrome, Firefox and Safari? Black-box test (2.7).
5. Forced colours: which behaviour does Izcal choose for SVG `fill`/`stroke` and `currentColor`, and how is it shown in DevTools (2.6)?
6. Filters: must the rasterizer be constant-time per pixel value, and can filters ever sample cross-origin frame content (4.3, 4.4)?
7. Which agent-facing "resolved scene" format: a JSON of resolved geometry and paint, the accessibility tree, or both (5.1-5.2)?
8. Does Izcal ship `inline-size` wrapping and CSS `d`, and cross-origin `<use>` with CORS, ahead of the standard (6.3-6.5)?

- 1.6: that no mainstream inspector shows resolved paint servers, filter regions or per-primitive results is recollection; a check of current Chrome, Firefox and Safari DevTools is needed.
- 1.7: SVGOMG and svg-path-editor descriptions and URLs were not re-fetched this session.

- 4.1: the paper measured HTML text boxes; that SVG text APIs give the same entropy is an inference, not a measured result.
