# Izcal images and media: security_robustness

Compiled 19 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Method notes.**
- Section 1's tally is this note's own count. Project Zero's 0-day "In the Wild" sheet ([P0 0-day ITW sheet](https://docs.google.com/spreadsheets/d/1lkNJ0uQwbeC1ZTRrxdtuPLCIl7mlUreoKfSIgajnSyY/)) was exported as xlsx on 19 October 2026 and parsed locally: **412 unique CVE rows** (the year tabs add one duplicate, CVE-2022-22265, which an earlier count included), 2014 to 2026 (the fonts note counted 412; two rows were added since). Rows were selected by reading every row whose product or description names an image, codec, media, audio, video, WebRTC, PDF image codec or graphics component, then classified by hand. CVE descriptions were checked against the CVE records.
- No source code of any browser or codec library was opened (M-1). Root causes come from Project Zero RCAs, vendor advisories, CVE records, researcher write-ups and maintainers' prose.
- The shared web-search budget ran out after 12 searches. Everything after that was read by fetching known primary pages directly. Items that could not be reached are graded Medium or Low and listed at the end.
- Overlap: the security scope notes already hold the TAG 2023 figures (media and codecs 4 of 37 Chrome 0-days, 11%), the CrabbyAVIF near-miss and the FORCEDENTRY sandbox escape. This note re-checks them where they carry the design and adds decoder-specific detail.

**Implications:** Every image exploit with a public root cause is a **size or count from the file that disagrees with an allocation** (2.1, 2.4, 2.6, 2.7). Izcal's image pipeline should decode only the format the Fetch/HTML sniffing rules selected, with one decoder per format, and never fall through to "any codec the platform has".

**Implications:** The dominant class is a mismatch between a value read from the file and the memory it governs. A parser generated from the format's own value ranges (3.4) plus allocation from checked arithmetic over those values removes it by construction; memory-safe code turns the rest into errors or panics. Races and lifecycle bugs need a different tool: an ownership model across threads and explicit codec state machines.

## Design implications for Izcal (ideas, not decisions)

1. **Generated and proved parsers.** Generate every header and container parser (ISO-BMFF, Matroska/EBML, Ogg pages, MPEG-TS, PNG chunks, JPEG markers, RIFF/WebP, GIF blocks, AV1 OBU and sequence headers, VP8/VP9 frame headers, H.264/HEVC parameter sets when parsed by Izcal, ICC tags, Exif IFDs) from a description that carries the specification's value ranges and cross-field constraints (3.4, 2.6), with EverParse-class proofs: bounds, exact acceptance, single read, no allocation, double-fetch freedom (8.2). Write entropy decoders and reconstruction in a restricted Rust subset where every index and arithmetic operation carries a discharged proof obligation (Wuffs's model, 6.6), and build Huffman and ANS tables in a separate validating pass before any table write (2.1).
2. **Panic and allocation policy.** Decoders cannot panic: no `unwrap`, no indexing that can fail, checked arithmetic that returns errors (7.5). All memory comes from a per-decode budgeted allocator sized from validated headers before any pixel or sample work; no allocation proportional to an unvalidated field; no recursion over input structure; a fuel counter on every loop driven by input. Budgets (pixels, bytes, frames, CPU) are canonical, per (site, container), and recorded under B1 (10.1–10.5). Any `unsafe` (SIMD should not need it after Rust 1.88, 6.2) is confined to one audited crate with its own fuzz target and Miri runs, because the one Rust media CVE was there (6.10).
3. **Fuzzing targets.** One structure-aware target per generated parser, driven from the same description; one target per decoder that **builds valid intermediate structures** (four maximal Huffman tables then one invalid, 2.2) rather than flipping bits; a **control-sequence** target for WebCodecs and `HTMLMediaElement` (configure, reset, flush, reconfigure, close in random order, 9.9); a **thread-interleaving** target for the audio graph (3.8, 3.9); differential targets against conformance streams and black-box engines; regression inputs for every root cause in Sections 2–5.
4. **Process placement.** Keep FP-D11 (b): one decoder process per (site, container), compute-only, no device, file or network access, normalised plane outputs re-validated by the GPU service and audio service, BlastDoor-style exponential restart throttling after crashes (9.3), and no decoder in the broker, GPU service or network service. OS decoders and CDMs run only in such processes (Q-SEC-4, SEC-33). Route every image and media byte through it, including images in fonts, PDF, favicons and notifications (2.4, 9.4).
5. **Surface.** One decoder per sniffed format and no fall-through (2.4); no legacy sub-features without web demand (BMP-embedded JPEG/PNG, 6.4); a "Lockdown"-style profile that drops formats and Web Audio for high-risk users (9.5, 9.6).
6. **Privacy.** Identical software output everywhere; codec support fixed per build (FP-D13); `powerEfficient` and smoothness reported from policy, not live hardware, unless the user opts in; content-dependent timing kept off cross-origin pixels; ORB's "subsequent" range marker set only by the network service, never the renderer (11.4).
