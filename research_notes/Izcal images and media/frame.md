# Izcal images and media: frame

Written 19 October 2026 (phase 1 of the first-principles-spec method, `.claude/skills/first-principles-spec/SKILL.md`).

## The problem and who has it

Images are most of the bytes of the web and video is most of the bytes of the internet. Izcal must turn encoded images (PNG and APNG, JPEG, GIF, WebP, AVIF, BMP and ICO, and a decision on JPEG XL), media containers (MP4/ISO-BMFF, WebM/Matroska, Ogg, MPEG-TS for HLS) and audio and video bitstreams (AV1, VP9, VP8, Opus, Vorbis, FLAC, MP3, and a decision on H.264, H.265 and AAC) into colour-correct pixels and sample-accurate sound, through the web's media APIs: `HTMLMediaElement`, Media Source Extensions, WebCodecs, Web Audio, media capture, WebRTC media, Encrypted Media Extensions, WebVTT, Picture-in-Picture and autoplay policy. HGBA-2 2.3.0 to 2.3.2 (M-1 part 1) exclude every library that does this work: libpng, libjpeg-turbo, giflib, libwebp, libavif, dav1d, libaom, libvpx, FFmpeg, GStreamer, Skia's codecs, image-rs and zune as engine components, Symphonia, cubeb and every library doing the same job. **OS media frameworks and hardware decoders are OS interfaces and are allowed.** Everything that ships must be available under MIT; anything else Izcal builds. Codec **patent** licensing is a separate question from copyright licensing and is treated separately.

The owner's direction (19 October 2026): no shortcuts for time or complexity; staging only for correctness, security or measurement reasons; cost is a planning fact. Image and media parsers are one of the top attack surfaces in browsers, so security is designed from first principles: the FP-D11 decoder process, memory safety, generated parsers, fuzzing.

Who has the problem:
- **People reading and watching**: images must appear quickly at the right size and colour, video must play smoothly with sound in sync, on battery, with captions, and a hostile file must never compromise them or fingerprint them. Paid streaming content must play (D-S7).
- **Web developers**: they need the formats and APIs other browsers support (P2), predictable decode timing (`decode()`, `loading=lazy`, `fetchpriority`), correct HDR and wide-gamut rendering, and visibility into why an image was slow, blurry or wrong in colour, or why a video stalled.
- **Real-time applications**: video calls (WebRTC media, `getUserMedia`), audio production (Web Audio, AudioWorklet) and media editors (WebCodecs) need low latency and stable timing.
- **Layout, paint, the GPU service, fonts and text, and the semantic plane**: they need intrinsic sizes, decoded pixels in a known colour space, frames on the compositor's clock, and alt text and captions.
- **Izcal's engineers and agents**: media must replay deterministically under B1 where it is web-observable, and every decoder must be testable against its specification and conformance streams without other engines' or codec libraries' code.

## What Izcal's specs already decide or constrain

- **HGBA-2 2.3.2** (`reports/HGBA 2 browser architecture spec.md`): M-1 parts 1–4 (no engine libraries; MIT only for everything shipped, with exceptions for standards bodies' data, test-only inputs, OS interfaces, drivers and the toolchain; another engine's source code is never evidence; spec-anchored oracles decide correctness); P1–P6 precedence; I-1 (never two sites' data in one address space), I-2 (zero ambient authority; I-2 note: the **protected-media host**), I-3 (layered in-process defences); HAL device class **`MediaCodec`** (OS hardware decoders and encoders) with a measured cost model, device loss and fallback semantics (Section 5); S-5 (library sandboxing, Stage 2). OS media frameworks are named among allowed OS interfaces.
- **HGBA-3** (`reports/Future software browser engine.md`): B1 deterministic substrate (DET-1), B2 typed capability IPC, B5 incremental core with reference path, B8 semantic plane, B9 agent principal, B10 AI off by default; VER-1 Tier 1 verified parsers include "image, font and media container headers"; PRIV-2 fingerprinting bound.
- **Stage 1 design** (`reports/HGBA Stage 1 architecture design.md`): process map (utility processes do "media and image decode"; the protected-media host); crate graph names `hg-media` and `hg-gpu`; G1–G9; Section 3 "GPU, audio, media: out of scope for simulation in Stage A"; 7.5 fuzzing of image and media container headers; M7 "Breadth: images, fonts, media and PDF via utility processes; EME with Clear Key and native PlayReady (Windows); protected media mode; autoplay policies; PQC for WebRTC DTLS". **D-S7 (decided)**: DRM through licensed components only (protected media mode via WebView2 and WKWebView; native PlayReady through Media Foundation at M7; Clear Key always; Linux Clear Key only until licensing succeeds; never an unlicensed CDM). DRM-1 and DRM-2 spikes (`m0/drm-spike/`) ran capability probes; playback tests deferred. **13.2 "Codecs"**: dav1d, libvpx (superseded by 2.3.0), H.264, AAC and HEVC only through OS decoders because of MPEG LA royalties, OpenH264 (Cisco binary) for WebRTC (not MIT; must be re-decided), AV1 kept despite Sisvel and Access Advance pools, legal review of codec exposure required before M7.
- **Security scope** (`reports/Izcal security scope.md`, draft 0.2, main repository): ATK-3 (hostile input to a privileged parser), TB-6, TB-9; Section 6.10 (codecs, images, fonts, PDF: Rust by default, C decoders sandboxed, OS decoders in utility processes where the OS allows, Q-SEC-4), 6.10a (WebRTC media in utility processes; native PlayReady in a dedicated CDM process per (site, container), SEC-33, Q-SEC-17); SEC-12, SEC-30; Q-SEC-13 (decoder placement).
- **JavaScript engine spec** (draft 0.3): **JS-D15** decision points are recorded B1 inputs; JS-D12 cross-ISA identity (no FMA contraction, one implementation of each math function); `hg-math` (L2s, JS-owned); G13–G18.
- **Resource footprint spec** (draft 0.3, accepted): **FP-D11 (b)** a decoder process per (site, container), never pooled across sites, exits after 10 s† idle (FP-38: ≤ 2 MiB† idle, 0 extra copies to the GPU service); 6.5 images (encoded bytes once per partition, decode on demand within a viewport margin, downscale on decode, one decoded copy in a GPU-service-fixed discardable shared region, animated images hold ≤ 2† decoded frames; AVIF and JPEG XL peak decode memory to be measured before the decoders are specified); **FP-D13 (a)** every codec ships in every build, identical everywhere, nothing fetched on demand; FP-13 (decoded image bytes); FP-14 (GPU budgets, ledger kind "video"); 6.8 background policy (audible media and PiP are declared reasons; "media pipeline as needed"); FP-17 to FP-23 (wakeups, energy, attribution); FP-25 (installer). **No explicit energy budget for video playback exists in FP**: this spec proposes one as an amendment. `hg-image` is FP's engine-image crate, so decoder crates need other names.
- **Networking spec** (draft 0.3.2): WebRTC transport (`hg-ice`, `hg-dtls`, `hg-srtp`, `hg-sctp`) in the partition service; decoded media never enters it; SRTP payloads never recorded; `hg-compress` (L2s, NW-owned) provides inflate for PNG; partition key (T, C, F, X, N, n) and the renderer projection (T, C, X, n) for in-process caches (P18); Fetch, range requests and the HTTP cache for media.
- **Fonts and text spec** (draft 0.3.3): PNG, JPEG and TIFF inside `sbix` and `CBDT` are decoded in the FP-D11 decoder process; OT-SVG glyphs are rendered by the renderer's own SVG engine in a restricted glyph mode; COLRv1 is TX's.
- **HTML and CSS parsing and style spec** (draft 0.3.2): CSS Color 4 and 5 parsing and computed values, `image-set()`, `calc()` through `hg-math`; layer rule G24 (L2s).
- **Phase 2 reconciliation**: L2s layer; G-rule registry (G19–G36 taken; the layout spec is reserved room; **this spec starts at G50**); partition-key projection; cache classes (FP-D16, canonical-exempt sub-class OD-4); combined staffing 216–285†.
- **Licence audit**: OS media frameworks, DRM modules and the WebView2/WKWebView runtimes are class 5 (OS interfaces); "software codecs written by Izcal are possible; hardware decode is not" an Izcal build.

## Success, in measurable terms

1. **Conformance**: every shipped decoder passes its format's conformance suite bit-exactly where the format defines exact output (AV1, VP9, VP8, Opus within its stated tolerance, FLAC, PNG, lossless WebP, JPEG within T.83 tolerances), and WPT `html/semantics/embedded-content/`, `media-source/`, `webcodecs/`, `webaudio/`, `mediacapture-*`, `webvtt/`, `encrypted-media/` and `css/css-color/`-related image tests pass at floors set at a named milestone.
2. **Security**: no decoder or demuxer runs in a renderer or the broker unless the security owner rules otherwise; every parser of a container or bitstream header is generated from a description or proved bounded; fuzzing with zero open crash bugs older than a set window.
3. **Footprint and energy**: FP-13 holds; a new video-playback energy budget is set from measurement and holds; hardware decode is used where the OS offers it and is measured.
4. **Smoothness**: dropped-frame and A/V-sync targets for playback; audio glitch targets; latency for Web Audio and WebRTC.
5. **Determinism**: decoder output is a pure function of input bytes (bit-identical across OS and ISA for software decoders); timing-dependent media decisions are recorded B1 inputs (JS-D15).
6. **Privacy**: codec and capability exposure adds no bits beyond the build (FP-D13, PRIV-2) except where hardware differences are unavoidable and are bounded.
