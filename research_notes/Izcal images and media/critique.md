# Izcal images and media: independent design critique (phase 8)

Written 19 October 2026 by a reviewer who did not write the spec. Subject: `reports/Izcal images and media.md`, draft 0.1 (line numbers below refer to that draft as read on 19 October 2026). Method: `.claude/skills/first-principles-spec/SKILL.md`, phases 6–8 (design critique against the existing specs, looking for contradictions, missed constraints, M-1 violations, infeasible or unfalsifiable targets and gaps), with `references/spec-template.md` and `references/izcal-capabilities.md`.

**Read against:** HGBA-2 2.3.2 (status line, M-1 parts 1–4, P1–P6, I-1 and its extensions, I-2 and the protected-media note, I-3, Section 5 HAL and 5.5, S-5); Stage 1 design (Section 1 process map, 2.2 G1–G9, 3.2–3.3, 8.1–8.3, 11 D-S1, 13.1a D-S7, 13.2 "Codecs"); security scope draft 0.2 (6.3a, 6.6 IPC-R1 to IPC-R17, 6.7, 6.10, 6.10a, SEC-12, SEC-30, SEC-33, SEC-D3, Q-SEC-4, Q-SEC-13, Q-SEC-17, TB-6, TB-9; read-only in the main checkout); coding standard draft 0.2 (6.2 tiers P/R/O/T, CS-ER-1, CS-ER-3, CS-TY-12, CS-TY-13, CS-TE-13, CS-T2; read-only in the main checkout); JavaScript engine spec 0.3 (JS-D9, JS-D12, JS-D15, JS-D17, G13–G18, 6.9); resource footprint spec 0.3 (FP-D4, FP-D11, FP-D13, FP-D19, FP-1, FP-13, FP-17 to FP-25, FP-36, FP-38, 6.5, 6.8, 8.2 and the rule "memory and energy thresholds are absolute"); networking spec 0.3.x (6.12, `hg-compress`, `hg-crypto` and G36, the (T, C, X, n) projection); fonts and text spec (6.1–6.3 placement table, `sbix`/`CBDT`, OT-SVG, TX-D18); style spec (6.9 `calc()` and colour via `hg-math`, G20–G24); layout spec draft (G37–G43); Phase 2 reconciliation (P1, P5, P7, P18, Sections 7 and 8) and `licence_audit.md` (OD-L2, class 5). The spec's eight research notes were read for the M-1 source check only.

**Owner direction applied as binding:** all engine work is Izcal's own (no libpng, libjpeg-turbo, giflib, libwebp, libavif, dav1d, libaom, libvpx, FFmpeg, GStreamer, Skia codecs, image-rs/zune, Symphonia, cubeb or any library doing this work; codec libraries count as engine libraries); OS media frameworks and hardware decoders are OS interfaces; MIT only for everything shipped; patents handled honestly and separately from copyright; no shortcuts for time or complexity, staging only for correctness, security or measurement; image and media parsers are a top attack surface; JS-D15, the FP budgets and decisions, and the NW decisions hold.

**Overall.** The spec's core is strong and original: one `.hgbits` description per format with generated, proved parsers; validated entropy tables (G52); budget handles and fuel; a pure-function output contract for software decode; canonical limits; a stateless autoplay rule; display conversion only at the end; and an honest treatment of H.264 patents. Its weak points are where it crosses process and trust boundaries it does not own, and where its targets are set without arithmetic. G56 (opaque media never in the renderer) is undermined by the spec's own byte routing; the per-site media process is given kernel-driver access that the security scope's strictest tier forbids; the renderer-to-media handoff violates IPC-R7 in exactly the libwebp pattern; MD-53, MD-31 and MD-54 cannot pass or cannot fail as written; MD-D11's reversal trigger cannot fire on the devices it harms; the AudioWorklet design depends on JS-engine properties the JS spec does not provide; and MD-D4's recommendation would read libvpx- and libopus-derived code when a black-box route exists.

## Summary

**Counts: 48 findings: 9 High, 21 Medium, 18 Low.** Plus 24 reconciliation items (R1–R24), the M-1 source-evidence check (no direct engine or codec source link; six grey-zone pages hosted in browser, engine or codec-library repositories, three of which carry a value into the report (one only as a Low-confidence motivation)) and the licence check (no non-MIT shipped dependency found; four classification gaps in "standards data").

High findings, one line each:

- **C1** G56 is defeated by the spec's own routing: opaque encoded bytes live in, and pass through, the renderer, and the media process is wrongly said to hold "nothing new".
- **C2** Encoded bytes reach the media process as a writable shared-memory handle with "no copy", against IPC-R7; G52's two-pass table build then double-fetches, the libwebp pattern.
- **C3** The per-site media process gets GPU and hardware-decoder kernel interfaces (video-only device, VideoToolbox, Media Foundation), which the security scope's strictest compute-only tier forbids; MD-D10's rationale ignores the sandbox-escape surface.
- **C4** MD-53's media-process memory caps (24 MiB at 1080p, 64 MiB at 4K) are smaller than AV1's mandatory reference-frame storage.
- **C5** MD-31's "no timing difference" clause cannot pass: `img.decode()` and load timing expose content-dependent decode cost by design.
- **C6** MD-D11 tells sites AV1 is `powerEfficient` on devices without AV1 hardware, and its reversal trigger is measured by MD-54, which excludes exactly those devices.
- **C7** MD-54 makes playback energy relative to the OS player, against FP's owner-accepted rule that energy thresholds are absolute; on Linux it compares Izcal's software H.264 with mpv's hardware decode.
- **C8** AudioWorklet on a real-time thread needs JS-engine guarantees (bounded per-agent GC, no cross-agent safepoints, no locks or W^X toggles) that the JS spec does not state; MD-9 and MD-10 rest on them with no fallback.
- **C9** MD-D4 recommends reading the libvpx- and libopus-derived code in RFC 6386 and RFC 6716, against the owner's direction and M-1 part 3, on the incorrect premise that exact VP8 is otherwise impossible.
