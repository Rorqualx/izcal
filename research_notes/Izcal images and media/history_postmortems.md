# Izcal images and media: history and postmortems

Compiled 19 October 2026. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

M-1 note: this file records ideas, dates, measurements and stated reasons. No source code of any browser or codec library was opened. Issue-tracker prose (Mozilla Bugzilla comments read through its REST API), mailing-list posts, release notes, blog posts and prose root-cause write-ups were used. Where a row says what a project "does", that is evidence to reason from, not a shape to copy.

**Method notes**
- About 40 searches and fetches were used. Apple's Safari release notes were read as structured text from developer.apple.com, so Safari version rows are High.
- Mozilla Bugzilla bugs 195280 (MNG removal) and 680385 (arithmetic JPEG) were read in full through the REST API. Their stated reasons are quoted.
- The Chromium issue tracker (JPEG XL removal, comment 85) refused automated access. The 2022 reasons are taken from press coverage that quotes them, graded Medium.
- Rows that rest on the researcher's recollection, not on a source read this session, are graded Low and repeated under "Claims not verified".

## 1. The first still-image formats: GIF, PNG, JPEG

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **GIF89a** defines LZW-compressed, palette-indexed images with a graphic control extension (delay, disposal, transparent index). Looping animation came from a vendor application extension (Netscape), not the base spec. Era constraint: 8-bit displays and modems; a palette and a dictionary coder were the cheapest useful choices. | ≤256 colours per frame, 1-bit transparency | [GIF89a specification](https://www.w3.org/Graphics/GIF/spec-gif89a.txt) | 1990-07-31 | Medium (looping extension origin from recollection) |
| 1.2 | Unisys enforced its LZW patent against software vendors from 1993; CompuServe and Unisys "quietly announced" a GIF royalty deal on 28 December 1994. | — | [Roelofs, "History of the PNG format"](http://www.libpng.org/pub/png/pnghist.html) | 1994-12-28 | High |
| 1.3 | **PNG** was designed in reaction: Thomas Boutell posted the first draft (then "PBF") on 4 January 1995; Draft 9 was "officially frozen" in early March 1995; libpng and zlib were usable by 1 May 1995; W3C Recommendation 1 October 1996; RFC 2083 in January 1997. The format used deflate because it was believed patent-free. | ~2 months draft to freeze | [Roelofs, PNG history](http://www.libpng.org/pub/png/pnghist.html) | 1995-1997 | High |
| 1.4 | Browser adoption of PNG was slow and partial: IE 4 beta (May 1997) incomplete; Netscape 4.04 (11 Nov 1997) native PNG; full alpha in Mozilla only by 13 August 2000. Netscape removed PNG-writing code in April 1998 "for legal reasons" over claimed deflate patents. | ~5 years from spec to full alpha | [Roelofs, PNG history](http://www.libpng.org/pub/png/pnghist.html) | 1997-2000 | High |
| 1.5 | The LZW patents expired (US June 2003, elsewhere by 2004), removing GIF's legal problem but leaving its technical limits. GIF survived as the animation format of the web because PNG declined to animate (see 2.x). | — | [Wikipedia, GIF (patent section)](https://en.wikipedia.org/wiki/GIF#Unisys_and_LZW_patent_enforcement) | 2003-2004 | Low |
| 1.6 | **JPEG (ITU-T T.81 / ISO 10918-1)** defines baseline sequential DCT, progressive DCT, arithmetic entropy coding, hierarchical and lossless modes. The web adopted only the Huffman baseline and progressive subsets, carried in **JFIF**. | 8-bit baseline; 12-bit extended | [ITU-T T.81](https://www.w3.org/Graphics/JPEG/itu-t81.pdf); [JFIF 1.02](https://www.w3.org/Graphics/JPEG/jfif3.pdf) | 1992-09 | Medium (from recollection of the text; both PDFs are the canonical copies) |
| 1.7 | **Progressive JPEG** shows a coarse image after part of the file: the dial-up era's answer to perceived latency. It survived because it also often compresses better than baseline with optimised Huffman tables (see 1.9). | — | [ITU-T T.81](https://www.w3.org/Graphics/JPEG/itu-t81.pdf) | 1992 | Medium |
| 1.8 | **Arithmetic-coded JPEG** stayed unsupported after its patents expired. Mozilla closed the request WONTFIX on 2015-04-13: "we'd need at least two browser vendors to commit... we won't implement this without evidence that it's going to be interoperable", noting Chrome had no plans. An early Mozilla reviewer (2011-08-19) feared "a fragmented market, since we'll load images that no other browser does". | 7-10% smaller files claimed | [Mozilla bug 680385](https://bugzilla.mozilla.org/show_bug.cgi?id=680385) | 2011-2015 | High |
| 1.9 | The libjpeg-turbo maintainer's measurement in the same bug: progressive arithmetic vs optimised progressive Huffman gave "2.4-10.2% (average 7.7%)" smaller files but "more than doubling the compute time"; supporting it in Firefox would need suspension support in the arithmetic decoder, unfunded. | 7.7% mean gain; >2× decode time | [Mozilla bug 680385, comments 2019-12-03 to 2020-05-05](https://bugzilla.mozilla.org/show_bug.cgi?id=680385) | 2019-2020 | High |
| 1.10 | IJG libjpeg (from 1991) was the de facto JPEG implementation. After IJG's libjpeg v7-v9 added non-standard extensions (SmartScale), the libjpeg-turbo project declined to follow and became the browsers' choice. A single C library became the effective definition of "JPEG on the web". | — | [libjpeg-turbo, "About libjpeg v9"](https://libjpeg-turbo.org/About/Jpeg-9); [IJG](https://www.ijg.org/) | 2009-2013 | Medium |

**Implications:** GIF and PNG show that patent licensing, not engineering, has twice decided which image formats the web has. JPEG shows that a spec's optional features (arithmetic, hierarchical, 12-bit) are effectively dead if browsers never ship them, and that interop pressure ("two vendors first") freezes the format set. Izcal must decode the web's actual JPEG subset bit-compatibly and should treat T.81 options outside it as a deliberate, documented decision.

## 2. Animated images: MNG lost, APNG won

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | The PNG group's own historian: "the principal failure of the PNG group was its delay in extending PNG to MNG." MNG work stalled after mid-1995 burnout; ~31 drafts by January 1997. | 31 drafts | [Roelofs, PNG history](http://www.libpng.org/pub/png/pnghist.html) | 1995-1997 | High |
| 2.2 | Mozilla removed MNG/JNG (bug filed 2003-02-27, fixed 2003-06-03). Stated reasons, verbatim in substance: the MNG decoder was "roughly the same size as all the other image decoders and libpr0n logic combined" (Linux: 241,492 vs 261,796 bytes); integration was rough with no active maintainers; animated GIF and Flash "cover much of the feature set"; "the formats are little used in the wild"; "the formats are not w3c recommended". | 131 comments | [Mozilla bug 195280](https://bugzilla.mozilla.org/show_bug.cgi?id=195280) | 2003 | High |
| 2.3 | The MNG developers called the reasons "all refuted to greater or lesser extent" and the removal "for not very well understood reasons". An MNG library author noted in the bug that MNG was popular in East Asia. Usage was never measured in the bug. | — | [MNG developers' 2003 news](https://png-mng.sourceforge.net/pub/mng/mng2003.html); [bug 195280](https://bugzilla.mozilla.org/show_bug.cgi?id=195280) | 2003 | Medium |
| 2.4 | **APNG** (Mozilla, 2004-2008) took the opposite design: a backward-compatible PNG with extra chunks, so old decoders show the first frame. Firefox 3 shipped it (2008). The PNG group voted against adopting it in 2007; Chrome added it only in 2017. | — | [Mozilla wiki, APNG specification](https://wiki.mozilla.org/APNG_Specification) | 2004-2017 | Medium (vote and Chrome date Low) |
| 2.5 | **PNG Third Edition** became a W3C Recommendation on 24 June 2025, the first revision since 2003. It standardises APNG and adds **cICP** (coding-independent code points for HDR and wide gamut) and Exif. The implementation report lists cICP support in Chromium, Firefox and WebKit on Apple platforms. | 22 years since 2nd edition | [PNG Third Edition](https://www.w3.org/TR/png-3/); [Implementation report](https://w3c.github.io/png/Implementation_Report_3e/) | 2025-06-24 | Medium (date in REC URL; report read as snippet) |

**Implications:** MNG lost on code size, maintenance and scope, not on capability; APNG won by being small, compatible and shipped. The lesson for Izcal is that a format's adoption follows its cost to implementers. Izcal should decode APNG and GIF as PNG and GIF variants with bounded frame state (FP 6.5: ≤ 2 decoded frames), and cICP from day one.

**Implications:** Every successful web image format (WebP, AVIF) was a video codec's intra mode, which shares a decoder with video. Izcal should decode every web image format with its own decoder, identical on every OS (FP-D13), and not expose an OS-only format.

Fuzzed before Nightly rollout and to be fuzzed again before the pref flip. | — | [dev-platform thread](https://groups.google.com/a/mozilla.org/g/dev-platform/c/3YMV4MS34KA) | 2026-08-24 | High |
| 4.9 | Performance pushback in the same thread: lossless JXL decoded 15-20× slower than lossless WebP (first measured 30.93×: 20.632 s vs 667.0 ms single-threaded) for ~10% smaller files; one engineer proposed shipping lossy only, arguing CDNs are "financially incentivized to use the highest compression option". With multithreading the intent author measured his benchmark "slightly ahead of Safari (using C++ libjxl)". | 15-20× decode cost; ~10% size gain | [dev-platform thread](https://groups.google.com/a/mozilla.org/g/dev-platform/c/3YMV4MS34KA) | 2026-08/09 | High |
| 4.10 | **Chrome 155** ships JPEG XL decoding (blog 6 October 2026) using jxl-rs, "a pure Rust implementation". Google reports no memory-safety bugs found across jxl-rs's history (fuzzing and AI code review). | — | [Chrome for Developers, "Shipping JPEG XL in Chrome"](https://developer.chrome.com/blog/jpeg-xl-in-chrome) | 2026-10-06 | High |

**Implications:** The JPEG XL saga moved the deciding question from "is there demand" to "is there a memory-safe, fast enough decoder". Both Chrome and Firefox now require a new format to arrive with a memory-safe implementation. Izcal's own Rust decoders meet that bar by construction, but the Firefox thread shows decode cost per byte saved must be measured (FP 6.5 already asks for JXL peak memory). Izcal should ship JPEG XL, since all three engines now do or will.

## 6. The plugin era and its end

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | Before HTML5, media on the web ran in plugins (RealPlayer, QuickTime, Windows Media, later Flash) through NPAPI or ActiveX: native code with the browser's privileges, each with its own codecs, network stack and update channel. Era constraints: no media element, no codec agreement, slow CPUs needing vendor-optimised code. | — | [Chromium Blog, "Saying Goodbye to Our Old Friend NPAPI"](https://blog.chromium.org/2013/09/saying-goodbye-to-our-old-friend-npapi.html) | 1995-2013 | Medium |

| 6.3 | **Flash Video** (Flash Player 6-7, 2002-2003, Sorenson Spark then On2 VP6; H.264 from 2007) won because it was installed almost everywhere and hid codec differences; YouTube (2005) built on it. | — | [Adobe, Flash Player EOL](https://www.adobe.com/products/flashplayer/end-of-life.html) | 2002-2007 | Low |

| Project | Fate | Stated reason (not guessed) | Source |

**Implications:** The recurring reasons are implementer cost (code size, maintainers, decode cost), patents, a missing second vendor, and attack surface. Capability alone never saved a format. Izcal should evaluate every format and codec on those four axes, with measurements, before committing to it.

## Open questions and black-box measurements needed

1. JPEG XL decode cost in Izcal's own decoder versus WebP and AVIF, per byte saved, single- and multi-threaded (Firefox's 15-20× lossless figure, row 4.9, is for jxl-rs and must not be assumed).
2. Which T.81 JPEG features occur on the live web (arithmetic, 12-bit, lossless, CMYK/YCCK, restart markers): measure on a crawl rather than adopt a library's choices.
3. Exact black-box behaviour of each engine for untagged images, CSS colours and video under wide-gamut and HDR displays (rows 5.2-5.8), to set Izcal's test oracles.
4. Which engine behaviours for animated-image timing (minimum frame delay clamps, GIF loop counts) are web-observable; measure in each browser rather than read source.
5. Chrome's current native HLS default status and supported codecs on desktop in October 2026.
6. Whether Safari's JPEG XL now supports animation and progressive decode (one secondary claim says not).
7. Firefox's current Theora status (Chrome's removal is documented; Firefox's was not found).
8. AV1 hardware decode share among Izcal's likely users (by OS and GPU generation), to size the software decoder's performance target.
