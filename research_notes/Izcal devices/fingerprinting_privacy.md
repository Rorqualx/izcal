## 1. What each API exposes, before and after permission

### 1a. Enumeration and identifier surface

|---|---|---|---|---|---|
| 1.1 | **WebUSB.** `navigator.usb.getDevices()` runs silently and returns only devices this origin was previously granted. `requestDevice()` needs transient activation and a **mandatory** filter list; the user picks from a chooser. ### 1b. Identifier scope, rotation and stability

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.7 | **USB serial numbers are global identifiers.** The spec makes manufacturer name, product name and serial a SHOULD from the device's string descriptors. Permission storage is keyed by **vendorId, productId and serialNumber**, so a device with a serial is re-identified across sessions by that serial. | 3-field permission key | [WebUSB §3.4, §5](https://usb.spec.whatwg.org/) | read 2026-10-21 | High |
| 1.8 | **USB devices without serials are conflated by model.** If `serialNumber` is undefined, the permission key is only VID/PID. Granting one unit then makes every identical unit of that model visible to the origin. | 2-field key | [WebUSB §5](https://usb.spec.whatwg.org/) | read 2026-10-21 | High |
| 1.9 | **WebHID is model-level, not unit-level.** No serial attribute exists, and the spec says the product name "SHOULD NOT contain any identifiers like a serial number or Bluetooth device address". The report descriptor's collections identify device type, not the individual unit. | 0 unit identifiers | [WebHID §7.4](https://hid.spec.whatwg.org/) | read 2026-10-21 | High |
| 1.10 | **Web Serial hides unit identifiers at the API.** The spec says an implementation will likely store VID, PID and serial number internally as stable identifiers, but "These would not be shared directly with sites and would be cleared when permission is revoked or site data in general is cleared." | 3 internal fields | [Web Serial §8](https://serial.spec.whatwg.org/) | read 2026-10-21 | High |
| 1.11 | **MIDI port IDs are designed to be globally persistent.** The UA MUST make the id unique, and SHOULD maintain it across application instances **and reboots**. The spec's own suggested construction is "some form of hash of the port interface manufacturer, name and index", which is origin-independent. No per-origin rule appears. | reboot-persistent; 3-field hash example | [Web MIDI §MIDIPort](https://webaudio.github.io/web-midi-api/) | read 2026-10-21 | High |
| 1.12 | **Bluetooth IDs are per-origin only by suggestion.** The spec says it "suggests that the UA use different device IDs for a single device when its user doesn't intend scripts to learn that it's a single device". The permission-data note says a deviceId lets a site track a device "possibly in a different realm", and that users generally do not want two origins to know they are using the same device. The TAG review describes `BluetoothDevice.id` as "origin-unique", "not available at all until permission is granted" and "persistent until permission is revoked". | 1 recommended scope; 0 MUSTs | [Web Bluetooth §3.4.1, §9](https://bluetooth.spec.whatwg.org/); [TAG design review](https://github.com/w3ctag/design-reviews/issues/64) | read 2026-10-21 | High (spec); Medium (review) |
| 1.13 | **Bluetooth names are global.** A device name is human-readable and "aren't guaranteed to be unique, but may well be". Per-origin IDs do not hide the name from a granted site, so a uniquely named device is a cross-origin correlator even when its `id` differs. | 1 name string | [Web Bluetooth §3.4](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 1.14 | **NFC UIDs are stable for most tags.** The spec says "most tags will have a stable unique identifier (UID)", some tags have none, and some "create a random number on each read". There is no rotation or per-origin rule; the same tag read by two origins yields the same `serialNumber`. | 4 or 7 numbers (32 or 56 bits if bytes) | [Web NFC §NDEFReadingEvent](https://w3c-cg.github.io/web-nfc/) | read 2026-10-21 | High |
| 1.15 | **Cross-session stability is the norm.** All six APIs keep grants and device identity across sessions; Bluetooth IDs persist until permission is revoked, USB serials persist for the life of the device, MIDI ids SHOULD survive reboot, NFC UIDs are tag-fixed. Only Web Serial's spec says stored identifiers are cleared with site data. | 5 of 6 stable | [specs above](https://usb.spec.whatwg.org/) | read 2026-10-21 | High |
| 1.16 | **Clearing cookies may not clear device grants.** The Bluetooth spec note says users do not intend unique identifiers to persist after they clear an origin's cookies. The TAG says stored device identifiers must be cleared when browsing data is cleared. Whether each shipping browser actually revokes device permissions on cookie clear is not documented in prose found; Izcal must observe it black-box. | to be observed | [Web Bluetooth §9](https://bluetooth.spec.whatwg.org/); [TAG §9](https://w3ctag.github.io/design-principles/) | 2026-10-21 | Medium |

**Implications:** The only API that recommends origin-scoped identifiers is Web Bluetooth, and it does so non-normatively. USB serial numbers, MIDI port ids and NFC UIDs are global identifiers that a granted site can read; HID and Serial deliberately stop at the model level. Izcal should treat device identity as a **per-grant capability with an origin-scoped handle**, not as an API-specific property to be copied from the specs, and must test whether clearing site data actually revokes grants and rotates handles.

## 2. What the specifications admit

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **WebUSB has no fingerprinting analysis.** Its Security and Privacy Considerations discuss abusing a device, attacking a device and attacking the host, plus secure contexts and single-driver ownership. A full-text search finds no "fingerprint", no identifier-tracking discussion, and no statement that the serial number is privacy-sensitive. | 0 fingerprint mentions | [WebUSB §3](https://usb.spec.whatwg.org/) | read 2026-10-21 | High |
| 2.2 | **WebHID has no fingerprinting section either.** It relies on a chooser, a second confirmation interaction, protected top-level collections and blocklists. Its only identifier rule is the SHOULD on product names. | 0 fingerprint mentions | [WebHID §3, §7.4](https://hid.spec.whatwg.org/) | read 2026-10-21 | High |
| 2.3 | **Web Serial names the identifier risk.** It says ports and devices carry "identifiers such as the vendor and product IDs ... as well as a serial number or MAC address", that implementations store them internally, and that incognito must not inherit normal-profile grants and must not persist its own. | 3 identifier classes | [Web Serial §8](https://serial.spec.whatwg.org/) | read 2026-10-21 | High |
| 2.4 | **Web Bluetooth has the fullest privacy analysis.** It admits that persistent device IDs "can be used, in combination with a large effort to catalog ambient devices, to discover a user's location", that a device ID can show two websites paired with the same device are one user, that many GATT services can fingerprint a device and a custom GATT service makes it easy, and that `getAvailability()` "increases the UA's fingerprinting surface by a bit". | 4 admitted channels | [Web Bluetooth §3.4–3.5](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 2.5 | **Web Bluetooth defends the radio, not the payload.** It states that the API "never exposes Bluetooth addressing, data signing or encryption keys", and that private addresses are regenerated about every 15 minutes, with a bonded device resolving them by IRK. It does not say that advertisement payloads can contain stable tokens. | 15 min rotation | [Web Bluetooth §3.3–3.4](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 2.6 | **Web MIDI admits enumeration fingerprinting.** "Allowing the enumeration of the user's MIDI interfaces is a potential target for fingerprinting; that is, uniquely identifying a user by the specific MIDI interfaces they have connected." The API exposes name, manufacturer and an opaque id. The spec compares the exposure to the Gamepad API and notes most systems have no MIDI interfaces. | 3 exposed fields | [Web MIDI §Privacy](https://webaudio.github.io/web-midi-api/) | read 2026-10-21 | High |
| 2.7 | **Web NFC admits UID and location exposure.** It says a fixed tag "may encode its ID or location in the data", so reading it exposes the reader's location to a site that knows the deployment. Its threat table names "device identifiers and user identifiers" and says implementations MAY use per-session or ephemeral permissions. | 1 location channel | [Web NFC §Security and Privacy](https://w3c-cg.github.io/web-nfc/) | read 2026-10-21 | High |
| 2.8 | **The TAG's device-access guidance is stricter than any of the six specs.** It says: "Create distinct identifiers for the same physical device for each origin"; "When the user chooses to clear browsing data, make sure any stored device identifiers are cleared"; "Look for ways to avoid enumerating devices"; if a list is unavoidable, "define the order"; and "access to anything outside of the logical origin boundary should be permission gated", with exclusive per-origin or active-tab access worth considering. | 5 rules | [W3C TAG Design Principles §9](https://w3ctag.github.io/design-principles/) | read 2026-10-21 | High |
| 2.9 | **What no spec does.** None sets an entropy budget, requires cross-origin unlinkability for serials or UIDs, or analyses correlation across APIs. WebUSB's note even permits a unified permission across WebHID and WebUSB, which would make one grant unlock two surfaces. | 0 cross-API rules | [specs above](https://usb.spec.whatwg.org/) | read 2026-10-21 | High |

**Implications:** The specs are honest about the radio layer and mostly silent about the identifier layer. WebUSB is the largest gap: it exposes a global serial number and has no identifier-privacy text at all. Izcal's device service should adopt the TAG rules as the baseline, then go beyond them for serials, UIDs and MIDI ids, where the specs leave the linkability unresolved.

## 3. Published fingerprinting and physical-tracking research

| # | Finding | Numbers | Source | Date | Conf. |

| 3.11 | **Physical tracking literature's common lesson.** Address randomization is necessary but insufficient: application-layer identifiers (payload tokens, names, service sets, serials, UIDs) survive rotation and are the durable correlators. **Implications:** Silent fingerprinting is measured in the tens of percent of top sites, but the device APIs are absent from those measurements because they need a grant. Their risk is **post-grant linkability**, where a serial, UID, name or payload token is far stronger than 18 bits of browser entropy. Izcal's PRIV-2 must add a device-surface inventory and a two-origin, same-device linkability test, because the public literature does not supply either number.

## 4. Permission-gated versus ambient enumeration, and oracles

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **No first-visit ambient device data.** None of the six APIs returns device details before a grant: USB, HID and Serial read prior grants only; Bluetooth `getDevices()` reads prior grants; NFC has no enumeration; MIDI is now permission-gated in Chrome 124+ and Firefox. The specification text still permits MIDI without a prompt. | 0 pre-grant device lists | [specs](https://usb.spec.whatwg.org/); [Chrome MIDI](https://developer.chrome.com/blog/web-midi-permission-prompt) | 2026-10-21 | High |
| 4.2 | **Silent re-enumeration after a grant.** `getDevices()` (USB, HID, Bluetooth) and `getPorts()` (Serial) never prompt; they return the origin's granted devices on page load. MIDI's `requestMIDIAccess()` returns all ports once the origin holds a grant. | 4 silent get* methods | [specs](https://usb.spec.whatwg.org/) | 2026-10-21 | High |
| 4.3 | **Empty result is ambiguous by design.** A pre-grant `getDevices()` returns an empty sequence; the page cannot tell "no devices attached" from "no permission". This is privacy-positive and should be preserved. | 2 states, 1 answer | [WebUSB §3.4](https://usb.spec.whatwg.org/); [WebHID §6.1](https://hid.spec.whatwg.org/) | read 2026-10-21 | High |
| 4.4 | **WebUSB's first call enumerates every attached device.** The algorithm must "enumerate all devices attached to the system" and then filter to grants. The UA may cache the enumeration. A page can time the first call, so the total device count may be a side channel even though no device is returned. | all devices enumerated | [WebUSB §3.4](https://usb.spec.whatwg.org/) | read 2026-10-21 | High (algorithm); Low (exploitability) |
| 4.5 | **Error names distinguish the page's own state, not device presence.** Missing activation or Permissions-Policy denial gives `SecurityError`; a cancelled chooser or no matching device gives `NotFoundError`; NFC denial gives `NotAllowedError`; MIDI denial gives `SecurityError`. A page learns whether it may ask and whether the user acted, not what else is attached. | 4 error names | [specs](https://usb.spec.whatwg.org/) | read 2026-10-21 | High |
| 4.6 | **Two ambient bits remain.** `navigator.bluetooth.getAvailability()` reports whether a radio exists and whether the UA blocks Web Bluetooth, without a prompt; the spec admits this adds a fingerprinting bit. `navigator.permissions.query()` for MIDI reveals whether the origin already holds a grant. | 1–2 bits | [Web Bluetooth §3.5](https://bluetooth.spec.whatwg.org/); [MDN requestMIDIAccess](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/requestMIDIAccess) | read 2026-10-21 | High |
| 4.7 | **Workers can enumerate silently.** USB, HID, Serial and MIDI are exposed to workers (HID also to service workers); only the `request*` calls are Window-only. A service worker can call `getDevices()` on navigation with no visible page. | 4 worker-exposed APIs | [WebUSB §5](https://usb.spec.whatwg.org/); [WebHID §6](https://hid.spec.whatwg.org/); [Web Serial §3](https://serial.spec.whatwg.org/) | read 2026-10-21 | High |
| 4.8 | **Chooser filters are not a silent oracle.** The page names filters before the chooser; it never sees the non-matching list. It can confirm a guess only through the user's selection or cancellation, which is user-mediated. WebUSB and WebHID make filters mandatory; Web Serial makes them optional; Web Bluetooth allows `acceptAllDevices`. | mandatory: 2 of 3 | [Chrome USB](https://developer.chrome.com/docs/capabilities/usb); [Chrome HID](https://developer.chrome.com/docs/capabilities/hid); [Web Bluetooth §4](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 4.9 | **The request itself leaks timing.** Populating a chooser takes longer with more matching devices; an origin can time a cancelled request. No published study measures this. It is strictly weaker than a returned list, and only user-initiated. | unmeasured | — | 2026-10-21 | Low |
| 4.10 | **"No prompt on enumeration" is the shared rule, with a scope limit.** The rule is safe only because enumeration is restricted to prior grants. Any Izcal change that returns ungranted devices would turn the rule into an ambient fingerprint. | 6 of 6 | [specs](https://usb.spec.whatwg.org/) | 2026-10-21 | High |

**Implications:** The current designs are permission-gated at first use but **silently enumerable forever after the first grant**. That is the correct shape for Izcal, provided the returned handle is origin-scoped and the first-call timing is flattened. The WebUSB enumeration step is the one spec-level timing channel found; cache or pad it. A device service must also decide whether service workers get silent `getDevices()` at all.

## 5. Device identity and linkability

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **Per-origin grants do not prevent linkability when the identifier is global.** Site A and site B cannot see each other's grants, but if both are granted the same USB device they both read the same serial; if both read the same NFC tag they both read the same UID. The grant isolates discovery, not identity. | 2 origins + 1 global ID | [WebUSB §3.4](https://usb.spec.whatwg.org/); [Web NFC](https://w3c-cg.github.io/web-nfc/) | 2026-10-21 | High |
| 5.2 | **Bluetooth is the counter-example and the warning.** Per-origin `id` blocks the obvious correlation, but the `name`, the GATT service set and advertisement payloads remain identical across origins. The spec admits GATT fingerprinting; it does not require name or payload normalisation. | 3 residual channels | [Web Bluetooth §3.4.1](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 5.3 | **Custom GATT services are device-unique.** The spec says "a device can easily expose a custom GATT service to make this easier", so the UUID set can identify a model and sometimes a firmware build. This is functional data; hiding it would break device drivers. | 128-bit UUIDs | [Web Bluetooth §3.4.1](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 5.4 | **WebUSB serial is a unit-level super-cookie.** The serial is a manufacturer string, often globally unique. The device can also return it over a control transfer, so even an API that hid the property would not hide the bytes. | variable length | [WebUSB §6, §9](https://usb.spec.whatwg.org/); [TAG review](https://github.com/w3ctag/design-reviews/issues/64) | read 2026-10-21 | High |
| 5.5 | **WebHID limits linkability to the model.** No serial and a product-name rule keep the unit from being named. A uniquely named product or a vendor-specific report descriptor can still correlate at model level. | 0 unit IDs | [WebHID §7.4](https://hid.spec.whatwg.org/) | read 2026-10-21 | High |
| 5.6 | **Web Serial is the best API-level minimisation.** `getInfo()` exposes only VID/PID or a service class, and the spec keeps the serial internal. The limit is the wire: a device may answer with its own serial after the grant. | 2 fields | [Web Serial §4.3, §8](https://serial.spec.whatwg.org/) | read 2026-10-21 | High |
| 5.7 | **MIDI's port id is the weakest design.** The spec wants the id stable across reboots and suggests a hash of manufacturer, name and index, with no per-origin rule. If Chrome follows that construction, two origins see the same id for the same port. Whether it does is not stated in published prose; it is a black-box check for Izcal. | reboot-stable; 0 per-origin rules | [Web MIDI §MIDIPort](https://webaudio.github.io/web-midi-api/) | read 2026-10-21 | High (spec); Medium (Chrome behaviour) |
| 5.8 | **NFC UID links tags, sessions and origins.** A tag's UID is usually stable for its lifetime; a fixed tag also ties a read to a physical place. The spec says implementations may use per-session permissions, which would reduce cross-session linkage but not cross-origin linkage within a session. | 4 or 7 numbers | [Web NFC §NDEFReadingEvent, §Security](https://w3c-cg.github.io/web-nfc/) | read 2026-10-21 | High |
| 5.9 | **Identical USB models without serials are one identity.** Because permission is keyed by VID/PID when no serial exists, a site granted one unit can see every identical unit. This is a functional convenience and a linkability surprise. | 2-field key | [WebUSB §5](https://usb.spec.whatwg.org/) | read 2026-10-21 | High |
| 5.10 | **Composite devices cross APIs.** A headset, keyboard or dev board can appear as USB, HID and Serial, sometimes with the same VID/PID and serial. A site granted one interface can correlate the others if the identifiers are visible; the USB spec explicitly permits unifying permissions across WebUSB and WebHID. | 3 APIs, 1 device | [WebUSB §5.1 note](https://usb.spec.whatwg.org/) | read 2026-10-21 | High |
| 5.11 | **Incognito and containers are the spec's only cross-session boundary.** Web Serial says normal-profile permissions must not carry into private browsing and private grants must not persist. No other spec read says this. | 1 of 6 | [Web Serial §8](https://serial.spec.whatwg.org/) | read 2026-10-21 | High |
| 5.12 | **Cross-session stability is required for function.** Reconnecting a saved device needs a stable handle; rotating it per session would break the primary use case. The privacy property must be **unlinkability across origins and containers**, not across time within one origin. | 1 origin, many sessions | [WebUSB §3.4](https://usb.spec.whatwg.org/); [TAG §9](https://w3ctag.github.io/design-principles/) | 2026-10-21 | High |

**Implications:** Identity is the hard part, not discovery. A per-origin grant plus a global serial or UID still lets two colluding sites join on the device. Bluetooth shows that rotating the API id is not enough when the name, service set and payload stay fixed. Izcal should define one device handle per (origin, container, physical device) and accept that device-provided bytes remain a correlator the browser cannot remove.

## 6. Mitigations in shipping browsers and what the evidence says

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **Chooser-first grants.** WebUSB and WebHID require filters and a user gesture; Web Serial requires a gesture; Chrome shows a device chooser and the user must select one device. The TAG prefers a UA-provided picker because it exposes "only ... one device at a time". | 4 APIs, 1-device chooser | [Chrome USB](https://developer.chrome.com/docs/capabilities/usb); [Chrome HID](https://developer.chrome.com/docs/capabilities/hid); [TAG §9](https://w3ctag.github.io/design-principles/) | read 2026-10-21 | High |
| 6.2 | **Per-origin grants are universal.** USB, HID, Serial, Bluetooth, NFC and (since Chrome 124) MIDI store permission per origin. A different origin gets an empty list until it asks and the user grants. | 6 of 6 | [specs](https://usb.spec.whatwg.org/); [Chrome MIDI](https://developer.chrome.com/blog/web-midi-permission-prompt) | 2026-10-21 | High |
| 6.3 | **Bluetooth per-origin random IDs.** The spec suggests distinct IDs per origin; the TAG describes the id as origin-unique and persistent until permission is revoked. Chrome is reported to implement per-origin IDs; this was not verified black-box here. | 1 API | [Web Bluetooth §3.4.1](https://bluetooth.spec.whatwg.org/); [TAG review](https://github.com/w3ctag/design-reviews/issues/64) | 2026-10-21 | Medium |
| 6.4 | **Radio-level rotation.** BLE private addresses rotate about every 15 minutes and bonded peers resolve them by IRK; the API never exposes the address. This protects against radio-layer tracking but not payload tokens (3.6, 3.7). | 15 min; 128-bit IRK | [Web Bluetooth §3.4](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 6.5 | **Scanning is restricted.** `requestDevice` needs a gesture and aborts when the page is hidden; `watchAdvertisements()` and `requestLEScan()` were still prototyped in Chromium and not enabled by default as of March 2024. `getDevices()` was also not confirmed as default-on. | 2 APIs off by default | [W3C mailing list, 2024-03-11](https://lists.w3.org/Archives/Public/public-web-bluetooth-log/2024Mar/0003.html); [implementation status](https://github.com/WebBluetoothCG/web-bluetooth/blob/main/implementation-status.md) | 2024-03-11 | Medium |
| 6.6 | **Protected classes and blocklists.** WebUSB blocks interfaces in classes Audio, HID, Mass Storage, Hub, Smart Card, Video, Audio/Video and Wireless Controller. Chrome's WebHID blocks protected top-level collections (keyboard, mouse) and FIDO security keys. These stop keylogging and credential theft, not tracking. | 8 USB classes | [WebUSB §6.4](https://usb.spec.whatwg.org/); [Chrome HID](https://developer.chrome.com/docs/capabilities/hid) | read 2026-10-21 | High |
| 6.7 | **Enterprise policy.** Chrome exposes "WebUSB API", "WebUSB API allowed devices", "WebHID API allowed devices", "Web Serial API" and "Web Serial API allowed devices", plus a Web Bluetooth policy. The device lists auto-grant URL patterns by VID/PID; the general policies offer user-decides, allow and block, with per-URL lists. No MIDI or NFC policy appeared in the sections read. | 6+ policies | [Google Admin Help](https://support.google.com/chrome/a/answer/2657289) | read 2026-10-21 | High |
| 6.8 | **Revocation exists.** Every API has `forget()` or a settings revoke path; Web Serial's spec also sets incognito rules. The TAG says stored identifiers must be cleared with browsing data. | 6 revoke paths | [specs](https://serial.spec.whatwg.org/); [TAG §9](https://w3ctag.github.io/design-principles/) | 2026-10-21 | High |
| 6.9 | **Browser support is narrow, which removes the surface entirely elsewhere.** WebUSB (Chrome 61+, Edge 79+), WebHID (Chrome 89+, Edge 89+), Web Serial and Web NFC are Chromium-only; Web Bluetooth is Chrome 56+ and Edge 79+, with no Firefox or Safari; Web MIDI is Chrome 43+, Edge 79+ and Firefox 108+, with no Safari. | 4 Chromium-only APIs | [caniuse WebUSB](https://caniuse.com/webusb); [WebHID](https://caniuse.com/webhid); [Web Bluetooth](https://caniuse.com/web-bluetooth); [Web MIDI](https://caniuse.com/midi); [Web NFC](https://caniuse.com/webnfc) | read 2026-10-21 | Medium |
| 6.10 | **No published effectiveness measurement.** No study found measures whether chooser filtering, per-origin IDs, scanning restrictions or enterprise policy actually reduce device-based linkability. The evidence for these mitigations is design intent and vendor documentation, not outcome data. | 0 studies | — | 2026-10-21 | Low |

**Implications:** The shipping stack relies on three layers: a user-mediated chooser, a per-origin grant, and (for Bluetooth only) an origin-scoped id. Each is documented, none is measured. The strongest documented mitigation is the one that keeps scanning off by default; the weakest is per-origin grants against global serials and UIDs. Izcal should keep the chooser, add container keying, and treat scanning as a privileged, foreground-only capability.

## 7. Attacks and tracking channels

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **USB serial super-cookie.** A site granted a device reads a global serial, stores it server-side, and recognises the same device at another site if that site also obtains a grant. The TAG calls a cross-domain hardware id a "super-cookie" and "not good". | 1 serial | [TAG review](https://github.com/w3ctag/design-reviews/issues/64); [WebUSB](https://usb.spec.whatwg.org/) | 2026-10-21 | High (exposure); Medium (prevalence) |
| 7.2 | **Bluetooth name and GATT correlation.** Two origins with grants see different `id`s but the same `name` and service set; a uniquely named device or a custom service UUID links them. | 2 channels | [Web Bluetooth §3.4](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 7.3 | **BLE payload tracking reaches the web.** Address-carryover tracking (3.6) works on payload tokens, and `watchAdvertisements()` exposes manufacturer and service data. A site with one grant can follow that device while in range, across address rotations. | 2 payload maps | [PETS 2019](https://petsymposium.org/popets/2019/popets-2019-0036.php); [Web Bluetooth §5.2.3](https://bluetooth.spec.whatwg.org/) | 2019; spec 2026-10-21 | High (research); Medium (web exploit) |
| 7.4 | **NFC UID and fixed-tag location.** A UID read on two sites joins them; a mounted tag's UID or payload tells a colluding site where the user is. The spec admits both. | 4 or 7 numbers | [Web NFC §Security](https://w3c-cg.github.io/web-nfc/) | read 2026-10-21 | High |
| 7.5 | **MIDI port id as a cross-origin key.** A reboot-stable hash of manufacturer, name and index is the same string in every origin, if implemented as the spec suggests. | 1 id | [Web MIDI](https://webaudio.github.io/web-midi-api/) | read 2026-10-21 | Medium |
| 7.6 | **Permission-prompt origin spoofing.** CVE-2022-0803 let a page spoof the origin shown in a hardware permission prompt, so a user could grant a device to an origin they did not intend. | 1 CVE | [SSRN 6141930](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=6141930) | 2026-01 | Low |
| 7.7 | **`file:` documents inherited grants.** The same analysis reports a `file:` URI Same-Origin-Policy flaw that let a local document use previously granted hardware permissions. | 1 flaw | [SSRN 6141930](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=6141930) | 2026-01 | Low |
| 7.8 | **Persistent grants plus XSS.** The Bluetooth spec says a compromised origin can use previously granted devices on a later visit without a new prompt; `getDevices()` makes this worse while reducing prompt fatigue. The same logic applies to USB, HID, Serial and MIDI. | 1 grant, many visits | [Web Bluetooth §3.2](https://bluetooth.spec.whatwg.org/) | read 2026-10-21 | High |
| 7.9 | **Malicious firmware and configuration writes.** A granted device is not trusted code: 22 models from 15 vendors were abused through device APIs to reach code execution outside the sandbox. A device grant is a capability grant, not a data-sharing grant. | 22 models; 15 vendors | [Peripheral Instinct](https://cispa.saarland/group/rossow/papers/webhid.pdf) | n.d. | Medium |
| 7.10 | **No in-the-wild device-API tracking campaign was found.** The literature reports physical-layer tracking and permission attacks, not a deployed web campaign that uses USB serials or NFC UIDs to join users across sites. Absence of a report is not evidence of absence. | 0 campaigns found | — | 2026-10-21 | Low |

**Implications:** The credible attacks are quiet and require a grant: a serial, UID, name or payload token is a durable join key, and persistent grants let a compromised origin reuse it. The browser cannot remove device-provided bytes, so the defence has to be grant scope, origin scoping of handles, and visibility of what a grant means, not content scrubbing.

## 8. Izcal principles for a device-access service

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | **Device handles are identity, not fingerprint noise.** D-S1's noise is seeded by (site, container, session); a device handle must instead be a stable pseudonym of (origin, container, physical device). Session rotation would break reconnect; the privacy goal is cross-origin and cross-container unlinkability. | 1 handle per (origin, container, device) | [TAG §9](https://w3ctag.github.io/design-principles/); rows 1.7–1.14, 5.12 | 2026-10-21 | High |
| 8.2 | **One broker, per-API capability scopes.** Route every API through one device service, but do not let one grant unlock another API for the same physical device. The WebUSB note permitting a unified WebHID/WebUSB permission is a warning, not a model. | 6 APIs, 6 scopes | [WebUSB §5.1 note](https://usb.spec.whatwg.org/); rows 2.9, 5.10 | 2026-10-21 | High |
| 8.3 | **Container keying.** Key grants and handles by (origin, container). The same device granted in two containers yields two unlinkable handles; deleting a container deletes its grants and handles. | 2 container scopes per origin | [TAG §9](https://w3ctag.github.io/design-principles/); rows 5.1–5.2 | 2026-10-21 | High (design) |
| 8.4 | **Normalise what is safe.** Enumeration order (define a stable order, as the TAG asks), timing (cache and pad the WebUSB first call), result counts, and API-level unit identifiers (serial, UID, port id) become per-(origin, container) pseudonyms. These preserve within-origin function. | 4 normalisable axes | [TAG §9](https://w3ctag.github.io/design-principles/); rows 1.11, 1.14, 4.4 | 2026-10-21 | High |
| 8.5 | **Do not normalise functional device data.** VID/PID, product and manufacturer names, GATT service UUIDs, HID collections, MIDI port names and raw device bytes must pass through. They are required to select a driver or a device, and a picker that hides them is unusable. | 6 pass-through classes | [TAG §9](https://w3ctag.github.io/design-principles/); rows 3.7, 5.3, 5.6 | 2026-10-21 | High |
| 8.6 | **Pseudonyms have a known cost.** A per-origin serial breaks server-side warranty or firmware matching that needs the true serial; a per-origin NFC UID breaks tag identity shared with a backend; a per-origin MIDI id breaks setup files moved between browsers. The true identifier should leave only through a separate, explicit, per-grant "expose hardware identifiers" choice, off by default. | 3 broken use cases | rows 5.4, 5.7, 5.8 | 2026-10-21 | High (design) |
| 8.7 | **Entropy budget, measured not asserted.** Public data gives no device-enumeration entropy. Practical widths are 4 or 7 numbers for an NFC UID (32 or 56 bits if each is a byte), 48 bits for a Bluetooth address (never exposed), and unbounded for a USB serial. PRIV-2 should measure cross-origin distinguishability with two unrelated origins granted the same device, and report the surface's residual bits over a device fleet. Target: the ≤1%† cross-site linkability already set for PRIV-2(a). | 32/56 bits (UID); 48 bits (BT address); ≤1%† target | HGBA-3 PRIV-2; rows 3.3, 3.8, 1.14 | 2026-10-21 | High (method); Low (numbers) |
| 8.8 | **Ambient bits get flattened.** `getAvailability()`, API presence, worker enumeration and the first-call timing are ambient. Return a constant availability on capable platforms, expose `getDevices()` only to documents and dedicated workers (not service workers) unless a recorded need exists, and make the first enumeration cache-only. | 4 ambient bits | rows 4.4, 4.6, 4.7 | 2026-10-21 | High (design) |
| 8.9 | **Scanning is foreground-only and grant-scoped.** Never ship an ambient BLE scan by default. `watchAdvertisements` should require a granted device, a visible foreground document and a user gesture; advertisement payloads pass through because they are the device's function, so the grant is the boundary. | 1 granted device; visible only | [Web Bluetooth §4](https://bluetooth.spec.whatwg.org/); rows 3.7, 6.5, 7.3 | 2026-10-21 | High (design) |
| 8.10 | **Chooser rules stricter than Web Bluetooth.** Require filters (no `acceptAllDevices`), one device per grant, a second confirmation interaction as WebHID recommends, and show the user what the grant will expose (serial/UID present or pseudonymised). | 1 device per grant; 2 interactions | [WebHID §3.4](https://hid.spec.whatwg.org/); rows 1.5, 6.1 | 2026-10-21 | High |
| 8.11 | **Incognito and ephemeral grants.** No carry-over from the normal profile; grants and handles die with the private session. Follow Web Serial's rule for every API, not one. | 6 of 6 APIs | [Web Serial §8](https://serial.spec.whatwg.org/); rows 5.11, 6.8 | 2026-10-21 | High |
| 8.12 | **PRIV-1 is the wrong metric here; count prompts.** Device access is user-initiated, so CAPTCHA rate does not capture its cost. Measure prompts per completed task and abandonment instead. Normalisation must not add a prompt to a path that already had a chooser. | 2 task metrics | HGBA-3 PRIV-1; row 6.1 | 2026-10-21 | High (design) |
| 8.13 | **Falsifiable targets for the spec.** Suggested: no API returns device data before a grant (0 surfaces); a handle is identical across two sessions in one origin and different across two origins/containers (100% of probes); clearing site data or deleting a container leaves no grant and no handle (0 residues); PRIV-2's two-origin same-device linkability ≤1%†. | 0 pre-grant; 100% handle checks; 0 residues; ≤1%† | [TAG §9](https://w3ctag.github.io/design-principles/); rows 5.12, 8.7 | 2026-10-21 | High (method) |

**Implications:** A device-access service can normalise ordering, timing, counts and API-level unit identifiers without breaking legitimate use, because those are presentation or identity artefacts. It cannot normalise VID/PID, names, GATT UUIDs, port names or device bytes without breaking device selection and drivers. That boundary, not identifier scrubbing, is where Izcal's device privacy has to be enforced: a per-(origin, container) handle, a chooser-first grant, no ambient scanning, and a measured linkability target under PRIV-2.
