# Izcal devices: history and postmortems

Compiled 21 October 2026. Primary sources were preferred (W3C and WHATWG specifications, W3C mailing-list archives, Mozilla and WebKit standards positions, Chromium and Mozilla release notes, USENIX/Black Hat/WWW papers). No browser, library, tool or OS source file, header, commit, diff or code review was read; specifications, issue-tracker prose and published papers only.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a source read only through a summary; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: this file records ideas, dates, measurements and reasons. It contains no code and no design template from any stack. Where it says what a stack or API "does", that is evidence to reason from, not a shape to copy.

Method notes: the six specifications were read at their canonical URLs on 21 October 2026 — `usb.spec.whatwg.org`, `hid.spec.whatwg.org`, `serial.spec.whatwg.org`, `bluetooth.spec.whatwg.org`, `w3c-cg.github.io/web-nfc/` and `w3.org/TR/webmidi/` — plus the W3C publication-history page for Web MIDI, the W3C Community Group pages, and the W3C `public-device-apis` and `public-review-comments` archives. Vendor positions were read from the `mozilla/standards-positions` and `WebKit/standards-positions` issue threads (prose only). Shipping dates come from `chromiumdash.appspot.com` release data and Chrome release notes. The 2026 venue change was observed black-box: `wicg.github.io/webusb`, `wicg.github.io/webhid`, `wicg.github.io/serial` and `webbluetoothcg.github.io/web-bluetooth` now redirect to `*.spec.whatwg.org`; the first three still render WICG/Community Group front matter, while Web Serial renders as a WHATWG Living Standard. Web-search budget covered the 2026 Firefox/W3C developments and the incident numbers; where it ran out, rows are graded Medium or Low and the gap is named in the text.

## 1. Pre-standard device access: plug-ins, applets and Chrome Apps (1995–2015)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | NPAPI, Java applets and ActiveX let a page run native or near-native code, which is how web pages of the era reached serial ports, USB peripherals and MIDI hardware. The browser itself had no device model; the plug-in or applet carried both the driver knowledge and the user's trust. Exact first dates for applets and ActiveX were not checked against a primary source this session. | — | (recollection; not checked) | 1995–96 | Low |
| 1.2 | Chrome's own postmortem on NPAPI: it "ushered in an early era of web innovation" but its "90s-era architecture has become a leading cause of hangs, crashes, security incidents, and code complexity." The web platform had become capable enough that the extension mechanism was no longer worth its attack surface. | — | [Chromium Blog, "Saying Goodbye to Our Old Friend NPAPI"](https://blog.chromium.org/2013/09/saying-goodbye-to-our-old-friend-npapi.html) | 2013-09-23 | High |
| 1.3 | The migration cost was measured in users, not developers: in the month before the announcement only six NPAPI plug-ins were used by more than 5% of Chrome users — Silverlight 15%, Unity 9.1%, Google Earth 9.1%, Java 8.9%, Google Talk 8.7%, Facebook Video 6.0%. Chrome blocked webpage-instantiated NPAPI by default from January 2014 and whitelisted those six temporarily. | 6 plug-ins >5%; Silverlight 15%, Unity 9.1%, Java 8.9% | [Chromium Blog, NPAPI](https://blog.chromium.org/2013/09/saying-goodbye-to-our-old-friend-npapi.html) | 2013-09-23 / 2014-01 | High |
| 1.4 | The phase-out slipped: the post expected complete removal "before the end of 2014", but NPAPI was removed with Chrome 45 in September 2015. Contemporary coverage records the removal; the Chrome release note itself was not read. | — | [Telerik, "Windows 10, Chrome 45+, and Silverlight"](https://www.telerik.com/blogs/windows-10-chrome-45-and-silverlight) | 2015-09-03 | Medium |
| 1.5 | Chrome's interim answer was **Chrome Apps** (launched 2013), packaged apps with privileged APIs including `chrome.usb`, `chrome.serial`, `chrome.hid` and `chrome.bluetooth`. The migration guide names WebUSB and Web Bluetooth as the replacements for `chrome.usb` and `chrome.bluetooth`; `chrome.serial` was ChromeOS-only. | — | [Chrome Apps migration guide](https://developer.chrome.com/docs/apps/migration); [chrome.serial reference](https://developer.chrome.com/docs/apps/reference/serial) | 2023-09-08 (guide) | High |
| 1.6 | Google retired that escape hatch: Chrome Apps were deprecated in 2020, new Chrome Web Store apps stopped in March 2020, support on Windows/Mac/Linux ended in 2021 after the August 2020 timeline change (policy extension to 2022), and ChromeOS support ended for all customers in June 2022. The stated reason was that "the web platform has made substantial progress since the launch of Chrome Apps in 2013". | 2013 → 2020-03 → 2021/2022 | [Chromium Blog, "Moving Forward from Chrome Apps"](https://blog.chromium.org/2020/01/moving-forward-from-chrome-apps.html); [timeline change](https://blog.chromium.org/2020/08/changes-to-chrome-app-support-timeline.html) | 2020-01-15 | High |
| 1.7 | The result was a gap of years, not months: a site that needed a serial port in 2014 could use a plug-in (being removed), a Chrome App (being deprecated) or a native helper via Native Messaging; the web API that replaced it (Web Serial) shipped in 2021, and in Firefox only in 2026. | ~7 years Chrome, ~12 years Firefox | Sections 4 and 8 | 2014–2026 | Medium |

**Implications:** The platform's device APIs exist because the plug-in model was deliberately killed for security and maintainability, not because the web had a clean design ready. Izcal should treat "no device access" as the default that plug-ins used to bypass, and any device capability it adds must not recreate a general native-code extension path.

## 2. WebUSB (2015–2026)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Who and where:** Reilly Grant (Google) proposed "a new API, WebUSB" to the WICG, arguing that the "long tail of devices that do not fit into one of the standardized device classes" forces vendors to ship native drivers and SDKs. The spec is a WICG Draft Community Group Report; editors are Reilly Grant, Ken Rockot and Ovidio Ruiz-Henríquez, all Google. | — | [WICG Discourse](https://discourse.wicg.io/t/a-usb-api-for-bringing-hardware-innovation-to-the-web/1201/); [WebUSB spec](https://usb.spec.whatwg.org/) | 2015-11-19 | High |
| 2.2 | **Why the chooser, not a registry:** the spec records that two designs were considered. One gave devices a list of allowed origins, optionally via a "public registry". It failed because it required new devices built for WebUSB — product cycles are long and an Editor's Draft "does not have the clout necessary to influence product planning" — and because it gave third-party developers no way to use an existing device. The adopted model is a **permission prompt** plus Permissions Policy. | two designs considered | [WebUSB spec §1](https://usb.spec.whatwg.org/) | 2026-06-05 (draft) | High |
| 2.3 | **Deployment:** Chrome 61 shipped WebUSB on desktop and Android in 2017. The same Chromium implementation reaches Microsoft Edge, Opera and Electron; Firefox and Safari never shipped it. | Chrome 61; 2 engines | [Chrome 61 release notes](https://developer.chrome.com/blog/new-in-chrome-61); [Peripheral Instinct](https://misc0110.net/web/files/peripheralinstinct_www25.pdf) | 2017-09-05 | High |
| 2.4 | Before shipping there was an origin trial in Chrome 54–59, and the initial proposal was followed by an Intent to Implement in 2016. The exact trial dates come from a secondary summary; the stable date is primary. | Chrome 54–59 | (search summary) | 2016–2017 | Medium |
| 2.5 | **Mozilla's objection:** the standards-position issue opened 2018-08-02; in November 2019 Mozilla marked it "harmful" (the recorded label is "position: negative"). Reasons in the thread: attacks on devices that can endanger the host, whether a prompt can yield informed consent, and ADB/phone flashing and hardware wallets as exemplars of the most problematic access. | issue 2018-08-02; harmful 2019-11-10/11 | [mozilla/standards-positions #100](https://github.com/mozilla/standards-positions/issues/100) | 2019-11-11 | High |
| 2.6 | **WebKit's objection:** WebKit cited privacy, agreed with Mozilla's security concerns, and objected that the spec "depends on a specific hardware technology" and "risks the device independence of the web". The rationale was posted 2022-10-10; the "position: oppose" label and closure came 2025-06-06. | 2022-10-10 → 2025-06-06 | [WebKit/standards-positions #68](https://github.com/WebKit/standards-positions/issues/68) | 2025-06-06 | High |
| 2.7 | **Security model in the spec:** protected interface classes are Audio (0x01), HID (0x03), Mass Storage (0x08), Hub (0x09), Smart Card (0x0B), Video (0x0E), Audio/Video (0x10) and Wireless Controller (0xE0); `claimInterface()` rejects them unless the `"usb-unrestricted"` policy is enabled. That policy is reserved for Isolated Web Apps, so ordinary pages cannot reach these classes. A VID/PID/version **blocklist** removes known-bad devices. | 8 protected classes | [WebUSB spec §3, §7, §8](https://usb.spec.whatwg.org/) | 2026-06-05 | High |
| 2.8 | The spec is explicit that the host cannot be saved by the browser alone: "If a device is compromised", it may attack the current or later hosts, and there is "nothing that can be done by the UA to prevent further damage"; signed firmware and physical access are the suggested defenses. | — | [WebUSB spec §3.3](https://usb.spec.whatwg.org/) | 2026-06-05 | High |
| 2.9 | **Standing in 2026:** still a WICG Draft Community Group Report dated 2026-06-05, hosted at a WHATWG address, eleven years after the proposal; there is no second independent implementation. | 11 years; 1 engine | [WebUSB spec](https://usb.spec.whatwg.org/) | 2026-06-05 | High |
| 2.10 | In 2026 a W3C staff formal objection named WebUSB (with the other four) as "detrimental to the security and privacy of users"; the objection's argument and the failed charter attempt are in section 8. | — | [W3C public-review-comments, 2026-07-23](https://lists.w3.org/Archives/Public/public-review-comments/2026Jul/0006.html) | 2026-07-23 | High |

**Implications:** WebUSB's durable ideas are the user-chosen device, the origin-bound per-device grant and the class/blocklist restrictions. Its unresolved problem is that the permission grant, once given, is the whole boundary: Izcal should not treat a USB device as trustworthy input, and should keep protected classes and a blocklist even if it exposes a richer device model.

## 3. WebHID (2018–2026)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Who and where:** Matt Reynolds (Google) proposed a HID API to the WICG on 2018-09-27, with a chooser-based permission model like WebUSB and Web Bluetooth. The spec is a WICG Draft Community Group Report with Matt Reynolds as sole editor. | — | [WICG Discourse](https://discourse.wicg.io/t/human-interface-device-hid-api/3070/); [WebHID spec](https://hid.spec.whatwg.org/) | 2018-09-27 | High |
| 3.2 | **Motivation — driver gaps, not hidden devices:** "Devices that are not well supported by the generic HID driver are often inaccessible to web applications", and "the outputs on most devices are also inaccessible". The spec's examples are niche devices, prototyping/hobbyist boards, VR controls, flight simulators and medical equipment; devices already served by PointerEvent/KeyboardEvent are explicitly not the target. The common shorthand that WebHID reaches "devices the OS hides" is a simplification: the OS exposes them through a generic driver, but not to the web with device-specific features. | — | [WebHID spec §2](https://hid.spec.whatwg.org/) | 2024-09-13 | High |
| 3.3 | **Deployment:** Chrome 89 shipped WebHID on desktop in 2021. Android support was still not shipped in the 2026 platform-status data, which lists a planned Android milestone of 154/157. Chromium derivatives inherit it; Firefox and Safari never shipped it. | Chrome 89; Android planned 154/157 | [Chrome 89 release notes](https://developer.chrome.com/blog/new-in-chrome-89); [Chrome Platform Status](https://chromestatus.com/api/v0/features?q=WebHID) | 2021-03-02 | High |
| 3.4 | An origin trial preceded shipping; Mozilla's position issue records the trial starting in Chrome 86. The trial was moved from Chrome 85 to 86–88 and a Chromium commit reverted an earlier enablement for missing approvals; those details are secondary. | Chrome 86 | [mozilla/standards-positions #459](https://github.com/mozilla/standards-positions/issues/459) | 2020 | Medium |
| 3.5 | **Mozilla's objection:** WebHID was recorded as "harmful" on 2021-07-26 and closed 2021-08-26, with the reasoning that it presents "security and privacy threats that are akin to those for WebUSB". | — | [mozilla/standards-positions #459](https://github.com/mozilla/standards-positions/issues/459) | 2021-08-26 | High |
| 3.6 | **WebKit's objection:** rationale posted 2026-09-14 and "position: oppose" recorded 2026-09-29. WebKit cited tests where "All these devices allow changes to persistent settings", said prompts "do not adequately convey the full security threats behind granting such permissions", rejected blocklists as insufficient, and argued such needs "would be better served by purpose-built, capability-level APIs". | 2026-09-14 → 2026-09-29 | [WebKit/standards-positions #510](https://github.com/WebKit/standards-positions/issues/510) | 2026-09-29 | High |
| 3.7 | **Security model:** access is consent-based; the chooser should require two separate interactions (select, then confirm); devices can be hidden by VID/PID or by descriptor, including a "top-level collection with the HID usage for a keyboard". The spec warns a malicious page could "generate trusted input events" or reprogram device macros, and that HID devices may have sensors that "collect information about its surroundings". | 2 interactions | [WebHID spec §3, §6](https://hid.spec.whatwg.org/) | 2024-09-13 | High |
| 3.8 | **Why it mattered to attackers:** the WWW '25 paper used WebHID to flash custom firmware onto a Logitech Unifying Receiver and to reprogram macros/key mappings, showing that a device the OS treats as an input peripheral is a writable computer from the page. | 1 receiver model, full chain | [Peripheral Instinct](https://misc0110.net/web/files/peripheralinstinct_www25.pdf) | 2025-04-28 | High |
| 3.9 | **Standing in 2026:** still a WICG Draft Community Group Report dated 2024-09-13; six years after proposal (September 2018 to September 2024), one engine (plus Chromium derivatives), no Android stable. | 6 years; 1 engine | [WebHID spec](https://hid.spec.whatwg.org/) | 2024-09-13 | High |

**Implications:** WebHID is the clearest case that the OS's "it is just a keyboard" classification is not a security boundary. Izcal should keep keyboards/pointers behind a separate, stronger gate than other HID collections, require an explicit confirm step in any chooser, and assume HID reports can reprogram the device.

The 2019 review is secondary here; the spec and the WICG venue are primary. | — | [W3C TAG design-reviews #431](https://github.com/w3ctag/design-reviews/issues/431); [Web Serial spec](https://serial.spec.whatwg.org/) | 2019-10 | Medium |

Chrome's platform data states "Web Serial is not implemented on Android"; an Android implementation was still "Proposed" for milestone 148 in 2026, with serial-over-Bluetooth RFCOMM in development for 138. | Chrome 89; Android proposed 148 | [Chrome 89 release notes](https://developer.chrome.com/blog/new-in-chrome-89); [Chrome Platform Status](https://chromestatus.com/api/v0/features?q=SerialPort) | 2021-03-02 | High |

Mozilla's Hacks post (2026-05-21) describes per-site and per-port grants, no enumeration until permission, add-on gating like Web MIDI, and an enterprise policy. | Firefox 151 | [Firefox 151 release notes](https://www.firefox.com/en-US/firefox/151.0/releasenotes/) | 2026-05-19 | High |

| 4.9 | **Security model:** `requestPort()` "requires user interaction and only supports granting access to a single device at a time"; `getPorts()` returns only previously authorized ports; `forget()` revokes. **Implications:** Web Serial is the one API that moved from single-engine to multi-engine in the period: Google shipped in 2021, Mozilla reversed a six-year objection in 2026, and the spec moved to WHATWG. That path worked only after the permission model was made per-port and origin-bound and an enterprise off-switch existed. Izcal should expect serial devices to be unidentified and untrusted by default, and should make the per-port grant revocable and enterprise-controllable.

## 5. Web Bluetooth (2014–2026)

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **Who and where:** the W3C **Web Bluetooth Community Group** was proposed on 2014-07-30 (Jeffrey Yasskin, Google) and launched 2014-07-31. Its stated purpose was "developing a specification for Bluetooth APIs" so sites can "communicate with devices in a secure and privacy-preserving way". Chairs are Jeffrey Yasskin and Reilly Grant. | — | [W3C new-work announcement](https://lists.w3.org/Archives/Public/public-new-work/2014Jul/0003.html); [CG home](https://www.w3.org/community/web-bluetooth/) | 2014-07-31 | High |
| 5.2 | **Design:** `requestDevice()` requires "transient activation"; the UA must prompt the user to choose; it "MUST NOT allow the user to pair entire classes of devices with a website"; and before prompting it must explain what the selected services let the site do. The chooser is the privacy boundary, because a general scan would expose both the user's device and the UA's own address. | — | [Web Bluetooth spec](https://bluetooth.spec.whatwg.org/) | 2026-06-03 | High |
| 5.3 | **Deployment:** Chrome 56 shipped a subset ("GATT Communication") in January 2017 on Android, ChromeOS and macOS. Windows support came later (version not verified here); Linux was never enabled by default. Firefox and Safari never shipped it. | Chrome 56; 1 engine | [Chrome 56 release notes](https://developer.chrome.com/blog/new-in-chrome-56); [CG post, 2017-02-08](https://www.w3.org/community/web-bluetooth/) | 2017-01-25 | High |
| 5.4 | **Standing:** still a Draft Community Group Report dated 2026-06-03, twelve years after the CG launched; it was never a W3C Working Group deliverable and is explicitly "not a W3C Standard nor ... on the W3C Standards Track". | 12 years; CG only | [Web Bluetooth spec](https://bluetooth.spec.whatwg.org/) | 2026-06-03 | High |
| 5.5 | **Mozilla's objection:** recorded "harmful" on 2020-06-12. Mozilla said the generic GATT model relies on a blocklist with "weaker protections than those in WebUSB" and concluded: "This model is unsustainable and presents a signficant [sic] risk to users and their devices." | — | [mozilla/standards-positions #95](https://github.com/mozilla/standards-positions/issues/95) | 2020-06-12 | High |
| 5.6 | **WebKit's objection:** "position: oppose" recorded 2025-12-02, citing the "same set of concerns as with USB"; WebKit called the API "insecure", "a massive privacy risk", and said it "doesn't meet the web platform's device-independence bar." | 2025-12-02 | [WebKit/standards-positions #570](https://github.com/WebKit/standards-positions/issues/570) | 2025-12-02 | High |
| 5.7 | **Fingerprinting is acknowledged in the spec:** `getAvailability()` reveals whether a radio exists "regardless of whether it is powered on or not", which "increases the UA's fingerprinting surface by a bit". Persistent device identifiers can enable location inference and cross-site correlation; without LE privacy "the UA broadcasts its persistent ID to any nearby Bluetooth radio". | — | [Web Bluetooth spec](https://bluetooth.spec.whatwg.org/) | 2026-06-03 | High |
| 5.8 | **Abandoned side quest:** a separate "Web Bluetooth Scanning" specification was never published at its expected URL (404 on 2026-10-21), and broad scanning was not shipped as part of the API; the chooser-based API is what survived. | — | (black-box check of `webbluetoothcg.github.io/web-bluetooth-scanning/`) | 2026-10-21 | Medium |
| 5.9 | In 2026 the W3C attempted to bring the five peripheral APIs into the Devices and Sensors Working Group as tentative deliverables; the attempt failed to reach consensus (section 8), leaving Web Bluetooth a Community Group draft. | — | [W3C public-device-apis, 2026-08-31](https://lists.w3.org/Archives/Public/public-device-apis/2026Aug/0009.html) | 2026-08-31 | High |

**Implications:** Web Bluetooth shows that a chooser plus a blocklist is not enough to earn a second implementation: a generic GATT surface lets any site talk to any class of device, and the spec itself concedes the fingerprinting cost of availability checks. Izcal should not adopt "generic GATT access" as the default shape; a device-class or capability-scoped API would face fewer objections.

| 6.5 | **WebKit's objection:** an issue opened 2025-12-03 carries "position: oppose"; the rationale was not read. | 2025-12-03 | [WebKit/standards-positions #584](https://github.com/WebKit/standards-positions/issues/584) | 2025-12-03 | High |
| 6.6 | **Scope:** "The current scope of this specification is NDEF" — reading and writing NDEF records. The permission is a "default powerful feature" named `"nfc"`; there is no device chooser because the tap is the selection. | NDEF only | [Web NFC spec](https://w3c-cg.github.io/web-nfc/) | 2026 | High |
| 6.7 | **Trust model in the spec:** "By default, NDEF doesn't provide any way to make the content trusted beyond allowing tags to be made permanently read-only"; the spec compares NFC tags to QR codes and relies on the user's tap as intent. It does not discuss relay attacks. | — | [Web NFC spec, Security and Privacy](https://w3c-cg.github.io/web-nfc/) | 2026 | High |
| 6.8 | **Why the tap is not proof of proximity:** relay research showed that a proxy token near a reader can relay to a proxy reader near the genuine token, so the reader believes the token is nearby. Hancke's 2005 technical report described the attack; Francis, Hancke, Mayes and Markantonakis demonstrated a phone-based, software-only relay in 2011–12, exploiting "the assumption that a contactless token within communication range is in close proximity". | 2 proxies; no crypto break | [IACR ePrint 2011/618](https://eprint.iacr.org/2011/618) | 2011-11-21 | High |
| 6.9 | **Fate:** the only shipping implementation is Chrome on Android; the only standards venue is a Community Group; the spec remains pre-CR and NDEF-only. | 1 engine, 1 platform | Sections 6.2–6.3 | 2026 | High |

**Implications:** Web NFC's "tap = intent" model is the weakest trust assumption of the six: the user selects a tag physically, but proximity is relayable and NDEF content is not trustworthy by default. Izcal should not treat an NFC tap as authentication, and should scope any NFC capability to NDEF-like data exchange rather than to a general tag protocol.

## 9. Physical device security incidents that shaped the APIs

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 9.1 | **BadUSB (SR Labs, Black Hat USA 2014)** showed that USB controller firmware in ordinary sticks can be reprogrammed, so a stick can "spoof various other device types" to take over a computer, exfiltrate data or spy on the user; the researchers demonstrated a full system compromise and a self-replicating USB virus "not detectable with current defenses". The lesson: a USB descriptor is a claim, not an identity. | 4 demos reported | [Internet Archive: BadUSB talk](https://archive.org/details/youtube-nuruzFqMgIw) | 2014-08-11 (listed) | Medium |
| 9.2 | **MouseJack (2016)** showed that wireless keyboard/mouse dongles can be made to inject keystrokes; the WWW '25 paper cites it as the class of attack reachable once a page can flash a wireless receiver. | — | [Peripheral Instinct](https://misc0110.net/web/files/peripheralinstinct_www25.pdf) | 2016 (cited) | Medium |
| 9.3 | **BlueBorne (Armis, 2017)** disclosed eight Bluetooth vulnerabilities affecting Android, Windows, Linux, iOS and macOS, with nine related zero-days in the security note's account (2.2); the vendor estimated about 5.3 billion devices were vulnerable and stressed that no pairing or user interaction was required. Vendor estimate; the primary report was not read. | 8 vulns (9 zero-days in security note 2.2); ~5.3B devices (vendor) | [Armis BlueBorne](https://www.armis.com/research/blueborne/) | 2017-09-12 | Medium |
| 9.4 | **KNOB (USENIX Security 2019)** showed that Bluetooth BR/EDR key negotiation could be driven to "only 1 byte (8 bits) of entropy", after which the key is brute-forceable and traffic can be decrypted and injected in real time. The evaluation covered "more than 14 Bluetooth chips" from Intel, Broadcom, Apple and Qualcomm; "all tested devices are vulnerable". | 8-bit key; 14+ chips | [USENIX Security 2019](https://www.usenix.org/conference/usenixsecurity19/presentation/antonioli) | 2019-08 | High |
| 9.5 | **BLESA (WOOT 2020)** showed that the BLE reconnection procedure has "two critical security weaknesses in the specification", so "even a device implementing the BLE protocol correctly may be vulnerable to spoofing"; the authors found exploitable logic in the Linux, Android and iOS stacks. The lesson: a prior pairing is not proof that the reconnecting peer is the same device. | 3 platform stacks | [USENIX WOOT 2020](https://www.usenix.org/conference/woot20/presentation/wu) | 2020-08 | High |
| 9.6 | **BrakTooth (SUTD, 2021)** disclosed 16 vulnerabilities in Bluetooth Classic stacks across 13 devices from 11 vendors, affecting more than 1,400 product listings; the attacks range from firmware crashes/deadlocks to arbitrary code execution in some chips, and require no pairing. The CVE count is 25 here and 20 in the security note (2.5, a secondary source); the spec states both. | 16 vulns; 25 CVEs (20 in security note 2.5); 13 devices; 11 vendors; >1,400 listings | [BrakTooth report](https://asset-group.github.io/disclosures/braktooth/braktooth.pdf) | 2021-08-31 | High |
| 9.7 | **NFC relay attacks** break the assumption that a token within range is in close proximity: a proxy token near the reader relays to a proxy reader near the genuine token, so the reader believes the token is nearby. No cryptography is broken. | 2 proxies | [IACR ePrint 2011/618](https://eprint.iacr.org/2011/618) | 2011-11-21 | High |
| 9.8 | **Peripheral Instinct (WWW '25)** reversed-engineered 22 device models from 15 vendors and built full exploit chains through WebHID, WebUSB, Web Serial and Web MIDI: custom firmware on a Logitech Unifying Receiver, macro/key-map changes on mice and keyboards, and AT-command attacks over Web Serial enabling "SMS and two-factor-code interception, GPS tracking, permanent SIM lockout". **Implications:** Every incident says the same thing in a different transport: the device is a computer that can lie about what it is and can be reprogrammed. A browser device API is therefore a capability to run an untrusted computer's firmware-update protocol from a web page; Izcal should treat device identity, descriptors and firmware as attacker-controlled, and should not assume that a user-chosen device is a safe device.

## 10. Fingerprinting, privacy, regulator and enterprise response

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 10.1 | The Web MIDI spec calls device enumeration "a potential target for fingerprinting" (names, manufacturers, opaque identifiers), while noting that most systems have no MIDI interfaces. | — | [Web MIDI spec, Privacy](https://www.w3.org/TR/webmidi/) | 2026-10-20 | High |
| 10.2 | The Web Bluetooth spec concedes that `getAvailability()` "increases the UA's fingerprinting surface by a bit", that persistent identifiers can enable location inference and cross-site correlation, and that without LE privacy the UA broadcasts a persistent ID to nearby radios. | — | [Web Bluetooth spec](https://bluetooth.spec.whatwg.org/) | 2026-06-03 | High |
| 10.3 | The Web Serial spec's privacy section warns that vendor/product IDs, serial numbers, MAC addresses and device-stored information can "identify the user between sessions", and recommends clearing permission-related identifiers with site data. For generic adapters, "there is no metadata that can be read to determine the identity of the device connected to the port." | — | [Web Serial spec, Privacy](https://serial.spec.whatwg.org/) | 2026-10-19 | High |
| 10.4 | Mozilla's WebUSB thread treated fingerprinting as a reason for the chooser ("using a device picker step is good API design to limit fingerprinting") but not as sufficient protection against device attacks. WebKit's WebUSB and Web Bluetooth positions list "concerns: privacy" alongside security. | — | [Mozilla #100](https://github.com/mozilla/standards-positions/issues/100); [WebKit #68](https://github.com/WebKit/standards-positions/issues/68) | 2019–2025 | High |
| 10.5 | The 2026 formal objection generalises the privacy problem: grants are "Too broad", "Too persistent and transferable" and "Too silent". It cites grants inherited after XSS, site compromise or domain re-registration — a privacy and security failure that survives the original session. | — | [W3C FO](https://lists.w3.org/Archives/Public/public-review-comments/2026Jul/0006.html) | 2026-07-23 | High |
| 10.6 | The WWW '25 paper shows how permission is obtained in practice: phishing pages impersonating legitimate vendors, and — citing Hazhirpasand et al. — a browser-game study that "convinced up to 95% of users into granting permissions". A prompt is not informed consent if the user cannot evaluate the device risk. | up to 95% of users (cited study) | [Peripheral Instinct](https://misc0110.net/web/files/peripheralinstinct_www25.pdf) | 2025-04-28 | High |
| 10.7 | **No dedicated peer-reviewed measurement of fingerprinting via these six APIs was found this session.** The evidence for fingerprinting is the specs' own admissions and the vendors' positions, not a published enumeration-entropy study. | — | (gap) | 2026-10-21 | High (that no study was found) |
| 10.8 | **Enterprise response:** Firefox 151 added `DefaultSerialGuardSetting`, and Firefox 152 disabled Web Serial by default when the browser is enterprise-managed. Chrome enterprise policy documentation for WebUSB/WebHID/WebSerial guard settings could not be read (JavaScript-only pages), so Chrome's exact policy names and versions are unknown here. | — | [Firefox Enterprise 151 notes](https://firefox-admin-docs.mozilla.org/release-notes/version/firefox-151...latest/) | 2026-06-16 | High (Firefox) / unknown (Chrome) |
| 10.9 | **Regulator response:** no regulator action specific to USB/Bluetooth/serial/HID/NFC web APIs was found. General device-fingerprinting guidance and browser-security standards exist, but none was read as binding on these APIs. | — | (gap) | 2026-10-21 | Low |

**Implications:** The privacy case against these APIs is not primarily about enumerating devices before permission — the chooser model mostly prevents that. It is about what a grant means after it is given: persistence, transfer through XSS or domain re-registration, and the user's inability to judge the device. Izcal should bind grants to origin and device with an expiry and a clear revocation path, and should not let a grant survive a site-identity change.

## 11. What survived, and why

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 11.1 | **The chooser survived.** WebUSB, WebHID, Web Serial and Web Bluetooth all require the user to pick a device; `getDevices()`/`getPorts()` return only devices already granted, not the full bus. This limits both drive-by access and enumeration fingerprinting. | 4 of 6 APIs | [WebUSB](https://usb.spec.whatwg.org/), [WebHID](https://hid.spec.whatwg.org/), [Web Serial](https://serial.spec.whatwg.org/), [Bluetooth](https://bluetooth.spec.whatwg.org/) | 2024–2026 | High |
| 11.2 | **Origin-bound, per-device grants survived.** WebUSB stores an allowed-device list per origin; Web Serial grants "a single device at a time" and has `forget()`; Web Bluetooth forbids pairing entire device classes; WebHID and WebUSB added `forget()` in Chrome 100–103. | 1 device per grant | [Web Serial §7](https://serial.spec.whatwg.org/); [Chrome Platform Status](https://chromestatus.com/api/v0/features?q=WebUSB) | 2022–2026 | High |
| 11.3 | **Class and blocklist restrictions survived.** WebUSB's eight protected interface classes and VID/PID blocklist, WebHID's keyboard/usage blocking and blocklist file, and Web Serial's Bluetooth service-class blocklist all encode "some devices are too dangerous to expose by default". | 8 classes | [WebUSB §3/§7](https://usb.spec.whatwg.org/); [WebHID §15](https://hid.spec.whatwg.org/) | 2026 | High |
| 11.4 | **Secure context and Permissions Policy survived.** All six require a secure context; the APIs are policy-controlled features with a default allowlist of `'self'` (WebUSB also defines `"usb-unrestricted"` only for Isolated Web Apps). | — | Specs, §§Integrations | 2026 | High |
| 11.5 | **User activation survived.** Web Bluetooth requires "transient activation" for `requestDevice()`; Web Serial's `requestPort()` "requires user interaction"; the anti-scanning rationale is explicit in the Bluetooth spec. | — | [Bluetooth spec](https://bluetooth.spec.whatwg.org/) | 2026-06-03 | High |
| 11.6 | **Capability tiers survived, but only in Web MIDI.** The `sysex` flag is a separate, stronger permission because SysEx can update firmware. No other API has an equivalent "this grant can rewrite the device" tier. | 2 tiers | [Web MIDI spec](https://www.w3.org/TR/webmidi/) | 2026-10-20 | High |
| 11.7 | **Add-on gating survived as a Mozilla-specific model.** Firefox gates Web MIDI (since 108) and Web Serial (since 151) behind a site-permission add-on, an origin-specific install rather than a prompt. It is the only working alternative permission mechanism among the six. | 2 APIs | [Firefox 108 notes](https://www.firefox.com/en-US/firefox/108.0/releasenotes/); [Firefox 151 notes](https://www.firefox.com/en-US/firefox/151.0/releasenotes/) | 2022–2026 | High |
| 11.8 | **The standards venue moved, not the security model.** Web Serial became a WHATWG Living Standard in 2026; WebUSB/HID/Bluetooth are hosted at WHATWG addresses but still carry Community Group front matter. Moving venue did not resolve the second-implementation problem. | 1 of 4 is a Living Standard | [Web Serial](https://serial.spec.whatwg.org/); [WebUSB](https://usb.spec.whatwg.org/) | 2026-10-19 | High |
| 11.9 | **The strongest lesson the specs themselves state:** the browser cannot make a compromised device safe — "nothing that can be done by the UA to prevent further damage" (WebUSB); host software "may be vulnerable to attack because it improperly validates input from connected devices" (Web Serial); a malicious page can "generate trusted input events" (WebHID). | — | Specs, Security sections | 2024–2026 | High |

**Implications:** What survived is not the device transports but the **permission architecture**: a user-chosen, origin-bound, per-device, revocable grant with class restrictions, a secure context and a policy hook. Izcal should build its device layer around that architecture and treat the transport (USB, HID, serial, Bluetooth, NFC, MIDI) as a set of protocol adapters behind it, with an explicit high-risk tier for anything that can rewrite device firmware.
