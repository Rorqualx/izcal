# Izcal devices: determinism, recording and testing

Compiled 21 October 2026. Primary sources were preferred (specifications, vendor documentation, papers, published protocol references).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**M-1 note.** No third-party project's source code, header, commit, diff or code review was read or cited for this note. Chrome's internal diagnostic pages, the DevTools protocol and the Web test APIs are cited as *published documentation and protocol references*; where a value appears only beside source code, it is left as an open question for black-box measurement. Test suites and vendor test tools are treated as **test-only inputs** under HGBA-2 2.3.2 and are marked as such; none is proposed for shipping.

**Method note.** The shared web-search budget was spent on the load-bearing questions first: the timing semantics of the six APIs, the corpus's own recording precedent, and the published emulation/test tooling. Claims taken from search snippets rather than a fetched page are graded Medium; claims that rest on the *absence* of published documentation are graded Medium or Low and are phrased as "no published documentation found". The sibling notes in this directory cover the APIs' status and permissions (`specs_standards.md`), OS backends (`os_interfaces.md`) and identifiers (`fingerprinting_privacy.md`); this note does not repeat them except where recording depends on them.

**Scope.** WebUSB, WebHID, Web Serial, Web MIDI, Web Bluetooth and Web NFC, as external inputs to a deterministic browser, and the DevTools/IIP surface that would record, replay and test them.

## 1. Device events as external nondeterministic input

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **WebUSB exposes two page-visible events, `connect` and `disconnect`**, and only for devices the origin is already paired with; a new device arrives only through the `requestDevice()` chooser. `getDevices()` returns paired attached devices. Arrival and removal are therefore asynchronous, page-unpredictable and partly grant-dependent. | 2 events | [MDN: USB](https://developer.mozilla.org/en-US/docs/Web/API/USB) | read 21 Oct 2026 | High |
| 1.2 | **WebUSB data movement is explicit, not event-driven.** The page calls `transferIn`, `transferOut`, `controlTransferIn` or `controlTransferOut`; the documentation states "Multiple transfers submitted to an endpoint always execute in order", so per-endpoint ordering is defined while *when* a device answers is not. A device cannot push data to the page; the page polls by issuing transfers. | 4 transfer methods; per-endpoint ordering | [Chrome: Access USB devices](https://developer.chrome.com/docs/capabilities/usb) | read 21 Oct 2026 | High |
| 1.3 | **WebHID delivers device data as `inputreport` events**, each carrying a `DataView`, a `reportId` and the device. The API is "asynchronous by design", and "HID data can be received at any time"; the documentation promises no latency, rate or ordering guarantees. Input-report timing is the device's and the OS's, not the page's. | 1 event class | [Chrome: Connecting to uncommon HID devices](https://developer.chrome.com/docs/capabilities/hid) | read 21 Oct 2026 | High |
| 1.4 | **Web Serial is a byte stream, not a message stream.** Data "can be received at any time" and may be "arbitrarily chunked"; the page monitors `connect` and `disconnect`, and disconnecting an open port surfaces as a stream error as well as an event. Chunk boundaries are an OS artifact that the page can observe, so they are part of the input, not an implementation detail. | 2 events; arbitrary chunking | [Chrome: Read and write from serial ports](https://developer.chrome.com/docs/capabilities/serial) | read 21 Oct 2026 | High |
| 1.5 | **Web MIDI separates receipt time from send time.** A `midimessage` event's `timeStamp` is "the time the message was received by the system" at high resolution. System Real-Time messages "may actually occur in the middle of other messages in the input stream" and are "dispatched as they occur", while ordinary messages are buffered until complete. `MIDIOutput.send(data, timestamp)` targets a time "relative to the navigation start", and equal timestamps must preserve call order. | receipt time vs target time; 0xF8 timing-clock stream | [Web MIDI API](https://webaudio.github.io/web-midi-api/) | read 21 Oct 2026 | High |
| 1.6 | **Web MIDI connection state can be stale by construction.** "Some underlying systems may not provide notification events for device connection status", with polling causing "long time delays"; on reconnection the system attempts to reopen before firing `statechange`, so the event reflects the final state, not the transition. A recorded `statechange` is therefore not evidence of when the physical change happened. | polling delay, no bound | [Web MIDI API](https://webaudio.github.io/web-midi-api/) | read 21 Oct 2026 | High |
| 1.7 | **Web Bluetooth signals only disconnection.** `gattserverdisconnected` fires when an active GATT connection is lost; the documentation describes no `connect` event, and pages cannot enumerate nearby devices. Advertisements are a separate explicit subscription (`watchAdvertisements()`), and each advertisement is a discrete packet with its own data. The advertisement stream, not a device list, is the nondeterministic input. | 1 connection event; advertisements opt-in | [MDN: BluetoothDevice](https://developer.mozilla.org/en-US/docs/Web/API/BluetoothDevice); [Chrome: Interact with Bluetooth devices](https://developer.chrome.com/docs/capabilities/bluetooth) | read 21 Oct 2026 | High (disconnect) / Medium (advertisement fields) |
| 1.8 | **Bluetooth advertisement records carry RSSI, TX power and manufacturer/service data**, which the DevTools protocol models as a `ScanEntry` it can simulate. RSSI and reception intervals are radio conditions, not device logic: the same peripheral in the same state produces different values run to run. | RSSI per advertisement | [CDP: BluetoothEmulation](https://chromedevtools.github.io/devtools-protocol/#/BluetoothEmulation) | read 21 Oct 2026 | Medium |
| 1.9 | **Web NFC is proximity-triggered and event-driven.** `NDEFReader.scan()` resolves when listening is established, not when a tag appears; while active, "the UA MUST listen to NDEF messages on all connected NFC adapters", and a read is "always performed" when devices are in range. The UA polls; the page cannot enumerate tags or poll a tag's presence. | 2 events (`reading`, `readingerror`) | [Web NFC](https://w3c-cg.github.io/web-nfc/) | read 21 Oct 2026 | High |
| 1.10 | **NFC serial numbers are not a stable identity.** `NDEFReadingEvent.serialNumber` is the anti-collision identifier, "empty string in case none is available", and "some tags even create a random number on each read". A recording must capture it as a value, but replaying it must not imply the tag will present the same number again. | 4- or 7-part colon-separated values, or empty | [Web NFC](https://w3c-cg.github.io/web-nfc/) | read 21 Oct 2026 | High |
| 1.11 | **Whole device classes are refused before any event exists.** Chrome blocks FIDO HID devices, and protected keyboard/mouse usages cannot exchange reports through WebHID. WebUSB's specification defines protected interface classes (audio, HID, mass storage, smart card, video, audio/video, wireless) that cannot be claimed. Refusal is a first-class device outcome, not an error path. | protected classes incl. audio, HID, mass storage, smart card, video, wireless; 2 protected HID usages | [Chrome: HID](https://developer.chrome.com/docs/capabilities/hid); [WebUSB](https://wicg.github.io/webusb/#has-a-protected-interface-class) | read 21 Oct 2026 | High (HID) / Medium (USB classes) |
| 1.12 | **Device identity reaches script.** WebUSB exposes `vendorId`, `productId`, `serialNumber`, `manufacturerName` and `productName`; Web Bluetooth exposes a `BluetoothDevice.id` that "uniquely identifies a device"; Web NFC exposes the serial number. These are stable, cross-site linkable values and are the main redaction surface of a device recording. | 5 USB identity fields | [MDN: USBDevice](https://developer.mozilla.org/en-US/docs/Web/API/USBDevice); [MDN: BluetoothDevice](https://developer.mozilla.org/en-US/docs/Web/API/BluetoothDevice) | read 21 Oct 2026 | High |

**Implications:** Device input is *external, asynchronous and partly page-driven*: USB and HID data arrives only because the page asked, while serial bytes, MIDI messages, advertisements and NFC reads arrive when the device, radio or user decides. A deterministic browser must therefore treat device events like clock, entropy and network bytes: substrate inputs recorded at a boundary, never ambient side effects. Refusals (protected classes, chooser cancellations) are inputs too and must be recordable.

## 2. What a device recording must contain

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Values.** Report, transfer and byte payloads, plus the descriptors the browser itself parses: the WebUSB documentation shows the browser reading the BOS descriptor and configuration descriptors during enumeration, and WebHID exposes `collections` as "a hierarchical description of the device's report formats". Descriptor bytes must be recorded because descriptor parsing is exactly where device bugs live. | device, configuration, BOS, report descriptors | [Chrome: Build for WebUSB](https://developer.chrome.com/docs/capabilities/build-for-webusb); [Chrome: HID](https://developer.chrome.com/docs/capabilities/hid) | read 21 Oct 2026 | High |
| 2.2 | **Order.** Per-endpoint USB transfer order is specified; per-port MIDI send order for equal timestamps is specified; cross-device order is not defined by any API and can only come from the browser's scheduler. A recording needs one global order, not six independent streams. | 1 global order + per-endpoint/port order | [Chrome: USB](https://developer.chrome.com/docs/capabilities/usb); [Web MIDI](https://webaudio.github.io/web-midi-api/) | read 21 Oct 2026 | High |
| 2.3 | **Timing.** Arrival timestamps on the substrate clock (USB completion, HID report, serial chunk, MIDI receipt, advertisement, NFC read) and page-supplied targets (MIDI `send()` timestamps). MIDI already defines receipt time as a high-resolution value, so it is recordable as a value rather than reconstructed. | per-event timestamp | [Web MIDI](https://webaudio.github.io/web-midi-api/) | read 21 Oct 2026 | High |
| 2.4 | **The page's calls.** `requestDevice`/chooser result, `open`/`close`, `claimInterface`, `selectConfiguration`, `transferIn/Out`, `sendReport`, `sendFeatureReport`, `open`/`close` of serial ports, `watchAdvertisements`, GATT connect/disconnect and operations, `scan`, `write`, `makeReadOnly`, `MIDIPort.open/close`, `send`. Without them a replay cannot know which transfer produced which reply. | six API surfaces | Sections 1.1–1.10; [MDN: USBDevice](https://developer.mozilla.org/en-US/docs/Web/API/USBDevice) | read 21 Oct 2026 | High |
| 2.5 | **Grant and chooser decisions.** WebUSB requires a user chooser for a new device; Web Bluetooth requires a chooser and cannot enumerate; Web NFC requires permission. The decision (and the persisted grant store) is an input: replay has no user and no hardware, so it must read the decision as a value, exactly as the network recording reads long-lived stores as the values read. | 1 decision per grant | [DevTools spec 6.1, DT-D2](../../reports/Izcal%20DevTools%20spec.md); [Izcal networking 6.16](../../reports/Izcal%20networking.md) | 21 Oct 2026 | High |
| 2.6 | **Adapter and device state.** Bluetooth adapter `absent`/`powered-off`/`powered-on` and LE support, the connected GATT tree, USB configuration and claimed interfaces, serial control signals, MIDI port state. The DevTools protocol's Bluetooth emulation treats adapter state as an explicit settable value, which confirms it is state, not an inference. | 3 adapter states | [CDP: BluetoothEmulation](https://chromedevtools.github.io/devtools-protocol/#/BluetoothEmulation) | read 21 Oct 2026 | Medium |
| 2.7 | **Errors and faults with typed reasons.** USB stall and reset, HID report errors, serial framing/parity errors and disconnect, GATT operation errors and disconnection, NFC `readingerror`, MIDI sysex refusal. A replay that records only successes cannot reproduce the page's error paths. | 1 typed reason per failure | [Chrome: Serial](https://developer.chrome.com/docs/capabilities/serial); [Web NFC](https://w3c-cg.github.io/web-nfc/) | read 21 Oct 2026 | High |
| 2.8 | **Chunk boundaries.** Serial data may be "arbitrarily chunked"; the page's reads see those boundaries. A recording that concatenates bytes and re-chunks them differently changes what the page observes even when the byte stream is identical. | boundary = input | [Chrome: Serial](https://developer.chrome.com/docs/capabilities/serial) | read 21 Oct 2026 | High |
| 2.9 | **What cannot be captured.** Bus transactions below the OS driver, radio packets and channel conditions, NFC tag frames, firmware state, and the physical event that caused a report. These are below the lowest boundary the browser can observe, as TLS secrets are below the network recording's boundary. | structural exclusion | [Izcal networking 6.16](../../reports/Izcal%20networking.md); [HGBA-2 4.6, device-access rule](../../reports/HGBA%202%20browser%20architecture%20spec.md) | 21 Oct 2026 | High |
| 2.10 | **Start state.** Process launch plus a freshly launched device service with a recording nonce, so the recording starts from known empty device state and holds no other tab's devices, as NW-D2 does for the partition service. | 1 launch boundary | [Stage 1 design 3.4](../../reports/HGBA%20Stage%201%20architecture%20design.md); [Izcal networking 6.16](../../reports/Izcal%20networking.md) | 21 Oct 2026 | High |

**Implications:** A device recording is an *input log at the device-service boundary plus the page's calls and grant decisions*, with descriptor bytes, per-event timestamps, chunk boundaries and typed failures. Recording only payloads would replay the happy path and miss exactly the state and timing bugs developers bring to DevTools.

## 3. Corpus precedent and its mapping to device sessions

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **NW-D2 records at the decryption boundary, in a fresh dedicated partition service, and replay never re-opens a socket.** The decision's rejected alternatives are Fetch-only (too high) and ciphertext plus crypto entropy (too low). The rule is "the lowest layer that holds no secret". A device session has the same shape: the API boundary is too high (it hides descriptor and protocol parsing), the bus/radio is too low (OS-specific, often unobservable), and the OS device interface is the lowest portable, secret-free boundary. | 3 candidate boundaries | [Izcal networking NW-D2](../../reports/Izcal%20networking.md), 6.16 | 21 Oct 2026 | High |
| 3.2 | **The recorded unit is a dedicated, freshly launched service with a recording nonce**, holding no other tab's traffic; reads from state that outlives the recording are recorded as *the values read*, and writes are re-executed and compared. Device analogue: a fresh device service per recording, permission-store reads as values, permission writes re-executed. | 1 service per recording | [Izcal networking 6.16](../../reports/Izcal%20networking.md) | 21 Oct 2026 | High |
| 3.3 | **Network recordings carry typed per-datagram records, receive times, decision points and outgoing plaintext hashes.** Device analogue: typed per-transfer/report/message records, arrival times, chooser and adapter decisions, and a hash per outgoing call. | per-record typing | [Izcal networking 6.16](../../reports/Izcal%20networking.md) | 21 Oct 2026 | High |
| 3.4 | **Replay feeds recorded outcomes into the same state machines and compares each outgoing hash, so divergence is found at the first differing byte.** Device replay should do the same above the device-service boundary. | first-byte divergence | [Izcal networking 6.16](../../reports/Izcal%20networking.md), NW-37 | 21 Oct 2026 | High |
| 3.5 | **DT-D2 starts recordings at process launch and never keeps a partial segment**; opening DevTools on a loaded page gives live views labelled "live: no history before now". Device sessions inherit this: a device connected before recording has no recorded attach event and must be labelled. | 1 start state | [DevTools spec DT-D2](../../reports/Izcal%20DevTools%20spec.md) | 21 Oct 2026 | High |
| 3.6 | **DT-D2's "never recorded" list is credential-shaped**: keystrokes and IME input into password, one-time-code and payment fields, password-manager fills, WebAuthn/FedCM/payment results. Device analogue: HID keyboard and mouse reports, FIDO reports, and any device payload typed into a credential field are never recorded; they become same-length, same-type placeholders. | never-recorded classes | [DevTools spec DT-D2](../../reports/Izcal%20DevTools%20spec.md) | 21 Oct 2026 | High |
| 3.7 | **Redaction replays the redacted bundle and reports the first divergence** ("reproduces exactly until 00:41; approximate after"), because a recording is an input log. Redacting a serial number or a Bluetooth id that the page branches on has exactly this cost, and must be measured the same way. | exact-until label | [DevTools spec 6.5 rule 6](../../reports/Izcal%20DevTools%20spec.md) | 21 Oct 2026 | High |
| 3.8 | **Pre-renderer decision records make broker-side refusals replayable.** A navigation blocked before a renderer exists is recorded as a decision record and can answer "would this have loaded without the entry?". Device analogue: a chooser refusal or protected-class block is a decision record, replayable and answerable as "would this device have been granted?". | 1 decision record | [DevTools spec DT-D2](../../reports/Izcal%20DevTools%20spec.md) | 21 Oct 2026 | High |
| 3.9 | **Live driving and simulation are separate.** Live network actions need write capability on the origin and are labelled in every view; a production recording cannot be re-run below its boundary. Device writes (a tag write, a device command, a firmware update) are *physical and sometimes irreversible*, so they belong to the live, labelled class and never to automatic replay. | 2 modes | [DevTools spec DT-D5](../../reports/Izcal%20DevTools%20spec.md) | 21 Oct 2026 | High |
| 3.10 | **DT-1's exclusion classes are listed, not open-ended** (GPU output, media, `SharedArrayBuffer` races, credential placeholders), and nothing past a divergence is shown as exact. Device classes (radio, wall-clock timing, protected devices) must be added to the same published list, not handled ad hoc. | 4 excluded classes today | [DevTools spec DT-1](../../reports/Izcal%20DevTools%20spec.md) | 21 Oct 2026 | High |
| 3.11 | **The replay host has no network, storage service or GPU device, and runs one recorded process under `hg-substrate-sim`.** The device analogue is structural: a replay host holds **no real device**, only a virtual device fed from the recording; engine crates receive only the simulator (G12). | 3 absent services today | [DevTools spec 6.1, G12](../../reports/Izcal%20DevTools%20spec.md) | 21 Oct 2026 | High |
| 3.12 | **Inspection must be invisible to content (DT-16).** A device recorder adds a listener inside the device service; the device APIs already promise no timing guarantees, but the recorder's effect must still be measured, and device recording is covered by DT-15's cost probe. | 1,000-of-1,000 target | [DevTools spec DT-15, DT-16](../../reports/Izcal%20DevTools%20spec.md) | 21 Oct 2026 | High |
| 3.13 | **The WebCrypto sensitive-draw class records values encrypted at rest and treats them as credential-class.** Device pairing and bonding material is held by the OS below the boundary, like TLS secrets, so it is never recorded; any device token the page itself sees is page content under the existing rules. | 1 precedent class | [Izcal WebCrypto 6.7](../../reports/Izcal%20WebCrypto.md); [Izcal networking 6.16](../../reports/Izcal%20networking.md) | 21 Oct 2026 | High |
| 3.14 | **DET-1 replays a recorded corpus with bit-identical engine outputs 1,000 of 1,000 times, and a recording missing its build ID, data versions or decision-point log is refused.** A device recording needs the same versioning fields plus the device-service build and the OS interface version, or it cannot be replayed honestly. | 1,000/1,000 | [Future software browser engine DET-1](../../reports/Future%20software%20browser%20engine.md); [Stage 1 design 3.3](../../reports/HGBA%20Stage%201%20architecture%20design.md) | 21 Oct 2026 | High |

**Implications:** Device recording is a fourth instance of the corpus's proven pattern—renderer, network, crypto, device—with one genuinely new problem: the physical layer below the OS interface is unobservable, so its exclusion classes are *structural* and must be named in the UI and in the target, not discovered per bug. The corpus IDs to reuse are DT-D2, DT-1, DT-15, DT-16, NW-D2, NW-37, REC-R1–R6 and G12.

**Implications:** Every real system emulates the *device class* (fake USB device, virtual Bluetooth adapter, mock NFC tag) or transports it at the OS boundary (USB/IP); none reproduces physics. The closest existing model to what Izcal needs is the WebUSB Testing API plus CDP's BluetoothEmulation: an in-browser fake device that answers the chooser and feeds typed events. Izcal should build its virtual-device oracle in that shape, one per class, driven by a recording.

## 5. Test oracles and corpora for device stacks

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **USB descriptor parsing has a published conformance oracle.** USB-IF's Chapter 9 (Device Framework) tests cover device, configuration, interface, endpoint, BOS and qualifier descriptors and the standard requests; every peripheral must pass Chapter 9 for certification, and USBCV is the free tool (USB20CV/USB30CV). The virtual-device oracle is therefore both a test asset and the replay host's device provider—one component, two uses.

## 6. DevTools design: an IIP device domain

**Recommended recording model (from the evidence).** Record at the **device-service boundary**: the typed events the OS device interface delivers to Izcal (USB transfers per endpoint, HID input/feature reports, serial bytes with chunk boundaries and control signals, MIDI bytes with receipt timestamps, Bluetooth adapter/discovery/GATT events, NFC reads), plus the page's calls and the broker's grant decisions. A fresh device service per recording carries a recording nonce. Descriptors are recorded as values, because the browser parses them. Replay replaces the OS interface with a virtual device fed from the record; no real device, radio or tag is ever opened, and outgoing calls are hashed and compared. This is NW-D2's structure applied to devices, with one acknowledged limit: the OS GATT stack and bus/radio sit below the boundary, so the excluded physical classes are named and labelled, not silently dropped.

## 8. Open questions

- **Q-DV-1.** What exactly does each OS deliver at the device-service boundary—raw HID reports or pre-parsed usages, GATT operations or ATT PDUs, USB transfers or URBs, NDEF messages or tag frames? The recording's fidelity and the exclusion list depend on it, and it needs black-box measurement per OS (sibling note `os_interfaces.md` is the starting point).
- **Q-DV-2.** Should a device recording sit above the OS device interface (portable, less fidelity) or, where the OS permits, below it (more fidelity, OS-specific formats)? The corpus's decryption-boundary rule favours one portable boundary; the USB/IP precedent shows a second, richer format is possible.
- **Q-DV-3.** Are device payloads page content by default, or is a device class (HID input, MIDI performance, NFC tag contents) sensitive by default? This is a policy decision with a direct effect on the "never recorded" list.
- **Q-DV-4.** Which of the six APIs are in Stage 1 scope? Chrome is the only shipping implementer for most of them, and Web Bluetooth's advertisement API and Web NFC's desktop support are themselves unsettled.
- **Q-DV-5.** Does the BiDi Bluetooth module become a stable cross-vendor oracle, or does it stay an experimental, browser-global CDP-shaped feature? Its scoping conflict is unresolved.
- **Q-DV-6.** Is there a usable test API for WebHID (and for Web MIDI) comparable to `navigator.usb.test` and `WebNFCTest`? No published one was found; if none exists, Izcal must build the fake at the service boundary.
- **Q-DV-7.** Should replay resample timing from a device model for what-if runs (like `hg-netsim`'s link model), and how should those runs be labelled so they are never confused with recorded timing?
- **Q-DV-8.** What is the licence of the community MIDI test files, and can any of the membership-gated Bluetooth/NFC test cases be reproduced from their public specifications without copying them? (Test-only use still needs a clean provenance record.)
- **Q-DV-9.** How should a device recording represent a device that was already connected at process launch, given that DT-D2's start state has no attach event? A synthetic "present at start" record, labelled, seems the only honest option.
- **Q-DV-10.** Do device identifiers need a per-recording mapping table (placeholder ↔ real value) that is itself encrypted, as the WebCrypto sealed-record rule does for keys, so a user can un-redact their own bundle?
- **Q-DV-11.** Can recording be made invisible to content (DT-16) when a HID device's report rate is itself observable by the page? The recorder must not change the event cadence it is measuring.
- **Q-DV-12.** What does a device replay do when the page calls an API the recording never exercised—return a typed "not in recording" error, or fall through to a virtual device's default? A defined error is testable; a default invents a session.
