# Izcal devices, draft 0.1 — independent design critique (phase 8)

Date: 21 October 2026. Status: phase 8 critique of draft 0.1. I did not write the specification.

**Method.** I read the shared phase-2c brief, the `first-principles-spec` skill and its `references/spec-template.md`, `reports/Izcal devices.md` (draft 0.1, 1,037 lines) and all seven research notes in `research_notes/Izcal devices/`, then judged the design independently against the corpus. I did not rewrite the spec, did not fact-check dates, links or note-row citations (a separate fact-checker does that), did not read or cite any third-party source code, and did not edit any existing document. This file is the only file I created. It contains no email address.

**Judged against.** HGBA-2 2.4.1 (M-1, P1–P6, I-1/I-2, B1/B2), HGBA-3 3.3.1 (B9, DET-1/DET-2, PRIV-2, AG-0), the Stage 1 architecture design 0.14.2 (process map, D-S1–D-S4, milestones, staffing), the security scope 0.3.6 (36 process kinds, 38 threat models, CON-R1–R5, ATK/TB tables, SEC-24, REC-R1–R6), the coding standard 0.3.5 (tiers, G-ranges, CS-ER-19, CS-TY-12/13), the shell 0.3 (SH-D2, 11 prompt classes, prompt ledger), DevTools 0.3.5 (DT-D2, DT-1, DT-13, IIP), resource footprint 0.4.3 (FP-1, FP-22, FP-D8/D13, FP-25, FP-36, §8.2), extensions 0.4 (Ring C, EX-D5), DOM/bindings 0.3 (6.18 web-API table, DM-D1/DM-D5), accessibility 0.2.4 (AX-D11), layout 0.4.2 (LY-D10, ST-D18), HTML/CSS parsing and style 0.3.5 (ST-D18), networking 0.3.3 (NW-D4, NW-37), and images and media 0.4.1 (MD-D3, MD-D10).

**Scope.** The six assignment areas: one boundary and the process/ticket/permission/prompt model; per-API stack placement, including Bluetooth/NFC and every parser; per-device/per-origin/container grants, identifiers and rotation; determinism, recording and replay; agents and extensions; footprint, energy, fuzzing and Stage 1/Stage 2 placement. Severity is about effect on the design, not confidence in the observation.

## What the design gets right

- **One boundary and one grant model.** Six APIs with six incompatible permission stories become one grant record, one chooser, one prompt ledger and one threat model. The per-API differences that remain (SysEx, Bluetooth filters, NFC's tap) are the API's own semantics, not accidents.
- **The ticket split is the right shape.** The broker mints, the arbiter verifies, the arbiter cannot mint. Signed rather than MACed is correct because the issuer and verifier differ and the verifier holds the OS handles; one verification per open/escalation and none per transfer is the right cost.
- **The arbiter/session/enumerate split is honest Rule-of-Two work.** The process with the OS handle does not parse attacker bytes; the parser has no handle; the pre-grant enumerator has neither. G215's link-time exclusion and DV-1's symbol/syscall probe are the right enforcement.
- **Protected classes are refused before the prompt, not at `claimInterface()`.** HID input and FIDO collections, USB's eight classes and hubs, serial consoles, GATT HID/FIDO and the Device Information serial characteristic, and NFC's NDEF-only scope are the correct starting refusals.
- **Privacy is designed, not appended.** Per-origin handles, per-origin `id`s and NFC pseudonyms; a separate, off-by-default identifier exposure; defined list ordering; fixed chooser windows; constant availability; and an explicit residual statement. The spec does not pretend the API's model-level surface can be normalised.
- **Recording at the device-service boundary is the correct boundary.** It captures the parser's input, not just the API's output. NDEF payloads are never recorded by default; replay has no OS device path (G216) and a syscall assertion (DV-8); exact/approximate/not-claimed labels are printed in the export.
- **Agents and extensions get the right shape.** Agents get a typed intent, person-present approval, task-scoped non-persistent grants, no inheritance and a visible ledger; extensions get a Ring C refusal with a written amendment, not a silent hole.
- **The parser discipline is real.** Tier P, input and arena caps, no recursion, checked arithmetic, named fuzz targets, 14-day crash rule, 80% branch coverage, and the GATT codec built as the oracle and promotion path (DV-D12 flags its cost to the owner).
- **The licence and portability work is clean.** No libusb, libnfc or pcsc-lite; OS interfaces and standards data only; BlueZ over D-Bus and never linked; Windows MIDI Services treated as an OS service; `hg-crypto` Ed25519; portable Rust with a riscv64 Linux reference.
- **The honesty is unusual and should not be churned.** The flagged claims (MIDI's inferred WG-resolution limb, WPT coverage, the vendor BlueBorne estimate), Q-DV-16/Q-DV-17, the Bluetooth own-stack rejection cost, the GATT codec cost, the AT gap and the recording-credential risk are all stated rather than buried.

## Findings

| ID | Area | Finding | Severity | Why it matters | Recommendation |
|---|---|---|---|---|---|
| **C1** | Architecture / isolation | The session is one process per **(top-level site**, container, family), shared by the site's documents (6.0); 6.16 says "(site, container, family)". A top-level site with a cross-site iframe that holds a device grant puts both origins' device bytes in one session; a parser bug or a compromised session crosses the origin boundary. The claim that a compromised session "cannot reach another site" is false for cross-site frames. | **Critical** | Device bytes are page data. P1/I-1 and the spec's own compromise analysis require the boundary; DV-13's "0 cross-origin device events" tests an honest demultiplexer, not a compromised session. | Key sessions by frame site (or per origin for device families), or give each origin its own channel in a per-site process with broker-enforced routing. Unify the key wording. Add a compromised-session cross-site test and update the process count and footprint. |
| **C2** | Architecture / ticket | The ticket carries **family-level capability bits only**: read, write, configure, pair, reset, sysex, write-tag, identifier-exposure. It has no signed list of interfaces/endpoints, HID collections/report IDs, GATT services/characteristics or serial port. The session parses the descriptor and decides that scope; the arbiter "checks the claimed interface and endpoint against the session's capability set" (6.3), but the set does not name interfaces. A compromised session can claim a protected interface or a refused collection. | **Critical** | The protected-class and HID-input refusals become **session policy**, not a boundary, and the session is explicitly in the compromise model. The enumeration configuration already parses the descriptor pre-grant; its result is not signed into the ticket. | Add a signed `scope` to the ticket from the enumeration parse (interfaces/endpoints, collections/report IDs, services/characteristics, port id); enforce it in the arbiter's claim table; the session cannot widen it. Add a DV-13 case for a lying session. |
| **C3** | Security / WebUSB | The arbiter validates a control transfer's setup packet by **range-checking** `bmRequestType`, `bRequest`, `wValue`, `wIndex` and `wLength` (6.3). Range checks do not stop standard `SET_CONFIGURATION` or `SET_INTERFACE`, so a page can desync the claim after the protected-class check. This is exactly the recorded bypass class (crafted `wIndex`, raw `SET_CONFIGURATION` desync; note 7.5). | **Critical** | It defeats "refuse at grant time" and the arbiter's claim table; the risk table itself rates a class bypass Critical. `selectConfiguration()` requiring `reset` does not help if the raw control transfer is allowed. | Refuse standard requests that change configuration, interface or alternate setting outside the explicit operations; re-validate the active configuration/interface/endpoint map after any control transfer and reset; add conformance cases and a claim-table fuzz target. |
| **C4** | API / MIDI | The design makes the first `MIDIOutput.send()` a `device-write` escalation and says a denial "returns `NotAllowedError` to the call" (6.6, 6.10). `send()` is synchronous and returns `undefined`; it cannot await a prompt, and its timestamp is relative to navigation start, so a prompt-delayed message is late. The first note is dropped, sent before approval, or blocks the thread. | **Critical** | MIDI is a Stage 1 API and the flagship of the "lowest-risk transports first" plan; the escalation model is unimplementable and the prompt's firmware warning is wrong for a note. | Put MIDI output in the capability decided at `requestMIDIAccess()` (the prompt already lists "send data"), keep SysEx as the separate escalation, and define a queued-send/`statechange` outcome if a prompt remains. Never specify an error return `send()` cannot produce. |
| **C5** | Exposure / ST-D18 | The two "Meets" verdicts are not supported by the table's own facts. MIDI has "no CR resolution yet" and the WG-resolution limb is inferred (flagged claim 2, Q-DV-16); MIDI and Serial both count a Firefox implementation "behind an add-on" as shipping in two engines, while 5.11 says "only behind an add-on gate". The rule says "WG resolution" and "ships in two engines". | **High** | These verdicts carry Stage 1 general exposure for the only two APIs exposed to all sites. The admission rule is the corpus's gate; an overclaim bypasses it. | Define "ships" (default-on in a release) and "resolution" (a recorded WG decision), then move MIDI/Serial to the experimental setting or named owner exceptions (DV-E5/E6) until Q-DV-16 closes and a second engine is default-on. Record the interpretation as an owner decision. |
| **C6** | Accessibility | All three device classes are high-risk; AT-invoked approval is refused until AX-D11 person-present evidence (6.10, 6.18, 9.5.9). The chooser's keyboard operability does not restore approval for voice/switch AT users, and MIDI/Serial are exposed to all sites in Stage 1. The gap is honestly stated and owner-flagged, but "use a pointer or keyboard" is not equivalent access. | **High** | An API that a class of people cannot approve is not shippable to all sites. AX-D11 already defines an OS-attested assistive-state path that this spec does not adopt. | Adopt AX-D11's OS-attested path for a named low-consequence subset (read-only MIDI; no write, no persistent grant) or gate MIDI/Serial general exposure on AX-D11. Keep the stated gap in the ledger either way. |
| **C7** | Security / arbiter | The process table says the arbiter holds no page data (6.0), but it proxies every device byte through its rings. The compromised-arbiter analysis says it cannot mint or create a session; it does not say a compromised arbiter can **read and inject every session's device traffic across origins**. The broker's grant table is the outer boundary for new opens, not for the data plane. | **High** | It understates the highest-value service process and contradicts the session-isolation claim if the arbiter is compromised. | State the residual (all sessions' device traffic is readable and injectable by a compromised arbiter); if unacceptable, split the arbiter per container/site or add per-session keys/rings; add a target. |
| **C8** | Architecture / performance | There is **no throughput or latency target** for USB bulk, 1 kHz HID, serial at the 20 Mbaud cap, GATT notifications or the proxy ring; Q-DV-9 asks only about MIDI. One arbiter proxies every family, with no stalled-device or head-of-line test, and the notes' recording-cost probe (p95 event-to-page with and without recording, note 7.9) is not in 6.16. | **High** | The "OS stack, one arbiter, session without a handle" shape is only feasible if the proxy is fast enough; one stalled transfer must not delay every device. | Add per-family p50/p99 latency and throughput targets on DC-16/DC-8/DC-4, a stalled-device liveness test, a ring benchmark at 8 MiB/32 MiB, and the recording-overhead probe. |
| **C9** | Footprint | The six-family row is "Arbiter 8 + six sessions 18" (6.16), but the arbiter row is 8 + **1.5 per additional open device**. Six families means up to six devices, so the arbiter is 15.5 (16.5 DC-4) and the row is 33.5/37.5, not 26/30. The 8 MiB per transfer and 32 MiB in flight per device are not charged at all; six devices can hold 192 MiB of shared rings. | **High** | DV-11 gates "every row met" on a row that understates the worst case by 7.5 MiB and omits the largest device allocation. FP-1's headroom claim is wrong. | Recompute with the per-additional-device arbiter cost and the rings, cap total in-flight per profile, add a ring row, and re-check FP-1's headroom; or lower the caps. |
| **C10** | Staffing | 9.3's seven roles sum to **23–31†** but the total says **22–30†**. 22–30† full strength over 4–5 years is **88–150 engineer-years**, but the total says **70–110†**. The three numbers cannot all hold. The Stage 1 9–13†/8–12† and the 67.5–96.5†/606–798† totals inherit the error. | **High** | The staffing addendum is a C-6 ledger commitment. An arithmetic error in the owner-facing total is a credibility and planning defect, and the risk table already flags under-estimation. | Recompute the roles and the total. If 70–110 engineer-years is intended, state the ramp (the average is 14–27.5, below the 22–30 full-strength claim); otherwise raise the engineer-years. Fix the Stage 1 share and the C-6 addendum. |
| **C11** | Security / HID | 6.4 exposes "only collections whose **top-level** usage is not an OS input source" and refuses a report ID **shared** between allowed and refused collections. A vendor-defined top-level collection can contain a **nested** keyboard collection with a **unique** report ID: the top-level test passes and the shared-ID test does not fire. This is the nested-collection bypass in the record (note 7.5). | **High** | It restores the trusted-input path WebHID's blocklist is meant to close; the parser already builds the full collection tree. | Refuse any collection at **any depth** with a refused usage, and any report ID used by one. Add nested vendor/keyboard cases to the 200-case DV-4 suite and the fuzz corpus. |
| **C12** | Security / Bluetooth | The shipping path is the OS radio stack (CoreBluetooth, WinRT GATT, BlueZ, `BluetoothGatt`). BlueBorne, KNOB and BrakTooth are OS/firmware vulnerability classes the browser cannot mediate, and `hg-device-gatt` is **not** the shipping ATT parser. The design answers BLESA, protected services and bonds, but not the OS stack's own exploit class. | **High** | A malicious BLE device can compromise the OS below the arbiter. The fuzz hours on the codec do not protect the OS parser, and the security chapter reads as if they do. | State the OS radio stack as an external trust boundary with a minimum patched-OS requirement. Separate BlueBorne/BrakTooth (OS/controller) from KNOB (BR/EDR) and BLESA (bond). State that the shipping ATT parser is the OS's. |
| **C13** | Exposure / setting | The Experimental device APIs setting is a **global switch**: when on, any site that requests WebUSB/WebHID/Web Bluetooth gets the chooser (6.15). DV-D9 says the setting gathers evidence "without exposing single-engine APIs to all sites", and 6.15 says it is "not an admission". Both claims are false for a global setting. | **High** | It is the de facto exposure path for the three APIs that fail ST-D18. A global switch is an exposure decision with a warning, not a test-only gate. | Make the setting a per-origin test-site list (the developer adds origins), or record it as an owner-visible exposure decision with a warning and a review. Do not claim it limits exposure to all sites. |
| **C14** | Security / enumeration | The compromised-participant analysis covers renderer, session, arbiter and broker, not the **enumerate** configuration. That process parses attacker descriptors and returns the summary the chooser uses for the class triple, BOS bit and "protected device class" label; a compromised enumerator can mislabel a protected device. | **Medium** | "Refuse before the prompt" depends on the enumerator's summary. The session may later refuse, but the person is shown a device the design says cannot be offered. | Add the enumerate configuration to the threat model; treat its summary as untrusted for security labels; re-check protected classes in the broker/arbiter from OS metadata plus signed policy. |
| **C15** | Architecture / Android | Q-DV-17 admits Android USB permission and NFC reader mode may need a broker-owned Activity (`PendingIntent`, foreground dispatch); the spec still states the arbiter is the only OS caller (G210, 6.0). The answer changes the Android process layout. | **Medium** | The "arbiter-only OS caller" claim is unproven on the one mobile platform; NFC is Stage 3, but Android USB is on the Stage 2 path. | Resolve Q-DV-17 at DV-M0. If an Activity is required, define it as a broker-owned consent surface that passes an fd/`PendingIntent` to the arbiter and record the G210 exception in 9.5. |
| **C16** | Architecture / GATT | `hg-device-gatt` (ATT/L2CAP/GATT) is the **oracle's** protocol engine, not the shipping parser on any desktop: the OS stack performs ATT/L2CAP. The 4–5† parser team and 500† fuzz-hours protect the oracle and the promotion path, not the data path. DV-D12 is honest about the cost, but the security chapter counts it as if it were the shipping parser. | **Medium** | The "every parser ours and fuzzed" principle is satisfied on paper while the actual bytes are parsed by the OS; an OS ATT bug is an OS vulnerability. | State the distinction in the threat model and the parser section. Keep the codec if the owner accepts DV-D12's promotion rationale, but do not count its fuzz hours as protection for the shipping GATT path. |
| **C17** | Exposure / owner exceptions | 6.15 says an owner exception is "for a stated period" and G219 requires "an expiry", but the DV-E1–DV-E4 table gives only a decision point and "review at DV-M5"; **no period or expiry is stated**. The four candidates are not granted in 0.1, so the defect is latent. | **Medium** | An exception without an expiry can become permanent; the corpus's owner-decision discipline depends on a re-decision point. | Add an expiry (for example 12 months† from the grant) and a re-decision event to each DV-E row; record it in 9.4 when granted. |
| **C18** | Staging | Web Bluetooth is placed in three stages: 6.15 says "Stage 1 experimental setting only; **Stage 2 GATT**"; 9.1 Stage 1 includes the Bluetooth GATT **backends**; DV-M2 (24–36) exposes Bluetooth behind the setting; DV-M4 (48–60) has "Bluetooth GATT on macOS, Windows and Linux". The table and the staging section disagree on what "GATT" means. | **Medium** | The Stage 1/Stage 2 boundary and the 22–30† plan depend on which reading is true. | Use one phrase per thing (backend, experimental exposure, general exposure) and one stage per phrase across 6.15, 9.1, 9.2 and 9.4. |
| **C19** | API / USB isochronous | WebUSB exposes `isochronousTransferIn/Out`; 6.3 refuses isochronous with `NotSupportedError` and says "the API's transfer model and the OS backends do not give a bounded, recordable isochronous path on all four platforms". The API **does** expose it, and the desktop OS backends support it; the real constraint is Android and recording. The refusal is a deliberate capability gap, not a consequence of the API. | **Medium** | A site with a custom isochronous device fails on Izcal only; the compatibility cost should be an explicit decision, not a sentence in the family section. | Record the refusal as a decision with the compatibility cost and a reversal trigger (Q-DV-5). Say which OS backends can and cannot support it; test the `NotSupportedError` path. |
| **C20** | Security / Serial | The serial digest is the OS port id plus VID/PID "if the OS exposes them"; the grant "follows the port, not the cable" (6.2). For a generic adapter with no VID/PID, a different device plugged into the same granted port inherits the grant, and a remember grant can reconnect silently. | **Medium** | A malicious device on a trusted port is exactly the swap the per-device grant model is meant to stop. The spec acknowledges the port binding but not the security consequence. | At open, compare any OS-exposed identity (VID/PID, USB serial) with the grant; if the port identity cannot be verified, require a fresh `device-connection` prompt. Document the residual. |
| **C21** | Privacy / NFC | The per-origin UID pseudonym is a deliberate deviation from Web NFC's `serialNumber` semantics, and the spec documents it (6.8, 6.11). The true UID is available only through identifier exposure, which is "not persistent by default"; an inventory app that keys on the UID cannot persist across sessions. | **Medium** | The privacy default is right; the legitimate app path is incomplete, so the deviation breaks the use case it is trying to protect. | Define a persistent identifier-exposure grant (separate high-risk prompt, 90-day† expiry, visible, revocable) for sites that need the true UID; keep the default off. |
| **C22** | Privacy / MIDI | 6.6 keeps the API's all-ports model after one consent and calls it "the one API where the spec's model is ambient enumeration after consent". The prompt lists every port, but the choice is all-or-nothing and the page learns every port's name and manufacturer. This is a privacy exception, **not a recorded decision** in 9.4. | **Medium** | It conflicts with the no-ambient-enumeration rule and is a rig fingerprint. The spec's honesty is good, but the owner has not been asked to accept the cost. | Add a decision (for example DV-D13) recording the all-ports exception, the prompt wording, the rig-fingerprint residual and a reversal trigger (a Web MIDI per-port grant change). Consider a user-selectable per-port mode. |
| **C23** | Privacy / Bluetooth | 6.10 makes `getAvailability()` constant true so a page cannot learn whether a radio is present or powered; 6.7 says an off adapter produces `NotFoundError` with "Bluetooth is off". The `DOMException` message is page-visible, so the page can distinguish adapter-off from no-match. | **Medium** | It reopens the adapter-state fingerprint the constant return was meant to close; the same applies to serial "os-permission-denied" messages. | Return a uniform `NotFoundError` with a generic page-visible message; show the adapter/permission detail in the chooser and the browser log, not in the `DOMException` text. |
| **C24** | Security / residual | 6.19 rejects a per-device process because "none of the six" can DMA or map memory into the process, and refuses hubs **as a device**. A hub in the physical path (not the granted device) and a DMA-capable bus below the USB stack are outside the browser boundary; the spec does not state that residual. | **Medium** | Hub injection and DMA are part of the attack record the design claims to answer; an absolute "none of the six" invites over-reading. | State that a hub in the path and DMA/IOMMU behaviour are OS/hardware responsibilities. Keep the hub refusal as a policy, not a physical guarantee; reference the OS USB stack and IOMMU. |
| **C25** | Parser / NDEF | The NDEF limits cap message, records, type and payload, but **not nesting depth**. Web NFC's `toRecords()` can expose nested messages; a malicious tag can nest records, and the parser's "explicit stack with a depth cap" has no stated NDEF cap. | **Medium** | A depth or total-record amplification can exhaust the 1 MiB arena or the session's stack; the parser's no-recursion rule needs a number. | Add an NDEF nesting depth cap (for example 4†) and a total decoded-record cap. Add nested/chunked cases to `fuzz_ndef` and the corpus. |
| **C26** | Determinism / recording | 6.12 says a device recording is "part of the tab's recorded session (DT-D2)", but the device session is a **separate process**; the security scope's REC-R6 records per process and joins by IDs. The amendment does not define the device stream, the join ID or the replay group. | **Medium** | The fidelity and "device present at start" claims depend on which process owns which events; an undefined join is a replay divergence. | Define the device session's recording as a per-process stream joined by the tab's recording id, name the replay group, and state the ordering rule across the renderer and session streams. |
| **C27** | Security / extensions | Ring C refuses the device APIs to extension origins (9.5.8), but a content script that injects a **main-world** script into a page with a device grant can use the page's handle. The refusal is about extension origins, not page-origin scripts; the devices spec does not state this reliance. | **Medium** | The extension path is closed at the front door, but a main-world injection can borrow a site's grant. The boundary depends on the extensions spec's injection rules. | State the reliance on the extension platform's main-world injection rules and the page-origin trust model. If main-world injection is allowed, consider a broker check that the caller is the page's own script or a visible warning. |
| **C28** | Prompts / MIDI | The `device-write` class covers every USB and Serial open, the first HID/GATT write and MIDI `send()`, with one consequence line: "This can alter its settings or firmware and may not be reversible." A MIDI note does not alter firmware, and a USB LED does not; the same line for all writes is inaccurate. | **Medium** | Over-warning causes prompt fatigue and teaches people to ignore the one prompt that matters (SysEx, firmware, bootloaders). The spec's consent theory depends on accurate consequences. | Make the consequence capability-specific: data write, configuration write, firmware/SysEx write. Keep the high-risk class but vary the text and the confirmations; use the `sysex` capability for the firmware line. |
| **C29** | Staffing / Bluetooth | 6.7 says the chosen OS-stack Bluetooth backend is "6–8† engineers inside the device team, already counted in 9.3". 9.3's 6–8† role is "Device boundary and OS backends" for all six families and four OSes. If 6–8 is Bluetooth-only, the total is understated; if it is the whole role, the sentence is wrong. | **Medium** | The Bluetooth own-stack rejection cost is an owner-facing number (DV-D3); its chosen alternative must be costed consistently. | Split the 6–8† into the boundary/arbiter work and the per-family backends, state the Bluetooth share, and make the DV-D3 comparison use the same units. |
| **C30** | Portability / riscv64 | The 6.16 rows are not marked **[ISA]**, and 7.4 asserts Ed25519 verification and parsing are "microseconds on any target, including riscv64" without a measurement. The FP spec marks ISA-dependent budgets [ISA] and FP-24/FP-25 cover three ISAs. | **Medium** | riscv64 is a target from the start; an unmeasured claim in the ticket hot path and the parser arena is exactly the kind of threshold the FP spec says must be measured per ISA. | Mark the rows that depend on the ISA, measure Ed25519 verify, parser throughput and session memory on the riscv64 reference device at DV-M0/DV-M3, and cite the numbers. |
| **C31** | Ticket / lifetime | A session ticket expires after at most **24 h†** (6.0/6.1); a long-lived MIDI, serial or GATT session (a DAW, a console) outlives it, and no renewal or re-verification path is defined. The request flow says the ticket carries "the scope", but the ticket table has **no scope field**. | **Low** | The expiry is a security control; without a renewal rule the implementation either drops long sessions or silently extends the ticket, and the scope claim is unimplementable from the table. | Define ticket renewal (broker re-mint on a fresh decision, or a longer max with a re-verification interval) and add the scope field or remove the claim. |
| **C32** | API / USB serial | Without identifier exposure the USB `serialNumber` is `""` (6.11); WebUSB's `serialNumber` is nullable and `""` is a legal serial value. A page cannot distinguish "no serial" from "not granted", and an app that tests `null` mishandles the result. | **Low** | A small compatibility deviation with a large debugging cost; the API's own unavailable value is `null`. | Return `null` when the identifier grant is absent, reserve `""` for an actual empty serial string, and document the choice in the API notes. |
| **C33** | Determinism / CI | The virtual device is a library and CLI (6.13), and the spec says the virtual serial and MIDI devices run in CI, but it does not name the **harness** that drives the Web API (a test-build binding, a headless browser run, or a WPT-style server). The stable test-only bindings are never in a release, so a CI job needs the test build. | **Low** | The oracle is only useful if CI can run it against the shipping session and the API; an unnamed harness is an integration risk at DV-M1. | Name the CI harness and the test-build entry point (for example a WPT-style runner with `navigator.usb.test`) and add a smoke job to DV-M1's exit. |
| **C34** | Licence / corpus | 7.1 lists WPT device tests and fakes as BSD-3-Clause test-only and allowed; G217 says "no third-party corpus without an MIT-compatible licence". BSD-3-Clause is permissive but not MIT, and the licence audit's test-only class is not named. | **Low** | The MIT-only rule is a shipped-dependency rule; test-only data is a separate class, but the spec should say so to avoid a licence-audit surprise. | Classify WPT fakes as test-only under the licence audit's class 3, record the licence in `tools/device-corpus/LICENSES.md`, and state that no WPT file ships. |
| **C35** | Privacy / target | DV-6 measures pairwise linkability ≤ 1%† above chance but excludes the model-level attributes the API requires (VID/PID, names, GATT UUIDs). A rare device model can link two origins through those attributes while DV-6 passes; the target does not say how the residual is reported. | **Low** | The spec is honest that the residual exists, but the target can be read as a clean bill of health for a corpus that excludes the strongest linker. | State whether DV-6's corpus includes rare model-level combinations and report the model-level linkability separately. Keep the ≤ 1% target for the pseudonymised attributes only. |
| **C36** | Corpus / extensions | 9.5.8 adds `usb`, `hid`, `serial`, `bluetooth`, `bluetoothSocket`, `bluetoothLowEnergy`, `nfc` and `midi` to the extensions Ring C list. The Ring C table is a list of `chrome.*` namespaces; the documented Chrome Apps namespaces are the first six, while `nfc` and `midi` are web API names, not extension namespaces. | **Low** | The amendment mixes two surfaces. The intent (no device API to extension origins) is right, but the extensions spec's per-namespace table cannot enforce a web API name. | Add the documented `chrome.*` namespaces that exist and a separate rule refusing the six web APIs to extension pages, content scripts and workers; record both in 9.5.8. |

## The five findings that most change the design

1. **C1 — the session key is the isolation boundary.** One session per top-level site puts a cross-site iframe's device bytes beside the top site's. Keying sessions by frame site (or per origin for device families) changes the process count, the footprint rows and the compromised-session claim; the existing "0 cross-origin events" test does not see a compromised session. This is the first thing to settle because it changes the process map, not just a paragraph.
2. **C2 — the ticket must carry the parsed scope.** Without a signed interface/collection/service/port list, the arbiter's claim table is fed by the session, and the session is the process assumed compromisable. Adding the scope changes the enumeration output, the ticket format, the open request and the DV-13 target; it is the difference between a boundary and a policy the parser enforces for itself.
3. **C3 — control transfers need semantic filtering.** Range-checking a setup packet does not stop `SET_CONFIGURATION` or `SET_INTERFACE`; the claim table can be desynced after the protected-class check. This is the concrete WebUSB bypass in the record, and it is fixable in the arbiter without changing the process shape; it should be a release-blocking conformance suite.
4. **C4 — MIDI's permission model does not fit a synchronous `send()`.** The first-send escalation cannot await a prompt or return `NotAllowedError`. Moving output into the `requestMIDIAccess()` grant (with SysEx separate) changes the flagship Stage 1 API's prompt flow, the `device-write` class and the recording model; leaving it as written ships an API whose first note is lost or unapproved.
5. **C5 — the ST-D18 verdicts decide what ships.** MIDI's "Meets" rests on an inferred WG resolution; MIDI and Serial count add-on-gated engines as shipped. If the rule is applied as written, neither gets general exposure at Stage 1; the experimental setting or a named owner exception is the honest path. This changes the Stage 1 exposure plan and the owner decision DV-D9, not just the table.

## Blocking draft 0.2

**C1–C4 block 0.2 unconditionally.** Each invalidates a claim the draft relies on (site isolation, the arbiter boundary, the protected-class refusal, and the MIDI escalation), and each fix changes a design element rather than a sentence.

**C5 and C6 block the Stage 1 exposure plan unless the owner records a decision.** C5 can be closed by defining "ships" and "WG resolution" with evidence, or by moving MIDI/Serial to the experimental setting/owner exceptions. C6 can be closed by adopting AX-D11's OS-attested path for a named read-only subset, or by the owner explicitly accepting that voice/switch users cannot approve MIDI/Serial. The draft currently states the gap but does neither, so it should not claim Stage 1 general exposure as settled.

**C9 and C10 are must-fix numbers in the same pass.** They do not need a design change, but DV-11's footprint gate and the C-6 staffing addendum are wrong as written; 0.2 should not carry either arithmetic error into an owner-facing total. C7 and C12 should be stated as residuals in 0.2 even if the owner accepts them; C14, C18, C20, C23, C26 and C27 should be fixed in the same pass because each is a small change that removes a contradiction or an unstated trust boundary.
