# Izcal devices: security and permissions

Compiled 21 October 2026. This strand covers the security and permission record for web device access: the page-to-device threat model for WebUSB, WebHID, Web Serial, Web MIDI, Web Bluetooth and Web NFC; the device-to-host threat model; the published vulnerability record in browser code and in USB, HID, Bluetooth and NFC stacks; chooser and permission research; the renderer-compromise delta; fuzzing evidence; and the governance record (security reviews, high-risk classes, blocklists, enterprise policy). Primary sources were preferred: specifications, peer-reviewed papers, vendor security documentation and CVE records.

**M-1 note.** No third-party project's source code, headers, commits, diffs or code reviews were read or cited (M-1 part 3). Specifications were read as published prose at their canonical URLs. Chromium material is limited to published security documentation pages and public issue-tracker text; no code file was opened. Blocklist data files were not opened; only the specification text that defines and consumes them. The Peripheral Instinct paper and its published PDF were read in full.

Companion evidence: `research_notes/Izcal shell/security_robustness.md` (21 Oct 2026) for generic permission-prompt telemetry, reused below only where marked "prior note"; `fingerprinting_privacy.md` in this folder covers device fingerprinting in depth, so this note keeps only the permission-relevant identity facts.

**Confidence key.** **High** = primary source read and the claim checked in its text. **Medium** = primary abstract or snippet, or a vendor claim without data. **Low** = secondary source only. **Gap** = no published evidence found. **Inference** = my conclusion from the cited rows, not a published finding. **S** after a confidence means a single primary source with no independent replication found.

**Method notes.** (1) The WebUSB, WebHID, Web Serial and Web Bluetooth specifications have moved from `wicg.github.io` / `webbluetoothcg.github.io` to `usb|hid|serial|bluetooth.spec.whatwg.org`; Web NFC has moved to `w3c-cg.github.io/web-nfc/`; Web MIDI remains at `webaudio.github.io/web-midi-api/`. All were retrieved and read as text on 2026-10-21. (2) CVE counts come from NVD API 2.0 `keywordSearch` queries run on 2026-10-21. They count English descriptions that contain the keyword, not a curated taxonomy, and are noisy: the four "Web NFC" hits are NFC-named products with no Web NFC API, and "Web Serial" (175) is unusable. I inspected every record behind the WebUSB, WebHID, Web Bluetooth and Web NFC totals and classify them in section 3; the stack totals are scale indicators only. (3) The Peripheral Instinct paper was read from the author-hosted PDF; the CISPA site was unreachable from this network. (4) Three Chromium issue-tracker items could not be rendered (sign-in wall) and are cited from search-result text at Medium or Low; they are used only to show that bypasses are publicly reported, not for their details. (5) Gaps found: no public Chrome security-review document for these APIs; no dedicated MIDI-parser fuzzing study; no relay-attack treatment in the Web NFC specification; no device-specific prompt-fatigue measurement.

## 1. Threat model: what a malicious page can do with each API

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **WebHID turns a page into a trusted input device.** With one grant, a page reprogrammed onboard macros on most tested HID peripherals and then emitted trusted keystrokes, escaping the browser sandbox. | 22 devices from 15 vendors; 14 of 22 allow macro reprogramming over WebHID (Logitech, Microsoft and others); injection 5 ms on Linux (Keychron V1Z2, fastest known), ~35 ms on Windows, ~125 ms on macOS; reprogramming "well below 1 s" for all devices. | Trampert et al., "Peripheral Instinct: How External Devices Breach Browser Sandboxes", WWW '25, [paper](https://misc0110.net/files/peripheralinstinct_www25.pdf), [DOI](https://doi.org/10.1145/3696410.3714637) | 2025-04-28 | High · S |
| 1.2 | **A page can flash a radio receiver and attack a different machine in the room.** WebHID firmware flashing of a Logitech Unifying Receiver with pre-2019 firmware, then MouseJack keystroke injection into a laptop using an MX Anywhere 2S; the target user does nothing. | Only precondition is the WebHID grant on the attacker's host; "no user interaction by the ultimate target user". | Peripheral Instinct, §4.1 | 2025-04-28 | High · S |
| 1.3 | **WebUSB exposes raw control transfers, so firmware/DFU writes are ordinary API use.** The specification accepts that once a device is compromised the user agent cannot stop the host attack. | "once the device is under the control of an attacker ... there is nothing that can be done by the UA to prevent further damage"; recommends signed firmware and physical access for configuration. | [WebUSB §3.3](https://usb.spec.whatwg.org/#security-and-privacy-considerations) | living, accessed 2026-10-21 | High |
| 1.4 | **Serial access is a console into hardware.** The spec names the threats: a robot causing physical damage; installing firmware to attack the host, including triggering a buffer overflow in other host software; malicious code injected into a trusted firmware-update site; a malicious device colluding with a malicious site as a bidirectional channel. | "data sent from a page to the device is an opaque sequence of bytes"; "there is no mechanism that will completely prevent this type of attack". | [Web Serial §7](https://serial.spec.whatwg.org/#security-considerations) | living | High |
| 1.5 | **Web MIDI System Exclusive is the strongest MIDI capability and a firmware channel.** The spec describes a site rewriting a USB-MIDI device's firmware so it enumerates as HID and injects keystrokes; SysEx can also read or replace samples and patches and fingerprint the rig. | "This could allow a malicious website to read or inject keystrokes or other events on the host computer"; "this is the biggest concern"; SysEx needs a separate, stronger permission. | [Web MIDI §Privacy, §Additional Security Considerations](https://webaudio.github.io/web-midi-api/) | living | High |
| 1.6 | **The MIDI firmware chain was demonstrated, not merely theorised.** A Launchpad MK2 was forced into its bootloader with a SysEx message, custom ARM firmware was flashed, and the USB layer was patched to present as HID. | Full chain to arbitrary code execution on the device; the device then presents as a keyboard. | Peripheral Instinct, §4.1 | 2025-04-28 | High · S |
| 1.7 | **GATT writes reach device parsers that assume a trusted host.** The Web Bluetooth spec says unknown services must be treated as complete control, HID-over-GATT can log keystrokes (hence a blocklist), and characteristic values are still byte arrays of unexpected length and format. | "makes it plausible to conduct large-scale attacks" on device firmware; pairing is per device, never per class. | [Web Bluetooth §3.1–3.3](https://bluetooth.spec.whatwg.org/#privacy-considerations) | living | High |
| 1.8 | **The API deliberately withholds link keys and addresses, which blocks packet-in-packet injection — but only on encrypted links.** | "this only works over encrypted links, which not all BLE devices are required to support." | Web Bluetooth §3.3 | living | High |
| 1.9 | **Web NFC reads and writes physical tags, and NDEF is neither signed nor encrypted by the API.** A page can overwrite a tag or make it permanently read-only, bricking a deployment; a fixed tag can reveal the reader's location; a cloned or overlaid tag can inject wrong data. | Reading is disabled when multiple tags are present, which blocks the tag-overlay attack; the spec has no relay-attack section. | [Web NFC §Security and Privacy](https://w3c-cg.github.io/web-nfc/) | living | High |
| 1.10 | **WebUSB's fallback protection is optional device-vendor behaviour.** The authors considered a CORS-like per-device origin allowlist and an out-of-band registry, rejected both (vendor burden, no third-party developer access), and settled on the prompt plus Permissions Policy. | Two alternatives considered and rejected; "the permission prompt ... and the integration with §8.1 Permissions Policy provide adequate protection". | [WebUSB §3.2](https://usb.spec.whatwg.org/#attacking-a-device) | living | High |
| 1.11 | **The WebHID grant is broader than the click suggests.** Selecting one device grants access to all of its HID interfaces; the chooser should present a multi-interface device as one item. | Chooser requires two separate interactions; an indicator is shown while a device is in use. | [WebHID §3.1, §3.4, §6.2](https://hid.spec.whatwg.org/#security-and-privacy-considerations) | living | High |
| 1.12 | **MIDI has the weakest consent step of the four Chromium device APIs.** The paper found Web MIDI uses a single-click prompt while WebHID/WebUSB recommend two clicks; the spec says approval "is not currently required". | Single click vs two-click chooser. | Peripheral Instinct §2; Web MIDI §Privacy | 2025-04-28 | High |

**Implications:** A device grant is not a confidentiality permission. WebHID and Web MIDI are the shortest paths to trusted input; WebUSB and Web Serial can write firmware; Web NFC is a write channel to physical objects. Izcal must scope every grant to the interfaces, usages and operations it actually needs, and must treat HID keyboards, programmable macros, DFU interfaces and serial consoles as high-risk by construction.

## 2. Threat model: what a hostile device can do to the host, and the physical/remote boundary

| 2.3 | **BlueFrag: Android Bluetooth RCE with no user interaction.** | CVE-2020-0022, CVSS 8.8; out-of-bounds write in packet reassembly; Android 8.0, 8.1, 9 and 10; "User interaction is not needed". | [NVD CVE-2020-0022](https://nvd.nist.gov/vuln/detail/CVE-2020-0022) | 2020-02-13 | High |

| 2.5 | **BrakTooth: directed fuzzing of the Bluetooth Classic link manager found 16 vulnerabilities across 13 chipsets from 11 vendors.** | 20 CVEs; ~1,400 commercial products estimated; no pairing or authentication; radio range; ESP32 arbitrary code execution (CVE-2021-28139). | [SecurityWeek](https://www.securityweek.com/braktooth-new-bluetooth-vulnerabilities-could-affect-millions-devices/) | 2021-09 | Low (secondary) |
| 2.6 | **NFC relay is a live criminal technique.** GhostTap relays NFC between a victim's provisioned wallet and a mule's phone at a point-of-sale terminal; a relay server removes the geographic constraint. | Named by ThreatFabric on 2024-11-20; builds on NFCGate (TU Darmstadt, 2015); precursor NGate used for ATM cash-outs against three Czech banks (Nov 2023–Mar 2024). | ThreatFabric, ["Ghost Tap"](https://www.threatfabric.com/blogs/ghost-tap-new-cash-out-tactic-with-nfc-relay) | 2024-11-20 | Medium (vendor research) |
| 2.7 | **A malicious NFC tag can spoof or overlay a legitimate one.** Web NFC cites a Cyrillic-homoglyph URL swap and disables reads when multiple tags are in the field, because shielding a tag is difficult and visible. | Multiple-tag read disabled. | Web NFC §Security and Privacy | living | High |
| 2.8 | **The remote/physical boundary has collapsed.** A remote web attacker who obtains one grant can persist by modifying device firmware and attack later hosts; the paper's threat model is a website, not an attacker who plugs something in. | "without requiring any physical interaction"; persistence across hosts. | Peripheral Instinct, Abstract and §1 | 2025-04-28 | High · S |
| 2.9 | **Host software still trusts devices more than it should.** The Web Serial spec states that host software may be vulnerable because it improperly validates device input, and that security research has encouraged vendors to treat connected devices as untrustworthy. | — | Web Serial §7 | living | High |
| 2.10 | **A browser grant is persistent where the OS grant is session-scoped.** Android grants USB permission per device by dialog, and for the attach-intent flow it lasts only "until the device is disconnected". | Per-device permission; no global grant; discovery can be broad but communication stays user-mediated. | [Android USB host guide](https://developer.android.com/guide/topics/connectivity/usb/host) | accessed 2026-10-21 | High |

**Implications:** The hostile-device path is structural: USB and Bluetooth stacks parse attacker-controlled descriptors and PDUs, and were written assuming faulty hardware rather than malicious hardware. Izcal cannot fix device firmware, so it must assume a granted device is hostile, isolate the drivers that parse its data, and never let a device-originated event count as trusted user intent without a policy decision.

## 4. Prompt and permission research

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **User mediation is normatively uneven across the six APIs.** WebHID says a device is not made available until explicit user access and recommends two separate interactions; Web Serial requires `requestPort()` and transient activation; WebUSB says the UA "may" display a prompt; Web MIDI says approval is not currently required. | WebHID two-click chooser; Web MIDI single click; WebUSB permissive wording. | WebHID §3.4; Web Serial §3.1; WebUSB §3.1; Web MIDI §Privacy | living | High |
| 4.2 | **Grants persist, and after the first grant the device is silently reachable.** The paper states that once permitted, a site can interact with the device "without further consent on future visits"; WebHID fires connect events for previously allowed devices; Web Bluetooth `getDevices()` returns devices granted earlier. | Permissions persist until the user or site revokes them. | Peripheral Instinct §3.1; WebHID §6.2; Web Bluetooth §4.1 | 2025-04-28 | High |
| 4.3 | **Persistence is a deliberate trade-off, and the spec admits it worsens the compromised-site risk.** Web Bluetooth: retrieving granted devices after reload helps an attacker who compromises the site later, but fewer prompts make the remaining prompts more likely to be read. | "Instead of having to get the user to grant access while the site is compromised, the attacker can take advantage of previously-granted devices". | Web Bluetooth §3.2 | living | High |
| 4.4 | **Revocation is required by one spec and optional in another.** Web Bluetooth: the UA MUST let the user inspect which sites have access to which devices and revoke pairings. Web Serial: implementations "may" show an indicator and controls for revoking "at any time". | Mandatory (Bluetooth) vs optional (Serial). | Web Bluetooth §3.1; Web Serial §7 | living | High |
| 4.5 | **Cross-API permission unification is permitted but not required.** WebHID says the UA MAY track WebHID + WebUSB access under one low-level device permission, and `forget()` may revoke additional permissions. | One unified permission is allowed; no API requires it. | WebHID §7.3 (`forget()`) | living | High |
| 4.6 | **Users grant under social engineering, and generic permission telemetry shows prompts are mostly dismissed.** A browser-game study convinced up to 95% of users to grant web permissions; prior-note Chrome telemetry found notification prompts were 74% of all prompts and granted 10% of the time on desktop. | Up to 95% grant (generic web permissions, not device-specific); 74% / 10% (prior note). | Hazhirpasand et al., "Tricking Johnny into Granting Web Permissions", EASE 2020, via Peripheral Instinct §3.1; Bilogrevic et al., USENIX Sec '21, via prior note | 2020; 2021-08 | Medium (95% via paper; telemetry prior note) |
| 4.7 | **Enterprise policy exposes block, ask and silent pre-grant.** `DefaultWebUsbGuardSetting`: 2 = block, 3 = ask; unset defaults to ask and users may change it. `WebUsbAskForUrls` / `WebUsbBlockedForUrls` override per origin. `WebUsbAllowDevicesForUrls` **automatically grants** specific origins access to specific VID/PID devices and takes precedence over both ask and block. WebHID has the equivalent `WebHidAskForUrls` / `WebHidBlockedForUrls` / `DefaultWebHidGuardSetting`, and Edge documents `WebHidAllowDevicesWithHidUsagesForUrls`, which auto-grants by top-level HID usage. | Auto-grant by VID/PID or usage; allowlist wins over block; URL patterns cannot contain `*`. | [DefaultWebUsbGuardSetting](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/defaultwebusbguardsetting), [WebUsbAllowDevicesForUrls](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/webusballowdevicesforurls), [WebHidAskForUrls](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/webhidaskforurls), [WebHidAllowDevicesWithHidUsagesForUrls](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/webhidallowdeviceswithhidusagesforurls) | updated 2026-06-15 / 2026-09-28 | High |
| 4.8 | **Device identity is the permission key, and it is attacker-controllable.** WebUSB/Serial store VID, PID and serial number as stable identifiers; blocklists key on VID/PID/bcdDevice; a device that reports a different identity is a different permission subject. | WebUSB blocklist entries are VID:PID[:bcdDevice]. | WebUSB §7, §8.2; Web Serial §8 | living | High |
| 4.9 | **Enumeration itself leaks identity.** Web MIDI exposes each interface's device name, manufacturer and opaque identifier, and patch/sample data can uniquely identify a system; Web Bluetooth device IDs can reveal location and link the same device across sites; the spec suggests per-site device IDs. | "uniquely identifying a user by the specific MIDI interfaces"; Bluetooth IDs plus an ambient-device catalogue can locate a user. | Web MIDI §Privacy; Web Bluetooth §3.4.1 | living | High |
| 4.10 | **Incognito and permission lifetime need explicit handling.** Web Serial: normal-profile grants must not carry into private sessions and private-session grants must not persist; the serial number may identify the user across sessions. | — | Web Serial §8 | living | High |
| 4.11 | **A per-device OS grant is shorter-lived than a per-origin browser grant.** Android's USB dialog grants one device until disconnect; the browser grant is per origin + device and survives reconnects and restarts until revoked. | Android "until the device is disconnected". | Android USB host guide; Peripheral Instinct §3.1 | accessed 2026-10-21 | High |

**Implications:** Prompt design cannot carry the security load: users grant, grants persist, and administrators can pre-grant silently. Izcal should use a two-interaction chooser, a single unified low-level-device permission across all six APIs, an explicit and visible grant lifetime (per-session by default for high-risk classes), a persistent active-device indicator, one-click revocation, and a separate, audited enterprise pre-grant path. Do not copy the Web MIDI single-click or optional-prompt model.

| 5.8 | **The specifications already implement pieces of zero ambient authority.** WebUSB/Web Serial have no enumeration before a chooser; `claimInterface()` fails if another execution context owns the interface; the UA acts as a user-space driver. | Single-owner interface claim; requestPort grants one device at a time. | WebUSB §3.1; Web Serial §7 | living | High |
| 5.9 | **Broker-side handles and policy are the existing pattern.** Web Bluetooth never exposes addresses or link keys; blocklists and permission storage live in the UA, not the page; WebUSB/HID blocklists are fetched and enforced by the UA. | Permission store and blocklists are UA-side. | Web Bluetooth §3.3; WebUSB §7; WebHID §15 | living | High |
| 5.10 | **Least privilege is the applicable principle.** Every device capability should be scoped to the interfaces/usages and operations the origin needs, minted by the broker after consent, and revocable. | — | Saltzer & Schroeder, "The Protection of Information in Computer Systems", Proc. IEEE, [DOI](https://doi.org/10.1109/PROC.1975.9939) | 1975-01 | High (classic) |
| 5.11 | **The Rule of Two forbids the current placement: a high-privilege process parsing untrusted device bytes.** Code should satisfy no more than two of (unsafe language, untrusted input, high privilege); Chromium's browser process is the high-privilege broker, so descriptor parsing there must be memory-safe or moved to a sandbox. WebHID specifies a report-descriptor parsing algorithm that runs in the UA. | Three-condition rule; WebHID parses descriptors; WebUSB parses device/config/interface/BOS descriptors. | ChromiumOS, ["C++ security best practices — The Rule of Two"](https://new.chromium.org/chromium-os/developer-library/reference/security/cpp-security-best-practices/#the-rule-of-two); WebHID §6.2; WebUSB §4 | accessed 2026-10-21 | High |

**Implications:** Assume renderer compromise from the start. Device access must be a broker-minted capability scoped to an interface or usage, held outside the renderer, revocable, and auditable; the renderer must never enumerate, never hold a durable handle, and never parse descriptors. Put descriptor, report, GATT and NDEF parsing in a memory-safe or sandboxed component, and keep the permission store, blocklists and chooser in the broker.

## 6. Fuzzing: evidence, bug density and where parsers should run

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **Device emulation is the proven way to fuzz USB drivers, and it finds high-impact bugs quickly.** USBFuzz feeds random device data across the hardware/software barrier; drivers were written assuming faulty hardware, not malicious hardware. | 26 new bugs, 10 CVEs, 11 upstreamed from one campaign across Linux, FreeBSD, macOS and Windows. | Peng & Payer, USBFuzz, USENIX Security '20, [paper](https://www.usenix.org/system/files/sec20-peng_0.pdf) | 2020-08 | High |
| 6.2 | **Firmware emulation extends fuzzing to the Bluetooth chip.** Frankenstein revives chip firmware in emulation, feeds fuzzed frames and stays interoperable with a real host stack. | 3 zero-click RCEs (Broadcom/Cypress); 1 Bluetooth 5.2 key-extraction design flaw; kernel panics through Wi-Fi coexistence. | Ruge et al., USENIX Security '20, [page](https://www.usenix.org/conference/usenixsecurity20/presentation/ruge) | 2020-08 | Medium |
| 6.3 | **Directed fuzzing of the Bluetooth Classic link manager scales to a whole silicon ecosystem.** | 16 vulnerabilities, 13 chipsets, 11 vendors, 20 CVEs, ~1,400 products (BrakTooth); 11 vulnerabilities (SweynTooth). | SecurityWeek | 2021-09 | Low (secondary) |
| 6.4 | **NDEF fuzzing has a published method and a bug record.** | GNFCVulFinder (2021) builds NDEF test cases with manual, generation and mutation strategies; ANDEFVulFinder found 8 vulnerabilities in MIUI and six apps; host-side NDEF parser CVE-2015-8041. | GNFCVulFinder, [DOI](https://doi.org/10.1155/2021/9946022); NVD CVE-2015-8041 | 2021; 2015-11-09 | Medium |
| 6.5 | **MIDI has no dedicated parser-fuzzing study.** The exposed surface is SysEx state machines and bootloader entry sequences; the demonstrated attack is a firmware update, not a parser crash. | — | Peripheral Instinct; NVD | 2025-04-28 | Gap |
| 6.6 | **HID report descriptors are parsed in the user agent as well as the kernel.** WebHID defines the parsing algorithm and the item model; the same byte format has produced 24 "HID report descriptor" and 24 "HID parser" CVE records. | WebHID main/global/local items, report IDs, usages; NVD counts in row 3.5. | WebHID §6.2; NVD | living; 2026-10-21 | High |
| 6.7 | **Bug density is high enough to justify continuous fuzzing of every device parser.** One USB campaign produced 26 bugs across four kernels; one Bluetooth Classic campaign produced 16 vulnerabilities across 11 vendors; NDEF fuzzing produced 8 app-level bugs. | 26 / 4 kernels; 16 / 11 vendors; 8 / MIUI + 6 apps. | USBFuzz; BrakTooth; ANDEFVulFinder | 2020–2021 | High for USB; Medium for the rest |
| 6.8 | **The placement rule follows from the Rule of Two.** A parser that handles untrusted device bytes may not also run in an unsafe language at high privilege; it must be memory-safe or sandboxed, and its output should be validated in the broker. | No more than two of three conditions. | ChromiumOS, Rule of Two | accessed 2026-10-21 | High |
| 6.9 | **Least privilege bounds the blast radius of a parser bug.** Scope each parser to one interface, usage or protocol and give it no ambient device access. | — | Saltzer & Schroeder 1975 | 1975-01 | High (classic) |
| 6.10 | **The blocklist and policy parsers are themselves untrusted-input surfaces.** WebUSB and WebHID fetch blocklists over the network and parse them; WebUSB re-fetch interval is unspecified. | Blocklist fetched from a GitHub raw URL; HID blocklist parsed as JSON; Bluetooth registries parsed from text. | WebUSB §7; WebHID §15; Web Bluetooth §9 | living | Inference |

**Implications:** Build a fuzzing programme before shipping any device API: USB descriptors (device, configuration, interface, endpoint, BOS), HID report descriptors and report items, GATT/ATT PDUs and characteristic values, NDEF records, MIDI/SysEx streams, and the blocklist/policy parsers. Run parsers in a memory-safe or sandboxed process, seed with published corpora, and track bugs per parser as a release metric.

## 7. Governance: reviews, high-risk classes, blocklists and enterprise policy

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **WebUSB defines high-risk "protected interface classes" and denies them to ordinary origins.** Audio, HID, Mass Storage, Hub, Smart Card, Video, Audio/Video and Wireless Controller are protected; the spec says high-level APIs give better protection. Access requires the `usb-unrestricted` policy, which MUST only be enabled for Isolated Web Apps that declare it in their manifest. | 8 protected classes; `usb-unrestricted` effective default `none`. | WebUSB §6.4, §8.1 | living | High |
| 7.2 | **WebUSB runs a remote blocklist of individual devices.** Entries are VID:PID[:bcdDevice]; the UA fetches the list from a GitHub raw URL and "should re-fetch ... periodically", with the interval unspecified. | Blocklist URL in the spec; no signing or versioning requirement stated. | WebUSB §7 | living | High |
| 7.3 | **WebHID blocks by device identity and by top-level HID usage, including keyboard-like collections.** Blocklist rules can match vendor, product, report ID, report type, usage page and usage; the chooser then hides matched devices or reports. | Rule fields: vendor, product, reportId, reportType, usagePage, usage. | WebHID §3.1, §15 | living | High |
| 7.4 | **Web Bluetooth blocks vulnerable GATT services, characteristics and descriptors, with HID-over-GATT keylogging as the named example.** | GATT blocklist from the WebBluetoothCG registries. | Web Bluetooth §3.3, §9 | living | High |
| 7.5 | **The blocklist/protected-class checks have been bypassed repeatedly in public reports.** WebUSB protected-class protection bypassed via crafted `wIndex` (tied to CVE-2026-5276 and the original CVE-2018-6125 protection); a raw `SET_CONFIGURATION` desync bypass; WebHID blocklist bypass via nested HID collections. | Three public Chromium issues: [520743499](https://issues.chromium.org/issues/520743499), [511732828](https://issues.chromium.org/issues/511732828), [522791354](https://issues.chromium.org/issues/522791354). | Chromium issue tracker (titles and summaries via search; pages did not render) | accessed 2026-10-21 | Medium |
| 7.6 | **No public Chrome security-review document for these APIs was found.** The public record is the specifications' security considerations, the blocklists and the issue tracker. The Chromium team's response to Peripheral Instinct was to improve the clarity of permission prompts; Logitech planned to move configuration to a separate usage. | No review doc located; two vendor responses. | Peripheral Instinct §1 (Responsible Disclosure); search for review documents | 2025-04-28 | Gap for the review; Medium for responses |
| 7.7 | **Enterprise and education deployment is policy-driven.** Administrators can block, ask, or silently pre-grant specific devices or HID usages; ChromeOS kiosk documents an "Allowed WebUSB Devices" setting; WebHID and Web Serial name classroom and hobbyist deployment as motivating use cases. | Allowlist matches on origin only, paths ignored; invalid entries void the policy. | Edge policy docs; WebHID §2.2; Web Serial §7; ChromeOS kiosk documentation | accessed 2026-10-21 | High for policies; Medium for kiosk |
| 7.8 | **The governance tension is explicit: the most exploitable devices are the intended users.** Web Serial says microcontroller boards "do not implement firmware signature verification", are "clearly exploitable", and "should not be blocked" because education and hobbyist use is a key case. Web MIDI rejected device allow/block lists because they "would significantly reduce the usability". | Two specs state the trade-off in their own text. | Web Serial §7; Web MIDI §Privacy | living | High |
| 7.9 | **Permissions are per API, not per device across the platform.** WebHID MAY unify WebHID + WebUSB permissions, but no spec requires a single device principal; enterprise policies are likewise per API (`WebUsb*`, `WebHid*`, `WebSerial*`, `WebBluetooth*`, `WebNfc*`). | Optional unification only. | WebHID §7.3; Edge policy docs | living; 2026-09-28 | High |
| 7.10 | **Web MIDI's governance is the weakest of the set.** It has no mandatory prompt, a single-click prompt in practice, and no blocklist in the specification (the paper notes every other API has one). | Single click; no blocklist. | Web MIDI §Privacy; Peripheral Instinct §2 | living; 2025-04-28 | High |

**Implications:** Copy the protected-class idea, not its implementation: deny high-risk classes (HID keyboards, mass storage, smart cards, hubs, wireless controllers) to ordinary origins and make them reachable only through a stronger app principal. Do not rely on VID/PID/usage blocklists as the primary control, because they are bypassable and identity is attacker-controlled; enforce at the interface and operation level. Ship policy and blocklists as signed, versioned data rather than fetching a mutable URL. Offer enterprise pre-grant only as an explicit, auditable policy with a visible indicator, and unify the device permission across all six APIs.
