# Izcal WebCrypto: fact-check (phase 8)

Checked 20 October 2026 against `reports/Izcal WebCrypto.md` (draft 0.1) by a checker who did not write the spec or its notes. Scope: the claims that carry a decision (WC-D1 to WC-D10), a target (WC-1 to WC-15) or the history; the W3C WebCrypto facts, the governing NIST/RFC documents, the dated history events, the usage numbers, whether each cited note row exists and supports the spec's wording, internal cross-references, cross-references to the other specs' IDs, and every link.

Primary sources were read directly: the [W3C Web Cryptography Level 2 FPWD](https://www.w3.org/TR/WebCryptoAPI/) and the [editor's draft](https://w3c.github.io/webcrypto/) (IDL, §10, §13.5, §14.2, §14.4, §18–34), the [2017 REC](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/) (§5.2, §13.4–13.5), the [2012 FPWD](https://www.w3.org/TR/2012/WD-WebCryptoAPI-20120913/), the [WebAuthn Level 1 REC](https://www.w3.org/TR/2019/REC-webauthn-1-20190304/), NIST's landing pages for [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final), [SP 800-227](https://csrc.nist.gov/pubs/sp/800/227/final) and [SP 800-57 Part 1 Rev. 5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) plus PDF existence checks for the rest of the governing set, [RFC 10024's datatracker page](https://datatracker.ietf.org/doc/html/rfc10024) and existence checks (200) for RFC 2104, 4122, 5280, 5208, 5958, 5869, 6979, 7515, 7517, 7518, 7748, 8017, 8018, 8032, 8439, 9180, npm's downloads API for the three packages (fetched live for the spec's exact week), the [Web Almanac 2025 security chapter](https://almanac.httparchive.org/en/2025/security), the [Chrome DevTools overview](https://developer.chrome.com/docs/devtools/overview), the [PuTTY P-521 advisory](https://www.chiark.greenend.org.uk/~sgtatham/putty/wishlist/vuln-p521-bias.html), [NIST's 21 April 2014 Dual_EC announcement](https://www.nist.gov/news-events/news/2014/04/nist-removes-cryptography-algorithm-random-number-generator-recommendations), the [ImperialViolet BoringSSL post](https://www.imperialviolet.org/2014/06/20/boringssl.html) and the [getrandom(2) man page](https://man7.org/linux/man-pages/man2/getrandom.2.html), plus one corroborating web search for the secure-curves merge date and the engine versions. All other spec-to-report IDs were read in the local reports and ledger. No web searches were spent on anything a local primary source answered. No personal data was sent in any request.

Verdicts: **Correct**; **Partly** (the substance holds but a number, scope, date or wording is off, or the spec overstates its note); **Wrong**; **Unverifiable** (the cited source does not contain the claim and no other source was found); **Not checked** (left to the note's own grading, usually High, for lack of priority). "Must-fix" marks a finding that a decision or target depends on, or a plain factual error in a load-bearing sentence. Every other fix is recommended.

## Must-fix

- **FC-M1 (Section 4.2, last sentence of the first paragraph).** "…`crypto.getRandomValues` (≤ 65 536 bytes per call) and `crypto.randomUUID` outside the secure-context gate" is **wrong about `randomUUID`**. The pinned spec's Crypto interface is: `[SecureContext] readonly attribute SubtleCrypto subtle; ArrayBufferView getRandomValues(ArrayBufferView array); [SecureContext] DOMString randomUUID();` — `randomUUID` is `[SecureContext]`-gated in the editor's draft, and both notes say so ([ER 4.4] "secure-context-only per MDN"; [HP 1.8] `getRandomValues` "remains the only `Crypto` member callable from an insecure context"). The sentence contradicts its own citation ([SA 1.1–1.5], whose rows do not make the claim) and a compat-surface statement is exactly the class P2 says must be exact. WC-D5, G161 and §6.4 do not repeat the claim, so the fix is local.
  - Replace with: "`[SecureContext]` exposure, and `crypto.getRandomValues` (≤ 65 536 bytes per call) — the one `Crypto` member callable outside a secure context; `crypto.randomUUID` is `[SecureContext]`-gated like `subtle`."
- **FC-M2 (Section 6.5, "Structured clone and workers").** "…only *export to script* is forbidden, so the wire record must carry the bytes ([SA 1.4][SA], [SA §4][SA])" — the **"so" claims the W3C spec forces bytes onto the wire, and it does not**. What the spec supports: cloning a non-extractable key is legal and IndexedDB persistence is the intended pattern (REC §5.2: "by allowing the `CryptoKey` to be used with the structured clone algorithm, any existing or future web storage mechanisms … can be used to store `CryptoKey` objects … without ever exposing that key material to … the JavaScript environment"), and export is `InvalidAccessError` (verified). But the REC's clone algorithm carries a **handle**, not bytes: "Let the `[[handle]]` internal slot of output refer to the same cryptographic key data represented by the `[[handle]]` internal slot of input." Carrying the bytes in `hg-clone-wire` records is Izcal's design choice for cross-process clones (there is no shared-handle channel in Izcal's model) — a sound choice, but a decision of this spec's, not a consequence of the W3C text. WC-D6 and the DM-D12 amendment build on this sentence.
  - Replace the clause with: "…only *export to script* is forbidden; the W3C clone itself carries a handle, not bytes (REC §13.4), so carrying the bytes in the wire record is this spec's decision — forced by the cross-process boundary and by the bytes' home outside the JS cage, and it is why the record inherits the sensitive-class handling (G162)."
- **FC-M3 (Summary paragraph; Section 9.3 total row).** "The work is **3–5† engineers**" / "Total | **3–5†**" does not follow from the track table: 2–3† (web-crypto surface) + 1–2† (`hg-crypto` additions, shared) + 0.5† (security response) = **3.5–5.5†**. G-18's whole complaint is that the work was "counted nowhere"; the answer must recompute. Either state "3.5–5.5†" or state the rounding convention ("3–5†, rounded to whole engineers, minimum including the 0.5† share"). The same total appears in the header summary paragraph.

## Recommended

- **FC-R1 (Section 3 first paragraph; 4.2; WC-2).** "The registry's sixteen algorithms" / "a closed algorithm registry of sixteen entries": sixteen is the **Level 1 REC** registry. The pinned snapshot candidate — the Level 2 editor's draft the spec pins — **registers eighteen** (the Algorithms chapter has RSASSA-PKCS1-v1_5, RSA-PSS, RSA-OAEP, ECDSA, ECDH, Ed25519, X25519, AES-CTR, AES-CBC, AES-GCM, AES-KW, HMAC, SHA, HKDF, PBKDF2; verified this pass). Since WC-2 and G168 measure "100% of registered (algorithm, operation) pairs" against the pinned snapshot, say how it counts: "the Level 1 registry's sixteen entries plus the merged secure curves (Ed25519, X25519) — eighteen in the pinned editor's draft". The spec's "sixteen plus the secure curves" phrasing in §3 and §1 is already consistent; §4.2's flat "sixteen entries" is the one to fix.
- **FC-R2 (Section 11.2, second bullet).** The main-thread folklore bullet cites "([SA][SA] background)", but [SA] contains no such background text — no row in `standards_algorithms.md` mentions threading or the main thread. Re-cite [GO 4.4] (the row that shows the spec fixes no thread and that any "ran on the worker" claim is a guess) or drop the citation. The flag itself is right and the spec's reliance statement ("this spec never relies on it") is correct.
- **FC-R3 (Section 6.9, first paragraph).** "The web's own threat model for `getRandomValues` is 'unguessable bytes', not identity ([SA 1.5][SA])": the quoted phrase appears nowhere in the W3C text (checked), and [SA 1.5] is the `[SecureContext]` row, not a threat-model row. The supporting rows are [ER 3.6] and [GO 2.2] ("no lower-bound on the information theoretic entropy"; the CSPRNG-seeding note). Reword without the quote marks and cite those.
- **FC-R4 (Section 3, "The permission answer already exists"; 6.9).** "the fingerprinting literature studies canvas, WebGL and fonts and never RNG output" states an absence-of-evidence result ([GO 3.4]) that the note grades **Low** "on purpose". WC-D7 does not depend on it (the decision rests on origin-scoped keys and P2, and the reversal trigger covers new evidence), but the claim should be hedged or added to 11.2: "no published study we found examines RNG output as a fingerprint feature ([GO 3.4], Low)".
- **FC-R5 (Section 3, "The implementations", last sentence).** "Cloudflare's Workers runtime added ML-KEM/ML-DSA to its Web Crypto layer in October 2026, ahead of every browser ([GO 6.1–6.4][GO])" states [GO 6.4], which is graded **Medium** (from a search summary), as fact. Add it to 11.2 (single-source, unverified against Cloudflare's own post) or fetch the post before draft 0.2.
- **FC-R6 (Section 6.4, platform table, macOS row).** "`CCRandomGenerateBytes` (the XNU CCRNG)": [ER 1.9] says the DRBG behind `CCRandomGenerateBytes` "is not documented in Apple prose", construction source-ascertainable †. Drop the parenthetical or mark it † — the interface name alone carries the design.
- **FC-R7 (Section 6.4, riscv64 bullet; WC-D4).** "the RISC-V `Zkr` entropy CSR is ratified but its kernel use is immature ([ER 2.5][ER])" states a Medium/Low row as fact. The decision (use the OS interface, not Zkr) is safe either way; add the maturity claim to 11.2 or mark it the note's assessment.
- **FC-R8 (Section 3, "What is used").** "`digest` on about 2.7–3.0%" — the note verified the exact figures (2.65% desktop / 2.98% mobile, [GO 5.1–5.2], re-verified against the Almanac this pass). Write "2.65% / 2.98%".
- **FC-R9 (Section 1, last bullet).** "the network tier-P set (NET-R5) names `hg-crypto` and its pins as advisory scope (SEC-25)" compresses two different lists: per ledger A-SEC-17, **NET-R5 lists `hg-tls` and `hg-crypto`** (the tier-P set); per A-SEC-19, **SEC-25's advisory scope covers `hg-crypto`'s pins and Izcal's own crypto**. Split the sentence.
- **FC-R10 (Section 6.3, 6.1 table, WC-D2; Section 9.5).** AES-CTR is marked "**New in `hg-crypto`**: pin + binding", but ledger **A-NW-5** (media, pending) already routes "AES-CTR and `cbcs`" into `hg-crypto` — the media spec may land the pin first. Acknowledge it in 6.3 or 9.5 so the two amendments do not double-count the same pin.
- **FC-R11 (Section 6.2, first sentence).** "the same generator discipline the DOM spec applies to WebIDL (DM-D2's inputs)": DM-D2 is the Web IDL front-end decision (Izcal writes `hg-webidl`); the generator-from-pinned-inputs discipline is **DM-D21** (pinned IDL inputs) with **G96** (generated items carry anchors; hand edits fail CI). Cite DM-D21/G96.
- **FC-R12 (Section 6.9, warning floors; Section 3).** Precision on error types: §3's "five error types, no reason field" is right **for `SubtleCrypto`** ([GO 1.3] says "for subtle"), but the W3C surface also defines `TypeMismatchError` (getRandomValues' non-integer-array throw) and `QuotaExceededError` (the 65 536 cap) on the `Crypto` interface. WC-D5 and G161 are unaffected; one clause ("five on `subtle`, plus the two `Crypto`-interface errors") closes the gap a reviewer would find first.
- **FC-R13 (Section 6.7, last bullet; Section 6.4).** "(the orders HTML permits)" and the sandbox phrase are Izcal phrasing with no citation; harmless, but if kept, anchor "orders" to the recording spec's ordering rule when one exists.
- **FC-R14 (Notes, not the spec).** (a) [SA 1.1] says "six operations" while listing twelve — the spec's "twelve" is right; fix the note. (b) [SA 1.10] cites w3c/webcrypto **#300** for the PQ discussion while [GO 6.1] cites **#367** ("Support for PQC algorithms: ML-KEM, ML-DSA and SLH-DSA", opened 2024-08-21) as "the umbrella ask"; reconcile — #367 is the PQ tracking issue the spec means. (c) [HP 1.6] says Firefox **130** (2024-09) for secure curves while [SA 1.7] says Ed25519 in Firefox **129**; the corroboration found this pass supports **129** (Ed25519 in Chrome 137, Firefox 129, Safari; X25519/X448 remainder), so fix HP 1.6 and raise [SA 1.7]'s grade to High. (d) [HP 4.9] says HACL* Curve25519 shipped in Firefox **57** while [SR 2.8] says NSS 3.39 / Firefox **62**; reconcile against the Mozilla blog before either is quoted again. (e) [SA 2.5]'s FIPS 197 link (`NIST.FIPS.197-upd1-2023.pdf`) returns 404; the document is at `NIST.FIPS.197-upd1.pdf` (200, verified). (f) [SA 2.10]'s SP 800-57 link (`/pubs/sp/800/57/part1/r5/final`) returns NIST's "Page Not Found"; the live page is `/pubs/sp/800/57/**pt1**/r5/final` (200, title "SP 800-57 Part 1 Rev. 5"). (g) [SA 1.6]'s merge citation points at `ipfs/in-web-browsers#204` — it resolves and its text matches the claim, but the Igalia survey (the row's other source) or a w3c/webcrypto link is the better home for a merge-date claim.
