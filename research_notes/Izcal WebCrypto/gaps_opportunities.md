# Izcal WebCrypto: gaps and opportunities

Compiled 2026-10-20. Primary sources were preferred (the W3C Web Cryptography API specification text, vendor documentation pages, issue-tracker discussion text, the Web Almanac chapter and npm's download API); the shared web-search budget was spent on observability, determinism, opportunity and post-quantum questions.
Confidence: **High** = primary source read this session and the claim checked in its text; **Medium** = primary snippet or issue title/date from a search summary, or a vendor claim without data; **Low** = secondary source only, or evidence known to be thin.

**Scope.** This strand covers phase 3 of the first-principles-spec method for WebCrypto: what current browsers' developer tools cannot see or do around the Web Cryptography API, where recording and replay of randomness has precedent and where it has none, why the API has no permission surface, which gaps an Izcal-first crypto design could take, what the API is actually used for, and where post-quantum algorithms stand in web APIs. It is research only (M-1): ideas and evidence, never code or templates.

**Relation to earlier notes.** The networking strand established the pattern this note reuses for crypto: [the platform's failures are reasonless *by specification* for the page, while the engine that owns the decision could tell the user's tools the exact reason](../Izcal%20networking/gaps_opportunities.md) (**[Net 1.1–1.2]**), and replay tools reach into the page because they cannot reach into the engine (WprGo overriding `Date`, **[Net 3.6]**). New here: the crypto API's own error taxonomy, the absence of any crypto view in every browser's DevTools, recorded randomness, the permission question, and the post-quantum track.

**Izcal constraints that apply.** HGBA-3 **B1** (deterministic substrate: recorded inputs, seeded scheduler, virtual clock — entropy is a recorded input in this model), **B2** (typed IPC with a simulation transport), **B9/B10** (agent principal, AI off by default), **ANC-1** (spec anchors joining engine behavior to specification steps), D-S11 (DevTools as an HTML app Izcal renders). The MIT-only dependency rule governs any crypto primitive library, which is what makes a from-FIPS-203-prose implementation of an ML-KEM spike the natural Izcal route.

**Method note.** 14 shared web searches were used; they went to the four priority areas (1, 2, 4, 6). Everything else came from direct reads: the [W3C Web Crypto API specification](https://www.w3.org/TR/WebCryptoAPI/) text, [Chrome's DevTools documentation](https://developer.chrome.com/docs/devtools/overview), [rr's documentation](https://rr-project.org/), the [@sinonjs/fake-timers documentation](https://github.com/sinonjs/fake-timers), the [WebDriver BiDi editor's draft](https://w3c.github.io/webdriver-bidi/), the [Web Almanac 2025 security chapter](https://almanac.httparchive.org/en/2025/security), [npm's download API](https://api.npmjs.org/downloads/point/last-week/crypto-js), and the Chromium blog. Rows built from search summaries only are graded Medium; the Stack Overflow tag volume and the fingerprinting surface are graded Low and the thinness is stated.

**Implications:** the API is opaque to the page *and* invisible to the developer — a double gap. Every crypto operation already crosses a process boundary in Izcal (B2), so a **crypto event stream** is a natural IPC output, not an add-on: algorithm as normalized, key handle and metadata (never material), outcome, and an internal typed reason at spec-step granularity. The WebAuthn panel (1.2) is the existence proof that browsers will surface credential-like state when the use case is theirs; Izcal can generalize it. And where the spec's five error types are a security compromise for the *page*, nothing obliges the engine to be equally mute to the *user's own tools* — the same page-blind/tool-sighted split the networking strand found for fetch failures ([Net 1.1–1.2]).

## 2. Recording and determinism of randomness

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Recording kernel randomness is established practice one layer down.** rr "records a group of Linux user-space processes and captures all inputs to those processes from the kernel, plus any nondeterministic CPU effects"; replay preserves "instruction-level control flow and memory and register contents" exactly, at ≤1.2× overhead on Firefox test suites. Randomness enters as a recorded input, which is why replay reproduces it | ≤1.2× overhead | [rr documentation](https://rr-project.org/) | read 2026-10-20 | High |
| 2.2 | The web API sits exactly at rr's recorded-input boundary but nothing on the web records it. The spec tells implementations to use a CSPRNG seeded from OS entropy (naming `/dev/urandom`), states there is "no lower-bound on the information theoretic entropy" of returned values, and puts `getRandomValues` outside WebCrypto's algorithm registry entirely — it is unregistered, unscoped and unlogged | 0 registry entries | [Web Crypto API spec, §10](https://www.w3.org/TR/WebCryptoAPI/) | read 2026-10-20 | High |
| 2.3 | **Under a recorded-input model, replay reproduces the same randoms — and that changes the meaning of page state.** Anything the page derived from `getRandomValues` (nonces, session tokens, idempotency keys, generated IDs) is identical on every replay; the spec itself warns "Do not generate keys using the getRandomValues method", so key generation is *not* in this class, but everything derived from raw randoms is. Two runs can no longer differ by chance, which is exactly what a reproducibility tool wants and exactly what a uniqueness-dependent page assumes will not happen | 1 policy decision | spec §10.1.1 note; this note's synthesis | read 2026-10-20 | High (spec) / Medium (consequence reading) |
| 2.4 | The opposite policy — fresh randomness on replay — buys realism and destroys reproducibility: any branch on a random value diverges the replay from the recording, and the divergence compounds. External replay tools already feel this from the *outside*: WprGo injects a script overriding `Date` to make replays behave, because it cannot reach the engine's randomness or clock ([Net 3.6]). The choice between recorded and fresh entropy is therefore a first-order design decision, not a detail | 1 injection script | [Net 3.6](../Izcal%20networking/gaps_opportunities.md) | n/d | Medium |
| 2.5 | **The test-tooling world has a hole exactly where crypto is.** fake-timers — the library under Sinon's and Vitest's fake clocks — fakes timers, `Date`, `performance.now`, `queueMicrotask`, `Intl` and `Temporal`, and documents no faking of `crypto.getRandomValues` or any randomness at all. The one mainstream impurity test frameworks do not control is randomness | 0 of 1 APIs faked | [@sinonjs/fake-timers documentation](https://github.com/sinonjs/fake-timers) | read 2026-10-20 | High |
| 2.6 | **The standard automation protocol has no random-source or crypto surface either.** WebDriver BiDi's emulation module covers geolocation, locale, media features, network conditions, timezone and user agent — and its ten modules (session, browser, browsingContext, emulation, network, script, storage, log, input, webExtension) contain nothing about cryptography or entropy. An automated test that wants deterministic randoms today must patch `crypto` from an init script and hope it races nothing | 10 modules, 0 crypto | [WebDriver BiDi ED](https://w3c.github.io/webdriver-bidi/) | ED 2026-10-08 | High |

**Implications:** randomness is a *recorded input*, and Izcal's substrate already treats it that way — the web platform's own RNG plumbing (OS CSPRNG → engine → page) is precisely rr's "inputs from the kernel" boundary (2.1), so recording entropy draws per call is architecturally natural. The design decision Izcal must own (2.3–2.4): per-container, labelled policy — **recorded randoms by default in simulation mode** (replay is exact; the tool reports "this value came from the recording") and **seeded fresh randoms as an explicit fault-injection mode** (test uniqueness assumptions on demand). That dual mode fills the fake-timers hole (2.5) at the engine level, where no monkey-patch race can exist, and gives BiDi-class clients (2.6) the knob no standard has. Because `getRandomValues` is called ~35–41% per page load (1.9), it is also the highest-volume event in the whole crypto log — budget it accordingly.

## 3. Permission, policy and fingerprinting surface

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **There is no permission gate, by design.** The entire access model is two structural properties: `crypto.subtle` is `[[SecureContext]]`-gated (WebIDL), and keys are scoped to the execution environment — the spec directs implementers to ensure `CryptoKey` objects are not shared between origins unless the author explicitly shares them. The only user-consent language in the spec is for **DoS mitigation**: implementations "may consider requiring user consent for operations that may be known to be disruptive" and limiting device limits on key sizes and iteration counts — consent as a load-shedding tool, not an access gate | 0 permission gates, 1 DoS clause | [Web Crypto API spec, §6.1–6.2, §10](https://www.w3.org/TR/WebCryptoAPI/) | read 2026-10-20 | High |
| 3.2 | Sharing a key out is irrevocable: once a `CryptoKey` has been explicitly shared (e.g. via `postMessage`), "the source origin can not later restrict or revoke access to the key". The spec also sets no normative storage requirement and permits implementations not to zeroize key memory — the platform's stance is that key *material* never leaves the API, and that is the whole security story | 1 revocation clause | [spec §6.1–6.2](https://www.w3.org/TR/WebCryptoAPI/) | read 2026-10-20 | High |
| 3.3 | **No enterprise policy gates WebCrypto.** No policy disabling `crypto.subtle` or `getRandomValues` surfaced in Chrome's enterprise documentation or anywhere else; the policy surface that does exist around crypto is transport-level — Chrome offered a temporary enterprise opt-out for post-quantum TLS when the Kyber rollout broke middleboxes. Searches for a WebCrypto policy returned nothing (the full policy list page could not be fetched this session, so this is an absence-of-evidence claim) | 0 policies found | [Chromium blog, 2024-05-23](https://blog.google/chromium/advancing-our-amazing-bet-on-asymmetric/); policy search | 2024; 2026-10 | Medium |
| 3.4 | **Fingerprinting: the evidence for `getRandomValues` as a signal is thin to absent.** The fingerprinting literature surfaced this session (surveys of browser fingerprint research, cross-browser OS/hardware-level studies, real-page risk assessments) studies canvas, WebGL, fonts, audio and TLS fingerprints; none of the results examined RNG output as a fingerprint feature, which matches expectations — uniform random output carries no device signal, and the API's presence is near-universal. The realistic fingerprinting angle for a *deterministic* browser is the opposite one: a replayed page could observe identical randoms across what should be independent runs. No published study quantifies this; graded Low on purpose | 0 studies found | fingerprinting-literature search, 2026-10-20 (surveys and studies listed in results; none covering RNG) | 2026-10 | Low |
| 3.5 | The only budget the spec defines is a buffer cap: `getRandomValues` throws `QuotaExceededError` above 65,536 bytes per call. There is no entropy accounting, no per-origin rate limit, no record of how much randomness a page consumed — a page can call it in a loop forever | 65,536 B cap, 0 rate limits | [spec §10.1.1](https://www.w3.org/TR/WebCryptoAPI/) | read 2026-10-20 | High |

**Implications:** the permission question answers itself in the spec's own terms: gates are unnecessary because the API is origin-scoped and material-blind, and the one consent hook (3.1) is about machine load, not secrecy. Izcal should keep that page-facing contract exactly — it is a sound design — and spend its novelty on the *observability* side the contract never touches: an entropy ledger per origin (bytes drawn, calls, purposes), visible in DevTools and to the agent principal, is information the page itself cannot have and the user's tools never got. Do not add prompts: nothing in the threat model justifies them, and 2.3's volume shows they would fire constantly.

## 4. Gaps an Izcal-first crypto design could take

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **A crypto event log is buildable here and nowhere else.** No engine exposes per-operation records; every engine runs its crypto behind a native boundary its DevTools cannot see into. Izcal's own implementation plus typed IPC (B2) and spec anchors (ANC-1) make each event carry: normalized algorithm name, key handle and metadata (usages, extractable, algorithm parameters — never material), outcome, the spec step that failed, and the thread that ran it. The anchor index turns "this import failed" into "this failed at the JWK `kty` check of §14.3.9" | 0 engines ship this | this note's synthesis of 1.1–1.6, izcal-capabilities B2/ANC-1 | 2026-10 | Medium (design) / High (gap) |
| 4.2 | **"Why did my import fail" is the single most-requested debugging improvement** in the tracker's texture: the format-mismatch class (1.5) is documented across 2017–2023 issues, and vendor positions (WebKit #82) debate import error handling as an open question. The tooling answer is deterministic: sniff the actual bytes (PEM armor, base64, DER tags, JWK shape), show what was detected vs what was requested, and render the normalization result ("you passed `"AES"`; recognized names are `AES-CTR`, `AES-CBC`, `AES-GCM`, `AES-KW`") | ≥4 issues, 2017–2023 | [#192](https://github.com/w3c/webcrypto/issues/192), [#310](https://github.com/w3c/webcrypto/issues/310), [#356](https://github.com/w3c/webcrypto/issues/356), [WebKit #82](https://github.com/WebKit/standards-positions/issues/82) | 2017–2022 | Medium |
| 4.3 | **A key inventory: non-extractable keys are today's invisible objects.** The spec guarantees key material "is not exposed" except via export/wrap — which means the recommended, non-extractable key cannot be inspected by any tool without changing the page. An inventory view (handle, algorithm, usages, extractable flag, creating origin, creating worker, creation event) shows security-relevant state with zero material exposure, exactly as the WebAuthn panel already shows credentials | 0 views, 1 precedent panel | [spec §6.2](https://www.w3.org/TR/WebCryptoAPI/); [Chrome DevTools overview](https://developer.chrome.com/docs/devtools/overview) | read 2026-10-20 | High (gap and precedent) |
| 4.4 | **Worker-boundary transparency: the spec does not even fix the thread.** Operations run "in parallel" with results queued on the crypto task source, and §14.2 states the spec "makes no specific requirements on the ordering of responses" — between calls, or against other task sources. A tool that claims to say "this op ran on the worker" is guessing today; an engine that owns its scheduler (B1) can attribute, order and replay every op instead | 0 ordering guarantees | [spec §14.2–14.3](https://www.w3.org/TR/WebCryptoAPI/) | read 2026-10-20 | High |
| 4.5 | **Determinism hooks: the frameworks have not asked, because no platform ever offered it.** Evidence for demand is indirect — fake-timers fakes everything *but* randomness (2.5), rr records it one layer down (2.1), and automation must monkey-patch (2.6). A first-class `seed` for the crypto RNG, per container, in simulation mode only, is the knob all three ecosystems improvise around; it should be labelled, logged and off in normal browsing | 0 platforms offer it | synthesis of 2.1–2.6 | 2026-10 | Medium |
| 4.6 | **The agent principal needs nondeterminism as data.** An automation agent driving a page (B9) can read the DOM but cannot know that the token it just saw came from entropy — i.e. that a re-run produces a different one. A crypto event stream makes "this operation is nondeterministic; its recorded value is X" a first-class fact an agent can plan around, rather than a silent source of flaky runs. AI stays off by default (B10) and the stream is tool-facing, never page-facing | 1 capability class | izcal-capabilities B9/B10; synthesis of 2.3–2.4 | 2026-10 | Medium (design) |
| 4.7 | The unifying rule, imported from the networking strand: **the page stays blind; the tools see everything.** Error reasons, key provenance, entropy ledgers and ordering facts are all things the spec withholds from page code for good security reasons — and all things an engine that implements the crypto itself can route to DevTools, exports and the agent channel without changing what the page can observe | — | [Net 1.1–1.2](../Izcal%20networking/gaps_opportunities.md); this note's 1.3–1.6 | 2026-10 | Medium |

**Implications:** the highest-leverage move is not a new API for pages — it is a **new observability plane under the existing API**, unchanged and spec-exact for page code (HGBA-2 P1 holds: nothing here gives the page more than it has). Concretely: one crypto event schema (op id, normalized algorithm, key handle + metadata, bytes in/out, entropy drawn, outcome + internal reason + spec anchor, thread, origin, worker) emitted over B2, consumed by three surfaces at once — a DevTools crypto view (4.1–4.4), a key inventory, and the agent channel (4.6). Every competitor feature in the tracker's complaint list (4.2) is then a query, not a browser release.

**Implications:** the post-quantum window is open at the WebCrypto layer precisely because the standards track is slow (6.1) while TLS moved years ago (6.3) and edge runtimes moved first (6.4). Izcal should treat the WICG draft (6.2) as the interface to implement and FIPS 203 as the primitive to implement it *from* — the pairing lets the ML-KEM spike be spec-anchored twice (once to FIPS 203 steps, once to WICG API steps, both in the anchor index), which is the exact discipline ANC-1 exists for. The same spike then exercises the whole observability plane for free: the first page-visible crypto operation no current DevTools can show is Izcal's demo case.
