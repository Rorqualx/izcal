# Izcal WebCrypto: history and postmortems

Compiled 2026-10-20. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Scope: the history of browser cryptography and CSPRNGs — the Web Crypto API itself, the platform libraries engines chose, the randomness failures that shaped the field, the constant-time turn, and the directions that died. Claims marked † are set from first principles (no single source states them). Per the strand's evidence rule, no engine or library source code was read; only prose documents (specs, papers, blogs, maintainer statements, issue-tracker discussion text).

## 1. WebCrypto: the standard's own history

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | The W3C **Web Cryptography Working Group** (chartered 2011) shipped a **First Public Working Draft with a completely different architecture**: a streaming, event-driven model — `CryptoOperation` inheriting `EventTarget` with `init()` / `processData(buffer)` / `complete()` / `abort()`, states "empty"/"processing"/"completing", and `onprogress` / `oncomplete` / `onerror` handlers — plus a synchronous per-origin **`KeyStorage`** interface (`getKeyById`, `removeKeyById`, `clear`), `Key` objects carrying `extractable` and `temporary`, and factory methods `createEncrypter` / `createSigner` / `createDigester`. **No promises anywhere.** | FPWD 2012-09-13; defined RSAES-PKCS1-v1_5, RSASSA-PKCS1-v1_5, RSA-PSS, RSA-OAEP, ECDSA, ECDH, AES-CTR/CBC/GCM, HMAC, **DH**, SHA, PBKDF2 | [Web Cryptography API FPWD](https://www.w3.org/TR/2012/WD-WebCryptoAPI-20120913/) | 2012-09-13 | High |
| 1.2 | The design was then **rewritten**: streaming was cut, `KeyStorage` was cut, and the API became one-shot **Promise-based `SubtleCrypto`** with an "algorithm normalization" step. Era constraint: the 2012 draft mimicked the event-driven DOM APIs of its day; promises were still new to the platform. The cut of streaming is visible today — every current operation takes one `BufferSource` and returns one promise. | 0 streaming methods survive; all operations one-shot | [Web Cryptography API FPWD](https://www.w3.org/TR/2012/WD-WebCryptoAPI-20120913/), [current /TR/WebCryptoAPI/](https://www.w3.org/TR/WebCryptoAPI/) | 2012–2017 | High |
| 1.3 | The spec became a **W3C Recommendation on 2017-01-26** — about 5.5 years after the 2011 charter and 4.5 after the FPWD. Both original editors had left the spec before REC: Ryan Sleevi (Google) until 2016-01-21, Mark Watson (Netflix) until 2016-11-01. | ~5.5 years charter → REC; REC 2017-01-26 | [Web Crypto API W3C Recommendation](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/), [/TR/WebCryptoAPI/ status block](https://www.w3.org/TR/WebCryptoAPI/) | 2017-01-26 | High |
| 1.4 | The shipped algorithm set dropped what the first draft had: **RSAES-PKCS1-v1_5** (insecure padding for encryption) and **DH** never reached REC, and AES-CFB, which appeared in intermediate drafts, was dropped too. Final REC set: RSASSA-PKCS1-v1_5, RSA-PSS, RSA-OAEP, ECDSA, ECDH, AES-CTR/CBC/GCM/KW, HMAC, SHA-1/256/384/512, HKDF, PBKDF2. The REC kept **SHA-1** and **AES-CBC** for compatibility — the standards body shipped known-weak primitives alongside good ones. | 2 drafts-only algorithms dropped; 16 algorithm families at REC | [REC-WebCryptoAPI-20170126](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/) | 2017-01-26 | High |
| 1.5 | The REC **mandates no algorithms** ("does not dictate a mandatory set of algorithms that MUST be implemented"), does not address key storage provisioning (secure elements, smart cards) or key discovery, and sets no zeroization requirements. Consequence: every engine implemented its own subset, and cross-browser support tables became the developer's real spec. | 0 mandatory algorithms; no key-discovery API at REC | [/TR/WebCryptoAPI/ sections 4.2–4.3](https://www.w3.org/TR/WebCryptoAPI/) | 2017-01-26 | High |
| 1.6 | **Secure curves (X25519/Ed25519) were absent from the 2017 REC.** They entered via a [WICG proposal](https://github.com/WICG/secure-curves) (2019) rather than a W3C working group, then shipped: Safari 17 (2023-09), Firefox 129 (2024-08), Chrome 133 for X25519 (beta 2025-01-15); Chrome's Ed25519 came later in 2025 (reported as version 137). That is roughly **8 years from REC to cross-browser Ed25519** — while TLS in the same engines had used Curve25519 for years. | 2017 REC → 2023–2025 engine shipments; ~88% global support for Ed25519 as of 2025 | [Chrome 133 beta notes](https://developer.chrome.com/blog/chrome-133-beta), [MDN SubtleCrypto](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto) | 2023-09 → 2025 | High (Chrome 133, X25519); Medium (Safari 17, Firefox 130, Chrome Ed25519 version) |
| 1.7 | **Web Crypto Level 2 sat dormant for years.** The current /TR/WebCryptoAPI/ page is not the 2017 REC but the **Level 2 First Public Working Draft of 2025-04-22**, published by the Web Application Security Working Group, edited by Daniel Huigens (Proton AG), adding Ed25519, X25519 and a reworked HKDF. Eight years passed between REC and a fresh first public draft. | Level 2 FPWD 2025-04-22, 8 years after REC | [/TR/WebCryptoAPI/ (Level 2 FPWD)](https://www.w3.org/TR/WebCryptoAPI/) | 2025-04-22 | High |
| 1.8 | `window.crypto.getRandomValues` shipped **years before the rest of WebCrypto** and alone: Chrome 11 (2011-04), Firefox 21 (2013-05), IE11 (2013-10). MDN marks the API Baseline "widely available since July 2015", and it remains the **only** `Crypto` member callable from an insecure context — the platform's one piece of settled crypto, isolated from the contested parts. | Chrome 11 (2011), Firefox 21 (2013), IE11 (2013); baseline 2015-07 | [MDN Crypto.getRandomValues](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues) | 2011-04 → 2015-07 | Medium (version numbers); High (insecure-context statement) |
| 1.9 | Why so long, from the record rather than from memory: the architecture was rewritten once (streaming → promises, row 1.2), two algorithms were negotiated out (row 1.4), the algorithm set was left optional so every engine could and did differ (row 1.5), and both original editors departed before REC (row 1.3). No single maintainer postmortem of the delay exists in a form this strand could find; the churn facts above are the documentable cause, and the low platform priority relative to engine TLS work is a † inference. | 1 architecture rewrite; 2+ algorithms dropped; 2 editors gone before REC | [FPWD](https://www.w3.org/TR/2012/WD-WebCryptoAPI-20120913/), [REC](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/) | 2012–2017 | High (facts); Low (priority attribution †) |

**Implications:** WebCrypto's history says the expensive parts of a crypto API are not the ciphers but the API shape: one streaming-vs-one-shot rewrite cost years, and an optional algorithm set cost a decade of compatibility matrices. Izcal's crypto surface should fix a small mandatory core, decide streaming deliberately up front, and treat new algorithms as cheap additions behind a stable normalization-free dispatch.

## 2. Why browsers used platform crypto libraries

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Gecko's crypto has been **NSS** since the Netscape era: NSS descends from Netscape's original SSL implementation, was open-sourced with the Mozilla codebase in 1998, and remains Firefox's TLS and WebCrypto backend. Era constraint: in 1995–1998 a browser team had to write its own TLS because no suitable free library existed — owning it later became inertia. | NSS used by Firefox since before 1.0 (2004); open-sourced 1998 | [MDN: NSS project docs](https://developer.mozilla.org/en-US/docs/Mozilla/Projects/NSS) | 1998 → today | Medium |
| 2.2 | WebKit took the opposite era-appropriate path: on Apple platforms it used the OS libraries (**Secure Transport / CommonCrypto**), which cost nothing to maintain but tied its crypto to macOS/iOS releases. Later generations of WebKit converged on BoringSSL for TLS (reported 2017–2018) — the same consolidation Chrome chose in 2014. | 1 platform library pair; convergence on BoringSSL ~2017–2018 | [Apple Secure Transport docs](https://developer.apple.com/documentation/security/secure_transport) | pre-2017 | Medium (WebKit switch: Low) |
| 2.3 | **Chromium forked OpenSSL into BoringSSL on 2014-06-20.** Adam Langley's stated reasons: Google carried **more than 70 patches** on OpenSSL across Android, Chrome and internal uses; "the effort involved in keeping all these patches … straight across multiple code bases is getting to be too much"; many patches could not land upstream because they conflicted with "OpenSSL's guarantee of API and ABI stability"; the fork imports upstream changes instead of rebasing, still feeds bug fixes upstream, and licenses new code under ISC. | >70 patches at fork time; announcement 2014-06-20 | [ImperialViolet: "BoringSSL"](https://www.imperialviolet.org/2014/06/20/boringssl.html) | 2014-06-20 | High |
| 2.4 | BoringSSL's own README states the posture: "a fork of OpenSSL that is designed to meet Google's needs", "**not intended for general use** … We don't recommend that third parties depend upon it", **no API or ABI stability guarantees**, consumers vendor their own copies. It is the SSL library of Chrome and Android, but not exposed in the Android NDK. | 0 stability guarantees; 2 products (Chrome, Android) | [BoringSSL README](https://github.com/google/boringssl/blob/main/README.md) | current (2026) | High |
| 2.5 | What the fork bought: the ability to delete rarely used code, drop API-stability promises Chrome did not need, and move at engine speed (BoringSSL shipped early TLS 1.3). What it cost, stated and derived: a permanent divergent fork whose fixes no longer benefit or come from the OpenSSL community, and no shared security response pool — each vendor ships its own copy. The upstream-relationship strain was structural, not personal: the two projects optimize for different users. † | 1 fork; N vendored copies; upstream imports continue | [ImperialViolet](https://www.imperialviolet.org/2014/06/20/boringssl.html), [README](https://github.com/google/boringssl/blob/main/README.md) | 2014 → today | High (stated); Low (costs †) |
| 2.6 | The OpenSSL era's defining postmortem: **Heartbleed** (2014-04-07, CVE-2014-0160) — a missing bounds check in the DTLS/TLS heartbeat extension read process memory including private keys, silently and remotely. It precipitated LibreSSL (OpenBSD's fork, April 2014) and hardened the case for BoringSSL, and it exposed the ecosystem's real constraint: critical internet crypto maintained on near-zero funding. | disclosed 2014-04-07; 1 missing bounds check; 2 forks within weeks | [heartbleed.com](http://heartbleed.com/) | 2014-04-07 | High (bug facts); Medium (funding claims) |

**Implications:** Engines fork or wrap crypto libraries for maintainability reasons that are still valid (70+ patches, ABI promises aimed at different consumers), and the cost — fork drift, divided security response — is permanent. Izcal should own its crypto layer per M-1 but design it as a small, spec-anchored core with explicit stability policy, not as a general-purpose library trying to serve everyone.

## 3. CSPRNG history and failures

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | The founding failure: Netscape's SSL (Navigator 1.1, 1995) seeded its PRNG with **time of day (seconds + microseconds), process ID and parent process ID**, mixed by unkeyed functions (`mklcpr`, MD5). Goldberg and Wagner reverse-engineered it by decompiling the binary (the seeding was not documented) and showed at most **47 bits** of entropy in a "128-bit" key — effectively "pid + (ppid << 12) has only 27 bits, not 30". Exhausting the remaining seeds took "about 25 seconds on an HP 712/80" locally; remote recovery was minutes; the 40-bit export variant fell to 30 hours of distributed brute force. | ≤47 bits vs 128 claimed; 25 s local; 30 h for 40-bit keys | [Goldberg & Wagner, "Randomness and the Netscape Browser", Dr. Dobb's](https://people.eecs.berkeley.edu/~daw/papers/ddj-netscape.html) | 1996-01 | High |
| 3.2 | Fate and fix: Netscape patched in Navigator 1.22 Security Update and 2.0 beta1 and adopted stronger seeding — but the lesson the authors drew, that **security code needs public design review and userspace-visible state is not entropy**, became the field's template. What survived: the practice of seeding from the kernel's entropy pool, never from process-visible state. | 2 patched releases; 1996 | [Goldberg & Wagner](https://people.eecs.berkeley.edu/~daw/papers/ddj-netscape.html) | 1996 | High |
| 3.3 | **The Debian OpenSSL bug** was introduced in **September 2006** (package 0.9.8c-1): the maintainer commented out two `MD_Update(&m, buf, j)` lines in `md_rand.c` while chasing **Valgrind warnings** about uninitialized memory, and asked about the change on a mailing list that was the wrong audience — no objection came back. The second removed line was harmless; the first was in `ssleay_rand_add`, so "the pool will never actually get the entropy intended for it". | introduced 2006-09-17; 2 lines removed; ~20 months latent | [Debian wiki: SSLkeys postmortem](https://wiki.debian.org/SSLkeys) | 2006-09 → 2008-05 | High |
| 3.4 | Effect and disclosure: OpenSSL was seeded **only by the process ID** — 32767 possible streams per architecture, "(2^15-1)*3 or 98301" total. DSA-1571 disclosed on 2008-05-13. Every OpenSSL-generated key since September 2006 had to be regenerated (SSH host keys, certificates, OpenVPN, DNSSEC, Tor), **plus any DSA key merely used** on an affected machine, because a known or repeated DSA nonce exposes the private key. CAs offered free reissuance; blacklists (`openssh-blacklist`, `dowkd.pl`) were distributed. | 32,767 streams per arch; 98,301 total; disclosure 2008-05-13 | [Debian wiki: SSLkeys](https://wiki.debian.org/SSLkeys) | 2008-05-13 | High |
| 3.5 | The postmortem's stated causes: "an overzealous, well-intentioned elimination of code" believed security-neutral, compounded by asking the wrong list and getting misleading answers. The generalizable failure modes, visible in the record: (a) cleanup patches to crypto code without crypto review; (b) the RNG degraded **silently** instead of failing loudly — nothing detected that the pool had stopped accumulating entropy. | ~20 months of weak keys worldwide; 1 reviewer; 0 detection | [Debian wiki: SSLkeys](https://wiki.debian.org/SSLkeys) | 2008 | High |
| 3.6 | **Dual_EC_DRBG** entered NIST SP 800-90 (final 2007-03) as one of four DRBGs, with constants influenced by NSA. At CRYPTO 2007 Shumow and Ferguson showed in a rump-session talk that whoever knows the constants' discrete log can recover the generator's internal state from a small output sample — a plausible backdoor built into a standard. FIPS-validated stacks (including platform libraries) adopted 800-90 DRBGs for compliance, which is how the design spread. | standard 2006/2007; 1 talk in 2007 exposed it | [Schneier: "The Strange Story of Dual_EC_DRBG"](https://www.schneier.com/blog/archives/2007/11/the_strange_sto.html), [NIST SP 800-90A](https://csrc.nist.gov/pubs/sp/800/90/a/r1/final) | 2006/2007 → 2007-08 | High (timeline); Medium (FIPS-driven spread) |
| 3.7 | Aftermath: Snowden documents (2013-09-05) showed NSA's Bullrun program influencing standards; ProPublica reported **$10M paid to RSA** to make Dual_EC the BSAFE default. NIST announced removal of Dual_EC_DRBG on **2014-04-21**; **SP 800-90A Rev. 1 (June 2015)** shipped without it; a Rev. 2 was still only at a pre-draft call for comments on 2025-09-04 — the standard took ~18 months to fix, the program ~11 years to revise. | removal announced 2014-04-21; Rev.1 2015-06; Rev.2 pre-draft 2025-09-04 | [NIST news](https://www.nist.gov/news-events/news/2014/04/nist-removes-cryptography-algorithm-random-number-generator-recommendations), [NIST SP 800-90A Rev.2 pre-draft](https://csrc.nist.gov/pubs/sp/800/90/a/r2/iprd), [ProPublica](https://www.propublica.org/article/the-nsas-secret-campaign-to-crack-undermine-internet-encryption) | 2013-09 → 2025-09 | High |
| 3.8 | The backdoor outlived the standard: **Juniper ScreenOS** (firewalls) shipped Dual_EC with modified constants plus an unauthorized SSH-equivalent password, disclosed 2015-12-17. Checkoway et al. (CCS 2016) analyzed it systematically: code had been borrowed across products without anyone re-deriving the constants — the same failure pattern Debian showed at smaller scale. | disclosed 2015-12-17; 1 vendor; constants reused undetected | [Checkoway et al., "A Systematic Analysis of the Juniper Dual EC Incident"](https://eprint.iacr.org/2016/376) | 2015-12-17 | Medium |
| 3.9 | Firefox's own stack had its entropy incident late and in a different place: **CVE-2020-6829** (fixed Firefox 80, advisory 2020-08-25) — "P-384 and P-521 vulnerable to an electro-magnetic side channel attack on signature generation", paired with CVE-2020-6830. The lesson: even after seeding is right, **nonce generation in signatures remains a leak channel**, and it took a hardware side channel to find it. | Firefox 80, 2020-08-25; 2 CVEs; 2 curves | [MFSA 2020-36](https://www.mozilla.org/en-US/security/advisories/mfsa2020-36/) | 2020-08-25 | High |
| 3.10 | **Chrome's early-Android era ran on a weak randomness substrate.** Google's own postmortem (2013-08-14): a Bitcoin transaction was compromised on 2013-08-11 because apps "may not receive cryptographically strong values" where the underlying PRNG was improperly initialized; Google shipped OpenSSL PRNG initialization fixes, made KitKat 4.4 the clean baseline, and told pre-4.3 apps to apply a `PRNGFixes` patch seeding from `/dev/urandom`. Kaplan et al. (WOOT '14) then demonstrated concrete attacks on the Linux PRNG on Android, including the early-boot window. | incident 2013-08-11; advisory 2013-08-14; Android 4.4 baseline | [Android Developers Blog: "Some SecureRandom Thoughts"](https://android-developers.googleblog.com/2013/08/some-securerandom-thoughts.html), [Kaplan et al., WOOT '14](https://www.usenix.org/system/files/conference/woot14/woot14-kaplan.pdf) | 2013-08 → 2014 | High |
| 3.11 | The modern settlement — **entropy is a kernel contract**: Linux 3.17 (2014) added `getrandom(2)`, which blocks until the pool is seeded, replacing per-app entropy folklore. The tradeoff surfaced as applications hanging at boot in low-entropy VMs and containers; Node.js's move of `crypto.randomBytes` onto the system generator was discussed openly in [nodejs/node issue #5798](https://github.com/nodejs/node/issues/5798) (2016). The pattern the three decades teach: **seed from the kernel, never build an app-level DRBG without need, and never fall back silently** — every disaster above (Netscape, Debian, Android 2013) is a silent fallback or a process-visible seed. | kernel API 2014; 1 blocking syscall; 3 silent-fallback disasters (1996, 2008, 2013) | [getrandom(2) man page](https://man7.org/linux/man-pages/man2/getrandom.2.html), [nodejs/node #5798](https://github.com/nodejs/node/issues/5798) | 2014 → 2016 | Medium |

**Implications:** Izcal's CSPRNG policy writes itself from this record: draw from the OS kernel via the strongest available contract, fail closed and visibly if it is not yet seeded, never ship a silent fallback or an app-level DRBG, and treat any change near entropy-gathering code — even two deleted lines — as a crypto change requiring crypto review. This is also the natural place for Izcal to expose randomness provenance to its DevTools, which no current browser does.

## 4. Constant-time: from Kocher to verified arithmetic

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | **Kocher (CRYPTO '96)** showed RSA, DH and DSS implementations leak keys through execution time, using only remote measurements; the deployed countermeasure (blinding) entered mainstream libraries in the following years. Side channels moved from lab curiosity to a property every crypto implementation must answer for. | 1 paper; remote measurements only | [Kocher, "Timing Attacks on Implementations…", CRYPTO '96](https://link.springer.com/chapter/10.1007/3-540-68697-5_9) | 1996 | High |
| 4.2 | **Bleichenbacher (CRYPTO '98)** turned PKCS #1 v1.5 padding error messages into an oracle: an adaptive chosen-ciphertext attack recovering RSA keys from SSL, needing on the order of 2^20 crafted messages. TLS spent the next two decades patching fragments of it instead of removing the construction. | ~2^20 chosen ciphertexts; 1 oracle class, 20+ years of patches | [Bleichenbacher, CRYPTO '98](https://link.springer.com/chapter/10.1007/BFb0055716) | 1998 | High |
| 4.3 | **Bernstein, "Cache-timing attacks on AES" (2005-04-14)** showed the AES table lookups leak enough through the CPU cache for a remote attacker — on hardware where AES was assumed safe. The structural answer was to stop using tables: hardware AES (AES-NI, from 2010) and table-free software. | 1 paper; table lookups → cache; AES-NI 2010 | [Bernstein 2005](https://cr.yp.to/antiforgery/cachetiming-20050414.pdf) | 2005-04-14 | High (paper); Medium (AES-NI date) |
| 4.4 | **Osvik, Shamir, Tromer** (ePrint 2005-11, CT-RSA 2006) systematized cache attacks: prime+probe and evict+time against AES on a local machine, recovering full keys in tens of milliseconds — the lab demonstration that made Bernstein's remote result believable. | 2 techniques; full AES key recovery, ~65 ms as reported | [Osvik–Shamir–Tromer, "Cache Attacks and Countermeasures: the Case of AES"](https://eprint.iacr.org/2005/271) | 2005-11 | Medium |
| 4.5 | **Lucky13 (IEEE S&P 2013)** broke the TLS/DTLS CBC record layer with timing differences at nanosecond scale — the MAC-then-encrypt construction itself was the defect. TLS 1.3 (RFC 8446, 2018-08) ended the class structurally: CBC and RSA key exchange removed, AEAD only. | 1 construction; ns-scale timing; CBC + TLS_RSA removed in TLS 1.3 | [AlFardan & Paterson, IEEE S&P 2013](https://doi.org/10.1109/SP.2013.42), [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446) | 2013-05 → 2018-08 | High |
| 4.6 | **Brumley & Tuveri, "Remote Timing Attacks Are Still Practical" (2011)**: remote recovery of a TLS server's ECDSA key from OpenSSL's Montgomery ladder on binary-field curves, via a lattice attack on leaked nonce timing — proof that Kocher's attack class had crossed fully into unauthenticated network territory, 15 years later. | 1 remote key recovery; 2011; curves over binary fields | [Brumley & Tuveri, ePrint 2011/232](https://eprint.iacr.org/2011/232) | 2011 | High |
| 4.7 | **ROBOT (disclosed 2017-12-12/13; USENIX Security 2018)** re-ran Bleichenbacher's 1998 attack against the live internet: vulnerable hosts on **27 of the Alexa top-100 domains**, including Facebook (proven by signing a test message), with vendors Cisco, Citrix, F5 and others affected; recommended fix was disabling TLS_RSA key exchange entirely. The 20-year-old oracle persisted because implementations kept returning distinguishable errors. The line continued with the Marvin Attack (2023). | 27/100 top domains; 2017-12-12; ≥7 vendors | [robotattack.org](https://robotattack.org/) | 2017-12-12 | High |
| 4.8 | Entropy-adjacent timing matured into a wallet-draining bug class: **Breitner & Heninger, "Biased Nonce Sense"** (ePrint 2019/023; Financial Crypto 2019) recovered ECDSA private keys from biased nonces in Bitcoin and Ethereum wallets via lattice attacks, while the Minerva work (2019) showed real devices leaking nonce length through timing alone. Signature nonce generation is now treated as a CSPRNG-adjacent correctness requirement, not an implementation detail. | 2 currencies drained; 1 lattice technique | [Breitner & Heninger, ePrint 2019/023](https://eprint.iacr.org/2019/023), [Minerva](https://minerva.crocs.fi.muni.cz) | 2019 | Medium |
| 4.9 | The response that became mainstream: **constant time by construction, with generated and formally verified arithmetic.** Fiat-Crypto (Coq-generated field arithmetic; IEEE S&P 2019) is deployed in Chrome's BoringSSL (per the project's papers) and, in Firefox, replaced 32-bit Curve25519 code in Firefox 77 (2020-06) with "nearly 10x" gains plus "~27%" on the 64-bit HACL\* code; HACL\* (F\*-verified, CCS 2017) shipped Curve25519 and ChaCha20/Poly1305 through NSS 3.39 (2018-09, the Firefox 62 baseline); the HACL\*/Vale/EverCrypt projects state deployment in Firefox's NSS, the Linux kernel, mbedTLS and Tezos. Why it won: hand-written constant-time assembly cannot be audited at acceptable cost, compilers keep breaking hand-written C, and verified generation removed the performance penalty that had justified unsafe code. | NSS 3.39 (2018-09); fiat-crypto Curve25519 in Firefox 77 (2020-06): ~10x and +27% speedups from verified code | [Mozilla Security Blog, 2020-07-06](https://blog.mozilla.org/security/2020/07/06/performance-improvements-via-formally-verified-cryptography-in-firefox/), [HACL\* paper](https://eprint.iacr.org/2017/536), [HACL\* site](https://hacl-star.github.io) | 2017 → 2020 | High (Firefox numbers); Medium (Chrome, kernel deployment claims) |

**Implications:** The constant-time record shows Izcal two things: first, timing is a remote, internet-scale attack class — a new engine's crypto must be constant-time by policy from day one, not patched after paper 4.7's successors; second, the winning technique is generation plus verification with proofs, at zero performance cost. Izcal's own `hg-crypto` should generate or verify its arithmetic the same way rather than trusting review to catch what test suites cannot.

## 5. Failed and abandoned browser-crypto directions

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | **Plugin crypto (1996–2015):** before WebCrypto, page crypto meant Java signed applets (JCA), ActiveX controls (CAPICOM), or Flash crypto libraries. Signed applets ran outside the sandbox, which was the whole point and the fatal flaw. Fate: Chrome announced the NPAPI sunset in 2013-09 and removed it by 2015-01; Firefox 52 (2017-03) dropped NPAPI except Flash; Flash reached end of life 2020-12-31. What survived from this era: the requirement that crypto code run inside the page sandbox with no native-plugin escape hatch. | 3 plugin platforms; ~20-year era; full removal 2015–2020 | [Chromium blog: NPAPI](https://blog.chromium.org/2013/09/saying-goodbye-to-our-old-friend-npapi.html), [Adobe Flash EOL](https://www.adobe.com/products/flashplayer/end-of-life.html) | 2013-09 → 2020-12-31 | Medium |
| 5.2 | **`window.crypto.signText`** — Netscape's JavaScript API for document signing — lingered as a non-standard, SHA-1-era relic and was **removed in Firefox 33** (2014-10). It was the last piece of the "browser as certificate-signing application" model from the 1990s; nothing replaced it inside `window.crypto`. | removed Firefox 33, 2014-10 | [MDN: Crypto.signText](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/signText) | 2014-10 | Medium |
| 5.3 | **Extractable keys as the default foot-gun.** `CryptoKey.extractable = true` keys live in JS-readable memory and were stolen through XSS; but `extractable = false` only protected against export — the key material still sat in process memory, and Spectre-class attacks (2018-01) made renderer memory readable in principle, forcing browsers to throttle timers. The platform's answer for high-value credentials was to move them out of JS reach entirely: **WebAuthn** (W3C Recommendation 2019-03-04) with hardware-backed, attested, non-exportable credentials. | Spectre: 2018-01; WebAuthn REC: 2019-03-04 | [Spectre paper](https://spectreattack.com/spectre.pdf), [WebAuthn REC](https://www.w3.org/TR/2019/REC-webauthn-1-20190304/) | 2018-01 → 2019-03-04 | Medium |
| 5.4 | **The missing streaming API pushed large-file crypto out of the platform.** With one-shot `encrypt()` calls, developers hand-rolled chunked AES-GCM (new IV per chunk — hand nonce management, a recurring failure) or moved to WebAssembly ports such as libsodium.js (2016). The 2012 draft's streaming model (row 1.1) was cut for good API reasons, but no replacement for bulk data ever arrived. | 0 streaming methods; WASM workaround since ~2016 | [/TR/WebCryptoAPI/](https://www.w3.org/TR/WebCryptoAPI/), [libsodium.js](https://github.com/jedisct1/libsodium.js) | 2012 → today | High (API facts); Low (developer-behavior pattern †) |
| 5.5 | **New algorithms stopped flowing through WebCrypto.** HPKE (RFC 9180, 2022-07) — the modern encryption construction used by platform features such as WebTransport — has no SubtleCrypto surface; secure curves shipped via a WICG proposal rather than a W3C working group (row 1.6); engines add what their platform features need and expose the rest nowhere. WebCrypto is effectively frozen at its 2017 algorithm set plus late additions. | RFC 9180: 2022-07; 0 HPKE methods in SubtleCrypto | [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180), [/TR/WebCryptoAPI/](https://www.w3.org/TR/WebCryptoAPI/) | 2019 → 2025 | Medium |
| 5.6 | **Web Crypto Level 2 stagnated and the WG moved on.** The Level 2 drafts (secure curves, new algorithms) advanced no further than working drafts for roughly a decade; the original editors left in 2016; the work moved first to WICG and now to the Web Application Security Working Group, whose Level 2 FPWD only appeared on 2025-04-22. The record's verdict: a crypto API standard is not maintained by continuous revision — it is revised by crisis or not at all, and engines route around the freeze. | ~2016 → 2025-04-22 between Level 2 milestones | [/TR/WebCryptoAPI/ status](https://www.w3.org/TR/WebCryptoAPI/) | 2016 → 2025 | High |

**Implications:** Every abandoned direction here died for a reason Izcal should design against: plugin crypto died because trust boundaries must not depend on installing code; signText died because signing user documents is a workflow, not a global function; extractable keys died because JS-reachable memory is not a key store; frozen WebCrypto died as a venue because standards bodies cannot sustain crypto-API velocity. Izcal's crypto surface should be small, mandatory-core, streaming-capable, and treat credentials and bulk data as separate designs from the start.

## 6. Chronology

| Year | Project / event | What it did | Why that way | Fate and why |
|---|---|---|---|---|
| 1995–96 | Netscape SSL RNG | Seeded SSL keys from clock + PID + PPID | No kernel RNG contract existed; seeding was undocumented and unreviewed | Broken publicly by Goldberg–Wagner (1996-01); patched in Navigator 1.22 / 2.0 beta1; founded the seed-from-kernel rule |
| 1996–98 | Kocher 1996; Bleichenbacher 1998 | Timing and padding-oracle attacks on RSA in SSL | Implementations optimized first, analyzed later | Blinding and (fragmentary) countermeasures deployed; the padding oracle kept resurfacing for 20+ years (ROBOT 2017) |
| 1998 | OpenSSL / NSS open-sourced | SSLeay → OpenSSL (1998-12); Netscape crypto → NSS | Browsers needed TLS and no maintained free library existed | Both dominated for 15+ years; both later forked (BoringSSL 2014, LibreSSL 2014) when engine needs diverged |
| 2001–12 | Plugin crypto era | Java applets, ActiveX/CAPICOM, Flash libs did page crypto | The page sandbox had no crypto at all | Died with NPAPI (Chrome 2015, Firefox 2017) and Flash (2020) — trust boundary could not survive native plugin code |
| 2006–08 | Debian OpenSSL bug | Entropy pool silently lost its inputs | Valgrind cleanup on crypto code without crypto review; wrong review channel | Disclosed 2008-05-13; 98,301 possible streams; global key regeneration; made silent RNG degradation the canonical fear |

## 7. Lessons

1. **Seed from the kernel; fail visibly.** Netscape (1996), Debian (2008) and Android (2013) all failed through process-visible seeds or silent fallbacks. Izcal: kernel RNG only, no app-level DRBG, fail closed and log loudly — and expose RNG provenance in DevTools.
2. **Entropy-adjacent code is crypto code.** Two deleted lines cost the internet its keys in 2008. Izcal: any patch near entropy, seeding or nonce generation requires crypto review, no matter how mechanical it looks.
3. **API shape costs more than ciphers.** WebCrypto's streaming→promise rewrite and optional algorithm set cost five years and a decade of compatibility matrices. Izcal: fix a small mandatory core, decide streaming in the first design pass, no per-algorithm negotiation.
4. **Standards velocity for crypto APIs is near zero.** Level 1 took 5.5 years; Level 2's next milestone came 8 years later; engines routed around via WICG and platform features. Izcal: anchor to stable specifications (RFCs, NIST docs) rather than betting the product on a working group's cadence.
5. **Legacy primitives ride along unless excluded.** The REC shipped SHA-1 and AES-CBC; TLS_RSA survived until ROBOT proved 27 of the top-100 sites exposed. Izcal: exclude the weak option entirely — "deprecated but present" is how oracle classes live for 20 years.
6. **Timing is a remote attack class.** From Kocher 1996 to Marvin 2023, every "too slow to exploit remotely" claim was eventually beaten. Izcal: constant-time by policy from day one, with a documented threat model for what is constant-time and why.
7. **Generate or verify, don't hand-write.** Verified generated arithmetic (Fiat-Crypto, HACL\*) won because it is auditable and fast — ~10x and +27% speedups in Firefox 77 — while hand-written assembly was unauditable at scale. Izcal: `hg-crypto` generates or verifies its field arithmetic with proofs anchored to the specs.
8. **JS-reachable memory is not a key store.** Extractable keys were stolen via XSS; "non-extractable" keys died with Spectre; credentials moved to WebAuthn's hardware-bound model. Izcal: separate credential-key design from bulk-data crypto; keep long-lived key material out of renderer processes entirely (consistent with HGBA-2 P1 isolation).
9. **Forking a crypto library is a permanent tax.** BoringSSL's >70-patch motivation was real, and so is the ongoing cost: divergent fixes, no shared response pool. Izcal builds its own core per M-1 — so it should be small enough that one team can audit all of it.
10. **Provenance of constants and designs matters.** Dual_EC entered a NIST standard through an unexplained constant and outlived its removal inside Juniper. Izcal: every parameter, curve and constant in its crypto specs carries a citation to a public standard or a derivation — nothing accepted because a vendor or authority shipped it.

**Known gaps in this note:** no maintainer postmortem of WebCrypto's 5.5-year delay was found in prose form (row 1.9 carries the documentable churn facts instead, with the priority attribution marked †); the WebKit move to BoringSSL is secondary-sourced (row 2.2, Low); OST's 65 ms figure and several browser version numbers for secure-curve shipments are graded Medium (rows 4.4, 1.6, 1.8) and should be re-checked in phase 8.
