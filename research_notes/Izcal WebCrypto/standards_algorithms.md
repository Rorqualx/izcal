# Izcal WebCrypto: standards and algorithms

Compiled 2026-10-20. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers). No third-party source code was read or cited; every finding is anchored to standards prose (W3C, IETF, NIST), published papers, or vendor status pages.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Izcal implements every primitive itself, from the specifications' prose only (M-1). This note inventories, per primitive, the governing document, its current status, and the implementation hazards the prose reveals.

*Corrections (phase 8 fact-check): the PQC issue link is w3c/webcrypto #367 (was #300); the FIPS 197 and SP 800-57 Pt1 Rev 5 URLs point at the canonical nvlpubs/csrc paths; row 1.2's operation count is twelve, not six (the list was already correct).*

## 1. The W3C Web Cryptography API surface

|---|---|---|---|---|---|
| 1.1 | [Web Cryptography API](https://www.w3.org/TR/WebCryptoAPI/) Level 1 reached W3C Recommendation; the spec has since continued as "Level 2" / editor's draft at [w3c.github.io/webcrypto](https://w3c.github.io/webcrypto/). The API defines one entry point, `SubtleCrypto`, with twelve operations: encrypt, decrypt, sign, verify, digest, generateKey, deriveKey, deriveBits, importKey, exportKey, wrapKey, unwrapKey. | 1 Rec (2017-01-26); L2 in continuous editor's draft | [W3C WebCryptoAPI](https://www.w3.org/TR/WebCryptoAPI/) | 2017-01-26 | High |
| 1.2 | The registered algorithm set is fixed in the spec's [algorithm registry](https://w3c.github.io/webcrypto/#algorithm-overview): AES-CBC, AES-CTR, AES-GCM, AES-KW, HMAC, SHA-1, SHA-256, SHA-384, SHA-512, HKDF, PBKDF2, RSASSA-PKCS1-v1_5, RSA-OAEP, RSA-PSS, ECDH, ECDSA. | 1.3 | ["Normalize an algorithm"](https://w3c.github.io/webcrypto/#algorithm-concepts) is the spec's central error funnel: an algorithm identifier is coerced to a dictionary, the operation is looked up in the registry, and failure produces `NotSupportedError` (unknown algorithm/operation) or `SyntaxError`/`TypeError` (malformed dictionary). | 1.4 | The [key model](https://w3c.github.io/webcrypto/#key-interface) is `CryptoKey` with `type`, `extractable`, `usages`, `algorithm`; importKey/exportKey accept `raw`, `spki`, `pkcs8`, `jwk`; wrap/unwrap compose export+encrypt. `extractable: false` keys cannot be exported, and a requested `usages` that the algorithm does not permit raises `SyntaxError`. | 4 formats, 8 usages per-algo | [W3C WebCrypto §CryptoKey](https://w3c.github.io/webcrypto/#key-interface) | 2024 | High |
| 1.5 | `SubtleCrypto` is `[SecureContext]`: `crypto.subtle` is only exposed in [secure contexts](https://w3c.github.io/webappsec-secure-contexts/) (HTTPS or localhost). Non-secure pages get `crypto.getRandomValues` but no `subtle`. | secure-context only | [W3C WebCrypto §Crypto interface](https://w3c.github.io/webcrypto/#crypto-interface) | 2024 | High |
| 1.6 | The ["secure curves"](https://wicg.github.io/webcrypto-secure-curves/) draft (X25519, X448, Ed25519) lived in WICG for years outside the main registry; its content was [merged into the main WebCrypto editor's draft in December 2024](https://github.com/ipfs/in-web-browsers/issues/204), and an Igalia survey (Feb 2025) found all three engines shipping Ed25519/X25519. | merged 2024-12 | [Igalia: Secure Curves in the Web Platform](https://bits.igalia.com/can-i-use-secure-curves-in-the-web-platform/), [WICG secure-curves](https://wicg.github.io/webcrypto-secure-curves/) | 2024-12 | High |
| 1.7 | Shipping status: Ed25519 in [Chrome 137](https://chromestatus.com/feature/5188291511054336) (2025), [Firefox 129](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/129), Safari earlier (17.x). X448 is defined by the draft but **not shipped** by any engine; Ed448 was dropped from the WICG draft. Interop reality: web applications cannot yet rely on Ed25519 everywhere pre-2024. | Chrome 137, FF 129, Safari 17 | [Igalia blog](https://bits.igalia.com/can-i-use-secure-curves-in-the-web-platform/), [chromestatus](https://chromestatus.com/feature/5188291511054336) | 2025 | Medium |
| 1.8 | Chrome ships one non-standard algorithm in SubtleCrypto, [CHACHA20-POLY1305](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto), never registered in W3C; MDN documents it as Chrome-only and non-standard. AES-CTR by contrast is standard and shipped everywhere. | 1 non-standard algo (Chrome) | [MDN SubtleCrypto](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto) | 2025 | Medium |
| 1.9 | WebCrypto defines **no** AES-SIV (RFC 5297), no ChaCha20-Poly1305, no SHA-3 (FIPS 202), no HPKE (RFC 9180). Community proposals exist: [WICG/webcrypto-modern-algos](https://github.com/WICG/webcrypto-modern-algos) (ChaCha20 et al.) and [wintercg/proposal-webcrypto-streams](https://github.com/wintercg/proposal-webcrypto-streams), none merged into W3C as of 2026-10. | 0 of 4 in W3C registry | [WICG proposal](https://github.com/WICG/webcrypto-modern-algos) | 2026 | High |
| 1.10 | Post-quantum: ML-KEM/ML-DSA are **not** in the W3C WebCrypto registry; discussion has run on the W3C WebAppSec issue tracker since 2024 with no merged spec. Ecosystem PQ exposure is currently TLS-only (see §3). Izcal must decide whether to expose a PQ surface as an extension or hold to the registry. | no PQ in registry | [w3c/webcrypto #367, the PQC tracking issue](https://github.com/w3c/webcrypto/issues/367) | 2026-10 | Medium |
| 1.11 | SHA-1 remains in the registry (digest only; the spec never allowed it for signatures), so engines cannot remove it without breaking the registry contract — NIST [deprecated SHA-1 entirely (SP 800-131A Rev 2) and disallowed it for signatures as of 2024](https://csrc.nist.gov/pubs/sp/800/131/a/r2/final). | SHA-1: digest-only in WebCrypto | [SP 800-131A Rev 2](https://csrc.nist.gov/pubs/sp/800/131/a/r2/final) | 2019-03 | High |

**Implications:** Izcal implements the full 16-algorithm registry plus the merged secure curves (X25519, Ed25519; X448 optional since no engine ships it) and must decide its position on Chrome's non-standard ChaCha20-Poly1305 — implementing it costs little (RFC 8439 is needed for TLS anyway) but naming it exactly `CHACHA20-POLY1305` is a compat decision, not a standards one. The registry's closed nature is itself a finding: WebCrypto is deliberately frozen, so Izcal's own extensions (PQ, SHA-3, HPKE) would be non-registry and should be named and documented as such.

## 2. Governing documents per primitive

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | SHA-1 and SHA-2 are governed by [FIPS 180-4](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf) (still the current version, no update since 2015). SHA-1's security limit is practical, not theoretical: [SHAttered](https://shattered.io/) demonstrated the first *practical* collision (2^63.1 work) and later work showed chosen-prefix collisions cheap enough to forge PDF/GPG signatures. Implication for Izcal: SHA-1 digest must exist, but nothing that signs with SHA-1 may verify as trusted. | 2^63.1 collision work | [FIPS 180-4](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf), [SHAttered](https://shattered.io/static/shattered.pdf) | 2017-02-23 | High |
| 2.2 | HMAC is [FIPS 198-1](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.198-1.pdf) and originally [RFC 2104](https://datatracker.ietf.org/doc/html/rfc2104). The only real hazard is key length: the prose says keys longer than the block size (64 B for SHA-256) are hashed first — implementations that truncate instead of hash break interop silently. | block 64 B (SHA-1/256), 128 B (SHA-384/512) | [FIPS 198-1](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.198-1.pdf) | 2008-07 | High |
| 2.3 | HKDF is [RFC 5869](https://datatracker.ietf.org/doc/html/rfc5869) (extract-then-expand), with test vectors in the RFC itself. WebCrypto's `deriveBits` maps directly; the known hazard is that WebCrypto `deriveKey` composes HKDF with an import step, so salt/info/length mistakes surface as derived-key `usages` errors, not HKDF errors. | 2 stages; vectors in RFC | [RFC 5869](https://datatracker.ietf.org/doc/html/rfc5869) | 2010-05 | High |
| 2.4 | PBKDF2 is [RFC 8018](https://datatracker.ietf.org/doc/html/rfc8018) (PKCS #5 v2.1) with NIST guidance in [SP 800-132](https://csrc.nist.gov/pubs/sp/800/132/final). The prose hazard is iteration count: the spec has no floor, and SP 800-132's ≥ 1000 is decades stale — OWASP's current floor is 600,000 for SHA-256. Izcal must set a policy floor, not inherit the RFC's. | OWASP floor 600k (SHA-256) | [RFC 8018](https://datatracker.ietf.org/doc/html/rfc8018), [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) | 2017-08 | High |
| 2.5 | AES is [FIPS 197](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.197.pdf) (updated 2023-05, no algorithm change). Block is always 128-bit; key sizes 128/192/256. WebCrypto exposes all three key sizes for CBC/CTR/GCM/KW. | 128-bit block; 3 key sizes | [FIPS 197 upd.1](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.197.pdf) | 2023-05 | High |
| 2.6 | AES-GCM is [SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf). The governing rule: the IV must be **unique** per key; a single reuse leaks GHASH authentication keys and enables forgery and plaintext recovery. The spec's own guidance: 96-bit random IVs limited to 2^32 invocations per key. WebCrypto requires 128-bit tags but permits other tag lengths (`length` in AesGcmParams) down to 32 bits — a footgun Izcal should floor at 96 or 128. | IV 96-bit recommended; ≤2^32 invocations; tag 128-bit in WebCrypto | [SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf), [W3C AesGcmParams](https://w3c.github.io/webcrypto/#aes-gcm) | 2007-11 | High |
| 2.7 | AES-CTR is [SP 800-38A](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38a.pdf). Hazard: counter-block management is left to the caller; WebCrypto's `counter` parameter is the full 128-bit initial block and the spec wraps the counter mod 2^128 — two libraries have historically disagreed on carry-out of the nonce half, so cross-implementation CTR vectors matter. | 128-bit counter, mod 2^128 | [SP 800-38A](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38a.pdf) | 2001-11 | High |
| 2.8 | AES-CBC (SP 800-38A) has no built-in authentication; WebCrypto's decrypt pads and throws `OperationError` on bad padding. The padding-oracle class ([Vaudenay 2002](https://www.iacr.org/archive/eurocrypt2002/23320530/cbc02_e02d.pdf), later [Lucky 13](https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/lucky13) at TLS layer) means an implementation whose padding error timing or message differs observable behavior is a live attack surface. Izcal must make decrypt failures indistinguishable in time and error shape. | padding oracle class | [SP 800-38A](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38a.pdf), [Lucky 13](https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/lucky13) | 2013 | High |
| 2.9 | AES-KW is [SP 800-38F](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-38F.pdf) (KW and KWP). The integrity check is a fixed 64-bit integrity register; failure must be `OperationError`. Key-wrap's hazard is subtle: it authenticates only, and WebCrypto's wrapKey composes export+encrypt so a raw KW on a non-key payload is possible — the prose permits it, callers must not. | 64-bit IC check | [SP 800-38F](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-38F.pdf) | 2013-01 | High |
| 2.10 | RSA is [RFC 8017](https://datatracker.ietf.org/doc/html/rfc8017) (PKCS #1 v2.2): RSASSA-PKCS1-v1_5, RSAES-OAEP, RSASSA-PSS. Key-size guidance is [SP 800-57 Part 1 Rev. 5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final): 2048-bit RSA ≈ 112-bit security, acceptable **through 2030**; 128-bit security needs 3072 bits. WebCrypto permits 2048+ for all RSA ops. | 2048-bit floor → 2030; 3072 for 128-bit | [SP 800-57 Pt1 R5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) | 2020-05 | High |
| 2.11 | RSA decryption hazards are the Bleichenbacher 1998 adaptive chosen-ciphertext attack on PKCS #1 v1.5 padding (returning distinct errors for "wrong padding" leaks decryption), and [Manger 2001](https://www.iacr.org/archive/crypto2001/21390229.pdf) for OAEP. The 2018 [ROBOT](https://robotattack.org/) survey found Bleichenbacher oracles still live in major TLS stacks 20 years on. Lesson for Izcal: decryption failure paths must be a single indistinguishable `OperationError`, never differentiated by padding validity, length, or timing. | Bleichenbacher 1998; Manger 2001; ROBOT 2018 | [Bleichenbacher CRYPTO'98](https://link.springer.com/chapter/10.1007/3-540-68697-5_9), [ROBOT](https://robotattack.org/) | 2018 | High |
| 2.12 | ECDSA is [FIPS 186-5](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.186-5.pdf) (2023-02, current; DSA removed for new generation). Per-message nonce `k` must be secret and never repeat: the [Sony PS3 signing-key recovery](https://www.bbc.com/news/technology-12116051) (2010) came from a constant `k`. [RFC 6979](https://datatracker.ietf.org/doc/html/rfc6979) deterministic nonce derivation removes the RNG dependence and is the safest prose-compliant choice. | PS3 key recovered 2010; RFC 6979 | [FIPS 186-5](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.186-5.pdf), [RFC 6979](https://datatracker.ietf.org/doc/html/rfc6979) | 2023-02 | High |
| 2.13 | Curves P-256/P-384 are specified in [SP 800-186](https://csrc.nist.gov/pubs/sp/800/186/final) with their primes; WebCrypto's ECDH/ECDSA accept `P-256`, `P-384`, `P-521` only. ECDSA in FIPS 186-5 additionally requires checking public keys on-curve and rejects non-canonical points. | 3 named curves in WebCrypto | [SP 800-186](https://csrc.nist.gov/pubs/sp/800/186/final) | 2023-02 | High |
| 2.14 | ECDH is [SP 800-56A](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-56Ar3.pdf) Rev 3: public keys must be validated (on-curve, correct order/cofactor) and the small-subgroup attack (a peer-supplied point of low order leaking key bits) is the canonical ECDH failure; static ECDH additionally needs key-confirmation. WebCrypto's `deriveBits` gives raw x-coordinates, so callers must KDF — `deriveKey` with HKDF/AES-KW does it in-spec. | public-key validation mandatory | [SP 800-56A R3](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-56Ar3.pdf) | 2018-04 | High |
| 2.15 | X25519/X448 are [RFC 7748](https://datatracker.ietf.org/doc/html/rfc7748). Section 6 requires implementations to **check for the all-zero shared secret** (result of an attacker-supplied low-order point) and abort; skipping the check silently accepts a hostile public key. X25519 also mandates clamping of the scalar, so key generation is canonical by construction. | all-zero output → abort; clamping mandatory | [RFC 7748 §6](https://datatracker.ietf.org/doc/html/rfc7748#section-6) | 2016-01 | High |
| 2.16 | Ed25519/Ed448 are [RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032). Hazards in prose: signatures are deterministic, but **malleability via non-canonical encodings** is real — verifiers must reject non-canonical point encodings and out-of-range scalars, or signatures can be forged/replicated. RFC 8032's test vectors cover exactly these. | canonical encodings mandatory on verify | [RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032) | 2016-01 | High |
| 2.17 | ChaCha20-Poly1305 is [RFC 8439](https://datatracker.ietf.org/doc/html/rfc8439), with full test vectors in the RFC. Needed by Izcal regardless of the WebCrypto decision because TLS 1.3 depends on it; the AEAD construction reuses the ChaCha block function so one primitive serves stream + MAC. | vectors in RFC §2.3.2, §2.5.2, A-C | [RFC 8439](https://datatracker.ietf.org/doc/html/rfc8439) | 2018-06 | High |

**Implications:** every primitive above is specified completely enough in prose (plus its RFC/SP test vectors) for a from-scratch implementation with no code reference — the harder problems are behavioral: indistinguishable RSA/CBC failure paths, GCM nonce discipline enforced in API design rather than documentation, mandatory point validation and canonical-encoding checks, and policy floors (PBKDF2 iterations, GCM tag length) that the prose leaves to the implementer.

## 3. Post-quantum: FIPS 203/204, SP 800-227, and TLS hybrids

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | [FIPS 203 ML-KEM](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf) was published 2024-08-13 as the KEM standard, built on the CRYSTALS-Kyber submission (Module-LWE). It is also the first algorithm in scope for FIPS 140-3 modules, so Izcal's implementation shape should anticipate the FIPS 140-3 module boundary (approved-mode boundaries, self-tests) even if never validated. | published 2024-08-13 | [FIPS 203](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf) | 2024-08-13 | High |
| 3.2 | Parameter sets and sizes (encapsulation key / ciphertext / shared secret), per FIPS 203: ML-KEM-512: 800 / 768 / 32 B; ML-KEM-768: 1184 / 1088 / 32 B; ML-KEM-1024: 1568 / 1568 / 32 B. Shared secret is always 32 bytes. | 3 param sets | [FIPS 203](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf) | 2024-08-13 | High |
| 3.3 | Decapsulation must never fail observably: FIPS 203 uses the **implicit rejection** scheme — on decapsulation failure, output a pseudorandom secret derived from the decapsulation key, indistinguishable from success. This is the FO-transform hazard: implementations that return distinct errors create a chosen-ciphertext oracle (the same class as Bleichenbacher for RSA). The Fujisaki-Okamoto transform in the prose is what makes IND-CCA hold; any deviation breaks the proof. | implicit rejection, no error path | [FIPS 203 §7.3](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf) | 2024-08-13 | High |
| 3.4 | [FIPS 204 ML-DSA](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.204.pdf) (Module-Lattice Signature, from Dilithium) published the same day; three sets (ML-DSA-44/65/87). WebCrypto ML-DSA remains unstandardized as of 2026-10 (same status as ML-KEM, §1.10). | 3 param sets | [FIPS 204](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.204.pdf) | 2024-08-13 | High |
| 3.5 | [SP 800-227](https://csrc.nist.gov/pubs/sp/800/227/final), *Recommendations for Key-Encapsulation Mechanisms*, is final (published 2025-09-18; draft 2025-01-07). It is the governing prose for how a KEM should be *used*: encapsulation-key validation, shared-secret handling (never use raw as a key, always KDF), and the same implicit-rejection discipline. Izcal should treat SP 800-227, not FIPS 203 alone, as the usage rulebook. | final 2025-09-18 | [SP 800-227](https://csrc.nist.gov/pubs/sp/800/227/final) | 2025-09-18 | High |
| 3.6 | The IETF TLS hybrid is [RFC 10024](https://datatracker.ietf.org/doc/html/rfc10024), *Post-Quantum Traditional (PQ/T) Hybrid Key Agreement for TLS 1.3* (published 2026-08, from draft-ietf-tls-ecdhe-mlkem). It defines X25519MLKEM768 (code point 4588, "Recommended: Y"), SecP256r1MLKEM768 (4587, for FIPS-only stacks), SecP384r1MLKEM1024 (4589), and obsoletes the experimental X25519Kyber768Draft00/SecP256r1Kyber768Draft00 code points. | 3 hybrids; cp 4587–4589 | [RFC 10024](https://datatracker.ietf.org/doc/html/rfc10024), [datatracker history](https://datatracker.ietf.org/doc/draft-ietf-tls-ecdhe-mlkem/) | 2026-08 | High |
| 3.7 | Engine deployment of X25519MLKEM768 in TLS was live well before the RFC (Chrome enabled it by default in 2024; Firefox and Safari followed through 2025), which means the *interop-tested* shape of ML-KEM on the web is the TLS handshake, not an exposed key API — browsers ship ML-KEM as a TLS-internal primitive, not via SubtleCrypto. | TLS-internal only, engine-side | [Cloudflare Radar PQ](https://radar.cloudflare.com/adoption-and-usage#post-quantum-cryptography), [Chrome PQ](https://blog.chromium.org/2024/04/updates-to-post-quantum.html) | 2026 | Medium |

**Implications:** if Izcal exposes any PQ surface beyond TLS, the prose base is complete (FIPS 203 + SP 800-227 + RFC 10024 all final), so a first-principles `hg-crypto` ML-KEM is feasible — but the API-design lesson is the whole point of the standard: decapsulation has no error path, and any Izcal extension that leaks one re-creates the Bleichenbacher class in a new algorithm. Web parity (no PQ in SubtleCrypto anywhere) means Izcal can phase PQ extension work after the core registry without breaking web compatibility.

## 4. Key formats and interop

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | WebCrypto's four export formats imply a real parsing surface: `raw` (opaque octets), `spki` and `pkcs8` (ASN.1 **DER** subsets: SubjectPublicKeyInfo per [RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280), PrivateKeyInfo per [RFC 5958](https://datatracker.ietf.org/doc/html/rfc5958) / [RFC 5208](https://datatracker.ietf.org/doc/html/rfc5208)), and `jwk` (RFC 7517/7518 with base64url). Izcal therefore needs a DER reader/writer for the SPKI/PKCS8 subset regardless of the crypto core. | 2 DER formats, 1 JSON, 1 raw | [W3C §JSONWebKey](https://w3c.github.io/webcrypto/#JsonWebKey-dictionary) | 2024 | High |
| 4.2 | JWK is base64url **without padding** ([RFC 7515 §2](https://datatracker.ietf.org/doc/html/rfc7515#section-2)); accepting padded base64, or emitting padded, is a classic interop break. RSA JWKs additionally carry five big integers whose DER-side DER-encoding must be unsigned (leading zero byte) — negative/mis-encoded INTEGERs are the historical ASN.1 failure. | base64url unpadded | [RFC 7515](https://datatracker.ietf.org/doc/html/rfc7515) | 2015-05 | High |
| 4.3 | The known JWK hazard class is `key_ops`/`use` mismatches against `extractable`/`usages`: the spec requires the imported JWK's `key_ops` to be consistent with the `usages` argument or import fails (`DataError`). Implementations that ignore the check, or disagree on whether `key_ops` may be absent, broke cross-engine round-trips. Izcal should enforce the spec's consistency rule and fuzz it. | DataError on mismatch | [W3C §importKey jwk steps](https://w3c.github.io/webcrypto/#SubtleCrypto-methods) | 2024 | Medium |
| 4.4 | `usages`/`extractable` checking on import is per-algorithm: e.g. an AES-GCM key cannot carry `deriveKey`; an ECDH private key cannot carry `sign`. Real-world bugs (keys imported with broader usages than permitted) have been engine bugs, not spec gaps — the prose table is the authority Izcal should encode as data, not code. | per-algo usage tables | [W3C §algorithm-specific usages](https://w3c.github.io/webcrypto/#algorithm-overview) | 2024 | High |
| 4.5 | DER safety is an attack surface, not just interop: hand-rolled BER/DER parsers are a CVE factory (length overflows, indefinite-length confusion, OID smuggling). Izcal restricts to the strict DER subset — definite lengths, no indefinite form, canonical encodings — and rejects everything else, which is exactly what SPKI/PKCS8 produced by real tooling contains. | DER subset only | [RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280), [BER/DER rules](https://www.itu.int/ITU-T/studygroups/com17/languages/X.690.pdf) | 2024 | High |

**Implications:** the format layer is where WebCrypto implementations break compat, not the math: a strict unpadded-base64url, strict-DER, spec-literal `key_ops`/`usages` enforcement will round-trip with all major engines, and Izcal should fuzz exactly the boundary cases the spec makes errors (mismatched `key_ops`, non-canonical integers, padded base64).

| 5.1 | NIST [ACVP](https://pages.nist.gov/ACVP/draft-fussnell-acvp-protocol.html) (Automated Cryptographic Validation Protocol) is the current vector-and-validation program; the older [CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program) is the legacy validation program whose vectors are frozen and whose coverage lacks modern primitives (no X25519/Ed25519/ML-KEM-era coverage parity). | 5.2 | [Project Wycheproof](https://github.com/C2SP/wycheproof) (now under [C2SP](https://c2sp.org/)) is the attack-vector corpus: invalid-curve points, small subgroups, Bleichenbacher-style error oracles, malleable/non-canonical Ed25519 signatures, ASN.1 edge cases. It exists precisely because spec-conforming vectors never test the failure paths — Izcal should run Wycheproof as a gate for ECDSA/ECDH/X25519/Ed25519/RSA import. | attack-case vectors, not interop | [Wycheproof](https://github.com/C2SP/wycheproof) | 2024 | High |
| 5.3 | RFC-embedded vectors are the primary ground truth for the newer primitives: RFC 5869 (HKDF), RFC 7748 (X25519/X448), RFC 8032 (Ed25519), RFC 8439 (ChaCha20-Poly1305), RFC 6979 (deterministic ECDSA). These cover the happy path plus (in 7748/8032) some invalid-input cases; they are free to embed in a test suite without external infrastructure. | 5 RFCs with vectors | [RFC 8439](https://datatracker.ietf.org/doc/html/rfc8439) et al. | 2018 | High |
| 5.4 | FIPS 203/204 ship with a small number of official KATs (ML-KEM: one KAT per parameter set in the FIPS appendices); the exhaustive vector sets are distributed via ACVP. For deterministic-reproducibility testing of the FO transform (implicit rejection determinism), ACVP's ML-KEM decapsulation-fail cases are the reference. | KATs in FIPS; bulk via ACVP | [FIPS 203](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf), [ACVP](https://pages.nist.gov/ACVP/) | 2025 | Medium |

**Implications:** the vector base is layered: RFC vectors in-tree for the modern primitives, FIPS/SP KATs for NIST algorithms, ACVP for exhaustive NIST coverage, Wycheproof for the failure paths. A from-scratch implementation is only as good as its worst failure path, so Wycheproof and ACVP decapsulation/negative cases carry the same weight as the happy-path KATs.
