# Izcal WebCrypto: security and robustness

Compiled 2026-10-20. Primary sources were preferred (papers, specifications, maintainers' posts, release notes, issue trackers). No third-party source code was read or cited; every finding is anchored to published papers, standards prose, project documentation, or vendor advisories. Two brief claims in the strand assignment were corrected against sources and are flagged where they occur (Breitner–Heninger 2018/2019 is a nonce-bias study, not remote timing; the 2024 ECDSA timing advisory is wolfSSL, not the wolfSSH DoS CVE).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

Izcal implements every primitive itself, from the specifications' prose only (M-1). This note is the evidence base for doing that **safely**: which operations leak secrets through timing, what the constant-time discipline requires, what verification tooling can actually prove, what shipped-software failures cost, and what a browser-specific threat model adds.

## 1. Timing side channels: the evidence line

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **Kocher 1996** founded the field: RSA, Diffie-Hellman and DSS leak the key through operation timing (modular-multiply time varies with key bits); the attack needs only timing measurements, no physical access. Every later result below is this attack, made more remote or more precise. | applies to RSA, DH, DSS | [Timing Attacks on Implementations of DH, RSA, DSS, and Other Systems](https://www.cryptography.com/resources/whitepapers/TimingAttacks.pdf), CRYPTO '96 | 1996-08 | High |
| 1.2 | **Bleichenbacher 1998** turned RSA PKCS #1 v1.5 decryption into a chosen-ciphertext oracle: a TLS server that answers differently for valid vs invalid padding lets an attacker decrypt ciphertexts with on the order of a million queries. **Manger 2001** showed the same class survives OAEP via a length-check branch. The class is a *failure-path* design flaw, not an arithmetic leak — it survives in new code whenever decrypt returns distinguishable errors. | ~2^20 chosen ciphertexts (1024-bit RSA) | [Bleichenbacher, CRYPTO '98](https://link.springer.com/chapter/10.1007/3-540-68697-5_9); [Manger, CRYPTO 2001](https://www.iacr.org/archive/crypto2001/21390229.pdf) | 1998-08 / 2001-08 | High |
| 1.3 | **Brumley–Boneh 2003**: the timing attack works *over a network*, against OpenSSL+Apache on ordinary servers, by exploiting CRT-based RSA (different timing for the two halves of the private exponent) — the same variant Kocher anticipated. "Remote" stopped being a mitigation in 2003. | LAN attack on stock OpenSSL/Apache | [Remote Timing Attacks are Practical](https://crypto.stanford.edu/~dabo/papers/ssl-timing.pdf), USENIX Security 2003 | 2003-08 | High |
| 1.4 | **Brumley–Tuveri 2011**: eight years later, remote ECDSA key recovery from OpenSSL's TLS-DHE, via timing of the Montgomery ladder on the scalar — the *scalar is secret* and the ladder leaked it. Confirms elliptic-curve scalar multiplication belongs to the secret-dependent class, not just RSA. | remote ECDSA key recovery, disclosed 2011-05 | [Remote Timing Attacks Are Still Practical](https://eprint.iacr.org/2011/232), ESORICS 2011 | 2011-09 | High |
| 1.5 | **Lucky13 (2013)**: TLS-CBC's decryption path leaks through the time difference between padding check and MAC check (~2^13 sessions per recovered 16-byte block by the paper's estimate). Decryption *error paths* are timing channels even when the arithmetic is constant-time. | ~2^13 TLS sessions/block (paper estimate) | [AlFardan–Paterson, USENIX Security '13](https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/lucky13) | 2013-08 | Medium |
| 1.6 | **Cache timing on AES**: Bernstein's 2005 remote cache-timing attack showed software AES's table lookups (indices derived from key+data) leak across a network; Osvik, Shamir and Tromer demonstrated local extraction the same year. This is why AES table-lookup implementations are in the secret-dependent class and AES-NI is not. | remote AES key extraction | [Bernstein, Cache-timing attacks on AES](https://cr.yp.to/antiforgery/cachetiming-20050414.pdf) | 2005-04-14 | High |
| 1.7 | **Breitner–Heninger** (assignment listed as "stronger remote timing" — corrected): the actual paper is *Biased Nonce Sense*, lattice attacks recovering ECDSA private keys from **biased nonces** at scale across cryptocurrencies. Relevance here: the nonce is the most fragile secret in ECDSA; any bias (RNG, side channel, deliberate determinism) is directly fatal. | hundreds of weak-key recoveries across chains | [Biased Nonce Sense, eprint 2019/023](https://eprint.iacr.org/2019/023) | 2019-01 | Medium |
| 1.8 | **Secret-dependence classification** for WebCrypto, from the attack targets above: secret-dependent = RSA private-key operations (decrypt, sign), ECDSA signing (scalar + nonce), ECDH/X25519 scalar multiplication, all modular/lattice **inversions on secret data**, PBKDF2's iterated hash over a secret password, and ML-KEM **decapsulation** (ciphertext processed under the secret key). Public-data = SHA-2/HMAC/HKDF-core arithmetic, ChaCha20-Poly1305 (ARX), AES **with AES-NI**, and every verify/encrypt-with-public-key operation. Full per-operation table at the end of this note. | — | derivation from 1.1–1.7 | 2026-10-20 | High |

**Implications:** Izcal's line is sharp: anything that touches a private key, a shared secret, a nonce or a password must be constant-time with a single indistinguishable failure path; everything else needs only correctness. The failure-path class (1.2, 1.5) is not fixed by constant-time arithmetic — it is fixed by API design, which is under Izcal's control (`OperationError` and nothing else on every decrypt/decap path).

## 2. Constant-time discipline and its verification

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | The **constant-time discipline**, as stated across the tooling literature: no secret-dependent **branches**, no secret-dependent **memory indices** (table lookups), no secret-dependent **division** or variable-time arithmetic; data flow through secret values must be independent of control flow and addressing. Division is included because hardware dividers' latency varies. | 3 forbidden constructs | [dudect (defines and tests the discipline)](https://eprint.iacr.org/2016/635) | 2016-07 | High |
| 2.2 | **ctgrind** (Langley): reuse Valgrind's undefined-value taint tracking — annotate secret inputs as "undefined", then any secret-dependent branch or memory index is reported like an uninitialized-memory read. A *binary-level taint check* runnable in CI; its published weakness is that known-constant values need manual annotation to avoid noise. | binary-level; valgrind-based | [ctgrind (imperialviolet)](https://www.imperialviolet.org/2010/04/01/ctgrind.html) | 2010-04-01 | High |
| 2.3 | **dudect**: statistical two-population test — run the function with fixed vs random secrets, apply **Welch's t-test** to the timing distributions; leakage if the t-statistic passes the conventional threshold. Works on real hardware, catches leaks taint-checking misses (e.g. early-exit loops too large for valgrind to model), but is a *qualitative* test: passing it is not a proof, and it needs controlled measurement conditions. | Welch's t-test on fixed-vs-random secret populations | [dudect, eprint 2016/635](https://eprint.iacr.org/2016/635) | 2016-07 | High |
| 2.4 | **maskVerif** (Barthe–Belaïd) automated verification of **higher-order masking** countermeasures (splitting secrets into d+1 shares so d observations reveal nothing), covering physical defaults. This is the tool line for the (rarely needed in a browser) case where constant-time alone is insufficient and power/EM analysis matters; the browser threat model makes timing the relevant channel, so Izcal records masking as out of scope rather than adopting it. | automated, higher-order, public-key primitives | [maskVerif, TCHES 2018(1), eprint 2018/888](https://eprint.iacr.org/2018/888) | 2018-01 | Medium |
| 2.5 | **ct-wasm** (POPL 2019): a strict WebAssembly extension whose type system enforces constant-time (secret values tracked in types, verified in **linear time**), plus **speculative non-interference** — a formal property covering Spectre-class speculative leaks. Demonstrates that a language-level gate is feasible *inside a browser* — directly applicable to Izcal's own scripting layer and to what Izcal can promise web-exposed crypto code. | linear-time verification | [ct-wasm, POPL 2019 (arXiv:1808.01348)](https://arxiv.org/abs/1808.01348) | 2019-01 | High |
| 2.6 | **Fiat-Crypto** generates field arithmetic from Coq proof scripts with machine-checked proofs of correctness; the published account claims provable absence of timing leaks ("constant-time by construction") and downstream use by major libraries and browsers. Performance is competitive with hand-written code (published benchmarks put verified P-256 field multiplication in the same sub-microsecond range as OpenSSL/BoringSSL). | Coq-checked; generated C/asm | [Fiat-Crypto](https://github.com/mit-plv/fiat-crypto) (POPL 2018) | 2018-01 | Medium |
| 2.7 | **Fiat-Crypto's own README is a lesson in verification honesty**: the current prose states "We do not provide any quality guarantees for code generated by the backends" and that compiler integer-size behavior is unverified. I.e. the proof attaches to the intermediate representation, not to what gcc/clang emit — "verified at level N" needs a stated level. Izcal's spec should name its verification level explicitly. | guarantees stop at the backend boundary | [Fiat-Crypto README prose](https://github.com/mit-plv/fiat-crypto) (read 2026-10-20) | 2026-10-20 | High |
| 2.8 | **HACL\*/EverCrypt/Vale (Project Everest)**: HACL* proves correctness + **secret independence** in F* and compiles to C; Vale provides verified assembly; EverCrypt adds a provider with CPU-feature dispatch. Project prose claims deployment at internet scale: HACL* Curve25519 replaced NSS's assembly and shipped in **NSS 3.39 / Firefox 62 (2018-09)**, and verified Curve25519/Poly1305/ChaCha20 code entered the **Linux kernel** via WireGuard (merged 5.6, 2020-03). Proof that generated/verified constant-time crypto is deployable at browser scale, not a research toy. | Firefox 62+, kernel 5.6 | [Project Everest](https://project-everest.github.io/), [HACL*](https://github.com/hacl-star/hacl-star) | 2018-09 / 2020-03 | Medium |
| 2.9 | **TVLA** (Test Vector Leakage Assessment): the physical-side-channel methodology — fixed-vs-random populations, Welch's t-test, **threshold t > 4.5** — standardized from the DPA-Contest lineage into ISO/IEC 17825 (2024 revision carries it). Its published caveats are as important as the test: it is *qualitative* (non-leaky ≠ secure), and naive use yields **false positives** (non-Gaussian timing, unbalanced populations) and misses leaks below the fixed threshold. | threshold t = 4.5; ISO 17825 battery | [Goodwill et al., NIST workshop](https://csrc.nist.gov/csrc/media/events/non-invasive-attack-testing-workshop/documents/08_goodwill.pdf); [Standaert, "How (not) to use Welch's t-test"](https://eprint.iacr.org/2017/138); [Saarinen on ISO 17825](https://mjos.fi/doc/20220628-host22-wip-pqc-leakage.pdf) | 2011 / 2017 / 2022-06-28 | High / Medium |
| 2.10 | What a published-account **CI constant-time gate** looks like, assembled from the above: (a) *by construction* — generate or prove the hot arithmetic (2.6–2.8); (b) *taint gate* — ctgrind-style valgrind run per PR with secrets annotated (2.2); (c) *statistical regression* — dudect/TVLA-style Welch test on representative hardware, treated as advisory because of false positives (2.3, 2.9). No single gate suffices: taint checks miss microarchitectural channels, statistics are qualitative, proofs stop at the compiler backend. | 3 complementary gates | derivation from 2.1–2.9 | 2026-10-20 | Medium |

**Implications:** Izcal should adopt all three gates, with roles: generated/verified arithmetic for the secret-dependent core (field ops, ladders — the Everest result shows this is deployable and fast), a valgrind taint gate as the cheap per-commit check, and Welch-based timing tests as periodic hardware-in-the-loop regression. Every gate's promise must be stated at its honest level (proof at the IR, binary taint, or qualitative statistics) — 2.7 is the cautionary prose.

## 3. Failure postmortems in shipped software

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Heartbleed (2014)**: not a crypto-math failure — a memory-safety failure in OpenSSL's heartbeat handler leaked up to **64 KB of process memory per request**, including private keys and session tickets, unlogged. A hand-managed C buffer bug in the most-audited library on the internet. Izcal's lesson is language-level: the crypto core should be in a memory-safe implementation or generated code, not hand-managed buffers. | 64 KB/request; undisclosed reads | [heartbleed.com](https://heartbleed.com) | 2014-04-07 | High |
| 3.2 | **Debian OpenSSL PRNG (2008)**: a well-meant patch removing reliance on uninitialized memory gutted entropy seeding; the PRNG drew from the **PID alone** (~2^15 possible keys per architecture) for almost two years (introduced 2006-09). Every key generated on Debian/Ubuntu in that window was enumerable. Lesson: entropy handling is load-bearing and fragile; changes to it need adversarial review and KAT-style self-tests at startup. | ~32,767 distinct keys/architecture | [Debian Security Advisory DSA-1571-1](https://www.debian.org/security/2008/dsa-1571) | 2008-05-13 | High |
| 3.3 | **Sony PS3 (2010)**: the console's firmware signing used ECDSA with a **constant nonce k**; given two signatures with the same k, the private signing key is high-school algebra — recovered publicly at 27C3, destroying the platform's code-signing trust root. The nonce is not a "minor parameter": 3.7 shows biased nonces fell at scale a decade later. | constant k → key recovered | [BBC report](https://www.bbc.com/news/technology-12116051) | 2010-12-29 | High |
| 3.4 | **ROCA (2017)**: Infineon's RSALib generated primes with a detectable structure visible in the public key, enabling **Coppersmith** factorization orders of magnitude below expected cost (512-bit keys factored in hours; national eID card populations — e.g. Estonia's — had to be reissued). A vendor's optimized-but-structured key generator shipped for years inside smartcards. "Optimized proprietary arithmetic" is itself a risk factor. | 512-bit factorable in ~2 CPU-h; Estonia eIDs reissued | [ROCA, CROCS/CCS 2017](https://crocs.fi.muni.cz/public/papers/rsa_ccs17) | 2017-10 | Medium |
| 3.5 | **PuTTY CVE-2024-31497 (2024)**: biased ECDSA nonces on **NIST P-521** in PuTTY 0.68–0.80 recovered the host/user key from roughly **60 signatures** — 14 years after the PS3, the same failure class, in a mature 25-year-old codebase, from a key-storage refactor that biased nonce generation. Fixed in 0.81. | ~60 signatures → P-521 key | [PuTTY advisory vuln-p521-bias](https://www.chiark.greenend.org.uk/~sgtatham/putty/wishlist/vuln-p521-bias.html), [NVD](https://nvd.nist.gov/vuln/detail/cve-2024-31497) | 2024-03 | High |
| 3.6 | **wolfSSL pre-5.6.6**: the vendor's own security page documents a "potential ECDSA nonce side channel attack" in `wc_ecc_sign_hash` before 5.6.6. (Assignment's "wolfSSH CVE-2024-0901" corrected: that CVE is a remote DoS/crash bug, not a timing channel.) Shipping timing/nonce bugs in 2023-2024 are routine, not exotic. | fixed in 5.6.6 | [wolfSSL security vulnerabilities](https://www.wolfssl.com/docs/security-vulnerabilities) | 2023-11 | Medium |
| 3.7 | **ROBOT (2017-12)**: the Bleichenbacher oracle class was found still exploitable in several major TLS stacks ~20 years after the 1998 paper — failure-path design flaws persist across generations of rewrites because each rewrite re-introduces distinguishable error handling. | oracle class live in major stacks | [robotattack.org](https://robotattack.org/) | 2017-12 | High |
| 3.8 | **Meta-lesson from 3.1–3.7**: every case was *hand-rolled or hand-modified* code escaping review, and every case would have been caught by one of: an independent audit, the standard negative test vectors (Wycheproof-class), or generated/verified arithmetic. None would have been caught by more careful conventional testing alone. | — | synthesis of 3.1–3.7 | 2026-10-20 | High |

**Implications:** Izcal's mitigations map 1:1 to the failures: memory safety at the language level (Heartbleed), adversarial review + startup self-tests for entropy (Debian), RFC 6979 deterministic nonces so no RNG can bias them (PS3, PuTTY, wolfSSL), no proprietary shortcuts in arithmetic (ROCA), and a single indistinguishable failure path (ROBOT/Bleichenbacher). All five are spec-checkable requirements, not aspirations.

## 4. Browser-specific threat model

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | WebCrypto key material — including `extractable: false` keys — lives in **renderer-process memory**. "Non-extractable" is an API-level restriction (no export through SubtleCrypto), not a protection boundary: the W3C issue tracker records that WebCrypto has **no standardized access to secure hardware**, in contrast to WebAuthn, and an attacker who compromises the renderer can call the key's usages regardless. | no hardware access in WebCrypto | [W3C webcrypto issue #263](https://github.com/w3c/webcrypto/issues/263); [CryptoKey.extractable](https://developer.mozilla.org/en-US/docs/Web/API/CryptoKey/extractable) | 2026-10-20 (read) | High |
| 4.2 | The published contrast boundary is the **platform authenticator** (WebAuthn): credentials are generated and held by the authenticator (TPM/Secure Enclave/security key) and are not exposed to the web platform's process — the spec's client/authenticator split is the boundary WebCrypto lacks. A renderer compromise cannot read a hardware-bound passkey's private material; it can always read a WebCrypto key's use. | credentials held outside the web process | [W3C WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/) | 2023-03 | Medium |
| 4.3 | **Spectre-class attacks make renderer memory readable by web-authored code**: Project Zero's 2018 disclosure included a JavaScript proof of concept reading process memory from a browser tab; the paper's authors note such attacks cross process boundaries. In-process secrets (4.1) are therefore not merely "unprotected from the renderer" — they are potentially readable from a malicious *page* under the right conditions. | JS PoC, 2018-01-03 disclosure | [Project Zero: Reading privileged memory with a side-channel](https://googleprojectzero.blogspot.com/2018/01/reading-privileged-memory-with-sidechannel.html); [Spectre](https://spectreattack.com/spectre.pdf) | 2018-01 | High |
| 4.4 | The shipped mitigation is **site isolation**: one process per site, so a site's attacker does not share an address space (or hardware cache footprint) with other sites' data or the browser's own secrets. Chromium's security prose presents this as the response to Spectre-class leakage; its known cost is memory. Where isolation collapses (shared processes), cross-site cache attacks are the documented fallback risk. | process-per-site | [Chromium Site Isolation](https://www.chromium.org/Home/chromium-security/site-isolation/) | 2026-10-20 (read) | High |
| 4.5 | The research frontier confirms the threat is not closed: **ct-wasm** defines speculative non-interference (4 §2.5 above), and the follow-up *Weakening WebAssembly* documents **speculative read gadgets** practical in shipped wasm engines — i.e. the languages web crypto runs in needed new guarantees, and engines needed to adopt them. | speculative gadgets in wasm engines | [Weakening WebAssembly, OSDI '19 (author PDF)](https://people.mpi-sws.org/~rossberg/papers/Watt,%20Rossberg,%20Pichon-Pharabod%20-%20Weakening%20WebAssembly%20%5BExtended%5D.pdf) | 2019-10 | Medium |
| 4.6 | **Out-of-process crypto — both published sides.** For moving crypto out of the renderer: key material never enters a content-compromised address space (4.1, 4.3) and engine practice has moved TLS crypto out of content processes in both major engines (Chrome's network-service split; Firefox's NSS in the parent) — [Low: secondary knowledge, not re-verified today]. Against it: WebCrypto's hot paths (AES-GCM over large payloads, PBKDF2) would pay IPC serialization per call, a cost engines have historically refused for same-process operations. This is an Izcal measurement question (M0-style), not a settled literature question. | IPC cost vs address-space isolation | [Chromium Site Isolation](https://www.chromium.org/Home/chromium-security/site-isolation/) (pro), engineering cost [Low] (contra) | 2026-10-20 | Low |
| 4.7 | **The browser adds a threat model that standalone libraries never have**: the *caller* (web page) is potentially hostile and co-resident with the implementation, secrets are reachable from interpreted code, and the process boundary is the only hard line. Constant-time discipline (§2) addresses the timing channel; site isolation addresses the address-space channel; nothing except out-of-process design or hardware addressing the *key is in the compromised process* problem. | caller-hostile architecture | synthesis of 4.1–4.6 | 2026-10-20 | High |

**Implications:** Izcal should (a) treat renderer compromise as the default threat and document that non-extractable WebCrypto keys are convenience, not protection, (b) keep the WebAuthn/platform-keystore boundary as the actual answer for high-value credentials rather than trying to make WebCrypto hardware-backed (no such surface exists in the platform), and (c) schedule an explicit measurement milestone for out-of-process crypto IPC cost before deciding placement — 4.6 is the one open architecture question in this note.

FIPS 140-3 is explicitly out of scope with the reasons recorded (5.6).

## 6. Recording and determinism

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **rr** (Mozilla-origin record-replay debugger) states its model in one line: it "records nondeterministic executions and debugs them deterministically" — nondeterministic *inputs* (syscall results, signals, scheduling) are captured during recording so replay reproduces the execution exactly, including the results of entropy syscalls. This is the OS-level precedent for Izcal's recording design. | record inputs → deterministic replay | [rr wiki](https://github.com/rr-debugger/rr/wiki) (read 2026-10-20) | 2026-10-20 | High |
| 6.2 | The WebCrypto surface Izcal must treat the same way: the W3C spec's `crypto.getRandomValues` is defined over a **CSPRNG with no seed API and no deterministic mode** — there is no standard way to pin it, so a recording engine must supply recorded entropy *outputs* rather than configure the generator. | no seed API in the platform | [W3C WebCrypto §Crypto interface](https://w3c.github.io/webcrypto/#crypto-interface) | 2026-10-20 (read) | High |
| 6.3 | **The observable contract**: any page can branch on `crypto.getRandomValues` bytes, so replay divergence is *web-visible* the first time a replayed page draws randomness that differs from the recording. Deterministic replay therefore requires recording and replaying the **API-visible outputs** (returned bytes, and entropy draws feeding key generation, nonces and IVs) — the rr model applied at the WebCrypto boundary. | divergence is page-visible | derivation from 6.1–6.2 | 2026-10-20 | Medium |
| 6.4 | **The security inversion**: a recording that stores raw entropy draws is a **key-recovery archive** — every WebCrypto key, ECDSA nonce and AES IV generated in the recorded session is derivable from them (the §1.7/§3.3 nonce lesson, replayed). Two safe shapes exist: record *outputs only* (ciphertexts, signatures, returned random bytes — no seed material), or store draws under the same access control as key material. Izcal's rule: never write generator state or raw draws into a replay archive in plaintext. | draws → all session keys recoverable | derivation from 1.7, 3.3, 6.1 | 2026-10-20 | Medium |

**Implications:** recording must sit *above* the entropy source, capturing what the page observed — never the entropy pool itself — and the replay archive inherits key-material handling (access control, redaction tools). This is the same discipline rr applies to syscall entropy, lifted one layer: Izcal records the *web-observable* crypto outputs so replay reproduces page-visible behavior without re-deriving any secret.

## Consolidated: operation → secret dependence → discipline → verification

| Operation | Secret-dependent? | Required discipline | Verification method |
|---|---|---|---|
| SHA-2 digest (SHA-1/256/384/512) | No (public data; pure arithmetic) | Standard correctness only | FIPS 180-4 / ACVP KATs |
| HMAC sign/verify | Key secret; SHA core is constant-time by construction | Constant-time **comparison** on verify; no other special handling | ACVP KATs |
| HKDF extract/expand | IKM may be secret; core constant-time by construction | No branches on derived material | RFC 5869 vectors |
| PBKDF2 | Yes (password secret, 10^5–10^6 iterations) | Constant-time hash core; public iteration count only | ACVP; timing regression (dudect) |
| AES-CBC/CTR/GCM/KW, **software table lookup** | Yes (table indices from key+data) | Bitsliced/constant-time implementation or forbid table variant | ctgrind taint gate; timing test |
