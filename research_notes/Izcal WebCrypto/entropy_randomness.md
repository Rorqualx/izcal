# Izcal WebCrypto: entropy and randomness

Compiled 2026-10-20. Primary sources were preferred (manual pages, kernel and platform documentation prose, NIST publications, W3C/ECMA specifications, papers, maintainer posts). No third-party source code was read or cited; a few facts are only ascertainable from source, marked † and graded Low.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

`crypto.getRandomValues` and `crypto.randomUUID` are the two draws on the platform's randomness that a browser must serve. Everything else in WebCrypto consumes randomness internally (key generation, IVs, nonces), so the entropy story is a whole-engine concern, not a single API. This note maps the OS interfaces per platform as of 2026, the kernel entropy history behind them, the NIST construction they correspond to, and what record-replay must do with randomness.

**Implications:** every target platform in 2026 has one documented, non-blocking, fd-free userspace interface — getrandom(2) (Linux), SecRandomCopyBytes/CCRandomGenerateBytes (Apple), ProcessPrng (Windows), arc4random_buf (BSD) — and Izcal should define one internal draw-point per process that calls exactly that interface, so the DRBG seam is testable and recordable. Nothing should read /dev/urandom directly on Linux (legacy, 32 MB cap, fd lifetime hazards) or RtlGenRandom on Windows (documented as superseded).

## 2. The Linux kernel entropy story

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Between Linux 4.8 and 5.6 the kernel's CSPRNG was switched to [ChaCha20](https://blogs.oracle.com/linux/post/rngd1), unifying the formerly separate blocking and non-blocking pools behind one generator; [LWN](https://lwn.net/Articles/686033/) covered the transition from per-pool SHA-1-era accounting to CRNG instances. | switch window 4.8–5.6 | [Oracle Linux blog: rngd](https://blogs.oracle.com/linux/post/rngd1) | 2021 | Medium |
| 2.2 | The [blocking pool was removed in 5.6](https://lwn.net/Articles/808575/): "reads from /dev/random behave like getrandom() with a flags value of zero (and turns the GRND_RANDOM flag into a noop)". Lutomirski's case: "Linux's CRNG generates output that is good enough to use even for key generation"; "the blocking pool is not stronger in any material way"; keeping it caused DoS (entropy starvation) and misuse. | Linux 5.6 (2020-03) | [LWN](https://lwn.net/Articles/808575/) | 2020-01 | Medium |
| 2.3 | Maintainer Ted Ts'o reversed his long-held position to accept the removal, arguing an honest kernel TRNG cannot be guaranteed across Linux's hardware variety — embedded systems where "everything is synchronized off of a single master oscillator" — and that a TRNG interface would leave developers blocked at boot: "systems will stop working and users will complain". This is the recorded reason the estimate-based blocking design died. | position reversal 2020-01 | [LWN](https://lwn.net/Articles/808575/) | 2020-01 | Medium |
| 2.4 | The "CRNG initialized" moment is the guarantee that matters: getrandom(2) "will block" until the urandom source is initialized; /dev/urandom may return pre-initialization data during early boot (documented under BUGS in random(4)). After initialization nothing blocks. Boot-time initialization was sped up partly by crediting [jitter entropy](https://blogs.oracle.com/linux/post/rngd1) (the jitterentropy_rng work), which is why Oracle still recommends running `rngd` on enterprise kernels. | 1 init moment; jitter entropy credited | [man-pages getrandom(2)](https://man7.org/linux/man-pages/man2/getrandom.2.html), [Oracle](https://blogs.oracle.com/linux/post/rngd1) | 2020/2021 | High/Medium |
| 2.5 | 5.18-era work [unified the random devices further](https://lwn.net/Articles/884875/) (LWN: "Uniting the Linux random-number devices", 2022-02), and Linux gained VMGenID-driven reseeding at ≥ 5.18 (see 5.2). riscv64: getrandom(2) is architecture-generic in the man page with no per-arch qualifiers; the [Zkr entropy-source extension](https://docs.riscv.org/reference/isa/v20260120/unpriv/scalar-crypto.html) is ratified (v1.0.1) with a `seed` CSR at 0x015 exposing "up to 16 physical entropy bits per read", M-mode by default, S/U-mode gated by `mseccfg`; mainline kernel use of Zkr is early (a 2024 KASLR-seeding proposal; no generic hw_random driver found in this pass) — kernel-side details are source-ascertainable †. | seed CSR 0x015; ≤16 bits/read | [RISC-V scalar crypto spec](https://docs.riscv.org/reference/isa/v20260120/unpriv/scalar-crypto.html), [LKML 2024 proposal](https://lists.openwall.net/linux-kernel/2024/06/01/256) | 2024-06 | Medium/Low |

**Implications:** a browser can assume: on any 2026 Linux (including riscv64), getrandom(2) blocks only until first initialization and never after; /dev/random is not a separate quality tier any more; and the hardware entropy story on riscv is still immature, so Izcal must not build anything that assumes fast first-boot entropy on embedded RISC-V — it should treat "getrandom blocks at startup" as a normal cold-start condition, not a hang.

## 3. NIST DRBG requirements and FIPS 140-3

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | [SP 800-90A Rev. 1](https://csrc.nist.gov/pubs/sp/800/90/a/r1/final) (2015-06-24) "specifies mechanisms for the generation of random bits using deterministic methods. The methods provided are based on either hash functions or block cipher algorithms." It defines Hash_DRBG, HMAC_DRBG and CTR_DRBG (the trio named in NIST-related literature; the landing page itself says only "hash functions or block cipher"). | 3.2 | Reseeding and prediction resistance are implementation policy inside 90A's constraints: the standard requires a DRBG to be reseeded within its declared seedlife and to support reseed on demand, but mandates no single interval — this is why Windows documents CTR_DRBG with Microsoft-chosen limits and Apple documents no interval at all. | 3.3 | [SP 800-90B](https://csrc.nist.gov/pubs/sp/800/90/b/final) (2018-01-10) covers the **entropy source**: "design principles and requirements for the entropy sources used in Random Bit Generators, and the tests" for validation — noise sources, conditioning, health tests, min-entropy estimation; its sources "are intended to be combined with Deterministic Random Bit Generator mechanisms" from 800-90A. | published 2018-01-10 | [NIST SP 800-90B](https://csrc.nist.gov/pubs/sp/800/90/b/final) | 2018-01-10 | High |
| 3.4 | [SP 800-90C](https://csrc.nist.gov/pubs/sp/800/90/c/final) (2025-09-25) gives the constructions: RBGs "that include DRBG mechanisms as specified in SP 800-90A" and "use entropy sources as specified in SP 800-90B", defining classes RBG1, RBG2, RBG3 and RBGC. | 3.5 | [FIPS 140-3](https://doi.org/10.6028/NIST.FIPS.140-3) (2019-03-22, supersedes 140-2) is scoped to cryptographic **modules** for federal use: "This standard shall be used in designing and implementing cryptographic modules that federal departments and agencies operate" — validated via CMVP against ISO/IEC 19790, in four levels. Nothing in it obliges a browser that makes no FIPS claim to use only validated entropy sources. | 4 levels; 2019-03-22 | [FIPS 140-3](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.140-3.pdf) | 2019-03-22 | High |
| 3.6 | What browsers actually promise is the WebCrypto spec's requirement, not FIPS: "Implementations should generate cryptographically strong random values using well-established cryptographic pseudo-random number generators seeded with high-quality entropy", with a note explaining the CSPRNG design: implementations avoid blocking or truly-random per-call sources "both for performance and to avoid depleting the system of entropy". MDN states the same: a PRNG "seeded with a value with enough entropy ... e.g. ... the Unix /dev/urandom device". Which specific DRBG each engine runs in userspace (seeded-from-OS vs direct OS bytes per call) is source-ascertainable † and not a documented contract. | seeded-from-OS pattern | [W3C WebCrypto §Crypto interface](https://w3c.github.io/webcrypto/#crypto-interface), [MDN getRandomValues](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues) | 2024 | High |

**Implications:** Izcal claims no FIPS compliance, so it is free to take the OS kernel CSPRNG as its entropy source and run its own userspace DRBG on top (the 800-90C shape, unvalidated). The design decision is per-draw semantics: seeding one process-lifetime DRBG from the OS is the documented-for-performance pattern the WebCrypto spec itself describes, while per-call OS draws are simpler but slower on every platform — this trade belongs in the spec with a measured cost, not assumed.

The 65536 cap is compat-mandated, not security-motivated; implement it exactly and say why in one sentence.

## 5. Failure modes and the fork/clone hazard

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 5.1 | The fork/clone hazard: nothing in the getrandom(2) man page promises distinct streams between a parent and a forked child — the documented guarantees cover blocking and partial reads only (checked). The vDSO design treats this as a first-class problem: vgetrandom state pages are mapped `VM_WIPEONFORK`, so "the state pages are zeroed in the child on fork, so a forked process gets fresh ... states rather than reusing the parent's key material — preventing two processes from emitting the same random stream". Linus Torvalds' original objection to the series was exactly this: a forked process periodically reseeded could duplicate random numbers. | VM_WIPEONFORK; syscall 463 | [LWN](https://lwn.net/Articles/978601/) | 2024 | Medium |
| 5.2 | VM snapshot/restore is the harder case: [Firecracker's documentation](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/random-for-clones.md) states "execution resumes precisely from the previously saved state", so all clones share RNG state; reads from /dev/random or /dev/urandom "does not lead to identical results for different clones" because timer and HWRNG noise are mixed in per read, but "it's not yet clear whether the noise ... is sufficient to consider their RNG states distinct". Guaranteed-identical: "All clones restored from the same snapshot will implicitly read the same value" from boot_id. Mitigations documented: VMGenID reseeding (kernels ≥ 5.18, with a race window between resume and reseed), explicit `RNDADDENTROPY` + `RNDRESEEDCRNG`, virtio-rng, and deleting `/var/lib/systemd/random-seed` before snapshotting. | VMGenID ≥ 5.18; 2 sysctl calls | [Firecracker: Random for clones](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/random-for-clones.md) | 2024 | Medium |
| 5.3 | The published paper record: [Everspaugh et al., "Not-So-Random Numbers in Virtualized Linux and the Whirlwind RNG"](https://rist.tech.cornell.edu/papers/vmrng.pdf) demonstrated that restoring VM snapshots yields repeated /dev/urandom output and identical RSA private keys across clones; the follow-up [Brooker et al., arXiv 2102.12892](https://arxiv.org/abs/2102.12892) frames the general problem — "cloning introduces the challenge of restoring the uniqueness of the VMs" for "UUIDs, secrets, and nonces" — and proposes `MADV_WIPEONSUSPEND` and `SysGenId`. Exact per-experiment counts are in the PDFs (the arXiv abstract page carries no numbers); grade for the headline claims is from abstract/snippet. | 2 proposed interfaces | [arXiv 2102.12892](https://arxiv.org/abs/2102.12892), [Whirlwind paper](https://rist.tech.cornell.edu/papers/vmrng.pdf) | 2021 | Medium |
| 5.4 | First-boot entropy was the other mass failure: [Heninger et al., "Mining Your Ps and Qs" (USENIX Security 2012, Best Paper)](https://www.usenix.org/conference/usenixsecurity12/technical-sessions/presentation/heninger) scanned ≈5.6 M TLS and ≈12.8 M SSH keys on network devices and found shared RSA prime factors (~0.5 % TLS, ~1 % SSH) and duplicated keys, caused by keys generated with insufficient entropy at first boot. Figures are from the paper's widely reproduced results (abstract text not captured in this pass); the scan scale and Best Paper award are confirmed on the landing page. | ≈5.6 M TLS / 12.8 M SSH keys; ~0.5 %/~1 % shared factors | [USENIX Sec 12 paper page](https://www.usenix.org/conference/usenixsecurity12/technical-sessions/presentation/heninger) | 2012-08 | Medium |
| 5.5 | Mitigation classes that survived into 2026 practice: (a) rely on kernel interfaces that are fork-aware (getrandom's initialization semantics, VM_WIPEONFORK vDSO state, arc4random's documented reseed "upon fork(2)"); (b) mix in clone/VM identity (VMGenID, new boot_id) before drawing; (c) never seed from time, PID or storage files as the sole source — the Debian-OpenSSL 2008 lesson (process-ID-only entropy) and the 2012 first-boot study are the recorded cost of that. Apps that fall back to Math.random or timestamp seeds in the browser break their own keys, not the browser's: getRandomValues has no failure mode that justifies a JS-side fallback. | 3 surviving mitigation classes | Darwin arc4random(3) (local man page), [Firecracker](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/random-for-clones.md), [Heninger et al.](https://www.usenix.org/conference/usenixsecurity12/technical-sessions/presentation/heninger) | 2012–2024 | High/Medium |

**Implications:** Izcal's renderer processes are created by fork or spawn from a common binary image — never by VM snapshot — so the classic identical-stream hazard does not arise in the normal path, and the kernel's fork-aware interfaces (getrandom, VM_WIPEONFORK) are the load-bearing safety. The residual hazard Izcal must design for explicitly is any future snapshot/restore feature (hibernation-like resume, checkpoint/restore of renderer processes): restore must count as re-seed-worthy, and the spec should require an explicit reseed event on restore, mirroring what VMGenID does for guests.

## 6. Determinism and recording

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | Record-replay at process level records **drawn values, never seeds**: [rr](https://rr-project.org/) "captures all inputs to those processes from the kernel, plus any nondeterministic CPU effects", and on replay "syscalls return the same data ... the addresses of objects don't change, register values are identical". The seed is never touched: the recorded getrandom return data *is* the randomness, and replaying it reproduces execution bit-for-bit. | inputs recorded; syscalls replayed | [rr-project.org](https://rr-project.org/) | 2024 | High |
| 6.2 | The vDSO complicates syscall-level recording on Linux: vDSO getrandom calls "will not appear in the trace output" of strace and are invisible to seccomp ([vdso(7)](https://man7.org/linux/man-pages/man7/vdso.7.html)), and glibc transparently uses the vDSO since November 2024. A browser-side recorder should therefore hook the draw-point inside the browser (where Izcal controls the call), not assume syscall visibility †. | 0 syscalls visible on vDSO path | [man-pages vdso(7)](https://man7.org/linux/man-pages/man7/vdso.7.html), [Phoronix](https://www.phoronix.com/news/glibc-getrandom-vDSO-Merged) | 2024-11 | High |
| 6.3 | Web-side tooling has no RNG determinism story: ECMA-262 defines no Math.random seed API and WebCrypto no deterministic mode (checked in both texts — High), and this pass found no documented DevTools/WebDriver capability to pin randomness; the practice that exists is userland monkey-patching of `Math.random`/`crypto.getRandomValues` via script injection (e.g. CDP `Page.addScriptToEvaluateOnNewDocument`) — secondary forum/blog evidence only (Low). rr's chaos mode perturbs scheduling to surface races but is not a randomness-seeding feature. | 0 documented browser knobs | [ECMA-262](https://tc39.es/ecma262/#sec-math.random), [W3C WebCrypto](https://w3c.github.io/webcrypto/#Crypto-interface), [rr](https://rr-project.org/) | 2026-10 | High/Low |
| 6.4 | Design rules for Izcal (first-principles, marked †): record the bytes each draw returned and replay them verbatim — never record or replay a seed; replay tools that "seed deterministically" change what the program observed and are not replay. Math.random is deterministic only if its seed is controlled, so replay must record its output too unless the engine is in a simulator mode. Security rule: **a shipping binary must never accept a caller-set CSPRNG seed** — seed injection is a simulator/testing-only build, compiled out of release, because a seedable CSPRNG is a downgrade oracle for every key generated in the process. | 2 recorded stream types; 0 seed APIs in release † | design derivation from [rr](https://rr-project.org/), [W3C WebCrypto](https://w3c.github.io/webcrypto/#Crypto-interface), [ECMA-262](https://tc39.es/ecma262/#sec-math.random) | 2026-10 | † (design) |

**Implications:** determinism is cheap if the seam is in the right place: one audited draw-point per process, recording at the WebCrypto/engine boundary (drawn bytes in, replayed bytes out), with no seed-taking path in release builds. This is also the answer to the vDSO blind spot — Izcal records what the page observed, not what the kernel returned, so the recorder survives interface changes underneath it.

## 7. Per-platform interface summary

| Platform | Best interface (2026) | Fallback | riscv64 note |
|---|---|---|---|
| Linux (desktop/server, glibc) | getrandom(2), ≤256 B draws until CRNG init confirmed; vDSO fast path via libc is a free optimization, never a contract | /dev/urandom read (legacy; avoid in new code) | getrandom(2) is architecture-generic; no riscv-specific differences documented in the man page |
| Linux riscv64 (embedded) | getrandom(2), blocking, with tolerant startup: first init may be slow where hardware entropy is thin (Zkr exists but kernel use is immature) | jitter-entropy-crediting kernels; virtio-rng where the VMM provides it | [Zkr](https://docs.riscv.org/reference/isa/v20260120/unpriv/scalar-crypto.html) seed CSR ratified (0x015, ≤16 bits/read, M-mode default) but not a usable userspace guarantee; treat boot delay as normal |
| macOS / iOS | [CCRandomGenerateBytes](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/2/getentropy.2.html) (CC_crypto) or SecRandomCopyBytes (Security framework) — the man page names both for "clients who simply require random data" | arc4random_buf (fork-reseeded, always successful); getentropy(2) for ≤256 B seeding only | n/a (Apple silicon is arm64; no riscv target) |
| Windows | [ProcessPrng](https://learn.microsoft.com/en-us/windows/win32/seccng/processprng) (documented, no failure return, Win 8+) | BCryptGenRandom with `BCRYPT_USE_SYSTEM_PREFERRED_RNG` (CTR_DRBG per SP 800-90) | n/a (riscv64 Windows is not a browser target in 2026) |
| BSDs | arc4random_buf (ChaCha20, fork-reseeded, cannot fail) | getentropy(2) ≤256 B | n/a |

**Open questions for the spec author:** (1) whether Izcal seeds one userspace DRBG per renderer or draws per call from the OS — needs a measured cost on all three platforms; (2) the exact reseed-on-restore rule for any future checkpoint feature; (3) whether Math.random gets per-page reseeding beyond the per-realm distinct-sequence floor — ECMA-262 does not require it, the fingerprinting guidance note describes randomization as a defense class, and no shipped engine does it today (Low).
