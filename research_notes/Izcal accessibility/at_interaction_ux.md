# Izcal accessibility: at_interaction_ux

Compiled 19 October 2026. Primary sources were preferred (WebAIM survey and Million pages, W3C specifications and Understanding documents, screen-reader vendor manuals, Apple, Microsoft and Android developer documentation, Chrome Platform Status entries, MDN browser-compat-data, CSSWG explainers and issues).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known fact not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no engine source code was read for this note. No code files, headers, commits, diffs, code-review pages or source browsers of Chromium, Gecko, WebKit, NVDA, Orca, AccessKit or Guidepup were opened. The NVDA User Guide (HTML prose), the MSEdgeExplainers caret-browsing explainer and the CSSWG `css-env-1` explainers (Markdown prose in repositories) were read as prose. GitHub API repository metadata (licence, description) was read for Guidepup, ARIA-AT and AT Driver repositories; no files in them were opened. Chrome Platform Status was read through its public JSON API (feature summaries and motivations, which are prose). MDN browser-compat-data 8.1.6 (2026-10-15, CC0) was read as version data. Where this note says what a browser or screen reader "does", it is user-facing behaviour from documentation, not a shape to copy.

Heading navigation, find-in-page and focus behaviour of menus/dialogs are what users exercise most, so they deserve conformance tests before rarer features.

**Implications:** Two architectures must both work: the Windows buffer readers (NVDA, JAWS) that pull the whole tree and expect in-process speed, and the live-document readers (Orca, VoiceOver, Narrator, mobile) that query on demand. AT-driven selection (3.5) and scroll-into-view must be broker→renderer commands.
