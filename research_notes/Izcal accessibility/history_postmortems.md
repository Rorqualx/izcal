**Implications:** Every OS API Izcal must serve is **synchronous and pull-based** at the client edge (UIA, IA2/MSAA, NSAccessibility, AT-SPI, Android). The design must answer pulls from a local copy in the broker. On Windows Izcal needs **both IA2 and UIA**: NVDA and JAWS still read web content through IA2, and NVDA 2026.2 still injects into the browser process to do so, so the broker must tolerate in-process AT code. On Linux, AT-SPI is mandatory today and Newton is a possible future push channel that fits a push-based core.

## 2. Browser accessibility architectures and their rewrites

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Single-process era:** ATs queried one tree, and Windows screen readers "often ran code in-process to build a 'virtual buffer'". **Implications:** Two of three engines (Chrome since about 2012, Firefox since 2023) converged on the same answer after costly detours: **renderers push incremental tree updates; the privileged process answers every OS query from its cache.** Izcal's site isolation and broker make this the only viable shape, and the Firefox data (128 s → 6 s) shows the size of the penalty for anything else. Izcal should design the cache, coordinate model (parent-relative bounds, separate scroll/transform), hit testing and the enable policy up front instead of discovering them in production. It must also avoid "accessibility on" being a global, expensive mode triggered by password managers.

## 6. What survived, and which assumptions no longer hold

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | **Survived:** MSAA's tree-of-objects model rooted at the desktop; IA2's web semantics on Windows (still preferred by NVDA in 2026); UIA's control patterns and TextPattern; AT-SPI's interfaces (only the transport changed); Chromium's AXNode/tree-update schema (copied by AccessKit and thus Servo, GTK, egui, Bevy). | — | rows 1.1–1.13, 4.3 | — | High |
| 6.2 | **Mismatch: single process.** MSAA, IA2 and in-process virtual buffers assume content lives in the process the AT can inject into. Sandboxing (2008+) and site isolation (2018+) broke this; every browser now needs a broker-side cache. | — | rows 2.1–2.2 | — | High |
| 6.3 | **Mismatch: synchronous pull across IPC.** Every OS API is pull; every modern engine is push internally. The cache is the adapter between the two. Async OS APIs are not coming soon. | 9 obstacles | rows 3.1–3.2 | 2025 | High |
| 6.4 | **Mismatch: "accessibility on" as one global switch.** Third-party software (password managers, antivirus) turns it on for 5–10% of desktop and ~7% of Android users; heuristics produce false positives (Linux 2020). Chrome's answer is graded modes (form-controls-only) and auto-disable on Android. | 5–10%; 7% | rows 2.7–2.10 | 2020–24 | High |
| 6.5 | **Mismatch: X11-era global coordinates.** AT-SPI assumed apps know global window positions; Wayland and Newton have no screen coordinates yet. | — | rows 1.17, 1.19 | 2023–24 | High |
| 6.6 | **Mismatch: web as second-class in OS APIs.** UIA lacks web roles, multiple labels, error-message relations and detailed live-region events; Microsoft is slow to extend it. | 7 gaps | row 1.26 | 2025 | High |

**Implications:** Izcal's semantic plane (HGBA-3 B8) is the right shape: a first-class, push-produced tree with stable IDs and incremental diffs is exactly what Chrome, Firefox, Servo and Newton converged on. What Izcal must add is what the others bolted on late or still lack: per-frame grafting with site-isolated iframes from day one, graded activation instead of a global switch, deterministic announcement semantics, and repairs that content cannot observe.
