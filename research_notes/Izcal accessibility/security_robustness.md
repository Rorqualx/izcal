# Izcal accessibility: security and robustness

Compiled 19 October 2026. Primary sources were preferred (specifications, OS vendor documentation, the NVD database, bug-tracker titles and discussion text, engine teams' prose design documents, WebAIM survey pages, papers).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known fact not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no engine source code was read for this note. No code files, headers, commits, diffs, code-review pages or source browsers of Chromium, Gecko, WebKit, AccessKit or NVDA were opened. Search results listed a Chromium commit (ariaNotify iframe policy), searchfox copies of Firefox docs and a WPT test file; none was opened or used. The Chromium "Security Guidelines for the Accessibility Tree", "Accessibility overview" and "Sandbox" pages, the Firefox DLL-blocklist page and the NVDA `nvdaHelper` readme are prose markdown in repositories and were read as prose only. Mozilla bug evidence uses bug **titles and metadata** from the Bugzilla REST API; no patch or attachment was opened. ## 1. The sandbox boundary: who talks to the OS accessibility API

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Chromium keeps each page's content in a separate, **sandboxed renderer** that "can't implement operating system APIs directly". The renderer builds an accessibility tree and sends it, as **small incremental updates**, to the browser process, which keeps a cache and implements the native APIs "using solely the information in that cache". | — | [Chromium Accessibility overview (prose)](https://chromium.googlesource.com/chromium/src/+/main/docs/accessibility/overview.md) | fetched 2026-10-19 | High |
| 1.2 | Chromium accessibility is "off by default and enabled automatically on-demand". The mode (`basic`, `form-controls`, `complete`) controls how much the renderer serializes. The doc gives no cost figures. | 3 named modes | Same | fetched 2026-10-19 | High |
| 1.3 | Chromium renderers on Windows run with **win32k lockdown** (`DisallowWin32kSystemCalls`) and **CIG / ProcessSignaturePolicy** ("prevents loading unsigned code … third party DLLs"), set pre-startup for renderers and post-startup for all sandboxed children. A renderer therefore cannot host MSAA/UIA/IA2 servers, and screen-reader DLLs cannot inject into it. The doc names no accessibility exception. | — | [Chromium Sandbox design (prose)](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md) | fetched 2026-10-19 | High |

| 1.11 | Both shipping multi-process engines accept a **parent-process attack surface**: the browser process parses renderer-supplied trees in C++. Sections 4.1–4.6 show this is the dominant 2024–26 bug class. | — | Inference from 1.4, 4.x | 2026 | Medium |

**Implications:** Izcal's broker must be the only process that speaks NSAccessibility, UIA, AT-SPI or Android; renderers produce semantic-plane diffs only. Because the broker is written in Rust, the memory-safety half of Chromium's guidance is met by construction, but the *semantic* half (IDs, cycles, offsets, cross-frame tokens) still needs an explicit validator at the capability-channel boundary.

**Implications:** the OS decides who may *read* Izcal; Izcal decides only what it *exposes*. **Implications:** every bug shape in 4.7–4.9 maps to a check Izcal's broker can make *structurally*: reject updates whose node would be its own ancestor, reject ID 0 or reused IDs, reject a node claimed by two parents, bind each tree to the capability channel of exactly one frame (no cross-actor attach), check enum/variant consistency at deserialization, and never cache derived tables across an update without revalidation. AT actions must never run script synchronously while the broker or the renderer holds tree references; route them as queued DOM events.

## 10. Open questions

1. **Bounds that only source code states**: maximum tree depth, node count, name length, and aria-owns resolution limits in Chromium, Gecko and WebKit. Measure black-box: deep nesting (10⁴–10⁶), 10⁶-node tables, labelledby chains and cycles, aria-owns cycles; record which engine truncates, hangs or crashes, and where.
2. **How Chrome identifies "accessibility software"** for its injection exemption (2.2) and whether the browser process carries any signature policy today. Black-box: load an unsigned test DLL under NVDA vs not.
3. **Fingerprinting entropy** of `prefers-reduced-motion`, `prefers-contrast`, `forced-colors`, `inverted-colors`, `prefers-reduced-transparency`: no population prevalence or bits found. Candidate sources: AmIUnique / EFF Cover Your Tracks datasets, HTTP Archive use counters.
4. **Safari and Brave behaviour** for these queries under their fingerprinting protections (6.8). Current Tor Browser behaviour for `prefers-contrast` (6.3 is snippet-only).
5. **Detection by timing**: is page performance (style/layout cost, `requestAnimationFrame` jitter) measurably different when a browser's accessibility mode is on? Izcal can measure this in deterministic simulation; no published measurement was found.
6. **Behavioural screen-reader detection accuracy** (5.12): no primary measurement found.
7. **Updated user attitudes**: WebAIM's 2014 detection numbers (5.8) are 12 years old and were criticised for lacking context. No NFB or later survey figure was found this session.
8. **WebKit**: no CVE count (4.11) and no prose description of how WebKit validates trees across the web/UI-process boundary.
9. **Screen-reader event budgets**: how many live-region or `ariaNotify` events per second NVDA, JAWS, VoiceOver, Orca and TalkBack can absorb before lagging; needed to set Izcal's per-frame rate limit.
10. **Newton status** after GNOME 48 (3.4): whether the protocol is final and whether GNOME Shell has moved off AT-SPI.
11. **Android 15–16 changes** to restricted settings and accessibility (behaviour-change pages could not be read in static HTML).
12. **Cause of the 2026 spike** (4.14): Chrome Releases and Mozilla advisories may credit reporters or tools; not checked.
