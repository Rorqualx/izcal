# Izcal accessibility: performance_architecture

Compiled 19 October 2026. Primary sources were preferred (engine teams' blog posts and prose design documents, OS vendor documentation, W3C specifications, maintainers' blogs, bug-tracker discussion text). Black-box measurements of stock Chrome were made for this note (Section 8).
Confidence: **High** = primary source read and the claim checked in its text, or measured by this researcher under the stated conditions; **Medium** = primary abstract or snippet, a vendor claim without data, or a well-known fact not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

M-1 note: no engine source code was read for this note. No code files, headers, commits, diffs, code-review pages or source browsers of Chromium, Gecko, WebKit or AccessKit were opened or used. Search results surfaced several Chromium and WebKit commit pages (for example an AXMode rename and a WebKit spell-check change); they were not opened, and no claim here rests on them. Chromium prose documents (`docs/accessibility/*.md`) and Firefox source docs (prose) were read as prose. WebKit Bugzilla pages were read for discussion text only; attached patches were not opened. AccessKit was read through its README only. Where only source code would state a value (for example the exact AXMode bit set, or Firefox's per-field cache layout), it is listed under "Open questions" as a black-box measurement.

**Implications:** Every multi-process engine converged on one shape: the sandboxed process pushes an incremental tree to the privileged process, which answers synchronous OS queries from its copy. Izcal should build B8's semantic plane in exactly that shape (renderer pushes diffs over a typed channel; broker serves the OS) and should not repeat the dirty-node "re-serialize everything" cost that Chrome had to patch with field-level fast paths: diffs should be per field from the start, as CtW's are.

## 2. Out-of-process iframes and tree stitching

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Chrome: **every frame is its own tree** with a globally unique **AXTreeID** (an UnguessableToken "for security reasons"). | 2.2 | Chrome composes the per-frame trees "into one virtual tree on the fly" during client traversal. | 2.3 | Chrome **focus**: the browser is "the source of truth" for window focus; focus is recomputed on any focus or window change by descending into iframes, and an event fires only if the deepest focused node changed. | — | [part 3](https://chromium.googlesource.com/chromium/src/+/main/docs/accessibility/browser/how_a11y_works_3.md) | read 2026-10-19 | High |

| 2.8 | **Why direct per-process OS access fails**: UIA's text pattern "has no mechanism for walking across process boundaries"; sandboxed content processes have no COM STA and are blocked from Win32k; accessibility code must run on the main thread while a single UIA search fans out into many provider calls. **Implications:** Izcal's site-per-process renderers make stitching mandatory, not optional. B8's stable node IDs need a two-level key (frame-tree token, node ID) where the token is unguessable and minted by the broker, and the broker must own focus and hit testing over the stitched tree. A z-ordered visible list pushed per frame (Firefox) fits Izcal better than async refinement (Chrome), because Izcal's immutable fragment tree already knows paint order.

Virtualizing very large documents (GNOME note) is an option only for the pushed copy, never for what the author's DOM exposes.

| 4.11 | Measured in stock Chrome: building a 20,000-row, 5-column table took ~330 ms with accessibility off, ~567 ms in `form-controls`, ~727 ms in `basic`, ~1,204 ms in `complete` (3.6x). **Implications:** Name invalidation needs a reverse dependency index (IDREF targets → dependent names), because accname reaches across the document; a dirty-subtree rule alone misses it (CtW's Gmail gap). Bounds should be pushed relative to scroll containers and transforms, so that Izcal's scroll and animation paths, which do not relayout, send only container updates. Izcal's flush-time data plane is the right batching point: emit one semantic diff per style/layout flush, never per mutation.

## Open questions

1. **Per-node memory.** No engine publishes it. Measure, black-box, Chrome and Firefox private-memory deltas (not RSS) per AX node on synthetic pages of 1k, 10k, 100k and 1M nodes, for each Chrome AX mode, and Firefox with and without a client.
2. **Firefox CtW memory and cache domains.** Rows 5.12 (cache domains) and the absence of CtW memory data need checking: when did Firefox add cache domains, which domains exist, and what does a non-AT client (password manager) trigger?
3. **Chrome AX mode contents.** The exact flag sets in `basic`, `form-controls` and `complete` (and the "extended properties"/screen-reader distinction) are stated only in code. Measure black-box: dump `getFullAXTree` under each forced mode and diff the properties present.
4. **Chrome's Auto Disable Accessibility result.** The blog says the measured cost is "quite high" but gives no number. Look for a public Chromium bug or BlinkOn talk with the figure.
5. **WebKit isolated tree status.** Is the isolated tree (secondary-thread AX) on by default in shipping Safari on macOS, and what fraction of requests still dispatch to the main thread? Not found in prose sources this session.
6. **Screen-reader latency perception.** No study of acceptable keypress-to-speech latency for screen-reader users was found. Measure NVDA and JAWS keypress-to-speech latency in Chrome and Firefox on the HTML spec and a Gmail-like app (rig253), and look for HCI literature.
7. **NVDA virtual-buffer build time.** No published timings beyond Teh's NVDA load times. Measure buffer render time on the HTML spec in Chrome and Firefox.
8. **AT-SPI activation properties.** Verify `org.a11y.Status` `IsEnabled` / `ScreenReaderEnabled` semantics and which apps set them (row 5.10).
9. **macOS activation signals.** Chromium's design doc names `AXEnhancedUserInterface`; Electron documents `AXManualAccessibility`. How did macOS 14 change these signals, and which non-AT apps (window managers, launchers) set them? Only commit messages surfaced, which this note may not use.
10. **IA2 embedded-object character** (row 6.2) should be verified in the IA2 spec text.
11. **Edge/Chromium UIA provider performance.** Is the UIA provider on by default in Edge or Chrome, and are there published timings for Narrator with TextPattern on large pages?
12. **Hit-testing accuracy.** Firefox's viewport cache vs Chrome's async refinement: no published comparison of first-hit accuracy. Measurable black-box with an AT harness on pages with overlays and transforms.
13. **Snapshot size for agents.** Token counts here use chars ÷ 4. Count with a real tokenizer and compare YAML aria snapshots, Chrome DevTools MCP `take_snapshot` (default and verbose) and a stable-ID diff format over a scripted session.
