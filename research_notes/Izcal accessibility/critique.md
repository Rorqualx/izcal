# Izcal accessibility: design critique

*Phase 8 independent design critique of `reports/Izcal accessibility.md` draft 0.1 (19 October 2026), by a critic who did not write the spec or its research notes. Date: 19 October 2026. Read against: HGBA-2 2.3.2 (M-1, P1–P6, I-1); HGBA-3 (B1, B4, B5, B8–B10, A11Y-1 to A11Y-4, Q-10, PRIV-2, R0); Stage 1 design (Sections 1, 2, 3.3, 4.1, 5.8, 8.1, 8.3); JavaScript engine 0.3 (JS-D4, JS-D11, JS-D15, H-2); resource footprint (6.4, 6.18.1, 8.2); parsing and style (6.10 environment snapshot, ST-D17); layout 0.4 (6.1, 6.9, 6.13, 6.14, 6.15, LY-16, LY-40); graphics (GR-D25, O9, 6.3); images and media (6.6, 6.12, MD-12); fonts and text (R24, TX-D12, `hg-unicode`); DevTools (DT-D6, G10); shell UI design (4.9, UI-1, UI-2); Phase 3 ledger (C-5 registry, G-10, G-17); reconciliation 2 (staffing, OD-6, OD-7); security scope 0.3 on its branch (6.1 ATK, 6.6 IPC-R1–R17, 6.6a CON-R1–R5, 6.7 sandbox table, 6.13 REC-R); the PDF spec draft in this tree (PD-D11, PD-D18); the DOM spec frame. No engine source code was opened for this critique.*

**Counts: 33 findings: 7 High, 15 Medium, 11 Low.** Plus 7 engine-source and licence items and 22 reconciliation items below.

The spec is strong on history, on the push-and-mirror architecture (AX-D4), on the validator, and on M-1 hygiene. Its weakest part is the claim that ties the design together: that **AT use is unobservable**. That claim depends on an extract mechanism (AX-D3) whose timing and threading the accepted specs do not support as written, and on an input-equivalence table that does not match the keyboard sequences it says it reproduces. The second weak area is the **broker as a target**. The spec hardens the renderer-to-broker edge well. It leaves three things open: the local-client edge (D-Bus, COM and AX calls from other programs into the unsandboxed broker), the consent path, and resource bounds on the mirror.

| 1 | **High** | **The "paint's shadow" extract cannot work as specified, and the parts that make it work leak AT use.** (a) It requires that paint run while the script thread is still blocked, because JS-D4 lets workers read node columns "only during a flush with the script thread blocked". No accepted spec says paint runs inside that window: LY 6.1 blocks script for style and layout, and GR 6.3 says only that `hg-paint` runs "after layout". If paint runs after script resumes, the extract breaks JS-D4. (b) The extract runs "on the same worker pool" as paint. The pool size is fixed per process (FP 6.18.1), so extract tasks take slots and memory bandwidth from paint, and paint ends later. "Never extends the flush" holds only for the extract's own cut-off; paint, and so the frame, gets longer. (c) "Publishes only complete extracts", plus "work not done carries over with the dirty set preserved", means that an extract larger than one paint window **never completes**. This covers the first full extract at L2 escalation (887k nodes on the HTML spec) and any page with sustained churn and little paint, so AX-12 (HTML spec ≤ 5 s) and AX-19 (catch up within 1 s) cannot be met. (d) The fix for semantic-only changes is an **idle flush** that blocks the script thread during HTML's idle period. It exists only when the level is above L0, so it shortens `requestIdleCallback` deadlines and delays tasks that arrive during it, which is a direct AT signal. ## Engine-source and licence items

1. **Bug-tracker pages.** The notes cite WebKit Bugzilla (193348, 204226, 243456, 305266) and Mozilla Bugzilla (1655053, 1864015, plus a security-keyword REST query). OD-7 covers prose documents in repositories, not bug pages, which often carry patch attachments and review diffs. Record in each note that only titles and comment prose were read and no attachment or diff was opened, or remove the rows.
2. **The `env(preferred-text-scale)` bucket values.** The spec adopts "the same 7 steps Chrome uses" (UX 7.5). The cited prose (chromestatus, explainer) gives the count, not the values; the values may exist only in Blink source. Measure them black-box (Q-AX) or set them † from first principles, and say which.
3. **Values adopted from Chrome's prose.** Android's 100 ms scroll throttle and the cap of 5 content-changed events (PE 3.10) come from a Chromium design document. That is allowed under OD-7, but the spec adopts them as Izcal's values without derivation. Mark them † and measure them against TalkBack (Q-AX-12).
4. **IA2 interface definitions (AX-D8).** The IA2 reference documentation is generated from the BSD-3-Clause IDL. GUIDs and vtable order are interface facts, but writing them "from the documentation" is in substance a transcription of the IDL. The owner classification the spec asks for is right; ask it as an M-1 part 1 question in those words, and also cover any IA2 proxy/stub Izcal might need (Q-AX-3).
5. **`AXWebConstants.h` (macOS 26 SDK, © 2025 Apple).** It is an OS interface definition, but it is specific to web content and evidently mirrors one engine's private attributes. Ask the owner to classify it the same way as AX-D8, and confirm that only constant names and documented meanings are used.
6. **AT source as evidence** (finding 22). NVDA (GPL-2.0), Orca (LGPL) and TalkBack (Apache-2.0) are not browser engines, so M-1 part 3 does not plainly forbid reading them, but their licences rule out shipping anything derived from them. This needs an explicit owner rule before the Windows track starts, because NVDA's in-process expectations are documented almost nowhere else. *Owner decision, 20 October 2026 (spec 0.2.1, AX-D25): no third-party source, ever; screen-reader behaviour comes from documentation, issue discussions and black-box testing in the AT lab.*
7. **Shipped standards data licence.** Before generating `hg-ax-mappings`, check each pinned W3C snapshot's licence footer. The permissive W3C Software and Document License allows derivatives; the older W3C Document License does not. The standards-body exception covers the source, but a table *derived* from a non-permissive document should be confirmed with the owner. Shipped crates (`windows*`, `objc2*`, `dispatch2`, `zbus`, `zvariant`, `jni`, `ndk`) are all available under MIT; this was checked against the spec's own table, not re-verified on crates.io.
