## 1. Event loops, task queues and task sources

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | Each **agent** has exactly one event loop. A similar-origin window agent's loop is a **window event loop**; dedicated, shared and service worker agents have **worker event loops**; worklet agents have **worklet event loops**. The spec says event loops "do not necessarily correspond to implementation threads": several window event loops may be cooperatively scheduled on one thread. Worker agents with [[CanBlock]] true effectively need a dedicated thread each, because of ECMAScript's forward-progress rules. | 3 kinds of event loop | [HTML 8.1.7.1 Definitions](https://html.spec.whatwg.org/multipage/webappapis.html#definitions-3) | 2026-10-19 | High |
| 1.2 | A **task queue is a set, not a queue**: the processing model takes "the first runnable task" from the chosen queue. The **microtask queue is not a task queue**. A task is a struct: steps, source, document (null outside window loops), and a script evaluation environment settings object set. A task is **runnable** only if its document is null or fully active. | — | [HTML #task-queue](https://html.spec.whatwg.org/multipage/webappapis.html#task-queue), [#concept-task-runnable](https://html.spec.whatwg.org/multipage/webappapis.html#concept-task-runnable) | 2026-10-19 | High |
| 1.3 | Every task source must be associated with one task queue **per event loop**; sources may share a queue. The spec's own example: a UA could give mouse and key events priority "three-quarters of the time" while never reordering tasks within one source. Ordering is guaranteed only **within a task source**. | — | [HTML #task-source](https://html.spec.whatwg.org/multipage/webappapis.html#task-source) | 2026-10-19 | High |
| 1.4 | **Generic task sources** in HTML 8.1.7.4: DOM manipulation, user interaction (trusted input events "must be fired using tasks queued with the user interaction task source"), networking, navigation and traversal, and **rendering** ("used solely to update the rendering"). | 5 generic sources | [HTML #generic-task-sources](https://html.spec.whatwg.org/multipage/webappapis.html#generic-task-sources) | 2026-10-19 | High |
| 1.5 | Other task sources defined in the HTML source (12 named `<dfn>`s in all, counting the 5 generic ones and microtask): timer, posted message, microtask (for microtasks moved into a task queue by spinning the loop), media element event, embed, JavaScript engine, speculation rules; plus each MessagePort's own **port message queue**, plus a virtual **unshipped port message queue** per event loop. Other specs add their own: bitmap (ImageBitmap), storage, the scheduler task sources and posted task source (Prioritized Task Scheduling), and the handle fetch and handle functional event sources (Service Workers). | 12 named in HTML plus port queues; at least 6 elsewhere | [HTML source on GitHub](https://raw.githubusercontent.com/whatwg/html/main/source) (grep of `<dfn>… task source</dfn>`); [Scheduling #scheduler-task-sources](https://wicg.github.io/scheduling-apis/#scheduler-task-sources); [SW #dfn-handle-fetch-task-source](https://w3c.github.io/ServiceWorker/#dfn-handle-fetch-task-source) | 2026-10-19 | High |
| 1.6 | Spec authors are told to use **queue a global task** (which derives the event loop and document from a global) or **queue an element task**. The older "implied event loop" and "implied document" are "vaguely-defined" and have "a lot of action-at-a-distance"; the spec hopes to remove them (issue #4980). The implied-document algorithm ends in "Assert: this step is never reached … Really?". | — | [HTML #queuing-tasks](https://html.spec.whatwg.org/multipage/webappapis.html#queuing-tasks), [#implied-document](https://html.spec.whatwg.org/multipage/webappapis.html#implied-document) | 2026-10-19 | High |
| 1.7 | Section 8.1.7.5 sets the rule for code running **in parallel**: it must not create or touch realm-bound objects, and cannot access `this`. It may use only Infra values, and must queue a global task, on a named task source and given a global, to affect JS-visible state. Its recommended template has three phases: synchronous setup on the loop, realm-agnostic work in parallel, then a queued global task. | — | [HTML #event-loop-for-spec-authors](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-for-spec-authors) | 2026-10-19 | High |

**Implications:** Izcal's scheduler can merge task sources into a few queues and choose freely between queues, but it must keep FIFO order within each source and skip tasks whose document is not fully active. The "in parallel → queue a global task" rule maps directly onto Izcal's typed IPC plus a per-agent task queue, and recording which task ran, and from which source, is enough to replay a run deterministically.

## 2. The event loop processing model and "update the rendering"

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | Processing model, in order: (1) choose **any** task queue that has a runnable task ("implementation-defined manner"); (2) take its first runnable task, record its start time and set the currently running task; (3) run its steps; (4) **perform a microtask checkpoint**; (5) report long tasks and record the task's end time; (6) on a window event loop with no runnable task, compute an idle deadline and start an idle period; (7) on a worker event loop, optionally run a dedicated worker's rAF callbacks and update its rendering, and destroy the loop when the closing flag is set and the queues are empty. | 7 phases | [HTML #event-loop-processing-model](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model) | 2026-10-19 | High |
| 2.2 | **"Update the rendering" is now itself a task**. A window event loop runs a separate in-parallel loop: wait until a navigable might have a rendering opportunity, set the *last render opportunity time*, then **queue a global task on the rendering task source** for each navigable that has one. The spec admits this "might cause redundant calls" and allows coalescing. | — | [HTML #update-the-rendering](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering) | 2026-10-19 | High |
| 2.3 | Document ordering in a rendering update: a child document comes after its container document, and siblings follow the shadow-including tree order of their navigable containers. Documents are then filtered out if they are render-blocked, have visibility "hidden", have rendering suppressed for view transitions, or their navigable has no rendering opportunity (**"Filter non-renderable documents"**). Documents are also dropped if the UA believes there would be no visible effect and the rAF map is empty (**"Unnecessary rendering"**), or "for other reasons", e.g. to coalesce timer callbacks with no rendering in between. | 3 filter steps | [HTML #update-the-rendering](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering) | 2026-10-19 | High |
| 2.4 | Ordered steps, run for each remaining document: **reveal**; flush **autofocus** candidates (top-level traversables only); **resize** steps; **scroll** steps; evaluate **media queries** and report changes; **update animations and send events**; **fullscreen** steps; canvas **context-lost** steps (contextlost/contextrestored); **animation frame callbacks** (rAF) with the frame timestamp; then a **style + layout loop** (recalc style and layout, determine `content-visibility: auto` proximity, gather and broadcast **ResizeObserver** observations at increasing depth, repeat; then deliver the resize-loop error if observations were skipped); **focus fix-up**; **perform pending view-transition operations**; update **IntersectionObserver** observations; record rendering time; **mark paint timing**; update the rendering/UI; **process top layer removals**. | 17 ordered steps (counting the style/layout/RO loop as one) | [HTML #update-the-rendering](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering), [#focus-fixup-rule](https://html.spec.whatwg.org/multipage/webappapis.html#focus-fixup-rule), [#context-lost-steps](https://html.spec.whatwg.org/multipage/webappapis.html#context-lost-steps) | 2026-10-19 | High |
| 2.5 | `requestVideoFrameCallback` and page-lifecycle "freeze" are **not** among HTML's update-the-rendering steps. Video frame callbacks are defined by a separate WICG spec (they were an Interop 2024 focus area). The HTML `source` has no `freeze`/`onfreeze` definitions (the only "frozen" hits are FrozenArray and "frozen base URL"). | 0 HTML hooks | [HTML #update-the-rendering](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering); [Interop 2024 README](https://github.com/web-platform-tests/interop/blob/main/2024/README.md) | 2026-10-19 | High |
| 2.6 | A **rendering opportunity** means the UA can present the navigable's contents "accounting for hardware refresh rate constraints and user agent throttling", even if the content is offscreen. The spec mandates no model; its examples are 60 Hz (≈16.7 ms), dropping to 30 per second under load, and "4 rendering opportunities per second, or even less" for pages that are not visible. | 60 / 30 / 4 Hz examples | [HTML #rendering-opportunity](https://html.spec.whatwg.org/multipage/webappapis.html#rendering-opportunity) | 2026-10-19 | High |
| 2.7 | Idle deadline: when a window event loop has no runnable task, `deadline` = last idle period start + **50 ms**, lowered to the earliest active timer, and further to last render opportunity + 1000/refresh rate if any same-loop window has rAF callbacks or pending rendering. The result is **coarsened** using cross-origin isolated capability. | 50 ms cap; 16.67 ms at 60 Hz | [HTML #idle-deadline-computation](https://html.spec.whatwg.org/multipage/webappapis.html#idle-deadline-computation) | 2026-10-19 | High |
| 2.8 | Dedicated workers can run animation frame callbacks inside the worker event loop (for OffscreenCanvas). BCD lists `DedicatedWorkerGlobalScope.requestAnimationFrame` in Chrome 69, Firefox 99 and Safari 16.4. | — | [HTML #event-loop-processing-model](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model); BCD 8.1.6 | 2026-10-15 | Medium |

**Implications:** The update-the-rendering order is a fixed, testable pipeline. Izcal should encode it as one ordered list with spec anchors and log each step in the mutation/frame log, so that DevTools and replay can show exactly which step ran. Because rendering is now a queued task, frame scheduling can be one more task source in the seeded scheduler, not a special path.

## 3. Microtasks, running script, spinning and pausing

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 3.1 | **Perform a microtask checkpoint** is guarded by a reentrancy flag. It drains the microtask queue (each microtask becomes the currently running task), then: notifies about rejected promises for every settings object of this loop, cleans up IndexedDB transactions, runs **ClearKeptObjects()** (which ends WeakRef keep-alives), and records microtask-checkpoint timing. | 4 post-drain steps | [HTML #perform-a-microtask-checkpoint](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint) | 2026-10-19 | High |
| 3.2 | **Clean up after running script** pops the realm execution context; if the JS execution context stack is then empty, it performs a microtask checkpoint. | 3.3 | **Spin the event loop** is defined as a macro: save and empty the JS execution context stack, perform a microtask checkpoint, wait in parallel for the goal, then queue a task on the **same task source** that restores the stack and resumes. A microtask that spins is moved into a task queue, the only case where a microtask's source and document matter. | — | [HTML #spin-the-event-loop](https://html.spec.whatwg.org/multipage/webappapis.html#spin-the-event-loop), [#queue-a-microtask](https://html.spec.whatwg.org/multipage/webappapis.html#queue-a-microtask) | 2026-10-19 | High |
| 3.4 | **Pause** (used for `alert()`, `confirm()`, `prompt()`, the beforeunload prompt and print) blocks the event loop: no further tasks run and script blocks, though the UA should stay responsive to input. The spec calls pausing "highly detrimental", encourages UAs to experiment with alternatives "even if doing so causes them to violate the exact semantics", and promises to change if a less drastic alternative is found web-compatible. | — | [HTML #pause](https://html.spec.whatwg.org/multipage/webappapis.html#pause) | 2026-10-19 | High |
| 3.5 | **Await a stable state** queues a microtask that runs a "synchronous section" (steps marked ⌛) and then resumes the algorithm in parallel. | — | [HTML #await-a-stable-state](https://html.spec.whatwg.org/multipage/webappapis.html#await-a-stable-state) | 2026-10-19 | High |
| 3.6 | Mutation-observer and custom-element bookkeeping lives **on the similar-origin window agent**, not on the event loop or the document: "mutation observer microtask queued", "pending mutation observers", the mutation observer counter, signal slots and the **custom element reactions stack**. | — | [DOM #mutation-observers](https://dom.spec.whatwg.org/#mutation-observers); [HTML #custom-element-reactions-stack](https://html.spec.whatwg.org/multipage/custom-elements.html#custom-element-reactions-stack) | 2026-10-19 | High |

**Implications:** Microtask timing comes from JS-stack depth (clean up after running script), not from task boundaries alone. Izcal's bindings layer must therefore run the checkpoint whenever a callback returns to an empty stack. Pause and spin are the two places where determinism and responsiveness collide; Izcal should implement them as explicit, recorded scheduler states.

## Open questions

- **Timer clamps in practice.** The spec says nesting >5 → 4 ms. Whether current engines still apply a 1 ms minimum for top-level `setTimeout(0)`, and what background-tab throttling they apply (for example 1 s, or budget-based), needs a black-box measurement. Values stated only in engine source must not be used.
- **Actual clock resolution.** hr-time allows 100 µs/5 µs or coarser. Measure `performance.now()` granularity and jitter in Chrome, Firefox and Safari, with and without cross-origin isolation.
- **Rendering-opportunity rates.** The 30 Hz and 4 Hz figures are examples. Measure rAF rates for hidden, occluded and cross-origin iframes in each engine.
- **Service worker idle termination.** No timeout is specified. Measure how long an idle SW survives in each engine, and how `waitUntil` extends it.
- **Event-loop priority between task sources and scheduler priorities.** The spec leaves it implementation-defined. Measure input vs `postTask("background")` vs timers ordering.
- **When "update the rendering" became a queued rendering-source task.** The commit was not located (the commit list available starts in September 2023), so it remains unchecked.
- **MessagePort `close` event.** It is not in the current HTML IDL; whether any engine ships it should be checked against BCD or WPT (BCD 8.1.6 has no entry).
- **WebKit's reasons for not implementing customized built-ins.** The search budget was exhausted; the WebKit standards-position text was not read.
- **Origin-keyed by default.** Chromium's M106 plan is from a search snippet only. Confirm the shipped state with a black-box `window.originAgentCluster` test on two same-site origins.
- **WPT subtest counts.** 18.6 counts files with a heuristic. wpt.fyi's per-directory subtest totals should replace it if precise numbers are needed.
