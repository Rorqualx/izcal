Compiled 19 October 2026. Primary sources were preferred: specifications, papers, engine teams' blog posts and prose design documents, standards-body threads, bug-tracker discussion text, release notes and MDN browser-compat data.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known date not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

## 1. DOM memory management: two collectors, one graph

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **IE's DOM was COM objects with reference counts; JScript had its own mark-and-sweep collector.** Microsoft's own explanation: "The cause of the leak in this pattern is based on COM reference counting. The script engine objects will hold a reference to the DOM element and will be waiting for any outstanding references to be removed." A cycle through an expando property is never released. | Cycles "at the end of a 30 object chain" are "much harder to detect" | [Rogers, "Understanding and Solving Internet Explorer Leak Patterns", MSDN](https://learn.microsoft.com/en-us/previous-versions/ms976398(v=msdn.10)) | 2005-06 | High |
| 1.2 | Microsoft named four patterns: **circular references** ("the root of nearly every leak"), **closures** ("the largest pattern to existing Web application architectures", e.g. an `attachEvent` handler closing over its element), **cross-page leaks** (DOM insertion order leaks internal book-keeping objects that survive navigation until process restart) and **pseudo-leaks** (rewriting `<script>` text keeps old code alive by design). The advice was to break cycles by hand on `onunload` and to avoid closures. | Insertion-order demo: 5,000 iterations, "only a few bytes" each | same | 2005-06 | High |
| 1.3 | **Era constraint stated by Microsoft:** leaks used to be invisible because "navigation between different locations within a site was a great way to clean up any loose memory". Long-lived Ajax pages ("might run for hours without being navigated") exposed them. | — | same | 2005-06 | High |
| 1.4 | **IE fixed it by making one collector own both sides.** In IE6 DOM/JScript cycles were broken only at process exit; in IE7 on navigation away; in IE8 "the JScript garbage collector treats DOM objects referenced by JScript objects as JScript objects." Compatibility cost: pages that "depend on garbage memory" that existed only through a leak now "reference unallocated memory and generate a fault". | IE6 → process exit; IE7 → navigation; IE8 → GC | [Microsoft, "Circular Memory Leak Mitigation"](https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/dd361842(v=vs.85)) | 2009 (IE8) | High |
| 1.5 | **Gecko's answer was a second collector.** Graydon Hoare's XPCOM cycle collector (Bugzilla 333078) is based on Bacon and Rajan's "Concurrent Cycle Collection in Reference Counted Systems"; classes opt in with helpers and modified AddRef/Release, and later patches walked the JS heap to find XPCOM↔JS cycles. Early runs collected "~100 nodes out of 10k scanned". Companion bugs were titled "Cycle collector makes AddRef about 6x slower" and "Release about 11x slower". | 6x / 11x refcount cost (bug titles) | [Bugzilla 333078](https://bugzilla.mozilla.org/show_bug.cgi?id=333078) | 2006–07 (Gecko 1.9, Firefox 3, 2008) | Medium (bug text read; exact dates and the Firefox 3 ship are recollection) |
| 1.6 | **The CC became a pause problem.** Andrew McCreight's 2011 meta bug: in normal browsing a CC took about **40–120 ms**, graph building ~90% of it; unlinking took about a third when closing tabs; pages with many DOM nodes outside the document caused **multi-second** pauses. Fixes: skip known-live subgraphs ("ForgetSkippable"), schedule CC around GC, asynchronous unlinking, and incremental CC. It was later closed as WORKSFORME: "No new bugs blocking this one in a decade." | 40–120 ms typical; seconds when leaky | [Bugzilla 698919](https://bugzilla.mozilla.org/show_bug.cgi?id=698919); [MozillaWiki CC perf improvements](https://wiki.mozilla.org/CC_perf_improvements) (target Firefox 13) | 2011–2012 | High |
| 1.7 | Later CC telemetry: p95 of a whole collection fell from about 624 ms to 463 ms after incremental CC slices; concurrent CC was judged a long-term project because "dead objects can become live again". | 624 → 463 ms p95 | [JS engine note gc_memory 4.5](../Izcal%20JavaScript%20engine/gc_memory.md) (Bugzilla 1304205) | 2016 | Medium |
| 1.8 | **Blink's Oilpan (DOM on a traced C++ heap).** Goals in Haraken's shipping-plan deck: "better security (use-after-frees are gone)", easier programming, better tools. Success criteria: faster than reference counting, no break of 60 fps (goal: **10 ms** GC), no peak-memory increase. Status (late 2014): on by default for everything **except the Node hierarchy**. | Linux: 96% of GCs < 20 ms; Nexus 7: 43% < 20 ms, **37% > 50 ms** ("Looks unacceptable"); Blink ~5% of renderer memory | [Oilpan's Performance & Shipping Plan (Google Slides)](https://docs.google.com/presentation/d/1Nid96XTjKSWowoQ8FQOpCnbe91kOXLAeiafKsDQ5Smw/htmlpresent) | ~late 2014 (undated; cites Oct 2014 data, targets 2015 Q1) | High (deck read); date Medium |
| 1.9 | Oilpan's 2014 problems were **pause time** on mobile animation benchmarks, Linux execution regressions (Page cycler −3.4%), and **memory locality**: "GC allocation spreads objects out, unlike reference counting, which reuses memory quickly". Parallel marking was off because marker threads polluted caches. Planned fixes: incremental sweeping (>50% pause cut estimated) and running GC from the Blink scheduler at idle times. | Speedometer: Nexus 7 +2.2%, Mac +0.6%, Linux 0.0% | same | ~2014 | High |
| 1.10 | V8's account of why Oilpan exists: Blink "originally used reference counting", which is "prone to memory leaks due to cycles", and counts were sometimes skipped for speed, "leading to use-after-free issues". Oilpan moved into V8 as the **cppgc** library (V8 9.4, Chromium M94). | — | [V8 blog "Oilpan library"](https://v8.dev/blog/oilpan-library) | 2021-11-10 | High |
| 1.11 | **Object grouping → cross-component tracing.** Up to Chrome 56, wrapper liveness was decided by document containment: "A group with all of its containing objects was kept alive as long as a single object was kept alive". It hid real retaining paths and collected wrappers too early, losing their JS properties. Chrome 57 (March 2017) traces "from JavaScript to the C++ implementation of the DOM and back", incrementally with write barriers. DevTools retaining paths became exact only in Chrome 66. | Chrome 57 / 65 / 66; no performance numbers given | [V8 blog "Tracing from JS to the DOM and back again"](https://v8.dev/blog/tracing-js-dom) | 2018-03-01 | High |
| 1.12 | **Servo** gave the JS collector "full responsibility for managing those native-code DOM objects" (reflectors), so cross-boundary cycles need no CC. Rooting used `JS<T>`, `Root<T>` and `JSRef<'a,T>` plus a custom lint that "will miss some mistakes". Stated open question: "how our garbage-collected DOM will perform compared to a traditional reference-counted DOM"; the expected big win was allocating DOM objects inside their reflectors. | — | [Mozilla Research, "JavaScript: Servo's only garbage collector"](https://research.mozilla.org/2014/08/26/javascript-servos-only-garbage-collector/) | 2014-08-26 | High |
| 1.13 | **WebKit keeps a reference-counted DOM** and decides wrapper liveness with marking constraints ("opaque roots") solved at a fixpoint in Riptide's stop-the-world phase. | — | [WebKit blog, Riptide](https://webkit.org/blog/7122/introducing-riptide-webkits-retreating-wavefront-concurrent-garbage-collector/); see [gc_memory 4.8](../Izcal%20JavaScript%20engine/gc_memory.md) | 2017-01-20 | Medium |
| 1.14 | **Ladybird** reportedly moved its DOM onto the LibJS collector (EventTargets as GC-allocated platform objects, no separate C++ wrappers) around 2022. The only sources found were commit messages and third-party mirrors, which M-1 excludes; recorded as an open question. | — | — | ~2022 | Low |

**Implications:** Every engine that split the DOM and JS between two memory managers paid with leaks (IE6/7, pre-57 Blink), pauses (Gecko CC, early Oilpan) or soundness gaps (Servo's lint). Izcal's single tracer for JS objects and DOM nodes (JS-D4) is the IE8/Servo conclusion done from the start; the remaining risks are Oilpan's: **pause time on small devices and allocation locality**, which Izcal's columnar node store must be measured against.

**Implications:** Each redesign (XPConnect → Paris, Perl → Python → bind_gen, DOMJIT, fast API calls) had the same two drivers: **getter call cost on tiny operations** and **spec-exact WebIDL behaviour**. Izcal owns both the IDL compiler and the JIT, so purity, slot caching and type facts can be one generated table consumed directly by the JIT rather than a retrofit; the target is a `firstChild`-class getter that costs a field load after inlining.

**Implications:** Removals cost years (Mutation Events: 13; unload: 3+ with staged percentages) and every one left a compatibility knob behind (deprecation trials, enterprise policies, opt-in headers). Izcal should not ship the removed features at all where the web no longer depends on them, and should treat the **synchronous, re-entrant designs** (Mutation Events, showModalDialog, sync XHR, unload) as the class to keep out of its event loop, since each one let script run inside an engine operation or block it.

## 7. Process models, Spectre and agent clusters

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 7.1 | **WebKit2** (2010) is "a new API layer for WebKit designed from the ground up to support a split process model": a UI process and a sandboxable web process, with non-blocking API calls, CoreIPC (mach messages on macOS) and shared-memory drawing. Chrome had the split already, but inside the browser rather than the framework. | — | [WebKit wiki, WebKit2](https://trac.webkit.org/wiki/WebKit2) | 2010-04 | High |
| 7.2 | **Spectre** (disclosed 3 Jan 2018): browsers coarsened `performance.now()` (Chrome 5 µs → 100 µs, plus jitter) and jointly disabled **SharedArrayBuffer** retroactively, since it builds a nanosecond timer. | 7.3 | **Site Isolation** (Reis, Moshchuk, Oskov, USENIX Security 2019): "almost 450k lines of code"; total memory overhead **9–13%**; page load latency up < **2.25%** (FCP 457 → 467 ms at p25); renderer processes per user +43.5% at p50 (4.4 → 6.2); navigations crossing a process boundary rose from **5.73% to 56.0%**; per-renderer private memory fell 51.5% at p50. "The Chrome team was willing to accept 9-13% memory overhead for the security benefits." | 9–13%; <2.25%; 450k LOC | [Reis et al. | 7.4 | **Out-of-process iframes** forced the browser to change its abstraction "from page (containing a tree of frames) to document (in a single frame)", with proxy objects and replicated state for frames in other processes; painting, input hit testing, find-in-page and messaging all had to be reworked. | — | same | 2019-08 | High |
| 7.5 | **Firefox Fission** (Mozilla Hacks, 18 May 2021, in Nightly and Beta): one OS process per site, sites compared by eTLD+1 using the public suffix list, cross-site subframes in their own processes, motivated by Spectre ("the only way to provide memory protections necessary to defend against Spectre-like attacks"). ## 8. Cross-cutting lessons

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | Two memory managers for one DOM↔JS graph failed in four engines; three ended by making one collector own both sides (IE8, Servo, Blink's unified heap), and Gecko kept a second collector with decade-long pause work. | IE 2005–09; Gecko 2007–2024; Blink 2013–2021 | 1.4, 1.6, 1.11, 1.12 | — | High |
| 8.2 | Synchronous re-entrancy is the common failure of removed APIs: Mutation Events, showModalDialog, sync XHR and unload all let script run inside, or block, the engine's own operation. Their replacements are batched or asynchronous (MutationObserver, `<dialog>`, `fetch`, `visibilitychange`). | 3.1, 3.5, 3.9, 3.12 | Section 3 | 2011–2026 | High |
| 8.3 | Scheduling primitives arrived in the order developers needed them, each patching the last: 10/4 ms clamps → rAF → rIC → `MessageChannel` hacks → isInputPending (now discouraged) → postTask/yield; and metrics followed (Long Tasks → LoAF, FID → INP). | 2008–2024 | Section 4 | — | High |
| 8.4 | Each spec was rewritten to match implementations only after a decade of divergence (session history 2022; Mutation Events removal 2024). Building from the current spec text avoids inheriting the divergent middle. | 5.3, 3.2 | — | — | High |

**Implications:** These are the four constraints the synthesis should carry into the spec: one tracer; no synchronous re-entry into DOM operations; a scheduler with priorities, yield and attribution from day one; and implementation of the post-rewrite HTML navigation model.
