Compiled 19 October 2026. Primary sources were preferred (specifications, papers, maintainers' posts, engine teams' prose design documents, release notes, published benchmark data, and one black-box measurement made for this note).
Confidence: **High** = primary source read and the claim checked in its text, or a black-box measurement made this session; **Medium** = primary abstract or snippet, secondary coverage that quotes the primary, a vendor claim without data, or a well-known date not re-checked this session; **Low** = secondary source only, or the researcher's recollection not checked against a source this session.

Every row was checked by fetching known primary pages directly: spec pages (DOM, Web IDL, HTML), v8.dev, webkit.org (post list from its own sitemap), hacks.mozilla.org (post list from its own sitemap), developer.chrome.com, blog.chromium.org / blog.google, almanac.httparchive.org, crates.io and npm registry metadata (for licences), GitHub READMEs and prose docs, ladybird.org newsletters (list from its RSS feed), and the Meyerovich and Bodík WWW 2010 PDF read with `pdftotext`.
- **Black-box measurement made for this note (section 1, rows 1.6–1.12).** Stock Google Chrome 155.0.8059.80, headless, macOS on Apple silicon, 19 October 2026 (rig `local`, light booking). For each scenario a fresh browser with a fresh profile loaded an empty page, forced garbage collection four times over the DevTools protocol (`HeapProfiler.collectGarbage`), and read (a) the summed `phys_footprint` of all renderer processes with macOS `footprint` and (b) `JSHeapUsedSize` from `Performance.getMetrics`. It then built N = 200,000 nodes, collected garbage again and re-read both. Each scenario ran 3 times; the medians are reported and the runs agreed within about 2%. The numbers are **process-level deltas per node**: they include allocator slack and any per-node style, layout and paint data, not only the DOM node object. They are evidence about Chrome's total cost, not its object sizes.

**Implications:** The DOM node itself is a small share of what a rendered element costs (about 89 B of about 800 B in Chrome), and a wrapper is smaller still. Izcal's columnar node storage should be judged on traversal and mutation speed and on what it makes cheap for style and layout, not on bytes per node alone. Rows 1.6–1.12 give a baseline Izcal can reproduce with the same black-box harness.

## 2. Data-oriented and columnar DOM ideas

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **Meyerovich and Bodík profiled Safari 4.0.3** on popular pages. ## Open questions

1. **Per-node cost in Gecko and WebKit**, measured with the same black-box harness as rows 1.6–1.12. Firefox needs WebDriver BiDi or `about:memory` dumps instead of CDP; Safari needs WebDriver and `footprint`. Also re-run Chrome on Linux and Android to see how allocator and platform change it.
2. **Fraction of nodes touched by script** on real pages: count wrappers created per node created during load and interaction, for example with V8 heap snapshots counting wrapper objects against `Performance.getMetrics` `Nodes` on top sites. No published number exists (1.15).
3. **Split of the +70 B footprint per wrapper** (1.9) between V8 heap pages, the Blink-side handle and GC metadata. Measure with heap snapshots, not footprint alone.
4. **Bindings share of Speedometer 3 time** in any engine (4.13). Measurable black-box with Chrome's runtime-call-stats tracing, or by sampling profiles in Firefox and Safari.

A black-box test: a getter loop such as `node.nodeType` in a hot loop with and without a DOM mutation in the loop, which would expose loop-invariant hoisting.
