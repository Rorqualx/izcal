# Izcal shell: phase 8 independent design critique

## Method

I am the independent phase 8 design critic; I did not write this specification. I read the first-principles-spec skill, especially phases 6–8 and the template; the phase 2c brief; the shell text supplied for this review (its header says draft 0.1 and its Appendix A says phase 8 has not run, while the review request calls it draft 0.2); all six research notes in `research_notes/Izcal shell/`; and the accepted or integration specifications named in the brief (Stage 1 design 0.12, shell UI design, accessibility 0.2.2, editing 0.3, storage, resource footprint 0.4.2, security scope 0.3.1, networking, content blocking, animation, extensions, DevTools, PDF, HGBA-2 2.3.3 and HGBA-3). Each finding names the section, quotes or paraphrases the problematic sentence, states the rule or first principle it fails, and proposes a specific fix. I did not read or cite any third-party source code; where I mention an external project it is only as the reviewed documents mention it. Today is 21 October 2026.

| 1 | Critical | The Windows UI host, not the broker, owns the prompt window and receives the raw OS input the broker later hit-tests. ## Verdict

Draft 0.2 is **not sound as written**, but its core architecture is worth keeping. The typed capability endpoints, the separate broker-placed prompt window, the prompt ledger, one history/bookmark store with provenance, the settings registry, the native recovery path and the recording design are all strong first-principles choices. The problem is that the consent trust chain is not closed: the UI host owns the prompt window and receives the raw input (finding 1), the broker accepts the prompt renderer's reported layout (2), and the shell content GPU paints the prompt (3). Each of those is a path to a false affirmative, and together they contradict CON-R1, CON-R3 and SEC-29. Add the page title in the identity row (4), the non-MIT CLDR data (5), the FP-1 ceiling raised before measurement (6), and the Stage 1 scope and staging contradictions (7–12), and the draft cannot go to the owner as a sound basis for a decision.

**Must change before the owner decides:** findings 1–12. In particular, make the broker the prompt-window owner and the real OS input receiver on every platform; make the prompt layout and pixels unforgeable by the prompt renderer and the shell content GPU; remove the page title from the site-panel identity row; resolve the `intl_pluralrules`/CLDR licence; fit FP-1 or obtain an explicit owner decision to raise it with a measured reason; and fix Stage 1 scope and milestones (extensions, containers, M0, M7/M8, storage service). Findings 13–35 are revision work that should be closed in draft 0.3 before implementation planning; they are not optional, but they do not individually block the owner's architecture decision, and the PD-D2 prompt class (34) and SH-R9 handle rule (35) should be fixed with the security surface work. Findings 36–47 can be deferred to implementation planning and logged.

After those changes, the design is sound in shape: a sandboxed shell with no ambient authority, a broker-owned consent record, a prompt ledger that explains decisions, history and bookmarks with provenance, and a recovery path that works when the engine does not. The revisions need to make the trust claims true rather than weaken them.
