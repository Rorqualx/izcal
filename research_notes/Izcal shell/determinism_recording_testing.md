# Izcal shell: determinism, recording and testing

Compiled 21 October 2026. Primary sources were preferred (specifications, papers, maintainers' documentation). No source code, headers, commits, diffs or code reviews were read (M-1 part 3); prose documents inside repositories were used only where they are documentation, not code. Values that are another browser's implementation detail are marked **observation**, not requirement. Single-source and vendor claims are marked in the finding.

Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, or a number taken from another note's reading; **Low** = secondary source only.

The shell is HTML rendered by the engine in a sandboxed renderer ([HGBA shell UI design 3](../../reports/HGBA%20shell%20UI%20design.md)); its UI is therefore a page, and the questions below are the ones that decide whether a shell session can be replayed, restored and tested like one.

## 1. Record and replay of user interfaces and browser sessions

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 1.1 | **rr** records Linux user-space processes at the kernel boundary (syscalls, signals and their timing) plus rare nondeterministic CPU effects; replay reproduces instruction-level control flow, memory and register contents with stable addresses and identical syscall results. | 1.3 | rr's limits are architectural: it "emulates a single-core machine", cannot record processes that share memory outside the recorded tree, has incomplete syscall coverage, and may need updates after kernel, library or CPU changes. Weak-memory-model bugs cannot be observed at arbitrary points. | single-core emulation | [rr project](https://rr-project.org/) | accessed 2026-10-21 | High |
| 1.4 | **WebReplay** (Firefox) recorded a content process at the non-Gecko system/library API boundary, storing call outputs including lock-acquisition order and atomics, and replayed them. Cross-machine replay required the same Firefox build and a similar OS. | same build; similar OS | [MDN WebReplay archive](https://mdn-archive.mossop.dev/en-US/docs/Mozilla/Projects/WebReplay) | archived 2019 | High |

| 1.7 | **Timelapse/Dolos** recorded and replayed web applications inside WebKit with "negligible" overhead. In a small evaluation, replay had no statistically significant effect on debugging speed or success, while reproducing a bug consumed 8–25% of task time. | 12 developers; <1.1x slowdown; 8–25% of task time | [Burg et al., UIST 2013](https://homes.cs.washington.edu/~mernst/pubs/record-replay-uist2013.pdf) | 2013 | Medium (abstract confirms no significant speedup; figures from the DevTools spec's reading) |
| 1.8 | **Replay.io** concluded it had started from technology rather than a validated problem: "We started with a solution and have been searching for a problem." It discontinued Test Suites on 31 August 2024. Users worried about sensitive recordings and needing a separate browser, and "most issues are reproducible once you can see the video and network requests". | Test Suites ended 2024-08-31 | [Replay, "A new direction"](https://replay.io/blog/a-new-direction) | 2024-07-24 | High |
| 1.9 | Replay's recordings require its own **Replay Browser**, built on Chromium 108. | 1.10 | **WebPageReplay** captured live pages through local DNS and HTTP(S) proxies so performance tests could "replay the same exact content" unaffected by origin servers and the network. | 1.11 | **rrweb** records an initial DOM snapshot plus "all HTML state changes (mutations) and user interactions", chains multiple page loads into one recording, and replays by restoring the snapshot and applying events in timestamp order. **Implications:** Record/replay is technically proven at browser scale (rr, WebReplay) but has repeatedly failed as a standalone product when it did not feed a concrete task (Timelapse, Replay.io). Izcal should record only for named tasks (bug reports, shell tests, DevTools why-queries), at process launch, with a measured cost and a declared boundary. Because the shell is a page, a shell recording is a shell-renderer segment plus the broker IPC inputs that drive it, not "a browser session" in the abstract.

## 2. What can and cannot be recorded: time, entropy, network, animation, fonts, pixels

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 2.1 | **FoundationDB** runs an entire cluster as a "deterministic simulation of an entire FoundationDB cluster within a single-threaded process". | 2.6 | `performance.now()` returns milliseconds from `timeOrigin` on a monotonic clock; it is coarsened for privacy to 5 µs in cross-origin-isolated contexts and 100 µs otherwise. | 5 µs / 100 µs | [MDN performance.now](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now) | accessed 2026-10-21 | High (observation) |
| 2.7 | Firefox's own guidance on intermittent tests lists the timing hazards: two async operations have no assumed order; arbitrary `setTimeout(handler, 500)` is guesswork; GC can collect a timer before it fires; clock skew can reach 16 ms; a test crossing midnight can fail; external sites must not be used. | 16 ms clock skew | [Firefox intermittent tests](https://firefox-source-docs.mozilla.org/testing/intermittent/index.html) | accessed 2026-10-21 | High |
| 2.8 | WPT's **Ahem** test font has exactly defined metrics: square em-square, ascent plus descent equal to the em, extent equal to line-height, baseline 0.8 em from the top; most ASCII glyphs are 1 em squares. | 2.9 | The same web font produces different line boxes on macOS and Windows because the OSes read different vertical metric tables; Chrome reports that about 10% of Google Fonts need OS-specific overrides. OS font sets can also change while a session runs when a language pack or app is installed. | ~10% of Google Fonts; ~90% same | [Chrome, improved font fallbacks](https://developer.chrome.com/blog/font-fallbacks); `research_notes/Izcal fonts and text/gaps_opportunities.md` | 2023-02-10 (blog); read 2026-10-19 | Medium-High |
| 2.10 | Rendering is machine-dependent: **Pixel Perfect** obtained 50 distinct renderings from 300 samples of Arial text, and 116 unique fingerprints in 294 experiments (5.73 bits); the signal measured graphics driver and GPU model, and ClearType/DPI mattered. Rendering was pixel-identical across trials for one user. | 50/300; 116/294; 5.73 bits | [Mowery and Shacham, W2SP 2012](https://hovav.net/ucsd/dist/canvas.pdf) | 2012 | Medium (single study; read via the graphics note) |
| 2.11 | Izcal's own determinism target **DET-1** requires 1,000 of 1,000 bit-identical DOM, fragment-tree, display-list and semantic-tree hashes under simulation, and explicitly excludes GPU-dependent output, media and audio, which are covered by `rr` and conventional tests instead. | 1,000/1,000; GPU/media excluded | [HGBA-3 DET-1](../../reports/Future%20software%20browser%20engine.md); [Stage 1 design 3.2–3.3](../../reports/HGBA%20Stage%201%20architecture%20design.md) | 2026-10-14 | High (project target) |
| 2.12 | Izcal's simulation network replays a recorded corpus archive: one archive per page load holding every request, response, timing and the seed; Stage 1 writes a compact format with a WARC importer so other tools' corpora can be reused. | one archive per page load | [Stage 1 design 3.2](../../reports/HGBA%20Stage%201%20architecture%20design.md) | 2026-10-14 | High (project design) |

**Implications:** Input completeness is the whole game. A recording must carry the virtual clock and scheduler choices, seeded entropy streams, the network archive and the exact engine configuration (including the mandatory worker-task mode); browser-coarsened `Event.timeStamp` and `performance.now` cannot be used to order a replay. Text, fonts and pixels are only deterministic if the font inventory is sealed and the raster path is either deterministic or excluded and labelled, as DET-1 does for GPU output. Animation timelines must be driven by the substrate clock, because no shipping automation tool owns the document timeline.

| 3.11 | **Gap:** no prose documentation of Chromium's on-disk session file format was found; what is public is support guidance and file names, and the internal schema would be source-level. **Implications:** Session restore is a versioned, user-facing state model, not a recording. It must serialize tabs, navigation entries, scroll/form state, pinned/grouped/discarded/frozen status and container identity, and it must define merge and failure semantics (restore into an existing session, corrupt file, crash loop). The Firefox checkpoint and Android process-death model give the two useful failure primitives: detect an unclean end, and restore only the small, validated state needed to rebuild the UI. The shell should not promise that a restored page equals the page that was closed.

## 4. Input recording, synthesis and trust

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 4.1 | HTML defines an **activation triggering input event** as "any event whose isTrusted attribute is true" of type keydown (not Esc or a reserved shortcut), mousedown, mouse pointerdown, non-mouse pointerup or touchend. A script-dispatched synthetic event is untrusted and does not qualify; activation notification runs before dispatch. | isTrusted true required | [HTML user activation](https://html.spec.whatwg.org/multipage/interaction.html#activation-triggering-input-event) | accessed 2026-10-21 | High |
| 4.2 | WebDriver actions must be "equivalent to performing the given input device manipulations" and "such that trusted events corresponding to the entries in list of events are dispatched". A non-normative note states the events have `isTrusted` set to true and that an activation trigger generated by WebDriver is indistinguishable from a real user's. | isTrusted true | [WebDriver 2, Actions](https://www.w3.org/TR/webdriver2/#actions) | accessed 2026-10-21 | High |
| 4.3 | WebDriver's **tick** is the basic time unit of actions; the next tick begins after the user agent has processed all DOM events from the current tick. Pointer and scroll movement compute a ratio from a **monotonic clock**; the initial movement is synchronous and later movements may be asynchronous at an implementation-defined rate. | tick; monotonic clock | [WebDriver 2, Actions](https://www.w3.org/TR/webdriver2/#actions) | accessed 2026-10-21 | High |
| 4.4 | The 2015 WebDriver editor's draft records the design trade-off for input synthesis: sending OS-specific input messages risks browser state and isolation, while using OS accessibility APIs requires window focus and prevents parallel WebDriver instances; the "most robust way" is to create events in the browser implementation itself. | focus; no parallel sessions | [WebDriver WD 2015](https://www.w3.org/TR/2015/WD-webdriver-20150915/) | 2015-09-15 | Medium (editor's-draft note) |
| 4.5 | **Marionette** controls Gecko browsers out of process, "can control both the chrome- and content documents", provides "ability to emulate user interaction", and is used by geckodriver to implement WebDriver. **Observation**. | chrome + content | [Firefox Marionette](https://firefox-source-docs.mozilla.org/remote/marionette/index.html) | accessed 2026-10-21 | High |
| 4.6 | Chrome's **Recorder** records a user flow as steps: click, doubleClick, hover, change, keyUp, keyDown, scroll, close, navigate, waitForElement, waitForExpression and setViewport. A step has a target, frame, timeout and selector list; selectors are chosen in the order ARIA, CSS (shared testing attributes first), XPath, Pierce, then shortest unique text. Hover is not captured automatically; each recording begins with setViewport and navigate, and the navigate step reloads the page on every replay. | 12 step types; selector order | [Chrome Recorder reference](https://developer.chrome.com/docs/devtools/recorder/reference) | accessed 2026-10-21 | High |
| 4.7 | The Recorder has **no separate assert step** (a `waitForElement` is configured as an assertion), defaults every step to a 5000 ms timeout, and reports a failure only after the timeout when an assertion fails or a target cannot be found. No automatic retry or fallback is documented. | 5000 ms default | [Chrome Recorder reference](https://developer.chrome.com/docs/devtools/recorder/reference) | accessed 2026-10-21 | High |
| 4.8 | **uinput** lets a userspace program create a virtual input device with specified capabilities and send events that are delivered to userspace and in-kernel consumers; the documentation says the example mouse "behaves like a physical mouse" but makes no explicit indistinguishability guarantee. Access is by writing `/dev/uinput`. | — | [Linux uinput](https://www.kernel.org/doc/html/latest/input/uinput.html) | accessed 2026-10-21 | High |
| 4.9 | **Gap:** the only shipped Chrome recording surface found is the flow Recorder. No published Chrome prose describing a debugging-grade record/replay of a browser session was found in this pass; Chromium's session files and input paths are not documented as a recording format. | — | [Chrome Recorder overview](https://developer.chrome.com/docs/devtools/recorder/overview) | last updated 2024-07-15 | Medium (absence in docs searched) |

**Implications:** `isTrusted` separates page script from the browser's input pipeline, but it does **not** separate a human from an automation client: WebDriver and Marionette input is trusted and can create user activation. The shell must therefore gate permission prompts, protected-media switches and credential confirmations on the **session principal** and the input's provenance, not on `event.isTrusted` alone, and record which principal and which activation state produced each input. OS-level injection (uinput, accessibility APIs) is a privileged test path; browser-API synthesis is the portable one.

## 6. Recording privacy, retention and redaction

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 6.1 | The Princeton **session-replay** study analysed seven top vendors (Yandex, FullStory, Hotjar, UserReplay, Smartlook, Clicktale, SessionCam), found them on 482 of the Alexa top 50,000 sites, and showed scripts collecting "keystrokes, mouse movements, and scrolling behavior" plus "the entire contents of the pages you visit", including form text before submission, with no visual indication. | 7 vendors; 482 of top 50,000 | [CITP, "No boundaries"](https://blog.citp.princeton.edu/2017/11/15/no-boundaries-exfiltration-of-personal-data-by-session-replay-scripts/) | 2017-11-15 | High |

**Implications:** A shell recording is sensitive by construction: it contains URLs, titles, page-derived strings, form values if typed, and the IPC that carries them. Defaults should be off, memory-only, per-recording consent, encrypted at rest, and deleted with the container. Redaction must be consistent across the bundle, carry a manifest and an "exact until" marker, and be tested with seeded canaries. Session-replay vendors show that masking inputs is not enough: URL PII and displayed text are the leak paths, and retention must be stated as a number, not implied.

## What the shell must record, and how it is tested

1. **Record at process launch, not at "record" pressed mid-session**: the shell renderer plus the broker IPC that drives it, with the engine configuration in the segment header (rows 1.1–1.5, 1.9, 2.3, 2.11).
2. **Record the substrate's clock, scheduler and entropy streams, never `Event.timeStamp` or wall time**: browser timers are coarsened to 0.1–16.7 ms and cannot order a replay (rows 2.4–2.6, 2.3).
3. **Record the network as one archive per page load with request, response, timing and seed**, and declare TLS and live-service boundaries rather than pretending they replay (rows 1.10, 2.12, 5.8).
4. **Seal the font inventory at session start and record it as an input**; text rendering differs by OS metrics and font sets, so a replay without the same font image is not exact (rows 2.8–2.10).
5. **Record input provenance and activation, not just `isTrusted`**: WebDriver and Marionette input is trusted, so the shell gates prompts on the session principal and records which principal produced each event (rows 4.1–4.5, 7.14).
6. **Test the shell as a page**: Chrome-WebUI-style component suites under the deterministic substrate, with keyboard walkthroughs and replay-based visibility checks (rows 7.1–7.2, 7.10–7.12, 7.14).
7. **Use exact visual oracles where determinism is claimed, and a published tolerance where it is not**: reftest/Gold exact match for shell goldens, fuzzy or 0.063-style thresholds only for anti-aliasing, with the tolerance recorded (rows 7.3–7.7).
8. **Treat accessibility automation as a floor**: 57% coverage by volume in the vendor study, and W3C says no tool alone can decide; pair CI checks with manual AT audits every release (rows 7.8–7.11).
9. **Model tab, window and session state as a state machine** and generate close/restore/discard/freeze/crash sequences with invariants (no lost tab, no duplicate, no prompt without a principal, bounded restore attempts) (rows 3.1–3.11, 7.12–7.13).
10. **Keep session restore and replay separate**: restore is a small, versioned, lossy serialization of tabs, history, scroll and form state; replay is an exact input log with a declared boundary (rows 1.7–1.9, 3.1–3.11).
11. **Make recordings off by default, memory-only until saved, redacted with a manifest and an "exact until" point, canary-tested, encrypted at rest, and retention-bounded** (rows 6.1–6.9).
12. **Detect crash loops with an explicit checkpoint and a bounded attempt counter**, then fall back to a fresh session or the native recovery window rather than retrying a corrupt session forever (rows 3.3–3.4, 3.11).
