# Izcal compliance and security response: today's security-response landscape (programmes, standards, formats and operations)

Compiled 24 October 2026. Primary sources were preferred (specifications, programme rules, standards bodies' pages, vendors' policy pages, maintainers' posts). News coverage was used where no primary page could be read, and is graded as such.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data, or a secondary report of a primary statement; **Low** = secondary source only, or from memory and unchecked.

**M-1 statement.** No third-party source code was opened, read, linked or cited: no code files, headers, commits, diffs, code reviews or repository data files (no JSON schemas inside code repositories). Every source is a standard, a programme's rules or policy page, a vendor's policy page, a maintainer's blog post or news coverage. The OSV schema was read as its published specification site, not as the schema file. Where a value seems to exist only in code (for example, a tool's default), it is recorded as an open question.

**Search budget.** The shared web-search budget ran out after about 30 searches in this strand. The highest priorities (CNA status and governance, advisory formats, SBOM guidance, bounties, cadence) were searched first. Section 8 and parts of Sections 2, 5 and 6 rest on primary pages read directly and on recalled facts, which are graded Medium or Low.

**Implications:** Izcal should become a **supplier CNA under the ENISA Root** before its first public binary. ENISA's scope fits an EU-facing open-source vendor and lines up with the CRA. Until then, GitHub's CNA is the fallback. The CNA rules already fit Izcal's design: publish the record within 72 hours, keep a public advisory page with stable URLs, and file engine bugs per implementation of a shared specification. The two-contact rule is a small, concrete reason to meet SEC-D4 (a second person) early. To avoid depending on one registry, every advisory should carry an Izcal-native stable ID and list the CVE ID, the EUVD ID and the GCVE ID as aliases (OSV `aliases`, CSAF `ids`). Izcal should also consider registering as a GNA, which costs little once it is a CNA.

**Implications:** Izcal should publish every advisory as **CSAF 2.0** at trusted-provider level (requirements 1–20, ROLIE optional), with a VEX document per release and the CSAF field in security.txt. CSAF 2.0 is the OASIS and ISO standard, and the BSI's CRA-aligned guidance points to it. Izcal should also export **OSV** for the Rust and OSV ecosystem, and move to CSAF 2.1 once it is a Standard. Signing should use **OpenPGP**, because CSAF requires it, alongside Izcal's TUF and attestation keys. This is a key-custody item for SEC-D4. The disclosure policy should cite 29147 and 30111 and be checked against their new editions. For flaws in specifications, the W3C channel is the route to use.

**Implications:** Izcal's severity scale should be its **own four-level, browser-specific scale**, with Mozilla-style definitions tied to Izcal's process tiers: renderer-only memory corruption is high, a sandbox escape or a broker or IPC logic bypass is critical. The **exploited tier** that drives SEC-1's 72 hours† and the CRA Art. 14 clock should use one written test: reliable evidence of malicious exploitation in the wild, never a public proof of concept alone. That keeps the KEV criterion, the CRA definition and the SEC-1 trigger the same.

**Implications:** Izcal should meet the **BSI TR** rather than the CRA's bare minimum. It is the most concrete CRA-aligned rule, and full depth is cheap for Izcal: almost all its code is its own, it has few external crates (the RustCrypto pins and tools), and it uses OS interfaces. Each release should have a build-time **CycloneDX 1.6+ JSON** SBOM (SPDX 3.0.1 optional), generated from `Cargo.lock`. It should list every `hg-*` crate and every pinned crate with SHA-512 hashes, purl, licences and the security.txt URL. It should stop at the first external level (OS libraries and drivers, listed as identified components). It should be signed and attested with the provenance of Stage 1 §7.8. Vulnerability status goes in the CSAF VEX, never in the SBOM. Note that the BSI's contact fields want a project contact address in the SBOM, which needs a role address. Q-1 below asks which.
