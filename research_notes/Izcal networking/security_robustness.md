# Izcal networking: security and robustness

Compiled 19 October 2026. Primary sources were preferred: CERT/CC vulnerability notes, CVE and GitHub/RustSec advisories, maintainers' posts, Chromium source and documentation, the WHATWG Fetch standard, and papers.
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, a vendor claim without data, a technical secondary source, or prior knowledge not re-fetched this session; **Low** = secondary source only (press, aggregators).

**Method notes.**
- The web search budget (about 25 queries) was spent on questions 1, 2, 4, 5 and 6 first. Chromium's `sandbox/policy/features.cc`, `testing/variations/fieldtrial_testing_config.json` and `net/data/ssl/chrome_root_store/faq.md` were downloaded from HEAD on 19 October 2026 and read directly. The Fetch standard's bad-port table was extracted from the live spec.
- Items marked Medium "(prior knowledge)" were not re-fetched this session. They are well known but must be re-checked before they anchor a spec requirement.
- No implementation source code of any network stack was read beyond the Chromium feature flags (M-1 rule: specs, advisories and papers only).
- Context assumed throughout: Izcal's network service is one sandboxed **tier P** process holding every site's cookies, cache and sockets; it aborts on panic (CS-D1(a)); renderers are assumed compromised and reach it only through typed capability IPC. That makes two attack surfaces: **(A) the network** (hostile servers, middleboxes, on-path attackers) and **(B) the renderer IPC** (a compromised renderer sending crafted requests). A panic on either surface is a whole-browser network outage, not a tab crash.

| 1.14 | **Chrome's QUIC has had memory-safety bugs reachable from the network and from a compromised renderer**: CVE-2017-15398 (stack buffer overflow in QUIC) and CVE-2017-15407 (out-of-bounds write in QUIC), both found by Ned Williamson in October 2017; CVE-2024-3837 (use-after-free in QUIC, "a remote attacker who had compromised the renderer process", fixed in Chrome 124); CVE-2026-13799 (use-after-free in QUIC "via malicious network traffic", High, fixed in Chrome 150) | 4 named | [SecurityWeek, Chrome 62](https://www.securityweek.com/chrome-62-update-patches-serious-vulnerabilities/amp/); [SUSE CVE-2026-13799](https://www.suse.com/security/cve/CVE-2026-13799.html); [SentinelOne CVE-2024-3837](https://www.sentinelone.com/vulnerability-database/cve-2024-3837/) | 2017-10 – 2026 | Medium (secondary; NVD fetch failed) |

**Which matter for a client.** Server-side DoS (Rapid Reset, most of the Netflix set aimed at request processing) does not threaten a browser. What does: (a) anything where the **server controls a size or count the client must store** (response header blocks, CONTINUATION chains, HPACK/QPACK table references, CRYPTO and stream reassembly gaps, ACK ranges, connection IDs, PATH_CHALLENGEs, server-pushed streams); (b) anything that makes the client **queue control frames** in reply (PING, SETTINGS, PATH_CHALLENGE, NEW_CONNECTION_ID); (c) **arithmetic on peer-supplied numbers** (quiche's ACK overflow, quinn's varint unwrap). In a single shared network process, (c) is the worst: under abort-on-panic one hostile site takes down every site's networking.

**Implications:** Every one of the Rust QUIC panics (1.8, 1.9) is exactly the class CS-D1(a) makes fatal for Izcal: `unwrap()` on a peer varint, unchecked arithmetic on a peer packet number, a state-machine misuse. Izcal's QUIC and HTTP/2/3 code must use explicit checked arithmetic on every peer-supplied integer (enabling `overflow-checks` does not help, because it turns an overflow into a panic and therefore an abort), a lint ban on `unwrap`/`expect`/indexing in tier P parsers, and a per-connection **budget** for every peer-driven queue and buffer, enforced at insertion time.

The hyper episode (2.3) is evidence for Izcal's own-code choice: the cost was the foreign-language boundary.

Model learning (3.2) is a cheap periodic check of the connection state machine against a spec-derived model.

**Implications:** Izcal should do what Chrome concluded (4.1, 4.2): **one cross-platform verifier** in Izcal's own code on top of rustls-webpki (path building with a signature budget, 4.8), **not** the platform verifier as the policy engine (4.9). It must enforce CT (2 SCTs, per Chrome/Apple/Mozilla policy) and ship pushed revocation (CRLite-style, possibly via upki) because OCSP is gone (4.5). All of this data (root store, CT log list, CRLite filter) needs a signed, versioned update channel with a fail-closed staleness rule.

**Implications:** rustls is a sound choice for the protocol and record layer, and its defaults (aws-lc-rs, PQ hybrid preferred, no legacy versions) already match a browser. Izcal must still write the **verifier policy** (Section 4), use the `quic` module from Izcal's own QUIC, and decide the provider: aws-lc-rs brings a C/assembly build (cmake) and FIPS; ring is smaller. Both are third-party unsafe code inside the tier P process, so a provider bug is Izcal's bug. Wire rustls's own fallible paths so a rustls error closes one connection, never aborts the process.

## 8. Robustness limits a client should impose

| # | Finding | Numbers | Source | Date | Conf. |
|---|---|---|---|---|---|
| 8.1 | **Header limits in practice**: Chrome caps HTTP/1.1 response headers at 256 KB; nginx and most servers default to 8–16 KB per request header line; HTTP/2 lets each side advertise `SETTINGS_MAX_HEADER_LIST_SIZE` (advisory, so the receiver must enforce its own limit) | 256 KB | Chromium `net/http` constants; RFC 9113 §6.5.2 | — | Medium (prior knowledge) |
| 8.2 | **Decompression bombs**: gzip/deflate peak ratio ~1,032:1; brotli can exceed 1,000,000:1 on degenerate input; zstd's ratio is bounded by the window. **RFC 9659** (2024) limits the zstd window for HTTP content coding to **8 MB**, so a decoder can refuse larger windows | ratio up to 10^6 | RFC 9659; RFC 7932 | 2024-09 | Medium (prior knowledge) |
| 8.3 | **Captive portals**: RFC 8908 (Captive Portal API) and RFC 8910 (DHCP/RA option 114) let the network announce a portal; browsers otherwise probe a known HTTP URL and treat interception as a portal. **Implications:** Every limit below must be a **named constant in one module**, enforced at allocation time through Izcal's fallible, capped allocator, and exercised by a test that sends exactly limit and limit+1. A limit breach is a stream or connection error with a typed reason, never a panic.

## Security requirements and limits for Izcal (proposed)

Numbers are starting points chosen to be at or above what real sites need and well below what an attacker needs; each must be validated against a crawl before the spec freezes them.

| # | Requirement | Limit / rule | Rationale |
|---|---|---|---|
| R1 | **No panic reachable from network or IPC input** in the network process: deny `unwrap`, `expect`, `panic!`, slice indexing, unchecked `as` casts and unchecked arithmetic on peer-supplied values in tier P parsers (Clippy deny list + CI) | 0 panics | 1.8, 1.9 were all this class; CS-D1(a) makes each a browser-wide outage |
| R2 | Per-connection **budget object** charged on every peer-driven allocation and queued control frame; exceeding it closes that connection (or stream) with a typed error | budget per connection, global cap per site and process | 1.1, 1.5, 1.10, 1.11 |
| R3 | HTTP/1.1 response header block | ≤ 256 KB total, ≤ 100 KB per line, ≤ 1,000 fields | 8.1 (Chrome parity) |
| R4 | HTTP/2 and HTTP/3 **decoded** header list, counted during HPACK/QPACK decoding | ≤ 256 KB; advertise `SETTINGS_MAX_HEADER_LIST_SIZE` accordingly | 1.6 HPACK bomb |
| R5 | HTTP/2 CONTINUATION | ≤ 16 CONTINUATION frames per header block and the R4 byte cap; empty CONTINUATION counts as a frame | 1.1–1.3 |
| R6 | HTTP/2 control-frame floods | PING, SETTINGS, empty DATA/HEADERS, WINDOW_UPDATE(0), RST_STREAM received counted per window; e.g. > 100/s or > 1,000 unanswered queued replies → GOAWAY(ENHANCE_YOUR_CALM) | 1.5 |
| R7 | **Disable HTTP/2 server push** (`SETTINGS_ENABLE_PUSH = 0`); treat PUSH_PROMISE as a protocol error | 0 pushed streams | 1.7; removes the only server-initiated stream source |
| R8 | HPACK/QPACK dynamic table | HPACK 4,096 B (default) ; QPACK `SETTINGS_QPACK_MAX_TABLE_CAPACITY` ≤ 64 KB; `SETTINGS_QPACK_BLOCKED_STREAMS` ≤ 16; encoder-stream buffered bytes ≤ table capacity | 1.13 |
| R9 | QUIC CRYPTO out-of-order buffer per epoch | ≤ 64 KB, then CRYPTO_BUFFER_EXCEEDED | 1.12 (RFC minimum 4,096 B) |
| R10 | QUIC stream reassembly | per-stream receive window caps buffered bytes; ≤ 64 non-contiguous gaps per stream | 1.12 fragmentation |
| R11 | QUIC ACK tracking | ≤ 256 ACK ranges stored per packet-number space; ACK of an unsent packet number = PROTOCOL_VIOLATION; all packet-number and cwnd arithmetic checked | 1.9, 1.10 |

| R16 | **One URL parser, one header-field parser, one cookie parser** for the whole browser; strict framing (reject CL+TE, duplicate differing CL, obs-fold, bare CR/LF in fields, NUL); a framing anomaly on HTTP/1.1 marks the connection non-reusable | strict | 2.3–2.7 |
| R17 | Cross-origin redirect hygiene | re-run all Fetch checks per hop; drop `Authorization`, cookies per mode; ≤ 20 redirects | 2.2, 7 |
