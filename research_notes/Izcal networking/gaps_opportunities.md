# Izcal networking: gaps, the invisible, and what no browser does

Compiled 19 October 2026. Primary sources were preferred (specifications and their source text, IETF Datatracker, papers read as full PDFs, protocol definition files, maintainers' documentation).
Confidence: **High** = primary source read and the claim checked in its text; **Medium** = primary abstract or snippet, or a vendor claim without data; **Low** = secondary source only.

**Scope.** This strand covers phase 3 of the first-principles-spec method for the network stack: what developers and users cannot see or do with browser networking today, which formats and tools exist and where they stop, how record/replay and network shaping fall short, what users struggle with, which new platform capabilities are open for a fresh stack, and what an agent principal needs from the network layer. It is research only (M-1): ideas and evidence, never code or templates.

**Relation to earlier notes.** The DevTools strand already covers the network-below-HTTP gaps, HAR and qlog basics, the Okta HAR breach, proxies and SSLKEYLOGFILE. This note cites those rows and does not repeat them: [invisible_gaps.md](../Izcal%20DevTools%20spec/invisible_gaps.md) (**[IG n]**), [protocols_standards.md](../Izcal%20DevTools%20spec/protocols_standards.md) (**[PS n]**), [history_postmortems.md](../Izcal%20DevTools%20spec/history_postmortems.md) (**[HP n]**), [agents_integrations.md](../Izcal%20DevTools%20spec/agents_integrations.md) (**[AI n]**) and the [fact-check](../Izcal%20DevTools%20spec/factcheck.md). New here: request-level vs packet-level shaping, record/replay fidelity numbers, deterministic protocol simulation, users' network failures, new platform features, and the exact shape of BiDi and CDP interception.

**Izcal constraints that apply.** HGBA-2 P1 (security and privacy) and M-1; **HGBA-2 is frozen at 2.3.0 (19 October 2026), and M-1 now excludes every library that does browser-engine work, so Izcal builds its own network protocol stack**; the Section 4.7 use of neqo is superseded ([HGBA-2 status line](../../reports/HGBA%202%20browser%20architecture%20spec.md)). The DevTools spec's "qlog from neqo" (its M5 row) therefore becomes "qlog from Izcal's own QUIC". I-1 extension (b): the network service partitions **all** its state (HTTP cache, connection pools, DNS cache, Alt-Svc, TLS tickets, HSTS, revocation caches, reporting endpoints, SW registrations) by (top-level site, container). HGBA-3 **B1** (substrate: `NetTransport` is held only by the network service; simulation mode replays a **recorded corpus archive**, one archive per page load with every request, response, timing and the seed, own format plus a **WARC importer**; faults injected by the scheduler: resets, slow and reordered bytes), **B2** (typed IPC with a simulation transport), **B9** (agent principal), **B10** (AI off by default); D-S4 (usage telemetry opt-in); Stage 1 design 3.4 (production recording off by default, per tab, user-initiated). DevTools spec decisions DT-D5 (protocol-level network views; driving the network), DT-10 (redacted exports), DT-18 and DT-21.

## 1. What developers and users cannot see today

The DevTools note established that DNS, TLS, QUIC, reuse and coalescing decisions are logged by every browser but kept in separate tools ([IG 2.1–2.12], [PS 11.1–11.4]). This section adds the gaps that sit **in the platform's own contracts**, not only in the tools.

**Implications:** the web platform must stay opaque to the **page** (1.1–1.2 are security properties, not bugs), but nothing stops the browser from telling the **user and the user's own tools** the exact reason. Izcal's network service owns the decision at every layer, so every failed fetch can carry a typed, internal **failure reason** (layer, step, spec anchor) that crosses IPC to DevTools and the shell but never to the renderer. HAR is the wrong carrier for it; the reason belongs in IIP events and in qlog-style logs, with HAR as a lossy export.

**Implications:** every external record/replay tool fights the same three problems: the page is non-deterministic (3.3, 3.6), TLS and QUIC must be defeated to see the bytes (3.5, 3.7), and the replay network is a guess at the original's timing (3.2). Izcal removes all three at once: the substrate makes the page deterministic (clock, entropy, scheduler), the recording is taken **inside** the network service above TLS and QUIC (so nothing is intercepted and no root is installed), and the transport below can be replayed as recorded or re-simulated under a seeded network model. Two separable recordings matter: the **content corpus** (what the servers said, for Stage 1's archive) and the **transport trace** (when packets moved). Replaying content with a fresh simulated transport is how "what if this page loaded on a lossy 3G link" becomes an exact, repeatable experiment. The corpus matcher still needs a policy for requests the page generates differently, but under the substrate that happens only when the page's inputs differ, which the simulator can report instead of guessing.

**Implications:** Izcal can offer the first **in-browser, packet- and protocol-level shaper** that is also **per tab, per origin and per container**: because the network service owns both the transport and the partition key, a link model (bandwidth, delay, loss, reordering, queue) can apply to one (site, container) without touching the host, and protocol faults (block UDP, fail DNS, drop the ECH config, reset stream N) can be injected at the exact layer. In simulation mode the same faults are seeded and replayable (B1). The constraint: in normal browsing these controls are a DevTools write capability (DT-21) for the inspected origin only, always labelled in the UI; a page must never be able to detect that it is being shaped beyond what real networks already reveal.

**Implications:** Izcal's network service sees every outgoing request with its partition key, container, route, cookies attached, referrer sent, IP used and the initiator chain, so it can keep a **"who received what" ledger** answering "which parties got data while I was on this site, and what kind" (cookie names not values, referrer origin, client IP class, request count, partitioned or not). It should report **flows and mechanisms**, not scores (5.2), and say "this request carried a cookie partitioned to X" rather than "tracker blocked".

| 6.4 | **DoH versus enterprise and split-horizon DNS:** Firefox disables default DoH when the canary domain `use-application-dns.net` does not resolve, and under enterprise policy or detected parental controls. **Implications:** most of these failures are diagnosable by the network service and invisible to the user. Izcal can give users a **plain-language "why this did not load" page** built from the typed failure reason (Section 1): which layer failed, on which route (container route, DoH resolver, proxy), and what the user can do, with a captive-portal state machine that consumes RFC 8908/8910 where offered. Warnings should follow 6.1–6.2's evidence (opinionated, error-specific design measurably changes behaviour; comprehension is hard), and Izcal should measure its own warnings only through opt-in telemetry (D-S4), which will undercount. Per-container routes (WireGuard, SOCKS, Arti) make route-aware explanations necessary, not optional: "this container sends traffic through Tor; this site blocks Tor exits" is a diagnosis no browser gives today.

**Implications:** a new stack can lead where the feature is **transport-shaped and specified** (WebTransport, compression dictionaries, Early Hints, fetchLater, OHTTP), because those are cheap for an owned HTTP/3 stack and need no web-exposed tracking surface. Speculation Rules is the clearest case of a network behaviour that is invisible today: Izcal should show each speculation, its rule, its partition and its fate. Single-vendor features with negative positions (DBSC, Topics) are not leads.

**Implications:** an agent principal (B9) needs interception that is **scoped by origin set and by container** (8.1 shows BiDi cannot even scope by user context), **typed by intent** (observe, mock, block, modify), **visible to the user** (a badge on affected tabs, every substituted response labelled in DevTools as DT-21 already requires), and **audited** (who intercepted which request in which partition, with the rule that matched). Agents should get network **summaries and decisions** by default, with bodies, cookies and credentials as sensitive classes needing a grant (DevTools spec Section 5 item 5). Izcal's BiDi adapter can implement `addIntercept` faithfully while the IIP underneath records the principal, scope and audit trail that BiDi lacks; the gaps in 8.1 and 1.6 (user-context scope, service-worker fields) are worth raising in the Browser Testing and Tools WG.
