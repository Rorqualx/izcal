| 1.28 | **H2/H3 coalescing as a linker** | One connection is reused across origins that share a certificate and IP. | 1.29 | **Cache probing despite partitioning** | Partitioning is "ineffective for requests from subdomains and window navigations". **Implications:** The engines agree on top-level site as the minimum key. They differ on the second key: Chrome triple-keys the cache, while Firefox and WebKit double-key everything. Whether shipped Chrome keys sockets and DNS more coarsely than its cache (a cross-site bit instead of the frame site) is not in published prose and is observed black-box at NW-M2 (1.9). A coarser connection key is still a design option on its own merits: it trades iframe-to-iframe probing under one top-level site for fewer connections. Every engine left something global: HSTS (Chrome), proxy and PAC DNS, the certificate verifier, and above all the **global socket cap**. Izcal's I-1(b) is stricter than any shipped engine, and its measured cost is small: Chrome +3.6% cache misses, Firefox ≤1.32% page load. Izcal should key the **HTTP cache by (top-level site, container, frame site or cross-site bit, cross-site-navigation bit)**, key **connection-level state by (top-level site, container, cross-site bit, route)**, and design the socket budget as per-partition and randomized. A global hard cap is itself a cross-partition channel.

**Implications:** Izcal's security scope already requires ORB before delivery. Because ORB is not in Fetch, Izcal must anchor to the `annevk/orb` draft at a pinned commit (M-1 part 2) and treat it as a spec risk. A blocked response should be a **network error**, not an empty body: that matches the fail-closed design and CS-ER-9 ("every network failure is the same Fetch network error"). Error events, timing and pool state are the leak channels. The network service should therefore make the **failure shape and timing of a blocked response identical to a generic network error**, as far as cost allows.

**Implications:** The evidence shows that a new engine is blocked by bot management. It does not isolate the network fingerprint as the cause (Ladybird's fix was mostly JS-visible compatibility and a vendor-side change). Izcal should still aim for an **honest but common-shape** wire profile:

- a ClientHello with GREASE and randomized extension order;
- the cipher, group and extension set of a mainstream browser, including X25519MLKEM768 (HGBA-2 4.7);
- H2 SETTINGS and frame order within the common browser range;
- QUIC transport parameters that are not idiosyncratic.

Izcal must not claim to *be* Chrome in the TLS layer. It should still avoid gratuitous uniqueness, because uniqueness is a cross-site identifier as well as a blocking risk. The owner should also plan **early outreach to the major bot-management vendors** (Cloudflare, Akamai, Fastly, Imperva). Ladybird's case shows the vendor side is part of the fix. Per-container routes (Tor, VPN) get these challenges much more often, whatever the fingerprint.

- ship DoH with a published resolver policy at least as strict as Mozilla's;
- honor the canary and enterprise signals;
- use OHTTP for **Izcal's own service traffic** (update checks, Safe Browsing-class lookups, CRLite fetches) so Izcal's servers never see user IPs.

ECH needs private DNS to be worth anything.

## Open privacy risks

1. **The global socket cap leak** (1.24) is unsolved in every engine. A per-partition budget plus randomized global capacity is untested at Izcal's scale and may cost throughput under many partitions.
2. **Upstream DNS caches** cannot be partitioned (Fetch §2.5). A DoH resolver sees every partition's queries from one client unless OHTTP/ODoH or a per-container route is used.
3. **Network fingerprint uniqueness.** A new TLS, H2 or QUIC stack is identifiable by JA4 and Akamai-style fingerprints. That is both a tracking vector and a bot-blocking risk (4.4). There is no evidence on how much the network shape, as opposed to JS behavior, drives blocking.
4. **ORB is not standardized in Fetch** (2.3). Izcal must pin a draft. Divergence from other engines is an XS-Leak and compatibility risk.
5. **The second key is unsettled** (Fetch issue #1035). Chrome's published design uses the frame site (F) for the cache and for network state (1.6, 1.7; what shipped Chrome uses for connections is observed at NW-M2, 1.9); Firefox and WebKit use neither. Izcal's choice affects cache hit rate (Chrome measured +3.6% misses for the triple key) and must be measured on Izcal's corpus.
6. **Clear-Site-Data semantics under partitioning** are unspecified (7.4).
7. **The cost of Storage Access and heuristic grants.** Each grant re-links partitions. Firefox's 30-day automatic grants are a privacy-for-compatibility trade-off that needs an owner decision.
8. **Route changes mid-session.** If R is not in every key, a container whose route changes reuses state learned on the old route. That would link the user's real IP to the proxied identity.
9. **Remaining cache-probing paths.** Subdomain and window-navigation probes, error-event probes and invalidation probes are only partly closed by the N bit (1.29).
10. **Certificate and revocation fetches** (OCSP, AIA) leak visited hosts to CAs and on the host network if they are not routed and partitioned. Pushed CRLite-style filters (Stage 1 §13.2) avoid most of these fetches. AIA chasing remains.
